# 1. Spring Transactional 事务传播与回滚

`@Transactional` 是 Spring 声明式事务注解。它通常通过 AOP 代理在方法调用前开启事务，在方法正常返回时提交事务，在出现满足规则的异常时回滚事务。

## 1. 基本执行流程

当外部调用一个被 `@Transactional` 代理的方法时，大致流程是：

```text
调用代理对象方法
  -> TransactionInterceptor 开启或加入事务
  -> 调用目标方法
  -> 方法正常返回: commit
  -> 方法抛出需要回滚的异常: rollback
```

事务真正是否生效，关键看调用是否经过 Spring 代理。

## 2. 方法内先调用普通方法再抛异常，会不会回滚

示例：

```java
@Service
public class OrderService {
    @Transactional
    public void createOrder() {
        saveOrder();       // 普通方法
        throw new RuntimeException("fail");
    }

    public void saveOrder() {
        // insert/update database
    }
}
```

如果 `createOrder()` 是从 Spring 容器外部通过代理对象调用的，那么会回滚。原因是：

1. 事务在进入 `createOrder()` 前已经开启。
2. `saveOrder()` 虽然没有注解，但它在同一个调用栈、同一个事务上下文里执行。
3. `createOrder()` 最后抛出未捕获的 `RuntimeException`，默认触发事务回滚。

所以答案不是看普通方法有没有注解，而是看外层事务方法有没有成功开启事务，以及异常是否满足回滚规则。

## 3. 什么情况不会回滚

常见不回滚场景：

1. **自调用导致事务未生效**：

```java
public void outer() {
    inner(); // this.inner()，没有经过代理
}

@Transactional
public void inner() {
    throw new RuntimeException();
}
```

如果 `outer()` 没有事务，且它直接调用同一个类里的 `inner()`，这次调用不会经过 Spring AOP 代理，`inner()` 上的 `@Transactional` 不生效。

2. **异常被吞掉**：

```java
@Transactional
public void createOrder() {
    try {
        saveOrder();
        throw new RuntimeException();
    } catch (Exception e) {
        log.warn("ignored", e);
    }
}
```

方法最终正常返回，事务拦截器看不到异常，默认会提交。除非手动设置回滚：

```java
TransactionAspectSupport.currentTransactionStatus().setRollbackOnly();
```

3. **抛出受检异常但未配置 rollbackFor**：

Spring 默认只对 `RuntimeException` 和 `Error` 回滚。对 checked exception，需要显式配置：

```java
@Transactional(rollbackFor = Exception.class)
```

4. **数据库操作不支持事务**：

例如 MySQL 使用 MyISAM 引擎，或者操作的是非事务资源，Spring 注解无法让底层具备事务能力。

5. **传播行为改变事务边界**：

如果内部方法使用 `REQUIRES_NEW`，它会开启新事务，和外层事务提交/回滚边界不同。外层回滚不一定回滚已经提交的内层新事务。

## 4. 常见传播行为

| 传播行为 | 含义 | 常见场景 |
| --- | --- | --- |
| `REQUIRED` | 有事务就加入，没有就新建 | 默认，最常用 |
| `REQUIRES_NEW` | 挂起当前事务，开启新事务 | 审计日志、独立流水 |
| `SUPPORTS` | 有事务就加入，没有就非事务执行 | 可事务可非事务查询 |
| `MANDATORY` | 必须已有事务，否则报错 | 强制由上游控制事务 |
| `NOT_SUPPORTED` | 挂起事务，非事务执行 | 不希望长事务包住慢操作 |
| `NESTED` | 嵌套事务，依赖保存点 | 局部回滚 |

## 5. 真实场景注意事项

1. 事务方法尽量放在 service 层，由外部通过 Spring Bean 调用。
2. 不要把远程 RPC、MQ 发送、文件上传等长耗时操作放在数据库事务里。
3. 事务里更新缓存要注意提交顺序，常见做法是事务提交后再删除缓存或发消息。
4. 批量操作要控制事务大小，避免长事务占用锁和 undo log。
5. 多数据源或跨服务事务不能只靠本地 `@Transactional`，要用 outbox、Saga、TCC 或最终一致方案。

## 6. 面试回答模板

如果一个方法加了 `@Transactional`，方法内部先调用普通方法再抛出 `RuntimeException`，只要这个事务方法是通过 Spring 代理对象从外部调用进来的，事务已经开启，普通方法里的数据库操作也在同一个事务里，最后异常未被捕获就会回滚。容易出错的是同类自调用、异常被 catch 吞掉、抛 checked exception 未配置 `rollbackFor`、底层数据库不支持事务，或者传播行为如 `REQUIRES_NEW` 改变了事务边界。
