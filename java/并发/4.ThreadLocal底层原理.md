# 4. ThreadLocal 底层原理

`ThreadLocal` 用来为每个线程保存一份独立变量副本。它解决的是线程封闭问题：同一个 `ThreadLocal` 变量在不同线程中看到的是不同的值，从而避免共享可变对象带来的竞争。

常见用途：

1. 保存请求上下文、traceId、用户身份等线程内上下文。
2. 保存线程内可复用对象，例如日期格式化器、缓冲区。
3. 在框架中把事务、连接、会话等绑定到当前线程。

## 1. 核心结构

`ThreadLocal` 的数据不存放在 `ThreadLocal` 对象里，而是存放在当前 `Thread` 对象的 `ThreadLocalMap` 中。

```text
Thread
  -> threadLocals: ThreadLocalMap
       -> Entry[]
            key   = WeakReference<ThreadLocal<?>>
            value = Object
```

也就是说，访问过程是：

```text
ThreadLocal.get()
-> 获取当前线程 Thread.currentThread()
-> 找到当前线程的 ThreadLocalMap
-> 用当前 ThreadLocal 对象作为 key 查找 Entry
-> 返回 Entry.value
```

每个线程都有自己的 `ThreadLocalMap`，所以不同线程之间不会读到对方的 value。

## 2. set/get/remove 流程

`set(value)`：

1. 获取当前线程。
2. 获取当前线程的 `ThreadLocalMap`，不存在则创建。
3. 用当前 `ThreadLocal` 的 hash 定位数组下标。
4. 找到相同 key 就覆盖 value；遇到 key 已被 GC 的脏 Entry 会做清理；否则线性探测找空位插入。

`get()`：

1. 获取当前线程的 `ThreadLocalMap`。
2. 根据当前 `ThreadLocal` 的 hash 找 Entry。
3. 命中则返回 value。
4. 未命中则调用 `initialValue()` 或 `withInitial()` 生成初始值并写入 map。

`remove()`：

1. 删除当前线程 map 中以当前 `ThreadLocal` 为 key 的 Entry。
2. 清理后 value 不再被线程强引用持有。
3. 在线程池场景中，用完必须调用 `remove()`。

## 3. ThreadLocalMap 为什么弱引用 key

`ThreadLocalMap.Entry` 的 key 是弱引用：

```java
static class Entry extends WeakReference<ThreadLocal<?>> {
    Object value;
}
```

原因是线程可能比业务对象活得更久，尤其是线程池线程。如果 key 使用强引用，业务代码即使不再持有 `ThreadLocal` 对象，它也会因为线程里的 map 引用而无法被回收。

但弱引用只能回收 key，不能自动回收 value。`Entry` 的 value 仍然是强引用：

```text
Thread -> ThreadLocalMap -> Entry -> value
```

如果线程长期存活，且没有调用 `remove()`，就可能出现 key 已经是 `null`，value 仍然挂在线程上的泄漏。`ThreadLocalMap` 会在后续 `get/set/remove` 时顺带清理这些脏 Entry，但不能保证及时清理。

## 4. 哈希和冲突处理

`ThreadLocal` 有自己的 `threadLocalHashCode`，每创建一个 `ThreadLocal` 会按固定增量递增。这个增量接近黄金分割比例，目的是让连续创建的 `ThreadLocal` 在 2 的幂长度数组中分布更均匀。

`ThreadLocalMap` 不是 `HashMap` 链表结构，它使用开放寻址和线性探测：

1. 下标计算：`index = hash & (len - 1)`。
2. 如果当前位置不是目标 key，就继续向后探测。
3. 删除或遇到 key 为 `null` 的 Entry 时，会触发局部清理和 rehash。

易错点是：线性探测依赖及时清理脏 Entry，否则探测路径会变长，既占内存也影响访问性能。

## 5. 线程池中的内存泄漏

线程池线程不会随请求结束而销毁，因此 `ThreadLocal` value 可能跨请求残留。

错误示例：

```java
private static final ThreadLocal<User> CURRENT_USER = new ThreadLocal<>();

void handle(Request request) {
    CURRENT_USER.set(request.user());
    doBusiness();
    // 忘记 remove，当前线程处理下一个请求时可能读到旧用户
}
```

推荐写法：

```java
void handle(Request request) {
    CURRENT_USER.set(request.user());
    try {
        doBusiness();
    } finally {
        CURRENT_USER.remove();
    }
}
```

这不仅防止内存泄漏，也防止请求上下文串号。

## 6. InheritableThreadLocal 和上下文传递

`InheritableThreadLocal` 可以让子线程创建时拷贝父线程的值，但它只在“创建线程”这一刻生效。在线程池里，工作线程早已创建，后续提交任务不会自动继承提交线程的上下文。

真实项目里如果要跨线程池传递 traceId、登录态或租户信息，可以考虑：

1. 显式把上下文作为方法参数传递。
2. 在线程池提交任务时包装 `Runnable/Callable`，捕获并恢复上下文。
3. 使用阿里 `TransmittableThreadLocal` 这类工具，但要理解其包装线程池和清理语义。
4. 在异步链路中优先依赖框架提供的上下文传播机制，例如 Reactor Context、OpenTelemetry Context。

## 7. 面试易错点

1. `ThreadLocal` 不是用来解决共享变量同步的，它是让每个线程不共享变量。
2. value 存在线程对象里，不存在 `ThreadLocal` 对象里。
3. key 是弱引用，value 是强引用，所以仍然需要 `remove()`。
4. 线程池里不清理会导致内存泄漏和上下文串号。
5. `InheritableThreadLocal` 不适合直接解决线程池上下文传递。
6. `ThreadLocal` 不等于请求上下文。协程、异步回调、响应式编程中，请求可能跨线程执行，普通 `ThreadLocal` 会失效。

## 8. 面试回答模板

`ThreadLocal` 的底层是每个 `Thread` 持有一个 `ThreadLocalMap`。`ThreadLocal` 对象本身作为 key，真正的值存在当前线程的 map 里，所以不同线程访问同一个 `ThreadLocal` 会得到各自线程的 value。`ThreadLocalMap.Entry` 的 key 是弱引用，value 是强引用；key 被 GC 后 value 仍可能被长生命周期线程持有，因此线程池场景必须在 `finally` 中 `remove()`。它适合保存线程内上下文，但异步和线程池上下文传播要额外处理。
