# Java 线程安全与常见工具

线程安全是指多个线程并发访问同一段代码或共享数据时，无论调度顺序如何，都能得到正确结果。Java 面试里回答线程安全，要围绕原子性、可见性、有序性，以及 Java 内存模型（JMM）来展开。

## 1. 线程安全问题从哪里来

常见问题：

1. **原子性不足**：`count++` 包含读、加、写三步，多线程下会丢更新。
2. **可见性不足**：一个线程修改变量，另一个线程可能迟迟看不到。
3. **有序性问题**：编译器和 CPU 可能重排序，导致另一个线程观察到不符合直觉的中间状态。
4. **复合操作不安全**：`if (!map.containsKey(k)) map.put(k, v)` 即使用并发容器，也不一定整体原子。
5. **对象逃逸**：构造未完成的对象被其他线程看见，可能读到未初始化状态。

## 2. synchronized

`synchronized` 是 Java 内置互斥机制，可以修饰方法或代码块：

```java
class Counter {
    private int count;

    public synchronized void inc() {
        count++;
    }

    public synchronized int get() {
        return count;
    }
}
```

作用：

1. 同一把锁保护的临界区互斥执行。
2. 进入锁和退出锁会建立 happens-before 关系，保证可见性。
3. 修饰实例方法锁的是当前对象；修饰静态方法锁的是 `Class` 对象。

易错点：锁粒度过大影响并发；锁对象如果暴露给外部，外部代码也能持有这把锁造成不可控阻塞。

## 3. volatile

`volatile` 保证可见性和一定的有序性，但不保证复合操作原子性。

适合场景：

```java
class Worker {
    private volatile boolean stopped = false;

    public void stop() {
        stopped = true;
    }

    public void run() {
        while (!stopped) {
            // do work
        }
    }
}
```

不适合：

```java
volatile int count = 0;
count++; // 仍然不是线程安全
```

`volatile` 常用于停止标志、配置发布、双重检查单例中的实例引用，但计数器要用锁或原子类。

## 4. 原子类和 CAS

`AtomicInteger`、`AtomicLong`、`AtomicReference` 等基于 CAS 实现无锁更新：

```java
import java.util.concurrent.atomic.AtomicInteger;

class Counter {
    private final AtomicInteger count = new AtomicInteger();

    public void inc() {
        count.incrementAndGet();
    }

    public int get() {
        return count.get();
    }
}
```

优点是低竞争时开销小；缺点是高竞争下 CAS 可能反复失败，自旋消耗 CPU。复杂状态更新还要考虑 ABA 问题，可以用版本号或 `AtomicStampedReference`。

## 5. Lock、读写锁和条件变量

`ReentrantLock` 比 `synchronized` 更灵活：

1. 可中断加锁。
2. 可限时 `tryLock`。
3. 可选择公平锁。
4. 可创建多个 `Condition` 等待队列。

读多写少场景可以用 `ReadWriteLock`：

```java
import java.util.concurrent.locks.ReentrantReadWriteLock;

class Cache {
    private final ReentrantReadWriteLock rw = new ReentrantReadWriteLock();
    private int value;

    public int read() {
        rw.readLock().lock();
        try {
            return value;
        } finally {
            rw.readLock().unlock();
        }
    }

    public void write(int v) {
        rw.writeLock().lock();
        try {
            value = v;
        } finally {
            rw.writeLock().unlock();
        }
    }
}
```

读写锁能提升读多写少吞吐，但写多或临界区很短时，锁管理成本可能抵消收益。

### 5.1 Java 中常见锁怎么分类

Java 里的“锁”可以从语言机制、并发包和实现思想三个层面回答：

1. **内置锁**：`synchronized` 基于对象 monitor，适合简单互斥。
2. **显式锁**：`ReentrantLock`、`ReentrantReadWriteLock`、`StampedLock`，提供可中断、超时、公平性、读写分离等能力。
3. **乐观并发工具**：`AtomicInteger`、`AtomicReference`、`LongAdder` 等基于 CAS，不先阻塞线程，冲突时重试。
4. **悲观锁**：进入临界区前先互斥，例如 `synchronized`、`ReentrantLock`、数据库 `SELECT ... FOR UPDATE`。
5. **读写锁**：读读并发、读写互斥、写写互斥，适合读多写少。
6. **公平锁 / 非公平锁**：公平锁按等待顺序获取，尾延迟更稳定；非公平锁允许插队，吞吐通常更好。
7. **可重入锁 / 不可重入锁**：同一线程能否重复获取同一把锁，`synchronized` 和 `ReentrantLock` 都是可重入锁。

面试回答时可以先说分类，再落到具体工具选择：简单临界区用 `synchronized`；需要超时、可中断、多条件队列用 `ReentrantLock`；读多写少用读写锁；计数和引用更新用原子类或 `LongAdder`。

### 5.2 `synchronized` 和 `ReentrantLock` 的区别

| 对比项 | `synchronized` | `ReentrantLock` |
| --- | --- | --- |
| 使用方式 | 语言关键字，进入/退出代码块自动加解锁 | API 显式 `lock()` / `unlock()` |
| 释放锁 | 退出同步块自动释放，异常也会释放 | 必须在 `finally` 中释放 |
| 可中断 | 等锁时通常不能响应中断 | `lockInterruptibly()` 支持中断 |
| 超时尝试 | 不支持 | `tryLock(timeout)` 支持 |
| 公平性 | 不能直接配置公平锁 | 构造函数可选择公平/非公平 |
| 条件队列 | 只有一个 wait set | 可以创建多个 `Condition` |
| 可重入 | 支持 | 支持 |

示例：

```java
ReentrantLock lock = new ReentrantLock();

lock.lock();
try {
    // 临界区
} finally {
    lock.unlock();
}
```

如果用 `tryLock()`，要特别注意只有成功拿到锁后才能 `unlock()`：

```java
ReentrantLock lock = new ReentrantLock();
boolean locked = false;

try {
    locked = lock.tryLock();
    if (!locked) {
        return;
    }

    // 临界区
} finally {
    if (locked) {
        lock.unlock();
    }
}
```

如果代码在 `tryLock()` 返回 `false` 或加锁前抛异常后仍然执行 `unlock()`，会抛出 `IllegalMonitorStateException`。因此面试里看锁代码时，要先判断锁是否一定获取成功，再看 `finally` 是否无条件释放。

选择建议：

1. 普通互斥优先用 `synchronized`，代码短，释放语义更安全，JVM 也有偏向锁、轻量级锁、自适应自旋等优化。
2. 需要超时获取锁、可中断等待、多个条件队列或公平锁时，用 `ReentrantLock`。
3. 使用 `ReentrantLock` 最常见错误是忘记在 `finally` 里 `unlock()`，导致永久阻塞。
4. 使用 `tryLock()` 时不要无条件 `unlock()`，必须用布尔标记或分支保证当前线程确实持有锁。
5. 不要为了“更高级”默认使用 `ReentrantLock`，复杂能力不用时只会增加代码风险。

### 5.3 `synchronized` 和 `ReentrantLock` 属于什么锁

如果面试官问“属于什么锁”，可以从多个维度回答，而不是只说一个名字。

`synchronized`：

1. **悲观锁**：进入临界区前先互斥，假设会有并发冲突。
2. **互斥锁 / 独占锁**：同一时刻只有一个线程持有对象 monitor。
3. **可重入锁**：同一线程可以重复进入同一把 monitor，退出次数和进入次数匹配后才释放。
4. **非公平锁倾向**：不能通过 API 配置公平性，调度顺序由 JVM 和操作系统决定。
5. **内置锁**：语义由 Java 语言和 JVM 保证，进入/退出同步块自动加锁解锁。

`ReentrantLock`：

1. **悲观锁**：同样通过互斥保护临界区。
2. **互斥锁 / 独占锁**：普通 `ReentrantLock` 是独占模式。
3. **可重入锁**：同一线程重复 `lock()` 会增加持有计数，需要对应次数 `unlock()`。
4. **可公平也可非公平**：`new ReentrantLock(true)` 是公平锁，默认构造是非公平锁。
5. **AQS 显式锁**：底层基于 `AbstractQueuedSynchronizer` 维护 state 和等待队列。

面试回答可以说：`synchronized` 是 JVM 内置的可重入互斥锁，属于悲观锁和独占锁；`ReentrantLock` 是 JUC 提供的显式可重入互斥锁，底层基于 AQS，可以选择公平或非公平，并支持可中断、超时和多个 Condition。

### 5.4 公平锁和非公平锁怎么选

公平锁按等待队列顺序获取锁，先等待的线程更有机会先拿到锁；非公平锁允许新来的线程在锁刚释放时直接竞争，可能插队。

| 类型 | 优点 | 缺点 | 适用场景 |
| --- | --- | --- | --- |
| 公平锁 | 等待时间更可预期，降低饥饿风险 | 吞吐通常更低，线程切换更多 | 任务耗时差异大、强 SLA、需要控制尾延迟或避免长期饥饿 |
| 非公平锁 | 吞吐更高，减少频繁唤醒和上下文切换 | 个别线程可能等待更久 | 普通 Web/RPC 服务、短临界区、高吞吐优先场景 |

默认情况下更常用非公平锁，因为大多数后端服务更关注整体吞吐和平均延迟。只有在明确存在饥饿、排队公平性要求或尾延迟治理需求时，才优先考虑公平锁。

易错点：

1. 公平锁不等于绝对按业务请求顺序执行，它只约束锁竞争队列。
2. 非公平锁不等于一定会饥饿，只是允许插队，吞吐通常更好。
3. 公平性是锁层面的策略，不能替代接口限流、队列调度和业务优先级设计。
4. `synchronized` 不能像 `ReentrantLock` 一样通过构造参数指定公平锁。

## 6. 并发容器

常见并发工具：

| 工具 | 适合场景 | 注意事项 |
| --- | --- | --- |
| `ConcurrentHashMap` | 高并发 key-value 读写 | 复合逻辑用 `compute/putIfAbsent` 等原子方法 |
| `CopyOnWriteArrayList` | 读多写极少的监听器列表 | 写入会复制数组，不适合频繁写 |
| `BlockingQueue` | 生产者消费者 | 注意队列容量和背压 |
| `ConcurrentLinkedQueue` | 无锁队列 | 只提供队列线程安全，不保证业务事务 |
| `ThreadLocal` | 线程私有上下文 | 线程池中要及时 `remove()` 防止泄漏 |

示例：

```java
map.compute(key, (k, oldValue) -> oldValue == null ? 1 : oldValue + 1);
```

这比 `get` 后再 `put` 更安全，因为更新过程由 `ConcurrentHashMap` 保证原子。

## 7. 线程安全单例

推荐写法之一是静态内部类：

```java
class Singleton {
    private Singleton() {}

    private static class Holder {
        private static final Singleton INSTANCE = new Singleton();
    }

    public static Singleton getInstance() {
        return Holder.INSTANCE;
    }
}
```

它利用类加载的线程安全保证懒加载。双重检查锁也可以，但实例字段必须是 `volatile`，否则可能因为重排序让其他线程看到半初始化对象。

### 7.1 不使用 synchronized 和 Lock 的单例

如果题目明确不能使用 `synchronized` 和 `Lock`，优先回答静态内部类或枚举单例，它们依赖 JVM 类初始化的线程安全保证。

静态内部类写法：

```java
public final class Singleton {
    private Singleton() {}

    private static class Holder {
        private static final Singleton INSTANCE = new Singleton();
    }

    public static Singleton getInstance() {
        return Holder.INSTANCE;
    }
}
```

特点：

1. `Singleton` 类加载时不会立即创建实例。
2. 第一次调用 `getInstance()` 时触发 `Holder` 初始化。
3. JVM 保证类初始化过程同一时刻只会被一个线程执行，其他线程会等待初始化完成。
4. 不需要显式 `synchronized`、`Lock` 或 CAS。

枚举写法更简单，也能防反射和反序列化破坏：

```java
public enum SingletonEnum {
    INSTANCE;

    public void doSomething() {
        // business logic
    }
}
```

面试里可以补充：双重检查单例虽然常见，但它内部仍然用 `synchronized`；如果禁用锁，静态内部类和 enum 是更稳的答案。需要懒加载且类可扩展控制时用静态内部类；需要最强防反射、防序列化破坏时用 enum。

## 8. 真实场景

1. **计数器**：低竞争用 `AtomicLong`，高并发统计用 `LongAdder`。
2. **本地缓存**：用 `ConcurrentHashMap`，加载过程用 `computeIfAbsent` 控制并发。
3. **任务队列**：用 `BlockingQueue` 做生产消费和背压。
4. **配置热更新**：用不可变配置对象 + `volatile` 引用整体替换。
5. **读多写少监听器**：用 `CopyOnWriteArrayList`，避免遍历时加锁。

## 8.1 加锁影响性能怎么办

加锁影响性能时，不要只说“换成 CAS”。要先判断瓶颈来自哪里：锁竞争、临界区太大、锁持有时间太长、阻塞唤醒频繁、读多写少没区分，还是共享状态设计不合理。

常见优化方向：

1. **缩小锁粒度**：只锁真正共享的数据，不把 I/O、RPC、数据库访问放进锁内。
2. **减少锁持有时间**：锁内只修改状态，耗时计算和回调放到锁外。
3. **拆分锁/分段锁**：按 key、bucket、用户、订单分片，降低单锁热点。
4. **读写分离**：读多写少用 `ReadWriteLock` 或 `StampedLock`，让读读并发。
5. **乐观并发**：低冲突计数、状态更新用 CAS、原子类；高冲突计数用 `LongAdder`。
6. **非公平锁**：公平锁减少饥饿但吞吐较低；默认非公平锁通常吞吐更好。
7. **不可变对象**：配置、规则、快照用不可变对象整体替换，读路径无锁。
8. **线程封闭**：把状态限制在单线程或单 event loop 内，跨线程用队列传消息。
9. **批量化**：多次小更新合并成批量更新，减少加锁次数。
10. **并发容器**：优先用 `ConcurrentHashMap`、`BlockingQueue` 等经过验证的工具。

示例：配置热更新可以用不可变对象 + `volatile` 引用：

```java
final class Config {
    final int timeoutMs;
    final Set<String> allowList;

    Config(int timeoutMs, Set<String> allowList) {
        this.timeoutMs = timeoutMs;
        this.allowList = Set.copyOf(allowList);
    }
}

class ConfigCenter {
    private volatile Config config = new Config(1000, Set.of());

    Config get() {
        return config; // 读无锁
    }

    void update(Config newConfig) {
        config = newConfig; // 整体发布
    }
}
```

什么时候不该优化：

1. 临界区很短、竞争不高，普通 `synchronized` 足够。
2. CAS 高竞争反复失败，可能比锁更浪费 CPU。
3. 读写锁在写多或读临界区很短时收益不明显。
4. 分段锁会增加实现复杂度，要确认热点真的存在。

面试回答模板：如果锁影响性能，我会先用 JFR、async-profiler、线程 dump 或监控确认锁竞争，而不是盲目换锁。优化上先缩小锁粒度和锁内耗时，再按场景选择分段锁、读写锁、不可变快照、CAS/LongAdder、并发容器或消息队列。公平锁换非公平锁可以提高吞吐但可能带来饥饿；CAS 适合低冲突，读写锁适合读多写少；核心原则是减少共享可变状态。

## 9. 面试回答模板

Java 线程安全主要解决原子性、可见性和有序性。简单互斥可以用 `synchronized`，它既保证互斥又通过 monitor 建立 happens-before；只需要可见性时可用 `volatile`，但 `i++` 仍不原子；计数和引用更新可以用原子类和 CAS；复杂等待和可中断锁用 `ReentrantLock/Condition`；读多写少可以用读写锁；集合优先使用 `ConcurrentHashMap`、`BlockingQueue` 等并发容器。工程上还要减少共享状态，使用不可变对象、线程封闭、消息队列和合理的锁粒度。
