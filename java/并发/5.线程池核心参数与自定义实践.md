# 5. 线程池核心参数与自定义实践

## 1. 问题背景

在高并发 Java 服务中，线程池是承载异步任务、IO 调用、批处理、定时任务等核心组件。线程是昂贵的系统资源，频繁创建销毁会带来巨大的开销，而无限制创建线程则可能耗尽 CPU、内存和文件描述符。`ThreadPoolExecutor` 提供了对线程池的精细化控制能力，但其七大核心参数若理解或配置不当，会引发任务堆积、内存溢出、响应延迟、雪崩等严重问题。

JDK 自带的 `Executors` 工具类虽然使用便捷，但其默认配置在生产环境中潜藏巨大风险，已被《阿里巴巴 Java 开发手册》明确禁止使用。

**假设条件：**

- 服务端为 Java 8+ 应用，使用 `java.util.concurrent` 包下的 `ThreadPoolExecutor`；
- 业务场景为高并发 Web 服务（如外卖、电商、社交），既有 CPU 密集型任务也有 IO 密集型任务；
- 单实例并发请求量峰值在数千至上万 QPS；
- 服务运行环境为容器化部署（Docker / K8s），内存 4–16 GB。

## 2. 问题现象

不当使用线程池或直接使用 `Executors` 可能出现以下现象：

1. **OOM**：日志出现 `java.lang.OutOfMemoryError: unable to create new native thread` 或 `Java heap space`；
2. **任务无响应**：提交的 Runnable / Callable 长时间不被执行，业务超时；
3. **任务被静默丢弃**：未捕获 `RejectedExecutionException`，任务直接丢失；
4. **接口延迟飙升**：线程数膨胀导致 CPU 上下文切换开销大，P99 延迟从 50ms 升至秒级；
5. **服务雪崩**：一个线程池阻塞导致整个服务不可用，进一步蔓延到上下游；
6. **难以排查**：线程命名默认为 `pool-1-thread-1`，线程栈难以定位归属业务。

## 3. 影响范围

| 影响维度 | 具体表现 |
|---------|---------|
| 用户体验 | 接口超时、下单失败、页面卡顿 |
| 业务指标 | 高峰期成功率下跌、转化率下降 |
| 系统稳定性 | 单服务 OOM / 雪崩，蔓延整个调用链 |
| 排障效率 | 线程命名混乱、监控缺失，故障定位耗时长 |
| 资源利用率 | 线程过多导致 CPU 空转，过少导致 IO 等待 |

## 4. 原因分析

### 4.1 ThreadPoolExecutor 七大核心参数

```java
public ThreadPoolExecutor(
    int corePoolSize,        // 核心线程数
    int maximumPoolSize,     // 最大线程数
    long keepAliveTime,      // 非核心线程空闲存活时间
    TimeUnit unit,           // 存活时间单位
    BlockingQueue<Runnable> workQueue,       // 任务等待队列
    ThreadFactory threadFactory,             // 线程工厂
    RejectedExecutionHandler handler         // 拒绝策略
)
```

**逐项解析：**

| 参数 | 作用 | 配置要点 |
|------|------|---------|
| `corePoolSize` | 核心线程数，即使空闲也不回收 | CPU 密集型：N_cpu；IO 密集型：2×N_cpu 或更高 |
| `maximumPoolSize` | 线程池允许的最大线程数 | 需结合队列容量和系统资源上限设置，不宜过大 |
| `keepAliveTime` | 非核心线程空闲超过此时间被回收 | 一般 60s，根据流量波动调整 |
| `unit` | keepAliveTime 的时间单位 | TimeUnit.SECONDS / MINUTES |
| `workQueue` | 存放等待执行任务的阻塞队列 | 必须有界！常用有界队列，容量根据业务测算 |
| `threadFactory` | 创建线程的工厂 | 必须自定义：命名线程、设置 daemon、UncaughtExceptionHandler |
| `handler` | 队列满且线程达上限时的拒绝策略 | 根据业务选择：记录日志 + 降级 / 调用者执行 / 丢弃最老 |

### 4.2 任务提交执行流程

```text
提交任务
  ↓
当前线程数 < corePoolSize？──是──→ 创建核心线程执行
  ↓否
任务入队列成功？──是──→ 等待空闲线程获取
  ↓否（队列满）
当前线程数 < maximumPoolSize？──是──→ 创建非核心线程执行
  ↓否
执行拒绝策略
```

**关键理解：** 线程池优先将任务放入队列，只有队列满了才会创建非核心线程。这意味着如果队列容量设置过大（如 `LinkedBlockingQueue` 默认 `Integer.MAX_VALUE`），`maximumPoolSize` 将永远不会生效。

### 4.3 为什么不建议用 Executors 工具类

| Executors 方法 | 创建的线程池 | 隐患 |
|---------------|-------------|------|
| `newFixedThreadPool(n)` | 固定线程数 + `LinkedBlockingQueue(Integer.MAX_VALUE)` | 队列无界，任务堆积导致 OOM |
| `newSingleThreadExecutor()` | 单线程 + `LinkedBlockingQueue(Integer.MAX_VALUE)` | 队列无界，任务堆积导致 OOM |
| `newCachedThreadPool()` | 核心线程 0 + `SynchronousQueue` + 最大 `Integer.MAX_VALUE` | 线程数无上限，高并发下创建大量线程导致 OOM |
| `newScheduledThreadPool(n)` | 固定核心线程 + `DelayedWorkQueue(Integer.MAX_VALUE)` | 队列无界，任务堆积导致 OOM |

**核心问题归纳：**

1. **无界队列**：`FixedThreadPool` 和 `SingleThreadExecutor` 使用无界队列，任务持续堆积不会触发拒绝策略，内存最终耗尽；
2. **无界线程**：`CachedThreadPool` 最大线程数为 `Integer.MAX_VALUE`，高并发下瞬间创建海量线程；
3. **默认线程命名**：`pool-N-thread-M`，无法区分业务模块，排障困难；
4. **无拒绝策略**：默认 `AbortPolicy` 直接抛异常，若无 catch 会导致任务丢失且无日志；
5. **非 daemon 线程**：默认创建非守护线程，可能阻止 JVM 优雅关闭。

## 5. 解决方案

### 5.1 自定义线程池完整模板

```java
import java.util.concurrent.*;
import java.util.concurrent.atomic.AtomicInteger;

public class ThreadPoolConfig {

    private static final int CPU_COUNT = Runtime.getRuntime().availableProcessors();

    public ThreadPoolExecutor orderPool() {
        return new ThreadPoolExecutor(
            CPU_COUNT,                                            // corePoolSize
            CPU_COUNT * 2,                                        // maximumPoolSize
            60L,                                                  // keepAliveTime
            TimeUnit.SECONDS,                                     // unit
            new LinkedBlockingQueue<>(1024),                      // 有界队列
            new NamedThreadFactory("order-pool"),                  // 自定义线程工厂
            new CustomRejectedExecutionHandler("order-pool")       // 自定义拒绝策略
        );
    }

    static class NamedThreadFactory implements ThreadFactory {
        private final AtomicInteger threadNumber = new AtomicInteger(1);
        private final String namePrefix;

        NamedThreadFactory(String namePrefix) {
            this.namePrefix = namePrefix + "-";
        }

        @Override
        public Thread newThread(Runnable r) {
            Thread t = new Thread(r, namePrefix + threadNumber.getAndIncrement());
            t.setDaemon(false);
            t.setUncaughtExceptionHandler((thread, ex) -> {
                System.err.println("Uncaught exception in " + thread.getName() + ": " + ex.getMessage());
            });
            return t;
        }
    }

    static class CustomRejectedExecutionHandler implements RejectedExecutionHandler {
        private final String poolName;

        CustomRejectedExecutionHandler(String poolName) {
            this.poolName = poolName;
        }

        @Override
        public void rejectedExecution(Runnable r, ThreadPoolExecutor executor) {
            System.err.println("[REJECT] pool=" + poolName
                + " queueSize=" + executor.getQueue().size()
                + " activeCount=" + executor.getActiveCount());
            // 降级处理：记录到 DB / MQ 后续重试，或走调用者线程执行
            if (!executor.isShutdown()) {
                r.run();
            }
        }
    }
}
```

### 5.2 核心参数配置策略

#### CPU 密集型任务

- `corePoolSize` = N_cpu（逻辑核心数）
- `maximumPoolSize` = N_cpu + 1
- 队列容量不宜过大，避免任务等待过久：128–512
- 拒绝策略：`CallerRunsPolicy` 或自定义降级

#### IO 密集型任务

- `corePoolSize` = 2 × N_cpu 或更高（需压测确定）
- `maximumPoolSize` = corePoolSize × 1.5–2
- 队列容量：512–2048（根据任务耗时和吞吐要求计算）
- 拒绝策略：自定义（记录日志 + 降级 + 异步重试）

#### 混合型任务

- 拆分为独立线程池，CPU 密集型和 IO 密集型分别配置；
- 避免用同一个线程池混合执行，防止 IO 阻塞型任务饿死 CPU 密集型任务。

### 5.3 队列容量计算公式

```text
队列容量 = 目标吞吐量 × 可接受最大等待时间

示例：
  目标吞吐量 = 5000 task/s
  可接受最大等待时间 = 200ms
  队列容量 ≈ 5000 × 0.2 = 1000
```

实际配置时还需考虑：
- 任务执行耗时的分布（P50 / P99）；
- 流量突增时的峰值倍数；
- 下游服务的承载能力。

### 5.4 拒绝策略选择

| 策略 | 行为 | 适用场景 |
|------|------|---------|
| `AbortPolicy`（默认） | 抛出 `RejectedExecutionException` | 必须保证调用方能感知到失败，且会处理异常 |
| `CallerRunsPolicy` | 调用者线程执行任务，起到自然反压 | 不能丢弃任务，且调用方能承受阻塞 |
| `DiscardPolicy` | 静默丢弃 | 任务可丢失，且无需通知（如非关键日志） |
| `DiscardOldestPolicy` | 丢弃队列最老任务，再尝试提交 | 任务时效性强（如实时数据更新） |
| 自定义 | 记录日志 + 落库 + 告警 + 降级 | 生产环境强烈推荐 |

## 6. 可选方案对比

| 方案 | 优点 | 缺点 | 推荐指数 |
|------|------|------|---------|
| `Executors.newFixedThreadPool` | 一行代码，简单 | 无界队列易 OOM | ★ |
| `Executors.newCachedThreadPool` | 弹性伸缩 | 线程数无上限易 OOM | ★ |
| `Executors.newSingleThreadExecutor` | 串行执行 | 无界队列易 OOM | ★ |
| 直接 `new ThreadPoolExecutor` | 参数完全可控 | 需要团队理解参数含义 | ★★★★★ |
| Spring `ThreadPoolTaskExecutor` | Spring 生态集成，支持配置文件 | 仍是对 ThreadPoolExecutor 的封装，需正确配置 | ★★★★ |
| Hippo4j / Dynamic-TP（动态线程池） | 参数动态调整，无需重启 | 引入额外组件，运维成本 | ★★★★ |
| 协程 / Loom 虚拟线程（JDK 21+） | 海量轻量级任务，IO 密集场景吞吐高 | 需 JDK 21+，部分库不兼容 | ★★★★ |

## 7. 推荐方案

### 短期（立即可用，零成本）

1. **禁用 Executors**：项目中全面替换为自定义 `ThreadPoolExecutor`；
2. **线程池统一管理**：建立 `ThreadPoolRegistry`，所有业务线程池集中注册、命名、监控；
3. **强制有界队列 + 自定义拒绝策略**：在代码评审中卡控。

### 中期（业务分级）

1. **业务隔离**：核心业务（订单、支付）独立线程池，避免互相影响；
2. **接入监控**：暴露线程池指标（核心线程数、活跃线程数、队列长度、拒绝次数）到 Prometheus / Micrometer；
3. **告警**：队列使用率 > 80%、拒绝次数 > 0、活跃线程数持续打满时告警。

### 长期（动态化、平台化）

1. **接入动态线程池**：使用 Hippo4j / Dynamic-TP，通过配置中心动态调整核心参数，无需重启；
2. **虚拟线程评估**：JDK 21+ 环境下评估虚拟线程（Project Loom）替换 IO 密集型线程池；
3. **统一框架**：基础架构团队封装统一 `BizThreadPool`，强制带监控、告警、动态参数。

## 8. 实施步骤

### 阶段一：盘点与评估（第 1 周）

1. 全代码扫描 `Executors.new`、`new Thread()`、`new ThreadPoolExecutor`；
2. 列出所有线程池及其当前参数、所属业务；
3. 对每个线程池评估 CPU/IO 类型、QPS、任务耗时分布。

### 阶段二：替换 Executors（第 2 周）

1. 编写统一的 `BizThreadPoolFactory` 工具类；
2. 逐个替换 `Executors` 调用为自定义线程池；
3. 添加自定义 `ThreadFactory`（含命名、daemon、异常处理）；
4. 添加自定义拒绝策略（含日志、降级）。

### 阶段三：监控接入（第 3 周）

1. 通过 `ThreadPoolExecutor` 提供的 `getActiveCount()`、`getQueue().size()`、`getCompletedTaskCount()` 等方法采集指标；
2. 上报 Prometheus / Micrometer，配置 Grafana 大盘；
3. 配置告警规则。

### 阶段四：动态化（第 4–8 周）

1. 引入 Hippo4j / Dynamic-TP；
2. 接入配置中心（Nacos / Apollo）；
3. 灰度验证动态参数调整。

## 9. 风险与注意事项

| 风险 | 影响 | 缓解措施 |
|------|------|---------|
| 队列容量过小导致正常请求被拒 | 业务损失 | 基于压测数据设置，留 30% 余量 |
| 队列容量过大导致响应延迟高 | 用户体验差 | 结合超时时间和 SLA 计算上限 |
| `CallerRunsPolicy` 阻塞调用线程 | 上游线程被拖垮 | 仅用于能承受阻塞的场景，避免在 Web 主线程使用 |
| 线程池关闭未优雅处理 | 任务丢失 | 使用 `shutdown()` + `awaitTermination()` 替代 `shutdownNow()` |
| 异常未捕获 | 线程静默退出，难以排查 | `ThreadFactory` 中设置 `UncaughtExceptionHandler` |
| 动态调整参数误操作 | 业务异常 | 配置变更需评审，支持快速回滚 |
| 业务共用一个线程池 | 故障扩散 | 核心业务隔离独立线程池 |

## 10. 验证方式

1. **静态扫描**
   - 使用 `grep -r "Executors\\.new"` 确认无残留；
   - 集成 ArchUnit / Checkstyle / 自定义 SpotBugs 规则在 CI 中卡控。
2. **单元测试**
   - 提交超过 `maximumPoolSize + queueCapacity` 个任务，验证拒绝策略被触发且行为符合预期；
   - 验证 `ThreadFactory` 创建的线程名符合规范，UncaughtExceptionHandler 生效。
3. **压力测试**
   - 模拟高并发提交任务，观察活跃线程数、队列长度、拒绝次数；
   - 持续运行 30 分钟，无 OOM、无线程泄漏；
   - 对比替换前后接口 P99 延迟变化。
4. **监控验证**
   - Grafana 大盘显示线程池核心指标（活跃数、队列长度、拒绝数、完成数）；
   - 触发模拟告警，验证告警链路通畅。
5. **线上观测**
   - 灰度发布后连续 3 个工作日观察峰值时段线程池指标；
   - 无拒绝异常、无 OOM、接口 SLA 达标。

## 11. 总结

线程池是高并发 Java 服务的基础设施，其核心在于 **七大参数的协同配置** 与 **业务隔离**。`Executors` 工具类因 **无界队列** 和 **无界线程** 两大致命缺陷，在生产环境中应被全面禁用。

正确的实践路径是：

1. **始终使用 `new ThreadPoolExecutor()`** 显式配置七大参数；
2. **核心 / 最大线程数** 根据 CPU 密集型 (N_cpu) 或 IO 密集型 (2×N_cpu+) 区分配置；
3. **必须使用有界队列**，容量基于吞吐量 × 等待时间计算；
4. **必须自定义 ThreadFactory**，提供业务化线程名和异常处理；
5. **必须自定义拒绝策略**，至少包含日志、降级和告警；
6. **核心业务独立线程池**，避免互相干扰；
7. **接入监控告警**，关键指标可观测；
8. **演进方向**：动态线程池（Hippo4j / Dynamic-TP）和 JDK 21+ 虚拟线程。

一句话：**线程池的核心不是创建线程，而是控制线程的边界与失败时的可预期行为。**

### 附：可能涉及的代码修改

**可能需要修改的模块：**

- 全局基础设施模块（线程池工厂、监控、配置中心接入）
- 业务异步处理模块（订单、支付、消息、定时任务）
- 框架封装模块（统一 `BizThreadPool`、装饰器、AOP）

**可能涉及的文件：**

- `ThreadPoolConfig.java` / `ThreadPoolFactory.java`：线程池工厂
- `NamedThreadFactory.java`：自定义线程工厂
- `CustomRejectedHandler.java`：自定义拒绝策略
- `ThreadPoolMonitor.java`：监控指标采集
- `application.yml` / Nacos / Apollo 配置：动态参数
- 业务 Service 中所有 `Executors.new*` 和 `new Thread()` 调用点

**核心修改逻辑：**

- 全面替换 `Executors.newXxx` 为 `new ThreadPoolExecutor(...)`；
- 所有线程池强制使用 **有界队列**（`LinkedBlockingQueue(capacity)` 或 `ArrayBlockingQueue`）；
- 所有线程池强制使用 **自定义 ThreadFactory**（业务化命名 + UncaughtExceptionHandler）；
- 所有线程池强制使用 **自定义拒绝策略**（日志 + 降级 + 告警）；
- 核心业务（订单、支付）独立线程池，避免与非核心业务共享。

**测试重点：**

- 拒绝策略触发测试：提交超容任务，验证降级逻辑；
- 监控指标准确性测试：人工触发任务，验证指标上报正确；
- 优雅关闭测试：`shutdown()` 后验证已提交任务全部完成；
- 长时间稳定性测试（72h+），关注线程泄漏和 OOM；
- 高并发压测：模拟峰值流量，观察拒绝率和延迟分布。
