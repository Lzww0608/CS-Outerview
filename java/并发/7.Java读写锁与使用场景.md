# 7. Java 读写锁与使用场景

## 1. 问题背景

在多线程程序中，如果多个线程同时访问共享数据，且至少有一个线程会修改数据，就必须考虑线程安全。最简单的方式是使用 `synchronized` 或 `ReentrantLock` 对整个临界区加互斥锁，但这种方式会让所有读操作和写操作都串行执行。

在很多业务场景中，数据访问呈现 **读多写少** 的特点，例如本地缓存、配置中心、路由表、黑白名单、商品类目树等。此时如果所有读请求都互斥执行，会严重降低并发性能。Java 的读写锁（ReadWriteLock）正是为这类场景设计的：**读读共享，读写互斥，写写互斥**。

**假设条件：**

- 使用 Java 8+；
- 主要讨论 JDK 自带的 `ReentrantReadWriteLock` 和 `StampedLock`；
- 业务场景以高并发服务中的本地缓存、配置读取、共享 Map 访问为主；
- 数据结构本身不是天然线程安全的，例如 `HashMap`、`ArrayList`。

## 2. 问题现象

如果读多写少场景仍使用普通互斥锁，可能出现：

1. **读请求被串行化**：多个线程只是读取数据，却互相阻塞；
2. **吞吐量低**：CPU 多核优势无法发挥，QPS 上不去；
3. **响应时间变长**：大量读线程等待锁，接口 P99 延迟升高；
4. **锁竞争严重**：线程频繁阻塞和唤醒，上下文切换开销增加；
5. **缓存访问慢**：本地缓存本应提升性能，却因为锁粒度过粗成为瓶颈。

示例问题：

```java
private final Map<String, String> cache = new HashMap<>();
private final ReentrantLock lock = new ReentrantLock();

public String get(String key) {
    lock.lock();
    try {
        return cache.get(key);
    } finally {
        lock.unlock();
    }
}
```

上面代码虽然线程安全，但所有读操作都会互斥执行，不适合读多写少场景。

## 3. 影响范围

| 影响维度 | 具体表现 |
|---------|---------|
| 性能 | 读请求无法并发，吞吐量下降 |
| 延迟 | 高并发下读线程排队，P99 延迟升高 |
| 资源 | 锁竞争导致线程阻塞、上下文切换增加 |
| 稳定性 | 写操作耗时过长时，大量读请求被阻塞 |
| 代码复杂度 | 锁使用不当可能引入死锁、锁泄漏、饥饿问题 |

## 4. 原因分析

### 4.1 普通互斥锁的问题

`synchronized` 和 `ReentrantLock` 都是互斥锁，同一时刻只允许一个线程进入临界区。它们无法区分当前操作是读还是写，因此即使多个线程只是读数据，也会互相阻塞。

对于读多写少场景，读操作之间并不会破坏数据一致性，真正需要互斥的是：

- 读操作与写操作不能并发；
- 写操作与写操作不能并发；
- 读操作与读操作可以并发。

### 4.2 读写锁的核心语义

Java 中常见读写锁是 `java.util.concurrent.locks.ReentrantReadWriteLock`。它内部维护两把锁：

1. **读锁（ReadLock）**：共享锁，多个线程可以同时持有；
2. **写锁（WriteLock）**：排他锁，同一时间只能一个线程持有。

其兼容关系如下：

| 当前锁状态 | 新读锁请求 | 新写锁请求 |
|------------|------------|------------|
| 无锁 | 允许 | 允许 |
| 已有读锁 | 允许 | 阻塞 |
| 已有写锁 | 阻塞 | 阻塞 |
| 已有读锁 + 等待写锁 | 非公平模式下可能允许插队，公平模式下按队列 | 阻塞等待 |

一句话：**读读不互斥，读写互斥，写写互斥**。

### 4.3 ReentrantReadWriteLock 的特点

1. **可重入**：同一线程可以重复获取读锁或写锁；
2. **支持公平 / 非公平模式**：默认非公平，吞吐量高，但可能导致写线程饥饿；
3. **支持锁降级**：写锁可以降级为读锁；
4. **不支持锁升级**：持有读锁时再获取写锁，容易死锁；
5. **基于 AQS 实现**：读写状态共用一个 `state` 字段，高 16 位记录读锁数量，低 16 位记录写锁重入次数。

### 4.4 为什么不能随便使用读写锁

读写锁不是无脑替代 `synchronized` 的工具。它适合读多写少，并且读操作耗时相对明显的场景。如果读写比例接近、临界区很短，读写锁的维护成本可能反而比互斥锁更高。

## 5. 解决方案

### 5.1 使用 ReentrantReadWriteLock 保护共享缓存

```java
import java.util.HashMap;
import java.util.Map;
import java.util.concurrent.locks.ReentrantReadWriteLock;

public class LocalCache {

    private final Map<String, String> cache = new HashMap<>();
    private final ReentrantReadWriteLock rwLock = new ReentrantReadWriteLock();
    private final ReentrantReadWriteLock.ReadLock readLock = rwLock.readLock();
    private final ReentrantReadWriteLock.WriteLock writeLock = rwLock.writeLock();

    public String get(String key) {
        readLock.lock();
        try {
            return cache.get(key);
        } finally {
            readLock.unlock();
        }
    }

    public void put(String key, String value) {
        writeLock.lock();
        try {
            cache.put(key, value);
        } finally {
            writeLock.unlock();
        }
    }

    public void remove(String key) {
        writeLock.lock();
        try {
            cache.remove(key);
        } finally {
            writeLock.unlock();
        }
    }
}
```

核心逻辑：

- `get()` 只读数据，使用读锁，允许多个线程并发读取；
- `put()` / `remove()` 修改数据，使用写锁，保证写操作独占；
- 所有加锁都必须放在 `try-finally` 中释放锁。

### 5.2 锁降级示例

锁降级是指：**先持有写锁，再获取读锁，最后释放写锁**。这样可以保证从写状态平滑过渡到读状态，避免中间被其他写线程插入。

```java
public String refreshAndGet(String key, String newValue) {
    writeLock.lock();
    try {
        cache.put(key, newValue);
        readLock.lock();
    } finally {
        writeLock.unlock();
    }

    try {
        return cache.get(key);
    } finally {
        readLock.unlock();
    }
}
```

注意：读写锁支持锁降级，但不支持锁升级。

错误示例：

```java
readLock.lock();
try {
    if (!cache.containsKey(key)) {
        writeLock.lock(); // 可能死锁，不推荐
    }
} finally {
    readLock.unlock();
}
```

如果需要从读转写，应先释放读锁，再获取写锁，并在获取写锁后重新检查条件。

### 5.3 使用 StampedLock 的乐观读

`StampedLock` 是 Java 8 引入的另一种读写锁，支持乐观读，适合读非常多、写较少的场景。

```java
import java.util.HashMap;
import java.util.Map;
import java.util.concurrent.locks.StampedLock;

public class StampedCache {
    private final Map<String, String> cache = new HashMap<>();
    private final StampedLock lock = new StampedLock();

    public String get(String key) {
        long stamp = lock.tryOptimisticRead();
        String value = cache.get(key);
        if (!lock.validate(stamp)) {
            stamp = lock.readLock();
            try {
                value = cache.get(key);
            } finally {
                lock.unlockRead(stamp);
            }
        }
        return value;
    }

    public void put(String key, String value) {
        long stamp = lock.writeLock();
        try {
            cache.put(key, value);
        } finally {
            lock.unlockWrite(stamp);
        }
    }
}
```

`StampedLock` 的特点：

- 乐观读不阻塞写线程；
- 读取后必须通过 `validate(stamp)` 校验期间是否发生写入；
- 不可重入，使用复杂度高；
- 不支持条件变量；
- 更适合性能敏感、读远多于写的底层组件。

## 6. 可选方案对比

| 方案 | 读并发 | 写并发 | 适用场景 | 优点 | 缺点 |
|------|--------|--------|---------|------|------|
| `synchronized` | 不支持 | 不支持 | 简单临界区 | 简单、安全、JVM 优化好 | 读操作也互斥 |
| `ReentrantLock` | 不支持 | 不支持 | 需要可中断、超时锁 | 功能比 synchronized 强 | 读读仍互斥 |
| `ReentrantReadWriteLock` | 支持 | 不支持 | 读多写少 | 读读并发，API 成熟 | 写线程可能饥饿，使用复杂 |
| `StampedLock` | 支持乐观读 | 不支持 | 极端读多写少 | 乐观读性能高 | 不可重入，易用错 |
| `ConcurrentHashMap` | 支持 | 支持分段/桶级并发 | Map 并发访问 | 开箱即用，性能好 | 仅适用于 Map 场景 |
| CopyOnWrite 容器 | 支持 | 写时复制 | 读极多写极少 | 读无锁 | 写成本高，占内存 |

## 7. 推荐方案

### 7.1 面试回答推荐

可以这样回答：

> Java 的读写锁主要是 `ReentrantReadWriteLock`，它把锁拆成读锁和写锁。读锁是共享锁，多个线程可以同时读；写锁是排他锁，写的时候不能有其他读写线程。它适合读多写少的场景，比如本地缓存、配置表、路由表、黑白名单等。使用时要注意读写锁不支持锁升级，但支持锁降级；另外默认是非公平锁，吞吐量高，但可能导致写线程饥饿。

### 7.2 工程实践推荐

1. 如果只是并发 Map 访问，优先使用 `ConcurrentHashMap`；
2. 如果是读多写少且需要保护一组复合数据结构，使用 `ReentrantReadWriteLock`；
3. 如果读远多于写且性能要求极高，可以评估 `StampedLock`；
4. 如果数据写入后很少修改，可以考虑不可变对象或 CopyOnWrite 容器；
5. 如果临界区很短、并发不高，普通 `synchronized` 可能更简单、更可靠。

## 8. 实施步骤

### 8.1 判断是否适合读写锁

1. 统计读写比例，确认是否读多写少；
2. 分析临界区耗时，如果读操作极短，读写锁收益可能不明显；
3. 判断数据结构是否需要整体一致性，如果只是 Map 单点访问，优先 `ConcurrentHashMap`；
4. 明确是否需要锁降级、超时、中断等高级能力。

### 8.2 改造步骤

1. 定义共享数据结构，例如 `Map`、`List`、配置对象；
2. 创建 `ReentrantReadWriteLock`；
3. 读方法使用 `readLock.lock()`；
4. 写方法使用 `writeLock.lock()`；
5. 所有解锁都放在 `finally` 中；
6. 避免在持锁期间执行远程调用、数据库查询、文件 IO 等耗时操作；
7. 编写并发测试，验证读读并发、读写互斥、写写互斥。

### 8.3 典型使用场景

1. **本地缓存**：读请求多，写请求来自定时刷新或后台更新；
2. **配置中心客户端**：配置读取频繁，变更较少；
3. **路由表 / 权限表**：查询远多于更新；
4. **黑白名单**：判断频繁，名单更新较少；
5. **商品类目树 / 字典表**：查询频繁，后台偶尔刷新；
6. **内存索引**：大量查询，定时重建或增量更新。

## 9. 风险与注意事项

| 风险 | 说明 | 解决方式 |
|------|------|---------|
| 忘记释放锁 | 线程永久阻塞 | 必须使用 `try-finally` |
| 锁升级死锁 | 持有读锁再申请写锁容易死锁 | 先释放读锁，再申请写锁，并重新检查条件 |
| 写线程饥饿 | 读线程持续进入，写线程长期等不到锁 | 使用公平锁或控制读流量 |
| 持锁时间过长 | 阻塞其他读写线程 | 锁内只做内存操作，避免 IO / RPC |
| 误用读锁修改数据 | 破坏线程安全 | 所有修改必须使用写锁 |
| 读写比例不适合 | 锁开销大于收益 | 通过压测确认收益 |
| StampedLock 不可重入 | 递归调用或重复加锁可能出问题 | 谨慎使用，封装统一工具 |
| 缓存对象内部可变 | 读锁保护了 Map，但返回对象被外部修改 | 返回不可变对象或防御性拷贝 |

## 10. 验证方式

### 10.1 功能验证

1. 多个线程同时执行 `get()`，验证不会互相阻塞；
2. 一个线程执行 `put()` 时，其他 `get()` 被阻塞；
3. 多个线程执行 `put()` 时，只能串行执行；
4. 写入后读取到的数据一致。

### 10.2 并发测试示例

```java
import java.util.concurrent.*;

public class ReadWriteLockTest {
    public static void main(String[] args) throws Exception {
        LocalCache cache = new LocalCache();
        ExecutorService pool = Executors.newFixedThreadPool(20);
        CountDownLatch latch = new CountDownLatch(1000);

        for (int i = 0; i < 1000; i++) {
            int index = i;
            pool.submit(() -> {
                try {
                    if (index % 10 == 0) {
                        cache.put("key" + index, "value" + index);
                    } else {
                        cache.get("key" + (index / 10));
                    }
                } finally {
                    latch.countDown();
                }
            });
        }

        latch.await();
        pool.shutdown();
    }
}
```

### 10.3 性能验证

1. 对比 `synchronized`、`ReentrantLock`、`ReentrantReadWriteLock` 在读多写少场景下的 QPS；
2. 压测不同读写比例：9:1、99:1、1:1；
3. 关注平均延迟、P99 延迟、锁等待时间、CPU 上下文切换次数；
4. 确认读写锁在目标场景下确实优于普通互斥锁。

## 11. 总结

Java 读写锁的核心思想是：**读读共享，读写互斥，写写互斥**。它适合读多写少的共享数据访问场景，可以显著提高读操作的并发能力。

核心结论：

1. `ReentrantReadWriteLock` 提供读锁和写锁；
2. 读锁是共享锁，多个线程可以同时持有；
3. 写锁是排他锁，写操作会阻塞其他读写操作；
4. 适合本地缓存、配置表、路由表、黑白名单等读多写少场景；
5. 使用时必须用 `try-finally` 释放锁；
6. 读写锁支持锁降级，不支持锁升级；
7. 如果只是并发 Map 操作，优先考虑 `ConcurrentHashMap`；
8. 如果读远多于写且性能敏感，可以评估 `StampedLock`；
9. 如果临界区很短或读写比例接近，普通互斥锁可能更合适。

一句话：**读写锁不是为了让写更快，而是为了让大量读操作不要互相阻塞。**
