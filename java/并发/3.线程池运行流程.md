## Java 线程池运行流程

### 1. 先创建线程池

比如用 `ThreadPoolExecutor` 或 `Executors` 创建。
线程池里会提前定义好：

- 核心线程数
- 最大线程数
- 任务队列
- 拒绝策略

------

### 2. 提交任务

你调用：

```java
executor.execute(task);
```

或者

```java
executor.submit(task);
```

把任务交给线程池。

------

### 3. 线程池先看当前线程数量

收到任务后，线程池不是马上新建线程，而是按规则判断：

#### 情况一：当前线程数 < 核心线程数

直接创建新线程来执行这个任务。

#### 情况二：当前线程数 >= 核心线程数

先不急着建新线程，而是尝试把任务放进任务队列。

------

### 4. 任务队列满了怎么办

如果队列已经放不下新任务了，线程池会继续判断：

#### 如果当前线程数 < 最大线程数

再创建新线程处理任务。

#### 如果当前线程数已经达到最大线程数

就触发**拒绝策略**。

------

### 5. 拒绝策略生效

常见几种：

- 直接报错
- 让提交任务的线程自己执行
- 丢掉当前任务
- 丢掉队列里最老的任务再尝试加入

------

### 6. 线程执行完任务后怎么办

线程不会立刻销毁。

- 核心线程通常会保留，等下一个任务
- 非核心线程如果空闲时间太久，可能会被回收

------

## 一句话总结流程

可以记成这句：

> **先开核心线程，再进队列，队列满了再开非核心线程，真的满了就拒绝。**

------

## 一个很简化的流程图思路

```text
提交任务
   ↓
核心线程没满？
   ├─ 是 → 创建核心线程执行
   └─ 否 → 放入队列
              ↓
          队列满了？
              ├─ 否 → 等待空闲线程执行
              └─ 是 → 最大线程没满？
                        ├─ 是 → 创建非核心线程执行
                        └─ 否 → 拒绝策略
```

------

## 你可以把它想成饭店

- 核心线程：固定员工
- 队列：排队区
- 最大线程：高峰期临时加的人
- 拒绝策略：实在接待不了时的处理方式

来一个顾客（任务）时：

1. 固定员工有空就直接接待
2. 固定员工满了，就去排队
3. 排队区满了，就叫临时工
4. 临时工也满了，就不接了或者换种处理方式

------

## 补一句 execute 和 submit 的区别

- `execute()`：只执行任务，没有返回值
- `submit()`：可以拿到 `Future`，以后能看结果、异常、是否完成

------

## ThreadPool 是怎么优化接口时间的

线程池优化接口耗时，本质上不是让单个任务的 CPU 指令变少，而是减少线程创建销毁成本、隔离慢任务，并把可以并行或异步的部分从主链路拆出去。

常见场景：

1. **复用线程**：避免每个请求都创建和销毁线程，减少上下文切换和调度开销。
2. **并行调用下游**：多个互不依赖的 RPC、数据库查询、文件处理可以并行执行，接口耗时从“多个耗时相加”变成“最慢分支耗时 + 汇总开销”。
3. **异步化非核心逻辑**：日志、埋点、通知、导出、发券、缩略图生成等不影响当次返回的任务放到线程池或 MQ。
4. **资源隔离**：CPU 密集、I/O 密集、慢下游、低优先级任务分开线程池，避免一个慢任务把所有业务线程占满。
5. **削峰和限流**：有界队列吸收短时波动，队列满时用拒绝策略快速失败或降级，保护主链路。

示例：

```java
CompletableFuture<User> userFuture =
        CompletableFuture.supplyAsync(() -> userService.getUser(userId), executor);

CompletableFuture<List<Order>> orderFuture =
        CompletableFuture.supplyAsync(() -> orderService.listRecentOrders(userId), executor);

CompletableFuture.allOf(userFuture, orderFuture).join();
return buildResponse(userFuture.join(), orderFuture.join());
```

这个写法只适合两个任务互不依赖的场景。如果第二个查询依赖第一个查询结果，就不能强行并行。

## 线程池优化的易错点

1. 线程数不是越大越好，过多线程会增加上下文切换、锁竞争和内存占用。
2. 队列不能无界，否则下游慢时请求会在内存里越积越多，最终 OOM。
3. 并行调用会放大下游压力，要同时关注数据库连接池、Redis 连接池和 RPC 限流。
4. 在线程池任务里同步等待同一个线程池的新任务，可能造成线程池死锁。
5. 异步任务失败不能只打日志，要有重试、告警、补偿或任务状态表。
6. 接口如果必须等待所有 Future 完成，整体耗时仍取决于最慢的那个分支。

## 面试回答模板

ThreadPool 能优化接口时间，主要是通过线程复用、并行化和异步化。线程复用减少频繁创建线程的成本；多个互不依赖的下游调用可以用线程池并行执行，降低串行等待时间；非核心任务可以异步投递，让主接口先返回。同时线程池还能做资源隔离，比如核心接口、导出任务、慢下游分别用不同线程池。工程上要强调有界队列、合理线程数、拒绝策略、超时和监控，否则线程池不仅不能优化耗时，还可能因为排队和 OOM 把系统拖垮。
