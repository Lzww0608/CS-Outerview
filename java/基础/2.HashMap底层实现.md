# 2. HashMap 底层实现

Java `HashMap` 是基于哈希表实现的 key-value 容器。面试问底层实现时，重点不是背 API，而是讲清楚数组、哈希扰动、冲突处理、扩容、树化和线程安全边界。

## 1. 核心结构

JDK 8 之后，`HashMap` 可以概括为：

```text
Node<K,V>[] table
  bucket 0 -> 链表或红黑树
  bucket 1 -> 链表或红黑树
  ...
```

每个节点保存：

```java
static class Node<K,V> {
    final int hash;
    final K key;
    V value;
    Node<K,V> next;
}
```

基本流程：

1. 对 key 计算 `hashCode()`。
2. 做高低位扰动，降低低位分布不均带来的冲突。
3. 用 `(n - 1) & hash` 定位桶下标，前提是容量 `n` 是 2 的幂。
4. 桶为空则直接插入；桶非空则比较 hash 和 key，找到相同 key 更新，否则挂到链表或红黑树中。

## 2. 为什么容量是 2 的幂

当数组长度是 2 的幂时，取模可以优化成位运算：

```java
index = (n - 1) & hash;
```

这样比 `% n` 更快，并且扩容为 2 倍时，旧元素的新位置只可能是：

```text
原下标 i
原下标 i + oldCap
```

判断依据是 `hash & oldCap` 是否为 0。JDK 8 扩容时会把旧链表拆成 low/high 两条链，避免对每个元素重新完整计算 hash。

## 3. 哈希冲突怎么处理

`HashMap` 使用链地址法。多个 key 映射到同一个桶时，先以链表保存：

```text
table[i] -> node1 -> node2 -> node3
```

链表过长时会退化为线性查询。JDK 8 引入树化策略：

| 参数 | 默认值 | 含义 |
| --- | --- | --- |
| `TREEIFY_THRESHOLD` | 8 | 链表长度达到阈值后考虑树化 |
| `UNTREEIFY_THRESHOLD` | 6 | 树节点数量较少时退化回链表 |
| `MIN_TREEIFY_CAPACITY` | 64 | table 至少达到该容量才树化 |

也就是说，链表长度达到 8 时不一定立刻树化。如果数组容量还小于 64，优先扩容，因为冲突可能只是容量太小导致的；扩容后元素分散，链表自然变短。

## 4. put 和 get 的核心过程

`put(k, v)` 的关键逻辑：

1. table 未初始化则懒初始化。
2. 根据 hash 找桶下标。
3. 桶为空，直接新建节点。
4. 桶首 key 相同，覆盖 value。
5. 桶是红黑树，走树插入或更新。
6. 桶是链表，遍历查找；没有相同 key 就尾插。
7. 插入后 size 超过 `threshold = capacity * loadFactor`，触发 resize。

`get(k)` 的关键逻辑：

1. 根据 key 的 hash 定位桶。
2. 先比较桶首节点。
3. 如果桶是树，按红黑树查找。
4. 否则遍历链表，使用 `==` 或 `equals()` 判断 key 是否相等。

平均复杂度接近 `O(1)`，前提是 hash 分布较均匀、容量足够、冲突链不长。极端冲突下，链表是 `O(n)`，树化后是 `O(log n)`。

## 5. loadFactor 和扩容

默认负载因子是 `0.75`。它是在空间和时间之间的折中：

1. 太小：冲突少，但数组更大，浪费内存。
2. 太大：数组利用率高，但冲突增多，查询和插入变慢。
3. `0.75` 在多数业务 key 分布下能保持较好的性能和空间利用率。

扩容代价较高，因为要重新分配 table 并迁移桶中节点。真实项目里如果能估算数据量，应在构造时指定初始容量，减少频繁 resize。

## 6. key 的 equals 和 hashCode

自定义对象作为 key 时必须遵守：

1. `equals()` 相等的对象，`hashCode()` 必须相等。
2. `hashCode()` 相等的对象，`equals()` 不一定相等。
3. key 放入 `HashMap` 后，不要修改参与 `equals/hashCode` 的字段。

错误示例是把可变对象作为 key，插入后修改字段，导致对象仍在原桶里，但用新 hash 已经找不到它。

## 7. 线程安全边界

普通 `HashMap` 不是线程安全的：

1. 并发 `put` 可能丢更新。
2. 扩容和链表/树结构修改期间被并发读写，可能读到不一致状态。
3. `size`、结构修改次数、迭代器 fail-fast 都不提供并发正确性保证。

多线程场景应使用：

1. `ConcurrentHashMap`。
2. 外部锁保护 `HashMap`。
3. 初始化后只读的不可变 Map。
4. 分片 Map + 分片锁，适合特定高并发写场景。

## 8. 和 ConcurrentHashMap 的区别

| 对比项 | HashMap | ConcurrentHashMap |
| --- | --- | --- |
| 线程安全 | 否 | 是 |
| null key/value | 允许一个 null key 和多个 null value | 不允许 null key/value |
| 并发写 | 可能破坏结构或丢更新 | 使用 CAS、桶级 synchronized、volatile 等控制并发 |
| 适用场景 | 单线程或外部同步 | 高并发共享 Map |

`ConcurrentHashMap` 不允许 null 的一个原因是避免并发语义歧义：`get(key) == null` 无法区分 key 不存在还是 value 本身为 null。

## 9. 易错点

1. JDK 8 的 `HashMap` 是数组 + 链表 + 红黑树，不是永远链表。
2. 链表长度达到 8 不一定树化，容量小于 64 时优先扩容。
3. 容量是 2 的幂，是为了快速定位和扩容迁移。
4. `HashMap` 平均 `O(1)` 不代表最坏 `O(1)`。
5. `HashMap` 不是线程安全容器，并发读写不能靠“概率上没出事”。

## 10. 面试回答模板

Java `HashMap` 底层是数组加链地址法，JDK 8 后冲突严重时链表会树化成红黑树。put 时先算 key 的 hashCode，并做高低位扰动，再用 `(n - 1) & hash` 找桶；桶为空直接插入，桶非空就比较 hash 和 equals，更新已有 key 或追加节点。默认负载因子 0.75，超过阈值会扩容为两倍，迁移时节点要么留在原下标，要么移动到 `原下标 + oldCap`。链表长度达到 8 且容量至少 64 才树化，否则优先扩容。普通 HashMap 不是线程安全的，多线程共享要用 ConcurrentHashMap 或外部同步。
