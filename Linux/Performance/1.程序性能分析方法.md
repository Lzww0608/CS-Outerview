# 程序性能分析方法

程序性能分析要先定义目标，再用工具定位瓶颈。不要一开始就改代码，否则很容易把 CPU、I/O、锁、内存或下游依赖混在一起。

## 1. 分析流程

推荐流程：

```text
明确目标
  -> 采集指标
  -> 定位瓶颈类型
  -> 找热点调用栈
  -> 修改一个变量
  -> 压测对比
  -> 观察线上回归
```

目标要量化，例如：

1. QPS 从 2w 提到 4w。
2. P99 延迟从 200ms 降到 80ms。
3. CPU 使用率从 800% 降到 400%。
4. 内存 RSS 增长停止。
5. 慢 SQL 数量或锁等待时间下降。

## 2. 常用工具

| 问题类型 | 工具 | 看什么 |
| --- | --- | --- |
| CPU 热点 | `top -H`、`pidstat`、`perf top/record/report`、火焰图 | 高 CPU 线程和热点函数 |
| 内存泄漏 | ASan/LSan、Valgrind、heaptrack、jemalloc/tcmalloc profile | 分配栈、未释放对象、增长曲线 |
| 系统调用 | `strace`、`perf trace`、eBPF/bpftrace | 调用频率、耗时、errno |
| 磁盘 I/O | `iostat`、`iotop`、`pidstat -d` | util、await、读写吞吐 |
| 网络 | `ss`、`sar -n`、`tcpdump`、`iftop` | 重传、连接状态、带宽、PPS |
| 锁竞争 | `perf lock`、`pstack`、TSan、日志埋点 | 等锁时间、阻塞栈 |
| 数据库 | 慢 SQL、`EXPLAIN ANALYZE`、性能视图 | 扫描行数、锁等待、执行计划 |

## 3. CPU 分析

常见命令：

```bash
top -H -p <pid>
pidstat -t -p <pid> 1
perf record -F 99 -p <pid> -g -- sleep 30
perf report
```

分析时要区分：

1. 用户态热点：算法、序列化、JSON、压缩、加密、日志格式化。
2. 内核态热点：系统调用太频繁、网络协议栈、锁竞争、软中断。
3. 上下文切换：线程过多、锁等待、条件变量频繁唤醒。
4. 忙等：自旋、轮询、无退避重试。

## 4. 内存分析

内存问题要区分：

1. **泄漏**：对象不再需要但仍被引用或未释放。
2. **膨胀**：缓存、队列、连接上下文增长但业务上仍可达。
3. **碎片**：分配器持有大量空闲块但难以归还 OS。
4. **峰值过高**：批量任务、排序、聚合或大对象临时分配导致。

常见手段：

```bash
pmap -x <pid>
cat /proc/<pid>/smaps_rollup
valgrind --leak-check=full ./app
heaptrack ./app
```

线上更常用 allocator profile、采样和监控，避免 Valgrind 这类高开销工具直接跑生产流量。

## 5. 优化原则

1. 一次只改一个主要因素，避免无法归因。
2. 用相同输入、相同压测条件对比优化前后。
3. 同时看平均值和 P95/P99，不能只看平均延迟。
4. 性能优化不能破坏正确性，尤其是锁、内存序、缓存一致性和失败重试。
5. 对热点路径做代码简化、减少分配、减少拷贝、批量化、缓存和算法复杂度优化。

## 6. 面试回答模板

程序性能分析我会先明确指标，例如 QPS、P99、CPU、RSS 或慢 SQL，然后用监控和压测复现。CPU 问题用 `top -H` 找线程，用 `perf` 和火焰图看热点；内存问题看 RSS、`pmap/smaps`、heap profile、ASan/Valgrind；I/O 问题用 `iostat/strace/tcpdump/ss`；锁竞争看线程栈、`perf lock` 或埋点。定位后按算法、数据结构、锁粒度、批量 I/O、缓存、连接池和下游依赖逐层优化，并用同一压测基准验证 P99、吞吐和资源占用是否真的改善。
