# 守护进程与服务异常监控

守护进程是长期运行在后台、通常不依赖终端的系统服务。面试问“创建一个守护进程监听服务进程异常状态，比如假死，怎么做”，重点不是只会 `fork`，而是要说明如何检测异常、如何恢复、如何避免误判和反复拉起。

## 1. 传统 daemonize 流程

经典守护进程化步骤：

1. `fork()`，父进程退出，让子进程脱离启动 shell。
2. `setsid()`，创建新会话，脱离控制终端。
3. 可选再次 `fork()`，避免重新获得控制终端。
4. `chdir("/")`，避免占用工作目录。
5. `umask(0)` 或设置合适的文件权限掩码。
6. 关闭或重定向标准输入输出错误到 `/dev/null` 或日志文件。
7. 写 pid file，并用文件锁避免重复启动。
8. 注册信号处理，例如 `SIGTERM` 优雅退出、`SIGHUP` 重载配置。

现代 Linux 服务更推荐交给 `systemd` 管理。业务进程可以前台运行，由 `systemd` 负责后台化、日志、重启、资源限制和依赖管理。

## 2. 监控服务进程崩溃

如果守护进程是服务进程的父进程，可以用 `waitpid` 监听子进程退出：

```cpp
for (;;) {
    pid_t pid = waitpid(child_pid, &status, 0);
    if (pid == child_pid) {
        // 记录退出码、信号、core dump 信息
        // 按策略拉起新服务进程
        child_pid = forkAndExecService();
    }
}
```

要记录：

1. 正常退出还是被信号杀死。
2. 退出码或信号编号。
3. 是否产生 core dump。
4. 重启次数和时间窗口。

不要无限制快速重启。应做退避和熔断，例如 1 分钟内连续崩溃 5 次就暂停拉起并告警。

## 3. 监控假死

假死指进程还活着，但不再处理请求或内部线程卡住。只检查 `kill(pid, 0)` 不够，因为它只能证明进程存在。

常见检测方式：

1. **心跳文件或共享内存时间戳**：服务定期更新时间戳，守护进程检查是否超时。
2. **本地 health check 端口**：守护进程定期请求 `/healthz`，验证事件循环、线程池、数据库依赖是否正常。
3. **业务探针**：发一条轻量真实请求，检查完整链路是否能返回。
4. **线程级 watchdog**：关键线程定期上报进度，主线程或监控线程发现某个线程长时间不前进就告警。
5. **指标监控**：QPS、延迟、队列积压、错误率、CPU、内存、fd 数、死锁指标。

健康检查要区分 liveness 和 readiness：

1. liveness：进程是否需要被重启。
2. readiness：进程是否暂时不能接流量，例如正在加载配置、下游不可用。

## 4. 恢复策略

发现异常后不要只做 `kill -9`：

1. 先记录现场：日志、堆栈、core、`pstack/gdb`、`/proc/<pid>`、关键指标。
2. 尝试优雅退出：发送 `SIGTERM`，给服务 flush 日志和释放资源的时间。
3. 超时未退出再 `SIGKILL`。
4. 拉起新进程并等待健康检查通过。
5. 向注册中心或负载均衡更新状态，避免异常实例继续接流量。
6. 重启加退避和次数限制，防止故障风暴。

线上更常用：

1. `systemd`：`Restart=on-failure`、`WatchdogSec=`、`sd_notify`。
2. Kubernetes：livenessProbe、readinessProbe、startupProbe。
3. supervisor、monit、s6、runit 等进程管理器。

## 5. 易错点

1. `kill(pid, 0)` 只能判断进程是否存在和权限是否足够，不能判断服务是否可用。
2. 健康检查不能太重，否则监控本身会压垮服务。
3. 拉起前要确认旧进程已退出或端口已释放，避免双实例抢资源。
4. pid file 可能过期，要结合进程启动时间或文件锁验证。
5. 监控进程本身也要被 systemd/K8s 管理，否则 watchdog 死了没人知道。
6. 假死排查要保留现场，直接杀进程会丢失死锁、阻塞点和 core 信息。

## 6. 面试回答模板

我会把监控拆成崩溃检测和假死检测。崩溃检测可以让守护进程作为父进程，用 `waitpid` 获取子进程退出状态，记录退出码、信号和 core，再按退避策略拉起。假死不能只用 `kill(pid,0)`，要用心跳时间戳、health check 端口或业务探针判断服务是否还在处理请求。发现异常后先抓日志、堆栈和指标，优雅 `SIGTERM`，超时再 `SIGKILL`，重启后等健康检查通过再接流量。真实生产优先使用 systemd 的 `Restart/WatchdogSec` 或 Kubernetes 的 liveness/readiness probe，而不是手写完整进程管理器。
