# 3. BPF 与 eBPF 原理和应用

BPF（Berkeley Packet Filter）最早是为高效抓包过滤设计的内核虚拟机。它允许用户态把一段受限的过滤程序加载到内核里，让内核在数据包进入用户态之前先判断“这个包要不要”。经典场景就是 `tcpdump 'tcp port 80'`：过滤表达式会被编译成 BPF 指令，在内核里执行，只把匹配的包复制给用户态，避免大量无用包跨内核态/用户态拷贝。

eBPF（extended BPF）是 BPF 的扩展版本。它不再局限于抓包过滤，而是变成了 Linux 内核中的安全可验证沙箱执行机制：用户可以把小程序加载到内核，在特定 hook 点运行，用 maps 和用户态交换数据，用 helper 调用内核提供的受控能力。它常用于网络、可观测性、安全、性能分析和内核行为扩展。

一句话概括：**BPF 是早期面向包过滤的内核虚拟机，eBPF 是通用的内核可编程框架；它通过 verifier 保证安全，通过 JIT 提升性能，通过 maps 保存状态，通过 hook 点接入网络、追踪和安全路径。**

## 1. BPF 和 eBPF 的区别

| 对比项 | 经典 BPF | eBPF |
| --- | --- | --- |
| 主要目标 | 数据包过滤 | 网络、追踪、安全、性能分析、内核扩展 |
| 指令集 | 简单，寄存器少 | 64 位 RISC 风格，寄存器更多 |
| 状态保存 | 基本无状态 | 可通过 BPF maps 保存和共享状态 |
| 加载校验 | 受限校验 | verifier 做复杂静态验证 |
| 执行方式 | 解释执行为主 | 解释执行或 JIT 为机器码 |
| 接入点 | socket packet filter | XDP、tc、kprobe、tracepoint、LSM、cgroup、uprobes 等 |
| 典型工具 | `tcpdump`、`libpcap` | `bcc`、`bpftrace`、`libbpf`、Cilium、Falco |

面试里不要把 BPF 简单说成“抓包工具”。抓包过滤只是 BPF 的起源；eBPF 更像“安全受控的内核插件机制”。

## 2. eBPF 的整体架构

eBPF 的典型工作流：

```text
用户编写 eBPF 程序
  -> clang/LLVM 编译成 eBPF bytecode
  -> 用户态 loader 通过 bpf() 系统调用加载
  -> 内核 verifier 做安全校验
  -> 通过后可解释执行或 JIT 成机器码
  -> 程序 attach 到 hook 点
  -> 内核事件触发时运行 eBPF 程序
  -> 通过 maps/ring buffer/perf buffer 把数据传回用户态
```

核心组件：

| 组件 | 作用 |
| --- | --- |
| eBPF bytecode | 运行在内核 eBPF VM 中的指令。 |
| verifier | 静态验证程序是否安全、是否会越界、是否可能无限循环。 |
| JIT | 把 eBPF 指令编译成本机机器码，提高执行效率。 |
| helper functions | 内核暴露给 eBPF 的受控函数，例如查 map、取时间、读上下文。 |
| BPF maps | 内核中的 key-value 数据结构，用于保存状态和用户态交互。 |
| hook/attach point | eBPF 程序被触发的位置，例如 XDP、tracepoint、kprobe。 |

## 3. verifier 为什么重要

eBPF 程序运行在内核态，一旦出错可能影响整机。因此内核在加载前会执行 verifier 校验。

典型校验包括：

1. **不能访问非法内存**：指针必须可追踪，访问范围必须可证明合法。
2. **不能无限循环**：早期要求无循环，现代内核支持有界循环，但必须能证明终止。
3. **栈空间受限**：eBPF 栈很小，不能放大对象。
4. **不能任意调用内核函数**：只能调用当前程序类型允许的 helper。
5. **不能泄露内核地址**：避免绕过 KASLR 或暴露敏感信息。
6. **类型和上下文受限**：不同 hook 点能访问的上下文字段不同。
7. **分支状态要可分析**：复杂分支会让 verifier 状态爆炸，导致加载失败。

verifier 的价值是让 eBPF 比传统内核模块更安全：内核模块可以做几乎任何事，bug 会直接破坏内核；eBPF 程序被限制在可验证的沙箱里。

## 4. BPF maps 是什么

BPF maps 是 eBPF 程序保存状态、聚合数据、和用户态通信的核心机制。它们存在于内核中，用户态和 eBPF 程序都可以通过 fd 或 helper 访问。

常见 map 类型：

| 类型 | 作用 | 场景 |
| --- | --- | --- |
| Hash map | key-value 查询 | 连接状态、进程统计、黑名单 |
| Array map | 固定下标数组 | 配置项、计数器 |
| Per-CPU map | 每 CPU 独立值 | 降低多核写计数竞争 |
| LRU hash | 自动淘汰冷 key | 连接跟踪、热点统计 |
| Ring buffer | 内核向用户态传事件 | 日志、审计、追踪事件 |
| Perf event array | 老式事件输出 | bcc/bpftrace 追踪输出 |
| Program array | 存放程序 fd | tail call，拆分复杂程序 |
| Sock map / Sock hash | socket 重定向 | L7 代理、service mesh 加速 |

例子：统计每个进程的系统调用次数，可以用 `pid -> count` 的 hash map；高频计数可用 per-CPU map，用户态定期汇总，避免所有 CPU 写同一个计数器造成 cache line 抖动。

## 5. 常见程序类型和 hook 点

eBPF 不同程序类型能挂到不同位置，拥有不同上下文和 helper。

| 程序类型 | 触发位置 | 典型应用 |
| --- | --- | --- |
| XDP | 网卡驱动收包早期，构造 `skb` 前 | DDoS 丢包、L4 负载均衡、快速转发 |
| tc BPF | qdisc 层 ingress/egress | 流量控制、重定向、容器网络 |
| socket filter | socket 收包过滤 | 抓包、包过滤 |
| kprobe/kretprobe | 内核函数入口/返回 | 动态内核追踪、性能分析 |
| tracepoint | 内核稳定追踪点 | 系统调用、调度、网络事件观测 |
| uprobe/uretprobe | 用户态函数入口/返回 | 追踪应用函数、库函数 |
| perf event | perf 采样事件 | CPU profile、硬件计数器分析 |
| cgroup BPF | cgroup 网络或资源 hook | 容器网络策略、连接控制 |
| LSM BPF | Linux Security Module hook | 安全审计、访问控制 |
| sockops/sk_msg | socket 操作和消息路径 | 透明代理、socket 加速 |

选择原则：

1. 要极早丢包或转发，用 XDP。
2. 要做容器网络、限速、重定向，用 tc/cgroup。
3. 要观测内核函数，用 kprobe，但要注意内核版本函数名变化。
4. 要更稳定的内核事件，用 tracepoint。
5. 要观测用户态函数，用 uprobe。
6. 要安全策略，用 LSM BPF 或 cgroup BPF。

## 6. eBPF 网络原理

网络是 eBPF 最典型的落地领域。

### 6.1 XDP

XDP 运行在网卡驱动收包非常早的位置，通常早于 `sk_buff` 构造。

```text
NIC 收包
  -> 驱动 RX ring
  -> XDP 程序
  -> 决定 DROP / PASS / TX / REDIRECT
  -> PASS 才进入常规协议栈
```

常见返回动作：

| 动作 | 含义 |
| --- | --- |
| `XDP_DROP` | 直接丢包，适合 DDoS 过滤。 |
| `XDP_PASS` | 放行到内核协议栈。 |
| `XDP_TX` | 从当前网卡发回去。 |
| `XDP_REDIRECT` | 重定向到其他网卡、CPU 或 AF_XDP socket。 |
| `XDP_ABORTED` | 程序异常，通常用于调试和统计。 |

XDP 的优势是早、快、开销低；限制是上下文少，不能直接使用完整协议栈能力。

### 6.2 tc BPF

tc BPF 挂在 qdisc ingress/egress，更靠近常规协议栈。

```text
收包：网卡 -> XDP -> skb -> tc ingress -> 协议栈
发包：协议栈 -> tc egress -> qdisc/驱动
```

它适合做：

1. 容器网络策略。
2. 包标记和重定向。
3. 简单 NAT、封装、隧道。
4. 流量统计、限速和分类。

### 6.3 Cilium 类容器网络

Cilium 使用 eBPF 在 Linux 内核里实现容器网络、服务负载均衡、网络策略和可观测性。相比传统 iptables 规则链，eBPF 可以用 map 做高效查表，并把策略逻辑直接挂到网络路径上，减少长规则链匹配成本。

这类系统常见结构：

```text
Kubernetes service / endpoint / policy
  -> 用户态 agent 写入 BPF maps
  -> datapath eBPF 程序在 XDP/tc/socket hook 执行
  -> 根据 map 决定转发、丢弃、NAT、负载均衡
```

## 7. eBPF 可观测性原理

传统排查常用日志、`strace`、`perf`、抓包。eBPF 的优势是可以在不改业务代码的情况下，把探针挂到内核或用户态函数上，低开销采集事件。

例子：

```bash
# 统计 execve 调用
bpftrace -e 'tracepoint:syscalls:sys_enter_execve { @[comm] = count(); }'

# 查看 TCP 重传事件
bpftrace -e 'tracepoint:tcp:tcp_retransmit_skb { @[comm] = count(); }'
```

可观测性常见用途：

1. 统计系统调用耗时和错误码。
2. 追踪 TCP 重传、连接建立、丢包、accept 延迟。
3. 分析调度延迟、run queue、off-CPU 时间。
4. 追踪文件系统、块 I/O、page cache 行为。
5. 观测用户态函数调用和延迟，例如数据库客户端、RPC 框架、加密库。
6. 生成 profile 和火焰图。

tracepoint 比 kprobe 更稳定，因为 tracepoint 是内核主动提供的观测点；kprobe 可以挂任意内核函数，更灵活但更依赖内核版本和函数实现。

## 8. eBPF 安全应用

安全场景常用 eBPF 做运行时检测和访问控制：

1. **系统调用审计**：监控 `execve`、`openat`、`connect`、`ptrace` 等敏感行为。
2. **容器逃逸检测**：发现异常 namespace、capability、挂载、cgroup 行为。
3. **网络安全**：检测端口扫描、异常连接、DDoS、可疑 DNS。
4. **文件访问控制**：结合 LSM BPF 约束敏感路径访问。
5. **进程行为画像**：按进程、容器、用户聚合行为基线。

典型工具包括 Falco、Tetragon 等。它们通常在内核 hook 采集事件，通过 ring buffer 传到用户态，再和策略规则匹配。

注意：eBPF 能增强安全可见性，但不是天然安全。加载 eBPF 程序本身需要权限，生产环境要控制 `CAP_BPF`、`CAP_SYS_ADMIN`、`unprivileged_bpf_disabled`、bpffs 权限和程序来源。

## 9. eBPF 开发方式

常见开发栈：

| 工具 | 适用场景 |
| --- | --- |
| `tcpdump/libpcap` | 经典 BPF 抓包过滤。 |
| `bpftrace` | 临时排查、一行脚本、快速观测。 |
| BCC | Python + C，适合脚本化 tracing。 |
| libbpf | 生产级 eBPF loader 和 CO-RE 支持。 |
| CO-RE | Compile Once, Run Everywhere，利用 BTF 适配不同内核结构体布局。 |
| bpftool | 查看、加载、dump、管理 BPF 程序和 maps。 |

生产项目更常用 libbpf + CO-RE：

```text
eBPF C 程序
  -> clang 编译成 .o
  -> skeleton 生成用户态加载代码
  -> loader 加载程序、创建 maps、attach hook
  -> 用户态读取 ring buffer 或 map 数据
```

CO-RE 解决的问题是不同内核版本里结构体字段偏移可能变化。BTF 提供内核类型信息，libbpf 可以在加载时做重定位，让同一个 eBPF object 适配多个内核版本。

## 10. eBPF 的限制和风险

1. **不是任意内核编程**：只能使用允许的 helper 和上下文，不能随意调用内核函数。
2. **verifier 可能拒绝复杂程序**：指针关系、边界判断、循环和分支过复杂都可能加载失败。
3. **内核版本差异**：程序类型、helper、BTF、CO-RE 能力依赖内核版本。
4. **性能不是零成本**：高频 hook、map 操作、ring buffer 输出都会消耗 CPU。
5. **观测可能改变系统行为**：过多事件输出会造成丢事件、锁竞争或 CPU 抖动。
6. **权限和安全风险**：恶意或有 bug 的 eBPF 程序虽然受限，但仍运行在敏感路径。
7. **调试复杂**：verifier log、内核符号、BTF、JIT 后指令都需要专门工具。

工程建议：

1. 临时排查用 bpftrace/BCC，长期生产能力用 libbpf/CO-RE。
2. 高频路径优先用 per-CPU map，减少共享写竞争。
3. ring buffer 输出要限速和采样，避免观测系统拖垮业务。
4. 网络 datapath 程序要配套 metrics、fallback 和灰度。
5. 线上启用前确认内核版本、权限、BTF、JIT 和 verifier 行为。

## 11. 和内核模块、ptrace、perf 的区别

| 技术 | 特点 | 适合场景 |
| --- | --- | --- |
| 内核模块 | 权限最大、能力最强、风险最高 | 设备驱动、深度内核扩展 |
| eBPF | 受 verifier 限制，安全可控，动态加载 | 网络、观测、安全策略 |
| ptrace/strace | 用户态调试接口，开销大，会影响被调试进程 | 开发和低频排查 |
| perf | 采样和性能事件强，适合 profiling | CPU 热点、火焰图、硬件事件 |
| ftrace | 内核内置 tracing 框架 | 内核函数追踪、调度和延迟排查 |

简单理解：内核模块是“把代码放进内核”，能力强但危险；eBPF 是“把受验证的小程序挂到内核事件点”，能力受限但更安全；perf/ftrace 偏观测，eBPF 既能观测也能在特定路径上做策略和转发。

## 12. 真实场景怎么回答

### 12.1 排查线上延迟

如果线上 RPC P99 延迟突然升高，可以用 eBPF 追踪：

1. `tcp_retransmit_skb` 看 TCP 重传是否增加。
2. syscall tracepoint 看 `send/recv/connect/accept` 耗时。
3. off-CPU 分析看线程是否被调度、锁或 I/O 阻塞。
4. uprobe 挂业务库函数，看 RPC 序列化、压缩、数据库调用耗时。

### 12.2 高性能负载均衡

L4 负载均衡可以在 XDP/tc 层做：

1. XDP 早期解析五元组。
2. 查 BPF map 得到后端。
3. 修改目的地址或重定向到出口。
4. 统计每个后端流量和丢包。

这样比用户态代理少走很多协议栈路径，但也要处理健康检查、会话保持、回退和可观测性。

### 12.3 容器网络策略

Kubernetes 中可以让 agent 监听 Pod、Service、NetworkPolicy 变化，把规则写入 BPF maps。数据包经过 tc/cgroup hook 时，eBPF 程序查 map 决定允许、拒绝、NAT 或转发。

优势是查表路径短、策略更新快、可观测性强；代价是对内核版本、调试能力和团队运维水平要求更高。

## 13. 易错点

1. BPF 不等于 eBPF。经典 BPF 主要用于包过滤，eBPF 是通用内核可编程框架。
2. eBPF 不等于内核模块。eBPF 受 verifier、helper、程序类型和上下文限制。
3. eBPF 不一定绕过协议栈。XDP 很早，tc 在 qdisc 附近，tracepoint/kprobe 是观测点，位置不同。
4. eBPF 不是只用于网络。它也广泛用于 tracing、安全、性能分析和容器观测。
5. verifier 通过不代表业务逻辑正确，只代表内核认为程序安全。
6. map 操作和事件输出不是免费的，高频场景要采样、聚合和限速。
7. kprobe 依赖内核函数实现，跨版本稳定性不如 tracepoint。
8. 生产环境要控制 eBPF 加载权限，不能让任意用户加载程序。

## 14. 面试回答模板

BPF 最早是 Berkeley Packet Filter，用于把抓包过滤程序放到内核里执行，避免无关数据包复制到用户态。eBPF 是它的扩展版本，变成了 Linux 内核里的安全可验证虚拟机和可编程框架。用户态用 clang/LLVM 把程序编译成 eBPF 字节码，通过 `bpf()` 系统调用加载；内核 verifier 会检查内存访问、循环、指针和 helper 使用是否安全，通过后解释执行或 JIT 成机器码，并 attach 到 XDP、tc、tracepoint、kprobe、uprobe、cgroup、LSM 等 hook 点。

eBPF 的核心机制包括 verifier、JIT、helper、BPF maps 和 hook。maps 用来保存状态和用户态通信，例如计数器、连接表、策略表；helper 是内核开放的受控能力；hook 决定程序什么时候执行。应用上，网络方向可以用 XDP/tc 做 DDoS 过滤、L4 负载均衡、容器网络和流量统计；可观测性方向可以追踪系统调用、TCP 重传、调度延迟、文件 I/O 和用户态函数；安全方向可以做运行时审计、容器逃逸检测和访问控制。

工程上我会强调 eBPF 不是万能的。它受 verifier、内核版本、权限、程序类型和性能开销限制。临时排查可以用 bpftrace/BCC，生产能力更适合 libbpf + CO-RE；高频路径要用 per-CPU map、采样和限速，网络 datapath 要有监控、灰度和 fallback。
