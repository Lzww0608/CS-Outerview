# 5. eBPF 观测数据库连接打满

能不能通过 BPF/eBPF 发现数据库连接是否打满？答案是：**可以发现很多连接打满的外部证据和内核侧信号，但不能只靠 eBPF 直接等价判断 MySQL 的 `max_connections` 已经打满。eBPF 更适合做无侵入观测：统计连接建立、accept、close、RST、连接耗时、客户端等待、错误码和网络状态；最终结论要和数据库内部指标 `Threads_connected`、`Threads_running`、`Max_used_connections`、`Connection_errors_max_connections`、`SHOW PROCESSLIST` 联动。**

简单说，eBPF 能回答：

1. 谁在连数据库。
2. 连了多少。
3. 建连是否变慢。
4. 是否大量连接失败、RST、超时。
5. 是客户端连不上，还是数据库 accept 慢，还是应用连接池耗尽。

但 eBPF 不能天然知道：

1. MySQL 的 `max_connections` 配置是多少。
2. 当前 MySQL 内部 `Threads_connected` 的精确语义。
3. 某个连接处于 MySQL `Sleep`、`Query`、锁等待还是事务状态。
4. MySQL 为什么拒绝连接，是账号限制、认证失败、连接上限还是其他错误。

这些需要 MySQL 指标、performance_schema、慢 SQL、连接池指标一起判断。

## 1. 数据库连接打满有哪些层次

“数据库连接打满”至少有三层含义：

| 层次 | 现象 | 典型指标 |
| --- | --- | --- |
| 应用连接池打满 | 应用拿不到连接，等待或超时 | HikariCP active/pending/timeout |
| MySQL 连接上限打满 | MySQL 无法接受更多普通连接 | `Too many connections`、`Threads_connected ~= max_connections` |
| 内核网络队列或 socket 压力 | TCP 建连慢、accept 队列堆积、RST/超时 | SYN/ESTABLISHED 数、accept 延迟、listen overflow |

eBPF 主要覆盖第三层，也能部分覆盖第一层和第二层的外部表现：

1. 通过内核网络 hook 看到 TCP 连接生命周期。
2. 通过 syscall tracepoint 看到 `connect()`、`accept()`、`close()`、`read()`、`write()` 的耗时和错误。
3. 通过 uprobe 观察用户态 MySQL 客户端库或连接池函数。
4. 通过进程、cgroup、容器维度聚合出是谁制造连接。

## 2. 可以观测哪些信号

### 2.1 客户端 connect 行为

对应用进程挂 syscall tracepoint：

```text
tracepoint:syscalls:sys_enter_connect
tracepoint:syscalls:sys_exit_connect
```

可以统计：

1. 每个进程向数据库 IP:PORT 发起了多少 `connect()`。
2. `connect()` 成功率。
3. `connect()` 返回错误码，例如 `ECONNREFUSED`、`ETIMEDOUT`、`EINPROGRESS`。
4. 阻塞 `connect()` 耗时。
5. 非阻塞 `connect()` 后续是否成功，可以结合 TCP 状态事件或 `getsockopt(SO_ERROR)` 观察。

如果数据库连接数打满，客户端可能表现为：

1. 建连成功但随后收到 MySQL 握手错误包。
2. 建连变慢。
3. 被代理或数据库主动关闭。
4. 应用连接池不再创建新连接，而是在本地排队。

所以 `connect()` 失败不是唯一信号。MySQL 达到 `max_connections` 时，TCP 连接可能已经建立，MySQL 再返回 `Too many connections` 协议错误并关闭连接。

### 2.2 服务端 accept 行为

如果能在数据库主机上观测 mysqld，可以追踪：

```text
tracepoint:syscalls:sys_enter_accept4
tracepoint:syscalls:sys_exit_accept4
```

或 kprobe 内核函数：

```text
tcp_v4_syn_recv_sock
inet_csk_accept
```

可以统计：

1. mysqld 每秒 accept 多少新连接。
2. accept 是否返回错误。
3. accept 之后连接是否很快关闭。
4. accept 队列是否有溢出迹象。

注意：MySQL 连接打满不一定等于内核 accept 队列满。很多时候 TCP 层仍能建立连接，只是 mysqld 在应用层判断已超过连接上限，然后返回错误。

### 2.3 TCP 状态和连接数量

可以通过 eBPF 观测 TCP 状态变化：

```text
tracepoint:sock:inet_sock_set_state
```

重点统计数据库端口相关连接：

1. `SYN_SENT`：客户端正在建连。
2. `ESTABLISHED`：连接已建立。
3. `CLOSE_WAIT`：对端已关闭，本端未关闭。
4. `TIME_WAIT`：短连接频繁关闭。
5. `RESET` 或异常关闭。

如果数据库连接数接近上限，常见现象：

1. 到数据库端口的 `ESTABLISHED` 数量持续高位。
2. 某些应用源 IP 或 Pod 的连接数异常多。
3. 大量短连接导致 `TIME_WAIT` 增加。
4. 大量异常关闭、RST 或连接寿命很短。

### 2.4 MySQL 错误响应

MySQL `Too many connections` 是应用层协议错误，不是 TCP 错误。eBPF 在内核网络层只能看到字节流，默认不知道 MySQL 协议语义。

可选方案：

1. 在用户态采集 MySQL 指标，这是最稳妥的方式。
2. 用 uprobe 挂 MySQL 客户端库，例如 `mysql_real_connect`、`mysql_stmt_execute` 等函数，采集返回码。
3. 用 eBPF socket 层解析 MySQL 协议握手错误包，但复杂、脆弱，不建议作为常规方案。
4. 在应用连接池层暴露指标，例如 HikariCP、Druid、Go sql.DB。

面试里可以说：**eBPF 可以帮助捕捉网络和系统调用症状，但 MySQL 协议错误和内部连接状态最好由数据库和连接池指标直接给出。**

## 3. eBPF 方案整体架构

推荐架构：

```text
eBPF probes
  -> connect/accept/close/send/recv/tcp_state
  -> BPF maps 聚合 pid、comm、cgroup、src/dst、port、errno、latency
  -> ring buffer 输出异常事件
  -> 用户态 agent enrich 元数据：Pod、服务名、实例、数据库名
  -> Prometheus / 日志 / Trace
  -> 和 MySQL exporter、连接池指标关联
```

采集维度：

```text
client_service
client_pod
client_pid
client_ip
db_host
db_port
mysql_instance
errno
tcp_state
latency_bucket
```

最终看板可以展示：

1. 每个服务到 MySQL 的连接数。
2. 每个服务新建连接速率。
3. 每个服务连接失败率。
4. 连接生命周期分布。
5. 数据库端口 ESTABLISHED/TIME_WAIT/CLOSE_WAIT 数。
6. connect/accept 延迟。
7. MySQL `Threads_connected / max_connections`。
8. 连接池 active/pending/timeout。

## 4. 临时排查可以怎么做

### 4.1 先用传统命令确认现象

```bash
ss -antp '( sport = :3306 or dport = :3306 )'
ss -ant state established '( sport = :3306 or dport = :3306 )' | wc -l
ss -ant state time-wait '( sport = :3306 or dport = :3306 )' | wc -l
```

MySQL 内部：

```sql
SHOW VARIABLES LIKE 'max_connections';
SHOW STATUS LIKE 'Threads_connected';
SHOW STATUS LIKE 'Threads_running';
SHOW STATUS LIKE 'Max_used_connections';
SHOW STATUS LIKE 'Connection_errors%';
SHOW PROCESSLIST;
```

如果 `Threads_connected` 接近 `max_connections`，同时 `Connection_errors_max_connections` 增加，基本可以确认 MySQL 连接上限被打到。

### 4.2 用 bpftrace 观察 connect 错误

临时排查可以按进程统计 `connect()` 返回错误：

```bash
bpftrace -e '
tracepoint:syscalls:sys_exit_connect
/args->ret < 0/
{
  @[comm, args->ret] = count();
}'
```

这只能看到 syscall 返回错误。对非阻塞连接、MySQL 应用层拒绝、连接池等待，不能完整覆盖。

### 4.3 观察 TCP 状态变化

可以追踪 `inet_sock_set_state`，按数据库端口过滤并统计状态迁移。伪代码逻辑：

```text
on inet_sock_set_state:
  if sport == 3306 or dport == 3306:
    count by oldstate -> newstate, src, dst, pid/cgroup
```

重点看：

1. `SYN_SENT -> ESTABLISHED` 是否变慢。
2. `ESTABLISHED -> CLOSE_WAIT` 是否堆积。
3. `ESTABLISHED -> TIME_WAIT` 是否异常多。
4. RST 相关关闭是否增加。

### 4.4 观察短连接风暴

数据库连接打满常见原因是应用没有复用连接，频繁新建短连接。

eBPF 可以记录连接生命周期：

```text
connect success timestamp
-> close timestamp
-> lifetime = close - connect
-> 按 service/db 聚合生命周期分布
```

如果大量连接生命周期只有几十毫秒，同时新建连接 QPS 很高，说明可能没有正确使用连接池，或者连接池配置导致频繁创建销毁。

## 5. 生产级实现关注点

### 5.1 Hook 点选择

| 目标 | 推荐 hook |
| --- | --- |
| 统计客户端建连 | syscall tracepoint `connect` |
| 统计服务端 accept | syscall tracepoint `accept4` |
| 统计 TCP 状态 | tracepoint `sock:inet_sock_set_state` |
| 统计网络重传 | tracepoint `tcp:tcp_retransmit_skb` |
| 观察 MySQL 客户端错误 | uprobe MySQL client library 或应用连接池函数 |
| 容器维度关联 | cgroup id、network namespace、Kubernetes metadata |

tracepoint 通常比 kprobe 稳定，生产长期运行优先使用 tracepoint。kprobe 更灵活，但依赖内核函数名和结构体实现，跨版本风险更高。

### 5.2 数据结构

常见 BPF maps：

1. `Hash map`：保存连接四元组到开始时间。
2. `LRU hash`：跟踪大量连接，自动淘汰冷连接。
3. `Per-CPU array/hash`：高频计数，降低多核写竞争。
4. `Ring buffer`：只输出异常事件，例如连接失败、超长建连、RST。

不要每个包都上报用户态。数据库连接观测通常是连接级事件，不需要包级全量采集。

### 5.3 开销控制

1. 高频计数用 per-CPU map。
2. 只按数据库端口过滤，例如 3306、5432、6379。
3. 只输出异常事件或采样输出。
4. 聚合后定期上报指标，不要每个连接都写日志。
5. 对高基数字段做限制，例如客户端 IP、SQL 文本不要直接放进 map。

### 5.4 权限和部署

生产环境加载 eBPF 通常需要较高权限：

1. 新内核可使用 `CAP_BPF`、`CAP_PERFMON`。
2. 旧内核可能需要 `CAP_SYS_ADMIN`。
3. 容器里要考虑 privileged、bpffs、BTF、内核版本。
4. 要限制谁能加载 eBPF，避免观测能力变成攻击面。

## 6. 如何判断“数据库连接打满”

建议用组合规则，而不是单一信号。

### 6.1 明确打满

满足以下条件，可以判定 MySQL 连接上限打满：

```text
Threads_connected / max_connections > 90% 或接近 100%
AND Connection_errors_max_connections 增加
AND 应用报 Too many connections 或连接池获取连接失败
```

eBPF 可补充：

```text
数据库端口 ESTABLISHED 连接数高位
新建连接失败或短连接异常增加
客户端 connect/close/RST 异常
```

### 6.2 连接池打满但数据库没满

如果：

```text
应用连接池 active 接近 maximumPoolSize
pending/timeout 增加
MySQL Threads_connected 远低于 max_connections
```

说明是应用连接池、线程池、慢 SQL 或连接泄漏问题，不是 MySQL 全局连接上限打满。

eBPF 可补充：

1. 应用进程是否还在创建新连接。
2. 已有连接是否长时间不关闭。
3. 应用线程是否卡在 futex、socket read/write、DNS、TLS 等位置。

### 6.3 网络队列或内核瓶颈

如果：

```text
connect 耗时升高
SYN_SENT/SYN_RECV 增加
accept 队列溢出
重传增加
MySQL Threads_connected 未接近 max_connections
```

那更可能是网络、内核队列、负载均衡或数据库主机压力问题，而不是连接上限。

## 7. 和 MySQL 指标如何联动

推荐告警规则：

```text
MySQL:
  Threads_connected / max_connections > 0.85 持续 5 分钟
  OR Connection_errors_max_connections 增加

App:
  connection_pool_pending > 0
  OR connection_pool_timeout 增加

eBPF:
  db_connect_error_rate 增加
  OR db_new_connection_rate 异常升高
  OR db_established_connections 高位
  OR db_connection_lifetime_p50 过短
```

组合解释：

| MySQL 指标 | 应用指标 | eBPF 指标 | 结论 |
| --- | --- | --- | --- |
| 连接接近上限 | 连接池超时 | ESTABLISHED 高 | MySQL 连接上限可能打满 |
| 连接未满 | 连接池 pending 高 | 建连不多 | 应用连接池太小或连接泄漏 |
| 连接未满 | 请求超时 | connect 慢、重传高 | 网络或主机压力 |
| 连接高 | Sleep 多 | 连接寿命长 | 空闲连接过多或连接池过大 |
| 连接高 | 慢 SQL 高 | 连接占用时间长 | 慢查询/锁等待导致连接堆积 |

## 8. 真实场景排查路径

线上告警：接口大量报数据库连接超时。

排查顺序：

1. 看应用连接池：active、idle、pending、timeout。
2. 看 MySQL：`Threads_connected`、`max_connections`、`Threads_running`、`Connection_errors_max_connections`。
3. 看 eBPF 连接视图：哪个服务、Pod、IP 对数据库连接数最多。
4. 看新建连接速率：是否短连接风暴。
5. 看连接生命周期：是否连接创建后很快关闭。
6. 看 TCP 状态：是否 CLOSE_WAIT/TIME_WAIT/SYN_SENT 异常。
7. 看 MySQL processlist：Sleep 多、Query 多还是锁等待多。
8. 看慢 SQL 和锁等待：是否请求执行变慢导致连接占用时间变长。

止血：

1. 限流高风险接口。
2. 暂停报表、导出、批任务。
3. 隔离连接暴涨的服务实例。
4. kill 明确异常的长查询或长事务。
5. 谨慎临时调大 `max_connections`，前提是 CPU、内存、线程调度还能承受。

长期治理：

1. 统一连接池预算。
2. 优化慢 SQL 和索引。
3. 修复连接泄漏。
4. 控制短连接，强制连接池复用。
5. 读写分离或拆分高成本查询。
6. 建立 eBPF + MySQL + 应用连接池的联合看板。

## 9. eBPF 的边界和风险

1. eBPF 看到的是内核事件，不天然理解 MySQL 业务语义。
2. MySQL 的 `Too many connections` 是应用层协议错误，不能只靠 TCP 状态推断。
3. uprobe MySQL 客户端库依赖符号、版本、静态链接和语言运行时，维护成本更高。
4. 连接数等于 socket 连接数，不等于 MySQL 内部线程状态。
5. 高基数连接追踪会消耗 map 内存，要使用 LRU、采样和聚合。
6. 生产加载 eBPF 要控制权限、灰度和回滚。
7. 如果部署在客户端节点，只能看到客户端视角；部署在数据库节点，才能看到数据库主机所有入站连接。

## 10. 面试回答模板

可以通过 eBPF 辅助发现数据库连接是否打满，但不能只靠 eBPF 下最终结论。eBPF 能在不改业务代码的情况下观测内核和用户态事件，比如客户端 `connect()` 成功率和耗时、服务端 `accept()`、TCP 状态迁移、到 3306 端口的 `ESTABLISHED/TIME_WAIT/CLOSE_WAIT` 数量、RST、重传、连接生命周期，以及哪个进程、Pod、服务在大量连接数据库。这些信息能帮助判断是短连接风暴、连接泄漏、网络异常，还是数据库端连接堆积。

但 MySQL 连接是否真正打满，要结合数据库内部指标确认，比如 `max_connections`、`Threads_connected`、`Threads_running`、`Max_used_connections`、`Connection_errors_max_connections` 和 `SHOW PROCESSLIST`。因为 MySQL 达到连接上限时，TCP 层可能已经连上了，只是 MySQL 在应用层返回 `Too many connections` 后关闭连接；eBPF 在网络层只能看到连接建立和关闭，不一定知道 MySQL 协议语义。

工程方案上，我会用 eBPF 采集 connect/accept/tcp_state 事件，按服务、Pod、进程、数据库实例聚合新建连接速率、当前连接数、连接失败率和连接生命周期；同时接入 MySQL exporter 和应用连接池指标。告警时如果 `Threads_connected` 接近 `max_connections`，`Connection_errors_max_connections` 增加，应用连接池 pending/timeout 上升，并且 eBPF 看到数据库端口连接数高位或新建连接异常，就可以判断连接上限或连接堆积问题。再根据 eBPF 找到主要来源服务，结合 processlist、慢 SQL 和锁等待定位根因。
