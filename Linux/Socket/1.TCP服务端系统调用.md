# TCP 服务端系统调用

TCP 服务端从启动监听到处理连接，核心是围绕 socket fd 做一组系统调用。面试里要把监听 fd 和连接 fd 区分清楚：监听 fd 只负责接收新连接，`accept` 返回的连接 fd 才用于和某个客户端读写数据。

## 基本调用链

```cpp
int listen_fd = socket(AF_INET, SOCK_STREAM | SOCK_NONBLOCK | SOCK_CLOEXEC, 0);

setsockopt(listen_fd, SOL_SOCKET, SO_REUSEADDR, &on, sizeof(on));

sockaddr_in addr{};
addr.sin_family = AF_INET;
addr.sin_addr.s_addr = htonl(INADDR_ANY);
addr.sin_port = htons(8080);

bind(listen_fd, reinterpret_cast<sockaddr*>(&addr), sizeof(addr));
listen(listen_fd, SOMAXCONN);

int epfd = epoll_create1(EPOLL_CLOEXEC);
epoll_ctl(epfd, EPOLL_CTL_ADD, listen_fd, &ev);

for (;;) {
    int n = epoll_wait(epfd, events, 1024, -1);
    for (int i = 0; i < n; ++i) {
        if (events[i].data.fd == listen_fd) {
            for (;;) {
                int conn = accept4(listen_fd, nullptr, nullptr,
                                   SOCK_NONBLOCK | SOCK_CLOEXEC);
                if (conn < 0 && (errno == EAGAIN || errno == EWOULDBLOCK)) {
                    break;
                }
                epoll_ctl(epfd, EPOLL_CTL_ADD, conn, &conn_ev);
            }
        } else {
            // 对连接 fd 做 recv/send，维护输入输出缓冲区
        }
    }
}
```

## TCP 客户端基本调用链

客户端和服务端的区别在于它主动发起连接，核心流程通常是：

```cpp
addrinfo hints{};
hints.ai_family = AF_UNSPEC;
hints.ai_socktype = SOCK_STREAM;

addrinfo* res = nullptr;
getaddrinfo("example.com", "443", &hints, &res);

int fd = socket(res->ai_family, res->ai_socktype | SOCK_NONBLOCK | SOCK_CLOEXEC,
                res->ai_protocol);

int ret = connect(fd, res->ai_addr, res->ai_addrlen);
if (ret < 0 && errno == EINPROGRESS) {
    // 把 fd 加入 epoll，监听 EPOLLOUT
}

int err = 0;
socklen_t len = sizeof(err);
getsockopt(fd, SOL_SOCKET, SO_ERROR, &err, &len);
if (err == 0) {
    // 连接建立成功，后续 send/recv
}

freeaddrinfo(res);
```

注意点：

1. `getaddrinfo()` 可能阻塞，客户端库常配合 DNS 缓存、异步解析或连接预热使用。
2. 非阻塞 `connect()` 返回 `EINPROGRESS` 不代表失败，只表示握手正在进行。
3. `epoll` 监听到可写后，必须用 `getsockopt(SO_ERROR)` 判断连接是否真的成功。
4. 客户端也要处理部分写、半包、超时、重连和连接池复用，不能把“连接建立成功”等同于“请求一定成功”。

## 每个调用做什么

1. `socket()`：创建套接字，返回监听 fd。
2. `setsockopt()`：设置端口复用、发送/接收缓冲区、`TCP_NODELAY`、`SO_KEEPALIVE` 等选项。
3. `bind()`：把监听 fd 绑定到本地 IP 和端口。
4. `listen()`：把主动 socket 转为监听 socket，并设置已完成连接队列长度。
5. `accept()/accept4()`：从已完成连接队列取出一个连接，返回新的连接 fd。
6. `recv()/read()`：从连接 fd 读取字节流。
7. `send()/write()`：向连接 fd 写数据。
8. `shutdown()`：半关闭连接，例如关闭写方向但仍接收数据。
9. `close()`：关闭 fd，引用计数归零后释放内核 socket 对象。

## 系统调用和 TCP 状态的关系

应用调用 socket API，真正的 TCP 状态转换主要由内核协议栈完成。面试里可以把“函数调用”和“TCP 状态”分开说：

| 阶段 | 典型函数 | 主要状态或队列 |
| --- | --- | --- |
| 创建 socket | `socket()` | 创建 fd，尚未绑定 TCP 连接 |
| 绑定地址 | `bind()` | 监听端记录本地 IP/端口 |
| 进入监听 | `listen()` | `LISTEN`，准备接收 SYN |
| 客户端发起连接 | `connect()` | 客户端 `SYN_SENT` |
| 服务端收到 SYN | 内核协议栈处理 | 服务端 `SYN_RCVD`，进入半连接队列 |
| 握手完成 | 客户端 ACK 到达 | 服务端连接进入全连接队列 |
| 应用取连接 | `accept()` | 返回已建立连接 fd，双方通常为 `ESTABLISHED` |
| 数据收发 | `send()/recv()` | 仍处于 `ESTABLISHED` 或半关闭状态 |
| 半关闭 | `shutdown(SHUT_WR)` | 本端发送 FIN，进入挥手流程 |
| 完全关闭 | `close()` | 可能进入 `FIN_WAIT_1/CLOSE_WAIT/LAST_ACK/TIME_WAIT` 等状态 |

注意点：

1. `accept()` 不是三次握手的一步，它只是从全连接队列取出已经建立好的连接。
2. `connect()` 在阻塞模式下可能等待握手完成；非阻塞模式下通常返回 `EINPROGRESS`，后续通过可写事件和 `SO_ERROR` 判断结果。
3. `close()` 不一定立刻让 TCP 连接消失，主动关闭方可能进入 `TIME_WAIT`。
4. 服务端大量 `CLOSE_WAIT` 通常是应用没有及时关闭连接；大量 `SYN_RCVD` 可能和突发连接、SYN flood 或半连接队列压力有关。

## 哪些 socket 函数可能阻塞

是否阻塞取决于 fd 是否设置 `O_NONBLOCK`、缓冲区状态、协议状态和 socket 选项。常见情况如下：

| 调用 | 阻塞条件 | 非阻塞表现 |
| --- | --- | --- |
| `connect()` | 三次握手未完成，要等待成功、失败或超时 | 返回 `-1`，`errno=EINPROGRESS`，后续监听可写并用 `getsockopt(SO_ERROR)` 判断结果 |
| `accept()` | 全连接队列为空 | 返回 `-1`，`errno=EAGAIN/EWOULDBLOCK` |
| `recv()/read()` | 接收缓冲区为空，且对端未关闭 | 返回 `-1`，`errno=EAGAIN/EWOULDBLOCK` |
| `send()/write()` | 发送缓冲区满，暂时无法写入更多数据 | 返回已写字节数，或 `-1` + `EAGAIN/EWOULDBLOCK` |
| `epoll_wait()` | 没有就绪事件且 timeout 不为 0 | timeout 为 0 时立即返回 |
| `close()` | 默认通常不阻塞；若设置 `SO_LINGER` 且有未发送数据，可能等待发送或超时 | 受 `SO_LINGER` 配置影响 |

`socket()`、`bind()`、`listen()` 通常不会因为网络数据等待而长期阻塞，但仍可能因为资源不足、端口占用、权限不足等立即失败。还有一个容易忽略的点：`getaddrinfo()` 不是 socket 系统调用，但 DNS 解析可能阻塞，客户端建连链路里也要考虑异步解析或缓存。

工程建议：

1. 高并发服务端统一使用非阻塞 fd，所有 I/O 状态交给 epoll 和应用层缓冲区管理。
2. 阻塞 I/O 简单但一连接一线程成本高，连接数大时会被线程栈、调度和阻塞等待拖垮。
3. 非阻塞 `send/recv` 必须处理部分读写和 `EAGAIN`，不能把一次系统调用等同于一条完整消息。

## 配合 epoll 的服务端流程

1. 监听 fd 设置为非阻塞并加入 epoll。
2. 监听 fd 可读表示有新连接可以 `accept`。
3. ET 模式下要循环 `accept4`，直到返回 `EAGAIN`。
4. 新连接 fd 设置非阻塞，加入 epoll 监听 `EPOLLIN`。
5. 可读事件到来后循环 `recv` 到 `EAGAIN`，把数据放入输入缓冲区。
6. 应用层按协议解析完整消息，生成响应。
7. 输出缓冲区非空时关注 `EPOLLOUT`。
8. 可写事件到来后循环 `send`，写完后取消 `EPOLLOUT`。
9. 连接异常、对端关闭、协议错误或超时后清理 fd、缓冲区和业务状态。

## 队列和 backlog

TCP 服务端涉及两个队列：

1. **半连接队列**：收到 `SYN`、回复 `SYN+ACK` 后，等待客户端最后 ACK。
2. **全连接队列**：三次握手完成后，等待应用调用 `accept` 取走。

`listen(backlog)` 主要影响全连接队列长度，半连接队列还受内核参数影响。服务端压测时如果 `accept` 不及时，客户端可能看到连接超时或拒绝。

### 半连接队列满了怎么办

半连接队列保存的是收到 `SYN`、已经回复 `SYN+ACK`、但还没有收到最后 ACK 的连接。它满了以后，新来的 `SYN` 可能被丢弃、延迟处理，或者在开启 SYN Cookie 时不再占用队列，而是把状态编码到 `SYN+ACK` 的序列号中，等客户端 ACK 回来再还原连接状态。具体行为受内核版本和参数影响，不能只用应用层 `accept` 速度解释。

常见处理手段：

1. **增大队列容量**：调整 `net.ipv4.tcp_max_syn_backlog`，同时关注 `listen(backlog)`、`net.core.somaxconn` 和应用 accept 速度，避免半连接队列和全连接队列都成为瓶颈。
2. **开启 SYN Cookie**：`net.ipv4.tcp_syncookies=1` 可以在 SYN flood 时保护半连接队列，但会牺牲部分 TCP 选项能力，不能替代正常容量规划。
3. **缩短异常半连接占用时间**：结合 `tcp_synack_retries` 控制 SYN+ACK 重传次数，减少伪造源地址或不可达客户端长期占用队列。
4. **入口层防护**：用四层负载均衡、高防、SYN proxy、ACL、连接速率限制把异常流量挡在业务机器前面。
5. **观测指标**：通过 `ss -ant state syn-recv`、`netstat -s`、SYN retransmit、连接超时率和 accept 队列溢出指标判断是突发正常流量还是攻击流量。

易错点：半连接队列满主要发生在握手完成前，应用还没有拿到连接 fd；`accept` 加速消费的是全连接队列，不能直接消费半连接队列。真正的工程方案通常是“内核参数 + SYN Cookie + 入口限流 + accept 及时消费”一起做。

## accept 和三次握手的关系

`accept` 不负责完成三次握手。三次握手主要由内核 TCP 协议栈处理：

```text
1. 客户端发 SYN
2. 服务端内核回 SYN+ACK，连接进入半连接队列
3. 客户端回 ACK
4. 服务端内核把连接放入全连接队列
5. 应用调用 accept，从全连接队列取出连接 fd
```

因此：

1. 连接可能已经完成三次握手，但应用还没 `accept`。
2. `accept` 返回时，拿到的是一个已经建立好的连接 fd。
3. 如果全连接队列满，新的握手完成连接可能被丢弃或触发重传，具体行为受内核参数影响。

## 建立连接还有哪些方式和优化

面试里问“建立连接还有其他方式吗”，可以从客户端、服务端和协议优化三层回答。

客户端侧：

1. **阻塞 `connect`**：调用线程等待三次握手完成或失败，简单但会阻塞。
2. **非阻塞 `connect`**：socket 设为非阻塞，`connect` 返回 `EINPROGRESS`，再用 `epoll` 监听可写，并通过 `getsockopt(SO_ERROR)` 判断连接结果。
3. **连接池**：提前建立并复用连接，减少每次请求的握手成本，数据库、RPC、HTTP 客户端常用。
4. **预连接**：预测后续会访问的目标，提前建立连接，例如浏览器或网关对热点 upstream 做预热。

协议侧：

1. **HTTP Keep-Alive**：复用同一 TCP 连接发送多个请求，减少重复握手。
2. **TCP Fast Open**：允许在 SYN 中携带数据，降低首次请求延迟，但依赖系统和中间网络支持。
3. **TLS 1.3 0-RTT/会话恢复**：减少安全握手成本，但要注意重放风险。
4. **QUIC 连接迁移和 0-RTT**：基于 UDP，在用户态实现连接标识和快速恢复。

服务端侧：

1. **accept 分发**：多 worker 可通过 accept mutex、`SO_REUSEPORT`、master accept 后传 fd、负载均衡层分发连接。
2. **backlog 和内核参数**：调整全连接队列、半连接队列和 SYN cookie，避免突发连接打满队列。
3. **限流和握手保护**：对异常来源、SYN flood、连接速率做限制，保护 accept 队列和 worker。

## accept 什么时候会阻塞

1. **阻塞监听 fd**：全连接队列为空时，`accept` 会阻塞，直到有新连接或被信号打断。
2. **非阻塞监听 fd**：全连接队列为空时，`accept` 立即返回 `-1`，`errno` 为 `EAGAIN/EWOULDBLOCK`。
3. **epoll LT 模式**：监听 fd 可读但没有一次取完，下次还会通知。
4. **epoll ET 模式**：监听 fd 可读后必须循环 `accept` 到 `EAGAIN`，否则可能遗漏队列中已有连接。

队列由内核维护，应用只通过 `listen(backlog)`、内核参数和及时 `accept` 来影响队列容量和消费速度。

## listen 返回 -1 的原因

`listen(fd, backlog)` 返回 `-1` 时要看 `errno`。它不是网络对端导致的失败，而是当前 socket 状态、参数或系统资源不满足监听要求。

常见原因：

| errno | 典型含义 | 场景 |
| --- | --- | --- |
| `EBADF` | fd 不是有效文件描述符 | fd 未创建、已经关闭、变量被覆盖 |
| `ENOTSOCK` | fd 不是 socket | 把普通文件 fd 传给 `listen` |
| `EOPNOTSUPP` | socket 类型不支持监听 | UDP socket 或不支持 listen 的类型 |
| `EINVAL` | socket 状态或参数不合法 | 未正确创建、重复状态错误、backlog 不合法等 |
| `EADDRINUSE` | 地址已经被占用 | 未设置 `SO_REUSEADDR/SO_REUSEPORT`，或端口已有监听者 |
| `EACCES` | 权限不足 | 普通用户监听低端口，或安全策略限制 |
| `ENOBUFS/ENOMEM` | 内核资源不足 | socket 缓冲区、内核内存或队列资源不足 |

排查顺序：

1. 检查调用链是否完整：`socket -> setsockopt -> bind -> listen`。
2. 打印 `errno` 和 `strerror(errno)`，不要只看返回值。
3. 用 `ss -lntp` 或 `netstat -lntp` 检查端口是否已被占用。
4. 检查监听端口是否小于 1024，以及进程是否有权限。
5. 检查 `somaxconn`、fd 上限、进程资源限制和容器限制。
6. 确认传入的是 `SOCK_STREAM` 这类面向连接的 socket。

面试回答可以说：`listen` 返回 `-1` 要结合 `errno` 判断，常见有 fd 无效、不是 socket、socket 类型不支持、地址端口被占用、权限不足、参数或状态不合法、内核资源不足。工程上会先打印 errno，再检查 bind 是否成功、端口占用、权限、backlog 和内核参数。

## `write/send` 成功返回后数据在哪里

对 TCP socket 调用 `write()` 或 `send()` 成功返回，只表示数据已经被内核接收，通常进入了该 socket 的发送缓冲区，不表示对端应用已经收到。

简化链路：

```text
用户态 buffer
  -> 内核 socket 发送缓冲区
  -> TCP 协议栈分段、排队、重传
  -> 网卡队列
  -> 网络传输
  -> 对端内核接收缓冲区
  -> 对端应用 read/recv
```

需要区分几个语义：

1. `send` 返回 `n > 0`：内核接受了 `n` 字节，应用可以复用或释放这段用户态 buffer。
2. 返回值可能小于请求写入长度：说明只写入了一部分，应用层要记录写偏移，下次继续写。
3. 非阻塞 socket 如果发送缓冲区满，会返回 `EAGAIN/EWOULDBLOCK`。
4. 阻塞 socket 可能等待缓冲区可用，但也不保证一次写完所有数据。
5. 对端 ACK 后，发送缓冲区中已确认的数据才能被内核真正释放；如果丢包，TCP 会负责重传。
6. 如果对端关闭或网络异常，错误可能在后续 `send`、`recv`、`poll/epoll` 事件或 `getsockopt(SO_ERROR)` 中体现。

工程上，高并发服务一般维护应用层输出缓冲区：写不完就保存剩余数据，注册 `EPOLLOUT`，等 socket 可写后继续发送。不要把 `send` 成功误解成“消息已经被对端业务处理完成”。

## 易错点

1. `accept` 返回的是新的连接 fd，不要在监听 fd 上读写业务数据。
2. `listen` 之后还没有真正接收业务数据，真正数据在连接 fd 上。
3. 非阻塞 `send` 可能只写出一部分，必须维护写偏移。
4. TCP 是字节流，`recv` 一次返回的数据不等于一条完整业务消息。
5. `close` 只关闭本进程 fd；如果 fd 被复制或多线程共享，内核对象可能还没释放。
6. 高并发服务要设置 `FD_CLOEXEC`，避免 `exec` 后 fd 泄露到子进程。
7. `accept` 不是三次握手的一部分，它只是从内核全连接队列取连接。

## 面试回答模板

TCP 服务端通常先 `socket` 创建监听 fd，再 `setsockopt` 设置端口复用等参数，`bind` 绑定 IP/端口，`listen` 进入监听状态。三次握手由内核 TCP 协议栈完成，完成后的连接进入全连接队列；`accept` 只是从这个队列取出连接并返回新的连接 fd，后续用这个连接 fd 做 `recv/send`。阻塞监听 fd 在队列为空时会阻塞，非阻塞监听 fd 会返回 `EAGAIN`。高并发场景会把监听 fd 和连接 fd 都设为非阻塞，加入 `epoll`，监听 fd 可读时循环 `accept` 到 `EAGAIN`，连接 fd 可读可写时循环读写到 `EAGAIN`，并由应用层缓冲区解决半包、粘包和部分写问题。
