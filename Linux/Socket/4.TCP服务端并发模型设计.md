# 4. TCP 服务端并发模型设计

面试里问“怎么设计一个 TCP 模型”，通常不是只问 TCP 协议本身，而是问一个服务端从监听、接收连接、读写数据、业务处理到关闭连接的整体并发模型。

## 1. 基本链路

一个 TCP 服务端的主链路是：

```text
socket
-> setsockopt
-> bind
-> listen
-> accept
-> recv/read
-> 业务处理
-> send/write
-> close
```

高并发场景会把监听 fd 和连接 fd 都设置为非阻塞，再交给 I/O 多路复用器管理：

```text
listen_fd 加入 epoll
-> listen_fd 可读，循环 accept4 到 EAGAIN
-> conn_fd 设置非阻塞，加入 epoll
-> conn_fd 可读，循环 recv 到 EAGAIN
-> 应用层缓冲区解析协议
-> 生成响应，先直接 send
-> 写不完就打开 EPOLLOUT，写完后关闭 EPOLLOUT
```

## 2. 单线程还是多线程

选择单线程还是多线程，要看连接数、业务耗时和机器资源。

| 模型 | 特点 | 适用场景 | 风险 |
| --- | --- | --- | --- |
| 阻塞 I/O + 单线程 | 实现最简单 | 教学、小工具、低并发客户端 | 一个连接阻塞会拖住全部请求 |
| 一连接一线程 | 编程直观 | 连接数少、业务阻塞多的内部工具 | 线程栈、调度和上下文切换成本高 |
| 单 Reactor 单线程 | 一个事件循环负责 accept/read/write/业务 | Redis 这类内存操作很快的服务 | 慢业务会阻塞所有连接 |
| 单 Reactor + 线程池 | I/O 线程分发事件，worker 做业务 | 简单 WebServer、RPC demo | 多线程访问连接对象要设计同步 |
| 主从 Reactor 多线程 | accept 和连接 I/O 分散到多个 EventLoop | 高并发长连接服务 | 连接归属、跨线程唤醒和生命周期更复杂 |
| Master/Worker 多进程 | 多进程隔离，worker 独立事件循环 | Nginx、代理、网关 | 进程间共享状态成本高 |

工程上常见答案是：Linux 后端服务用 `epoll + 非阻塞 socket + Reactor + 线程池`。I/O 线程只做轻量读写、协议解析和事件分发，耗时业务、磁盘 I/O、数据库访问放到业务线程池。

## 3. 推荐模型：one loop per thread

`one loop per thread` 是 C++ 网络库常见模型：

```text
主 EventLoop
  -> accept 新连接
  -> 选择一个子 EventLoop
  -> 把 conn_fd 投递给该子 EventLoop

子 EventLoop
  -> epoll_wait
  -> 处理该 loop 负责的连接读写
  -> 必要时把业务投递到 worker pool
  -> 业务完成后投递回所属 loop 写响应
```

核心原则：

1. 一个连接固定归属一个 I/O 线程，输入缓冲区、输出缓冲区和连接状态尽量只在该线程访问。
2. 其他线程不要直接改连接 fd 的 epoll 事件，而是投递任务到连接所属 EventLoop。
3. 跨线程唤醒可以用 `eventfd`、pipe 或条件变量。
4. 业务线程池不要持有裸 fd 长时间操作，避免 fd 关闭和复用导致误写。
5. 线程池队列要有上限，否则短时流量会转化为内存上涨和长尾延迟。

## 4. 怎么监听

监听不是只调用 `listen()`，还包括地址复用、backlog、非阻塞和事件注册：

```cpp
int fd = ::socket(AF_INET, SOCK_STREAM | SOCK_NONBLOCK | SOCK_CLOEXEC, 0);

int on = 1;
::setsockopt(fd, SOL_SOCKET, SO_REUSEADDR, &on, sizeof(on));

sockaddr_in addr{};
addr.sin_family = AF_INET;
addr.sin_addr.s_addr = htonl(INADDR_ANY);
addr.sin_port = htons(8080);

::bind(fd, reinterpret_cast<sockaddr*>(&addr), sizeof(addr));
::listen(fd, SOMAXCONN);

int epfd = ::epoll_create1(EPOLL_CLOEXEC);
epoll_event ev{};
ev.events = EPOLLIN;
ev.data.fd = fd;
::epoll_ctl(epfd, EPOLL_CTL_ADD, fd, &ev);
```

`listen()` 只是把 socket 转为监听状态，三次握手由内核协议栈完成。应用通过 `accept()` 从全连接队列取出已经建立好的连接。

## 5. 连接对象要保存什么

一个生产级连接对象至少要保存：

1. fd 和所属 EventLoop。
2. 输入缓冲区：处理半包、粘包和多包。
3. 输出缓冲区：处理部分写和慢客户端。
4. 协议状态机：例如读请求头、读 body、处理中、等待写回。
5. 超时时间和定时器节点。
6. 关闭状态：正常关闭、半关闭、错误关闭、等待写完关闭。
7. 业务上下文：trace id、用户 id、请求 id、限流状态等。

不要把一次 `recv` 当成一条完整消息，也不要把一次 `send` 当成完整响应已经发出。TCP 是字节流，消息边界必须由应用层协议定义。

## 6. 真实场景取舍

1. **连接少、业务简单**：阻塞 I/O 或 `select` 也能工作，代码简单。
2. **Linux 高并发长连接**：优先 `epoll + 非阻塞 + Reactor`。
3. **业务 CPU 重**：I/O 线程只读写，CPU 任务进入计算线程池。
4. **业务 I/O 阻塞多**：拆独立 I/O 线程池或使用异步客户端，避免 worker 被慢下游占满。
5. **极致性能网关**：考虑多 Reactor、`SO_REUSEPORT`、绑定 CPU、批量读写、零拷贝、内存池和协议解析优化。

## 7. 易错点

1. `accept` 返回的是连接 fd，监听 fd 不能用来收发业务数据。
2. ET 模式下监听 fd 可读后要循环 `accept4` 到 `EAGAIN`。
3. `EPOLLOUT` 不要一直监听，只有输出缓冲区非空时再打开。
4. 业务线程不能随意关闭 I/O 线程正在处理的 fd，要有统一关闭协议。
5. fd 数字会复用，连接对象最好带 generation 或生命周期保护。
6. 线程越多不一定越快，锁竞争、上下文切换和下游限额都可能成为瓶颈。

## 8. 面试回答模板

我会用非阻塞 socket 加 epoll 设计 TCP 服务端。启动时 `socket/bind/listen` 创建监听 fd，把监听 fd 加入 epoll；监听 fd 可读时循环 `accept4` 到 `EAGAIN`，新连接设置非阻塞并分配给某个 EventLoop。连接可读时循环 `recv` 到 `EAGAIN`，写入输入缓冲区并按协议状态机解析；业务如果耗时就投递到线程池，完成后回到连接所属 EventLoop 写响应。写响应时先直接 `send`，写不完就放入输出缓冲区并关注 `EPOLLOUT`，写完后关闭写事件。单线程适合业务很轻的场景，复杂后端通常用多 Reactor 或 Reactor 加线程池，但要保证连接归属清晰、队列有界、关闭和跨线程访问安全。
