# 5. Linux 网卡协议栈实现原理

面试里问“Linux 中网卡协议栈具体实现是什么，原理是什么”，不要只回答 TCP/IP 四层模型。更准确的回答应该把用户态 socket、内核协议栈、网络设备驱动、DMA、中断、软中断、`sk_buff`、`net_device`、队列、路由、Netfilter 和 qdisc 串起来。

一句话概括：**Linux 网络协议栈是内核中的分层 packet processing pipeline，向上通过 socket 给用户态提供 TCP/UDP 等接口，向下通过 `net_device` 和网卡驱动操作硬件，中间用 `sk_buff` 表示网络包，用软中断、NAPI、队列和协议处理函数完成收发包。**

## 1. 整体架构

Linux 网络路径可以按对象和层次理解：

```text
用户态应用
  -> socket API：send/recv、read/write、epoll
  -> socket 层：struct socket、struct sock、发送/接收缓冲区
  -> 传输层：TCP、UDP、ICMP、RAW
  -> 网络层：IPv4/IPv6、路由、分片、邻居子系统
  -> 二层：Ethernet、VLAN、Bridge、bond、macvlan
  -> qdisc/traffic control：排队、整形、调度
  -> net_device：网络设备抽象
  -> 网卡驱动：DMA ring、中断、NAPI、硬件 offload
  -> NIC 硬件和物理链路
```

核心抽象：

| 抽象 | 作用 |
| --- | --- |
| `struct socket` | BSD socket 层对象，面向系统调用语义。 |
| `struct sock` | 协议栈内部 socket 状态，例如 TCP 状态机、缓冲区、端口、队列。 |
| `struct sk_buff` | Linux 网络包核心结构，保存数据区、协议头偏移、设备、校验、路由等元信息。 |
| `struct net_device` | 网络设备抽象，代表物理网卡、虚拟网卡、loopback、veth、tun/tap 等。 |
| `net_device_ops` | 驱动向协议栈注册的操作集合，例如打开设备、发包、设置 MAC。 |
| NAPI | 中断和轮询结合的高性能收包机制，降低高包量下的中断风暴。 |
| qdisc | 发包队列规则，负责排队、调度、限速和丢弃策略。 |

## 2. 为什么网卡不是普通字符设备

字符设备通常通过 `/dev/xxx` 和 `read/write/ioctl` 直接和用户态交互；网卡不是这么工作的。网卡驱动注册的是 `net_device`，上层通过协议栈和 socket 收发。

原因：

1. 网络包需要经过 MAC、VLAN、IP、TCP/UDP、路由、防火墙、队列管理等多层处理。
2. 多个进程可以同时使用同一块网卡，靠端口、协议、命名空间和路由规则复用。
3. 网卡高频收发包，必须依赖 DMA、批处理、软中断和多队列，不适合普通文件读写模型。
4. 网络协议栈要统一支持物理网卡和虚拟设备，例如 `lo`、`veth`、`tun/tap`、bridge、bond。

所以用户态看到的是 socket fd，而不是直接读写网卡设备文件。

## 3. 收包路径

典型 TCP/UDP 收包路径：

```text
网卡收到以太网帧
  -> DMA 写入 RX ring 中的内存 buffer
  -> 网卡触发 MSI/MSI-X 中断
  -> 驱动中断处理函数关闭或抑制后续中断
  -> napi_schedule 把 NAPI poll 挂到 NET_RX softirq
  -> 软中断调用驱动 poll 函数批量取包
  -> 驱动为包构造 skb，并调用 napi_gro_receive/netif_receive_skb
  -> 二层处理：Ethernet、VLAN、Bridge、Netfilter PREROUTING
  -> 三层处理：IPv4/IPv6 校验、路由、本机投递或转发、分片重组
  -> 四层处理：TCP/UDP 根据端口和四元组找到 sock
  -> 数据放入 socket 接收缓冲区
  -> 唤醒等待队列，epoll ready list 产生可读事件
  -> 应用 recv/read，从内核拷贝到用户缓冲区
```

关键点：

1. **DMA**：网卡直接把数据写入内存，CPU 不逐字节搬运网卡数据。
2. **硬中断只做少量工作**：记录状态、屏蔽中断、调度 NAPI，避免在硬中断里做复杂协议处理。
3. **软中断批量处理**：`NET_RX` softirq 中轮询多个包，提高吞吐。
4. **`skb` 贯穿协议栈**：二层、三层、四层处理都围绕 `skb` 的指针和元数据推进。
5. **socket 缓冲区和 epoll 分离**：包到 socket 缓冲区后才可读，`epoll` 只是通知，不负责拷贝数据。

## 4. NAPI 的原理

早期模型是“一个包一个中断”，包量大时 CPU 会被中断打爆。NAPI（New API）的思路是中断和轮询结合：

```text
低流量：
  包到达 -> 中断 -> 立即调度处理

高流量：
  包到达 -> 第一次中断 -> 关闭该队列中断
  -> softirq 中 poll 一批包
  -> 如果一次 poll 没处理完，继续下轮 softirq
  -> 如果队列清空，再打开中断
```

NAPI 的收益：

1. 降低高 PPS 下的中断次数。
2. 批量构造和处理 `skb`，提高 cache 命中。
3. 允许驱动控制每次 poll 的预算，避免单个网卡长期霸占 CPU。

代价：

1. 高负载下包可能在队列里多等一小段时间。
2. 软中断如果集中在单核，会出现单核 `si` 很高。
3. 参数、队列数、RSS/RPS、irq affinity 配不好时，会造成收包不均衡。

## 5. `sk_buff` 是什么

`sk_buff` 简称 `skb`，是 Linux 网络协议栈里最核心的数据结构。它不是只有包内容，还包含包在协议栈中流转所需的元信息。

可以抽象为：

```text
struct sk_buff
  -> data/head/tail/end：数据缓冲区指针
  -> mac_header/network_header/transport_header：各层协议头偏移
  -> dev：当前关联的 net_device
  -> protocol：二层协议类型，例如 IPv4/IPv6/ARP
  -> len/data_len：包长度
  -> mark/priority/hash：路由、过滤、调度辅助信息
  -> ip_summed：校验和 offload 状态
  -> cb：协议栈临时控制块
```

为什么需要 `skb`：

1. 避免每层都重新分配对象。
2. 通过移动 header 指针完成封装和解封装。
3. 让驱动、协议栈、Netfilter、qdisc、socket 缓冲区都能传递同一个包对象。
4. 支持 clone、fragment、GSO/GRO 等优化。

易错点：`skb` 不是业务层 socket buffer 的简单等价物。它是单个网络包在内核里的描述结构；socket 接收缓冲区里可能排着多个 `skb`，TCP 还会把字节流按序重组后交给应用。

## 6. 发包路径

典型 TCP 发包路径：

```text
应用 send/write
  -> 系统调用进入内核
  -> socket 层把用户数据拷贝到内核发送缓冲区
  -> TCP 层按 MSS、窗口、拥塞控制切分 segment
  -> IP 层查路由，选择出口设备和下一跳
  -> 邻居子系统通过 ARP/ND 找下一跳 MAC
  -> Netfilter OUTPUT/POSTROUTING
  -> qdisc 排队和调度
  -> 驱动 ndo_start_xmit
  -> 把 skb 映射到 DMA，放入 TX ring
  -> 网卡 DMA 读取内存并发送到物理链路
  -> 发送完成中断或清理流程释放 skb
```

UDP 发包少了 TCP 状态机、重传和拥塞控制，但仍然要经过 IP、路由、邻居、qdisc、驱动和网卡。

关键点：

1. `send()` 返回成功通常表示数据进入内核发送缓冲区，不代表对端已经收到。
2. TCP 真正什么时候发包受 Nagle、拥塞窗口、接收窗口、MSS、TSO、qdisc 等影响。
3. 路由决定从哪个 `net_device` 出去；ARP/ND 决定下一跳 MAC。
4. qdisc 可以改变发包顺序、限速、排队和丢包行为。
5. 驱动只负责把已经经过协议栈封装的包交给硬件发送。

## 7. qdisc 和流量控制

qdisc（queueing discipline）位于协议栈和网卡驱动之间，控制发包排队和调度。

常见作用：

1. **排队**：网卡忙时临时缓存待发送 `skb`。
2. **调度**：不同 flow 或 class 按优先级、公平队列、令牌桶发送。
3. **限速**：例如 TBF、HTB。
4. **主动丢弃**：例如 fq_codel，降低 bufferbloat。
5. **多队列分发**：结合多队列网卡提高并行度。

面试中可以说：TCP 拥塞控制决定“协议认为能发多少”，qdisc 决定“本机出口队列怎么排队和什么时候交给网卡”。两者不是同一层。

## 8. Netfilter 在哪里

Netfilter 是 Linux 内核里的包过滤和修改框架，iptables/nftables 都基于它。

典型 hook 位置：

```text
收包：
  PREROUTING -> 路由判断 -> INPUT -> 本机 socket

转发：
  PREROUTING -> 路由判断 -> FORWARD -> POSTROUTING -> 出口网卡

本机发包：
  OUTPUT -> 路由/邻居 -> POSTROUTING -> 出口网卡
```

它可以做：

1. 包过滤和防火墙。
2. NAT，例如 DNAT、SNAT、MASQUERADE。
3. 连接跟踪 conntrack。
4. 标记包，配合策略路由或 qdisc。

高并发场景要注意 conntrack 表、iptables 规则数量、NAT 和防火墙规则都会增加协议栈处理成本。

## 9. 多队列、RSS、RPS、RFS

现代网卡通常有多个 RX/TX 队列，目标是让多个 CPU 并行处理网络包。

| 机制 | 作用 |
| --- | --- |
| RSS | 网卡硬件根据 hash 把不同流分到不同 RX queue。 |
| MSI-X | 每个队列可以有独立中断，方便绑定不同 CPU。 |
| irq affinity | 控制某个中断由哪些 CPU 处理。 |
| RPS | 软件层把收包处理分散到多个 CPU。 |
| RFS | 尽量把包分到运行对应应用线程的 CPU，提高 cache locality。 |
| XPS | 发包时按 CPU 或队列选择 TX queue。 |

真实服务里常见优化：

1. 网卡队列数接近 CPU 核数或 I/O 线程数。
2. 中断绑定到本地 NUMA 节点 CPU。
3. 网络 I/O 线程也绑定到同一 NUMA 节点。
4. 避免所有 `NET_RX` 软中断集中在 CPU0。
5. 对小包高 PPS 服务关注包处理能力，而不是只看带宽 Gbps。

## 10. 硬件 offload

Linux 协议栈和网卡硬件会配合做 offload，减少 CPU 工作。

常见能力：

| 能力 | 含义 |
| --- | --- |
| checksum offload | TCP/UDP/IP 校验和由网卡计算或验证。 |
| TSO | TCP Segmentation Offload，内核给大块数据，网卡切成多个 TCP 段。 |
| GSO | Generic Segmentation Offload，协议栈通用分段延后。 |
| LRO | Large Receive Offload，网卡接收侧聚合多个包。 |
| GRO | Generic Receive Offload，内核接收侧聚合多个包。 |
| VLAN offload | 网卡处理 VLAN tag 插入和剥离。 |

收益是减少 CPU 协议处理和包数量；风险是抓包看到的包可能和线上真实线缆上的包不完全一致，排查时要知道 offload 可能影响 tcpdump 现象。

## 11. 虚拟网卡和容器网络

Linux 协议栈不只服务物理网卡，也服务虚拟网络设备：

1. `lo`：回环设备，`127.0.0.1` 走协议栈但不经过物理网卡。
2. `veth pair`：成对虚拟网卡，常用于容器和 namespace 连接。
3. `bridge`：二层交换，Docker 默认 bridge 网络常见。
4. `tun/tap`：用户态虚拟网络设备，VPN 常用。
5. `bond/team`：多网卡聚合。
6. `macvlan/ipvlan`：让容器或虚拟机更像直接挂在物理网络上。

容器网络的本质是把不同 network namespace 的 `net_device`、路由表、iptables 和 bridge/veth 组合起来。应用仍然使用 socket，只是它看到的是自己 namespace 内的网卡、IP、路由和端口空间。

## 12. 常见性能瓶颈

| 位置 | 现象 | 排查方向 |
| --- | --- | --- |
| 网卡 RX ring 满 | 网卡统计里 rx_missed、rx_dropped 增加 | `ethtool -S`、调大 ring、提高处理能力 |
| 软中断过高 | `top` 里 `si` 高，单核打满 | `/proc/softirqs`、RSS/RPS、irq affinity |
| socket 接收队列堆积 | `ss -ntm` 看到 Recv-Q 增大 | 应用是否及时读、业务线程是否阻塞 |
| listen 队列溢出 | 连接建立慢或 reset | backlog、somaxconn、syn backlog、accept 速度 |
| TCP 重传高 | 延迟抖动、吞吐下降 | `ss -s`、`netstat -s`、抓包、链路质量 |
| qdisc 排队 | 出口延迟高 | `tc -s qdisc`、限速、队列策略 |
| conntrack 满 | 新连接失败、NAT 异常 | `nf_conntrack` 表大小、超时、规则优化 |
| NUMA 跨节点 | CPU 高、延迟长尾 | 中断、线程、内存和网卡所在 NUMA 对齐 |

常用命令：

```bash
ip link
ip addr
ip route
ss -ntm
ss -s
ethtool -S eth0
ethtool -k eth0
cat /proc/softirqs
mpstat -P ALL 1
tc -s qdisc show dev eth0
nstat
netstat -s
```

## 13. XDP 和 DPDK 的位置

传统 Linux 协议栈功能完整，但每个包要经过 `skb`、协议栈、Netfilter、qdisc、socket 等路径，小包极高 PPS 场景成本较高。

两类常见优化：

1. **XDP/eBPF**：在驱动收包很早的位置执行 eBPF 程序，可以快速丢包、转发、负载均衡或重定向，避免构造完整 `skb` 后再处理。
2. **DPDK**：绕过内核协议栈，用户态直接轮询网卡队列，适合极高性能转发、网关、NFV，但需要自己处理协议、内存、队列和 CPU 独占。

选择建议：

1. 普通后端服务优先使用内核协议栈，配合 epoll/io_uring、零拷贝、内核参数和队列调优。
2. DDoS 过滤、L4 负载均衡、包转发可以考虑 XDP。
3. 极限转发和专用网络设备可以考虑 DPDK。
4. 不要为了“高性能”过早绕过内核，运维、可观测性和协议完整性成本很高。

## 14. 易错点

1. `epoll` 不收包，它只监听 fd 就绪；真正收包的是网卡、驱动、协议栈和 socket 缓冲区。
2. `send()` 成功不代表包上了网卡，更不代表对端收到。
3. `127.0.0.1` 不经过物理网卡，但仍经过 TCP/IP 协议栈和 loopback 设备。
4. Unix Domain Socket 不经过完整 TCP/IP 协议栈，但仍然走内核 socket/IPC 路径。
5. 网卡驱动不是字符设备驱动的简单 `read/write`，它注册 `net_device` 并接入网络协议栈。
6. TCP 拥塞控制、qdisc 队列、网卡 ring、socket buffer 是不同层的队列，不要混为一谈。
7. offload 会改变抓包观察结果，排查校验和错误、大包时要注意 TSO/GSO/GRO。
8. 高带宽不等于高 PPS，小包场景瓶颈常在 CPU、软中断和 cache。

## 15. 面试回答模板

Linux 的网卡协议栈可以理解为内核里的分层包处理流水线。用户态通过 socket 系统调用进入内核，内核用 `struct socket` 和 `struct sock` 维护连接状态和收发缓冲；网络包在协议栈里主要用 `sk_buff` 表示；物理网卡或虚拟网卡通过 `net_device` 注册到内核，驱动负责 DMA ring、中断、NAPI 和硬件 offload。

收包时，网卡先把帧 DMA 到内存，然后触发中断；驱动通常只做很少工作并调度 NAPI，后续在 `NET_RX` 软中断里批量 poll 包，构造 `skb` 后进入二层、IP 层、TCP/UDP 层。TCP/UDP 根据端口和四元组找到对应 socket，把数据放入接收缓冲区，再唤醒等待队列，`epoll` 看到 fd 可读，应用最后调用 `recv/read` 拷贝到用户态。

发包时，应用 `send/write` 进入 socket 层，TCP/UDP 构造传输层报文，IP 层查路由和邻居表，经过 Netfilter、qdisc 后调用驱动的发送函数，把 `skb` 映射到 DMA 并放入 TX ring，网卡再从内存读取并发到链路上。工程排查时要分层看：网卡统计、软中断、协议栈计数、socket 队列、qdisc、conntrack 和应用是否及时读写。
