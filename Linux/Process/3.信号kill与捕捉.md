# 3. 信号、kill 与捕捉

Linux 信号是内核向进程或线程发送异步通知的机制。`kill` 命令名字虽然叫 kill，但本质是给进程发送信号。

## 1. kill 和 kill -9 的区别

```bash
kill <pid>      # 默认发送 SIGTERM，编号 15
kill -9 <pid>   # 发送 SIGKILL，编号 9
```

区别：

1. `SIGTERM` 是优雅退出请求，进程可以捕捉、清理资源、写日志、关闭连接后退出。
2. `SIGKILL` 不能被捕捉、阻塞或忽略，内核会强制终止进程。
3. `kill -9` 不会给程序执行析构、flush、释放锁、提交事务的机会，可能留下临时文件、半写数据或未完成状态。
4. 如果进程处于不可中断睡眠 `D` 状态，`SIGKILL` 也要等内核等待条件结束后才能真正生效。

生产上通常先 `SIGTERM`，设置超时；超时仍不退出再 `SIGKILL`。

## 2. 如何捕捉信号

C/C++ 程序推荐使用 `sigaction`：

```c
#include <signal.h>
#include <unistd.h>

static volatile sig_atomic_t stop = 0;

void on_signal(int signo) {
    stop = 1;
}

int main() {
    struct sigaction sa = {};
    sa.sa_handler = on_signal;
    sigemptyset(&sa.sa_mask);
    sigaction(SIGTERM, &sa, nullptr);
    sigaction(SIGINT, &sa, nullptr);

    while (!stop) {
        pause();
    }

    // 在主流程里做清理，而不是在信号处理函数里做复杂操作
    return 0;
}
```

信号处理函数里只能做很少的 async-signal-safe 操作。不要在 handler 里直接加锁、分配内存、写复杂日志、操作 C++ 容器或调用非安全库函数，否则可能死锁或破坏状态。常见做法是在 handler 里设置 `sig_atomic_t` 标记、写 pipe/eventfd，主循环再处理清理逻辑。

## 3. 所有信号都能捕捉吗

不是。`SIGKILL` 和 `SIGSTOP` 不能被捕捉、忽略或阻塞。

常见信号：

| 信号 | 默认含义 | 能否捕捉 |
| --- | --- | --- |
| `SIGTERM` | 请求终止 | 可以 |
| `SIGINT` | 终端 Ctrl+C | 可以 |
| `SIGHUP` | 终端断开或重载配置 | 可以 |
| `SIGQUIT` | 退出并可能生成 core | 可以 |
| `SIGSEGV` | 非法内存访问 | 可以捕捉，但通常只用于记录和退出 |
| `SIGKILL` | 强制杀死 | 不可以 |
| `SIGSTOP` | 强制暂停 | 不可以 |

## 4. 工程场景

1. WebServer 收到 `SIGTERM` 后停止 accept 新连接，等待存量请求结束，再退出。
2. 守护进程或 systemd 先发 `SIGTERM`，宽限期后再发 `SIGKILL`。
3. 服务用 `SIGHUP` 触发配置重载，但要保证配置替换是原子的。
4. 崩溃信号如 `SIGSEGV` 不适合“恢复继续运行”，更适合记录最小信息、生成 core 后退出。

## 5. 面试回答模板

`kill` 默认发送 `SIGTERM`，是可捕捉的优雅退出请求；`kill -9` 发送 `SIGKILL`，不能被捕捉、阻塞或忽略，会由内核强制终止进程。程序捕捉信号一般用 `sigaction`，handler 里只做设置标记或写 pipe 这类安全操作，真正清理放到主流程。不是所有信号都能捕捉，`SIGKILL` 和 `SIGSTOP` 一定不行；生产上不要一上来就 `kill -9`，否则应用没有机会释放资源和落盘状态。
