# 4. Shell 脚本健壮性与远程长任务

Shell 脚本在面试中常被追问两个方向：错误处理是否可靠，以及远程执行长任务时网络中断怎么办。

## Shell 解析流程

Shell 不是把一整行命令直接交给内核执行，而是先完成一系列解析和展开，再通过 `fork/exec` 或内建命令执行。

常见顺序可以概括为：

1. **词法切分**：按空白、引号、转义符把输入拆成单词。
2. **变量和命令替换**：展开 `$VAR`、`${VAR}`、`$(cmd)`、反引号等。
3. **通配符展开**：把 `*.log` 这类模式展开成匹配到的文件名列表。
4. **重定向绑定**：处理 `> file`、`2>&1`、`< file` 等，把 fd 指向对应文件或其他 fd。
5. **执行命令**：内建命令在当前 shell 中执行；外部命令通常由子进程 `execve()` 加载程序。
6. **收集退出状态**：前台命令结束后，Shell 把退出码保存到 `$?`。

易错点是引号和展开顺序。双引号会保留变量展开但抑制通配符展开，单引号会把内容几乎原样保留：

```bash
name="a b"
printf '<%s>\n' "$name"   # 一个参数: a b
printf '<%s>\n' $name     # 两个参数: a 和 b
```

工程中处理路径、用户输入、文件名时，变量一般要加双引号，避免空格、换行或通配符导致参数被错误拆分。

## 输入输出重定向和退出状态码

Linux 进程默认有三个标准 fd：

| fd | 名称 | 默认含义 |
| --- | --- | --- |
| 0 | stdin | 标准输入 |
| 1 | stdout | 标准输出 |
| 2 | stderr | 标准错误 |

常见重定向：

```bash
cmd > out.log          # stdout 覆盖写入文件
cmd >> out.log         # stdout 追加写入文件
cmd 2> err.log         # stderr 写入文件
cmd > all.log 2>&1     # stderr 指向当前 stdout，合并输出
cmd < input.txt        # stdin 来自文件
```

重定向顺序从左到右生效。下面两个命令含义不同：

```bash
cmd > all.log 2>&1     # stdout 和 stderr 都进入 all.log
cmd 2>&1 > all.log     # stderr 仍指向原来的 stdout，只有 stdout 进入 all.log
```

`$?` 保存上一条前台命令的退出状态码，`0` 通常表示成功，非 `0` 表示失败：

```bash
grep "ERROR" app.log
code=$?
if [ "$code" -ne 0 ]; then
    echo "grep failed or no match: $code"
fi
```

注意 `$?` 会被下一条命令立即覆盖，所以需要马上保存。管道默认只返回最后一个命令的退出码，想让任意阶段失败都暴露出来，应配合 `set -o pipefail`。

## `set -e` 的作用

`set -e` 表示脚本中简单命令返回非 0 状态时，脚本立即退出，避免错误被忽略后继续执行危险操作。

```bash
#!/usr/bin/env bash
set -e

make
make install
```

如果 `make` 失败，脚本不会继续执行 `make install`。

常见组合：

```bash
set -euo pipefail
```

含义：

1. `-e`：命令失败时退出。
2. `-u`：使用未定义变量时报错退出。
3. `pipefail`：管道中任意命令失败，整个管道返回失败。

## `set -e` 的易错点

`set -e` 不是异常机制，下面场景要特别注意：

1. `if cmd; then ... fi`、`while cmd; do ... done` 中的条件命令失败通常不会让脚本退出。
2. `cmd || true` 会显式吞掉错误。
3. 没有 `set -o pipefail` 时，`cmd1 | cmd2` 默认只看最后一个命令 `cmd2` 的退出码。
4. 子 shell、命令替换、后台任务中的错误可能不按直觉传播，需要明确检查退出码。
5. 清理临时文件、释放锁等逻辑要用 `trap` 保证执行。

示例：

```bash
#!/usr/bin/env bash
set -euo pipefail

tmp=$(mktemp)
trap 'rm -f "$tmp"' EXIT

grep "ERROR" app.log > "$tmp"
```

如果 `grep` 找不到内容会返回 1，在 `set -e` 下脚本会退出；如果“找不到”是允许结果，要显式处理：

```bash
grep "ERROR" app.log > "$tmp" || true
```

## 远程长任务如何避免网络中断影响

如果本地脚本通过 SSH 连接服务器执行长时间任务，网络断开可能导致远程进程收到 `SIGHUP` 或 SSH 会话退出。常见解决方案是让任务脱离当前 SSH 会话，并把状态落到远端。

### 1. 使用 `tmux` 或 `screen`

```bash
tmux new -s job
./long_task.sh
```

断线后重新登录：

```bash
tmux attach -t job
```

适合需要人工观察输出、临时调试、交互式任务。

### 2. 使用 `nohup`、`setsid`、后台运行

```bash
nohup ./long_task.sh > task.log 2>&1 &
echo $! > task.pid
```

或：

```bash
setsid ./long_task.sh > task.log 2>&1 < /dev/null &
```

适合非交互式任务。要把日志、PID、退出状态写到远端文件，后续通过 `tail -f task.log`、`ps -p $(cat task.pid)` 检查。

### 3. 使用 `systemd-run`

在使用 systemd 的服务器上，可以把一次性长任务交给 systemd 管理：

```bash
systemd-run --unit=batch-job --same-dir ./long_task.sh
journalctl -u batch-job -f
```

优点是生命周期、日志、失败状态更清晰，适合生产环境临时运维任务。

### 4. SSH 保活只能降低断线概率

```bash
ssh -o ServerAliveInterval=30 -o ServerAliveCountMax=3 user@host
```

保活可以更快发现断线，也能减少部分 NAT/防火墙空闲超时，但不能从根本上保证长任务继续运行。真正可靠的做法仍然是让任务在远端托管运行。

## 工程注意事项

1. 长任务要幂等：重复执行不会产生脏数据或重复副作用。
2. 关键步骤要有 checkpoint：断点续跑比从头重跑更可靠。
3. 日志要落盘并带时间戳，避免只输出到 SSH 终端。
4. 远程脚本要明确退出码，调用方才能判断成功、失败还是部分完成。
5. 涉及部署或数据修复时，最好用任务系统、CI/CD、systemd、Kubernetes Job，而不是依赖一条长 SSH 会话。

## 面试回答模板

`set -e` 用来让脚本在命令失败时尽早退出，但它有例外，管道要配合 `set -o pipefail`，未定义变量可配合 `set -u`，资源清理用 `trap`。远程执行很久的任务时，不应该依赖 SSH 会话一直稳定，可以用 `tmux/screen` 保留交互会话，非交互任务用 `nohup`、`setsid` 或 `systemd-run` 托管到远端，同时把日志、PID、状态文件落盘，并通过幂等和 checkpoint 保证断线后可恢复。
