# 7. netstat 连接状态与 top 负载指标

Linux 服务部署和压测时，面试常把 `netstat/ss`、`top`、Load Average、CPU 利用率放在一起问。回答时要把“命令能看到什么”和“指标代表什么风险”分开讲。

## 1. netstat 和 ss 看什么

`netstat` 是传统网络查看工具，现代 Linux 更推荐 `ss`，因为 `ss` 直接从内核 socket 统计接口读取，连接很多时更快。

常用命令：

```bash
netstat -antp
ss -antp
ss -lntp
ss -s
```

参数含义：

1. `-a`：显示监听和非监听 socket。
2. `-n`：不做 DNS 和服务名解析，避免命令本身卡住。
3. `-t`：TCP。
4. `-u`：UDP。
5. `-l`：只看监听端口。
6. `-p`：显示进程 PID 和进程名，需要权限。

## 2. 常见 TCP 连接状态

| 状态 | 含义 | 常见排查方向 |
| --- | --- | --- |
| `LISTEN` | 服务端正在监听端口 | 服务是否启动、绑定地址是否正确 |
| `SYN_SENT` | 主动发起连接，等待对端 SYN+ACK | 目标不可达、防火墙、服务没监听 |
| `SYN_RECV` | 服务端收到 SYN，等待第三次握手 ACK | SYN backlog、SYN Flood、网络丢包 |
| `ESTABLISHED` | 连接已建立 | 正常业务连接，也可能是连接泄漏 |
| `FIN_WAIT1` | 主动关闭方已发 FIN，等待 ACK | 对端或网络响应慢 |
| `FIN_WAIT2` | 主动关闭方已收 ACK，等待对端 FIN | 对端迟迟不关闭 |
| `CLOSE_WAIT` | 被动关闭方收到 FIN，但应用还没 close | 应用层忘记关闭 socket，资源泄漏高危 |
| `LAST_ACK` | 被动关闭方已发 FIN，等待最后 ACK | 对端 ACK 丢失或网络异常 |
| `TIME_WAIT` | 主动关闭方等待 2MSL | 短连接过多、主动关闭太多 |
| `CLOSING` | 双方几乎同时关闭 | 少见，通常不是主要矛盾 |

面试里要特别区分：

1. 大量 `TIME_WAIT` 不一定是 bug，通常说明本端主动关闭了很多短连接。
2. 大量 `CLOSE_WAIT` 更危险，通常说明应用收到对端关闭后没有及时 `close()`。
3. 大量 `SYN_RECV` 可能是握手队列积压、丢包或 SYN Flood。

## 3. 大量 TIME_WAIT 怎么处理

先判断是否真的造成问题，例如端口耗尽、fd 不足、连接失败率升高、内存占用异常。如果只是数量多但无影响，不要盲目调内核参数。

优先级更高的优化：

1. 使用长连接、HTTP keep-alive、RPC 连接池，减少短连接。
2. 调整协议，让非核心服务端或客户端承担主动关闭。
3. 扩大本地临时端口范围，降低端口耗尽概率。
4. 排查上游重试风暴，避免失败请求快速创建和关闭连接。
5. 谨慎使用 `tcp_tw_reuse` 等参数，结合内核版本、NAT 和时间戳语义评估风险。

不要把 `SO_REUSEADDR` 理解成“消灭 TIME_WAIT”。它主要帮助服务端重启后绑定本地地址端口，并不直接减少 TIME_WAIT 数量。

## 4. Load Average 是什么

`uptime`、`top` 第一行会显示 1 分钟、5 分钟、15 分钟 Load Average：

```text
load average: 2.31, 1.80, 1.20
```

Linux 的 Load Average 不是 CPU 使用率，而是单位时间内处于以下状态的任务数量平均值：

1. 正在运行或等待 CPU 的任务。
2. 不可中断睡眠任务，常见于磁盘 I/O、某些内核等待。

因此：

1. CPU 很高、Load 高：可能 CPU 饱和。
2. CPU 不高、Load 高：可能大量任务卡在 I/O、锁、网络或不可中断等待。
3. 1 分钟负载远高于 15 分钟：最近突增。
4. 15 分钟也很高：持续性压力。

判断高不高要结合 CPU 核数。4 核机器 Load 接近 4 表示 CPU 运行队列大致打满；长期远高于 4，说明任务排队明显。但如果高负载来自 `D` 状态 I/O 等待，就不能只靠加 CPU 解决。

## 5. 进程 CPU 利用率会超过 100% 吗

会。`top` 中单个进程的 `%CPU` 通常以“一个 CPU 核 = 100%”计算。一个多线程进程如果同时跑满 4 个核，可能显示接近 `400%`。

常见口径：

1. 单线程计算密集任务最多约 `100%`。
2. 多线程进程可以超过 `100%`，上限接近 `CPU 核数 * 100%`。
3. `top` 的整体 `%Cpu(s)` 是全机器聚合比例，和单进程 `%CPU` 口径不同。
4. 容器里还要考虑 cgroup quota，看到的核数和实际可用 CPU 配额可能不一致。

## 6. top 还能看什么

`top` 常见指标：

| 指标 | 含义 | 排查意义 |
| --- | --- | --- |
| `us` | 用户态 CPU | 业务代码计算开销 |
| `sy` | 内核态 CPU | 系统调用、网络协议栈、锁竞争 |
| `id` | 空闲 CPU | CPU 是否有余量 |
| `wa` | I/O wait | 磁盘、网络存储或块设备等待 |
| `hi/si` | 硬/软中断 | 网卡包量、中断压力 |
| `st` | steal time | 虚拟化环境 CPU 被宿主机拿走 |
| `VIRT` | 进程虚拟地址空间 | mmap、共享库、堆栈预留 |
| `RES` | 常驻物理内存 | 实际占用内存重点看这个 |
| `SHR` | 共享内存 | 共享库、共享映射 |
| `S` | 进程状态 | R/S/D/Z 等 |
| `TIME+` | 累计 CPU 时间 | 判断长期热点进程 |

常用组合命令：

```bash
top -H -p <pid>      # 看进程内各线程 CPU
pidstat -p <pid> 1  # 按进程观察 CPU
pidstat -t -p <pid> 1 # 按线程观察 CPU
vmstat 1            # 看运行队列、内存、swap、IO、CPU
mpstat -P ALL 1     # 看每个 CPU 核
```

## 6.1 查询进程资源占用常用命令

面试里问“Linux 中查询进程占用”，可以按 CPU、内存、线程、fd 和 I/O 分开回答：

```bash
ps -eo pid,ppid,stat,%cpu,%mem,rss,vsz,cmd --sort=-%cpu | head
ps -eo pid,ppid,stat,%cpu,%mem,rss,vsz,cmd --sort=-rss | head
top -p <pid>
top -H -p <pid>
pidstat -u -r -d -p <pid> 1
lsof -p <pid> | wc -l
ls /proc/<pid>/fd | wc -l
cat /proc/<pid>/status
```

关注点：

1. `%CPU` 看 CPU 时间占比，单进程多线程可能超过 100%。
2. RSS 更接近实际驻留物理内存，VSZ 是虚拟地址空间大小，不等于实际占用。
3. `top -H` 和 `pidstat -t` 能定位到具体线程，再用 GDB/perf 看线程栈。
4. fd 数量过高可能导致 `Too many open files`，要查 socket、文件、epoll、eventfd 是否泄漏。
5. I/O 占用要结合 `pidstat -d`、`iotop`、`iostat`，不能只看 CPU。

## 7. 面试回答模板

`netstat` 和 `ss` 用来看端口监听、连接四元组、TCP 状态和对应进程。常见状态有 `LISTEN`、`SYN_RECV`、`ESTABLISHED`、`CLOSE_WAIT`、`TIME_WAIT` 等；大量 `TIME_WAIT` 常见于短连接和主动关闭过多，优先用长连接、连接池和协议调整处理；大量 `CLOSE_WAIT` 通常是应用没及时关闭 socket。`top` 里 Load Average 表示运行队列加不可中断睡眠任务的平均数量，不等于 CPU 使用率，要结合核数和 `wa/D` 状态判断。单进程 `%CPU` 可以超过 100%，因为多线程可以同时使用多个核。
