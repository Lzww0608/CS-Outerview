# 12. 操作系统内存回收机制与阈值设置

操作系统内存回收是指：当空闲物理页不足或某个内存控制边界被触发时，内核通过回收文件页、回写脏页、换出匿名页、压缩内存、触发 OOM 等方式，重新获得可分配物理页。它不是简单的“内存不够就杀进程”，而是一套分层、分水位、分冷热、分 cgroup 的回收体系。

面试里可以先说结论：**Linux 内存回收主要围绕 watermark、LRU、kswapd、direct reclaim、dirty writeback、swap、compaction、cgroup reclaim 和 OOM 展开。阈值设置不合理会导致频繁回收、抖动、I/O 飙升、延迟长尾、吞吐下降，甚至提前 OOM 或内存长期浪费。**

## 1. 内存为什么需要回收

Linux 会尽量利用空闲内存做缓存，例如 Page Cache、dentry/inode cache、slab cache。`free` 里看到 buff/cache 很大通常不是问题，因为这部分很多可以回收。

真正需要回收的场景：

1. 进程分配新页，空闲页不足。
2. Page Cache、slab、匿名页占用增长，超过系统承受范围。
3. cgroup 或容器达到 memory limit。
4. 高阶连续页分配失败，需要内存规整和回收。
5. 脏页太多，需要回写后释放。
6. NUMA 某个 node 或 zone 的空闲页低于水位线。

回收对象大致分为：

| 类型 | 是否可直接释放 | 说明 |
| --- | --- | --- |
| 干净文件页 | 可以 | Page Cache 中未修改的文件页，丢弃后可从磁盘重读 |
| 脏文件页 | 不能直接释放 | 必须先 writeback 回写磁盘 |
| 匿名页 | 通常不能直接释放 | 进程堆、栈等匿名内存，可能换出到 swap |
| slab cache | 部分可回收 | dentry、inode 等内核缓存可 shrink |
| mlocked/unevictable 页 | 通常不可回收 | 被锁定或特殊用途页 |

## 2. watermark 水位线

Linux 按 NUMA node 和 zone 管理物理页，每个 zone 有水位线：

```text
high  -> 空闲页充足，kswapd 可以停止
low   -> 空闲页偏低，唤醒 kswapd 后台回收
min   -> 空闲页很低，分配路径可能 direct reclaim，必要时 OOM
```

可以通过下面命令查看：

```bash
cat /proc/zoneinfo
cat /proc/sys/vm/min_free_kbytes
```

触发逻辑可以简化为：

```text
free_pages > high:
  系统较安全

free_pages < low:
  唤醒 kswapd 后台扫描和回收

free_pages < min:
  进程分配内存时可能进入 direct reclaim
  如果仍无法满足分配，可能触发 OOM
```

`min_free_kbytes` 会影响水位线。它不是越小越好，也不是越大越好。

1. 太小：系统保留页不足，突发分配时更容易 direct reclaim、分配失败、网络/驱动收包分配失败。
2. 太大：大量内存被保留不用，应用可用内存变少，可能提前回收或提前 OOM。

## 3. kswapd 后台回收

`kswapd` 是内核后台页回收线程。当某个 zone 空闲页低于 low watermark 时，内核会唤醒 `kswapd`。

流程：

```text
空闲页低于 low
  -> 唤醒 kswapd
  -> 扫描 LRU 队列
  -> 回收干净文件页
  -> 触发脏页回写
  -> 必要时换出匿名页
  -> 空闲页恢复到 high 左右后休眠
```

特点：

1. 后台异步回收，通常比 direct reclaim 对业务延迟影响小。
2. 回收会消耗 CPU 和 I/O，尤其是脏页多、匿名页多时。
3. 如果 `kswapd` 长期高 CPU，说明内存压力持续存在或回收效率差。

排查：

```bash
top -H | grep kswapd
vmstat 1
sar -B 1
cat /proc/vmstat | egrep "pgscan|pgsteal|kswapd|allocstall"
```

重点看：

1. `pgscan_kswapd` 是否持续增加。
2. `pgsteal_kswapd` 和 `pgscan_kswapd` 比例是否很低，低说明扫描很多但回收少。
3. `kswapd` CPU 是否长期较高。

## 4. direct reclaim 直接回收

direct reclaim 是指业务进程在分配内存时发现空闲页不足，自己进入内核回收路径。

```text
应用 malloc/new/page fault
  -> 需要分配物理页
  -> 空闲页不足
  -> 当前线程进入 direct reclaim
  -> 扫描、回写、换出、等待 I/O
  -> 分配成功或失败
```

它比 kswapd 更危险，因为回收发生在业务请求路径上，会直接造成延迟长尾。

常见现象：

1. P99/P999 延迟突然变高。
2. CPU usage 不一定高，但 Load 变高。
3. `vmstat` 中 `si/so` 或 `wa` 可能升高。
4. `/proc/vmstat` 中 `allocstall`、`pgscan_direct`、`pgsteal_direct` 增加。
5. 线程可能卡在内核内存分配或文件系统回写路径。

如果面试官问“为什么内存回收会影响接口延迟”，重点就是 direct reclaim：本来是业务线程处理请求，结果它被迫去回收内存或等回写 I/O。

## 5. LRU 与冷热页扫描

Linux 不维护精确 LRU，而是用 active/inactive 等队列近似冷热。大致可以理解为：

```text
文件页:
  active_file
  inactive_file

匿名页:
  active_anon
  inactive_anon
```

回收时：

1. 优先扫描 inactive 队列。
2. 最近访问过的页可能被晋升到 active。
3. 长时间未访问的页留在 inactive，更容易被回收。
4. 干净文件页可以直接丢弃。
5. 脏文件页先回写。
6. 匿名页需要 swap 才能换出。

回收不是“谁占内存多就回收谁”，而是结合页类型、冷热、是否脏、是否可换出、cgroup、NUMA 等策略。

## 6. Page Cache 与脏页回写

写文件时，数据通常先写入 Page Cache 并标记为 dirty，之后由内核异步回写到磁盘。相关阈值包括：

```bash
cat /proc/sys/vm/dirty_background_ratio
cat /proc/sys/vm/dirty_ratio
cat /proc/sys/vm/dirty_background_bytes
cat /proc/sys/vm/dirty_bytes
cat /proc/sys/vm/dirty_expire_centisecs
cat /proc/sys/vm/dirty_writeback_centisecs
```

含义：

| 参数 | 作用 |
| --- | --- |
| `dirty_background_ratio/bytes` | 脏页超过该阈值后，后台 writeback 线程开始回写 |
| `dirty_ratio/bytes` | 脏页超过该阈值后，写入进程可能被阻塞并参与回写 |
| `dirty_expire_centisecs` | 脏页多老之后应该被回写 |
| `dirty_writeback_centisecs` | 后台周期性回写间隔 |

阈值不合理的后果：

1. `dirty_background` 太高：脏页积累很多，突然回写造成 I/O 尖刺。
2. `dirty_ratio` 太高：应用短期写得很快，但后续可能被长时间阻塞在回写。
3. 阈值太低：频繁小批量回写，吞吐下降，磁盘 IOPS 抖动。
4. 写回太慢：脏页无法变成可回收干净页，内存回收效率变差。

数据库、日志系统、对象存储这类写密集服务要特别关注脏页阈值和刷盘策略。

## 7. 匿名页、swap 与 swappiness

匿名页主要来自进程堆、栈、匿名 mmap。它不像干净文件页那样可以直接丢弃，回收时通常需要写入 swap。

相关参数：

```bash
cat /proc/sys/vm/swappiness
```

`swappiness` 越高，内核越倾向于换出匿名页；越低，越倾向于保留匿名页、回收文件页。

不合理后果：

1. `swappiness` 太高：延迟敏感服务可能把热匿名页换出，之后访问触发 major page fault，造成严重长尾。
2. `swappiness` 太低：系统可能过度回收 Page Cache，文件 I/O 命中率下降；匿名页压力大时更接近 OOM。
3. 没有 swap：可以避免换页抖动，但内存峰值时更容易 OOM。
4. swap 设备很慢：一旦发生 swap storm，系统可能几乎不可用。

排查：

```bash
vmstat 1        # si/so
free -h
sar -B 1
cat /proc/vmstat | egrep "pswpin|pswpout|pgmajfault"
```

## 8. slab 和内核缓存回收

内核自己也会消耗内存，例如 dentry、inode、网络缓存、文件系统元数据、kmem cache。它们通常通过 slab/slub 管理。

查看：

```bash
slabtop
cat /proc/slabinfo
cat /proc/meminfo | egrep "Slab|SReclaimable|SUnreclaim"
```

重点区分：

1. `SReclaimable`：理论上可回收的 slab，例如部分 dentry/inode。
2. `SUnreclaim`：不容易回收的内核内存。

如果 dentry/inode cache 很大但可回收，一般不是问题；如果 `SUnreclaim` 持续增长，可能是内核内存泄漏、网络对象泄漏、驱动问题或特殊内核缓存增长。

## 9. cgroup / 容器内存回收

在容器环境里，内存回收不只看整机，还要看 cgroup 限制。

常见机制：

1. cgroup 达到 `memory.high`：触发限速式回收，进程可能变慢但不一定 OOM。
2. cgroup 达到 `memory.max`：如果回收失败，触发 cgroup OOM。
3. `memory.low/min`：保护重要 cgroup 的一部分内存不被轻易回收。
4. kubelet eviction：节点内存压力下，Kubernetes 可能驱逐 Pod。

排查：

```bash
cat /sys/fs/cgroup/memory.current
cat /sys/fs/cgroup/memory.max
cat /sys/fs/cgroup/memory.events
cat /sys/fs/cgroup/memory.stat
```

阈值不合理的后果：

1. limit 太小：容器频繁 reclaim、GC、OOMKilled。
2. `memory.high` 太低：应用没 OOM，但长期被内存回收节流，延迟升高。
3. request/limit 配置不合理：节点 overcommit 后多个 Pod 同时抢内存，引发驱逐。
4. 只看宿主机 free 很多，却忽略容器 cgroup 已经到 limit。

## 10. OOM 触发和选择

当回收、回写、swap、压缩都无法满足分配，内核可能触发 OOM Killer。

OOM 不是随便杀进程，内核会根据 badness 评分选择牺牲者，考虑内存占用、`oom_score_adj` 等因素。

查看：

```bash
dmesg -T | egrep -i "out of memory|oom|killed process"
cat /proc/<pid>/oom_score
cat /proc/<pid>/oom_score_adj
```

注意：

1. cgroup OOM 可能只杀容器内进程。
2. 系统级 OOM 影响整机。
3. `oom_score_adj` 可以保护关键进程，但不能滥用，否则可能杀掉更不该杀的进程。
4. OOM 前通常已经有内存压力、回收、major fault、swap 或 direct reclaim 信号。

## 11. 阈值设置不合理会导致什么

| 阈值/策略 | 过低的后果 | 过高的后果 |
| --- | --- | --- |
| `min_free_kbytes` | 保留页不足，突发分配更容易 direct reclaim 或失败 | 可用内存减少，提前回收或提前 OOM |
| `dirty_background_ratio` | 频繁后台回写，吞吐和 IOPS 抖动 | 脏页堆积，后续回写尖刺 |
| `dirty_ratio` | 写入进程过早被 throttle | 脏页过多，回收困难，写阻塞长尾 |
| `swappiness` | Page Cache 被过度回收，文件 I/O 变慢 | 热匿名页换出，major fault 和延迟长尾 |
| cgroup `memory.high` | 容器过早被 reclaim 节流 | 无法提前抑制内存增长，接近 max 才剧烈回收 |
| cgroup `memory.max` | 容器频繁 OOMKilled | 单容器占用过多，影响节点其他服务 |
| `vm.max_map_count` | mmap/线程/小映射多的进程失败 | 过高通常不是主要风险，但会掩盖 VMA 滥用 |
| overcommit 策略 | 分配保守，可能申请失败 | 承诺过多，触碰页面时 OOM 风险增大 |

典型线上问题：

1. **频繁 direct reclaim**：接口 P99 抖动，业务线程卡在分配内存。
2. **kswapd 长期高 CPU**：系统持续内存压力，吞吐下降。
3. **swap storm**：`si/so` 持续高，系统响应极慢。
4. **脏页回写风暴**：写入突然卡住，磁盘 await 飙升。
5. **Page Cache 被冲掉**：读请求命中率下降，磁盘读放大。
6. **提前 OOM**：阈值或 cgroup limit 太紧，应用峰值内存没空间。
7. **内存浪费**：保留阈值太高或 cache 策略不合理，业务可用内存变少。

## 12. 如何排查内存回收问题

### 12.1 看整体内存压力

```bash
free -h
vmstat 1
sar -B 1
cat /proc/meminfo
```

关注：

1. `MemAvailable` 是否持续很低。
2. `si/so` 是否持续非 0。
3. `wa` 是否升高。
4. major page fault 是否增加。

### 12.2 看回收计数

```bash
cat /proc/vmstat | egrep "pgscan|pgsteal|allocstall|kswapd|pgmajfault|pswpin|pswpout|compact|oom"
```

重点：

1. `pgscan_kswapd`：后台回收扫描。
2. `pgscan_direct`：业务线程直接回收扫描。
3. `allocstall`：分配路径被迫等待回收。
4. `pgmajfault`：需要磁盘 I/O 的缺页。
5. `pswpin/pswpout`：swap 换入换出。
6. `compact_*`：内存规整活动。

### 12.3 看进程和 cgroup

```bash
top
pidstat -r 1
ps -eo pid,ppid,rss,vsz,stat,comm --sort=-rss | head
cat /proc/<pid>/smaps_rollup
cat /proc/<pid>/status
```

容器：

```bash
cat /sys/fs/cgroup/memory.current
cat /sys/fs/cgroup/memory.events
cat /sys/fs/cgroup/memory.stat
```

### 12.4 看 I/O 和回写

```bash
iostat -xz 1
pidstat -d 1
cat /proc/meminfo | egrep "Dirty|Writeback"
cat /proc/vmstat | egrep "nr_dirty|nr_writeback|writeback"
```

如果 Dirty/Writeback 高，且磁盘 await 高，说明脏页回写可能是回收瓶颈。

### 12.5 看 OOM 和内核日志

```bash
dmesg -T | egrep -i "oom|out of memory|killed process|memory allocation failure|page allocation failure"
journalctl -k
```

OOM 日志会告诉你被杀进程、内存状态、cgroup 信息和当时的内存分布。

## 13. 解决思路

按根因处理：

1. **工作集超过内存**：扩容内存、降低并发、拆分服务、限制缓存、优化数据结构。
2. **Page Cache 污染**：大文件扫描限速，使用 `posix_fadvise`，把批处理和在线服务隔离。
3. **脏页回写抖动**：降低 dirty 阈值、分批写、异步日志、提升磁盘能力。
4. **频繁 swap**：降低匿名内存占用、调整 swappiness、扩容内存，延迟敏感服务谨慎使用 swap。
5. **cgroup OOM**：合理设置 request/limit、memory.high、拆分 Pod、减少峰值内存。
6. **direct reclaim 长尾**：预分配/复用对象、控制队列、避免请求路径大块分配。
7. **slab 异常增长**：查 dentry/inode、网络对象、内核模块和驱动，必要时升级内核或修复泄漏。
8. **高阶页分配失败**：关注内存碎片、透明大页、compaction，避免运行时频繁申请大连续页。

## 14. 易错点

1. `free` 很小不一定是内存不足，Linux 会用空闲内存做缓存，重点看 `available`。
2. Page Cache 大不一定要清理，盲目 `drop_caches` 会让后续读 I/O 变慢。
3. OOM 不是回收的第一步，而是回收失败后的最后手段。
4. direct reclaim 比 kswapd 更影响业务延迟，因为它发生在分配线程上。
5. `swappiness=0` 不代表绝对不 swap，也不一定总是最优。
6. 容器里宿主机内存充足，不代表 cgroup 内存充足。
7. dirty 阈值太高会把短期写吞吐变好，但可能换来更严重的回写长尾。

## 15. 面试回答模板

操作系统内存回收是内核在空闲物理页不足或 cgroup 达到限制时，通过回收 Page Cache、回写脏页、换出匿名页、回收 slab、内存规整，最后必要时 OOM 的过程。Linux 里每个 zone 有 `min/low/high` watermark：低于 low 会唤醒 `kswapd` 后台回收，低于 min 时分配路径可能进入 direct reclaim；如果回收仍失败，就可能触发 OOM。回收时会扫描 active/inactive LRU，优先回收干净文件页，脏页要先回写，匿名页通常要 swap 才能换出，还要考虑 NUMA、cgroup、swappiness 和 dirty page 策略。

阈值设置不合理会带来明显线上问题。`min_free_kbytes` 太低会导致突发分配时频繁 direct reclaim 或分配失败，太高会浪费内存并提前回收；dirty 阈值太高会积累大量脏页，后续回写风暴导致写阻塞和 I/O await 飙升，太低会频繁小批量回写；swappiness 太高可能把热匿名页换出导致 major fault 和长尾，太低可能过度回收 Page Cache；cgroup limit 太小会导致容器频繁 reclaim 或 OOMKilled。排查时我会看 `free/vmstat/sar -B`，再看 `/proc/vmstat` 的 `pgscan_direct、allocstall、pgmajfault、pswpin/pswpout`，结合 `iostat`、`pidstat -r/-d`、`memory.events` 和 OOM 日志定位是 Page Cache、匿名页、脏页回写、swap 还是 cgroup 限制导致。
