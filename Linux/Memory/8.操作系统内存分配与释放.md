# 操作系统内存分配与释放

操作系统内存管理分两层看：内核负责管理物理页、虚拟地址空间和页表；用户态分配器负责在进程堆或 mmap 区中切分小块内存，服务 `malloc/new`。

## 1. 内核如何管理物理内存

Linux 以页为基本单位管理物理内存，常见页大小是 4KB。内核会把物理页按 zone、NUMA 节点和迁移类型组织起来。

核心机制：

1. **伙伴系统**：管理连续物理页，按 2 的幂次拆分和合并，适合分配页框。
2. **slab/slub 分配器**：在页之上缓存固定大小内核对象，例如 `task_struct`、inode、socket。
3. **页回收**：内存压力大时回收 page cache、匿名页换出到 swap，或触发 OOM。
4. **COW**：`fork` 后父子进程共享只读物理页，写入时再复制。

伙伴系统释放页时会尝试和相邻空闲 buddy 合并，降低外部碎片。但长时间运行后仍可能难以分配大块连续物理页，所以 DMA、大页和驱动缓冲区对内存碎片更敏感。

### 1.1 伙伴系统怎么分配和合并

伙伴系统按 `order` 管理连续页块，`order = n` 表示这个块包含 `2^n` 个连续页。假设页大小是 4KB，`order=0` 是 4KB，`order=1` 是 8KB，`order=10` 通常就是 4MB。

分配过程可以这样理解：

1. 内核先根据申请大小向上取整到合适的 `order`。
2. 如果目标 `order` 的空闲链表有块，直接取出。
3. 如果没有，就向更高 `order` 找更大的块。
4. 找到后不断一分为二，拆到目标 `order`。
5. 一个块返回给调用方，另一个 buddy 放回对应空闲链表。

释放过程反过来：

1. 根据页框号和 `order` 计算 buddy 块位置。
2. 如果 buddy 也空闲且同阶，就把两个块合并成更高一阶。
3. 继续向上尝试合并，直到无法合并或到达最大阶。

易错点：

1. 伙伴系统解决的是**物理连续页框**分配，不是直接给用户态对象分配任意字节。
2. 它按 2 的幂分配，天然会有内部碎片；但合并逻辑能降低外部碎片。
3. `malloc` 返回的用户虚拟地址连续，不代表底层物理页一定连续；普通匿名内存通常不要求物理连续。
4. 大页、DMA、某些驱动 buffer 更关心物理连续性，所以更容易受内存碎片影响。

## 2. 用户态 malloc/new 如何申请内存

`new` 通常会调用 `operator new`，底层再使用 C 库分配器；`malloc` 会从用户态堆或 mmap 区拿内存。

常见路径：

1. 小对象：分配器从已有 arena、bin、tcache 中取空闲块。
2. 堆空间不够：通过 `brk/sbrk` 扩大 heap。
3. 大对象：直接通过 `mmap` 申请匿名映射，释放时 `munmap` 归还给内核。
4. 多线程：分配器可能维护多个 arena 或线程缓存，减少全局锁竞争。

释放时，`free/delete` 通常先把块还给用户态分配器。是否立刻归还操作系统取决于块大小、是否位于堆顶、分配器策略和内存压力。

### 2.1 malloc 到内核页分配的完整链路

面试问“`malloc` 底层有哪些系统调用”，可以按用户态分配器和内核内存管理两层回答：

```text
malloc(size)
  -> glibc ptmalloc / jemalloc / tcmalloc
  -> 命中 tcache、bin、arena、span 时直接返回
  -> 内存不够或大对象时调用 brk/mmap
  -> 内核建立 VMA 和页表相关元数据
  -> 首次访问触发缺页异常
  -> 内核通过伙伴系统分配物理页
  -> 建立虚拟页到物理页的映射
```

关键点：

1. `malloc` 本身是 C 库函数，不是系统调用。
2. 小对象分配通常完全在用户态完成，不会每次都陷入内核。
3. `brk/sbrk` 主要扩展传统 heap，适合连续增长的堆区。
4. `mmap/munmap` 常用于大块内存、独立映射、共享内存和直接归还 OS。
5. Linux 通常按需分配物理页，`malloc` 成功只说明拿到虚拟地址，不代表物理内存立即全部到位。

真实服务里，频繁小对象分配的瓶颈往往不是 `brk/mmap` 本身，而是分配器锁竞争、元数据维护、碎片、缓存 miss 和跨线程释放。优化时可以用对象池、批量分配、buffer 复用，或替换 jemalloc/tcmalloc，并用 heap profile 验证热点。

## 3. 如何操作进程堆空间

面试里问“有什么方法可以操作操作系统的堆空间”，可以分成语言接口、C 库分配器接口和系统调用三层回答。

常见方式：

1. **C/C++ 分配接口**：`malloc/free/calloc/realloc`、`new/delete`、`new[]/delete[]`。
2. **C++ 定制分配**：重载全局或类作用域 `operator new/delete`，使用 STL allocator、内存池、对象池、arena。
3. **进程堆边界**：`brk/sbrk` 调整 program break，传统小块堆增长可能走这条路径。
4. **匿名映射**：`mmap(MAP_PRIVATE | MAP_ANONYMOUS)` 申请大块虚拟内存，`munmap` 释放。
5. **分配器调优**：glibc `mallopt`、jemalloc/tcmalloc/mimalloc 的配置、profile 和 purge 策略。

典型层次关系：

```text
new T(...)
  -> operator new(sizeof(T))
  -> malloc 或自定义分配器
  -> 用户态 arena/bin/tcache
  -> 不够时 brk 或 mmap 向内核申请虚拟内存
```

注意事项：

1. `brk/sbrk` 是进程级堆边界接口，现代业务代码通常不直接使用，避免和 libc 分配器状态冲突。
2. `mmap` 得到的是页粒度映射，适合大块、对齐、共享内存、内存池底层申请，不适合每个小对象都直接调用。
3. `new` 和 `malloc` 的层次不同：`new` 还会调用构造函数，`malloc` 只返回未初始化原始字节。
4. 高并发服务频繁小对象分配时，真正瓶颈可能是分配器锁、缓存行争用、碎片和 TLB/cache miss。

## 4. 虚拟内存和物理内存的关系

进程申请内存一般先获得虚拟地址，不一定立刻占用物理页。第一次写入时可能触发缺页异常，内核再分配物理页并建立页表映射。

```text
malloc/new -> 获得虚拟地址
第一次访问 -> page fault
内核分配物理页 -> 更新页表 -> 指令重试
```

这解释了为什么程序的 VIRT 可能很大，但 RSS 不一定大。

## 5. 易错点

1. `free` 后内存不一定马上还给 OS，可能留在分配器缓存中复用。
2. 虚拟地址连续不代表物理地址连续。
3. 小对象频繁分配释放容易产生碎片和锁竞争，可以用对象池、内存池或批量分配优化。
4. 大页能降低 TLB miss，但需要考虑物理连续性、碎片和 NUMA。
5. 内存泄漏、悬垂指针和 double free 是用户态生命周期问题，不是内核自动能修复的。

## 6. 面试回答模板

操作系统按页管理物理内存，Linux 内核常用伙伴系统分配连续物理页，用 slab/slub 管理固定大小内核对象。用户态的 `malloc/new` 通常先从分配器缓存拿内存，小块走 arena/bin/tcache，大块可能走 `mmap`，堆不够时用 `brk` 扩展。操作堆空间可以通过 `malloc/free`、`new/delete`、自定义 `operator new`、STL allocator、内存池，底层再落到 `brk/sbrk` 或 `mmap/munmap`。申请到的是虚拟地址，物理页通常按需在第一次访问时由缺页异常分配。释放时内存可能只回到用户态分配器，不一定立即归还 OS。
