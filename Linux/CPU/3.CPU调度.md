# 3.CPU 调度

CPU 调度的核心问题是：当系统里有多个可运行任务时，操作系统应该选择哪个任务占用 CPU，以及运行多长时间。

## 1. 怎么理解 CPU 调度？

CPU 调度本质上是在多个目标之间做权衡：

1. **公平性**：每个可运行任务都应该有机会获得 CPU。
2. **响应时间**：交互式任务不能长时间等不到 CPU。
3. **吞吐量**：单位时间完成尽可能多的任务。
4. **优先级**：高优先级或实时任务应该更快被调度。
5. **局部性**：尽量减少频繁迁移带来的缓存失效和 NUMA 远程访问。

一次调度通常发生在这些时机：

1. 任务主动阻塞，例如等待 I/O、锁、网络数据。
2. 时间片用完，被定时器中断触发抢占。
3. 有更高优先级任务被唤醒。
4. 任务退出或让出 CPU。

调度的结果是一次上下文切换：保存当前任务寄存器、栈、程序计数器等上下文，再恢复下一个任务的上下文。

## 1.1 调度的基本单位是什么

现代 Linux 中，调度器调度的基本单位是内核任务 `task_struct`。普通说法里可以回答“线程是 CPU 调度的基本单位，进程是资源分配的基本单位”。

原因是 Linux 的进程和线程底层都用 `task_struct` 表示，只是线程通过 `clone()` 共享地址空间、文件描述符表、信号处理等资源。同一进程内的多个线程会分别参与调度，调度器看到的是可运行任务，而不是把整个进程作为一个不可拆分的执行单元。

面试里可以这样区分：

1. **资源视角**：进程拥有独立地址空间、文件描述符表等资源。
2. **执行视角**：线程拥有独立寄存器、栈和调度上下文。
3. **Linux 内核视角**：调度对象是 `task_struct`，进程和线程主要区别在资源共享程度。

## 2. 常见调度算法

| 算法 | 思路 | 特点 |
| --- | --- | --- |
| FCFS | 先来先服务 | 简单，但短任务可能被长任务阻塞 |
| SJF | 最短作业优先 | 平均等待时间低，但需要知道任务运行时间 |
| SRTF | 最短剩余时间优先 | SJF 的抢占式版本 |
| RR | 时间片轮转 | 适合分时系统，响应性好 |
| Priority | 按优先级调度 | 可能导致低优先级任务饥饿 |
| MLFQ | 多级反馈队列 | 兼顾短任务、交互任务和长任务 |
| CFS | 按虚拟运行时间保持公平 | Linux 普通任务的主要调度思路 |

## 3. 如果实现短任务或优先级调度，用什么数据结构？

如果面试官问“让你实现短任务或优先级 CPU 调度，你用什么数据结构”，可以按场景回答。

### 3.1 短任务优先

用 **小根堆** 比较自然：

```text
key = 预计运行时间 / 剩余运行时间
value = task
```

每次取堆顶任务运行，插入和取出复杂度都是 `O(log n)`。如果是抢占式的最短剩余时间优先，新任务到达时和当前任务剩余时间比较，必要时抢占当前任务并重新入堆。

难点在于“运行时间”通常无法准确知道，只能通过历史运行时间、任务类型或业务侧估计值近似。

### 3.2 固定优先级调度

可以用 **多队列 + bitmap**：

```text
priority 0: queue[task...]
priority 1: queue[task...]
priority 2: queue[task...]
...
bitmap: 标记哪些优先级队列非空
```

取任务时先通过 bitmap 找到最高优先级的非空队列，再从该队列取出任务。优先级范围固定时，这种方式可以接近 `O(1)`。

### 3.3 多级反馈队列

多级反馈队列适合兼顾短任务和交互式任务：

1. 新任务先进入高优先级队列。
2. 如果任务很快阻塞或完成，说明它可能是短任务/交互任务，继续保持较高优先级。
3. 如果任务用完整个时间片，说明它偏 CPU 密集，下沉到低优先级队列。
4. 为避免饥饿，可以定期提升低优先级任务。

这类结构本质上也是多队列，只是任务会根据运行行为动态调整所在队列。

## 4. Linux 是怎么实现调度的？

Linux 调度不是只有一个全局队列，而是每个 CPU 都有自己的运行队列 `rq`。这样可以减少多核竞争，也方便利用 CPU cache locality。

核心结构可以概括为：

```text
task_struct
  ├── sched_entity se      普通 CFS 调度实体
  ├── sched_rt_entity rt   实时任务调度实体
  ├── sched_dl_entity dl   deadline 调度实体
  ├── policy               调度策略
  ├── prio/static_prio     优先级
  └── cpus_mask            CPU 亲和性

每个 CPU:
rq
  ├── cfs_rq   普通任务运行队列
  ├── rt_rq    实时任务运行队列
  └── dl_rq    deadline 任务运行队列
```

Linux 通过调度类组织不同类型任务，优先级大致是：

```text
stop > deadline > realtime > fair > idle
```

普通进程主要走 CFS。

## 4.1 多个 CPU 如何让程序并行

单个线程在同一时刻只能运行在一个 CPU 上。多个 CPU 能同时执行一个程序，通常依赖这个程序拥有多个可运行的线程，或者系统中存在多个属于同一服务的进程。

Linux 的基本机制：

1. 每个 CPU 有自己的运行队列，调度器在每个 CPU 上选择一个可运行任务。
2. 同一进程内的多个线程底层都是 `task_struct`，可以分别进入不同 CPU 的运行队列。
3. 负载不均时，内核会做任务迁移和负载均衡，把任务从繁忙 CPU 移到相对空闲的 CPU。
4. `taskset` 或 `sched_setaffinity` 可以设置 CPU 亲和性，限制任务在哪些 CPU 上运行。
5. 多核并行会引入共享数据竞争，需要用锁、原子变量、无锁结构或消息传递保证正确性。

性能上还要考虑 cache locality、false sharing 和 NUMA 远程访问。一个线程频繁在 CPU 之间迁移，可能导致缓存失效；跨 NUMA 节点访问内存，也可能比本地内存慢。

因此面试里可以回答：多个 CPU 不是把一个线程拆开执行，而是操作系统把多个可运行线程或进程分别调度到不同 CPU 上并行执行；能否充分利用多核，取决于程序是否有足够的并行任务，以及同步和数据局部性设计是否合理。

## 5. CFS 的核心：红黑树 + vruntime

CFS（Completely Fair Scheduler）不再直接使用传统固定时间片，而是维护每个任务的 **虚拟运行时间 `vruntime`**。

直观理解：

1. 每个可运行任务都有一个 `vruntime`。
2. 任务实际运行越久，`vruntime` 越大。
3. 优先级越高，`vruntime` 增长越慢。
4. CFS 每次选择 `vruntime` 最小的任务运行。

CFS 使用红黑树组织可运行任务：

```text
key = vruntime
value = sched_entity
```

红黑树最左侧节点就是当前最“亏”的任务，也就是最应该被调度的任务。入队、出队、更新位置通常是 `O(log n)`，选择最左节点可以做到很快。

## 5.1 进程队列到底是什么队列

面试里说“进程队列”要先区分是哪一类队列：

1. **运行队列**：保存可运行任务。Linux 中每个 CPU 有自己的 `rq`，普通任务在 `cfs_rq` 中按 `vruntime` 组织，实时任务在 `rt_rq` 中按优先级队列组织。
2. **等待队列**：保存等待某个事件的任务，例如等待 I/O、锁、定时器、socket 数据。事件发生后内核唤醒任务，把它重新放回运行队列。
3. **阻塞队列不是统一的一条队列**：不同内核对象有自己的 wait queue，比如文件、管道、socket、futex 都可能维护等待者。
4. **就绪态到运行态**：调度器从运行队列选择任务；运行态被抢占时会回到就绪态，重新进入运行队列。

所以回答“CPU 调度的进程队列”时，不应笼统说 FIFO。Linux 普通任务主要是 CFS 红黑树，实时任务更接近按优先级组织的多队列，等待事件时则挂到对应内核对象的等待队列。

## 6. 面试回答模板

CPU 调度就是操作系统在多个可运行任务之间分配 CPU 的策略。它要平衡公平性、响应时间、吞吐量、优先级和缓存局部性。短任务优先可以用按剩余时间排序的小根堆；固定优先级可以用多级队列加 bitmap；多级反馈队列可以根据任务行为动态调整优先级。

Linux 里每个 CPU 有自己的运行队列，普通任务使用 CFS。CFS 用 `vruntime` 衡量任务已经获得的 CPU 份额，并用红黑树按 `vruntime` 排序，每次选择最左边，也就是 `vruntime` 最小的任务运行。实时任务和 deadline 任务则走更高优先级的调度类。
