# CPU 三级缓存与缓存一致性

CPU 访问寄存器最快，访问内存慢得多。为了缩小 CPU 和内存之间的速度差，现代处理器在核心和内存之间加入多级缓存，常见结构是 L1、L2、L3。

## 1. L1、L2、L3 分别是什么

1. **L1 Cache**：最靠近核心，容量最小、延迟最低，通常分为指令缓存 L1I 和数据缓存 L1D。
2. **L2 Cache**：容量比 L1 大，延迟更高，很多架构中每个核心独享一份 L2。
3. **L3 Cache**：容量最大，延迟最高，通常由一个 CPU 插槽内多个核心共享。

缓存以 cache line 为单位读写，常见大小是 64 字节。即使程序只读取一个 `int`，CPU 也可能把它所在的整条 cache line 加载进缓存。

## 2. 为什么缓存能提升性能

缓存利用的是局部性原理：

1. **时间局部性**：刚访问过的数据很可能马上再次访问，例如循环计数器、热哈希桶。
2. **空间局部性**：访问某个地址后，很可能访问附近地址，例如顺序遍历数组。

因此顺序访问数组通常比链表快。数组元素连续，预取器和 cache line 能发挥作用；链表节点分散，容易频繁 cache miss。

### 二维数组行遍历和列遍历

C/C++ 的普通二维数组按行优先存储：

```cpp
int a[1024][1024];
```

内存中相邻的是 `a[0][0]、a[0][1]、a[0][2] ...`，而不是 `a[0][0]、a[1][0]、a[2][0] ...`。

因此给每个元素加 100 时，行遍历更符合空间局部性：

```cpp
for (int i = 0; i < n; ++i) {
    for (int j = 0; j < m; ++j) {
        a[i][j] += 100;
    }
}
```

列遍历会按较大的步长跳跃访问：

```cpp
for (int j = 0; j < m; ++j) {
    for (int i = 0; i < n; ++i) {
        a[i][j] += 100;
    }
}
```

当数组较大时，列遍历更容易导致 cache miss 和 TLB miss，CPU 预取器也更难发挥作用。真实工程里的矩阵计算、图像处理和批量数据清洗通常会关注遍历顺序，必要时还会做 blocking/tiling，把大矩阵切成能放进缓存的小块来处理。

## 3. 缓存一致性

多核 CPU 中，不同核心可能缓存同一内存地址。如果一个核心修改了数据，其他核心的旧缓存副本必须失效或更新，否则会读到过期值。

常见协议是 MESI：

| 状态 | 含义 |
| --- | --- |
| Modified | 当前核心独占且已修改，内存中的值是旧的 |
| Exclusive | 当前核心独占，内容和内存一致 |
| Shared | 多个核心可共享读取，内容和内存一致 |
| Invalid | 当前缓存行无效，需要重新读取 |

一致性协议保证“同一个地址”的缓存可见性，但不等于自动解决并发问题。程序仍然需要互斥锁、原子操作和内存序来约束操作顺序。

## 4. 伪共享

伪共享是多线程性能问题的高频考点。两个线程修改不同变量，但这两个变量落在同一条 cache line 上，就会导致缓存行在核心之间反复失效。

示例：

```cpp
struct Counter {
    std::atomic<long long> a;
    std::atomic<long long> b;
};
```

如果线程 1 高频修改 `a`，线程 2 高频修改 `b`，即使逻辑上没有共享变量，也可能因为 `a` 和 `b` 在同一 cache line 中产生严重缓存一致性流量。可以通过填充或 `alignas(64)` 把高频写变量分离到不同 cache line。

## 5. 真实场景应用

1. **数据结构选择**：热路径优先考虑连续内存结构，例如 `vector`、数组、扁平哈希表。
2. **减少随机访问**：图、链表、树结构如果节点分散，cache miss 可能比算法复杂度更影响实际耗时。
3. **批处理**：把多次小操作合并，提升预取效果和缓存命中率。
4. **避免伪共享**：线程局部计数器、分片队列、按 cache line 对齐的统计项常用于高并发系统。
5. **NUMA 优化**：多路 CPU 机器上，线程访问本 NUMA 节点内存通常比跨节点访问更快。

### 对象布局和缓存友好设计

面试里问“类成员分别 `new` 和整体 `new` 有什么区别”时，本质是在考数据布局、局部性和所有权管理。

如果一个对象把多个热成员放在同一块连续内存里：

```cpp
struct Player {
    int hp;
    int mp;
    int x;
    int y;
};

auto p = std::make_unique<Player>();
```

访问 `hp/mp/x/y` 时更容易落在同一条或相邻 cache line 上，分配和释放也只需要管理一个对象。相反，如果每个成员都单独 `new`：

```cpp
struct Player {
    int* hp;
    int* mp;
    int* x;
    int* y;
};
```

访问一次逻辑对象可能要跳到多个分散地址，带来更多 cache miss、TLB miss、堆分配元数据开销和生命周期管理风险。除非成员很大、生命周期独立、可选加载或需要多态共享，否则热路径对象通常不建议把小成员拆成多个堆对象。

面向对象设计也可能影响缓存：

1. 大量虚函数和指针间接访问会让 CPU 难以内联和预取。
2. 链表式对象图表达灵活，但随机访问多，可能比连续数组慢很多。
3. 游戏、图像处理和高频交易场景常把热字段改成 SoA（Structure of Arrays），例如把 `x[]`、`y[]`、`hp[]` 分开连续存放，便于批量遍历和 SIMD。
4. 业务代码不应为了“缓存友好”盲目破坏可维护性；通常先用 perf、VTune、cachegrind 等工具确认瓶颈，再调整布局。

## 6. 同功能代码为什么内存性能不同

同样功能的代码，内存层面可能差很多，原因通常不在语法本身，而在访问模式和数据布局。

1. **连续访问 vs 随机访问**：`vector` 顺序遍历能利用 cache line 和预取器，链表、树、散乱对象容易产生 cache miss。
2. **TLB 命中率**：跨很多页面随机访问会增加 TLB miss；批量连续处理、页内局部性更好。
3. **分配次数**：大量小对象频繁 `new/delete` 会带来分配器锁、元数据、碎片和 cache 污染。
4. **拷贝次数**：无意义的临时对象、字符串拼接、容器扩容会增加内存带宽消耗。
5. **对象大小和对齐**：结构体字段顺序影响 padding；热点字段过大或夹杂冷字段会浪费 cache line。
6. **伪共享**：不同线程写不同变量，如果落在同一条 cache line，会被缓存一致性协议反复失效。
7. **NUMA 远程访问**：线程在一个 NUMA 节点运行，却频繁访问另一个节点分配的内存，会增加延迟。

示例：如果只需要批量更新坐标，下面的 SoA 布局可能比 AoS 更适合 SIMD 和顺序扫描：

```cpp
struct PlayerAoS {
    float x;
    float y;
    int hp;
};

struct PlayersSoA {
    std::vector<float> x;
    std::vector<float> y;
    std::vector<int> hp;
};
```

但 SoA 会牺牲面向单个对象的封装便利，所以工程上通常只在热点路径、批处理和性能证据明确时使用。

内存层面优化的面试回答可以按“先测量，再调整”展开：用 perf/cachegrind/VTune 观察 cache miss、TLB miss、分配热点和锁竞争，再针对性做连续存储、减少分配、对象池、字段重排、批处理、预取、对齐和 NUMA 亲和。

## 7. 面试回答模板

CPU 三级缓存是为弥补 CPU 和内存速度差设计的层次化缓存。L1 最快最小，L2 居中，L3 最大且常被多个核心共享；缓存以 cache line 为单位加载，常见 64 字节。缓存提升性能依赖时间局部性和空间局部性，所以连续数组通常比分散链表更友好。多核下通过 MESI 等协议维护缓存一致性，但一致性不等于线程安全，互斥、原子和内存序仍然需要程序保证。实际优化时要关注 cache miss、伪共享、数据布局、预取、批处理和 NUMA。
