# 4. CPU 占用率优化与条件断点

CPU 占用率优化不能只靠猜代码热点。正确做法是先确认 CPU 高的类型，再用采样、火焰图、线程栈和指标定位热点，最后按算法、锁、I/O、调度和编译参数分层优化。

## 1. 先判断 CPU 高在哪里

常见观察命令：

```bash
top -H -p <pid>
mpstat -P ALL 1
pidstat -t -p <pid> 1
pidstat -w -p <pid> 1
perf top -p <pid>
perf record -F 99 -p <pid> -g -- sleep 30
perf report
```

重点区分：

1. **用户态 CPU 高**：业务计算、序列化、压缩、JSON、加密、日志格式化、死循环。
2. **内核态 CPU 高**：系统调用频繁、网络包处理、锁竞争、软中断、文件 I/O。
3. **上下文切换高**：线程过多、锁竞争、条件变量频繁唤醒。
4. **软中断高**：网络包量大、网卡中断、协议栈处理压力。

如果只看总 CPU，不看线程和调用栈，很容易优化错方向。

## 1.1 CPU 状态怎么看

分析 CPU 状态时，先看整机，再看进程和线程，最后看调用栈。`top`、`mpstat`、`pidstat` 中常见字段含义如下：

| 指标 | 含义 | 常见原因 |
| --- | --- | --- |
| `us`/user | 用户态 CPU | 业务计算、序列化、压缩、加密、循环计算 |
| `sy`/system | 内核态 CPU | 系统调用频繁、网络协议栈、文件 I/O、锁和调度 |
| `wa`/iowait | 等待块设备 I/O | 磁盘慢、日志刷盘、数据库读写、page cache 回写 |
| `hi`/hardware irq | 硬中断 | 网卡、磁盘等硬件中断压力 |
| `si`/softirq | 软中断 | 网络收包、协议栈处理、包量过大 |
| `st`/steal | 被宿主机偷走的 CPU | 虚拟化环境 CPU 争抢 |
| `id`/idle | 空闲 CPU | CPU 不是瓶颈，可能瓶颈在 I/O、锁、下游 |

进一步判断：

1. **单核打满，多核空闲**：可能是单线程瓶颈、锁串行化、连接分配不均或 CPU 亲和性问题。
2. **load average 高但 CPU 不高**：可能大量线程处于不可中断 I/O、锁等待或队列堆积。
3. **上下文切换高**：用 `pidstat -w` 看自愿和非自愿切换，常见于线程过多、锁竞争、频繁唤醒。
4. **软中断集中在单核**：可能需要看网卡队列、RSS/RPS、irq affinity 和包量。
5. **用户态热点集中**：用 `perf record/report` 或火焰图看函数栈，再决定是算法、对象分配还是序列化问题。

## 2. 常见优化方向

### 2.1 算法和数据结构

1. 降低复杂度，例如从 `O(n^2)` 改成 `O(n log n)` 或 `O(n)`。
2. 用哈希表、堆、索引、缓存减少重复扫描。
3. 对热点路径做预计算、增量计算或批量处理。
4. 避免在循环里频繁分配内存、格式化字符串和做正则匹配。

### 2.2 锁和线程

1. 缩小临界区，避免持锁做 I/O 或耗时计算。
2. 使用读写锁、分片锁、无锁队列或消息队列降低竞争。
3. 控制线程池大小，线程过多会增加上下文切换。
4. 避免忙等，轮询要加阻塞等待、退避或事件通知。

### 2.3 I/O 和网络

1. 非阻塞 I/O + epoll，避免线程卡在慢连接上。
2. 批量读写、批量刷日志，减少系统调用次数。
3. 大文件传输考虑 `sendfile`、mmap、零拷贝。
4. 小包低延迟场景评估 `TCP_NODELAY`，吞吐场景评估批量发送。

### 2.4 编译和运行时

1. 开启合理优化级别，例如 `-O2`。
2. 保留符号，方便 perf 和火焰图定位。
3. 对 C++ 服务关注内存分配器，必要时评估 jemalloc、tcmalloc。
4. 对频繁日志使用异步日志、采样日志或日志级别开关。

## 3. CPU 优化案例回答

可以按下面结构回答：

```text
现象 -> 定位工具 -> 热点函数 -> 根因 -> 优化方案 -> 指标结果
```

示例：

1. `top -H` 发现某个 worker 线程长期占满 CPU。
2. `perf record/report` 看到热点集中在 JSON 序列化和字符串拼接。
3. 进一步看代码发现每条消息重复构造相同字段。
4. 优化为预生成静态字段、批量序列化和减少临时对象。
5. 再压测对比 P99、CPU 使用率和 QPS。

## 4. 条件断点为什么慢

条件断点慢的原因是：程序每次执行到断点位置都要陷入调试器，由调试器读取变量、求值条件，再决定是否真正停下。即使条件不满足，也已经发生了断点陷入和调试器交互。

在高频循环、网络收包、渲染帧循环、排序比较器等路径上设置复杂条件断点，会让程序慢几个数量级。

## 5. 条件断点慢怎么解决

常见替代方案：

1. **把条件写进代码**：临时加 `if (cond) __builtin_trap();`、`DebugBreak()` 或日志。
2. **降低命中频率**：把断点下沉到更靠近问题的分支，而不是放在大循环入口。
3. **使用命中次数断点**：跳过前 N 次，直接在可疑次数附近停。
4. **使用日志点/tracepoint**：不暂停程序，只打印关键变量。
5. **采样而不是断点**：性能问题用 perf、火焰图、采样 profiler，不用逐次断点。
6. **数据断点/watchpoint**：关注某个变量何时被写坏，但硬件 watchpoint 数量有限。
7. **缩小数据集复现**：构造最小输入，让断点命中次数减少。

C++ 临时代码示例：

```cpp
if (user_id == target_user && state == State::Error) {
    __builtin_trap(); // Linux/Clang/GCC 下触发调试中断
}
```

Windows 下可用：

```cpp
if (cond) {
    DebugBreak();
}
```

## 6. 易错点

1. CPU 高不一定是算法慢，也可能是锁竞争、忙等、日志、系统调用或软中断。
2. 加线程不一定降低 CPU，可能增加调度和锁开销。
3. 条件断点即使“不停下”也可能非常慢，因为每次命中断点位置都要调试器求值。
4. 性能优化要有前后对比指标，否则无法证明收益。
5. 不要在生产环境随意插入会中断进程的调试语句，应使用采样、日志和灰度手段。

## 7. 面试回答模板

优化 CPU 占用我会先定位，不会直接改代码。先用 `top -H` 或 `pidstat -t` 找到高 CPU 线程，再用 `perf` 或火焰图看热点函数，区分是用户态计算、系统调用、锁竞争、上下文切换还是软中断。优化方向包括降低算法复杂度、减少重复计算和内存分配、缩小锁粒度、避免忙等、批量 I/O、异步日志和合理线程池大小。条件断点慢是因为每次执行到断点都要陷入调试器并求值条件，高频路径上代价很大。解决方式是降低断点命中频率，把条件写进代码触发 trap，使用命中次数断点、日志点、watchpoint，或者用 perf 采样替代断点。
