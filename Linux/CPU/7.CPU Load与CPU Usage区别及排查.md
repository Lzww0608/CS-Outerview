# 7. CPU Load 与 CPU Usage 区别及排查

CPU Load（负载）和 CPU Usage（利用率）经常一起出现在 `top`、`uptime`、监控面板里，但它们不是一个概念。面试里要把“有多少任务在排队或不可中断等待”和“CPU 时间被用了多少”区分开。

一句话概括：

```text
CPU Usage = CPU 时间花在哪里
CPU Load  = 有多少任务正在运行、等待运行，或卡在不可中断等待
```

## 1. CPU Usage 是什么

CPU Usage 表示一段时间内 CPU 时间的使用比例。`top`、`mpstat`、`pidstat` 常见字段包括：

| 指标 | 含义 | 常见原因 |
| --- | --- | --- |
| `us` | 用户态 CPU | 业务计算、序列化、压缩、加密、JSON、正则 |
| `sy` | 内核态 CPU | 系统调用频繁、网络协议栈、文件 I/O、锁和调度 |
| `wa` | iowait | 等块设备 I/O，常见于磁盘、网络盘、page cache 回写 |
| `hi` | 硬中断 | 网卡、磁盘控制器等硬件中断 |
| `si` | 软中断 | 网络收包、协议栈、定时器等软中断 |
| `st` | steal time | 虚拟机环境中 CPU 被宿主机拿走 |
| `id` | idle | CPU 空闲 |

如果 CPU Usage 很高，通常表示 CPU 时间真的被消耗了：

1. `us` 高：业务代码或用户态库在消耗 CPU。
2. `sy` 高：内核态开销高，可能是系统调用、网络包、锁或文件系统。
3. `si/hi` 高：中断压力高，常见于小包网络流量或设备中断。
4. `wa` 高：CPU 统计上在等 I/O，不是用户态计算忙。
5. `st` 高：云主机或虚拟机宿主机争抢 CPU。

单进程 `%CPU` 可能超过 `100%`。在 `top` 的常见口径里，一个 CPU 核是 `100%`，多线程进程跑满 4 个核可能接近 `400%`。

## 2. CPU Load 是什么

Load Average 表示一段时间内系统平均活跃任务数量。`uptime` 和 `top` 第一行会显示 1 分钟、5 分钟、15 分钟负载：

```text
load average: 12.30, 8.70, 5.10
```

Linux 的 load average 统计的不只是正在使用 CPU 的任务，通常包括：

1. `R` 状态：正在运行或等待 CPU 的任务。
2. `D` 状态：不可中断睡眠任务，常见于磁盘 I/O、网络文件系统、块设备、某些内核等待。

所以 Load 更像“调度压力 + 不可中断等待压力”的综合指标，而不是 CPU 使用率。

判断 Load 高不高要结合 CPU 核数：

| 机器 | Load 含义示例 |
| --- | --- |
| 1 核 Load=1 | 大致刚好有一个任务需要 CPU 或不可中断等待 |
| 4 核 Load=4 | 大致接近满载，但要看 CPU usage 和 D 状态 |
| 4 核 Load=20 | 明显有大量任务排队或卡住 |
| 64 核 Load=20 | 不一定高，可能还有 CPU 余量 |

Load 的趋势也重要：

1. 1 分钟高、15 分钟低：最近突增。
2. 1/5/15 分钟都高：持续压力。
3. Load 高但 CPU idle 也高：重点怀疑 D 状态 I/O 等待或内核等待。

## 3. 高 Load 代表什么

高 Load 代表系统中活跃任务多，任务可能在抢 CPU，也可能在不可中断等待。

常见组合：

| 现象 | 可能含义 |
| --- | --- |
| Load 高，CPU usage 高，`r` 高 | CPU 真的饱和，任务排队等 CPU |
| Load 高，CPU usage 低，`b` 高，`D` 多 | 大量任务卡在不可中断 I/O 等待 |
| Load 高，`wa` 高 | 磁盘、网络存储、块设备 I/O 慢 |
| Load 高，`st` 高 | 虚拟化宿主机 CPU 争抢 |
| Load 高，单核 100%，其他核空闲 | 单线程瓶颈、CPU 亲和性、锁串行、队列倾斜 |
| Load 高，线程数暴涨 | 线程池无界、请求堆积、阻塞调用扩散 |

高 Load 不一定说明 CPU 不够。它只能说明系统里“想运行或卡住不能中断的任务很多”。下一步必须区分这些任务到底在 `R` 还是 `D`。

## 4. 高 CPU Usage 代表什么

高 CPU Usage 表示 CPU 时间被实际消耗。它可能是正常负载，也可能是异常热点。

常见原因：

1. **业务计算密集**：排序、压缩、加密、JSON、正则、复杂算法。
2. **死循环或忙等**：while 空转、锁自旋、无退避重试。
3. **锁竞争和上下文切换**：线程太多、频繁唤醒、竞争热点锁。
4. **系统调用频繁**：小包网络、频繁日志、频繁文件读写。
5. **网络软中断高**：小包 PPS 高、RSS/RPS 配置不均、单核软中断打满。
6. **GC 或运行时开销**：Java/Go/Python 等运行时回收、调度、解释器开销。
7. **虚拟化 steal**：业务拿不到足够 CPU 时间。

排查高 CPU Usage 要用线程级和调用栈：

```bash
top -H -p <pid>
pidstat -t -p <pid> 1
perf top -p <pid>
perf record -F 99 -p <pid> -g -- sleep 30
perf report
```

## 5. CPU 利用率低但 Load 很高的原因

这是面试重点。低 CPU 高 Load 通常说明：**不是 CPU 正在忙，而是很多任务被计入 Load，但没有真正消耗 CPU**。

最常见原因如下。

### 5.1 大量 D 状态不可中断 I/O 等待

`D` 状态任务会计入 Load，但它们不消耗 CPU。常见来源：

1. 磁盘 I/O 慢或磁盘故障。
2. NFS、Ceph、NAS、云盘等网络存储卡住。
3. 文件系统元数据锁或 journal 卡住。
4. Page Cache 脏页回写阻塞。
5. swap 换入换出。
6. 块设备队列满。
7. 内核驱动或存储路径异常。

典型现象：

```text
load average 很高
%Cpu(s) 里 id 仍然不低
wa 可能高
ps 里很多进程 STAT=D
```

### 5.2 线程池大量阻塞

应用线程池过大或无界，遇到慢下游时很多线程同时阻塞。即使它们不消耗 CPU，也可能造成 Load 上升。

常见阻塞点：

1. 数据库慢查询。
2. Redis、MQ、RPC、HTTP 下游超时。
3. 同步日志刷盘。
4. 文件锁、分布式锁、futex 等等待。
5. 连接池等待。

如果阻塞最终落到可中断睡眠 `S`，它通常不计入 Load；如果落到不可中断等待或频繁变成 runnable，就可能推高 Load。工程上仍要查线程栈和等待点。

### 5.3 I/O wait 高但 CPU 计算低

`wa` 高表示 CPU 有空闲时间，但这段时间系统有任务在等块 I/O 完成。它常和高 Load 一起出现。

常见原因：

1. 磁盘 util 接近 100%。
2. await 很高，单次 I/O 延迟大。
3. 数据库或日志大量随机写。
4. 内存不足导致频繁 swap。
5. 云盘性能额度耗尽。

### 5.4 短时大量任务排队

瞬时流量、定时任务、批处理、重试风暴会让 runnable 任务短时暴涨。此时 CPU usage 可能还没来得及持续升高，Load 的 1 分钟值先升。

排查要看：

1. 1 分钟 Load 是否远高于 5/15 分钟。
2. 请求量、队列长度、线程数是否突增。
3. 是否有定时任务、批处理、重试放大。

### 5.5 容器和 cgroup 口径问题

容器里看到的 CPU 核数、Load、CPU quota 可能不一致。

例子：

```text
宿主机 64 核
容器 CPU quota = 2 核
容器内看到 load = 8
```

如果按 64 核判断，会误以为 Load 不高；但对容器可用的 2 核来说，Load 8 已经很高。Kubernetes 里还要看 CPU limit、throttling、node pressure。

### 5.6 虚拟化 steal time

云主机里 `st` 高表示虚拟 CPU 想运行，但物理 CPU 被宿主机调度给其他虚拟机。此时应用可能感觉慢，Load 可能升高，但本机 CPU usage 看起来不一定高。

## 6. 排查思路

### 6.1 先看整机

```bash
uptime
top
vmstat 1
mpstat -P ALL 1
```

重点看：

1. Load 的 1/5/15 分钟趋势。
2. CPU 核数和可用 CPU quota。
3. `us/sy/id/wa/si/hi/st`。
4. `vmstat` 的 `r` 和 `b`。

`vmstat` 里：

| 字段 | 含义 |
| --- | --- |
| `r` | runnable 队列，正在运行或等待 CPU 的任务数 |
| `b` | blocked，不可中断睡眠任务数 |
| `wa` | I/O wait |
| `si/so` | swap in/out |
| `cs` | context switch |
| `in` | interrupts |

判断：

1. `r` 高、`id` 低：CPU 饱和。
2. `b` 高、`wa` 高：I/O 或 D 状态等待。
3. `st` 高：虚拟化争抢。
4. `cs` 高：线程切换和锁竞争可能严重。

### 6.2 找 D 状态任务

```bash
ps -eo pid,ppid,stat,wchan:32,comm,args | awk '$3 ~ /D/ {print}'
```

看：

1. 哪些进程/线程处于 `D`。
2. `wchan` 卡在哪个内核等待点。
3. 是否集中在某个业务、数据库、日志、备份、NFS、云盘进程。

也可以看单个进程：

```bash
ps -L -o pid,tid,stat,wchan:32,comm -p <pid>
cat /proc/<pid>/stack
```

`/proc/<pid>/stack` 需要权限，并且对用户态阻塞不一定有完整信息，但对内核等待点很有价值。

### 6.3 查磁盘和块设备

```bash
iostat -xz 1
pidstat -d 1
iotop
df -h
dmesg -T | egrep -i "error|timeout|reset|blk|nvme|scsi|ext4|xfs"
```

关注：

1. `%util` 是否接近 100%。
2. `await` 是否很高。
3. `r/s`、`w/s`、`rkB/s`、`wkB/s` 是否异常。
4. 是否有磁盘错误、超时、reset。
5. 是否有某个进程 I/O 很高。

如果是云盘，要看云厂商监控里的 IOPS、吞吐、burst credit、队列深度和限速。

### 6.4 查内存和 swap

```bash
free -h
vmstat 1
sar -B 1
cat /proc/meminfo
```

关注：

1. `available` 是否很低。
2. `si/so` 是否持续非 0。
3. major page fault 是否增加。
4. 是否触发 direct reclaim、kswapd 高 CPU 或 OOM。

内存不足会导致换页和回收，表现可能是 CPU 利用率不高但 Load、延迟和 I/O wait 都很高。

### 6.5 查网络和远程存储

如果使用 NFS、Ceph、对象存储挂载、分布式文件系统或远程块设备，要继续看网络：

```bash
ss -s
sar -n DEV,TCP,ETCP 1
ethtool -S eth0
ping <storage-or-db>
tcpdump -i eth0 host <ip>
```

关注：

1. TCP 重传、丢包、连接超时。
2. 网卡 drop、error。
3. 网络存储服务端是否慢。
4. DNS、VIP、负载均衡是否异常。

### 6.6 查应用线程和锁

```bash
top -H -p <pid>
pidstat -t -p <pid> 1
pstack <pid>
jstack <pid>      # Java
go tool pprof     # Go
perf sched timehist
perf lock report
```

关注：

1. 线程数是否暴涨。
2. 是否大量线程等待同一把锁。
3. 是否大量线程阻塞在数据库、RPC、文件 I/O、日志、连接池。
4. 是否有无界队列和重试风暴。

## 7. 典型案例

### 7.1 磁盘慢导致低 CPU 高 Load

现象：

```text
Load 80
CPU idle 60%
wa 35%
大量进程 D 状态
iostat await 很高
```

结论：CPU 不是瓶颈，任务在等磁盘。处理方向是查慢盘、云盘额度、日志刷盘、数据库 I/O、文件系统错误，而不是盲目加 CPU。

### 7.2 NFS 卡住导致 Load 飙升

现象：

```text
业务 CPU 不高
Load 持续上升
ps 看到大量 D 状态
wchan 指向 nfs/rpc 相关等待
```

处理方向：

1. 查 NFS 服务端健康。
2. 查网络丢包和重传。
3. 评估挂载参数、超时、重试。
4. 避免核心请求路径同步依赖网络文件系统。

### 7.3 线程池阻塞导致队列堆积

现象：

```text
CPU 不高
Load 上升
线程数上升
连接池等待和下游超时增加
```

处理方向：

1. 给线程池和连接池设置上限。
2. 设置合理超时和熔断。
3. 对慢下游隔离线程池。
4. 减少同步等待，核心链路降级。

## 8. 处理方案

不同根因对应不同处理：

| 根因 | 处理方向 |
| --- | --- |
| CPU 饱和 | 优化热点、扩容 CPU、减少锁竞争、降低算法复杂度 |
| 磁盘 I/O 慢 | 优化 SQL/日志、加索引、批量写、换盘、提升云盘规格 |
| 网络存储卡住 | 查服务端、网络、挂载参数，把核心链路从网络盘移出 |
| 内存不足和 swap | 降低内存占用、限制缓存、扩内存、调整 cgroup、减少 swap |
| 线程池阻塞 | 有界队列、隔离、超时、熔断、减少同步调用 |
| 单核瓶颈 | 分片、多线程、调整亲和性、优化锁和事件分发 |
| 虚拟化 steal | 换宿主机、升级实例、独享型资源、联系云厂商 |

## 9. 易错点

1. Load 不等于 CPU 使用率，高 Load 不一定要加 CPU。
2. Linux Load 会统计 D 状态任务，所以 I/O 卡住也会让 Load 很高。
3. `wa` 高说明在等块 I/O，不代表业务代码在消耗 CPU。
4. 单进程 CPU 超过 100% 是正常的，表示使用了多个核。
5. 容器里判断 Load 要结合 CPU quota，不是只看宿主机核数。
6. `top` 只能初筛，低 CPU 高 Load 必须继续看 `vmstat`、D 状态、`iostat`、线程栈和内核等待点。
7. D 状态进程通常不能被普通信号立即杀死，要先解决它等待的内核资源。

## 10. 面试回答模板

CPU Usage 表示 CPU 时间被使用的比例，能告诉我 CPU 时间花在用户态、内核态、iowait、中断还是 steal 上；CPU Load 表示一段时间内活跃任务数量，在 Linux 里通常包括正在运行或等待 CPU 的 `R` 状态任务，以及不可中断睡眠的 `D` 状态任务。所以高 CPU Usage 代表 CPU 时间真的被消耗，高 Load 代表系统里排队或卡住的任务很多，不一定是 CPU 忙。

如果 CPU 利用率低但 Load 很高，我会优先怀疑大量任务处于 `D` 状态或 I/O 等待，例如磁盘慢、NFS/Ceph/云盘卡住、swap、文件系统问题、线程池阻塞在慢下游。排查时先用 `uptime/top/vmstat 1/mpstat` 看 load、`r/b`、`us/sy/id/wa/st`；如果 `b` 和 `wa` 高，就用 `ps` 找 D 状态任务，看 `wchan` 和 `/proc/<pid>/stack`，再用 `iostat -xz 1`、`pidstat -d`、`iotop`、`dmesg` 查磁盘和块设备；如果是应用阻塞，则用 `top -H`、`pstack/jstack/pprof` 看线程栈、连接池和下游超时。处理方案要按根因来，CPU 饱和才加 CPU，I/O 或 D 状态导致的高 Load 要解决存储、网络、内存或阻塞链路。
