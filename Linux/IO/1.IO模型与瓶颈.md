# 1. I/O 模型与瓶颈

I/O 模型描述应用线程、内核和设备之间如何协作完成读写。面试里要区分“就绪通知”和“完成通知”：`epoll` 通知 fd 可读写，但真正的数据复制仍由应用调用 `read/write` 完成；异步 I/O 则更强调提交后由内核或运行时完成，完成后通知应用。

## 常见 I/O 模型

| 模型 | 含义 | 典型接口 |
| --- | --- | --- |
| 阻塞 I/O | 没有数据时线程睡眠，直到 I/O 完成或出错 | blocking `read/recv` |
| 非阻塞 I/O | 没准备好立即返回 `EAGAIN` | `O_NONBLOCK` |
| I/O 多路复用 | 一个线程等待多个 fd 就绪 | `select/poll/epoll` |
| 信号驱动 I/O | fd 就绪时发信号通知 | `SIGIO` |
| 异步 I/O | 提交请求后返回，完成后通知 | POSIX AIO、Linux AIO、`io_uring` |

## 同步 I/O 与异步 I/O

同步和异步的关键区别不是“调用会不会阻塞”，而是数据拷贝和 I/O 完成这件事由谁来等。

按 POSIX 语义理解：

1. **同步 I/O**：真正的 I/O 操作完成前，调用方要参与等待。阻塞 I/O、非阻塞 I/O、I/O 多路复用都属于同步 I/O，因为最终仍由应用线程调用 `read/write` 完成数据拷贝。
2. **异步 I/O**：应用提交请求后返回，内核或运行时完成 I/O 和数据拷贝，完成后再通知应用取结果。

容易混淆的几组概念：

| 概念 | 判断标准 |
| --- | --- |
| 阻塞 / 非阻塞 | 发起调用时，如果条件不满足，线程是否睡眠等待 |
| 同步 / 异步 | I/O 完成和数据拷贝是否由调用方等待完成 |
| 就绪通知 | fd 现在可读可写，但应用还要自己读写 |
| 完成通知 | I/O 已经完成，应用拿结果或处理回调 |

所以 `epoll` 常被工程上称作异步事件驱动，但严格说它是同步非阻塞 I/O 的就绪通知机制；`io_uring`、Windows IOCP 更接近完成通知模型。

## 异步 I/O 都有哪些

1. **POSIX AIO**：接口跨平台，但 Linux 上实现和适用场景有限。
2. **Linux native AIO**：主要面向 direct I/O，接口复杂，生态不如 `epoll` 和 `io_uring`。
3. **io_uring**：通过提交队列 SQ 和完成队列 CQ 批量提交/回收 I/O，减少系统调用和上下文切换；可以覆盖文件、网络、定时器等更多操作。
4. **Windows IOCP**：典型完成端口模型，应用收到的是完成事件。
5. **语言运行时封装**：例如 libuv、Boost.Asio、Go netpoller，底层可能是 epoll/kqueue/IOCP/io_uring 的组合。

严格说，`select/poll/epoll` 是同步非阻塞 + 就绪通知，不是完成式异步 I/O。

## 异步 I/O 的资源生命周期

异步 I/O 的难点不是“提交后返回”，而是提交请求后，缓冲区、连接对象、回调上下文还能不能安全存活到完成事件到来。

常见做法：

1. **引用计数**：请求提交前给连接上下文或 buffer 增加强引用，完成回调里释放。C++ 可以用 `shared_ptr` 或自研 intrusive refcount。
2. **所有权转移**：把任务对象移动到 I/O 框架或线程池，完成后由框架销毁，调用方不再访问。
3. **完成队列通知**：io_uring CQE、IOCP completion、future/promise、事件循环任务队列都可以表示“资源可以回收或进入下一状态”。
4. **取消协议**：连接关闭或超时时，先标记 closing，再取消未完成 I/O；完成事件迟到时看到状态已关闭，只做清理不再执行业务回调。
5. **统一线程归属**：连接状态只在所属 event loop 修改，其他线程通过任务队列投递操作，减少跨线程释放竞争。

示例状态机：

```text
submit read
  -> context ref +1
  -> completion event
  -> process result or ignore canceled result
  -> context ref -1
```

易错点：

1. 不能把栈上 buffer 提交给异步 I/O 后立即返回，完成时栈帧已经失效。
2. 不能关闭 fd 后假设没有完成事件，内核或运行时可能仍返回取消、错误或部分完成结果。
3. 回调里不要无条件访问业务对象，要先判断连接状态、请求版本或 cancellation token。
4. 队列积压会延长资源生命周期，导致内存上涨，所以异步系统也需要背压。

## I/O 的瓶颈在哪里

I/O 瓶颈要按链路拆：

1. **设备瓶颈**：磁盘 IOPS、吞吐、fsync 延迟，网卡带宽和 PPS。
2. **内核开销**：系统调用、上下文切换、中断、协议栈处理、内核锁竞争。
3. **数据拷贝**：用户态/内核态拷贝，协议栈 buffer 拷贝，日志格式化拷贝。
4. **队列排队**：线程池队列、磁盘队列、网卡队列、连接池队列。
5. **应用处理**：序列化、压缩、加密、JSON 解析、日志格式化、锁竞争。
6. **远端依赖**：数据库、缓存、RPC 下游慢，导致本地 I/O 线程被占满。

## 优化思路

1. 网络服务用非阻塞 fd + epoll/io_uring + 应用层缓冲区，避免一连接一线程。
2. 批量读写、批量提交、批量刷盘，减少系统调用和 fsync 次数。
3. 使用零拷贝能力，例如 `sendfile`、`splice`、mmap、DMA、`io_uring` registered buffer。
4. 日志、指标、埋点异步化，避免主链路同步刷盘。
5. 控制队列长度和超时，防止慢下游把线程池打满。
6. 通过压测和观测定位瓶颈：CPU、iowait、磁盘 util、网络重传、队列长度、P99 延迟。

## 阻塞 I/O 服务器怎么设计

阻塞 I/O 不是不能做服务器，关键是要限制阻塞范围，避免一个慢连接拖住整个进程。

常见模型：

1. **单进程单线程阻塞 I/O**：实现最简单，一次只能服务一个连接，只适合教学或极低并发。
2. **一连接一进程**：主进程 `accept` 后 `fork` 子进程处理连接。隔离性好，但进程开销大。
3. **一连接一线程**：主线程 `accept`，每个连接交给一个线程阻塞读写。编程直观，但高并发下线程数、栈内存和调度成本很高。
4. **线程池 + 阻塞队列**：固定 worker 数量，连接或请求进入队列，避免无限创建线程。
5. **prefork/prethread**：提前创建进程或线程，减少请求到来时创建成本。

早期 Apache 的典型 MPM：

1. **prefork MPM**：预先 fork 多个进程，每个进程一次处理一个连接。隔离性强，兼容非线程安全模块，但内存占用高。
2. **worker MPM**：多进程 + 每进程多线程，一个线程处理一个连接，资源利用率比 prefork 好。
3. **event MPM**：把 keep-alive 空闲连接从工作线程中拆出来，用事件机制管理空闲连接，降低长连接占用线程的问题。

阻塞模型的核心问题是：阻塞点会占住执行单元。连接数少、业务简单时它很稳；连接数大、慢客户端多、长连接多时，事件驱动模型更合适。

## 阻塞 I/O 和事件驱动的选择

1. 业务连接数低、开发速度优先，可以用阻塞 I/O + 线程池。
2. 长连接、慢连接、高并发接入层，优先非阻塞 I/O + epoll。
3. CPU 密集业务不应放在事件循环里，仍需要 worker pool。
4. 数据库、文件、RPC 等慢依赖要有超时、连接池和队列上限，否则异步化也会堆积。

## 易错点

1. 非阻塞 I/O 不等于异步 I/O。
2. epoll 只能告诉你 fd 就绪，读写仍可能读不完、写不完。
3. I/O 慢不一定是磁盘或网络，也可能是日志格式化、锁竞争、线程池排队。
4. 异步化不是免费午餐，会引入队列积压、内存上涨、乱序和失败重试问题。

## 面试回答模板

Linux 常见 I/O 模型有阻塞、非阻塞、多路复用、信号驱动和异步 I/O。`select/poll/epoll` 是就绪通知，应用还要自己 `read/write`；POSIX AIO、Linux AIO、io_uring、Windows IOCP 更接近完成通知。I/O 瓶颈可能在设备吞吐和延迟、系统调用和上下文切换、内核协议栈、数据拷贝、应用序列化/压缩/加密、线程池队列或远端依赖。优化要先观测定位，再做批量、异步、零拷贝、连接复用和队列治理。
