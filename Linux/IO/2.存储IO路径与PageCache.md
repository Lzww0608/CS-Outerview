# 2. 存储 I/O 路径与 Page Cache

存储面试里问 `pwrite`、direct I/O、buffered I/O、Page Cache、DMA、`io_uring` 和 SPDK，本质是在考一条数据从应用到设备、再从设备回到 CPU 的完整路径，以及每种路径省掉了什么开销、引入了什么约束。

## 1. `pwrite` 的整体流程

`pwrite(fd, buf, len, offset)` 和 `write` 的核心区别是：它显式指定文件偏移，不修改 `struct file` 中共享的 `f_pos`。这使它适合多线程并发写同一个文件的不同偏移。

一次普通 buffered `pwrite` 大致经过：

1. 用户态调用 `pwrite` 进入内核态。
2. 内核根据 `fd` 找到进程 fd 表，再找到打开文件对象 `struct file`、inode 和文件系统操作表。
3. 校验权限、偏移、长度和用户缓冲区地址。
4. 进入 VFS 写路径，调用具体文件系统的 write_iter。
5. 如果是 buffered I/O，把用户数据 `copy_from_user` 到 Page Cache 对应的页中。
6. 标记页为 dirty，写调用可能很快返回。
7. 后台回写线程或 `fsync/fdatasync/sync` 把脏页提交到块层。
8. 文件系统把文件逻辑块映射到设备逻辑块，块层合并、调度请求。
9. NVMe/SATA 驱动提交命令，设备通过 DMA 从内存取数据并写入介质。
10. 设备完成后中断或轮询通知内核，内核更新请求状态。

如果打开文件时使用 `O_DIRECT`，路径会绕过 Page Cache：内核尽量让设备 DMA 直接在用户缓冲区和磁盘之间搬运数据，但通常要求地址、长度和 offset 按块大小对齐。

## 2. Direct I/O 和 Buffered I/O

| 对比项 | Buffered I/O | Direct I/O |
| --- | --- | --- |
| 缓存路径 | 经过 Page Cache | 尽量绕过 Page Cache |
| 数据拷贝 | 用户缓冲区和 Page Cache 之间有 CPU 拷贝 | 可减少一次内核页缓存拷贝 |
| 顺序读 | 受 readahead/page cache 加速，通常很好 | 依赖应用自己做并发和预取 |
| 随机读 | 命中缓存时快，未命中时仍有页缓存管理开销 | 延迟更稳定，不污染 page cache |
| 写入返回 | 写到 Page Cache 后可能返回，持久性依赖刷盘 | 更接近设备 I/O 完成，但仍要看 FUA/fsync/设备缓存 |
| 使用难度 | 简单，适合通用应用 | 需要对齐、缓冲区管理、队列深度控制 |

顺序读场景下，buffered I/O 经常更快或更省心，因为内核能识别顺序访问并提前预读；direct I/O 如果只是单线程小块读，可能反而慢。数据库、KV 引擎和自研存储更常用 direct I/O，是因为它们自己管理 buffer pool/cache，希望避免“数据库缓存 + Page Cache”双缓存，并减少 page cache 污染。

## 3. Page Cache 预读机制

Page Cache 是内核用空闲内存缓存文件页的机制。顺序读时，内核会维护每个文件访问流的 readahead 状态，发现连续页被访问后，把后续页提前提交 I/O。

常见影响因素：

1. 文件访问是否呈现顺序模式。
2. 块设备 readahead 参数，例如 `/sys/block/<dev>/queue/read_ahead_kb`。
3. 应用是否调用 `posix_fadvise(fd, 0, 0, POSIX_FADV_SEQUENTIAL)` 或 `POSIX_FADV_RANDOM`。
4. 内存压力和 page cache 回收。
5. cgroup 内存限制。

Page Cache 的大小不是由某个固定配置单独决定的。Linux 会把未被应用使用的内存尽量用于文件缓存，在应用需要内存时回收干净缓存页；脏页则受 `vm.dirty_ratio`、`vm.dirty_background_ratio` 等参数影响，需要先回写再回收。

## 4. 从磁盘到 CPU L1 Cache 的数据路径

以 buffered read 为例：

```text
SSD/NVMe
  -> 设备 DMA 写入内存中的 Page Cache 页
  -> 内核 copy_to_user 拷贝到用户缓冲区
  -> CPU 执行用户代码读取这段内存
  -> Cache line 被加载到 L3/L2/L1
```

几个关键点：

1. DMA 负责设备和主内存之间的数据搬运，不需要 CPU 一个字节一个字节复制。
2. DMA 写入内存不等于数据自动进入 CPU L1 Cache。CPU 真正访问这段地址时，才按 cache line 从内存或 LLC 拉到 L1。
3. 现代平台有 cache coherency 机制，设备 DMA 和 CPU cache 之间要通过一致性协议、cache flush/invalidate 或 IOMMU 配合，避免 CPU 看到旧数据。
4. direct I/O 可以让 DMA 直接面向用户页，但这些页通常要 pin 住，避免 I/O 过程中被换出或移动。

同步 I/O 下，CPU 不一定一直忙等。阻塞 read/write 通常会让线程睡眠，CPU 去运行别的任务；但提交系统调用、文件系统路径、拷贝、校验、完成中断处理仍然消耗 CPU。如果使用轮询模式，CPU 可能主动忙等完成事件，以换取更低延迟。

## 5. `io_uring` 相比 Linux AIO 好在哪里

传统 Linux native AIO 主要服务 direct I/O，接口割裂，很多操作仍可能退化或受限制。`io_uring` 的核心改进是用共享内存队列连接用户态和内核态：

1. **减少系统调用**：应用把多个 SQE 放入提交队列，一次 submit 批量提交；完成结果批量从 CQE 读取。
2. **减少上下文切换**：开启 SQPOLL 后，内核线程轮询提交队列，用户线程提交时可减少陷入内核。
3. **统一操作类型**：文件、socket、timeout、fsync、accept 等可以进入同一套完成队列模型。
4. **注册资源**：registered files、registered buffers 减少 fd 查找、页 pin 和地址校验开销。
5. **更适合批量和高队列深度**：数据库、日志系统、代理服务可以把多个 I/O 合并提交。

但 `io_uring` 不是自动更快。它要求较新内核，接口复杂度更高，不同文件系统和驱动支持程度不同，错误处理、取消和生命周期管理也更难。

## 6. `io_uring` polling 模式和 SPDK

| 对比项 | `io_uring` polling | SPDK |
| --- | --- | --- |
| 所在层次 | 仍走 Linux 内核块层/文件系统能力 | 用户态 NVMe 驱动，绕过内核块层 |
| 轮询对象 | SQPOLL/IOPOLL 轮询提交或完成 | 用户态线程轮询 NVMe 队列 |
| 数据路径 | 仍可使用文件系统、权限、page cache/direct I/O 语义 | 通常面向裸设备或用户态存储栈 |
| 开发复杂度 | 中等，保留内核生态 | 高，需要自己处理更多存储栈能力 |
| 延迟 | 比普通中断模型更低 | 极低，适合极致 NVMe 性能 |
| CPU 占用 | 轮询线程会消耗 CPU | 通常固定核心忙轮询 |

如果业务需要文件系统语义、较好可维护性和通用 Linux 部署，优先考虑 `io_uring`。如果是自研存储引擎、裸 NVMe、追求极低延迟和极高 IOPS，并能接受独占 CPU、绑核、NUMA 和用户态驱动复杂度，才考虑 SPDK。

## 7. SSD Cache 对性能测试的影响

SSD 内部可能有 DRAM cache、SLC cache、FTL 映射缓存和写缓冲；操作系统还有 Page Cache。短时间测试很容易测到缓存性能，而不是介质稳态性能。

更可靠的压测做法：

1. 用 `fio` 明确 `direct=1` 或说明 buffered 测试目的。
2. 测试前做 precondition，把盘写到稳态，避免只测空盘 SLC cache。
3. 测试时间足够长，观察吞吐和 P99/P999 延迟是否在 SLC cache 耗尽后下降。
4. 区分顺序/随机、读/写、块大小、队列深度、线程数。
5. buffered 测试前按场景决定是否 `echo 3 > /proc/sys/vm/drop_caches`，但不要在线上随意执行。
6. 对持久性敏感的写测试要区分 `fsync`、`fdatasync`、FUA、设备断电保护和磁盘写缓存。

## 8. 面试回答模板

`pwrite` 会通过 fd 找到内核打开文件对象和 inode，但它使用显式 offset，不修改共享文件偏移。buffered I/O 先写入或读取 Page Cache，顺序读能利用 readahead，适合通用场景；direct I/O 绕过 Page Cache，减少双缓存和缓存污染，但要求对齐和应用自己管理缓存、并发和预取。磁盘到内存主要靠 DMA，数据不会自动进入 L1，CPU 访问时才进入缓存层级。`io_uring` 用 SQ/CQ 共享队列、批量提交、注册资源和 polling 减少系统调用、上下文切换和页管理开销；SPDK 更进一步绕过内核块层，延迟更低但复杂度和 CPU 成本更高。
