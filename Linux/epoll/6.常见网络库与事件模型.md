# 6. 常见网络库与事件模型

面试问“看过哪些网络库”，重点不是罗列名字，而是说明它们解决了什么问题、底层事件模型是什么、连接和回调如何组织。

## 1. 网络库要解决什么

一个成熟网络库通常封装这些能力：

1. socket 创建、监听、连接、关闭。
2. 非阻塞 I/O 和 I/O 多路复用。
3. 事件循环和回调分发。
4. 输入/输出缓冲区，处理半包、粘包、部分写。
5. 定时器和连接超时。
6. 线程模型，例如 one loop per thread、线程池、主从 Reactor。
7. 协议编解码和应用层 handler。
8. 错误处理、资源释放、日志和指标。

## 2. 常见网络库

| 网络库 | 语言/生态 | 典型模型 | 特点 |
| --- | --- | --- | --- |
| Muduo | C++ | Reactor + epoll | one loop per thread，接口清晰，适合学习 C++ 网络库设计 |
| libevent | C | Reactor | 跨平台，封装 select/poll/epoll/kqueue，事件、定时器、buffer 较完整 |
| libev | C | Reactor | 更轻量，关注事件循环核心 |
| libuv | C | Reactor + 线程池 | Node.js 底层库，跨平台，文件 I/O 等阻塞任务交给线程池 |
| Boost.Asio | C++ | Proactor 风格接口 | 异步操作抽象统一，可基于 epoll、IOCP 等后端 |
| Netty | Java | Reactor | NIO 事件循环、pipeline、codec 体系成熟 |
| Nginx | C | 多进程事件驱动 | 高性能代理服务器，事件模块可适配 epoll/kqueue |

## 3. Muduo 的典型设计

Muduo 是 C++ 后端面试常见网络库，核心对象可以这样理解：

```text
EventLoop
  -> Poller/EpollPoller
  -> Channel
  -> TcpServer
  -> TcpConnection
  -> Buffer
```

1. `EventLoop` 表示事件循环，通常一个线程一个 loop。
2. `Channel` 封装 fd 及其关注事件、回调函数。
3. `Poller` 封装 epoll，负责等待就绪事件。
4. `TcpConnection` 管理连接生命周期、读写缓冲区和业务回调。
5. `Buffer` 处理字节流，解决半包、粘包和部分写。

Muduo 的核心思想是：I/O 事件在所属 EventLoop 线程内处理，跨线程操作通过任务队列投递回对应 loop，避免多个线程同时操作同一个连接对象。

## 3.1 Muduo 请求生命周期与线程切换

一次典型 TCP 请求在 Muduo 中可以按这条链路理解：

```text
Acceptor 接收新连接
-> TcpServer 从 EventLoopThreadPool 选择一个 sub loop
-> 在 sub loop 中创建 TcpConnection 和 Channel
-> epoll_wait 返回可读事件
-> Channel 调用 TcpConnection::handleRead
-> 数据读入 Buffer
-> messageCallback 做协议解析和业务分发
-> send 写入输出 Buffer
-> 必要时关注 EPOLLOUT
-> 写完后关闭 EPOLLOUT 或触发 writeCompleteCallback
```

这里有几个面试高频点：

1. `Acceptor` 只负责监听 fd 和 `accept`，真正连接通常分配给子 `EventLoop`。
2. `EventLoopThreadPool` 体现 one loop per thread，每个连接归属于固定 loop，减少锁竞争。
3. 跨线程调用连接方法时，不能直接改 fd 状态，而要通过 `runInLoop` 或 `queueInLoop` 投递到归属 loop。
4. `queueInLoop` 需要唤醒正在 `epoll_wait` 的线程，Muduo 通常用 `eventfd` 做跨线程唤醒。
5. `TcpConnection` 常用 `shared_ptr` 管理生命周期，用 `weak_ptr` 防止 Channel 回调时对象已释放。
6. 业务如果很耗 CPU，不应长时间阻塞 I/O loop，而是投递到业务线程池，处理完成后再把结果投递回 loop 发送。

易错点是把 Muduo 理解成“多线程同时读写一个连接”。它的设计恰恰相反，同一连接的 I/O 状态由一个 loop 串行维护，跨线程只提交任务，从而把复杂并发问题收敛到任务队列和唤醒机制上。

## 4. Reactor 和网络库

Linux 上大多数高性能网络库以 Reactor 为基础：

```text
epoll_wait 返回 fd 就绪
-> EventLoop 找到对应 Channel
-> 调用 read/write 回调
-> 数据进入 Buffer
-> 协议解析后触发业务 handler
-> 输出写入发送缓冲区
-> 必要时关注 EPOLLOUT
```

这里的“异步”通常指事件驱动和非阻塞，不等于内核完成了读写。真正的 `read/write` 仍由应用线程执行。

## 5. 如何选择网络库

1. **学习 C++ Reactor**：Muduo 结构清晰，适合解释 one loop per thread、Channel、Buffer。
2. **跨平台 C 事件库**：libevent/libuv 更合适。
3. **C++ 异步接口统一**：Boost.Asio 适合需要 TCP、UDP、定时器、协程适配的项目。
4. **Java 后端高并发网络**：Netty 生态成熟，适合 RPC、网关、长连接。
5. **代理和静态资源服务**：Nginx 是生产级参考，但模块和配置体系更复杂。

## 6. 易错点

1. epoll 不是网络库，它只是 Linux I/O 多路复用机制。
2. 非阻塞 I/O 不是异步 I/O，Reactor 通知的是就绪事件。
3. 网络库必须处理部分读、部分写和应用层消息边界。
4. `EPOLLOUT` 不应长期关注，只有发送缓冲区有待写数据时再打开。
5. 多线程网络库要明确连接归属线程，否则容易出现 fd 并发读写和生命周期问题。

## 7. 面试回答模板

我了解的网络库可以按事件模型讲。C++ 里 Muduo 是典型 Reactor 网络库，一个 EventLoop 绑定一个线程，Channel 封装 fd 和回调，Poller 封装 epoll，TcpConnection 维护连接和缓冲区；libevent/libuv 提供跨平台事件循环，Netty 是 Java NIO 的成熟 Reactor 框架，Boost.Asio 用统一异步接口封装不同平台后端。它们共同解决的是非阻塞 I/O、事件分发、缓冲区、定时器、连接生命周期和线程模型问题。
