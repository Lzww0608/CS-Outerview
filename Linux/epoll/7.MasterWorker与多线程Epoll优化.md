# 7. Master/Worker 与多线程 epoll 优化

高并发网络服务常见两种组织方式：多进程 master/worker 和多线程 Reactor。Nginx 是典型的 master/worker 多进程事件驱动模型；很多 C++ WebServer 则使用 one loop per thread 的多线程 Reactor。

## 1. Master/Worker 架构

Master 进程通常不处理具体请求，而是负责管理。

Master 常见职责：

1. 读取和校验配置。
2. 创建监听 socket。
3. fork 多个 worker。
4. 处理信号，例如 reload、stop、graceful shutdown。
5. 监控 worker，异常退出后拉起新 worker。
6. 平滑升级时管理新旧 worker 切换。

Worker 常见职责：

1. 继承或接收监听 fd。
2. 运行事件循环，例如 `epoll_wait`。
3. `accept` 新连接。
4. 处理读写事件、定时器和连接状态。
5. 执行业务逻辑或把耗时任务投递给线程池。

这种架构的优点是隔离性好。某个 worker 崩溃不会直接拖垮 master；reload 时可以启动新 worker，旧 worker 处理完存量连接后退出。

## 2. 多 worker accept 的问题

多个 worker 监听同一个 socket 时，会遇到连接分配和惊群问题。

常见方案：

1. **accept mutex**：一次只允许一个 worker 监听 accept 事件，降低惊群。
2. **SO_REUSEPORT**：每个 worker 创建自己的监听 socket，内核把新连接分配给不同 socket。
3. **主进程 accept 后分发 fd**：master accept，再通过 Unix Domain Socket 把连接 fd 发给 worker。
4. **负载均衡层分发**：前面用 LVS/Nginx/Envoy 把连接分到多个实例。

`SO_REUSEPORT` 简化了多 worker accept，但要注意内核负载均衡可能受四元组 hash 影响，连接分布不一定完全均匀。

## 3. 多线程 epoll 模型

进一步提高 epoll 服务效率，通常不是“所有线程共享一个 epoll 实例一起抢事件”，而是采用 one loop per thread。

常见模型：

```text
main acceptor thread
  -> accept new connection
  -> choose one EventLoop thread
  -> connection fd belongs to that loop

worker EventLoop thread
  -> epoll_wait
  -> read/write connection
  -> run callbacks
```

原则：

1. 一个连接 fd 固定归属一个 EventLoop，减少跨线程锁竞争。
2. 其他线程要操作该连接时，通过队列投递任务到所属 EventLoop。
3. EventLoop 用 `eventfd`、pipe 或 timerfd 唤醒。
4. CPU 密集或阻塞任务进入独立业务线程池，完成后再投递回 EventLoop 写响应。

## 4. 怎么提高 epoll 效率

优化方向：

1. **所有 fd 非阻塞**：读写循环到 `EAGAIN`，避免事件循环卡死。
2. **减少 epoll_ctl**：只在状态变化时关注 `EPOLLOUT`，没有待写数据时不要一直监听写事件。
3. **批量处理事件**：`epoll_wait` 一次取多个事件，应用层批量读写和批量日志。
4. **合理使用 ET/LT**：ET 减少重复通知，但必须循环读写到 `EAGAIN`。
5. **连接归属固定**：避免多个线程同时处理一个 fd。
6. **accept4**：直接设置 `SOCK_NONBLOCK | SOCK_CLOEXEC`，减少额外系统调用和 fd 泄漏风险。
7. **连接和缓冲区复用**：减少频繁分配释放。
8. **定时器管理**：用时间轮、小顶堆或 timerfd 管理超时连接。
9. **避免长回调**：事件循环线程只做轻量逻辑，慢任务交给线程池。
10. **NUMA 和亲和性**：极致场景下让 worker 绑定 CPU，减少跨 NUMA 访问。

## 5. 什么时候用多进程，什么时候用多线程

| 模型 | 优点 | 缺点 | 适用场景 |
| --- | --- | --- | --- |
| 多进程 worker | 隔离性好，崩溃影响小，热重载方便 | 进程间共享状态成本高 | Nginx、代理、静态资源服务 |
| 多线程 Reactor | 共享内存方便，连接调度灵活 | 线程安全和锁竞争更复杂 | C++/Java/Go 应用服务 |
| 多进程 + 多线程 | 隔离和多核利用兼顾 | 架构复杂，调试成本高 | 高性能网关、复杂业务服务 |

真实工程里，网络 I/O 线程数量通常接近 CPU 核数或网卡队列数，业务线程池大小要按 CPU/IO 类型和压测结果调整，不是越多越好。

## 6. 易错点

1. epoll 只通知就绪，不负责真正读写。
2. 阻塞 fd 放进 epoll 仍然可能卡住事件循环。
3. 多线程共享同一个连接 fd 处理读写，容易出现乱序和锁竞争。
4. ET 模式忘记读到 `EAGAIN` 会丢事件感知。
5. 长耗时任务放在 EventLoop 中会拖慢所有连接。
6. 增加线程不一定提高吞吐，可能增加上下文切换、缓存失效和锁竞争。

## 7. 面试回答模板

Master/Worker 架构里 master 主要负责配置、fork worker、信号、reload、监控和拉起 worker，worker 负责 epoll 事件循环、accept、读写和连接生命周期。多个 worker 监听同一个 socket 时要处理 accept 惊群，可以用 accept mutex、`SO_REUSEPORT` 或 master accept 后分发 fd。进一步提高 epoll 效率时，我会采用 one loop per thread，让一个连接固定归属一个 EventLoop，跨线程操作通过队列和 eventfd 唤醒；事件循环只做非阻塞读写和轻量回调，耗时业务交给线程池。优化点包括非阻塞 fd、ET 读到 `EAGAIN`、减少 `epoll_ctl`、批量处理、缓冲区复用、合理定时器和压测调参。
