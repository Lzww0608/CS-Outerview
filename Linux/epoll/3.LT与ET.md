# 3. epoll 的 LT 和 ET

`epoll` 支持两种主要触发模式：水平触发 LT（Level Trigger）和边缘触发 ET（Edge Trigger）。它们的区别在于：fd 处于可读/可写状态时，内核是否会反复通知。

## 水平触发 LT

LT 是默认模式。只要 fd 仍然满足条件，例如接收缓冲区还有数据没读完，`epoll_wait` 就会反复返回这个事件。

优点：

1. 编程简单，不容易漏事件。
2. 即使一次没有读完，下次还会继续收到通知。
3. 适合普通业务服务器、低风险实现、迁移旧代码。

缺点：

1. 如果应用没有及时处理，事件会反复返回，可能造成无效唤醒。
2. 高并发下可能比 ET 多一些事件通知开销。

## 边缘触发 ET

ET 只在状态发生变化时通知。例如从“不可读”变成“可读”时通知一次；如果通知后没有把数据读完，只要状态仍然是可读，后续可能不再通知。

优点：

1. 通知次数少，适合高性能事件循环。
2. 可以减少反复唤醒和重复事件处理。

缺点：

1. 必须使用非阻塞 fd。
2. 必须循环读写直到 `EAGAIN/EWOULDBLOCK`。
3. 代码复杂，容易因为没有 drain 完缓冲区而“看起来丢数据”。

## 怎么解决 ET 可能读丢数据

ET 不是内核真的丢数据，而是应用没有读干净，之后状态没有新的边缘变化，所以收不到下一次通知。解决方法：

1. fd 设置为非阻塞。
2. 收到读事件后循环 `read/recv`。
3. 直到返回 `EAGAIN/EWOULDBLOCK` 才停止。
4. 应用层维护输入缓冲区，按协议解析完整消息。
5. 对写事件也一样，循环写到发送缓冲区满或待发送数据写完。

示例：

```c
for (;;) {
    ssize_t n = recv(fd, buf, sizeof(buf), 0);
    if (n > 0) {
        append_to_input_buffer(buf, n);
        continue;
    }
    if (n == 0) {
        close(fd);
        break;
    }
    if (errno == EAGAIN || errno == EWOULDBLOCK) {
        break;
    }
    if (errno == EINTR) {
        continue;
    }
    close(fd);
    break;
}
```

## 适用场景

1. **LT**：默认优先选择，适合业务复杂、正确性优先、连接数中等的场景。
2. **ET**：适合高并发、高性能网络框架，开发者能严格管理非阻塞读写和缓冲区。
3. **EPOLLONESHOT**：适合多线程处理同一连接，确保同一时刻只有一个线程处理该 fd，处理完后重新 arm。

## Muduo 为什么默认用 LT

Muduo 是 Reactor 风格的 C++ 网络库，强调连接生命周期、Buffer、Channel、EventLoop 等抽象的正确性和可维护性。它默认使用 LT 的核心原因是：LT 在连接事件处理上更稳，不容易因为业务回调没有一次性 drain 完输入输出缓冲区而漏掉后续通知。

可以从几个角度回答：

1. **正确性优先**：LT 下只要 fd 仍然可读，下次 `epoll_wait` 还会返回事件，对业务回调更宽容。
2. **减少使用约束**：ET 必须非阻塞并循环读写到 `EAGAIN`，否则应用层很容易误以为“丢事件”。
3. **Buffer 已经能削峰**：Muduo 通过输入/输出缓冲区和事件开关管理连接，不需要单纯依赖 ET 减少通知。
4. **可写事件按需打开**：LT 最大的坑是 `EPOLLOUT` 频繁触发，Muduo 这类网络库会在输出缓冲区非空时才关注写事件，写完后关闭。
5. **业务回调不可控**：网络库无法保证用户回调一定短小、无阻塞、一次读写干净，LT 的容错性更好。

所以 Muduo 用 LT 不是因为 ET 性能一定差，而是权衡了代码复杂度、正确性和通用性。成熟网络库真正的性能来源通常还包括 one loop per thread、非阻塞 I/O、Buffer 复用、定时器、批量处理和减少跨线程锁竞争。

## 什么情况下用 ET

ET 更适合开发者能完全控制事件循环和读写协议的场景：

1. 连接数巨大、活跃连接相对少，希望减少重复就绪通知。
2. 每个 fd 都是非阻塞，读写处理严格循环到 `EAGAIN`。
3. 应用有成熟输入/输出缓冲区和协议解析器，能处理半包、粘包和部分写。
4. 回调逻辑短小，不在 I/O 线程里做慢 SQL、阻塞 RPC 或大计算。
5. 多线程抢同一 fd 时配合 `EPOLLONESHOT`，处理完再重新注册。

典型使用方式：

```cpp
ev.events = EPOLLIN | EPOLLET | EPOLLRDHUP;
epoll_ctl(epfd, EPOLL_CTL_ADD, fd, &ev);
```

收到事件后必须：

```text
read/recv 直到 EAGAIN
send/write 直到 EAGAIN 或输出缓冲区为空
异常和半关闭及时关闭连接
```

如果团队没有完善的网络库封装，只是在业务代码里直接使用 epoll，LT 通常是更稳的默认选择。

## 阻塞和非阻塞 fd 都可以用 LT 和 ET 吗

从接口上看，阻塞 fd 和非阻塞 fd 都可以注册到 epoll，LT 和 ET 也都可以设置。但从工程正确性看：

1. **LT + 阻塞 fd**：简单场景可以工作，但事件处理函数里仍可能因为读写阻塞卡住整个事件循环。
2. **LT + 非阻塞 fd**：服务端常用默认组合，正确性更稳，读写遇到 `EAGAIN` 就回到事件循环。
3. **ET + 非阻塞 fd**：高性能网络库常用组合，必须循环读写到 `EAGAIN`。
4. **ET + 阻塞 fd**：不推荐，甚至可以认为是错误用法；如果一直读到“没有数据”为止，最后一次读会阻塞，事件循环被卡死。

为什么 ET 必须配合非阻塞 fd：

```text
ET 只在状态变化时通知一次
-> 应用需要一次性 drain 缓冲区
-> drain 到最后没有数据时，非阻塞 fd 返回 EAGAIN
-> 如果 fd 是阻塞的，最后一次 read/recv 会睡眠等待新数据
```

写事件也一样：非阻塞 `send` 写到发送缓冲区满时返回 `EAGAIN`；阻塞 `send` 可能卡住 I/O 线程。

面试里可以回答：语法上都能注册，但高并发服务应统一使用非阻塞 fd。LT 在阻塞 fd 上也可能跑通简单程序，但有卡住事件循环的风险；ET 必须用非阻塞 fd，并读写到 `EAGAIN`，否则要么漏事件感知，要么阻塞住整个 loop。

## ET 的应用层状态成本

ET 的优势是减少内核反复通知，但代价是应用层必须更认真地保存状态：

1. **输入缓冲区**：一次 `recv` 不一定拿到完整协议包，要保存半包并继续解析。
2. **输出缓冲区**：一次 `send` 可能只写出部分数据，要保存未写完内容和写偏移。
3. **连接状态机**：认证中、读请求、处理业务、等待回写、关闭中等状态要由应用维护。
4. **事件开关**：只有输出缓冲区非空时才打开 `EPOLLOUT`，写完后及时关闭。
5. **异常处理**：`EAGAIN`、`EINTR`、半关闭、超时、慢连接都要明确处理。

所以 ET 并不是“只通知一次就一定更省”。它把一部分重复通知成本从内核转移到了应用层状态管理。高性能网络库选择 ET，是因为它们有成熟的 buffer、codec、connection 和 event loop 抽象；普通业务服务如果没有这些封装，LT 往往更稳。

## LT 如何处理可写事件

LT 下只要 socket 发送缓冲区还有空间，`epoll_wait` 就会持续返回 `EPOLLOUT`。大多数连接在大多数时间都是可写的，所以不能在连接建立后一直监听写事件，否则事件循环会被大量“无意义可写”唤醒打满。

正确做法是把写事件当成**输出缓冲区非空时的补偿机制**：

1. 业务生成响应后，先尝试直接 `send`。
2. 如果一次写完，不注册 `EPOLLOUT`。
3. 如果只写出一部分，保存剩余数据和写偏移，打开 `EPOLLOUT`。
4. 下次 LT 可写事件到来后继续写，直到写完或遇到 `EAGAIN`。
5. 写完后立刻从关注事件里移除 `EPOLLOUT`，继续保留 `EPOLLIN`。

典型伪代码：

```cpp
void enableWriteIfNeeded(Connection& c) {
    if (!c.output.empty()) {
        modEpoll(c.fd, EPOLLIN | EPOLLOUT);
    }
}

void handleWritable(Connection& c) {
    while (!c.output.empty()) {
        ssize_t n = ::send(c.fd, c.output.data(), c.output.size(), 0);
        if (n > 0) {
            c.output.consume(n);
        } else if (errno == EAGAIN || errno == EWOULDBLOCK) {
            return;
        } else {
            closeConnection(c);
            return;
        }
    }
    modEpoll(c.fd, EPOLLIN); // 没有待写数据后关闭 EPOLLOUT
}
```

真实 Web 服务里，这个输出缓冲区还要配合高水位线做反压：如果对端长期不读，应用不能无限堆积待发送数据，而是要限速、降级或关闭慢连接。

## 易错点

1. ET 下不能只读一次就返回事件循环。
2. ET 下阻塞 fd 可能让事件循环卡死。
3. `EPOLLOUT` 通常不要一直关注，否则大多数 socket 都会频繁返回可写；有待发送数据时再打开写事件，写完后关闭。
4. `EPOLLHUP`、`EPOLLERR` 也要处理，否则异常连接可能残留。

## 面试回答模板

LT 是水平触发，只要 fd 状态仍然可读或可写就会反复通知；ET 是边缘触发，只在状态变化时通知，因此 ET 必须配合非阻塞 fd，并循环读写到 `EAGAIN`。Muduo 默认使用 LT，主要是为了正确性和易用性：业务回调没有一次读完时 LT 还会继续提醒，输出缓冲区也可以通过按需打开 `EPOLLOUT` 避免无效唤醒。ET 适合高性能网络库内部使用，前提是有成熟的 Buffer、状态机、错误处理和事件重新注册逻辑。
