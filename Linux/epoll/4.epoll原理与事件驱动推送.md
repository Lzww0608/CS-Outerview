# 4. epoll 原理与事件驱动推送

`epoll` 是 Linux 上高并发网络服务常用的 I/O 多路复用机制。它的核心优势是把“关注哪些 fd”和“等待哪些 fd 就绪”拆开，避免每次等待都全量传入和扫描 fd 集合。

## epoll 核心对象

1. **epoll 实例**：由 `epoll_create1()` 创建，本身也是一个 fd。
2. **兴趣列表**：通过 `epoll_ctl()` 注册进来的 fd 和事件集合。
3. **等待队列回调**：被监听 fd 状态变化时，内核通过回调把事件放入就绪队列。
4. **就绪队列 ready list**：保存已经就绪、等待 `epoll_wait()` 返回的事件。

老资料常说 epoll 内部用红黑树管理 fd，用链表保存就绪事件。新内核实现细节可能变化，但面试回答抓住“兴趣集合 + 等待队列回调 + 就绪队列”更稳。

## epoll 调用流程

```c
int epfd = epoll_create1(0);

struct epoll_event ev;
ev.events = EPOLLIN | EPOLLET;
ev.data.fd = fd;
epoll_ctl(epfd, EPOLL_CTL_ADD, fd, &ev);

for (;;) {
    int n = epoll_wait(epfd, events, 1024, -1);
    for (int i = 0; i < n; ++i) {
        handle(events[i]);
    }
}
```

流程解释：

1. `epoll_ctl(ADD)`：把 fd 加入 epoll 兴趣列表，并在 fd 对应对象的等待队列上挂回调。
2. fd 状态变化：例如 socket 收到数据，协议栈把数据放入接收缓冲区，触发等待队列。
3. epoll 回调执行：把该 fd 的事件加入 ready list。
4. `epoll_wait()`：如果 ready list 非空就返回；为空则睡眠等待。

## epoll 操作复杂度和内核结构

面试里常追问 `epoll_ctl`、`epoll_wait` 的复杂度，可以这样回答：

1. `epoll_create1()`：创建 epoll 实例，通常可以认为是 `O(1)`。
2. `epoll_ctl(ADD/MOD/DEL)`：在兴趣集合中增删改 fd，并维护等待队列回调。经典说法是红黑树查找和更新，复杂度约 `O(log n)`；实际内核实现细节可能演进，但它不是每次等待都全量扫描。
3. `epoll_wait()`：主要从 ready list 拷贝已经就绪的事件，复杂度接近 `O(ready)`，也就是和本次返回的就绪事件数相关。

`select/poll` 的主要问题是每次调用都要把 fd 集合从用户态传入内核，并线性扫描所有 fd；`epoll` 把“注册关注”和“等待就绪”拆开，关注集合长期保存在内核里，fd 就绪时通过回调进入 ready list，所以大量空闲连接下效率更稳定。

回答时要避免绝对化：不是所有 `epoll` 操作都严格 `O(1)`，也不是只要使用 epoll 就一定高性能。连接状态管理、应用层缓冲区、业务线程池、锁竞争和慢客户端同样会成为瓶颈。

## 配置中心推送怎么用事件驱动做

配置中心服务端需要维护大量客户端长连接。事件驱动模型通常是：

1. 监听 socket 设置非阻塞，并加入 epoll。
2. 新连接到来时 `accept4(..., SOCK_NONBLOCK | SOCK_CLOEXEC)`，把连接 fd 加入 epoll。
3. 客户端发订阅请求，服务端记录 `namespace -> connection_set`。
4. 配置变更后，服务端只把变更版本号写入对应连接的发送缓冲区。
5. 对这些连接打开 `EPOLLOUT`。
6. `EPOLLOUT` 到来时尽量写出数据；写完后关闭 `EPOLLOUT`，继续监听 `EPOLLIN`。

这样不会为每个连接创建阻塞线程，少量事件循环线程就能管理大量空闲连接。

## 发送缓冲区设计

每个连接一般维护：

1. 输入缓冲区：保存半包订阅请求。
2. 输出缓冲区：保存还没写完的推送消息。
3. 订阅集合：该连接订阅了哪些配置。
4. 连接状态：认证中、已订阅、关闭中等。

写 socket 时可能只写出部分数据，所以要记录写偏移。只有输出缓冲区非空时才关注 `EPOLLOUT`，否则可写事件会频繁触发。

## epoll_ctl 是线程安全的吗

`epoll_ctl` 是系统调用，内核会对 epoll 实例和被监听 fd 的内部结构做必要同步。因此多个线程对同一个 epoll fd 调用 `epoll_ctl`，不会因为内核数据结构本身并发访问就直接损坏。

但工程上不能把它理解成“应用层可以随便并发操作连接”。需要注意：

1. **操作顺序仍然有竞态**：一个线程 `DEL` fd，另一个线程同时 `MOD` fd，最终语义取决于实际执行顺序。
2. **fd 复用问题**：线程 A 关闭 fd 后，系统可能很快把同一个 fd 数字分配给新连接；线程 B 再对旧 fd 做 `epoll_ctl` 可能误操作新连接。
3. **事件和连接对象生命周期**：`epoll_wait` 返回事件时，应用层保存的连接对象可能已经被其他线程关闭或释放。
4. **one loop per thread 模型**：通常让一个连接只归属一个 EventLoop，跨线程修改关注事件时投递任务到所属 loop，再由该 loop 调用 `epoll_ctl`。
5. **多线程处理同一 fd**：可以配合 `EPOLLONESHOT`，处理完后由负责线程重新 arm，避免多个线程同时读写同一连接。

面试回答可以说：内核层面 `epoll_ctl` 有同步保护，可以被多线程调用；但业务层面仍要设计连接归属、fd 生命周期、事件重入和关闭协议，否则会出现竞态、误删、重复处理或 use-after-free。

## 易错点

1. `epoll` 通知的是就绪，不是读写已经完成。
2. ET 模式必须配合非阻塞 fd，并读写到 `EAGAIN`。
3. 关闭连接前要清理订阅关系，避免推送到无效 fd。
4. fd 会复用，不能只靠裸 fd 判断连接身份，最好带连接对象指针或 generation。
5. 推送大量客户端时要做限速、批量发送和慢连接淘汰，否则慢客户端会拖垮内存。

## 应用场景

`epoll` 适合“连接很多，但同一时刻真正活跃的连接相对有限”的 I/O 密集场景。它把关注集合长期保存在内核中，只把就绪事件返回给用户态，因此比每次全量扫描 fd 集合更适合高并发长连接。

典型场景：

1. 网关、IM、游戏网关、配置中心推送这类大量 TCP 长连接服务。
2. Redis、Nginx、RPC 框架等事件驱动网络服务。
3. 协程调度器底层 I/O 等待：协程发起非阻塞读写，未就绪时挂起，fd 就绪后由 epoll 唤醒对应协程。
4. 多线程 one loop per thread 模型：每个 I/O 线程维护自己的 epoll 实例，连接按 hash 或 accept 分发到固定 loop。
5. 配合 timerfd、eventfd、signalfd，把定时器、跨线程唤醒和信号也统一纳入事件循环。

不适合的场景：

1. fd 数量很少时，select/poll/阻塞 I/O 的复杂度更低，收益不明显。
2. 磁盘普通文件通常总是“就绪”，用 epoll 不能解决磁盘 I/O 延迟，应该考虑 io_uring、AIO 或线程池。
3. CPU 密集型业务不会因为 epoll 自动变快，需要业务线程池、分片、批处理或异步化。
4. 如果应用层缓冲区、连接生命周期、慢客户端背压没设计好，epoll 只能更快地暴露瓶颈。
