# 4. epoll 原理与事件驱动推送

`epoll` 是 Linux 上高并发网络服务常用的 I/O 多路复用机制。它的核心优势是把“关注哪些 fd”和“等待哪些 fd 就绪”拆开，避免每次等待都全量传入和扫描 fd 集合。

## epoll 核心对象

1. **epoll 实例**：由 `epoll_create1()` 创建，本身也是一个 fd。
2. **兴趣列表**：通过 `epoll_ctl()` 注册进来的 fd 和事件集合。
3. **等待队列回调**：被监听 fd 状态变化时，内核通过回调把事件放入就绪队列。
4. **就绪队列 ready list**：保存已经就绪、等待 `epoll_wait()` 返回的事件。

老资料常说 epoll 内部用红黑树管理 fd，用链表保存就绪事件。新内核实现细节可能变化，但面试回答抓住“兴趣集合 + 等待队列回调 + 就绪队列”更稳。

## epoll 调用流程

```c
int epfd = epoll_create1(0);

struct epoll_event ev;
ev.events = EPOLLIN | EPOLLET;
ev.data.fd = fd;
epoll_ctl(epfd, EPOLL_CTL_ADD, fd, &ev);

for (;;) {
    int n = epoll_wait(epfd, events, 1024, -1);
    for (int i = 0; i < n; ++i) {
        handle(events[i]);
    }
}
```

流程解释：

1. `epoll_ctl(ADD)`：把 fd 加入 epoll 兴趣列表，并在 fd 对应对象的等待队列上挂回调。
2. fd 状态变化：例如 socket 收到数据，协议栈把数据放入接收缓冲区，触发等待队列。
3. epoll 回调执行：把该 fd 的事件加入 ready list。
4. `epoll_wait()`：如果 ready list 非空就返回；为空则睡眠等待。

## 配置中心推送怎么用事件驱动做

配置中心服务端需要维护大量客户端长连接。事件驱动模型通常是：

1. 监听 socket 设置非阻塞，并加入 epoll。
2. 新连接到来时 `accept4(..., SOCK_NONBLOCK | SOCK_CLOEXEC)`，把连接 fd 加入 epoll。
3. 客户端发订阅请求，服务端记录 `namespace -> connection_set`。
4. 配置变更后，服务端只把变更版本号写入对应连接的发送缓冲区。
5. 对这些连接打开 `EPOLLOUT`。
6. `EPOLLOUT` 到来时尽量写出数据；写完后关闭 `EPOLLOUT`，继续监听 `EPOLLIN`。

这样不会为每个连接创建阻塞线程，少量事件循环线程就能管理大量空闲连接。

## 发送缓冲区设计

每个连接一般维护：

1. 输入缓冲区：保存半包订阅请求。
2. 输出缓冲区：保存还没写完的推送消息。
3. 订阅集合：该连接订阅了哪些配置。
4. 连接状态：认证中、已订阅、关闭中等。

写 socket 时可能只写出部分数据，所以要记录写偏移。只有输出缓冲区非空时才关注 `EPOLLOUT`，否则可写事件会频繁触发。

## 易错点

1. `epoll` 通知的是就绪，不是读写已经完成。
2. ET 模式必须配合非阻塞 fd，并读写到 `EAGAIN`。
3. 关闭连接前要清理订阅关系，避免推送到无效 fd。
4. fd 会复用，不能只靠裸 fd 判断连接身份，最好带连接对象指针或 generation。
5. 推送大量客户端时要做限速、批量发送和慢连接淘汰，否则慢客户端会拖垮内存。
