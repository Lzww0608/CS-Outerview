# 2. select、poll 和 epoll

`select`、`poll` 和 `epoll` 都属于 I/O 多路复用：一个线程可以同时等待多个 fd 的就绪事件。它们通知的是“fd 可以读/可以写”，不是直接完成读写。

## select 的工作方式

`select` 每次调用都要把 fd 集合从用户态拷贝到内核态，内核扫描集合判断哪些 fd 就绪，然后把结果拷贝回用户态。

适用场景：

1. fd 数量很少的简单程序。
2. 跨平台代码，因为 `select` 在类 Unix 和 Windows 上都常见。
3. 临时工具、教学代码、低并发客户端。

弊端：

1. **fd 数量限制**：通常受 `FD_SETSIZE` 限制，常见默认值是 1024。
2. **O(n) 扫描**：每次都要遍历全部 fd。
3. **重复拷贝**：每次调用都要拷贝 fd 集合。
4. **集合会被修改**：返回后需要重新设置监听集合，写法容易出错。

### 5000 个客户端连接用 select 会怎样

如果 5000 个连接对应的 fd 值超过 `FD_SETSIZE`，常见默认值是 1024，直接用 `FD_SET(fd, &set)` 可能越界写 `fd_set` 位图，属于未定义行为，可能表现为内存破坏、崩溃，也可能暂时看不出问题。它不一定会在 `select` 调用处返回一个清晰错误。

即使通过重新编译把 `FD_SETSIZE` 调大，`select` 仍然有这些问题：

1. 每次调用都要把完整 fd 集合拷贝进内核。
2. 内核和用户态都要按 `nfds` 线性扫描。
3. 返回后集合被修改，下一轮要重新构造。
4. fd 上限还受 `RLIMIT_NOFILE`、进程资源和内存影响。

所以高并发长连接服务通常不会用 `select` 扛几千、几万连接，而是使用 `epoll`、`kqueue`、IOCP 或成熟网络库。

### fd 最大值和 fd 数量不是一回事

`select` 的接口里有两个容易混淆的限制：

```c
int select(int nfds, fd_set* readfds, fd_set* writefds,
           fd_set* exceptfds, struct timeval* timeout);
```

1. `nfds` 不是 fd 数量，而是“需要检查的最大 fd 值 + 1”。
2. `fd_set` 通常是固定大小位图，默认受 `FD_SETSIZE` 限制，常见是 1024。
3. 进程能打开多少 fd 还受 `ulimit -n` / `RLIMIT_NOFILE` 限制。
4. 系统总 fd 资源还受内核参数和内存影响，例如 `/proc/sys/fs/file-max`。

因此有两种不同问题：

```text
fd 数量不多，但最大 fd 值 >= FD_SETSIZE -> FD_SET 可能越界
fd 数量很多，但最大 fd 值也很大 -> select 还要按 nfds 线性扫描
```

`poll` 不用固定大小位图，而是传 `pollfd` 数组，所以没有 `FD_SETSIZE` 这个固定 1024 限制；但它仍然每次传入完整数组并线性扫描。`epoll` 则把关注列表保存在内核里，等待时主要返回就绪事件，适合大量长连接。

### select 为什么要把 fd 集合拷贝到内核空间

`select` 是系统调用，内核不能直接信任用户态传入的指针和内存内容。调用开始时，内核要把 `readfds/writefds/exceptfds` 从用户态复制到内核空间，形成一次稳定快照，然后在内核里扫描这些 fd 的状态。

返回时，`select` 还会把“哪些 fd 就绪”的结果写回用户态 fd_set。也就是说它有两类拷贝：

```text
调用进入: 用户态 fd_set -> 内核态临时集合
调用返回: 内核态就绪结果 -> 用户态 fd_set
```

这样设计的原因：

1. **安全性**：用户态地址可能非法，内核需要 `copy_from_user/copy_to_user` 做访问检查。
2. **一致性**：系统调用执行期间，用户线程不应通过同一块内存影响内核正在扫描的集合。
3. **接口语义**：`select` 会原地修改 fd_set，只保留就绪 fd，所以必须把结果拷贝回去。

代价是每次等待都要全量传入和全量扫描。大量长连接但活跃连接很少时，这部分拷贝和 `O(n)` 扫描会成为主要瓶颈；`epoll` 通过 `epoll_ctl` 预先注册 fd，避免每次 `epoll_wait` 都传完整集合。

## poll 的工作方式

`poll` 使用 `pollfd` 数组描述 fd 和事件：

```c
struct pollfd {
    int fd;
    short events;
    short revents;
};
```

相比 `select`：

1. 不再受固定 `FD_SETSIZE` 限制，fd 数量主要受内存和系统资源限制。
2. 入参和出参分离，`events` 表示关注事件，`revents` 表示返回事件。
3. 仍然每次调用都要把数组传给内核，内核仍要线性扫描。

适用场景：

1. fd 数量中等、代码想比 `select` 更简单。
2. 需要类 Unix 上较好的可移植性。
3. 高并发不是核心瓶颈的网络工具或客户端。

弊端：

1. 每次调用仍是 `O(n)` 扫描。
2. 每次仍要传入完整 fd 数组。
3. 大量长连接且活跃连接很少时效率不如 `epoll`。

### select 和 poll 是同步还是异步

严格按 POSIX I/O 语义，`select` 和 `poll` 都属于同步 I/O 多路复用。它们只负责等待 fd 变成“可读/可写/异常”，返回后应用线程仍然要自己调用 `read/write/recv/send` 完成数据拷贝。

容易混淆的是：

1. **阻塞与非阻塞**：`select/poll` 本身可以阻塞等待事件，也可以设置 timeout 为 0 立即返回。
2. **同步与异步**：同步看的是 I/O 完成是否还要调用方参与。`select/poll` 返回的只是就绪事件，不是完成事件。
3. **事件驱动不等于完成式异步**：Reactor 常用 `select/poll/epoll` 做事件驱动，但底层仍是同步非阻塞 I/O；`io_uring`、IOCP 更接近完成通知。

面试可以回答：`select`、`poll`、`epoll` 都是 I/O 多路复用和就绪通知机制，通常归类为同步 I/O；工程上常说“异步事件驱动”是编程模型上的说法，不是内核完成式异步 I/O。

## epoll 的工作方式

`epoll` 把“注册 fd”和“等待事件”拆开：

1. `epoll_create1()` 创建 epoll 实例。
2. `epoll_ctl()` 把 fd 和关注事件注册到内核。
3. fd 就绪时，内核把事件放入 ready list。
4. `epoll_wait()` 从 ready list 取就绪事件返回。

更底层一点，`epoll_ctl(ADD)` 时内核会把被监听 fd 挂到 epoll 实例的兴趣列表中，并在目标 fd 的等待队列上注册回调函数。当网卡收包、socket 接收缓冲区变为可读，或发送缓冲区变为可写时，内核唤醒等待队列，回调会把对应事件放入 epoll 的就绪队列。`epoll_wait()` 只是睡眠等待并取走这些就绪事件。

可以概括为：

```text
epoll_ctl: 注册 fd + 事件 + 回调
fd 状态变化: 内核回调加入 ready list
epoll_wait: 从 ready list 拿事件返回给用户态
```

### epoll 常用 API 和事件

面试里如果问“`epoll` 相关 API”，核心是三个系统调用：

1. `epoll_create1(flags)`：创建 epoll 实例，返回一个 epoll fd。常用 `EPOLL_CLOEXEC`，避免 `exec` 后 fd 泄漏。
2. `epoll_ctl(epfd, op, fd, event)`：维护关注列表，`op` 可以是 `EPOLL_CTL_ADD`、`EPOLL_CTL_MOD`、`EPOLL_CTL_DEL`。
3. `epoll_wait(epfd, events, maxevents, timeout)`：等待就绪事件，返回写入 `events` 数组的事件个数。

常见事件：

| 事件 | 含义 | 注意点 |
| --- | --- | --- |
| `EPOLLIN` | 可读 | 可能是数据到达、对端关闭、监听 fd 有连接可 `accept` |
| `EPOLLOUT` | 可写 | 大多数空闲 socket 都可写，通常只在输出缓冲区非空时关注 |
| `EPOLLRDHUP` | 对端关闭写方向 | 长连接建议关注，用来发现半关闭 |
| `EPOLLERR` | fd 出错 | 即使没有显式关注也可能返回，要处理 |
| `EPOLLHUP` | 挂起或关闭 | 通常需要清理连接 |
| `EPOLLET` | 边缘触发 | 必须非阻塞并读写到 `EAGAIN` |
| `EPOLLONESHOT` | 事件触发一次后禁用 | 多线程处理同一 fd 时常用，处理完要重新 `MOD` |

一个典型服务端流程：

```text
socket/listen fd 设置非阻塞
-> epoll_create1
-> epoll_ctl ADD 监听 fd 的 EPOLLIN
-> epoll_wait
-> 监听 fd 可读: accept4 循环接收新连接
-> 连接 fd 可读: recv 到 EAGAIN，写入输入缓冲区并解析协议
-> 需要回包: 先尝试 send，没写完再 MOD 打开 EPOLLOUT
-> 写完输出缓冲区: MOD 关闭 EPOLLOUT
```

易错点：

1. `EPOLL_CTL_DEL` 时内核不再需要 `event` 内容，新内核可传 `nullptr`，但跨平台代码要注意兼容。
2. fd 关闭前最好明确从 epoll 删除或保证连接对象生命周期正确，避免 fd 复用后误处理旧事件。
3. `epoll_wait` 返回事件后，真正的数据搬运仍要靠 `read/recv/write/send`。
4. `epoll` 高性能依赖非阻塞 fd、应用层缓冲区、连接状态机和短回调，不是只换 API 就能提升性能。

适用场景：

1. 高并发网络服务，例如网关、RPC server、IM 长连接服务。
2. 大量 fd 长期存在，但同一时间只有少量活跃。
3. Reactor 模型：一个或多个事件循环线程负责分发事件。

弊端：

1. Linux 专有，跨平台性不如 `select`。
2. 对 fd 生命周期要求高，关闭 fd、复用 fd、从 epoll 中删除 fd 都要小心。
3. 边缘触发模式使用复杂，必须配合非阻塞 I/O 和循环读写。
4. fd 全都很活跃时，`epoll` 优势会变小，因为返回和处理事件本身也有成本。

## epoll 为什么要配合非阻塞 I/O

`epoll` 只告诉你“现在可能可读/可写”。如果 fd 是阻塞的，事件处理线程调用 `read/recv` 时仍可能因为以下原因阻塞：

1. 多线程或多进程竞争，同一个 fd 的数据已经被其他线程读走。
2. 边缘触发下没有一次性读到 `EAGAIN`，后续可能不再收到通知。
3. 写事件就绪只表示发送缓冲区有空间，不代表能一次写完所有数据。

因此工程上通常设置：

```c
fcntl(fd, F_SETFL, old_flags | O_NONBLOCK);
```

事件到来后循环读写，直到返回 `EAGAIN/EWOULDBLOCK`，再回到 `epoll_wait`。

## select、poll 和 epoll 的核心区别

| 对比项 | select | poll | epoll |
| --- | --- | --- | --- |
| fd 集合 | `fd_set` 位图，每次传入 | `pollfd` 数组，每次传入 | `epoll_ctl` 先注册到内核 |
| 查找就绪 fd | 线性扫描 | 线性扫描 | ready list 返回 |
| fd 数量 | 常受 `FD_SETSIZE` 限制 | 无固定 1024 限制 | 主要受系统资源限制 |
| 复杂度 | O(n) | O(n) | 活跃 fd 近似 O(ready) |
| 触发模式 | 水平触发 | 水平触发 | 支持 LT/ET/ONESHOT |
| 跨平台 | 较好 | 类 Unix 较好 | Linux 专有 |

## 什么场景分别使用

1. `select`：fd 很少、跨平台优先、教学或临时工具。
2. `poll`：fd 数量可能超过 `select` 限制，但并发规模不大，且希望保持类 Unix 可移植性。
3. `epoll`：Linux 高并发长连接服务，大量 fd 长期存在但活跃 fd 相对较少。

如果所有 fd 都非常活跃，`epoll` 的优势会变小，因为事件处理本身已经是主要成本。

## 哪些开源软件使用 I/O 多路复用

1. **Nginx**：典型事件驱动服务器，Linux 下使用 epoll，BSD/macOS 下可用 kqueue。
2. **Redis**：事件循环封装多平台 I/O 多路复用，Linux 下常用 epoll。
3. **Memcached**：基于 libevent，底层可选择 epoll/kqueue/poll/select。
4. **Node.js/libuv**：跨平台事件循环，Linux 使用 epoll，Windows 使用 IOCP。
5. **Muduo**：C++ Reactor 网络库，Linux 下使用 epoll。
6. **Envoy/HAProxy**：高性能代理，会根据平台使用 epoll/kqueue 等事件机制。

## 面试回答模板

`select` 适合 fd 少、跨平台、简单场景；缺点是 fd 数量有限、每次都要拷贝和 O(n) 扫描。`poll` 用数组表达 fd，突破了 `FD_SETSIZE` 限制，但仍然是每次传入完整数组并线性扫描。`epoll` 适合 Linux 高并发长连接场景，把 fd 注册和等待事件分开，内核维护就绪队列，避免每次全量扫描。`epoll` 通常要配合非阻塞 I/O，否则事件循环可能卡在某个 fd 的阻塞读写上。
