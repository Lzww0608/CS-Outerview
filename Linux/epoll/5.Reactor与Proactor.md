# 5. Reactor 与 Proactor

## 1. Reactor 是什么

Reactor 是“就绪事件驱动”模型。I/O 多路复用器只通知应用：某个 fd 已经可读或可写。真正的 `read/write` 仍由应用线程自己执行。

典型流程：

```text
epoll_wait 返回可读事件
-> Reactor 分发给 handler
-> handler 调用 read/recv 读取数据
-> 解析协议并执行业务
-> 需要写时注册可写事件或直接尝试 write
```

Linux 上常见组合是：

```text
非阻塞 socket + epoll + 事件循环 + 应用层缓冲区
```

## 2. Proactor 是什么

Proactor 是“完成事件驱动”模型。应用先发起异步 I/O 操作，内核或运行时负责完成读写，完成后通知应用。

典型流程：

```text
应用提交异步 read
-> 内核/运行时执行 I/O
-> I/O 完成后投递 completion event
-> handler 处理已经读到的数据
```

Proactor 通知的是“操作已经完成”，而不是“现在可以读写”。

## 3. 核心区别

| 对比项 | Reactor | Proactor |
| --- | --- | --- |
| 事件含义 | fd 就绪 | I/O 完成 |
| 读写动作 | 应用线程自己调用 `read/write` | 内核或运行时完成 |
| 常见基础 | `select/poll/epoll/kqueue` | Windows IOCP、Linux io_uring/AIO |
| 编程重点 | 非阻塞、缓冲区、状态机 | 提交请求、处理完成回调 |
| 典型框架 | Redis、Nginx、Netty、libevent | IOCP 服务、Boost.Asio 的完成模型、io_uring 框架 |

## 4. Reactor 的常见形态

1. **单 Reactor 单线程**：一个线程负责 accept、读写和业务。实现简单，适合 Redis 这类内存操作快的场景。
2. **单 Reactor 多线程**：Reactor 线程负责 I/O 事件，业务交给线程池。
3. **主从 Reactor 多线程**：主 Reactor 负责 accept，从 Reactor 负责连接读写，业务再交给工作线程池。高并发服务常见。

## 4.1 one loop per thread

`one loop per thread` 是 Reactor 网络库常见线程模型：每个 I/O 线程拥有一个独立的 EventLoop、epoll 实例、定时器、任务队列和一批连接。同一个连接从创建到关闭都归属于固定 EventLoop，读写事件和连接状态修改都在该线程内串行执行。

典型流程：

```text
main loop accept 新连接
-> 按轮询/负载选择一个 sub loop
-> 把连接 fd 投递到该 sub loop
-> sub loop 负责后续 read/write/close/timer
-> 跨线程操作通过 queueInLoop + eventfd 唤醒
```

它的意义：

1. **减少锁竞争**：同一连接只在一个 I/O 线程里操作，输入输出缓冲区不需要多线程同时加锁。
2. **利用多核**：多个 EventLoop 分摊连接和 I/O 事件，避免单线程事件循环成为瓶颈。
3. **连接亲和性好**：连接状态、缓冲区和回调长期在同一线程访问，缓存局部性更好。
4. **跨线程边界清晰**：业务线程不能直接改 socket 关注事件，只能把任务投递回连接所属 loop。

易错点：

1. `one loop per thread` 不是“一连接一线程”，一个 loop 可以管理大量连接。
2. I/O loop 不能执行耗时业务，否则这个 loop 上所有连接都会被拖慢。
3. 跨线程唤醒要有可靠机制，常见做法是 `eventfd`、pipe 或条件变量加任务队列。
4. 连接分配要考虑负载，简单轮询可能在长连接负载不均时失衡。

## 4.2 Reactor 的瓶颈在哪里

Reactor 的瓶颈通常不是 `epoll` 这个系统调用本身，而是事件循环线程承载了太多工作。

常见瓶颈：

1. **单 loop CPU 打满**：一个 EventLoop 上连接过多，读写、回调、定时器和任务队列都在同一线程串行执行。
2. **业务回调阻塞**：handler 里访问数据库、磁盘、RPC 或做 CPU 密集计算，会拖慢该 loop 上所有连接。
3. **小包和拆包很多**：大量小请求会放大 read、buffer 移动、Length-Prefix 状态机、解码和对象分配成本。
4. **跨线程唤醒过多**：worker 每生成一个响应都唤醒 I/O loop，会带来 eventfd 写入、锁竞争和上下文切换。
5. **输出缓冲积压**：慢客户端导致发送队列变长，内存上涨，并且频繁关注 `EPOLLOUT` 会让 loop 忙于可写事件。
6. **连接负载不均**：长连接或热点用户集中到某个 sub loop，简单轮询无法反映真实负载。

优化思路：

1. 使用 main-sub Reactor，让 accept 和连接读写分离。
2. one loop per thread，把连接固定到某个 EventLoop，避免多个线程抢同一 fd。
3. I/O 线程只做非阻塞读写、framing 和轻量校验，重业务交给 worker。
4. 对轻量请求减少不必要的跨线程投递，或批量投递、批量唤醒。
5. 使用对象池、环形缓冲、批量日志和按需关注 `EPOLLOUT` 降低常数开销。
6. 用 P99、队列长度、loop latency、CPU 火焰图和跨线程唤醒次数判断优化是否有效。

## 5. 易错点

1. `epoll` 本身不是 Proactor，它通知的是就绪事件。
2. Reactor 不等于单线程，Reactor 是事件分发模型，可以搭配线程池。
3. 非阻塞 I/O 不是异步 I/O。非阻塞 `read` 只是立即返回，数据复制仍由当前线程完成。
4. Proactor 对操作系统支持要求更高，接口和内存生命周期管理也更复杂。

## 6. 面试回答模板

Reactor 和 Proactor 最大区别是事件语义。Reactor 通知“fd 可读可写”，应用收到事件后自己调用 `read/write`，所以 Linux 上常见的是非阻塞 socket 加 epoll；Proactor 通知“I/O 已完成”，应用先提交异步读写请求，完成后再处理结果，例如 Windows IOCP 或 Linux io_uring 更接近这个模型。Nginx、Redis、Netty 这类常见网络框架主要是 Reactor 思路。
