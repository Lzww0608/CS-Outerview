# 8. 用户线程与内核线程

用户线程和内核线程是从“谁负责创建、调度和阻塞管理”角度对线程实现方式的划分。面试里要把语言层面的线程、操作系统调度对象和协程区分开。

## 1. 基本概念

**内核线程**由操作系统内核感知和调度。Linux 中普通进程和线程底层都用 `task_struct` 描述，线程通常通过 `clone()` 创建，并共享同一进程的地址空间、文件描述符等资源。

**用户线程**由用户态运行时或线程库管理。内核可能只看到一个或少量内核线程，用户态运行时自己保存用户线程的栈、寄存器上下文和调度队列。

常见模型：

| 模型 | 含义 | 典型特点 |
| --- | --- | --- |
| 1:1 | 一个用户线程对应一个内核线程 | Linux pthread、C++ `std::thread` 常见实现 |
| N:1 | 多个用户线程映射到一个内核线程 | 用户态切换快，但一个阻塞系统调用会阻塞全部 |
| M:N | 多个用户线程映射到多个内核线程 | 运行时调度复杂，Go goroutine 是典型思路 |

## 2. 用户线程和内核线程的区别

| 对比项 | 用户线程 | 内核线程 |
| --- | --- | --- |
| 调度者 | 用户态运行时 | OS 内核调度器 |
| 切换开销 | 通常低，不一定陷入内核 | 需要内核参与上下文切换 |
| 阻塞影响 | N:1 下阻塞调用可能卡住整个调度器 | 一个线程阻塞，内核可调度其他线程 |
| 多核并行 | 取决于是否绑定多个内核线程 | 天然可被调度到多个 CPU |
| 可见性 | 内核通常看不到每个用户线程 | `top -H`、`ps -L` 可看到内核线程 |
| 实现复杂度 | 运行时要处理栈、调度、阻塞包装 | 交给内核，接口更通用 |

## 3. 和协程的关系

协程通常是用户态调度的轻量执行单元。它不一定等同于线程：

1. 协程切换通常由运行时在用户态完成，成本低于内核线程切换。
2. 协程可以很多，但真正并行执行仍依赖底层内核线程数量。
3. 如果协程执行阻塞系统调用，运行时必须用非阻塞 I/O、epoll、io_uring 或线程池托管阻塞操作，否则会卡住承载它的内核线程。
4. Go 的 goroutine 是 M:N 模型，运行时把大量 goroutine 调度到少量 OS 线程上。
5. C++20 coroutine 是语言级协程机制，本身不自带调度器，是否多线程执行取决于框架。

## 4. 真实场景怎么选

1:1 内核线程适合需要直接利用多核、阻塞调用多、和系统 API 交互直接的服务。例如 C++ 线程池、数据库 worker、后台压缩线程。

用户态协程适合大量高并发 I/O、每个请求状态机复杂但计算量不大的场景。例如 RPC 框架、网关、爬虫、IM 长连接。它的优势是减少线程数量和上下文切换，让异步代码写起来接近同步代码。

生产系统常用混合模型：

```text
少量 I/O 线程: epoll 处理连接事件
大量协程: 表达请求处理流程
业务线程池: 托管 CPU 密集或阻塞任务
```

这样可以让连接层保持轻量，同时避免阻塞操作卡住事件循环。

## 5. 易错点

1. “用户线程快”不代表一定能多核并行，N:1 模型只能用一个内核线程。
2. `std::thread` 不是用户态协程，主流 Linux 实现通常对应一个 pthread，也就是 1:1 内核线程模型。
3. 协程数量可以远大于内核线程数量，但阻塞调用必须被运行时接管。
4. 内核线程切换不一定很慢到不能用，CPU 密集任务反而更适合固定数量内核线程。
5. 用户态调度降低了切换开销，但也要求框架处理定时器、I/O 等待、取消、超时和异常传播。

## 6. 面试回答模板

用户线程由用户态运行时管理，切换可以不陷入内核，开销低，但阻塞系统调用和多核并行要靠运行时处理。内核线程由操作系统调度，Linux 中线程和进程底层都是 `task_struct`，能直接被调度到多个 CPU 上，一个线程阻塞时内核可以运行其他线程。常见 pthread 和 `std::thread` 是 1:1 模型，Go goroutine 更接近 M:N 模型。真实服务里通常用少量 I/O 线程配合 epoll 管连接，用协程表达异步流程，再把阻塞或 CPU 密集任务交给线程池。
