# 4. 线程阻塞与休眠

## 1. 阻塞和休眠的区别

线程阻塞和休眠都会让线程暂时不占用 CPU，但触发原因不同：

1. **阻塞**：线程等待某个事件，例如锁可用、条件变量满足、I/O 可读、子进程退出。
2. **休眠**：线程主动让出 CPU，等待一段时间后再运行，例如 `sleep()`、`nanosleep()`、`std::this_thread::sleep_for()`。

阻塞通常由资源或事件驱动，休眠通常由时间驱动。

## 2. 线程阻塞怎么实现

Linux 内核调度的核心思路是：

1. 线程发现条件不满足。
2. 把自己挂到某个等待队列上。
3. 设置任务状态，例如 `TASK_INTERRUPTIBLE` 或 `TASK_UNINTERRUPTIBLE`。
4. 调用调度器 `schedule()` 让出 CPU。
5. 事件发生后，其他线程或中断路径调用唤醒函数，把等待线程放回运行队列。
6. 调度器后续重新调度该线程运行。

以 mutex 为例：

1. 用户态先用原子操作尝试抢锁。
2. 无竞争时直接成功，不进入内核。
3. 有竞争时调用 futex wait，把线程挂到 futex 对应等待队列。
4. 持锁线程 unlock 时调用 futex wake，唤醒等待者。

这就是现代 Linux `pthread_mutex` / `std::mutex` 常见的快路径 + 慢路径设计。

## 3. 条件变量阻塞过程

`std::condition_variable::wait(lock, pred)` 的关键动作是：

1. 持有互斥锁检查谓词。
2. 如果条件不满足，原子地释放锁并进入等待。
3. 被 `notify_one/notify_all` 唤醒后重新竞争锁。
4. 拿到锁后再次检查谓词。

必须重新检查谓词，因为可能发生虚假唤醒，也可能多个线程被唤醒后只有一个线程真正消费到资源。

## 4. 休眠怎么实现

`sleep()`、`nanosleep()`、`clock_nanosleep()` 这类接口通常会：

1. 创建或设置一个内核定时器。
2. 把当前线程状态改为可中断睡眠。
3. 调用调度器让出 CPU。
4. 定时器到期或收到信号后唤醒线程。
5. 线程重新进入运行队列，等待调度。

`std::this_thread::sleep_for()` 底层一般会映射到系统的 sleep API。它不保证精确唤醒，只保证至少休眠接近指定时间，实际唤醒时间受调度延迟、系统负载和定时器精度影响。

## 5. 阻塞、睡眠、自旋的选择

1. **自旋**：等待时间极短时使用，避免上下文切换，但会消耗 CPU。
2. **阻塞**：等待时间不可控或较长时使用，让出 CPU。
3. **休眠**：需要基于时间延迟或周期任务时使用，不应用来替代正确同步。

错误示例：

```cpp
while (!ready) {
    std::this_thread::sleep_for(std::chrono::milliseconds(1));
}
```

这种轮询会引入延迟和 CPU 浪费。更好的方式是条件变量：

```cpp
std::unique_lock<std::mutex> lock(m);
cv.wait(lock, [] { return ready; });
```

## 6. 易错点

1. 睡眠不是同步机制，不能用 `sleep(1)` 来“等另一个线程准备好”。
2. 阻塞等待要配合状态变量，不能只依赖通知信号。
3. futex wait 会在内核中再次检查用户态值，避免检查和睡眠之间丢唤醒。
4. 可中断睡眠可能被信号打断，系统调用返回 `EINTR` 时要决定是否重试。
5. 高精度定时任务要关注时钟源、定时器精度、调度延迟和系统负载。

## 7. 面试回答模板

线程阻塞本质是把当前线程挂到某个等待队列，设置睡眠状态，然后调用调度器让出 CPU；事件发生后再被唤醒放回运行队列。互斥锁通常先在用户态用 CAS 抢锁，无竞争不进内核，竞争时通过 futex 进入内核等待队列。线程休眠则是设置内核定时器并让出 CPU，定时器到期后唤醒线程。阻塞是等事件，休眠是等时间，工程上不要用 sleep 代替条件变量或信号量。
