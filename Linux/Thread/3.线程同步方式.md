# 3. 线程同步方式

## 1. 为什么需要线程同步

同一进程内多个线程共享地址空间。共享内存访问带来性能便利，也带来数据竞争、可见性和执行顺序问题。线程同步的目标是：

1. 保证临界区互斥。
2. 保证线程之间的执行顺序。
3. 保证一个线程写入的数据对另一个线程可见。
4. 避免忙等浪费 CPU。

## 2. 常见同步方式

| 方式 | 典型 API | 作用 | 适用场景 |
| --- | --- | --- | --- |
| 互斥锁 | `std::mutex`、`pthread_mutex_t` | 临界区互斥 | 保护共享变量、容器 |
| 读写锁 | `std::shared_mutex`、`pthread_rwlock_t` | 多读单写 | 读多写少缓存 |
| 条件变量 | `std::condition_variable`、`pthread_cond_t` | 等待某个条件成立 | 生产者消费者、任务队列 |
| 信号量 | `sem_t`、`std::counting_semaphore` | 资源计数 | 连接池、限流、固定容量队列 |
| 原子变量 | `std::atomic` | 无锁读写和内存序控制 | 计数器、状态位、无锁结构 |
| 自旋锁 | `pthread_spinlock_t` | 短临界区忙等 | 锁持有极短、不能睡眠场景 |
| 屏障 | `std::barrier`、`pthread_barrier_t` | 多线程阶段同步 | 并行计算分阶段推进 |
| latch | `std::latch` | 一次性等待多个任务完成 | 主线程等待 N 个 worker 初始化 |
| future/promise | `std::future`、`std::promise` | 一次性结果传递 | 异步任务返回值 |

## 2.1 常见同步方式背后的系统调用

面试中如果要求“说出具体系统调用”，可以从 Linux 的阻塞和唤醒路径回答：

1. `pthread_mutex_lock` 不是每次都进内核。无竞争时通常在用户态用原子指令完成；竞争严重时会通过 `futex` 进入内核睡眠。
2. `pthread_cond_wait` 会在释放互斥锁后把线程挂到等待队列，底层常依赖 `futex` 阻塞；`pthread_cond_signal`/`broadcast` 唤醒等待线程。
3. `pthread_rwlock_*` 读写锁同样通常由用户态原子状态加 `futex` 等待队列实现。
4. POSIX 信号量 `sem_wait`/`sem_post` 可以表示资源计数，阻塞路径也可能进入内核。
5. `eventfd`、pipe 常用于线程间唤醒 I/O 线程，写端写入事件，读端被 `epoll` 监听。
6. `sched_yield` 只是主动让出 CPU，不是可靠同步机制，不能用来等待条件成立。

所以锁的性能不是简单地等于“一定系统调用”。真正昂贵的是竞争导致的阻塞、唤醒、上下文切换和缓存一致性流量。

## 3. 条件变量标准写法

条件变量必须和互斥锁、谓词状态一起使用：

```cpp
std::mutex m;
std::condition_variable cv;
bool ready = false;

void consumer() {
    std::unique_lock<std::mutex> lock(m);
    cv.wait(lock, [] { return ready; });
    // 条件成立，继续消费资源
}

void producer() {
    {
        std::lock_guard<std::mutex> lock(m);
        ready = true;
    }
    cv.notify_one();
}
```

这里 `wait(lock, pred)` 等价于：

```cpp
while (!pred()) {
    cv.wait(lock);
}
```

它能同时处理虚假唤醒和先 notify 后 wait 的问题。

## 4. 互斥锁、条件变量、信号量的区别

1. **互斥锁**保护临界区，核心是“同一时刻只能一个线程进入”。
2. **条件变量**不是资源计数器，核心是“某个状态变化后唤醒等待者”，状态必须由业务变量保存。
3. **信号量**内部有计数，`post` 可以累积，适合表示可用资源数量。

生产者消费者可以用条件变量，也可以用信号量。条件变量更适合复杂谓词，例如“队列非空且没有停止”；信号量更适合固定资源计数。

## 4.1 线程间通信方式

线程属于同一进程，共享虚拟地址空间，所以线程间“通信”本质上通常是共享内存上的同步与协作，而不是像进程间通信那样必须经过内核对象传递数据。

常见方式：

1. **共享变量 + 锁**：最基础方式，互斥锁保护共享数据，适合共享状态和容器。
2. **条件变量**：一个线程等待条件成立，另一个线程修改状态后唤醒，适合任务队列和生产者消费者。
3. **信号量**：用计数表示可用资源数量，适合限流、连接池、固定容量队列。
4. **原子变量**：适合状态位、引用计数、无锁队列中的索引推进。
5. **future/promise**：适合一次性结果传递，一个线程生产结果，另一个线程等待结果。
6. **管道/eventfd**：虽然常用于进程间通信，但也可在线程间配合 `epoll` 唤醒事件循环线程。
7. **线程安全队列/channel**：工程中常把锁、条件变量和队列封装成消息通道，降低共享状态复杂度。

面试里要注意区分：线程通信不是只能用“消息”，共享内存天然可见，但必须用锁、原子变量或条件变量保证互斥、可见性和顺序。

## 4.2 多线程服务器中怎么选

多线程服务器里线程间通信通常不是随便选一种 API，而是根据线程模型决定：

1. **I/O loop 之间或业务线程回投 I/O 线程**：优先使用任务队列 + `eventfd`/pipe 唤醒，让 socket 的读写和事件关注修改回到所属 loop 执行。
2. **线程池任务派发**：使用互斥锁 + 条件变量保护任务队列，空队列时 worker 阻塞等待。
3. **连接数、并发数、资源池控制**：使用信号量或令牌桶表达“还有多少资源可用”。
4. **统计计数和状态位**：使用 `std::atomic`，但多个变量的不变量仍需要锁。
5. **读多写少配置或缓存**：使用读写锁，或者用 RCU/Copy-On-Write 思路降低读路径加锁。

在 one loop per thread 模型中，比较推荐“消息投递”而不是多个线程直接共享同一个连接对象。这样可以把复杂的多线程读写问题收敛为：任务队列是否线程安全、唤醒是否可靠、队列堆积时是否有背压。

## 5. 易错点

1. 不要用裸 `cv.wait(lock)`，应使用带谓词版本。
2. `notify_one()` 不保存状态，真正保存状态的是 `ready`、队列长度等业务变量。
3. `std::atomic` 只能保证单变量原子操作，多个变量不变量通常仍需要锁。
4. 自旋锁不适合长临界区，否则会浪费 CPU。
5. 锁的粒度过大影响并发，粒度过小容易引入死锁和复杂度。

## 6. 真实场景

线程池任务队列通常用：

1. `std::mutex` 保护任务队列。
2. `std::condition_variable` 在队列为空时阻塞 worker。
3. `stop` 标志用于线程池关闭。
4. `notify_one/notify_all` 唤醒 worker 或广播退出。

共享缓存读多写少时可以用读写锁；高频计数器可以用原子变量；连接池可以用信号量限制并发借用数量。

## 7. 多线程安全问题和锁选择

多线程安全问题通常来自三类：共享数据被并发修改导致数据竞争，写入对其他线程不可见导致读到旧值，多步操作被线程切换打断导致不变量被破坏。锁的选择要从临界区长度、读写比例、是否允许睡眠、是否跨进程、是否需要公平性几个维度判断。

| 锁或同步方式 | 适用场景 | 注意事项 |
| --- | --- | --- |
| 互斥锁 | 保护普通共享对象、容器、连接状态 | 临界区不要做慢 I/O；避免锁顺序不一致导致死锁 |
| 读写锁 | 配置、路由表、缓存这类读多写少数据 | 写多时可能退化；注意写者饥饿策略 |
| 自旋锁 | 内核或低延迟场景中极短临界区 | 持锁期间不能阻塞；用户态长临界区会浪费 CPU |
| 递归锁 | 兼容历史代码中同线程重复进入的调用链 | 容易掩盖设计问题，优先拆清调用边界 |
| 条件变量 | 等待“队列非空”“状态变化”等条件 | 必须配合谓词循环，不能只依赖 notify |
| 信号量 | 连接池、令牌桶、固定资源计数 | 表达资源数量，不适合保护复杂不变量 |
| 原子变量 | 状态位、计数器、无锁结构索引 | 多变量不变量仍要锁；内存序要说明清楚 |
| RCU/COW | 极端读多写少、读路径低延迟 | 写路径和内存回收复杂，需要清晰生命周期 |

面试回答可以按“先保证正确，再谈性能”展开：普通共享状态用 mutex；读多写少用 shared_mutex 或 RCU；短小计数用 atomic；线程池等待任务用 condition_variable；资源配额用 semaphore；I/O 线程跨线程唤醒用 eventfd/pipe 加 epoll。不要为了“无锁”牺牲可维护性，无锁结构还要处理 ABA、内存回收和内存序。
