# 7. 线程池设计与轻量化

线程池是提前创建一组工作线程，复用这些线程执行任务，避免每个请求都创建和销毁线程。它解决的是线程创建成本、并发数量失控和任务排队治理问题。

## 1. 核心组件

一个基础线程池通常包含：

1. **任务队列**：保存待执行任务，可以是有界队列或无界队列。
2. **工作线程**：循环从队列取任务并执行。
3. **互斥锁和条件变量**：保护队列，并在无任务时阻塞 worker。
4. **停止标志**：用于优雅退出。
5. **背压策略**：队列满时拒绝、阻塞、降级或让调用线程执行。

## 2. 简化 C++ 实现

```cpp
#include <condition_variable>
#include <functional>
#include <mutex>
#include <queue>
#include <thread>
#include <vector>

class ThreadPool {
public:
    explicit ThreadPool(size_t n) {
        for (size_t i = 0; i < n; ++i) {
            workers_.emplace_back([this] { run(); });
        }
    }

    ~ThreadPool() {
        {
            std::lock_guard<std::mutex> lock(mu_);
            stop_ = true;
        }
        cv_.notify_all();
        for (auto& t : workers_) {
            if (t.joinable()) {
                t.join();
            }
        }
    }

    bool submit(std::function<void()> task) {
        {
            std::lock_guard<std::mutex> lock(mu_);
            if (stop_ || tasks_.size() >= max_queue_) {
                return false;
            }
            tasks_.push(std::move(task));
        }
        cv_.notify_one();
        return true;
    }

private:
    void run() {
        while (true) {
            std::function<void()> task;
            {
                std::unique_lock<std::mutex> lock(mu_);
                cv_.wait(lock, [this] {
                    return stop_ || !tasks_.empty();
                });
                if (stop_ && tasks_.empty()) {
                    return;
                }
                task = std::move(tasks_.front());
                tasks_.pop();
            }
            task();
        }
    }

    std::mutex mu_;
    std::condition_variable cv_;
    std::queue<std::function<void()>> tasks_;
    std::vector<std::thread> workers_;
    size_t max_queue_ = 1024;
    bool stop_ = false;
};
```

## 3. “轻量级”体现在哪里

面试里说线程池轻量，不能只说“线程少”。可以从这些点解释：

1. **线程复用**：避免频繁 `pthread_create` 和线程栈/TLS 初始化。
2. **固定上限**：限制并发执行单元，防止请求风暴把机器打满。
3. **任务对象小**：任务只保存必要参数，避免在队列中持有大对象或长生命周期资源。
4. **临界区短**：只在入队、出队时持锁，真正执行任务时释放锁。
5. **有界队列**：队列满时快速返回或降级，避免内存无限增长。
6. **线程亲和性**：I/O 线程和计算线程分离，避免事件循环被慢任务阻塞。

## 3.1 操作任务队列需要加锁吗

普通 `std::queue`、`std::deque`、`std::priority_queue` 都不是线程安全的。多个提交线程和多个 worker 同时访问任务队列时，入队、出队、检查空和停止状态必须同步。

最常见做法是：

```text
mutex 保护任务队列和停止标志
condition_variable 负责队列空时阻塞 worker
submit 入队后 notify_one
worker 被唤醒后取任务，释放锁，再执行任务
```

关键点：

1. **加互斥锁**：保护队列结构和 `stop` 标志，避免 data race。
2. **条件变量 wait 带谓词**：处理虚假唤醒和先 notify 后 wait。
3. **临界区要短**：只在入队、出队时持锁，不能持锁执行任务。
4. **有界队列**：队列满时要拒绝、阻塞、降级或调用方执行。
5. **关闭语义一致**：停止后是否继续执行队列中已有任务，要在状态机里定义清楚。

示例：

```cpp
std::mutex mu;
std::condition_variable cv;
std::queue<Task> tasks;
bool stop = false;

void submit(Task t) {
    {
        std::lock_guard<std::mutex> lock(mu);
        if (stop) {
            throw std::runtime_error("stopped");
        }
        tasks.push(std::move(t));
    }
    cv.notify_one();
}

void worker() {
    for (;;) {
        Task task;
        {
            std::unique_lock<std::mutex> lock(mu);
            cv.wait(lock, [&] { return stop || !tasks.empty(); });
            if (stop && tasks.empty()) {
                return;
            }
            task = std::move(tasks.front());
            tasks.pop();
        }
        task();
    }
}
```

什么锁更合适：

1. **`std::mutex`**：默认选择，任务执行时间远大于入队出队成本时足够好。
2. **自旋锁**：临界区极短且不会阻塞时才考虑；线程池队列可能等待条件变量，一般不用自旋锁。
3. **读写锁**：任务队列写多读少，入队出队都会修改结构，读写锁收益不大。
4. **无锁 MPMC 队列**：高频低延迟场景可用，但要处理 ABA、内存回收、容量和失败重试，面试手写不建议上来就选。
5. **分片队列/work stealing**：任务量大、锁竞争明显时，把全局队列拆成每线程本地队列，空闲线程窃取任务。

面试回答可以说：需要加锁，除非使用已经验证过的并发队列。基础线程池用 `mutex + condition_variable` 保护任务队列，入队和出队持锁，执行任务前释放锁。锁的粒度要小，队列要有容量上限；如果锁竞争成为瓶颈，再考虑 MPMC 无锁队列、分片队列或 work stealing。

## 4. 线程数怎么选

1. **CPU 密集型**：接近 CPU 核心数，通常为 `Ncpu` 或 `Ncpu + 1`。
2. **I/O 密集型**：可以多于核心数，但要结合下游连接池、队列等待和 P99 延迟压测。
3. **混合任务**：拆成 I/O 线程池和计算线程池，避免慢 I/O 占满计算线程。
4. **事件驱动服务**：one loop per thread 负责连接读写，CPU 或阻塞任务投递给 worker pool。

经验公式可以作为起点：

```text
线程数 = CPU 核数 * (1 + 等待时间 / 计算时间)
```

但最终要以压测和线上指标为准，观察 CPU 利用率、上下文切换、队列长度、任务等待时间和尾延迟。

## 4.1 如何平衡性能和开销

线程池提升性能的前提是“复用线程 + 控制并发”，不是线程越多越好。平衡时可以从收益和成本两边看：

收益：

1. 复用工作线程，避免频繁创建、销毁线程。
2. 限制同时运行任务数量，避免请求风暴把 CPU、内存和下游连接池打满。
3. 通过任务队列吸收短时峰值，让主链路有缓冲。
4. 将 I/O loop 和耗时业务隔离，避免一个慢任务卡住所有连接。

成本：

1. 每个线程都有栈、TLS、调度上下文和内核 task 结构。
2. 线程过多会增加上下文切换、运行队列长度和缓存/TLB 失效。
3. 共享任务队列可能产生锁竞争，队列越长尾延迟越高。
4. 阻塞任务太多时，会占满 worker，导致后续任务排队。
5. 下游容量固定时，盲目扩线程只会把压力转移到数据库、Redis 或 RPC。

工程判断方法：

1. CPU 密集任务看 CPU 利用率、run queue、上下文切换和火焰图热点。
2. I/O 密集任务看排队时间、下游连接池等待、超时率和下游 P99。
3. 队列长度持续增长说明消费能力不足或上游流量过大，要扩容、限流或降级。
4. 线程数增加后 QPS 不涨、P99 变差，通常说明锁竞争、调度开销或下游瓶颈已经出现。

## 4.2 线程池如何动态调整线程数

动态线程池通常会区分核心线程、最大线程、空闲回收时间和队列容量。调整依据不是单个指标，而是多个指标组合：

1. **队列长度和排队时间**：队列持续接近上限，且任务没有过期，说明需要扩容或扩实例。
2. **活跃线程比例**：活跃线程长期接近总线程数，说明 worker 被打满。
3. **CPU 利用率**：CPU 已经接近饱和时，不应继续扩 CPU 密集线程。
4. **上下文切换**：切换数明显上升且吞吐不升，说明线程过多。
5. **下游限额**：数据库连接池、RPC 并发、磁盘 I/O 已满时，扩线程没有意义。
6. **任务类型**：阻塞 I/O 可以适当扩，CPU 计算更应接近核心数。

一个保守策略：

```text
队列高水位 + CPU 未满 + 下游健康 -> 每次小步增加 worker
队列低水位 + 空闲时间超过阈值 -> 回收非核心 worker
CPU 满或下游超时升高 -> 不扩线程，优先限流、降级或拆分线程池
```

动态调整要避免抖动：

1. 设置扩容和缩容的冷却时间。
2. 使用高低水位线，而不是一个阈值来回切。
3. 每次只调整少量线程。
4. 对不同业务使用独立线程池，避免慢任务拖垮核心链路。
5. 指标要看一段时间窗口，不能被瞬时尖峰带偏。

## 5. 队列满和异常处理

线程池最容易被忽略的是失败路径：

1. **拒绝策略**：直接返回错误、丢弃低优先级任务、调用方同步执行、阻塞等待或扩容。
2. **超时控制**：任务排队时间超过阈值时取消，避免执行已经过期的请求。
3. **异常隔离**：任务内部异常必须捕获，不能让 worker 线程异常退出。
4. **优雅关闭**：停止接收新任务，等待已有任务完成或到超时后强制退出。
5. **可观测性**：暴露队列长度、活跃线程数、拒绝次数、任务耗时和排队耗时。

## 6. 易错点

1. `notify_one` 之前必须修改队列状态，否则可能丢通知。
2. `cv.wait` 必须带谓词，处理虚假唤醒和先 notify 后 wait。
3. 不要在持锁状态下执行任务，否则所有 worker 串行化。
4. 无界队列会把短时流量冲击转化为内存上涨和长尾延迟。
5. 线程池不能让阻塞依赖无限堆积，数据库、Redis、RPC 都要有超时和连接池上限。

## 7. 真实场景

对象存储、网关和 RPC 服务里，常见做法是：网络 I/O 线程只负责收发和协议解析，耗时的校验、压缩、磁盘读写、元数据查询交给 worker pool。线程池任务队列必须有上限，队列满时对客户端返回限流或稍后重试，不能让后台任务无限积压。
