# 10. 进程间同步方式

进程间同步是让多个进程按正确顺序访问共享资源。它和 IPC 传输数据不同：管道、消息队列、共享内存解决“数据怎么传”，同步原语解决“什么时候能读写、谁先谁后、并发是否安全”。

## 1. 除了 mutex 还能用什么

常见进程间同步方式：

| 方式 | 典型 API | 核心语义 | 适用场景 |
| --- | --- | --- | --- |
| POSIX 信号量 | `sem_open/sem_wait/sem_post` | 计数许可证 | 资源池、生产者消费者、进程间通知 |
| System V 信号量 | `semget/semop` | 信号量集合，支持多操作原子执行 | 老系统、复杂 IPC 原子操作 |
| eventfd | `eventfd/read/write` | 64 位计数器 fd | 唤醒 epoll 线程、共享内存消息通知 |
| futex | `futex(FUTEX_WAIT/WAKE)` | 用户态原子变量 + 内核等待队列 | 自定义高性能锁、条件变量、信号量 |
| 文件锁 | `flock/fcntl` | 基于文件的互斥 | 单实例、跨进程任务互斥 |
| 原子变量 | `std::atomic` 放在共享内存 | 无锁状态同步 | ring buffer 索引、版本号、状态位 |
| 条件变量 | `pthread_condattr_setpshared` | 条件等待和唤醒 | 多进程共享队列，配合进程间 mutex |
| 管道/UDS | `pipe/socketpair` | 阻塞读写或事件通知 | 简单同步、唤醒、父子进程协调 |

## 2. 信号量

信号量内部是一个计数器。`wait/P` 尝试获取一个资源，计数不够时阻塞；`post/V` 释放资源并唤醒等待者。

适合场景：

1. 固定容量队列：空槽数量和可读元素数量分别用两个信号量表示。
2. 限制并发数：最多允许 N 个进程同时进入某段逻辑。
3. 共享内存通知：生产者写入数据后 `sem_post`，消费者 `sem_wait` 后读取。

易错点：二值信号量可以模拟互斥，但它没有 mutex 那种严格所有权语义，`post` 多一次会把并发上限放大。

### 2.1 信号量如何在不同进程间同步

跨进程信号量的关键是：同步对象必须被多个进程共同看见。常见做法有三种。

1. **POSIX 命名信号量**：用 `sem_open` 创建或打开一个带名字的内核对象，不要求进程有亲缘关系。
2. **POSIX 未命名信号量 + 共享内存**：把 `sem_t` 放在 `mmap` 或 `shm_open` 得到的共享内存里，并用 `sem_init(&sem, 1, value)`，其中 `pshared=1` 表示进程间共享。
3. **System V 信号量**：用 `semget/semop/semctl` 管理信号量集合，适合老系统和需要多信号量原子操作的场景。

简化流程：

```text
生产者进程:
  写共享内存数据
  sem_post(data_ready)

消费者进程:
  sem_wait(data_ready)
  读共享内存数据
```

注意事项：

1. 信号量只负责同步或计数，不负责传输大数据；数据本体通常放共享内存、文件或 socket。
2. `sem_wait` 可能被信号中断返回 `EINTR`，生产代码要处理重试或退出。
3. 命名信号量要用 `sem_unlink` 清理名字，防止下次启动继承旧状态。
4. 持有资源的进程崩溃时，信号量计数可能无法自动恢复，关键路径要考虑超时、健康检查和重建。

## 3. eventfd

`eventfd` 是 Linux 提供的事件计数器，返回一个 fd。一个进程写入 8 字节整数，另一个进程可以读出计数。因为它是 fd，所以可以加入 `epoll`。

典型组合：

```text
共享内存 ring buffer 传输数据
eventfd 通知“有新数据”
epoll 同时监听 socket、timerfd、eventfd
```

优点：

1. 比 pipe 更轻量，语义是计数而不是字节流。
2. 能和 Reactor 事件循环统一。
3. 支持跨线程和跨进程通知。

注意：eventfd 只适合通知，不适合承载大数据；数据本体仍应放共享内存、文件或 socket 中。

## 4. futex 和进程间锁

futex 的思想是“无竞争在用户态解决，有竞争才进入内核”。共享内存里放一个整数，进程先用原子操作尝试修改；如果发现资源不可用，再调用 futex 把自己挂到内核等待队列。

简化流程：

```text
尝试 CAS 抢锁
  -> 成功：不进内核
  -> 失败：futex wait 睡眠
解锁方修改状态
  -> futex wake 唤醒等待者
```

glibc 的 pthread mutex、条件变量、POSIX 信号量在 Linux 上通常都会利用 futex 优化竞争路径。多进程使用时，同步变量必须位于共享内存中，并设置 `PTHREAD_PROCESS_SHARED`。

## 5. 文件锁

文件锁适合简单、低频的跨进程互斥，例如：

1. 防止同一个定时任务重复启动。
2. 多个部署脚本抢同一个发布锁。
3. 多进程更新同一个本地索引文件。

常用选择：

1. `flock`：接口简单，通常锁整个文件。
2. `fcntl` record lock：可锁文件范围，更灵活，也更复杂。

文件锁不适合高频临界区。它涉及内核文件对象和系统调用，性能通常不如共享内存中的原子变量或 futex。

## 6. 真实场景怎么选

1. **共享内存高吞吐队列**：原子变量维护读写下标，eventfd 或信号量负责阻塞唤醒。
2. **多个 worker 竞争有限资源**：信号量表达资源数量，例如最多 N 个进程同时执行压缩任务。
3. **单实例运行**：文件锁最简单，进程退出后锁随 fd 释放。
4. **高性能自研同步结构**：基于共享内存原子变量 + futex，但要严格验证内存序和崩溃恢复。
5. **复杂条件等待**：进程间 `pthread_mutex_t` + `pthread_cond_t`，属性设置为 `PTHREAD_PROCESS_SHARED`。

## 7. 易错点

1. 进程间同步对象必须对所有参与进程可见，通常要放在共享内存或内核命名对象中。
2. 普通 `std::mutex` 不能直接跨进程使用。
3. 持锁进程崩溃会导致其他进程永久等待，生产环境要考虑 robust mutex、超时和重建。
4. 原子变量跨进程可用的前提是放在共享映射中，并且平台和 ABI 对该原子类型支持共享内存上的原子操作。
5. 同步原语不能替代业务协议，写入多字段结构时仍要有版本号、提交标记或校验。

## 8. 面试回答模板

除了 mutex，进程间同步还可以用信号量、eventfd、futex、文件锁、共享内存里的原子变量、进程间条件变量，以及管道或 Unix Domain Socket 做通知。共享内存传大数据时常见组合是“共享内存 ring buffer + 原子读写下标 + eventfd/信号量唤醒”。信号量适合资源计数，eventfd 适合接入 epoll 事件循环，futex 适合实现高性能阻塞原语，文件锁适合低频互斥。工程上还要处理持锁进程崩溃、超时、内存序和共享段生命周期。
