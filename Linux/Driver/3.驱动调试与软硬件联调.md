# 3. 驱动调试与软硬件联调

驱动问题通常不是纯软件问题，也不是纯硬件问题。面试问“驱动编写中遇到问题怎么解决”，可以按“先确认现象，再分层定位，软件和硬件交叉验证”的思路回答。

## 1. 软件侧排查

软件侧先确认内核有没有正确识别设备、匹配驱动、申请资源和执行数据路径。

常用手段：

```bash
dmesg -w
lsmod
modprobe xxx
cat /proc/interrupts
cat /proc/iomem
ls /sys/bus/i2c/devices
ls /sys/kernel/debug
```

排查顺序：

1. **驱动是否加载**：模块是否 insmod，built-in 驱动是否进入 init/probe。
2. **设备是否匹配**：设备树 `compatible`、I2C 地址、platform name 是否和驱动表一致。
3. **资源是否正确**：寄存器基地址、中断号、GPIO、clock、reset、regulator、pinctrl。
4. **接口是否注册**：`/dev` 节点、sysfs、input、netdev、V4L2、ALSA 等是否出现。
5. **错误码路径**：每个内核 API 返回值都要检查，失败时打印具体资源和错误码。
6. **并发和上下文**：中断上下文不能睡眠，锁顺序、引用计数和设备移除要正确。

常用内核调试工具：

1. `printk` / `dev_dbg` / dynamic debug。
2. ftrace、tracepoint、perf。
3. `strace` 看用户态系统调用是否到达驱动。
4. `hexdump` / `devmem` 辅助看寄存器，但生产环境谨慎使用。
5. KASAN、lockdep、kmemleak 定位内存和锁问题。

## 2. 硬件侧排查

硬件侧要确认设备真的处在可通信、可工作的电气状态。

常见检查：

1. **供电**：电压是否正确，电源时序是否满足数据手册。
2. **时钟**：外部晶振、MCLK、总线 clock 是否存在。
3. **复位**：reset GPIO 极性和释放时序是否正确。
4. **管脚复用**：pinctrl 是否切到 I2C/SPI/UART/GPIO 对应功能。
5. **焊接和连线**：SCL/SDA 是否接反，片选/中断线是否接错。
6. **波形**：逻辑分析仪或示波器看 START、ACK、频率、上升沿、噪声。
7. **中断线**：电平/边沿触发是否正确，是否有抖动或一直拉低。

## 3. 软硬件联合定位例子

I2C sensor 读不到 ID：

```text
软件:
  dmesg 看 probe 是否进入
  检查设备树 compatible、reg 地址和 clock-frequency
  i2cdetect 看地址是否 ACK
  在读 ID 前打印 reset、power、寄存器地址

硬件:
  万用表量 VDD/IOVDD
  逻辑分析仪看 SCL/SDA 是否有 START、地址和 ACK
  检查上拉电阻、地址引脚、reset 引脚
  对照数据手册确认上电后等待时间
```

如果逻辑分析仪上没有波形，多半是 pinctrl、clock、控制器或代码路径问题；如果有地址但无 ACK，优先看地址、电源、reset、焊接和电平；如果 ACK 正常但读值不对，再看寄存器地址宽度、大小端、时序和初始化序列。

## 4. 易错点

1. 只看驱动代码，不看设备树和板级原理图。
2. I2C 地址把 8 位地址当 7 位地址使用。
3. 忘记打开 clock/regulator 或 reset 没释放。
4. 在中断上半部做耗时 I2C/SPI 读写，导致中断处理过长。
5. `printk` 过多改变时序，偶发问题可能被日志掩盖。
6. 忽略 suspend/resume，设备休眠后寄存器丢失或电源被关。

## 5. 面试回答模板

我排查驱动问题会先分层：软件看驱动是否加载、设备树是否匹配、probe 是否执行、资源申请是否成功、接口是否注册、错误码和上下文是否正确；硬件看供电、时钟、reset、pinctrl、连线、上拉和真实波形。比如 I2C 设备读不到 ID，软件侧查 compatible、reg 地址、clock-frequency、i2cdetect 和 dmesg；硬件侧用万用表看电源，用逻辑分析仪看 START、地址、ACK 和数据。如果没有波形偏软件和 pinmux，如果有地址无 ACK 偏地址/供电/reset/焊接，如果 ACK 正常但数据错，再查寄存器地址宽度、初始化序列和时序。
