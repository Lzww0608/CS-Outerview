# 22. 大文件单词频率统计

题目：一个大文件内存放不下，如何统计每个单词出现频率？如果一个 `hash_map` 存不下怎么办？

这个问题本质是海量数据计数。核心思路是先顺序扫描，再用分桶、外部排序或分布式计算把“全局大哈希表”拆成多个可以处理的小问题。

## 1. 内存足够

如果文件和词表都能放进内存，直接流式读取并用哈希表计数：

```cpp
#include <fstream>
#include <string>
#include <unordered_map>

std::unordered_map<std::string, std::uint64_t> countWords(const std::string& path) {
    std::ifstream in(path);
    std::unordered_map<std::string, std::uint64_t> freq;
    std::string word;
    while (in >> word) {
        ++freq[word];
    }
    return freq;
}
```

时间复杂度平均 `O(n)`，内存复杂度和不同单词数量、字符串长度、哈希表装载因子有关。

## 2. hash_map 存不下：哈希分桶

当全量 `hash_map` 放不下时，用同一个哈希函数把单词写入多个桶文件：

1. 选择桶数 `N`，让每个桶的不同单词集合预期能放入内存。
2. 顺序扫描原文件，解析单词。
3. 计算 `bucket = hash(word) % N`。
4. 把单词追加写入对应临时桶文件。
5. 逐个处理桶文件：用内存 `unordered_map` 统计该桶词频。
6. 把每个桶的统计结果写到最终结果文件或数据库。

相同单词的哈希值相同，因此一定进入同一个桶，不会出现同一个单词散落多个桶导致重复合并的问题。

```text
原始大文件
  -> bucket_0.tmp
  -> bucket_1.tmp
  -> ...
  -> bucket_N.tmp

逐桶加载 -> 内存计数 -> 输出局部结果
```

如果某个桶仍然过大，可以二次分桶，或者对该桶使用外部排序兜底。

## 3. 外部排序方案

外部排序适合后续还要按字典序输出结果，或者哈希分桶倾斜明显的场景。

步骤：

1. 分块读取大文件，每块能放进内存。
2. 在内存中把单词排序并局部计数，生成有序 run。
3. 对多个 run 做多路归并。
4. 归并时相同单词连续出现，累加频率并输出。

优点是顺序 I/O 友好、结果有序；缺点是排序成本通常高于哈希分桶。

## 4. 分布式方案

数据远超单机能力时，可以用 MapReduce、Spark 或 Flink：

```text
Map:    word -> (word, 1)
Shuffle: 相同 word 汇聚到同一个 reducer
Reduce: word -> sum(count)
```

这和单机哈希分桶思想一致，只是桶变成了分布式 shuffle 分区。真实场景要处理数据倾斜，例如热点词可以用两阶段聚合：先局部预聚合，再全局合并。

## 5. 工程注意事项

1. **单词定义**：要明确按空白、标点、大小写、Unicode 规则还是业务分词器切词。
2. **流式解析**：不要 `readAll`；使用缓冲读，处理跨缓冲区的半个单词。
3. **临时文件缓冲**：每个单词一次写系统调用会很慢，要用缓冲区或批量写。
4. **哈希倾斜**：桶大小差异大时要二次分桶或换哈希函数。
5. **超长单词**：限制最大 token 长度或单独处理异常输入。
6. **失败清理**：临时文件要带任务 id，失败后能清理或从中间结果恢复。
7. **输出很大**：结果也可能放不下内存，要流式写出。

## 6. 面试回答模板

如果内存足够，我会边读文件边用 `unordered_map<string, uint64_t>` 统计。`hash_map` 放不下时，我会先做哈希分桶：顺序扫描大文件，把每个单词按 `hash(word) % N` 写入对应临时桶，相同单词一定落在同一个桶；然后逐桶加载到内存统计词频并输出结果。如果单个桶仍然过大，可以二次分桶或改用外部排序。数据超过单机能力时，用 MapReduce/Spark 的 map、shuffle、reduce 做分布式词频统计，并通过局部预聚合降低网络 shuffle 压力。
