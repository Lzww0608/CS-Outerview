# 动态网络最短路径

题目：一千台服务器两两连接，服务器间延迟不断变化，如何确定任意两台服务器之间的最短路径？

这是动态带权图最短路径问题。服务器是点，网络链路是边，延迟是边权。关键要先判断规模、更新频率和查询频率。

## 问题建模

1. 点数：`V = 1000`。
2. 两两连接：接近完全图，边数 `E = V * (V - 1) / 2`，约 50 万条无向边。
3. 边权：实时或周期性测得的网络延迟。
4. 查询：任意两点最短路径。
5. 更新：延迟不断变化，边权会频繁更新。

## 查询少、更新多：按需 Dijkstra

如果查询不多，每次查询时从源点跑 Dijkstra：

```text
时间复杂度: O(E log V)
空间复杂度: O(V + E)
```

在 1000 台服务器、50 万边规模下，单次 Dijkstra 可接受，但如果 QPS 很高就不合适。

适用：

1. 查询频率低。
2. 延迟变化频繁。
3. 能接受单次查询毫秒级到更高延迟。

## 查询多、更新少：全源最短路缓存

如果查询非常多，可以预计算所有点对最短路：

1. Floyd-Warshall：`O(V^3)`，`V=1000` 时约 10 亿级操作。
2. 从每个源点跑 Dijkstra：`O(V * E log V)`，稀疏图更适合；完全图下也不轻。

预计算后查询：

```text
dist[u][v] O(1)
next[u][v] 可恢复路径
```

空间：

```text
dist[1000][1000] 约 100 万个数
double/int64 存储约 8MB
```

空间不是问题，问题在于边权动态变化会让预计算结果过期。

## 延迟不断变化：周期快照 + 增量更新

工程上通常不会对每次延迟抖动都全量重算，而是做快照和增量：

1. Agent 周期性探测链路 RTT，聚合成平滑延迟，例如 EWMA。
2. 控制面维护当前图快照。
3. 延迟变化小于阈值时不触发重算，避免抖动。
4. 定期全量计算所有点对最短路。
5. 对变化较大的边，触发局部重算或相关源点 Dijkstra。
6. 查询走最近一次稳定快照，保证低延迟。

这样牺牲一点实时性，换取稳定和可控成本。

## 分层和近似方案

1000 台服务器两两连接可以全局算，但真实跨机房网络更适合分层：

1. 机房内：计算机房内部最短路径。
2. 机房间：抽象为较小的骨干图。
3. 查询时先走机房级路径，再展开到服务器级路径。

如果只需要“足够好”的路径，可以使用：

1. K 条候选路径缓存。
2. A* 启发式搜索。
3. Landmark/ALT 预处理。
4. 限制跳数或限制候选邻居数量。

## 链路延迟数据怎么来

1. 主动探测：ping、TCP ping、应用层探测。
2. 被动观测：真实请求 RTT、连接建立耗时、丢包重传。
3. 平滑处理：EWMA、滑动窗口 P95，避免瞬时尖峰导致路径频繁抖动。
4. 异常剔除：丢包、超时、探测失败要转换为高权重或不可达。

## 易错点

1. 延迟是动态的，不能只回答一次 Floyd。
2. 最短延迟路径不一定是最稳定路径，工程上可能要考虑抖动、丢包和带宽。
3. 每次边权变化都全量重算会造成控制面抖动。
4. 完全图边很多，探测本身也有成本，要控制探测频率。
5. 查询路径要和数据快照版本绑定，否则可能出现路径不一致。

## 面试回答模板

我会把 1000 台服务器建模成带权图，服务器是点，链路延迟是边权。因为两两连接大约 50 万条边，如果查询少，可以按需对源点跑 Dijkstra，单次 `O(E log V)`；如果查询多，可以周期性预计算 `dist[u][v]`，查询 `O(1)`。由于延迟不断变化，工程上不会每次变化都全量重算，而是用探测数据做 EWMA 平滑，维护图快照，定期全量重算，边权变化超过阈值时做局部或相关源点重算。真实系统还会考虑丢包、抖动、带宽和路径稳定性，而不是只看瞬时最短 RTT。
