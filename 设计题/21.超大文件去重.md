# 21. 超大文件去重

超大文件去重的核心是：内存放不下全集时，不能直接把所有数据放进 `unordered_set`，要用外部存储做分治，让相同数据一定被分到同一个可处理的小问题里。

## 1. 精确去重：哈希分桶

如果文件按行去重，常见流程：

```text
顺序读取大文件
-> 对每一行计算 hash(line)
-> 写入 bucket[hash(line) % N]
-> 逐个 bucket 在内存中去重
-> 输出每个 bucket 的去重结果
```

因为相同内容的哈希值相同，所以相同内容一定落入同一个桶。只要每个桶能放进内存，就能在桶内用哈希集合精确去重。

### 1.1 10 个 1GB 文件，内存只有 200MB

如果题目具体说“10 个 1GB 文件，机器只有约 200MB 内存，找出去重后的内容”，可以把所有文件当成一个 10GB 输入流，不能分别在内存里建 10 个集合。

一个可落地方案：

1. 估算记录平均大小和内存上限，选择足够多的桶，例如 256、512 或更多。
2. 顺序扫描 10 个文件，对每条记录计算稳定哈希。
3. 按 `hash(record) % bucket_count` 追加写入对应临时桶。
4. 逐个处理桶：桶小于内存阈值时，用 `unordered_set` 去重并输出；桶仍过大时继续二次分桶。
5. 输出结果流式写到目标文件，不把全部去重结果再合并进内存。

需要强调两点：

1. 相同记录必须使用同一个哈希和同一个分桶规则，这样它们一定进入同一个桶，桶内去重才是全局正确的。
2. 桶数量不是固定答案，要根据内存、记录大小、数据倾斜和临时磁盘空间调整。哈希严重倾斜时要对大桶二次拆分。

## 2. 桶仍然过大怎么办

如果某个小文件中没有重复数据，但再次合并后仍超过单机内存，说明问题不是“重复太多”，而是**唯一数据本身太多**。这时不能强行合并到内存，而要继续使用外部算法：

1. **二次分桶**：对过大的 bucket 使用另一个哈希或更大的 `N` 再分桶。
2. **外部排序**：每块内存排序去重生成有序 run，再做多路归并，归并时跳过重复行。
3. **流式输出**：如果目标只是生成去重后的文件，不需要把全部结果放入内存，处理完一个桶就顺序写出。
4. **分布式处理**：用 MapReduce/Spark/Flink，按 hash shuffle，相同 key 到同一个 reducer。

## 3. 外部排序方案

外部排序适合需要输出全局有序去重结果的场景：

```text
读取内存可容纳的一块数据
-> 内存排序并去重
-> 写成一个有序 run 文件
-> 多路归并所有 run
-> 只输出和上一条不同的记录
```

多路归并只需要保留每个 run 当前的一条记录和一个小顶堆，内存复杂度与 run 数量相关，而不是与总数据量相关。

## 4. 近似去重

如果只需要判断“是否可能出现过”，可以用布隆过滤器；如果只需要估算不同元素数量，可以用 HyperLogLog。但它们不是精确去重：

1. 布隆过滤器有误判，可能把新元素误认为已存在。
2. HyperLogLog 只能估算基数，不能输出去重后的明细。

## 5. 工程注意事项

1. 哈希函数要稳定且分布均匀，避免数据倾斜。
2. 临时文件写入要有缓冲，减少小 I/O。
3. 记录边界要定义清楚，是按行、按 token 还是按二进制块。
4. 超长行要单独处理，避免单条记录超过内存。
5. 临时文件要能失败清理和断点续跑。
6. 如果是跨机器去重，要考虑网络 shuffle、数据压缩和 reducer 热点。

## 6. 面试回答模板

超大文件去重我会先用哈希分桶：顺序扫描文件，把每条记录按 `hash(record) % N` 写入临时桶，相同记录一定进入同一桶，然后逐桶加载到内存中用哈希集合去重并输出。如果某个桶仍然过大，就对这个桶继续二次分桶，或者改用外部排序：分块排序去重生成 run，再多路归并，只保留不同记录。即使拆出来的小文件本身没有重复，最终结果太大也不应该合并进内存，而是流式写出或分布式处理。
