# 18. 大文件不同字符串计数

## 1. 题目

一个很大的文件，内容是用空格隔开的字符串，内存放不下整个文件，要求计算其中有多少个不同的字符串。

这个问题本质是海量数据去重计数。

## 2. 如果内存足够

直接用哈希集合：

```text
unordered_set<string> seen
逐个读取 token
插入 seen
答案 = seen.size()
```

时间复杂度平均 `O(n)`，但内存会随不同字符串数量线性增长。

## 3. 精确方案：哈希分桶

内存不足时使用分治：

1. 顺序扫描大文件，按空格解析每个字符串。
2. 对字符串计算哈希值 `h = hash(s)`。
3. 写入第 `h % N` 个临时桶文件。
4. 因为相同字符串哈希值相同，所以一定落到同一个桶。
5. 逐个处理桶文件，在内存中用 `unordered_set` 去重并累加不同字符串数量。
6. 删除临时文件。

关键是选择 `N`，让每个桶内的不同字符串集合能放入内存。

```text
answer = 0
for bucket in buckets:
    seen.clear()
    for token in bucket:
        seen.insert(token)
    answer += seen.size()
```

## 4. 精确方案：外部排序

也可以用外部排序：

1. 分块读取文件，每块在内存中排序并去重，生成有序 run。
2. 对多个 run 做多路归并。
3. 归并时只要和上一个输出字符串不同，就把计数加 1。

外部排序的优势是结果有序，适合后续还要输出所有不同字符串的场景；缺点是排序成本通常高于哈希分桶。

## 5. 近似方案：HyperLogLog

如果只要求估算不同字符串数量，可以用 HyperLogLog：

1. 内存很小。
2. 可合并，适合分布式统计。
3. 有误差，不能得到精确答案。

Redis 的 `PFADD/PFCOUNT` 就是典型应用。

布隆过滤器不适合直接给出精确不同数量。它可以判断“可能存在/一定不存在”，但有误判率，直接计数会低估或引入偏差。

## 6. 工程注意事项

1. 解析 token 时要处理连续空格、换行、制表符和超长字符串。
2. 写桶文件时使用缓冲，避免每个 token 一次系统调用。
3. 哈希函数要分布均匀，避免某个桶特别大。
4. 如果某个桶仍然过大，可以对该桶二次分桶。
5. 临时文件要有清理机制，失败重试要避免重复累加。

## 7. 面试回答模板

如果内存够，直接用 `unordered_set` 统计不同字符串数量。文件太大时，我会用哈希分桶：顺序扫描文件，把每个字符串按 `hash(s) % N` 写到对应临时文件，相同字符串一定进入同一个桶；然后逐桶加载到内存，用哈希集合去重并把每个桶的 distinct 数相加。这样是精确方案。若只要估算，可以用 HyperLogLog，内存很小且可合并，但有误差。
