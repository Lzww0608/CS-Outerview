# 海量 IP 出现次数查询

题目：海量 IP 中，给定一个 IP，输出它出现的次数，并分析时间复杂度和空间复杂度。回答时要先区分“只查询一次”还是“要支持多次查询”，两种方案完全不同。

## 只查询一次

如果只给定一个目标 IP，最简单也最稳的是顺序扫描：

```text
count = 0
for ip in file:
    if ip == target:
        count++
return count
```

复杂度：

1. 时间复杂度：`O(n)`，必须读完整份数据。
2. 空间复杂度：`O(1)`，只需要一个计数器。

优点是内存最低、实现简单；缺点是每次查询都要全量扫描，无法支撑高频查询。

### 日志文件里按 IP 统计

如果日志每一行都有 `IP time context`，并且 IP 是第一列，可以直接用 `awk` 精确按字段统计：

```bash
awk -v target="192.168.1.10" '$1 == target { cnt++ } END { print cnt + 0 }' access.log
```

如果 IP 不固定在第一列，要先明确日志格式。可以用结构化解析、正则提取或日志系统字段索引，避免简单 `grep 192.168.1.1` 把 `192.168.1.10`、上下文里的字符串也误算进去。

多文件或压缩日志可以用：

```bash
zgrep -h "192.168.1.10" *.log.gz | awk '$1 == "192.168.1.10" { cnt++ } END { print cnt + 0 }'
```

单次命令本质仍是顺序扫描，时间 `O(n)`、空间 `O(1)`。如果要频繁按 IP 查询，应在采集或入库阶段把 IP 解析成结构化字段，并建立倒排索引、列式索引或 `IP -> count` 聚合表。

## 多次查询：构建索引

如果要支持很多次查询，可以预处理构建 `IP -> count` 的索引。

### 内存足够

用哈希表：

```cpp
#include <cstdint>
#include <string>
#include <unordered_map>

uint32_t parseIPv4(const std::string& ip); // 把 a.b.c.d 转为 uint32_t

std::unordered_map<uint32_t, uint64_t> buildIndex(const std::vector<std::string>& ips) {
    std::unordered_map<uint32_t, uint64_t> cnt;
    cnt.reserve(ips.size());
    for (const auto& ip : ips) {
        ++cnt[parseIPv4(ip)];
    }
    return cnt;
}
```

复杂度：

1. 预处理时间：`O(n)`。
2. 查询时间：平均 `O(1)`。
3. 空间复杂度：`O(m)`，`m` 是不同 IP 个数。

### IPv4 全量数组

IPv4 只有 `2^32` 种地址。如果用 `uint32_t count[2^32]` 精确计数，空间大约：

```text
2^32 * 4B = 16GB
```

如果计数可能超过 `uint32_t`，用 `uint64_t` 需要 32GB。这个方案查询是 `O(1)`，但内存成本高，适合内存充足且查询极频繁的离线/专用场景。

## 内存不足：分桶外排

如果数据量和不同 IP 数都很大，内存放不下哈希表，可以分桶：

1. 第一遍扫描文件，把每个 IP 按 `hash(ip) % B` 写入对应桶文件。
2. 因为相同 IP 的 hash 一样，所以一定落到同一个桶。
3. 查询目标 IP 时，只需要计算目标桶编号，读取该桶并计数。
4. 如果要构建全量索引，就逐个桶加载到内存计数后输出结果。

复杂度：

1. 构建分桶时间：`O(n)`。
2. 查询目标 IP：`O(size(bucket))`，平均约 `O(n / B)`。
3. 内存复杂度：由单桶大小决定，可控制在内存上限内。
4. 额外磁盘空间：约等于原始数据大小。

## 如果只问是否存在

如果题目改成“判断 IP 是否出现过”，可以用 Bitmap：

```text
2^32 bit = 512MB
```

但 Bitmap 只能表示是否出现，不能统计出现次数。要统计次数需要计数数组、哈希表或外部分桶。

## IPv6 怎么办

IPv6 地址空间是 `2^128`，不能用全量数组或全量 Bitmap。通常选择：

1. 哈希表统计活跃地址。
2. 外部分桶。
3. 数据库/LSM/KV 存储。
4. 近似统计用 Count-Min Sketch，但会有误差。

## 易错点

1. 只查询一次时，不要过度设计，顺序扫描就是最优空间方案。
2. Bitmap 不能直接统计次数，只能做存在性判断，除非扩展为计数数组。
3. 哈希表平均 `O(1)`，但内存开销远大于 key/value 本身。
4. 分桶时必须保证相同 IP 进入同一桶，否则无法精确统计。
5. 文本 IP 解析成本不低，高性能场景应转为 `uint32_t` 存储。

## 面试回答模板

如果只给一个目标 IP 查询一次，我会顺序扫描文件，遇到目标 IP 就计数，时间 `O(n)`，空间 `O(1)`。如果要支持大量查询，就预处理构建 `IP -> count` 的索引，内存足够用哈希表，构建 `O(n)`、查询平均 `O(1)`、空间 `O(m)`。IPv4 也可以用 `2^32` 的计数数组，`uint32_t` 计数约 16GB，查询严格 `O(1)`，但内存成本高。内存不够时按 hash 分桶，相同 IP 落同一桶，查询时只扫目标桶，或者逐桶构建外部索引。
