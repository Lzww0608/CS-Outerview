# 数据库存储引擎详解

## 一、存储引擎概述

存储引擎是数据库管理系统（DBMS）的核心组件，负责数据的物理存储、索引管理、事务处理和并发控制。不同的存储引擎采用不同的数据结构、锁策略和日志机制，适用于不同的业务场景。

## 二、MySQL 存储引擎

### 2.1 InnoDB 存储引擎

**定位**：MySQL 5.5+ 的默认存储引擎，面向在线事务处理（OLTP）场景。

**核心特性**：

1. **事务支持**：完整的 ACID 事务支持，通过 redo log 和 undo log 实现
2. **行级锁**：采用 MVCC（多版本并发控制），支持读不阻塞写
3. **聚簇索引**：主键索引的叶子节点存储完整行数据
4. **崩溃恢复**：通过 redo log 实现崩溃安全恢复
5. **外键约束**：支持外键引用完整性

**数据结构**：B+ 树（支持主键索引、唯一索引、普通索引）

**适用场景**：
- 订单系统、支付系统、库存系统等一致性要求高的业务
- 高并发读写混合场景
- 需要事务支持的应用

```sql
-- 查看 InnoDB 状态
SHOW ENGINE INNODB STATUS;

-- 创建 InnoDB 表（默认引擎）
CREATE TABLE orders (
    id BIGINT PRIMARY KEY,
    user_id BIGINT NOT NULL,
    amount DECIMAL(10,2),
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
) ENGINE=InnoDB;
```

### 2.2 MyISAM 存储引擎

**定位**：MySQL 早期的默认引擎，非事务型，已逐步被 InnoDB 替代。

**核心特性**：

1. **表级锁**：不支持行级锁，并发写入性能较差
2. **不支持事务**：没有 ACID 保障
3. **非聚簇索引**：索引和数据分离，索引叶子存储数据指针
4. **压缩表**：支持表压缩，节省存储空间
5. **全文索引**：早期 MySQL 唯一支持全文索引的引擎

**数据结构**：B+ 树（索引）+ 堆文件（数据）

**适用场景**：
- 以读为主、很少更新的场景
- 全文检索需求
- 历史数据归档

```sql
-- 创建 MyISAM 表
CREATE TABLE logs (
    id BIGINT PRIMARY KEY,
    message TEXT,
    created_at TIMESTAMP
) ENGINE=MyISAM;
```

### 2.3 Memory 存储引擎

**定位**：数据完全存储在内存中的引擎，重启后数据丢失。

**核心特性**：

1. **内存存储**：所有数据存储在内存，访问速度极快
2. **哈希索引**：默认使用哈希索引，查找复杂度 O(1)
3. **表级锁**：并发写入性能受限
4. **固定长度**：所有字段固定长度，不支持 BLOB/TEXT
5. **数据易失**：服务重启或崩溃后数据丢失

**适用场景**：
- 临时表、缓存表
- 会话管理、排行榜
- 需要快速查找的中间结果

```sql
-- 创建 Memory 表
CREATE TABLE session_cache (
    session_id VARCHAR(64) PRIMARY KEY,
    user_data TEXT,
    expires_at TIMESTAMP
) ENGINE=Memory;
```

### 2.4 Archive 存储引擎

**定位**：面向归档和压缩存储的引擎，适合历史数据归档。

**核心特性**：

1. **高压缩比**：使用 zlib 压缩，存储空间节省 80%+
2. **只支持插入和查询**：不支持 UPDATE 和 DELETE
3. **行级锁**：支持并发插入
4. **无索引**：只能顺序扫描

**适用场景**：
- 日志归档、审计记录
- 历史数据存档
- 统计分析的只读数据

### 2.5 InnoDB 与 MyISAM 对比

| 对比项 | InnoDB | MyISAM |
|--------|--------|--------|
| 事务支持 | 完整 ACID | 不支持 |
| 锁粒度 | 行锁 + 意向锁 | 表锁 |
| 并发能力 | 高 | 低（写入锁表） |
| 崩溃恢复 | 自动恢复 | 需要手动修复 |
| MVCC | 支持 | 不支持 |
| 外键 | 支持 | 不支持 |
| 索引结构 | 聚簇索引 | 非聚簇索引 |
| 适用场景 | OLTP 业务 | OLAP 只读 |

## 三、列式存储引擎

### 3.1 ClickHouse

**定位**：俄罗斯 Yandex 开源的列式数据库，面向在线分析处理（OLAP）。

**核心特性**：

1. **列式存储**：同列数据连续存储，压缩率高，列查询快
2. **向量化执行**：SIMD 指令加速计算
3. **分布式架构**：支持分片副本，横向扩展
4. **MergeTree 表引擎**：支持实时数据写入和后台合并
5. **MaterializedMySQL**：同步 MySQL 数据

**数据结构**：MergeTree 系列（类似 LSM-Tree 的变体）

**适用场景**：
- 用户行为分析、漏斗分析
- 实时报表、监控大屏
- 日志存储与分析

```sql
-- ClickHouse 建表
CREATE TABLE events (
    event_date Date,
    user_id UInt64,
    event_type String,
    properties Map(String, String)
) ENGINE = MergeTree()
PARTITION BY toYYYYMM(event_date)
ORDER BY (user_id, event_date);
```

### 3.2 Apache Parquet / ORC

**定位**：列式数据存储格式，常用于数据湖、Hive、Spark。

**核心特性**：

1. **列式存储**：按列存储，列压缩效率高
2. **嵌套结构**：支持复杂嵌套数据类型
3. **元数据存储**：包含列式统计信息，加速查询
4. **多种编码**：字典编码、RLE 编码等

## 四、键值存储引擎

### 4.1 RocksDB

**定位**：Facebook 开源的嵌入式 KV 存储引擎，源自 LevelDB。

**核心特性**：

1. **LSM-Tree 结构**：写入性能极高，通过后台 Compaction 平衡读性能
2. **灵活配置**：支持手动调优 memtable 大小、Compaction 策略等
3. **多版本支持**：支持快照、事务
4. **广泛使用**：MyRocks、TiDB、Cassandra 等底层引擎

**数据结构**：LSM-Tree（MemTable → Immutable MemTable → SSTable）

**适用场景**：
- 写入密集型场景（日志、监控）
- 需要高吞吐的 KV 存储
- 嵌入式数据库

```cpp
// RocksDB 基础操作
rocksdb::DB* db;
rocksdb::Options options;
options.create_if_missing = true;
rocksdb::Status status = rocksdb::DB::Open(options, "/tmp/testdb", &db);

// 写入
db->Put(rocksdb::WriteOptions(), "key1", "value1");

// 读取
std::string value;
db->Get(rocksdb::ReadOptions(), "key1", &value);

// 删除
db->Delete(rocksdb::WriteOptions(), "key1");
```

### 4.2 LevelDB

**定位**：Google 开源的 KV 存储引擎，RocksDB 的前身。

**核心特性**：

1. **LSM-Tree 实现**：写入先写日志，再写 MemTable
2. **顺序写入优化**：写入吞吐量高
3. **不支持并发**：单线程写入，多线程读取
4. **简单可靠**：代码量小，适合学习

### 4.3 RocksDB vs LevelDB 对比

| 对比项 | RocksDB | LevelDB |
|--------|---------|---------|
| 开发活跃度 | 活跃（持续更新） | 较低（维护状态） |
| 并发支持 | 支持多线程写入 | 单线程写入 |
| 性能调优 | 丰富配置项 | 较简单 |
| 二次开发 | 支持插件、ColumnFamily | 不支持 |

## 五、时序存储引擎

### 5.1 InfluxDB

**定位**：专为时序数据设计的数据库，支持高写入吞吐和高效聚合查询。

**核心特性**：

1. **时间线索引**：按标签快速定位时间线
2. **LSM-Tree + TSM**：类似 InfluxDB 的 TSM 引擎
3. **数据压缩**：高效压缩时序数据
4. **连续查询**：支持预聚合，定期计算
5. **保留策略**：自动过期老数据

**数据结构**：TSM（Time-Structured Merge Tree）

**适用场景**：
- IoT 传感器数据
- 监控系统指标
- 金融行情数据

### 5.2 TimescaleDB

**定位**：PostgreSQL 的时序扩展，基于 Hypertable 实现。

**核心特性**：

1. **Hypertable**：自动分区，按时间范围分 chunk
2. **兼容 PostgreSQL**：完整的 SQL 支持
3. **自动压缩**：按时间策略压缩历史数据
4. **持续聚合**：实时更新聚合结果

## 六、文档存储引擎

### 6.1 MongoDB WiredTiger

**定位**：MongoDB 的默认存储引擎，面向文档型数据。

**核心特性**：

1. **文档级锁**：比 MyISAM 的表锁并发能力更强
2. **MMAPv1/ WiredTiger**：早期 MMAPv1，已被 WiredTiger 替代
3. **B+ 树索引**：支持多种索引类型
4. **压缩存储**：支持 snappy、zstd 压缩
5. **事务支持**：MongoDB 4.0+ 支持副本集内事务

### 6.2 Elasticsearch

**定位**：基于 Lucene 的搜索引擎，也是一种文档存储引擎。

**核心特性**：

1. **倒排索引**：全文检索的核心
2. **分布式架构**：天然支持分片副本
3. **聚合分析**：强大的聚合查询能力
4. **Near Real-Time**：写入后秒级可查询

## 七、存储引擎选择指南

### 7.1 选择维度

| 维度 | 考虑因素 |
|------|----------|
| 事务需求 | 是否需要 ACID 事务 |
| 并发读写 | 读写比例、并发量 |
| 数据量 | 数据规模、增长速度 |
| 查询模式 | 点查、范围查、全文检索 |
| 一致性要求 | 强一致、最终一致 |
| 运维复杂度 | 团队技术栈、运维能力 |

### 7.2 选择决策树

```text
是否需要事务？
    │
    ├── 否 → 数据是否需要持久化？
    │         │
    │         ├── 是 → 是否需要 SQL 支持？
    │         │         │
    │         │         ├── 是 → MyISAM / Archive
    │         │         └── 否 → RocksDB / LevelDB
    │         │
    │         └── 否 → Memory / Redis
    │
    └── 是 → 是否分析为主？
              │
              ├── 是 → ClickHouse / Druid / Pinot
              │
              └── 否 → InnoDB / PostgreSQL
```

## 八、面试常见问题

### Q1: InnoDB 和 MyISAM 的区别？

1. **事务支持**：InnoDB 支持完整 ACID 事务，MyISAM 不支持
2. **锁粒度**：InnoDB 行锁 + 意向锁，MyISAM 表锁
3. **并发能力**：InnoDB 并发读写强，MyISAM 写入会锁表
4. **崩溃恢复**：InnoDB 自动恢复，MyISAM 需要手动 repair
5. **索引结构**：InnoDB 聚簇索引，MyISAM 非聚簇索引

### Q2: 为什么 InnoDB 适合 OLTP 场景？

1. 事务支持保证数据一致性
2. 行级锁降低并发冲突
3. MVCC 让读不阻塞写
4. 聚簇索引优化主键查询
5. redo log 保证崩溃恢复

### Q3: LSM-Tree 和 B+Tree 的区别？

| 对比项 | LSM-Tree | B+Tree |
|--------|----------|--------|
| 写入性能 | 高（顺序写） | 中等（随机写） |
| 读取性能 | 较低（需合并） | 高 |
| 空间放大 | 较高 | 较低 |
| 写入放大 | 较高 | 较低 |
| 典型引擎 | RocksDB、LevelDB | InnoDB、MyISAM |

LSM-Tree 通过将随机写入转化为顺序写入（MemTable 写日志 + 后台 Compaction）获得高写入性能，但读取需要合并多层 SSTable。

### Q4: 存储引擎和索引结构的关系？

存储引擎决定了数据的物理组织方式，索引结构是引擎内部的数据结构：

1. InnoDB 引擎使用 B+Tree 作为索引结构（聚簇索引 + 普通索引）
2. MyISAM 引擎使用 B+Tree 作为索引结构（非聚簇索引）
3. Memory 引擎使用哈希索引
4. RocksDB 使用 LSM-Tree（MemTable + SSTable）

## 九、总结

数据库存储引擎是数据库系统的核心，决定了数据的组织方式、事务能力、并发性能和适用场景。

**MySQL 引擎选择**：
- InnoDB：在线业务首选，完整事务支持
- MyISAM：历史场景，已逐步淘汰
- Memory：临时缓存，追求极致性能

**专用存储引擎**：
- ClickHouse：OLAP 分析场景
- RocksDB/LevelDB：嵌入式 KV 存储
- InfluxDB：时序数据
- Elasticsearch：全文检索和文档存储

选择存储引擎时，需要综合考虑事务需求、并发能力、数据规模、查询模式和运维成本等因素。
