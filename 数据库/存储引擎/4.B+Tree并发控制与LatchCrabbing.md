# 4. B+Tree 并发控制与 Latch Crabbing

## 1. 问题背景

B+Tree 是数据库索引最常见的底层结构之一。单线程场景下，查找、插入、删除只需要保证树结构满足有序、平衡和节点容量约束；但在数据库系统里，同一棵 B+Tree 会被大量线程并发访问，如果没有并发控制，就可能出现读到半更新结构、节点分裂丢失、父子指针不一致、删除合并冲突等问题。

这里要区分两个容易混淆的概念：

1. **Lock**：事务锁，保护逻辑数据，例如行锁、间隙锁、Next-Key Lock，用来实现事务隔离，可能持有到事务提交。
2. **Latch**：闩锁，保护内存中的物理结构，例如页、节点、buffer frame、根指针，临界区很短，一般不参与事务隔离语义。

`latch crabbing` 也叫 `latch coupling` 或锁耦合，是 B+Tree 并发控制中的经典做法。它的核心思想是：从根节点向叶子节点下降时，先持有父节点 latch，确定子节点后再持有子节点 latch，只有在确认子节点对当前操作是安全的情况下，才释放父节点或更早的祖先节点 latch。这个过程像螃蟹走路一样一只脚站稳后再移动另一只脚，因此称为 crabbing。

**假设条件**：

1. 本文讨论的是数据库存储引擎内部的 B+Tree 页级 latch，不是 SQL 层的行锁、表锁或事务隔离锁。
2. B+Tree 节点按页管理，内部节点保存分隔 key 和 child page id，叶子节点保存 key-value 或 key-record id。
3. 每个页支持读写 latch，例如 shared latch 和 exclusive latch。
4. 插入可能触发节点分裂，删除可能触发借位或合并，根节点也可能变化。
5. 如果真实系统使用 B-link Tree、Bw-Tree、Copy-on-Write 或 MVCC 索引，具体实现会不同，但问题本质仍是保护索引结构修改。

## 2. 问题现象

如果 B+Tree 并发控制设计不合理，常见现象包括：

1. **全局锁性能差**：用一把全局 latch 保护整棵树，实现简单但所有查找、插入、删除都串行化，高并发下吞吐很低。
2. **读到不一致结构**：线程 A 正在分裂节点，线程 B 同时查找，可能看到父节点尚未更新、叶子节点已经分裂的中间状态。
3. **节点分裂丢失**：两个线程同时向同一个满叶子插入，如果没有互斥保护，可能覆盖彼此的插入结果或破坏 sibling 指针。
4. **父子关系不一致**：子节点分裂后需要把分隔 key 插入父节点，如果父节点没有被正确保护，父节点可能缺少新子节点入口。
5. **删除合并冲突**：一个线程正在合并叶子节点，另一个线程仍然通过旧父指针访问被删除或复用的页。
6. **死锁**：线程持有子节点再等待父节点，另一个线程持有父节点再等待子节点，锁顺序不一致会互相等待。
7. **根节点竞争严重**：所有操作都从 root 开始，如果 root latch 持有时间过长，会成为索引并发瓶颈。

一个典型错误流程如下：

```text
线程 T1：持有叶子节点 L，发现 L 满了，准备向父节点 P 插入分隔 key
线程 T2：持有父节点 P，准备下降到叶子节点 L

如果 T1 先拿 L 再等 P，T2 先拿 P 再等 L，就可能死锁。
```

Latch crabbing 的目的就是用固定的自顶向下 latch 顺序，兼顾结构安全和并发性能。

## 3. 影响范围

B+Tree latch crabbing 会影响存储引擎的多个核心模块：

1. **Index Manager**：索引查找、插入、删除、范围扫描都要遵守统一的 latch 协议。
2. **B+Tree Page**：内部页、叶子页需要提供容量判断、分裂、合并、借位、父子指针维护等能力。
3. **Buffer Pool**：页从磁盘加载到内存后，需要 pin 住页面并持有 latch，防止并发驱逐或修改。
4. **Page Guard / RAII Guard**：负责自动释放 latch 和 unpin，避免异常返回时 latch 泄漏。
5. **Root Page 管理**：根节点分裂、根节点收缩、root page id 更新需要额外保护。
6. **Iterator / Range Scan**：叶子节点链表遍历涉及 sibling latch，容易和删除合并发生冲突。
7. **WAL 与恢复**：结构修改操作需要与日志顺序配合，避免崩溃后索引结构无法恢复。

如果涉及代码实现，可能需要修改的模块包括：

1. `BPlusTree`：统一封装 `FindLeafPage`、`Insert`、`Remove`、`GetValue` 等操作的 latch 策略。
2. `BPlusTreeInternalPage` / `BPlusTreeLeafPage`：提供 `IsFull`、`CanBorrow`、`CanMerge`、`GetMinSize`、`GetMaxSize` 等判断。
3. `BufferPoolManager`：提供安全的 `FetchPage`、`UnpinPage`、dirty 标记和页生命周期管理。
4. `PageGuard` / `ReadPageGuard` / `WritePageGuard`：用 RAII 管理 latch 和 pin。
5. `IndexIterator`：处理叶子页向右扫描时的 sibling latch 顺序。
6. `Transaction` 或 `Context`：保存当前操作持有的 page guard 栈，便于在节点安全时批量释放祖先 latch。

## 4. 原因分析

B+Tree 并发控制的核心难点在于：普通查找只读树结构，而插入和删除可能触发 **结构修改操作**，也就是 SMO，Structural Modification Operation。

常见 SMO 包括：

1. 叶子节点分裂。
2. 内部节点分裂。
3. 新 root 创建。
4. 删除后的 sibling 借位。
5. 删除后的节点合并。
6. 根节点收缩。

这些操作不只修改一个节点，往往会向父节点甚至祖先节点传播。例如插入时叶子节点满了，需要分裂叶子，并把分隔 key 插入父节点；如果父节点也满了，又要继续向上分裂。因此，线程下降到子节点时，不能总是立刻释放父节点，必须判断子节点是否对当前操作是安全的。

所谓 **safe node**，含义取决于当前操作：

| 操作 | 子节点什么时候安全 | 为什么可以释放祖先 latch |
| --- | --- | --- |
| 查找 | 子节点已经被 latch 住 | 查找不会改变树结构 |
| 插入 | 子节点未满 | 插入不会导致该子节点分裂，也就不会向父节点传播 |
| 删除 | 子节点删除后仍不少于最小容量 | 删除不会导致借位、合并，也就不会向父节点传播 |

Latch crabbing 的关键不在于“多拿几把锁”，而在于控制 **什么时候可以释放祖先 latch**。释放太晚会降低并发，释放太早会导致结构修改缺少父节点保护。

从死锁角度看，B+Tree latch crabbing 还要求所有线程按一致顺序获取 latch：

```text
root -> internal page -> leaf page
```

也就是自顶向下。不能在已经持有子节点 latch 后再回头等待父节点 latch，否则很容易和另一个下降中的线程形成环形等待。

## 5. 解决方案

### 5.1 基本 Latch Crabbing 流程

基本流程如下：

```text
1. latch root
2. 在当前节点中查找目标 child
3. latch child
4. 判断 child 对当前操作是否安全
5. 如果 child 安全，释放当前节点以及更早祖先节点
6. 如果 child 不安全，继续持有祖先 latch
7. 移动到 child，重复直到叶子节点
```

伪代码示例：

```cpp
PageGuard FindLeafPage(const Key &key, Operation op) {
  std::vector<PageGuard> ancestors;
  PageGuard guard = FetchRootWithLatch(op);
  ancestors.push_back(std::move(guard));

  while (!ancestors.back().Page()->IsLeaf()) {
    Page *parent = ancestors.back().Page();
    page_id_t child_id = parent->LookupChild(key);

    PageGuard child = FetchChildWithLatch(child_id, op);

    if (IsSafe(child.Page(), op)) {
      ReleaseAllExcept(ancestors, child);
    }

    ancestors.push_back(std::move(child));
  }

  return std::move(ancestors.back());
}
```

真实实现中不能直接照搬这段代码，因为 `PageGuard` 的 move、release、unpin 和 dirty 标记需要非常严格，但核心逻辑就是：先拿 child，再判断是否释放 parent。

### 5.2 查找流程

查找不会修改 B+Tree 结构，因此可以使用读 latch：

```text
1. 对 root 加 read latch
2. 找到 child 后对 child 加 read latch
3. child latch 成功后释放 parent read latch
4. 重复直到 leaf
5. 在 leaf 中二分查找 key
6. 释放 leaf read latch
```

查找场景下，parent 不需要一直持有，因为只要 child 已经被 latch 住，child 就不会在当前线程读取时被并发结构修改破坏。

### 5.3 插入流程

插入可能导致分裂，因此需要写 latch。保守做法是：

```text
1. 从 root 开始加 write latch
2. 下降到 child 前先加 child write latch
3. 如果 child 未满，说明 child 是 safe node，释放所有祖先 write latch
4. 如果 child 已满，继续持有祖先 latch
5. 到 leaf 后执行插入
6. 如果 leaf 分裂，把分隔 key 插入 parent
7. 如果 parent 继续分裂，沿已持有的祖先链向上传播
```

这个做法正确性强，但如果每次插入都从 root 开始持有写 latch，root 和高层内部节点竞争会比较明显。

### 5.4 删除流程

删除可能导致节点低于最小容量，需要借位或合并，因此也需要写 latch。删除时 safe node 的判断与插入相反：

```text
1. child 删除一个 key 后仍然大于等于最小容量，则 child 安全
2. child 删除后可能 underflow，则 child 不安全，需要继续持有 parent
3. 到 leaf 删除后，如果 underflow，需要从 sibling 借位或与 sibling 合并
4. 合并会删除 parent 中的分隔 key，可能继续向上传播
```

删除比插入更容易出错，因为它可能涉及 sibling latch。工程实现中要规定 sibling latch 顺序，例如按 page id 从小到大获取，或者使用 no-wait sibling latch，失败则释放并重试，避免死锁。

### 5.5 Optimistic Latch Crabbing

多数插入不会触发分裂，多数删除不会触发合并。如果所有写操作都从 root 开始持有写 latch，会损失大量并发。常见优化是乐观 latch crabbing：

```text
1. 先像查找一样，用 read latch 从 root 下降到 leaf
2. 到 leaf 后释放 read latch，重新获取 leaf write latch
3. 如果 leaf 对当前操作安全，直接修改 leaf
4. 如果 leaf 不安全，说明可能需要向上分裂或合并，释放 latch
5. 使用保守写 latch crabbing 从 root 重试
```

插入的乐观路径：

```text
read latch 下降 -> leaf write latch -> leaf 未满 -> 插入成功
```

如果 leaf 满：

```text
释放 -> 从 root 开始 pessimistic write crabbing -> 分裂并插入
```

这样可以把常见路径的高层节点写 latch 时间降到很低。

### 5.6 Root Latch 处理

root 是特殊节点，因为 root page id 可能变化：

1. root 分裂时，需要创建新 root，并更新 root page id。
2. root 删除后只剩一个 child 时，可能收缩为 child。
3. 空树第一次插入时，需要创建 root leaf。

因此通常需要额外的 root latch 或 header page latch 来保护 root page id。常见做法是：

```text
1. 读取 root page id 前持有 root/header latch
2. 成功 latch root page 后，可以释放 root/header latch
3. 如果操作可能改变 root page id，需要持有 root/header write latch
```

## 6. 可选方案对比

| 方案 | 优点 | 缺点 | 适用场景 |
| --- | --- | --- | --- |
| 全局 B+Tree latch | 实现最简单，正确性容易保证 | 所有操作串行化，吞吐差 | 教学、小型内存索引、低并发场景 |
| 基础 latch crabbing | 正确性强，避免结构修改冲突 | 写操作高层节点竞争较重 | 实现简单的数据库内核、课程项目 |
| Optimistic latch crabbing | 常见路径并发高，减少 root 写竞争 | 需要重试逻辑，边界更复杂 | 大多数插入不分裂、删除不合并的 OLTP 索引 |
| B-link Tree | 通过 high key 和 right sibling 降低分裂时父节点依赖 | 实现复杂，查找需要处理右跳 | 高并发索引结构 |
| MVCC + page latch | 读写逻辑隔离好，读事务可见性清晰 | 物理结构修改仍需要 latch | 支持事务隔离的成熟数据库 |
| Copy-on-Write B+Tree | 读路径可以更少阻塞，适合快照 | 写放大和空间回收复杂 | LMDB、文件系统、快照型存储 |
| Bw-Tree / Delta Chain | 避免传统 page latch，适合无锁方向 | 实现和调试难度高，GC复杂 | 研究型或高并发内存索引 |

面试中一般重点讲 latch crabbing 和 optimistic latch crabbing，再补充 B-link Tree 是进一步优化方向即可。

## 7. 推荐方案

推荐采用 **乐观 latch crabbing + 保守重试 + RAII PageGuard** 的组合。

核心原则：

1. 查找使用 read latch crabbing，child read latch 成功后释放 parent。
2. 插入优先走乐观路径，只在 leaf 满时退化为保守写 latch crabbing。
3. 删除优先走乐观路径，只在可能 underflow 时退化为保守写 latch crabbing。
4. 所有 latch 获取顺序保持自顶向下。
5. sibling latch 必须有固定顺序或 no-wait 重试策略。
6. root page id 更新必须用单独的 root/header latch 保护。
7. 用 RAII guard 管理 latch 和 page pin，避免提前 return、异常或错误分支导致 latch 泄漏。
8. 事务 lock 和 page latch 分层处理，不能用 page latch 代替行锁或隔离级别。

推荐回答模板：

```text
B+Tree 的 latch crabbing 是一种页级并发控制方法。
线程从 root 向 leaf 下降时，先持有父节点 latch，再获取子节点 latch。
如果子节点对当前操作是安全的，就释放父节点和祖先节点。
查找只需要读 latch；插入要保证子节点不满；删除要保证子节点不会 underflow。
为了提升性能，工程上常用 optimistic crabbing：先用读 latch 下降，只有叶子不安全时才从 root 用写 latch 重试。
它保护的是物理索引结构，不等价于事务行锁。
```

## 8. 实施步骤

### 8.1 定义 Page Latch 与 Guard

需要先给 page frame 提供读写 latch：

```cpp
class Page {
 public:
  void RLatch();
  void RUnlatch();
  void WLatch();
  void WUnlatch();
};
```

然后用 guard 封装生命周期：

```cpp
class WritePageGuard {
 public:
  WritePageGuard(BufferPoolManager *bpm, page_id_t page_id);
  WritePageGuard(WritePageGuard &&other) noexcept;
  ~WritePageGuard();

  Page *GetPage();
  void Drop();

 private:
  BufferPoolManager *bpm_;
  Page *page_;
  bool is_dirty_;
};
```

Guard 的职责是：

1. 构造时 pin page 并获取 latch。
2. 析构时释放 latch 并 unpin。
3. 支持 move，禁止 copy。
4. 显式 `Drop()` 后不能二次释放。

### 8.2 实现 Safe Node 判断

建议把判断独立成函数：

```cpp
enum class Operation { Search, Insert, Delete };

bool IsSafe(const BPlusTreePage *page, Operation op) {
  if (op == Operation::Search) {
    return true;
  }
  if (op == Operation::Insert) {
    return page->GetSize() < page->GetMaxSize();
  }
  if (op == Operation::Delete) {
    return page->GetSize() > page->GetMinSize();
  }
  return false;
}
```

注意删除场景是否使用 `>` 还是 `>=` 要结合实现定义。如果删除前 `size > min_size`，删除一个 key 后仍然不低于下限；如果删除后再判断，则条件不同。

### 8.3 实现 FindLeafPage

`FindLeafPage` 应该支持不同操作模式：

```text
Search：read latch crabbing
Insert optimistic：read latch 到 leaf，再尝试 leaf write
Insert pessimistic：write latch crabbing
Delete optimistic：read latch 到 leaf，再尝试 leaf write
Delete pessimistic：write latch crabbing
```

上下文对象可以保存当前持有的 ancestors：

```cpp
struct BPlusTreeContext {
  std::vector<WritePageGuard> write_set_;
  std::vector<ReadPageGuard> read_set_;
  page_id_t root_page_id_;
};
```

当 child safe 时：

```cpp
void ReleaseAncestors(BPlusTreeContext *ctx) {
  for (auto &guard : ctx->write_set_) {
    guard.Drop();
  }
  ctx->write_set_.clear();
}
```

真实代码要注意不要释放当前 child guard。

### 8.4 插入实现

插入建议分两阶段：

1. 先走 optimistic insert。
2. 如果 leaf 满，则释放所有 latch，从 root 开始 pessimistic insert。

核心逻辑：

```text
Insert(key, value):
  leaf = FindLeafOptimistic(key)
  if leaf has space:
    insert into leaf
    return

  release leaf
  leaf = FindLeafPessimistic(key)
  insert into leaf
  if leaf overflow:
    split leaf
    insert separator into parent
    while parent overflow:
      split parent
  if root overflow:
    create new root
```

### 8.5 删除实现

删除也可以先乐观再保守：

```text
Remove(key):
  leaf = FindLeafOptimistic(key)
  if key not exists:
    return false
  if leaf size > min_size:
    remove key
    return true

  release leaf
  leaf = FindLeafPessimistic(key)
  remove key
  if leaf underflow:
    borrow from sibling or merge
    update parent separator
    if parent underflow:
      propagate upward
```

删除测试要覆盖借左兄弟、借右兄弟、向左合并、向右合并、根节点收缩。

### 8.6 处理范围扫描

范围扫描通常需要沿叶子链表向右移动。为避免和删除合并死锁，建议：

1. 当前叶子读 latch 下读取 next page id。
2. 获取 next leaf read latch。
3. 成功后释放当前 leaf。
4. 如果需要写 sibling，按 page id 顺序或 no-wait 获取。

不要在持有多个叶子写 latch 时再回头获取父节点 latch。

### 8.7 测试重点

如果涉及代码实现，测试重点包括：

1. **查找并发测试**：多个线程并发读取同一索引，结果稳定。
2. **插入分裂测试**：并发插入递增 key、随机 key，验证没有丢 key。
3. **删除合并测试**：并发删除触发 borrow、merge、root shrink。
4. **混合读写测试**：读、插入、删除同时运行，检查树结构不损坏。
5. **死锁测试**：设置超时检测，压力测试中不应出现线程永久阻塞。
6. **Latch 泄漏测试**：每次操作结束后 page pin count 和 latch 状态应归零。
7. **结构不变量测试**：所有叶子同层、key 有序、节点容量合法、父子指针一致、叶子链表完整。
8. **TSAN/并发检测**：检查 data race。

## 9. 风险与注意事项

1. **不要把 latch 当成事务锁**  
   Latch 只保护物理结构，不保证可重复读、幻读控制或事务回滚。

2. **不要在持有 latch 时执行慢操作**  
   持有 page latch 时应避免磁盘慢 IO、RPC、用户回调、复杂日志打印和长时间计算。

3. **避免 latch upgrade 死锁**  
   多个线程同时持有 read latch 后尝试升级 write latch，容易互相等待。更稳妥的做法是释放后按写路径重试。

4. **child latch 成功前不能释放 parent**  
   否则 parent 指向的 child 可能被并发合并、删除或结构调整。

5. **unsafe child 不能提前释放祖先**  
   插入时 child 满、删除时 child 可能 underflow，都说明结构变化可能向上传播。

6. **sibling latch 要有固定顺序**  
   删除借位、合并和范围扫描都可能访问 sibling，必须避免左右互相等待。

7. **root page id 需要单独保护**  
   根分裂和根收缩会改变入口页，不能只保护旧 root page。

8. **RAII guard 必须正确 move**  
   Guard 被移动后，原对象不能在析构时再次释放 latch 或 unpin page。

9. **WAL 顺序不能忽略**  
   如果存储引擎支持崩溃恢复，页结构修改前后要正确写日志，保证 redo/undo 能恢复一致结构。

10. **乐观路径必须能重试**  
   发现 leaf 不安全后，不要试图在原路径上临时补锁祖先，因为祖先已经释放，应释放当前 latch 后从 root 重试。

## 10. 验证方式

验证 B+Tree latch crabbing 不能只看单线程功能测试，需要同时验证正确性、并发性和性能。

### 10.1 正确性验证

1. 插入大量随机 key 后，全量扫描应严格有序。
2. 删除部分 key 后，被删除 key 查不到，未删除 key 都能查到。
3. 每个内部节点的分隔 key 与 child key range 一致。
4. 每个节点 size 满足 B+Tree 最小和最大容量约束。
5. 所有叶子节点位于同一层。
6. 叶子链表从左到右完整且有序。

### 10.2 并发验证

1. 多线程只读查询，结果一致且无 data race。
2. 多线程插入不重复 key，最终 key 数量等于插入成功数量。
3. 多线程插入重复 key，唯一约束结果稳定。
4. 多线程删除和查询交错，不出现崩溃、死锁或非法页访问。
5. 多线程插入、删除、扫描混合运行，最终与单线程 reference map 对比一致。

### 10.3 死锁与资源验证

1. 压测中所有线程能在超时时间内结束。
2. 操作结束后没有 page pin 泄漏。
3. 操作结束后没有 latch 未释放。
4. 使用 TSAN 或类似工具检查 data race。
5. 对异常分支、提前返回、重复 key、key 不存在等路径做覆盖。

### 10.4 性能验证

可以对比以下方案：

1. 全局 tree latch。
2. 基础 pessimistic latch crabbing。
3. optimistic latch crabbing。

观察指标包括：

1. QPS/吞吐。
2. P95/P99 延迟。
3. root latch 等待时间。
4. 页 latch 冲突次数。
5. 乐观路径重试比例。
6. split/merge 次数。

如果 optimistic crabbing 的重试比例很高，说明节点分裂或合并频繁，可能需要调整页大小、填充因子、批量写入策略或删除合并策略。

## 11. 总结

B+Tree 的 latch crabbing 是数据库存储引擎中保护索引物理结构的一种并发控制协议。它的核心是 **自顶向下获取 latch，先拿 child，再根据 child 是否 safe 决定是否释放 parent 和 ancestors**。

面试回答时可以抓住四点：

1. Latch 是短期物理结构保护，Lock 是事务逻辑隔离，二者不能混淆。
2. 查找用 read latch crabbing；插入和删除用 write latch crabbing。
3. safe node 是释放祖先 latch 的判断依据：插入看是否未满，删除看是否不会 underflow。
4. 工程上常用 optimistic crabbing 提升并发：先用读路径到叶子，只有叶子不安全时才从 root 走保守写路径重试。

一个完整的工程实现还需要处理 root page id、sibling latch、PageGuard、buffer pool pin、WAL 顺序、死锁规避和并发测试。Latch crabbing 不是为了让 B+Tree 完全无锁，而是在保证结构正确性的前提下，尽量缩短高层节点 latch 的持有时间，从而提升索引在高并发读写场景下的吞吐。
