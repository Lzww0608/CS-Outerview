# 2. 高并发 KV 写缓冲与顺序刷盘

高并发 KV 存储里，如果每次 `insert(key, value)` 都随机写底层介质，会产生大量小随机写、锁竞争和刷盘抖动。常见思路是借鉴 LSM-Tree：前台把随机插入写入内存或非易失性内存中的写缓冲，后台把缓冲冻结后批量顺序刷写。

## 1. 核心目标

1. `insert` 线程安全。
2. 不使用全局大锁阻塞所有写入。
3. 随机 key 插入转成批量顺序写。
4. `flush` 能一次性顺序写出稳定快照。
5. 崩溃后能根据 WAL 或 NVM 持久数据恢复。

## 2. 基本架构

```text
insert
-> per-thread buffer / sharded memtable
-> WAL 或 NVM append log
-> active memtable
-> immutable memtable
-> flush 成有序文件或顺序段
-> 后台 compaction
```

如果底层是非易失性内存（NVM/PMem），可以把写缓冲或 WAL 放在 NVM 上，利用 cache line flush 指令保证持久化；但仍要避免大量随机持久化写直接打散介质访问和 CPU cache。

## 3. insert 如何避免全局锁

常见方案是分片或线程本地化：

1. **按 key hash 分片**：`shard = hash(key) % N`，每个 shard 有自己的 MemTable、锁、WAL offset 和内存配额。
2. **线程本地缓冲**：每个写线程先写本地 buffer，达到阈值后发布到 shard 队列。
3. **原子追加 offset**：WAL 或 NVM log 使用 `fetch_add(len)` 申请连续写入空间，避免全局 mutex。
4. **细粒度锁或无锁队列**：每个 shard 内部用轻量锁、读写锁、跳表 latch 或 MPSC 队列，而不是所有写入共用一把锁。
5. **批量提交**：多个 insert 合并成一个 batch，减少持久化屏障和系统调用次数。

示意：

```cpp
struct Record {
    uint64_t seq;
    std::string key;
    std::string value;
};

class Shard {
public:
    void insert(Record r) {
        uint64_t offset = log_offset.fetch_add(encodedSize(r), std::memory_order_relaxed);
        appendLog(offset, r);      // 顺序写 WAL/NVM log
        persistLog(offset, r);     // NVM 场景执行 clwb/sfence 或封装库持久化

        std::lock_guard<std::mutex> lk(mu);
        memtable.insert(std::move(r));
    }

private:
    std::atomic<uint64_t> log_offset{0};
    std::mutex mu;
    MemTable memtable;
};
```

这里没有全局锁，但单个 shard 内仍可用小锁保护内部结构。面试里“不使用全局锁”不等于完全无锁，重点是把竞争拆散，并让热点只影响局部分片。

## 4. flush 如何高效顺序刷写

`flush` 不能一边遍历 active MemTable，一边让写线程继续修改它。通常采用“切换 active + 冻结 immutable”的方式：

```text
1. 对某个 shard 短暂加锁或 CAS 切换 active memtable
2. 旧 active 变成 immutable memtable
3. 新 insert 写入新的 active memtable
4. 后台 flush 线程遍历 immutable，按 key 顺序写出 SSTable 或顺序段
5. flush 成功后记录 manifest/checkpoint，再释放 immutable
```

好处：

1. 前台写入只在切换瞬间短暂受影响。
2. flush 看到的是稳定快照，不需要和 insert 互相抢同一份结构。
3. MemTable 内部如果有序，例如跳表、红黑树、排序数组，flush 可以顺序遍历写出。
4. 多个 shard 的 immutable 可以并行 flush，也可以归并成全局有序文件。

如果 MemTable 是无序哈希表，flush 前需要排序，会增加 CPU 和内存成本。写多读少 KV 通常选择跳表、SkipList、B-Tree like memtable 或者先写无序 buffer、阈值后排序成 run。

## 5. NVM 场景注意事项

非易失性内存不是“普通内存断电不丢”这么简单，还要处理持久化顺序和崩溃一致性：

1. **cache line flush**：CPU cache 中的数据不一定已经持久化，需要 `clwb/clflushopt` 加 `sfence`，或使用 PMDK 等库。
2. **写入顺序**：先写 record 内容，再写 commit 标记；恢复时只重放完整提交的 record。
3. **原子粒度**：不能假设任意长度写入都是原子的，元数据要用校验和、长度、版本和 commit bit。
4. **磨损和写放大**：仍要批量、顺序、合并，避免小随机持久化写。
5. **恢复流程**：启动时扫描 WAL/NVM log，校验 record，重建 MemTable 或已 flush 文件索引。

一个 record 可以设计为：

```text
magic | length | seq | key_len | value_len | key | value | crc | committed
```

恢复时遇到未提交、CRC 错误或长度非法的尾部记录就停止或截断。

## 6. 并发一致性

需要明确读写视图：

1. 每次 insert 分配全局或分片内单调递增 `seq`。
2. 读请求读取 active、immutable 和已 flush 文件时，按最大 `seq` 的记录为准。
3. flush 文件写完后先落数据，再原子更新 manifest，避免崩溃后引用半文件。
4. 删除操作写 tombstone，不能只从 MemTable 删除，否则旧 SSTable 中的值会复活。
5. 多 shard flush 要记录每个 shard 的 checkpoint，恢复时按 checkpoint 之后的 log 重放。

## 7. 易错点

1. 只加一个全局 mutex 虽然简单，但高并发下会把所有 insert 串行化。
2. active MemTable 直接 flush 会和 insert 并发修改冲突，必须冻结快照。
3. 只写 NVM 内存不代表持久化完成，CPU cache 里的脏数据可能还没刷出。
4. batch 太大降低写放大，但会增加单次延迟和恢复时间。
5. 顺序写提升写入吞吐，但读路径会有多层查找和 compaction 成本。

## 8. 面试回答模板

我会把随机 insert 转成 LSM 风格的写路径：前台先追加 WAL 或 NVM log，再写 active MemTable；MemTable 满了以后短暂切换 active，旧表冻结成 immutable，后台按 key 顺序 flush 成 SSTable 或顺序段。并发上不使用全局锁，而是按 key hash 分片，每个 shard 有独立写缓冲、锁和 log offset，或者用线程本地 buffer 加 MPSC 队列批量发布。NVM 场景要注意 cache line flush、sfence、commit 标记、CRC 和恢复扫描，不能以为写了内存就一定持久。这个设计牺牲了一部分读放大和 compaction 成本，换来高并发写入和顺序刷盘吞吐。
