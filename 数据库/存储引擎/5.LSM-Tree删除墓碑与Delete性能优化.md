# 5. LSM-Tree 删除墓碑与 Delete 性能优化

## 1. 问题背景

LSM-Tree 的核心思路是把随机写转成顺序写：写入先追加 WAL，再写入 MemTable；MemTable 满后变成 Immutable MemTable，并 flush 成有序 SSTable；后台 compaction 再把多个 SSTable 归并到更低层级。

在这种结构下，`delete(key)` 通常不会立刻去所有 SSTable 中找到并删除旧值，而是写入一条特殊记录：**删除标记**，也就是 tombstone，中文常称为墓碑。

```text
Put(k, v1) -> 写入新版本
Delete(k)  -> 写入 tombstone，表示在该时间点之后 k 不存在
```

墓碑存在的原因是：LSM-Tree 里同一个 key 的旧版本可能分散在 MemTable、L0 SSTable、L1 SSTable、L2 SSTable 等多个位置。如果删除时只从 MemTable 删除，那么更老的 SSTable 中的旧值仍然存在，后续查询或 compaction 时可能“复活”旧数据。

**假设条件**：

1. 本文讨论的是通用 LSM-Tree 存储引擎，例如 LevelDB、RocksDB、HBase、Cassandra 类系统的设计思想。
2. `delete` 采用 tombstone 语义，不立即原地修改旧 SSTable。
3. 系统可能存在 snapshot、事务读、时间戳版本、备份、复制、CDC 或二级索引，因此墓碑不能随意提前删除。
4. 文中的 `compaction` 泛指后台 SSTable 归并，不限定 leveled、tiered、universal 或 size-tiered 策略。
5. 真实系统的 tombstone 清理条件会受具体版本可见性、保留策略和一致性协议影响。

## 2. 问题现象

大量 delete 或 tombstone 清理不及时，会带来一系列性能和存储问题：

1. **读放大增加**：查询一个已经删除的 key，可能需要查 MemTable、L0 多个文件、低层 SSTable，最后才确认墓碑覆盖旧值。
2. **空间放大增加**：墓碑本身占空间，被墓碑覆盖的旧 value 在 compaction 前也仍然占空间。
3. **写放大增加**：tombstone 会随着 compaction 被反复读取、写入、下推，直到满足清理条件。
4. **Compaction 压力变大**：大量 tombstone 会触发更多文件重写，后台 IO 和 CPU 抖动明显。
5. **尾延迟升高**：compaction 抢占磁盘带宽和 CPU，前台读写 P99 延迟变差。
6. **缓存污染**：频繁查询已删除 key 可能把 tombstone、索引块、filter block 加载进 block cache。
7. **范围扫描变慢**：扫描时需要跳过大量 tombstone 和旧版本，iterator 需要做更多归并判断。
8. **磁盘空间迟迟不降**：业务删除了大量数据，但底层 SSTable 没有完成最终 compaction，磁盘占用不立即下降。

一个典型场景：

```text
业务每天删除 1 亿条过期订单索引。
前台 delete 写入很快，但底层只是写 tombstone。
如果 compaction 跟不上，旧 value 和 tombstone 同时存在。
结果是磁盘空间不降，查询已删除订单仍然要扫描多层文件，后台 compaction 持续打满 IO。
```

## 3. 影响范围

LSM-Tree delete 和 tombstone 会影响以下模块：

1. **Write Path**：delete 会写 WAL、MemTable 和 sequence number，本质上是一种写入。
2. **Read Path**：读路径必须识别 tombstone，并判断它是否覆盖旧版本。
3. **Iterator**：点查和范围扫描都要合并多层版本，并跳过被删除的数据。
4. **Compaction Picker**：需要选择哪些文件参与合并，尽快消除 tombstone 覆盖的旧数据。
5. **Version/Snapshot Manager**：决定最老活跃快照之前的数据和墓碑能否清理。
6. **Manifest/元数据管理**：compaction 输出新文件后要原子切换版本。
7. **Block Cache 和 Bloom Filter**：delete-heavy workload 会改变缓存命中率和过滤器效果。
8. **监控告警**：需要暴露 tombstone 数量、compaction backlog、空间放大、读放大等指标。
9. **业务 TTL/归档策略**：过期删除、批量删除和冷热分层会直接影响 tombstone 规模。

如果涉及代码实现，可能需要修改的模块包括：

1. `DBImpl::Delete` / `WriteBatch`：将 delete 编码为 tombstone entry。
2. `MemTable`：支持同一个 key 的 put/delete 多版本记录。
3. `InternalKeyComparator`：按 user key、sequence number、value type 排序。
4. `MergingIterator`：读取时处理 tombstone 覆盖关系。
5. `CompactionJob`：在 compaction 中丢弃旧 value 和满足条件的 tombstone。
6. `SnapshotList` / `VersionSet`：提供最老可见 sequence number。
7. `CompactionPicker`：识别 tombstone 密集文件，触发 targeted compaction。
8. `Metrics`：记录 tombstone count、drop count、pending compaction bytes、read amplification。

## 4. 原因分析

### 4.1 为什么不能立刻物理删除

LSM-Tree 的 SSTable 是不可变文件。不可变带来几个好处：

1. 写入可以顺序追加和批量 flush。
2. 文件元数据切换简单，便于崩溃恢复。
3. 读路径可以并发读取旧文件，不需要原地更新锁。
4. compaction 可以生成新文件后再原子替换旧文件。

但代价是：旧值不能被原地删除。删除一个 key 时，只能写入一个更高 sequence number 的 tombstone，表示旧版本被覆盖。

### 4.2 什么时候能删除墓碑

墓碑能被删除，通常要同时满足几个条件：

1. **墓碑已经被 compact 到足够低的层级**  
   它覆盖范围内的旧版本都已经和墓碑相遇，或者可以证明更低层没有这个 key 的旧版本。

2. **不存在比墓碑更老、仍可能读取旧版本的快照**  
   如果某个 snapshot 创建在 tombstone 之前，它可能仍然需要读到旧 value。此时不能删除旧 value，也不能删除用于遮蔽旧 value 的 tombstone。

3. **没有保留历史版本的需求**  
   如果系统支持时间旅行查询、审计、备份增量、CDC 或多版本保留，墓碑要等保留窗口结束才能删除。

4. **tombstone 覆盖的 key range 已经确认没有更低层旧值**  
   对 leveled compaction 来说，如果墓碑所在层和下一层重叠文件已参与 compaction，且没有更低层可能包含旧值，墓碑才可以安全丢弃。

5. **复制和恢复语义允许清理**  
   如果下游副本、增量备份或变更订阅还需要看到 delete 事件，墓碑不能过早清理。

简化判断可以表达为：

```text
Tombstone 可以删除 =
  它覆盖的旧版本已经全部被清理
  且没有任何活跃 snapshot 需要旧版本
  且没有历史保留/复制/审计需求依赖它
```

### 4.3 大量 Delete 为什么会拖垮性能

大量 delete 的本质是大量写入 tombstone。它不会立即释放空间，反而会先增加写入量和数据版本数。

影响路径如下：

```text
大量 Delete
-> WAL 和 MemTable 写入增加
-> Flush 产生带 tombstone 的 SSTable
-> 查询需要识别 tombstone 和旧版本
-> Compaction 要反复归并 tombstone 与旧 value
-> IO/CPU/缓存资源被消耗
-> 前台读写延迟升高
```

如果 delete key 分布很随机，墓碑会散落到大量 SSTable 和 key range 中，compaction 很难一次性清掉所有旧版本；如果 delete 集中在某些 key range，局部文件会产生 tombstone storm，范围扫描和 compaction 会明显变慢。

## 5. 解决方案

### 5.1 正确的 Delete 语义

delete 必须写入 tombstone，而不是只删除 MemTable 中的记录：

```cpp
Status Delete(const WriteOptions &options, const Slice &key) {
  WriteBatch batch;
  batch.Delete(key);
  return Write(options, &batch);
}
```

内部记录通常会编码成：

```text
InternalKey = user_key + sequence_number + value_type
value_type = kTypeDeletion
```

读路径遇到同一个 user key 的最新记录是 tombstone 时，应返回 not found：

```text
key@seq=105, type=delete
key@seq=100, type=value, value=v1

对于 seq >= 105 的读：返回 NotFound
对于 snapshot seq = 102 的读：仍可能返回 v1
```

### 5.2 Compaction 中清理旧版本和墓碑

Compaction 是 tombstone 真正发挥作用和被清理的地方。合并多个 SSTable 时，对于同一个 user key：

1. 保留对当前可见读有意义的最新版本。
2. 删除被更新覆盖的旧版本。
3. 如果 tombstone 覆盖了旧 value，丢弃旧 value。
4. 如果可以证明 tombstone 不再需要遮蔽任何旧 value，也丢弃 tombstone。

伪代码：

```cpp
for (auto entry : merge_iterator) {
  if (entry.user_key != last_user_key) {
    ResetKeyState(entry.user_key);
  }

  if (entry.seq > oldest_snapshot_seq) {
    Keep(entry);
    continue;
  }

  if (entry.type == kTypeDeletion) {
    if (DefinitelyNoOlderVersionInLowerLevels(entry.user_key) &&
        NoSnapshotNeedsOlderVersion(entry.seq)) {
      DropTombstone(entry);
    } else {
      KeepTombstone(entry);
    }
    MarkOlderVersionsDeleted(entry.user_key);
    continue;
  }

  if (IsCoveredByNewerTombstone(entry.user_key, entry.seq)) {
    DropOldValue(entry);
  } else {
    Keep(entry);
  }
}
```

这段逻辑的核心不是代码形式，而是两个判断：

```text
旧 value 是否已经被墓碑覆盖？
墓碑是否还需要继续遮蔽更低层旧 value？
```

### 5.3 Tombstone-aware Compaction

如果删除很多，不能只靠普通 size-based compaction，需要让 compaction 感知墓碑密度：

1. 统计每个 SSTable 的 tombstone 数量和比例。
2. 统计 tombstone 覆盖的 key range。
3. 对墓碑密集文件触发 targeted compaction。
4. 优先 compact 能释放最多空间或降低最多读放大的文件。
5. 对范围删除使用范围墓碑，避免逐 key tombstone 爆炸。

例如：

```text
文件 F1：100 MB，tombstone 占 60%，与 L2 的 3 个文件重叠
策略：优先 compact F1 和重叠文件，尽快清理旧版本和墓碑
```

### 5.4 Range Tombstone

如果业务经常删除连续 key range，例如删除某个用户、租户、日期分区下的数据，逐个 key 写 tombstone 会非常昂贵。可以使用范围墓碑：

```text
DeleteRange([user:1000:order:0000, user:1000:order:9999])
```

范围墓碑的优点：

1. 减少写入条数。
2. 降低 WAL、MemTable、SSTable 中 tombstone 数量。
3. 对批量过期删除更友好。

风险是：

1. 读路径要判断 key 是否被 range tombstone 覆盖。
2. Compaction 要正确切分和传播 range tombstone。
3. 范围过大时可能误伤后续新写入，需要结合 sequence number 判断。
4. Iterator 和 snapshot 语义更复杂。

### 5.5 TTL 和按时间分区

如果删除主要来自过期数据，最好不要把所有过期都转成随机 delete。更推荐：

1. key 设计中带时间维度。
2. 按时间分区、按租户分区或按业务域分区。
3. 过期时直接丢弃整个文件、分区、column family 或 key range。
4. 对冷数据先归档，再删除主存储。

例如时序数据：

```text
metric:{day}:{tenant}:{series_id}:{timestamp}
```

如果按天生成 SSTable 或分区，过期时可以删除整天数据文件，而不是写入海量单 key tombstone。

### 5.6 Delete 节流与后台治理

大量 delete 本身也是写流量，应该限速和削峰：

1. 批量删除分批执行，避免一次性打爆 WAL 和 MemTable。
2. 对 delete-heavy 任务设置后台低优先级。
3. 使用 rate limiter 控制 delete 写入速率。
4. 对 compaction backlog 设置告警和自动扩容。
5. 前台读写和后台 compaction 资源隔离。
6. 在业务低峰期执行大规模清理任务。

### 5.7 使用业务级替代方案

有些场景不适合用单 key delete：

1. **逻辑删除**：先标记状态，异步物理清理。
2. **版本切换**：新数据写到新 namespace，旧 namespace 整体下线。
3. **整库重建**：大规模删除后，重建 compacted 数据集再切流。
4. **冷热分层**：旧数据迁移到低成本存储，主库只保留热数据。
5. **Column Family 隔离**：不同生命周期的数据放到不同 CF，便于独立 compaction 和 drop。

## 6. 可选方案对比

| 方案 | 优点 | 缺点 | 适用场景 |
| --- | --- | --- | --- |
| 单 key tombstone | 语义简单，点删准确，兼容普通读写 | 大量删除时 tombstone 爆炸，读写放大明显 | 少量随机删除 |
| Range tombstone | 批量删除成本低，适合连续 key range | 读路径和 compaction 更复杂 | 按租户、时间、前缀删除 |
| Tombstone-aware compaction | 能主动清理旧值和墓碑，降低空间放大 | 消耗后台 IO，策略调参复杂 | 删除后空间迟迟不降 |
| TTL compaction filter | 自动过期清理，业务侵入小 | 依赖时间判断，snapshot/备份语义要小心 | 缓存、时序、日志数据 |
| 分区/drop partition | 删除最快，几乎不产生 tombstone | 需要提前设计 key 和数据布局 | 时间分区、租户隔离 |
| 逻辑删除 + 异步清理 | 前台稳定，便于恢复和审计 | 存储占用持续更久，查询要过滤状态 | 订单、账号、审批类业务 |
| 重建数据集后切流 | 清理彻底，最终数据最干净 | 成本高，需要双写/校验/切流 | 删除比例极高、碎片严重 |

## 7. 推荐方案

推荐按 delete 的规模和模式分层处理：

1. **少量随机删除**：使用普通 tombstone，依赖正常 compaction 清理。
2. **大量连续范围删除**：优先使用 range tombstone 或按分区 drop。
3. **过期数据删除**：优先 TTL、时间分区、冷热分层，不要逐 key delete。
4. **删除后读放大严重**：启用 tombstone-aware compaction，优先 compact 墓碑密集文件。
5. **删除后空间不释放**：检查 snapshot、备份、复制、compaction backlog 是否阻塞墓碑清理。
6. **删除比例极高**：考虑离线重建或迁移到新 column family，再切流。

面试回答可以这样组织：

```text
LSM-Tree 的 delete 不是立即物理删除，而是写 tombstone。
墓碑只有在 compaction 过程中确认旧版本已经被清理，并且没有 snapshot 或历史保留需求依赖旧版本时，才能被删除。
大量 delete 会导致读放大、写放大、空间放大和 compaction 压力上升。
优化上要避免逐 key 删除，能按时间/租户分区就 drop 分区，能范围删除就用 range tombstone；同时用 tombstone-aware compaction、delete 限速、TTL compaction filter 和监控治理。
```

## 8. 实施步骤

### 8.1 定义内部 Key 版本模型

LSM-Tree 通常会把用户 key 转换成内部 key：

```cpp
struct InternalKey {
  std::string user_key;
  uint64_t sequence;
  ValueType type;  // kTypeValue / kTypeDeletion / kTypeRangeDeletion
};
```

排序规则通常是：

```text
user_key 升序
sequence 降序
type 参与同 sequence 下的比较
```

这样读路径可以先看到最新版本或最新墓碑。

### 8.2 写入 Delete

delete 写路径和 put 类似：

```cpp
Status DB::Delete(const WriteOptions &options, const Slice &key) {
  uint64_t seq = versions_->NewSequence();
  WALAppend(DeleteRecord(key, seq));
  memtable_->Add(seq, kTypeDeletion, key, Slice{});
  MaybeScheduleFlushOrCompaction();
  return Status::OK();
}
```

核心修改逻辑：

1. delete 必须分配 sequence number。
2. delete 必须写 WAL，保证崩溃后不会旧值复活。
3. delete 写入 MemTable 后，读路径要能立即看到删除。
4. Flush 后 tombstone 要进入 SSTable。

### 8.3 读取时处理 Tombstone

点查流程：

```text
1. 查 MemTable
2. 查 Immutable MemTable
3. 查 L0 文件
4. 查 L1/L2/... 文件
5. 遇到目标 key 最新可见版本：
   - value：返回 value
   - tombstone：返回 NotFound
```

伪代码：

```cpp
LookupResult Get(const ReadOptions &options, const Slice &key) {
  uint64_t snapshot_seq = ResolveSnapshot(options);

  for (auto source : SearchOrder()) {
    auto entry = source.Lookup(key, snapshot_seq);
    if (!entry.found) {
      continue;
    }
    if (entry.type == kTypeDeletion) {
      return NotFound();
    }
    return Value(entry.value);
  }
  return NotFound();
}
```

### 8.4 Compaction 中 Drop Tombstone

Compaction 需要知道最老活跃快照：

```cpp
uint64_t oldest_snapshot_seq = snapshots_->GetOldestSnapshotSequence();
```

简化清理规则：

```cpp
bool CanDropTombstone(const Entry &tombstone,
                      const CompactionContext &ctx) {
  if (tombstone.sequence > ctx.oldest_snapshot_seq) {
    return false;
  }
  if (ctx.MayExistInLowerLevel(tombstone.user_key)) {
    return false;
  }
  if (ctx.NeedKeepHistory(tombstone.user_key, tombstone.sequence)) {
    return false;
  }
  return true;
}
```

实现重点：

1. `oldest_snapshot_seq` 控制历史读可见性。
2. `MayExistInLowerLevel` 控制墓碑是否还需要遮蔽更低层旧值。
3. `NeedKeepHistory` 控制 TTL、审计、备份、CDC 等保留语义。
4. Drop tombstone 前必须确保旧 value 不会在未来读路径中复活。

### 8.5 增加 Tombstone 监控

建议暴露指标：

```text
num_tombstones
tombstone_ratio_by_level
obsolete_keys_dropped
tombstones_dropped
pending_compaction_bytes
compaction_read_bytes
compaction_write_bytes
read_amplification
write_amplification
space_amplification
oldest_snapshot_age
delete_qps
range_delete_qps
```

没有监控时，很容易把“磁盘不释放”误判成 delete 失败，实际上可能是 snapshot 长时间未释放或 compaction backlog 过大。

### 8.6 针对大量 Delete 做治理

可以按以下步骤治理：

1. 先判断 delete 是随机点删、范围删、TTL 过期还是整批数据下线。
2. 如果是范围删，改成 range tombstone 或 key 前缀分区。
3. 如果是 TTL，改成 TTL compaction filter 或按时间分区 drop。
4. 如果是一次性历史清理，分批限速执行。
5. 如果 compaction 跟不上，提高 compaction 线程、IO 配额或临时扩容。
6. 如果 snapshot 阻塞清理，定位长事务、长 iterator、备份任务和只读查询。
7. 如果删除比例极高，评估重建数据集再切流。

### 8.7 测试重点

如果涉及代码实现，测试重点包括：

1. **删除可见性测试**：delete 后立即 get 返回 NotFound。
2. **旧值不复活测试**：flush、重启、compaction 后旧值不能复活。
3. **Snapshot 测试**：delete 之前创建的 snapshot 仍能按语义读取旧值，delete 之后的读返回 NotFound。
4. **墓碑清理测试**：compaction 后确认旧 value 和可丢弃 tombstone 被删除。
5. **不可清理测试**：有活跃 snapshot 时，tombstone 不能提前删除。
6. **Range tombstone 测试**：范围内 key 被删除，范围外 key 不受影响，新写入版本不被旧 range tombstone 误删。
7. **大量 delete 压测**：观察读放大、写放大、空间放大和 P99 延迟。
8. **崩溃恢复测试**：delete 写 WAL 后崩溃恢复，删除语义仍然成立。

## 9. 风险与注意事项

1. **墓碑不能过早删除**  
   如果更低层还有旧 value，墓碑被提前删除后，旧 value 会在读路径中复活。

2. **长 snapshot 会阻塞清理**  
   长事务、长时间 iterator、备份任务可能让 oldest snapshot 很旧，导致旧 value 和 tombstone 都不能清理。

3. **Delete 不等于释放空间**  
   Delete 只是写 tombstone，空间释放依赖后续 compaction。业务上要避免承诺“删除后磁盘立刻下降”。

4. **大量随机 delete 对 LSM 不友好**  
   随机墓碑会分散到很多 key range，compaction 很难快速清理，读放大和空间放大会明显增加。

5. **Range tombstone 要处理 sequence number**  
   旧 range tombstone 不能覆盖其之后写入的新 value，否则会误删新数据。

6. **Compaction Filter 要谨慎**  
   TTL 或自定义 filter 如果依赖本地时间、外部状态或非确定性逻辑，可能导致副本间结果不一致。

7. **删除风暴会影响前台延迟**  
   大量 delete 造成 flush、compaction、cache miss 和 IO 抖动，需要限速和隔离。

8. **监控要区分逻辑删除和物理清理**  
   逻辑删除成功不代表 tombstone 已清理，也不代表旧 value 已释放空间。

9. **二级索引要同步处理**  
   主表 delete 后，如果二级索引仍保留旧 key，会造成查询脏结果或额外 tombstone。

10. **备份和 CDC 会延长保留时间**  
   下游系统如果依赖 delete 事件或历史版本，墓碑清理策略要和数据链路协同。

## 10. 验证方式

### 10.1 功能验证

1. `put(k, v1) -> delete(k) -> get(k)` 应返回 NotFound。
2. `put(k, v1) -> flush -> delete(k) -> compact -> get(k)` 不应复活旧值。
3. `delete(k) -> put(k, v2)` 后，新版本应可见，旧 tombstone 不应误删新值。
4. 重启恢复后，delete 语义仍然正确。

### 10.2 Snapshot 验证

```text
put(k, v1)
snapshot = create_snapshot()
delete(k)

get(k) with snapshot -> v1
get(k) without snapshot -> NotFound
```

释放 snapshot 并完成 compaction 后，旧 value 和 tombstone 才可能被清理。

### 10.3 Compaction 验证

1. 构造多层 SSTable，让低层存在旧 value，高层存在 tombstone。
2. 执行 compaction，检查旧 value 被丢弃。
3. 如果低层不再有旧 value 且无 snapshot，检查 tombstone 被丢弃。
4. 如果存在活跃 snapshot，检查 tombstone 和旧 value 被保留。

### 10.4 性能验证

压测维度：

1. delete QPS。
2. tombstone ratio。
3. read amplification。
4. write amplification。
5. space amplification。
6. compaction pending bytes。
7. compaction IO 带宽。
8. P95/P99/P999 读写延迟。
9. block cache hit ratio。
10. range scan 吞吐。

建议对比：

1. 普通逐 key delete。
2. range tombstone。
3. TTL compaction filter。
4. 按分区 drop。
5. tombstone-aware compaction。

### 10.5 运维验证

排查磁盘不释放时，按顺序看：

```text
1. 是否真的写入了 tombstone？
2. tombstone 是否已经 flush 到 SSTable？
3. compaction backlog 是否很高？
4. oldest snapshot age 是否过大？
5. 是否有长 iterator、备份、CDC 阻塞清理？
6. tombstone 是否已经 compact 到覆盖旧 value 的层级？
7. 是否有低层文件仍可能包含旧 value？
```

## 11. 总结

LSM-Tree 的 delete 操作不是立即物理删除，而是写入 tombstone。墓碑的作用是遮蔽旧 SSTable 中的旧 value，防止删除后旧数据复活。墓碑真正能被删除，一般要等 compaction 证明它覆盖的旧版本已经被清理，并且没有 snapshot、历史保留、备份、CDC 或复制链路继续依赖它。

大量 delete 会先增加系统负担，而不是立刻释放资源。它会带来读放大、写放大、空间放大、compaction 压力、缓存污染和尾延迟抖动。治理思路不是简单加机器，而是根据删除模式选择合适策略：

1. 少量随机删除用普通 tombstone。
2. 大量范围删除用 range tombstone。
3. 过期数据用 TTL、时间分区或 drop partition。
4. 删除后空间不降要检查 compaction backlog 和长 snapshot。
5. tombstone 密集时使用 tombstone-aware compaction。
6. 删除比例极高时考虑重建数据集或冷热迁移。

面试里可以用一句话收束：

```text
LSM-Tree 的 delete 是写 tombstone，墓碑要等 compaction 确认旧版本不可见且不再需要遮蔽低层数据后才能删除；大量 delete 会造成 tombstone 堆积，引发读放大、写放大和空间放大，解决上要结合 range tombstone、TTL/分区、compaction 调度、限速和 snapshot 治理。
```
