# 7. 追加式 KV 存储与 WAL Compaction

面试里问“KV 存储怎么实现、写读删和崩溃恢复怎么走、WAL 会不会越来越大、compaction 时 offset 失效怎么办”，本质是在考一个单机追加式 KV 引擎的完整生命周期。典型思路接近 Bitcask：磁盘文件顺序追加记录，内存索引保存每个 key 最新记录的位置。

## 1. 核心模型

追加式 KV 存储把随机覆盖写转换成顺序追加写：

```text
Put/Delete
  -> append record 到 active segment / WAL
  -> 更新内存索引 key -> record pointer

Get
  -> 查内存索引
  -> 根据 file_id + offset 读取磁盘记录
  -> 校验 key、seq、crc 后返回 value

Compaction
  -> 扫描旧 segment
  -> 只复制仍然存活的最新记录
  -> 原子发布新 segment 和新索引指针
  -> 延迟删除旧 segment
```

这里的 WAL 和数据文件可以是同一个追加日志，也可以分开。简单自研 KV 常把每条操作都追加到 segment 中，segment 既承担恢复日志，又承担 value 存储；LSM/LevelDB 则通常是先 WAL，再 MemTable，后续 flush 成 SSTable。

## 2. 记录格式和内存索引

一条磁盘记录至少要能自描述长度、操作类型和校验信息：

```text
magic | version | seq | op | key_len | value_len | key | value | crc32c
```

内存索引保存的是最新可见版本的位置，而不是只保存裸 offset：

```cpp
struct RecordPtr {
    uint32_t file_id;
    uint64_t offset;
    uint32_t size;
    uint64_t seq;
    bool deleted;
};

std::unordered_map<std::string, RecordPtr> index;
```

`seq` 用来判断新旧版本，`deleted` 用来表示墓碑，`file_id + offset + size` 用来定位磁盘记录。真实系统还会把索引按 shard 拆分，降低锁竞争，并用 Bloom Filter、hint file 或 checkpoint 加速启动恢复。

## 3. 写入、读取、删除、恢复流程

### 3.1 写入 Put

```text
1. 分配全局递增 seq。
2. 编码 put record，包含 key、value、长度和 crc。
3. 追加写入 active segment。
4. 按持久性要求决定是否 fdatasync/fsync。
5. 写成功后更新内存索引 key -> 新 RecordPtr。
6. 返回成功。
```

顺序必须是先落追加日志，再更新内存索引。否则进程在更新索引后崩溃，重启时磁盘没有这条记录，内存状态无法恢复。

### 3.2 读取 Get

```text
1. 查内存索引。
2. 不存在或 deleted=true，返回 NotFound。
3. 根据 pointer 读取 segment 中的 record。
4. 校验 magic、length、crc 和 key 是否匹配。
5. 返回 value。
```

读取时不要完全信任 offset。磁盘文件可能损坏，旧 index 也可能来自异常恢复过程，所以要校验 key 和 crc；如果只按 offset 读 value，一旦 offset 错乱就可能返回别的 key 的数据。

### 3.3 删除 Delete

删除通常不是立刻去旧文件里擦除 value，而是追加一条 tombstone：

```text
Delete(k)
  -> append tombstone(k, seq)
  -> index[k] = {file_id, offset, size, seq, deleted=true}
```

这样可以保持写路径顺序追加。旧 value 的空间要等 compaction 确认它不再是最新版本后才能回收。

### 3.4 崩溃恢复

启动时按 segment 顺序扫描：

```text
1. 读取 manifest，确定有效 segment 列表和 active segment。
2. 从最早需要恢复的 segment 开始顺序扫描 record。
3. 校验 magic、length、crc。
4. 对合法 record 按 seq 更新内存索引。
5. 遇到尾部半条记录或 crc 错误，截断到最后一条合法记录。
```

崩溃恢复只能恢复到“已经完整写入且满足持久化语义”的记录。默认只写到页缓存时，进程崩溃通常可恢复；断电或内核崩溃能否保留，取决于是否做了 `fsync/fdatasync`、磁盘缓存策略和文件系统语义。

## 4. WAL 会不会越来越大

会。如果所有更新和删除都只是追加记录，旧版本和 tombstone 会一直占空间。因此需要把日志分段，并对旧 segment 做 compaction。

常见策略：

1. **segment rotation**：active segment 达到阈值后封存为 immutable segment，新写入进入新 segment。
2. **存活率统计**：记录每个 segment 中 live bytes / stale bytes，优先 compact 垃圾多的 segment。
3. **后台合并**：扫描旧 segment，只复制仍然是当前最新版本的记录到新 segment。
4. **manifest 原子发布**：新 segment 写完并 fsync 后，更新 manifest 指向新文件集合。
5. **延迟删除旧文件**：确认没有读请求持有旧 segment 后再删除。

```text
segment-1: k1@1, k2@2, k1@3, del(k2)@4
index:
  k1 -> k1@3
  k2 -> tombstone@4

compact segment-1:
  copy k1@3
  可选择保留或丢弃 k2 的 tombstone，取决于是否还需要遮蔽更老版本
```

如果系统还有快照、备份、CDC 或复制链路，tombstone 不能过早删除，否则旧数据可能在某个旧视图里“复活”。

## 5. compaction 后 offset 失效怎么办

offset 失效的根本原因是：compaction 会把存活记录从旧文件复制到新文件，物理位置变了。解决方式不是让 offset 永远不变，而是把 offset 当作可更新的物理指针，并控制发布时间。

推荐做法：

1. **复制后再发布**：compaction 先写新 segment，构建 `key -> new RecordPtr` 的临时映射。
2. **按 seq 校验当前性**：发布前检查内存索引中该 key 的 seq 是否仍等于被复制记录的 seq。若前台已经写入更新版本，不能用旧记录覆盖新指针。
3. **原子替换指针**：在 shard 锁、RCU 或 copy-on-write map 下，把仍然有效的 key 指向新 offset。
4. **文件引用计数或 epoch**：旧 segment 即使不再被 index 引用，也要等正在读取旧 pointer 的请求结束后再删除。
5. **manifest 持久化**：新 segment 和索引变更持久化后，再把旧 segment 标记可回收。

一个常见并发场景：

```text
t1: compaction 读取旧记录 k@seq=10
t2: 前台 Put(k) 写入 k@seq=20，index 指向新 active segment
t3: compaction 准备发布 k@seq=10 的新 offset

正确行为：发现 index[k].seq = 20，不发布 k@seq=10 的指针。
```

如果不做 seq 校验，compaction 可能把已经更新的新值覆盖成旧值，这是追加式 KV 里很严重的数据回退 bug。

## 6. compaction 过程中读写请求怎么办

服务通常不需要停下来。正确模型是“前台读写 active segment，后台 compact immutable segment”。

写请求：

1. 继续追加到当前 active segment。
2. 更新内存索引为新 `RecordPtr`。
3. 不直接写正在被 compact 的旧 segment。

读请求：

1. 先查内存索引，拿到一个稳定的 `RecordPtr`。
2. 读取 pointer 指向的 segment。
3. 如果 compaction 正在迁移该 key，读旧位置或新位置都可以，只要对应 seq 是当前可见版本。
4. 旧 segment 删除前要保证没有读请求还在使用它。

后台 compaction：

1. 只扫描 sealed segment，不扫描正在追加的 active segment。
2. 写新 segment 时不影响前台写。
3. 发布新指针时只短暂持有 shard 锁或使用 RCU。
4. 做 I/O 限速，避免 compaction 抢占前台读写带宽导致 P99 抖动。

如果实现简单，也可以在 compaction 发布阶段短暂阻塞某个 shard 的写入，但不应长时间暂停整个服务。真正要停服的通常是离线重建、格式升级或没有并发控制的教学实现。

## 7. Bitcask、LevelDB、RocksDB 怎么对比

| 引擎 | 核心结构 | 优点 | 代价 | 适用场景 |
| --- | --- | --- | --- | --- |
| Bitcask 类追加 KV | append-only log + 内存哈希索引 | 点查快、写入顺序追加、实现简单 | 全量 key 常驻内存，范围查询弱，compaction 需处理 offset 更新 | 单机缓存、会话状态、小型本地 KV |
| LevelDB | WAL + MemTable + SSTable + LSM compaction | 写吞吐高、key 有序、范围查询可用 | compaction 抖动、读放大、单进程嵌入式 | 本地嵌入式有序 KV |
| RocksDB | 增强 LSM，多列族、丰富 compaction 和调参 | 工程能力强、可调参数多、生态成熟 | 配置复杂，写放大/读放大需要治理 | 存储系统、流处理状态、消息队列元数据 |

面试里可以这样区分：Bitcask 更像“内存索引 + 追加日志”的简单高速点查 KV；LevelDB/RocksDB 是有序 LSM KV，支持范围扫描和更成熟的 compaction，但读写放大和参数复杂度更高。

## 8. 易错点

1. **只保存 offset 不保存 seq**：compaction 发布时容易把旧版本覆盖新版本。
2. **删除直接从 index 移除**：恢复时旧 segment 里的老值可能重新出现，应该追加 tombstone。
3. **读请求不持有 segment 生命周期**：旧文件被后台删除后，读线程可能读到不存在的文件。
4. **manifest 不 fsync**：新文件写好了但元数据没持久化，崩溃后不知道哪些文件有效。
5. **目录不 fsync**：原子 rename 后如果目录项没持久化，断电恢复可能丢失新 manifest。
6. **compaction 不限速**：后台顺序读写也会抢磁盘带宽，让前台 P99 变差。
7. **把 WAL 写入成功等同于 fsync 成功**：页缓存写成功和稳定存储持久化不是一回事。
8. **只测正常重启**：还要测试尾部半写、CRC 错误、manifest 损坏、compaction 中崩溃和重复恢复。

## 9. 面试回答模板

我会把单机 KV 设计成追加式日志结构：写入时先把 `put/delete` record 追加到 active segment，再更新内存索引 `key -> file_id/offset/size/seq/deleted`；读取先查索引，再按 offset 读磁盘并校验 key 和 crc；删除不直接擦旧值，而是追加 tombstone。崩溃恢复时顺序扫描 segment，校验完整 record，重建内存索引，遇到尾部半条记录就截断。

WAL 或 segment 会越来越大，所以要做分段和 compaction。compaction 扫描 immutable segment，只复制当前仍然存活的最新 record 到新 segment。offset 变化是正常的，发布新指针时必须用 seq 校验，确认前台没有写入更新版本；旧 segment 需要引用计数或 epoch 保护，等没有读请求后再删除。前台读写不需要停服，写请求继续追加 active segment，读请求使用当前索引指针，后台 compaction 只在发布阶段短暂同步并做 I/O 限速。
