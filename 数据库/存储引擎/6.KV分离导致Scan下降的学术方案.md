# 6. KV 分离导致 Scan 下降的学术方案

## 1. 问题背景

LSM-Tree 的 compaction 会反复搬运 key 和 value。对于大 value 场景，value 在不同层级之间被多次读写，写放大非常高。KV 分离的核心思路是：**LSM-Tree 里只保存 key、sequence、metadata 和 value pointer，把真正的 value 追加写到独立的 value log/blob file 中**。

典型写入路径：

```text
Put(key, value)
-> append value to value log
-> write key -> value_pointer into LSM-Tree
```

代表性系统包括 WiscKey、RocksDB BlobDB、Titan 等。KV 分离能明显降低 compaction 时搬运大 value 的成本，但会破坏 Scan 的顺序性：key 在 LSM 中仍然有序，而 value log 往往按写入时间追加，范围扫描时会变成“顺序扫描 key + 随机读取 value”。

**假设条件**：

1. 本文讨论的是 LSM-Tree 上的 KV 分离，不是关系型数据库里的覆盖索引或回表问题。
2. value 主要存储在 value log/blob file 中，LSM 中保存 value pointer。
3. Scan 指按 key 范围顺序读取 key-value 对，例如 `Scan(start_key, limit)` 或范围查询。
4. 存储介质以 SSD/NVMe 为主，随机读比 HDD 时代便宜，但大量小随机读仍会造成延迟和吞吐问题。
5. “学术界方案”主要指论文和原型系统中的设计方向，工程系统落地时需要结合 workload、硬件和成本取舍。

## 2. 问题现象

KV 分离后，Scan 性能下降常见表现包括：

1. **范围扫描吞吐下降**：扫描 1 万个连续 key 时，value 可能分散在 value log 的 1 万个不同位置。
2. **P99 延迟升高**：少数 value pointer 指向冷文件、远位置或被 GC 迁移后的区域，导致长尾。
3. **预读失效**：LSM 的 SSTable 顺序读可以预读，但 value log 访问顺序不连续，操作系统和存储设备难以预测。
4. **I/O 放大转移**：compaction 写放大降低，但 scan 的读放大和随机 I/O 增加。
5. **GC 与 Scan 相互影响**：value log GC 会迁移 value 并更新 pointer，Scan 同时读取可能遇到更多间接访问和版本判断。
6. **小 value 更吃亏**：小 value 原本内联在 SSTable 中可以顺序读，分离后反而多一次 pointer 解析和随机读。
7. **缓存命中率下降**：block cache 缓住 key block 不等于缓住 value，Scan 还要访问 blob cache/value cache。

一个简单例子：

```text
LSM 中 key 顺序：
k001 -> ptr(file7, offset900)
k002 -> ptr(file1, offset120)
k003 -> ptr(file9, offset300)
k004 -> ptr(file2, offset800)

Scan(k001, 4)：
key 读取是顺序的，但 value 读取变成 file7、file1、file9、file2 的随机访问。
```

## 3. 影响范围

KV 分离导致 Scan 性能下降，会影响以下模块：

1. **Scan Iterator**：需要从 LSM iterator 中取 pointer，再读取 value log。
2. **Value Log Manager**：决定 value 的写入位置、文件布局、GC 和迁移策略。
3. **Compaction**：不再直接搬运 value，但需要维护 pointer、版本和 tombstone。
4. **Garbage Collection**：value log 中旧 value 清理会影响 value 的物理顺序。
5. **Cache**：需要区分 block cache、blob cache、value cache、prefetch buffer。
6. **Read Scheduler**：Scan 过程中可能需要异步批量读取 value。
7. **Key Layout / Partitioning**：key range 是否和 value log group 对齐，会决定范围扫描是否顺序。
8. **Workload Router**：点查、写入、范围扫、分析查询可能需要不同存储策略。

如果涉及代码实现，可能需要修改的模块包括：

1. `ValueLogWriter`：支持按 key range、group、hotness 或 size 分类写入 value。
2. `ValueLogGC`：GC 时按 key 顺序重写 value，或者按 scan 热度调整 group。
3. `LSMIterator` / `ScanIterator`：支持 pointer 批量收集、异步预取、offset 排序读。
4. `BlobCache` / `ValueCache`：缓存 scan 读取过的 value block。
5. `CompactionJob`：在 compaction 或 GC 时协同更新 value pointer。
6. `ColumnFamilyOptions`：支持小 value inline、大 value 分离、scan-heavy CF 禁用 KV 分离。
7. `Metrics`：记录 scan value random read 次数、value log 顺序度、GC 重写量、scan P99。

## 4. 原因分析

KV 分离把 LSM 的写放大问题，转化成了 value log 的布局和 GC 问题。

传统 LSM-Tree 中，SSTable 按 key 有序，key 和 value 一起存储：

```text
SSTable:
k001:v001, k002:v002, k003:v003, k004:v004
```

Scan 可以顺序读取 SSTable block。

KV 分离后：

```text
SSTable:
k001:ptrA, k002:ptrB, k003:ptrC, k004:ptrD

Value Log:
... v003 ... v001 ... v004 ... v002 ...
```

Scan 的访问变成：

```text
顺序读 key/pointer
-> 随机读 value
-> 合并输出 key-value
```

造成 Scan 下降的根因主要有四个：

1. **逻辑顺序和物理顺序分离**  
   key 的逻辑顺序由 LSM 保证，value 的物理顺序由写入时间决定，两者不一致。

2. **更新破坏 value 局部性**  
   即使 GC 曾经把某个 key range 的 value 整理成顺序，一轮随机更新后，新 value 又会追加到 log 尾部，顺序性重新被破坏。

3. **GC 目标和 Scan 目标冲突**  
   GC 通常想减少无效 value 和迁移成本，而 Scan 想让相邻 key 的 value 物理相邻。两者优化目标不完全一致。

4. **小 value 分离收益不足**  
   小 value 本身搬运成本低，分离后少量写放大收益抵不过 Scan 随机读成本。

因此，学术界的解决方向大多围绕一个问题展开：**如何在降低写放大的同时，恢复或近似恢复 value 的 key 顺序局部性**。

## 5. 解决方案

### 5.1 WiscKey：KV 分离基线与并行随机读

WiscKey 是 KV 分离的经典代表。它把 value 从 LSM 中移出，只在 LSM 里保留 key 和 value pointer，从而降低 compaction 搬运 value 的写放大。它的基本判断是：在 SSD 上，随机读和顺序读的差距比 HDD 小，而且 SSD 有内部并行性，因此可以用并行随机读缓解 value log 读取成本。

对 Scan 的处理思路可以概括为：

1. LSM 负责顺序扫描 key 和 pointer。
2. 批量收集一批 value pointer。
3. 对 value log 发起并行读取。
4. 利用 SSD 并发能力隐藏部分随机读延迟。

这个思路适合：

1. value 较大，compaction 写放大收益明显。
2. 存储设备随机读性能较强。
3. Scan 不是绝对主路径，或者 Scan 能容忍一定随机读。

局限是：

1. 对小 value 或 scan-heavy workload 不友好。
2. 并行随机读不能完全替代顺序读。
3. 随机读多了会抢占点查和写入的 I/O 资源。

### 5.2 选择性 KV 分离：小 Value Inline，大 Value 分离

很多工程和论文方向都会采用阈值策略：

```text
if value_size <= threshold:
    store key-value inline in SSTable
else:
    store value in value log, keep pointer in LSM
```

核心原因是：小 value 的 compaction 搬运成本不高，分离后反而增加 Scan 随机读；大 value 搬运成本高，分离收益明显。

阈值可以静态配置，也可以根据 workload 动态调整：

1. value 越大，越适合分离。
2. scan 越多，越倾向 inline。
3. update 越多，越倾向分离。
4. block cache 命中越高，inline 更有价值。

这是最容易落地的方案，也是很多工业系统的默认取舍。

### 5.3 Scan-aware Layout：按 Key Range 组织 Value Log

FenceKV 这类方案的核心是：不要让 value log 完全按写入时间无序追加，而是按 key range 把 value 映射到不同 group，让同一段 key range 的 value 更可能落在相近物理位置。

示意：

```text
Group 0: [a, f)
Group 1: [f, m)
Group 2: [m, t)
Group 3: [t, z)
```

写入 `key = h001` 的 value 时，不是简单写入全局 log 尾部，而是写入 `[f, m)` 对应的 value group。

这样做的收益：

1. 范围扫描时，相邻 key 的 value 更可能在同一 group。
2. GC 可以对某个 key range 的 group 做整理。
3. GC 后可以把有效 value 按 key 顺序重写，恢复 Scan 顺序性。

代价是：

1. 随机写入会分散到多个 group。
2. group 空间管理和 GC 更复杂。
3. 热点 key range 容易形成局部写放大和空间压力。
4. key range 边界需要随数据分布变化调整。

### 5.4 GC 时按 Key 顺序重写 Value

一种直接思路是：既然 value log 被更新打乱，那么在 GC 时把有效 value 重新按 key 顺序排列。

流程：

```text
1. 选择一个 value log segment 或 key-range group
2. 判断其中哪些 value 仍然有效
3. 按 user key 排序有效 value
4. 顺序写入新的 value log 区域
5. 批量更新 LSM 中的 value pointer
6. 回收旧 segment
```

这样可以把 GC 从单纯的空间回收，变成同时优化 Scan 的物理重排。

问题在于：

1. 需要校验 value 是否有效，可能要查询 LSM 或维护额外索引。
2. 按 key 排序会增加 CPU 和内存成本。
3. 更新 pointer 会向 LSM 写入大量元数据，带来新的写放大。
4. 随机更新会再次破坏顺序，需要周期性维护。

### 5.5 HashKV：优化更新和 GC，不直接优化 Scan

HashKV 通过 hash-based grouping 让同一个 key 的不同版本落到确定的 group 中，降低 value log GC 时验证有效性的成本。它主要解决的是 update-intensive workload 下 KV 分离的 GC 开销，而不是范围扫描顺序性。

它的价值在于提醒一个重要取舍：

```text
按 hash 分组：更新和 GC 更友好，但相邻 key 的 value 不一定相邻
按 key range 分组：Scan 更友好，但更新热点和 group 管理更复杂
```

因此，如果面试问题问的是 Scan 性能下降，HashKV 不能作为主要答案，但可以作为对比方案说明：学术界并不是所有 KV 分离优化都关注 Scan，有些更关注 update 和 GC。

### 5.6 SoKV：动态分组与 GC 驱动的 Key Space 管理

较新的研究开始把 Scan 热度、GC 和 LSM 元数据管理结合起来。SoKV 这类方案关注 KV 分离下 Scan 需要先访问 LSM 获取地址、再访问 value space 的两段开销，提出两类思路：

1. **Value Space 动态分组**  
   根据 scan hotness 和 update 情况调整 value group。Scan 热的 group 可以更快触发 GC、拆分成更小 group，从而更快恢复 value 的 key 顺序；Scan 冷的 group 可以延迟 GC，减少无谓搬运。

2. **GC-based LSM-tree Management**  
   当某个 value group GC 后，部分 LSM 中的 pointer 信息已经失效，可以在元数据层面减少无效 SSTable 对 Scan 的干扰，降低 key space 的扫描成本。

这类方案比固定 key range 分组更进一步：不是只在写入时决定 layout，而是让 GC 根据访问模式持续调整 layout。

### 5.7 读路径批量预取与 Offset 排序

即使底层 value 布局无序，也可以在读路径减少随机读成本。

常见做法：

```text
1. Scan 从 LSM 中先拉取一批 key-pointer
2. 按 value file id 和 offset 对 pointer 分组排序
3. 对相近 offset 合并成较大 I/O
4. 异步并行读取 value
5. 读完后按 key 顺序重新输出
```

这类似数据库里的 batched key access 或回表优化。

优点：

1. 不改变写路径。
2. 对已有 value log 兼容。
3. 能减少小随机 I/O 数量。

缺点：

1. 需要缓存一批扫描结果，增加内存。
2. 输出必须按 key 顺序，需要 reorder buffer。
3. 批越大，吞吐越好，但首包延迟越高。
4. 如果 pointer 分布极散，收益有限。

### 5.8 多布局或双写：Scan 友好副本

对于 scan-heavy 业务，可以维护一个 Scan 友好副本：

1. 主存储使用 KV 分离，优化写入和点查。
2. 异步构建按 key 顺序组织的只读 run、列式文件或冷数据副本。
3. 范围扫描走 Scan 副本，点查和更新走主存储。

这类方案本质上是用空间换读性能，接近 LSM 与列式/分析副本的混合架构。

适合：

1. Scan 是明确的业务主路径。
2. 数据更新和 Scan 可以接受一定异步延迟。
3. 存储空间比 P99 延迟更便宜。

不适合：

1. 强一致 Scan。
2. 写入后必须立即范围可见。
3. 存储成本极敏感场景。

## 6. 可选方案对比

| 方案 | 核心思路 | 优点 | 缺点 | 适用场景 |
| --- | --- | --- | --- | --- |
| WiscKey 并行随机读 | 利用 SSD 并行性批量读 value | 实现相对直接，写放大收益明显 | Scan 仍然随机读，小 value 不友好 | 写多、点查多、大 value |
| 小 value inline | 小值仍放 SSTable，大值分离 | 简单有效，Scan 不至于劣化太多 | 阈值需要调参 | 混合 value size |
| Key-range value group | 按 key range 存放 value | 范围扫描顺序性更好 | group 管理和 GC 复杂 | Scan-heavy 且 key range 明确 |
| GC 按 key 顺序重写 | GC 时恢复 value 顺序 | 同时回收空间和优化 Scan | pointer 更新和排序成本高 | 更新后 Scan 变慢明显 |
| Hash-based grouping | 同 key 多版本进同组 | 更新和 GC 友好 | 对范围扫描帮助有限 | update-heavy |
| 动态分组 | 根据 scan hotness 调整 group | 适应 workload 变化 | 实现复杂，监控依赖强 | 访问模式变化明显 |
| Offset 排序预取 | 读路径批量收集 pointer 并排序读 | 不改写路径，兼容性好 | 增加内存和首包延迟 | 中长范围扫描 |
| Scan 副本 | 维护按 key 顺序的只读副本 | Scan 性能最好 | 空间和一致性成本高 | OLTP + OLAP 混合 |

## 7. 推荐方案

推荐采用分层组合，而不是单点优化：

1. **默认启用选择性 KV 分离**  
   小 value inline，大 value 分离，避免小 value Scan 被随机读拖垮。

2. **Scan 路径做批量预取**  
   ScanIterator 先收集一批 pointer，按 file id 和 offset 合并读取，再按 key 顺序输出。

3. **对 Scan-heavy 数据使用 key-range group**  
   如果业务明显按租户、时间、前缀范围扫，value log 应按这些 range 分组。

4. **GC 同时恢复 value 顺序**  
   对 Scan 热点 group，GC 时按 key 顺序重写有效 value，而不是只追求空间回收。

5. **对 update-heavy 但 scan-light 数据使用 hash grouping 或普通 value log**  
   不要为了 Scan 牺牲所有写入和 GC 性能。

6. **按 Column Family 或表维度隔离策略**  
   点查写多表用 KV 分离；范围扫多表减少分离或维护 Scan 副本。

面试回答可以概括为：

```text
KV 分离把 value 从有序 SSTable 移到按写入顺序追加的 value log，导致 Scan 时 key 顺序和 value 物理顺序不一致，范围扫描变成大量随机读。
学术界主要有几类方案：WiscKey 利用 SSD 并行随机读缓解；选择性 KV 分离让小 value inline；FenceKV 类方案按 key range 组织 value log 并在 GC 中恢复顺序；HashKV 更偏更新和 GC 优化；SoKV 类方案根据 scan hotness 动态分组并结合 GC 管理 LSM 元数据；读路径还可以做 pointer 批量预取和 offset 排序。
工程上推荐小值内联 + 批量预取 + scan 热点 key-range grouping + GC 重排。
```

## 8. 实施步骤

### 8.1 建立 Value 分离阈值

先实现最基础的选择性分离：

```cpp
bool ShouldSeparateValue(const Slice &key, const Slice &value,
                         const ColumnFamilyOptions &opts) {
  if (!opts.enable_kv_separation) {
    return false;
  }
  if (value.size() < opts.min_blob_size) {
    return false;
  }
  if (opts.scan_heavy_column_family) {
    return false;
  }
  return true;
}
```

核心修改逻辑：

1. 小 value 直接写入 SSTable。
2. 大 value 写入 value log，LSM 中保存 pointer。
3. 不同 Column Family 可以配置不同阈值。
4. 监控阈值调整前后的写放大和 Scan 延迟。

### 8.2 实现 Scan 批量预取

ScanIterator 不要每拿到一个 pointer 就同步读一个 value，而是批量处理：

```cpp
struct ValuePointer {
  uint32_t file_id;
  uint64_t offset;
  uint32_t size;
  std::string key;
};

std::vector<ValuePointer> batch;
while (lsm_iter.Valid() && batch.size() < batch_size) {
  batch.push_back(lsm_iter.ValuePointer());
  lsm_iter.Next();
}

auto read_order = SortByFileAndOffset(batch);
auto values = AsyncReadValues(read_order);
return ReorderByKey(batch, values);
```

测试重点：

1. 输出顺序必须仍然按 key 排序。
2. snapshot sequence 不能被异步读取破坏。
3. 批量越大，吞吐越高，但首包延迟和内存越高。
4. 异步读失败后要能降级或重试。

### 8.3 按 Key Range 组织 Value Group

为 value log 引入 group：

```text
ValueGroup {
  group_id
  start_key
  end_key
  active_segment
  gc_score
  scan_hotness
}
```

写入时：

```cpp
group = PickGroupByKeyRange(key);
ptr = group.Append(value);
lsm.Put(key, ptr);
```

GC 时：

```text
1. 选择 scan_hotness 高、无效率高的 group
2. 找到 group 对应 key range 内仍有效的 value
3. 按 key 顺序重写到新 segment
4. 批量更新 LSM pointer
5. 回收旧 segment
```

### 8.4 动态调整 Group

固定 key range 会遇到数据倾斜，需要动态 split/merge：

```text
if group.scan_hotness high and group.size large:
    split group by key median

if group.scan_hotness low and adjacent groups cold:
    merge groups
```

调整依据：

1. Scan 次数。
2. Scan 覆盖的 key range。
3. Update 次数。
4. Group 无效 value 比例。
5. GC 后顺序度改善幅度。

### 8.5 增加 Scan 感知指标

建议增加以下指标：

```text
scan_qps
scan_p95_latency
scan_p99_latency
scan_value_random_reads
scan_value_prefetch_hit
value_pointer_locality_score
value_group_scan_hotness
value_group_gc_bytes
blob_cache_hit_rate
inline_value_ratio
separated_value_ratio
```

其中 `value_pointer_locality_score` 可以粗略定义为：

```text
同一个 Scan batch 内，相邻 pointer 是否落在同一 file 且 offset 距离较近。
```

### 8.6 代码模块设计

可能涉及的文件或模块：

1. `db/write_batch.cc`：写入时决定 inline 还是分离。
2. `table/block_based_table_builder.cc`：SSTable 中编码 inline value 或 value pointer。
3. `blob/value_log_writer.cc`：按 group 写 value。
4. `blob/value_log_reader.cc`：支持批量异步读取和 prefetch。
5. `blob/value_log_gc.cc`：GC 时按 key 顺序重写 value。
6. `db/compaction_job.cc`：协调 pointer 更新和 tombstone/version 处理。
7. `db/scan_iterator.cc`：实现批量 pointer 收集、offset 排序和 reorder 输出。
8. `monitoring/statistics.cc`：增加 Scan 与 value locality 指标。

## 9. 风险与注意事项

1. **不要盲目 KV 分离**  
   KV 分离优化的是大 value compaction 写放大，不是所有 workload 都更快。Scan-heavy、小 value 场景可能明显变慢。

2. **Offset 排序不能破坏 key 顺序输出**  
   读 value 可以按 offset 顺序，返回给上层必须恢复 key 顺序。

3. **异步预取要遵守 snapshot**  
   Pointer 对应的 value 版本必须和 LSM iterator 的 snapshot 语义一致，GC 不能提前回收正在读取的 value。

4. **GC 重排会带来新的写放大**  
   为了恢复 Scan 顺序而频繁搬运 value，可能抵消 KV 分离降低写放大的收益。

5. **Key-range group 会遇到热点倾斜**  
   某个租户或时间段特别热时，对应 group 会成为写入和 GC 热点，需要动态 split。

6. **Hash grouping 和 Scan 目标冲突**  
   HashKV 类方案适合 update-heavy，但它把相邻 key 打散，对范围扫描帮助有限。

7. **小 value inline 阈值需要压测**  
   阈值过低会导致 Scan 随机读多；阈值过高会让 compaction 写放大回升。

8. **Scan 副本会引入一致性成本**  
   如果维护按 key 顺序的副本，需要处理双写、延迟、回放和校验。

9. **硬件差异很大**  
   NVMe、SATA SSD、HDD、ZNS SSD、云盘的随机读并发和尾延迟不同，策略不能脱离硬件。

## 10. 验证方式

### 10.1 功能验证

1. inline value 和 separated value 混合时，点查结果正确。
2. Scan 输出严格按 key 顺序。
3. GC 后 pointer 更新正确，旧 value 不再被读到。
4. Snapshot 下 Scan 看到的版本稳定。
5. Delete/tombstone 与 separated value 组合时，旧 value 不复活。

### 10.2 性能验证

对比以下方案：

1. 传统 LSM，不做 KV 分离。
2. 全量 KV 分离。
3. 小 value inline + 大 value 分离。
4. KV 分离 + Scan 批量预取。
5. KV 分离 + key-range group。
6. KV 分离 + GC 按 key 顺序重写。

关键指标：

1. Scan QPS。
2. Scan P50/P95/P99。
3. 每次 Scan 的 value random read 次数。
4. value log 读带宽。
5. compaction write amplification。
6. GC write amplification。
7. blob/value cache hit rate。
8. 设备队列深度和 I/O util。

### 10.3 Workload 验证

至少覆盖：

1. 大 value + 点查多。
2. 大 value + Scan 多。
3. 小 value + Scan 多。
4. update-heavy。
5. append-only。
6. Zipf 热点。
7. 时间范围扫描。
8. 租户前缀范围扫描。

### 10.4 正确性压力测试

压测流程：

```text
1. 并发 Put/Delete/Scan
2. 后台持续 GC 和 compaction
3. 随机创建 snapshot
4. 随机 crash/recover
5. 与 reference map 或传统 LSM 结果对比
```

重点验证：

1. pointer 不悬空。
2. value 不被 GC 提前回收。
3. Scan 不漏 key、不重复 key。
4. 重启后 pointer 和 value log 元数据一致。

## 11. 总结

KV 分离的本质是用 value log 降低 LSM compaction 搬运大 value 的写放大，但它把 key 的有序性和 value 的物理布局分开，导致 Scan 时出现大量 value 随机读。这个问题不是 bug，而是 KV 分离架构的核心代价。

学术界和工程界主要有几类解决方向：

1. WiscKey 利用 SSD 并行随机读缓解 Scan 随机访问。
2. 选择性 KV 分离让小 value inline，只分离大 value。
3. FenceKV 类方案按 key range 组织 value log，提高范围扫描局部性。
4. GC 时按 key 顺序重写 value，恢复 value 物理顺序。
5. HashKV 类方案优化 update 和 GC，但不直接解决范围扫描。
6. SoKV 类方案根据 scan hotness 动态分组，并结合 GC 管理 key space。
7. 读路径用 pointer 批量预取、offset 排序和异步 I/O 降低随机读长尾。
8. 对 scan-heavy 业务维护 Scan 友好副本或禁用 KV 分离。

最终推荐不是“KV 分离一定好”或“一定不好”，而是按 workload 决策：

```text
写多、点查多、大 value：KV 分离收益大。
范围扫多、小 value：谨慎 KV 分离，优先 inline 或 scan-aware layout。
同时有大 value 写入和 Scan：小值内联 + 大值分离 + 批量预取 + key-range group + GC 重排。
```

1. WiscKey: Separating Keys from Values in SSD-Conscious Storage.
2. HashKV: Enabling Efficient Updates in KV Storage via Hashing.
3. FenceKV: Enabling Efficient Range Query for Key-Value Separation.
4. SoKV: Scan performance optimization for KV separation with adaptive dynamic grouping and GC-based LSM-tree management.
