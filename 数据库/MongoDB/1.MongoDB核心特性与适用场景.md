# MongoDB 核心特性与适用场景

MongoDB 是面向文档的 NoSQL 数据库，核心数据模型是 BSON 文档。它不像关系型数据库那样以固定二维表为中心，而是把一组相关字段组织成一个文档，适合 schema 经常变化、对象结构天然嵌套、读写链路更偏文档整体访问的场景。

## 1. MongoDB 常用特性

### 文档模型

MongoDB 的一条记录是一个 BSON 文档，可以包含嵌套对象和数组：

```json
{
  "_id": "player_1001",
  "name": "alice",
  "level": 35,
  "items": [
    { "id": 101, "count": 3 },
    { "id": 205, "count": 1 }
  ],
  "profile": {
    "region": "cn",
    "last_login": "2026-05-04T10:00:00Z"
  }
}
```

优点是业务对象和存储结构更接近，读取一个玩家档案、内容配置、订单快照时可以少做 Join。代价是数据容易冗余，跨文档一致性和复杂查询要更谨慎。

### 灵活 Schema

MongoDB 不强制所有文档字段完全一致。它适合：

1. 字段经常变化的业务，例如配置、活动、内容管理。
2. 不同类型对象字段差异明显，但又希望放在同一集合中查询。
3. 需要快速迭代的后台系统或中台元数据。

注意：灵活 schema 不代表没有 schema。真实项目仍要在应用层或 JSON Schema 校验字段类型、必填项、版本号和兼容逻辑，否则长期演进后数据会变得很难治理。

### 索引

MongoDB 支持单字段索引、复合索引、多键索引、TTL 索引、文本索引、地理位置索引等。现代 MongoDB 默认 WiredTiger 存储引擎，索引通常是 B-tree 类结构。

常见原则：

1. 高频过滤、排序字段建立复合索引。
2. 复合索引同样要关注字段顺序，尽量贴合查询模式。
3. 数组字段建立索引会形成多键索引，一个文档可能产生多个索引项。
4. TTL 索引适合验证码、临时会话、过期日志等自动清理。
5. 索引越多，写入维护成本越高。

### 副本集和分片

副本集提供高可用：一个 primary 接收写入，多个 secondary 复制数据。primary 故障后会选举新的 primary。

分片用于水平扩展：按 shard key 把数据分布到多个分片。shard key 选择很关键：

1. 区分度要高，避免热点集中在单个分片。
2. 查询最好经常带 shard key，避免 scatter-gather。
3. 单调递增 key 可能造成写热点，需要哈希分片或复合 shard key。
4. shard key 选错后迁移成本很高。

### 聚合管道

聚合管道通过 `$match`、`$group`、`$sort`、`$project`、`$lookup` 等阶段处理数据，适合做中等复杂度统计和转换。

易错点：

1. `$match` 尽量前置，先减少进入后续阶段的数据量。
2. `$sort`、`$group` 数据量大时可能占用大量内存或落盘。
3. `$lookup` 可以做类似 Join 的操作，但不能把 MongoDB 当关系数据库无限 Join。
4. 复杂分析、报表和大范围聚合更适合同步到 ClickHouse、Doris、Elasticsearch 等系统。

## 2. MongoDB 适用场景

适合：

1. **用户画像和玩家档案**：字段多、结构嵌套、经常整体读取。
2. **内容和配置管理**：不同内容类型字段差异大，schema 变化频繁。
3. **订单快照和事件记录**：保留当时完整业务上下文，后续回放或审计。
4. **物联网和日志类数据**：写入量大、字段可能不断扩展，配合 TTL 或冷热归档。
5. **地理位置查询**：使用 2dsphere 索引做附近位置、范围查询。

不太适合：

1. 强事务、强一致资金账本。
2. 多表复杂 Join 和高度规范化关系模型。
3. 任意维度 ad-hoc 分析和超大范围聚合。
4. 对唯一约束、外键约束、复杂事务依赖很重的核心关系数据。

## 3. MongoDB 和 Redis 怎么选

| 对比项 | MongoDB | Redis |
| --- | --- | --- |
| 数据模型 | 文档数据库，BSON 文档 | 内存 KV，String/Hash/List/Set/ZSet 等 |
| 主要用途 | 半结构化数据持久化、文档查询 | 缓存、计数、排行榜、锁、限流、临时状态 |
| 查询能力 | 支持字段过滤、复合索引、聚合管道 | 主要按 key 或特定数据结构访问 |
| 持久化定位 | 可作为业务主存储之一 | 通常作为缓存或辅助状态，虽有持久化但不适合作为所有核心账本 |
| 延迟 | 毫秒级为主，依赖磁盘和缓存命中 | 内存访问，通常更低延迟 |
| 容量 | 可通过分片扩展到较大数据集 | 受内存成本约束更明显 |

选择建议：

1. 需要按文档字段查询、更新和持久化，选 MongoDB。
2. 需要极低延迟 key-value 访问、TTL、排行榜、计数器，选 Redis。
3. MongoDB 可以保存玩家档案或活动配置，Redis 缓存热点玩家摘要、在线状态和排行榜。
4. 关键资产变更不要只放 Redis；需要持久化、审计和补偿的状态应落到数据库或日志系统。

## 4. Redis 和 MySQL 有什么区别

Redis 和 MySQL 经常一起使用，但定位不同：

| 对比项 | MySQL | Redis |
| --- | --- | --- |
| 类型 | 关系型数据库 | 内存型 KV/数据结构存储 |
| 数据模型 | 表、行、列，schema 固定 | key-value 和多种内置数据结构 |
| 查询方式 | SQL、Join、事务、索引优化 | 按 key 或数据结构命令访问 |
| 一致性 | InnoDB 支持 ACID 事务 | 单命令原子，事务能力有限 |
| 持久化 | redo/binlog、崩溃恢复成熟 | RDB/AOF，通常用于缓存和辅助状态 |
| 典型用途 | 权威数据、订单、用户、资产、关系数据 | 缓存、锁、限流、计数、排行榜、会话 |

真实项目中，MySQL 常作为权威数据源，Redis 作为加速层或协调辅助。比如查询商品详情时先读 Redis，miss 后回源 MySQL 并回填缓存；扣库存时可以用 Redis Lua 做前置资格校验，但最终仍要用数据库条件更新、唯一约束、幂等表或事务兜底。

## 5. 易错点

1. MongoDB schema 灵活不等于可以不做数据治理。
2. MongoDB 支持事务，但跨分片事务成本高，不能按关系数据库的使用方式滥用。
3. Redis 有持久化不等于适合作为所有核心业务的唯一数据库。
4. MySQL 有索引也不适合任意维度全文检索和复杂聚合，必要时要引入 ES/OLAP。
5. 数据库选型要从访问模式出发：点查、范围查、全文检索、聚合分析、事务一致性、延迟和容量要求都要一起看。

## 6. 面试回答模板

MongoDB 是文档型数据库，使用 BSON 文档保存半结构化数据，支持灵活 schema、复合索引、多键索引、TTL、地理位置索引、副本集、分片和聚合管道。它适合用户画像、玩家档案、内容配置、订单快照这类文档整体读写和字段经常变化的场景；不适合强事务账本和复杂 Join。Redis 更偏内存 KV 和数据结构，适合缓存、排行榜、限流、分布式锁和临时状态；MySQL 是关系型数据库，适合作为订单、资产、用户等权威数据源。真实后端通常是 MySQL 管强一致权威数据，Redis 做加速和短期状态，MongoDB 承接半结构化文档和灵活查询。
