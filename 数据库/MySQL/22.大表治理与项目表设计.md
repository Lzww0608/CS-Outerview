# 22. 大表治理与项目表设计

面试里问“你项目里最大的表多大”“MySQL 几张表都存什么”，不是只要报数字，而是考你是否理解数据模型、索引、增长趋势、慢 SQL 风险和治理方案。

## 1. 项目表怎么介绍

介绍 MySQL 表时可以按业务域分组，而不是逐字段背表结构：

1. **核心实体表**：用户、订单、内容、商品、文档、会话等，保存业务主状态。
2. **关系表**：用户-角色、订单-商品、文档-标签、关注关系等，表达多对多关系。
3. **流水/明细表**：支付流水、积分流水、操作记录、访问记录，数据量通常增长最快。
4. **配置表**：活动配置、策略配置、模型配置、灰度规则，读多写少。
5. **任务表**：异步任务、重试任务、补偿任务、导入导出任务，常带状态机。
6. **审计表**：管理员操作、权限变更、关键业务动作，要求可追溯。

回答时要说明每张核心表的主键、关键索引、数据量级、读写频率和保留策略。

## 2. 最大表数据量怎么回答

如果真实项目没有特别大的表，也可以诚实说明数据量级，并补充设计思路：

```text
最大表是 xxx_log / order_item / document_chunk，
当前约 N 万 / N 百万行，
日增量约 M，
主要查询模式是按 user_id/status/time 或 doc_id/version 查询，
索引是 ...，
超过某个量级后会做归档、分表或异构存储。
```

不要只说“几百万行没问题”。更完整的回答要包含：

1. **行数和容量**：行数、单行大小、索引大小、总容量。
2. **增长速度**：每天新增多少，多久翻倍。
3. **访问模式**：等值查询、范围查询、排序分页、聚合统计还是后台扫描。
4. **热点分布**：是否有大租户、大用户、热门内容导致数据倾斜。
5. **保留策略**：冷热分层、归档、删除、压缩或转存到 ClickHouse/ES/对象存储。

## 3. 大表风险

大表真正的问题通常不是“行数大”本身，而是访问模式和维护成本：

1. 索引不合适导致全表扫描。
2. 大分页 `LIMIT offset, size` 扫描和丢弃大量行。
3. 排序、分组、临时表落盘导致 CPU 和 I/O 飙升。
4. Online DDL、加索引、字段变更耗时长，可能影响主库。
5. 历史数据和热数据混在一起，Buffer Pool 命中率下降。
6. 单表写入热点集中，例如按自增主键或单个业务 key 高频写。
7. 备份、恢复、迁移和回滚窗口变长。

## 4. 大表治理手段

治理顺序通常是先优化查询和索引，再考虑拆分架构。

1. **索引治理**：围绕高频查询建联合索引和覆盖索引，删除重复和低价值索引。
2. **SQL 改写**：避免 `SELECT *`、函数包索引列、隐式转换、大 offset 和无条件批量扫描。
3. **冷热分离**：热表只保留近期数据，历史数据归档到历史表、对象存储、ClickHouse 或 ES。
4. **分区表**：按时间分区便于归档和删除，但不能替代合理索引。
5. **水平分表**：按用户、订单、租户或 hash 分表，降低单表体积和热点。
6. **读写分离**：报表、导出、低实时查询走只读库或离线链路。
7. **预聚合和缓存**：统计类查询提前计算，避免在线扫明细。
8. **Online DDL**：使用 gh-ost、pt-online-schema-change 或数据库原生 online DDL，控制变更风险。

## 5. 表设计注意事项

1. 主键尽量短、稳定、递增或局部有序，避免二级索引膨胀。
2. 联合索引按查询条件设计，不是字段越多越好。
3. 状态字段要配合时间或业务 ID 建联合索引，否则低基数字段选择性差。
4. 金额用整数分或 decimal，避免浮点误差。
5. 时间字段统一时区和精度，便于范围查询和归档。
6. 软删除字段要谨慎，大量 `deleted=1` 会污染热表，必要时归档。
7. 审计和日志类数据不要无限堆在业务主表里。

## 6. 真实场景

RAG 项目的 MySQL 可以这样拆：

1. `document`：文档元信息，保存标题、来源、版本、权限、状态。
2. `document_chunk`：chunk 元数据，保存 `chunk_id、doc_id、section_path、token_count、vector_id`。
3. `conversation`：会话主表，保存用户、标题、创建时间和状态。
4. `message`：消息明细，保存用户问题、模型回答、引用和 token 成本。
5. `ingest_task`：文档入库任务，保存解析、embedding、索引写入状态和错误。
6. `feedback`：用户反馈，保存点赞、纠错、无答案和人工标注。

其中 `message`、`document_chunk`、`ingest_task` 可能增长最快，要按用户/文档/时间设计索引，并考虑归档和统计表。

## 7. 面试回答模板

我介绍项目 MySQL 表时会先按业务域说：核心实体表保存主状态，关系表表达多对多，流水明细表记录变化过程，任务表承载异步状态，审计表做追溯。最大表不能只报行数，还要说行大小、索引大小、日增量、查询模式和保留策略。大表治理我会先从慢 SQL、执行计划和索引入手，避免全表扫描、大分页和临时表；再做冷热分离、归档、读写分离、预聚合，必要时按业务 key 或时间分表。上线改表要用 online DDL、灰度和回滚方案，不能直接在高峰期锁大表。
