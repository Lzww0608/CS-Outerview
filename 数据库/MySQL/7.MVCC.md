# Q7. MVCC

MVCC（Multi-Version Concurrency Control，多版本并发控制）是数据库用来提高读写并发的一种机制。它的核心思想是：写操作生成数据的新版本，读操作按照自己的快照读取可见版本，从而减少读写之间的阻塞。

在 InnoDB 中，MVCC 主要依赖：

1. **隐藏字段**：
   - `trx_id`：最后一次修改该行的事务 ID。
   - `roll_pointer`：指向 undo log 中的旧版本记录。
2. **Undo Log**：保存行记录被修改前的旧值，多个旧版本通过 `roll_pointer` 串成版本链。
3. **Read View**：一致性读时生成的快照，用来判断某个版本对当前事务是否可见。

## Read View 如何判断可见性

Read View 中通常包含几个关键信息：

1. `creator_trx_id`：创建该 Read View 的事务 ID。
2. `m_ids`：创建快照时仍然活跃的事务 ID 列表。
3. `min_trx_id`：活跃事务列表中的最小事务 ID。
4. `max_trx_id`：下一次将要分配的事务 ID。

判断某行版本是否可见，可以按下面的思路理解：

1. 如果版本的 `trx_id` 等于当前事务 ID，说明是自己改的，可见。
2. 如果版本的 `trx_id` 小于 `min_trx_id`，说明在快照创建前已经提交，可见。
3. 如果版本的 `trx_id` 大于等于 `max_trx_id`，说明是快照创建后才出现的事务，不可见。
4. 如果版本的 `trx_id` 在 `m_ids` 中，说明快照创建时该事务还没提交，不可见。
5. 其他情况说明该事务在快照创建前已经提交，可见。

如果当前版本不可见，就沿着 undo log 版本链向前查找，直到找到可见版本或版本链结束。

## RC 和 RR 下的区别

1. **READ COMMITTED**：每次一致性读都会生成新的 Read View，所以同一事务内两次查询可能看到其他事务新提交的数据。
2. **REPEATABLE READ**：事务第一次一致性读时生成 Read View，后续复用同一个 Read View，所以同一事务内普通快照读结果可重复。

这也是为什么 InnoDB 在 RR 下可以通过 MVCC 解决普通快照读的不可重复读问题。

## 快照读和当前读

1. **快照读**：普通 `SELECT`，读取 Read View 可见的历史版本，不加锁。
2. **当前读**：`SELECT ... FOR UPDATE`、`UPDATE`、`DELETE`、`INSERT` 等，读取最新已提交版本，并加锁保证后续修改安全。

需要注意，MVCC 主要优化的是快照读，不代表写写冲突也无锁。更新同一行时仍然要加行锁。

## 易错点

1. MVCC 不是只靠 undo log，Read View 才决定“哪个版本可见”。
2. MVCC 不能解决所有幻读。InnoDB 的 RR 还需要 Next-Key Lock / Gap Lock 处理当前读场景下的幻读。
3. 长事务会长期持有 Read View，导致 undo log 旧版本不能及时清理，进而拖慢查询和膨胀存储。
4. 业务上的“库存扣减”“余额扣减”不能只依赖 MVCC，需要条件更新、行锁、乐观锁或流水表保证并发正确性。
