根据记录数据变更的方式不同，MySQL的binlog主要有**三种格式**：

1.  **STATEMENT** (SBR - Statement-Based Replication)
2.  **ROW** (RBR - Row-Based Replication)
3.  **MIXED** (Mixed-Based Replication)

接下来，我将从它们的**工作原理**、**优缺点**以及**适用场景**三个维度，结合深层原理和实例来进行详细阐述。

---

### 1. STATEMENT 模式 (基于语句的复制)

#### 工作原理
在这种模式下，binlog记录的是**原始的、导致数据发生变更的SQL语句**。主库执行一条`UPDATE`或`INSERT`语句，binlog中就记录这条`UPDATE`或`INSERT`语句的原文。从库在同步时，会取出这些SQL语句并**重新执行一遍**，从而实现数据同步。

#### 优点
*   **日志文件体积小**：只需要记录SQL语句，相比记录每一行的数据变更，日志量要小得多，可以节省磁盘I/O和网络I/O。
*   **可读性好**：可以直接通过`mysqlbinlog`工具查看日志内容，清晰地知道执行了哪些SQL语句，方便数据库审计和问题排查。
*   **与存储引擎无关**：日志记录的是逻辑SQL，不依赖于具体的存储引擎实现。

#### 缺点 (这是其致命弱点)
*   **可能导致主从数据不一致**：这是最严重的问题。某些SQL语句在主库和从库上执行可能会产生不同的结果。这类语句被称为“不确定性语句 (Non-Deterministic Statements)”。
    *   **依赖系统状态的函数**：如 `UUID()`, `NOW()` (在某些情况下), `RAND()`。主库执行`INSERT INTO t VALUES(UUID())`和从库执行时，生成的UUID是不同的。
    *   **依赖执行顺序的语句**：如 `UPDATE ... LIMIT 1`。如果没有`ORDER BY`子句，在不同的数据库版本或存储引擎下，更新的行可能是不同的。
    *   **存储过程、触发器、UDF(用户自定义函数)**：这些内部可能包含不确定性逻辑，在从库上执行的结果可能与主库不一致。

#### 适用场景
*   **场景非常简单**：系统中所有的DML操作都是简单的、确定性的SQL语句（如基于主键的`UPDATE`或`DELETE`），不涉及任何不确定性函数或逻辑。
*   **审计需求**：当需要清晰地知道数据库上执行了哪些SQL操作时，Statement模式的日志更便于分析。
*   **在旧版本的MySQL中（5.7.7之前）比较常见，但现在基本不推荐作为生产环境的默认选项。**

---

### 2. ROW 模式 (基于行的复制)

#### 工作原理
ROW模式不记录SQL语句原文，而是记录**每一行数据被修改的具体细节**。它会记录下被修改行的**前镜像 (Before Image)** 和 **后镜像 (After Image)**。
*   对于`INSERT`操作，只记录新插入行的后镜像。
*   对于`DELETE`操作，只记录被删除行的前镜像。
*   对于`UPDATE`操作，同时记录被修改行的前镜像和后镜像。

从库接收到这些行变更事件后，直接根据这些信息在自己的数据表中找到对应的行（通常通过主键），然后应用这些变更，而**不需要重新执行SQL语句**。

#### 优点
*   **数据一致性最高，最安全**：完美地解决了Statement模式的“不确定性”问题。无论SQL语句多么复杂，最终落到数据行的变更都是确定的，因此可以保证主从数据的高度一致性。
*   **对复杂SQL支持更好**：对于包含存储过程、触发器等复杂逻辑的操作，也能准确复制。

#### 缺点
*   **日志文件体积大**：例如，一条`UPDATE`语句更新了100万行数据，Statement模式只记录一条SQL，而ROW模式需要记录100万行数据的前后镜像，日志量会急剧膨胀。这会增加磁盘和网络的开销。
*   **可读性差**：日志内容是经过编码的二进制行数据，无法直接阅读，需要借助`mysqlbinlog --base64-output=DECODE-ROWS -v`等复杂命令来解析。

#### 适用场景
*   **绝大多数现代应用场景**：对于数据一致性要求极高的系统，如金融、电商等，ROW模式是**唯一推荐**的选择。
*   系统中存在大量的不确定性SQL、存储过程、触发器等。
*   **从MySQL 5.7.7版本开始，ROW模式已经是默认的binlog格式**，这也体现了官方对数据安全性和一致性的重视。

---

### 3. MIXED 模式 (混合模式复制)

#### 工作原理
MIXED模式是Statement和ROW模式的**折衷方案**。MySQL会根据执行的SQL语句**自动判断**采用哪种模式。
*   对于**确定性的、安全的**SQL语句（如大部分普通的`INSERT`, `UPDATE`, `DELETE`），它会采用**Statement**模式记录，以节省日志空间。
*   对于**不确定性的、可能导致主从不一致**的SQL语句（如使用了`UUID()`函数、或者DML操作影响了带有自增ID的表），它会自动切换到**ROW**模式记录。

#### 优点
*   **兼顾了两种模式的优点**：在保证数据一致性的前提下，尽量减少日志文件的体积。

#### 缺点
*   **判断逻辑本身存在不确定性**：虽然MySQL的判断机制已经非常成熟，但在某些极端或边缘场景下，开发者无法100%预知某条SQL到底会以哪种格式记录，给问题的诊断带来了一定的复杂性。
*   **版本依赖**：不同MySQL版本对于“不安全语句”的判断标准可能存在差异。

#### 适用场景
*   希望在日志大小和数据一致性之间找到一个平衡点的场景。
*   大部分操作是安全的，但偶尔会有不确定性操作的系统。
*   在实际生产中，由于ROW模式的可靠性以及当前存储成本的降低，MIXED模式的使用场景也在减少，大家更倾向于直接使用ROW模式来消除任何潜在的风险。

---

### 总结与对比

为了让您更清晰地理解，我做了一个表格来总结：

| 特性               | STATEMENT 模式 (SBR) | ROW 模式 (RBR)           | MIXED 模式 (MLR)                     |
| :----------------- | :------------------- | :----------------------- | :----------------------------------- |
| **记录内容**       | SQL语句原文          | 行数据的变更（前后镜像） | 动态选择SBR或RBR                     |
| **数据一致性**     | **差** (可能不一致)  | **高** (最安全)          | **较高** (理论上安全)                |
| **日志文件大小**   | **小**               | **大**                   | 介于两者之间                         |
| **可读性**         | **高** (直接可读)    | **差** (二进制)          | 部分可读，部分不可读                 |
| **对不确定性函数** | **不支持** (不安全)  | **支持** (安全)          | **支持** (自动切换为RBR)             |
| **默认模式**       | MySQL 5.7.7 之前     | **MySQL 5.7.7 及之后**   | -                                    |
| **推荐场景**       | 基本不推荐用于生产   | **所有生产环境**         | 对日志大小敏感但仍需保证一致性的场景 |

### 实践中的代码示例

**1. 查看当前的binlog格式：**
```sql
SHOW VARIABLES LIKE 'binlog_format';
/*
+---------------+-------+
| Variable_name | Value |
+---------------+-------+
| binlog_format | ROW   |
+---------------+-------+
*/
```

**2. 为什么Statement模式不安全？一个直观的例子：**
假设我们有一个用户表`users`，我们想随机更新其中一个用户的积分。
```sql
CREATE TABLE users (id INT PRIMARY KEY, score INT);
INSERT INTO users VALUES (1, 100), (2, 200), (3, 300);

-- 执行一条不确定性的UPDATE
UPDATE users SET score = score + 10 ORDER BY RAND() LIMIT 1;
```
*   **在Statement模式下**：binlog记录的就是`UPDATE users SET score = score + 10 ORDER BY RAND() LIMIT 1;`这条语句。
    *   主库执行时，可能更新了`id=2`的用户。
    *   从库同步时，重新执行`RAND()`，可能更新了`id=1`的用户。**主从数据就不一致了。**
*   **在ROW模式下**：假设主库更新了`id=2`的用户。
    *   binlog记录的是：`Table: users, PK: id=2, Before Image: {id:2, score:200}, After Image: {id:2, score:210}`。
    *   从库收到这个变更事件，直接找到`id=2`的行，将其`score`从200更新为210。**结果是确定的，数据保持一致。**
