# 10. 创建索引原则

## 1. 索引的目标

MySQL 索引的目标不是“越多越好”，而是用额外的存储和写入维护成本，换取查询时更少的扫描、更少的排序、更少的回表。

创建索引前先明确：

1. 高频 SQL 是什么。
2. 过滤条件、排序字段、分组字段是什么。
3. 返回行数大概多少。
4. 写入频率和表大小如何。
5. 是否能通过覆盖索引减少回表。

## 2. 适合建索引的字段

1. **高频出现在 WHERE 条件中的字段**：例如用户 ID、订单 ID、状态 + 时间。
2. **区分度高的字段**：例如手机号、身份证号、订单号。
3. **连接字段**：`JOIN` 的关联列，例如 `user_id`、`order_id`。
4. **排序和分组字段**：`ORDER BY`、`GROUP BY` 如果能匹配索引顺序，可以减少 filesort。
5. **唯一约束字段**：用唯一索引保证业务唯一性，例如订单号、邮箱。

不适合单独建索引的字段：

1. 区分度很低的字段，例如性别、布尔值。
2. 更新非常频繁且查询很少的字段。
3. 过长的大字段，例如完整 `TEXT`，除非使用合理前缀索引或全文索引。

## 3. 联合索引设计原则

联合索引要围绕具体 SQL 设计，而不是把所有字段随意拼在一起。

常见顺序：

```text
等值条件字段 -> 范围条件字段 -> 排序/分组字段 -> 覆盖查询字段
```

示例：

```sql
SELECT id, amount
FROM orders
WHERE user_id = 100
  AND status = 1
  AND created_at >= '2026-01-01'
ORDER BY created_at DESC
LIMIT 20;
```

可以考虑：

```sql
CREATE INDEX idx_user_status_time
ON orders(user_id, status, created_at DESC);
```

原因：

1. `user_id`、`status` 是等值条件，可以快速缩小范围。
2. `created_at` 是范围和排序字段，可以继续按时间扫描。
3. 如果查询字段都在索引里，可以进一步做覆盖索引。

## 4. 最左前缀和范围条件

联合索引 `(a, b, c)` 按 `a -> b -> c` 排序。能否用好索引取决于条件是否连续匹配最左前缀。

可以用到较多索引能力：

```sql
WHERE a = 1
WHERE a = 1 AND b = 2
WHERE a = 1 AND b = 2 AND c = 3
WHERE a = 1 AND b > 10
```

较差：

```sql
WHERE b = 2
WHERE a > 1 AND b = 2
```

范围条件后的列通常不能继续用于精确定位，但可能用于覆盖索引或 ICP。

## 5. 覆盖索引

覆盖索引是指查询需要的列都能从二级索引中拿到，不需要回表。

```sql
SELECT user_id, status, created_at
FROM orders
WHERE user_id = 100
ORDER BY created_at DESC;
```

如果有索引：

```sql
CREATE INDEX idx_user_time_status
ON orders(user_id, created_at DESC, status);
```

查询可能只扫二级索引即可。覆盖索引适合高频查询，但不要为了覆盖把大量低价值字段塞进索引，索引越宽，写入和缓存成本越高。

## 6. 索引数量和长度控制

索引不是免费资源：

1. 插入、删除、更新都要维护索引。
2. 二级索引叶子节点保存主键，主键越长，二级索引越大。
3. 索引越多，优化器选择成本越高。
4. 索引越宽，Buffer Pool 能缓存的索引页越少。

建议：

1. 删除长期不用或重复的索引。
2. 避免多个索引前缀重复，例如已有 `(a,b,c)`，通常不需要单独建 `(a,b)`。
3. 长字符串可以考虑前缀索引，但要评估区分度。
4. 主键尽量短、稳定、递增或趋势递增。

### 每个字段都建索引会怎样

不建议给每个字段都建索引。问题包括：

1. **写入变慢**：每次 `INSERT/DELETE/UPDATE` 都要维护多棵 B+ 树。
2. **占用更多磁盘和 Buffer Pool**：索引页变多，缓存命中率下降。
3. **更新成本高**：被更新字段如果有索引，需要删除旧索引项并插入新索引项。
4. **优化器选择变复杂**：大量相似索引可能增加优化器评估成本，还可能选到不理想索引。
5. **低选择性索引收益低**：性别、布尔状态这类字段单独建索引，命中行太多时可能还不如全表扫描。
6. **重复索引浪费**：已有联合索引 `(a,b,c)` 时，再建 `(a)`、`(a,b)` 往往重复。

更好的做法是围绕高频 SQL 建少量高质量索引，用联合索引、覆盖索引、唯一索引解决真实查询路径，并通过 `EXPLAIN` 和慢 SQL 验证。

### 怎么判断和治理索引太多

线上索引治理不能只凭感觉删索引，要先确认它是否被使用、是否重复、是否支撑唯一约束或外键约束。

常见排查方式：

1. `SHOW INDEX FROM table_name` 查看索引列、顺序、基数和是否唯一。
2. `performance_schema`、`sys.schema_unused_indexes` 观察长期未使用索引。
3. 慢 SQL 和 `EXPLAIN` 反推核心查询是否真的依赖该索引。
4. 检查重复索引，例如已有 `(user_id, status, created_at)` 时，单独的 `(user_id)` 可能可以合并，但要看查询和约束。
5. 对高风险索引先设置为 invisible index，灰度观察执行计划和慢 SQL，再决定删除。

治理原则：

1. 唯一索引除了查询优化，还承担业务约束，不能只因为查询少就删除。
2. 删除索引前要确认没有离线任务、报表任务、低频管理后台依赖它。
3. 写多读少的表更要控制索引数量，因为每个二级索引都会放大写入、binlog 和 Buffer Pool 压力。
4. 宽联合索引要关注列长度和主键长度，过宽会降低缓存命中率。
5. 索引变更要避开高峰，并使用在线 DDL 或变更工具，防止长时间锁表。

### 用户和时间两个字段怎么建索引

如果一张表有 `user_id` 和 `created_at` 两列，需求是：

1. 根据用户查。
2. 根据日期查。
3. 根据日期和用户查。

没有一个普通联合索引能同时把三种查询都做到最优。需要根据查询频率和选择性设计索引。

常见选择：

```sql
CREATE INDEX idx_user_time ON t(user_id, created_at);
CREATE INDEX idx_time_user ON t(created_at, user_id);
```

原因：

1. `idx_user_time` 支持 `WHERE user_id = ?`，也支持 `WHERE user_id = ? AND created_at BETWEEN ? AND ?`。
2. `idx_time_user` 支持 `WHERE created_at BETWEEN ? AND ?`，也可以支持先按日期范围缩小后再过滤用户。
3. 单独只有 `(user_id, created_at)` 时，日期单独查询不能利用最左前缀做高效定位。
4. 单独只有 `(created_at, user_id)` 时，用户单独查询也不能高效定位。

如果写入非常频繁、不能承受两个索引，要按业务取舍：

1. 用户查询和用户时间查询最频繁：优先 `(user_id, created_at)`，日期查询走离线报表、分区表或异构存储。
2. 日期范围查询最频繁：优先 `(created_at, user_id)`。
3. 日期通常是按天归档或删除：可以考虑按时间分区，再在分区内建 `(user_id, created_at)`。
4. 如果查询只需要少量字段，可以把返回字段放到联合索引末尾做覆盖索引，但要控制索引宽度。

示例：

```sql
-- 查某个用户最近记录
SELECT id, created_at, action
FROM t
WHERE user_id = ?
ORDER BY created_at DESC
LIMIT 20;

-- 适合 idx_user_time

-- 查某天全量记录
SELECT id, user_id, action
FROM t
WHERE created_at >= '2026-05-03'
  AND created_at <  '2026-05-04';

-- 适合 idx_time_user
```

易错点是回答“建一个 `(user_id, created_at)` 就行”。它不能高效支持纯日期查询，因为联合索引必须先命中最左列。

## 7. 验证方式

创建索引前后要用数据验证：

1. `EXPLAIN` 看 `type`、`key`、`rows`、`Extra`。
2. `EXPLAIN ANALYZE` 看真实执行时间和扫描行数。
3. 慢 SQL 日志看线上高频慢查询。
4. 结合业务读写比例，确认写入成本可接受。

## 8. 易错点

1. 有索引不代表一定会用，优化器会基于成本选择。
2. 单列索引很多不等于性能好，联合索引更要贴合 SQL。
3. 对索引列做函数、表达式或隐式类型转换，可能导致索引失效。
4. 小表或返回大比例数据时，全表扫描可能比走索引更快。
5. 索引设计要关注业务变化，历史索引需要定期巡检。

## 9. 面试回答模板

MySQL 创建索引要从 SQL 出发。优先给高频过滤条件、连接字段、排序分组字段和唯一约束建索引；联合索引一般按等值条件、范围条件、排序字段、覆盖字段设计，并遵守最左前缀。字段要有足够区分度，索引长度和数量要控制，因为索引会增加写入维护成本和占用 Buffer Pool。不要每个字段都建索引，低价值索引会拖慢写入、占用缓存并干扰优化器。建完索引后用 `EXPLAIN`、慢 SQL、线上扫描行数验证，而不是凭感觉加索引。
