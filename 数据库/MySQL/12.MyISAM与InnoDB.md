# 12. MyISAM 与 InnoDB

MyISAM 和 InnoDB 都是 MySQL 存储引擎。现代 MySQL 默认使用 InnoDB，因为它支持事务、行级锁、崩溃恢复和 MVCC，更适合在线业务系统。

## MySQL 存储引擎在架构中的位置

MySQL 可以粗略分为 Server 层和存储引擎层。

```text
客户端连接
  -> 连接器 / 权限校验
  -> 解析器
  -> 优化器
  -> 执行器
  -> 存储引擎接口
  -> InnoDB / MyISAM / Memory / Archive ...
```

Server 层负责 SQL 解析、优化、执行计划、函数、视图、权限等通用逻辑；存储引擎层负责真正的数据组织、索引结构、锁、事务、崩溃恢复和物理读写。不同引擎可以共用同一套 SQL 层，但底层能力差别很大。

常见引擎：

1. **InnoDB**：事务型引擎，支持 MVCC、行锁、redo/undo、聚簇索引，是在线业务默认选择。
2. **MyISAM**：非事务型引擎，表锁，数据和索引分离，历史场景较多。
3. **Memory**：数据放内存，重启丢失，适合临时表或小型中间结果。
4. **Archive**：面向归档压缩写入，查询和更新能力有限。

## 核心区别

| 对比项 | InnoDB | MyISAM |
| --- | --- | --- |
| 事务 | 支持 ACID 事务 | 不支持事务 |
| 锁粒度 | 行锁为主，也有表锁、意向锁、间隙锁 | 表锁 |
| 崩溃恢复 | 支持 redo/undo 崩溃恢复 | 恢复能力弱，异常后可能需要修复表 |
| MVCC | 支持 | 不支持 |
| 外键 | 支持 | 不支持 |
| 索引组织 | 聚簇索引，主键叶子节点保存完整行 | 非聚簇，索引叶子通常保存数据文件地址 |
| 写并发 | 较好 | 写入会锁表，并发写差 |
| 全文索引 | 现代 InnoDB 支持 | 历史上 MyISAM 支持较早 |

## InnoDB 为什么更常用

1. 支持事务，适合订单、支付、库存、账户等一致性要求高的场景。
2. 行级锁降低并发更新冲突。
3. MVCC 让普通读不阻塞写，提高读写并发。
4. redo log 保证崩溃恢复，undo log 支持回滚和快照读。
5. 聚簇索引按主键组织数据，主键查询非常高效。

从底层看，InnoDB 以页为单位管理数据，常见页大小为 16KB。数据页通过 B+ 树组织，Buffer Pool 缓存热点页，redo log 负责崩溃恢复，undo log 负责回滚和 MVCC 版本链。写入通常不是每次都直接刷数据页，而是先写日志，再由后台线程把脏页刷回磁盘。

## MyISAM 适合什么场景

MyISAM 现在较少用于核心业务表。它更适合历史包袱、只读或读多写少且不需要事务的简单场景。对于新系统，除非有明确理由，否则优先选择 InnoDB。

## 易错点

1. InnoDB 行锁依赖索引，SQL 不走索引时可能扫描并锁住大量记录。
2. InnoDB 聚簇索引要求主键尽量短、稳定、趋势递增，否则会影响二级索引大小和页分裂。
3. MyISAM 表锁不是完全不能并发读，但写入会明显影响并发。
4. “MyISAM 查询一定比 InnoDB 快”是过时说法，要结合缓存、索引、事务、并发和崩溃恢复成本看。

## 面试回答模板

MySQL 架构上可以分为 Server 层和存储引擎层。Server 层负责连接、权限、解析、优化和执行，存储引擎层负责数据页、索引、锁、事务和物理读写。InnoDB 是事务型引擎，支持 ACID、行级锁、MVCC、外键和崩溃恢复，索引是聚簇 B+ 树，Buffer Pool 缓存数据页，redo/undo 保证恢复和回滚，适合在线交易类业务。MyISAM 不支持事务和 MVCC，主要是表锁，崩溃恢复能力弱，索引和数据分离。现代 MySQL 核心业务表一般选 InnoDB，除非是非常特殊的只读或历史场景。
