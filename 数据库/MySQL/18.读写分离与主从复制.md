# MySQL 读写分离与主从复制

读写分离是把写请求打到主库，把读请求分发到一个或多个从库，用复制链路把主库变更同步到从库，从而提高读扩展能力并降低主库压力。

## 1. 主从复制流程

MySQL 经典主从复制基于 binlog：

```text
Client 写主库
  -> Master 执行事务并写 redo/binlog
  -> Slave I/O Thread 拉取 Master binlog
  -> 写入本地 relay log
  -> Slave SQL Thread 回放 relay log
  -> 从库数据追上主库
```

核心组件：

1. **binlog**：主库记录逻辑或行级变更。
2. **dump thread**：主库把 binlog 发送给从库。
3. **I/O thread**：从库拉取 binlog 并写 relay log。
4. **SQL thread / worker**：从库回放 relay log。
5. **GTID**：用全局事务 ID 标识复制位点，便于故障切换和追增量。

## 2. 同步方式

| 方式 | 特点 | 风险 |
| --- | --- | --- |
| 异步复制 | 主库提交不等从库确认，吞吐高 | 主库宕机可能丢最近事务 |
| 半同步复制 | 至少等一个从库收到 binlog 后再返回 | 延迟增加，从库慢会影响写入 |
| 组复制 / 强一致方案 | 多副本协议保证更强一致性 | 架构复杂，写延迟更高 |

普通互联网业务常用异步或半同步复制，并通过业务补偿、读主库、延迟监控处理一致性问题。

## 2.1 MySQL 集群常见形态

面试问“MySQL 集群”时，要先说明它可能指高可用、读扩展、写扩展或分布式数据库，不同目标对应不同方案。

| 形态 | 核心目标 | 典型方案 | 主要风险 |
| --- | --- | --- | --- |
| 一主多从 | 读扩展、备份、容灾 | 主库写，从库读，binlog 复制 | 复制延迟、主库写瓶颈 |
| 主主复制 | 双向复制、切换方便 | 两个主库互为主从 | 自增冲突、双写冲突、脑裂 |
| MGR / Group Replication | 多副本一致和自动选主 | MySQL Group Replication、InnoDB Cluster | 写延迟更高、运维复杂 |
| 分库分表 | 写扩展和容量扩展 | ShardingSphere、MyCat、业务路由 | 跨分片事务、全局查询、扩缩容 |
| 云数据库 HA | 托管高可用 | RDS、PolarDB、Aurora 等 | 受云厂商能力和配置约束 |

一主多从是最常见的在线业务基础架构。它能扩展读能力，但不能提升单主写入上限；写入瓶颈通常要靠垂直拆分、分库分表、异步削峰、热点行拆分或业务模型调整。

主主复制不等于可以随便双写。除非业务能保证不同主库写入不同数据范围，否则网络分区或复制延迟下很容易出现冲突。生产里更多把主主当作热备或双中心容灾的一部分，而不是无约束多写。

MGR 这类方案可以提供更强的自动选主和一致性能力，但它也会引入 quorum、写放大和网络延迟成本。交易核心链路如果追求更强一致，可以考虑这类方案；普通读多写少系统通常一主多从加成熟故障切换已经足够。

## 3. 读写分离路由

常见实现方式：

1. **业务代码路由**：写接口走主库，普通读走从库，写后读走主库。
2. **数据库中间件**：ShardingSphere、ProxySQL、MyCat 等根据 SQL 类型和规则转发。
3. **DAO 层注解/上下文**：事务内强制主库，非事务读可走从库。
4. **连接池隔离**：主库连接池和从库连接池分别限流，避免互相拖垮。

读写分离真正难点不是“把 SELECT 发从库”，而是复制延迟和一致性。

## 4. 复制延迟与一致性

复制延迟来源：

1. 主库写入太快，从库回放跟不上。
2. 大事务、DDL、长事务阻塞回放。
3. 从库机器配置差或承担了过多查询。
4. 网络抖动、跨机房 RTT 增加。
5. 从库并行复制粒度不足。

常见处理：

1. **写后读主库**：用户刚更新的数据，在一段时间内强制读主库。
2. **按 GTID/位点等待**：读从库前等待从库追到某个事务位点。
3. **延迟监控和摘除**：从库延迟超过阈值时从读池摘除。
4. **拆分大事务**：避免一个大事务长期阻塞从库回放。
5. **并行复制**：开启基于 logical clock 或 write set 的并行回放能力。
6. **缓存一致性配合**：写数据库后删除缓存，必要时用 binlog/MQ 做补偿删除。

## 5. 故障切换

主库故障时通常要：

1. 选择复制位点最新、数据最完整的从库。
2. 提升为新主库。
3. 让其他从库改为复制新主库。
4. 更新业务连接地址或 VIP/域名/代理路由。
5. 检查旧主库恢复后是否存在脑裂写入，必要时重做或重建。

半同步只能降低丢数据概率，不等于绝对不丢。跨机房场景还要额外考虑网络分区、仲裁和写入可用性。

## 6. MySQL 容灾设计

MySQL 容灾要同时回答 RPO（最多能丢多少数据）和 RTO（多久恢复服务）。主从复制只是容灾链路的一部分，它不能替代备份，因为误删、误更新、DDL 事故会被同步到从库。

常见方案：

1. **备份 + PITR**：定期全量备份，持续归档 binlog。故障或误操作后先恢复全量备份，再按 binlog 回放到指定时间点或 GTID。
2. **主从高可用**：一主多从配合 GTID、半同步复制、复制延迟监控和自动故障切换工具，如 MHA、Orchestrator 或云数据库 HA。
3. **延迟从库**：保留一个延迟复制从库，例如延迟 30 分钟到数小时，用于抵御误删被立刻同步的问题。
4. **跨机房/跨可用区副本**：主库和从库分布在不同故障域，结合代理层或注册中心切换写入口。
5. **演练和校验**：定期恢复备份、校验主从数据一致性，监控 `Seconds_Behind_Master`、relay log 积压、复制错误和磁盘空间。

真实场景里的取舍：

1. 金融、交易类业务更关注 RPO，可能需要半同步、组复制或更强一致的分布式数据库。
2. 内容、日志、推荐特征类业务更关注吞吐和成本，可以接受短暂数据丢失，通过离线任务补偿。
3. 跨地域容灾会显著增加写延迟，如果所有写都同步到异地，业务要评估可用性和一致性的权衡。
4. 自动切主必须防止脑裂：旧主恢复后不能继续接收写请求，要通过 fencing、VIP/代理切换、只读开关或仲裁机制隔离旧主。

## 6.1 容灾面试回答模板

我会把 MySQL 容灾分成备份恢复和在线高可用两层。备份层做全量备份加 binlog 归档，支持按时间点恢复，解决误删和逻辑损坏；高可用层用一主多从、GTID、半同步复制和自动故障切换，把最新从库提升为主，并让代理或注册中心切换流量。跨机房还要考虑网络分区和脑裂，所以需要仲裁、旧主隔离和定期容灾演练。主从复制能提升可用性，但不是备份的替代品。

## 7. 易错点

1. 读写分离提升的是读扩展能力，不提升单主写入上限。
2. 从库可能读到旧数据，事务内读、写后读、强一致读应该走主库或等待位点。
3. 主从复制不是备份的替代品，误删会被同步到从库，仍然需要备份和 PITR。
4. 只做 `SELECT` 路由不够，`SELECT ... FOR UPDATE`、临时表、函数副作用、事务上下文都要特殊处理。
5. 从库承担复杂报表查询时，可能反过来拖慢复制回放，最好做分析库隔离。

## 8. 面试回答模板

MySQL 读写分离一般是一主多从，写主库，读从库。主从复制通过主库 binlog、从库 I/O 线程拉取 relay log、SQL 线程回放来同步数据。异步复制吞吐高但可能丢最近事务，半同步会等待至少一个从库收到 binlog，降低丢失概率但增加写延迟。读写分离的核心问题是复制延迟：写后读要走主库或等 GTID 位点，从库延迟过高要摘除；大事务、DDL、跨机房网络都会造成延迟。故障切换要选择最新从库提升为主，并处理旧主脑裂和数据补偿。
