# 20. redo log、undo log 和 binlog

MySQL 面试里问 redo log、undo log、binlog，核心是在问 InnoDB 如何保证事务、崩溃恢复和主从复制。三者不在同一层：redo/undo 主要属于 InnoDB 存储引擎，binlog 属于 MySQL Server 层。

## 1. 三类日志分别做什么

| 日志 | 所属层 | 记录内容 | 主要作用 |
| --- | --- | --- | --- |
| redo log | InnoDB | 数据页的物理修改 | 崩溃恢复、保证持久性 |
| undo log | InnoDB | 旧版本数据和回滚信息 | 事务回滚、MVCC 快照读 |
| binlog | Server 层 | 逻辑变更或行级变更事件 | 主从复制、数据恢复、审计、异构同步 |

### redo log

redo log 是重做日志。事务提交时不要求立刻把脏页刷到数据文件，只要先把相关修改写入 redo log 并按策略刷盘，崩溃后就可以根据 redo log 把已提交事务的修改重新做一遍。

这就是 WAL（Write-Ahead Logging）：先写日志，再写数据页。

优势：

1. 把随机刷数据页转换成顺序写日志。
2. 允许 Buffer Pool 延迟刷脏页，提高写入性能。
3. 崩溃后能恢复已提交但尚未落盘的数据页修改。

### undo log

undo log 是回滚日志。它记录的是修改前的旧值或能够构造旧版本的信息。

主要作用：

1. **回滚事务**：事务失败或主动 rollback 时，根据 undo log 把数据恢复到修改前。
2. **MVCC**：一致性读通过 Read View 判断当前版本不可见时，可以沿 undo 版本链找到历史版本。

注意：undo log 也需要持久化，它本身的修改也会受到 redo log 保护。

### binlog

binlog 是 Server 层的二进制日志，记录数据库发生了哪些逻辑变更。常见格式有 Statement、Row、Mixed，生产中更常使用 Row 格式。

主要作用：

1. 主从复制：从库拉取主库 binlog 并回放。
2. 时间点恢复：备份 + binlog 可以恢复到某个时间点。
3. 异构同步：Canal/Debezium 订阅 binlog，同步到 Redis、ES、数据仓库。
4. 审计：追踪数据变更来源。

## 2. 为什么 MySQL 需要这些日志

因为它们解决的是不同问题，不能互相替代。

1. **只靠数据页不行**：如果每次提交都同步刷所有脏页，随机 I/O 成本太高。
2. **redo 不能替代 undo**：redo 负责“已提交的修改丢了要重做”，undo 负责“未提交或回滚的修改要撤销”。
3. **redo 不能替代 binlog**：redo 是 InnoDB 内部物理日志，循环写，主要用于崩溃恢复；binlog 是 Server 层逻辑日志，可归档，用于复制和恢复。
4. **binlog 不能替代 redo**：binlog 粒度和时机不适合做 InnoDB 数据页级崩溃恢复。

## 3. redo 和 binlog 的两阶段提交

InnoDB 事务提交时，redo log 和 binlog 都要成功，才能既保证本机崩溃恢复，又保证主从复制一致。

典型流程：

```text
1. InnoDB 写 redo log，状态为 prepare
2. Server 写 binlog
3. InnoDB 把 redo log 标记为 commit
```

崩溃恢复时：

1. redo 是 prepare，binlog 存在：说明事务应该提交，可以补 commit。
2. redo 是 prepare，binlog 不存在：说明 binlog 没写成功，事务回滚。
3. redo 是 commit：事务提交。

两阶段提交的目的，是避免“主库恢复后有这笔事务，但 binlog 没有，从库永远同步不到”这类不一致。

## 4. 执行 SQL 会不会造成索引树分裂

要看 SQL 是否修改了 B+ 树中的索引记录，以及目标页是否有空间。

可能触发页分裂的场景：

1. `INSERT` 新行，目标主键页已满。
2. 更新了索引列，等价于删除旧索引项再插入新索引项。
3. 随机主键或随机二级索引值导致插入落在树中间的满页。

不直接触发页分裂的场景：

1. 只执行普通 `SELECT`。
2. 更新非索引列，且行大小变化没有引发页空间问题。
3. 写 redo/undo/binlog 本身不会让业务表的索引树分裂；真正导致分裂的是数据页或索引页插入/移动记录。

为什么递增主键更友好：

1. 新记录大多追加到最右叶子页。
2. 页分裂更少，Buffer Pool 局部性更好。
3. 二级索引叶子保存主键，短且递增的主键也能降低二级索引成本。

## 5. 易错点

1. redo log 是物理日志，binlog 是逻辑/行级变更日志，不要混为一谈。
2. undo log 不只是回滚，也服务于 MVCC。
3. binlog 属于 Server 层，因此 MyISAM 也可以有 binlog，但没有 InnoDB 的 redo/undo 事务能力。
4. 事务提交不是简单“先写 binlog 再写 redo”，要通过两阶段提交保证一致。
5. 页分裂和日志不是一个层面的概念，日志记录变更，页分裂是 B+ 树物理维护动作。

## 6. 面试回答模板

redo log、undo log 和 binlog 作用不同。redo log 是 InnoDB 的物理重做日志，配合 WAL 保证提交后的修改崩溃可恢复；undo log 记录旧版本，用于事务回滚和 MVCC；binlog 是 Server 层的逻辑或行级变更日志，用于主从复制、时间点恢复和异构同步。MySQL 需要 redo 提升刷盘性能并保证持久性，需要 undo 支持回滚和快照读，需要 binlog 做复制和归档。redo 和 binlog 之间通过两阶段提交保证主库崩溃恢复和从库复制的一致性。
