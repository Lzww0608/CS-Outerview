# 32. 纯 MySQL 防高并发重复点赞

面试题：不借助 Redis，纯 MySQL 方案防止高并发重复点赞。场景是用户对某个内容（文章、评论、商品）点赞和取消点赞，高并发下不能出现同一用户对同一内容重复点赞。

核心约束：**每个用户对特定内容最多只有一个有效赞**。

## 1. 表结构设计

### 1.1 核心点赞表

```sql
CREATE TABLE user_like (
    id          BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    user_id     BIGINT UNSIGNED NOT NULL,
    target_type TINYINT UNSIGNED NOT NULL COMMENT '1-文章, 2-评论, 3-商品',
    target_id   BIGINT UNSIGNED NOT NULL,
    status      TINYINT(1) NOT NULL DEFAULT 1 COMMENT '1-已点赞, 0-已取消',
    created_at  DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at  DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    UNIQUE KEY uk_user_target (user_id, target_type, target_id)
) ENGINE=InnoDB;
```

**关键设计**：

1. **唯一索引 `uk_user_target`**：天然保证同一用户对同一目标最多一条记录。重复插入直接报错，写入时就能发现冲突。
2. **不删行，只改 `status`**：用户既可能点赞也可能取消，取消后不清除记录，避免后续再次点赞时的主键冲突和计数不准。
3. **`target_type + target_id` 组合**：支持多种业务实体共用同一张表，避免为每类内容建一张表。

### 1.2 计数表

```sql
CREATE TABLE target_like_count (
    target_type TINYINT UNSIGNED NOT NULL,
    target_id   BIGINT UNSIGNED NOT NULL,
    like_count  INT UNSIGNED NOT NULL DEFAULT 0,
    PRIMARY KEY (target_type, target_id)
) ENGINE=InnoDB;
```

点赞计数从 `user_like` COUNT 会非常慢，必须用计数表实时维护。

## 2. 点赞操作

### 2.1 INSERT ... ON DUPLICATE KEY UPDATE

```sql
INSERT INTO user_like (user_id, target_type, target_id, status)
VALUES (?, ?, ?, 1)
ON DUPLICATE KEY UPDATE
status = 1,
updated_at = NOW();
```

核心思路：

1. 如果记录**不存在**，插入新行，`status=1`。
2. 如果记录**已存在**（唯一索引冲突），把 `status` 更新为 1（已点赞）。
3. 如果用户之前取消过点赞（`status=0`），再次点赞时也会变为 1。

这个单条 SQL 天然兼顾"首次点赞"和"再次点赞"，不需要业务代码先查再写。

### 2.2 判断是否需要更新计数

可以用 `ROW_COUNT()` 判断是插入还是更新：

- 插入：`ROW_COUNT() = 1`，表示新行。
- 更新：`ROW_COUNT() = 2`（匹配一行，更新一行）。
- `status` 已经是 1：`ROW_COUNT() = 0`，表示没有实际变化。

但 `ROW_COUNT()` 在不同驱动和连接池行为下有细微差异。更稳妥的方式是在事务中先更新点赞表，再用 `SELECT status INTO @old FROM user_like WHERE ...` 判断变更前状态，决定计数是否增减。

### 2.3 事务 + 条件更新计数

```sql
START TRANSACTION;

INSERT INTO user_like (user_id, target_type, target_id, status)
VALUES (?, ?, ?, 1)
ON DUPLICATE KEY UPDATE status = 1;

-- 检查是否是首次有效点赞
SELECT status INTO @old_status
FROM user_like
WHERE user_id = ? AND target_type = ? AND target_id = ?
FOR UPDATE;

IF ROW_COUNT() > 0 OR @old_status != 1 THEN
    UPDATE target_like_count
    SET like_count = like_count + 1
    WHERE target_type = ? AND target_id = ?;
END IF;

COMMIT;
```

更简洁的写法是利用 `status` 从 0 变 1 这个事实：

```sql
UPDATE target_like_count AS t
JOIN user_like AS u
  ON u.user_id = ? AND u.target_type = t.target_type AND u.target_id = t.target_id
SET t.like_count = t.like_count + 1
WHERE u.status = 1 AND (/* u 刚刚从 0 变 1 或首次插入 */);
```

实际工程常用方案是把点赞和取消幂等化的同时，利用**影响行数判断**避免 SQL 过于复杂。

## 3. 取消点赞

```sql
UPDATE user_like
SET status = 0, updated_at = NOW()
WHERE user_id = ? AND target_type = ? AND target_id = ? AND status = 1;
```

加上 `AND status = 1` 条件，如果没有影响任何行说明已经取消或不曾点赞，避免重复扣减计数。

取消后同步更新计数表。

## 4. 不删行的原因

取消点赞时不删行，保留 `status=0` 的记录。原因：

1. **下次再点赞不会主键冲突**：同一用户再点赞时 `INSERT ... ON DUPLICATE KEY UPDATE` 只会更新 status，不会报错。
2. **保留用户历史**：可以分析用户点赞行为。
3. **避免唯一索引上的间隙锁竞争加剧**：删行后重新插入，InnoDB 要在索引上删除死行再插入新行，锁成本高于原地更新。

## 5. 悲观锁 vs 乐观锁

### 5.1 悲观锁弊端

在高并发的点赞场景下，下面这种写法不可取：

```sql
START TRANSACTION;

SELECT COUNT(*) FROM user_like
WHERE user_id = ? AND target_type = ? AND target_id = ?
FOR UPDATE;

IF count = 0 THEN
    INSERT INTO user_like ...;
    UPDATE target_like_count SET like_count = like_count + 1;
ELSE
    -- 已点赞，不允许重复
END IF;

COMMIT;
```

弊端：

1. **`FOR UPDATE` 锁住索引记录**：同一用户对同一内容并发点赞时，后到的事务必须等前一个提交，直接排队。虽然唯一约束保证了最终正确，但请求吞吐大幅下降。如果用户快速连点，所有请求串行化。
2. **秒钟级热点锁争用**：热门内容可能有几万用户同时点赞，不同用户对不同内容本身不会冲突；但如果业务用错了锁范围（如锁了内容维度而不是用户+内容维度），锁竞争会骤增。
3. **事务持锁时间长**：`FOR UPDATE` 后会等待业务代码判断、INSERT、UPDATE 计数后才释放，锁持有时间较长。
4. **死锁风险**：如果多条 SQL 的锁顺序不统一（例如先查 content 表再查 user_like 表），可能产生 AB-BA 死锁。

### 5.2 唯一索引方案本身就是乐观锁

上面提到的 `INSERT ... ON DUPLICATE KEY UPDATE` 不需要 `FOR UPDATE`。它的核心思想是：

1. 假设没有冲突。
2. 如果真的冲突了（唯一索引报错），InnoDB 内部自动转化为更新操作。
3. 不需要应用程序显式上锁。

这是数据库内置的乐观并发控制：**唯一索引 + UPSERT 语义**，比应用程序自己加乐观锁更简洁高效。

### 5.3 什么时候悲观锁还该用

唯一约束无法覆盖的场景：

1. 库存扣减：需要 `stock > 0` 条件，唯一约束解决不了。
2. 余额操作：需要 `balance >= amount` 条件。
3. 领取任务：一个任务只能一个人领取，且领取后标记状态。

这些场景需要 `UPDATE ... WHERE stock > 0` 条件更新或 `FOR UPDATE` 读锁。

## 6. 计数一致性与补偿

纯 MySQL 方案的核心挑战是：**点赞表和计数表如何保证严格一致**。

### 6.1 计数最终一致性

```sql
START TRANSACTION;

-- 先操作点赞表
INSERT INTO user_like (user_id, target_type, target_id, status)
VALUES (?, ?, ?, 1)
ON DUPLICATE KEY UPDATE status = 1;

-- 再更新计数
INSERT INTO target_like_count (target_type, target_id, like_count)
VALUES (?, ?, 1)
ON DUPLICATE KEY UPDATE
like_count = like_count + 1;

COMMIT;
```

即使如此，在事务提交前，其他事务看到的是旧计数。这在读多写少场景是可接受的。

### 6.2 定期对账

最终一致性不能完全信任实时计数，需要定时补偿：

```sql
-- 核对某内容的点赞数
SELECT COUNT(*) FROM user_like
WHERE target_type = ? AND target_id = ? AND status = 1;
```

如果和计数表不同，用真实 COUNT 修正。补偿频率按业务容忍度决定，活动期间可以每分钟核对热门内容。

### 6.3 Binlog 补偿

不是所有公司都愿意用事务 + COUNT 对账。另一种方案是监听 MySQL binlog，通过 Canal 同步点赞变更到 Redis 计数，再异步持久化回 MySQL 计数表。但题目问的是纯 MySQL 方案，走事务 + 计数表是标准答案。

## 7. 性能边界

纯 MySQL 方案能抗多大并发：

1. **写入吞吐**：高频写入场景（秒杀点赞）单库单表可能成为瓶颈。热点内容写入集中在唯一索引的同一页，可能触发索引页锁竞争。
2. **计数表写放大**：每个赞都触发 `target_like_count` 更新，对 InnoDB 的 redo log 和主键索引写入压力大。

超出 MySQL 写入能力时，典型演进路径：

1. 独立计数服务，内存合并后批量回写。
2. 引入 Redis 先记数，异步刷到 MySQL。
3. 点赞流水进 MQ，异步消费处理。

但在面试中，**纯 MySQL 方案的底线是唯一索引 + UPSERT + 事务计数**，面试官想听的是你知道这些约束和边界，而不是一上来就说"用 Redis"。

## 8. 易错点

1. 没有唯一索引，靠先查再写判断：高并发下两个请求同时查出 count=0，都执行 INSERT，出现重复点赞。
2. 取消点赞时删行而不是更新 status：导致同一用户反复点赞取消时，唯一索引插入报错需捕获异常处理。
3. 点赞表上加悲观锁 `FOR UPDATE`：不必要的串行化，把并发降到 1。
4. 计数不独立维护，查询时 `COUNT(*)` 实时统计：千万级数据 COUNT 很慢。
5. 点赞成功但计数更新失败：需要事务或补偿机制。
6. 唯一索引 UV 主键自增浪费：可以改用 `(user_id, target_type, target_id)` 作为联合主键，省掉自增 id。

## 9. 总结

纯 MySQL 防止高并发重复点赞的核心方案是**唯一约束 + UPSERT 语义**：`INSERT ... ON DUPLICATE KEY UPDATE` 保证每个用户对每个目标只有一条记录，取消点赞只改 status 不删行，计数通过事务同步维护。不需要 `FOR UPDATE` 悲观锁。瓶颈在 MySQL 写入能力和锁竞争，热点内容需要引入缓存或 MQ 降级。面试时先讲方案，再指出边界：唯一索引能保证正确但扛不住亿级点赞，需要分层架构和补偿机制兜底。
