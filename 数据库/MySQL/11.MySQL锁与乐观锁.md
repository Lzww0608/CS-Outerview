# 11. MySQL 锁与乐观锁

锁是数据库保证隔离性和并发正确性的核心机制。InnoDB 同时使用 MVCC 和锁：普通一致性读尽量不阻塞写，当前读和写操作则需要加锁保证结果正确。

## MySQL 常见锁类型

| 锁类型 | 粒度/含义 | 典型场景 |
| --- | --- | --- |
| 表锁 | 锁整张表 | DDL、MyISAM 写入、显式 `LOCK TABLES` |
| 行锁 | 锁具体索引记录 | InnoDB 按主键或唯一索引更新单行 |
| 记录锁 Record Lock | 锁已有索引记录 | `UPDATE ... WHERE id = 1` |
| 间隙锁 Gap Lock | 锁索引记录之间的范围 | RR 下防止范围幻读 |
| Next-Key Lock | 记录锁 + 前面的间隙锁 | RR 下范围当前读 |
| 意向锁 | 表级锁，表示事务将要加行锁 | 表锁和行锁兼容性判断 |
| 共享锁 S Lock | 允许读，阻塞写 | `SELECT ... LOCK IN SHARE MODE` |
| 排他锁 X Lock | 独占读写修改权 | `UPDATE/DELETE/SELECT ... FOR UPDATE` |
| 元数据锁 MDL | 保护表结构元数据 | DDL 与 DML 并发控制 |

## 什么情况下使用

1. **普通查询**：InnoDB 在 RC/RR 下通常走 MVCC 快照读，不主动加行锁。
2. **更新/删除**：对扫描到的索引记录加排他锁；范围条件可能触发 Next-Key Lock。
3. **库存扣减、余额扣减**：用条件更新或 `SELECT ... FOR UPDATE`，让并发写串行化。
4. **读多写少**：应用层可用读写锁，数据库层通过 MVCC 降低读写冲突。
5. **防止重复创建**：优先使用唯一索引，而不是只靠应用锁。

### 不是只有 UPDATE 和 INSERT 才加锁

数据库加锁取决于“是否需要读最新数据、是否会改变数据、是否要保护结构或约束”，不只发生在 `UPDATE` 和 `INSERT`：

1. `UPDATE` / `DELETE`：当前读并对命中的索引记录加排他锁，范围条件在 RR 下可能加 Next-Key Lock。
2. `INSERT`：会加插入意向锁，还会参与唯一索引、外键检查；多个事务插入同一间隙时可能互相等待。
3. `SELECT ... FOR UPDATE`：显式排他锁，适合先查再改的短事务。
4. `SELECT ... LOCK IN SHARE MODE` / `FOR SHARE`：显式共享锁，允许并发读但阻塞写。
5. 普通 `SELECT`：通常是快照读，不加行锁，但会持有 MDL 读锁，和 DDL 互斥。
6. DDL：`ALTER TABLE`、`DROP TABLE` 等需要 MDL 写锁，可能被长事务的查询阻塞。
7. 外键和唯一约束：为了保证约束正确性，插入或更新时也可能访问并锁定相关索引记录。

面试里可以补一句：InnoDB 的行锁实际加在索引项上，不走索引时会扫描大量记录并逐个加锁，表现上像“锁了很多行”，所以加锁范围和 SQL 执行计划强相关。

## 死锁如何产生、查看和解决

死锁是多个事务互相持有对方需要的锁，形成循环等待。InnoDB 会做死锁检测，发现后回滚其中一个事务并返回 `Deadlock found when trying to get lock`，业务侧要把它视为可重试的并发冲突。

典型场景：

```text
事务 A：UPDATE account SET balance = balance - 100 WHERE id = 1;
事务 B：UPDATE account SET balance = balance - 50  WHERE id = 2;

事务 A：UPDATE account SET balance = balance + 100 WHERE id = 2; -- 等 B
事务 B：UPDATE account SET balance = balance + 50  WHERE id = 1; -- 等 A
```

两个事务锁资源的顺序相反，就会形成循环等待。类似地，非唯一索引范围更新、间隙锁、批量更新 ID 顺序不一致，也容易产生死锁。

排查手段：

1. `SHOW ENGINE INNODB STATUS\G`：查看 `LATEST DETECTED DEADLOCK`，包含等待锁、持有锁和相关 SQL。
2. `performance_schema.data_locks` / `data_lock_waits`：查看当前锁和等待关系。
3. 慢 SQL、应用日志、trace id：还原同一时间窗口内的事务顺序。

解决思路：

1. 统一访问顺序，例如批量更新前按主键排序。
2. 缩短事务，事务里不要做 RPC、文件 I/O、复杂计算和用户交互。
3. 让条件命中合适索引，减少范围锁和扫描锁。
4. 高冲突热点改成条件更新、队列化、分片计数或乐观锁。
5. 应用层捕获死锁错误，做有限次数、带随机退避的重试。

## 隔离性如何保证

1. **读已提交 RC**：每次一致性读生成新的 Read View，能看到其他事务已提交的新版本。
2. **可重复读 RR**：事务内第一次一致性读生成 Read View，后续复用，保证普通快照读可重复。
3. **当前读**：`UPDATE`、`DELETE`、`SELECT ... FOR UPDATE` 读取最新已提交并加锁，不能只靠 MVCC。
4. **幻读控制**：InnoDB RR 下，快照读靠 MVCC；范围当前读靠 Next-Key Lock / Gap Lock 阻止插入。

## SELECT ... FOR UPDATE 怎么用

`SELECT ... FOR UPDATE` 是当前读，会读取最新已提交版本，并对命中的索引记录加排他锁。它常用于“先查状态，再基于状态修改”的场景，例如余额扣减、订单抢占、任务领取。

典型写法：

```sql
START TRANSACTION;

SELECT balance
FROM account
WHERE id = 1
FOR UPDATE;

UPDATE account
SET balance = balance - 100
WHERE id = 1
  AND balance >= 100;

COMMIT;
```

使用要点：

1. 必须在事务中使用，事务提交或回滚时释放锁。
2. 条件要命中索引，最好是主键或唯一索引；如果不走索引，可能扫描并锁住大量记录。
3. RR 下范围 `FOR UPDATE` 可能加 Next-Key Lock，阻止其他事务往范围内插入记录。
4. RC 下间隙锁使用更少，并发更高，但范围约束更依赖唯一键、条件更新或业务校验。
5. 锁等待和死锁是正常并发现象，业务代码要处理超时、死锁重试和幂等。

如果只是扣库存，很多时候一条条件更新更简单：

```sql
UPDATE sku_stock
SET stock = stock - 1
WHERE sku_id = 10001
  AND stock > 0;
```

根据影响行数判断是否扣减成功。这样避免“先查再改”之间的业务逻辑过长，也缩短持锁时间。

## 什么是乐观锁

乐观锁不是真的数据库锁，而是一种并发控制思想：先假设冲突少，不在读取时阻塞别人，提交更新时再检查数据是否被改过。

常见实现是在表里加版本号：

```sql
CREATE TABLE account (
  id BIGINT PRIMARY KEY,
  balance DECIMAL(18,2) NOT NULL,
  version BIGINT NOT NULL DEFAULT 0
) ENGINE=InnoDB;
```

更新时带上旧版本：

```sql
UPDATE account
SET balance = balance - 100,
    version = version + 1
WHERE id = 1
  AND version = 7
  AND balance >= 100;
```

如果影响行数是 1，说明更新成功；如果是 0，说明版本不匹配或余额不足，需要重新读取、重试或返回失败。

## 乐观锁设计要点

1. version 字段随每次业务更新递增。
2. 更新 SQL 必须把旧 version 放在 `WHERE` 条件里。
3. 通过 affected rows 判断是否成功。
4. 高冲突场景要限制重试次数，并加退避，避免活锁。
5. 乐观锁适合读多写少、冲突概率低；热点库存、秒杀扣减等高冲突场景更适合条件更新、行锁、队列化或 Redis 原子脚本。

## 易错点

1. 只在应用内比较 version，不放进 SQL 条件，不能防并发写。
2. version 字段本身也要在同一条 SQL 中递增，避免读改写拆成多个无保护步骤。
3. 乐观锁失败不等于系统错误，通常是并发冲突或业务条件不满足。
4. MySQL 行锁是加在索引上的，条件不走索引可能扩大锁范围甚至退化成大量扫描。

## 面试回答模板

InnoDB 的隔离性主要靠 MVCC 和锁。普通一致性读用 Read View 读历史版本，减少读写阻塞；当前读和写操作要加锁，包括记录锁、间隙锁和 Next-Key Lock。乐观锁是一种提交时校验的并发控制方式，常用 version 字段实现：更新时 `WHERE id = ? AND version = ?`，同时 `version = version + 1`，根据影响行数判断成功。它适合冲突较少的场景，高冲突热点要谨慎重试或改用行锁、队列化、原子扣减。
