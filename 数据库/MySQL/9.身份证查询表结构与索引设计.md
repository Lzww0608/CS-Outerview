# 9. 身份证查询表结构与索引设计

## 1. 场景理解

如果 MySQL 存储全国人民的社保缴费信息，并要求输入身份证号快速查询，核心不是简单建一个大表，而是要拆清楚：

1. 身份信息是相对稳定的维表。
2. 缴费记录是持续增长的事实表。
3. 身份证号是高敏感字段，需要考虑加密、脱敏和审计。
4. 查询入口是身份证号，但明细查询通常还会带时间范围、地区、险种等条件。

## 2. 身份证号用 string 还是 int

身份证号应该用字符串类型，不应该用整数类型。

原因：

1. 身份证号不是用于数学计算的数字，而是业务标识。
2. 18 位身份证号可能包含校验位 `X`。
3. 身份证号可能有前导 0，用整数会丢失格式信息。
4. 18 位数字可能超过很多语言和数据库整数类型的安全表示范围。
5. 使用数值比较会引入隐式类型转换，可能导致索引失效。

在 MySQL 中可以使用：

```sql
id_card CHAR(18) CHARACTER SET ascii COLLATE ascii_bin NOT NULL
```

`CHAR(18)` 适合固定长度身份证号；`ascii_bin` 可以避免大小写、字符集和排序规则带来的额外比较成本。写入前在应用层统一去空格、转大写、校验格式。

## 3. 推荐表结构

一种更合理的设计是把身份索引表和缴费明细表拆开。

身份表：

```sql
CREATE TABLE person_identity (
    person_id BIGINT NOT NULL,
    id_card_hash BINARY(32) NOT NULL COMMENT 'HMAC-SHA256(id_card)，用于等值检索',
    id_card_cipher VARBINARY(128) NOT NULL COMMENT '身份证号密文，用于必要时解密核验',
    name_cipher VARBINARY(128) NULL,
    created_at DATETIME NOT NULL,
    updated_at DATETIME NOT NULL,
    PRIMARY KEY (person_id),
    UNIQUE KEY uk_id_card_hash (id_card_hash)
) ENGINE=InnoDB;
```

缴费明细表：

```sql
CREATE TABLE social_security_payment (
    person_id BIGINT NOT NULL,
    pay_year SMALLINT NOT NULL,
    pay_month TINYINT NOT NULL,
    region_code CHAR(6) NOT NULL,
    insurance_type TINYINT NOT NULL,
    amount DECIMAL(12, 2) NOT NULL,
    pay_status TINYINT NOT NULL,
    paid_at DATETIME NULL,
    created_at DATETIME NOT NULL,
    PRIMARY KEY (person_id, pay_year, pay_month, insurance_type),
    KEY idx_region_year (region_code, pay_year, pay_month),
    KEY idx_paid_at (paid_at)
) ENGINE=InnoDB;
```

查询流程：

1. 应用层对输入身份证号做规范化和格式校验。
2. 计算 `HMAC-SHA256(id_card)`。
3. 查询 `person_identity.uk_id_card_hash` 得到 `person_id`。
4. 用 `person_id` 查询缴费明细表，必要时带上年份、月份、地区等条件。

这样可以避免在每条缴费明细里重复保存身份证号，也能让明细表主键更短。

## 4. 全国规模下的分库分表

全国社保缴费记录量很大，单表长期承载所有明细会带来索引膨胀、备份恢复慢、DDL 风险高等问题。

常见拆分策略：

1. **身份表按身份证 hash 或 person_id hash 分库分表**：输入身份证号后可以直接路由到唯一分片。
2. **缴费表按 person_id hash 分库分表**：同一个人的缴费记录落在同一分片，个人查询不跨库。
3. **大明细按年份分区或冷热分离**：近几年热数据保留在在线库，历史数据归档到低成本存储或 OLAP。
4. **地区字段建辅助索引**：地区维度常用于统计和管理，但个人点查不建议只按地区路由，因为人员可能跨地区流动。

如果查询模式是“身份证号查个人全部缴费记录”，最关键的是让身份证号到分片的路由稳定且唯一，避免广播查询。

## 5. 索引长度的影响

索引字段越长，影响越明显：

1. 单个 B+ 树页能容纳的索引项更少，树的扇出降低，树高可能增加。
2. 二级索引叶子节点会保存主键，主键越长，所有二级索引都会变大。
3. 索引占用更多 Buffer Pool，缓存命中率下降。
4. 字符串比较比整数比较更贵，尤其在复杂字符集和排序规则下。
5. 写入、更新、页分裂和 redo/binlog 体积都会增加。

但身份证号只有 18 位，完整索引长度是可以接受的。不要为了省空间盲目使用身份证前缀索引，例如 `id_card(6)` 区分度很差，也不能唯一定位一个人。真实系统更常见的是使用固定长度 hash 做检索索引，同时密文保存原始身份证号用于合规核验。

## 6. 索引失效和隐式类型转换

如果身份证号字段是字符串，但 SQL 写成数字比较：

```sql
SELECT *
FROM person_identity_plain
WHERE id_card = 110101199001011234;
```

MySQL 可能把字符串列转换成数字再比较，相当于对索引列做函数转换，B+ 树的有序性无法直接用于定位，可能导致全表扫描或全索引扫描。

正确方式是使用字符串参数：

```sql
SELECT *
FROM person_identity_plain
WHERE id_card = '110101199001011234';
```

在代码中也要确保绑定参数类型是字符串，而不是整数。

## 7. 易错点

1. 身份证号不要用 `INT`、`BIGINT`，也不要在代码里用浮点数承接。
2. 前缀索引适合长文本的辅助过滤，不适合身份证号这种强唯一等值查询。
3. 如果使用加密字段，普通随机加密无法直接等值检索，需要额外保存 HMAC/hash 检索列。
4. hash 检索列虽然碰撞概率极低，但高安全系统仍应在取出候选记录后做密文解密核验。
5. 社保数据属于高敏感数据，除了索引性能，还要考虑字段加密、最小权限、访问审计、脱敏展示和密钥轮换。

## 8. 面试回答模板

身份证号应该用字符串，不应该用整数。表设计上我会拆成身份索引表和缴费明细表：身份表用 `id_card_hash` 建唯一索引，保存身份证密文和 `person_id`；缴费表用 `person_id` 作为主查询键，主键可以设计为 `(person_id, pay_year, pay_month, insurance_type)`。全国规模下按身份证 hash 或 `person_id` hash 分库分表，个人查询可以直接路由到单分片；明细再按年份做分区或冷热归档。索引长度会影响 B+ 树扇出、Buffer Pool 命中率和二级索引大小，但 18 位身份证完整索引本身不长，真正要避免的是隐式类型转换、前缀索引误用和敏感数据明文裸存。
