# 31. 用户签到表设计与索引优化

签到是典型的"高频写入、按维度查询"业务。面试题：用户表 + 签到表结构，按月查单人签到记录，索引应该怎么设计。背后考的是表结构设计、索引选择、覆盖索引、热点写入和大表治理。

## 1. 业务需求拆解

签到业务通常包括几类查询：

1. **写**：用户每天签到 1 次，幂等，重复签到不报错也不重复计数。
2. **按月查单人**：查某用户某月所有签到日期，渲染日历视图。
3. **判断今日是否签到**：登录或进入页面时查询当天是否签到。
4. **连续签到天数**：连续 N 天签到送奖励。
5. **累计签到次数**：用户中心展示总签到天数。
6. **聚合统计**（可选）：某天总签到人数、月活、签到 TOP 榜。

不同查询模式对索引和存储结构要求不同，纯关系表方案要权衡。

## 2. 表结构设计

### 2.1 基础设计

```sql
CREATE TABLE user_checkin (
    id          BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    user_id     BIGINT UNSIGNED NOT NULL,
    checkin_date DATE NOT NULL,
    created_at  DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    UNIQUE KEY uk_user_date (user_id, checkin_date),
    KEY idx_date (checkin_date)
) ENGINE=InnoDB;
```

关键设计：

1. **`checkin_date` 用 DATE 类型**：只存日期不存时分秒，方便按日去重和范围查询。
2. **`uk_user_date(user_id, checkin_date)` 唯一索引**：天然防止重复签到，写入时 `INSERT IGNORE` 即可幂等。
3. **`idx_date` 辅助索引**：支持按天统计签到人数。

### 2.2 为什么不存时间戳

如果存 `DATETIME`，同一天可能存在多条记录（不同时刻），需要业务代码截断到日，麻烦且易错。直接用 `DATE` 让数据库帮你保证天粒度唯一。

## 3. 索引设计

### 3.1 按月查单人签到

```sql
SELECT checkin_date
FROM user_checkin
WHERE user_id = ?
  AND checkin_date >= '2026-06-01'
  AND checkin_date <  '2026-07-01';
```

最优索引是 `(user_id, checkin_date)`：

1. 等值条件 `user_id` 走索引前缀。
2. 范围条件 `checkin_date` 走索引后续列。
3. SELECT 只查 `checkin_date`，索引已包含，**覆盖索引**，无需回表。

执行计划应该是 `type=range, key=uk_user_date, Extra=Using index`。

### 3.2 为什么不是 `(checkin_date, user_id)`

如果顺序反过来：

```sql
KEY idx_date_user (checkin_date, user_id)
```

按月查单人会变成：

1. `checkin_date` 范围扫描，覆盖整月所有用户的签到记录。
2. 在范围扫描结果中过滤 `user_id`。

扫描行数远大于必要，且无法利用索引的最左前缀做等值跳跃。

记住索引顺序原则：**等值列在前，范围列在后**。

### 3.3 判断今日是否签到

```sql
SELECT 1 FROM user_checkin
WHERE user_id = ? AND checkin_date = CURDATE()
LIMIT 1;
```

`uk_user_date(user_id, checkin_date)` 直接命中等值查询，索引唯一定位，O(log n)。

### 3.4 连续签到天数

纯 SQL 计算连续签到比较绕，常用窗口函数：

```sql
SELECT user_id, checkin_date,
       DATEDIFF(checkin_date, '1970-01-01') 
         - ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY checkin_date) AS grp
FROM user_checkin
WHERE user_id = ?
ORDER BY checkin_date DESC;
```

按 `grp` 分组，相同 `grp` 是连续签到段。但生产环境通常不在 SQL 算，而是用 Redis Bitmap 或单独维护 `continuous_days` 字段：

```sql
CREATE TABLE user_checkin_stat (
    user_id          BIGINT UNSIGNED PRIMARY KEY,
    total_days       INT UNSIGNED NOT NULL DEFAULT 0,
    continuous_days  INT UNSIGNED NOT NULL DEFAULT 0,
    last_checkin_date DATE,
    updated_at       DATETIME NOT NULL
);
```

签到成功后判断 `last_checkin_date == today - 1` 决定连续天数 +1 还是重置。

## 4. 写入幂等

### 4.1 INSERT IGNORE

```sql
INSERT IGNORE INTO user_checkin (user_id, checkin_date)
VALUES (?, CURDATE());
```

利用唯一索引拦截重复。返回受影响行数：1 表示首次签到，0 表示今天已经签过。

### 4.2 ON DUPLICATE KEY UPDATE

如果需要在已签到时更新某些字段（例如签到来源）：

```sql
INSERT INTO user_checkin (user_id, checkin_date, source)
VALUES (?, CURDATE(), ?)
ON DUPLICATE KEY UPDATE source = VALUES(source);
```

注意：`ON DUPLICATE KEY` 在主从复制和自增主键场景有副作用（自增 ID 跳号、binlog 模式敏感），高并发场景优先用 `INSERT IGNORE`。

## 5. 高并发挑战

### 5.1 唯一索引锁竞争

热门活动期间，大量用户同时签到。`uk_user_date` 写入会涉及插入意向锁（Insert Intention Lock）和间隙锁（在 RR 隔离级别）。不同 `user_id` 写入不冲突，因此实际锁争用主要发生在**同一用户重复提交**。

防止用户疯狂点击的关键：

1. 前端按钮防抖。
2. 后端用 Redis 分布式锁限制同一用户每秒只能尝试 1 次。
3. 数据库唯一索引兜底。

### 5.2 写入热点

当 `user_id` 自增，且签到时间集中（如每天 0 点），插入位置集中在 B+ 树同一页，可能造成页分裂和热点。解决：

1. `user_id` 通常不连续（不同用户分散），实际热点不严重。
2. 如果用户量极大，可以分表（按 `user_id % N`）。

### 5.3 大表治理

签到表数据量增长极快。1000 万用户每天签到，每天新增 1000 万行。一年 36 亿行。

治理方案：

1. **按月分表**：`user_checkin_202606`，按时间归档。历史月份表只读，主表写入只在当月表。
2. **按 user_id 分库分表**：`user_checkin_${user_id % 64}`。
3. **冷热分离**：超过 N 个月的数据归档到 OLAP 或对象存储。
4. **改用 Bitmap**：把每日签到当成 1 个 bit，按 `user_id` 维度存 `user:1001:checkin:202606`，30 天只需 30 bit。MySQL 也可以用 `BIT(31)` 或 `BIGINT`（位运算）存某月签到位图。

## 6. Bitmap 方案对比

如果业务规模大且查询模式集中在"按月查签到位图"，可以直接在 MySQL 里用整数位图：

```sql
CREATE TABLE user_checkin_bitmap (
    user_id     BIGINT UNSIGNED NOT NULL,
    year_month  CHAR(6) NOT NULL,    -- '202606'
    bitmap      INT UNSIGNED NOT NULL DEFAULT 0,   -- 31 位足够一个月
    PRIMARY KEY (user_id, year_month)
) ENGINE=InnoDB;
```

签到：

```sql
UPDATE user_checkin_bitmap
SET bitmap = bitmap | (1 << (DAY(CURDATE()) - 1))
WHERE user_id = ? AND year_month = DATE_FORMAT(CURDATE(), '%Y%m');
```

按月查：直接 `SELECT bitmap`，业务代码解析每一位。

优点：

1. 一行存一个月，行数从天粒度变月粒度，体积缩小 30 倍。
2. 无需 `INSERT IGNORE`，UPDATE 天然幂等。
3. 月签到位图天然支持快速判断"是否签到""签到次数 popcount""连续签到段"。

缺点：

1. 不便记录每次签到的额外字段（来源、IP）。
2. 跨月查询要拼接多行 bitmap。

生产环境常组合：明细表 + 月度位图汇总表。

## 7. 真实场景索引检查清单

设计完表后用 EXPLAIN 验证：

1. 按月查单人是否走 `uk_user_date`，`type=range`，`Extra=Using index`。
2. 判断今日签到是否走唯一索引，`type=const` 或 `ref`。
3. 按天统计签到人数是否走 `idx_date`。
4. 大查询是否扫描行数过多，必要时增加覆盖列。

## 8. 易错点

1. `checkin_date` 用 `DATETIME` 导致同天多记录，需要额外去重。
2. 索引顺序写反成 `(checkin_date, user_id)`，按月查单人无法用索引前缀。
3. 没有唯一索引，靠业务代码判断，高并发下出现重复签到。
4. 连续签到天数实时计算，每次查询全表扫描，应该单独维护统计字段。
5. 大表不分表不归档，几年后磁盘和查询性能都崩。
6. 用 Redis 计数但不持久化，Redis 故障后丢失签到记录。

## 9. 总结

用户签到表设计核心是：用 `(user_id, checkin_date)` 作为唯一索引，既保证天粒度幂等又支持按月查单人的覆盖索引扫描；判断今日签到走等值查询；连续签到独立维护统计字段，不在主表实时算。大规模场景下用按月分表或按 `user_id` 分表减小单表体积，或者引入位图把月度数据压缩到一行。Bitmap 方案适合极致存储优化但牺牲明细信息。索引顺序遵守"等值在前、范围在后"，所有查询用 EXPLAIN 验证执行计划。
