# 19. 商品购买表与库存表设计

场景：有 `n` 个商品，每个商品有若干库存，用户可以购买每种商品的一个。核心问题是表结构要能表达商品、库存、订单和“每个用户每种商品最多买一个”的约束，并且在并发下避免超卖和重复购买。

## 核心表设计

### 商品表

```sql
CREATE TABLE product (
    id BIGINT PRIMARY KEY,
    name VARCHAR(128) NOT NULL,
    status TINYINT NOT NULL,
    created_at DATETIME NOT NULL,
    updated_at DATETIME NOT NULL
);
```

### 库存表

```sql
CREATE TABLE product_inventory (
    product_id BIGINT PRIMARY KEY,
    stock INT NOT NULL,
    sold INT NOT NULL DEFAULT 0,
    updated_at DATETIME NOT NULL,
    CONSTRAINT chk_stock_non_negative CHECK (stock >= 0)
);
```

库存表可以和商品表拆开，原因是库存更新频率通常高于商品基础信息，拆表后可以减少行宽、降低热点字段更新对商品信息的影响。

### 订单表

```sql
CREATE TABLE purchase_order (
    id BIGINT PRIMARY KEY,
    user_id BIGINT NOT NULL,
    status TINYINT NOT NULL,
    amount DECIMAL(10, 2) NOT NULL DEFAULT 0,
    idempotency_key VARCHAR(64) NOT NULL,
    created_at DATETIME NOT NULL,
    updated_at DATETIME NOT NULL,
    UNIQUE KEY uk_user_idem (user_id, idempotency_key),
    KEY idx_user_created (user_id, created_at)
);
```

### 订单明细表

```sql
CREATE TABLE purchase_order_item (
    id BIGINT PRIMARY KEY,
    order_id BIGINT NOT NULL,
    user_id BIGINT NOT NULL,
    product_id BIGINT NOT NULL,
    quantity INT NOT NULL,
    created_at DATETIME NOT NULL,
    UNIQUE KEY uk_user_product (user_id, product_id),
    UNIQUE KEY uk_order_product (order_id, product_id),
    KEY idx_order_id (order_id),
    KEY idx_product_id (product_id)
);
```

`uk_user_product(user_id, product_id)` 用来保证“每个用户每种商品最多购买一个”。如果业务允许取消后再次购买，可以改成在购买资格表中维护状态，或把唯一约束设计为 `(user_id, product_id, active_flag)` 并用条件更新控制。

## 下单流程

单库事务内的基本流程：

```text
校验商品状态
-> 插入订单主表，利用 idempotency_key 防止重复提交
-> 对每个商品扣库存
-> 插入订单明细，利用唯一约束防止重复购买
-> 提交事务
```

扣库存推荐使用条件更新：

```sql
UPDATE product_inventory
SET stock = stock - 1,
    sold = sold + 1,
    updated_at = NOW()
WHERE product_id = ?
  AND stock > 0;
```

如果影响行数为 0，说明库存不足或商品不存在，需要回滚事务。不要先 `SELECT stock` 再无条件 `UPDATE`，并发下容易超卖。

## 并发控制

常见方案：

1. **数据库条件更新**：`stock > 0` 作为扣减条件，依赖行锁和原子更新避免超卖。
2. **唯一约束防重**：用 `(user_id, product_id)` 阻止同一用户重复购买同一商品。
3. **幂等键**：客户端重试时携带同一个 `idempotency_key`，避免重复创建订单。
4. **短事务**：事务内只做必要的库存和订单写入，不调用外部 RPC。
5. **热点商品优化**：秒杀类场景可用 Redis 预扣库存、队列削峰，再异步落库，但最终仍要有数据库约束兜底。

## 库存扣减时锁的时机

库存链路里要区分 Redis 分布式锁、数据库行锁和乐观锁条件，它们解决的问题不同。

典型流程：

```text
校验请求和幂等键
-> 获取细粒度锁（可选，例如 lock:sku:{skuId}:user:{userId}）
-> 开启数据库事务
-> 条件扣减库存或 SELECT ... FOR UPDATE 后更新
-> 插入订单和订单明细
-> 提交事务，数据库行锁释放
-> finally 释放分布式锁
```

关键点：

1. **加锁时机**：如果使用分布式锁，应在进入共享资源临界区前获取，例如同一用户同一商品防重复提交、缓存重建互斥或低频资源互斥。
2. **释放时机**：业务状态已经持久化后再释放锁，代码上放在 `finally` 中；数据库行锁会在事务提交或回滚时释放。
3. **锁粒度要小**：不要用全局 `lock:stock` 串行化所有商品，应该按活动、商品、SKU、用户等维度拆分，例如 `lock:seckill:{activityId}:{skuId}`。
4. **不要持锁做慢操作**：外部 RPC、支付、发消息、远程库存查询不要放在锁内或数据库事务内，否则会放大锁等待和死锁概率。
5. **数据库仍要兜底**：Redis 锁可能过期、误释放、主从切换或客户端暂停，最终防超卖仍要靠数据库条件更新、唯一约束和事务。

为什么还要乐观锁或条件更新：

```sql
UPDATE product_inventory
SET stock = stock - 1,
    sold = sold + 1,
    version = version + 1
WHERE product_id = ?
  AND stock > 0
  AND version = ?;
```

`stock > 0` 防止库存扣成负数，`version = ?` 防止并发覆盖同一行状态。即使上层已经有 Redis 预扣或分布式锁，数据库层也要做最后一道一致性防线，因为上层锁属于性能优化和流量治理，不应该成为唯一正确性来源。

## 多商品一次购买

如果一次订单里包含多个商品，要注意固定加锁顺序。可以按 `product_id` 排序后依次扣库存，避免不同请求按不同顺序锁多行造成死锁。

```text
请求 A: 商品 1 -> 商品 2
请求 B: 商品 2 -> 商品 1
```

这种交错容易形成等待环。统一按商品 ID 升序处理，可以显著降低死锁概率。

## 易错点

1. 只在业务代码里判断“买过没有”不可靠，必须用唯一约束兜底。
2. `SELECT` 后再 `UPDATE` 不是原子操作，库存扣减要用条件更新或显式锁。
3. 订单状态要有状态机，例如 `INIT -> WAIT_PAY -> PAID -> CANCELLED/FINISHED`。
4. 库存扣减、订单明细插入、用户购买限制要放在同一事务或有补偿机制。
5. 大促热点商品会形成单行热点，需要缓存预扣、分桶库存或排队削峰。

## 面试回答模板

我会拆成商品表、库存表、订单表和订单明细表。库存扣减用 `UPDATE inventory SET stock = stock - 1 WHERE product_id = ? AND stock > 0` 保证原子性；订单明细加 `(user_id, product_id)` 唯一约束保证每个用户每种商品只能买一个；订单主表加幂等键防止重试重复下单。多商品购买时按商品 ID 固定顺序扣库存，减少死锁。热点场景可以用 Redis 预扣和消息队列削峰，但数据库事务和唯一约束仍是最终兜底。
