# 数据库快照隔离与版本冲突检测

## 一、问题背景

数据库快照是 MVCC（多版本并发控制）的核心机制。当多个事务并发执行时，每个事务都会看到一个数据库的"快照"——某个时间点的数据视图。关键问题是：**如何保证多个快照之间不冲突，同时又允许并发读写？**

---

## 二、快照隔离的基本原理

### 2.1 什么是快照

快照是事务在某个时间点看到的数据状态。在 MVCC 中：

```text
时间线 ──────────────────────────────────────────────────────►

事务 T1: ───────────┬──────────────►
                     │              ↑
                     │              │
                     │          T1 提交
                     │         写入新版本
                     ▼
                 快照A（可见）

事务 T2: ───────────────────┬────────────────────►
                           │                    ↑
                           │                    │
                           │                T2 提交
                           ▼
                       快照B（可见）
```

- **快照 A**：T1 启动时看到的数据状态
- **快照 B**：T2 启动时看到的数据状态
- 两个快照可以同时存在，互不干扰

### 2.2 快照的版本链

InnoDB 通过版本链管理多个数据版本：

```text
┌─────────────────────────────────────────────────────────────────┐
│                        版本链                                    │
│                                                                 │
│  ┌─────────┐     ┌─────────┐     ┌─────────┐                  │
│  │ Version 3│◄────│ Version 2│◄────│ Version 1│              │
│  │trx_id=30│     │trx_id=20│     │trx_id=10│                  │
│  │ roll_ptr│     │ roll_ptr│     │ roll_ptr│                  │
│  └────┬────┘     └────┬────┘     └────┬────┘                  │
│       │                │                │                        │
│       ▼                ▼                ▼                        │
│   数据版本3        数据版本2        数据版本1                   │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

每行数据通过 `roll_pointer` 指向 undo log 中的旧版本，形成版本链。读取时根据 Read View 找到可见版本。

## 三、Read View 与快照可见性

### 3.1 Read View 的组成

Read View 是快照的核心，包含判断可见性的关键信息：

```c
struct ReadView {
    trx_id_t creator_trx_id;    // 创建该快照的事务ID
    trx_id_t min_trx_id;         // 活跃事务列表中的最小ID
    trx_id_t max_trx_id;         // 下一次将要分配的事务ID
    std::vector<trx_id_t> m_ids; // 创建快照时活跃的事务ID列表
    bool closed;                  // 快照是否已关闭
};
```

### 3.2 可见性判断规则

```text
可见性判断流程：
                    
                    ┌──────────────────────────────┐
                    │   获取行的 trx_id           │
                    └──────────────┬───────────────┘
                                   │
                                   ▼
                    ┌──────────────────────────────┐
                    │   trx_id == creator_trx_id? │──Yes──► 可见（自己的修改）
                    └──────────────┬───────────────┘
                                   │ No
                                   ▼
                    ┌──────────────────────────────┐
                    │   trx_id < min_trx_id?      │──Yes──► 可见（已提交）
                    └──────────────┬───────────────┘
                                   │ No
                                   ▼
                    ┌──────────────────────────────┐
                    │   trx_id >= max_trx_id?      │──Yes──► 不可见（快照后产生）
                    └──────────────┬───────────────┘
                                   │ No
                                   ▼
                    ┌──────────────────────────────┐
                    │   trx_id in m_ids?           │──Yes──► 不可见（未提交）
                    └──────────────┬───────────────┘
                                   │ No
                                   ▼
                                可见（已提交）
```

### 3.3 快照不冲突的核心机制

**关键点**：每个事务看到的快照是**逻辑隔离**的，不是物理隔离数据副本。

1. **写不阻塞读**：其他事务写入的数据对自己不可见，所以读操作不需要等待
2. **读不阻塞写**：自己的修改对自己可见，不影响其他事务的快照
3. **版本链追溯**：通过 roll_pointer 找到事务开始时可见的版本

## 四、快照冲突检测机制

### 4.1 什么是快照冲突

快照冲突发生在**写写冲突**场景：当两个事务试图修改同一行数据时。

```text
事务 T1: BEGIN ──── SELECT(id=1) ──── UPDATE(id=1, val=2) ──── COMMIT
                                      ↑
                                      │
                              T2 也在这里修改 id=1 ──┘

时间:        t1         t2            t3              t4
```

如果 T1 和 T2 都修改同一行，这就是**写写冲突**。

### 4.2 First-Commit-Wins 策略

InnoDB 使用的是**基于锁的乐观并发控制**：

```text
T1: BEGIN ──── SELECT ──── UPDATE(id=1) ──┬─── COMMIT
                                         │
T2: BEGIN ──── SELECT ──── UPDATE(id=1) ──┘
                     │                      │
                     │                 T2 被阻塞！
                     │                      │
                     ▼                      ▼
              T1 的 UPDATE 先获取行锁
              T2 必须等待 T1 提交或回滚
```

**冲突检测流程**：
1. T2 执行 UPDATE，尝试获取行锁
2. T1 已持有该行锁，T2 被阻塞等待
3. T1 提交后，T2 获取锁，检查数据是否被修改
4. 如果数据已被修改，T2 的 UPDATE 影响 0 行，抛出异常或重试

### 4.3 MVCC + 行锁的配合

```c
// UPDATE 语句的简化执行流程
void execute_update(TABLE *table, uchar *record, uchar *new_value) {
    // 1. 读取当前可见版本（快照读）
    ReadView *view = get_read_view();
    uchar *old_value = find_visible_version(record, view);
    
    // 2. 检查行锁（当前读）
    lock_t *lock = lock_get_row_lock(table, record->id);
    if (lock_is_held_by_other_trx(lock)) {
        // 等待锁释放
        wait_for_lock(lock);
        // 重新读取最新版本
        old_value = get_latest_version(record);
    }
    
    // 3. 检查数据是否被修改（冲突检测）
    if (has_conflict(old_value, snapshot_value)) {
        throw CONFLICT_ERROR;  // 快照冲突
    }
    
    // 4. 写入新版本
    insert_new_version(record, new_value);
}
```

## 五、快照隔离级别

### 5.1 不同隔离级别下的快照

| 隔离级别 | 快照生成时机 | 快照稳定性 |
|----------|-------------|-----------|
| READ UNCOMMITTED | 无快照，直接读最新 | 无隔离 |
| READ COMMITTED | 每次 SELECT 生成新快照 | 不可重复读 |
| REPEATABLE READ | 事务第一次 SELECT 生成快照 | 可重复读 |
| SERIALIZABLE | 快照 + 锁 | 完全串行 |

### 5.2 RC vs RR 的区别

**READ COMMITTED（每次生成新快照）**：
```sql
-- T1 在时间 t1 启动
START TRANSACTION;
SELECT * FROM orders WHERE id = 1;  -- 快照A：value=100
                                        -- T2 在 t2 提交，value=200
SELECT * FROM orders WHERE id = 1;  -- 快照B：value=200（重新生成快照）
COMMIT;
```

**REPEATABLE READ（复用同一快照）**：
```sql
-- T1 在时间 t1 启动
START TRANSACTION;
SELECT * FROM orders WHERE id = 1;  -- 快照A：value=100
                                        -- T2 在 t2 提交，value=200
SELECT * FROM orders WHERE id = 1;  -- 快照A：value=100（复用同一快照）
COMMIT;
```

### 5.3 快照冲突与幻读

```text
幻读场景：

T1: BEGIN ──── SELECT WHERE id<10 ──── INSERT(id=5) ──── SELECT WHERE id<10
                                │                               ↑
                                │                               │
                            没有 id=5                     T1 自己看到了自己的插入
                                                        这就是"幻读"
```

InnoDB 通过 **Next-Key Lock** 解决 RR 级别下的幻读：
- 锁定 id<10 的所有间隙
- INSERT id=5 被阻塞，直到 T1 提交

## 六、快照与 Undo Log 清理

### 6.1 为什么需要清理旧版本

```text
快照版本过多的问题：

版本链过长：
┌─────┐   ┌─────┐   ┌─────┐   ┌─────┐   ┌─────┐
│ V5  │──►│ V4  │──►│ V3  │──►│ V2  │──►│ V1  │
└─────┘   └─────┘   └─────┘   └─────┘   └─────┘
长事务 T 持有快照，版本链不能被 purge
```

### 6.2 Purge 机制

```c
// InnoDB 的 Purge 协调进程
void purge_coordinator() {
    while (running) {
        // 1. 找到最老的快照（最老活跃事务的 start_trx_id）
        trx_id_t purge_trx_id = get_oldest_active_trx_id();
        
        // 2. 删除不再需要的旧版本
        for (table in InnoDB) {
            for (record in table) {
                while (record.has_old_version(purge_trx_id)) {
                    purge_old_version(record);  // 物理删除 undo log
                }
            }
        }
        
        // 3. 等待一段时间
        sleep(PURGE_INTERVAL);
    }
}
```

### 6.3 快照与长事务

```sql
-- 长事务阻止旧版本清理
START TRANSACTION;
SELECT * FROM orders;  -- 事务开始，快照生成
-- ... 长时间不操作 ...
COMMIT;  -- 事务结束，快照释放，旧版本可以被 purge
```

**最佳实践**：
- 避免长事务
- 使用 `SHOW PROCESSLIST` 监控长时间运行的事务
- 定期提交事务，不要在一个事务中做太多操作

## 七、多版本快照的实际应用

### 7.1 一致性读

```sql
-- 在时间点 t1 执行备份
mysqldump --single-transaction -A > backup_t1.sql

-- 备份期间其他事务正常写入
-- 备份看到的是 t1 时刻的快照，不受影响
```

`--single-transaction` 使用 MVCC 快照，保证备份数据一致性。

### 7.2 读写分离中的延迟问题

```text
主库写入 ──► 从库复制 ──► 从库可见

如果从库延迟较大，读到的数据可能是"过去"的数据
这是快照在分布式场景下的局限性
```

### 7.3 Flashback 查询

```sql
-- MySQL 8.0 支持 AS OF 语法（部分版本）
SELECT * FROM orders AS OF TIMESTAMP '2024-01-01 10:00:00';
```

类似 PostgreSQL 的 `AS OF`，可以查询历史快照数据。

## 八、面试常见问题

### Q1: 快照隔离是如何保证不冲突的？

核心是**版本链 + Read View + 行锁**的配合：

1. 每个事务根据 Read View 读取可见的数据版本
2. 不同事务可能看到不同版本，但都是该事务开始时的合法数据
3. 写操作通过行锁互斥，后写的事务会发现数据已被修改，触发冲突处理

### Q2: MVCC 能完全避免幻读吗？

不能。MVCC 主要优化快照读（普通 SELECT），当前读（UPDATE/DELETE）仍需要锁。

InnoDB 在 RR 级别下使用 **Next-Key Lock** 锁定间隙，防止其他事务在当前读的事务执行期间插入新行，从而解决幻读。

### Q3: 快照冲突和写写冲突的区别？

| 类型 | 发生场景 | 处理机制 |
|------|----------|----------|
| 快照冲突 | 乐观并发控制，两事务修改同一行 | 后提交的事务发现数据变化，UPDATE 影响 0 行 |
| 写写冲突 | 两个事务同时写同一行 | 行锁互斥，先获取锁的事务先执行 |

### Q4: 为什么长事务会影响性能？

1. **undo log 膨胀**：旧版本不能被 purge，存储空间持续增长
2. **版本链变长**：读取时需要遍历更多版本，性能下降
3. **锁持有时间长**：长事务持有的锁会阻塞其他事务

### Q5: Read View 什么时候生成和释放？

| 隔离级别 | Read View 生成时机 | Read View 释放时机 |
|----------|-------------------|-------------------|
| READ COMMITTED | 每次 SELECT | SELECT 结束后 |
| REPEATABLE READ | 事务第一次 SELECT | 事务提交/回滚 |
| SERIALIZABLE | 每次 SELECT + 隐式锁定 | SELECT 结束后 |

## 九、总结

### 快照不冲突的核心机制

1. **多版本链**：每行数据维护多个版本，通过 roll_pointer 连接
2. **Read View**：事务启动时生成快照，决定哪些版本可见
3. **可见性判断**：基于事务 ID 和活跃事务列表判断
4. **行锁配合**：写操作通过锁互斥，冲突时后者失败
5. **Purge 清理**：定期清理不再需要的旧版本

### 快照隔离的优势

- 读写不互斥，提高并发度
- 事务看到的数据是某个时间点的稳定状态
- 支持一致性备份和 Flashback 查询

### 快照隔离的局限

- 不能完全避免幻读（需要 Gap Lock 配合）
- 长事务导致 undo log 膨胀
- 分布式场景下快照一致性受限于复制延迟
