# 数据库三范式

数据库三范式是关系型数据库表结构设计的基本规范，目标是减少数据冗余、避免更新异常，并让数据依赖关系更清晰。面试里不要只背“第一范式、第二范式、第三范式”，要能说明它们分别解决什么问题。

## 1. 第一范式 1NF

第一范式要求字段具有原子性，也就是每一列都不可再拆分成多个重复值或集合。

错误例子：

| user_id | phones |
| --- | --- |
| 1 | 13800000000,13900000000 |

问题是电话无法方便地查询、去重和建立索引。更合理的做法是拆成用户表和用户电话表：

```text
user(id, name)
user_phone(user_id, phone)
```

注意：原子性和业务有关。如果系统永远只把地址当成完整字符串展示，地址字段可以是一个字段；如果需要按省市区查询，就应该拆分。

## 2. 第二范式 2NF

第二范式要求在满足 1NF 的基础上，非主属性必须完全依赖整个候选键，不能只依赖联合主键的一部分。

典型问题出现在联合主键表：

```text
order_item(order_id, product_id, product_name, product_price, count)
主键：(order_id, product_id)
```

其中 `product_name`、`product_price` 只依赖 `product_id`，不依赖完整的 `(order_id, product_id)`，这就是部分依赖。问题是商品名称改动时需要更新很多订单明细，容易产生不一致。

更合理的拆分：

```text
product(product_id, product_name, product_price)
order_item(order_id, product_id, count)
```

真实订单系统还要注意：订单里的商品成交价通常不能直接依赖商品当前价格，因为历史订单需要保留当时的快照价。因此可以在 `order_item` 中保留 `deal_price`，这是业务需要的冗余，不是简单违反范式。

## 3. 第三范式 3NF

第三范式要求在满足 2NF 的基础上，非主属性不能传递依赖于主键。也就是说，非主属性之间不应该存在“由 A 推出 B”的依赖关系。

错误例子：

```text
student(student_id, student_name, dept_id, dept_name)
```

主键是 `student_id`，但 `dept_name` 依赖 `dept_id`，`dept_id` 又依赖 `student_id`，形成：

```text
student_id -> dept_id -> dept_name
```

更合理的拆分：

```text
student(student_id, student_name, dept_id)
department(dept_id, dept_name)
```

这样部门名称只维护一份，修改部门名称时不会出现多行不一致。

## 4. 范式和反范式

范式强调一致性和低冗余，但工程里不是越规范越好。高并发读场景经常会做适度反范式，把常用冗余字段放在主表或宽表中，减少 join 和跨库查询。

常见反范式场景：

1. 订单表冗余用户昵称、商品标题、成交价，保证历史快照。
2. 内容列表冗余作者名、点赞数、评论数，减少列表页多表查询。
3. 数据仓库宽表把维度字段展开，提升分析查询效率。
4. 分库分表后避免跨分片 join，必要时冗余查询字段。

反范式的代价是写入和更新复杂度上升，所以要配套一致性策略：同步更新、异步事件、补偿任务、定期校验或以某个数据源为准重建。

## 5. 数据库设计流程

面试里问“数据库设计”时，可以按业务和查询链路展开，而不是只说建几张表。

一般流程：

1. **识别实体和关系**：用户、订单、商品、库存、支付、关注关系等分别是什么实体，关系是一对一、一对多还是多对多。
2. **确定主键**：主键要稳定、短、唯一，InnoDB 中还会影响聚簇索引和所有二级索引大小。
3. **设计字段和约束**：字段类型、长度、是否允许 NULL、默认值、唯一约束、外键或应用层约束。
4. **围绕查询建索引**：根据高频 SQL 设计联合索引、覆盖索引和唯一索引，而不是每个字段都建索引。
5. **考虑数据增长**：预估行数、写入量、冷热数据、归档、分区、分库分表。
6. **考虑一致性边界**：哪些操作必须强一致，哪些可以异步最终一致。
7. **考虑反范式**：列表页、历史快照、跨库查询可以适度冗余，但要设计同步和补偿。
8. **验证和演进**：用真实 SQL、`EXPLAIN`、压测和数据量增长模型验证设计。

例如订单系统通常会把订单主表、订单明细、支付单、库存流水拆开；订单明细中保留商品名称和成交价快照，这是为了历史正确性而有意反范式。

### 5.1 书籍、作者和作者别名表设计

书籍管理系统里“一本书可能有多个作者，一个作者可能有多个名字”，核心是两个关系：

1. 书籍和作者是多对多关系，需要中间表。
2. 作者和名字是一对多关系，其中一个名字可以标记为主展示名。

一种规范设计：

```sql
CREATE TABLE book (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    isbn VARCHAR(32) UNIQUE,
    title VARCHAR(255) NOT NULL,
    publisher VARCHAR(255),
    published_at DATE,
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
);

CREATE TABLE author (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    canonical_name VARCHAR(255) NOT NULL,
    birth_date DATE NULL,
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
);

CREATE TABLE author_name (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    author_id BIGINT NOT NULL,
    name VARCHAR(255) NOT NULL,
    name_type VARCHAR(32) NOT NULL DEFAULT 'alias',
    is_primary TINYINT NOT NULL DEFAULT 0,
    UNIQUE KEY uk_author_name (author_id, name),
    KEY idx_name (name),
    CONSTRAINT fk_author_name_author
        FOREIGN KEY (author_id) REFERENCES author(id)
);

CREATE TABLE book_author (
    book_id BIGINT NOT NULL,
    author_id BIGINT NOT NULL,
    author_order INT NOT NULL DEFAULT 1,
    role VARCHAR(32) NOT NULL DEFAULT 'author',
    PRIMARY KEY (book_id, author_id, role),
    KEY idx_author_book (author_id, book_id),
    CONSTRAINT fk_book_author_book
        FOREIGN KEY (book_id) REFERENCES book(id),
    CONSTRAINT fk_book_author_author
        FOREIGN KEY (author_id) REFERENCES author(id)
);
```

以“鲁迅”和“周树人”为例，`author` 中只有一条真实作者记录，`author_name` 中保存多个名字：

```text
author:      id=1, canonical_name='鲁迅'
author_name: author_id=1, name='鲁迅', is_primary=1
author_name: author_id=1, name='周树人', is_primary=0
```

查询某本书的作者时：

```sql
SELECT b.title, an.name AS author_name, ba.author_order
FROM book b
JOIN book_author ba ON ba.book_id = b.id
JOIN author_name an ON an.author_id = ba.author_id AND an.is_primary = 1
WHERE b.id = ?
ORDER BY ba.author_order;
```

按作者任意名字搜索作品时：

```sql
SELECT DISTINCT b.id, b.title
FROM author_name an
JOIN book_author ba ON ba.author_id = an.author_id
JOIN book b ON b.id = ba.book_id
WHERE an.name = ?;
```

注意事项：

1. 不要在 `book` 表中用一个字符串字段保存多个作者名，这违反第一范式，也不方便检索和去重。
2. 不要把“鲁迅”和“周树人”当成两个作者，否则同一人的作品统计会重复。
3. `book_author` 中保留 `author_order`，因为作者顺序通常有业务含义。
4. `role` 可以区分作者、译者、编者、绘者；如果业务不需要，也可以去掉简化。
5. 外键是否真的落库要看团队规范。高并发互联网业务可能用应用层约束，但逻辑关系和索引仍要设计清楚。

## 6. 易错点

1. 第一范式不是要求“字段越细越好”，而是要求字段在当前业务语义下不可再分。
2. 第二范式主要针对联合主键下的部分依赖。
3. 第三范式主要针对非主属性之间的传递依赖。
4. 范式解决的是结构冗余和更新异常，不直接解决性能问题。
5. 面试里说反范式要讲清楚一致性维护方案，不能只说“为了性能冗余字段”。
6. 数据库设计不能脱离查询模式，表结构和索引要围绕真实读写链路。
7. InnoDB 主键设计会影响聚簇索引和二级索引，不只是逻辑唯一标识。

## 7. 面试回答模板

三范式是关系型数据库表设计规范。第一范式要求字段原子，避免一列保存多个重复值；第二范式要求非主属性完全依赖整个候选键，主要解决联合主键下的部分依赖；第三范式要求非主属性不能传递依赖主键，避免一个表里保存可以由其他非主属性推出的数据。真实系统会在范式基础上做适度反范式，例如订单冗余商品快照价、列表页冗余计数，但要用同步更新、异步补偿或定期校验保证数据一致性。

做数据库设计时，我会先识别实体和关系，再确定主键、字段类型、约束和索引；索引围绕高频查询设计，表结构要考虑数据增长、冷热归档、分库分表和一致性边界。范式保证结构清晰和减少更新异常，反范式解决性能和历史快照问题，关键是讲清楚冗余数据如何同步、补偿和校验。
