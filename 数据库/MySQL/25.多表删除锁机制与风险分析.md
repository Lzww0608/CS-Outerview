# MySQL 多表删除操作的锁机制与风险分析

## 一、问题背景

生产环境中，执行 `DELETE FROM A WHERE id IN (SELECT ... FROM B JOIN C ...)` 这类带子查询的多表删除操作时，MySQL 会加什么锁？可能会导致什么问题？这是 DBA 和后端开发必须掌握的核心知识点。

---

## 二、DELETE 操作的锁机制

### 2.1 DELETE 的基本加锁流程

```sql
DELETE FROM orders WHERE id = 100;
```

执行过程：

```text
┌─────────────────────────────────────────────────────────────────┐
│ 1. InnoDB 定位记录                                              │
│    - 根据主键/索引找到 id=100 的行                               │
│    - 在内存中查找或从磁盘加载                                    │
└─────────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────────┐
│ 2. 获取行锁（X 锁，排他锁）                                     │
│    - 对找到的记录加排他锁                                        │
│    - LOCK_ORDINARY（非唯一索引）或 LOCK_REC_NOT_GAP（唯一索引）   │
└─────────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────────┐
│ 3. 标记删除                                                      │
│    - 将记录标记为已删除                                          │
│    - 事务提交后由 purge 线程物理删除                            │
└─────────────────────────────────────────────────────────────────┘
```

### 2.2 行锁类型详解

| 锁类型 | 说明 | 场景 |
|--------|------|------|
| LOCK_ORDINARY | 记录锁 + 间隙锁 | 非唯一索引删除 |
| LOCK_REC_NOT_GAP | 仅记录锁 | 唯一索引删除 |
| LOCK_GAP | 间隙锁 | 范围查询删除 |
| LOCK_X | 排他锁 | DELETE/UPDATE |
| LOCK_S | 共享锁 | SELECT ... LOCK IN SHARE MODE |

```sql
-- 非唯一索引删除，加记录锁 + 间隙锁
DELETE FROM orders WHERE status = 'pending';

-- 唯一索引删除，仅加记录锁
DELETE FROM orders WHERE id = 100;  -- id 是主键

-- 范围删除，加间隙锁
DELETE FROM orders WHERE id BETWEEN 100 AND 200;
```

## 三、子查询的锁行为

### 3.1 相关子查询 vs 非相关子查询

**非相关子查询**（子查询不依赖外层查询）：

```sql
DELETE FROM orders
WHERE user_id IN (SELECT id FROM users WHERE status = 'active');
```

执行流程：
1. 先执行子查询，得到 `user_id` 列表
2. 再执行 DELETE，基于 `user_id` 列表删除
3. 锁范围：只锁 orders 表相关行

**相关子查询**（子查询依赖外层查询）：

```sql
DELETE FROM orders
WHERE EXISTS (SELECT 1 FROM users WHERE users.order_id = orders.id);
```

执行流程：
1. 遍历 orders 表每行
2. 对每行执行子查询检查
3. 锁范围：orders 表所有行 + users 表相关行

### 3.2 JOIN 子查询的锁行为

```sql
DELETE o FROM orders o
JOIN users u ON o.user_id = u.id
JOIN products p ON o.product_id = p.id
WHERE o.status = 'completed' AND u.level = 'vip';
```

**锁分析**：

```text
┌─────────────────────────────────────────────────────────────────┐
│                       DELETE 涉及的锁                            │
│                                                                 │
│  orders 表：                                                    │
│  ┌──────────────────────────────────────────────────────────┐  │
│  │ 记录锁 + 间隙锁（根据 status 索引）                       │  │
│  │ 锁定所有 status='completed' 的行及前后间隙               │  │
│  └──────────────────────────────────────────────────────────┘  │
│                                                                 │
│  users 表：                                                     │
│  ┌──────────────────────────────────────────────────────────┐  │
│  │ 记录锁（根据 user_id 索引）                               │  │
│  │ 只锁定 JOIN 命中的行                                      │  │
│  └──────────────────────────────────────────────────────────┘  │
│                                                                 │
│  products 表：                                                  │
│  ┌──────────────────────────────────────────────────────────┐  │
│  │ 记录锁（根据 product_id 索引）                             │  │
│  │ 只锁定 JOIN 命中的行                                      │  │
│  └──────────────────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────────────────┘
```

### 3.3 不同子查询方式的锁差异

```sql
-- 方式1：IN 子查询
DELETE FROM orders WHERE user_id IN (SELECT id FROM users WHERE level = 'vip');

-- 方式2：EXISTS 子查询
DELETE FROM orders WHERE EXISTS (SELECT 1 FROM users WHERE users.id = orders.user_id AND level = 'vip');

-- 方式3：JOIN
DELETE o FROM orders o INNER JOIN users u ON o.user_id = u.id WHERE u.level = 'vip';
```

| 方式 | 锁范围 | 性能 | 适用场景 |
|------|--------|------|----------|
| IN | orders 所有匹配行 + users 索引行 | 较好 | 子查询结果集小 |
| EXISTS | orders 全表扫描 + users 索引行 | 较差 | 子查询结果集大 |
| JOIN | orders 索引扫描 + users 索引行 | 最好 | 简单 JOIN |

## 四、生产环境风险分析

### 4.1 锁等待与死锁

**最常见问题**：长时间锁等待或死锁。

```sql
-- 事务A执行
DELETE FROM orders WHERE status = 'pending';  -- 锁定 orders 表大量行

-- 同时事务B执行
UPDATE users SET last_order_time = NOW() WHERE id = 1;  -- 锁定 users 表某行
UPDATE orders SET status = 'processing' WHERE user_id = 1;  -- 被A阻塞！
```

**死锁场景**：

```text
时间线：

T1: DELETE orders WHERE user_id=1  ──► 锁定 orders[user_id=1] ──► 等待子查询...
     │
     │  同时
     ▼
T2: DELETE users WHERE id=1        ──► 锁定 users[id=1] ──► 等待...
                                              │
                                              ▼
                                       orders[user_id=1] 被 T1 锁定
                                       死锁检测发现环，T2 被回滚！
```

### 4.2 间隙锁导致的阻塞

```sql
-- 假设 orders 表有索引 idx_status
DELETE FROM orders WHERE status = 'pending';
```

执行后：
- 锁定所有 `status='pending'` 的行
- 锁定这些行之间的所有间隙
- 其他事务插入 `status='pending'` 的操作被阻塞

```text
索引 idx_status 的锁范围：

        [cancelled]  [completed]  [pending]  [processing]  [shipped]
              │            │          │           │            │
T1 锁定:  ────┼────────────┼──────────┼───────────┼────────────┼────
              │            │     记录锁+间隙锁    │            │
              │            │          ▼           │            │
              │            │    锁定 pending      │            │
              │            │    及前后间隙         │            │
```

### 4.3 长事务导致的 undolog 膨胀

```sql
START TRANSACTION;

-- 删除100万行，每行都会写入 undo log
DELETE FROM orders WHERE created_at < '2024-01-01';

COMMIT;
```

问题：
1. 事务持续时间长，锁持有时间长
2. 大量 undo log 占用存储空间
3. MVCC 快照链变长，影响后续查询性能

## 五、生产环境最佳实践

### 5.1 分批删除

**错误做法**（一次性删除大量数据）：

```sql
-- 危险！可能导致主从延迟、死锁、undo 膨胀
DELETE FROM orders WHERE created_at < '2024-01-01';
-- 影响行数：1,000,000+
-- 锁定时间：可能几分钟
```

**正确做法**（分批删除）：

```sql
-- 每批删除1000行，减少锁影响
DELETE FROM orders 
WHERE created_at < '2024-01-01' 
  AND id IN (
    SELECT id FROM (
      SELECT id FROM orders 
      WHERE created_at < '2024-01-01' 
      LIMIT 1000
    ) AS tmp
  );

-- 循环执行，直到删除完毕
-- 或使用存储过程
DELIMITER //
CREATE PROCEDURE batch_delete_orders()
BEGIN
    DECLARE done INT DEFAULT FALSE;
    DECLARE v_id BIGINT;
    
    DECLARE cur CURSOR FOR 
        SELECT id FROM orders WHERE created_at < '2024-01-01' LIMIT 1000;
    DECLARE CONTINUE HANDLER FOR NOT FOUND SET done = TRUE;
    
    REPEAT
        DECLARE CONTINUE HANDLER FOR SQLEXCEPTION SET done = FALSE;
        
        DELETE FROM orders 
        WHERE id IN (SELECT id FROM tmp_ids);
        
        DELETE FROM tmp_ids;
        
        -- 添加短暂延迟，让其他事务有机会获得锁
        DO SLEEP(0.1);
        
        UNTIL done END REPEAT;
END //
DELIMITER ;
```

### 5.2 使用表替代子查询

```sql
-- 子查询方式（可能锁全表）
DELETE FROM orders 
WHERE user_id IN (SELECT id FROM users WHERE level = 'vip');

-- 优化：使用临时表分批处理
CREATE TEMPORARY TABLE tmp_users AS 
SELECT id FROM users WHERE level = 'vip';

DELETE FROM orders 
WHERE user_id IN (SELECT id FROM tmp_users);

DROP TEMPORARY TABLE tmp_users;
```

### 5.3 索引优化

确保子查询和 JOIN 条件有合适索引：

```sql
-- 查看执行计划
EXPLAIN DELETE FROM orders o
JOIN users u ON o.user_id = u.id
WHERE u.level = 'vip';

-- 确保索引存在
CREATE INDEX idx_orders_user_id ON orders(user_id);
CREATE INDEX idx_users_level ON users(level);
CREATE INDEX idx_users_id ON users(id);  -- 如果 users.id 不是主键
```

### 5.4 监控与告警

```sql
-- 查看当前锁等待
SELECT 
    r.trx_id,
    r.trx_mysql_thread_id,
    r.trx_query,
    r.trx_state,
    r.trx_started,
    r.trx_rows_locked,
    b.lock_table,
    b.lock_index,
    b.lock_type
FROM information_schema.INNODB_LOCKS b
JOIN information_schema.INNODB_TRX r ON b.lock_trx_id = r.trx_id;

-- 查看事务状态
SELECT * FROM information_schema.INNODB_TRX\G

-- 查看锁等待关系
SELECT * FROM information_schema.INNODB_LOCK_WAITS;
```

### 5.5 主从环境注意事项

```sql
-- 主从延迟监控
SHOW SLAVE STATUS\G
-- 关注 Seconds_Behind_Master

-- 大删除操作在从库执行
-- 主库只做必要的删除
-- 从库延迟执行清理任务
```

## 六、案例分析

### 案例1：批量删除订单导致死锁

**场景**：每天凌晨清理历史订单

```sql
-- 凌晨2点执行
DELETE FROM orders WHERE status = 'completed' AND created_at < DATE_SUB(NOW(), INTERVAL 1 YEAR);
```

**问题**：
1. 锁定 orders 表大量行
2. 凌晨高峰期仍有用户下单
3. 新订单插入被间隙锁阻塞
4. 用户下单失败投诉

**解决方案**：
1. 改用分批删除
2. 避开业务高峰期
3. 从库执行清理任务

### 案例2：子查询锁全表

**场景**：删除 VIP 用户的所有订单

```sql
DELETE FROM orders WHERE user_id IN (SELECT id FROM users WHERE level = 'vip');
```

**问题**：
1. users 表可能有百万级 VIP 用户
2. 子查询结果集巨大
3. orders 表几乎所有行都被锁定

**解决方案**：
1. 使用临时表
2. 分批处理
3. 先统计影响范围

## 七、面试常见问题

### Q1: DELETE 操作会加什么锁？

DELETE 操作会对匹配的行加 **排他锁（X 锁）**：
- 唯一索引：记录锁（LOCK_REC_NOT_GAP）
- 非唯一索引：记录锁 + 间隙锁（LOCK_ORDINARY）
- 无索引：锁定所有扫描到的行，可能锁表

### Q2: 子查询会导致锁全表吗？

可能。如果子查询返回结果集很大，且没有合适索引，可能导致：
1. 全表扫描
2. 锁定大量行
3. 长时间锁等待

优化方法：
1. 确保索引存在
2. 使用临时表
3. 分批处理

### Q3: 如何避免死锁？

1. **减少锁范围**：使用精确索引，避免全表扫描
2. **保持加锁顺序一致**：多表操作按相同顺序加锁
3. **短事务**：尽快提交事务，减少锁持有时间
4. **分批删除**：避免一次性锁定大量数据
5. **监控告警**：及时发现锁等待和死锁

### Q4: DELETE 和 TRUNCATE 的区别？

| 特性 | DELETE | TRUNCATE |
|------|--------|----------|
| 锁类型 | 行锁 | 表锁 |
| 回滚 | 支持 | 不支持 |
| 触发器 | 触发 | 不触发 |
| 性能 | 较慢 | 极快 |
| 删除方式 | 逐行删除 | 释放数据页 |
| 自增主键 | 不重置 | 重置 |

## 八、总结

### 多表删除的锁机制

1. **DELETE 加排他锁**：对匹配行加 X 锁
2. **子查询加锁**：相关子查询可能锁定子表
3. **JOIN 加锁**：所有参与的表都会被加锁
4. **间隙锁**：非唯一索引范围删除会锁定间隙

### 潜在风险

1. **锁等待**：长时间锁定导致其他事务阻塞
2. **死锁**：多事务交叉锁定导致死锁
3. **主从延迟**：大量操作导致从库复制延迟
4. **Undo 膨胀**：长事务导致 undo log 膨胀

### 最佳实践

1. **分批删除**：减少单次锁范围
2. **索引优化**：确保查询走索引
3. **短事务**：尽快提交，减少锁持有时间
4. **监控告警**：及时发现锁问题
5. **从库清理**：大删除操作在从库执行
