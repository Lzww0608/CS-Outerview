# 5.B+树索引结构

数据库索引的物理结构不是单纯的“内存里的树”，而是面向磁盘页组织的数据结构。以 InnoDB 为例，索引通常以 B+ 树组织，每个节点对应一个或多个数据页，页是磁盘和 Buffer Pool 之间读写的基本单位。

## 1. 数据库索引的物理结构是什么？

InnoDB 表本身就是按主键聚簇组织的一棵 B+ 树：

```text
聚簇索引 / 主键索引:
root page
  -> internal page
      -> leaf page: primary key + complete row
```

二级索引也是 B+ 树，但叶子节点不直接保存完整行，而是保存：

```text
secondary key + primary key
```

所以通过二级索引查完整数据时，通常需要两步：

1. 先在二级索引 B+ 树里找到主键。
2. 再拿主键去聚簇索引 B+ 树里查完整行，这一步叫回表。

如果查询字段都在二级索引里，则可以走覆盖索引，避免回表。

## 2. B+ 树是什么结构？

B+ 树是一种多路平衡搜索树，特点是：

1. 所有叶子节点在同一层，树高稳定。
2. 非叶子节点只存 key 和子节点指针，主要用于导航。
3. 真实数据或数据指针都在叶子节点。
4. 叶子节点之间按 key 有序链接，适合范围查询。
5. 每个节点可以存很多 key，扇出很高，所以树高很低。

示意：

```text
                 [30 | 60]
              /      |      \
       [10|20]    [40|50]    [70|80|90]
          |          |           |
        leaf <----> leaf <----> leaf
```

数据库喜欢 B+ 树，核心原因是它能把一次查找控制在很少的页访问次数内。磁盘 I/O 比内存比较贵得多，所以降低树高比减少几次 CPU 比较更重要。

## 3. 为什么不是普通二叉树或红黑树？

普通二叉树或红黑树的扇出太小，数据量大时树高很高。即使红黑树是平衡的，`N` 很大时也可能需要几十层访问。如果每一层都可能对应一次磁盘页访问，I/O 成本会很高。

B+ 树一个节点可以容纳大量 key。例如一个 16KB 页里可以放很多索引项，扇出可能达到几百甚至上千。这样几千万甚至上亿行数据，树高通常也只有 3 到 4 层。

平衡二叉树或红黑树更适合内存数据结构，例如 `std::map`。它们每个节点通常只有两个孩子，节点之间通过指针跳转，局部性较差；数据库索引面对的是磁盘页和 Buffer Pool，核心目标是减少页访问次数和支持范围扫描。B+ 树把一个节点设计成一个页，单页容纳大量 key，树高低，顺序扫描时还能沿叶子链表向后读。

## 3.1 B 树和 B+ 树的区别

| 对比项 | B 树 | B+ 树 |
| --- | --- | --- |
| 数据存放位置 | 内部节点和叶子节点都可以存数据 | 数据通常只在叶子节点 |
| 内部节点容量 | 存 key + 数据，扇出相对小 | 只存 key + 指针，扇出更大 |
| 范围查询 | 需要中序遍历，跨层访问 | 叶子节点链表顺序扫描 |
| 查询路径 | 命中内部节点可能提前结束 | 通常都走到叶子节点 |
| 数据库索引适配 | 点查可以，但范围扫描不如 B+ 树 | 更适合磁盘页、范围查询和预读 |

数据库更常选 B+ 树的原因：

1. **扇出更高**：内部节点不存完整数据，同样 16KB 页能放更多 key，树更矮。
2. **范围查询更强**：叶子节点有序链表，定位起点后顺序扫描即可。
3. **查询更稳定**：所有数据都在叶子层，路径长度更一致。
4. **更适合磁盘预读**：叶子页顺序访问更容易利用局部性和预读。

### 3.1.1 为什么不用哈希表做数据库索引

哈希表适合等值查询，但不适合作为通用数据库索引：

1. 不支持范围查询，例如 `where age between 20 and 30`。
2. 不支持有序遍历，无法直接服务 `order by`、`min/max`、前缀范围扫描。
3. 联合索引的最左前缀、有序匹配能力较弱。
4. 哈希冲突需要额外处理，数据倾斜时性能不稳定。
5. 扩容、重哈希和持久化页结构维护成本较高。

MySQL 中也不是完全没有哈希能力，例如 Memory 引擎支持 Hash Index，InnoDB 有 Adaptive Hash Index。但这些通常是特定场景下的辅助优化，不能替代 B+ 树作为通用磁盘索引。

### 3.2 为什么说 B 树树高可能更高

B 树和 B+ 树都是多路平衡树，不是说 B 树一定“层数非常高”，而是在数据库页大小固定时，B 树内部节点要存 key 和数据记录或数据指针，单个页能容纳的分支数更少，扇出更低，所以同样数据量下树高更容易增加。

可以用一个简化估算说明：

```text
页大小 = 16KB
内部节点每个 key + child pointer = 16B
B+ 树内部节点扇出 ≈ 16KB / 16B ≈ 1024
```

如果 B 树内部节点还要保存一部分行数据，假设每项变成 `128B`：

```text
B 树内部节点扇出 ≈ 16KB / 128B ≈ 128
```

树高大约是 `log_M N`，`M` 是扇出。对 `1e8` 条记录：

```text
log_1024(1e8) ≈ 3
log_128(1e8)  ≈ 4
```

在内存算法里多一层可能只是几次 CPU 比较；但在数据库里，一层常常意味着多访问一个页，可能触发一次 Buffer Pool miss 和磁盘 I/O。因此数据库索引更关心“页访问次数”，B+ 树通过提高内部节点扇出降低树高，同时把所有数据放在叶子层，范围扫描也更顺。

## 3.3 索引关键字大小会影响什么

B+ 树的扇出和索引项大小强相关。页大小固定时，单个 key 越宽，一个内部页能放下的 key 和 child pointer 越少，树高更容易增加，Buffer Pool 能缓存的索引项也更少。

简化估算：

```text
页大小 16KB
每个内部索引项约 16B -> 扇出约 1000
每个内部索引项约 128B -> 扇出约 100
```

这会带来几个影响：

1. **树高增加**：同样数据量下页访问次数可能增加。
2. **缓存命中率下降**：Buffer Pool 同样大小能缓存的索引页覆盖数据变少。
3. **二级索引膨胀**：InnoDB 二级索引叶子节点保存二级 key 和主键，主键过长会放大每个二级索引。
4. **写入维护成本上升**：索引越宽，页分裂、redo、Buffer Pool 污染和磁盘空间成本越高。

工程建议：

1. 主键尽量短、稳定、递增或大体有序。
2. 长字符串可以考虑前缀索引，但要评估区分度和回表过滤成本。
3. 联合索引不要盲目堆很多宽字段，优先服务高频 SQL 的过滤、排序和覆盖需求。
4. 对 UUID 主键，可以考虑有序 UUID、雪花 ID 或额外短整型主键，避免随机插入和索引膨胀。

## 3.4 `std::map`、红黑树和 B+ 树对比

`std::map` 的典型实现是红黑树，它是面向内存的节点式平衡二叉搜索树；MySQL InnoDB 索引使用 B+ 树，它是面向页和磁盘 I/O 的多路平衡树。

| 对比项 | `std::map` / 红黑树 | B+ 树 |
| --- | --- | --- |
| 主要场景 | 进程内有序映射 | 数据库索引、文件系统索引 |
| 节点结构 | 一个节点通常存一个 key-value、父子指针和颜色 | 一个页内存很多 key 和子页指针 |
| 扇出 | 二叉，最多 2 个孩子 | 多路，常见数百到上千 |
| 树高 | `O(log_2 N)` | `O(log_M N)`，`M` 是页扇出 |
| 局部性 | 指针跳转多，cache locality 较差 | 页内连续存储，适合预读和 Buffer Pool |
| 范围扫描 | 中序遍历，节点跳转多 | 叶子链表顺序扫描 |
| 迭代器稳定性 | 插入通常不使已有迭代器失效 | 数据库不暴露 STL 迭代器语义 |

性能上，红黑树的单次比较和旋转适合内存对象管理，例如 `std::map` 要保证有序、插入删除稳定、迭代器不轻易失效；但它每层只淘汰一半搜索空间，节点又分散在堆上，数据量大时容易产生大量 cache miss。

B+ 树把一个节点设计成一个页，一次页访问可以带回大量 key，树高很低。数据库查询的瓶颈往往是页访问、Buffer Pool 命中和磁盘 I/O，而不是几次 CPU 比较，所以 B+ 树更适合数据库。内存空间上，红黑树每个元素有父指针、左右指针、颜色和 allocator 元数据；B+ 树按页批量存储 key，页内空间利用率更高，但会有页目录、页分裂、填充因子和碎片管理成本。

## 4. SELECT 在 B+ 树里的复杂度

假设 B+ 树有 `N` 条记录，单个内部节点平均有 `M` 个分支，那么树高大约是：

```text
O(log_M N)
```

因此一次等值查询的页访问复杂度可以回答为：

```text
O(log_M N)
```

但面试里最好补充具体场景：

1. **主键等值查询**：直接走聚簇索引，复杂度约 `O(log_M N)`。
2. **二级索引等值查询且需要完整行**：先查二级索引，再回表查聚簇索引，约 `O(log_M N) + O(log_M N)`。
3. **覆盖索引**：只查二级索引即可，避免回表。
4. **范围查询**：先 `O(log_M N)` 定位到范围起点，然后沿叶子链表顺序扫描，复杂度约 `O(log_M N + K)`，`K` 是命中的记录或页数量。

## 5. 面试回答模板

MySQL InnoDB 的索引物理上是按页组织的 B+ 树。主键索引是聚簇索引，叶子节点保存完整行；二级索引叶子节点保存二级索引 key 和主键，所以查询完整行时可能需要回表。B+ 树是多路平衡树，非叶子节点负责导航，叶子节点保存数据并通过链表连接，因此既适合点查，也适合范围查。它比红黑树/AVL 更适合数据库，是因为扇出高、树高低、页访问少；相比 B 树，B+ 树范围扫描和磁盘预读更友好。

查一条数据的复杂度不是按二叉树的 `log_2 N` 理解，而是按 B+ 树扇出 `M` 来看，大约是 `O(log_M N)`。由于 `M` 很大，实际树高通常很低，查询主要成本是少量页访问。

## 6. 插入时页满了怎么办

InnoDB 的 B+ 树节点以页为单位组织。插入新记录时，如果目标叶子页还有空间，直接插入并维护页内有序；如果页已经达到上限，就会触发页分裂。

大致过程：

1. 定位到要插入的叶子页。
2. 发现页空间不足。
3. 申请一个新的页。
4. 把原页中的部分记录移动到新页，让两个页大致保持有序和平衡。
5. 更新叶子页之间的双向链表指针。
6. 把新页的最小 key 或分隔 key 插入父节点。
7. 如果父节点也满了，继续向上分裂。
8. 如果根节点满了，会创建新的根节点，树高加 1。

示意：

```text
插入前:
parent: [50]
leaf:   [10 20 30 40 50]  // 页满

插入 35 后分裂:
parent: [35 | 50]
leaf1:  [10 20 30]
leaf2:  [35 40 50]
```

真实 InnoDB 还会考虑页目录、记录头、页内碎片、填充因子、顺序插入优化等细节。顺序递增主键通常只在最右叶子页追加，分裂更可控；随机主键会导致各处叶子页频繁分裂和页内移动，增加写放大和碎片。

## 7. 页分裂带来的影响

1. **写放大**：一次插入可能变成多个页修改，还可能递归修改父节点。
2. **页碎片**：分裂后两个页可能都不满，空间利用率下降。
3. **锁竞争**：热点页频繁插入会带来 latch 竞争。
4. **缓存扰动**：新页和父页修改会影响 Buffer Pool。

工程建议：

1. 主键尽量使用递增或大体有序的值，减少随机插入导致的页分裂。
2. 避免过长主键，因为二级索引叶子节点会保存主键，主键越长二级索引越大。
3. 对写入很重的表，索引不要建太多，每个二级索引都要维护一棵 B+ 树。
4. 批量导入时按主键顺序导入，通常比随机顺序更友好。

## 8. MySQL 为什么常说用 B+ 树，MongoDB 为什么常说用 B 树

这个问题要先纠正一个容易误导的说法：MongoDB 的具体索引结构取决于存储引擎，现代 MongoDB 默认 WiredTiger，官方也会把索引称为 B-tree 结构；它并不是简单等同于教科书里“内部节点存完整记录、叶子节点不链表”的 B 树。面试中更重要的是说明两类数据库的访问模式和存储目标不同。

MySQL InnoDB 选择 B+ 树的原因：

1. **面向磁盘页和范围查询**：内部节点只放 key 和页指针，扇出高，树高低；叶子节点按 key 有序连接，范围扫描非常高效。
2. **聚簇索引模型**：主键 B+ 树叶子节点保存完整行，二级索引叶子节点保存二级 key 和主键，适合 SQL 中大量范围、排序、分页和 Join 前置过滤。
3. **Buffer Pool 友好**：索引页和数据页以固定页缓存，顺序扫描能利用预读。

MongoDB 索引常被说成 B-tree 的原因：

1. **文档数据库点查和灵活索引多**：MongoDB 面向 BSON 文档，常按 `_id`、单字段、复合字段、数组多键索引做查询，B-tree 类结构适合通用有序查找。
2. **文档位置和索引分离**：索引项通常指向文档记录位置，不像 InnoDB 主键叶子直接组织整行；文档更新变大时还涉及记录移动和索引维护。
3. **存储引擎实现差异**：WiredTiger 也使用页、缓存、压缩和 B-tree 类结构，但它的内部页、叶子页、行存/列存能力和 InnoDB 聚簇索引不是同一套语义。

更准确的回答是：关系型数据库 InnoDB 强调页访问少、范围扫描和聚簇索引，因此 B+ 树非常合适；MongoDB 使用的是存储引擎里的 B-tree 类索引结构，服务于文档位置查找、复合索引和多键索引。不要把“MongoDB 用 B 树”理解成它完全不需要范围查询，也不要把 MySQL 的 B+ 树优势简单说成“层数一定比 B 树少”，核心还是页扇出、叶子顺序扫描和存储模型的取舍。
