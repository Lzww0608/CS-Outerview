# 5.B+树索引结构

数据库索引的物理结构不是单纯的“内存里的树”，而是面向磁盘页组织的数据结构。以 InnoDB 为例，索引通常以 B+ 树组织，每个节点对应一个或多个数据页，页是磁盘和 Buffer Pool 之间读写的基本单位。

## 1. 数据库索引的物理结构是什么？

InnoDB 表本身就是按主键聚簇组织的一棵 B+ 树：

```text
聚簇索引 / 主键索引:
root page
  -> internal page
      -> leaf page: primary key + complete row
```

二级索引也是 B+ 树，但叶子节点不直接保存完整行，而是保存：

```text
secondary key + primary key
```

所以通过二级索引查完整数据时，通常需要两步：

1. 先在二级索引 B+ 树里找到主键。
2. 再拿主键去聚簇索引 B+ 树里查完整行，这一步叫回表。

如果查询字段都在二级索引里，则可以走覆盖索引，避免回表。

## 2. B+ 树是什么结构？

B+ 树是一种多路平衡搜索树，特点是：

1. 所有叶子节点在同一层，树高稳定。
2. 非叶子节点只存 key 和子节点指针，主要用于导航。
3. 真实数据或数据指针都在叶子节点。
4. 叶子节点之间按 key 有序链接，适合范围查询。
5. 每个节点可以存很多 key，扇出很高，所以树高很低。

示意：

```text
                 [30 | 60]
              /      |      \
       [10|20]    [40|50]    [70|80|90]
          |          |           |
        leaf <----> leaf <----> leaf
```

数据库喜欢 B+ 树，核心原因是它能把一次查找控制在很少的页访问次数内。磁盘 I/O 比内存比较贵得多，所以降低树高比减少几次 CPU 比较更重要。

## 3. 为什么不是普通二叉树或红黑树？

普通二叉树或红黑树的扇出太小，数据量大时树高很高。即使红黑树是平衡的，`N` 很大时也可能需要几十层访问。如果每一层都可能对应一次磁盘页访问，I/O 成本会很高。

B+ 树一个节点可以容纳大量 key。例如一个 16KB 页里可以放很多索引项，扇出可能达到几百甚至上千。这样几千万甚至上亿行数据，树高通常也只有 3 到 4 层。

## 4. SELECT 在 B+ 树里的复杂度

假设 B+ 树有 `N` 条记录，单个内部节点平均有 `M` 个分支，那么树高大约是：

```text
O(log_M N)
```

因此一次等值查询的页访问复杂度可以回答为：

```text
O(log_M N)
```

但面试里最好补充具体场景：

1. **主键等值查询**：直接走聚簇索引，复杂度约 `O(log_M N)`。
2. **二级索引等值查询且需要完整行**：先查二级索引，再回表查聚簇索引，约 `O(log_M N) + O(log_M N)`。
3. **覆盖索引**：只查二级索引即可，避免回表。
4. **范围查询**：先 `O(log_M N)` 定位到范围起点，然后沿叶子链表顺序扫描，复杂度约 `O(log_M N + K)`，`K` 是命中的记录或页数量。

## 5. 面试回答模板

MySQL InnoDB 的索引物理上是按页组织的 B+ 树。主键索引是聚簇索引，叶子节点保存完整行；二级索引叶子节点保存二级索引 key 和主键，所以查询完整行时可能需要回表。B+ 树是多路平衡树，非叶子节点负责导航，叶子节点保存数据并通过链表连接，因此既适合点查，也适合范围查。

查一条数据的复杂度不是按二叉树的 `log_2 N` 理解，而是按 B+ 树扇出 `M` 来看，大约是 `O(log_M N)`。由于 `M` 很大，实际树高通常很低，查询主要成本是少量页访问。
