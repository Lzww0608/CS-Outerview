# 26. 数据库连接数打满如何发现和优化

数据库连接数打满是指数据库实例允许的连接资源被耗尽，新请求无法拿到连接，典型表现是应用报错、接口超时、连接池等待队列堆积，MySQL 里常见错误是 `Too many connections`。

面试里可以先说结论：**连接数打满不一定是数据库配置太小，更多时候是慢 SQL、长事务、连接泄漏、连接池配置不合理、突发流量、实例容量不足或上下游超时不一致导致连接被长期占用。处理时要先止血，再定位谁占连接、连接在等什么，最后从 SQL、连接池、限流、超时、读写分离和容量规划上治理。**

## 1. 为什么连接数会打满

数据库连接不是一个轻量的数字。每个连接通常会占用：

1. 数据库端线程或会话状态。
2. 连接相关内存，例如排序缓冲、Join 缓冲、临时表、网络缓冲。
3. 事务上下文、锁等待状态和执行计划相关资源。
4. 应用端连接池槽位、业务线程和等待队列。

所以 `max_connections` 不是越大越好。连接数过大时，数据库可能从“连接不够”变成“线程调度、内存、锁等待和 I/O 全部变差”。

常见根因：

1. 慢 SQL 或大查询执行时间过长，占住连接不释放。
2. 长事务不提交，连接一直处于 `Sleep`、`Query` 或锁等待状态。
3. 应用连接泄漏，代码拿到连接后没有关闭或归还连接池。
4. 连接池过大，多个服务实例叠加后超过数据库承载能力。
5. 连接池过小，应用侧先被打满，随后请求堆积形成雪崩。
6. 突发流量、重试风暴、定时任务同时启动。
7. 数据库锁等待、元数据锁、行锁等待导致连接堆积。
8. 数据库 CPU、I/O、Buffer Pool 命中率下降，导致每个请求变慢，从而拉高并发连接数。

## 2. 如何发现连接数打满

### 2.1 应用侧现象

常见报错：

```text
Too many connections
Connection is not available, request timed out
Communications link failure
SQLTransientConnectionException
HikariPool - Connection is not available
```

应用侧重点看：

1. 数据库连接池活跃连接数是否接近最大值。
2. 连接池等待连接的线程数是否上升。
3. 获取连接耗时是否变长。
4. 接口 P95/P99 是否变差。
5. 错误率是否集中在访问数据库的接口。

以 HikariCP 为例，重点指标包括：

1. `hikaricp.connections.active`：正在使用的连接数。
2. `hikaricp.connections.idle`：空闲连接数。
3. `hikaricp.connections.pending`：等待连接的线程数。
4. `hikaricp.connections.timeout`：获取连接超时次数。
5. `hikaricp.connections.creation`：创建连接耗时。

如果 `active` 长期接近 `maximumPoolSize`，同时 `pending` 和超时上升，说明应用侧连接池已经成为瓶颈。

### 2.2 数据库侧指标

MySQL 常用命令：

```sql
SHOW VARIABLES LIKE 'max_connections';
SHOW STATUS LIKE 'Threads_connected';
SHOW STATUS LIKE 'Threads_running';
SHOW STATUS LIKE 'Max_used_connections';
SHOW STATUS LIKE 'Aborted_connects';
SHOW STATUS LIKE 'Connection_errors%';
SHOW PROCESSLIST;
```

关键含义：

| 指标 | 含义 | 判断方式 |
| --- | --- | --- |
| `max_connections` | 数据库最大连接数 | 上限，不代表应该用满 |
| `Threads_connected` | 当前已建立连接数 | 接近 `max_connections` 时危险 |
| `Threads_running` | 当前正在执行的线程数 | 高说明数据库正在忙，低但连接高说明大量连接空闲或等待 |
| `Max_used_connections` | 启动以来达到过的最大连接数 | 判断峰值是否接近上限 |
| `Aborted_connects` | 连接失败次数 | 持续增加说明建连异常或认证/网络问题 |
| `Connection_errors_*` | 不同类型连接错误 | 用于区分 max、网络、认证等原因 |

`SHOW PROCESSLIST` 重点看：

1. `Command=Sleep` 很多：连接空闲但未释放，可能是连接池太大或连接泄漏。
2. `State=Waiting for ... lock`：锁等待导致连接堆积。
3. `State=Sending data` 很久：大查询、索引失效或回表/排序成本高。
4. `Time` 很大：长时间占用连接，需要进一步看 SQL 和事务。
5. 相同 SQL 大量出现：热点接口或重试风暴。

更完整可以查 `performance_schema`：

```sql
SELECT *
FROM performance_schema.threads
WHERE TYPE = 'FOREGROUND';

SELECT *
FROM performance_schema.events_statements_summary_by_digest
ORDER BY SUM_TIMER_WAIT DESC
LIMIT 10;

SELECT *
FROM performance_schema.data_lock_waits;
```

### 2.3 系统侧现象

连接数打满时，还要判断数据库是真的忙，还是连接被占住：

```bash
top
vmstat 1
iostat -x 1
ss -ant | grep 3306 | wc -l
```

常见组合：

1. CPU 高、`Threads_running` 高：数据库计算或执行压力大。
2. I/O await 高：磁盘瓶颈导致 SQL 变慢，连接堆积。
3. `Threads_connected` 高但 `Threads_running` 低：大量连接空闲、Sleep、锁等待或应用连接池配置过大。
4. 网络连接很多但数据库线程不高：可能有连接风暴、短连接或中间代理异常。

## 3. 线上如何先止血

连接数打满是故障类问题，不能一上来就调参数。推荐顺序是：

1. **限制入口流量**：对非核心接口限流、降级、熔断，避免继续打爆数据库。
2. **暂停批处理任务**：导出、报表、补偿任务、定时任务先暂停。
3. **定位异常 SQL**：用 `SHOW PROCESSLIST`、慢 SQL、`performance_schema` 找出长时间运行的 SQL。
4. **处理异常连接**：确认安全后 kill 长事务、锁等待或异常大查询。
5. **隔离问题服务**：如果某个服务实例连接暴涨，先下线或缩小它的连接池。
6. **临时扩容**：只在确认数据库资源还扛得住时，临时提高 `max_connections` 或扩容实例。

kill 连接示例：

```sql
SHOW PROCESSLIST;
KILL 12345;
```

注意：不要批量盲目 kill。要先确认是不是核心写事务、DDL、迁移任务或主从复制相关线程，避免造成更大问题。

## 4. 根因定位思路

### 4.1 是连接池打满还是数据库打满

先分清两个上限：

1. 应用连接池上限：例如 HikariCP `maximumPoolSize`。
2. 数据库实例上限：MySQL `max_connections`。

如果应用连接池满，但数据库连接没满，说明应用侧并发、慢 SQL 或连接池配置有问题。

如果数据库连接满，但单个应用连接池没满，通常是多个服务实例、多个应用、任务脚本、BI 工具、运维连接共同叠加超过上限。

### 4.2 是活跃连接多还是空闲连接多

```sql
SHOW STATUS LIKE 'Threads_connected';
SHOW STATUS LIKE 'Threads_running';
SHOW PROCESSLIST;
```

判断：

1. `Threads_connected` 高、`Threads_running` 高：数据库处理不过来，重点查 SQL、索引、锁、CPU、I/O。
2. `Threads_connected` 高、`Threads_running` 低、`Sleep` 多：连接池太大、连接未归还、空闲连接回收不合理。
3. `Threads_running` 不高但接口超时：可能连接池等待、锁等待、网络、下游超时配置问题。

### 4.3 是否存在慢 SQL 或锁等待

慢 SQL 会拉长单个连接占用时间。并发量不变时，单次请求耗时越长，需要的连接数越多。

可以用 Little's Law 理解：

```text
并发连接数 ≈ QPS × 平均数据库占用时间
```

例如：

```text
QPS = 1000
每次数据库访问平均占用连接 10ms
需要连接数约 10

如果慢 SQL 让占用时间变成 200ms
需要连接数约 200
```

所以连接数打满经常是慢 SQL 的结果，而不是独立问题。

锁等待排查：

```sql
SHOW ENGINE INNODB STATUS\G

SELECT *
FROM performance_schema.data_lock_waits;
```

常见锁问题：

1. 长事务持有行锁不提交。
2. 大范围更新导致大量记录锁和间隙锁。
3. DDL 等待元数据锁。
4. 缺索引导致更新扫描过多行，锁范围扩大。

### 4.4 是否连接泄漏

连接泄漏是指应用从连接池取出连接后，没有在 finally、try-with-resources 或框架生命周期内归还。

Java 示例：

```java
// 不好：异常时 connection 可能无法归还
Connection conn = dataSource.getConnection();
PreparedStatement ps = conn.prepareStatement(sql);
ResultSet rs = ps.executeQuery();

// 好：使用 try-with-resources 自动关闭资源
try (Connection conn = dataSource.getConnection();
     PreparedStatement ps = conn.prepareStatement(sql);
     ResultSet rs = ps.executeQuery()) {
    // handle result
}
```

HikariCP 可以临时打开泄漏检测：

```properties
spring.datasource.hikari.leak-detection-threshold=30000
```

注意：泄漏检测有开销，通常用于排查，不建议长期设置过低。

### 4.5 是否连接池配置不合理

常见错误配置：

1. 每个服务实例 `maximumPoolSize=100`，部署 50 个实例，总连接上限理论值就是 5000。
2. 主库、从库、多个数据源分别配置连接池，却没有合并计算总连接数。
3. 连接池超时时间比接口超时时间长，导致用户请求已经失败，后台线程还在等连接。
4. 连接池最大连接数大于业务线程池，或者业务线程池远大于连接池，引发大量等待。
5. 空闲连接回收太慢，低峰期也占满数据库连接。

推荐估算方式：

```text
数据库可分配给业务的连接数 = max_connections - 管理连接 - 复制连接 - 运维/监控预留 - 安全余量

单实例连接池上限 ≈ 数据库可用连接数 / 服务实例数 / 数据源数量
```

例如数据库 `max_connections=1000`，预留 200，业务有 20 个服务实例访问主库：

```text
单实例主库连接池上限 ≈ (1000 - 200) / 20 = 40
```

真实配置还要结合 QPS、SQL 耗时、CPU 核数、数据库规格和压测结果。

## 5. 如何优化

### 5.1 SQL 和事务优化

优先处理会长期占用连接的 SQL：

1. 对慢 SQL 建合适的联合索引和覆盖索引。
2. 避免 `SELECT *`、大 offset 分页、无索引条件、隐式类型转换。
3. 大查询、大导出走异步任务或只读库。
4. 大批量更新拆批，减少单事务时间。
5. 事务里不要包含远程 RPC、消息发送、文件上传等慢操作。
6. 及时提交或回滚事务，避免长事务占连接和锁。

事务示例：

```java
// 不好：事务里包含远程调用，连接和锁被长时间占用
beginTransaction();
updateOrder();
callRemoteService();
commit();

// 更好：把远程调用移出本地数据库事务，必要时使用事务消息或补偿
beginTransaction();
updateOrder();
saveOutboxEvent();
commit();
publishEventAsync();
```

### 5.2 连接池优化

连接池配置目标不是“越大越好”，而是让数据库在可承受并发内稳定工作。

常见参数：

| 参数 | 作用 | 优化建议 |
| --- | --- | --- |
| `maximumPoolSize` | 最大连接数 | 按实例数和数据库总容量计算 |
| `minimumIdle` | 最小空闲连接 | 不要盲目等于最大连接数 |
| `connectionTimeout` | 获取连接最大等待时间 | 应小于接口总超时，避免请求堆积 |
| `idleTimeout` | 空闲连接回收时间 | 低峰期释放多余连接 |
| `maxLifetime` | 连接最大生命周期 | 小于数据库或代理的连接回收时间 |
| `leakDetectionThreshold` | 泄漏检测阈值 | 排查时临时开启 |

推荐原则：

1. 连接池上限要按“数据库总连接预算”统一分配。
2. 核心服务和非核心服务使用不同账号、不同连接池或不同实例。
3. 获取连接超时要短，失败后快速降级，不要无限等待。
4. 连接池指标必须接入监控。
5. 多数据源场景要分别计算主库、从库和分片连接数。

### 5.3 数据库参数优化

`max_connections` 可以调，但要谨慎。

调大前要确认：

1. 数据库内存是否足够。
2. CPU 是否还有余量。
3. 当前瓶颈是不是连接上限，而不是慢 SQL、锁等待或 I/O。
4. 应用连接池是否已经治理。
5. 是否给管理连接、复制线程、监控连接预留空间。

MySQL 8.0 可以关注管理连接能力，例如 `admin_address`、`admin_port`，避免普通连接打满后运维也连不上。

示例：

```sql
SHOW VARIABLES LIKE 'max_connections';
SET GLOBAL max_connections = 1500;
```

注意：`SET GLOBAL` 对新连接生效，重启后是否保留取决于配置文件或参数组。

### 5.4 架构层治理

当单库连接容量已经接近上限时，可以从架构上减少数据库压力：

1. **缓存热点读**：高频读请求走 Redis 或本地缓存。
2. **读写分离**：读请求分摊到从库，主库连接池单独限流。
3. **异步化**：报表、导出、批处理放到 MQ 或任务系统。
4. **请求合并**：同一时间窗口内相同查询合并。
5. **限流和熔断**：按接口、租户、SQL 签名化维度限流。
6. **分库分表**：单实例连接和吞吐到上限时拆分数据和流量。
7. **数据库代理**：ProxySQL、RDS Proxy 等可以复用连接，但不能替代 SQL 优化和容量规划。

数据库代理适合解决短连接、连接风暴和连接复用问题，但如果后端 SQL 很慢，代理只会让连接排队位置变化，不会从根本上提升数据库执行能力。

## 6. 典型场景

### 6.1 大量 Sleep 连接

现象：

1. `Threads_connected` 接近上限。
2. `Threads_running` 不高。
3. `SHOW PROCESSLIST` 里大量 `Sleep`。

处理：

1. 检查连接池是否过大。
2. 检查是否有连接泄漏。
3. 调低 `minimumIdle`、合理设置 `idleTimeout`。
4. 多应用统一做连接预算。
5. 必要时清理异常客户端连接。

### 6.2 慢 SQL 导致连接堆积

现象：

1. 活跃连接多。
2. 相同 SQL 在 `PROCESSLIST` 中重复出现。
3. CPU 或 I/O 压力高。

处理：

1. 开启慢 SQL 日志或查 `events_statements_summary_by_digest`。
2. 用 `EXPLAIN ANALYZE` 看执行计划。
3. 补索引、改 SQL、减少返回行数。
4. 热点查询加缓存。
5. 临时对问题接口限流。

### 6.3 锁等待导致连接堆积

现象：

1. `PROCESSLIST` 中大量 `Waiting for ... lock`。
2. 更新、删除、DDL 或事务接口超时。
3. `SHOW ENGINE INNODB STATUS` 能看到等待关系。

处理：

1. 找到持锁事务并评估是否 kill。
2. 缩短事务范围。
3. 给更新条件补索引，减少锁范围。
4. 大批量变更拆批执行。
5. DDL 使用在线变更工具或低峰执行。

### 6.4 重试风暴导致连接打满

现象：

1. 数据库轻微抖动后请求量突然放大。
2. 应用日志中大量超时重试。
3. 连接池 pending 暴涨。

处理：

1. 重试加退避和抖动。
2. 设置最大重试次数。
3. 对不可重试错误不要重试。
4. 连接池等待超时要短于接口超时。
5. 对数据库访问加隔离舱和熔断。

## 7. 易错点

1. 连接数打满不等于直接调大 `max_connections`。
2. `Threads_connected` 高不一定表示数据库正在执行很多 SQL，要结合 `Threads_running` 看。
3. 应用连接池总量要按所有实例累计计算，而不是只看单机配置。
4. 慢 SQL 会通过拉长连接占用时间，间接把连接池打满。
5. 空闲连接多也会占数据库资源，连接池不是越大越安全。
6. 获取连接超时过长会让请求堆积，形成线程池、连接池和数据库的级联故障。
7. 数据库代理能缓解连接复用问题，但不能解决慢 SQL 和锁等待。
8. 长事务不仅占连接，还会占锁、阻碍 purge、放大 MVCC 历史版本压力。

## 8. 面试回答模板

数据库连接数打满时，我会先从应用侧和数据库侧同时确认。应用侧看连接池的 active、idle、pending、获取连接超时和接口 P99；数据库侧看 `max_connections`、`Threads_connected`、`Threads_running`、`Max_used_connections` 和 `SHOW PROCESSLIST`。如果报 `Too many connections`，说明数据库连接上限已经被打到；如果是 HikariCP 获取连接超时，可能只是应用连接池先满。

定位时我会先区分是活跃连接多还是空闲连接多。`Threads_connected` 高但 `Threads_running` 低，通常是连接池太大、Sleep 连接多或连接泄漏；两者都高，通常是慢 SQL、锁等待、CPU/I/O 瓶颈导致每个请求占用连接时间变长。然后看慢 SQL、`EXPLAIN ANALYZE`、`performance_schema`、锁等待和长事务，确认是不是某个热点 SQL、批处理任务、DDL 或重试风暴把连接占住。

处理上先止血：限流降级、暂停报表导出和批处理、kill 明确异常的长查询或长事务、隔离异常服务实例。长期优化包括：优化慢 SQL 和索引，缩短事务，把远程调用移出事务；合理配置连接池的 `maximumPoolSize`、`connectionTimeout`、`idleTimeout` 和 `maxLifetime`；统一计算所有服务实例的连接预算；必要时做缓存、读写分离、异步化、请求合并、分库分表或使用数据库代理。`max_connections` 可以调大，但前提是数据库 CPU、内存和 I/O 还有余量，否则只会把故障从“连不上”变成“整体更慢”。
