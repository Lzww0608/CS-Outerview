# 30. UPDATE 语句执行流程

面试里问“MySQL 执行一条 UPDATE 语句会经过哪些过程”，核心不是只回答“会加锁”，而是要把 Server 层解析优化、InnoDB 访问数据、锁、undo、redo、binlog 和提交串起来。

## 1. 一条 UPDATE 的整体链路

以这条语句为例：

```sql
UPDATE account
SET balance = balance - 100
WHERE id = 1;
```

典型执行流程：

```text
客户端发送 SQL
-> Server 层解析、权限校验、优化执行计划
-> 执行器调用 InnoDB 按索引定位记录
-> InnoDB 做当前读并加排他锁
-> 写 undo log，保存旧版本
-> 在 Buffer Pool 中修改数据页
-> 写 redo log prepare
-> Server 层写 binlog
-> InnoDB redo log commit
-> 返回成功，后续由刷脏线程把数据页落盘
```

如果语句命中主键或唯一索引，InnoDB 可以快速定位一行；如果 `WHERE` 条件没有合适索引，可能扫描大量记录并对扫描到的记录加锁，锁范围和性能风险都会变大。

## 2. Server 层做什么

Server 层负责 SQL 通用能力：

1. **连接和权限校验**：确认用户是否有库表和列的更新权限。
2. **解析 SQL**：词法、语法分析，构建语法树。
3. **语义检查**：确认表、列、函数、表达式合法。
4. **优化器选择执行计划**：选择索引、访问路径和扫描方式。
5. **执行器调用存储引擎**：按执行计划逐行读取和更新。
6. **binlog 记录逻辑变更**：用于主从复制、恢复和异构同步。

注意：优化器选择的执行计划会影响加锁范围。比如 `WHERE id = 1` 命中主键通常只锁一条记录；如果条件不走索引，InnoDB 可能扫描很多记录，表现为锁等待扩大。

## 3. InnoDB 层做什么

InnoDB 负责事务、锁、MVCC 和物理存储：

1. **当前读**：UPDATE 不能读历史快照，它要读取最新可见版本并准备修改。
2. **加排他锁**：对命中的索引记录加 X 锁；范围更新在 RR 下可能涉及 Next-Key Lock。
3. **写 undo log**：记录旧值，用于事务回滚和 MVCC 历史版本。
4. **修改 Buffer Pool 中的数据页**：不一定立刻把数据页刷到磁盘。
5. **写 redo log**：记录物理修改，崩溃后可以重做已提交事务。
6. **维护索引**：如果更新了索引列，通常等价于删除旧索引项再插入新索引项。

如果只更新非索引列，主要修改聚簇索引记录本身；如果更新二级索引列，还要维护对应二级索引 B+ 树，写放大会更明显。

## 4. undo、redo、binlog 的配合

UPDATE 涉及三类日志：

| 日志 | 作用 | 关键点 |
| --- | --- | --- |
| undo log | 回滚和 MVCC | 记录修改前的旧值 |
| redo log | 崩溃恢复 | WAL，先写日志再延迟刷数据页 |
| binlog | 复制和恢复 | Server 层逻辑或行级变更日志 |

提交时 redo 和 binlog 通过两阶段提交保持一致：

```text
1. InnoDB 写 redo prepare
2. Server 写 binlog
3. InnoDB 写 redo commit
```

这样可以避免主库崩溃恢复后有某个事务，但 binlog 没有记录，导致从库和主库不一致。

## 5. 加锁和隔离级别

UPDATE 是当前读，会对要修改的记录加锁：

1. **主键等值更新**：通常是记录锁。
2. **唯一索引等值更新**：命中存在记录时通常锁对应记录。
3. **普通索引范围更新**：RR 下可能加 Next-Key Lock，防止范围内幻写影响当前读语义。
4. **无索引条件更新**：可能扫描大量记录，加锁范围明显扩大。
5. **唯一约束检查**：更新唯一索引列时还要检查新值是否冲突。

示例：

```sql
UPDATE order_item
SET status = 'CANCELLED'
WHERE order_id = 100
  AND status = 'CREATED';
```

如果有联合索引 `(order_id, status)`，锁范围通常更可控；如果没有索引，可能全表扫描并造成大量锁等待。

## 6. 易错点

1. UPDATE 不是快照读，而是当前读；它要读取最新版本并加锁。
2. “数据落盘”不等于提交时立刻刷完整数据页，提交关键是 redo/binlog 按策略持久化。
3. redo log 不能替代 binlog，binlog 也不能替代 redo log，二者层级和用途不同。
4. 更新非索引列和更新索引列成本不同，后者会维护二级索引。
5. `WHERE` 条件是否命中索引，决定扫描行数、锁范围和死锁概率。
6. 事务里做远程 RPC、慢计算或等待用户输入，会拉长持锁时间。

## 7. 面试回答模板

一条 UPDATE 先在 Server 层完成连接、权限、解析、优化和执行计划选择，然后执行器调用 InnoDB 按索引定位记录。InnoDB 对要修改的记录做当前读并加排他锁，写 undo log 保存旧值，在 Buffer Pool 中修改数据页并写 redo log。提交时先把 redo 写到 prepare，再由 Server 层写 binlog，最后 redo commit，通过两阶段提交保证崩溃恢复和主从复制一致。真正的数据页可以后续异步刷盘。回答时还要补充：UPDATE 的锁范围和执行计划强相关，不走索引可能扫描并锁住大量记录；更新索引列会带来额外索引维护成本。
