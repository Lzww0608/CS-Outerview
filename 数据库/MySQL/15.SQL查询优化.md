# SQL 查询优化

SQL 查询优化的目标是减少扫描行数、减少回表、减少排序/临时表、减少锁等待和网络传输。面试里应按“定位 -> 改写 SQL -> 调整索引 -> 优化数据和架构”的顺序回答。

## 先定位问题

常用手段：

1. 慢 SQL 日志：找到高频慢查询。
2. `EXPLAIN`：看访问类型、使用索引、扫描行数、额外操作。
3. `EXPLAIN ANALYZE`：看真实执行耗时和行数。
4. 监控：QPS、P95/P99、Buffer Pool 命中率、锁等待、临时表、排序。

`EXPLAIN` 重点字段：

1. `type`：访问类型，常见从好到差有 `const`、`ref`、`range`、`index`、`ALL`。
2. `key`：实际使用的索引。
3. `rows`：优化器估算扫描行数。
4. `Extra`：是否 `Using index`、`Using where`、`Using filesort`、`Using temporary`。

## 慢 SQL 线上排查和处理

线上发现慢 SQL 时，建议按“止血 -> 定位 -> 优化 -> 验证”的顺序处理。

止血手段：

1. 对明显异常的接口做限流、降级或临时关闭非核心查询。
2. 如果是报表、导出、大分页拖慢主库，先切到只读库或离线任务。
3. 对锁等待严重的 SQL，先确认是否有长事务占锁，必要时 kill 长事务或异常查询。

定位手段：

1. 开启或查看慢 SQL 日志，关注 `query_time`、`lock_time`、`rows_examined`、`rows_sent`。
2. 用 `SHOW PROCESSLIST` 或 performance_schema 看当前正在执行、等待锁或临时表的语句。
3. 用 `EXPLAIN ANALYZE` 对比优化器估算行数和真实扫描行数，判断统计信息是否失真。
4. 看表大小、索引基数、Buffer Pool 命中率、临时表落盘、磁盘 I/O 和主从延迟。

常见根因：

1. 索引失效导致全表扫描。
2. 联合索引顺序不匹配，范围条件截断后续列。
3. 返回行数太多，回表、排序或网络传输成本高。
4. 大事务、间隙锁、元数据锁导致查询等待。
5. 数据分布变化后统计信息过旧，优化器选错执行计划。

处理方式：

1. 改写 SQL，让条件命中索引并减少返回字段。
2. 新增或调整联合索引，优先覆盖高频核心查询。
3. 大表分批处理，避免一次扫描或更新过多行。
4. 把强实时要求不高的查询改成缓存、预聚合或异步离线计算。
5. 优化后用线上相同量级数据验证 P95/P99、扫描行数和执行计划，而不是只看本地小数据。

## SQL 写法优化

1. 避免 `SELECT *`，只查需要字段，增加覆盖索引机会。
2. 避免对索引列使用函数或表达式。
3. 避免隐式类型转换，例如字符串列用字符串常量比较。
4. `LIKE 'abc%'` 可用前缀索引，`LIKE '%abc'` 通常不能用 B+ 树。
5. 大分页避免 `LIMIT offset, size`，改用基于游标的 seek pagination。
6. `OR` 条件两侧都要有可用索引，否则考虑改写为 `UNION ALL`。
7. 小心 `NOT IN`、`!=`、`IS NOT NULL`，选择性差时可能全表扫描。

示例：把函数条件改成范围条件：

```sql
-- 不好：对列做函数
WHERE DATE(created_at) = '2026-04-25'

-- 好：保留列原值的有序性
WHERE created_at >= '2026-04-25'
  AND created_at <  '2026-04-26'
```

## 索引优化

1. 高频过滤字段、连接字段、排序/分组字段优先考虑索引。
2. 联合索引遵守最左前缀，一般按等值条件、范围条件、排序字段、覆盖字段设计。
3. 使用覆盖索引减少回表。
4. 控制索引数量和宽度，避免写入成本过高。
5. 删除重复索引和长期不用的索引。

示例：

```sql
SELECT id, amount
FROM orders
WHERE user_id = 100
  AND status = 1
ORDER BY created_at DESC
LIMIT 20;
```

可考虑：

```sql
CREATE INDEX idx_user_status_time_amount
ON orders(user_id, status, created_at DESC, amount);
```

如果 `id` 是主键，InnoDB 二级索引叶子节点自带主键值，查询可能形成覆盖索引。

## Join 优化

1. 小结果集驱动大表。
2. Join 字段类型和字符集保持一致，避免隐式转换。
3. Join 字段建立索引。
4. 先过滤再 Join，减少参与连接的数据量。
5. 对复杂多表 Join，可以拆分 SQL 或用临时结果表。

## 排序和分组优化

1. `ORDER BY` 尽量和联合索引顺序一致。
2. `WHERE` 等值条件 + `ORDER BY` 字段可以组合成联合索引。
3. `GROUP BY` 字段如果符合索引顺序，可以减少临时表。
4. 如果无法避免排序，限制返回行数，减少排序数据。

## 架构和数据层优化

当单条 SQL 已经优化到位但仍扛不住时，考虑：

1. 缓存热点查询。
2. 读写分离。
3. 分库分表。
4. 冗余字段或反范式设计。
5. 离线预聚合、物化视图、ClickHouse/ES 等异构存储。
6. 归档冷数据，减少热表体积。

### 数据库成为瓶颈时动态查询怎么提效

动态查询通常指筛选条件多、组合不固定、排序分页复杂的查询，例如后台列表、搜索页、运营报表。数据库成为瓶颈时，不能只靠继续加索引，因为条件组合过多会导致索引爆炸。

常见优化方向：

1. **拆分读模型**：交易库保留写入和强一致点查，把复杂检索同步到 ES、ClickHouse、Doris 或宽表。
2. **缓存热点查询**：对高频筛选结果、首页列表、TopN 做短 TTL 缓存，key 需要包含筛选条件版本。
3. **预计算和物化视图**：把按天、按用户、按状态的统计提前聚合，查询时读结果表。
4. **限制查询自由度**：前端不允许无限组合条件、超大时间范围和深分页；必须带租户、用户、时间等收敛条件。
5. **游标分页**：用 `WHERE id < last_id ORDER BY id DESC LIMIT n` 替代大 offset。
6. **冷热分离**：近期热数据放 MySQL，历史数据归档到 OLAP 或对象存储。
7. **读写分离和只读副本**：把报表、导出、后台查询从主库隔离出去。

动态查询索引设计要先找“必带条件”。例如 SaaS 后台列表通常强制带 `tenant_id`，再组合状态和时间：

```sql
CREATE INDEX idx_tenant_status_time
ON orders(tenant_id, status, created_at);
```

如果没有必带条件，任意字段都可筛选，MySQL 很难靠少量 B+ 树索引兜住，应该转搜索引擎或列式分析库。

### 百万级单表从前端、Java 后台、数据库三层优化

前端层：

1. 分页查询，禁止一次加载全部数据。
2. 输入框防抖，筛选条件变更后合并请求。
3. 虚拟列表渲染，避免 DOM 渲染成为瓶颈。
4. 导出大数据走异步任务，前端轮询或 SSE 看进度。
5. 明确最大时间范围和最大页数，避免深分页拖垮后端。

Java 后台层：

1. 参数校验，强制带必要过滤条件，例如用户、租户、时间范围。
2. 使用游标分页或 search_after，不把大 offset 直接透传数据库。
3. 只返回需要字段，DTO 裁剪，避免大对象序列化。
4. 热点查询加本地缓存或 Redis 缓存，注意缓存穿透和失效。
5. 连接池、线程池、超时、限流和降级要配置，避免慢查询拖垮服务。
6. 对导出、统计、复杂查询异步化，写任务表或 MQ，避免同步 HTTP 长时间占用线程。

数据库层：

1. 围绕高频 SQL 建联合索引和覆盖索引。
2. 避免 `SELECT *`、函数包列、隐式类型转换、前导模糊匹配。
3. 用 `EXPLAIN ANALYZE` 看真实扫描行数、回表、filesort 和临时表。
4. 大表历史数据归档，或按时间分区。
5. 读多写少场景可以加只读副本，复杂分析迁移到 OLAP。
6. 对必须分页的列表，使用稳定排序键，例如 `(created_at, id)`，避免翻页重复或漏数据。

## MySQL 配置优化

配置优化不是第一步，只有在 SQL、索引和数据模型确认合理后才有意义。常见关注点：

1. **Buffer Pool**：`innodb_buffer_pool_size` 决定 InnoDB 缓存数据页和索引页的能力。过小会导致频繁磁盘 I/O，过大可能挤压系统页缓存和其他进程。
2. **Redo Log**：`innodb_log_file_size`、`innodb_log_buffer_size` 会影响写入峰值和 checkpoint 频率。日志太小可能导致频繁刷脏页。
3. **临时表和排序**：`tmp_table_size`、`max_heap_table_size`、`sort_buffer_size` 配置不合理时，复杂查询容易临时表落盘或消耗过多会话内存。
4. **连接数和线程**：`max_connections` 不能盲目调大，连接过多会放大内存和上下文切换；应结合连接池、慢查询和限流一起治理。
5. **刷盘策略**：`innodb_flush_log_at_trx_commit` 和 `sync_binlog` 决定提交持久性和写性能取舍。金融强一致链路通常更保守，日志/统计类场景可以评估放宽。
6. **统计信息**：数据分布变化后，`ANALYZE TABLE` 或持久化统计信息可以减少优化器选错索引。

配置优化要结合监控指标验证，例如 Buffer Pool 命中率、脏页比例、redo checkpoint age、临时表落盘数、磁盘 util、慢 SQL P99，而不是照抄一组“万能参数”。

## 易错点

1. 有索引不代表一定更快，返回大量数据时全表扫描可能更优。
2. 单列索引很多不一定好，联合索引更依赖具体 SQL。
3. 优化不能只看 `EXPLAIN`，还要看真实数据分布和线上耗时。
4. 缓存不是 SQL 优化的替代品，缓存命中失败时数据库仍要能承受。
5. 索引提升查询但拖慢写入，要结合读写比例取舍。

## 面试回答模板

我会先通过慢 SQL 和 `EXPLAIN/EXPLAIN ANALYZE` 定位慢在哪里，看是否全表扫描、扫描行数过大、没用索引、回表多、filesort 或临时表。SQL 层面避免 `SELECT *`、函数包索引列、隐式类型转换、前导模糊匹配和大 offset；索引层面围绕高频 SQL 建联合索引和覆盖索引，遵守最左前缀；Join 要保证关联字段有索引且类型一致。再往上可以用缓存、读写分离、分库分表、预聚合或异构存储。优化后要用真实执行时间和扫描行数验证。
