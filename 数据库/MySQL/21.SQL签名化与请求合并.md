# 21. SQL 签名化与请求合并

SQL 签名化是把具体 SQL 中的字面量、空白、注释等差异归一化，得到一个稳定的“查询形状”标识。它常用于慢 SQL 聚合、缓存 key 设计、请求合并和风控审计。

## 1. 什么是 SQL 签名化

例如两条 SQL：

```sql
SELECT * FROM orders WHERE user_id = 1001 AND status = 'PAID';
SELECT * FROM orders WHERE user_id = 2002 AND status = 'PAID';
```

签名化后可以归一为：

```sql
SELECT * FROM orders WHERE user_id = ? AND status = ?;
```

再对归一化结果做 hash：

```text
signature = hash(normalized_sql)
```

这样可以把同一类查询聚合到一起。

## 2. 为什么需要签名化

1. **慢 SQL 聚合**：不同参数的同类 SQL 聚合到一个指标上，便于发现真正的慢查询模式。
2. **请求合并**：同一时间窗口内相同签名的请求可以合并，减少重复查库。
3. **缓存 key 设计**：签名表示查询模板，参数表示具体查询对象，二者组合生成稳定 key。
4. **安全审计**：识别异常 SQL 模式，而不是被大量不同参数干扰。
5. **限流和熔断**：按 SQL 模板维度限流，避免某一类查询拖垮数据库。

## 3. 如何实现

工程上优先使用 SQL Parser，而不是手写正则。

基本步骤：

1. 去掉注释和多余空白。
2. 统一关键字大小写。
3. 把字符串、数字、时间等字面量替换为占位符。
4. 对 `IN (...)` 这类列表做长度归一或保留长度分桶。
5. 保留表名、列名、操作类型、排序和分页结构。
6. 对归一化结果计算 hash。

示例：

```text
SELECT name FROM student WHERE id IN (1,2,3)
-> SELECT name FROM student WHERE id IN (?,?,?)
-> hash(...)
```

是否把 `IN` 列表统一成 `IN (?)` 要看场景。慢 SQL 聚合可以更粗，执行计划分析则要保留列表规模，因为列表大小会影响优化器选择。

## 4. 请求合并怎么做

如果多个请求在短时间内查询同一类数据，可以按业务 key 合并，而不是每个请求都打数据库。

以“多个 SQL 合并后只查最小时间戳”为例，常见思路是：

```text
请求1: query(user=A, since=10:00)
请求2: query(user=A, since=10:05)
请求3: query(user=A, since=10:03)

合并成:
query(user=A, since=min(10:00,10:05,10:03))
```

一次查出从最小时间戳之后的全量增量数据，再在内存中按各请求的原始时间戳过滤返回。

适用前提：

1. 多个请求的查询对象相同或可归并。
2. 时间窗口很短，例如几毫秒到几十毫秒。
3. 查询结果可以被安全拆分给不同请求。
4. 数据库一次宽查询的成本小于多次重复窄查询。

注意点：

1. 合并窗口不能太长，否则增加尾延迟。
2. 单次合并查询可能返回更多数据，要控制上限。
3. 需要处理并发 map、等待队列、超时和异常唤醒。
4. 权限和租户必须作为合并 key 的一部分，不能跨用户合并敏感数据。

## 5. 本地数据库和连接复用

如果是在端上 SDK 查询本地 SQLite 或类似嵌入式数据库，不应每次请求都重新建立连接。更常见做法是：

1. SDK 初始化时打开连接或连接池。
2. 查询走预编译语句，减少 SQL 解析和编译开销。
3. 写入使用事务批量提交。
4. 读多写少时控制并发读写模型，避免长事务阻塞 UI 或业务线程。
5. 连接生命周期跟 SDK 或应用进程绑定，退出时统一关闭。

服务端数据库也类似，高频请求依赖连接池复用连接，而不是每次 TCP/TLS/认证/建连。

## 6. 易错点

1. SQL 签名化不能用简单字符串替换解决所有问题，注释、转义字符串、多语句、函数和方言差异都可能误判。
2. 签名化不能替代参数化查询。防 SQL 注入仍要用预编译和绑定参数。
3. 请求合并不是越多越好，合并窗口过大会牺牲延迟。
4. 只按 SQL 模板合并可能串数据，必须把租户、用户、权限、查询对象一起纳入 key。
5. 合并查询返回更多数据时，可能增加网络和内存成本，要用真实压测验证。

## 7. 面试回答模板

SQL 签名化就是把 SQL 的字面量和格式差异归一化，得到稳定的查询模板，例如把 `user_id=1001`、`user_id=2002` 都变成 `user_id=?`，再计算 hash。它常用于慢 SQL 聚合、缓存 key、请求合并和限流。实现上最好用 SQL Parser，归一化字面量、空白、大小写和 `IN` 列表。请求合并时，可以把同一用户、同一查询对象、短时间窗口内的多个查询合成一次更宽的查询，例如取最小时间戳查一次，再按各请求条件拆分结果。要注意权限隔离、合并窗口、返回数据量和异常唤醒。
