

| ACID 特性                | 核心含义                                         | 主要保证机制（InnoDB）                                  |
| ------------------------ | ------------------------------------------------ | ------------------------------------------------------- |
| **A**tomicity (原子性)   | 事务要么全部成功，要么全部失败回滚。             | **Undo Log (回滚日志)**                                 |
| **C**onsistency (一致性) | 事务使数据库从一个有效状态转移到另一个有效状态。 | **由 A、I、D 共同保证 + 数据库自身约束**                |
| **I**solation (隔离性)   | 并发事务之间互不干扰。                           | **MVCC + 锁机制 (Locking)**                             |
| **D**urability (持久性)  | 一旦事务提交，其结果就是永久性的。               | **Redo Log (重做日志)** / **Write-Ahead Logging (WAL)** |

------



### 1. 原子性 (Atomicity) - 由 Undo Log 保证

原子性要求一个事务内的所有操作要么全部完成，要么全部不做，不能只做一半。如果事务在执行过程中发生错误，它必须能**回滚（Rollback）**到事务开始前的状态。

这个“回滚”的能力就是由 **Undo Log** 提供的。

- **工作原理**：
  1. 当一个事务要修改数据时（`INSERT`, `UPDATE`, `DELETE`），InnoDB **首先**会将“如何撤销这个修改”的信息记录到 Undo Log 中。
     - 对于 `INSERT`，Undo Log 记录下新数据的主键，以便回滚时可以 `DELETE`。
     - 对于 `DELETE`，Undo Log 记录下被删除数据的完整内容，以便回滚时可以 `INSERT` 回去。
     - 对于 `UPDATE`，Undo Log 记录下被修改列的旧值，以便回滚时可以 `UPDATE` 回去。
  2. 如果事务需要回滚（无论是用户执行 `ROLLBACK` 还是系统崩溃），InnoDB 就会根据 Undo Log 中的记录执行相反的操作，从而将数据恢复到事务开始前的状态。

**简单来说，Undo Log 就是一份“后悔药”清单，保证了事务可以被完美撤销。**

> **补充**：Undo Log 还有一个重要作用，就是为 MVCC 提供旧版本的数据快照，以实现隔离性。

### 1.1 回滚失败怎么办

面试里问“实现原子性时，回滚失败怎么办”，不能回答成“回滚一定成功”。更准确的说法是：数据库把回滚本身也设计成可恢复的过程，崩溃后由恢复流程继续完成。

InnoDB 的处理思路：

1. **修改前先写 undo**：事务修改数据前，先把旧版本或反向操作写入 undo log。只要 undo 已经持久化到足够可靠的位置，后续就有恢复依据。
2. **WAL 保证日志先行**：redo log 记录数据页和 undo 页的物理修改。崩溃恢复时先用 redo 把系统恢复到崩溃瞬间的物理状态。
3. **识别未提交事务**：恢复阶段根据事务状态和日志，找出崩溃前没有提交完成的事务。
4. **继续 rollback**：对未提交事务执行 undo，把它们的影响撤销。即使上一次回滚过程中又崩溃，重启后仍能继续恢复。
5. **清理历史版本**：回滚完成后，undo 版本不会立刻都删除，还要等待没有 Read View 引用时由 purge 线程清理。

需要区分两类“失败”：

1. **事务回滚期间数据库进程崩溃**：数据库重启后通过 redo + undo 继续恢复，这是事务系统要保证的能力。
2. **外部副作用无法回滚**：例如已经发出短信、调用三方支付、发送 MQ。这些不属于数据库本地事务，不能靠 MySQL rollback 自动撤销，需要用本地消息表、Outbox、事务消息、幂等状态机和补偿任务处理。

真实业务里，强一致状态应先落在数据库事务内，例如订单状态、扣款流水、库存流水；对外通知和异步事件放到事务提交后投递，或者通过 outbox 表让后台任务可靠发送。这样即使服务在回滚或提交边界崩溃，也可以根据数据库中的权威状态恢复。



### 2. 持久性 (Durability) - 由 Redo Log 保证

持久性要求一旦事务成功提交（`COMMIT`），它对数据库的修改就必须是永久的，即使之后系统发生崩溃、断电等故障，数据也不能丢失。

这个保证主要依赖于 **Redo Log** 和它的 **Write-Ahead Logging (WAL)** 策略。

- **问题**：直接将修改后的数据写入磁盘（数据文件）是一个缓慢的随机I/O过程。如果在写入过程中发生崩溃，数据文件就可能损坏。
- **解决方案 (WAL)**：
  1. 当事务修改数据时，数据首先在内存的 **Buffer Pool** 中被修改。
  2. **同时**，InnoDB 会将“如何重做这个修改”的物理操作日志（例如，“在哪个文件的哪个页的哪个偏移量写入了什么数据”）以**顺序I/O**的方式，快速写入到磁盘上的 **Redo Log** 文件中。这被称为“预写日志”。
  3. 当事务 `COMMIT` 时，它**不一定**需要等待内存中的脏数据页（Dirty Page）刷回磁盘数据文件，它只需要确保对应的 Redo Log 记录已经成功写入磁盘。一旦 Redo Log 落盘，`COMMIT` 操作就可以成功返回。
  4. **崩溃恢复**：如果系统在数据页完全刷盘前崩溃，重启后 InnoDB 会检查 Redo Log。它会把所有已经提交但尚未写入数据文件的操作，根据 Redo Log 的记录重新执行一遍（Redo），从而将数据恢复到崩溃前的最终状态，保证了已提交数据的持久性。

**简单来说，Redo Log 就是一份“保险”，保证了即使发生意外，只要是提交了的操作，就一定能被恢复。**



### 3. 一致性 (Consistency) - 由 A、I、D 共同保证

一致性是 ACID 中最抽象、也是最终极的目标。它指的是事务的执行不能破坏数据库的完整性约束，必须使数据库从一个**一致的（合法的）状态**转变到另一个**一致的（合法的）状态**。

一致性不是由某一个单一机制来保证的，它是一个**综合性的结果**，依赖于：

1. **原子性（A）的保证**：如果事务执行到一半失败，原子性会通过 Undo Log 回滚所有操作，防止数据库出现“钱扣了但没到账”这种不一致的中间状态。
2. **隔离性（I）的保证**：如果多个事务并发执行，隔离性通过 MVCC 和锁机制防止它们互相干扰，从而避免产生不一致的结果（例如，两个事务同时修改库存导致最终数量错误）。
3. **持久性（D）的保证**：确保一旦事务成功提交，这个一致的新状态就不会丢失。
4. **数据库自身的约束**：
   - 主键约束、唯一约束
   - 外键约束（Referential Integrity）
   - 数据类型约束（例如，年龄字段不能存入字符串）
   - `NOT NULL` 约束

**所以，一致性是事务的终极目标，而原子性、隔离性和持久性是实现这个目标的手段和基石。**

### 4. 隔离性 (Isolation) - 由 MVCC 和锁保证

隔离性解决的是并发事务互相影响的问题。没有隔离性时，可能出现脏读、不可重复读、幻读、丢失更新等问题。

InnoDB 主要用两类机制保证隔离性：

1. **MVCC**：普通一致性读通过 Read View 读取符合可见性规则的历史版本，减少读写互相阻塞。
2. **锁机制**：当前读和写操作通过记录锁、间隙锁、Next-Key Lock、意向锁等控制并发修改。

不同隔离级别侧重点不同：

| 隔离级别 | 典型可见性 | 主要问题 |
| --- | --- | --- |
| READ UNCOMMITTED | 可能读到未提交数据 | 脏读 |
| READ COMMITTED | 每次读看到已提交的新版本 | 不可重复读 |
| REPEATABLE READ | 事务内快照读可重复 | 当前读仍需锁处理幻读 |
| SERIALIZABLE | 近似串行执行 | 并发能力最低 |

在 MySQL InnoDB 默认的 REPEATABLE READ 下：

1. 普通 `SELECT` 是快照读，通过事务首次一致性读生成的 Read View 保证可重复读。
2. `SELECT ... FOR UPDATE`、`UPDATE`、`DELETE` 是当前读，读取最新版本并加锁。
3. 范围当前读通常用 Next-Key Lock 锁住记录和间隙，避免其他事务插入新记录造成幻读。

面试里可以总结：隔离性不是单靠锁或单靠 MVCC，而是二者配合。MVCC 解决读写并发，锁解决写写冲突和当前读下的范围一致性。

### 4.0 MySQL 默认隔离级别和读已提交的问题

MySQL InnoDB 默认隔离级别通常是 `REPEATABLE READ`。可以用下面命令确认：

```sql
SELECT @@transaction_isolation;
```

`READ COMMITTED` 的特点是每次一致性读都会生成新的 Read View，所以它不会读到未提交事务的数据，但仍可能出现：

1. **不可重复读**：同一事务内两次读取同一行，第二次可能看到其他事务已经提交的新值。
2. **幻读**：同一事务内两次范围查询，第二次可能看到其他事务新插入或删除后提交的行。
3. **写偏斜风险**：两个事务分别读到满足条件的快照后，各自更新不同记录，最终破坏跨行约束。
4. **业务读写不一致**：读写分离场景下，如果读从库，还可能叠加主从复制延迟。

如果业务使用 RC，要根据场景处理：

1. 对单行并发更新，用条件更新、版本号或 `SELECT ... FOR UPDATE`。
2. 对范围约束，用唯一索引、状态机、业务幂等表或显式锁兜底。
3. 对写后读，读主库或等待 GTID/位点。
4. 对强一致交易链路，不要只依赖普通快照读，要用当前读、行锁、唯一约束和事务边界。

### 4.1 幻读是什么，怎么解决

幻读是指同一个事务内，两次按相同范围条件读取，第二次多出了或少了满足条件的记录，像“出现了幻影行”。它和不可重复读的区别是：不可重复读关注同一行内容变化，幻读关注结果集行数变化。

典型例子：

```sql
-- 事务 A
SELECT * FROM orders WHERE amount > 100;

-- 事务 B
INSERT INTO orders(id, amount) VALUES(10, 200);
COMMIT;

-- 事务 A 再次读取相同范围，发现多了一行
SELECT * FROM orders WHERE amount > 100;
```

InnoDB 中要区分快照读和当前读：

1. **快照读**：普通 `SELECT` 在 RR 下通过 MVCC 的 Read View 保证同一事务内读取同一份快照，通常看不到其他事务新插入的数据。
2. **当前读**：`SELECT ... FOR UPDATE`、`LOCK IN SHARE MODE`、`UPDATE`、`DELETE` 要读最新数据并加锁，范围条件下通过 Next-Key Lock 锁住记录和间隙，阻止其他事务插入幻影行。
3. **Serializable**：更强的隔离级别，通过更保守的锁让并发效果接近串行，但并发性能最低。

易错点：

1. 不能简单说“MVCC 完全解决幻读”。在 InnoDB RR 下，普通快照读主要靠 MVCC，当前读防幻读靠 Next-Key Lock / Gap Lock。
2. MySQL 的 RR 比 SQL 标准 RR 更强一些，配合 MVCC 和 Next-Key Lock 能处理很多幻读场景。
3. 在 RC 隔离级别下，InnoDB 一般减少间隙锁使用，并发更好，但范围当前读更容易出现幻读，需要业务接受或显式加锁。

### 4.2 RR 为什么说是“部分解决幻读”

说 InnoDB 的 `REPEATABLE READ` 部分解决幻读，是因为要区分快照读和当前读：

1. 普通 `SELECT` 是快照读，同一事务内复用 Read View，所以事务开始后其他事务新插入并提交的记录通常不可见。从“多次普通查询结果一致”这个角度看，幻读被 MVCC 屏蔽了。
2. `SELECT ... FOR UPDATE`、`UPDATE`、`DELETE` 是当前读，需要读最新已提交版本并加锁。它不能只读旧快照，否则后续写入会基于过期数据。
3. 当前读要防止范围内再插入新记录，依赖的是 Next-Key Lock / Gap Lock，而不是 MVCC 本身。

典型场景：

```sql
-- 表 t(id primary key, status int)，当前没有 id = 10

-- 事务 A，RR
BEGIN;
SELECT * FROM t WHERE id = 10; -- 普通快照读，未查到

-- 事务 B
INSERT INTO t(id, status) VALUES(10, 1);
COMMIT;

-- 事务 A
SELECT * FROM t WHERE id = 10;            -- 普通快照读，仍通常查不到
SELECT * FROM t WHERE id = 10 FOR UPDATE; -- 当前读，可以查到 B 已提交记录并加锁
COMMIT;
```

这个例子里，A 第一次普通查询没有加锁，也没有锁住 `id = 10` 所在间隙，所以 B 可以插入并提交。A 后续普通查询仍读自己的旧快照；但 A 后续执行 `FOR UPDATE` 是当前读，会读取最新已提交记录，因此能看到 B 插入的行。

如果 A 一开始执行的是范围当前读：

```sql
BEGIN;
SELECT * FROM t WHERE id BETWEEN 1 AND 20 FOR UPDATE;
```

在 RR 下 InnoDB 会尝试对扫描到的记录和相关间隙加 Next-Key Lock，B 再插入 `id = 10` 可能被阻塞。这个差异就是面试里最容易混淆的点：普通读靠 Read View 保持一致，锁定读靠锁阻止并发插入。

### 5. 面试回答模板

ACID 分别是原子性、一致性、隔离性、持久性。InnoDB 中原子性靠 undo log 回滚，持久性靠 redo log 和 WAL，隔离性靠 MVCC + 锁，一致性是最终目标，由 A/I/D 加数据库约束共同保证。隔离性里，普通一致性读通过 Read View 读历史版本，写操作和当前读通过行锁、间隙锁、Next-Key Lock 保证并发正确。RR 下普通快照读能让同一事务多次查询结果稳定，但当前读仍会读最新已提交版本；要防止范围幻读，需要依赖 Next-Key Lock / Gap Lock。
