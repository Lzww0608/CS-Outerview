# 8. 索引失效与最左前缀

索引失效是指 SQL 中虽然存在索引，但优化器无法有效利用索引定位数据，最终退化为全表扫描、全索引扫描、额外排序或大量回表。

## 最左前缀法则

联合索引 `(a, b, c)` 的 B+ 树排序规则是：

```text
先按 a 排序，a 相同再按 b 排序，b 相同再按 c 排序
```

因此查询必须从最左列开始连续使用索引，才能利用联合索引的有序性。

可以较好利用索引：

```sql
WHERE a = 1
WHERE a = 1 AND b = 2
WHERE a = 1 AND b = 2 AND c = 3
WHERE a = 1 AND b > 2
```

不能完整利用索引：

```sql
WHERE b = 2
WHERE b = 2 AND c = 3
WHERE a > 1 AND b = 2
WHERE a = 1 AND c = 3
```

`WHERE a = 1 AND c = 3` 可以利用联合索引的 `a` 做定位，但跳过了 `b`，`c` 通常不能继续作为索引定位条件，只能在扫描 `a = 1` 的范围时做过滤，或通过 ICP 在存储引擎层减少回表。

`WHERE a > 1 AND b = 2` 中，`a > 1` 是范围条件，通常只能用到 `a` 的范围定位，`b` 很难继续用于精确缩小扫描范围，但可能用于 ICP 或覆盖索引减少回表。

### 联合索引 `(a, b, c)` 的面试判断题

如果索引是：

```sql
CREATE INDEX idx_abc ON t(a, b, c);
```

常见追问可以这样判断：

| 查询条件 | 能否利用索引定位 | 说明 |
| --- | --- | --- |
| `a = ? AND b > ? AND c = ?` | 通常用到 `a` 和 `b` 范围 | `b` 是范围条件，`c` 不能继续用于缩小 B+ 树扫描范围，但可能用于 ICP 或覆盖索引过滤 |
| `a = ? AND c = ?` | 通常只用到 `a` | 跳过了 `b`，`c` 不能作为连续前缀定位条件 |
| `b = ? AND c = ?` | 通常不能用 `idx_abc` 做有效定位 | 缺少最左列 `a`，不满足最左前缀 |
| `a = ? AND b = ? AND c = ?` | 可以完整利用 | 三列都是连续等值条件 |
| `a > ? AND b = ? AND c = ?` | 通常只用到 `a` 范围 | 最左列已经是范围，后续列难以继续定位 |

注意：优化器可能在 `Extra` 中显示 `Using index condition`，这表示存储引擎层可以用后续列做过滤，减少回表，但它不等同于“后续列也用于 B+ 树范围定位”。面试里最好把“定位范围”“过滤”“覆盖索引”三件事分开说。

### `WHERE B > 10 AND A = 1 AND C < 20` 用到哪些列

假设有联合索引：

```sql
CREATE INDEX idx_abc ON t(A, B, C);
```

SQL 写成：

```sql
SELECT *
FROM t
WHERE B > 10
  AND A = 1
  AND C < 20;
```

判断结果：

1. 优化器会按逻辑条件重排，不受 `WHERE` 中书写顺序影响。
2. B+ 树定位通常用到 `A = 1` 和 `B > 10`：先定位到 `A = 1` 的区间，再在该区间里扫描 `B > 10` 的范围。
3. `C < 20` 不能继续缩小 B+ 树扫描范围，因为 `B` 已经是范围条件；但 `C` 在联合索引里，可能通过 ICP 在存储引擎层过滤，或者在覆盖索引场景直接用索引列判断。

可以这样总结：

| 字段 | 作用 |
| --- | --- |
| `A` | 等值定位，命中最左前缀 |
| `B` | 范围定位，决定扫描区间 |
| `C` | 通常不能继续定位，只能过滤；可能参与 ICP 或覆盖索引 |

如果 `EXPLAIN` 里 `key=idx_abc` 且 `Extra=Using index condition`，不要把它理解成 `C` 也参与了索引范围查找。更准确的说法是：`C` 没有参与 B+ 树的起止边界计算，但可以在扫描二级索引时提前判断，减少不必要的回表。

### Server 层和存储引擎层分别做什么

还是以上面的 SQL 为例，MySQL 大致执行链路是：

1. **Server 层**：解析 SQL、做权限检查、语义分析、条件等价改写和成本估算。
2. **优化器**：选择 `idx_abc`，生成范围条件，例如 `A = 1 AND B > 10`，判断是否可以使用 ICP、是否需要回表、是否可能覆盖索引。
3. **存储引擎层**：根据范围条件在 InnoDB B+ 树中定位到起始位置，沿叶子节点顺序扫描满足 `A = 1 AND B > 10` 的索引项。
4. **索引下推**：如果启用 ICP，InnoDB 在二级索引扫描阶段用索引中的 `C` 判断 `C < 20`，不满足的记录尽量不回表。
5. **回表或覆盖**：如果查询列不都在二级索引里，InnoDB 根据二级索引叶子里的主键回到聚簇索引取整行；如果是覆盖索引，则不需要回表。
6. **Server 层最终处理**：对存储引擎返回的行做剩余条件判断、投影、排序、聚合、LIMIT 等，再返回客户端。

面试回答要把三个概念拆开：索引范围定位决定扫描多少索引项，ICP 决定能否在引擎层提前过滤，覆盖索引决定是否需要回表。

## 常见索引失效原因

1. **不满足最左前缀**：联合索引跳过左侧列。
2. **在索引列上使用函数或表达式**：

```sql
WHERE DATE(create_time) = '2026-02-16'
WHERE age + 1 = 20
```

可以改成范围条件：

```sql
WHERE create_time >= '2026-02-16'
  AND create_time <  '2026-02-17'
```

3. **隐式类型转换**：

```sql
WHERE phone = 13800138000 -- phone 是 varchar
```

可能导致列被转换后比较，应写成：

```sql
WHERE phone = '13800138000'
```

4. **前导模糊匹配**：

```sql
WHERE name LIKE '%abc'
```

`LIKE 'abc%'` 才能利用 B+ 树前缀有序性。

5. **OR 条件部分无索引**：`OR` 两边只要有一边无法用索引，整体可能退化。
6. **负向条件选择性差**：`!=`、`NOT IN`、`IS NOT NULL` 往往命中大量数据，优化器可能不用索引。
7. **低选择性字段**：性别、状态这类字段区分度低，单独建索引收益有限。
8. **排序方向或字段不匹配**：`ORDER BY` 不符合联合索引顺序时可能 filesort。
9. **返回行太多**：即使用索引，如果优化器估算回表成本太高，也可能选择全表扫描。

## SQL 优化思路

1. 用 `EXPLAIN` 看 `type`、`key`、`rows`、`Extra`。
2. 让高频查询条件匹配联合索引最左前缀。
3. 高选择性字段放在联合索引更靠前的位置，但还要兼顾等值、范围、排序。
4. 尽量使用覆盖索引，减少回表。
5. 避免 `SELECT *`，只查需要字段。
6. 大分页改为基于游标或上一页最后一个 key 查询。
7. 对复杂查询考虑拆 SQL、临时表、冗余字段、ES/OLAP 等方案。

## 让索引生效的 SQL 怎么写

假设有联合索引：

```sql
CREATE INDEX idx_user_status_time
ON orders(user_id, status, created_at);
```

较好的写法：

```sql
SELECT id, amount, created_at
FROM orders
WHERE user_id = 10001
  AND status = 1
  AND created_at >= '2026-04-01'
  AND created_at <  '2026-05-01'
ORDER BY created_at
LIMIT 50;
```

原因：

1. `user_id`、`status` 命中联合索引最左侧等值条件。
2. `created_at` 用范围条件，避免对列做函数。
3. `ORDER BY created_at` 和索引顺序一致，可以减少额外排序。
4. 查询字段尽量少，有机会形成覆盖索引。

不好的写法：

```sql
SELECT *
FROM orders
WHERE DATE(created_at) = '2026-04-01'
  AND status = 1;
```

问题：

1. 跳过了联合索引最左列 `user_id`。
2. 对 `created_at` 使用函数，B+ 树中原始有序值难以直接定位。
3. `SELECT *` 增加回表和 I/O 成本。

再比如字符串列要避免隐式类型转换：

```sql
-- phone 是 varchar，错误写法可能导致索引失效
WHERE phone = 13800138000

-- 正确写法
WHERE phone = '13800138000'
```

## 易错点

1. 有索引不代表一定会用索引，优化器会基于成本选择执行计划。
2. 联合索引不是每个字段都能独立高效使用，顺序非常重要。
3. 范围查询后的列不一定能继续用于定位，但可能仍能用于覆盖索引或 ICP。
4. `EXPLAIN` 是估算结果，真实线上还要结合慢 SQL、执行耗时、扫描行数和 buffer pool 命中率。
5. 联合索引 `(A,B,C)` 只给 `A,C` 时，不是完全不能用索引，而是通常只能用到 `A` 的连续前缀，`C` 不能跳过 `B` 直接定位。
