# 1. 时序数据库存储引擎设计

时序数据库面向的是带时间戳的数据，例如监控指标、IoT 采样、交易行情、日志指标和用户行为计数。它的特点是写入量大、按时间范围查询多、旧数据可过期清理、压缩收益高。

## 1. 数据模型

常见模型：

```text
metric: cpu_usage
tags:   host=web-1, region=shenzhen, app=pay
fields: value=0.83
time:   2026-04-26T12:00:00Z
```

核心设计是把数据按 metric、tag、time 组织，既支持按标签过滤，也支持按时间范围顺序扫描。

## 2. 写入路径

高性能写入通常采用 LSM 思路：

```text
写请求
  -> WAL
  -> MemTable / 内存 buffer
  -> 按时间分区刷成不可变文件
  -> 后台 compaction / 压缩
```

这样可以把随机小写变成顺序写。WAL 用于崩溃恢复，MemTable 满后生成 segment 或 SSTable 类文件。

## 3. 分区和索引

1. **时间分区**：按小时、天、周切分，方便范围查询和过期删除。
2. **标签倒排索引**：`tag=value -> series_id set`，快速定位时间序列。
3. **series id**：把 metric + tags 映射成内部 ID，减少重复存储。
4. **块索引**：每个数据块记录最小/最大时间、偏移、压缩方式，查询时跳过无关块。

查询流程：

```text
tag filter -> series_id 集合 -> time partition -> block index -> 解压扫描 -> 聚合
```

## 4. 压缩机制

时序数据通常相邻时间和值变化平稳，适合压缩：

1. **时间戳 delta-of-delta**：时间间隔稳定时，二阶差分很小。
2. **值压缩**：Gorilla XOR、RLE、字典编码、浮点差分。
3. **列式存储**：时间列、值列、标签列分开压缩和读取。
4. **降采样**：旧数据保留分钟级、小时级聚合，删除秒级明细。

压缩要平衡 CPU 和查询延迟。热点数据可以压缩轻一点，冷数据压缩重一点。

## 5. 过期清理和冷热分层

时序数据库通常有 retention policy：

1. 热数据保留在 SSD 和内存索引中。
2. 温数据放低成本磁盘。
3. 冷数据降采样或归档到对象存储。
4. 过期分区直接删除整个目录或文件，避免逐行删除。

按时间分区的好处是清理成本低，只要删除过期 partition，元数据更新也简单。

## 6. 易错点

1. tag 基数过高会导致 series 数爆炸，例如把 user_id 当 tag。
2. 小文件太多会增加 compaction 和元数据压力。
3. 压缩率高不等于查询快，解压 CPU 也可能成为瓶颈。
4. 乱序写会破坏顺序写和压缩效果，需要设置乱序窗口或单独合并。
5. 查询跨度太大时要使用降采样结果，不应扫描多年明细。

## 7. 面试回答模板

时序数据库存储引擎我会按时间分区和 series 组织数据。写入先写 WAL，再进内存 buffer，后台刷成不可变文件并 compaction；索引用 metric/tags 映射到 series_id，再按时间分区和块索引定位数据。压缩上用时间戳 delta-of-delta、值 XOR/RLE、列式存储和降采样。过期清理通过 retention policy 删除整段时间分区，冷热分层把热数据放 SSD，冷数据归档对象存储。要特别注意高基数 tag、乱序写、小文件和长时间范围查询。
