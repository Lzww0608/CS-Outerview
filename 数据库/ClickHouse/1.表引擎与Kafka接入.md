# 1. 表引擎与 Kafka 接入

## 1. ClickHouse 表引擎是什么

ClickHouse 的表引擎决定一张表的数据如何存储、如何索引、如何复制、如何从外部系统读取数据。面试里问“表引擎分别是什么”，本质是在问这张表承担什么角色：是落盘明细表、分布式路由表、Kafka 消费表，还是聚合结果表。

常见引擎：

| 表引擎 | 作用 | 典型场景 |
| --- | --- | --- |
| `MergeTree` | 最核心的本地列式存储引擎 | 明细日志、事实表 |
| `ReplicatedMergeTree` | 带副本复制的 MergeTree | 生产集群高可用 |
| `Distributed` | 分布式查询和写入路由，不直接存储数据 | 跨 shard 查询入口 |
| `Kafka` | 从 Kafka 消费数据的流式引擎 | Kafka 到 ClickHouse 接入层 |
| `ReplacingMergeTree` | 按 key 合并新旧版本 | 去重、最终状态表 |
| `SummingMergeTree` | 合并时对数值列求和 | 预聚合指标 |
| `AggregatingMergeTree` | 保存聚合状态 | 多维分析预聚合 |

## 2. MergeTree 家族

`MergeTree` 是 ClickHouse 最常用的存储引擎。它按列存储数据，数据写入后形成多个 part，后台异步 merge。建表时最关键的是：

1. `PARTITION BY`：分区键，常按天/月分区，便于裁剪和 TTL 删除。
2. `ORDER BY`：排序键，也是稀疏主键索引的基础，决定查询跳数和压缩效果。
3. `PRIMARY KEY`：默认等于 `ORDER BY`，也可以单独指定更短前缀。
4. `TTL`：数据生命周期，日志场景常按时间清理。

示例：

```sql
CREATE TABLE log_detail_local
(
    event_time DateTime,
    dt Date,
    app_id UInt64,
    user_id UInt64,
    trace_id String,
    level LowCardinality(String),
    message String
)
ENGINE = MergeTree
PARTITION BY toYYYYMMDD(dt)
ORDER BY (app_id, event_time, user_id, trace_id)
TTL event_time + INTERVAL 30 DAY DELETE;
```

## 3. Kafka 表引擎

`Kafka` 引擎用于把 Kafka topic 暴露成 ClickHouse 表。它本身通常不作为最终存储表，而是作为消费入口。真实落盘一般依赖物化视图写入 `MergeTree` / `ReplicatedMergeTree`。

典型链路：

```text
Kafka Topic
  -> Kafka Engine Table
  -> Materialized View
  -> MergeTree / ReplicatedMergeTree Local Table
  -> Distributed Table
```

示例：

```sql
CREATE TABLE log_kafka
(
    event_time DateTime,
    app_id UInt64,
    user_id UInt64,
    trace_id String,
    level String,
    message String
)
ENGINE = Kafka
SETTINGS
    kafka_broker_list = 'broker1:9092,broker2:9092',
    kafka_topic_list = 'app_log',
    kafka_group_name = 'clickhouse_log_consumer',
    kafka_format = 'JSONEachRow',
    kafka_num_consumers = 4;
```

通过物化视图写入本地表：

```sql
CREATE MATERIALIZED VIEW log_mv
TO log_detail_local
AS
SELECT
    event_time,
    toDate(event_time) AS dt,
    app_id,
    user_id,
    trace_id,
    level,
    message
FROM log_kafka;
```

## 4. ReplicatedMergeTree

生产环境通常不会只用单副本 `MergeTree`。`ReplicatedMergeTree` 通过 ClickHouse Keeper / ZooKeeper 协调多个副本的元数据和 part 复制。

示例：

```sql
CREATE TABLE log_detail_local ON CLUSTER ck_cluster
(
    event_time DateTime,
    dt Date,
    app_id UInt64,
    user_id UInt64,
    trace_id String,
    level LowCardinality(String),
    message String
)
ENGINE = ReplicatedMergeTree(
    '/clickhouse/tables/{shard}/log_detail_local',
    '{replica}'
)
PARTITION BY toYYYYMMDD(dt)
ORDER BY (app_id, event_time, user_id, trace_id);
```

副本的作用：

1. 节点故障时仍可读写，提高可用性。
2. 数据冗余，降低单机磁盘损坏风险。
3. 查询可以分摊到多个副本，提升读吞吐。
4. 维护、升级、重启时降低服务中断概率。

常见生产配置是每个 shard 2 到 3 个 replica。2 副本是成本和可用性的常见平衡；3 副本容错更好，但存储和写入放大更明显。

## 5. Distributed 表

`Distributed` 表是逻辑表，用于把查询或写入路由到多个 shard 的本地表：

```sql
CREATE TABLE log_detail_all ON CLUSTER ck_cluster
AS log_detail_local
ENGINE = Distributed(
    ck_cluster,
    default,
    log_detail_local,
    cityHash64(user_id)
);
```

它不直接存储数据，真正数据仍在各节点的本地 `MergeTree` / `ReplicatedMergeTree` 表里。

## 6. Kafka 到 ClickHouse 的一致性注意事项

1. Kafka 引擎消费后通常按 block 写入 ClickHouse，失败重试可能导致重复写入。
2. 不要默认 Kafka 到 ClickHouse 是严格 exactly-once，日志场景更常按 at-least-once 设计。
3. 如果业务不能接受重复，要使用业务唯一键、`ReplacingMergeTree`、去重 token 或离线去重。
4. 物化视图中要做字段解析、类型转换和脏数据处理，避免一条坏数据阻塞消费。
5. Kafka topic 的 partition 数应不小于 ClickHouse 消费并行度，否则 `kafka_num_consumers` 再大也无法提高消费能力。

## 7. 面试回答模板

Kafka 进 ClickHouse 通常不是直接落到最终表，而是用 ClickHouse 的 `Kafka` 表引擎作为消费入口，再通过 Materialized View 写入 `MergeTree` 或 `ReplicatedMergeTree` 明细表。明细表用 `PARTITION BY` 按日期分区，`ORDER BY` 按高频查询条件设计排序键。生产集群一般每个 shard 做 2 到 3 个 replica，用 `ReplicatedMergeTree` 保证高可用；跨 shard 查询对外暴露 `Distributed` 表。需要注意 Kafka 到 ClickHouse 通常按 at-least-once 处理，要考虑重复数据、脏数据和消费并行度。
