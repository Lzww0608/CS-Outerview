# 2. SkipList 与适用场景

LevelDB 是一个嵌入式有序 KV 存储，核心结构是 LSM Tree。写入先进入 WAL 和 MemTable，MemTable 写满后刷成 SSTable，再由后台 compaction 合并。

## 1. 为什么 MemTable 选择 SkipList

LevelDB 的 MemTable 底层使用 SkipList，主要是因为它适合内存中的有序写入和范围遍历。

SkipList 的特点：

1. 平均查找、插入、删除复杂度是 `O(log n)`。
2. 节点按 key 有序，天然支持顺序遍历和范围查询。
3. 插入时只需要随机生成层高并修改局部指针，实现比红黑树简单。
4. 对并发读友好，LevelDB 的 MemTable 写入受外层写锁保护，读路径可以较少依赖复杂旋转维护。
5. 刷盘生成 SSTable 时可以直接按顺序遍历 SkipList，输出有序数据。

为什么不是哈希表：

1. 哈希表无序，不适合范围查询。
2. SSTable 要求 key 有序，哈希表刷盘前还要额外排序。
3. LSM Tree 的 compaction 本质是有序归并，前台内存结构保持有序能简化后续流程。

为什么不是红黑树：

1. 红黑树也能有序，但旋转和重平衡实现更复杂。
2. SkipList 依赖随机层数实现概率平衡，工程实现短小直接。
3. SkipList 顺序遍历和并发扩展更容易做工程优化。

## 2. LevelDB 适合什么场景

适合：

1. 本地嵌入式 KV 存储，不需要单独部署数据库服务。
2. 写多读少或写入吞吐要求高的场景。
3. key 有序、需要范围扫描的场景。
4. 元数据、本地缓存、消息队列索引、小型状态库。
5. 可以接受最终刷盘和后台 compaction 抖动的场景。

不适合：

1. 多机分布式事务和强一致 SQL 查询。
2. 复杂二级索引、JOIN、聚合分析。
3. 多进程同时写同一个数据库目录。
4. 超高并发远程服务，如果没有额外封装网络层、分片和副本。
5. 对尾延迟极敏感且无法容忍 compaction 抖动的场景。

## 3. 作为日志存储时 LevelDB 和 WAL 的区别

WAL 是追加日志，LevelDB 是完整 KV 存储。二者都用顺序写提升性能，但目标不同。

| 对比项 | WAL | LevelDB |
| --- | --- | --- |
| 主要目标 | 崩溃恢复、顺序追加 | 持久化有序 KV 查询 |
| 写入方式 | 追加 record | 先 WAL，再 MemTable，再 SSTable |
| 读取能力 | 通常按 offset 顺序读 | 按 key 点查、范围扫 |
| 删除更新 | 需要上层定义格式和清理策略 | 用 sequence number、tombstone 和 compaction 处理 |
| 空间回收 | 日志截断或分段删除 | 后台 compaction 回收旧版本 |
| 复杂度 | 简单、吞吐高 | 查询能力强，但 compaction 更复杂 |

如果只需要“按顺序追加、按顺序回放”，WAL 更简单；如果需要“按 key 查询最新值、范围扫描、崩溃恢复、空间回收”，LevelDB 更合适。很多系统会同时使用两者：WAL 保证崩溃恢复，LSM/LevelDB 结构提供查询能力。

## 4. 易错点

1. LevelDB 不是关系型数据库，也不是分布式数据库。
2. WAL 写成功不等于数据已经进入 SSTable，崩溃后需要重放 WAL。
3. LSM Tree 写入快，但读可能要查 MemTable、Immutable MemTable、多个 SSTable 和 block cache。
4. compaction 会带来写放大和尾延迟抖动，需要监控 pending compaction、磁盘 IO 和 level 文件数量。
5. SkipList 的 `O(log n)` 是概率意义上的平均复杂度，不是严格平衡树保证。

## 5. 面试回答模板

LevelDB 的 MemTable 选 SkipList，是因为它在内存里能用较简单的实现提供平均 `O(log n)` 的查找和插入，同时保持 key 有序，方便范围查询和后续顺序刷盘生成 SSTable。LevelDB 适合嵌入式、本地、有序 KV、写入较多的场景，不适合复杂 SQL、分布式事务和多进程写。作为日志存储时，如果只是追加和回放，用 WAL 更简单；如果还要按 key 查询最新值、范围扫和自动回收旧版本，LevelDB 更合适，但要承担 compaction 和写放大的成本。
