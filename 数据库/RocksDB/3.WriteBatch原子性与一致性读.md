# 3. WriteBatch 原子性与一致性读

## 1. 问题背景

RocksDB 是典型的 LSM-Tree KV 存储引擎。写入先进入 WAL，再进入 MemTable；MemTable flush 后生成 SSTable，后台 compaction 负责归并多版本数据。面试里问 `WriteBatch` 和一致性读，本质是在问三个问题：

1. 多个 `Put/Delete/Merge` 放进同一个 `WriteBatch` 后，RocksDB 如何保证它们作为一个逻辑批次提交。
2. 崩溃恢复时，如何避免只恢复半个 batch。
3. 并发读写时，读请求如何在 MemTable、Immutable MemTable 和 SSTable 中看到同一个时间点的数据。

RocksDB 的核心机制是 **WAL batch 边界 + 连续 sequence number + snapshot sequence + internal key 多版本可见性**。

**假设条件**：

1. 本文讨论 RocksDB 普通 `DB` 写入路径，不展开 `TransactionDB`、`WritePrepared`、`WriteUnprepared` 的事务协议。
2. `WriteBatch` 指 RocksDB 原生批量写接口，包含多个 key 的写操作。
3. 一致性读指 RocksDB snapshot 语义下的读一致性，不等价于关系型数据库的可串行化事务。
4. MemTable 以 SkipList 或其他有序结构保存 internal key，internal key 包含 `user_key + sequence + value_type`。
5. 不讨论跨多个 RocksDB 实例、分布式副本或上层业务事务的一致性。

## 2. 问题现象

如果没有这些机制，会出现以下问题：

1. **半个 batch 可见**：一个 `WriteBatch` 中有 10 条写入，读请求可能看到前 5 条，看不到后 5 条。
2. **崩溃后部分恢复**：WAL 里只重放了 batch 的一部分，导致多个 key 的业务约束被破坏。
3. **MemTable 并发读不一致**：写线程正在插入 batch，读线程扫 MemTable 时读到中间状态。
4. **新旧版本混读**：同一次读请求在 MemTable 读到新版本，在 SSTable 又读到不该可见的旧版本。
5. **Delete 语义错误**：读请求忽略 tombstone，导致删除后的旧值从低层 SSTable 复活。
6. **Snapshot 失效**：创建 snapshot 后，后续写入仍然被该 snapshot 读到。
7. **WAL 关闭后的误解**：业务以为 batch 原子就等于断电后不丢，但 `disableWAL` 或未 `sync` 时持久性语义不同。

一个典型业务例子：

```text
WriteBatch:
  Put(user:1:name, "Alice")
  Put(user:1:index:email, "alice@example.com")
  Delete(user:1:old_index:email)

如果只写入部分 key 可见，主数据和二级索引就会不一致。
```

## 3. 影响范围

该问题影响 RocksDB 的核心读写链路：

1. **WriteBatch 编码**：batch 内操作数量、sequence 起点、record 边界。
2. **WriteThread / Group Commit**：多个写线程如何排队、合并写 WAL、分配 sequence number。
3. **WAL**：保证恢复时按 batch 边界重放，尾部不完整记录丢弃。
4. **MemTable 插入**：把 batch 中每条操作编码为带 sequence 的 internal key。
5. **Snapshot 管理**：读请求确定可见的最大 sequence number。
6. **Get / MultiGet / Iterator**：按 snapshot sequence 在多层结构中选择可见版本。
7. **SuperVersion**：读请求持有一组稳定的 MemTable、Immutable MemTable 和 Version 视图。
8. **Compaction**：根据 snapshot 和 sequence 判断旧版本、tombstone 是否可以清理。

如果涉及代码实现，可能需要修改的模块包括：

1. `write_batch.cc`：WriteBatch 编码、解码、迭代和 count 校验。
2. `db_impl_write.cc`：写线程排队、group commit、sequence 分配、WAL 写入、MemTable 插入。
3. `log_writer.cc` / `log_reader.cc`：WAL record 写入、checksum、分片和恢复读取。
4. `memtable.cc`：把 batch 写入 MemTable，并按 internal key 查询。
5. `snapshot_impl.cc`：snapshot sequence 分配、引用和释放。
6. `db_iter.cc` / `merging_iterator.cc`：根据 snapshot sequence 合并多层版本。
7. `version_set.cc`：发布 last sequence 和 SuperVersion。
8. `db_test` / `write_batch_test`：补充崩溃恢复、并发读写和 snapshot 测试。

## 4. 原因分析

### 4.1 WriteBatch 为什么需要原子性

`WriteBatch` 往往承载多个 key 的逻辑一致性，例如主记录和索引记录一起更新、多个计数器一起写入、删除旧值并写入新值。如果 batch 中的操作被读请求部分看到，或者崩溃恢复后只恢复一部分，就会破坏上层业务约束。

RocksDB 不提供关系型数据库那种通用事务隔离，但它必须保证同一个 `WriteBatch` 的提交边界清晰：

```text
成功提交后：batch 中所有操作都可见
提交失败后：batch 中所有操作都不可见
崩溃恢复后：完整 batch 被重放，不完整尾部被丢弃
```

### 4.2 一致性读为什么依赖 Sequence Number

LSM-Tree 中同一个 user key 可能同时存在多个版本：

```text
k@seq=105, type=delete
k@seq=100, type=value, value=v1
k@seq=080, type=value, value=v0
```

如果读请求没有一个明确的时间点，就无法判断该返回哪个版本。RocksDB 用全局递增 sequence number 表示写入顺序，用 snapshot sequence 表示读请求的可见上界：

```text
读请求只能看到 sequence <= snapshot_seq 的版本
同一个 user key 返回不超过 snapshot_seq 的最新版本
```

### 4.3 MemTable 为什么也能做一致性读

MemTable 不是简单的哈希表 `key -> value`，而是保存带版本的 internal key。它的排序规则大致是：

```text
user_key 升序
sequence 降序
value_type 参与比较
```

因此，同一个 user key 的新版本排在旧版本前面。读取时用 `LookupKey(user_key, snapshot_seq)` 定位到不大于 snapshot sequence 的最新版本，遇到 value 就返回，遇到 delete marker 就返回 NotFound。

### 4.4 Batch 部分插入 MemTable 时为什么不会被读到

这是面试里容易追问的点。

写线程可能已经把 batch 的一部分插入 MemTable，但还没全部插入完成。如果此时读线程遍历 MemTable，会不会看到半个 batch？

关键在于：**RocksDB 只有在 batch 写 WAL 并插入 MemTable 完成后，才发布新的 last sequence。普通读请求获取的 read sequence 不会超过已经发布的 last sequence。**

假设当前已发布 `last_sequence = 100`，某个 batch 分配到 `101~110`：

```text
1. 写线程开始写 WAL
2. 写线程把 batch 插入 MemTable，期间部分 key@101..110 可能已经在 MemTable 中
3. 但 last_sequence 仍然是 100
4. 并发读请求如果没有显式 snapshot，只能拿到 read_seq = 100
5. 读 MemTable 时会忽略 sequence > 100 的记录
6. batch 完整插入后，系统发布 last_sequence = 110
7. 后续读请求 read_seq = 110，才能看到整个 batch
```

所以一致性读并不是靠“读线程完全看不到正在插入的 MemTable entry”，而是靠 sequence 可见性过滤掉未发布版本。

## 5. 解决方案

### 5.1 WriteBatch 编码 batch 边界

`WriteBatch` 会把多条操作编码到一个批次中。逻辑结构可以理解为：

```text
WriteBatch:
  header:
    sequence_start
    count
  records:
    Put(key1, value1)
    Delete(key2)
    Merge(key3, operand)
```

其中：

1. `sequence_start` 是该 batch 第一条操作的 sequence number。
2. `count` 是 batch 内操作数量。
3. 每条 record 带有操作类型和 key/value 数据。
4. batch 内第 `i` 条操作的 sequence 可以理解为 `sequence_start + i`。

这样 WAL 重放时可以知道 batch 边界和每条操作的顺序。

### 5.2 先 WAL 后 MemTable

RocksDB 写入路径的核心顺序是：

```text
1. 写线程进入 WriteThread 队列
2. leader 组织一个 write group
3. 给 group 中每个 batch 分配连续 sequence range
4. 把 batch 或 group 写入 WAL
5. WAL 成功后，把 batch 插入 MemTable
6. MemTable 插入成功后，发布新的 last sequence
7. 唤醒等待的写线程
```

伪代码：

```cpp
Status WriteImpl(WriteBatch *batch, const WriteOptions &options) {
  Writer *w = write_thread.JoinBatchGroup(batch);
  if (!w->is_leader) {
    return write_thread.Wait(w);
  }

  WriteGroup group = write_thread.BuildBatchGroup(w);
  SequenceNumber start = versions_->LastSequence() + 1;
  AssignSequenceNumbers(group, start);

  Status s = log_writer->AddRecord(group.SerializedBatch());
  if (s.ok() && options.sync) {
    s = log_file->Sync();
  }

  if (s.ok()) {
    s = InsertIntoMemTables(group);
  }

  if (s.ok()) {
    versions_->SetLastSequence(start + group.Count() - 1);
  }

  write_thread.ExitBatchGroup(group, s);
  return s;
}
```

真实 RocksDB 实现会更复杂，例如并发写 MemTable、two write queues、unordered write、manual WAL flush 等，但核心语义仍是：**WAL 和 sequence 边界先确定，MemTable 可见性通过 last sequence 发布控制**。

### 5.3 WAL 如何保证恢复原子性

WAL record 通常有长度、类型和 checksum。一个大的 batch 可能被物理切成多个 fragment，但逻辑上仍有完整 record 边界。恢复时：

```text
1. 顺序读取 WAL record
2. 校验 checksum 和长度
3. 解析 WriteBatch header 和 records
4. 如果 record 完整，就重放到 MemTable
5. 如果遇到不完整尾部或 checksum 错误，丢弃尾部
```

因此：

1. 完整写入 WAL 的 batch 会整体重放。
2. 未完整写入的 batch 不会被当成成功 batch 重放。
3. 如果 WAL 写入成功但 MemTable 未插入就崩溃，恢复时会从 WAL 重放。
4. 如果 WAL 都没成功，恢复时不会看到该 batch。

注意：这说的是崩溃恢复的 batch 原子性。是否断电后一定不丢，还要看 `WriteOptions::sync`、文件系统、磁盘缓存和 WAL flush 策略。

### 5.4 连续 Sequence Number 保证 Batch 可见性

假设 batch 中有 3 条操作：

```text
Put(a, 1)
Put(b, 2)
Delete(c)
```

分配 sequence：

```text
a@101
b@102
c@103
```

只有当 `last_sequence` 从 `100` 发布到 `103` 后，普通最新读才能看到这三个版本。发布前，即使 MemTable 里部分 entry 已经插入，读请求的 snapshot sequence 仍然是 `100`，因此不会看到 `101~103`。

这就是 MemTable 中避免 batch 半可见的关键。

### 5.5 Snapshot 一致性读

RocksDB 的显式 snapshot 可以理解为固定一个 read sequence：

```cpp
const Snapshot *s = db->GetSnapshot();
ReadOptions ro;
ro.snapshot = s;

db->Get(ro, key, &value);
db->ReleaseSnapshot(s);
```

如果 snapshot 创建时 `last_sequence = 100`，那么后续读请求只看：

```text
sequence <= 100
```

即使之后有写入：

```text
k@105 = v2
k@100 = v1
```

该 snapshot 仍然读到 `v1`。

### 5.6 MemTable 中如何查可见版本

MemTable 查询可以理解为：

```cpp
LookupKey lookup(user_key, snapshot_seq);
auto iter = memtable->Seek(lookup.internal_key());

while (iter.Valid() && SameUserKey(iter.key(), user_key)) {
  ParsedInternalKey ikey = Parse(iter.key());
  if (ikey.sequence > snapshot_seq) {
    iter.Next();
    continue;
  }
  if (ikey.type == kTypeDeletion) {
    return NotFound();
  }
  if (ikey.type == kTypeValue) {
    return ikey.value;
  }
  iter.Next();
}
```

实际实现会用更高效的编码和比较器，但原则是：

1. Seek 到 `user_key + snapshot_seq` 附近。
2. 找到不大于 snapshot sequence 的最新版本。
3. 对 delete marker、merge operand、value 类型分别处理。
4. 如果 MemTable 没找到，再查 Immutable MemTable 和 SSTable。

### 5.7 SuperVersion 保证读视图稳定

一次读不只查 MemTable，还会查 Immutable MemTable 和 SSTable。RocksDB 通过类似 `SuperVersion` 的结构，让读请求持有一组稳定引用：

```text
SuperVersion:
  current mutable memtable
  immutable memtable list
  current Version of SST files
```

这样即使后台发生 flush 或 compaction，读请求仍然能在自己的引用视图中完成查询，不会读到一半时底层文件集合被释放。

## 6. 可选方案对比

| 方案 | 原理 | 优点 | 缺点 | 适用场景 |
| --- | --- | --- | --- | --- |
| 单条写入 | 每次 Put/Delete 独立写 WAL 和 MemTable | 简单 | 多 key 无原子边界，吞吐低 | 简单 KV 写 |
| WriteBatch | 多条操作共享 batch 边界和 sequence range | 多 key 原子、吞吐高 | 不提供复杂事务隔离 | 主数据和索引一起更新 |
| Group Commit | 多个 writer 合并写 WAL | 降低 fsync 和锁开销 | 延迟可能受 group leader 影响 | 高并发写 |
| 显式 Snapshot | 固定 read sequence | 读视图稳定 | 长 snapshot 阻塞旧版本回收 | 备份、长扫描、一致性读取 |
| 默认 latest read | 读取当前已发布 last sequence | 使用简单，延迟低 | 多次读取之间不是同一快照 | 普通点查 |
| TransactionDB | 额外提供事务冲突检测和提交协议 | 更强语义 | 成本和复杂度更高 | 跨 key 事务 |

## 7. 推荐方案

如果是在项目中借鉴 RocksDB 设计，推荐采用以下原则：

1. **WriteBatch 必须有明确边界**  
   日志中保存 batch header、操作数量、record 类型和 checksum，恢复时只重放完整 batch。

2. **给 batch 分配连续 sequence range**  
   batch 内每条操作有确定顺序，读路径通过 sequence 判断可见性。

3. **先写 WAL，再写 MemTable**  
   WAL 成功后再修改内存结构，崩溃后可以重放。

4. **最后发布 commit sequence**  
   只有 MemTable 插入完成后，才把 `last_sequence` 推进到 batch 末尾，避免读到半个 batch。

5. **MemTable 保存 internal key 多版本**  
   不要用简单 `key -> value` 覆盖模型，否则 snapshot 和一致性读无法成立。

6. **读请求固定 read sequence**  
   无显式 snapshot 时使用当前已发布 sequence；有 snapshot 时使用 snapshot sequence。

7. **读视图要引用稳定的 MemTable/SSTable 集合**  
   防止 flush/compaction 期间文件或 MemTable 被提前释放。

面试回答模板：

```text
RocksDB 的 WriteBatch 原子性主要靠 WAL batch 边界、连续 sequence number 和写入顺序保证。
写线程先给 batch 分配连续 sequence，先写 WAL，再写 MemTable，最后发布 last sequence。
崩溃恢复时按 WAL 中完整 batch 边界重放，不完整尾部丢弃。
一致性读依赖 snapshot sequence，读请求只看 sequence <= read_seq 的版本。
MemTable 中保存的是 internal key，而不是简单 key-value，所以即使并发写正在插入 MemTable，未发布的高 sequence 也不会被当前读看到。
```

## 8. 实施步骤

### 8.1 实现 WriteBatch 编码

定义 batch 格式：

```cpp
struct BatchHeader {
  uint64_t sequence_start;
  uint32_t count;
};

enum class ValueType {
  kTypeValue,
  kTypeDeletion,
  kTypeMerge,
};

struct BatchRecord {
  ValueType type;
  std::string key;
  std::string value;
};
```

要求：

1. `count` 必须和 record 数量一致。
2. 编码要支持校验和边界检查。
3. 解码失败时不能部分应用。

### 8.2 实现写入提交顺序

核心流程：

```text
AssignSequence -> AppendWAL -> InsertMemTable -> PublishLastSequence
```

不要把 `PublishLastSequence` 放到 MemTable 插入之前。

错误示例：

```text
AssignSequence -> PublishLastSequence -> InsertMemTable
```

这样会导致读请求拿到新 read sequence，但 MemTable 里 batch 还没插完，从而读到部分结果或读不到应该可见的结果。

### 8.3 实现 MemTable Internal Key

Internal key 编码：

```cpp
struct InternalKey {
  std::string user_key;
  uint64_t sequence;
  ValueType type;
};
```

比较规则：

```text
先比较 user_key 升序；
user_key 相同时，sequence 降序；
必要时比较 value_type。
```

插入：

```cpp
memtable.Add(seq, kTypeValue, key, value);
memtable.Add(seq, kTypeDeletion, key, "");
```

### 8.4 实现 Snapshot

Snapshot 只需要记录创建时的 last sequence：

```cpp
class Snapshot {
 public:
  explicit Snapshot(uint64_t seq) : sequence_(seq) {}
  uint64_t sequence() const { return sequence_; }

 private:
  uint64_t sequence_;
};
```

读请求：

```cpp
uint64_t read_seq = options.snapshot != nullptr
                    ? options.snapshot->sequence()
                    : versions.LastPublishedSequence();
```

### 8.5 实现 MemTable 查询

查询时用 read sequence 过滤：

```cpp
Status MemTable::Get(const std::string &user_key,
                     uint64_t read_seq,
                     std::string *value) {
  InternalKey seek_key{user_key, read_seq, ValueType::kTypeValue};
  auto it = table_.lower_bound(seek_key);

  for (; it != table_.end(); ++it) {
    if (it->user_key != user_key) {
      break;
    }
    if (it->sequence > read_seq) {
      continue;
    }
    if (it->type == ValueType::kTypeDeletion) {
      return Status::NotFound();
    }
    *value = it->value;
    return Status::OK();
  }
  return Status::NotFound();
}
```

### 8.6 实现稳定读视图

读请求开始时引用当前视图：

```text
Ref current SuperVersion
-> read MemTable
-> read Immutable MemTables
-> read SSTables in Version
-> Unref SuperVersion
```

这样 flush 和 compaction 可以发布新版本，但旧版本要等读请求释放引用后才能销毁。

### 8.7 测试重点

如果涉及代码实现，测试重点包括：

1. **Batch 原子可见性测试**：并发读不能看到半个 WriteBatch。
2. **WAL 恢复测试**：完整 batch 重放，不完整尾部丢弃。
3. **Sequence 连续性测试**：batch 内 sequence 范围连续且顺序正确。
4. **Snapshot 测试**：snapshot 创建后，后续写入不可见。
5. **MemTable 多版本测试**：同一个 key 多次 Put/Delete，按 read sequence 返回正确版本。
6. **并发读写测试**：写线程插入 MemTable 时，读线程结果稳定。
7. **Flush/Compaction 并发测试**：读请求持有旧 SuperVersion 时，旧文件不能被释放。
8. **disableWAL 测试**：确认内存可见性和崩溃持久性边界。

## 9. 风险与注意事项

1. **WriteBatch 原子性不等于事务隔离**  
   普通 RocksDB WriteBatch 保证一个批次写入的原子提交边界，但不提供复杂事务冲突检测、回滚和可串行化隔离。

2. **原子可见不等于同步持久**  
   `WriteOptions::sync=false` 时，写成功返回后可能还没强制落盘。进程崩溃和机器断电的持久性边界不同。

3. **disableWAL 会改变恢复语义**  
   关闭 WAL 后，batch 可以在内存中原子应用，但崩溃后不能依赖 WAL 恢复。

4. **不能提前发布 last sequence**  
   如果先发布 sequence，再插入 MemTable，读请求可能认为新版本已提交，但实际只插入了一部分。

5. **MemTable 不能只存最新值**  
   覆盖式 `key -> value` 会破坏 snapshot，一旦覆盖旧值，老 snapshot 就无法读取旧版本。

6. **长 Snapshot 会阻塞回收**  
   snapshot sequence 很旧时，compaction 不能删除该 snapshot 仍可能读取的旧版本和 tombstone。

7. **Merge 操作比 Put/Delete 更复杂**  
   Merge operand 需要在读路径或 compaction 中按 sequence 合并，测试要覆盖。

8. **Iterator 也要固定 read sequence**  
   范围扫描不是每个 key 单独取最新值，而是整个 iterator 应该基于同一个 read sequence。

9. **SuperVersion 引用不能泄漏**  
   读请求忘记释放引用，会阻塞 MemTable/SSTable 回收，造成内存和空间膨胀。

## 10. 验证方式

### 10.1 WriteBatch 原子性验证

构造 batch：

```text
Put(a, 1)
Put(b, 2)
Put(c, 3)
```

验证：

1. 写成功后，`a/b/c` 全部可见。
2. 模拟 WAL 尾部损坏后恢复，batch 不应部分可见。
3. 并发读期间不能出现只看到 `a`、看不到 `b/c` 的情况。

### 10.2 Sequence 发布验证

测试流程：

```text
last_sequence = 100
batch 分配 101~110
在 MemTable 插入过程中并发读
```

预期：

1. batch 发布前，普通读的 read sequence 仍为 100，看不到 101~110。
2. batch 发布后，普通读 read sequence 为 110，看到整个 batch。

### 10.3 Snapshot 验证

```text
Put(k, v1)
snapshot = GetSnapshot()
Put(k, v2)

Get(k, snapshot) -> v1
Get(k, latest)   -> v2
```

再加入 delete：

```text
snapshot = GetSnapshot()
Delete(k)

Get(k, snapshot) -> 旧值
Get(k, latest)   -> NotFound
```

### 10.4 MemTable 多版本验证

构造：

```text
k@100 = v1
k@105 = v2
k@110 = delete
```

验证：

1. `read_seq=99` 返回 NotFound。
2. `read_seq=100` 返回 `v1`。
3. `read_seq=105` 返回 `v2`。
4. `read_seq=110` 返回 NotFound。

### 10.5 崩溃恢复验证

测试场景：

1. WAL 写完整，MemTable 未写完时崩溃，恢复后 batch 应完整可见。
2. WAL record 尾部不完整时崩溃，恢复后 batch 应整体不可见。
3. WAL checksum 错误时，不应重放损坏 batch。
4. `sync=false` 和 `sync=true` 分别测试持久化边界。

### 10.6 并发验证

并发压测：

```text
N 个写线程持续 WriteBatch
M 个读线程持续 Get/MultiGet/Iterator
后台持续 Flush/Compaction
周期性创建和释放 Snapshot
```

验证：

1. 没有半 batch 读。
2. Iterator 输出符合 snapshot。
3. Delete 不会让旧值复活。
4. Flush/Compaction 后结果不变。
5. 没有 data race、引用泄漏和内存增长异常。

## 11. 总结

RocksDB 的 `WriteBatch` 原子性和一致性读可以从两个层次理解。

写入层面：

1. `WriteBatch` 把多个操作编码为有边界的逻辑批次。
2. 写线程给 batch 分配连续 sequence number。
3. 写入顺序是先 WAL，再 MemTable。
4. MemTable 完整插入后才发布新的 last sequence。
5. 崩溃恢复时按 WAL 中完整 batch 重放，不完整尾部丢弃。

读取层面：

1. RocksDB 用 sequence number 表示版本顺序。
2. snapshot 固定 read sequence。
3. 读请求只看 `sequence <= read_seq` 的版本。
4. MemTable 保存 internal key，而不是简单 `key -> value`。
5. 同一次读持有稳定 SuperVersion，避免 flush/compaction 破坏读视图。

面试中最关键的一句话是：

```text
RocksDB 避免读到半个 WriteBatch，不是因为并发读完全看不到正在插入的 MemTable entry，而是因为 batch 的 sequence 在完整写入 MemTable 前不会发布；读请求的 read sequence 小于这些未发布 entry，所以即使物理上 entry 已经插入，也会被可见性规则过滤掉。
```
