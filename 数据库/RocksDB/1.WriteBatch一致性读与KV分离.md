# 1. WriteBatch、一致性读与 KV 分离

RocksDB 是典型 LSM-Tree KV 引擎。面试中常围绕删除、墓碑、KV 分离、WriteBatch 原子性和快照一致性读展开。

## 1. LSM-Tree 的 delete 和墓碑

LSM 中删除通常不是立刻从所有 SSTable 中找到旧值并删除，而是写入一条 delete marker，也叫 tombstone。

```text
Delete(k)
  -> WAL 追加 delete 记录
  -> MemTable 插入 (k, seq, delete)
  -> 后续读看到 delete 后认为 key 不存在
  -> compaction 时清理旧版本和 tombstone
```

墓碑什么时候能删除，取决于它是否还需要屏蔽更老版本：

1. compaction 已经看到该 key 在更低层的所有旧版本。
2. tombstone 已经到达最底层，或者能够证明更低层不存在该 key。
3. 没有活跃 snapshot 需要读取 tombstone 之前的旧版本。
4. range tombstone 还要确认覆盖范围内的旧数据都已被处理。

如果还有 snapshot 指向旧 sequence number，过早删除 tombstone 或旧版本会破坏一致性读。

## 2. 大量 delete 的影响和解决方案

大量删除会带来：

1. **读放大**：点查可能先读到 tombstone，还要靠 Bloom Filter、索引和层级规则判断。
2. **写放大**：delete 本身写一次，后续 compaction 还要多次携带和清理。
3. **空间放大**：旧值和 tombstone 在 compaction 前共存。
4. **尾延迟**：delete storm 可能制造 compaction debt，让前台写被限速。
5. **范围扫描变慢**：扫描要跳过大量 deleted key 或 range tombstone。

常见解决方案：

1. 使用 `DeleteRange` 删除连续 key 范围，减少逐点 tombstone。
2. 通过 TTL、按时间/租户分区、整文件或整分区丢弃，避免海量 point delete。
3. 调整 compaction 策略和后台线程，及时下推 tombstone。
4. 对删除密集业务做 key 空间隔离，避免污染热点读路径。
5. 定期手动 compaction，但要避开流量高峰并控制 I/O。
6. 保持 snapshot 生命周期短，避免旧版本长期无法回收。

## 3. KV 分离

KV 分离的思想是：LSM 树里只存 key、metadata 和 value pointer，大 value 放到独立 value log/blob file 中。代表性思路包括 WiscKey，工程实现里有 RocksDB BlobDB、Titan 等。

目的：

1. 减少 compaction 时反复搬运大 value。
2. 降低 LSM 写放大。
3. 让索引结构更小，提高 cache 命中率。

写入路径通常是：

```text
append value to value log/blob file
write key -> value pointer into LSM
```

## 4. KV 分离的负面影响

1. **点查多一次随机读**：先查 LSM 拿 pointer，再读 value log。
2. **范围 Scan 变差**：key 在 LSM 中有序，但 value log 往往按写入顺序组织，扫描变成大量随机 value 读取。
3. **GC 复杂**：value log 中旧 value 需要垃圾回收，GC 本身会读写 value 并更新 pointer。
4. **一致性更复杂**：value 写入和 LSM pointer 写入要处理崩溃恢复。
5. **空间放大迁移**：LSM 写放大降低，但 value log 垃圾和 GC 可能增加空间放大。

解决方向：

1. 小 value 仍然 inline，只分离超过阈值的大 value。
2. 对 scan 热点或范围型 workload 保持 value 与 key 近似有序。
3. 读取 scan 时批量预取 value log，增加并发 I/O。
4. value log 做冷热分离，冷数据减少 GC，热数据更容易聚合回收。
5. GC 时按存活率选择文件，避免搬运大量仍然存活的 value。
6. 用 block cache/blob cache 缓解点查二次读取。

学术和工程上针对 Scan 下降的常见思路是“选择性 KV 分离 + scan-aware layout”：小值或范围扫描敏感的数据不分离；大值分离后在 GC 或 compaction 中尽量按 key 顺序重写 value；扫描时对 value pointer 排序、批量异步预取或并行读取，减少随机 I/O 的长尾。

## 5. RocksDB `WriteBatch` 如何保证原子性

`WriteBatch` 是多个 Put/Delete/Merge 的逻辑批次。RocksDB 保证同一个 batch 要么在恢复后整体可见，要么整体不可见。

核心机制：

1. batch 内多条操作被序列化为一条逻辑 WAL record 或连续受保护的日志片段。
2. 写线程给 batch 分配连续 sequence number。
3. 先写 WAL，再写 MemTable。
4. WAL 写失败则不会把 batch 当作成功提交。
5. 崩溃恢复时重放 WAL，按 batch 边界恢复 MemTable。
6. 写线程组提交时，多个 batch 可以合并写 WAL，但每个 batch 的 sequence 范围和边界仍然明确。

如果项目自己实现原子性，通常也会采用类似原则：先写 redo/WAL，记录事务或 batch 边界；WAL 持久化成功后再修改内存索引；恢复时按日志重放完整 batch，遇到不完整尾部丢弃。

## 6. 一致性读与 MemTable 可见性

RocksDB 的一致性读依赖 sequence number 和 snapshot。

1. 每次写入获得递增 sequence number。
2. key 在内部会编码成 `user_key + sequence + value_type`。
3. 读取时如果没有显式 snapshot，通常读取当前 latest sequence。
4. 如果创建 snapshot，读请求只看 `sequence <= snapshot_seq` 的版本。
5. 遇到 delete marker 时，如果该 marker 对当前 snapshot 可见，则认为 key 不存在。

MemTable 中也能保证一致性读，是因为 MemTable 保存的是带 sequence number 的 internal key，而不是简单的 `key -> value`。查找时会在同一个 user key 下找到不大于 snapshot sequence 的最新版本。Immutable MemTable 和 SSTable 也遵循同样的版本可见性规则。

易错点：

1. `WriteBatch` 原子不等于一定同步落盘；是否断电不丢还要看 WAL sync 策略。
2. snapshot 生命周期过长会阻止旧版本和 tombstone 回收。
3. KV 分离降低的是 compaction 搬运 value 的写放大，不是所有读写都更快。
4. scan-heavy workload 盲目 KV 分离可能显著变慢。

## 7. 面试回答模板

LSM 删除一般写 tombstone，读路径看到 tombstone 就认为 key 不存在；只有 compaction 能证明更老版本都被覆盖，且没有 snapshot 还需要旧版本时，tombstone 才能被删除。大量 delete 会增加读放大、写放大、空间放大和 compaction 压力，可以用 DeleteRange、TTL、分区丢弃、缩短 snapshot 生命周期和调 compaction 缓解。KV 分离把大 value 放到 value log，只在 LSM 存 pointer，能降低 compaction 写放大，但点查多一次随机读，范围 scan 变差，还要处理 value log GC。RocksDB 的 WriteBatch 通过 WAL batch 边界、连续 sequence number 和先 WAL 后 MemTable 保证原子恢复；一致性读通过 snapshot sequence number 在 MemTable/SSTable 中选择可见版本。
