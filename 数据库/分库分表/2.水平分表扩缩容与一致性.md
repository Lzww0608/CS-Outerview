# 2. 水平分表扩缩容与一致性

水平分表是把同一张逻辑表的数据按分片键拆到多张物理表或多个库中。它解决单表容量、索引膨胀、写入热点和单库吞吐问题，但会引入路由、扩缩容、数据迁移和一致性成本。

## 1. 固定哈希分表

最简单的水平分表方式是固定取模：

```text
table_index = hash(user_id) % N
```

优点：

1. 路由简单，应用无需查路由表。
2. 数据分布相对均匀，适合按用户或订单点查。
3. 单分片查询性能稳定。

缺点：

1. `N` 固定后扩容困难。
2. 增加或减少表数量会导致大量 key 重新映射。
3. 分片键选错后，非分片键查询容易广播。
4. 热点用户或热点商家仍可能打爆单个分片。

所以固定哈希适合数据规模可预估、扩容频率低的系统。设计时常预分较多逻辑分片，例如 1024 个逻辑表，再把逻辑表映射到较少物理库。

## 2. 加表、删表怎么办

固定 `hash % N` 下直接把 `N` 改成新值是危险的，因为大部分数据路由都会变化，线上读写会乱。

常见方案：

1. **预分片**：一开始就定义较多逻辑分片，扩容时只迁移部分逻辑分片到新物理库，不改变 `hash % logical_shard_count`。
2. **路由表**：把 `logical_shard -> physical_db/table` 存在配置中心或元数据库，应用按版本读取路由。
3. **双写迁移**：迁移期间新旧分片双写，读路径优先新库或按迁移状态判断。
4. **后台搬迁**：按主键范围小批量复制历史数据，记录迁移进度，可暂停、可重试。
5. **校验切流**：对比行数、校验和、抽样数据和业务查询结果，再逐步切读。
6. **灰度回滚**：路由版本可回退，迁移任务和双写都要幂等。

典型扩容流程：

```text
增加新物理库
-> 更新路由表为迁移中
-> 历史数据小批量搬迁
-> 增量数据双写或订阅 binlog 同步
-> 数据校验
-> 灰度切读
-> 停止旧分片写入
-> 清理旧数据
```

### 2.1 16 张表不停服迁移到 64 张表

从 16 张表扩到 64 张表，本质是在线分片重路由。不能直接把路由从 `hash(key) % 16` 改成 `hash(key) % 64`，否则大量读请求会查到新表但数据还在旧表，写请求也可能新旧两边分裂。

一种稳妥流程：

1. **冻结逻辑分片规则**：先明确逻辑分片数和物理表映射。更推荐一开始就有 1024 个逻辑分片，再映射到 16 张物理表；扩到 64 张时只调整 `logical_shard -> physical_table`，业务路由仍按逻辑分片算。
2. **建新表和路由版本**：提前创建 64 张新表，路由配置带版本号和迁移状态，例如 `OLD_ONLY`、`DUAL_WRITE`、`READ_NEW_FALLBACK_OLD`、`NEW_ONLY`。
3. **历史数据分批搬迁**：按主键范围或逻辑分片小批量复制，控制每批行数、事务时间和 QPS，避免打满主库。
4. **增量同步**：迁移期间对相关业务写操作双写新旧表，或通过 binlog/CDC 把旧表增量同步到新表。双写要用业务主键幂等，CDC 要记录位点。
5. **读路径灰度**：先让少量流量读新表，未命中时回源旧表并补写新表；观察错误率、延迟、数据差异后逐步扩大。
6. **数据校验和对账**：按分片做行数、主键集合、checksum、抽样业务查询校验；发现差异按权威源重放。
7. **切主和回滚**：确认追平后切到 `NEW_ONLY`，保留旧表只读一段时间。路由版本要能回退，迁移任务要可暂停、可重试、可续跑。

关键 SQL 要保证幂等。例如迁移历史数据时用主键或唯一键避免重复写：

```sql
INSERT INTO order_64_x (...)
SELECT ...
FROM order_16_y
WHERE id > ? AND id <= ?
ON DUPLICATE KEY UPDATE updated_at = VALUES(updated_at);
```

易错点：

1. 只搬历史数据、不处理增量写入，切流时一定丢数据。
2. 双写没有幂等，重试会造成重复流水或覆盖新值。
3. 读切换没有回源策略，迁移中的数据会出现随机查不到。
4. 缺少路由版本日志，线上排查时不知道某个请求按哪套规则访问。
5. 大事务一次迁移太多行，会造成锁等待、binlog 暴涨、主从延迟和 Buffer Pool 污染。

## 3. 一致性哈希能解决什么

一致性哈希把 key 和节点映射到同一个哈希环上，节点增删时只影响环上相邻区间，减少数据迁移量。

它解决的是扩缩容时“迁移范围过大”的问题，不是自动解决所有一致性问题。

工程上还要补：

1. **虚拟节点**：改善物理节点少时的数据倾斜。
2. **权重**：不同机器配置不同时，给高配节点更多虚拟节点。
3. **副本策略**：同一份数据顺时针找多个不同故障域节点保存。
4. **成员变更协议**：所有客户端要在一致的路由版本下访问，避免一部分走旧环、一部分走新环。
5. **迁移状态**：区分未迁移、迁移中、已切读、已完成。

## 4. 哈希环单点故障怎么办

哈希环上的“节点”如果是单个物理实例，一旦宕机，该区间数据就不可用。因此必须引入冗余和故障转移。

常见做法：

1. **多副本**：每个 key 保存到顺时针多个不同节点，避免单节点丢失。
2. **主从或 Raft 组**：一个分片不是一台机器，而是一组有复制和选主能力的节点。
3. **故障域隔离**：副本分布在不同机架、可用区或机房，避免同故障域同时失效。
4. **健康检查和摘除**：故障节点从可写路由中移除，读写切到副本。
5. **反熵修复**：故障恢复后通过 Merkle Tree、binlog 或版本号补齐缺失数据。
6. **限流迁移**：故障转移和数据重平衡要限速，避免恢复流量打爆集群。

如果是 MySQL 分库分表，通常不会直接把哈希环节点设计成单 MySQL 实例，而是设计成“逻辑分片 -> 主从集群/分片组”。

## 5. 怎么保证数据一致性

分表扩缩容中一致性主要有两类：路由一致性和数据一致性。

路由一致性：

1. 路由配置要有版本号。
2. 应用启动和热更新都要校验路由版本。
3. 迁移中读写策略要明确，例如旧写新写、读旧读新、回源规则。
4. 关键写请求可以把路由版本写入日志，方便排查。

数据一致性：

1. **双写幂等**：写新旧分片时使用业务主键或幂等 key。
2. **binlog 追增量**：历史全量搬迁后，用 Canal/Debezium 等订阅旧库增量。
3. **校验对账**：按分片和主键范围做行数、checksum、抽样查询校验。
4. **最终一致补偿**：发现缺失或冲突后按权威源重放。
5. **分布式事务慎用**：跨分片强事务成本高，优先把同一事务内的数据放到同一分片。
6. **读写切换灰度**：先切少量流量，观察错误率、延迟、数据差异，再扩大比例。

## 6. 什么时候考虑分库分表

分库分表不是 SQL 优化的第一步。它解决的是单库单表容量、吞吐和维护边界问题，但会引入路由、跨分片查询、事务、扩容和运维复杂度。

优先优化：

1. SQL 写法和索引设计是否合理。
2. 是否能通过缓存、读写分离、冷热归档、异步化、预聚合解决。
3. 是否存在少数热点查询或热点写入，而不是整体容量不足。
4. 业务是否真的需要在线查询全量历史数据。

可以考虑分库分表的信号：

1. 单表数据量持续增长，索引膨胀导致查询和 DDL 维护成本明显上升。
2. 单库写入 QPS、连接数、磁盘 I/O 或 Buffer Pool 已接近瓶颈。
3. 数据天然按用户、商家、租户、订单等维度隔离，核心查询能带上分片键。
4. 冷热数据差异明显，历史数据可以归档或拆到独立存储。
5. 单库故障影响面过大，需要把容量和风险拆散。

不适合贸然分库分表的情况：

1. 核心查询经常不带分片键，需要大量广播查询。
2. 强依赖跨表 join、全局排序、全局唯一约束和跨分片事务。
3. 当前瓶颈只是缺索引、慢 SQL、缓存击穿或硬件配置不足。
4. 团队缺少迁移、路由、对账、灰度和回滚能力。

## 7. 水平拆分和垂直拆分

水平拆分是把同一张逻辑表的不同行按分片规则拆开，例如订单按 `user_id` 或 `order_id` 分到不同库表。它主要解决单表行数、写入吞吐和单库容量问题。

垂直拆分是按业务领域或字段访问频率拆分：

1. **按业务拆库**：用户库、订单库、支付库、物流库分开，降低模块耦合。
2. **按字段拆表**：把大字段、低频字段拆到扩展表，例如商品详情、用户画像、订单备注。
3. **按读写模型拆分**：交易主表保留强一致核心字段，列表页宽表或 ES 保存查询字段。

对比：

| 方式 | 解决问题 | 典型收益 | 主要代价 |
| --- | --- | --- | --- |
| 水平拆分 | 单表行数、单库吞吐、容量上限 | 容量和写入可横向扩展 | 路由、跨分片查询、扩容迁移 |
| 垂直拆分 | 模块耦合、宽表、冷热字段混杂 | 边界清晰，减少无用字段读取 | 跨业务查询和事务更复杂 |

真实项目常常组合使用：先按业务垂直拆库，再对订单、消息、日志等大表水平分片。

## 8. 分片键怎么选

分片键决定数据如何路由，是分库分表里最关键的设计点。好的分片键要同时满足查询命中、分布均匀、事务内聚和扩展可控。

选择原则：

1. **高频查询必须带得上**：例如用户订单列表按 `user_id`，订单详情按 `order_id`，要设计映射或复合路由。
2. **数据分布尽量均匀**：避免某些大商家、大客户、热门活动形成热点分片。
3. **事务尽量内聚**：同一事务内经常一起更新的数据最好落在同一分片。
4. **生命周期匹配**：按时间拆分适合归档，但近期写入可能集中到最新分片。
5. **稳定不可变**：分片键一旦变化，数据迁移和引用关系都会很复杂。
6. **隐私和安全**：用户可见 ID 如果直接暴露分片规则，可能泄露业务规模或方便爬取。

常见选择：

1. `user_id`：适合用户维度查询，但大用户可能热点，订单详情按 `order_id` 需要映射。
2. `order_id`：适合订单点查和写入均匀，但用户订单列表可能 fan-out。
3. `merchant_id`：适合商家后台，但头部商家容易热点。
4. `tenant_id`：适合 SaaS 租户隔离，但大租户可能需要二级分片。
5. `create_time`：适合时间归档和范围扫描，但最新时间段写入集中。

如果无法让所有查询都带同一个分片键，可以补充：

1. 映射表，例如 `order_id -> shard`。
2. 全局二级索引，例如 `user_id -> order_id list`。
3. 搜索引擎或宽表承接复杂检索。
4. 冗余读模型减少跨分片 join。

## 9. 易错点

1. 直接把 `hash % N` 改成 `hash % (N + 1)` 会导致大规模路由变化。
2. 一致性哈希减少迁移量，但不等于不需要数据迁移。
3. 分片键要围绕核心查询设计，不能只看写入均匀。
4. 扩容时只搬历史数据不追增量，会在切读后读到旧数据。
5. 分片过多会放大连接数、路由复杂度和跨分片聚合成本。
6. 分表后跨分片 join、全局唯一约束、全局排序和事务都会变复杂。

## 10. 面试回答模板

分库分表要在 SQL、索引、缓存、读写分离和冷热归档都不足以解决问题时再考虑。水平拆分解决单表行数、单库容量和写入吞吐，垂直拆分解决业务边界、宽表和冷热字段混杂。固定哈希分表一般是 `hash(key) % N`，路由简单但扩缩容困难，因为改变 `N` 会导致大量数据重新映射。工程上更常用预分逻辑分片加路由表，扩容时只迁移部分逻辑分片到新物理库；迁移流程包括新库准备、路由版本、历史数据搬迁、增量双写或 binlog 同步、校验、灰度切读和清理。分片键要围绕核心查询、数据分布、事务内聚和稳定性选择，非分片键查询要靠映射表、全局索引、ES 或宽表减少广播。数据一致性靠路由版本、幂等双写、增量同步、对账校验、补偿任务和灰度切流保证。
