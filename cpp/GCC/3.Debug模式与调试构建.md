# Debug 模式与调试构建

C++ 没有语言层面的“Debug 模式”。所谓 Debug/Release 是构建系统、编译器选项、标准库调试开关和运行时检查共同形成的构建配置。

## Debug 模式通常做了什么

1. **保留调试信息**：用 `-g` 生成 DWARF 调试信息，让 GDB/LLDB 能看到源码行号、变量、类型和栈帧。
2. **降低优化等级**：常用 `-O0` 或 `-Og`，避免优化把变量消除、内联或重排到难以调试。
3. **开启断言**：不定义 `NDEBUG` 时，`assert()` 生效；Release 常用 `-DNDEBUG` 关闭断言。
4. **启用 Sanitizer**：如 ASan、UBSan、TSan，用于检查越界、Use-After-Free、未定义行为、数据竞争等。
5. **启用标准库 Debug Iterator**：如 libstdc++ 的 `-D_GLIBCXX_DEBUG`，可以检查迭代器越界、非法比较、失效迭代器使用等。
6. **增加日志和检查宏**：通过 `-DDEBUG`、`#ifdef DEBUG` 控制调试日志、额外校验和诊断代码。

典型编译选项：

```bash
g++ -std=c++20 -g -O0 -DDEBUG -Wall -Wextra main.cpp -o app_debug
g++ -std=c++20 -O2 -DNDEBUG main.cpp -o app_release
```

带 Sanitizer：

```bash
g++ -std=c++20 -g -O1 -fsanitize=address,undefined -fno-omit-frame-pointer main.cpp -o app_asan
```

## 编译器和调试器如何配合

1. 编译器把源码位置、变量类型、函数符号、行号映射写入调试信息。
2. 链接器把多个目标文件的调试信息整合到可执行文件或独立符号文件中。
3. 调试器读取调试信息，把机器地址映射回源码行，支持断点、单步、查看变量和栈回溯。
4. 如果开启优化，变量可能被寄存器分配、内联、消除或重排，所以调试时可能显示 `<optimized out>`。

## Debug 和 Release 的差异

| 对比项 | Debug | Release |
| --- | --- | --- |
| 优化 | `-O0` / `-Og` | `-O2` / `-O3` / LTO |
| 调试信息 | 通常开启 `-g` | 可关闭，也可保留符号用于线上排查 |
| 断言 | 通常开启 | 通常 `-DNDEBUG` 关闭 |
| 运行时检查 | 可开启 ASan/UBSan/TSan | 通常关闭，降低开销 |
| 性能 | 较低 | 较高 |
| 行为 | 更容易暴露错误或停在错误点 | UB 可能被优化放大，问题更隐蔽 |

## 易错点

1. Debug/Release 行为差异不应该依赖业务逻辑分支，否则容易出现“Debug 能跑，Release 崩”的问题。
2. 未定义行为在 Debug 下看起来正常，在 Release 优化后可能完全不同。
3. `-g` 不一定显著影响运行性能，主要影响二进制体积；真正影响性能的是优化等级和运行时检查。
4. Sanitizer 构建不能完全替代单元测试和代码审查，它只覆盖实际执行到的路径。
5. `_GLIBCXX_DEBUG` 会改变标准库类型 ABI，不能和未开启该宏的库随意混用 STL 对象。

## 真实场景

1. 开发阶段使用 `-g -O0` 或 `-Og` 方便断点调试。
2. 本地和 CI 增加 ASan/UBSan，提前发现越界、悬垂指针、错误 delete 等问题。
3. 线上 Release 可以保留独立符号文件，崩溃后通过 core dump + 符号文件定位。
4. 性能敏感服务用 Release 构建压测，不能用 Debug 性能判断线上容量。

## 面试回答模板

C++ 的 Debug 模式不是语言特性，而是一组构建选项。通常会加 `-g` 生成调试信息，降低优化到 `-O0` 或 `-Og`，保留 assert，不定义 `NDEBUG`，并可能启用 ASan/UBSan/TSan 或标准库 debug iterator。调试器通过编译器生成的 DWARF 符号把机器地址映射回源码。Release 则通常打开优化、关闭断言和重型检查。要注意未定义行为在 Debug 下可能不暴露，Release 优化后可能表现完全不同。
