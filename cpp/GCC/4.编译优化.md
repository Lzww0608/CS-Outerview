# 编译优化

编译优化是编译器在不改变程序可观察行为的前提下，对代码进行等价变换，以提升运行速度、降低代码体积或减少资源消耗。面试里可以从优化等级、常见优化手段、风险和工程实践四个层次回答。

## 1. 常见优化等级

GCC/Clang 常见优化选项：

| 选项 | 含义 | 适用场景 |
| --- | --- | --- |
| `-O0` | 基本不优化 | 调试，变量和源码对应关系更直观 |
| `-Og` | 保留较好调试体验的轻量优化 | 日常 Debug 构建 |
| `-O1` | 开启基础优化 | 兼顾编译速度和运行性能 |
| `-O2` | 常用 Release 优化 | 服务端线上构建常见选择 |
| `-O3` | 更激进优化，如更多内联、向量化 | 计算密集型代码，需要压测验证 |
| `-Os` | 优化代码体积 | 嵌入式、指令缓存敏感场景 |
| `-Ofast` | 允许破坏严格标准语义的优化 | 谨慎使用，尤其是浮点计算 |

线上服务通常从 `-O2` 开始，再结合压测决定是否使用 `-O3`、LTO 或 PGO。

## 2. 常见优化手段

### 2.1 内联

函数内联把函数体展开到调用点，减少调用开销，并暴露更多跨函数优化机会。代价是可能增加代码体积，导致指令缓存压力变大。

注意：`inline` 关键字只是给编译器的建议和链接语义工具，不保证一定内联。是否内联主要由优化器决定。

### 2.2 常量传播和死代码删除

编译器会把已知常量向后传播，并删除不可达或无副作用的代码：

```cpp
if (false) {
    expensive();
}
```

这类代码在优化后会被移除。

### 2.3 循环优化

常见循环优化包括：

1. 循环展开：减少分支判断次数。
2. 循环不变量外提：把循环内不变计算移到循环外。
3. 自动向量化：使用 SIMD 指令一次处理多个元素。
4. 强度削弱：把乘法等较重运算转换成加法或位移。

### 2.4 逃逸分析和栈上分配

部分编译器或运行时可以分析对象是否逃逸出当前作用域，未逃逸对象有机会放在栈上或被标量替换，减少堆分配。

C++ 中这类优化常表现为返回值优化 RVO/NRVO、拷贝省略、临时对象消除等。

### 2.5 LTO 和 PGO

1. **LTO**：链接时优化，让编译器跨翻译单元分析，做跨文件内联、死代码删除和全局优化。
2. **PGO**：Profile-Guided Optimization，先用真实或接近真实流量采集热点路径，再根据 profile 优化分支布局、内联决策和代码布局。

对大型服务来说，PGO 的收益依赖流量代表性；profile 不准可能让冷热点判断错误。

## 3. 优化和未定义行为

编译器优化基于“程序没有未定义行为”的假设。代码一旦存在越界、悬垂指针、有符号整数溢出、数据竞争等 UB，Debug 下可能看起来正常，Release 优化后可能表现完全不同。

典型例子：

```cpp
int x = INT_MAX;
if (x + 1 < x) {
    // 编译器可以认为有符号溢出不会发生，从而删除这类分支
}
```

所以性能优化之前要先保证代码行为定义明确，并用 ASan、UBSan、TSan、静态分析和测试覆盖关键路径。

## 4. 工程实践

1. Debug 构建使用 `-g -O0` 或 `-g -Og`，方便定位问题。
2. Release 构建通常使用 `-O2 -DNDEBUG`，必要时保留符号文件用于 core dump 分析。
3. 性能瓶颈先用 perf、火焰图、benchmark 定位，不要凭感觉改代码。
4. 热点代码再考虑内联、减少分配、缓存友好布局、SIMD、LTO、PGO。
5. 对延迟敏感服务，要同时看平均延迟、P99、CPU、指令缓存 miss、分支 miss 和内存分配。

## 5. 易错点

1. `-O3` 不一定比 `-O2` 快，代码体积变大可能降低指令缓存命中率。
2. `volatile` 不是多线程同步工具，也不能替代原子变量。
3. `inline` 不等于一定内联，递归、大函数、间接调用通常不容易内联。
4. 打开优化后调试器可能看到变量被优化掉或执行顺序和源码不完全一致。
5. 不要用依赖 UB 的代码追求“看起来更快”，优化器可能把假设放大成线上 bug。

## 6. 面试回答模板

编译优化是在不改变程序可观察行为的前提下提升性能或减少体积。GCC 常见优化等级有 `-O0/-Og/-O2/-O3/-Os`，线上服务一般用 `-O2` 起步。常见优化包括函数内联、常量传播、死代码删除、循环展开、循环不变量外提、自动向量化、拷贝省略，以及跨文件的 LTO 和基于真实 profile 的 PGO。要注意优化建立在没有未定义行为的假设上，Release 下 UB 可能被放大，所以应先用测试、Sanitizer 和性能分析工具定位瓶颈，再对热点路径做有证据的优化。
