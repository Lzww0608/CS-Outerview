# 调试流程与 GDB 使用边界

面试里问“你是怎么做调试的，是不是直接上 GDB”，重点不是否定 GDB，而是说明你有一套可复现、可观测、可验证的定位流程。GDB 适合看线程栈、断点、变量、core 和崩溃现场，但很多问题一开始更应该先通过日志、监控、最小复现、Sanitizer 或性能剖析缩小范围。

## 1. 调试的基本流程

推荐按下面顺序推进：

```text
复现问题
  -> 保留现场
  -> 判断问题类型
  -> 缩小范围
  -> 用合适工具验证假设
  -> 修复后补测试或回归用例
```

1. **复现问题**：确认输入、配置、版本、环境、并发度和触发频率。
2. **保留现场**：保存日志、core、请求样本、二进制和符号文件，线上问题还要保留容器镜像或构建产物。
3. **判断类型**：崩溃看 core，内存错误看 ASan/Valgrind，性能问题看 perf/火焰图，锁问题看线程栈和锁等待。
4. **缩小范围**：二分最近改动、减少输入规模、关闭可疑功能开关、构造最小复现。
5. **验证假设**：一次只改一个条件，用同样输入确认问题是否消失。

## 2. 什么时候直接用 GDB

适合直接用 GDB 的场景：

1. 程序稳定崩溃，已经生成 core。
2. 本地可复现，并且需要单步观察变量变化。
3. 多线程死锁或卡死，需要看所有线程栈。
4. 某个断言、异常分支或系统调用返回值需要现场确认。

常用命令：

```gdb
gdb ./server core
bt
bt full
info threads
thread apply all bt
frame 3
print variable
set scheduler-locking on
```

如果是线上进程，不建议长时间 attach 并单步执行。可以先用 `pstack <pid>`、`gcore <pid>`、`coredumpctl gdb` 离线分析，降低对线上服务的影响。

## 3. 什么时候不应该一上来 GDB

1. **偶发并发问题**：GDB 单步会改变调度时序，可能把竞态隐藏掉，优先用 TSan、日志埋点、压测复现和线程栈采样。
2. **性能问题**：断点会严重扰动执行，优先用 `perf`、火焰图、`top -H`、`pidstat`、allocator profile。
3. **内存泄漏**：GDB 能看对象，但难以全局统计分配路径，优先用 ASan/LSan、Valgrind、heaptrack、jemalloc/tcmalloc profile。
4. **线上请求异常**：先看日志、traceId、指标、下游状态、配置和灰度版本，避免把系统性问题当成单点代码问题。
5. **协议或网络问题**：先抓包、看 `ss/netstat`、错误码、重传和连接状态，再决定是否进入进程内部。

## 4. 内存问题定位示例

如果 C++ 程序运行一段时间后 RSS 持续上涨，不要只在 GDB 里随便看指针。更合理的顺序是：

1. 用监控确认是 RSS、heap、cache 还是 mmap 增长。
2. 用 `pmap -x <pid>`、`/proc/<pid>/smaps_rollup` 判断匿名内存、文件映射和堆的占比。
3. 本地打开 ASan/LSan 或用 heaptrack 跑同样压测。
4. 如果怀疑缓存膨胀，检查队列长度、map size、LRU 淘汰和 TTL。
5. 如果怀疑碎片，检查分配器 profile 和大对象释放后是否归还 OS。

## 5. 易错点

1. 没有符号文件时，GDB 栈可能只显示地址，构建时要保留 `-g` 和对应版本二进制。
2. `-O2` 优化会导致变量被优化掉、栈帧合并或内联，必要时用 Debug 构建复现。
3. 调试多线程时，当前线程的 `bt` 不代表所有线程状态，要用 `thread apply all bt`。
4. 条件断点会明显拖慢程序，热点循环中可改用日志采样、计数器或硬件 watchpoint。
5. core 文件只记录某一时刻的现场，无法替代请求链路、日志和监控。

## 6. 面试回答模板

我不会所有问题都直接上 GDB。一般先复现问题并保留现场，再根据问题类型选工具：崩溃和 core 用 GDB 看 `bt full`、线程栈和局部变量；内存泄漏用 ASan、Valgrind、heaptrack 或分配器 profile；性能问题用 `top -H`、`perf` 和火焰图；死锁用 `thread apply all bt` 或 `pstack` 看锁等待链。GDB 是验证假设和分析现场的工具，不是替代日志、监控、最小复现和压测的方法。
