# 头文件重复包含与 include guard

头文件会被预处理器文本展开到每个包含它的 `.cpp` 文件中。如果一个头文件被同一个翻译单元重复包含，可能导致类型、函数或变量重复定义。防止重复包含的常见方式是 include guard 或 `#pragma once`。

## 1. include guard

传统写法：

```cpp
#ifndef PROJECT_NET_CONNECTION_H_
#define PROJECT_NET_CONNECTION_H_

class Connection {
public:
    void close();
};

#endif // PROJECT_NET_CONNECTION_H_
```

第一次包含时宏未定义，头文件内容会展开；第二次包含时宏已经定义，内容会被跳过。

优点：

1. 标准 C/C++ 预处理机制，跨编译器兼容性最好。
2. 不依赖文件系统路径判断。
3. 可以精确控制宏名，适合复杂构建环境。

缺点：

1. 宏名写错或重复会导致错误跳过或重复展开。
2. 模板生成、拷贝文件时容易忘记改 guard 名称。

## 2. #pragma once

现代项目常见写法：

```cpp
#pragma once

class Connection {
public:
    void close();
};
```

它告诉编译器同一个头文件在同一个翻译单元中只展开一次。

优点：

1. 写法简洁，不会出现 guard 宏名冲突。
2. 编译器可利用文件缓存，通常处理更快。
3. 可读性好，减少样板代码。

缺点：

1. 不是 C++ 标准语法，但主流编译器基本都支持。
2. 在符号链接、网络文件系统、生成文件、硬链接等复杂场景下，编译器对“同一个文件”的判断可能存在边界问题。

## 3. 二者区别

| 对比项 | `#ifndef` include guard | `#pragma once` |
| --- | --- | --- |
| 标准性 | 标准预处理写法 | 非标准但主流支持 |
| 可移植性 | 最好 | 现代编译器基本没问题 |
| 维护成本 | 需要维护唯一宏名 | 简洁 |
| 路径敏感 | 不依赖路径 | 依赖编译器识别文件唯一性 |
| 常见问题 | 宏名冲突、复制后忘改 | 复杂文件系统下识别边界 |

真实工程中，两者任选其一即可；有些项目为了极端兼容会同时使用，但通常没有必要。

## 4. 防重复包含不等于解决所有重复定义

include guard 只能防止同一个头文件在同一翻译单元内重复展开，不能解决这些问题：

1. 非 `inline` 函数定义放头文件，被多个 `.cpp` 包含后会链接期重复定义。
2. 非 `inline` 全局变量定义放头文件，也会多重定义。
3. 模板和 `inline` 函数可以放头文件，因为需要在实例化或内联点可见。
4. 头文件循环包含需要前向声明和拆分依赖，不是只靠 guard 就能让类型完整可用。

错误示例：

```cpp
// bad.h
#pragma once

int global_count = 0; // 多个 .cpp 包含后仍可能违反 ODR
void helper() {}      // 非 inline 函数定义也会重复
```

更好的写法：

```cpp
// good.h
#pragma once

extern int global_count;
void helper();

// good.cpp
int global_count = 0;
void helper() {}
```

## 5. 头文件工程建议

1. 每个头文件都要自包含，单独 include 后能编译。
2. 项目内部头文件用双引号，标准库和系统库用尖括号。
3. 能前向声明就前向声明，减少不必要的包含和编译依赖。
4. 头文件尽量不要定义非 `inline` 全局对象和普通函数。
5. 公共头文件要少包含重型依赖，避免全项目重编译。

## 6. 面试回答模板

防止头文件重复包含可以用 `#ifndef/#define/#endif` 的 include guard，也可以用 `#pragma once`。include guard 是标准预处理写法，兼容性最好，但要保证宏名唯一；`#pragma once` 写法更简洁，主流编译器都支持，但不是标准，复杂文件系统下可能有边界问题。需要注意，防重复包含只解决同一翻译单元重复展开，不代表可以把非 `inline` 函数或全局变量定义随便放头文件，否则多个 `.cpp` 包含后仍可能违反 ODR。
