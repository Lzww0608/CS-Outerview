# 双检查冲突锁

《C++并发编程实战》中3.3.1章节中讲了一个Double-Checked Locking，并着重讲了它所存在的问题，原文代码和描述如下：

```c++
std::shared_ptr<some_resource> resource_ptr;
std::mutex resource_mutex;

void undefined_behaviour_with_double_checked_locking()
{
    if(!resource_ptr) // ①
    {
        std::lock_guard<std::mutex> lk(resource_mutex);
        if(!resource_ptr) // ②
        {
            resource_ptr.reset(new some_resource); // ③
        }
    }
    resource_ptr->do_something(); // ④
}
```

>这个模式为什么声名狼藉呢？因为这里有潜在的条件竞争，因为外部的读取锁①没有与内部的
>写入锁进行同步③。因此就会产生条件竞争，这个条件竞争不仅覆盖指针本身，还会影响到其
>指向的对象；即使一个线程知道另一个线程完成对指针进行写入，它可能没有看到新创建的
>some_resource实例，然后调用do_something()④后，得到不正确的结果。这个例子是在一种
>典型的条件竞争——数据竞争，C++标准中这就会被指定为“未定义行为”。

这段话讲的不是很清楚，经过查阅资料后了解到。实际原理应该如下：

操作1之后进行上锁，所以无论进行上锁，操作1均可执行。如果某个线程A上锁后执行至操作3，操作3实际分为三步：

1. 为some_resource对象分配一块内存

2. 构造一个对象，将对象放入分配的内存

3. 将resource_ptr指针指向这片区域

   

然而，在编译器实际执行过程中，可能会进行指令重排优化，将执行的顺序变为132，即步骤3在步骤2之前。此时步骤3执行之后，步骤2执行之前，线程2进行操作1，得到指针为非空，然后执行操作4，对指针进行操作，此时指针指向未初始化的内存，野指针的产生会导致未定义行为(Undefined Behavior)。

## `instance = new Singleton()` 并发时的问题

这行代码可以拆成三个逻辑步骤：

```text
1. 分配原始内存
2. 在这块内存上调用 Singleton 构造函数
3. 把内存地址赋值给 instance
```

在没有同步约束时，编译器和 CPU 可能让其他线程先观察到第 3 步的结果，而第 2 步构造尚未对该线程可见。于是另一个线程看到 `instance != nullptr`，直接返回这个指针并调用成员函数，就可能访问到未构造完成的对象。

问题不只来自“指令重排”，还来自 C++ 内存模型里的数据竞争：

1. 一个线程写 `instance`，另一个线程无锁读 `instance`，如果 `instance` 不是原子变量，就已经是 data race。
2. 即使指针值可见，对象内部成员的写入也未必对其他线程可见。
3. 互斥锁只保护锁内读写，锁外第一次检查必须与写入建立同步关系，否则仍不安全。

## C++11 后的推荐写法

最简单的线程安全单例是函数内局部静态变量：

```cpp
class Singleton {
public:
    static Singleton& instance() {
        static Singleton obj;
        return obj;
    }

private:
    Singleton() = default;
};
```

C++11 保证函数内局部静态变量初始化是线程安全的，编译器通常用 guard variable 和 acquire/release 语义保证只初始化一次。

如果必须使用懒汉式指针和双检锁，至少要把指针做成原子，并用 acquire/release 发布对象：

```cpp
#include <atomic>
#include <mutex>

class Singleton {
public:
    static Singleton* instance() {
        Singleton* p = instance_.load(std::memory_order_acquire);
        if (p == nullptr) {
            std::lock_guard<std::mutex> lock(mutex_);
            p = instance_.load(std::memory_order_relaxed);
            if (p == nullptr) {
                p = new Singleton();
                instance_.store(p, std::memory_order_release);
            }
        }
        return p;
    }

private:
    Singleton() = default;
    static std::atomic<Singleton*> instance_;
    static std::mutex mutex_;
};
```

`release` 保证构造函数完成前的写入不会重排到发布指针之后；`acquire` 保证读到非空指针后，也能看到对象构造时写入的状态。

## 易错点

1. 只给第二次检查加锁不够，第一次无锁读也要避免 data race。
2. `volatile` 不能替代 `std::atomic`，它不提供跨线程同步语义。
3. 手写双检锁复杂且容易错，面试和工程中优先回答函数内 static 或 `std::call_once`。
4. 单例析构顺序也要注意，跨翻译单元静态对象在退出阶段互相访问可能出问题。
