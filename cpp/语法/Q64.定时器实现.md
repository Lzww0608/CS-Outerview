## Linux 如何实现微秒级定时器

如果面试问“精确到微秒”，要先区分**定时器精度**和**线程被调度执行的准时程度**。Linux 可以用高精度定时器把超时时间设置到微秒甚至纳秒级，但用户态线程真正醒来还会受到调度延迟、CPU 负载、抢占、时钟源和电源管理影响，因此不能承诺严格实时。

常见实现方式：

1. **事件循环场景**：使用 `timerfd_create(CLOCK_MONOTONIC, TFD_NONBLOCK | TFD_CLOEXEC)` 创建定时器 fd，用 `timerfd_settime` 设置过期时间，再把 fd 加入 `epoll`。这样网络事件和定时事件都走同一个 Reactor。
2. **单次精准休眠**：使用 `clock_nanosleep(CLOCK_MONOTONIC, TIMER_ABSTIME, ...)`，用绝对时间避免循环休眠带来的误差累积。
3. **信号或回调场景**：使用 POSIX timer，如 `timer_create`、`timer_settime`，但信号处理复杂，网络服务器里通常不如 `timerfd` 好维护。
4. **极短等待**：低于调度开销的几十微秒级等待，如果必须非常准，可能需要忙等、自旋、实时调度策略、CPU 绑核和隔离，但这会浪费 CPU，普通 Web 服务不建议这样做。

示例：

```cpp
int fd = timerfd_create(CLOCK_MONOTONIC, TFD_NONBLOCK | TFD_CLOEXEC);

itimerspec spec{};
spec.it_value.tv_sec = 0;
spec.it_value.tv_nsec = 500 * 1000; // 500 微秒后触发
timerfd_settime(fd, 0, &spec, nullptr);

epoll_event ev{};
ev.events = EPOLLIN;
ev.data.fd = fd;
epoll_ctl(epfd, EPOLL_CTL_ADD, fd, &ev);
```

易错点：

1. 不要用 `gettimeofday` 做超时计算，它会受系统时间调整影响；网络服务更适合 `CLOCK_MONOTONIC`。
2. `usleep(1)` 不代表线程一定 1 微秒后执行，它只是最短睡眠意图。
3. 大量业务定时器不能为每个任务都创建一个内核 timerfd，通常只用一个驱动 fd，内部用最小堆、红黑树或时间轮管理任务。
4. 如果需要硬实时级精度，要讨论实时内核、`SCHED_FIFO/SCHED_RR`、CPU 隔离、时钟源和系统负载，而不是只写一个 API。

## 面试题2：手撕一个定时器

## 服务器如何处理超时连接

网络服务器通常会给连接设置读超时、写超时、空闲超时和业务请求超时。核心做法是：每个连接维护 `expire_time`，收到数据、成功写出或完成业务时刷新超时时间；事件循环定期找出已经过期的连接并关闭。

典型流程：

```text
accept 新连接
-> 设置 expire_time = now + idle_timeout
-> 收到读写事件后刷新 expire_time
-> 定时器到期检查连接是否真的过期
-> 过期则关闭 fd、清理缓冲区和业务上下文
```

注意点：

1. 定时器触发时要二次检查当前连接的最新过期时间，避免旧定时任务误关活跃连接。
2. 连接关闭要同时从 epoll、连接表、定时器结构和业务状态中移除。
3. 对慢客户端要限制输出缓冲区大小，不能只靠超时，否则内存可能先被打满。
4. 心跳超时和 TCP keepalive 不等价，应用层心跳更能表达业务连接是否可用。

## 大量定时器怎么实现

大量定时器的关键不是每毫秒扫描所有连接，而是用合适的数据结构按过期时间组织任务。

常见选择：

1. **最小堆**：堆顶就是最近过期任务，插入和调整 `O(log n)`，实现简单，适合中等规模定时器。
2. **红黑树**：按过期时间排序，Nginx 常用类似思路，插入删除 `O(log n)`，可以高效找最小过期节点。
3. **时间轮**：把时间切成槽，定时器挂到对应槽，插入删除接近 `O(1)`，适合海量连接超时、心跳等精度要求不高的任务。
4. **层级时间轮**：用多层时间轮扩大时间跨度，Kafka、Netty 这类系统常见。

时间轮示意：

```text
current_tick -> slot[i]
每次 tick 前进一格
触发当前槽上的任务
未到轮次的任务 rounds--
```

选型建议：

1. 定时器数量少、精度要求高：最小堆或红黑树。
2. 百万连接空闲超时、心跳检测：时间轮更合适。
3. 定时任务跨度很大：层级时间轮或红黑树更容易控制内存。
4. Linux 服务可用 `timerfd` 驱动事件循环，但底层任务集合仍要自己组织。

## 超时时间节点的查找和修改复杂度

面试里问“查找需要更改超时时间的节点需要多少时间？更改需要多少时间？”要先说明使用的数据结构。定时器常见有红黑树、最小堆、时间轮、跳表等，不同结构复杂度不同。

| 数据结构 | 找到最早超时 | 按句柄查找某个节点 | 修改某个节点超时时间 | 适用场景 |
| --- | --- | --- | --- | --- |
| 红黑树 | `O(log n)` 或缓存最小节点后 `O(1)` | 有节点指针/句柄为 `O(1)`，按 key 查为 `O(log n)` | 删除旧节点再插入新 key，`O(log n)` | Nginx、事件循环定时器 |
| 最小堆 | `O(1)` 看堆顶 | 如果只有堆数组无索引，查找 `O(n)`；配合 id->index 为 `O(1)` | 上浮/下沉 `O(log n)` | libevent/libuv 常见思路 |
| 跳表 | `O(1)` 看头部最小 | 按 key 查 `O(log n)` | 删除再插入 `O(log n)` | Redis zset 类结构 |
| 时间轮 | 当前槽触发接近 `O(1)` | 有句柄为 `O(1)` | 从旧槽摘下再挂新槽，通常 `O(1)` | 大量定时任务、精度可控 |

如果以 Nginx 红黑树为例：

1. 每个连接保存自己的 timer event 指针，所以要修改该连接超时时间时，不需要从树里全局扫描，定位事件对象是 `O(1)`。
2. 但红黑树按过期时间排序，修改 key 会破坏树序，因此通常先删除旧节点，再用新过期时间插入，复杂度 `O(log n)`。
3. 查找“最近要触发的节点”可以取红黑树最左节点，复杂度 `O(log n)`；如果实现缓存最小节点，可以做到近似 `O(1)` 读取，但插入删除要维护缓存。

工程上如果“修改超时时间”很频繁：

1. 最小堆要配合 `id -> index` 哈希表，否则找任意节点是 `O(n)`。
2. 时间轮修改很快，但精度、跨度和跨轮迁移更复杂。
3. 大量连接超时管理通常更看重批量触发、内存占用和实现复杂度，而不只是单次大 O。

面试回答模板：定时器按过期时间组织时，找最早超时看数据结构；红黑树取最小节点 `O(log n)` 或缓存后 `O(1)`，修改某个已有连接的超时时间如果连接里有节点句柄，定位是 `O(1)`，真正调整红黑树要删除再插入，是 `O(log n)`。最小堆如果没有反向索引，找任意节点是 `O(n)`；加哈希表后定位 `O(1)`、调整 `O(log n)`。时间轮适合大量定时器，插入修改通常接近 `O(1)`，但有精度和跨度权衡。

## TimerManager 接口如何设计

如果面试要求“设计一个 `TimerManager` 管理多个定时器”，不要只说使用小顶堆或时间轮，还要把接口、生命周期和取消语义讲清楚。

一个常见接口可以设计成：

```cpp
using TimerId = uint64_t;
using Callback = std::function<void()>;

class TimerManager {
public:
    TimerId add(std::chrono::milliseconds delay, Callback cb);
    bool del(TimerId id);
    bool update(TimerId id, std::chrono::milliseconds newDelay);
    void tick(std::chrono::steady_clock::time_point now);
    std::chrono::milliseconds nextTimeout() const;
};
```

核心语义：

1. `add`：生成全局唯一 `TimerId`，记录过期时间、回调、版本号，把节点放入堆、红黑树或时间轮。
2. `del`：按 `TimerId` 取消任务。小顶堆如果不维护反向索引，可以采用懒删除，把 `id` 标记为取消，到堆顶弹出时再丢弃。
3. `update`：本质是修改过期时间。红黑树通常删除旧节点再插入新节点；小顶堆可配合 `id -> index` 后上浮/下沉，也可用“版本号 + 新节点”的懒更新。
4. `tick`：循环取出所有 `expire_time <= now` 的有效节点，执行回调；执行前要再次检查是否被取消或版本是否过期。
5. `nextTimeout`：返回离最近一次过期还剩多久，给 `epoll_wait`、`poll` 或 `timerfd_settime` 使用。

以“小顶堆 + 哈希表 + 版本号”为例，结构可以是：

```cpp
struct TimerNode {
    TimerId id;
    uint64_t version;
    std::chrono::steady_clock::time_point expire;
    Callback cb;
};

std::priority_queue<TimerNode, std::vector<TimerNode>, ExpireGreater> heap;
std::unordered_map<TimerId, uint64_t> latestVersion;
```

`update` 时不一定要在堆里找到旧节点，可以让 `latestVersion[id]++`，再插入一个新过期时间的新节点。`tick` 弹出堆顶时，如果节点版本不等于 `latestVersion[id]`，说明它是旧节点，直接跳过。这个做法实现简单，适合定时器数量中等、更新频繁的服务端；缺点是堆里会短期积累无效节点，需要在触发时清理。

工程注意事项：

1. 时间应使用 `steady_clock`，不要用会被 NTP 或人工调整影响的系统墙钟。
2. 回调里不要长时间阻塞事件循环，耗时任务应投递到工作线程池。
3. 回调执行期间如果允许新增、删除定时器，要避免迭代器失效和重入问题。
4. 多线程调用 `add/del/update` 时，要么给 `TimerManager` 加锁，要么使用事件循环线程亲和：其他线程只通过队列投递修改请求。
5. 网络服务器里常把 `nextTimeout()` 作为 `epoll_wait` 的超时时间，或用 `timerfd` 把定时器事件统一成 fd 事件。

面试回答模板：我会先明确精度、数量和更新频率。中等规模可以用小顶堆管理最近过期任务，配合 `TimerId`、哈希表和版本号实现 `add/delete/update`；大量连接超时可以用时间轮，牺牲一部分精度换取接近 `O(1)` 的插入删除。接口上至少提供 `add`、`del`、`update`、`tick` 和 `nextTimeout`，并且要处理取消后的懒删除、回调阻塞、时间源选择和多线程访问问题。
