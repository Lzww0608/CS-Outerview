# 异步日志方案spdlog

`spdlog` 是一款高效的 `C++` 日志库，它以其极**高的性能**和**零成本的抽象**而著称。`spdlog` 支持**异步**和**同步**日志记录，提供多种日志级别，并允许用户将日志输出到控制台、文件或自定义的接收器。

+ **多线程使用和同步、异步日志没有关系**

+ **是否在同一线程处理也和同步、异步日志没有关系**





#### 区别： spdlog::info()调用之后是否打印成功，如果调用到其他线程中打印则为异步日志。

## 同步日志和异步日志的区别

同步日志指业务线程在调用日志接口时，直接完成格式化和写入，至少会等待日志写入 sink 的主要工作完成后才返回。异步日志指业务线程只把日志事件放入队列，后台线程再批量格式化或写入文件、控制台、网络。

| 对比项 | 同步日志 | 异步日志 |
| --- | --- | --- |
| 调用返回时机 | 写入动作基本完成后返回 | 入队成功后返回 |
| 延迟影响 | 业务线程直接承担 I/O 和格式化开销 | 业务线程更轻，延迟更低 |
| 吞吐 | 高并发下容易被锁和 I/O 限制 | 可批量消费，吞吐更高 |
| 可靠性 | 崩溃前已经写出的日志更确定 | 队列中未刷出的日志可能丢失 |
| 复杂度 | 简单 | 需要队列、后台线程、退出 flush、溢出策略 |

异步日志关键组件：

1. **前端 logger**：业务线程构造日志事件。
2. **有界队列**：缓存待写日志，避免无限占内存。
3. **后台 worker**：批量从队列取日志并写入 sink。
4. **overflow policy**：队列满时阻塞、丢弃新日志、丢弃旧日志或降级同步写。
5. **flush 策略**：按级别、时间、条数或程序退出时刷盘。

## 易错点

1. 异步日志不是一定不丢日志，进程崩溃时队列里的日志可能还没落盘。
2. 同步日志也不等于一定持久化到磁盘，操作系统页缓存和 `fsync` 策略会影响持久性。
3. 队列不能无限大，否则流量突刺时会把内存打满。
4. 错误级别和审计日志可以选择同步或强制 flush，普通 debug/info 可以异步。
5. 日志格式化可能比写文件更耗 CPU，高频日志要关注格式化成本和采样。





+ **零成本抽象**：spdlog 通过**模板和内联函数**来实现零成本抽象，
  确保只有在真正需要时才进行日志记录。
+ **异步日志记录**：spdlog 支持异步日志记录，这意味着它可以将

## 自定义 sink 怎么实现

`sink` 是 spdlog 的输出端抽象。一个 logger 可以挂多个 sink，例如控制台 sink、文件 sink、网络 sink、自定义压缩文件 sink。自定义 sink 的核心是继承 spdlog 提供的 sink 基类，并实现真正写入和 flush 的逻辑。

常见写法是继承 `spdlog::sinks::base_sink<Mutex>`：

```cpp
#include <spdlog/sinks/base_sink.h>
#include <spdlog/details/null_mutex.h>

template <typename Mutex>
class compress_file_sink final : public spdlog::sinks::base_sink<Mutex> {
public:
    explicit compress_file_sink(std::string filename)
        : filename_(std::move(filename)) {}

protected:
    void sink_it_(const spdlog::details::log_msg& msg) override {
        spdlog::memory_buf_t formatted;
        this->formatter_->format(msg, formatted);
        // 写入文件、缓存或投递到后台压缩队列
        write_to_file(formatted);
    }

    void flush_() override {
        // 刷新文件缓冲区
    }

private:
    std::string filename_;
};

using compress_file_sink_mt = compress_file_sink<std::mutex>;
using compress_file_sink_st = compress_file_sink<spdlog::details::null_mutex>;
```

要点：

1. `sink_it_` 里拿到的是已经包含时间、级别、线程号、payload 等信息的 `log_msg`。
2. `formatter_` 由父类维护，自定义 sink 不应绕过它直接拼格式。
3. `_mt` 版本使用真实 mutex，适合多线程共享同一个 sink；`_st` 版本不加锁，适合单线程或外层已保证串行。
4. sink 的职责是输出，复杂耗时操作可以投递到后台线程，避免阻塞业务日志调用。

## sink 是线程安全的吗

spdlog 的线程安全取决于 sink 类型，而不是只看 logger 名字。

1. `xxx_mt` sink 内部有锁，多线程同时写同一个 sink 是安全的。
2. `xxx_st` sink 不加锁，性能更高，但只能在单线程或外部串行保证下使用。
3. 多个 logger 共享同一个 sink 时，必须确认这个 sink 是 `_mt` 或者共享路径外部有锁。
4. 自定义 sink 如果继承 `base_sink<std::mutex>`，父类会在调用 `sink_it_` 和 `flush_` 前加锁；如果自己继承更底层接口，就要自己处理并发。

注意：sink 内部加锁只能保护 sink 自己的数据结构，例如文件句柄、formatter、缓存队列。它不能自动保证“日志轮转 + 压缩 + 删除旧文件”这类跨组件操作的完整一致性，这些仍要单独设计状态机和锁。

## 日志压缩怎么实现

日志压缩通常不是在业务线程里同步完成，而是和日志轮转结合：

1. 当前日志文件达到大小或时间阈值。
2. 日志线程关闭当前文件句柄，把 `app.log` rename 成 `app.log.20251121.1`。
3. 重新打开新的 `app.log` 继续写入。
4. 把已轮转文件路径放入压缩任务队列。
5. 后台压缩线程读取旧文件，写成 `.gz`、`.zst` 或 `.zip`。
6. 压缩成功后删除原始旧文件，必要时执行保留天数或保留数量清理。

关键竞争点：

1. **写入与压缩竞争**：必须只压缩已经关闭并完成 rename 的旧文件，不能压缩正在写的当前文件。
2. **轮转与清理竞争**：清理线程不能删除正在压缩的文件，可以通过任务状态、临时后缀或文件锁区分。
3. **多生产者竞争**：多个 logger 或多个进程写同一路径时，需要进程内锁或跨进程文件锁；更推荐每个进程独立日志文件。
4. **退出竞争**：进程退出时要先停止接收新任务，再 drain 压缩队列，最后 join 后台线程。
5. **失败重试**：压缩失败不能直接丢任务，应记录错误并保留原文件，避免日志丢失。

## 异步压缩任务什么时候 notify

生产者负责改变任务队列状态，改变完成后负责 `notify_one()` 或 `notify_all()`。典型生产者是日志轮转逻辑：它把旧日志文件路径压入压缩队列，然后通知压缩线程。

```cpp
void enqueue_compress(std::string path) {
    {
        std::lock_guard<std::mutex> lk(mutex_);
        jobs_.push(std::move(path));
    }
    cv_.notify_one();
}

void compress_worker() {
    for (;;) {
        std::string job;
        {
            std::unique_lock<std::mutex> lk(mutex_);
            cv_.wait(lk, [&] { return stopped_ || !jobs_.empty(); });
            if (stopped_ && jobs_.empty()) {
                break;
            }
            job = std::move(jobs_.front());
            jobs_.pop();
        }
        compress_file(job);
    }
}
```

这段代码里，即使先 `notify` 后 `wait`，任务也不会丢。因为 `notify` 是瞬时信号，任务队列才是持久状态；消费者使用 `wait(lock, predicate)` 会先检查 `!jobs_.empty()`，队列非空就直接处理，不会睡眠等待下一次通知。

如果压缩队列是有界队列，还需要两个条件：

1. `not_empty`：生产者入队后通知消费者。
2. `not_full`：消费者出队后通知可能阻塞的生产者。

关闭时一般设置 `stopped_ = true` 并 `notify_all()`，确保所有等待线程都能醒来退出。

#### 面试题：spdlog中的每一个logname对应一个shared_ptr吗？


在spdlog库中，每个日志记录器（logger）通常由一个`shared_ptr`管理。这意味着每个具有唯一名称（logname）的记录器都是通过一个`shared_ptr`来引用和管理的。这样做的好处是便于记录器的共享和自动管理内存。

当你创建一个记录器时，例如使用`spdlog::get(name)`或`spdlog::basic_logger_mt(name, filename)`，如果这个名字的记录器已经存在，`spdlog`将返回一个指向现有记录器的`shared_ptr`。如果记录器不存在，则会创建一个新的记录器，并以`shared_ptr`的形式返回。

这种设计允许多个部分的代码共享对同一个记录器的访问，而不需要担心何时释放相关资源，因为当最后一个`shared_ptr`被销毁时，记录器的内存将自动被释放。

## 面试回答模板

同步日志是业务线程直接完成写日志，简单可靠但会把格式化、锁、I/O 延迟带到主链路；异步日志是业务线程把日志投递到队列，后台线程批量写入，能降低业务线程延迟、提高吞吐，但要处理队列满、退出 flush、崩溃丢日志和错误日志强刷。真实系统通常普通日志异步，关键错误、审计、交易流水要更严格地落盘或单独通道处理。
