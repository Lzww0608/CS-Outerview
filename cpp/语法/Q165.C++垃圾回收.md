# C++垃圾回收

C++ 标准没有强制提供像 Java、Go 那样的 tracing GC。C++ 的主流资源管理模型是**确定性析构 + RAII**：对象离开作用域时立即析构，析构函数释放内存、文件描述符、锁、socket、数据库连接等资源。

## 1. C++ 为什么通常不用 GC

GC 的核心目标是自动发现不可达对象并回收堆内存，降低手动释放内存的负担。但 C++ 更强调：

1. **确定性释放**：对象生命周期结束时立即执行析构，适合锁、文件、socket、事务句柄等非内存资源。
2. **低延迟可控**：服务端、游戏、交易系统不希望不可预测的 GC pause 影响尾延迟。
3. **零成本抽象**：不使用某能力就不付出运行时成本。
4. **兼容手动内存布局**：C++ 常直接操作内存池、placement new、共享内存和硬件资源。

因此 C++ 更推荐用类型表达所有权，而不是依赖后台 GC 扫描。

## 2. C++ 中类似 GC 的机制

### 2.1 RAII

RAII 不是 GC，但它能解决大多数资源泄漏问题：

```cpp
class File {
public:
    explicit File(FILE* f) : f_(f) {}
    ~File() {
        if (f_ != nullptr) {
            fclose(f_);
        }
    }

    File(const File&) = delete;
    File& operator=(const File&) = delete;

private:
    FILE* f_;
};
```

### 2.2 智能指针

1. `std::unique_ptr`：独占所有权，离开作用域释放。
2. `std::shared_ptr`：引用计数，最后一个强引用释放对象。
3. `std::weak_ptr`：不延长生命周期，用于打破 `shared_ptr` 循环引用。

引用计数可以看作一种局部自动内存管理，但它不是 tracing GC，无法自动处理强引用环。

### 2.3 第三方保守式 GC

C++ 可以接入 Boehm GC 这类保守式垃圾回收器。它会扫描栈、寄存器和全局区，把看起来像指针的值当作根对象。这种方案能减少部分手动释放，但也有明显代价：

1. 不能精准知道所有对象类型和生命周期。
2. 可能把普通整数误判成指针，导致对象延迟回收。
3. 对析构函数、RAII 和非内存资源支持不自然。
4. 会引入停顿和额外运行时成本。

## 3. 为什么游戏服务端更谨慎使用 GC

游戏服务端通常关注帧同步、房间 tick、网络包延迟和玩家交互一致性。GC 的不可控暂停可能带来：

1. 房间 tick 抖动，影响技能判定和移动同步。
2. 瞬时延迟上升，导致客户端感知卡顿。
3. 拍卖、交易等关键链路超时。
4. 内存占用峰值难以预测。

所以 C++ 游戏服务端更常见的做法是：

1. 用 RAII 和智能指针表达对象生命周期。
2. 用对象池、内存池减少频繁分配。
3. 按场景或房间批量创建和销毁对象。
4. 对热路径避免 `shared_ptr` 原子引用计数开销。
5. 用 ASan、Valgrind、heap profile 和线上监控发现泄漏。

## 4. 易错点

1. `shared_ptr` 不是万能 GC，循环引用仍会泄漏。
2. GC 只能管理内存，不会天然正确释放 socket、锁、文件、事务等非内存资源。
3. RAII 不等于不能泄漏；所有权不清、回调持有、容器缓存不淘汰仍会导致资源长期存活。
4. 手写对象池也可能泄漏，必须定义清楚对象归还、复用和销毁策略。

## 5. 面试回答模板

C++ 标准没有强制的垃圾回收机制，主流方式是 RAII 和确定性析构。堆对象用 `unique_ptr`、`shared_ptr`、`weak_ptr` 表达所有权，文件、锁、socket 也封装成析构自动释放的对象。`shared_ptr` 的引用计数有点像自动回收，但不能处理循环引用，仍需要 `weak_ptr`。C++ 也可以接入 Boehm GC 这类保守式 GC，但在游戏服务端或低延迟系统里通常不常用，因为 GC pause 和析构时机不可控，项目里更倾向于 RAII、对象池和内存泄漏检测工具。
