# Q147. STL 容器增长、删除与迭代器失效

## 1. vector 怎么增长

`std::vector` 是连续内存容器，内部通常维护三个指针或等价状态：

```text
begin: 已用空间起点
end: 已用空间终点
cap: 已分配空间终点
```

当 `push_back` 时：

1. 如果 `size() < capacity()`，直接在尾部构造新元素。
2. 如果 `size() == capacity()`，需要重新申请一块更大的连续内存。
3. 把旧元素移动或拷贝到新内存。
4. 析构旧元素并释放旧内存。
5. 在新内存尾部构造新元素。

增长倍率由标准库实现决定，常见是约 1.5 倍或 2 倍。标准只要求摊还 `O(1)` 的 `push_back`，不规定具体倍率。

## 1.1 vector 的实现原理

`vector` 的核心是“连续内存 + 动态扩容 + allocator 管理对象生命周期”。一个简化实现通常包含：

```cpp
template <typename T, typename Alloc = std::allocator<T>>
class Vector {
    T* begin_;
    T* end_;
    T* cap_;
    Alloc alloc_;
};
```

含义：

1. `begin_` 指向已分配连续空间的起点。
2. `end_` 指向已构造元素的尾后位置，`size() = end_ - begin_`。
3. `cap_` 指向已分配空间的尾后位置，`capacity() = cap_ - begin_`。
4. `alloc_` 负责申请/释放原始内存，以及构造/析构对象。

关键接口语义：

1. `reserve(n)`：只保证容量至少为 `n`，不改变 `size()`，不构造新元素。
2. `resize(n)`：改变元素个数，变大时构造新元素，变小时析构多余元素。
3. `push_back/emplace_back`：容量足够时尾部构造；容量不足时扩容、搬移旧元素、再构造新元素。
4. `erase(pos)`：析构目标元素，并把后续元素向前移动，返回下一个有效迭代器。
5. `shrink_to_fit()`：只是非强制请求，标准不保证一定释放多余容量。

扩容搬移时，标准库会尽量使用移动构造；如果移动构造不是 `noexcept`，为了提供强异常安全保证，很多实现会选择拷贝构造。原因是移动过程中如果抛异常，旧对象可能已经被部分“掏空”，难以恢复原状态。

易错点：

1. `vector` 的元素地址稳定性很弱，扩容后所有旧指针和迭代器失效。
2. `reserve` 只改容量，`resize` 才改元素数量。
3. `operator[]` 不做越界检查，`at()` 会检查并抛异常。
4. 频繁 `push_back` 大对象时，应关注移动构造是否 `noexcept`。
5. `vector<bool>` 是标准库特化，通常按 bit 压缩，不是普通 `vector<T>` 语义。

## 2. vector push_back 后迭代器会怎样

`vector` 的迭代器本质上可以理解为指向连续数组元素的指针。

1. **未扩容**：已有元素地址不变，原有迭代器、指针、引用通常仍有效；但 `end()` 会失效，因为尾后位置变了。
2. **发生扩容**：旧内存被释放，所有迭代器、指针、引用全部失效。
3. **中间插入或删除**：插入点或删除点之后的迭代器、指针、引用会失效，因为元素需要搬移。

工程上如果要长期保存位置，优先保存下标而不是保存迭代器；如果能预估大小，先 `reserve()` 可以减少扩容次数。

## 3. map 的底层数据结构

`std::map` 通常用红黑树实现，满足：

1. key 有序，迭代器按 key 从小到大遍历。
2. 查找、插入、删除复杂度都是 `O(log n)`。
3. 节点式存储，每个元素单独分配节点，插入删除不会像 `vector` 那样整体搬移元素。
4. 迭代器通常比较稳定：插入不会使已有迭代器失效；删除只会使被删除元素的迭代器失效。

标准没有强制规定必须是红黑树，但要求有序关联容器满足对应复杂度和迭代顺序，红黑树是主流实现。

### map 常见操作和复杂度

| 操作 | 语义 | 复杂度 | 注意事项 |
| --- | --- | --- | --- |
| `find(key)` | 查找 key | `O(log n)` | 找不到返回 `end()` |
| `insert({k, v})` | 插入键值对 | `O(log n)` | key 已存在时插入失败 |
| `emplace(args...)` | 原地构造节点 | `O(log n)` | 可减少临时对象 |
| `erase(key)` | 按 key 删除 | `O(log n)` | 返回删除数量 |
| `erase(it)` | 按迭代器删除 | 均摊常数或实现相关调整成本 | 返回值从 C++11 起可接住下一个迭代器 |
| `operator[]` | 查找或插入默认值 | `O(log n)` | 只读查询不要滥用，可能插入新元素 |
| `at(key)` | 查找并返回引用 | `O(log n)` | 不存在会抛 `std::out_of_range` |
| `lower_bound(key)` | 第一个不小于 key 的位置 | `O(log n)` | 常用于范围查询 |
| `upper_bound(key)` | 第一个大于 key 的位置 | `O(log n)` | 常和 `lower_bound` 配合 |

真实项目中，如果只是判断 key 是否存在，用 `find` 或 C++20 的 `contains`；如果需要“没有就插入”，用 `try_emplace` 或 `insert` 更能表达意图，避免 `operator[]` 默认构造大对象。

## 4. 红黑树和平衡二叉树的区别

面试里“平衡二叉树”通常指 AVL 树。

| 对比项 | AVL 树 | 红黑树 |
| --- | --- | --- |
| 平衡要求 | 更严格，左右子树高度差不超过 1 | 相对宽松，通过颜色和黑高约束保持近似平衡 |
| 树高 | 更低，查找路径更短 | 略高，但仍是 `O(log n)` |
| 插入删除 | 旋转和维护成本更高 | 旋转次数通常更少，更新更友好 |
| 适合场景 | 查找远多于修改 | 插入、删除、查找都频繁 |
| 典型应用 | 一些内存索引、查询密集结构 | `std::map`、`std::set`、Linux CFS 运行队列等 |

红黑树不是绝对平衡，而是用“最长路径不超过最短路径 2 倍”的性质换取更低的更新成本。因此标准库有序容器更常选红黑树。

## 4.1 set 和 map 为什么用红黑树

`std::set` 和 `std::map` 都是有序关联容器，区别是：

1. `set` 只保存 key，key 本身就是排序依据。
2. `map` 保存 key-value，按 key 排序，value 不参与排序。
3. `multiset` 和 `multimap` 允许等价 key 重复出现。

它们底层通常是红黑树节点：

```text
node {
    parent;
    left;
    right;
    color;
    value;
}
```

选择红黑树的原因：

1. **有序遍历**：迭代器中序遍历即可按 key 从小到大输出。
2. **范围查询**：`lower_bound`、`upper_bound`、`equal_range` 能在 `O(log n)` 定位边界后顺序扫描。
3. **更新成本稳定**：插入删除最多做有限次旋转和染色，适合读写都频繁的通用容器。
4. **迭代器稳定**：节点式存储下，插入通常不影响已有迭代器，删除只让被删节点迭代器失效。
5. **比较器通用**：只要求 strict weak ordering，不要求 key 可哈希。

为什么不用其他结构：

1. 哈希表平均查找更快，但不保序，不能高效支持范围查询，rehash 还会导致迭代器失效。
2. AVL 树查找路径更短，但平衡更严格，插入删除维护成本更高。
3. B+ 树更适合磁盘页和块设备，标准库容器主要面向内存对象，单节点小对象管理更方便。
4. 跳表也能有序，但标准库历史实现和最坏复杂度要求更倾向红黑树。

面试中可以概括为：`map/set` 需要“有序 + 范围查询 + 稳定 O(log n) + 迭代器较稳定”，红黑树在查询和更新之间折中最好，所以成为主流实现。

## 5. map 怎么循环删除满足条件的元素

删除时不要在 `erase` 后继续使用已经失效的迭代器。

C++11 以后推荐：

```cpp
#include <map>
#include <string>

void eraseByCondition(std::map<int, std::string>& m) {
    for (auto it = m.begin(); it != m.end(); ) {
        if (it->first % 2 == 0) {
            it = m.erase(it);
        } else {
            ++it;
        }
    }
}
```

`erase(it)` 会删除当前节点，并返回下一个有效迭代器。

C++20 可以用：

```cpp
#include <map>
#include <string>

std::erase_if(m, [](const auto& kv) {
    return kv.first % 2 == 0;
});
```

## 6. list 插入元素后迭代器会怎样

`std::list` 是双向链表，插入或删除一个节点不会移动其他节点。

1. 插入元素：已有迭代器、指针、引用仍有效。
2. 删除元素：只有被删除元素的迭代器、指针、引用失效。
3. 访问不支持随机下标，查找第 `n` 个元素需要 `O(n)`。

因此 `list` 适合已经定位到节点后频繁插入删除的场景，不适合随机访问和缓存友好的顺序扫描。

## 7. `map`、`vector`、`list` 底层结构对比

| 容器 | 底层结构 | 访问/查找 | 插入删除 | 典型特点 |
| --- | --- | --- | --- | --- |
| `vector` | 连续动态数组 | 下标访问 `O(1)`，按值查找 `O(n)` | 尾插摊还 `O(1)`，中间插删 `O(n)` | 缓存友好，扩容会搬移元素 |
| `list` | 双向链表 | 不支持随机访问，查找 `O(n)` | 已知位置插删 `O(1)` | 迭代器稳定，但缓存局部性差 |
| `map` | 通常是红黑树 | 按 key 查找 `O(log n)` | 插入删除 `O(log n)` | key 有序，支持范围遍历 |

选择时可以按访问模式判断：

1. 随机访问和顺序扫描多，优先 `vector`。
2. 已经拿到节点位置且频繁插删，才考虑 `list`。
3. 需要按 key 有序遍历、范围查询或稳定 `O(log n)` 查找，用 `map`。
4. 只需要等值查询且不要求有序，通常优先考虑 `unordered_map`。

## 7.1 STL 容器分类

面试问“STL 中有哪些容器”时，可以按标准库分类回答：

| 分类 | 常见容器 | 核心特点 | 适用场景 |
| --- | --- | --- | --- |
| 顺序容器 | `vector`、`deque`、`list`、`forward_list`、`array` | 按元素位置组织数据 | 列表、队列、批量扫描、需要稳定顺序的数据 |
| 有序关联容器 | `set`、`multiset`、`map`、`multimap` | 通常基于红黑树，按 key 有序 | 范围查询、排序遍历、稳定 `O(log n)` 查找 |
| 无序关联容器 | `unordered_set`、`unordered_multiset`、`unordered_map`、`unordered_multimap` | 基于哈希表，平均 `O(1)` 等值查找 | 去重、计数、缓存索引、字典查询 |
| 容器适配器 | `stack`、`queue`、`priority_queue` | 在底层容器上限制接口 | 栈、FIFO 队列、Top K、优先调度 |

补充说明：

1. `string` 不是容器分类里的通用容器，但接口很像连续字符容器。
2. `std::span` 是非拥有视图，不负责管理元素生命周期。
3. `priority_queue` 默认底层是 `vector` 加堆算法，不支持遍历有序输出。
4. `stack` 和 `queue` 默认通常基于 `deque`，也可以指定满足要求的底层容器。

回答时不要只背名字，还要说明选择依据：是否需要随机访问、是否需要有序、是否需要等值查询、是否频繁中间插删、迭代器稳定性要求如何。

## 7.2 常用 STL 容器怎么选

面试问“经常用哪些 STL 容器”时，可以按访问模式回答，而不是只背容器名：

1. **默认顺序存储用 `vector`**：连续内存、缓存友好、下标访问快，适合绝大多数列表、批量扫描和排序场景。
2. **两端频繁进出用 `deque`**：适合双端队列，`queue` 默认底层也是 `deque`。
3. **已定位节点后频繁插删才用 `list`**：它的单次插删是 `O(1)`，但查找和遍历缓存局部性差，所以工程中不应滥用。
4. **需要 key 有序和范围查询用 `map/set`**：底层通常是红黑树，复杂度稳定为 `O(log n)`。
5. **只做等值查询优先 `unordered_map/unordered_set`**：平均 `O(1)`，但要关注哈希质量、rehash 和最坏退化。
6. **TopK 或动态取最值用 `priority_queue`**：底层通常是堆，插入和弹出堆顶都是 `O(log n)`。

如果面试官追问“`vector` 和 `list` 常用哪个”，一般回答优先 `vector`。原因是现代 CPU 对连续内存顺序访问非常友好，`list` 虽然插删不搬移元素，但每个节点单独分配、指针跳转多、缓存命中差，只有在已经持有迭代器且中间插删极频繁时才更合适。

## 8. 典型迭代器失效追问

### 删除 vector 第 4 个元素，第 3 个元素迭代器会失效吗

如果 `vector` 有 10 个元素，迭代器指向第 3 个元素，现在删除第 4 个元素：

```cpp
auto it3 = v.begin() + 2;
v.erase(v.begin() + 3);
```

`it3` 通常仍然有效，因为 `vector::erase` 会使“被删除位置及其之后”的迭代器、指针、引用失效。第 3 个元素在删除点之前，没有被搬移。

但要注意：

1. 指向第 4 个元素以及之后元素的迭代器都会失效。
2. 原来的 `end()` 也会失效。
3. 如果保存的是下标，第 4 个元素之后的下标含义会变化。
4. 不要把这个规则误用到插入场景，插入可能触发扩容，扩容会让所有迭代器失效。

### unordered_map 插入会让旧迭代器失效吗

`unordered_map` 插入元素是否让已有迭代器失效，关键看是否触发 rehash：

1. **未触发 rehash**：已有迭代器通常仍有效，新增元素进入某个 bucket。
2. **触发 rehash**：bucket 数组重建，所有迭代器失效。
3. **删除元素**：只有被删除元素的迭代器失效。
4. **引用和指针**：rehash 通常不移动节点对象，所以指向元素的引用/指针一般仍有效；但被删除元素一定失效。

如果要批量插入，建议提前：

```cpp
std::unordered_map<int, int> m;
m.reserve(10000);
```

`reserve` 可以减少 rehash 次数，使迭代器失效更可控，也能降低重复扩容成本。

## 9. 面试回答模板

`vector` 是连续内存，典型实现维护 begin/end/cap 三个指针并通过 allocator 管理对象。容量不够时会重新分配更大的空间并移动或拷贝元素，所以扩容会导致所有迭代器、指针、引用失效；未扩容时 `push_back` 只会让 `end()` 失效。`reserve` 只改变容量，`resize` 改变元素数量。`map` 通常是红黑树，查找、插入、删除都是 `O(log n)`，插入不影响已有迭代器，删除只影响被删节点。循环删除 `map` 时要写 `it = m.erase(it)`，不能删除后再对旧迭代器自增。`list` 是链表，插入不影响已有迭代器，删除只影响被删除节点。
