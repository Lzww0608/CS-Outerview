在使用 `std::condition_variable` 时，通常建议使用 `std::unique_lock` 而不是 `std::lock_guard`，主要是因为 `std::unique_lock` 提供了更灵活的锁定和解锁的能力。

主要区别有两点：

1. **灵活性：** `std::unique_lock` 对象可以被显式地创建和销毁，而且它支持在生命周期内多次锁定和解锁。这是由于 `std::unique_lock` 的构造函数和析构函数允许你在构造和销毁时进行锁定和解锁，而 `std::lock_guard` 是在构造时锁定，在析构时解锁。
2. **条件变量的等待：** `std::unique_lock` 提供了在等待条件变量时可以显式释放锁的功能，而 `std::lock_guard` 没有这个特性。这在等待条件变为真时释放锁是很有用的，因为这样可以避免在等待期间一直持有锁，从而允许其他线程修改共享数据。

在使用 `std::condition_variable` 时，通常的模式是在等待条件变量之前使用 `std::unique_lock` 对互斥锁进行锁定，然后在等待期间通过 `wait` 函数释放锁。这样可以确保在等待期间其他线程有机会获取锁并修改共享数据。

```c++
#include <mutex>
#include <condition_variable>

std::mutex mtx;
std::condition_variable cv;
bool ready = false;

void worker_thread() {
    std::unique_lock<std::mutex> lock(mtx);

    // 在等待期间释放锁，允许其他线程修改共享数据
    cv.wait(lock, []{ return ready; });

    // 条件满足后的操作
    // ...
}

int main() {
    std::thread worker(worker_thread);

    // 准备数据
    {
        std::unique_lock<std::mutex> lock(mtx);
        ready = true;
    }

    // 通知等待的线程条件已满足
    cv.notify_one();

    // 等待 worker 线程结束
    worker.join();

    return 0;
}
```

## 条件变量的正确使用模式

条件变量本身不保存“条件”，它只负责睡眠和唤醒。真正的条件必须由共享变量表示，并且这个共享变量要受同一把互斥锁保护。

标准写法：

```cpp
#include <condition_variable>
#include <mutex>
#include <queue>

std::mutex m;
std::condition_variable cv;
std::queue<int> q;
bool stopped = false;

void consumer() {
    std::unique_lock<std::mutex> lk(m);
    cv.wait(lk, [&] {
        return !q.empty() || stopped;
    });

    if (!q.empty()) {
        int value = q.front();
        q.pop();
        lk.unlock();
        process(value);
    }
}

void producer(int value) {
    {
        std::lock_guard<std::mutex> lk(m);
        q.push(value);
    }
    cv.notify_one();
}
```

`cv.wait(lk, pred)` 内部等价于循环检查谓词：如果条件不满足，就原子地释放锁并睡眠；被唤醒后先重新加锁，再检查谓词。

## 为什么必须用 `unique_lock`

`condition_variable::wait` 需要在等待时临时释放互斥锁，唤醒后再重新加锁。`std::lock_guard` 只支持构造加锁、析构解锁，不支持中途 unlock/lock；`std::unique_lock` 支持这些操作，所以条件变量接口要求使用 `unique_lock<mutex>`。

常见坑：

1. **虚假唤醒**：线程可能在没有 `notify` 或条件不满足时醒来，所以必须用谓词或 `while`。
2. **先 notify 后 wait**：如果没有共享状态谓词，通知可能丢失；正确做法是先改状态，再通知，等待方检查状态。
3. **持锁做耗时任务**：从队列取出任务后应尽快释放锁，再执行业务处理。
4. **退出流程**：线程池关闭时要设置 `stopped=true` 并 `notify_all`，否则消费者可能永久睡眠。
5. **notify 位置**：通常先在锁内修改共享状态，释放锁后再通知，减少被唤醒线程马上竞争同一把锁的概率。

## 面试回答模板

`condition_variable` 要和互斥锁、共享谓词一起使用。等待线程用 `std::unique_lock` 加锁，然后调用 `cv.wait(lock, predicate)`；如果条件不满足，wait 会原子释放锁并睡眠，唤醒后重新加锁并再次检查条件。不能用 `lock_guard`，因为它不支持 wait 过程中临时释放和重新加锁。条件变量可能虚假唤醒，也可能先通知后等待，所以必须用谓词保护真实状态，而不是把 notify 当成可靠消息。
