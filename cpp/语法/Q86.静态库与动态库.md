# Q86.静态库与动态库

### 静态库 (Static Library)

- **文件扩展名**：在Windows上通常是`.lib`，在Unix/Linux上通常是`.a`。
- **链接时间**：在编译时或链接时将库的代码嵌入到最终生成的可执行文件中。
- 优点：
  - 执行文件独立，不需要额外的库文件来运行。
  - 运行时加载速度较快，因为所有需要的代码都已经在可执行文件中。
- 缺点：
  - 可执行文件会较大，因为包含了库的所有代码。
  - 更新库代码需要重新编译和链接可执行文件。
  - 不同可执行文件使用同一个静态库时，每个可执行文件中都会有库的副本，浪费存储空间。

### 动态库 (Dynamic Library)

- **文件扩展名**：在Windows上通常是`.dll`，在Unix/Linux上通常是`.so`。
- **链接时间**：在运行时加载库文件。
- 优点：
  - 可执行文件较小，因为库的代码是单独存放的。
  - 可以方便地更新库而不需要重新编译和链接可执行文件，只需替换动态库文件。
  - 多个可执行文件可以共享同一个动态库，节省存储空间。
- 缺点：
  - 运行时需要加载动态库，可能会导致启动时间稍长。
  - 需要确保动态库在运行时能够找到，可能需要配置库路径或依赖安装。
  - 如果动态库的接口发生变化，可能会导致兼容性问题，需要小心版本控制。



### 多个进程访问动态库，会有冲突吗？

多个进程访问动态库时，通常不会产生冲突。这是因为操作系统提供了机制来确保动态库的安全共享和独立运行。以下是一些相关的细节：

### 动态库共享机制

1. **内存映射**：当一个动态库被多个进程加载时，操作系统会将该库映射到共享内存区域。这意味着所有进程都会使用同一个动态库实例，这样可以节省内存。
2. **代码共享**：库中的代码是只读的，因此可以安全地在多个进程之间共享。每个进程会有自己的数据段和堆栈段，避免了数据的冲突。

### 进程独立性

1. **私有数据**：尽管代码是共享的，但每个进程都有自己的数据段和堆栈。这意味着库的全局变量和静态变量在每个进程中都有独立的副本。
2. **线程安全**：动态库内部的数据结构如果需要被多个进程或线程访问，应当设计为线程安全的。通常通过互斥锁（mutex）等同步机制来实现。

### 潜在问题和解决方法

1. **非线程安全代码**：如果动态库中的某些函数不是线程安全的，那么在多进程或多线程环境下调用这些函数可能会导致数据竞争和冲突。解决方法是使用线程安全的编程实践，或者使用互斥锁来保护临界区。
2. **全局状态和静态变量**：如果动态库使用了全局状态或静态变量，需要确保这些变量的访问是线程安全的。
3. **动态库版本不一致**：如果不同的进程加载了同名但不同版本的动态库，可能会导致兼容性问题。确保所有进程使用相同版本的动态库是很重要的。

### 实践建议

- **使用线程安全库**：尽量使用线程安全的动态库，或者确保库的设计考虑了多进程和多线程环境。
- **共享资源保护**：在共享资源（如文件、网络连接）时，使用适当的同步机制保护访问。
- **版本管理**：在部署动态库时，确保所有进程使用一致的版本，避免兼容性问题。

总的来说，操作系统已经为动态库的共享和访问提供了良好的机制，只要库本身是线程安全的，多进程访问通常不会产生冲突。

## 静态链接和动态链接

静态库/动态库是库文件形态，静态链接/动态链接是链接方式。

### 静态链接

静态链接发生在构建可执行文件时。链接器把目标文件和静态库中被引用的代码、数据复制进最终可执行文件，并完成符号解析和重定位。

优点：

1. 部署简单，运行时不依赖外部 `.so`。
2. 启动时少一些动态装载和符号解析成本。
3. 版本可控，不容易被系统库变化影响。

缺点：

1. 可执行文件更大。
2. 多个进程不能共享同一份库代码页。
3. 库更新后需要重新链接和发布可执行文件。
4. 安全补丁不能只替换动态库完成。

### 动态链接

动态链接把库依赖保留到运行时，由动态链接器加载 `.so`，解析符号并做重定位。

常见过程：

```text
execve
-> loader 读取 ELF 依赖
-> 映射动态库到进程地址空间
-> 做符号解析和重定位
-> 跳到程序入口
```

动态链接可以在启动时完成，也可以通过 `dlopen/dlsym` 运行期手动加载。

优点：

1. 可执行文件更小。
2. 多进程共享动态库只读代码页，节省内存。
3. 更新库更方便。
4. 支持插件化和按需加载。

缺点：

1. 部署要处理库搜索路径、版本兼容和 ABI。
2. 首次调用可能有 PLT/GOT 懒绑定开销。
3. 符号冲突和依赖地狱更复杂。

## 运行期调用动态库函数

如果程序启动时就确定要依赖某个动态库，通常在链接阶段使用 `-L`、`-l` 指定库，运行时由动态链接器加载。如果要做插件化、可选能力或按需加载，可以在运行期手动打开动态库并查找函数符号。

Linux/Unix 常见写法：

```cpp
#include <dlfcn.h>
#include <iostream>

using AddFn = int (*)(int, int);

int main() {
    void* handle = dlopen("./libcalc.so", RTLD_NOW);
    if (!handle) {
        std::cerr << dlerror() << '\n';
        return 1;
    }

    dlerror(); // 清空旧错误
    auto add = reinterpret_cast<AddFn>(dlsym(handle, "add"));
    if (const char* err = dlerror()) {
        std::cerr << err << '\n';
        dlclose(handle);
        return 1;
    }

    std::cout << add(1, 2) << '\n';
    dlclose(handle);
}
```

编译时通常要链接动态加载库：

```bash
g++ main.cpp -ldl -o main
```

Windows 下对应的是 `LoadLibrary`、`GetProcAddress` 和 `FreeLibrary`。

易错点：

1. 导出的函数如果给 C/C++ 混合或插件系统调用，建议使用 `extern "C"` 避免 C++ name mangling 影响符号名。
2. 不要跨动态库边界传递不稳定 ABI 对象，例如不同编译器或不同 STL 实现里的 `std::string/std::vector`。
3. 谁分配谁释放，跨库传递内存时最好提供成对的 `create/destroy` 接口，避免分配器不一致。
4. `dlopen` 成功不代表所有调用都安全，还要处理版本、线程安全、初始化顺序和 `dlclose` 后函数指针失效。

## 多个库的链接顺序

Linux 下静态库链接通常对顺序敏感。GNU ld 默认从左到右扫描目标文件和库：当扫描到某个库时，只会从库里抽取“当前已经出现的未解析符号”所需的目标文件。因此依赖方要写在前面，被依赖库要写在后面。

```bash
# main.o 依赖 libfoo.a，libfoo.a 又依赖 libbar.a
g++ main.o -lfoo -lbar -o app   # 常见正确顺序
g++ main.o -lbar -lfoo -o app   # 可能 undefined reference
```

如果库之间存在循环依赖，可以用：

```bash
g++ main.o -Wl,--start-group -lfoo -lbar -Wl,--end-group -o app
```

但 `--start-group` 会让链接器多轮扫描，链接时间更长，不应滥用。更好的方式是理清依赖方向，拆分公共库或调整接口。

动态库也有依赖顺序和符号解析问题，但运行时还受到 `DT_NEEDED`、`rpath/runpath`、`LD_LIBRARY_PATH`、全局符号可见性、`RTLD_GLOBAL/LOCAL` 等影响。工程上应使用 CMake/Makefile 明确目标依赖，不要靠手写命令碰运气。

## 不同编译器编译的库能否混用

能否混用取决于 ABI 是否兼容，而不是只看语言都是 C++。

1. **C ABI 通常更稳**：`extern "C"` 函数、POD 结构、固定宽度整数、谁分配谁释放，跨编译器更容易兼容。
2. **C++ ABI 风险更高**：name mangling、异常、RTTI、虚表布局、`std::string/std::vector` 内部结构、内存分配器都可能不同。
3. **同一编译器不同版本也要小心**：尤其是标准库 ABI 变更、编译选项不同、Debug/Release CRT 不一致。
4. **跨库边界不抛 C++ 异常**：异常对象和栈展开 ABI 不兼容时会出问题，建议转换成错误码或状态对象。

插件系统常见做法是导出稳定 C 接口：

```cpp
extern "C" Plugin* create_plugin();
extern "C" void destroy_plugin(Plugin*);
```

同时避免让调用方释放库内部分配的对象，所有跨边界资源都提供成对创建和销毁函数。

## 面试回答模板

静态链接是在链接阶段把需要的库代码复制进可执行文件，部署简单但文件更大，库升级要重新发版。动态链接是在运行时由动态链接器加载 `.so`，通过 GOT/PLT 等机制完成符号解析和重定位，多个进程可以共享动态库代码页，升级更方便，但要处理库路径、版本和 ABI 兼容问题。插件系统通常用动态链接和 `dlopen/dlsym`。多个库链接时，静态库通常按“依赖方在前、被依赖方在后”的顺序排列；不同编译器的 C++ 库混用要看 ABI，最好用稳定 C 接口隔离。
