# Q163. C++模板基础与实例化

C++ 模板是泛型编程的基础。它允许把类型、常量或模板本身作为参数，让同一份代码在编译期生成适配不同类型的具体实现。

## 1. 函数模板

函数模板用于描述一类函数：

```cpp
template <typename T>
T maxValue(const T& a, const T& b) {
    return a < b ? b : a;
}
```

调用时编译器会根据实参类型做模板参数推导：

```cpp
int a = maxValue(1, 2);          // T = int
double b = maxValue(1.0, 2.0);   // T = double
```

模板参数推导通常不考虑返回值，只看函数实参、显式模板参数和上下文约束。

## 2. 类模板

类模板用于生成一族类型：

```cpp
template <typename T>
class Box {
public:
    explicit Box(T value) : value_(value) {}
    const T& value() const { return value_; }

private:
    T value_;
};

Box<int> a(1);
Box<std::string> b("hello");
```

`Box<int>` 和 `Box<std::string>` 是两个不同类型。模板本身不是类型，模板实例化之后才形成具体类型。

## 3. 非类型模板参数

模板参数不只能是类型，也可以是编译期常量：

```cpp
template <typename T, std::size_t N>
class Array {
public:
    T data[N];
};

Array<int, 16> arr;
```

常见场景包括固定大小数组、对齐值、哈希桶数量、矩阵维度等。非类型模板参数必须能在编译期确定。

## 4. 模板实例化

模板实例化分为隐式实例化和显式实例化：

1. **隐式实例化**：使用某个模板实参时，编译器自动生成对应代码。
2. **显式实例化**：手动要求编译器生成某个实例，例如 `template class Box<int>;`。
3. **显式特化**：为某个类型提供专门实现，例如 `template <> class Box<bool> { ... };`。

模板通常要把定义放在头文件里。原因是编译器在实例化时需要看到完整定义；如果只有声明，其他翻译单元无法生成对应类型的代码，容易产生链接错误。

## 4.1 模板特化与偏特化

模板特化是为某些模板参数提供更专门的实现。它常用于类型 traits、容器对特殊类型优化、策略选择等场景。

### 全特化

全特化要求把所有模板参数都固定下来：

```cpp
template <typename T>
struct TypeName {
    static const char* value() { return "generic"; }
};

template <>
struct TypeName<int> {
    static const char* value() { return "int"; }
};
```

`TypeName<int>` 会走专门实现，其他类型走通用模板。

### 偏特化

偏特化只固定一部分模板参数，或者对参数形态做约束。类模板支持偏特化：

```cpp
template <typename T>
struct IsPointer {
    static constexpr bool value = false;
};

template <typename T>
struct IsPointer<T*> {
    static constexpr bool value = true;
};
```

这里 `T*` 是一种参数形态，`int*`、`std::string*` 都会匹配偏特化版本。

函数模板不支持偏特化。如果需要类似效果，通常使用函数重载、`std::enable_if`、tag dispatch 或 C++20 Concepts。

### 特化匹配原则

1. 编译器会在可匹配的模板中选择最专门的版本。
2. 全特化比偏特化更具体。
3. 多个偏特化同样匹配且无法判断谁更专门时，会产生二义性。
4. 特化版本要和主模板声明保持语义一致，否则调用方很难理解。

真实场景：

1. `std::hash<T>` 为自定义 key 提供特化。
2. type traits 通过偏特化识别指针、引用、数组、const 类型。
3. `std::vector<bool>` 是标准库中著名的特化，用位压缩节省空间，但也带来引用代理等副作用。

## 5. 模板和多态

模板常用于静态多态，虚函数常用于动态多态：

| 对比项 | 模板/静态多态 | 虚函数/动态多态 |
| --- | --- | --- |
| 决定时机 | 编译期 | 运行期 |
| 调用开销 | 通常可内联，无虚调用 | 需要 vptr/vtable 间接调用 |
| 代码体积 | 不同类型会生成多份实例 | 一份接口，多态派发 |
| 适合场景 | 容器、算法、数值库、策略可在编译期确定 | 插件、运行时对象集合、接口稳定扩展 |

示例：策略通过模板参数传入：

```cpp
template <typename Compare>
void sortWithPolicy(std::vector<int>& nums, Compare comp) {
    std::sort(nums.begin(), nums.end(), comp);
}
```

## 6. SFINAE、Concepts 和约束

模板错误信息可能很复杂，因为模板会在实例化时才检查具体表达式。常见约束方式：

1. **SFINAE**：替换失败不是错误，可让不满足条件的重载从候选集中移除。
2. **`std::enable_if` / type traits**：按类型性质选择模板。
3. **C++20 Concepts**：直接声明模板参数要满足的语义约束，可读性更好。

```cpp
#include <concepts>

template <std::integral T>
T addOne(T x) {
    return x + 1;
}
```

## 6.1 什么是元编程

元编程是“编写在编译期生成、检查或选择代码的代码”。C++ 元编程主要依赖模板、类型 traits、`constexpr`、SFINAE、Concepts、折叠表达式等机制，把一部分计算和分支从运行期提前到编译期。

常见用途：

1. **类型计算**：判断类型是否可拷贝、是否为指针、是否有某个成员函数。
2. **编译期分发**：根据类型特征选择不同实现，例如 POD 类型用快速拷贝，非平凡类型逐个构造。
3. **静态约束**：在编译期拒绝不满足接口约定的类型，减少运行期错误。
4. **零开销抽象**：把策略、维度、容量、分配器等作为模板参数，让编译器内联和优化。
5. **编译期常量计算**：例如固定维度矩阵、协议字段布局、查表数据生成。

示例：用 type traits 做编译期分支：

```cpp
#include <type_traits>

template <typename T>
void destroy(T* p) {
    if constexpr (!std::is_trivially_destructible_v<T>) {
        p->~T();
    }
}
```

易错点：

1. 元编程不是运行期反射，模板实例化发生在编译期。
2. 过度模板化会导致编译慢、错误信息长、二进制膨胀。
3. 编译期分支也要关注 ABI 和接口稳定性，公共 SDK 过多暴露模板实现会增加兼容成本。
4. C++20 Concepts 更适合表达约束，不要所有场景都用复杂 `enable_if`。

## 7. 易错点

1. 模板定义通常放头文件，不只是声明放头文件。
2. 模板不是运行期反射，它是在编译期生成代码。
3. 模板参数推导不看返回值。
4. 模板过度使用可能导致编译慢、错误信息长、二进制体积膨胀。
5. 静态多态不能替代所有动态多态，运行期才知道对象类型时仍需要虚函数、类型擦除或 `std::variant` 等方案。
6. 函数模板不能偏特化，遇到这个面试追问要回答“用重载或约束替代”。

## 8. 真实场景

1. STL 容器和算法大量使用模板，例如 `std::vector<T>`、`std::sort`。
2. 序列化、RPC、数学库常用模板消除运行期开销。
3. `std::function`、`std::any`、`std::variant` 等库设施在内部结合模板和类型擦除。
4. 高性能服务中，编译期策略可用模板注入，例如哈希函数、比较器、分配器。

## 9. 模板和类封装怎么选

面试里问“模板和类封装各自在什么情况下使用，有什么优缺点”，要先说明二者不是同一维度的概念。

1. **类封装**强调把数据和操作组织到稳定接口后面，隐藏实现细节。
2. **模板**强调把类型、常量或策略参数化，在编译期生成适配不同类型的代码。

### 9.1 适合使用类封装的场景

类封装适合表达运行期对象、业务实体、资源生命周期和稳定接口：

1. 需要隐藏内部状态，只暴露受控方法。
2. 对象有明确生命周期，例如 socket、文件、锁、数据库连接。
3. 调用方不应该关心内部数据结构。
4. 需要通过继承、组合或接口隔离组织复杂业务。

示例：

```cpp
class TcpConnection {
public:
    void send(const std::string& data);
    void close();

private:
    int fd_ = -1;
    Buffer input_;
    Buffer output_;
};
```

这里重点是资源和状态封装，而不是泛型。

### 9.2 适合使用模板的场景

模板适合表达和类型无关、但逻辑结构相同的代码：

1. 容器：`vector<T>`、`optional<T>`。
2. 算法：`sort(first, last, comp)`。
3. 策略：比较器、哈希函数、分配器。
4. 编译期常量：固定大小矩阵、环形缓冲区容量。
5. 高性能路径：希望编译器内联并消除运行期开销。

示例：

```cpp
template <typename T, typename Compare>
const T& selectBetter(const T& a, const T& b, Compare comp) {
    return comp(a, b) ? a : b;
}
```

这里调用方传入不同类型和比较策略，编译器生成对应代码。

### 9.3 优缺点对比

| 对比项 | 类封装 | 模板 |
| --- | --- | --- |
| 主要目标 | 隐藏状态和实现，提供稳定接口 | 泛型和编译期复用 |
| 决定时机 | 多数行为运行期决定 | 类型和策略编译期决定 |
| 性能 | 普通调用，虚函数可能有间接开销 | 可内联，通常零运行期开销 |
| 灵活性 | 运行期替换对象更自然 | 类型必须编译期确定 |
| 编译成本 | 较低 | 可能增加编译时间和二进制体积 |
| 错误信息 | 通常较直接 | 模板错误可能较长 |
| ABI 稳定性 | 更容易隐藏实现和保持 ABI | 模板定义常放头文件，暴露实现 |

### 9.4 真实工程取舍

1. **运行期扩展**：插件、协议 handler、设备适配器更适合抽象类、工厂和虚函数。
2. **编译期策略**：排序比较器、哈希函数、固定容量容器更适合模板。
3. **稳定 ABI**：对外 SDK 不希望暴露实现时，优先普通类、Pimpl 或纯虚接口。
4. **性能敏感基础库**：容器、算法、数值计算优先模板。
5. **复杂模板约束**：C++20 可用 Concepts 改善可读性和错误信息。

模板和封装也可以组合：类模板本身仍然可以封装状态，例如 `std::vector<T>` 既是模板，也是对动态数组内存管理的封装。

## 10. 面试回答模板

C++ 模板是编译期泛型机制，可以写函数模板、类模板，也可以使用非类型模板参数。模板在使用具体类型时实例化，生成对应代码，所以定义通常要放在头文件里。模板支持静态多态，调用可内联、没有虚函数开销，但可能导致代码膨胀和编译变慢；虚函数是运行期多态，适合对象类型运行时才确定的场景。复杂模板可以用 SFINAE、type traits 或 C++20 Concepts 做约束。

模板和类封装不是互斥关系。类封装关注隐藏状态和实现，适合资源管理、业务对象和稳定接口；模板关注类型参数化和编译期复用，适合容器、算法、策略和性能敏感基础库。运行期扩展更适合接口和工厂，编译期策略更适合模板。工程中常把二者结合，例如 `std::vector<T>` 既是模板，也是对动态数组的封装。
