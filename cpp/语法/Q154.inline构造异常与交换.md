# Q154. inline、构造异常与无临时变量交换

## 1. inline 函数可以递归吗

`inline` 的语义是给编译器一个“可内联展开”的建议，同时允许函数定义出现在多个翻译单元中，不违反 ODR。它不等于强制把函数体展开。

递归函数可以声明为 `inline`：

```cpp
inline int fact(int n) {
    return n <= 1 ? 1 : n * fact(n - 1);
}
```

但递归调用不可能无限展开。编译器最多在能证明收益和深度有限时展开一部分，更多时候仍然生成普通函数调用。

易错点：

1. `inline` 不是性能保证，是否展开由编译器决定。
2. 类内定义的成员函数默认具有 inline 属性。
3. 递归、函数过大、包含复杂控制流或取函数地址，都可能让编译器放弃内联。

## 2. 构造函数中能否抛异常

构造函数可以抛异常。对象构造过程中如果抛出异常，这个对象被认为没有构造完成，因此它自己的析构函数不会被调用。

但是已经构造成功的成员对象和基类子对象会按逆序析构：

```cpp
#include <stdexcept>
#include <string>

struct A {
    std::string s;
    A() {
        throw std::runtime_error("failed");
    }
    ~A() {
        // A 没有构造完成时不会执行到这里
    }
};
```

工程实践：

1. 构造函数失败时抛异常是合理的，因为构造函数没有返回值表达失败。
2. 构造函数里已经获取的资源，应交给成员对象管理，例如 `std::unique_ptr`、`std::vector`、文件句柄 RAII 包装类。
3. 不要在析构函数中抛异常，尤其是栈展开期间再次抛异常会导致 `std::terminate`。

## 3. 不使用第三个变量交换两个数

常见写法有算术法和异或法：

```cpp
a = a + b;
b = a - b;
a = a - b;
```

```cpp
a ^= b;
b ^= a;
a ^= b;
```

但真实工程不推荐这样写：

1. 算术法可能发生有符号整数溢出，属于未定义行为。
2. 异或法要求整数类型，且如果两个引用指向同一对象会把值变成 0。
3. 可读性差，编译器对 `std::swap` 已经能生成高效代码。

真实代码应使用：

```cpp
using std::swap;
swap(a, b);
```

面试中如果题目限制“不给额外变量”，可以说明算术法和异或法，再主动指出溢出、同址和可读性风险。

## 4. 面试回答模板

`inline` 函数可以递归，但递归调用不会被无限展开，`inline` 只是允许内联和多翻译单元定义的语义，不保证性能。构造函数可以抛异常，抛出后对象本身不算构造完成，所以不会调用该对象析构函数，但已经构造完成的成员和基类会被析构。两个变量不借助第三个变量可以用加减法或异或法交换，但有溢出、同址和可读性问题，工程里应使用 `std::swap`。
