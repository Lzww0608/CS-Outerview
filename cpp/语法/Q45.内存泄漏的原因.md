# 内存泄漏的原因

1. **未释放动态分配的内存**：在C和C++中，使用 `new` 或 `malloc` 等函数动态分配内存后，如果忘记使用 `delete` 或 `free` 释放内存，就会发生内存泄露。
2. **资源泄露**：除了内存外，其他资源如文件句柄、数据库连接、网络连接等，如果没有被适时释放，也可以被视为内存泄露。
3. **循环引用**：在某些语言（如 Java 和 Python）中，使用垃圾收集器来自动管理内存。但如果对象间存在循环引用，垃圾收集器可能无法正确识别并回收这些对象，从而导致内存泄露。
4. **内存分配与释放不匹配**：在C++中，如果使用 `new[]` 分配内存，但用 `delete` 而非 `delete[]` 释放内存，会导致部分内存未被释放。
5. **程序逻辑错误**：程序中的逻辑错误可能导致某些内存只在特定条件下被释放，或者根本不被释放。
6. **数据结构的不当使用**：例如，无限增长的数据结构（如某些类型的日志记录器或缓存实现）如果没有适当的大小限制或过期策略，可能会不断消耗更多内存。
7. **静态和全局变量**：过度使用静态和全局变量可能导致内存无法释放，因为这些变量在程序整个生命周期内都存在。
8. **内存碎片**：虽不严格算作内存泄露，但长时间运行的程序可能因频繁分配和释放小块内存导致内存碎片，从而降低内存使用效率。

## 内存泄漏最后会怎么样

内存泄漏不会立刻必然崩溃，它的影响取决于泄漏速度、进程生命周期、机器内存、cgroup 限制和系统 overcommit 策略。

常见发展过程：

1. **进程 RSS 持续上涨**：泄漏对象被引用或无法释放，常驻内存越来越大。
2. **触发频繁缺页和回收**：系统开始回收 page cache，进程和其他程序的 I/O 性能下降。
3. **swap 或内存压缩压力上升**：如果启用 swap，延迟会明显抖动。
4. **分配失败**：`malloc` 返回 `NULL`，`new` 抛 `std::bad_alloc`。
5. **被 OOM Killer 杀死**：Linux 在内存紧张且无法回收时，会选择进程杀掉；容器环境下通常先触发 cgroup OOM。

对其他程序的影响：

1. 同一台机器内存是共享资源，泄漏进程会挤占 page cache 和可用内存。
2. 其他进程可能因为 page cache 减少导致磁盘 I/O 变慢。
3. 系统可能进入 swap，导致整体延迟上升。
4. OOM Killer 不一定杀泄漏进程，可能杀掉分值更高或更关键的进程。
5. 在容器里如果设置了内存限制，通常影响被限制在该 cgroup 内，但宿主机仍可能受到 page cache 和 I/O 压力影响。

工程排查：

1. 看 RSS、VIRT、PSS、page fault、`/proc/<pid>/smaps`。
2. 用 ASan、Valgrind、heaptrack、gperftools、jemalloc profile 定位分配栈。
3. 区分“真正泄漏”和“缓存未设置上限”。缓存可能能释放，但没有淘汰策略时效果和泄漏类似。
4. 长生命周期服务要做压测和 soak test，观察内存是否随请求数线性上涨。
