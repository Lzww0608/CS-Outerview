# 虚函数表与虚函数表指针

虚函数表与虚函数表是用来实现**多态**的，每一个类只有一个虚函数表

**静态多态**：函数重载（编译期确定）

**动态多态**：虚函数（运行期确定）





### 虚函数表的创建时机：

+ 生成时间：
  + 编译期生成，识别到`virtual`关键字修饰的函数，**虚函数地址的数组**
  + `.bss`: 未初始化的或者自动初始化为0的全局、静态变量
  + `.data`: 已经初始化的全局、静态变量
  + `.rodata`: 只读数据段，虚函数表，常量数据
+ 存放在哪里： 可执行程序（磁盘，只读数据段`.rodata`）， 运行状态（内存）



### 虚函数指针：

+ 存放位置：
  + 一般在类的最开始位置，4字节(32位)， 8字节(64位)
  + `vptr` 是对象内的隐藏指针字段，对象在栈上、堆上或静态区时，`vptr` 也跟着对象存放在对应位置；它指向只读数据段中的虚函数表
  + 同一个动态类型的不同对象各自有一份 `vptr` 存储空间，但通常指向同一张虚函数表
+ 创建时间：
  + 类对象构造的时候，初始化`vptr`
  + 如果对象是派生类，在`vptr`随着构造函数逐层向下进行构造，每个类指向自己的虚函数表；即构造函数先分配堆或者栈的内存，然后初始化`vptr`，然后初始化其他成员并执行构造函数体
  + **注：`vptr`在构造期间可能多次更新。当基类构造函数运行时，`vptr`指向基类虚函数表。而当派生类构造函数执行时，`vptr`会更新为指向派生类的虚函数表。这保证了构造期间，任何函数的调用都将解析到当前构造阶段的正确版本。**
+ 对象析构：
  + 同理，在析构期间，从子类析构到父类，`vptr`将依次被设置会每个级别的基类。
  + 这里也引出了另外一个问题，在继承结构中析构函数最好为虚函数，这样当指向派生类的基类指针这种结构出现的时候，我们进行析构，通过虚函数指针的作用可以先执行子类的析构，再执行父类的析构，防止析构子类之后找不到父类的析构函数了（这是另外一个较大的问题，这里太小写得简略一下，可以自行搜索一下）。

## 构造函数可不可以是虚函数

构造函数不能是虚函数。

原因：

1. 虚函数调用依赖对象里的 `vptr`。
2. 构造函数的职责之一就是初始化对象，包括初始化当前构造阶段对应的 `vptr`。
3. 构造开始前，对象还没有形成完整的动态类型，无法通过虚表做动态派发。
4. 构造函数没有普通成员函数那样的继承重写语义，派生类构造必须显式或隐式先构造基类。

如果想根据类型创建对象，可以用工厂函数：

```cpp
class Base {
public:
    virtual ~Base() = default;
};

std::unique_ptr<Base> createByType(int type);
```

## 纯虚函数和普通虚函数

普通虚函数有默认实现，派生类可以选择重写，也可以直接继承基类实现：

```cpp
struct Base {
    virtual void run() {
        // default behavior
    }
};
```

纯虚函数用 `= 0` 声明，表示这个接口在当前类中没有可直接使用的完整行为。包含纯虚函数的类是抽象类，不能直接实例化：

```cpp
struct Handler {
    virtual ~Handler() = default;
    virtual void handle() = 0;
};
```

核心区别：

1. 普通虚函数强调“可覆盖”，纯虚函数强调“必须由具体派生类补全接口契约”。
2. 派生类如果没有实现所有纯虚函数，派生类仍然是抽象类。
3. 纯虚函数仍然会占据虚表槽位，动态派发机制和普通虚函数一致。
4. 纯虚函数也可以在类外提供定义，例如基类析构流程中复用公共逻辑，但它仍然保持纯虚属性。

```cpp
struct Base {
    virtual void f() = 0;
};

void Base::f() {
    // optional common implementation
}
```

典型应用场景：

1. 接口类：例如 RPC handler、插件接口、存储引擎抽象。
2. 模板方法：基类固定流程，派生类补全关键步骤。
3. 单元测试替身：用抽象接口隔离网络、文件、数据库等外部依赖。

易错点：

1. 抽象类不能实例化，但可以定义指针或引用指向派生类对象。
2. 不要在构造函数或析构函数里调用纯虚函数；构造/析构期间动态类型不是最终派生类，可能触发未定义行为或运行时错误。
3. 多态基类如果有虚函数，通常要提供虚析构函数，否则通过基类指针删除派生类对象不安全。

## 析构函数可不可以是虚函数

析构函数可以是虚函数，而且如果一个类要通过基类指针删除派生类对象，基类析构函数必须是虚函数。

错误示例：

```cpp
struct Base {
    ~Base() {}
};

struct Derived : Base {
    ~Derived() {}
};

Base* p = new Derived();
delete p; // 未定义行为，可能只调用 Base::~Base()
```

正确写法：

```cpp
struct Base {
    virtual ~Base() = default;
};
```

如果类不打算作为多态基类，可以不写虚析构，避免每个对象增加 vptr 成本。

## 构造和析构期间虚函数调用

构造和析构期间调用虚函数，不会动态派发到“更外层”的派生类版本。

1. 基类构造阶段，对象还只是基类部分，`vptr` 指向基类虚表。
2. 派生类构造阶段，`vptr` 再更新为派生类虚表。
3. 析构时顺序相反，派生类析构后进入基类析构，`vptr` 会退回基类虚表。

因此不要依赖构造函数或析构函数中的虚函数调用实现多态行为。

## 一个对象只能有一个虚表指针吗

不一定。单继承且只有一个多态基类时，一个对象通常只有一个主 `vptr`；但在多继承、虚继承等复杂对象模型下，一个完整对象中可能包含多个基类子对象，每个需要独立动态派发的子对象都可能有自己的 `vptr`。

示例：

```cpp
struct A {
    virtual void fa() {}
    int a = 0;
};

struct B {
    virtual void fb() {}
    int b = 0;
};

struct C : A, B {
    void fa() override {}
    void fb() override {}
    int c = 0;
};
```

在 64 位常见 ABI 下，`C` 对象里通常会有 `A` 子对象的一份 `vptr`，也会有 `B` 子对象的一份 `vptr`。通过 `A*` 调用 `fa()` 和通过 `B*` 调用 `fb()` 时，指针看到的是不同基类子对象起始地址，编译器需要用对应子对象的虚表完成动态派发，必要时还会生成 this 指针调整 thunk。

因此回答“对象里有没有虚表指针”时要分层：

1. 非多态类对象：没有 `vptr`。
2. 单继承多态类对象：通常一个 `vptr`。
3. 多继承或虚继承多态对象：可能多个 `vptr`，对象大小和布局由 ABI 决定。
4. 虚函数表本身不在对象里，对象只保存指向虚表的指针。

## 虚函数调用过程

通过基类指针或引用调用虚函数时，典型过程是：

1. 编译器发现调用目标是虚函数，生成间接调用代码。
2. 运行时先从对象起始位置或对应基类子对象位置取出 `vptr`。
3. 根据编译期确定的虚函数槽位偏移，从虚表中取出函数地址。
4. 用该地址发起间接调用，必要时先调整 `this` 指针。

这也是虚函数相比普通函数多出的开销来源：一次内存读取、一次间接跳转，以及可能阻碍内联和分支预测。但它换来了运行时多态，适合插件、RPC handler、抽象接口、状态机等需要按真实对象类型分发行为的场景。

## 查询虚表的时间复杂度

虚函数调用不是在虚表里按函数名查找，也不是遍历虚表。编译器在编译期已经知道“要调用的是第几个虚函数槽位”，运行时只需要：

1. 从对象或对应基类子对象中取出 `vptr`。
2. 用固定槽位偏移访问虚表中的函数指针。
3. 通过函数指针做一次间接调用。

因此虚表查询本身是 `O(1)`。真正的额外成本主要来自固定常数开销：

1. 多一次或几次内存读取。
2. 间接跳转可能降低分支预测命中率。
3. 动态派发通常会阻碍内联优化。
4. 多继承场景可能还要做 `this` 指针调整，但仍然是常数复杂度。

所以面试中可以回答：虚表查找复杂度是 `O(1)`，但它不是“完全没有成本”，性能差异常体现在缓存命中、间接分支和内联机会减少上。

## 虚函数地址是怎么定位的

从机器实现角度看，虚函数调用通常不是“按函数名查表”，而是编译器在编译期确定槽位，运行期按固定偏移取函数指针。

可以抽象成：

```text
对象地址 obj
  -> 读取 obj 中的 vptr
  -> vptr + slot_index * sizeof(void*)
  -> 读取虚函数地址
  -> 间接 call
```

在 Itanium C++ ABI 这类常见 ABI 下，虚表地址点附近还可能有 `offset-to-top`、RTTI 指针等元数据。对象里的 `vptr` 不一定指向虚表物理起点，而是指向虚函数槽位区域的“地址点”。多继承时，不同基类子对象可能各有自己的 `vptr`，某些虚函数槽位还会指向 thunk，用来在调用真正函数前调整 `this` 指针。

因此面试里可以这样回答：

1. 虚函数的槽位编号由编译器根据类定义和 ABI 规则确定。
2. 调用时从对象或基类子对象取 `vptr`，按槽位偏移取函数地址。
3. 多继承、虚继承可能涉及多个 `vptr` 和 `this` 调整。
4. 不同编译器/ABI 的虚表布局细节不同，所以不能跨 ABI 假设对象布局兼容。

## 基类和子类声明顺序不一样怎么办

虚函数调用不是按“派生类里第几个声明的函数”临时查找，而是按基类虚函数槽位和 ABI 规则确定。因此派生类重写函数时，核心是函数签名匹配哪个基类虚函数，而不是派生类源码里的声明顺序。

示例：

```cpp
struct Base {
    virtual void f();
    virtual void g();
};

struct Derived : Base {
    void g() override;
    void f() override;
};
```

虽然 `Derived` 里先声明 `g` 再声明 `f`，但 `Derived` 的虚表中，`Base::f` 对应的槽位仍会被 `Derived::f` 覆盖，`Base::g` 对应的槽位仍会被 `Derived::g` 覆盖。通过 `Base* p = new Derived; p->f();` 调用时，编译器仍然按 `Base::f` 的固定槽位取地址。

派生类新增虚函数时，通常会在派生类自己的虚表区域增加新槽位：

```cpp
struct Derived2 : Base {
    void g() override;  // 覆盖 Base::g 槽位
    virtual void h();   // 新增槽位
};
```

容易混淆的是函数隐藏和重载：

```cpp
struct Bad : Base {
    void f(int); // 不是 override Base::f，而是隐藏 Base::f
};
```

工程上建议给所有重写函数加 `override`。如果签名不匹配，编译器会直接报错，避免误以为覆盖了基类虚函数。

## 虚表里存的是绝对地址吗

面试里可以先回答“运行时可以把虚表槽位理解为可调用目标地址”，再补充它不一定是源码层面或文件层面的固定绝对地址。

更准确地说：

1. 在进程运行时，虚表槽位通常保存函数入口地址或调整 `this` 的 thunk 地址，虚调用会把这个地址取出来间接 `call`。
2. 在目标文件、动态库或 PIE 可执行文件里，这些地址可能先以重定位项、相对偏移或 GOT/PLT 相关形式存在，加载器会在装载时根据实际加载基址完成重定位。
3. 开启 ASLR 后，同一个程序每次运行的代码段、动态库和虚表地址都可能不同，因此不能把虚表项当成跨进程、跨运行稳定的绝对地址。
4. 多继承场景下，虚表槽位可能不是直接指向最终成员函数，而是指向 thunk，先调整 `this` 再跳到真实函数。

所以工程上不要依赖虚表项的具体数值。能依赖的是 C++ 语言语义：通过基类指针或引用调用虚函数，会按对象当前动态类型完成派发。

## 虚函数的作用

虚函数的核心作用是实现运行时多态：调用方只依赖基类接口，实际执行哪个实现由对象的动态类型决定。

典型场景：

1. **接口抽象**：业务代码依赖 `Storage`，运行时可以替换成本地文件、Redis、MySQL、Mock 实现。
2. **插件扩展**：基类定义统一入口，插件派生类提供具体行为。
3. **框架回调**：框架持有基类指针，在事件到来时调用派生类实现。
4. **状态机/策略对象**：同一接口下根据不同状态或策略执行不同逻辑。

需要注意：

1. 虚函数提供扩展性，但会带来一次间接调用成本，也可能影响内联。
2. 如果不需要运行时多态，可以用普通函数、模板、函数对象或 CRTP 做编译期多态。
3. 多态基类通常要有虚析构函数，避免通过基类指针删除派生类对象时出现未定义行为。

## 虚函数能不能是 `static`

虚函数不能是 `static` 成员函数。

原因：

1. 虚函数调用依赖对象的动态类型，需要通过对象中的 `vptr` 找到虚函数表。
2. `static` 成员函数不属于某个具体对象，没有 `this` 指针，也无法访问对象内的 `vptr`。
3. 虚函数表达的是“同一个接口在不同对象上的不同行为”，而静态成员函数表达的是“属于类作用域的普通函数”，两者语义冲突。

错误写法：

```cpp
struct Base {
    // static virtual void f(); // 错误：static 和 virtual 不能同时使用
};
```

如果想实现“根据类型分发静态行为”，常见替代方式有：

1. 普通虚函数：让调用依赖对象。
2. 工厂函数：根据类型创建不同派生类对象。
3. CRTP：用模板实现编译期多态。
4. 注册表或函数指针表：用 `type -> function` 的映射做手动分发。

## 类中哪些函数不能为虚函数

严格来说，只有非静态成员函数才可能成为虚函数。常见不能或不适合作为虚函数的情况：

| 函数 | 能否为虚函数 | 原因 |
| --- | --- | --- |
| 构造函数 | 不能 | 对象还在构造，完整动态类型尚未形成 |
| 静态成员函数 | 不能 | 没有 `this` 指针，无法通过对象 `vptr` 动态派发 |
| 普通全局函数 | 不能 | 不属于类成员，没有对象动态类型 |
| 友元函数 | 不能直接作为虚函数 | friend 不是成员函数；可以让它内部调用虚成员函数 |
| 成员函数模板 | 不能是虚函数 | 虚表槽位需要固定函数签名，模板实例集合在编译期不固定 |
| 析构函数 | 可以 | 多态基类通常应该写成 virtual |
| 内联函数 | 可以 | `inline` 不影响虚函数语义，只是优化建议 |
| `final` 函数 | 可以 | `final` 表示不能被更深层派生类继续 override |

成员函数模板不能是虚函数的例子：

```cpp
struct Base {
    template <typename T>
    // virtual void handle(T value); // 错误：成员函数模板不能是 virtual
    void handle(T value);
};
```

原因是虚表需要在编译期为每个虚函数确定槽位，而函数模板本身不是一个具体函数，只有实例化成具体签名后才是函数。可替代方案包括：

1. 把可变类型擦除为 `std::any`、`std::variant` 或基类指针。
2. 用普通虚函数承载稳定接口。
3. 用模板做外层静态分发，内部调用普通虚接口。

## static 成员函数如何实现类似虚函数的功能

`static` 成员函数没有 `this`，不能直接动态派发。如果想实现“按类型或消息调用不同处理逻辑”，常见方案是消息分发机制。

### 1. 注册表分发

用 `message_type -> handler` 的映射表，把静态入口转发给具体处理函数：

```cpp
#include <functional>
#include <string>
#include <unordered_map>

class Dispatcher {
public:
    using Handler = std::function<void(const std::string&)>;

    static void registerHandler(int type, Handler handler) {
        handlers()[type] = std::move(handler);
    }

    static void dispatch(int type, const std::string& payload) {
        auto it = handlers().find(type);
        if (it != handlers().end()) {
            it->second(payload);
        }
    }

private:
    static std::unordered_map<int, Handler>& handlers() {
        static std::unordered_map<int, Handler> table;
        return table;
    }
};
```

这不是 C++ 语言层面的虚函数，而是应用层手动动态分发。它适合网络消息、插件命令、GUI 事件和脚本回调。

### 2. 静态入口 + 对象虚调用

如果最终仍然需要对象多态，可以让静态函数只做查找，再调用对象的虚函数：

```cpp
struct Handler {
    virtual ~Handler() = default;
    virtual void handle(const std::string& payload) = 0;
};

class Router {
public:
    static void dispatch(int type, const std::string& payload) {
        Handler* h = findHandler(type);
        if (h != nullptr) {
            h->handle(payload); // 这里才是真正的虚调用
        }
    }
};
```

### 3. CRTP 静态多态

如果类型在编译期确定，可以用 CRTP：

```cpp
template <typename Derived>
struct Base {
    void run() {
        static_cast<Derived*>(this)->runImpl();
    }
};
```

CRTP 没有虚表开销，但不能像虚函数一样把未知派生类型统一放进基类指针容器里做运行期分发。

## 面试回答模板

虚函数表通常由编译器生成并放在只读数据段，虚表指针 `vptr` 在对象构造过程中由构造函数写入。虚函数调用时先通过对象的 `vptr` 找到虚表，再按槽位取函数地址做间接调用，核心作用是实现运行时多态。构造函数不能是虚函数，因为虚调用依赖已经初始化好的 `vptr` 和完整对象动态类型，而构造函数正是在建立对象。虚函数也不能是 `static`，因为静态成员函数没有 `this` 指针和对象 `vptr`。析构函数可以是虚函数，多态基类应当有 virtual 析构，否则通过基类指针删除派生类对象会产生未定义行为。一个对象不一定只有一个 `vptr`，多继承或虚继承时可能因为多个多态基类子对象而出现多个 `vptr`。
