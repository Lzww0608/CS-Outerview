# C++ 多线程编程

C++ 多线程编程的核心不是“会创建线程”，而是能正确管理线程生命周期、共享数据同步、任务调度和异常退出路径。

## 1. 基本组件

| 组件 | 作用 | 常见场景 |
| --- | --- | --- |
| `std::thread` | 创建和管理线程 | 后台任务、并行计算、I/O worker |
| `std::mutex` | 互斥访问共享数据 | 保护 map、队列、连接状态 |
| `std::lock_guard` | RAII 加锁解锁 | 简单临界区 |
| `std::unique_lock` | 可手动 lock/unlock，可配合条件变量 | 等待条件、复杂锁生命周期 |
| `std::condition_variable` | 条件等待和唤醒 | 生产者消费者、线程池任务队列 |
| `std::atomic` | 原子读写和内存序 | 计数器、状态位、无锁结构 |
| `std::future/promise` | 线程间传递一次性结果 | 异步任务返回值 |

示例：

```cpp
#include <condition_variable>
#include <mutex>
#include <queue>

std::mutex m;
std::condition_variable cv;
std::queue<int> q;
bool stop = false;

void producer(int x) {
    {
        std::lock_guard<std::mutex> lk(m);
        q.push(x);
    }
    cv.notify_one();
}

bool consumer(int& out) {
    std::unique_lock<std::mutex> lk(m);
    cv.wait(lk, [] { return stop || !q.empty(); });

    if (q.empty()) {
        return false;
    }

    out = q.front();
    q.pop();
    return true;
}
```

## 2. 线程生命周期

`std::thread` 创建后必须在析构前变成非 joinable，否则程序会调用 `std::terminate()`。

常见处理方式：

1. `join()`：当前线程等待子线程结束，适合必须回收结果或保证任务完成的场景。
2. `detach()`：线程脱离 `std::thread` 对象独立运行，适合极少数不依赖外部对象生命周期的后台任务。
3. C++20 `std::jthread`：析构时自动请求停止并 join，适合更安全的线程生命周期管理。

```cpp
#include <thread>

void work();

void run() {
    std::thread t(work);

    if (t.joinable()) {
        t.join();
    }
}
```

不建议随意 `detach()`。被 detach 的线程如果访问了已经析构的对象、栈变量或日志资源，很容易产生悬垂引用和退出期崩溃。

## 2.1 一个线程崩溃会影响其他线程吗

同一进程内的线程共享地址空间和进程资源，所以一个线程发生严重错误通常会导致整个进程退出，其他线程也会被操作系统一起终止。

常见情况：

1. **未捕获 C++ 异常逃出线程入口函数**：标准库会调用 `std::terminate()`，进程结束。
2. **空指针、越界、UAF 等触发 `SIGSEGV`**：信号是发给进程中的某个线程处理的；如果没有安装可靠处理逻辑，默认动作是终止整个进程。
3. **调用 `abort()` 或断言失败**：默认终止整个进程，并可能生成 core dump。
4. **线程写坏共享内存**：即使没有立即崩溃，也可能破坏其他线程的数据结构，之后在别的线程表现为崩溃。

线程崩溃和进程崩溃的关键区别：

1. 多进程模型中，一个 worker 进程崩溃通常不会直接破坏其他进程地址空间，master 可以拉起新 worker。
2. 多线程模型中，线程之间隔离弱，一个线程的内存错误会污染整个进程。
3. 这也是浏览器、Nginx、数据库、插件系统常用“多进程 + 进程内多线程/事件循环”混合架构的原因之一。

工程防护：

1. 在线程入口处捕获业务异常，记录日志并安全退出线程。
2. 用 ASan/TSan/UBSan、core dump、`thread apply all bt` 定位崩溃线程和其他线程状态。
3. 对不可信插件、脚本、图像解码任务使用独立进程或沙箱隔离。
4. 共享数据用 RAII、锁、原子变量和清晰的所有权模型，减少内存破坏。

## 2.2 多线程一定比单线程快吗

不一定。多线程能提升性能的前提是任务可以并行、共享状态少、调度和同步成本低，并且瓶颈不在同一个串行资源上。

多线程可能更快的场景：

1. CPU 密集任务可以拆分到多个核上并行执行。
2. I/O 密集任务可以在等待磁盘、网络、数据库时让其他线程继续工作。
3. 生产者消费者模型能把主链路和后台任务解耦，例如异步日志、异步压缩。

多线程可能不快甚至更慢的原因：

1. 线程创建、销毁和上下文切换有成本。
2. 锁竞争、条件变量等待、原子自旋会消耗 CPU。
3. 共享数据会带来缓存一致性流量、伪共享和内存屏障开销。
4. 任务太小，调度成本大于并行收益。
5. 瓶颈在数据库、磁盘、网卡或下游服务，增加线程只会增加排队。

面试可以总结为：单线程模型简单、没有锁竞争；多线程能利用多核和隐藏 I/O 等待，但要通过压测证明收益。Nginx/Redis 这类系统常把核心事件循环做得很轻，再把耗时任务拆出去，而不是盲目增加线程。

## 2.3 并发和并行的区别

并发（concurrency）强调“同时处理多个任务”的结构设计，并不要求这些任务在同一时刻真的运行；并行（parallelism）强调“同一时刻在多个 CPU 核上同时执行多个任务”。

典型区别：

1. **单核事件循环**：可以并发处理很多连接，但同一时刻只有一个任务在 CPU 上执行，不是并行。
2. **多线程 CPU 计算**：多个线程在多核上同时跑矩阵计算或排序，属于并行。
3. **I/O 密集服务**：通过 epoll、协程或线程池让等待 I/O 的任务让出执行权，核心目标是提升并发能力。
4. **CPU 密集任务**：需要把任务拆到多个核上并行执行，核心目标是缩短计算时间。

工程上常见误区是把“并发数高”等同于“并行度高”。例如一个 Reactor 线程可以维护十万连接，但业务回调如果都在同一个线程里执行，CPU 计算仍然是串行瓶颈。反过来，开很多线程也不一定带来并行收益，如果线程都在抢同一把锁、等同一个数据库连接池或频繁上下文切换，吞吐反而会下降。

## 2.4 线程数量可以无限创建吗

不能。`std::thread` 最终会创建操作系统线程，线程数量受内存、内核参数、用户限制和调度开销共同约束。

主要限制：

1. **线程栈**：每个线程都有独立栈，Linux 默认 pthread 栈常见是数 MB 级，线程越多虚拟地址和物理提交压力越大。
2. **用户进程数限制**：`ulimit -u` 或 `/etc/security/limits.conf` 会限制某个用户可创建的进程/线程数量。
3. **系统线程上限**：`/proc/sys/kernel/threads-max`、`pid_max`、cgroup `pids.max` 都可能限制创建数量。
4. **内存和 cgroup 限制**：容器中即使宿主机资源很多，也可能被 memory/pids cgroup 限制。
5. **调度成本**：线程太多会带来上下文切换、运行队列排队、缓存失效和锁竞争，吞吐可能下降。

可以用 `pthread_attr_setstacksize` 调整 pthread 栈大小，C++ 标准库 `std::thread` 本身不直接暴露栈大小参数；工程上更常见的做法是使用线程池，避免按请求无限创建线程。

面试回答可以说：能创建多少没有固定数字，要看线程栈大小、系统限制、容器限制和业务负载。服务端通常按 CPU 核数、I/O 等待比例和压测结果配置线程池，而不是让每个连接或每个请求创建一个线程。

## 3. 共享数据同步

多线程 bug 通常来自三类问题：

1. **数据竞争**：多个线程并发访问同一对象，至少一个写，且没有同步。
2. **死锁**：多把锁顺序不一致，或同一线程重复获取非递归锁。
3. **可见性和重排序**：一个线程写入的状态，另一个线程没有用正确同步方式读取。

常见策略：

1. 能不共享就不共享，用消息队列、线程封闭或不可变对象降低复杂度。
2. 复杂不变量用 mutex 保护，锁住的是数据不变量，不只是某行代码。
3. 简单状态位和计数器可以用 `std::atomic`。
4. 等待某个条件时用 `condition_variable`，不要用 `sleep` 死循环轮询。
5. 多把锁统一加锁顺序，或使用 `std::scoped_lock` 一次性加多把锁。

## 3.1 原子操作和互斥锁怎么选

`std::atomic` 适合保护单个变量上的简单原子操作，例如计数器、状态位、一次性发布标记、无锁结构中的指针 CAS。它的优势是无锁或低锁开销，但它只保证单次原子操作的不可分割性。

`std::mutex` 适合保护一组数据的不变量，或者保护包含多步操作的临界区。例如“队列非空时取出元素”“同时更新 map 和 size”“三个字段必须一起变成新版本”，这些都更适合用同一把 mutex。

典型选择：

| 场景 | 推荐方式 | 原因 |
| --- | --- | --- |
| 请求计数、错误计数 | `std::atomic<int64_t>` | 单变量自增，语义简单 |
| 停止标记 | `std::atomic<bool>` | 一个线程写，其他线程读 |
| 共享队列 push/pop | `std::mutex + condition_variable` | 队列结构和条件需要一起保护 |
| 多字段配置整体更新 | `std::mutex` 或不可变快照 + 原子指针 | 需要读到同一个版本 |
| 无锁栈/队列 | atomic + CAS + 内存回收方案 | 需要处理 ABA 和安全释放 |

如果给三个变量赋值，分别用三个原子变量只能保证每个变量单独读写是原子的，不能保证读者看到的是同一时刻的组合状态。

```cpp
std::atomic<int> x, y, z;

// 写线程
x.store(1);
y.store(2);
z.store(3);

// 读线程可能看到 x=1, y=0, z=0 这类中间状态
```

如果业务要求三个变量作为一个整体发布，可以用：

1. **mutex**：写和读都在同一把锁下，最直观。
2. **不可变快照**：构造 `Config{x, y, z}`，再用 `std::atomic<std::shared_ptr<const Config>>` 或类似方式发布新版本。
3. **版本号协议**：写前后更新版本号，读者检测版本是否一致，适合读多写少且能接受重试的场景。

面试回答可以说：atomic 适合“单变量简单状态”，mutex 适合“多变量不变量和复合操作”。不要因为 atomic 看起来更轻就用它拆散一个本该整体保护的临界区。

## 3.2 互斥锁和读写 MySQL 会造成上下文切换吗

会不会上下文切换要看是否阻塞。

1. **无竞争 mutex**：通常只走用户态原子操作，不发生系统调用，也不发生线程上下文切换。
2. **竞争严重的 mutex**：线程拿不到锁，可能通过 futex 进入内核睡眠，之后被唤醒，这会发生上下文切换。
3. **读写 MySQL**：本质是 socket I/O。阻塞 socket 等待网络、MySQL 执行、磁盘或锁时，线程会睡眠，发生用户态到内核态切换和线程调度。
4. **连接池等待**：如果连接池没有可用连接，线程在条件变量上等待，也可能阻塞和切换。
5. **非阻塞 I/O/异步客户端**：可以减少业务线程阻塞，但仍然有系统调用、事件通知和调度成本。

所以“使用互斥锁和读写 MySQL 一定造成上下文切换”不准确。准确说法是：无竞争锁通常没有上下文切换；一旦锁竞争、条件等待、阻塞 I/O 或数据库慢查询导致线程睡眠，就会产生上下文切换和排队延迟。

## 3.3 为什么不轻易使用无锁设计

无锁不是没有代价。它适合少数热点路径，但不适合作为默认工程方案。

主要原因：

1. **正确性复杂**：要处理 ABA、内存序、对象生命周期、安全释放内存。
2. **内存回收困难**：无锁链表/队列删除节点后，其他线程可能还在读，需要 Hazard Pointer、Epoch/RCU 等机制。
3. **高竞争下可能退化**：CAS 失败会反复重试，消耗 CPU，尾延迟可能比 mutex 更差。
4. **可维护性差**：代码难审查、难调试、难复现 bug。
5. **业务临界区复杂**：多个字段、多个容器、I/O 操作、异常处理通常更适合 mutex 或消息队列。

工程上优先选择清晰同步模型：线程封闭、消息传递、分片锁、读写锁、RCU 或不可变快照。只有在压测证明某个短小热点锁成为瓶颈，并且能严格控制内存生命周期时，才考虑无锁结构。

## 3.4 `volatile int` 在多线程下安全吗

不安全。C++ 里的 `volatile` 主要表示“这个对象可能被编译器无法感知的外部因素改变”，用于内存映射 I/O、信号处理中的极少数场景，不能替代锁或原子变量。

`volatile int` 在多线程下的问题：

1. **不保证原子性**：`++x` 仍然是读、改、写三步，多个线程并发会丢更新。
2. **不建立 happens-before**：一个线程写入，另一个线程读取，不会因为 `volatile` 自动获得同步关系。
3. **不提供内存序**：不能阻止 CPU 层面的可见性问题，也不能表达 acquire/release。
4. **不保护复合不变量**：多个字段之间的一致性仍然需要 mutex、版本号或不可变快照。

错误示例：

```cpp
volatile int counter = 0;

void add() {
    ++counter; // 多线程下仍然有数据竞争
}
```

正确做法：

```cpp
std::atomic<int> counter{0};

void add() {
    counter.fetch_add(1, std::memory_order_relaxed);
}
```

如果是多个变量组成一个状态，应该用 `std::mutex` 或整体快照，而不是把每个字段都写成 `volatile` 或 atomic。

## 3.5 线上怎么排查死锁

线上死锁的典型表现是：进程还活着，CPU 可能不高，请求延迟升高或完全无响应，线程栈停在 `pthread_mutex_lock`、`futex`、`condition_variable::wait` 等位置。

排查步骤：

1. **确认现象**：看 QPS、P99、线程数、CPU、load、连接数和队列长度，确认不是下游慢或 CPU 打满。
2. **抓线程栈**：用 `pstack <pid>`、`gdb -p <pid>` 后执行 `thread apply all bt`，或生成 core 后离线分析。
3. **找等待环**：观察哪些线程卡在拿锁，哪些线程持锁后又等待其他资源。
4. **查看锁对象地址**：GDB 栈上通常能看到 mutex 地址，可结合代码定位是哪把锁。
5. **检查加锁顺序**：多把锁是否存在 A 线程先拿 L1 再拿 L2，B 线程先拿 L2 再拿 L1。
6. **补充监控**：对关键锁记录等待时间、持锁时间、owner 线程和调用点，方便下次快速定位。

常用 GDB 命令：

```gdb
info threads
thread apply all bt
thread <id>
bt
frame <n>
p variable
```

解决思路：

1. 统一多把锁的获取顺序。
2. 使用 `std::scoped_lock` 一次性加多把锁。
3. 缩小临界区，禁止持锁做 I/O、RPC、日志刷盘等慢操作。
4. 必要时使用 `try_lock` + 回退，或者把共享状态改成消息投递模型。
5. 用 TSan、死锁检测工具或压测场景提前发现。

## 4. 条件变量易错点

条件变量不保存通知。正确写法必须配合谓词：

```cpp
cv.wait(lock, [] {
    return ready;
});
```

原因：

1. 可能先 `notify` 后 `wait`，没有谓词会丢通知。
2. 可能出现虚假唤醒，线程被唤醒后条件仍不满足。
3. 谓词必须在同一把锁保护下检查，保证条件和等待队列状态一致。

## 5. 工程场景

1. **线程池**：主线程投递任务到队列，worker 用 `condition_variable` 阻塞等待，关闭时设置 `stop` 并唤醒全部线程。
2. **异步日志**：业务线程只入队日志，后台线程批量落盘，减少业务线程 I/O 阻塞。
3. **连接处理**：Reactor 线程负责 I/O 事件，业务处理交给工作线程池。
4. **并行计算**：按数据分片拆任务，注意结果合并、缓存行伪共享和负载均衡。

## 6. 常见多线程模式

| 模式 | 核心思路 | 适用场景 |
| --- | --- | --- |
| 生产者消费者 | 生产者写入有界/无界队列，消费者异步处理 | 日志、任务队列、消息处理 |
| 线程池 | 固定或动态 worker 消费任务队列 | RPC 业务处理、后台任务 |
| Reactor + worker | I/O 线程负责事件分发，worker 处理业务 | WebServer、网关、长连接服务 |
| Pipeline | 多个阶段串联，每个阶段可以独立并行 | 编解码、图像处理、ETL |
| Fork-Join | 大任务拆成子任务并行执行，再合并结果 | 并行排序、批量计算 |
| Actor/消息传递 | 每个 actor 串行处理自己的消息，避免共享状态 | 状态机、游戏房间、IM 会话 |

选择时要看瓶颈在哪里：

1. I/O 密集型任务通常配合事件驱动和线程池。
2. CPU 密集型任务线程数一般接近 CPU 核数，过多线程会增加上下文切换。
3. 共享状态多时，优先考虑消息传递或按 key 分片，减少锁竞争。
4. 长耗时任务要和短任务隔离，避免线程池被慢任务占满。

## 7. 生产者消费者和背压

生产者消费者模式用队列把“生产速度”和“消费速度”解耦。项目中常见结构是：

```text
producer threads -> bounded queue -> consumer worker threads
```

如果生产者太快、消费者太慢，不能只让队列无限增长，否则会把内存打满。常见处理方式：

1. **有界队列**：队列满时生产者阻塞等待，最直接形成背压。
2. **超时入队**：等待一段时间仍然满就失败，让上游重试、降级或返回忙。
3. **丢弃策略**：日志、指标、监控这类可降级数据可以丢弃低优先级或旧数据。
4. **批量消费**：消费者一次取多条，减少锁竞争和系统调用开销。
5. **扩容消费者**：增加 worker，但要确认瓶颈不是数据库、磁盘或下游 RPC。
6. **限流削峰**：在入口限制生产速率，或用令牌桶控制突发流量。
7. **分级队列**：高优先级任务独立队列，避免被低优先级任务淹没。
8. **监控告警**：监控队列长度、入队失败数、消费延迟、任务处理耗时。

一个有界队列的关键谓词通常是：

```text
not_full:  queue.size() < capacity || stopped
not_empty: !queue.empty() || stopped
```

生产者等待 `not_full`，消费者等待 `not_empty`。关闭时设置 `stopped` 并 `notify_all()`，避免线程永久阻塞。

## 8. 面试回答模板

C++ 多线程我会从线程生命周期和共享数据同步两层回答。线程用 `std::thread` 创建后必须 `join` 或 `detach`，否则析构会 `terminate`，现代 C++ 可以用 `std::jthread` 简化退出。共享数据要避免 data race，复杂状态用 `mutex + lock_guard/unique_lock`，等待条件用 `condition_variable` 并配合谓词，简单计数器和状态位可以用 `atomic`。真实项目里更常见的是线程池、异步日志、生产者消费者和 Reactor + worker 线程模型，重点是减少共享、控制锁粒度、处理关闭流程和异常路径。
