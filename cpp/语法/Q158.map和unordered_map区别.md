# Q158. map 和 unordered_map 的区别

`std::map` 和 `std::unordered_map` 都是关联容器，区别在于底层数据结构、顺序语义、复杂度稳定性和适用场景。

## 1. 底层结构

| 容器 | 底层常见实现 | key 顺序 |
| --- | --- | --- |
| `std::map` | 红黑树等平衡二叉搜索树 | 按 key 有序 |
| `std::unordered_map` | 哈希表，通常是 bucket + 链表或节点 | 无序 |

`map` 依赖比较函数，默认是 `std::less<Key>`；`unordered_map` 依赖哈希函数和相等比较，默认是 `std::hash<Key>` 和 `std::equal_to<Key>`。

## 2. 复杂度对比

| 操作 | `map` | `unordered_map` |
| --- | --- | --- |
| 查找 | `O(log n)` | 平均 `O(1)`，最坏 `O(n)` |
| 插入 | `O(log n)` | 平均 `O(1)`，rehash 时可能 `O(n)` |
| 删除 | `O(log n)` | 平均 `O(1)` |
| 有序遍历 | 支持 | 不支持 |
| 范围查询 | 支持，例如 `lower_bound` | 不适合 |

`unordered_map` 的平均 `O(1)` 依赖哈希分布好、负载因子合理。哈希冲突严重或被恶意构造输入时，可能退化。

## 3. 内存和迭代器

`map` 每个节点通常保存 key/value、颜色、父子指针，单节点开销较大，但没有 bucket 数组。

`unordered_map` 除节点外还需要 bucket 数组；元素很多时通常查找更快，但内存占用不一定更低。

迭代器失效规则：

1. `map` 插入不影响已有迭代器，删除只影响被删除元素。
2. `unordered_map` 插入如果触发 rehash，会使所有迭代器失效；删除只影响被删除元素。
3. `unordered_map` 中元素节点地址通常在 rehash 后仍可能保持，但不要依赖非标准细节，长期保存迭代器更危险。

## 4. 怎么选择

优先用 `unordered_map` 的场景：

1. 只需要按 key 做等值查找。
2. 不需要按 key 有序遍历。
3. 对平均查找性能敏感。
4. 可以提供可靠哈希函数。

优先用 `map` 的场景：

1. 需要按 key 有序遍历。
2. 需要范围查询，例如 `lower_bound/upper_bound`。
3. 需要稳定 `O(log n)`，不希望受哈希冲突影响。
4. key 不容易哈希，但容易比较。
5. 数据量不大，代码语义上更依赖顺序。

## 5. unordered_map 使用注意

大量插入前可以提前扩容：

```cpp
#include <string>
#include <unordered_map>

std::unordered_map<std::string, int> cnt;
cnt.reserve(100000);
cnt.max_load_factor(0.75);
```

自定义 key 时，哈希和相等判断必须语义一致：

```cpp
struct Point {
    int x;
    int y;
};

struct PointHash {
    size_t operator()(const Point& p) const {
        return std::hash<int>{}(p.x) ^ (std::hash<int>{}(p.y) << 1);
    }
};

struct PointEq {
    bool operator()(const Point& a, const Point& b) const {
        return a.x == b.x && a.y == b.y;
    }
};
```

### unordered_map 如何解决哈希冲突

标准没有强制规定 `std::unordered_map` 的具体冲突解决实现，只规定平均复杂度、接口语义和迭代器行为。主流标准库实现通常采用 bucket 数组加节点链表或等价的链地址法结构：

1. 先用 `std::hash<Key>` 计算哈希值。
2. 根据 bucket 数量定位桶。
3. 同一个桶里如果有多个 key，就通过链表或节点序列保存。
4. 查找时先定位桶，再在桶内用 `key_equal` 比较真实 key。

链地址法的好处是删除节点相对简单，rehash 时可以重新把节点挂到新桶上；缺点是冲突严重时桶内链过长，查询会退化。工程上要通过可靠哈希函数、合理 `max_load_factor`、提前 `reserve` 和限制不可信输入来降低冲突风险。

需要注意：不要把所有哈希表都理解成链地址法。开放寻址、Robin Hood Hashing、SwissTable/F14 这类哈希表更偏连续数组和探测序列，缓存局部性更好，但它们不是 `std::unordered_map` 标准要求的唯一实现。

## 6. 易错点

1. `unordered_map` 不保证遍历顺序，不能把顺序写进业务逻辑。
2. 平均 `O(1)` 不等于永远 `O(1)`。
3. rehash 会导致迭代器失效。
4. 哈希函数和 `operator==` 语义不一致会导致查找错误。
5. `map` 的 `operator[]` 查不到 key 时会插入默认值，`unordered_map` 也是如此。

## 7. unordered_map 怎么排序

`unordered_map` 本身没有顺序语义，不能“原地排序”。如果需要按 key 或 value 输出有序结果，常见做法是拷贝到 `vector` 后排序：

```cpp
#include <algorithm>
#include <string>
#include <unordered_map>
#include <vector>

std::unordered_map<std::string, int> mp{{"b", 2}, {"a", 3}, {"c", 1}};

std::vector<std::pair<std::string, int>> items(mp.begin(), mp.end());

std::sort(items.begin(), items.end(), [](const auto& lhs, const auto& rhs) {
    if (lhs.second != rhs.second) {
        return lhs.second > rhs.second; // 先按 value 降序
    }
    return lhs.first < rhs.first;       // value 相同时按 key 升序
});
```

如果业务一直需要有序遍历或范围查询，直接用 `std::map` 更合适；如果只是偶尔做一次排序展示，`unordered_map + vector sort` 更常见。

## 8. 面试回答模板

`map` 通常基于红黑树，key 有序，查找、插入、删除都是稳定 `O(log n)`，支持范围查询和有序遍历。`unordered_map` 基于哈希表，key 无序，平均查找插入是 `O(1)`，但受哈希质量和负载因子影响，最坏可能退化；主流实现通常用 bucket 加链地址法处理冲突，rehash 还会导致迭代器失效。只做等值查询一般选 `unordered_map`，需要有序遍历、范围查询或稳定复杂度时选 `map`。大量插入 `unordered_map` 前最好 `reserve`，自定义 key 时要保证 hash 和相等比较一致。
