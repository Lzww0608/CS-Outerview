# Q157. vector容量管理与最大元素数

`std::vector` 是 C++ 中最常用的顺序容器之一，底层是连续动态数组。它适合随机访问、顺序遍历、排序、批量处理等场景。

## 1. vector 底层是什么

一个典型 `vector<T>` 可以抽象成三个指针：

```cpp
template <class T, class Alloc = std::allocator<T>>
class vector {
    T* begin_; // 已构造元素起点
    T* end_;   // 已构造元素尾后
    T* cap_;   // 已分配内存尾后
    Alloc alloc_;
};
```

对应关系：

```text
size     = end_ - begin_
capacity = cap_ - begin_
```

`vector` 的内存是连续的，所以：

1. 下标访问是 `O(1)`。
2. 顺序遍历缓存友好。
3. 可以和 C API 通过 `data()` 交互。
4. 扩容时必须重新申请连续空间并搬移元素。

### 1.1 如果让你设计一个 vector

面试里设计 `vector`，重点不是把标准库所有接口背完，而是说清楚**连续存储、容量管理、对象生命周期、迭代器和异常安全**。

一个最小可用接口通常包括：

1. 构造/析构：默认构造、指定大小构造、拷贝构造、移动构造、析构。
2. 赋值和资源管理：拷贝赋值、移动赋值、`swap`。
3. 容量接口：`size()`、`capacity()`、`empty()`、`reserve()`、`resize()`。
4. 访问接口：`operator[]`、`at()`、`front()`、`back()`、`data()`。
5. 修改接口：`push_back()`、`emplace_back()`、`pop_back()`、`insert()`、`erase()`、`clear()`。
6. 迭代器接口：`begin()`、`end()`、`cbegin()`、`cend()`，随机访问迭代器语义。

核心成员变量可以是：

```cpp
template <class T, class Alloc = std::allocator<T>>
class Vector {
public:
    using iterator = T*;
    using const_iterator = const T*;

private:
    T* begin_ = nullptr; // 已分配空间起点
    T* end_ = nullptr;   // 已构造元素尾后
    T* cap_ = nullptr;   // 已分配空间尾后
    Alloc alloc_;
};
```

为什么不用 `new T[n]` 直接申请？因为 `vector` 需要区分“已经分配的原始内存”和“已经构造的对象”。`reserve(100)` 只应该申请能放 100 个 `T` 的原始内存，不能默认构造 100 个元素；`resize(100)` 才改变元素个数并构造新元素。因此实现上应使用 allocator：

```cpp
using traits = std::allocator_traits<Alloc>;

T* p = traits::allocate(alloc_, n);              // 申请原始内存
traits::construct(alloc_, p + i, value);         // 在指定位置构造对象
traits::destroy(alloc_, p + i);                  // 析构对象
traits::deallocate(alloc_, p, n);                // 释放原始内存
```

如果手写极简版本，也可以用 `::operator new(sizeof(T) * n)` 申请原始内存，再用 placement new 构造对象；不要用 `malloc` 后直接当作 `T[]` 使用，因为它不会调用构造函数，也不表达对象生命周期。标准库容器通过 allocator 把这件事封装起来。

扩容时要保证异常安全：

1. 先申请新内存。
2. 在新内存中移动或拷贝构造旧元素。
3. 新元素全部构造成功后，再析构旧元素并释放旧内存。
4. 如果中途抛异常，要销毁已构造的新元素并释放新内存，旧 `vector` 保持原状。

迭代器设计上，`vector` 的迭代器可以直接是指针，因为连续内存天然支持 `*it`、`++it`、`it + n`、`it2 - it1` 和比较操作，满足随机访问迭代器要求。如果为了调试越界和版本校验，也可以封装成类，内部保存指针、所属容器和版本号，但发布构建中通常希望接近裸指针开销。

## 2. `sizeof(vector)` 多大

`sizeof(std::vector<T>)` 统计的是 `vector` 对象本身的控制块大小，不包含动态分配出来的元素数组。

典型 64 位 libstdc++/libc++ 实现里，`vector` 内部主要是 `begin/end/cap` 三个指针，所以常见结果是 24 字节；32 位环境常见是 12 字节。实际大小不由标准规定，可能受这些因素影响：

1. 指针宽度：32 位和 64 位不同。
2. allocator 是否有状态：无状态 allocator 可以被空基类优化，带状态 allocator 可能增加对象大小。
3. 调试模式：MSVC 或 STL debug iterator 可能额外保存迭代器检查信息。
4. ABI 和标准库实现差异。

因此 `vector<int> v(4, 100)` 里，`sizeof(v)` 不会因为有 4 个元素而变大；元素在 `v.data()` 指向的动态缓冲区中。`sizeof(std::vector<int>)` 和 `sizeof(std::vector<double>)` 在常见实现里通常相同，但这不是语言标准保证的结论。

## 3. push_back 时发生什么

当执行 `push_back` 或 `emplace_back`：

1. 如果 `size() < capacity()`，直接在 `end_` 位置构造新元素，然后 `end_++`。
2. 如果 `size() == capacity()`，分配更大的连续内存。
3. 把旧元素移动或拷贝到新内存。
4. 在新内存里构造新元素。
5. 析构旧元素并释放旧内存。
6. 更新 `begin_ / end_ / cap_`。

增长倍率由标准库实现决定，常见是 1.5 倍或 2 倍。标准只保证尾插摊还 `O(1)`，不规定具体扩容倍率。

### 3.1 扩容申请内存时 OS 层面发生什么

`vector` 自身不会直接操作页表。它通过 allocator 调用 `::operator new`，再进入 C/C++ 运行时分配器，例如 glibc `malloc`、tcmalloc、jemalloc 或 MSVC CRT。分配器再决定从已有堆块里切一块，还是向操作系统申请更多虚拟内存。

大致链路：

```text
vector 扩容
  -> allocator::allocate(n)
  -> ::operator new(bytes)
  -> malloc / 内存分配器
  -> brk/sbrk 或 mmap/VirtualAlloc 申请虚拟地址空间
  -> 首次触碰页面时触发缺页
  -> 内核分配物理页并建立页表映射
```

需要注意几件事：

1. **申请成功不一定立刻分配物理页**：Linux 开启 overcommit 时，`malloc` 返回的可能主要是虚拟地址承诺，物理页常在第一次写入时通过缺页异常分配。
2. **小对象通常来自分配器缓存**：小规模扩容可能只是从 arena、tcache 或线程缓存里切内存，不一定每次都陷入内核。
3. **大块连续虚拟内存更难**：`vector` 要求连续地址空间，元素总字节数很大时，即使总空闲内存够，也可能因为地址空间、容器限制或提交限制失败。
4. **扩容峰值更高**：搬迁期间新旧两块内存可能同时存在，峰值内存约为旧容量加新容量，再加分配器元数据。
5. **搬迁影响缓存和 TLB**：大量移动元素会产生内存带宽压力、cache miss、TLB miss，复杂对象还会调用移动或拷贝构造。
6. **释放不等于马上还给 OS**：旧内存释放后可能留在分配器缓存中，RSS 不一定立刻下降。

所以回答“`vector` 扩容时操作系统做了什么”时，可以分层说：C++ 层申请更大连续原始内存并移动元素；运行时分配器负责复用或向 OS 申请虚拟内存；OS 在需要时建立虚拟页到物理页的映射，并可能通过缺页异常实际分配物理页。

## 4. reserve 和 resize 区别

| 操作 | 改变 size | 改变 capacity | 是否构造元素 |
| --- | --- | --- | --- |
| `reserve(n)` | 不改变 | 至少变为 `n` | 不构造新元素 |
| `resize(n)` | 改变 | 必要时扩容 | 变大时构造新元素，变小时析构尾部元素 |
| `shrink_to_fit()` | 不改变 | 请求缩小 | 非强制，标准不保证一定释放 |

工程上如果能预估元素数量，应先 `reserve`，减少扩容次数和迭代器失效。

### 4.1 `push_back` 和 `emplace_back` 的区别

`push_back` 和 `emplace_back` 都是在尾部新增元素，区别在于参数语义和构造方式。

| 接口 | 参数 | 构造方式 |
| --- | --- | --- |
| `push_back(const T&)` | 已经存在的左值对象 | 拷贝构造到 `end_` |
| `push_back(T&&)` | 已经存在的右值对象 | 移动构造到 `end_` |
| `emplace_back(args...)` | 构造 `T` 所需参数 | 在 `end_` 位置直接完美转发构造 |

示例：

```cpp
struct User {
    User(std::string name, int age) : name(std::move(name)), age(age) {}
    std::string name;
    int age;
};

std::vector<User> users;

User u{"alice", 18};
users.push_back(u);                    // 拷贝 u
users.push_back(User{"bob", 20});       // 构造临时 User，再移动进 vector
users.emplace_back("carol", 22);        // 直接在尾部构造 User
```

`emplace_back` 的“原地构造”指的是：容量足够时，`vector` 直接在 `end_` 指向的未构造内存上调用 allocator 的 `construct`，等价于 placement new，然后移动 `end_`。如果容量不够，仍然要先扩容，把旧元素搬到新内存，再在新内存尾部构造新元素。

易错点：

1. `emplace_back` 不一定总比 `push_back` 快；如果参数本来就是一个 `T` 对象，二者差异很小。
2. `emplace_back` 可能调用意料之外的构造函数，尤其是有 `initializer_list`、多个重载或窄化转换时。
3. 扩容时旧元素仍会移动或拷贝，所以大对象更要关注移动构造是否 `noexcept`。

### 4.2 空 `vector` 执行 `resize(1000)` 会构造多少次

会。`resize(1000)` 的语义是把 `size()` 变成 1000，因此要让 `[0, 1000)` 这 1000 个位置都成为已经构造好的合法对象。

```cpp
std::vector<std::string> v;
v.resize(1000); // 默认构造 1000 个 string
```

对于类类型，会调用默认构造函数 1000 次；对于 `int` 这类标量类型，`resize(1000)` 会值初始化，通常得到 1000 个 0。这个成本和 `reserve(1000)` 完全不同：

```cpp
std::vector<std::string> v;
v.reserve(1000);       // 只申请原始容量，不构造 string

for (auto& name : input) {
    v.emplace_back(name); // 真正有元素时再构造
}
```

如何避免不必要开销：

1. 只是预留容量，用 `reserve`，不要用 `resize`。
2. 需要逐步填充对象，用 `reserve + emplace_back/push_back`。
3. 需要按下标写入且元素必须存在，才用 `resize`。
4. 如果只是要一块未初始化字节缓冲，用 `std::vector<std::byte>`、`std::unique_ptr<std::byte[]>` 或专门 buffer，而不是 `vector<T>::resize` 一个复杂对象数组。
5. 对非平凡类型，标准 `vector` 不能把 `size` 扩大但不构造对象；未构造对象不能通过下标当作 `T` 使用。

## 5. 最多能存多少元素

最多元素数不是一个固定值，受这些因素影响：

1. `vector<T>::max_size()`：由 allocator、`size_type` 和实现限制决定。
2. 进程虚拟地址空间：32 位进程和 64 位进程差距很大。
3. 可用物理内存和 overcommit 策略。
4. 单个连续虚拟内存块是否能申请成功。
5. `sizeof(T)`、对齐、对象构造成本。
6. 系统限制，例如 cgroup、容器内存限制、ulimit。

估算方式：

```text
可存元素数 ≈ 可用连续内存字节数 / sizeof(T)
```

例如 `vector<int>` 存 1 亿个元素，元素本身约 400MB；如果扩容过程中同时存在新旧两块内存，峰值可能接近 600MB 到 800MB 甚至更多，还不包括 allocator 元数据和其他内存。

## 6. 迭代器和指针失效

`vector` 扩容后，所有旧迭代器、指针、引用都失效，因为旧内存已经释放。

未扩容时：

1. 尾插会让旧 `end()` 失效。
2. 中间插入会让插入点及其后的迭代器、指针、引用失效。
3. `erase` 会让删除点及其后的迭代器、指针、引用失效。

如果需要长期保存位置，优先保存下标；如果要长期保存对象地址，可以考虑 `deque`、节点容器或稳定对象池。

## 7. 为什么移动构造最好是 noexcept

扩容搬迁元素时，标准库希望提供强异常安全保证。若 `T` 的移动构造可能抛异常，而拷贝构造可用，很多实现会选择拷贝而不是移动。因为移动一半后抛异常，旧对象可能已经处于被移动状态，难以恢复。

因此资源型对象的移动构造和移动赋值通常应该标记 `noexcept`：

```cpp
class Buffer {
public:
    Buffer(Buffer&& other) noexcept;
    Buffer& operator=(Buffer&& other) noexcept;
};
```

## 8. `vector<int> v(4, 100)` 在哪里分配

如果写在普通函数局部变量里：

```cpp
std::vector<int> v(4, 100);
```

可以分成两部分理解：

1. `vector` 对象本身是一个局部自动变量，通常在当前线程栈上，里面保存类似 `begin/end/cap` 的指针和 allocator 状态。
2. 4 个 `int` 元素所在的连续缓冲区由 allocator 动态申请，通常在堆/自由存储区。

也就是说，`v` 这个“小控制块”在栈上，`v.data()` 指向的元素数组通常在堆上。

如果写成：

```cpp
auto p = new std::vector<int>(4, 100);
```

则 `vector` 对象本身也在堆/自由存储区，内部 4 个 `int` 元素的缓冲区仍然是另一块由 allocator 管理的动态内存。释放时：

```cpp
delete p;
```

会先析构 `vector`，由 `vector` 释放内部元素缓冲区，再释放 `vector` 对象本身。

注意：标准不强制实现必须调用名为“堆”的具体机制，但语义上元素存储来自动态存储分配；`vector` 不像某些 `string` 实现那样有小对象内联优化，元素通常不直接塞进 `vector` 对象本体。

## 9. 易错点

1. `capacity()` 不是当前元素个数，`size()` 才是。
2. `reserve` 不会让 `operator[]` 访问新位置变合法。
3. `vector` 需要连续内存，不是总空闲内存够就一定能申请成功。
4. `vector<bool>` 是特殊压缩版本，不是普通 `vector<T>`。
5. 扩容导致地址变化，不要把 `data()` 返回的指针长期缓存。
6. 删除大量元素后容量不一定下降，`shrink_to_fit` 也只是请求。

## 10. 面试回答模板

`vector` 底层是连续动态数组，典型实现维护 `begin/end/cap` 三个指针，通过 allocator 申请原始内存并构造对象。`sizeof(vector)` 只包含控制块，不包含元素数组，64 位常见实现通常是 24 字节但标准不保证。尾插容量足够时直接构造，容量不足时重新申请更大的连续空间，把旧元素移动或拷贝过去，再释放旧空间，所以 `push_back` 摊还 `O(1)`，但扩容会导致所有迭代器、指针、引用失效。扩容申请内存时，标准库通常经 allocator、`operator new` 和运行时分配器走到 `mmap/brk` 或平台对应接口；物理页可能在首次触碰时由缺页异常分配。最多能存多少元素取决于 `max_size()`、进程虚拟地址空间、可用连续内存、`sizeof(T)` 和容器内存限制，不是固定值。工程上大量插入前要 `reserve`，大对象要关注移动构造是否 `noexcept`。

## 12. vector 两倍扩容的数学推导

面试中常考一个经典问题：**如果 vector 最终有 L 个元素，按两倍扩容机制，算整个过程中一共扩容了多少次，复制了多少个元素？**

### 12.1 问题分析

假设 vector 初始容量为 1，每次扩容为当前容量的 2 倍：

```
容量序列：1, 2, 4, 8, 16, 32, ..., 2^k
```

当最终元素数量为 L 时，需要找到最小的 k 使得 `2^k >= L`。

### 12.2 扩容次数

扩容发生的时机是容量从 `2^(k-1)` 增长到 `2^k`，直到容量刚好能容纳 L 个元素。

```cpp
// 扩容次数公式
扩容次数 = ceil(log2(L)) - 1  // 去掉初始容量那次

// 或者用数学表达
// 如果 L 是 2 的幂，如 L = 8
// 容量变化：1 -> 2 -> 4 -> 8，共扩容 2 次
// 如果 L = 9
// 容量变化：1 -> 2 -> 4 -> 8 -> 16，共扩容 4 次
```

更精确的表达：

```cpp
// 扩容次数 = floor(log2(L-1)) + 1
// 其中 floor(log2(L-1)) 是 L-1 的二进制位数 - 1

// 或者简化为
int扩容次数(int L) {
    int count = 0;
    int capacity = 1;
    while (capacity < L) {
        capacity *= 2;
        count++;
    }
    return count;
}
```

### 12.3 元素复制次数

这是更重要的指标。每次扩容时，需要把所有已有元素复制到新内存：

```
第 1 次扩容：复制 1 个元素（从容量 1 到 2）
第 2 次扩容：复制 2 个元素（从容量 2 到 4）
第 3 次扩容：复制 4 个元素（从容量 4 到 8）
...
第 k 次扩容：复制 2^(k-1) 个元素
```

总复制次数：

```cpp
// 等比数列求和
// 总复制次数 = 1 + 2 + 4 + ... + 2^(k-1) = 2^k - 1
// 其中 k = ceil(log2(L))

// 最终公式
总复制次数 = 2 * L - 1 - (2^ceil(log2(L)) - L)
//          ≈ 2L - 1 - 冗余空间
```

### 12.4 具体计算示例

```cpp
// 示例：L = 10

// 容量变化：
// 初始: 1
// 第1次扩容到 2，复制 1 个元素
// 第2次扩容到 4，复制 2 个元素
// 第3次扩容到 8，复制 4 个元素
// 第4次扩容到 16，复制 8 个元素（实际只需要 2 个）

// 扩容次数：4 次
// 总复制次数：1 + 2 + 4 + 8 = 15 次

// 如果 L = 8
// 容量变化：1 -> 2 -> 4 -> 8
// 扩容次数：3 次
// 总复制次数：1 + 2 + 4 = 7 次 = 2*8 - 1 = 15？不对

// 重新分析：
// 当 L = 8 时，实际不需要最后一次扩容
// 容量达到 8 时刚好够用
// 扩容次数：2（1->2, 2->4）
// 复制次数：1 + 2 = 3

// 精确公式：
// 扩容次数 = floor(log2(L-1))
// 总复制次数 = L - 1 - floor(log2(L))
```

### 12.5 摊还分析

虽然最坏情况下单次扩容可能复制 `O(n)` 个元素，但**摊还分析**显示 `push_back` 的均摊成本仍然是 `O(1)`：

```cpp
// n 次 push_back 的总成本 = 1 + 2 + 4 + ... + 2^k ≈ 2n
// 摊还到每次 push_back = O(1)

// 这就是"摊还 O(1)"的含义
// 不代表每次都是 O(1)，而是 n 次操作的总成本是 O(n)
```

### 12.6 不同扩容倍率的对比

| 扩容倍率 | 扩容次数 | 总复制次数 | 空间浪费 |
| --- | --- | --- | --- |
| 1.5 倍 | ~log₁.₅ n | 较高 | 较少 |
| 2 倍 | ~log₂ n | 中等 | 最多可达 50% |
| 1.1 倍 | ~log₁.₁ n | 最高 | 最少 |

```cpp
// 扩容倍率的影响：
// - 2 倍扩容：空间换时间，扩容次数少但浪费多
// - 1.5 倍扩容：平衡策略，GCC libstdc++ 采用
// - 1.1 倍扩容：空间利用率高，但扩容频繁
```

## 13. vector 和 list 怎么选

`vector` 和 `list` 的核心区别是内存布局。`vector` 是连续数组，`list` 是双向链表节点。

| 对比项 | `vector` | `list` |
| --- | --- | --- |
| 内存布局 | 连续内存 | 节点分散，每个节点有前后指针 |
| 随机访问 | `O(1)` | 不支持按下标快速访问 |
| 顺序遍历 | cache 友好，通常很快 | 容易 cache miss |
| 中间插入删除 | 需要移动后续元素，`O(n)` | 已有迭代器定位时插删 `O(1)` |
| 查找某个值 | `O(n)`，但常数小 | `O(n)`，常数大 |
| 迭代器失效 | 扩容会全部失效 | 插入不影响其他迭代器，删除只影响被删节点 |
| 额外内存 | 只需要容量冗余 | 每个节点额外保存指针，分配次数多 |

面试里不要简单说“频繁插删用 list”。如果插删前还要线性查找位置，`list` 的整体复杂度仍然是 `O(n)`，并且因为节点分散，真实性能经常不如 `vector`。只有在已经持有稳定迭代器、需要频繁在中间 splice/erase、元素很大且移动成本高、并且随机访问不重要时，`list` 才更合适。

真实场景中，游戏对象、网络连接、批量消息、排序数据通常优先考虑 `vector` 或 `deque`，因为遍历和 cache 局部性更重要；LRU 链表、需要稳定节点地址的队列、频繁移动节点位置的结构可以考虑 `list`，但常会配合 `unordered_map` 保存节点迭代器。
