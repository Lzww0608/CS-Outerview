# Q149. C++ 程序内存分布

## 1. 典型内存区域

C++ 程序运行时常见内存区域可以按生命周期和用途划分：

| 区域 | 内容 | 生命周期 |
| --- | --- | --- |
| 代码段 `.text` | 编译后的机器指令 | 程序运行期间 |
| 只读数据段 `.rodata` | 字符串字面量、虚函数表、只读常量 | 程序运行期间 |
| 已初始化数据段 `.data` | 已初始化的全局变量、静态变量 | 程序运行期间 |
| 未初始化数据段 `.bss` | 未初始化或初始化为 0 的全局/静态变量 | 程序运行期间 |
| 堆 heap | `new/malloc` 动态分配对象 | 手动释放或进程结束 |
| 栈 stack | 函数栈帧、局部变量、返回地址 | 函数调用期间 |
| mmap 区 | 动态库、文件映射、大块匿名映射 | 映射存在期间 |
| TLS 区 | `thread_local` 变量 | 线程生命周期 |

不同平台、编译器和链接方式会影响具体布局，但大方向一致。

## 1.1 从低地址到高地址怎么看

典型 Linux 用户态虚拟地址空间可以按低地址到高地址理解为：

```text
低地址
  .text / .rodata / .data / .bss
  heap                 向高地址增长
  mmap 区              动态库、文件映射、匿名大块内存
  stack                向低地址增长
高地址
```

这只是概念模型。实际地址会受架构位数、PIE、ASLR、栈随机化、线程栈和 mmap 分配策略影响，不能死记具体地址。

## 2. 示例

```cpp
const int g_const = 1;      // 可能在 .rodata
int g_init = 2;             // .data
int g_zero;                 // .bss
static int s_init = 3;      // .data

int main() {
    int local = 4;          // stack
    static int local_s = 5; // .data
    auto* p = new int(6);   // p 在 stack，*p 在 heap
    const char* str = "hi"; // str 在 stack，"hi" 在 .rodata
    delete p;
}
```

## 2.0 变量到底放在哪里

判断变量放在哪里，不能只看类型，要看它的存储期、定义位置和是否动态分配。

| 写法 | 变量本身常见位置 | 指向或管理的对象位置 | 说明 |
| --- | --- | --- | --- |
| `int x;` 函数内局部变量 | 栈 | 无 | 自动存储期，离开作用域销毁 |
| `static int x;` 函数内 | `.bss/.data` | 无 | 静态存储期，不在栈上 |
| `int g;` 全局变量 | `.bss` | 无 | 静态存储期，零初始化 |
| `int g = 1;` 全局变量 | `.data` | 无 | 已初始化静态对象 |
| `const char* s = "hi";` 函数内 | `s` 在栈上 | 字符串字面量通常在 `.rodata` | 指针和指向内容位置不同 |
| `int* p = new int(1);` 函数内 | `p` 在栈上 | `*p` 在堆上 | 指针变量不是堆对象本身 |
| `auto p = std::make_unique<int>(1);` | `p` 在栈上 | 被管理对象在堆上 | RAII 负责离开作用域释放 |
| `thread_local int x;` | TLS 区 | 无 | 每个线程一份 |
| `mmap` 返回地址 | 指针变量看定义位置 | mmap 区 | 可映射文件、共享内存或匿名页 |

易错点：

1. “局部变量在栈上”只适用于普通自动变量；局部 `static` 不在栈上。
2. 指针变量在哪里和它指向的对象在哪里是两个问题。
3. 编译器优化后，小的局部变量可能只在寄存器中，不一定真的落到栈内存。
4. `new` 的对象通常来自堆分配器，但自定义 `operator new` 或 placement new 可以改变实际来源。

## 2.1 常量存储区、全局变量和静态变量

面试里说“常量存储区”通常指只读数据段 `.rodata`，但要注意并不是所有 `const` 变量都一定放在 `.rodata`：

1. 字符串字面量通常在 `.rodata`。
2. 全局 `const` 且不需要动态初始化的对象，可能放在 `.rodata`。
3. 局部 `const int x = 1` 可能直接被编译器当成立即数优化，不一定有实际存储。
4. 需要动态初始化或有非平凡构造的 `const` 对象，可能放在 `.data`，初始化后通过页面权限或类型系统保证只读语义。

全局变量和静态变量都具有静态存储期，生命周期从程序启动到程序结束：

| 写法 | 作用域/链接属性 | 常见存储区域 |
| --- | --- | --- |
| `int g = 1;` | 全局作用域，外部链接 | `.data` |
| `int g;` | 全局作用域，外部链接 | `.bss` |
| `static int g = 1;` | 文件作用域，内部链接 | `.data` |
| `static int x;` 函数内 | 块作用域，静态存储期 | `.bss` |
| `const char* p = "hi";` | 指针变量看定义位置，字面量在只读段 | p 可能在栈/数据段，`"hi"` 在 `.rodata` |

要区分三个概念：

1. **作用域**：名字在哪里可见。
2. **链接属性**：能否跨翻译单元链接到同一个实体。
3. **存储期**：对象活多久。

`static` 可以改变链接属性或存储期，但不等于“都在栈上/堆上”。

## 2.2 `.data` 和 `.bss` 为什么分开

`.data` 和 `.bss` 都存放静态存储期对象，区别在于是否需要在可执行文件里保存初始值：

1. `.data` 存放已经显式初始化且初始值非 0 的全局变量、静态变量。链接器需要把这些初始字节写进可执行文件，加载器运行时再把它们映射或拷贝到进程地址空间。
2. `.bss` 存放未初始化或初始化为 0 的全局变量、静态变量。ELF 中 `.bss` 通常是 `NOBITS` 类型，只记录大小、地址和权限，不在文件里存一大段 0。
3. 程序启动时，加载器会为 `.bss` 建立零填充映射，保证 C/C++ 对静态存储期对象的零初始化语义。

示例：

```cpp
int g1 = 10;                 // .data
int g2;                      // .bss
int g3 = 0;                  // 通常在 .bss
static char buf[1 << 20];    // .bss，文件里不需要保存 1MB 的 0
```

分开存储的核心价值：

1. **减小可执行文件体积**：大型零初始化数组如果放进 `.data`，文件会膨胀；放进 `.bss` 只需要记录长度。
2. **加载更高效**：`.data` 需要从文件读取初始内容，`.bss` 可以由内核按需提供零页，真正写入时再分配物理页。
3. **权限和映射更清晰**：加载器可以按段权限把代码、只读数据、可写数据分开映射，便于保护和共享。
4. **符合语言语义**：全局变量、静态变量如果没有显式初始化，标准要求在动态初始化前先进行零初始化。

易错点：

1. 局部自动变量 `int x;` 不在 `.bss`，它在栈上，值未初始化。
2. `static int x;` 即使写在函数内部，也有静态存储期，通常在 `.bss`。
3. `.bss` “不占文件空间”不等于“不占内存”。程序运行后，只要页面被访问或写入，仍然会消耗虚拟地址空间和可能的物理内存。
4. 具体归属会受编译器、链接选项、优化级别和目标文件格式影响，面试回答说“通常”更严谨。

## 3. 栈和堆的区别

1. 栈由编译器和运行时按函数调用自动管理，分配释放很快。
2. 堆由分配器管理，适合生命周期跨函数或大小运行期决定的对象。
3. 栈空间通常较小，大数组或深递归容易栈溢出。
4. 堆分配有元数据、锁或线程缓存成本，也可能产生碎片。

## 3.1 为什么栈通常比堆快

栈快不是因为“栈一定在高速内存、堆一定在低速内存”，它们最终都映射到进程虚拟地址空间和物理内存。栈通常更快，主要是管理方式更简单：

1. **分配释放只是移动栈指针**：进入函数时调整 `sp/rsp`，退出函数时恢复，接近几条指令。
2. **生命周期严格后进先出**：不需要查找空闲块，也不需要合并碎片。
3. **缓存局部性好**：栈帧连续增长，函数局部变量通常集中访问，CPU cache 命中率高。
4. **无通用分配器元数据成本**：堆分配要维护 chunk/header、空闲链表、大小类等结构。
5. **多线程竞争更少**：每个线程有自己的栈；堆分配器虽然有线程缓存，但跨线程释放、大对象分配仍可能有锁或同步成本。

堆慢的主要来源：

1. 分配器要寻找合适大小的空闲块。
2. 释放时可能要合并相邻空闲块或放回对应大小类。
3. 频繁申请释放会造成内存碎片和缓存不友好。
4. 大块内存可能走 `mmap/brk` 或触发缺页，成本更高。

易错点：

1. 栈空间有限，不能把超大数组或深递归都放栈上。
2. 栈上对象离开作用域自动销毁，不能返回局部变量地址。
3. 堆对象适合跨函数、跨线程或大小运行期决定的生命周期，但要用 RAII 或智能指针管理。
4. 现代分配器如 jemalloc、tcmalloc、mimalloc 会优化小对象分配，但仍不改变栈的 LIFO 管理优势。

## 3.2 `new` 出来的数据存放在哪里

面试里问“`new` 出来的数据在哪里”，要区分指针变量和它指向的对象：

```cpp
int* p = new int(10);
```

通常情况下：

1. `p` 是一个局部指针变量，如果定义在函数内，`p` 本身在栈上。
2. `new int(10)` 创建的 `int` 对象在堆上。
3. 堆上的对象生命周期不随函数返回自动结束，需要 `delete p` 或交给智能指针管理。

如果写成：

```cpp
auto p = std::make_unique<int>(10);
```

`unique_ptr` 对象本身可能在栈上，但它管理的 `int` 仍在堆上；离开作用域时 `unique_ptr` 析构并释放堆对象。

还要注意几个特殊情况：

1. **数组 new**：`new int[100]` 在堆上分配一段连续数组对象，应使用 `delete[]` 释放。
2. **placement new**：`new (buffer) T()` 只在已有内存上构造对象，不分配堆内存，存放位置取决于 `buffer`。
3. **自定义 `operator new`**：类或全局可以重载分配函数，对象可能来自内存池、共享内存或 mmap 区。
4. **虚拟内存视角**：`new` 底层通常经由分配器管理堆虚拟地址，物理页可能按需分配，不一定在 `new` 返回时立刻占满物理内存。

因此标准回答是：普通 `new` 创建的对象在自由存储区，通常由堆分配器管理；保存地址的指针变量在哪里，取决于指针变量本身的定义位置。

## 3.3 堆是如何分配的

C++ 语义上的自由存储区通常由用户态内存分配器管理。分配器并不是每次 `new/malloc` 都立刻进入内核，而是先在进程已有的 heap、arena、bin、tcache 或内存池中找可用块。

简化流程：

```text
new T
  -> operator new(sizeof(T))
  -> 用户态分配器按大小对齐并查找空闲块
  -> 小块可能来自 tcache/bin/arena
  -> 堆不够时通过 brk 扩展 heap
  -> 大块可能直接 mmap 匿名映射
  -> 返回原始内存
  -> 调用 T 的构造函数
```

释放时：

```text
delete p
  -> 调用析构函数
  -> operator delete(p)
  -> 分配器根据 chunk 元数据知道大小
  -> 放回缓存/空闲链表，或对大块 munmap
```

真实工程里常见优化：

1. 小对象走线程缓存，减少全局锁竞争。
2. 固定大小对象用对象池或 slab，降低碎片和元数据开销。
3. 大块内存走 `mmap`，释放时更容易归还给操作系统。
4. jemalloc、tcmalloc、mimalloc 等分配器会按 size class、arena、线程缓存优化高并发分配。

易错点：

1. `free/delete` 后内存可能只是回到分配器，不一定马上还给 OS。
2. 堆分配得到的是虚拟地址，物理页可能在首次访问时才分配。
3. 堆不是单一连续数组，长时间运行会受碎片、线程缓存和 mmap 区影响。
4. 自定义 `operator new`、placement new、内存池会改变对象实际来源。

## 3.4 栈的生长方向

在常见 x86/x86-64 Linux 用户态进程中，主线程栈通常位于用户虚拟地址空间的高地址附近，并向低地址方向增长。也就是说，函数调用加深、局部变量和栈帧增加时，栈指针一般向更小的地址移动。

示意：

```text
高地址
  stack 起始区域
  新栈帧不断向低地址扩展
低地址
```

但面试回答要加上“通常”：

1. C/C++ 标准不规定栈必须向哪个方向增长。
2. 不同 CPU 架构、ABI、操作系统可能不同。
3. Linux 线程栈通常有 guard page，继续越界增长会触发缺页异常并导致栈溢出。
4. 多线程程序中每个线程有自己的线程栈，大小可由 `pthread_attr_setstacksize` 或启动参数调整。
5. 不要写依赖栈增长方向的业务代码；判断对象生命周期应看存储期和所有权，而不是猜地址大小。

## 4. 虚函数表在哪里

虚函数表通常由编译器在编译期生成，作为只读数据放在 `.rodata` 或类似只读段中。对象里保存的是虚函数表指针 `vptr`，不是虚表本身。

对象构造时，构造函数会初始化或调整 `vptr`。在继承层次中，基类构造阶段 `vptr` 指向基类虚表，派生类构造阶段再更新为派生类虚表。

## 4.1 类对象内存分布与生命周期

一个 C++ 对象的内存里主要放非静态数据成员，以及实现多态或虚继承所需的隐藏指针。成员函数代码、静态成员变量、虚函数表本体都不在每个对象内部。

常见布局可以这样理解：

```text
对象地址
  [vptr]                  // 有虚函数时常见
  [Base 子对象成员]
  [Derived 自己的成员]
  [padding 对齐填充]
```

生命周期要拆成“存储期”和“对象生命期”：

1. 栈上对象：进入作用域时获得存储并构造，离开作用域时析构并释放栈帧。
2. 堆上对象：`operator new` 先分配原始内存，构造函数开始后对象生命期才开始；`delete` 先析构，再释放原始内存。
3. 静态对象：存储期贯穿程序运行，动态初始化顺序跨翻译单元不可靠，退出时按规则析构。
4. placement new：存储早已存在，调用 placement new 只是在该内存上开始对象生命期。

易错点：

1. 对齐填充也会占对象大小，`sizeof(T)` 不一定等于成员大小之和。
2. 空类对象大小至少为 1，保证不同对象有不同地址。
3. 基类构造期间虚调用不会分派到派生类版本，因为此时对象还处在基类构造阶段。
4. 对象析构后继续通过原指针访问是未定义行为，即使那块内存还没被覆盖，也不能认为“还能用”。

## 5. 和虚拟内存的关系

上面说的是进程虚拟地址空间中的逻辑区域。真实物理内存由操作系统按页映射：

1. 程序看到的是连续虚拟地址。
2. 物理内存可以不连续。
3. 没访问的页可能没有实际分配物理页。
4. 动态库的只读代码页可以被多个进程共享。

## 5.1 共享库映射区是做什么的

共享库通常映射在进程的 mmap 区。它的作用不是简单“复制一份库到进程里”，而是把 `.so` 文件的不同段按权限映射到进程虚拟地址空间：

1. 代码段和只读数据段通常是只读、可执行或只读映射，多进程可以共享同一份物理页。
2. 可写数据段一般是私有映射，进程写入时通过 copy-on-write 获得自己的物理页。
3. 动态链接器会处理重定位、GOT/PLT、符号绑定和懒加载。
4. ASLR 会随机化共享库加载基址，提高攻击者预测地址的难度。

因此 `top` 中的 SHR 往往包含共享库代码页。共享库能节省内存、支持独立升级，但也引入动态链接搜索路径、ABI 兼容和符号劫持等问题。

## 6. 面试回答模板

C++ 程序内存分布通常包括代码段、只读数据段、`.data`、`.bss`、堆、栈、mmap 区和 TLS 区。全局和静态变量生命周期贯穿程序，已初始化的在 `.data`，未初始化或 0 初始化的在 `.bss`；字符串字面量、虚函数表常在只读段；局部变量通常在栈上；`new/malloc` 得到的对象在堆上；动态库和大块映射常在 mmap 区。常量存储区一般指 `.rodata`，但局部 `const` 可能被优化成立即数，不一定实际占一块只读内存。注意这些都是虚拟地址空间布局，真正物理内存由页表按需映射。
