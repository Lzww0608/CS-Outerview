# Q177. C++ 内存序与 release-acquire 的 happens-before

## 1. 问题背景

C++ 多线程程序里，`std::atomic` 不只是“原子读写”。它还允许程序员通过 `std::memory_order` 指定内存序，约束编译器和 CPU 对内存操作的重排序，并建立线程之间的可见性关系。

面试里问“内存序都有哪些，对于 release-acquire，happens-before 是如何建立的”，核心考察三件事：

1. 是否知道 C++ 原子操作的几种内存序。
2. 是否理解原子性、可见性、有序性不是一回事。
3. 是否能讲清楚 release/acquire 如何通过同一个 atomic 对象建立同步关系，从而让普通变量的写入对另一个线程可见。

**假设条件**：

1. 本文讨论的是 C++11 之后的 C++ 内存模型和 `std::atomic`。
2. 这里的 “release-acquire” 指 `memory_order_release` 写和 `memory_order_acquire` 读形成的同步关系。
3. 不讨论 Java JMM 的 happens-before 规则，只在必要时类比。
4. 不深入不同 CPU 架构的汇编实现，只说明语言层语义和工程使用方式。

一句话回答：

```text
C++ 内存序包括 relaxed、consume、acquire、release、acq_rel、seq_cst。
release-acquire 的 happens-before 建立条件是：线程 A 对某个 atomic 对象做 release 写，线程 B 对同一个 atomic 对象做 acquire 读，并且 B 读到了 A 写入的值，或读到了以 A 为头的 release sequence 中的值；此时 A 中 release 之前的操作 happens-before B 中 acquire 之后的操作。
```

## 2. 问题现象

如果不理解内存序，常见问题包括：

1. **认为 atomic 一定解决所有并发问题**：`atomic<bool> ready` 是原子的，但如果用错内存序，普通数据的发布可能不可见。
2. **把 `relaxed` 当成轻量锁使用**：`relaxed` 只保证原子变量自身读写不撕裂，不保证跨变量顺序。
3. **错误发布对象**：一个线程构造对象后设置 ready，另一个线程看到 ready 后读取对象，但缺少 release/acquire。
4. **在不同 atomic 上做 release/acquire 却以为能同步**：release 和 acquire 必须通过同一个 atomic 对象或明确的同步链路连接。
5. **误用 `volatile`**：C++ `volatile` 不是线程同步工具，不能替代 `std::atomic`。
6. **过度使用 `seq_cst`**：逻辑没错但性能偏重，尤其在高频无锁结构中可能有额外屏障或全局顺序成本。
7. **过度使用弱内存序**：为了性能把所有操作改成 `relaxed`，导致偶现脏读、乱序和难复现 bug。

典型错误例子：

```cpp
#include <atomic>
#include <string>

std::string data;
std::atomic<bool> ready{false};

void producer() {
    data = "hello";
    ready.store(true, std::memory_order_relaxed); // 错误：只保证 ready 原子写
}

void consumer() {
    while (!ready.load(std::memory_order_relaxed)) {
    }
    // 这里不一定能可靠看到 data = "hello"
    // data 是普通对象，缺少同步关系时会有数据竞争/可见性问题
    use(data);
}
```

正确做法通常是：

```cpp
void producer() {
    data = "hello";
    ready.store(true, std::memory_order_release);
}

void consumer() {
    while (!ready.load(std::memory_order_acquire)) {
    }
    use(data); // 能看到 producer 在 release 之前对 data 的写入
}
```

## 3. 影响范围

内存序影响所有低层并发代码：

1. **无锁数据结构**：无锁队列、无锁栈、环形缓冲区、RCU、seqlock。
2. **对象发布**：一个线程初始化对象，另一个线程通过原子指针或状态位读取。
3. **停止标志**：后台线程通过 atomic flag 判断是否退出。
4. **引用计数**：`shared_ptr` 控制块、侵入式引用计数。
5. **统计计数器**：QPS、命中率、错误数等只需要原子性时可用 relaxed。
6. **双缓冲和快照发布**：写线程构造新配置，release 发布指针，读线程 acquire 获取。
7. **跨平台并发代码**：x86、ARM、RISC-V 内存模型强弱不同，必须依赖 C++ 标准语义而不是平台侥幸。

如果涉及代码实现，可能需要修改的模块包括：

1. `AtomicFlag` / `StopToken`：停止标志的内存序。
2. `LockFreeQueue` / `RingBuffer`：head/tail 指针、数据发布和消费顺序。
3. `ConfigPublisher`：不可变配置快照的原子发布。
4. `RefCount`：引用计数增减和对象析构同步。
5. `OnceInit`：一次性初始化和对象可见性。
6. `MetricsCounter`：纯计数器可改成 relaxed。
7. `ThreadPool`：任务入队、出队和停止状态的同步。

可能涉及的文件包括：

1. `atomic_utils.h`、`lock_free_queue.h`、`ring_buffer.h`。
2. `config_manager.cpp`、`snapshot_store.cpp`。
3. `thread_pool.cpp`、`stop_token.h`。
4. `ref_counted.h`、`intrusive_ptr.h`。
5. `tests/atomic_memory_order_test.cpp`。
6. `bench/atomic_order_bench.cpp`。

## 4. 原因分析

### 4.1 为什么需要内存序

单线程程序里，编译器和 CPU 可以重排序，只要不改变单线程可观察行为即可。

多线程程序里，如果两个线程访问同一普通变量，且至少一个是写，并且没有 happens-before 关系，就会产生数据竞争。C++ 中数据竞争是未定义行为。

`std::atomic` 解决两层问题：

1. **原子性**：对 atomic 对象的读写不会被撕裂，不会出现半写入状态。
2. **同步与排序**：通过内存序建立跨线程的可见性和顺序。

不同内存序提供不同强度的约束。约束越强，程序越容易写对，但潜在成本越高；约束越弱，性能空间更大，但更容易写错。

### 4.2 C++ 常见内存序

C++ 标准库中常见内存序包括：

| 内存序 | 典型操作 | 语义 |
| --- | --- | --- |
| `memory_order_relaxed` | load/store/RMW | 只保证 atomic 对象自身原子性，不建立跨线程同步 |
| `memory_order_consume` | load | 依赖顺序，理论上弱于 acquire，实践中长期不推荐依赖 |
| `memory_order_acquire` | load/RMW | acquire 之后的读写不能重排到 acquire 之前 |
| `memory_order_release` | store/RMW | release 之前的读写不能重排到 release 之后 |
| `memory_order_acq_rel` | RMW | 同时具备 acquire 和 release，常用于 fetch_add/CAS 等读改写 |
| `memory_order_seq_cst` | load/store/RMW/fence | 最强语义，所有 seq_cst 操作参与一个全局单一顺序 |

注意：

1. `release` 主要用于写或 RMW，不用于普通 load。
2. `acquire` 主要用于读或 RMW，不用于普通 store。
3. `acq_rel` 用在读改写操作上，例如 `exchange`、`fetch_add`、`compare_exchange` 成功路径。
4. `seq_cst` 是默认内存序，即不显式传 `memory_order` 时通常使用它。
5. `consume` 由于规范和实现复杂，实践中通常用 `acquire` 替代。

### 4.3 happens-before 是什么

`happens-before` 是 C++ 内存模型里的顺序关系。若操作 A happens-before 操作 B，则 A 的效果对 B 可见，并且编译器和 CPU 不能把它们重排成破坏该关系的形式。

常见来源：

1. **sequenced-before**：同一线程内，语句按语言规则形成先后关系。
2. **synchronizes-with**：跨线程同步关系，例如 release 写和 acquire 读匹配。
3. **transitive**：happens-before 具有传递性，A hb B，B hb C，则 A hb C。

内存序的关键不是“某条 atomic 指令很特殊”，而是它能否建立 `synchronizes-with`，再通过传递性形成 happens-before。

### 4.4 release-acquire 如何建立 happens-before

release-acquire 建立同步必须满足条件：

1. 线程 A 对 atomic 对象 `M` 执行 release 操作。
2. 线程 B 对同一个 atomic 对象 `M` 执行 acquire 操作。
3. B 的 acquire 读到了 A 的 release 写入的值，或者读到了以 A 的 release 写为头的 release sequence 中的值。

满足后：

```text
线程 A 中 release 之前的普通写
sequenced-before
release store
synchronizes-with
acquire load
sequenced-before
线程 B 中 acquire 之后的普通读
```

因此：

```text
A 中 release 前的写 happens-before B 中 acquire 后的读
```

示意代码：

```cpp
#include <atomic>
#include <cassert>

int x = 0;
std::atomic<bool> ready{false};

void producer() {
    x = 42;                                      // A
    ready.store(true, std::memory_order_release); // B
}

void consumer() {
    while (!ready.load(std::memory_order_acquire)) { // C
    }
    assert(x == 42); // D
}
```

关系链：

```text
A sequenced-before B
B synchronizes-with C
C sequenced-before D
所以 A happens-before D
```

这就是 release-acquire 发布数据的核心。

### 4.5 release sequence

如果 acquire load 没有直接读到 release store 的值，而是读到后续 RMW 操作产生的值，也可能通过 release sequence 建立同步。

简化理解：

```text
release store 写入 M
后面若干个对 M 的原子 RMW 操作
acquire load 读到这些 RMW 产生的值
```

这种情况下，acquire 仍可以和最初的 release 建立同步链。

示例：

```cpp
std::atomic<int> state{0};
int payload = 0;

void t1() {
    payload = 100;
    state.store(1, std::memory_order_release);
}

void t2() {
    state.fetch_add(1, std::memory_order_relaxed); // RMW，可能成为 release sequence 的一部分
}

void t3() {
    int v = state.load(std::memory_order_acquire);
    if (v >= 1) {
        use(payload);
    }
}
```

工程上不要过度依赖复杂 release sequence 推理。大多数场景使用简单的 release store + acquire load 更清晰。

## 5. 解决方案

### 5.1 纯计数器用 relaxed

如果只关心计数值本身原子递增，不用通过它发布其他数据，可以用 relaxed。

```cpp
std::atomic<uint64_t> qps{0};

void on_request() {
    qps.fetch_add(1, std::memory_order_relaxed);
}
```

适合：

1. 统计计数。
2. 引用计数增加。
3. 不要求跨变量可见性的状态采样。

不适合：

1. 通过 flag 发布普通数据。
2. 维护多个变量之间的不变量。
3. 依赖操作顺序进行同步。

### 5.2 对象发布用 release-acquire

典型模式：

```cpp
struct Config {
    int timeout;
    int retry;
};

Config config;
std::atomic<bool> ready{false};

void writer() {
    config.timeout = 100;
    config.retry = 3;
    ready.store(true, std::memory_order_release);
}

void reader() {
    if (ready.load(std::memory_order_acquire)) {
        use(config.timeout, config.retry);
    }
}
```

`release` 保证 `config` 的写不会被重排到 ready 之后；`acquire` 保证读取到 ready 后，后续读取 `config` 不会被重排到 ready 之前，并能看到 release 前的写。

### 5.3 原子指针发布

不可变对象发布常用 atomic pointer 或 `atomic<shared_ptr>`。

```cpp
#include <atomic>
#include <memory>

struct Table {
    int value;
};

std::atomic<Table*> g_table{nullptr};

void publish() {
    auto* t = new Table{42};
    g_table.store(t, std::memory_order_release);
}

void read() {
    Table* t = g_table.load(std::memory_order_acquire);
    if (t) {
        use(t->value);
    }
}
```

注意对象生命周期。release-acquire 解决可见性，不解决内存回收。无锁结构中还要考虑 hazard pointer、epoch reclamation、RCU 或引用计数。

### 5.4 CAS 成功和失败使用不同内存序

`compare_exchange` 可以指定成功和失败内存序。

```cpp
std::atomic<int> state{0};

bool try_start() {
    int expected = 0;
    return state.compare_exchange_strong(
        expected,
        1,
        std::memory_order_acq_rel,  // 成功：读旧值并写新值
        std::memory_order_acquire   // 失败：只读到了当前值
    );
}
```

注意：

1. 成功路径是 RMW，可用 `acq_rel`。
2. 失败路径没有写入，不能用 `release` 或 `acq_rel`。
3. 失败内存序通常不应强于成功内存序。

### 5.5 不确定时先用 mutex 或 seq_cst

如果不是在写底层无锁结构，不建议过早优化内存序。常见建议：

1. 复杂共享状态优先用 `std::mutex`。
2. 原子变量只做状态位或计数器时再考虑 `std::atomic`。
3. 不确定用什么内存序时，先用默认 `seq_cst` 保证正确，再根据性能瓶颈收紧。
4. 弱内存序优化必须配测试、代码审查和注释。

## 6. 可选方案对比

| 方案 | 能力 | 优点 | 风险 | 典型场景 |
| --- | --- | --- | --- | --- |
| `relaxed` | 只保证原子性 | 成本低 | 不建立同步 | 统计计数器 |
| `release/acquire` | 建立发布-获取同步 | 性能和语义平衡 | 必须读写同一 atomic 并读到对应值 | 发布对象、状态位 |
| `acq_rel` | RMW 同时发布和获取 | 适合 CAS/fetch_add | 推理比 load/store 复杂 | 无锁状态机 |
| `seq_cst` | 全局单一顺序 | 最容易理解 | 可能成本更高 | 默认选择、复杂同步 |
| `mutex` | 互斥 + acquire/release | 语义清晰，保护多变量不变量 | 可能阻塞 | 复杂共享状态 |
| `condition_variable` | 等待通知 + mutex | 适合阻塞等待 | 要处理虚假唤醒 | 生产者消费者 |
| RCU/Seqlock | 读优化 | 读性能高 | 实现复杂，内存回收难 | 读多写少 |

面试里可以这样区分：

```text
relaxed 解决单个 atomic 的原子性；
release/acquire 解决跨线程发布数据；
seq_cst 在 release/acquire 基础上再提供全局一致顺序；
mutex 既解决互斥，也通过 unlock/lock 建立 release/acquire 类似的同步。
```

## 7. 推荐方案

推荐按场景选择：

1. **普通业务并发**：优先 `std::mutex`、`std::shared_mutex`、线程安全队列，不手写弱内存序。
2. **纯计数器**：使用 `fetch_add(..., memory_order_relaxed)`。
3. **停止标志**：如果只停止循环且不发布其他数据，`relaxed` 可能足够；如果同时发布状态或结果，用 release/acquire。
4. **对象发布**：写线程初始化对象后 release store，读线程 acquire load。
5. **无锁数据结构**：根据算法证明选择 acquire/release/acq_rel，并配合内存回收方案。
6. **不确定时**：先用 `seq_cst` 或锁写对，再通过 profiling 判断是否需要优化。

推荐注释写法：

```cpp
// release: publish all writes to config before setting ready=true.
ready.store(true, std::memory_order_release);

// acquire: after observing ready=true, subsequent reads can see published config.
if (ready.load(std::memory_order_acquire)) {
    use(config);
}
```

弱内存序代码如果没有注释说明同步对象、发布内容和对应 acquire 点，后续维护风险很高。

## 8. 实施步骤

### 8.1 识别共享数据

先列出：

1. 哪些变量被多个线程访问。
2. 哪些变量是 atomic。
3. 哪些普通变量依赖 atomic 发布。
4. 哪些不变量跨多个变量。
5. 是否有对象生命周期问题。

### 8.2 判断是否存在数据竞争

规则：

1. 两个线程访问同一普通对象。
2. 至少一个访问是写。
3. 两者之间没有 happens-before。

满足这三个条件就是数据竞争，C++ 中属于未定义行为。解决方式通常是锁、atomic、消息传递或线程封闭。

### 8.3 设计同步边

如果使用 release/acquire，要明确同步边：

```text
Producer:
  写普通数据
  release store 到 atomic flag

Consumer:
  acquire load 同一个 atomic flag
  读普通数据
```

必须回答：

1. release 操作在哪个 atomic 对象上？
2. acquire 操作是否读同一个 atomic 对象？
3. acquire 是否读到了 release 写入的值？
4. release 前发布了哪些数据？
5. acquire 后读取哪些数据？

### 8.4 编写核心代码

发布-获取模板：

```cpp
template <class T>
class Publisher {
public:
    void publish(T value) {
        data_ = std::move(value);
        ready_.store(true, std::memory_order_release);
    }

    bool try_get(T& out) {
        if (!ready_.load(std::memory_order_acquire)) {
            return false;
        }
        out = data_;
        return true;
    }

private:
    T data_;
    std::atomic<bool> ready_{false};
};
```

注意：这个模板只适合一次发布或发布后只读。如果 `data_` 会被反复修改，需要额外锁、双缓冲、版本号或不可变快照。

### 8.5 修改代码时的核心逻辑

如果把错误的 relaxed 发布改成 release/acquire：

```text
旧逻辑：
  普通写 data
  atomic flag relaxed store
  另一线程 relaxed load flag 后读 data

新逻辑：
  普通写 data
  atomic flag release store
  另一线程 acquire load flag，读到 true 后读 data
```

如果发现多个普通变量需要整体一致：

```text
不要给每个字段加 atomic；
优先把这些字段放进一个不可变对象；
写线程构造新对象后 release 发布指针；
读线程 acquire 获取指针后读取稳定快照。
```

### 8.6 测试重点

如果涉及代码实现，测试重点包括：

1. **TSan 测试**：检查普通变量是否仍存在数据竞争。
2. **压力测试**：多线程循环运行，观察是否出现断言失败。
3. **弱内存模型测试**：尽量在 ARM/RISC-V 或模拟弱内存环境下测试。
4. **生命周期测试**：原子指针发布后，对象是否会被提前释放。
5. **CAS 失败路径测试**：`compare_exchange` 失败内存序是否合理。
6. **性能基准**：比较 relaxed、acquire/release、seq_cst、mutex 的吞吐和延迟。
7. **代码审查**：检查每个 release 是否有对应 acquire，每个 acquire 是否读同一 atomic。

## 9. 风险与注意事项

1. **atomic 不等于锁**  
   atomic 只保证单个对象的原子操作。多个变量之间的不变量通常仍要锁或快照。

2. **relaxed 不建立 happens-before**  
   用 relaxed flag 发布普通数据是常见错误。

3. **release/acquire 必须通过同一个 atomic 连接**  
   对 `a` release store，对 `b` acquire load，不会自动同步。

4. **acquire 必须读到 release 写入的值**  
   如果 load 读到旧值或其他无关值，就没有建立对应同步关系。

5. **release 只约束之前的操作**  
   release store 之后的写不会被发布给 acquire 侧。

6. **acquire 只约束之后的操作**  
   acquire load 之前的读写不受它保护。

7. **consume 不建议依赖**  
   实践中通常用 acquire 替代。

8. **seq_cst 不是性能灾难，但也不是必须**  
   先保证正确，再根据性能热点优化。

9. **内存序不解决对象生命周期**  
   发布指针后，何时释放对象仍需要引用计数、epoch、hazard pointer 或锁。

10. **跨平台不能依赖 x86 直觉**  
    x86 内存模型较强，某些错误在 x86 上不容易暴露，但在 ARM/RISC-V 上可能失败。

## 10. 验证方式

### 10.1 happens-before 逻辑验证

检查是否存在完整链路：

```text
普通写
sequenced-before
release store
synchronizes-with
acquire load
sequenced-before
普通读
```

缺任意一环，都不能声称普通写对普通读可见。

### 10.2 单元测试

可以写消息传递测试：

```cpp
#include <atomic>
#include <cassert>
#include <thread>

int data = 0;
std::atomic<bool> ready{false};

int main() {
    for (int i = 0; i < 100000; ++i) {
        data = 0;
        ready.store(false, std::memory_order_relaxed);

        std::thread t1([] {
            data = 42;
            ready.store(true, std::memory_order_release);
        });

        std::thread t2([] {
            while (!ready.load(std::memory_order_acquire)) {
            }
            assert(data == 42);
        });

        t1.join();
        t2.join();
    }
}
```

### 10.4 Code Review 检查清单

1. 每个 atomic 的用途是什么？计数、状态、发布还是 CAS？
2. 是否有普通变量依赖 atomic 发布？
3. 如果有，是否使用 release/acquire？
4. acquire 是否读取同一个 atomic？
5. 是否处理对象生命周期？
6. 多变量不变量是否错误地拆成多个 atomic？
7. CAS 失败内存序是否使用了非法或过强语义？
8. 是否有注释说明内存序选择？

## 11. 总结

C++ 内存序的核心是控制原子操作之间以及普通内存访问之间的可见性和顺序。

常见内存序：

1. `relaxed`：只保证 atomic 自身原子性。
2. `consume`：依赖顺序，实践中通常不用。
3. `acquire`：读取发布结果，阻止后续读写跑到 acquire 前。
4. `release`：发布之前写入，阻止之前读写跑到 release 后。
5. `acq_rel`：RMW 同时 acquire 和 release。
6. `seq_cst`：最强，所有 seq_cst 操作形成全局顺序。

release-acquire 建立 happens-before 的关键是：

```text
同一个 atomic 对象上，
release 写入某个值，
acquire 读到该值或读到对应 release sequence 中的值，
则 release synchronizes-with acquire。

再结合线程内 sequenced-before 和传递性，
release 前的普通写 happens-before acquire 后的普通读。
```

面试回答可以这样说：

```text
C++ 的 memory_order 主要有 relaxed、consume、acquire、release、acq_rel、seq_cst。relaxed 只保证原子性，不保证跨变量顺序；release 用于发布，保证它之前的普通写不能重排到 release 之后；acquire 用于获取，保证它之后的普通读写不能重排到 acquire 之前；acq_rel 用在 CAS、fetch_add 这类 RMW；seq_cst 最强，所有 seq_cst 操作有一个全局顺序。

release-acquire 建立 happens-before 的条件是：线程 A 对某个 atomic 变量做 release store，线程 B 对同一个 atomic 变量做 acquire load，并且 B 读到了 A 写入的值，或者读到了以 A 为头的 release sequence 的值。此时 release store synchronizes-with acquire load。由于 A 中普通写 sequenced-before release，B 中 acquire sequenced-before 后续普通读，所以通过传递性，A 的普通写 happens-before B 的普通读，B 就能安全看到 A 发布的数据。
```
