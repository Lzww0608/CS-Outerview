# 4. LRU-K 算法

LRU-K 是 LRU 的改进版。普通 LRU 只看“最近一次访问时间”，而 LRU-K 看“第 K 次最近访问时间”，用访问历史判断数据是否真的有稳定热度。

## 1. 为什么需要 LRU-K

普通 LRU 的问题是容易被一次性扫描污染：

```text
热点数据: A B C D
扫描数据: X1 X2 X3 ... X10000
```

如果缓存容量有限，扫描数据会不断被放到 LRU 链表头，把真正的热点数据挤出去。但这些扫描数据可能只访问一次，之后再也不会用。

LRU-K 的核心思想是：只有一个 key 至少被访问过 K 次，才说明它更可能是热点。淘汰时优先淘汰第 K 次最近访问时间最久的数据。

## 2. 核心原理

以 LRU-2 为例，每个 key 维护最近两次访问时间：

```text
key A: [t10, t20]
key B: [t03, t30]
key C: [t25]       // 只访问过一次
```

淘汰规则：

1. 访问次数少于 K 的 key，说明热度还没有被证明，通常放在 history 队列中。
2. 访问次数达到 K 的 key，放入 cache 队列。
3. cache 队列里按第 K 次最近访问时间排序，越老越先淘汰。
4. history 队列满了也要淘汰，避免只访问一次的 key 无限增长。

直观理解：LRU 认为“刚访问过一次”就是热；LRU-K 要求“最近一段时间访问过多次”才算热。

## 3. 常见数据结构

工程实现通常维护两部分：

```text
history: 访问次数 < K 的 key
cache:   访问次数 >= K 的 key
```

每个节点保存：

1. `key/value`
2. 最近 K 次访问时间队列
3. 当前所在队列
4. 链表迭代器或堆位置

简化实现可以用：

1. `unordered_map<key, Node>` 定位节点。
2. `list` 管理 history 和 cache 中的顺序。
3. 小顶堆按第 K 次最近访问时间淘汰，但要处理堆中旧版本节点。

## 4. 和 LRU、LFU 的区别

| 算法 | 依据 | 优点 | 缺点 |
| --- | --- | --- | --- |
| LRU | 最近一次访问 | 简单，O(1)，适合局部性明显场景 | 容易被一次性扫描污染 |
| LRU-K | 第 K 次最近访问 | 能过滤偶发访问，更抗扫描 | 需要保存访问历史，参数 K 要调 |
| LFU | 访问频率 | 能保留长期热点 | 容易保留过期热点，需要衰减 |
| 2Q/SLRU | 分段或多队列 | 工程实现较简单，抗扫描 | 参数和队列比例要调 |

LRU-K 更像是在 LRU 和 LFU 之间折中：它不是统计无限历史频率，而是用最近 K 次访问判断热度。

## 5. 真实应用

1. **数据库 Buffer Pool**：数据库经常有全表扫描，不能让扫描页冲掉索引页和热点数据页，因此会使用 LRU 变体。
2. **本地缓存**：配置、商品摘要、规则表等读多写少数据，可以用 LRU-K 或 TinyLFU 提高命中率。
3. **对象缓存**：大对象加载成本高时，可以把“访问多次才进入主缓存”作为准入策略。

## 6. 易错点

1. K 不是越大越好。K 太大，新热点进入缓存变慢；K 太小，接近普通 LRU。
2. 访问历史本身也占内存，history 队列必须有容量上限。
3. 带 TTL 的缓存中，TTL 过期和 LRU-K 淘汰是两套逻辑。
4. 多线程实现时，访问历史、哈希表和链表/堆必须保持一致，通常需要锁或分段锁。
5. 如果业务热点变化极快，LRU-K 可能反应慢，需要配合时间衰减或窗口统计。

## 7. 面试回答模板

LRU-K 是 LRU 的抗扫描改进。普通 LRU 只看最近一次访问，扫描数据访问一次也会进入缓存头部，可能把热点冲掉；LRU-K 记录每个 key 最近 K 次访问时间，只有访问次数达到 K 次才认为它有稳定热度，淘汰时看第 K 次最近访问时间。工程上通常分 history 队列和 cache 队列，访问不足 K 次的 key 先在 history 中观察，达到 K 次后进入主缓存。它适合数据库 Buffer Pool、本地缓存这类要抵抗偶发扫描的场景，代价是保存访问历史和调参复杂度更高。
