# 4. 适配器模式

适配器模式（Adapter Pattern）用于把一个已有对象或第三方库的接口，转换成调用方期望的接口。它解决的是“接口不兼容但功能可以复用”的问题。

## 1. 核心角色

| 角色 | 说明 |
| --- | --- |
| Target | 调用方希望使用的目标接口 |
| Adaptee | 已经存在但接口不匹配的类、SDK 或旧系统 |
| Adapter | 负责做接口转换、参数转换、异常转换和语义对齐 |
| Client | 只依赖 Target，不直接依赖 Adaptee |

典型结构：

```text
Client -> Target 接口
              ^
              |
           Adapter -> Adaptee
```

适配器不是为了“包一层显得优雅”，而是为了让业务代码依赖稳定接口，把第三方接口变化、旧接口兼容和平台差异隔离在边界层。

## 2. 适用场景

1. **接入第三方 SDK**：短信、支付、对象存储、地图、推送服务的 API 不统一，对内暴露统一接口。
2. **兼容旧系统**：旧接口不能立刻改造，但新业务希望使用新的领域接口。
3. **跨平台适配**：Windows、Linux、Android、iOS 的系统 API 不一致，对上层提供统一抽象。
4. **协议或数据格式转换**：把外部 JSON、XML、Protobuf、私有 TLV 转成内部 DTO。
5. **测试隔离**：把难以 mock 的外部依赖包到接口后面，单测使用 fake adapter。

## 3. 示例

假设项目内部希望所有消息发送器都实现同一个接口：

```cpp
#include <memory>
#include <string>

class MessageSender {
public:
    virtual ~MessageSender() = default;
    virtual bool send(const std::string& to, const std::string& content) = 0;
};
```

但第三方短信 SDK 的接口长这样：

```cpp
class SmsSdk {
public:
    int pushSms(const char* phone, const char* text);
};
```

可以写一个对象适配器：

```cpp
class SmsSenderAdapter : public MessageSender {
public:
    explicit SmsSenderAdapter(std::shared_ptr<SmsSdk> sdk)
        : sdk_(std::move(sdk)) {}

    bool send(const std::string& to, const std::string& content) override {
        return sdk_->pushSms(to.c_str(), content.c_str()) == 0;
    }

private:
    std::shared_ptr<SmsSdk> sdk_;
};
```

这样业务层只依赖 `MessageSender`，将来从短信换成邮件、企业微信、APNs 或 FCM，只需要新增适配器，不需要改业务流程。

## 4. 类适配器和对象适配器

| 类型 | 实现方式 | 特点 |
| --- | --- | --- |
| 类适配器 | 通过继承 Adaptee 并实现 Target | 依赖继承，耦合更强，C++ 多继承时可用但要谨慎 |
| 对象适配器 | Adapter 内部持有 Adaptee 对象 | 更灵活，组合优于继承，工程中更常见 |

真实项目里优先使用对象适配器，因为第三方 SDK 的生命周期、连接池、重试策略和配置通常都需要组合管理。

## 5. 和其他模式的区别

| 模式 | 重点 |
| --- | --- |
| 适配器模式 | 转换接口，让不兼容接口可以协作 |
| 代理模式 | 控制访问，例如鉴权、远程代理、缓存、延迟加载 |
| 装饰器模式 | 不改变接口，动态增强功能 |
| 外观模式 | 给复杂子系统提供更简单的统一入口 |

一句话区分：适配器改变“接口形状”，装饰器增强“原接口能力”，代理控制“访问过程”，外观简化“子系统使用方式”。

## 6. 易错点

1. 适配器不能掩盖领域模型混乱。内部 Target 接口必须稳定，否则会出现一层套一层。
2. 不要把所有转换逻辑都塞进业务 service，边界转换应放在 adapter 层。
3. 注意异常、错误码、超时、重试和幂等语义转换，不能只转换参数。
4. 热路径上的适配器要关注分配、拷贝、虚调用和序列化成本。
5. 适配器层不要泄露第三方类型，否则调用方仍然被外部 SDK 绑定。

## 7. 真实场景

1. **支付系统**：内部定义 `PaymentGateway`，微信、支付宝、Stripe 各自实现 adapter。
2. **对象存储**：内部定义 `ObjectStorage`，底层适配 S3、COS、OSS、MinIO。
3. **推送系统**：内部统一 `PushSender`，底层适配 APNs、FCM、厂商通道和短信。
4. **RPC 网关**：HTTP 请求适配成内部 RPC 请求，或把 gRPC 错误码适配成统一业务错误码。
5. **老系统迁移**：新服务按领域接口调用，旧 SOAP/HTTP 接口由 adapter 封装，迁移时逐步替换实现。

## 8. 面试回答模板

适配器模式用于解决接口不兼容的问题。调用方依赖一个稳定的 Target 接口，Adapter 内部持有旧系统或第三方 SDK 的 Adaptee，把参数、返回值、异常、超时和错误语义转换成内部统一模型。它常用于接第三方支付、短信、对象存储、推送 SDK，或做老系统兼容。工程上我会优先用对象适配器，并保证第三方类型不泄露到业务层；否则适配器只是多包了一层，不能真正降低耦合。
