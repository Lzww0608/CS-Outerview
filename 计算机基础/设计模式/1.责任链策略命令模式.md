# 1. 责任链、策略模式和命令模式

下单前置校验经常会问：为什么用责任链模式，而不是策略模式或命令模式。关键在于先判断业务结构：下单校验通常是多个校验步骤按顺序执行，任一步失败就中断，因此更符合责任链。

## 责任链模式

责任链模式把多个处理器串成一条链，请求沿着链依次传递，每个处理器只负责自己的判断，处理完再决定是否交给下一个处理器。

适合场景：

1. 有多个校验步骤，例如参数校验、登录校验、风控校验、库存校验、价格校验、优惠券校验。
2. 校验之间有顺序关系，前面的失败可以直接终止。
3. 希望方便插拔、调整顺序、按业务场景复用部分节点。

下单前置校验使用责任链，可以把每个校验点拆成独立 handler：

```text
参数校验 -> 用户状态校验 -> 风控校验 -> 库存校验 -> 优惠券校验 -> 价格校验
```

## 策略模式

策略模式是把一组可互相替换的算法封装起来，运行时选择其中一个执行。它强调的是“多选一”，而不是“一组步骤依次执行”。

适合场景：

1. 不同会员价计算策略。
2. 不同运费计算策略。
3. 不同支付渠道费率策略。
4. 不同活动的优惠计算策略。

如果下单校验只有“普通商品校验”“秒杀商品校验”“预售商品校验”三套互斥流程，可以用策略模式先选择一个校验策略。但每个策略内部仍然可能是一条责任链。

## 命令模式

命令模式把一个请求封装成对象，支持排队、撤销、重试、日志记录和异步执行。它强调的是“把动作对象化”，而不是组织校验流程。

适合场景：

1. 订单取消命令、退款命令、发货命令。
2. 任务队列异步执行。
3. 操作日志、撤销/重做。
4. 工作流系统中把每个动作持久化。

下单前置校验一般不优先用命令模式，因为校验通常是同步、轻量、无副作用或弱副作用的判断逻辑，不需要把每个校验封装成可排队、可撤销的命令。

## 对比总结

| 模式 | 核心语义 | 更适合的问题 | 用在下单中的位置 |
| --- | --- | --- | --- |
| 责任链 | 多个处理器依次处理，可中断 | 多步骤校验、过滤器、拦截器 | 下单前置校验主流程 |
| 策略模式 | 多个算法选一个 | 价格、运费、优惠、渠道选择 | 某个校验节点内部的算法选择 |
| 命令模式 | 把请求封装成可执行对象 | 异步、排队、撤销、重试 | 取消订单、退款、履约任务 |

一句话回答：下单前置校验是“多个校验点按顺序执行并可短路”，所以责任链最自然；策略模式解决“多种算法选一种”，命令模式解决“请求对象化并支持排队/撤销/重试”，语义都不如责任链贴合。
