# 3. MVC、工厂模式和单例模式

MVC、工厂模式和单例模式都常在客户端、服务端和工具类项目中出现。面试里不要只背定义，要说明它们解决什么耦合问题、适合什么变化点，以及滥用会带来什么代价。

## 1. MVC 模式

MVC 把界面应用拆成三类职责：

| 部分 | 职责 | 例子 |
| --- | --- | --- |
| Model | 数据和业务状态 | 用户信息、文档模型、设备状态、网络返回数据 |
| View | 展示和用户交互 | 窗口、按钮、列表、图表、渲染视图 |
| Controller | 接收输入、协调 Model 和 View | 点击处理、命令分发、页面跳转、调用服务 |

核心思想是让 UI 展示、用户输入和业务状态解耦。

典型流程：

```text
用户操作 View
    -> Controller 接收事件
    -> Controller 调用 Model 或 Service
    -> Model 状态变化
    -> View 根据状态刷新
```

真实项目里经常会演化出 MVP、MVVM、Redux/Flux 等变体：

1. **MVP**：Presenter 更主动地更新 View，常见于传统客户端。
2. **MVVM**：ViewModel 通过数据绑定驱动 View，常见于 Qt/QML、WPF、前端框架。
3. **Flux/Redux**：单向数据流，适合复杂状态管理。

### MVC 易错点

1. View 不应直接写复杂业务逻辑。
2. Controller 不应膨胀成“上帝类”，复杂业务应下沉到 Service 或 Model。
3. Model 不等于数据库表，客户端里也可以是内存状态、领域对象或缓存。
4. MVC 不是目录命名游戏，核心是依赖方向和职责边界。

## 2. 工厂模式

工厂模式把对象创建逻辑从使用方抽离出来，让调用方依赖抽象接口，而不是直接依赖具体类。

适合场景：

1. 根据配置、协议类型、平台或运行时条件创建不同对象。
2. 构造过程复杂，需要封装参数校验、资源申请和依赖注入。
3. 调用方只关心接口，不希望知道具体实现类。
4. 插件化系统中，按名称或类型创建 handler。

示例：

```cpp
#include <memory>
#include <stdexcept>
#include <string>
#include <utility>

class Codec {
public:
    virtual ~Codec() = default;
    virtual void decode() = 0;
};

class H264Codec : public Codec {
public:
    void decode() override {}
};

class H265Codec : public Codec {
public:
    void decode() override {}
};

std::unique_ptr<Codec> createCodec(const std::string& type) {
    if (type == "h264") {
        return std::make_unique<H264Codec>();
    }
    if (type == "h265") {
        return std::make_unique<H265Codec>();
    }
    throw std::invalid_argument("unsupported codec type");
}
```

更复杂的系统可以用注册表：

```text
type -> creator function
```

这样新增类型时只注册创建函数，不需要修改一个巨大的 `if/else`。

## 3. 单例模式

单例模式保证一个类在进程内只有一个实例，并提供全局访问点。典型对象包括日志器、配置中心、全局调度器、指标上报器等。

C++11 后推荐使用局部静态变量实现线程安全懒加载：

```cpp
class Config {
public:
    static Config& instance() {
        static Config config;
        return config;
    }

    Config(const Config&) = delete;
    Config& operator=(const Config&) = delete;

private:
    Config() = default;
};
```

非多线程环境中，普通懒加载指针也能工作，但不推荐在现代 C++ 中优先使用：

```cpp
class Singleton {
public:
    static Singleton* instance() {
        if (inst_ == nullptr) {
            inst_ = new Singleton();
        }
        return inst_;
    }
private:
    Singleton() = default;
    static Singleton* inst_;
};
```

问题是：多线程下可能创建多个实例，退出时释放顺序也不好控制。

### 多线程单例注意事项

1. C++11 局部静态变量初始化天然线程安全。
2. 双重检查锁要依赖正确的内存模型，不建议面试手写复杂版本。
3. 单例如果持有线程、文件、socket，要明确 `shutdown` 时机。
4. 单例会引入全局状态，测试隔离和依赖替换更困难。
5. 不是所有“只想少传参数”的对象都应该做成单例。

如果看到类似下面的手写懒汉式：

```cpp
if (instance == nullptr) {
    instance = new Singleton();
}
```

在并发下有两个问题：

1. 多个线程可能同时看到 `instance == nullptr`，从而创建多个对象。
2. `new Singleton()` 可以拆成申请内存、构造对象、把地址赋给指针等步骤；如果发布指针和构造完成之间没有正确同步，其他线程可能看到未完全构造的对象。

因此现代 C++ 优先用函数内局部静态变量，或用 `std::call_once`：

```cpp
#include <memory>
#include <mutex>

class Singleton2 {
public:
    static Singleton2& instance() {
        std::call_once(flag_, [] {
            inst_.reset(new Singleton2);
        });
        return *inst_;
    }

private:
    Singleton2() = default;

    static std::once_flag flag_;
    static std::unique_ptr<Singleton2> inst_;
};
```

## 4. 观察者模式

观察者模式用于一个对象状态变化后通知多个订阅者。典型例子是事件系统、GUI 回调、配置变更通知、消息分发。

基本结构：

```text
Subject 保存 observer 列表
Observer 提供 onEvent 接口
Subject 状态变化时遍历列表并通知 observer
```

多线程下的难点不在“怎么遍历”，而在 observer 生命周期和回调重入：

1. 通知过程中 observer 可能被注销或析构，直接保存裸指针容易悬空。
2. 持有锁回调 observer，observer 里再调用 Subject 可能死锁。
3. 一个慢 observer 会拖慢整个通知链路。
4. 多线程注册、注销和通知并发时，需要定义清晰的一致性语义。

常见工程做法：

1. observer 用 `weak_ptr` 注册，通知前 `lock()` 成 `shared_ptr`，失效则清理。
2. 复制一份 observer 快照后释放锁，再逐个回调，避免持锁执行外部代码。
3. 事件量大时改成消息队列或 event bus，由专门线程异步分发。
4. 明确回调线程模型：是在调用线程同步触发，还是投递到目标线程执行。

## 5. 三者在项目中的关系

一个 PC 客户端或工具类项目中可能这样组合：

1. MVC 负责拆分 UI、输入事件和业务状态。
2. 工厂模式负责根据配置创建不同协议 handler、渲染器或设备适配器。
3. 单例模式负责全局配置、日志和指标上报。

但它们解决的问题不同：

| 模式 | 解决问题 | 风险 |
| --- | --- | --- |
| MVC | UI、输入、状态解耦 | Controller 或 Model 膨胀 |
| 工厂 | 创建逻辑和使用逻辑解耦 | 过度抽象、类型注册分散 |
| 单例 | 控制全局唯一资源 | 全局状态、测试困难、生命周期问题 |

## 6. 面试回答模板

MVC 是把界面应用拆成 Model、View、Controller：Model 管业务状态，View 管展示，Controller 处理输入并协调二者，目的是降低 UI 和业务逻辑耦合。工厂模式用于封装对象创建，调用方依赖抽象接口，适合根据配置或运行时类型创建不同实现。单例模式保证全局唯一实例，C++11 推荐用函数内局部静态变量实现线程安全懒加载。工程上我会谨慎使用单例，因为它会引入全局状态和生命周期问题；工厂和 MVC 则更适合明确扩展点和职责边界。
