# 2. BST、AVL 树和红黑树

二叉搜索树、AVL 树和红黑树都属于搜索树，核心目标是在动态集合中支持查找、插入、删除和有序遍历。面试里要说明它们的有序性、平衡策略、复杂度和工程取舍。

## 二叉搜索树 BST

二叉搜索树满足：

1. 任意节点的左子树所有 key 小于当前节点。
2. 任意节点的右子树所有 key 大于当前节点。
3. 中序遍历可以得到有序序列。

查找过程类似二分：

```text
key < node.key  -> 去左子树
key > node.key  -> 去右子树
key == node.key -> 找到
```

复杂度取决于树高 `h`：

1. 查找、插入、删除都是 `O(h)`。
2. 树平衡时 `h = O(log n)`。
3. 如果按有序数据连续插入，BST 可能退化成链表，复杂度变成 `O(n)`。

## AVL 树

AVL 树是严格平衡的二叉搜索树。它要求任意节点左右子树高度差不超过 1，通常通过记录节点高度或平衡因子来维护。

核心操作：

1. 插入或删除后沿祖先链更新高度。
2. 如果平衡因子失衡，通过旋转恢复平衡。
3. 常见旋转有 LL、RR、LR、RL 四类。

特点：

1. 查询路径更短，查找性能稳定。
2. 插入删除后可能需要更多旋转和高度维护。
3. 适合读多写少、对查询延迟更敏感的内存索引。

## 红黑树

红黑树是近似平衡的二叉搜索树，通过颜色和黑高约束控制树高。典型性质包括：

1. 每个节点是红色或黑色。
2. 根节点通常是黑色。
3. 叶子 NIL 节点视为黑色。
4. 红色节点不能有红色子节点。
5. 从任意节点到其所有后代 NIL 节点的路径上，黑色节点数量相同。

这些性质保证最长路径不会超过最短路径的 2 倍，因此树高仍是 `O(log n)`。

红黑树的工程特点：

1. 平衡约束比 AVL 宽松，插入删除旋转次数通常更少。
2. 查找略逊于 AVL，但更新更友好。
3. 适合查找、插入、删除都频繁的场景。
4. C++ `std::map/std::set`、Linux CFS 运行队列、Nginx 定时器等常用红黑树或类似有序树结构。

## 三者对比

| 对比项 | 普通 BST | AVL 树 | 红黑树 |
| --- | --- | --- | --- |
| 是否自平衡 | 否 | 是，严格平衡 | 是，近似平衡 |
| 最坏树高 | `O(n)` | `O(log n)` | `O(log n)` |
| 查找性能 | 取决于树形 | 最稳定，路径较短 | 稳定，路径略长于 AVL |
| 插入删除成本 | 简单但可能退化 | 旋转和高度维护较多 | 旋转较少，更新更友好 |
| 有序遍历 | 支持 | 支持 | 支持 |
| 适用场景 | 教学、小规模、输入随机 | 读多写少 | 读写都频繁、标准库有序容器 |

## 易错点

1. “平衡二叉树”在面试里经常默认指 AVL，但广义上红黑树也是自平衡二叉搜索树。
2. 红黑树不是绝对平衡，它保证的是黑高约束下的近似平衡。
3. BST 的中序遍历有序，但这不代表它一定高效；如果树退化，单次查找是 `O(n)`。
4. `std::map` 标准没有强制必须用红黑树，但要求有序和 `O(log n)` 复杂度，主流实现采用红黑树。
5. 数据库索引更常用 B+ 树，不是红黑树，因为 B+ 树扇出高、树高低，更适合磁盘页和范围扫描。

## 真实场景

1. 内存中的有序字典、范围查询、定时器管理可以使用红黑树。
2. 查询远多于修改的内存索引可以考虑 AVL 或只读排序数组。
3. 如果只需要等值查询且不要求有序，哈希表通常比树更合适。
4. 如果数据存放在磁盘或 SSD 上，优先考虑 B/B+ 树或 LSM Tree，而不是二叉搜索树。

## 面试回答模板

BST 通过“左小右大”维护有序性，中序遍历有序，查找插入删除复杂度是 `O(h)`，但普通 BST 可能退化成链表。AVL 是严格平衡二叉搜索树，左右子树高度差不超过 1，查找路径短但插入删除维护成本高。红黑树通过颜色和黑高约束保持近似平衡，最长路径不超过最短路径 2 倍，查找、插入、删除都是 `O(log n)`，更新成本比 AVL 低，所以 `std::map/std::set` 等工程结构更常用红黑树。
