# 13. Count-Min Sketch 原理与应用

Count-Min Sketch，简称 CMS，是一种用于**流式频率估计**的概率数据结构。它适合回答：

```text
在一条持续到来的事件流里，某个 key 大概出现了多少次？
```

例如：某个商品被浏览了多少次、某个 IP 请求了多少次、某个词在日志里出现了多少次、某个缓存 key 历史访问频率有多高。

它的核心价值是：**用固定且很小的内存，估计海量 key 的访问频率**。代价是结果有误差，并且在只处理正向计数时，估计值只会偏大，不会偏小。

## 1. 为什么需要 Count-Min Sketch

如果用哈希表精确统计频率：

```text
HashMap<key, count>
```

优点是准确，缺点是 key 的数量越多，内存越大。对于日志、埋点、网络包、缓存访问流这类场景，distinct key 可能非常多，甚至无法提前估算。

CMS 的思路是：不保存原始 key，只保存一组计数器。不同 key 可能撞到同一个计数器，因此会产生误差；但只要计数器矩阵足够大、哈希函数足够均匀，重频 key 的估计就比较可靠。

它和布隆过滤器很像：

| 对比项 | Bloom Filter | Count-Min Sketch |
| --- | --- | --- |
| 解决问题 | 判断是否可能存在 | 估计出现次数 |
| 底层结构 | bit array | counter matrix |
| 插入 | 多个 bit 置 1 | 多个计数器加 1 |
| 查询 | 所有 bit 是否为 1 | 多个计数器取最小值 |
| 误差方向 | 可能误判存在 | 可能高估频率 |
| 典型场景 | 防穿透、去重、黑名单预判 | 热点统计、限流特征、缓存准入 |

## 2. 基本结构

CMS 维护一个二维计数器矩阵：

```text
depth = d 行
width = w 列

counter[d][w]
```

每一行配一个独立哈希函数：

```text
h1(key), h2(key), ..., hd(key)
```

每个哈希函数把 key 映射到这一行的一个列下标：

```text
col_i = h_i(key) % width
```

### 插入 / 增加计数

当事件 `key` 出现一次时，对每一行对应的计数器加 1：

```text
for i in [0, d):
    counter[i][h_i(key) % w] += 1
```

如果一次增加 `delta`，就把 `1` 换成 `delta`。

### 查询频率

查询 `key` 的频率时，取每一行对应计数器的最小值：

```text
estimate(key) = min(counter[i][h_i(key) % w])
```

为什么取最小值？

1. 每个计数器都包含 `key` 自己的真实次数。
2. 碰撞只会把其他 key 的次数加进来，所以每个计数器都可能偏大。
3. 多行哈希独立时，不太可能每一行都被大量其他 key 污染。
4. 取最小值可以选择污染最少的那一行。

所以对于只增加、不减少的流：

```text
true_count(key) <= estimate(key)
```

CMS 不会低估，只会高估。

## 3. 误差和参数选择

CMS 常用两个参数描述误差：

1. `epsilon`：相对总流量的误差上界。
2. `delta`：超过误差上界的失败概率。

常见保证可以写成：

```text
以至少 1 - delta 的概率：
true_count(x) <= estimate(x) <= true_count(x) + epsilon * N

N = 所有事件的总次数
```

常见参数选择：

```text
width  = ceil(e / epsilon)
depth  = ceil(ln(1 / delta))
space  = width * depth * counter_size
update = O(depth)
query  = O(depth)
```

直观理解：

1. `width` 越大，每一行越宽，哈希冲突越少，误差越小。
2. `depth` 越大，独立哈希行越多，“每一行都被严重污染”的概率越低。
3. `epsilon` 控制误差幅度，`delta` 控制不幸概率。
4. CMS 的误差和总事件数 `N` 相关，而不是和某个 key 的真实次数直接相关。

示例：

```text
目标：epsilon = 0.001, delta = 0.01

width = ceil(e / 0.001) ≈ 2719
depth = ceil(ln(1 / 0.01)) ≈ 5

如果 counter 使用 4 字节 int：
内存约为 2719 * 5 * 4 ≈ 54KB
```

这意味着：以约 99% 的概率，某个 key 的估计值不会超过真实值加上 `0.1% * N`。

## 4. 实现细节

### 4.1 哈希函数

工程里不一定真的准备 `d` 个完全独立哈希函数，常用做法是双哈希：

```text
h_i(x) = h1(x) + i * h2(x)
```

再对 `width` 取模。这样可以减少哈希计算成本。

注意点：

1. 哈希分布要均匀，否则某些列会被过度污染。
2. 外部用户可控 key 要注意 HashDoS，必要时使用带随机种子的 hash。
3. `width` 如果是 2 的幂，可以用位运算取模，但前提是 hash 的低位质量足够好。

### 4.2 计数器大小和溢出

计数器可以是 `uint8`、`uint16`、`uint32`、`uint64`，取决于流量规模和是否允许饱和。

常见策略：

1. 大流量精确累加：使用 `uint32` 或 `uint64`。
2. 缓存准入频率估计：使用 4-bit 或 8-bit 小计数器，配合周期性衰减。
3. 达到最大值后饱和，不再增加，避免溢出回绕。

缓存场景里，频率只用于比较“谁更热”，不需要保存精确次数，所以小计数器很常见。

### 4.3 Conservative Update

普通 CMS 插入时会把所有行对应计数器都加一。Conservative Update 会先查询当前估计值 `m`，只更新等于 `m` 的计数器：

```text
m = query(key)
for i in [0, d):
    c = counter[i][h_i(key) % w]
    if c == m:
        c += 1
```

它的作用是减少无意义的过度抬高，降低高估偏差。

代价是实现稍复杂，一次更新需要先读再写。对高并发场景，还要考虑原子性和并发竞争。

### 4.4 衰减和时间窗口

CMS 的基本版本只会增加，不会自然遗忘旧数据。如果用于缓存、热点、风控，旧热点可能长期影响结果。

常见解决方式：

1. **周期性衰减**：每隔一段时间把所有计数器除以 2。
2. **滑动窗口**：维护多个按时间分片的 CMS，例如最近 5 分钟拆成 5 个 1 分钟 sketch。
3. **按天/小时建 sketch**：查询时只查某个时间段，或者合并多个时间段。
4. **指数衰减**：更新时引入时间权重，让越旧的数据权重越低。

这就是很多人说的 temporal CMS 或 time-decayed CMS 的核心：**频率不是全历史频率，而是某个时间窗口内的近似频率**。

如果这里的 `Temporal` 指的是 Temporal.io 工作流框架，需要注意：Temporal.io 本身不是 Count-Min Sketch 的典型核心应用；CMS 更常见于 Temporal 周边的可观测性、限流、热点统计、指标聚合系统里。

### 4.5 合并

两个参数相同、哈希种子相同的 CMS 可以按计数器逐格相加：

```text
merged[i][j] = cms1[i][j] + cms2[i][j]
```

这让 CMS 很适合分布式统计：

1. 每台机器本地维护一个 sketch。
2. 周期性把 sketch 上报到中心节点。
3. 中心节点 merge 后得到全局近似频率。

前提是 `width`、`depth`、hash seed 和 counter 类型一致。

## 5. 代码示例

下面是一个简化版 Python 实现，重点体现核心逻辑：

```python
import hashlib
import math


class CountMinSketch:
    def __init__(self, epsilon: float, delta: float):
        self.width = math.ceil(math.e / epsilon)
        self.depth = math.ceil(math.log(1 / delta))
        self.table = [[0] * self.width for _ in range(self.depth)]

    def _hash(self, key: str, row: int) -> int:
        data = f"{row}:{key}".encode("utf-8")
        digest = hashlib.blake2b(data, digest_size=8).digest()
        return int.from_bytes(digest, "big") % self.width

    def add(self, key: str, count: int = 1) -> None:
        for row in range(self.depth):
            col = self._hash(key, row)
            self.table[row][col] += count

    def estimate(self, key: str) -> int:
        ans = float("inf")
        for row in range(self.depth):
            col = self._hash(key, row)
            ans = min(ans, self.table[row][col])
        return ans


cms = CountMinSketch(epsilon=0.001, delta=0.01)
cms.add("hotel:123")
cms.add("hotel:123")
cms.add("flight:456")

print(cms.estimate("hotel:123"))  # >= 2，可能略大
```

真实工程不会直接用上面这种哈希方式做高性能实现，通常会用更快的非加密 hash、双哈希、连续数组和紧凑计数器。

## 6. 和 TinyLFU 的关系

TinyLFU 是缓存准入策略，解决的问题不是“缓存满了淘汰谁”这么简单，而是：

```text
一个新来的 key 是否值得进入缓存？
```

如果只用 LRU，顺序扫描会污染缓存：一次性访问的大量冷数据会把真正的热点挤出去。TinyLFU 用频率估计来做准入判断：

```text
candidate = 新来的缓存项
victim    = 当前准备被淘汰的缓存项

if freq(candidate) > freq(victim):
    接纳 candidate，淘汰 victim
else:
    拒绝 candidate，保留 victim
```

这里的 `freq()` 就可以由 Count-Min Sketch 估计。

### Caffeine 的 Window TinyLFU

Java 缓存库 Caffeine 使用 Window TinyLFU。它不是单纯 LFU，而是结合了 recency 和 frequency：

1. **Window LRU**：新数据先进入一个小窗口，给新热点一个试用机会。
2. **Main Space**：主缓存区域通常由 Segmented LRU 管理，区分 probation/protected。
3. **TinyLFU Admission**：窗口淘汰出的候选项和主区 victim 比较频率。
4. **Count-Min Sketch**：用小计数器估计访问频率，避免为每个 key 保存精确计数。
5. **Reset / Aging**：周期性把计数器衰减，避免“昨日热点”长期占据优势。

一次访问的大致流程：

```text
read(key)
  -> 记录访问到频率 sketch
  -> 如果命中：更新缓存内部 recency 队列
  -> 如果未命中：加载 value，进入 window
  -> window 满：产生 candidate
  -> main probation 产生 victim
  -> 比较 estimate(candidate) 和 estimate(victim)
  -> 决定接纳 candidate 还是保留 victim
```

为什么 Caffeine 不直接做精确 LFU？

1. 精确 LFU 要给每个 key 维护计数和复杂链表，内存和 CPU 成本高。
2. 精确 LFU 对旧热点不敏感，容易出现“昨日英雄”问题。
3. CMS + aging 可以低成本估计近期热度。
4. Window LRU 给新热点试用机会，避免新数据饥饿。

## 7. Temporal / 时序窗口中的用法

在时序系统里，问题通常不是“全历史某个 key 出现多少次”，而是：

```text
最近 1 分钟、5 分钟、1 小时内，某个 key 出现了多少次？
```

可以用多个 CMS 做时间分桶：

```text
bucket_10:00 -> CMS
bucket_10:01 -> CMS
bucket_10:02 -> CMS
bucket_10:03 -> CMS
bucket_10:04 -> CMS
```

查询最近 5 分钟时，把 5 个 bucket 的估计结果相加，或者先 merge 这 5 个 sketch。

典型应用：

1. **热点商品/酒店/航班统计**：每分钟记录商品 ID，估计近期访问量。
2. **风控限流**：估计某 IP、账号、设备指纹在窗口内的请求次数。
3. **日志平台**：估计某错误码、接口、用户维度的出现次数。
4. **监控告警**：发现某类事件的近似 Top 热点。

Redis 的 Count-Min Sketch 可以按天、小时或业务窗口建多个 sketch。TimescaleDB Toolkit 提供 `count_min_sketch()` 聚合函数，适合在时序查询里对某列做近似频率统计。Spark 和 Databricks 也提供 Count-Min Sketch 相关接口，用于大规模数据的近似频率汇总。

## 8. 真实框架中的例子

### 8.1 Redis / RedisBloom

Redis 的概率数据结构模块提供 Count-Min Sketch 命令，例如：

```text
CMS.INITBYPROB key error probability
CMS.INCRBY key item increment
CMS.QUERY key item
CMS.MERGE dest numKeys key ...
CMS.INFO key
```

应用方式：

1. 每次商品被浏览：`CMS.INCRBY product_views product_id 1`
2. 查询商品热度：`CMS.QUERY product_views product_id`
3. 每天一个 sketch：`product_views:2026-05-04`
4. 查询多天趋势：对多个 sketch 做 merge 或分别 query 后汇总。

注意点：

1. Redis CMS 适合高频近似统计，不适合低频精确统计。
2. 低于误差阈值的小计数应视为噪声。
3. 如果要列出 TopK，需要额外维护候选集合；CMS 本身不能枚举 key。

### 8.2 Apache Spark / Databricks

Spark 的 `CountMinSketch` 面向分布式数据集频率估计。它可以把每个分区里的统计合并成全局 sketch。

适用场景：

1. 对海量日志估算某个 userId、query、itemId 的出现次数。
2. 在作业执行前估计数据倾斜，辅助判断热点 key。
3. 对多个批次的 sketch 做 merge，降低内存和 shuffle 成本。

Databricks SQL 提供 `count_min_sketch(column, epsilon, confidence, seed)` 聚合函数，返回二进制 sketch，适合 SQL 分析链路。

### 8.3 Caffeine / TinyLFU

Caffeine 的 W-TinyLFU 使用频率 sketch 估计历史访问频率，并用它做缓存准入判断。

它解决的核心问题是：

1. LRU 会被顺序扫描污染。
2. LFU 会被旧热点污染。
3. 精确计数太贵。
4. 只保留近期访问又可能错过真正高频对象。

W-TinyLFU 的工程取舍是：

```text
小窗口保留 recency
+ 频率 sketch 提供 frequency
+ 周期性 reset 提供 aging
+ admission policy 抵抗扫描污染
```

### 8.4 Akka FrequencySketch

Akka 内部也有 `FrequencySketch`，用于 TinyLFU cache admission policy。它包含 TinyLFU 的 reset 操作，会周期性把计数衰减，避免频率无限增长。

这类设计说明：CMS 在缓存框架里通常不是单独暴露给用户，而是作为内部组件，服务于缓存准入、热点识别和低成本频率估计。

### 8.5 TimescaleDB / 时序近似统计

TimescaleDB Toolkit 的 `count_min_sketch()` 是时序数据库里的例子。它把某列聚合成 CMS，再用 accessor 查询某个值的近似出现次数。

适合：

1. 某时间窗口内接口错误码频次。
2. 某时间窗口内用户事件类型频次。
3. 某时间窗口内商品或内容 ID 热度。

这类系统强调 temporal，也就是“频率必须带时间语义”。工程上通常会配合 `time_bucket`、保留策略和连续聚合。

## 9. 局限和易错点

1. **不能枚举 key**：CMS 不保存原始 key，只能查询已知 key 的估计频率。要找 TopK，需要额外维护候选集合或小顶堆。
2. **不适合精确低频统计**：低频 key 的估计值很容易被碰撞噪声淹没。
3. **只加不减时才保证不低估**：如果支持负更新，误差性质会复杂很多。
4. **不是基数统计结构**：估计不同元素数量应该用 HyperLogLog，不是 CMS。
5. **不是存在性判断结构**：判断是否存在应该用 Bloom Filter、Cuckoo Filter 或真实索引。
6. **参数必须提前设计**：`epsilon` 太大误差高，`delta` 太大不稳定，counter 太小会溢出或饱和。
7. **热点候选要另外保存**：CMS 能告诉你“这个 key 大概多热”，不能主动告诉你“谁最热”。
8. **哈希冲突可被攻击**：外部 key 可控时要考虑随机种子和哈希函数选择。

## 10. 面试回答模板

可以这样回答：

> Count-Min Sketch 是一种用于流式频率估计的概率数据结构。它维护一个 `depth * width` 的计数器矩阵，每一行对应一个哈希函数。某个 key 出现时，在每一行哈希到一个计数器并加一；查询时取这些计数器的最小值作为频率估计。因为哈希冲突只会把别的 key 的次数加进来，所以在只做正向计数时 CMS 不会低估，只可能高估。参数上通常用 `epsilon` 控制误差幅度，用 `delta` 控制失败概率，空间大约是 `ceil(e / epsilon) * ceil(log(1 / delta)) * counter_size`。
>
> 工程上 CMS 适合热点统计、近似 TopK 候选过滤、风控请求频率、缓存准入等场景。它不能枚举 key，也不适合精确低频统计；如果要找 TopK，需要 CMS 配合小顶堆或候选集合。Caffeine 的 Window TinyLFU 就是典型例子：用 4-bit Count-Min Sketch 估计 key 的历史访问频率，配合小 LRU window 和周期性 reset，在新候选和旧 victim 之间做准入判断，从而同时利用 recency 和 frequency，抵抗顺序扫描和旧热点污染。时序场景里可以按分钟、小时维护多个 CMS，或者周期性衰减计数，实现 temporal frequency estimation。
