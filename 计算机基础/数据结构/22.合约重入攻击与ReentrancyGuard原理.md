# 22. 合约重入攻击与 ReentrancyGuard 原理

## 1. 问题背景

重入攻击是智能合约最经典的安全漏洞之一。2016 年 The DAO 事件导致 360 万 ETH 被盗，核心原因就是重入攻击。理解重入攻击原理和防护措施是智能合约开发者的必修课。

```text
┌─────────────────────────────────────────────────────────────┐
│                                                             │
│  重入攻击本质：                                            │
│                                                             │
│  合约 A                                            合约 B  │
│  ┌─────────────────┐                              ┌───────┐ │
│  │ withdraw()     │                              │       │ │
│  │ 1. 检查余额    │                              │       │ │
│  │ 2. 转账 ETH    │────── call ──────►           │       │ │
│  │ 3. 清零余额    │                              │       │ │
│  └─────────────────┘                              └───────┘ │
│       ▲                                                  │   │
│       │                                                  │   │
│       └── fallback() 调用 withdraw() ───────────────────┘   │
│                                                             │
│  问题：在第 3 步清零之前，攻击者多次调用 withdraw()         │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

---

## 2. 问题现象

| 现象 | 描述 |
|------|------|
| 余额检查失效 | 攻击者反复提取资金 |
| 资金被盗 | 合约 ETH 被全部抽走 |
| 状态不一致 | 内部记录与实际不符 |
| 合约冻结 | ETH 耗尽无法操作 |

## 4. 原因分析

### 4.1 重入攻击原理

```solidity
// 有漏洞的合约

contract VulnerableBank {
    mapping(address => uint256) public balances;
    
    // 有漏洞的 withdraw 函数
    function withdraw(uint256 amount) external {
        // 1. Checks: 检查余额
        require(balances[msg.sender] >= amount, "Insufficient balance");
        
        // 2. Effects: 更新状态（但这行在转账之后！）
        // 实际上这里的顺序有问题
        
        // 3. Interactions: 转账（调用外部合约）
        (bool success, ) = msg.sender.call{value: amount}("");
        require(success, "Transfer failed");
        
        // 状态更新（太晚了！）
        balances[msg.sender] -= amount;
    }
    
    function deposit() external payable {
        balances[msg.sender] += msg.value;
    }
}

// 攻击合约

contract Attacker {
    VulnerableBank public bank;
    address public owner;
    
    constructor(address _bank) {
        bank = VulnerableBank(_bank);
        owner = msg.sender;
    }
    
    // 存入一些 ETH
    function attack() external payable {
        require(msg.value >= 1 ether);
        bank.deposit{value: 1 ether}();
        bank.withdraw(1 ether);
    }
    
    // fallback 会被反复调用
    fallback() external payable {
        if (address(bank).balance >= 1 ether) {
            bank.withdraw(1 ether);
        }
    }
    
    // 提取被盗资金
    function withdraw() external {
        payable(owner).transfer(address(this).balance);
    }
}
```

### 4.2 攻击流程详解

```text
┌─────────────────────────────────────────────────────────────┐
│                                                             │
│  攻击时间线：                                               │
│                                                             │
│  T0: 攻击者部署 Attacker，存入 1 ETH                       │
│                                                             │
│  T1: Attacker 调用 withdraw(1 ETH)                         │
│                                                             │
│  T2: Bank 检查余额 1 ETH >= 1 ETH ✓                        │
│                                                             │
│  T3: Bank 调用 Attacker.call{value: 1 ETH}()               │
│                                                             │
│  T4: Attacker fallback 被触发，再次调用 withdraw(1 ETH)   │
│                                                             │
│  T5: Bank 再次检查余额（仍是 1 ETH，因为还没清零！）       │
│                                                             │
│  T6: 重复 T3-T5...直到 Bank 余额不足                      │
│                                                             │
│  结果：Bank 被抽空，攻击者获得远超其存款的资金              │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 4.3 重入类型

```text
┌─────────────────────────────────────────────────────────────┐
│                                                             │
│  重入类型：                                                 │
│                                                             │
│  1. 单函数重入                                             │
│     同一函数在未完成时被再次调用                            │
│     例子：withdraw() → withdraw()                          │
│                                                             │
│  2. 跨函数重入                                            │
│     从一个函数重入到另一个函数                             │
│     例子：withdraw() → transfer()                          │
│                                                             │
│  3. 跨合约重入                                            │
│     从一个合约重入到另一个合约                             │
│     例子：A.withdraw() → B.flashLoan()                     │
│                                                             │
│  4. 跨调用链重入                                          │
│     通过多层调用链进行重入                                 │
│     例子：A → B → C → A                                    │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

## 5. 解决方案

### 5.1 Checks-Effects-Interactions 模式

```solidity
// 修复：正确的顺序

contract SecureBank {
    mapping(address => uint256) public balances;
    
    function withdraw(uint256 amount) external {
        // 1. Checks：检查条件
        require(balances[msg.sender] >= amount, "Insufficient balance");
        
        // 2. Effects：更新状态（在转账之前！）
        balances[msg.sender] -= amount;
        
        // 3. Interactions：执行外部调用（在最后）
        (bool success, ) = msg.sender.call{value: amount}("");
        require(success, "Transfer failed");
    }
    
    function deposit() external payable {
        balances[msg.sender] += msg.value;
    }
}
```

### 5.2 ReentrancyGuard 原理

```solidity
// OpenZeppelin ReentrancyGuard

abstract contract ReentrancyGuard {
    // 非可重入状态：0 = 未进入，1 = 进入中
    uint256 private constant _NOT_ENTERED = 1;
    uint256 private constant _ENTERED = 2;
    
    // 关键状态变量
    uint256 private _status;
    
    constructor() {
        // 初始化为非重入状态
        _status = _NOT_ENTERED;
    }
    
    // 修饰符：防止重入
    modifier nonReentrant() {
        // 检查：确保未进入
        require(_status != _ENTERED, "ReentrancyGuard: reentrant call");
        
        // 设置状态为进入中
        _status = _ENTERED;
        
        try _execute() finally {
            // 无论成功与否，都重置状态
            _status = _NOT_ENTERED;
        }
    }
    
    // 实际执行（由子类实现）
    function _execute() internal virtual;
}

// 使用示例

contract SecureWithdraw is ReentrancyGuard {
    mapping(address => uint256) public balances;
    
    function withdraw(uint256 amount) external nonReentrant {
        // 1. Checks
        require(balances[msg.sender] >= amount);
        
        // 2. Effects
        balances[msg.sender] -= amount;
        
        // 3. Interactions
        (bool success, ) = msg.sender.call{value: amount}("");
        require(success);
    }
}
```

### 5.3 Pull Payment 模式

```solidity
// Pull Payment：让用户主动来取款

contract PullPayment {
    mapping(address => uint256) public payments;
    
    // 不直接转账，而是记录欠款
    function _asyncTransfer(address to, uint256 amount) internal {
        payments[to] += amount;
    }
    
    // 用户主动调用 withdraw 取款
    function withdraw() external {
        uint256 payment = payments[msg.sender];
        require(payment > 0, "No payment");
        
        payments[msg.sender] = 0;
        payable(msg.sender).transfer(payment);
    }
}

// 使用 Pull Payment 的安全合约

contract SecureVault is PullPayment {
    mapping(address => uint256) public balances;
    
    function deposit() external payable {
        balances[msg.sender] += msg.value;
    }
    
    // 使用 _asyncTransfer 而不是直接转账
    function withdraw(uint256 amount) external {
        require(balances[msg.sender] >= amount);
        balances[msg.sender] -= amount;
        
        // Pull Payment：记录欠款
        _asyncTransfer(msg.sender, amount);
    }
}
```

### 5.4 使用 OpenZeppelin 完整示例

```solidity
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.20;

import "@openzeppelin/contracts/security/ReentrancyGuard.sol";
import "@openzeppelin/contracts/security/PullPayment.sol";

contract SecureStaking is ReentrancyGuard, PullPayment {
    struct Stake {
        uint256 amount;
        uint256 startTime;
    }
    
    mapping(address => Stake) public stakes;
    uint256 public constant APY = 5; // 5%
    
    function stake() external payable nonReentrant {
        require(msg.value > 0, "Must stake positive amount");
        
        stakes[msg.sender].amount += msg.value;
        stakes[msg.sender].startTime = block.timestamp;
    }
    
    function unstake() external nonReentrant {
        Stake storage stake_ = stakes[msg.sender];
        require(stake_.amount > 0, "No stake");
        
        uint256 reward = calculateReward(msg.sender);
        uint256 total = stake_.amount + reward;
        
        // 清零状态
        delete stakes[msg.sender];
        
        // 使用 Pull Payment
        _asyncTransfer(msg.sender, total);
    }
    
    function calculateReward(address user) public view returns (uint256) {
        Stake memory stake_ = stakes[user];
        uint256 duration = block.timestamp - stake_.startTime;
        return (stake_.amount * APY * duration) / (365 days * 100);
    }
    
    // 用户需要主动调用 withdraw() 领取
}
```

## 6. 可选方案对比

| 方案 | 优点 | 缺点 | 适用场景 |
|------|------|------|----------|
| CEI 模式 | 简单直接 | 需注意所有代码路径 | 通用 |
| ReentrancyGuard | 强制保护 | 增加 gas 成本 | 高风险操作 |
| Pull Payment | 完全避免 | 用户需主动操作 | 退款场景 |
| 限定调用者 | 彻底解决 | 功能受限 | 已知合约 |

### 7.1 最佳实践

│                                                             │

### 7.2 完整检查清单

```text
✅ 所有涉及 msg.sender.call 的函数都要加 ReentrancyGuard
✅ 状态更新必须在外部调用之前
✅ 使用 transfer 而非 call（2300 gas 限制）
✅ 检查所有代码路径，包括失败回滚
✅ 考虑跨函数和跨合约重入
✅ 使用静态分析工具（Slither, Mythril）
```

        require(state >= amount);           // Checks
        state -= amount;                     // Effects

## 11. 总结

1. **重入攻击本质**：外部调用期间状态未更新，导致可重复提取
2. **CEI 模式**：Checks → Effects → Interactions，状态优先于外部调用
3. **ReentrancyGuard**：通过状态标记阻止重入，gas 换安全
4. **Pull Payment**：彻底避免重入，但用户体验不同
5. **最佳实践**：CEI + ReentrancyGuard + 自动化检测 + 代码审计
