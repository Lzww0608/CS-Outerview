# EVM 执行模型 SLOAD 与 SSTORE Gas 消耗分析

## 1. 问题背景

在以太坊虚拟机（EVM）中，SLOAD 和 SSTORE 是操作存储（Storage）的两个核心 opcode。它们的 Gas 消耗差异巨大，理解这一差异对于智能合约开发和 Gas 优化至关重要。

```text
┌─────────────────────────────────────────────────────────────┐
│                                                             │
│  EVM Storage 操作 Gas 消耗对比：                           │
│                                                             │
│  SLOAD（读取存储）：2100 Gas（cold）/100 Gas（warm）    │
│  SSTORE（写入存储）：20000 Gas（首次写入）               │
│                              /2900 Gas（修改）            │
│                              /900 Gas（删除）             │
│                                                             │
│  差异原因：SSTORE 需要持久化写入，成本远高于读取        │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

---

## 2. 问题现象

| 现象 | 描述 |
|------|------|
| Gas 消耗差异大 | SSTORE 比 SLOAD 贵约 10-100 倍 |
| 首次写入更贵 | 新 key 比修改现有 key 更贵 |
| 删除有退款 | SELFDESTRUCT 和 SSTORE 0 有 Gas 退款 |
| Cold vs Warm | 访问同一个 key 第二次更便宜 |

---

## 3. 影响范围

- 智能合约 Gas 优化
- 合约开发成本控制
- Layer 2 解决方案设计
- 存储密集型应用

## 4. 原因分析

### 4.1 EVM 存储层次结构

```text
┌─────────────────────────────────────────────────────────────┐
│                                                             │
│  EVM 存储层次：                                           │
│                                                             │
│  Stack（栈）                                             │
│      │ 读取：0 Gas                                        │
│      ▼                                                    │
│  Memory（内存）                                          │
│      │ 读取：~100 Gas（按字节收费）                      │
│      ▼                                                    │
│  Storage（存储）                                          │
│      │ 读取：2100/100 Gas                                │
│      ▼ 写入：20000/2900/900 Gas                          │
│  Persistent State（持久化状态）                           │
│                                                             │
│  每层都比上一层更贵，因为需要持久化到区块链状态        │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 4.2 Gas 消耗的底层原因

```text
┌─────────────────────────────────────────────────────────────┐
│                                                             │
│  SLOAD Gas 消耗原因：                                      │
│                                                             │
│  1. 状态树查找                                           │
│     • 需要在 Merkle Patricia Trie 中查找 key               │
│     • 需要从数据库读取 trie node                           │
│     • 需要验证 proof（如果从外部调用）                    │
│                                                             │
│  2. 访问成本                                             │
│     • Cold access：2100 Gas（首次访问）                  │
│     • Warm access：100 Gas（同一 transaction 内再次访问） │
│                                                             │
│  3. RLP 编解码                                           │
│     • Key 和 value 需要 RLP 编解码                        │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

```text
┌─────────────────────────────────────────────────────────────┐
│                                                             │
│  SSTORE Gas 消耗原因：                                     │
│                                                             │
│  1. 数据库写入成本                                         │
│     • 写入新 value 到 Storage Trie                        │
│     • 需要更新多个 trie nodes                             │
│     • 写入 LevelDB/RocksDB 等持久化存储                  │
│                                                             │
│  2. 状态更新传播                                         │
│     • 所有全节点需要同步新状态                            │
│     • 影响 State Root                                   │
│                                                             │
│  3. 存储碎片化控制                                       │
│     • 防止无限写入                                       │
│     • 反映真实的资源消耗                                  │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 4.3 SSTORE 不同场景的 Gas 消耗

```text
┌─────────────────────────────────────────────────────────────┐
│                                                             │
│  SSTORE Gas 消耗详解：                                    │
│                                                             │
│  Case 1: 首次写入 (0 → non-zero)                        │
│  • 消耗: 20000 Gas                                       │
│  • 原因: 在 trie 中创建新 node，并持久化                 │
│                                                             │
│  Case 2: 修改现有值 (non-zero → non-zero)              │
│  • 消耗: 2900 Gas                                       │
│  • 原因: 更新已有 node，但不需要创建新 node              │
│                                                             │
│  Case 3: 删除 (non-zero → 0)                           │
│  • 消耗: 900 Gas                                        │
│  • 退款: 15000 Gas (上限 20%)                           │
│  • 原因: 删除操作本身需要 Gas，但会退款以鼓励清理       │
│                                                             │
│  Case 4: 从 0 改回 0                                    │
│  • 消耗: 900 Gas                                        │
│  • 原因: 检测到无效操作                                  │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 4.4 Warm vs Cold Access

```text
┌─────────────────────────────────────────────────────────────┐
│                                                             │
│  EIP-2929 引入的 Warm/Cold 访问：                        │
│                                                             │
│  Cold Access（新访问）：                                   │
│  • 消耗: 2100 Gas (SLOAD) / 20000 Gas (SSTORE)         │
│  • 定义: 当前 transaction 内首次访问该 storage slot       │
│                                                             │
│  Warm Access（热访问）：                                   │
│  • 消耗: 100 Gas (SLOAD) / 100 Gas + 2900/20000 Gas   │
│  • 定义: 同一 transaction 内已访问过的 slot               │
│                                                             │
│  目的：                                                   │
│  • 避免 DoS 攻击                                        │
│  • 区分实际需要读取的开销 vs 重复访问的开销             │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

## 5. 解决方案

### 5.1 合约开发 Gas 优化

```solidity
// 优化方案 1：减少 SSTORE 操作

// ❌ 低效：每次调用都写入
contract BadExample {
    uint public counter;
    function increment() external {
        counter++;  // SSTORE: 20000 / 2900 Gas
    }
}

// ✅ 高效：批量更新
contract GoodExample {
    uint public counter;
    function increment(uint times) external {
        counter += times;  // 一次 SSTORE
    }
}
```

```solidity
// 优化方案 2：使用 events 代替 storage 存储

// ❌ 低效
contract BadLogger {
    LogEntry[] public logs;
    function addLog(string memory data) external {
        logs.push(LogEntry(block.timestamp, data));  // SSTORE
    }
}

// ✅ 高效：events 不消耗 storage Gas
contract GoodLogger {
    event NewLog(uint256 timestamp, string data);
    function addLog(string memory data) external {
        emit NewLog(block.timestamp, data);  // 几乎 0 Gas
    }
}
```

```solidity
// 优化方案 3：内存缓存 + 批量写入

contract CachedWriter {
    struct Cache {
        uint value;
        bool isDirty;
    }
    mapping(address => Cache) public cache;
    
    function setValue(address user, uint value) external {
        cache[user] = Cache(value, true);  // 只写 memory
    }
    
    function flush() external {
        for (address user : getAllUsers()) {
            if (cache[user].isDirty) {
                storageMap[user] = cache[user].value;  // 批量 SSTORE
                cache[user].isDirty = false;
            }
        }
    }
}
```

### 5.2 Struct Packing 优化

```solidity
// 优化方案 4：Struct Packing 减少存储大小

// ❌ 低效：每个变量独立 slot
contract Inefficient {
    uint public a;  // slot 0: 32 bytes
    uint public b;  // slot 1: 32 bytes
    uint public c;  // slot 2: 32 bytes
}

// ✅ 高效：紧凑打包
contract Efficient {
    uint128 public a;  // slot 0: 16 bytes
    uint128 public b;  // slot 0: 16 bytes
    uint64 public c;   // slot 1: 8 bytes
    // 总共只占用 2 个 slots
}
```

### 5.3 状态预加载

```solidity
// 优化方案 5：在一次调用中多次使用同一 storage 值

// ❌ 低效：多次读取
contract MultipleReads {
    mapping(address => User) users;
    function process(address user) external {
        uint balance = users[user].balance;  // SLOAD
        uint limit = users[user].limit;      // SLOAD
        if (balance < limit) {
            // ...
        }
    }
}

// ✅ 高效：减少 storage 访问次数
contract SingleRead {
    function process(address user) external {
        User memory u = users[user];  // 一次 SLOAD
        if (u.balance < u.limit) {
            // ...
        }
    }
}
```

## 6. 可选方案对比

| 优化方案 | 效果 | 适用场景 | 复杂度 |
|----------|------|----------|--------|
| 减少 SSTORE | 高 | 频繁写入 | 中 |
| Events 替代 | 高 | 日志记录 | 低 |
| 批量写入 | 高 | 批量操作 | 中 |
| Struct Packing | 中 | 多小变量 | 低 |
| Memory 缓存 | 中 | 临时计算 | 低 |

## 11. 总结

1. **Gas 差异根源**：SSTORE 需要持久化写入数据库，SLOAD 只需读取
2. **SSTORE 三种场景**：首次写入（20000）> 修改（2900）> 删除（900，有退款）
3. **Cold vs Warm**：EIP-2929 引入，首次访问贵，后续访问便宜
4. **优化核心**：减少 SSTORE、使用 events、Struct Packing、Memory 缓存
5. **工程实践**：先测基准、识别热点、逐项优化、验证功能不变
