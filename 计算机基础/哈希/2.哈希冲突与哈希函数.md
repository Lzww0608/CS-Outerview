# 哈希冲突与哈希函数

哈希表通过哈希函数把 key 映射到数组下标。理想情况下，插入、查找和删除接近 `O(1)`；但如果多个 key 映射到同一个位置，就会产生哈希冲突，性能会退化。

## 哈希函数要满足什么

好的哈希函数通常追求：

1. **确定性**：同一个 key 每次得到同一个 hash。
2. **均匀性**：不同 key 尽量均匀落到桶中，减少冲突。
3. **雪崩效应**：输入微小变化会让输出大幅变化。
4. **速度快**：哈希表是高频路径，函数不能过重。
5. **低碰撞概率**：尤其是去重、签名、分片等场景。

不同场景选择不同函数：

1. 内存哈希表常用 MurmurHash、CityHash、xxHash、SipHash 等非加密哈希。
2. 安全场景使用 SHA-256、BLAKE3 等密码学哈希。
3. 分布式分片常用一致性哈希、Rendezvous Hash、CRC32/CRC64 等。

## 常见冲突解决方式

## HashMap 的核心原理

HashMap 可以理解为“数组 + 哈希函数 + 冲突处理 + 扩容策略”。基本流程是：

1. 对 key 计算 hash 值。
2. 根据桶数量把 hash 映射到数组下标，例如 `index = hash & (capacity - 1)` 或 `hash % capacity`。
3. 在对应桶中查找 key；如果不存在则插入，存在则更新 value。
4. 当元素数量过多、装载因子超过阈值时扩容并 rehash。

一次查询平均接近 `O(1)`，前提是哈希函数分布较均匀、装载因子合理、冲突链不长。最坏情况下，如果大量 key 落到同一个桶，链地址法可能退化到 `O(n)`；Java 8 HashMap 会在链表足够长且表容量足够大时树化为红黑树，把极端查询降低到 `O(log n)`。

工程上要关注：

1. **扩容成本**：扩容需要搬迁元素，延迟敏感场景可以预估容量并提前 `reserve`，或采用渐进式 rehash。
2. **等价关系**：hash 相同不代表 key 相等，最终必须用 `==` 或 equals 判断。
3. **线程安全**：普通 HashMap/`unordered_map` 不是并发安全容器，多线程读写要加锁、分片锁或使用并发哈希表。
4. **攻击面**：外部输入作为 key 时，恶意构造冲突可能拖垮服务，Web 框架常用随机种子 hash 或 SipHash。

### 文件中关键字出现次数用什么数据结构

如果要统计一个文件中关键字出现次数，最直接的数据结构是哈希表：

```cpp
std::unordered_map<std::string, std::size_t> count;
```

处理流程：

1. 流式读取文件，避免一次性把大文件全部读入内存。
2. 对每个 token 做归一化，例如大小写、标点、编码和分词规则。
3. 用 `unordered_map` 把关键字映射到出现次数。
4. 如果只统计给定关键字集合，先把目标关键字放进 `unordered_set`，读取时只统计命中的词。

示例：

```cpp
#include <cstddef>
#include <fstream>
#include <string>
#include <unordered_map>
#include <unordered_set>

std::unordered_map<std::string, std::size_t>
countKeywords(const std::string& path,
              const std::unordered_set<std::string>& keywords) {
    std::ifstream in(path);
    std::unordered_map<std::string, std::size_t> cnt;
    std::string word;

    while (in >> word) {
        if (keywords.empty() || keywords.find(word) != keywords.end()) {
            ++cnt[word];
        }
    }
    return cnt;
}
```

真实场景要看规模和输出要求：

1. 需要按字典序输出，用 `map` 或统计后排序。
2. 关键字有前缀匹配、敏感词匹配需求，用 Trie 或 AC 自动机。
3. 文件远大于内存，用哈希分桶切成多个小文件，再分别统计并归并；分布式场景可以用 MapReduce。
4. 只判断是否出现，用 `unordered_set` 或 Bloom Filter；要精确计数仍需要计数数组、哈希表或外部聚合。

### 1. 链地址法

每个桶挂一个链表、红黑树或小数组，冲突元素放到同一个桶里。

优点：

1. 删除简单。
2. 装载因子可以大于 1。
3. 扩容和搬迁逻辑相对直观。

缺点：

1. 指针跳转多，缓存局部性较差。
2. 冲突严重时链表退化为 `O(n)`。
3. 需要额外节点内存。

Java 8 的 `HashMap` 在链表过长且容量足够时会树化，用红黑树降低极端冲突下的查询成本。

### 2. 开放寻址法

所有元素都放在数组里。冲突时按探测序列寻找下一个空位。

常见探测方式：

1. **线性探测**：`h, h+1, h+2...`，缓存友好，但容易形成主聚集。
2. **二次探测**：`h+1^2, h+2^2...`，缓解主聚集。
3. **双重哈希**：用第二个哈希函数决定步长，分布更好。

优点：

1. 内存连续，缓存友好。
2. 不需要链表节点。

缺点：

1. 装载因子不能太高，否则探测次数激增。
2. 删除需要 tombstone 标记，否则会打断探测链。
3. 扩容时通常要整体 rehash。

### 3. 再哈希和扩容

当装载因子超过阈值时，哈希表会扩容并重新分布元素。扩容可以降低冲突，但会带来瞬时成本。工程上常见优化：

1. 渐进式 rehash，例如 Redis 字典。
2. 预估容量并提前 `reserve`。
3. 分段扩容，降低单次停顿。

rehash 时要注意资源处理。对于 C++ `unordered_map`，节点式实现通常会重新挂接节点到新桶数组，元素对象本身不一定逐个重新构造，但迭代器通常会失效；对于开放寻址哈希表，元素往往需要搬迁到新数组，移动构造、异常安全和 tombstone 清理都要一起考虑。业务对象如果持有文件、socket、锁等资源，应使用 RAII 和正确的移动/拷贝语义，不要依赖按字节复制。

## 桶数量为什么常选质数

桶下标通常来自：

```text
index = hash % bucket_count
```

如果 `bucket_count` 是合数，且 key 的 hash 值存在固定步长或低位分布很差，就容易只落在一部分桶里。例如所有 hash 都是偶数，而桶数也是偶数，则一半桶永远用不上。选择质数可以降低这类周期性模式和桶数量产生公因子的概率，让取模后的分布更稳。

但这不是唯一方案。很多现代哈希表会把桶数设为 2 的幂，然后使用：

```text
index = hash & (bucket_count - 1)
```

这样速度更快，但它强依赖 hash 函数的低位质量。工程中常见做法是：

1. **质数桶 + 取模**：对低质量 hash 更宽容，代价是取模稍慢；一些 `libstdc++` 版本的 `unordered_map` 使用过 prime rehash policy。
2. **2 的幂桶 + 位运算**：下标计算快，适合高质量 hash 或额外做扰动混合；很多高性能哈希表采用这种方式。
3. **外部接口不要依赖桶数常数**：C++ 标准不规定 `unordered_map` 的桶数量序列，不同标准库实现会不同。

面试回答时不要绝对化为“桶数必须是质数”。更准确的说法是：质数能缓解取模分布问题；如果使用 2 的幂桶，就必须保证 hash 的低位足够随机，或者在取下标前做 hash mixing。

## 装载因子

装载因子：

```text
load_factor = 元素个数 / 桶数量
```

装载因子越高，空间利用率越高，但冲突越多。不同实现的阈值不同，例如 C++ `unordered_map` 可以通过 `max_load_factor` 和 `reserve` 控制。

## 易错点

1. 哈希冲突不可完全避免，只能降低概率和控制退化成本。
2. 密码学哈希不一定适合哈希表，安全性高但可能太慢。
3. 取模桶数如果选择不当，可能放大低质量 hash 的分布问题。
4. 哈希表平均 `O(1)` 不等于最坏 `O(1)`。
5. 自定义 key 用 `unordered_map` 时，`hash` 和 `operator==` 必须语义一致。

## 真实场景

1. `unordered_map` 存大量元素前先 `reserve`，避免多次 rehash。
2. Redis 字典用链地址法和渐进式 rehash，避免一次性扩容阻塞太久。
3. Web 框架处理外部输入 key 时，可能使用带随机种子的 SipHash 防止哈希碰撞攻击。
4. 分布式缓存用一致性哈希或 Rendezvous Hash 减少节点扩缩容时的数据迁移。

## 面试回答模板

哈希冲突是多个 key 被哈希到同一个桶。常见解决方法有链地址法、开放寻址法和扩容 rehash。链地址法删除简单、装载因子可以较高，但指针跳转影响缓存；开放寻址法内存连续、缓存友好，但装载因子太高会导致探测次数激增，删除还要 tombstone。好的哈希函数要确定、均匀、快速，并具备较好的雪崩效应。真实项目里还要控制装载因子、提前 reserve、选择合适的哈希函数，并防止恶意冲突攻击。
