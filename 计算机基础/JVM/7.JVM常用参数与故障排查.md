# 7. JVM 常用参数与故障排查

JVM 参数调优不是背一组固定模板，而是围绕内存、GC、线程、日志和诊断能力建立可观测、可验证的运行环境。面试里问“JVM 有哪些参数可以调、OOM 或 CPU 100% 怎么解决”，建议先定位现象，再结合参数和工具处理。

## 1. 常用参数分类

### 堆内存

```bash
-Xms2g
-Xmx2g
```

`-Xms` 是初始堆大小，`-Xmx` 是最大堆大小。线上服务通常把两者设成相同值，避免运行时堆扩缩容带来的抖动。堆不是越大越好，堆越大可能降低 Full GC 频率，但单次停顿和故障恢复成本也会上升。

### 线程栈

```bash
-Xss512k
```

`-Xss` 控制每个 Java 线程栈大小。栈大可以容纳更深调用，但会降低同一机器可创建线程数量；栈小可能更容易 `StackOverflowError`。无法创建线程时，要同时看 `-Xss`、线程池、容器内存、系统 `ulimit` 和 pids 限制。

### 元空间和直接内存

```bash
-XX:MaxMetaspaceSize=512m
-XX:MaxDirectMemorySize=1g
```

元空间保存类元数据，动态代理、热部署、脚本引擎容易推高 Metaspace。直接内存常见于 Netty、NIO、文件传输和堆外缓冲区，Java 堆不高但 RSS 高时要重点排查。

### GC 收集器和停顿目标

```bash
-XX:+UseG1GC
-XX:MaxGCPauseMillis=200
-XX:InitiatingHeapOccupancyPercent=45
```

`MaxGCPauseMillis` 是目标而不是承诺。G1 会尽量按目标选择回收集合，但如果分配速度太快、Humongous 对象太多或回收收益不足，仍可能出现长停顿或 Full GC。

### GC 日志和诊断

JDK 9+：

```bash
-Xlog:gc*:file=gc.log:time,level,tags
-XX:+HeapDumpOnOutOfMemoryError
-XX:HeapDumpPath=/data/dump
-XX:NativeMemoryTracking=summary
```

JDK 8 常见写法：

```bash
-XX:+PrintGCDetails
-XX:+PrintGCDateStamps
-Xloggc:/data/logs/gc.log
```

这些参数的价值是保留证据：OOM 时有 dump，GC 异常时有日志，native 内存异常时能用 NMT 看分类。

## 2. 内存溢出怎么排查

先判断是哪类内存出问题：

1. **Java heap space**：堆对象过多或一次性加载过大。
2. **GC overhead limit exceeded**：频繁 GC 但回收很少。
3. **Metaspace**：动态类或类加载器泄漏。
4. **Direct buffer memory**：堆外内存不足。
5. **unable to create native thread**：线程过多、栈过大或系统限制不足。

排查流程：

```text
确认 OOM 类型
-> 查看 GC 日志和监控曲线
-> 抓 heap dump / thread dump / NMT
-> 用 MAT、JProfiler、JFR、Arthas 分析
-> 修复对象生命周期、缓存上限、批处理大小或线程池配置
-> 回归压测并观察 P95/P99、GC 次数和内存水位
```

不要一上来只调大 `-Xmx`。如果是缓存无上限、ThreadLocal 未清理、一次性导出全量数据，调大堆只会延后故障。

## 3. CPU 100% 怎么排查

Java 进程 CPU 100% 时，先定位线程，再定位代码栈：

```bash
top -H -p <pid>
jstack <pid> > thread.txt
printf "%x\n" <tid>
```

把 `top -H` 中的线程 ID 转成 16 进制，在 `jstack` 里搜索对应 `nid`。常见原因：

1. 死循环、递归或忙等。
2. 正则回溯、JSON 序列化、加解密、压缩等 CPU 密集逻辑。
3. 大量 GC，用户线程看似 CPU 高但实际被 GC 拖慢。
4. 锁竞争导致频繁自旋或上下文切换。
5. 日志风暴、异常风暴、重试风暴。
6. MySQL 慢查询、MQ 重复重试导致应用线程大量消耗 CPU。

进一步工具：

1. **Arthas**：`thread -n 5`、`dashboard`、`trace`、`watch`。
2. **async-profiler**：生成 CPU 火焰图，定位热点方法。
3. **JFR**：低开销记录线程、锁、GC、分配和方法采样。
4. **GC 日志**：判断 CPU 是否被频繁 GC 消耗。

## 4. 参数调优的注意事项

1. 参数修改必须有指标基线和验证结果，不能凭经验套模板。
2. 容器环境要确认 JVM 是否识别 cgroup 限制，避免堆加直接内存超过容器 limit。
3. 堆、直接内存、线程栈、Metaspace、Code Cache 和 native 库都占进程 RSS。
4. 低延迟服务要同时看平均延迟和 P99/P999，不能只看吞吐。
5. GC 调优应先减少对象分配和大对象，再调收集器参数。

## 5. 面试回答模板

JVM 常调的参数包括堆 `-Xms/-Xmx`、线程栈 `-Xss`、元空间 `MaxMetaspaceSize`、直接内存 `MaxDirectMemorySize`、GC 收集器和停顿目标、GC 日志、OOM dump、NMT 等。OOM 时我会先区分堆、元空间、直接内存还是线程创建失败，再用 GC 日志、heap dump、MAT、JFR、Arthas、NMT 定位；CPU 100% 时用 `top -H` 找热点线程，把 tid 转成 16 进制后对照 `jstack`，再用 Arthas 或火焰图确认是业务死循环、序列化、锁竞争、GC 还是重试风暴。参数调优必须结合监控和压测验证，不能只靠调大内存解决问题。
