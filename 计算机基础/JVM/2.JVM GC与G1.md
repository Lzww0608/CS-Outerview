# 2. JVM GC 与 G1

JVM GC 负责自动发现不再被引用的对象并回收堆内存。面试里问“介绍 GC 方法、G1 原理、何时发生 GC、大对象放哪里”，要把算法、收集器和触发条件区分开。

## 1. 常见 GC 算法

| 算法 | 定义 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 标记-清除 | 标记存活对象，再清理未标记对象 | 不移动对象，实现直观 | 产生碎片 |
| 标记-整理 | 标记后把存活对象向一端压缩 | 解决碎片 | 移动对象，停顿更长 |
| 复制算法 | 把存活对象复制到另一块空间 | 回收快、无碎片 | 需要额外空间，存活多时成本高 |
| 分代回收 | 新生代和老年代用不同策略 | 利用多数对象朝生夕死 | 需要跨代引用维护 |

JVM 收集器是这些算法和工程机制的组合，例如 Serial、Parallel、CMS、G1、ZGC、Shenandoah。

## 1.1 标记-复制算法详解

### 算法原理

标记-复制算法把内存分成两块，每次只使用一块。当这块内存满了，就把存活的对象复制到另一块上，然后一次性清理整块内存。

```text
初始状态：
┌─────────────────────┬─────────────────────┐
│     From Space      │      To Space       │
│   (使用中)          │    (空闲)           │
└─────────────────────┴─────────────────────┘

GC 时：
1. 标记存活对象：A, B, C
2. 复制存活对象到 To Space
3. 一次性清理 From Space

┌─────────────────────┬─────────────────────┐
│     From Space       │     To Space        │
│   (清空)             │  (A -> B -> C)      │
└─────────────────────┴─────────────────────┘
```

### 优缺点分析

**优点**：
1. **回收效率高**：不需要遍历全量对象，只需处理存活对象，且存活对象是少量
2. **无内存碎片**：对象移动后连续存放，分配只需移动指针
3. **分配简单**：空闲区域是连续的，只需维护一个指针，分配复杂度 O(1)

**缺点**：
1. **空间浪费**：可用内存减半，对大堆不友好
2. **存活对象多时成本高**：如果存活对象多，复制开销大
3. **不适合老年代**：老年代对象存活率高，复制成本太高

### 为什么适合新生代

标记-复制算法最适合"对象大量朝生夕死"的场景，而新生代正是这样的场景：

1. **对象生命周期短**：大量对象创建后很快变成垃圾
2. **存活对象少**：每次 GC 需要复制的对象通常很少（默认 10%）
3. **避免碎片**：新对象分配频繁，碎片会影响分配效率

### 8:1:1 比例详解

JVM 新生代采用 `Eden : Survivor0 : Survivor1 = 8 : 1 : 1` 的比例设计：

```text
┌─────────────────────────────────────────────────────┐
│                    新生代 (Young)                   │
├─────────────────────────────────────────────────────┤
│  Eden 区 (80%)  │  Survivor 0 (10%) │ Survivor 1 (10%) │
└─────────────────────────────────────────────────────┘
```

**为什么是这个比例**：
1. **空间效率**：如果只有一个 Survivor 区，GC 时需要预留 50% 空间给存活对象，实际可用只有 50%
2. **8:1:1 只需 10% 预留**：Eden 区对象复制到 Survivor，Survivor 空间足够容纳少量存活对象
3. **实际可用空间**：`Eden + 1个Survivor = 90%` 的新生代空间，而非 50%

**工作流程**：
```text
1. 新对象在 Eden 区分配
2. Eden 区满后触发 Minor GC
3. 存活对象复制到 Survivor 0（From 区）
4. 年龄计数器 +1

5. 下次 Minor GC：
   - Eden + Survivor 0 存活对象复制到 Survivor 1（To 区）
   - 年龄 +1
   - 交换 Survivor 0 和 Survivor 1 的角色

6. 对象年龄达到阈值（默认 15，-XX:MaxTenuringThreshold）
   - 晋升到老年代
```

**年龄阈值为什么是 15**：
1. 对象头中的年龄字段只有 4 位，最大表示 15
2. 15 已经足够大多数对象在新生代被回收
3. 如果需要更大阈值，可以调整，但通常不建议

**动态年龄判定**：
JVM 还会根据实际情况动态调整晋升阈值：如果 Survivor 空间中相同年龄所有对象大小之和超过 Survivor 空间的 50%，则年龄 >= 该年龄的对象都会提前进入老年代。

**配置参数**：
```bash
# 新生代比例配置（Parallel Scavenge）
-XX:NewRatio=2  # 新生代:老年代 = 1:2

# 显式配置 Survivor 比例
-XX:SurvivorRatio=8  # Eden:Survivor = 8:1

# 最大晋升阈值
-XX:MaxTenuringThreshold=15
```

### 标记-复制 vs 标记-整理

| 对比项 | 标记-复制 | 标记-整理 |
| --- | --- | --- |
| 内存利用率 | 50%（需要一块空闲区） | 100% |
| 碎片 | 无 | 有，需整理 |
| 移动对象 | 是 | 是 |
| 适用区域 | 新生代 | 老年代 |
| GC 停顿 | 短（只需复制存活对象） | 长（需整理所有对象） |
| 实现复杂度 | 简单 | 复杂 |

## 1.2 标记-清除算法详解

### 算法原理

标记-清除算法分两个阶段：
1. **标记阶段**：从 GC Roots 出发，标记所有存活对象
2. **清除阶段**：遍历整个堆，清除所有未标记的对象

```text
标记前：        标记后：          清除后：
┌───┬───┐     ┌─X─┬───┐       ┌───┬───┐
│ A │ B │     │ A │ B │       │ A │   │
├───┼───┤     ├───┼───┤       ├───┼───┤
│ C │ D │     │ C │ X │       │ C │   │
├───┼───┤     ├───┼───┤       ├───┼───┤
│ E │ F │     │ X │ F │       │   │ F │
└───┴───┘     └───┴───┘       └───┴───┘
（X = 已标记存活对象）
```

### 优缺点

**优点**：
1. **不需要额外空间**：和复制算法不同，不需要预留一半空间
2. **适合老年代**：老年代存活对象多，复制开销大，标记-清除更合适

**缺点**：
1. **产生内存碎片**：清除后内存不连续
2. **效率不稳定**：存活对象多时，标记和清除都要遍历全堆
3. **分配效率低**：需要用空闲链表等复杂分配策略

### 空间分配策略

清除后产生的碎片需要用空闲链表管理：
```java
// 分配时需要遍历空闲链表找到合适大小的块
if (freeBlock.size >= requiredSize) {
    allocate from freeBlock;
}
```

这比复制算法的指针碰撞分配慢很多。

## 1.3 标记-整理算法详解

### 算法原理

标记-整理是标记-清除的改进版本，在清除前增加了一步整理操作：
1. **标记阶段**：和标记-清除相同
2. **整理阶段**：让存活对象向一端移动
3. **清除阶段**：清理边界以外的区域

```text
整理前：        整理后：          清除后：
┌───┬───┐     ┌───┬───┐       ┌───┬───┐
│ A │ B │     │ A │ B │       │ A │ B │
├───┼───┤     ├───┼───┤       ├───┼───┤
│ C │ D │     │ C │ F │       │ C │ F │
├───┼───┤     ├───┼───┤       ├───┼───┤
│ E │ F │     │ E │   │       │   │   │
└───┴───┘     └───┴───┘       └───┴───┘
（移动所有存活对象到一端）
```

### 优缺点

**优点**：
1. **无内存碎片**：整理后内存连续
2. **分配效率高**：和复制算法一样，可用指针碰撞分配

**缺点**：
1. **移动成本高**：所有存活对象都要移动
2. **GC 停顿长**：需要遍历和移动所有存活对象
3. **实现复杂**：需要处理引用更新

### 与标记-复制的对比

| 场景 | 标记-复制 | 标记-整理 |
| --- | --- | --- |
| 新生代（存活少） | 优 | 差（移动成本不必要） |
| 老年代（存活多） | 差（复制成本高） | 优（无需复制，只需要移动） |
| 内存利用率 | 50% | 100% |
| 碎片 | 无 | 无 |

## 2. G1 的核心原理

G1（Garbage First）把堆切成许多大小相同的 Region，不再要求新生代和老年代是连续大块内存。每个 Region 可以在某个阶段扮演 Eden、Survivor、Old 或 Humongous。

核心机制：

1. **Region 化**：把大堆拆成小块，回收时可以选择一部分 Region。
2. **Remembered Set**：记录其他 Region 指向当前 Region 的引用，避免扫描全堆。
3. **SATB 并发标记**：以标记开始时的对象图快照为基础，配合写屏障记录旧引用。
4. **Evacuation 复制转移**：把选中 Region 的存活对象复制到新 Region，旧 Region 整体释放。
5. **Garbage First**：优先回收垃圾比例高、收益大的 Region，以满足停顿时间目标。

## 3. G1 的优势

1. **停顿可预测**：通过 `-XX:MaxGCPauseMillis` 给出停顿目标，G1 按收益选择回收集合。
2. **适合大堆**：Region 化后不用每次都处理整个老年代。
3. **并发标记**：大部分标记工作和用户线程并发执行。
4. **整理内存**：Evacuation 复制存活对象，能缓解碎片。
5. **混合回收**：Young GC 后可以逐步回收部分老年代 Region。

注意：G1 不是“绝不 Full GC”。如果 Evacuation 失败、Humongous 对象过多或老年代增长过快，仍可能退化到 Full GC。

## 4. 何时会发生 GC

常见触发条件：

1. **Young GC**：Eden 空间不足，新对象无法继续分配。
2. **Mixed GC**：并发标记完成后，G1 发现部分老年代 Region 回收收益高，会在后续停顿中混合回收。
3. **Concurrent Mark**：老年代占用达到 IHOP 阈值，触发并发标记周期。
4. **Full GC**：元空间不足、晋升失败、Evacuation 失败、堆空间严重不足等兜底场景。
5. **System.gc()**：显式请求，是否真的执行取决于 JVM 参数和收集器。

## 5. 年轻代放不下大对象怎么办

传统分代收集器里，大对象如果 Eden 放不下，可能直接进入老年代，或者触发 Young GC 后仍放不下再走老年代分配。这是为了避免大对象在 Survivor 区来回复制。

G1 里有 Humongous 对象概念：如果对象大小超过一个 Region 的一半，就会被分配到一个或多个连续的 Humongous Region。Humongous Region 逻辑上归老年代管理，通常在并发标记后的清理阶段回收。

风险：

1. 大对象需要连续 Region，容易造成空间碎片。
2. 短命大对象会增加老年代压力。
3. Humongous 对象过多可能提前触发并发标记甚至 Full GC。

优化思路：

1. 避免一次性构造超大数组或字符串，改为分块处理、流式处理。
2. 调整 Region 大小，让对象不轻易落入 Humongous，但不能盲目调大。
3. 控制缓存对象大小，避免把大 JSON、大文件内容直接放堆内存。
4. 通过 GC 日志观察 `Humongous regions`、晋升失败、Full GC 原因。

## 6. 面试回答模板

GC 算法常见有标记-清除、标记-整理、复制算法和分代回收。G1 是 Region 化的分代收集器，把堆切成很多 Region，通过 Remembered Set 维护跨 Region 引用，用 SATB 做并发标记，再选择垃圾收益高的 Region 做 Evacuation 复制回收。它的优势是适合大堆、停顿目标更可控、能整理碎片并做 Mixed GC。GC 通常在 Eden 不足、老年代占用达到阈值、元空间不足、晋升失败或显式 `System.gc()` 时发生。大对象在传统分代里可能直接进老年代；G1 中超过半个 Region 的对象会进入 Humongous Region，过多时容易导致碎片和 Full GC。
