“1位计数器”（1-bit Reference Counting）是引用计数法（Reference Counting, RC）的一种**极端优化**形式，通常也被称为**“粘滞引用计数”（Sticky Reference Counts）**的一个特例。

它的核心思想是：**我们不记录对象到底有多少个引用，只记录它是“被独占的”还是“被共享的”。**

为了理解它，我们需要先看标准引用计数的问题，再看 1 位计数器是如何解决（以及妥协）的。

------

### 1. 为什么要搞“1位”？（背景）

在标准的引用计数法中，每个对象头里都有一个整型计数器（比如 32 位或 64 位）。这带来了两个问题：

1. **空间浪费**：每个对象都要多占几个字节。
2. **性能开销**：每次指针复制或销毁，都要更新计数器，如果是多线程环境，还需要原子操作（Atomic），非常慢。

研究发现，在大多数程序中，**绝大部分对象的引用计数都是 1**（即只有一个变量指向它，它是独享的）。

于是科学家想：既然大部分时候都是 1，那我们干脆只用 **1 个 bit** 来存状态，能不能行？

### 2. 1位计数器的核心逻辑

这个 bit 不代表数字 0 或 1，而是代表两种**状态**：

- **状态 0 (UNIQUE/Exlusive)**：表示引用计数 **等于 1**。
  - 含义：当前只有唯一一个指针指向这个对象。
- **状态 1 (SHARED/Sticky)**：表示引用计数 **大于 1**。
  - 含义：这个对象被多个指针共享。

由于 1 个 bit 最多只能表示到这里，一旦状态变为 1（共享），计数器就“溢出”或者是“粘滞”住了，无论以后再增加多少引用，它都保持为 1。

### 3. 工作流程详解

让我们看看在这个系统下，对象的生命周期是怎样的：

#### A. 分配（Allocation）

当你 `new` 一个对象时，只有一个指针指向它。

- **动作**：将 bit 设为 `0` (UNIQUE)。 

#### B. 复制引用（Copying）

当你把一个对象赋值给另一个变量（`b = a`），导致引用增加时：

- **如果是 UNIQUE (0)**：说明它原本是独享的，现在变成两个引用了。
  - **动作**：将 bit 更新为 `1` (SHARED)。
- **如果是 SHARED (1)**：说明它已经是共享的了（引用数 > 1）。
  - **动作**：**什么都不做**。bit 保持为 `1`。这里省去了昂贵的原子加法操作。

#### C. 删除引用（Deletion）

当一个引用离开作用域或被置空时：

- **如果是 UNIQUE (0)**：说明这是指向该对象的**唯一**一根线。既然这根线断了，对象就没人要了。
  - **动作**：**立即回收对象**（Free）。
- **如果是 SHARED (1)**：问题来了。因为计数器“卡”在 1，我们不知道它到底有 2 个、3 个还是 100 个引用。删掉一个引用后，我们不知道它是不是变成了 0，也不知道是不是变回了 1。
  - **动作**：**什么都不做**。哪怕此时它真的变成了垃圾，我们也暂时不回收它。

### 4. 那么，那些 SHARED 的垃圾怎么办？

你肯定发现了漏洞：**状态为 SHARED (1) 的对象，即使所有引用都断了，也不会被立即回收。** 这会导致内存泄漏。

所以，1位计数器法通常**不能独立工作**，它必须配合一个**备份的垃圾回收器（Backup Tracing GC）**，比如标记-清除（Mark-Sweep）算法。

**完整的混合回收策略如下：**

1. **主要阶段**：程序运行时，主要依靠 1 位计数器。
   - 如果是 `UNIQUE` 对象的销毁，**秒级回收**，速度极快，不需要停顿。
   - 如果是 `SHARED` 对象，暂时不管，留给堆里。
2. **兜底阶段**：当内存不足时，启动**标记-清除 GC**。
   - 这个 GC 会扫描整个堆，重新标记所有活着的对象。
   - 它不仅能回收那些“假装 SHARED 其实已经是垃圾”的对象，还能顺便处理**循环引用**（Reference Counting 的另一个死穴）。
   - 同时，GC 还可以把那些曾经是 `SHARED` 但现在只剩一个引用的对象，把它们的 bit 重置回 `UNIQUE`。

### 5. 总结

1位计数器法（1-bit Reference Counting）是一种**“乐观”的内存管理策略**。

- **它的赌注**：赌大部分对象都是独享的（Unique）。对于这部分对象，它有着极高的回收效率和极低的空间开销。
- **它的代价**：对于共享对象（Shared），它放弃了精确计数的权利，转而依赖一个周期性运行的、较重的 GC 来进行清理。

| **特性**         | **标准引用计数** | **1位计数器 (Sticky RC)**     |
| ---------------- | ---------------- | ----------------------------- |
| **计数器大小**   | 32/64 bit        | 1 bit                         |
| **独享对象回收** | 立即             | **立即 (且更快)**             |
| **共享对象回收** | 引用归零时立即   | **延迟 (需等待兜底 GC)**      |
| **循环引用**     | 无法处理         | **靠兜底 GC 处理**            |
| **原子操作开销** | 高 (频繁修改)    | **低 (只在 0->1 变化时修改)** |

这种技术在一些对**实时性要求高**、但又不想引入全量引用计数开销的场景（或者特定的函数式语言实现中）非常有价值。
