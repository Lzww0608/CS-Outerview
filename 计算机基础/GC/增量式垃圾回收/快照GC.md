这个术语通常指的是**基于“快照”语义的并发标记算法**。
最著名的实现是 **SATB (Snapshot-At-The-Beginning)**，它是 **G1 GC** 的核心算法之一。
另一个相关的概念是 **Yuasa's Algorithm**（Yuasa 在 1990 年提出的实时 GC 算法），它奠定了 SATB 的理论基础。

**核心思想**：

*   **并发标记的难题**：GC 正在标记，用户线程改了引用。
    *   比如：A -> B。GC 扫描了 A，认为 A 是黑的，B 是灰的。
    *   用户线程执行：`A.ptr = null;` `C.ptr = B;`（C 是黑的）。
    *   结果：B 失去了 A 的引用，但获得了 C 的引用。
    *   如果 GC 不知道 C 引用了 B（因为 C 已经扫过了），B 就会被误回收。
*   **快照（Snapshot）的思路**：
    *   GC 说：“我不关心你现在怎么改，我只关心**GC 开始那一刻**堆是什么样子的。”
    *   在 GC 开始的一瞬间，逻辑上给堆拍了一张照片（快照）。
    *   **原则**：**在快照时刻是活的对象，全都要标记为活的。** 哪怕它在 GC 过程中被用户线程删掉了（变成浮动垃圾），也先留着，下次再收。
    *   **实现**：利用**写屏障（Write Barrier）**。
    *   当用户线程执行 `A.ptr = B` （覆盖引用）时，即 `A.ptr` 原本指向 `OldValue`，现在要改成 `NewValue`。
    *   SATB 的写屏障会把 **`OldValue`** 记录下来，扔进一个队列里。
    *   GC 线程会去处理这个队列，把 `OldValue` 标记为活的。
    *   **逻辑**：既然 `OldValue` 在快照时刻是被引用的，那它就是快照的一部分，我就要保它不死。

**对比**：

*   **增量更新 (Incremental Update)**：CMS 使用的算法。它关注的是 `NewValue`。如果 A 引用了新的 B，把 A 重新标灰。
*   **SATB (Snapshot-At-The-Beginning)**：G1 使用的算法。它关注的是 `OldValue`。如果 A 断开了旧的 B，把旧的 B 记录下来。

**回答构建**：

1.  **定义**：一种并发标记算法，保证 GC 标记的是“GC 开始时刻”的对象图快照。
2.  **代表作**：G1 GC 的 SATB。
3.  **核心原理**：
    *   逻辑快照。
    *   写屏障记录旧引用（Pre-Write Barrier）。
4.  **如何解决漏标**：
    *   当引用断开时，把断开的对象记录下来，强制标记为活。
    *   宁可错杀（浮动垃圾），不可放过（漏标）。
5.  **优缺点**：
    *   优：标记过程不需要重新扫描根（Remark 阶段快）。
    *   缺：浮动垃圾多。



**快照 GC（Snapshot GC）**，在现代垃圾回收领域，通常特指**基于“起始快照”（Snapshot-At-The-Beginning, SATB）技术的并发标记算法**。

它是 **G1 GC** 的核心算法，也是解决并发 GC 中“对象引用动态变化”这一难题的一种优雅方案。

它的核心哲学是：**“我不管你在 GC 过程中怎么折腾，我只负责回收那些在 GC 开始那一刻就已经死亡的对象。”**

---

### 1. 核心问题：并发标记的“漏标”风险

在并发标记过程中，GC 线程和用户线程同时运行。这会导致一个严重问题：**用户线程可能会切断一个对象的引用，同时把这个对象挂到一个已经扫描过的对象下面。**

*   **场景**：对象 A（已扫描，黑色）断开了对对象 B（灰色）的引用，同时对象 C（已扫描，黑色）引用了 B。
*   **后果**：GC 以为 B 没人要了（因为 A 断开了），又不会去重新扫描 C。结果 B 被当成垃圾回收了，程序崩溃。

---

### 2. 快照 GC 的解决方案：SATB

快照 GC（SATB）引入了一个逻辑上的**“快照”**概念：

1.  **定格时间**：在 GC 开始的一瞬间（Initial Mark），GC 认为堆内存的状态被“定格”了。
2.  **承诺**：凡是在这个时刻**存活**的对象，在本次 GC 中都**必须被视为存活**，绝对不能回收。哪怕它在 GC 过程中被用户线程删除了，也得留到下次 GC 再处理。

#### 如何实现“快照”？—— 写屏障

GC 不可能真的把内存拷贝一份（太慢了）。它是通过**写屏障（Write Barrier）**来模拟快照的。

*   **动作**：当用户线程修改引用时，例如 `A.field = NewObj`。
*   **拦截**：这就意味着 `A.field` 原来指向的 `OldObj` 被断开了。
*   **记录**：SATB 的写屏障会捕获这个 **`OldObj`**，把它放入一个队列（SATB Buffer）。
*   **标记**：GC 线程会处理这个队列，**把 `OldObj` 强制标记为存活（涂黑）**。

**逻辑解释**：
“虽然你现在断开了 `OldObj`，但在 GC 开始的那一刻，它是活的。为了维持快照的一致性，我必须把它当做活对象处理。”

---

### 3. 与 CMS 的“增量更新”对比

*   **CMS (Incremental Update)**：关注**新引用**。
    *   如果你把 C 指向了 B，我就把 C 重新标记为灰色（下次重扫 C）。
    *   *缺点*：Remark 阶段必须重新扫描所有发生变化的地方，停顿时间可能较长。
*   **G1 (SATB)**：关注**旧引用**。
    *   如果你断开了 A 对 B 的引用，我就把 B 记录下来保住它。
    *   *优点*：Remark 阶段不需要重新扫描堆，只需要处理 SATB 队列，**速度极快**。

---

### 4. 优缺点总结

**优点**：

*   **Remark 阶段极快**：不需要像 CMS 那样重新扫描大量脏对象，停顿时间短且可控。
*   **算法简单稳健**：逻辑上非常清晰，就是维护一张逻辑快照。

**缺点**：

*   **浮动垃圾（Floating Garbage）**：
    *   如果一个对象在 GC 过程中真的死了（引用断开且没人接盘），SATB 依然会把它强行保活。
    *   这些垃圾只能等到**下一次 GC** 才能被回收。这会稍微浪费一点内存空间。

**总结**：
快照 GC（SATB）是 G1 能够实现**低延迟、可预测停顿**的关键技术之一。它宁可多留一点垃圾（浮动垃圾），也要保证标记过程的快速和准确。
