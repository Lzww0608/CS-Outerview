# 1. 协程

## 1. 协程是什么

协程是一种用户态的可暂停、可恢复执行单元。它相比线程更轻量，切换通常不需要陷入内核，也不需要切换完整内核线程上下文。

可以把协程理解为：

```text
函数 + 可保存的执行状态 + 调度器
```

协程执行到等待 I/O、定时器或主动让出时，会保存当前位置，之后由调度器恢复执行。

## 2. 和线程的区别

| 对比项 | 线程 | 协程 |
| --- | --- | --- |
| 调度者 | 操作系统内核 | 用户态运行时/框架 |
| 切换成本 | 较高，需要内核参与 | 较低，多数在用户态完成 |
| 栈 | 通常较大，MB 级默认值常见 | 可很小，可增长或无栈 |
| 并行能力 | 多线程可真正并行 | 取决于绑定的线程数 |
| 阻塞风险 | 阻塞当前线程 | 阻塞调用若未 hook 会卡住底层线程 |

协程提升的是并发组织能力，不等于自动提升 CPU 并行能力。CPU 密集型任务仍需要多线程或多进程利用多核。

## 3. 有栈协程和无栈协程

1. **有栈协程**：每个协程有自己的栈，可以在深层调用里挂起。Go goroutine、libco、fiber 常见。
2. **无栈协程**：状态由编译器转换成状态机，挂起点通常只能在协程函数内。C++20 coroutine、JavaScript async/await 常见。

有栈协程写法更像同步代码，但栈管理更复杂；无栈协程开销更可控，但异步传播会影响函数签名。

## 3.1 C++20 协程和 Go goroutine 的实现差异

C++20 coroutine 是典型的无栈协程。编译器会把协程函数改写成状态机，并把跨挂起点仍然需要保留的状态放进协程帧中：

1. 当前挂起点，也就是恢复时应该从哪里继续执行。
2. 跨 `co_await` 存活的局部变量、参数和临时对象。
3. `promise_type`、awaiter、返回对象和异常状态等运行时需要的信息。

协程帧通常在堆上分配，但编译器在能证明生命周期的情况下可以做分配消除。C++20 标准只提供协程语义，不内置调度器；什么时候恢复协程，取决于框架、事件循环或用户实现的 awaiter。

Go goroutine 更接近有栈协程和运行时调度线程的组合。它有可增长栈，由 Go runtime 通过 G-M-P 调度模型映射到多个操作系统线程上执行。goroutine 切换常见触发点包括 channel 阻塞、mutex 阻塞、网络 I/O、timer、系统调用、`runtime.Gosched()`，以及运行时为了避免长时间独占 CPU 做的抢占。

对比：

| 对比项 | C++20 coroutine | Go goroutine |
| --- | --- | --- |
| 栈模型 | 无栈，编译器生成状态机和协程帧 | 有可增长栈 |
| 调度器 | 标准库不内置，依赖框架实现 | Go runtime 内置 GMP 调度 |
| 切换点 | `co_await`、`co_yield`、`co_return` 等显式挂起点 | 阻塞点、运行时调度点和异步抢占 |
| 并行能力 | 取决于协程调度器绑定多少线程 | 可直接由 runtime 调度到多线程 |
| 工程优势 | 控制力强、零成本抽象空间大、适合高性能 C++ 网络库 | 使用简单、调度和网络轮询由 runtime 接管 |

所以面试里可以说：C++20 协程更像“语言级状态机转换能力”，Go goroutine 更像“语言级轻量线程 + 运行时调度系统”。两者都能用同步写法组织异步流程，但 C++ 需要自己或框架补齐调度、取消和 I/O 集成，Go 默认由 runtime 处理。

## 4. 协程和 I/O

高并发网络服务里，协程通常和事件循环配合：

```text
协程发起 read
-> 没数据，注册 fd 到 epoll，协程挂起
-> epoll 返回可读事件
-> 调度器恢复协程
-> 协程继续执行
```

这样可以用同步风格写异步逻辑，减少回调嵌套。

## 4.1 为什么使用协程

协程的价值不只是“切换快”，更重要的是让异步流程更容易组织。

常见收益：

1. **同步写法表达异步流程**：数据库、Redis、RPC、定时器等待可以写成顺序代码，减少 callback hell。
2. **降低线程数量**：大量连接或任务等待 I/O 时，不需要一连接一线程。
3. **减少上下文切换成本**：协程挂起和恢复通常在用户态完成，比内核线程切换轻。
4. **保留局部状态**：函数挂起后局部变量和执行位置保留，恢复后继续执行。
5. **更容易做超时和取消**：协程调度器可以统一管理等待队列、定时器和取消 token。

适用场景：

1. RPC 网关、游戏服务端、IM、爬虫这类高并发 I/O。
2. 业务流程需要串联多个异步步骤，例如读缓存、查数据库、调用下游、写回响应。
3. 希望保持同步代码可读性，同时避免阻塞线程。

不适合场景：

1. CPU 密集计算，协程不能自动利用多核。
2. 阻塞系统调用没有被运行时接管，会卡住底层线程。
3. 对调用栈、取消、异常传播没有设计清楚的复杂流程。

## 4.2 协程切换和内核线程切换的区别

协程切换通常由用户态运行时触发，例如遇到未就绪 I/O、定时器、`co_await`、`yield` 或框架主动让出。切换时保存的是协程恢复所需的状态：执行位置、少量寄存器、栈指针或编译器生成的状态机对象。这个过程多数不进入内核，也不切换页表。

内核线程切换由操作系统调度器负责，常见触发点包括时间片用完、阻塞系统调用、锁等待、更高优先级线程唤醒和中断返回前抢占。内核要保存当前线程寄存器、程序计数器、内核栈等上下文，选择下一个可运行线程，再恢复它的上下文；如果切换到不同进程，还可能切换页表并影响 TLB。

对比可以概括为：

| 对比项 | 协程切换 | 内核线程切换 |
| --- | --- | --- |
| 触发方式 | 多为协作式，让出点明确 | 可抢占，内核决定 |
| 执行位置 | 用户态运行时 | 内核调度器 |
| 保存内容 | 协程状态、栈/状态机、少量上下文 | 寄存器、PC、内核栈、调度信息 |
| 地址空间 | 通常不切换 | 跨进程切换时可能切换 |
| 成本 | 通常更低 | 更高，可能伴随缓存/TLB 影响 |

面试里不要把“协程切换快”说成绝对结论。协程如果数量极大、栈很大、调度队列复杂，或者运行时需要 hook 大量阻塞调用，也会有明显成本；线程如果在同一进程内切换，成本也低于跨进程切换。

## 5. 易错点

1. 协程不是线程，单线程协程不能利用多核并行。
2. 协程里调用阻塞系统调用，如果运行时没有 hook，会阻塞整个线程。
3. 协程数量很大时，也要关注栈、调度队列、定时器和上下文对象内存。
4. CPU 密集型任务不适合只靠协程解决，应交给线程池或进程池。
5. 协程取消、超时、异常传播和资源释放要设计清楚。

## 6. 面试回答模板

协程是用户态可暂停、可恢复的执行单元，本质是保存执行状态并由运行时调度。它比线程更轻，切换通常不进内核，适合高并发 I/O 场景。协程常和 epoll/io_uring 这类事件机制配合：I/O 未就绪时挂起协程，事件就绪后恢复执行。要注意协程不等于多核并行，阻塞系统调用可能卡住底层线程，CPU 密集任务仍要用多线程或多进程。
