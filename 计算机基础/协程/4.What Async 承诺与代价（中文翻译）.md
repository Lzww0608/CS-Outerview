# Async 的承诺与代价

*2026年4月*

每一代方案都解决了上一代最严重的问题，却又引入了新的问题。

操作系统线程有开销：一个 OS 线程要为它的栈预留虚拟地址空间，在现代 Linux 上创建需要几十微秒量级。上下文切换发生在内核空间，消耗 CPU 周期，O(n) 的就绪轮询（select、poll）在大规模场景下也会累积。一个处理数千并发连接的服务器，如果每连接分配一个线程，就意味着数千个线程各自占用内存、竞争调度机会。系统花大量时间在线程管理上，而这些时间本可用于做更有价值的工作。

这就是 C10K 问题，由 Dan Kegel 于 1999 年提出。如果你在构建 Web 服务器、聊天系统或任何需要大量同时连接的应用，你需要一种方式在不每连接一线程的情况下处理并发。

答案一波接一波地出现，每一波都解决了上一波最严重的问题，却又引入新的问题。之前我们探讨过 Go 的 channel 和 Erlang 的 actor。现在来聊聊 async，它如今无处不在。

## 回调函数

第一波方案很简单：不要阻塞线程。与其等待 I/O 操作完成，不如注册一个函数，等操作结束时调用，然后继续处理下一个任务。事件循环（select、poll、epoll、kqueue）将数千连接复用到了少数几个线程上，回调函数则是程序员操作这套机制的接口。

Node.js 在这个模型上构建了整套生态系统，用单线程处理数千并发连接。Nginx 的事件驱动架构是它能在高并发场景下取代 Apache 的主要原因。

这很好地解决了性能问题，但代价是：回调函数颠倒了控制流。不是把"做 A，然后 B，然后 C"写成三个顺序语句，而是写成"做 A，完成后调用这个函数，做 B，那个完成后调用另一个函数，做 C"。程序员的意图分散在嵌套闭包里。JavaScript 开发者称之为"回调地狱"，还专门建了一个网站来诉苦。

回调函数的问题不止于美观，还有更深的隐患，比如错误处理被割裂。每个回调都需要自己的错误处理路径。错误无法沿着调用栈自然传播，因为根本不存在调用栈（回调运行在与注册时不同的上下文中）。在回调链中处理部分失败，意味着要在链上的每个函数中传递错误状态。

此外，回调函数没有取消机制。如果你启动了一个异步操作，后来又觉得不需要结果了，没有通用的方法停止它。回调最终还是会触发，你的代码需要处理"已经不关心结果"的情况。

回调函数通过制造一个 ergonomics 问题（代码难写、难读、难用对）来解决资源问题（线程过多）。

## Promise 与 Future

下一波方案始于一个好的想法：如果异步操作不是传入回调等待后续调用，而是立即返回一个代表最终结果的对象呢？

这就是 Promise（JavaScript）或 Future（Java、Rust 等）。这个概念可以追溯到 1977 年的 Baker 和 Hewitt，但直到 2010 年代 C10K 的压力才推动它进入主流编程。JavaScript 在 ES2015 标准化了原生 Promise（遵循社区驱动的 Promises/A+ 规范），Java 8 引入了 `CompletableFuture`。

Promise 比回调更人性化。首先，Promise 是可组合的：`promise.then(f).then(g)` 读起来像管道而不是嵌套金字塔。错误处理也集中了：链末端的 `.catch()` 可以处理任意步骤的失败。Promise 还是可以存储、传递、返回的值。指向"尚未完成的计算结果"的初级句柄，将讨论从原始线程转向了数据依赖。"这个值依赖于尚未结束的某个计算"——这种表达能力是有价值的。

下面是 JavaScript 读取用户资料然后获取最近订单的例子，先用回调，再用 Promise：

```javascript
// 回调：嵌套，每层都要错误处理
getUser(userId, (err, user) => {
    if (err) return handleError(err);
    getOrders(user.id, (err, orders) => {
        if (err) return handleError(err);
        render(user, orders);
    });
});

// Promise：链式，错误处理集中
getUser(userId)
    .then(user => getOrders(user.id).then(orders => [user, orders]))
    .then(([user, orders]) => render(user, orders))
    .catch(handleError);
```

在这个小例子中，基于 Promise 的版本改进不大，但复杂性增加后差异就明显了：回调嵌套五层几乎无法阅读，而五个 `.then()` 链式调用至少是线性的。

但 Promise 也带来了自己的问题：

**Promise 是一次性的。** Promise 只能 resolve 一次。这使得它们不适合建模流、事件、重复消息或任何持续通信。接收消息流的 WebSocket 无法映射到"一个稍后存在的值"。这迫不得已产生了分裂：Promise 用于请求-响应模式，其他情况（事件发射器、响应式流、或者又回到回调）用于其他场景。

**组合笨拙。** 上面的例子已经暗示了这一点：要把 `user` 和 `orders` 都弄到最终的 `.then()` 里，需要嵌套或别扭地使用 `Promise.all`。两个独立的异步操作很简单（`Promise.all([a, b])`），但任何更复杂的情况（条件分支、循环中的异步操作、早期退出）都需要越来越复杂的组合器模式。这些模式能用，但它们是函数式编程的惯用法强行嫁接到命令式语言上，用起来不自然。

**错误静默消失。** 最初，JavaScript 的 Promise 在拒绝但没有 `.catch()` 处理器时直接吞掉错误。值丢失导致失败不可见。这问题足够严重，以至于 Node.js 最终把未处理拒绝从警告改成了进程崩溃，浏览器也添加了 `unhandledrejection` 事件。一个本为改善错误处理而设计的功能，居然创造了一类全新的、回调中根本不存在的静默失败。

**类型分裂。** 每个函数现在要么返回值，要么返回值的 Promise。所以调用者需要知道他们拿到的是哪种，库作者也需要决定提供哪种。原本同步的函数，加了数据库调用后就变成异步的了，现在每个调用者都需要处理 Promise 而不是值。这是着色问题的一种温和形式，而下一波会让它变本加厉。

## Async/Await

Promise 链仍然与开发者为其他一切写的顺序代码毫无相似之处。Async/await 由 C# 在 2012 年首创，随后被 JavaScript（ES2017）、Python（3.5）、Rust（1.39）、Kotlin、Swift 和 Dart 采用，终于做到了这一点：

```javascript
// Promise 链
function loadDashboard(userId) {
    return getUser(userId)
        .then(user => getOrders(user.id)
            .then(orders => [user, orders]))
        .then(([user, orders]) => render(user, orders));
}

// Async/await
async function loadDashboard(userId) {
    const user = await getUser(userId);
    const orders = await getOrders(user.id);
    return render(user, orders);
}
```

async/await 版本读起来像顺序代码。变量自然绑定。可以使用 `try/catch` 而不是 `.catch()`。循环内部可以用 `await`。对于线性的异步操作序列，这是 ergonomics 的胜利。

业界采纳得很快，JavaScript 框架全面投入，Python 的 asyncio 成为并发 I/O 的标准方案，Rust 将 async/await 稳定化为高性能网络之路。短短几年，async/await 成为大多数主流语言编写并发 I/O 代码的默认方式。

## 为函数着色税买单

2015 年，正当 async/await 势头正盛，Bob Nystrom 发表了《你的函数是什么颜色？》，这是一个思想实验：假设每种函数要么是"红色"要么是"蓝色"。红色函数可以调用蓝色函数，但蓝色函数要调用红色函数需要特殊仪式。每个函数必须选择一种颜色，如果你从蓝色函数调用红色函数，蓝色函数就变成红色，在整个代码库中病毒式传播。

这是对 async/await 的类比：async 函数是红色的，同步函数是蓝色的。async 函数可以毫无问题地调用 sync 函数，但从 sync 函数调用 async 函数需要阻塞线程或重构代码。程序中每个函数都必须选择颜色，而这种选择会传播到每个调用者。

Nystrom 的文章之所以引起共鸣，是因为它为开发者一直在经历但没有词汇表达的东西起了名字。函数着色重塑了整个代码库和生态系统。

Rust async 生态围绕互相不兼容的运行时碎片化（Tokio、async-std、smol），它们提供的基础类型（如 TCP 流和定时器）实现不兼容。用 Tokio 编写的库无法轻易用于 async-std。流行的 HTTP 客户端 `reqwest` 直接要求 Tokio，如果你的项目使用不同的运行时，那就是你的问题。现在库作者要么选择 Tokio（排除替代方案），要么尝试运行时无关的抽象（增加复杂性，有时还有性能开销）。

Tokio 的主导地位就是生态系统层面的函数着色。这种税在其他层面也有体现：

**在函数层面**，给一个原本同步的函数加一个 I/O 调用，会改变它的签名、返回类型和调用约定。每个调用者都必须更新，调用者的调用者也必须更新。这种变化沿着调用图蔓延，直到触及框架入口点或 main 函数。一行数据库查询可能需要修改几十个文件。

**在库层面**，作者面临选择：写同步库排除 async 用户，或写 async 库强迫同步用户添加运行时依赖（或两者都维护）。很多人选择"两者都做"，API 表面翻倍，测试矩阵翻倍，维护负担翻倍。在 Python 中，`requests` 库（同步）和 `aiohttp`（异步）是两个不同作者做的不同项目做同一件事。`httpx` 最终出现，从一个包提供两种接口，但这只是因为分裂才需要的改进。

**在生态系统层面**，上面的 Rust 例子是常态，不是例外。每个接触 I/O 的库都必须选择一种颜色，而这种选择限制了它能与哪些其他库协作。Rust async book 本身就指出："同步和异步代码也倾向于推广不同的设计模式，这使得组合适用于不同环境的代码变得困难。"

而且成本不止于后勤层面：async/await 引入了一些线程根本不存在的全新 bug 类别。O'Connor 记录了一类他称之为"futurelock"的 async Rust 死锁：future 获取锁后停止被 poll，而另一个 future 试图获取同一个锁。用线程的话，持有锁的线程总是朝着释放锁的方向推进（除非你做每个人都知道很危险的事，比如 `SuspendThread`）。而 async Rust 中，`select!`、缓冲流和 `FuturesUnordered` 等标准工具经常停止 poll 持有资源的 future。Oxide 的原始 futurelock 需要 core dump 和反汇编器才能诊断。

## 顺序陷阱

一个更微妙、较少被关注的成本是：async/await 最大的优势——让异步代码看起来是顺序的——也是一种认知陷阱。

```javascript
async function loadDashboard(userId) {
    const user = await getUser(userId);
    const orders = await getOrders(user.id);
    const recommendations = await getRecommendations(user.id);
    return render(user, orders, recommendations);
}
```

这顺序获取订单和推荐：`getRecommendations` 要等 `getOrders` 完成后才开始。但这两个操作是独立的，因为推荐不依赖订单。所以它们可以并行运行，但实际上没有。代码看起来干净正确，却在性能上打了折扣。

并行版本需要程序员显式打破顺序风格：

```javascript
async function loadDashboard(userId) {
    const user = await getUser(userId);
    const [orders, recommendations] = await Promise.all([
        getOrders(user.id),
        getRecommendations(user.id)
    ]);
    return render(user, orders, recommendations);
}
```

这种模式在小例子之外难以扩展。在一个有几十个 async 调用的真实应用中，确定哪些操作是独立的、可以被并行化，需要程序员手动分析依赖并重构代码。顺序语法积极地掩盖了依赖结构，即告诉你什么可以并行运行的那一条信息。

引入 async/await 是为了让异步代码更容易写。它把"什么可以并发运行"变成了程序员必须手动确定并通过组合器模式表达的东西，而那些模式打破了本来是其全部意义的顺序流。

## Async 做对了什么

公平地说，async 抽象确实改善了一些东西。

async/await 对线性序列的 ergonomics 比回调或 Promise 链更好。对于本质上顺序但恰好包含 I/O 的代码，async/await 消除了真正的语法噪音。它比基于回调的代码更容易阅读和调试。

一些语言设计者选择了不同的路径。例如，Go 有意选择了 goroutine，以更重的运行时为代价换取了完全没有函数着色。Java 的 Project Loom（Java 21 的虚拟线程）也下了不同的赌注：轻量级线程看起来和行为都像普通线程，所以不需要任何代码改变颜色。Loom 团队明确引用了函数着色作为他们想要避免的问题。

Zig 走得更远：完全移除了编译器级别的 async/await，围绕 i/o 操作接受的 Io 接口参数重建。运行时（线程化、事件循环，或用户提供任何实现）来实现接口。函数签名不会因为调度方式而改变，async/await 成为库函数而不是语言关键字。不过也有人认为 Io 参数本身就是一种着色。

研究过其他生态中 async/await 经验教训的语言设计者得出结论：函数着色的成本超过收益，于是选择了不同的路径。

## 累积的成本

每个解决方案都解决了一个问题，但也引入了新的成本。这些成本是结构性的，影响着代码库中每个程序、库和 API 的形态。

| 波浪 | 解决了 | 引入了 |
| --- | --- | --- |
| 回调 | 每连接一线程的资源耗尽 | 控制流反转、错误处理碎片化、回调地狱 |
| Promise | 嵌套、错误合并、值优于回调 | 一次性限制、错误静默吞掉、轻度类型分裂 |
| Async/Await | 线性异步序列的 ergonomics | 函数着色、生态系统碎片化、新类别死锁、顺序陷阱 |

每一波都让编写异步代码的本地体验更愉快，却让全局体验更复杂。写单个 async 函数的开发者从未如此轻松，而维护大型混合 sync/async 代码库、管理跨运行时依赖兼容性、在看起来顺序的 `await` 链背后寻找并行机会的团队，正在承担这些抽象引入之前根本不存在的负担。

这不是工程做得差的问题。设计回调、Promise 和 async/await 的人解决的都是真实问题，每一步都是对前一步失败的合理回应。但十五年和若干次迭代之后，累积的税赋相当可观，一个模式清晰可见：每个修复都治标不治本，留下结构完整。

从回调到 Promise 再到 async/await 的弧线可能是本系列至今最清晰的例证：以"如何管理并发执行？"为起点的方案，在每个抽象层次都不断产生新问题。在一个生态系统中，在一个十年内，你可以实时观察这一点。
