# 大量连接请求下协程 CPU 占用分析与优化

## 1. 问题背景

面试问题是：大量连接请求进入服务端，每个请求分配一个协程处理时，CPU 占用率里哪一部分会比较高？这里的 CPU 占用率需要拆成 User CPU、System CPU、硬中断和软中断来看，而不是只看一个总的百分比。

假设条件：

1. 服务运行在 Linux 上，网络 I/O 使用非阻塞 socket，底层由 `epoll`、`io_uring` 或运行时 netpoller 驱动。
2. “每个请求一个协程”指每个活跃请求或连接上下文由协程承载，协程不是每个请求一个内核线程。
3. 请求以网络连接和 RPC/HTTP 处理为主，不是单纯的本地 CPU 计算任务。
4. 讨论的 CPU 分类以 `top`、`mpstat`、`pidstat` 常见字段为准：`us`、`sy`、`hi`、`si`、`wa` 等。

核心结论：如果大量请求主要是网络 I/O、连接建立、收发小包和协议栈处理，那么更容易看到 **System CPU 和软中断 CPU 升高**；如果请求进入业务逻辑后有大量序列化、压缩、加解密、JSON 解析、规则计算或协程调度本身很重，则 **User CPU 也会升高**。硬中断通常不会长期占比最高，因为现代网卡常用 NAPI 把大量包处理转移到软中断或轮询路径。

## 2. 问题现象

常见现象包括：

1. 总 CPU 使用率升高，但业务代码火焰图不一定全是热点。
2. `top` 中 `sy`、`si` 比例明显上升，尤其是小包、高 PPS、短连接或连接频繁建立时。
3. `mpstat -P ALL` 看到某些 CPU 核上的 `soft` 或 `%soft` 很高，说明网络软中断可能集中在少数核。
4. `pidstat -w` 或 `vmstat` 看到上下文切换数、系统调用数、中断数升高。
5. 服务表现为 P99 延迟上升、吞吐到达平台期、连接建立变慢、accept 队列或业务队列开始堆积。

面试回答不要直接说“协程是用户态，所以一定是 User CPU 高”。协程调度本身多在用户态，但大量连接请求会触发网络协议栈、系统调用、内核 socket 缓冲区、epoll 就绪通知和软中断处理，这些通常会体现在 System CPU 和 softirq 上。

## 3. 影响范围

这个问题影响的是高并发网络服务的整体吞吐和尾延迟，常见于：

1. RPC 网关、HTTP API 服务、IM 长连接服务、游戏网关、推送服务。
2. Go goroutine、C++ coroutine、Rust async、Java virtual thread 或 gevent 这类轻量并发模型。
3. 短连接风暴、突发流量、心跳过密、小包高 PPS、请求体较小但请求数极高的场景。
4. 业务逻辑较轻时，瓶颈容易从应用层转移到网络协议栈、内核态处理和软中断。
5. 业务逻辑较重时，User CPU 仍可能成为主要瓶颈，协程只解决并发组织，不减少业务计算量。

## 4. 原因分析

CPU 时间可以先按执行位置拆开：

| CPU 类型 | 含义 | 大量连接请求下的典型来源 |
| --- | --- | --- |
| User CPU | 用户态代码执行时间 | 协程调度、业务逻辑、编解码、序列化、压缩、加解密、日志格式化 |
| System CPU | 内核态执行时间 | `accept`、`read`、`write`、`epoll_wait`、`epoll_ctl`、socket buffer、TCP 协议栈、内核锁 |
| Hard IRQ | 硬中断处理时间 | 网卡中断上半部、设备中断确认 |
| Soft IRQ | 软中断处理时间 | `NET_RX`、`NET_TX`、NAPI 轮询、协议栈下半部、包收发批处理 |
| I/O wait | CPU 空闲但等待 I/O 的时间 | 磁盘或某些阻塞 I/O，纯网络高并发不一定主要体现为 `wa` |

大量连接请求进入服务端时，链路大致是：

```text
网卡收包
-> DMA 写入内存
-> 硬中断或 NAPI 触发
-> 软中断处理网络包和协议栈
-> TCP socket 接收缓冲区变为可读
-> epoll ready list 产生事件
-> 用户态事件循环返回
-> 恢复对应协程处理请求
-> 协程读写 socket，必要时再次挂起
```

所以 CPU 占用升高来自多层叠加：

1. **网络包处理推高软中断**：小包高 PPS、连接数多、ACK 多、重传多时，`NET_RX`、`NET_TX` 压力上升。
2. **系统调用和协议栈推高 System CPU**：大量 `accept/read/write/epoll_wait/epoll_ctl`、socket buffer 拷贝、TCP 状态维护都会进入内核。
3. **协程调度和业务逻辑推高 User CPU**：协程创建、恢复、挂起、定时器维护、任务队列调度，以及业务编解码都在用户态。
4. **锁和队列竞争放大开销**：多线程共享 epoll、共享任务队列、共享连接表或日志队列，会带来锁竞争和 cache 抖动。
5. **短连接比长连接更容易推高内核态成本**：三次握手、四次挥手、TIME_WAIT、accept 队列和连接对象创建都会增加内核和用户态开销。

一个实用判断：

1. `us` 高：优先看业务火焰图、协程调度、编解码、压缩、加密、日志。
2. `sy` 高：优先看系统调用频率、socket 读写策略、epoll 使用方式、内核锁和拷贝。
3. `si` 高：优先看网络 PPS、网卡队列、RSS/RPS、软中断是否单核打满、是否有小包风暴。
4. `hi` 高：优先看设备中断是否异常、网卡中断亲和性、是否有中断风暴。

## 5. 解决方案

优化原则是先定位 CPU 时间花在哪里，再对症处理。

1. **降低连接和请求进入内核的频率**
   - 使用长连接、连接池、HTTP keep-alive、HTTP/2 多路复用。
   - 避免高频短连接导致握手、挥手和 TIME_WAIT 压力。
   - 合理设置 `somaxconn`、listen backlog、SYN backlog、fd 上限和端口范围。

2. **优化网络 I/O 模型**
   - 使用非阻塞 I/O + `epoll`，避免一连接一线程。
   - 每个 EventLoop 负责固定连接，减少跨线程操作同一个 fd。
   - 批量 `accept`、批量 `read/write` 到 `EAGAIN`，减少事件遗漏和系统调用抖动。
   - 避免频繁 `epoll_ctl` 增删改，尽量复用事件关注状态。

3. **控制协程数量和调度开销**
   - 协程不是越多越好，要限制活跃请求数、队列长度和超时时间。
   - 区分 I/O 协程和 CPU 密集任务，CPU 密集任务放入独立 worker pool。
   - 避免协程内忙等、无界重试、无界定时器和无限制 fan-out。

4. **降低用户态业务 CPU**
   - 使用更高效的协议和序列化格式，减少 JSON 热点。
   - 减少重复拷贝、字符串拼接、日志格式化和临时对象分配。
   - 对压缩、加密、复杂规则计算做批量化、缓存或异步化。

5. **优化软中断和网卡侧配置**
   - 检查 RSS、RPS、RFS、网卡多队列和 IRQ affinity，避免软中断集中在单核。
   - 使用 NAPI、GRO、GSO、TSO 等批处理和 offload 能力。
   - 对小包风暴做聚合、限流或协议层批量发送。

6. **建立背压和保护机制**
   - 对连接数、请求队列、协程数、下游并发数设置上限。
   - 队列满时快速失败、限流、熔断或降级。
   - 避免协程无限堆积把 CPU 问题放大成内存问题和尾延迟问题。

## 6. 可选方案对比

| 方案 | 优点 | 缺点 | 适用场景 |
| --- | --- | --- | --- |
| 一请求一协程 + 非阻塞 I/O | 编程模型清晰，适合高并发 I/O | 仍有调度、内存和定时器成本 | 大量 I/O 等待、业务逻辑中等 |
| 纯事件回调 Reactor | 极致可控，少一层协程调度 | 代码可读性和错误处理复杂 | 高性能 C/C++ 网络库核心层 |
| 一连接一线程 | 编程简单 | 线程栈、内核调度和上下文切换成本高 | 连接数较少、内部工具或低并发服务 |
| 协程 + CPU worker pool | I/O 和 CPU 隔离，避免事件循环被阻塞 | 架构复杂，需要队列和背压 | 有加解密、压缩、复杂计算的服务 |
| 多 Reactor + 连接归属 | 多核扩展好，锁竞争低 | 连接迁移和跨线程投递要设计清楚 | 高并发长连接、网关、IM、游戏服务 |

## 7. 推荐方案

推荐使用“多 Reactor / 多 EventLoop + 一请求一协程 + 有界队列 + CPU 任务隔离”的方案。

具体思路：

1. 网络层使用非阻塞 I/O，每个连接固定归属一个 EventLoop。
2. EventLoop 只做 accept、read、write、协议编解码和轻量调度。
3. 每个请求由协程承载，遇到 I/O、定时器或下游等待就挂起。
4. CPU 密集任务不要直接在 I/O 协程里跑，投递到独立 worker pool。
5. 对连接数、协程数、请求队列和下游并发数设置硬上限。
6. 监控按 `us/sy/si/hi` 拆分，定位后再优化业务、系统调用或软中断。

面试里可以这样回答：

> 大量连接请求下，不一定是 User CPU 最高。协程调度和业务逻辑在用户态，会增加 User CPU；但连接建立、socket 读写、epoll、TCP 协议栈会增加 System CPU；网卡收包和协议栈下半部会增加软中断 CPU，尤其小包高 PPS 时 `si` 可能很高。硬中断一般不会长期最高，因为现代 Linux 网络收包常用 NAPI，把大量处理放到软中断和轮询里。最终要用 `top/mpstat/perf/softirqs` 拆开看，而不是只凭“每请求一个协程”判断。

## 8. 实施步骤

1. **采集 CPU 分类**
   - 用 `top`、`mpstat -P ALL 1` 查看 `us/sy/hi/si/wa`。
   - 用 `pidstat -u -t -p <pid> 1` 查看进程和线程级 CPU。
   - 用 `vmstat 1` 查看 `in/cs`、运行队列和上下文切换趋势。

2. **定位用户态热点**
   - 用 `perf top`、`perf record`、火焰图或语言运行时 profiler。
   - Go 服务重点看 goroutine 数、调度延迟、GC、mutex、block profile。
   - C++ 服务重点看协程调度器、协议解析、内存分配、锁竞争和日志。

3. **定位内核态和系统调用热点**
   - 用 `strace -c -p <pid>` 观察系统调用频率，但生产环境要谨慎。
   - 用 `perf` 看内核符号，如 TCP、epoll、copy、skb、锁相关热点。
   - 检查是否频繁 `epoll_ctl`、小块 `read/write`、短连接过多。

4. **定位软中断压力**
   - 查看 `/proc/softirqs` 中 `NET_RX`、`NET_TX` 是否增长异常。
   - 用 `mpstat -P ALL 1` 看软中断是否集中在单核。
   - 检查网卡队列数、RSS/RPS、IRQ affinity 和 PPS。

5. **实施代码和配置优化**
   - 先减少短连接和小包，再优化系统调用批量化。
   - 再隔离 CPU 密集任务，控制协程和队列规模。
   - 最后调整网卡、多队列、亲和性和内核参数。

如果涉及代码实现，真实服务中可能需要关注：

| 项目 | 说明 |
| --- | --- |
| 可能需要修改的模块 | 网络接入层、EventLoop/Reactor、协程调度器、请求队列、worker pool、限流与超时模块、日志模块 |
| 可能涉及的文件 | `server/acceptor.*`、`net/event_loop.*`、`net/connection.*`、`runtime/scheduler.*`、`worker_pool.*`、`config/*.yaml`、`monitoring/*.yaml` |
| 核心修改逻辑 | 连接固定归属 EventLoop，批量 accept/read/write，减少频繁 epoll_ctl；CPU 密集逻辑投递 worker pool；请求队列有界；协程超时和取消可控 |
| 测试重点 | 高并发连接压测、短连接和长连接对比、P99 延迟、`us/sy/si/hi` 分布、协程数量、队列长度、丢包重传、软中断是否单核打满 |

## 9. 风险与注意事项

1. 协程不是免费的。大量协程会消耗调度器、内存、栈或协程帧、定时器和队列资源。
2. 协程不能自动减少网络协议栈成本。包量和系统调用仍然会消耗 System CPU 和 softirq。
3. 不要在 I/O 协程里执行长时间 CPU 计算，否则会阻塞 EventLoop 或拖慢同线程其他协程。
4. 不要只看平均延迟，高并发下 P95/P99/P999 更能反映队列堆积和调度抖动。
5. 调整网卡 offload、RPS/RFS、IRQ 亲和性前要做灰度验证，不同网卡、内核版本和流量模型差异较大。
6. `strace`、调试日志和过细指标可能显著影响高频路径，排查时要控制采样范围。
7. 短连接优化不能只靠调内核参数，协议层连接复用通常更关键。

## 10. 验证方式

可以用压测和观测闭环验证：

1. **基线压测**：记录当前 QPS、P50/P95/P99、错误率、连接数、协程数、CPU 分类。
2. **CPU 分类对比**：优化前后对比 `us/sy/si/hi`，确认瓶颈是否移动。
3. **火焰图验证**：确认用户态热点是否下降，内核态热点是否符合预期。
4. **软中断验证**：检查 `/proc/softirqs`、`mpstat -P ALL`，确认 `NET_RX/NET_TX` 是否均衡。
5. **系统调用验证**：确认 `accept/read/write/epoll_ctl` 调用频率是否下降或更批量化。
6. **稳定性验证**：长时间压测连接泄漏、内存增长、协程泄漏、队列堆积和超时错误。
7. **故障注入**：模拟慢客户端、下游超时、小包洪峰、短连接洪峰，验证限流、背压和降级是否生效。

## 11. 总结

大量连接请求下，每个请求一个协程并不意味着 CPU 主要消耗在 User CPU。协程调度和业务逻辑会消耗用户态 CPU，但网络高并发通常还会显著消耗 System CPU 和软中断 CPU。短连接、小包高 PPS、频繁系统调用和协议栈处理越重，`sy` 和 `si` 越容易升高；业务计算、编解码、压缩加密和日志越重，`us` 越容易升高。

推荐回答要点是：先拆 CPU 分类，再结合请求模型判断。工程上用非阻塞 I/O、连接复用、批量读写、多 EventLoop、CPU 任务隔离、有界队列和软中断均衡来优化，并通过 `top`、`mpstat`、`perf`、`/proc/softirqs` 和压测指标验证效果。
