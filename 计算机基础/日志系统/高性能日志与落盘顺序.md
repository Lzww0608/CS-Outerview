# 高性能日志与落盘顺序

高并发服务里，日志既是排障依据，也可能成为性能瓶颈。面试里问“高性能时候日志该怎么处理”“日志有什么瓶颈”“怎么防止最终落盘被打乱”，重点是区分业务线程产生日志、日志线程批量写入和最终落盘顺序。

## 1. 日志瓶颈在哪里

常见瓶颈：

1. **格式化 CPU**：时间格式化、字符串拼接、JSON 序列化、堆栈打印都耗 CPU。
2. **锁竞争**：多个业务线程抢同一个 logger、文件句柄或队列锁。
3. **系统调用**：每条日志都 `write` 会产生大量 syscall。
4. **刷盘延迟**：每条日志都 `fsync` 会被磁盘延迟拖垮。
5. **磁盘吞吐**：日志量超过磁盘顺序写能力。
6. **队列堆积**：异步日志如果队列无界，会把内存打爆。
7. **跨线程乱序**：多线程直接写同一个文件，业务时间顺序和落盘顺序可能不一致。

所以高性能日志通常遵循：

```text
业务线程快速入队
-> 日志线程批量格式化或批量写
-> 单 writer 顺序追加
-> 周期性 flush / fsync
-> 后台滚动、压缩、上传
```

## 2. 推荐架构

```text
Producer Threads
  -> bounded MPSC/MPMC queue 或 ring buffer
  -> Log Worker
  -> batch write
  -> file sink / stdout / Kafka
```

关键设计：

1. **异步化**：业务线程只做轻量封装和入队，不同步等待磁盘。
2. **有界队列**：队列满时按策略阻塞、丢弃低级别日志或降级采样。
3. **批量写**：日志线程攒一批后 `writev` 或连续 `write`，减少 syscall。
4. **单写者**：一个文件最好只有一个日志线程写，天然保证该线程内顺序。
5. **分级策略**：ERROR 可同步或强 flush，INFO/DEBUG 可异步批量。
6. **落盘策略**：按时间或字节数 flush，关键场景才 `fsync`。
7. **滚动和压缩**：日志滚动、压缩和上传不要阻塞业务线程。

## 3. 怎么防止落盘被打乱

先明确“顺序”的含义：

1. **单线程内顺序**：同一个线程先打的日志先落盘。
2. **全局入队顺序**：所有线程按进入日志队列的顺序落盘。
3. **真实事件时间顺序**：按业务事件发生时间排序。

最常见需求是保证全局入队顺序。做法：

1. 每条日志入队时用原子自增分配 `seq`。
2. 所有日志进入同一个有序队列，或每线程队列最后按 `seq` 归并。
3. 由单个日志线程按 `seq` 顺序写文件。
4. 一条日志记录一次性格式化成完整行，避免半行交错。
5. 文件追加只由日志线程持有，业务线程不要直接写同一个 fd。

如果使用每线程缓冲区：

```text
thread local buffer A: seq 1, 4, 7
thread local buffer B: seq 2, 3, 6
thread local buffer C: seq 5, 8
        -> log worker 按 seq 归并写出
```

但归并会增加复杂度和延迟。多数业务只需要“单 logger 单队列单 writer”，再配合 `seq` 和时间戳排查即可。

## 4. O_APPEND 和 fsync 的边界

`O_APPEND` 可以让内核把每次 `write` 追加到文件末尾，避免多个进程覆盖同一位置，但它不等于业务语义上的全局顺序。

注意点：

1. 多线程多次小 `write` 可能出现不同日志行交错，尤其是一条日志拆成多次写时。
2. `fsync` 只能保证数据尽量持久化到磁盘，不保证多生产者的业务时间顺序。
3. 多进程写同一个日志文件更难保证顺序，最好按进程拆文件或集中到日志服务。
4. 如果强要求审计顺序，应使用单 writer、WAL、序列号和确认机制。

## 5. 丢日志、阻塞和采样怎么取舍

高性能日志必须明确队列满时策略：

1. **阻塞业务线程**：日志不丢，但可能拖慢核心链路，适合审计日志。
2. **丢弃低级别日志**：保护业务延迟，适合 DEBUG/INFO。
3. **采样**：高频重复日志按比例保留。
4. **降级为计数器**：同类日志只记录次数和少量样本。
5. **本地落盘兜底**：远程日志系统不可用时先写本地文件，后台补传。

交易、支付、权限变更这类审计日志不能随意丢；普通访问日志和调试日志可以采样或降级。

## 6. 面试回答模板

高性能日志我会做成异步有界队列。业务线程只分配序列号、封装日志事件并快速入队，日志线程批量格式化和写文件，减少锁竞争、系统调用和同步刷盘。瓶颈主要在格式化 CPU、队列锁、write syscall、fsync、磁盘吞吐和队列堆积。为了防止落盘顺序被打乱，我会让同一个日志文件只有一个 writer，并在入队时用原子自增生成 `seq`，日志线程按入队顺序写完整日志行；如果每线程缓冲，就按 `seq` 归并后再写。队列满时要按日志级别取舍：审计日志可以阻塞或强落盘，普通 INFO/DEBUG 可以采样、丢弃或降级为计数器。
