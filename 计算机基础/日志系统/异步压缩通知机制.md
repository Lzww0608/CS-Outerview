既然我们确定了采用**异步压缩**的方案，那么**主业务线程（生产者）**和**后台压缩线程（消费者）**之间就存在一个典型的**生产者-消费者模型**。

这里的资源竞争主要集中在**任务队列**和**条件变量**上。

下面我将深入细节，剖析“谁来 notify”、“何时 notify”以及底层的竞争处理。

---

### 1. 核心数据结构

为了实现异步压缩，我们需要一个任务队列。这个队列就是两个线程争夺的“临界资源”。

```cpp
struct CompressionTask {
    std::string file_path_to_compress; // 待压缩的文件路径，如 "server.log.1"
    std::string target_gz_path;        // 目标路径，如 "server.log.1.gz"
};

// 全局或静态成员管理的任务队列
class AsyncCompressor {
private:
    std::queue<CompressionTask> task_queue_; // 临界资源
    std::mutex queue_mutex_;                 // 保护队列的锁
    std::condition_variable cv_;             // 用于通信的条件变量
    bool stop_ = false;                      // 停止标志
    std::thread worker_thread_;              // 后台线程
    
    // ...
};
```

---

### 2. 谁负责 Notify？（生产者）

**负责 Notify 的是：执行日志滚动（Rotate）的那个业务线程。**

当 `rotate()` 发生时，业务线程是生产者，它产生了一个“旧文件”。

#### 具体过程与竞争细节：

1.  **持有 Sink 锁**：业务线程首先持有了 `Sink` 内部的锁（防止其他线程写日志）。
2.  **执行重命名**：`rename("server.log", "server.log.1")`。
3.  **生成任务**：准备好任务数据 `{ "server.log.1", ... }`。
4.  **推入队列（竞争点 A）**：
    *   业务线程需要获取 `queue_mutex_`。
    *   **注意**：此时业务线程可能同时持有两把锁（Sink 的锁 + 队列的锁）。为了避免死锁和减少 Sink 锁的持有时间，最佳实践是**先完成 Rotate，释放 Sink 锁，再获取队列锁推任务**（或者将任务推入队列的操作放在 Sink 锁之外，如果逻辑允许）。
5.  **执行 Notify**：调用 `cv_.notify_one()`。

**代码片段：**

```cpp
// 业务线程执行的逻辑
void on_rotate_finished(std::string old_file_path) {
    {
        // 获取队列锁
        std::lock_guard<std::mutex> lock(compressor.queue_mutex_);
        // 推入任务
        compressor.task_queue_.push({old_file_path, old_file_path + ".gz"});
    } // 离开作用域，自动释放队列锁

    // 通知后台线程
    // 注意：notify_one 不需要在锁内部调用，放在锁外可以减少上下文切换时的竞争
    compressor.cv_.notify_one(); 
}
```

### 3. 什么时候 Notify？（时机选择）

通常有两种策略，涉及到性能权衡：

#### 策略 A：每次 Rotate 都 Notify（Immediate Notification）
*   **时机**：只要产生了一个旧文件，立马 `notify_one`。
*   **优点**：实时性高，磁盘空间回收快。
*   **缺点**：如果日志滚动极快（例如压测时每秒滚动一次），会频繁唤醒后台线程，导致频繁的上下文切换（Context Switch）。
*   **适用场景**：绝大多数通用场景。

#### 策略 B：批处理/阈值 Notify（Batching）
*   **时机**：队列里积攒了 N 个文件，或者距离上次压缩过了 M 秒，才 Notify。
*   **优点**：减少线程唤醒开销。
*   **缺点**：逻辑复杂，且可能导致大量未压缩的日志堆积占用磁盘。
*   **结论**：对于日志压缩这种重 IO 操作，**策略 A (立即通知)** 通常就足够了。因为压缩本身很慢，后台线程大部分时间都在忙着压缩（或者在 sleep），频繁 notify 并不是瓶颈，真正的瓶颈是 CPU 和 磁盘带宽。

### 4. 资源竞争的深层问题

这里有几个非常隐蔽的竞争点，面试时指出来会很加分：

#### 竞争点 1：后台线程还在压，前台又来了任务（忙碌时的 Notify）
*   **场景**：后台线程正在 `Gzip` 压缩 `log.1`（很耗时，未持有锁）。此时业务线程产生了 `log.2`，获取锁，push 到队列，调用 `notify_one`。
*   **行为**：
    *   `std::condition_variable` 的机制保证了，如果后台线程正在忙（没在 `wait` 状态），`notify` 信号其实是被“忽略”的（或者说没用，因为线程本身就是醒着的）。
    *   但这没关系。后台线程的逻辑通常是 `while(!queue.empty())`。等它压缩完 `log.1`，它会再次检查队列，发现 `log.2` 已经在那里了，于是继续工作，不会休眠。
*   **结论**：这是安全的，设计良好的消费者循环能自动处理这种情况。

#### 竞争点 2：虚假唤醒 (Spurious Wakeup)
*   **场景**：后台线程正在 `cv_.wait()` 等待。操作系统因为某些调度原因，莫名其妙唤醒了它，但此时队列是空的。
*   **解决**：必须使用 `while` 循环配合 `predicate` 检查，而不是 `if`。
    ```cpp
    // 后台线程逻辑
    std::unique_lock<std::mutex> lock(queue_mutex_);
    cv_.wait(lock, [this]{ return stop_ || !task_queue_.empty(); }); // 核心防守
    ```

#### 竞争点 3：程序退出时的竞争 (Shutdown Race)
这是最容易崩的地方。
*   **场景**：程序收到 `SIGTERM` 要退出了。主线程调用 `compressor.stop()`。
*   **问题**：如果队列里还有没压缩完的日志怎么办？直接杀掉线程会导致文件损坏。
*   **解决**：
    1.  设置 `stop_ = true`。
    2.  `cv_.notify_all()` （唤醒线程让它处理剩余任务或退出）。
    3.  `worker_thread_.join()` （主线程**等待**后台线程把活干完）。
    
    **谁负责 Notify？** 此时是**主线程（析构函数或 Shutdown 钩子）**负责 `notify_all`。

### 5. 总结回答范式

如果让我总结，我会这样告诉面试官：

**关于资源竞争和 Notify 机制，我的设计如下：**

1.  **模型**：这是一个标准的**多生产者-单消费者**模型。
2.  **谁 Notify**：
    *   **正常运行时**：由触发日志滚动的**业务线程**负责。当它完成文件重命名并将任务推入队列后，调用 `notify_one`。
    *   **程序退出时**：由**主线程/管理类析构函数**负责。设置退出标志位后，调用 `notify_all` 唤醒后台线程进行清理。
3.  **竞争控制**：
    *   使用 `std::mutex` 保护任务队列。
    *   **关键优化**：业务线程在推入任务时，应尽量**先释放 Sink 自身的文件锁**，再获取**压缩队列的锁**。避免锁嵌套（Lock Nesting），防止因压缩队列繁忙而反向阻塞写日志的业务线程。
4.  **鲁棒性**：后台线程必须使用 `while` 循环检查队列状态，以处理**忙碌时收到的通知**以及**虚假唤醒**问题。同时，程序退出时必须 `join` 等待后台线程处理完剩余的压缩任务，防止数据丢失。
