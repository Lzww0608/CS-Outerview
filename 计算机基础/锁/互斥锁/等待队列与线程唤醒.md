# 互斥锁的等待队列与线程唤醒机制

## 1. 概述

当线程获取互斥锁失败时，它会被挂起并放入锁的等待队列。理解这个等待队列的组织方式和唤醒机制，是理解 Linux 并发编程的关键。

## 2. 互斥锁的等待队列

### 2.1 互斥锁的结构

Linux 中互斥锁的基本结构（在 futex 之上构建）：

```cpp
struct pthread_mutex {
    int type;           // 锁类型
    int status;         // 0=未占用, 1=已占用
    int nwaiters;       // 等待者数量
    // 在 futex 之上，还会有其他元数据
};
```

### 2.2 等待队列的组织

当线程无法获取互斥锁时，内核会把它放入与该锁关联的等待队列：

```text
等待队列:
┌─────────────────────────────────────────────┐
│  Futex Wait Queue                          │
│  ┌─────────┐  ┌─────────┐  ┌─────────┐    │
│  │ Thread 1│──│ Thread 2│──│ Thread 3│── NULL│
│  │ (TID=1001)│ │ (TID=1002)│ │ (TID=1003)│      │
│  └─────────┘  └─────────┘  └─────────┘       │
└─────────────────────────────────────────────┘
       ↑
       └── 新等待的线程加到队列尾部（FIFO）
```

等待队列的特点：
- **FIFO 顺序**：按等待顺序排列，先到先得
- **内核管理**：等待队列由内核 futex 机制维护
- **睡眠状态**：队列中的线程处于 TASK_INTERRUPTIBLE 或 TASK_UNINTERRUPTIBLE 状态

## 3. 线程睡眠的机制

### 3.1 睡眠状态

Linux 中的进程/线程状态：

| 状态 | 说明 | 可被信号唤醒 |
| --- | --- | --- |
| TASK_RUNNING | 可运行，正在 CPU 上执行或等待 CPU | - |
| TASK_INTERRUPTIBLE | 可中断睡眠，等待某事件 | ✅ |
| TASK_UNINTERRUPTIBLE | 不可中断睡眠，不响应信号 | ❌ |
| TASK_STOPPED | 已停止，收到 SIGSTOP | ✅ |
| TASK_TRACED | 被跟踪，如 GDB | ✅ |

互斥锁等待通常使用 TASK_INTERRUPTIBLE（可中断睡眠），允许被信号唤醒。

### 3.2 线程如何进入睡眠

```c
// 简化伪代码
void mutex_lock_slow_path(mutex_t* m) {
    // 1. 标记自己为等待状态
    current->state = TASK_INTERRUPTIBLE;
    
    // 2. 加入锁的等待队列
    wait_queue_add(&m->wait_queue, current);
    
    // 3. 释放 CPU（调度出去）
    schedule();
    
    // 4. 被唤醒后，重新尝试获取锁
    // ...
}
```

### 3.3 睡眠的代价

线程进入睡眠涉及：
1. **状态切换**：从 TASK_RUNNING 变为 TASK_INTERRUPTIBLE
2. **上下文切换**：保存当前上下文，切换到其他线程
3. **调度开销**：唤醒后再次调度回 CPU

这就是为什么自旋锁适合短临界区：自旋避免了睡眠/唤醒的开销，但浪费 CPU 时间片。

## 4. 线程唤醒的机制

### 4.1 唤醒触发点

当持有锁的线程释放锁时，会触发唤醒：

```c
void mutex_unlock(mutex_t* m) {
    // 1. 释放锁
    m->status = 0;
    
    // 2. 检查是否有等待者
    if (m->nwaiters > 0) {
        // 3. 唤醒等待队列中的一个线程
        wake_up(&m->wait_queue);
    }
}
```

### 4.2 wake_up 的工作原理

```c
void wake_up(wait_queue_head_t* q) {
    // 1. 从等待队列头部取出一个线程
    task_struct* task = dequeue(q);
    
    if (task) {
        // 2. 设置状态为可运行
        task->state = TASK_RUNNING;
        
        // 3. 加入 CPU 运行队列
        enqueue_to_runnable(task);
        
        // 4. 触发调度（可能立即切到被唤醒的线程）
        schedule();
    }
}
```

### 4.3 唤醒策略

| 策略 | 说明 | 场景 |
| --- | --- | --- |
| wake_one | 唤醒队列中一个线程 | 互斥锁（FIFO） |
| wake_all | 唤醒队列中所有线程 | 条件变量广播 |
| wake_up_interruptible | 只唤醒可中断的 | 允许被信号中断 |

### 4.4 条件变量的特殊唤醒

条件变量的 signal/broadcast：
- **signal**：通常唤醒一个等待的线程
- **broadcast**：唤醒所有等待的线程

```c
pthread_cond_signal(&cond);    // 唤醒一个
pthread_cond_broadcast(&cond); // 唤醒所有
```

## 5. 互斥锁 vs 自旋锁的睡眠策略

### 5.1 何时睡眠

| 锁类型 | 获取失败时 | 适用场景 |
| --- | --- | --- |
| 互斥锁 | 线程睡眠，等待唤醒 | 临界区时间长 |
| 自旋锁 | 线程自旋，CPU 忙等 | 临界区时间极短 |

### 5.2 混合锁（自适应锁）

Linux 内核和一些高性能库采用混合策略：

```c
void adaptive_mutex_lock(mutex_t* m) {
    while (atomic_test_and_set(&m->locked)) {
        // 如果锁持有者正在运行，自旋等待
        if (m->holder && task_is_running(m->holder)) {
            cpu_relax();  // pause 指令，减少 CPU 争用
            continue;
        }
        
        // 否则，睡眠等待
        schedule();
    }
}
```

## 6. 面试高频问题

### Q1: 互斥锁的等待队列存在哪里？

**回答要点**：
- 在用户态，锁本身的数据结构（如 pthread_mutex）可能包含等待计数
- 真正的等待队列在内核中，由 futex 系统调用管理
- futex 通过锁变量的地址索引内核中的等待队列
- 线程调用 futex(WAIT) 时被加入内核等待队列

### Q2: 线程睡眠后是如何被唤醒的？

**回答要点**：
- 持有锁的线程释放时调用 futex(WAIT)
- futex(WAIT) 在内核中检查锁状态，如果已释放立即返回
- 如果锁仍被占用，线程加入内核等待队列，状态设为 TASK_INTERRUPTIBLE
- 释放锁时调用 futex(WAKE)，内核唤醒队列中的线程
- 被唤醒的线程状态变为 TASK_RUNNING，加入 CPU 运行队列

### Q3: 互斥锁和自旋锁各有什么优缺点？

**回答要点**：
- 互斥锁：线程睡眠，不消耗 CPU，但有上下文切换开销，适合临界区时间长
- 自旋锁：线程忙等，不切换上下文，但消耗 CPU 时间片，适合临界区极短
- 实际选择取决于锁的预期持有时间和上下文切换成本

## 7. 真实场景

### 7.1 高并发服务器

```
场景：处理 10000 并发连接
问题：每个连接一个线程？线程太贵

解决：
1. I/O 多路复用（epoll）+ 事件驱动
2. 少量工作线程处理业务逻辑
3. 用互斥锁保护共享数据（如连接池）

锁的持有时间要尽可能短，否则大量请求阻塞
```

### 7.2 数据库连接池

```
场景：100 个数据库连接，1000 个请求

解决：
1. 连接池用互斥锁保护
2. 获取连接时：
   - 有空闲连接 → 直接使用
   - 无空闲连接 → 等待或超时
3. 释放连接时唤醒一个等待者

关键：等待队列在内核中，进程可以睡眠让出 CPU
```

## 8. 总结

互斥锁的等待队列和唤醒机制：

1. **等待队列位置**：用户态锁 + 内核 futex 等待队列
2. **线程睡眠**：调用 futex(WAIT)，状态变为 TASK_INTERRUPTIBLE
3. **唤醒机制**：持有者调用 futex(WAKE)，唤醒队列中的线程
4. **调度恢复**：被唤醒的线程加入运行队列，等待 CPU 调度

理解这些底层机制，有助于写出高效的多线程程序。
