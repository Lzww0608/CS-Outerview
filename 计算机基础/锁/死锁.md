# 死锁

死锁是指多个线程或进程在并发执行时，彼此持有对方需要的资源，导致所有参与者都无法继续向前推进。

## 死锁的四个必要条件

1. **互斥条件**：资源一次只能被一个线程或进程占用。
2. **占有并等待**：已经持有资源的同时，还在等待其他资源。
3. **不可抢占**：资源不能被外部强制剥夺，只能由持有者主动释放。
4. **循环等待**：存在一个等待环，例如 A 等 B 的锁，B 等 C 的锁，C 又等 A 的锁。

四个条件同时满足才可能形成死锁。破坏其中任意一个条件，都可以避免死锁。

## 典型死锁场景

最常见的代码场景是两把锁的获取顺序不一致：

```cpp
std::mutex m1, m2;

void f1() {
    std::lock_guard<std::mutex> a(m1);
    std::lock_guard<std::mutex> b(m2);
}

void f2() {
    std::lock_guard<std::mutex> b(m2);
    std::lock_guard<std::mutex> a(m1);
}
```

如果线程 A 执行 `f1` 拿到 `m1`，线程 B 执行 `f2` 拿到 `m2`，随后 A 等 `m2`，B 等 `m1`，就形成循环等待。

修复方式：

```cpp
void f1() {
    std::scoped_lock lk(m1, m2);
}

void f2() {
    std::scoped_lock lk(m1, m2);
}
```

`std::scoped_lock` 会用标准库的死锁避免算法一次性获取多把锁，或者工程上规定所有地方都按统一顺序加锁。

## 常见解决方式

1. **固定加锁顺序**：所有线程按统一顺序获取锁，破坏循环等待。
2. **一次性申请资源**：执行前拿齐所需资源，破坏占有并等待。
3. **加锁超时和 try_lock**：拿不到锁时释放已持有资源并重试。
4. **缩小锁粒度和临界区**：减少持锁时间，降低死锁概率。
5. **死锁检测**：数据库、操作系统可维护等待图，发现环后回滚或杀死一个参与者。

## 出现死锁后怎么发现、定位和解决

发现死锁通常依赖现象和监控：

1. 线程长时间无进展，QPS 下降但 CPU 不高。
2. 请求堆积、线程池活跃线程全部卡住、队列长度持续增长。
3. 锁等待耗时、超时数、慢请求和 watchdog 告警异常。
4. 数据库返回 deadlock 错误或锁等待超时。

定位思路：

1. **抓线程栈**：C++ 服务可以用 `gdb -p <pid>` 后执行 `thread apply all bt`，或用 `pstack <pid>`/`gcore` 保留现场。
2. **看锁等待链**：从调用栈中找线程分别卡在哪把锁、哪个条件变量、哪个 I/O。
3. **查锁顺序日志**：关键锁可以记录 lock/unlock、线程 id、对象 id 和持锁耗时。
4. **数据库死锁**：MySQL 用 `SHOW ENGINE INNODB STATUS` 看 LATEST DETECTED DEADLOCK，定位互相等待的 SQL 和索引。
5. **复现和压测**：把线上堆栈对应的代码路径抽成最小复现，再加 TSan、死锁检测工具或锁顺序断言。

解决方式：

1. 统一多把锁的获取顺序。
2. 用 `std::scoped_lock` 一次性获取多把锁。
3. 减少持锁范围，持锁时不调用外部回调、RPC、磁盘 I/O。
4. 使用 `try_lock`、超时锁和失败回滚，避免永久等待。
5. 对数据库事务缩短事务时间，统一访问表和行的顺序，确保 SQL 命中索引。

## 死锁预防、避免、检测、解除

这四个概念容易混淆：

1. **死锁预防**：在设计上破坏死锁四个必要条件之一，让死锁不可能发生。例如一次性申请所有资源、固定加锁顺序。
2. **死锁避免**：资源分配前判断这次分配是否会让系统进入不安全状态，只在安全时分配。银行家算法属于死锁避免。
3. **死锁检测**：允许死锁发生，周期性构建资源分配图或等待图，发现环后处理。
4. **死锁解除**：检测到死锁后回滚事务、杀死进程、抢占资源或释放锁。

工程里最常用的是预防和检测：代码中通过锁顺序、RAII、超时重试降低死锁概率；数据库通过等待图检测死锁并回滚一个事务。

## 进程调度算法能解决死锁吗

普通 CPU 调度算法本身不负责解决死锁。FCFS、RR、优先级调度、CFS 解决的是“哪个可运行任务先占用 CPU”，而死锁的根因是资源等待环。一个线程即使被调度到 CPU 上运行，如果它等待的锁或资源仍被其他线程持有，仍然无法继续推进。

两者的关系可以这样理解：

1. **调度可以影响死锁暴露概率**：不同调度顺序可能让两个线程更容易交错到互相持锁等待的状态。
2. **调度不能破坏资源等待环**：只要互斥、占有并等待、不可抢占、循环等待同时成立，单纯换一个 CPU 调度策略无法解除死锁。
3. **操作系统可以配合检测和恢复**：内核或数据库可以维护等待图，发现环后杀进程、回滚事务或返回超时错误，但这属于死锁检测/解除，不是调度算法本身。
4. **实时系统会用优先级继承解决优先级反转**：它能避免高优先级任务被低优先级持锁任务间接饿死，但也不等于通用死锁解决方案。

因此面试里如果被问“进程调度算法怎么解决死锁”，建议先纠正前提：调度算法不能直接解决死锁，死锁要从资源分配、加锁顺序、超时回滚、等待图检测和银行家算法等方向处理。

## 银行家算法

银行家算法用于判断资源分配后系统是否仍处于安全状态。它需要知道：

1. `Available`：当前可用资源数量。
2. `Max`：每个进程最多需要的资源。
3. `Allocation`：每个进程已经分配的资源。
4. `Need = Max - Allocation`：每个进程还需要的资源。

判断流程：

1. 假设给某个进程分配资源。
2. 尝试寻找一个进程，使得它的 `Need <= Available`。
3. 找到后认为该进程可以执行完并释放资源：`Available += Allocation`。
4. 重复这个过程。
5. 如果所有进程都能按某个顺序完成，则系统安全；否则这次分配会导致不安全状态，应拒绝。

安全状态不等于当前没有死锁，而是存在一种执行顺序，可以让所有进程最终完成。不安全状态也不等于已经死锁，只是未来可能死锁。

银行家算法的限制：

1. 需要提前知道每个进程最大资源需求，现实中往往很难。
2. 资源类型和数量较多时维护成本高。
3. 更适合操作系统教材模型，通用工程代码中较少直接使用。

## C++ 中的注意事项

1. 使用 `std::lock` 同时获取多个 mutex，避免手写顺序出错。
2. 使用 `std::lock_guard`、`std::unique_lock` 做 RAII，避免异常路径忘记释放锁。
3. 不要在持锁时调用未知外部回调、RPC、耗时 IO，容易放大等待链。
4. 多把锁必须定义全局顺序，例如按对象地址、ID 或层级顺序加锁。

### `std::lock` 和 `std::lock_guard` 怎么组合

C++11/14 里，如果需要同时持有多把锁，可以先用 `std::lock` 以死锁避免算法拿到所有锁，再用 `std::lock_guard` 的 `std::adopt_lock` 接管所有权：

```cpp
#include <mutex>

std::mutex m1;
std::mutex m2;

void update() {
    std::lock(m1, m2);
    std::lock_guard<std::mutex> lk1(m1, std::adopt_lock);
    std::lock_guard<std::mutex> lk2(m2, std::adopt_lock);

    // 同时持有 m1 和 m2
}
```

易错点：

1. `std::adopt_lock` 的前提是当前线程已经持有这把锁，否则行为未定义。
2. `std::lock` 如果中途失败，会释放已经拿到的锁，避免异常路径漏锁。
3. C++17 后更推荐 `std::scoped_lock lk(m1, m2);`，语义更短，也支持多把锁。

### `std::timed_mutex` 的作用

`std::timed_mutex` 在普通互斥锁基础上提供 `try_lock_for` 和 `try_lock_until`，允许线程等待一段时间后放弃：

```cpp
#include <chrono>
#include <mutex>

std::timed_mutex m;

bool tryUpdate() {
    if (!m.try_lock_for(std::chrono::milliseconds(50))) {
        return false;
    }

    std::lock_guard<std::timed_mutex> lk(m, std::adopt_lock);
    // 临界区
    return true;
}
```

它适合做超时降级、避免请求线程无限等待、线上定位锁等待过长等场景。但 `timed_mutex` 不能从根本上修复锁顺序混乱；如果业务存在循环等待，只是把“永久卡死”变成“超时失败和重试”，仍要回到锁层级、临界区和资源依赖设计上处理。

## 面试回答模板

死锁需要四个必要条件：互斥、占有并等待、不可抢占、循环等待。解决时一般破坏其中一个条件，工程里最常用的是固定加锁顺序、减少持锁时间、try_lock/超时重试、RAII 自动释放锁；数据库或操作系统还可以通过等待图检测死锁并回滚其中一个事务。

如果问银行家算法，它属于死锁避免：每次分配前都模拟分配后的状态，检查是否存在一个安全序列让所有进程完成；存在则分配，不存在则拒绝。
