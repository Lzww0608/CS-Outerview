# 死锁

死锁是指多个线程或进程在并发执行时，彼此持有对方需要的资源，导致所有参与者都无法继续向前推进。

## 死锁的四个必要条件

1. **互斥条件**：资源一次只能被一个线程或进程占用。
2. **占有并等待**：已经持有资源的同时，还在等待其他资源。
3. **不可抢占**：资源不能被外部强制剥夺，只能由持有者主动释放。
4. **循环等待**：存在一个等待环，例如 A 等 B 的锁，B 等 C 的锁，C 又等 A 的锁。

四个条件同时满足才可能形成死锁。破坏其中任意一个条件，都可以避免死锁。

## 常见解决方式

1. **固定加锁顺序**：所有线程按统一顺序获取锁，破坏循环等待。
2. **一次性申请资源**：执行前拿齐所需资源，破坏占有并等待。
3. **加锁超时和 try_lock**：拿不到锁时释放已持有资源并重试。
4. **缩小锁粒度和临界区**：减少持锁时间，降低死锁概率。
5. **死锁检测**：数据库、操作系统可维护等待图，发现环后回滚或杀死一个参与者。

## 死锁预防、避免、检测、解除

这四个概念容易混淆：

1. **死锁预防**：在设计上破坏死锁四个必要条件之一，让死锁不可能发生。例如一次性申请所有资源、固定加锁顺序。
2. **死锁避免**：资源分配前判断这次分配是否会让系统进入不安全状态，只在安全时分配。银行家算法属于死锁避免。
3. **死锁检测**：允许死锁发生，周期性构建资源分配图或等待图，发现环后处理。
4. **死锁解除**：检测到死锁后回滚事务、杀死进程、抢占资源或释放锁。

工程里最常用的是预防和检测：代码中通过锁顺序、RAII、超时重试降低死锁概率；数据库通过等待图检测死锁并回滚一个事务。

## 银行家算法

银行家算法用于判断资源分配后系统是否仍处于安全状态。它需要知道：

1. `Available`：当前可用资源数量。
2. `Max`：每个进程最多需要的资源。
3. `Allocation`：每个进程已经分配的资源。
4. `Need = Max - Allocation`：每个进程还需要的资源。

判断流程：

1. 假设给某个进程分配资源。
2. 尝试寻找一个进程，使得它的 `Need <= Available`。
3. 找到后认为该进程可以执行完并释放资源：`Available += Allocation`。
4. 重复这个过程。
5. 如果所有进程都能按某个顺序完成，则系统安全；否则这次分配会导致不安全状态，应拒绝。

安全状态不等于当前没有死锁，而是存在一种执行顺序，可以让所有进程最终完成。不安全状态也不等于已经死锁，只是未来可能死锁。

银行家算法的限制：

1. 需要提前知道每个进程最大资源需求，现实中往往很难。
2. 资源类型和数量较多时维护成本高。
3. 更适合操作系统教材模型，通用工程代码中较少直接使用。

## C++ 中的注意事项

1. 使用 `std::lock` 同时获取多个 mutex，避免手写顺序出错。
2. 使用 `std::lock_guard`、`std::unique_lock` 做 RAII，避免异常路径忘记释放锁。
3. 不要在持锁时调用未知外部回调、RPC、耗时 IO，容易放大等待链。
4. 多把锁必须定义全局顺序，例如按对象地址、ID 或层级顺序加锁。

## 面试回答模板

死锁需要四个必要条件：互斥、占有并等待、不可抢占、循环等待。解决时一般破坏其中一个条件，工程里最常用的是固定加锁顺序、减少持锁时间、try_lock/超时重试、RAII 自动释放锁；数据库或操作系统还可以通过等待图检测死锁并回滚其中一个事务。

如果问银行家算法，它属于死锁避免：每次分配前都模拟分配后的状态，检查是否存在一个安全序列让所有进程完成；存在则分配，不存在则拒绝。
