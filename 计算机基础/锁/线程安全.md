# 线程安全

线程安全是指多个线程同时访问同一段代码或同一份共享数据时，不会因为执行顺序不确定而产生错误结果。它通常涉及三个问题：原子性、可见性和有序性。

## 为什么会不安全

1. **原子性问题**：`count++` 看起来是一行，实际包含读取、加一、写回多个步骤，多线程并发会丢失更新。
2. **可见性问题**：一个线程修改了共享变量，另一个线程可能因为缓存、寄存器或编译优化看不到最新值。
3. **有序性问题**：编译器和 CPU 可能在不改变单线程语义的前提下重排指令，但多线程下会暴露异常结果。

## 常见解决方式

1. **互斥锁**：用 mutex、`synchronized`、`ReentrantLock` 等保护临界区，适合复杂共享状态。
2. **读写锁**：读多写少时允许并发读，写操作独占。
3. **原子操作**：用 CAS、FAA 等硬件原语实现计数器、状态位等简单变量的并发更新。
4. **不可变对象**：对象创建后不再修改，多线程只读天然安全。
5. **线程封闭**：数据只在一个线程内访问，例如 ThreadLocal、Actor 单线程事件循环。
6. **消息传递**：通过 channel、队列、事件总线传递数据，减少共享内存。
7. **并发容器**：使用语言或库提供的线程安全集合，例如 ConcurrentHashMap、sync.Map。

## 什么时候可以去掉锁

项目面试里问“这段代码能不能把上锁解锁去掉”，不要直接回答“可以”或“不可以”，要先证明共享状态是否仍然安全。能去锁通常只有几类情况：

1. **线程封闭**：数据只被一个线程访问，例如单线程 EventLoop、Actor 模型、每个连接固定归属一个 worker。
2. **不可变数据**：对象构造完成后不再修改，多个线程只读同一份快照。
3. **所有权转移**：数据通过队列或 channel 从一个线程移交给另一个线程，同一时刻只有一个所有者。
4. **原子变量足够表达状态**：只有单个计数器、标志位或指针发布，且内存序写对。
5. **无锁数据结构**：用 CAS、序列号、内存屏障和安全回收替代互斥锁，例如 SPSC ring buffer、MPMC queue。
6. **分片降低共享**：全局结构拆成 per-thread/per-cpu/shard，本地更新无锁，低频聚合时再同步。

不能去锁的典型情况：

1. 多个字段之间存在不变量，例如 `size/head/tail` 必须一起保持一致。
2. 容器会扩容、rehash、删除节点，其他线程可能同时读写旧内存。
3. 一段逻辑包含“检查再执行”，例如 `if (!exists) insert()`，单独原子化某个变量不够。
4. 需要条件等待、阻塞唤醒、关闭队列、超时取消等复杂语义。
5. 对象生命周期不清楚，去锁后可能出现 use-after-free。

判断流程可以这样说：

```text
共享状态是什么
-> 哪些线程读写
-> 是否有跨字段不变量
-> 是否有生命周期风险
-> 去锁后用什么机制保证原子性、可见性和有序性
-> 用压测、TSan、单测和代码审查验证
```

示例：一个配置表如果只在启动时构造，运行期只读，可以去掉读锁；如果运行期需要热更新，可以改成构造新快照后用原子指针发布，旧快照用 `shared_ptr`/RCU 延迟释放。但如果是普通 `unordered_map` 一边读一边写，不能靠“读多写少”去掉锁，因为 rehash 和节点释放会破坏读线程安全。

## 线程安全和可重入函数的区别

**线程安全**关注的是多个线程同时调用同一段代码或访问同一份共享数据时，结果是否仍然正确。它可以通过锁、原子操作、不可变对象、线程局部存储等方式实现。

**可重入函数**关注的是函数在一次调用尚未结束时，又被同一个线程或其他执行流再次进入，是否仍然正确。典型重入场景包括信号处理函数中再次调用、递归调用、回调中再次进入同一函数。可重入函数通常不依赖可变的全局变量、静态局部变量或共享缓冲区，只使用栈变量、参数和调用方显式传入的上下文。

两者关系可以这样理解：

1. 可重入函数通常更容易做到线程安全，因为它不持有隐藏的共享可变状态。
2. 线程安全函数不一定可重入。例如函数内部用普通互斥锁保护全局状态，多线程调用是安全的，但如果信号处理函数或回调在持锁期间再次进入，可能因为重复加锁而死锁。
3. 可重入也不等于所有场景都线程安全。如果调用方把同一份可变上下文传给多个线程，而函数本身不做同步，仍然会有数据竞争。
4. `malloc`、日志库、标准 I/O 这类库函数可能是线程安全的，但通常不适合在信号处理函数里调用，因为它们可能内部加锁或修改复杂全局状态。

常见例子：

```c
// 不可重入：返回静态缓冲区，下一次调用会覆盖上一次结果
char *format_time_bad(time_t t) {
    static char buf[64];
    struct tm *tm = localtime(&t);
    strftime(buf, sizeof(buf), "%F %T", tm);
    return buf;
}

// 更好的方向：缓冲区由调用方提供
void format_time(char *buf, size_t n, time_t t) {
    struct tm tm_buf;
    localtime_r(&t, &tm_buf);
    strftime(buf, n, "%F %T", &tm_buf);
}
```

工程中判断一个函数是否可重入，可以看它是否使用了隐藏共享状态、是否在内部加锁、是否调用了不可重入函数。Linux 信号处理函数尤其严格，通常只设置 `sig_atomic_t` 标记、写 pipe/eventfd，复杂逻辑交给主循环处理。

## 读方法和自增方法如何保证并发安全

如果一个类里有读方法和自增方法，例如：

```cpp
class Counter {
public:
    int get() const;
    void inc();

private:
    int value_ = 0;
};
```

要先判断共享状态是不是只有一个整数。

### 1. 单个计数器

如果只有一个计数值，且读操作只需要读到某个原子时刻的值，可以直接用原子变量：

```cpp
#include <atomic>

class Counter {
public:
    int get() const {
        return value_.load(std::memory_order_relaxed);
    }

    void inc() {
        value_.fetch_add(1, std::memory_order_relaxed);
    }

private:
    std::atomic<int> value_{0};
};
```

这里 `relaxed` 足够用于纯计数，不表达跨变量的顺序关系。如果 `inc()` 后还要发布其他数据，就需要考虑 `release/acquire` 或用锁保护整体状态。

### 2. 多字段不变量

如果自增时还要同时修改多个字段，例如 `value_`、`version_`、`updated_at_` 必须保持同一个版本，不能把每个字段简单改成原子变量。此时要用同一把锁保护整体不变量：

```cpp
#include <mutex>

class Counter {
public:
    int get() const {
        std::lock_guard<std::mutex> lock(mu_);
        return value_;
    }

    void inc() {
        std::lock_guard<std::mutex> lock(mu_);
        ++value_;
        ++version_;
    }

private:
    mutable std::mutex mu_;
    int value_ = 0;
    int version_ = 0;
};
```

读多写少时可以把 `mutex` 换成读写锁：读方法加共享锁，自增方法加独占锁。但如果写很频繁，读写锁内部维护读者计数也会有竞争，可能不如普通互斥锁。

### 3. 不可变快照

如果读路径非常高频、写很少，可以构造新快照后原子替换指针，读线程只读不可变对象：

```text
writer: build new Snapshot -> atomic publish
reader: atomic load Snapshot -> read fields
```

这种方式适合配置、路由表、实验参数等读多写少场景，代价是写入时要复制或重建快照，并处理旧快照生命周期。

## 易错点

1. 线程安全不是“加了锁就一定安全”，锁的范围、锁顺序、异常释放都可能出问题。
2. 原子变量只能保证单个变量的原子操作，多个变量之间的不变量仍然需要锁或事务。
3. `volatile` 通常解决可见性和禁止部分重排序，不等价于互斥锁，不能保证复合操作原子性。
4. 读多写少才适合读写锁；写多时读写锁可能比普通互斥锁更慢。
5. 无锁结构也需要考虑 ABA、内存回收和内存序，不是简单使用 CAS 就结束。

## 面试回答模板

可以先定义线程安全，再从问题来源和解决手段回答：

> 线程安全是多个线程并发访问共享资源时仍能得到正确结果。问题通常来自原子性、可见性和有序性。解决方式包括减少共享、不可变设计、线程封闭、消息传递；必须共享时用互斥锁、读写锁、原子操作或并发容器。真实业务里还要根据读写比例、临界区大小和一致性要求选择方案。

如果类里只有一个计数器，读方法和自增方法可以用 `std::atomic`；如果有多个字段必须整体一致，就要用同一把互斥锁或读写锁保护整个临界区。读多写少可以考虑读写锁或不可变快照，写多时普通 mutex 往往更简单稳定。
