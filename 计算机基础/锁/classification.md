# 锁的分类

| 分类                            | 机制名称                 | 线程状态      | 核心原理与特征                                               | 适用场景                                                     |
| :------------------------------ | :----------------------- | :------------ | :----------------------------------------------------------- | :----------------------------------------------------------- |
| **1. 忙等待类**<br>(不释放CPU)  | **自旋锁 (Spinlock)**    | 忙循环 (Spin) | 循环检测锁状态。**开销小，但不公平，且浪费CPU。**            | 临界区极小（几条指令），且不可睡眠的场景（如中断上下文）。   |
|                                 | **Ticket Lock**          | 忙循环        | **排队叫号机制**。解决了自旋锁的“不公平”问题，但仍有缓存抖动。 | 需要公平性（FIFO）的自旋场景。                               |
|                                 | **MCS / CLH Lock**       | 忙循环        | **基于链表的队列锁**。线程只在本地变量自旋，减少总线竞争。   | 多核、高并发下的自旋场景（Java AQS底层参考了CLH）。          |
| **2. 睡眠/阻塞类**<br>(释放CPU) | **互斥锁 (Mutex)**       | 睡眠 (Sleep)  | 拿不到锁就挂起，等待唤醒。**有上下文切换开销。**             | 临界区较长，或者临界区内可能发生阻塞/睡眠。                  |
|                                 | **信号量 (Semaphore)**   | 睡眠          | **计数器机制**。允许 N 个线程同时访问。                      | 资源池管理（如数据库连接池），或控制并发数量。               |
|                                 | **条件变量 (Cond Var)**  | 睡眠          | 依赖互斥锁，**等待特定条件满足**（Wait/Notify）。            | 生产者-消费者模型，线程间的协调通知。                        |
|                                 | **Futex**                | 混合          | **快慢路径结合**。无竞争时在用户态（原子操作），竞争时才陷入内核睡眠。 | Linux下大多数现代互斥锁的底层实现，性能优异。                |
|                                 | **自适应锁 (Adaptive)**  | 先自旋后睡眠  | 尝试自旋一小会儿，如果不成功再睡眠。                         | 这种智能策略是现代操作系统（如Solaris, Linux）互斥锁的默认行为。 |
| **3. 读写优化类**<br>(区分读写) | **读写锁 (RW Lock)**     | 睡眠/自旋皆有 | **读共享，写独占**。写锁优先级通常较低（可能导致写饥饿）。   | 读多写少，且读者对数据实时性要求高的场景。                   |
|                                 | **顺序锁 (Seqlock)**     | 读自旋/写自旋 | **版本号机制**。写者不阻塞读者，读者发现版本号变了就重试。   | 读多写少，且**写操作优先级极高**（不允许写者被读者饿死）的场景。 |
|                                 | **StampedLock**          | 混合          | **乐观读**。先假设没锁去读，读完校验版本。比RWLock快。       | Java 8+ 中对性能要求极高的读多写少场景。                     |
|                                 | **RCU**                  | **读无锁**    | **写时复制 + 宽限期**。读者完全无开销，写者负责回收旧数据。  | **读极多写极少**（如路由表、目录项），对数据实时性要求不严苛。 |
| **4. 底层与无锁**<br>(基础原语) | **原子操作 (Atomic)**    | 无锁          | **CAS / FAA**。硬件指令保证单变量操作的原子性。              | 计数器、标志位、无锁数据结构（Lock-free Queue）。            |
|                                 | **内存屏障 (Barrier)**   | -             | 禁止指令重排序，保证内存可见性。                             | 实现锁的底层工具，或驱动开发中控制硬件时序。                 |
|                                 | **Per-CPU 变量**         | 无锁          | **数据分片**。每个CPU只操作自己的数据，完全无竞争。          | 统计计数、缓存分配等追求极致性能的场景。                     |
| **5. 辅助控制**                 | **栅栏 (CyclicBarrier)** | 睡眠等待      | **集合点**。所有线程都到达栅栏位置后，才能一起继续。         | 并行计算中，需要多线程分阶段同步的场景。                     |
|                                 | **倒计时 (Latch)**       | 睡眠等待      | **减法计数**。等待 N 个任务执行完毕。                        | 主线程等待子线程初始化完成。                                 |

## C++ 常见锁和同步工具

面试问“C++ 有哪些锁”时，可以把标准库里的锁对象、锁管理器和同步原语分开回答。

| 类型 | 代表组件 | 作用和注意点 |
| --- | --- | --- |
| 互斥锁 | `std::mutex` | 最常用的独占锁，保护共享数据不变量；同一线程重复加锁会死锁。 |
| 递归互斥锁 | `std::recursive_mutex` | 允许同一线程重复加锁，但容易掩盖设计问题，工程上应谨慎使用。 |
| 定时互斥锁 | `std::timed_mutex`、`std::recursive_timed_mutex` | 支持 `try_lock_for/try_lock_until`，适合需要超时退出的场景。 |
| 读写锁 | `std::shared_mutex`、`std::shared_timed_mutex` | 多读共享、写独占，适合读多写少；要关注写饥饿和升级锁问题。 |
| 锁管理器 | `std::lock_guard`、`std::unique_lock`、`std::scoped_lock` | 不是锁本身，而是 RAII 管理加锁和解锁；`unique_lock` 可手动解锁并配合条件变量，`scoped_lock` 适合一次拿多把锁。 |
| 条件变量 | `std::condition_variable` | 不是互斥锁，负责等待和通知；必须和互斥锁、谓词一起使用，避免丢通知和虚假唤醒。 |
| 原子变量 | `std::atomic<T>` | 适合单变量计数器、状态位和无锁结构；不能替代多字段不变量的互斥保护。 |
| C++20 同步工具 | `std::counting_semaphore`、`std::binary_semaphore`、`std::latch`、`std::barrier` | 控制资源数量、等待一组任务完成或让多线程分阶段推进。 |

真实项目里选择锁要看临界区长度、读写比例、竞争程度和是否需要等待条件。短临界区可以考虑自旋或原子；普通共享状态优先 `std::mutex + RAII`；读多写少可以用读写锁；生产者消费者通常是 `mutex + condition_variable + 有界队列`。不要因为“无锁更快”就默认使用 atomic，复杂不变量用一把清晰的锁往往更可靠。

## 简单对比总结

*   **最快但最危险：** Per-CPU 变量（完全无锁）。
*   **读性能之王：** RCU（读者几乎零开销）。
*   **最通用：** Mutex（配合 Futex 优化）。
*   **短任务首选：** Spinlock。
*   **Java/高级语言常用：** Monitor (`synchronized`), StampedLock, AQS (CLH变种)。
