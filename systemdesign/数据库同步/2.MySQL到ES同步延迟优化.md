# 2. MySQL 到 ES 同步延迟优化

MySQL 到 Elasticsearch 同步通常是把 MySQL 作为权威写库，把 ES 作为搜索和复杂查询的读模型。同步延迟来自 binlog 产生、采集、消息队列、索引写入、ES refresh 和下游消费积压等多个环节。

## 1. 典型链路

```text
MySQL commit
  -> binlog
  -> Canal / Debezium
  -> MQ
  -> Indexer 消费
  -> bulk 写 ES
  -> ES refresh 后可搜索
```

其中 MySQL 保证权威数据正确，ES 负责按搜索场景组织倒排索引和聚合字段。业务上通常接受最终一致，但要明确最大可接受延迟。

## 2. 延迟来源

1. **MySQL 写入侧**：大事务、DDL、binlog 刷盘、主库压力过高。
2. **采集侧**：Canal/Debezium 解析慢、位点落后、网络抖动。
3. **MQ 侧**：topic 分区不足、消费者组 rebalance、消息堆积。
4. **Indexer 侧**：消费并发不足、单条写 ES、序列化或字段转换过慢。
5. **ES 侧**：bulk 太小或太大、refresh 间隔、分片热点、merge 压力、mapping 设计不合理。
6. **一致性保护**：为了幂等和顺序做串行化，吞吐可能下降。

## 3. 优化思路

### 3.1 链路观测

先把延迟拆开，而不是只看最终搜索结果慢。

关键指标：

1. MySQL 当前 binlog 位点和采集组件消费位点差距。
2. MQ lag、堆积条数、最老消息年龄。
3. Indexer 消费 QPS、失败率、重试数、单批耗时。
4. ES bulk 写入耗时、拒绝数、refresh/merge/thread pool 指标。
5. 端到端延迟：数据更新时间到 ES 可查询时间。

### 3.2 提高消费吞吐

1. MQ 按业务 key 分区，提高并行消费能力。
2. Indexer 水平扩容，消费者数不超过有效分区数。
3. 使用 ES Bulk API，按条数和字节数控制批量。
4. 将字段转换、富化、序列化做成批处理。
5. 对失败消息做重试和死信队列，避免单条坏数据阻塞整个分区。

### 3.3 优化 ES 写入

1. 合理设置 `refresh_interval`，高写入期可以调大，降低频繁 refresh 成本。
2. 控制 shard 数量，避免分片过多或热点分片。
3. mapping 明确字段类型，避免动态 mapping 引发冲突。
4. 不需要分词的字段用 `keyword`，减少索引膨胀。
5. 使用外部版本号或更新时间字段保证幂等，避免旧消息覆盖新数据。

### 3.4 保证最终一致

同步链路可能重复、乱序或延迟，因此写 ES 要幂等：

```text
document_id = business_primary_key
version = update_time / binlog position /业务版本号
```

处理规则：

1. 同一个主键多次更新，只保留最新版本。
2. 消息重复消费时，写入结果不变。
3. 删除事件要能正确转成 ES delete 或软删除字段。
4. 全量重建和增量同步要记录切换位点，避免漏数据。

## 4. 查询侧兜底

如果业务要求“写后立刻可见”，不能只依赖 ES 最终一致链路。

常见兜底：

1. 写后短时间查询主库。
2. 查询 ES 后按主键回源 MySQL 校验关键字段。
3. 页面提示搜索结果有秒级延迟。
4. 对强一致场景不使用 ES 作为唯一判定依据。

## 5. 易错点

1. 不要承诺 MySQL 到 ES 强一致，除非引入同步写和很高成本。
2. 延迟不一定在 Canal，也可能在 MQ、Indexer、ES refresh 或分片 merge。
3. bulk 不是越大越好，太大会增加单批延迟和失败重试成本。
4. 只按主键分区可能保证单 key 顺序，但热点 key 会造成分区倾斜。
5. ES 里旧文档覆盖新文档是常见事故，必须用版本号或更新时间防护。

## 6. 面试回答模板

MySQL 到 ES 同步一般走 binlog -> Canal/Debezium -> MQ -> Indexer -> ES bulk 写入，属于最终一致链路。优化延迟要先拆指标，看 binlog 位点差、MQ lag、消费耗时、bulk 写入耗时和 ES refresh/merge。吞吐上可以增加 MQ 分区和消费者、批量写 ES、优化字段转换；ES 侧调 `refresh_interval`、shard 和 mapping。正确性上用业务主键做 document id，用更新时间、binlog 位点或版本号做幂等，防止重复和乱序覆盖。强一致读要回源 MySQL 或做写后读主库兜底，不能默认 ES 立即可见。
