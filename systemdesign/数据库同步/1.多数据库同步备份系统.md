# 多数据库同步备份系统

多数据库同步备份系统的目标是把不同数据库中的数据稳定、可恢复地复制到备库、数仓、对象存储或灾备中心。面试中不要只回答“定时 dump”，要把全量、增量、一致性、恢复和多数据源适配讲清楚。

## 1. 核心架构

一个支持很多数据库的同步备份系统通常拆成以下模块：

1. **Connector 层**：为 MySQL、PostgreSQL、MongoDB、Redis、ClickHouse 等数据库实现独立连接器，屏蔽协议、权限、分页、游标和日志格式差异。
2. **元数据中心**：保存任务配置、库表白名单、字段映射、主键、分片规则、checkpoint、schema 版本和运行状态。
3. **全量采集器**：对存量数据做快照导出，按主键范围、时间范围或物理分片拆分任务。
4. **增量采集器**：消费 MySQL binlog、PostgreSQL WAL、MongoDB oplog 或业务 CDC 日志，捕获 insert、update、delete、DDL。
5. **标准化事件模型**：把不同数据库事件转成统一格式，例如 `{source, table, op, pk, before, after, ts, txid}`。
6. **传输和削峰层**：使用 Kafka、Pulsar、RocketMQ 或内部队列承接增量事件，提供重放、限速和背压能力。
7. **写入与备份层**：写入目标库、数据湖、对象存储或归档文件，并支持压缩、加密、校验和生命周期管理。
8. **监控与恢复层**：监控延迟、吞吐、失败率、checkpoint 推进、数据校验差异，并定期做恢复演练。

## 2. 全量同步和增量同步

全量同步解决历史数据，增量同步解决全量期间和之后发生的新变更。常见流程：

1. 记录源库当前增量位点，例如 binlog file/pos、GTID、WAL LSN、oplog timestamp。
2. 开始全量快照，按主键或分片并发扫描数据。
3. 全量数据写入目标端，写入过程要幂等，避免重试导致重复数据。
4. 全量完成后，从第 1 步记录的位点开始回放增量。
5. 当增量延迟追平后切换为持续同步。

全量快照要关注一致性。如果源库支持事务快照，优先使用 MVCC 一致性读；如果不支持，需要短暂加锁、按业务时间切片，或接受弱一致后用校验任务修正。

## 3. 多数据库适配怎么设计

多数据库系统的关键不是把所有逻辑写死在一个采集器里，而是设计稳定的抽象接口：

```text
SourceConnector
  -> discoverSchema()
  -> createSnapshotReader(split)
  -> createChangeReader(checkpoint)
  -> parseDDL(event)
  -> commitCheckpoint(position)
```

需要重点处理：

1. **类型映射**：例如 MySQL `datetime`、PostgreSQL `timestamp with time zone`、MongoDB document、ClickHouse Array 类型在目标端可能没有完全等价类型。
2. **主键缺失**：没有主键的表很难幂等更新，通常要求补充唯一键，或退化为追加日志加离线合并。
3. **DDL 变更**：新增列、删除列、改类型要记录 schema 版本，写入端按版本解析事件。
4. **事务语义**：单表同步可以按行事件处理，跨表事务则要按事务边界提交，否则目标端可能短暂看到半事务状态。
5. **大小库差异**：小库可以周期快照，大库必须分片全量 + CDC，否则备份窗口过长。

## 4. 一致性和可靠性

同步备份通常很难做到真正的端到端 exactly once，工程上更常见的是“至少一次投递 + 幂等写入 + checkpoint”：

1. **checkpoint**：记录已经成功写入并可恢复的源端位点，进程重启后从 checkpoint 继续。
2. **幂等写入**：目标端按主键 upsert，或用事件唯一 ID 去重。
3. **顺序保证**：同一主键或同一分片的事件必须有序，避免旧更新覆盖新更新。
4. **失败重试**：可重试错误进入退避重试，不可重试错误进入死信队列并告警。
5. **数据校验**：按行数、主键范围 checksum、抽样比对、业务聚合值校验发现不一致。
6. **恢复演练**：备份系统价值取决于能否恢复，必须定期验证 RPO、RTO 和恢复脚本。

## 5. 备份存储设计

面向恢复的备份不只是同步到另一个库，还需要可长期保存和可审计：

1. **分层存储**：热备库用于快速切换，冷备份放对象存储或归档存储。
2. **文件格式**：结构化数据可使用 Parquet、ORC、Avro、CSV；日志事件可使用 JSON 或 Protobuf。
3. **压缩和加密**：使用 zstd、snappy、gzip 压缩，敏感数据在传输和落盘时加密。
4. **保留策略**：按天、周、月保留快照，增量日志保留到能覆盖任意时间点恢复。
5. **PITR**：Point-In-Time Recovery 依赖一次全量快照加一段连续增量日志。

## 6. 易错点

1. 只做全量 dump 不能满足持续同步，也无法保证较小的 RPO。
2. 只记录任务成功失败不够，必须记录可恢复的源端位点。
3. 多线程并发同步不能破坏同一主键或同一事务内事件顺序。
4. 目标端写入成功后再提交 checkpoint，否则失败恢复可能丢数据。
5. 备份没有恢复演练等于没有备份，面试中要主动提恢复验证。
6. 数据库异构同步不能忽略类型精度、时区、字符集和 DDL 演进。

## 7. 真实场景

1. **业务灾备**：主库跨机房同步到备库，主机房故障时根据 checkpoint 和延迟指标切换。
2. **数据分析**：MySQL binlog 经 Flink CDC 进入 Kafka，再写入 Hive、Iceberg 或 ClickHouse。
3. **审计归档**：把变更事件压缩加密后写入对象存储，保留多年用于追溯。
4. **数据库迁移**：先全量迁移，再增量追平，最后短暂停写完成割接。

## 8. 面试回答模板

我会把多数据库同步备份系统拆成 Connector、元数据、全量采集、增量 CDC、消息队列、写入备份、监控恢复几层。全量阶段先记录增量位点，再按主键范围并发快照；全量完成后从该位点回放 binlog、WAL 或 oplog，追平后进入持续同步。可靠性上用 checkpoint 保证可恢复，用幂等写入和事件去重应对重复投递，用同一主键分区保证顺序。备份端要考虑压缩、加密、保留策略和 PITR，最后必须通过 checksum 和恢复演练验证数据真的可用。
