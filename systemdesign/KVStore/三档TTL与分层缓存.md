# 三档 TTL 与分层缓存

三档 TTL 是一种按数据重要性、变化频率和可接受陈旧程度来设置不同缓存过期策略的方式。分层缓存则是把本地缓存、分布式缓存和数据库组合起来，尽量让热点读在更近、更快的一层命中。

## 1. 为什么要分层

典型链路：

```text
本地缓存 Caffeine/进程内 LRU
  -> Redis / 分布式缓存
  -> MySQL / 权威存储
```

各层取舍：

| 层级 | 优点 | 缺点 | 适合数据 |
| --- | --- | --- | --- |
| 本地缓存 | 延迟最低、无网络开销 | 多实例不一致、容量小 | 热点配置、字典、只读快照 |
| Redis | 跨实例共享、数据结构丰富 | 网络开销、依赖外部集群 | 热点对象、计数、幂等、排行榜 |
| MySQL | 权威、事务、可持久化 | QPS 和延迟成本高 | 真实业务数据 |

每一层的职责要分清：

1. **本地缓存**：服务进程内最快的一层，只放低基数、热点、可短暂陈旧的数据，例如配置、字典、商品热点摘要。它主要降低 Redis 网络开销，但多实例之间天然不一致，必须有短 TTL、版本号或消息通知兜底。
2. **Redis**：跨实例共享的分布式缓存，承接大多数热点读、空值缓存、布隆过滤器、幂等标记、限流计数等能力。它比数据库快，但不是权威源，写入失败或数据丢失时要能从数据库恢复。
3. **数据库**：最终事实来源，负责事务、约束和持久化。余额、库存扣减、订单状态这类强一致结果必须以数据库或专门的事务存储为准，缓存只能做读优化。

典型读链路：

```text
读本地缓存
  -> 未命中读 Redis
  -> Redis 未命中读 MySQL
  -> 回填 Redis
  -> 回填本地缓存
```

典型写链路：

```text
更新 MySQL
  -> 提交成功
  -> 删除 Redis
  -> 通过 MQ/binlog 通知各实例删除本地缓存
```

分层的目标不是把所有数据都缓存三份，而是让读路径优先命中更便宜的层，并在缓存失效时有可控回源。

## 2. 三档 TTL 怎么设计

可以按数据变化频率划分：

| 档位 | TTL | 适用场景 | 说明 |
| --- | --- | --- | --- |
| 短 TTL | 秒级到分钟级 | 价格、状态、库存展示 | 新鲜度优先，命中率相对低 |
| 中 TTL | 分钟级到小时级 | 商品摘要、用户标签、广告候选 | 命中率和新鲜度折中 |
| 长 TTL | 小时级到天级 | 配置、字典、静态规则 | 命中率优先，配合版本号失效 |

真实系统还会叠加：

1. **随机抖动**：`ttl = base + random(0, jitter)`，避免同一批 key 同时过期。
2. **逻辑过期**：缓存值里带过期时间，读到旧值可以先返回，再后台刷新。
3. **版本号**：key 或 value 带版本，发布新版本时自然切换。
4. **主动失效**：数据库更新后通过 MQ/binlog/配置中心通知删除或刷新缓存。

## 3. key 和 value 怎么设计

key 要表达业务维度、版本和隔离边界：

```text
业务前缀:租户:用户/对象:版本:字段维度
ad:profile:user:123:v5
goods:detail:sku:10086:v2
```

设计原则：

1. 租户、用户、地域、实验分组等隔离维度不能漏。
2. key 不能过长，否则浪费内存和网络带宽。
3. 能用版本号切换的，不要全量扫描删除。
4. 热点 key 要考虑拆分、复制或本地缓存兜底。

value 不一定是数据库整行，通常是按读路径裁剪后的查询模型：

1. 页面只需要摘要，就不要缓存完整大对象。
2. value 中可以带 `expireAt`、`version`、`source`、`lastRefreshTime`，便于判断旧值和排查问题。
3. 大 value 要警惕序列化成本、网络传输和 Redis 大 key。

## 4. 如何知道访问哪一档缓存

常见方式：

1. **按业务配置**：不同 key pattern 配置缓存层级和 TTL，例如 `goods:*` 走本地 + Redis，`order:*` 只走 Redis 或直接查库。
2. **按数据标签**：数据注册时标注变化频率、重要性和最大可陈旧时间。
3. **按命中统计动态调整**：监控命中率、回源耗时、更新频率，自动把高热点提升到本地缓存。
4. **按降级策略**：Redis 慢或不可用时，本地缓存允许返回短时间旧值，强一致数据则 fail closed。

工程上通常先用配置驱动，足够稳定后再加入动态策略。动态策略要能回滚，避免错误配置把强一致数据放进长 TTL 本地缓存。

## 5. 拿到过期值怎么办

要看业务能否接受陈旧数据。

1. **强一致读**：不返回过期值，直接回源或返回失败。
2. **弱一致读**：返回旧值，同时异步刷新，降低用户等待。
3. **逻辑过期 + 互斥刷新**：只有一个线程拿刷新锁回源，其他线程返回旧值或等待短时间。
4. **stale-if-error**：回源失败或下游故障时，允许返回短时间旧值兜底。

面试里要说清楚：返回旧值可以降低尾延迟和雪崩风险，但会牺牲新鲜度，适合广告候选、推荐配置、非强一致展示，不适合余额、库存扣减、支付状态。

## 6. 指标和真实应用

需要监控：

1. 各层命中率：本地命中率、Redis 命中率、总命中率。
2. 回源 QPS 和回源 P99。
3. 旧值返回次数和最大陈旧时间。
4. 热点 key、大 key、缓存重建耗时。
5. 删除/刷新消息延迟和失败重试。

真实场景：

1. 广告 SDK：本地缓存广告候选，数量有限，展示时快速选择；过期后后台刷新。
2. 商品详情：本地缓存热点摘要，Redis 存完整展示模型，MySQL 是权威源。
3. 配置中心：本地不可变快照 + 版本号，Redis 或配置服务做分发。

## 7. 易错点

1. 分层缓存不是越多越好，每多一层都增加一致性和排查成本。
2. TTL 不能替代主动失效，数据更新频繁时只靠 TTL 会长时间读旧值。
3. 本地缓存容量小，不能放用户级高基数大对象。
4. 命中率不能只看整体，要按接口、key 类型和热点分布拆开看。
5. 缓存配置要和权限、租户、实验分组一起考虑，避免串数据。

## 8. 面试回答模板

三档 TTL 是按数据变化频率和可接受陈旧程度设置不同过期时间：短 TTL 保新鲜，中 TTL 折中，长 TTL 追求命中率。分层缓存通常是本地缓存、Redis、MySQL，读路径从近到远查，写路径先写权威存储，再删除或刷新缓存。key 要包含业务前缀、对象 ID、租户、版本和必要维度；value 只存读路径需要的查询模型，并带版本和刷新时间。是否返回过期值取决于业务一致性要求，广告候选、配置这类可以 stale-while-revalidate，余额库存这类不能随便返回旧值。
