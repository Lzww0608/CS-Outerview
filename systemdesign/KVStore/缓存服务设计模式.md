# 缓存服务设计模式

面试里问“如果开发一个缓存服务会使用什么模式”，要先区分缓存的读写模式，再说明淘汰、分片、一致性、故障降级和热点治理。

## 1. 缓存读写模式

### Cache Aside

业务代码先读缓存，未命中再读数据库，并把结果写回缓存。更新时通常先更新数据库，再删除缓存。

适用场景：

1. 最常见，业务可控性强。
2. 适合缓存不是唯一数据源的系统。
3. 可以针对不同 key 设置不同 TTL 和降级策略。

注意事项：更新数据库后更推荐删除缓存而不是直接写缓存，减少并发写入下的旧值覆盖问题。

### Read Through

业务只访问缓存层，缓存层自己负责未命中时加载后端数据源。它把加载逻辑封装在缓存服务内部。

适用场景：

1. 多个业务共享同一类缓存加载逻辑。
2. 希望业务代码不感知数据源细节。
3. 可接受缓存层复杂度提高。

### Write Through

写请求先写缓存，缓存同步写数据库，两个都成功才返回。优点是一致性较好；缺点是写延迟更高，缓存服务和数据库强耦合。

### Write Back

写请求先写缓存并返回，后续异步刷回数据库。优点是写入吞吐高；缺点是缓存故障可能丢数据，需要 WAL、复制和刷盘机制兜底。

### Refresh Ahead

在热点 key 过期前提前异步刷新，避免大量请求同时穿透到后端。适合热点稳定、加载成本高、延迟敏感的场景。

## 2. 缓存服务核心设计

一个缓存服务至少要考虑：

1. **数据结构**：字符串、哈希、列表、集合、Sorted Set、Bitmap、HyperLogLog 等。
2. **淘汰策略**：TTL、LRU、LFU、分段 LRU、按成本淘汰。
3. **分片策略**：固定哈希、一致性哈希、虚拟节点、范围分片。
4. **复制与高可用**：主从复制、哨兵、Raft/一致性复制、故障转移。
5. **持久化**：RDB 快照、AOF 日志、WAL 或无持久化纯缓存。
6. **协议层**：Redis 协议、自定义二进制协议、HTTP/gRPC 管理面。
7. **可观测性**：命中率、延迟、内存、淘汰数、热 key、慢请求和复制延迟。

## 3. 一致性设计

缓存和数据库之间无法天然强一致，常见策略是根据业务容忍度选择：

1. **旁路缓存 + 删除缓存**：更新数据库成功后删除缓存，下一次读再加载。
2. **延迟双删**：更新数据库后删除缓存，短暂延迟后再删一次，降低并发读写导致的脏缓存概率。
3. **版本号/CAS**：缓存值带版本，写入时只允许新版本覆盖旧版本。
4. **Binlog 订阅**：通过 Canal、Debezium 等订阅数据库变更，异步刷新或删除缓存。
5. **强一致读**：对余额、库存等关键链路直接读主库或走事务，不依赖缓存判断最终正确性。

## 4. 热点与击穿治理

1. **缓存穿透**：查询不存在的数据。解决方式是布隆过滤器、空值缓存、参数校验。
2. **缓存击穿**：热点 key 过期瞬间大量请求打到数据库。解决方式是互斥加载、逻辑过期、refresh ahead。
3. **缓存雪崩**：大量 key 同时过期或缓存集群故障。解决方式是 TTL 加随机抖动、多级缓存、限流降级。
4. **大 key**：单个 key 过大导致阻塞和迁移困难。解决方式是拆分、分页、压缩或改数据模型。
5. **热 key**：单 key 流量过大打爆一个分片。解决方式是本地缓存、读副本、key 分裂、请求合并。

## 5. 本地缓存和分布式缓存

本地缓存延迟最低，但容量受单机内存限制，且多实例一致性弱。适合存放配置、字典、热点只读数据、概率查找表等读多写少数据。

分布式缓存容量和共享能力更强，但有网络开销和集群故障风险。真实系统常做多级缓存：

```text
process local cache -> Redis cluster -> database
```

本地缓存命中直接返回；未命中查 Redis；Redis 未命中再查数据库。更新时通过 MQ、配置中心、binlog 或版本号通知各节点失效。

## 6. 面试回答模板

如果设计缓存服务，我会优先使用 Cache Aside：读缓存，未命中查数据库并回填；写路径先更新数据库再删除缓存。缓存层要支持 TTL、LRU/LFU、分片、复制、持久化和指标监控。对热点 key 使用本地缓存、互斥加载或逻辑过期，对穿透使用布隆过滤器和空值缓存，对雪崩给 TTL 加随机抖动并准备限流降级。对于写入吞吐特别高且能接受短暂丢失风险的场景，可以考虑 Write Back，但要配 WAL 和异步刷盘来控制风险。
