# 分布式云盘上传下载流程

分布式云盘的核心思路是把“元数据控制面”和“文件数据面”拆开：元数据服务负责目录树、权限、版本、分块映射和状态流转，数据服务或对象存储负责真正的大文件块读写。这样 API 服务不会被大文件连接拖垮，数据面也可以按带宽和存储容量独立扩容。

## 1. 核心组件

1. **客户端**：负责登录态维护、文件分块、哈希计算、断点续传、本地变更监听和本地索引缓存。
2. **API Gateway**：负责鉴权、限流、灰度、负载均衡和 TLS 终止。
3. **Metadata Service**：维护文件树、用户权限、版本号、分片清单、上传会话状态。
4. **Metadata DB**：保存强一致元数据，常用 MySQL 分库分表或 NewSQL。
5. **Block Service / Object Storage**：存储文件块，可以自建块服务，也可以让客户端拿预签名 URL 直传 S3、OSS、MinIO、Ceph。
6. **Cache**：缓存用户信息、目录列表、热门文件元数据、分块索引。
7. **Message Queue**：异步触发通知、索引构建、杀毒扫描、缩略图生成、冷热迁移。
8. **Notification Service**：通过长轮询、WebSocket 或推送通道通知其他设备拉取增量变更。

## 2. 上传流程

典型大文件上传流程：

1. 客户端计算文件整体 hash，并按固定大小或内容定义分块切成 chunk。
2. 客户端向 Metadata Service 发起 `initUpload`，携带文件名、大小、整体 hash、chunk hash 列表和目标目录。
3. Metadata Service 做权限检查、目录冲突检查、配额检查和去重检查。
4. 如果整体 hash 或部分 chunk 已存在，服务端返回可秒传的块列表；客户端只上传缺失 chunk。
5. 对缺失 chunk，服务端返回上传 token、Block Service 地址或对象存储预签名 URL。
6. 客户端并发上传 chunk，每个 chunk 携带 `uploadId`、`chunkIndex`、`chunkHash`、`offset`、`size`。
7. Block Service 校验 chunk hash，写入对象存储，并把 chunk 完成状态写回元数据或临时上传表。
8. 客户端调用 `completeUpload`，Metadata Service 校验所有 chunk 均完成，原子创建文件版本和 `file_block_map`。
9. Metadata Service 投递文件变更事件到消息队列，通知其他设备、搜索索引和后台任务。

简化接口：

```text
POST /files/uploads/init
PUT  /files/uploads/{uploadId}/chunks/{chunkIndex}
GET  /files/uploads/{uploadId}/chunks
POST /files/uploads/{uploadId}/complete
```

## 3. 下载流程

典型下载流程：

1. 客户端请求文件元数据，携带文件 ID 和期望版本号。
2. Metadata Service 校验用户权限，返回文件大小、版本号、整体 hash、chunk 列表、下载 token 或预签名 URL。
3. 客户端根据 chunk 列表并发下载，可使用 HTTP Range 做断点续传。
4. 每个 chunk 下载完成后做 hash 校验，失败则重试或切换副本。
5. 所有 chunk 完成后按 `chunkIndex` 组装为目标文件，并校验整体 hash。
6. 如果文件是热点文件，可以通过 CDN、边缘缓存或 P2P 分块分发降低源站压力。

下载侧要注意：元数据版本和本地缓存版本必须匹配。如果文件在下载过程中被覆盖，服务端应让旧版本仍可读，或让客户端感知版本冲突后重新拉取。

## 4. 元数据模型

核心表可以拆为：

| 表 | 关键字段 | 作用 |
| --- | --- | --- |
| `file` | `file_id,user_id,parent_id,name,type,current_version` | 目录树和当前版本 |
| `file_version` | `version_id,file_id,size,checksum,status` | 文件版本和整体校验 |
| `block` | `block_hash,size,storage_key,ref_count` | 物理块和去重引用 |
| `file_block_map` | `version_id,chunk_index,block_hash,offset,size` | 文件版本到块序列的映射 |
| `upload_session` | `upload_id,user_id,file_id,status,expire_at` | 断点续传会话 |
| `upload_part` | `upload_id,chunk_index,block_hash,status` | 分片完成状态 |

元数据更新要保证事务性：创建文件版本、更新当前版本、插入块映射、更新引用计数应在同一事务或可恢复的 Saga 中完成，避免出现“数据块已写入但文件不可见”或“文件可见但块缺失”。

## 5. 一致性和可靠性

1. **幂等上传**：`uploadId + chunkIndex` 重复上传同内容直接成功，内容不同则拒绝。
2. **版本隔离**：覆盖文件不是原地修改旧版本，而是生成新版本，读者按版本读取。
3. **校验闭环**：chunk hash 防止局部损坏，整体 hash 防止组装顺序或缺块错误。
4. **断点续传**：服务端记录已完成 chunk bitmap，客户端恢复时只补传缺失块。
5. **副本和纠删码**：对象存储层通过多副本或 erasure coding 保证持久性。
6. **后台清理**：过期 upload session、孤儿块、引用计数为 0 的块要异步回收。
7. **事件可靠投递**：元数据变更和消息投递可以用 outbox 表，避免 DB 提交成功但消息丢失。

## 6. Redis 在云盘中的作用

Redis 更适合放高频、可重建、短生命周期的数据：

1. 上传会话的 chunk bitmap 和进度缓存。
2. 目录列表、文件权限、用户配额的热点缓存。
3. 下载限速令牌、接口限流计数器。
4. 热点文件元数据和预签名 URL 短期缓存。
5. 异步任务去重标记。

不适合只存在 Redis 的数据包括文件树、权限、版本、块引用计数等强一致元数据。这些数据应落到 MySQL/NewSQL，对 Redis 采用 cache-aside、过期时间和主动失效。

## 7. 易错点

1. 不要让 API Server 直接转发大文件流，否则元数据接口和上传下载会互相拖垮。
2. 秒传必须做权限和内容校验，不能因为 hash 命中就泄露他人文件信息。
3. 只按文件名做断点续传不可靠，必须绑定文件大小、版本、hash 或 uploadId。
4. 分块越小不一定越好，过小会放大请求数、元数据和对象存储小文件成本。
5. 上传完成不代表文件立刻对外可见，必须等元数据事务提交和整体校验通过。
6. 多端同步要处理冲突，例如同一文件离线修改后同时上传，通常生成冲突副本或基于版本合并。

## 8. 面试回答模板

分布式云盘会把控制面和数据面拆开：API/Metadata Service 管目录树、权限、版本和块映射，Block Service 或对象存储处理大文件块。上传时客户端分块、算 hash、初始化上传会话，服务端做权限和去重检查，只上传缺失 chunk，完成后原子写入文件版本和块映射，再通过 MQ 通知其他设备。下载时先取元数据和 chunk 列表，再并发下载或 Range 续传，按 chunk hash 和整体 hash 校验。工程上要重点保证幂等、断点续传、版本隔离、孤儿块清理、热点缓存和元数据强一致。
