### 问题 1：什么是文件块 (File Block)，和普通文件有什么区别？

在操作系统层面，文件是连续的字节流；但在分布式存储系统（如 Google Drive, HDFS, Ceph）中，为了处理海量数据，我们将文件切分成固定大小的片段，这就是**文件块 (Block / Chunk)**。

#### 1.1 核心区别对比

| 特性         | 普通文件 (Logical File)                    | 文件块 (File Block/Chunk)                                   |
| :----------- | :----------------------------------------- | :---------------------------------------------------------- |
| **定义**     | 用户看到的一个完整文件（如 `photo.jpg`）。 | 系统内部存储的物理切片（如 `blk_hash_01`, `blk_hash_02`）。 |
| **大小**     | 不固定，从几字节到几 TB。                  | **固定大小**（通常为 4MB, 64MB 或 128MB）。                 |
| **标识**     | 文件路径 + 文件名。                        | **哈希值 (SHA-256)**。                                      |
| **存储方式** | 作为一个整体存储。                         | 分散存储在不同的服务器/磁盘上。                             |
| **复用性**   | 很难复用。                                 | **极高复用性**（不同文件的相同部分可共享同一个块）。        |

#### 1.2 为什么要切成块？（三大杀手级优势）

**A. 秒传与去重 (Deduplication)**
这是网盘最核心的技术。
*   **场景：** 1000 个用户都上传了同一部 2GB 的电影。
*   **普通文件模式：** 服务器存 1000 份，浪费 2TB 空间。
*   **块模式：** 客户端计算文件的 Block Hash。上传时，服务器发现这些 Hash 已经存在于数据库中，直接告诉客户端“不用传了”，并在元数据表中给该用户添加一条记录指向现有的 Block。**物理存储只有一份，空间节省 99.9%。**

**B. 断点续传与失败重试**
*   **场景：** 上传 10GB 文件，传到 99% 时网络断了。
*   **普通文件模式：** 必须从头开始重传。
*   **块模式：** 客户端知道哪些 Block 已经上传成功（通过查询服务器）。网络恢复后，**只上传剩下的那 1% 的 Block**。

**C. 并行传输 (Parallelism)**
*   **原理：** 一个大文件被切成 100 个块。客户端可以开启 5 个线程，**同时**向服务器上传/下载 5 个不同的块。这能跑满带宽，极大提升速度。

### 问题 2：长轮询 (Long Polling) 为什么相比 WebSocket 对服务器资源的消耗更加“可控”？

在 Google Drive / Dropbox 这种**文件同步**场景下，长轮询往往优于 WebSocket。这听起来反直觉（因为 WebSocket 是全双工，更先进），但从**大规模分布式系统运维**的角度来看，长轮询有独特的优势。

#### 2.1 场景差异：同步 vs. 聊天
*   **聊天应用 (WhatsApp/Slack)：** 消息极其频繁，双向交互多，延迟要求毫秒级 -> **适合 WebSocket**。
*   **网盘同步 (Google Drive)：**
    *   **低频：** 你可能几小时才改一个文件，大部分时间客户端是“静默”的。
    *   **单向为主：** 主要是服务器通知客户端“有变动”，客户端极少通过这个通道发数据给服务器（上传走的是 Block Server）。

#### 2.2 为什么长轮询资源更“可控”？

**1. 状态维护成本 (State Management)**
*   **WebSocket:** 是一个**有状态**的持久 TCP 连接。服务器必须在内存中维护每个连接的上下文（Session, Ping/Pong 心跳状态）。如果服务器有 1000 万在线用户，就需要维护 1000 万个活跃对象的内存结构。
*   **Long Polling:** 本质上是标准的 HTTP 请求。虽然连接挂起，但现代 Web 服务器（如 Nginx, Go HTTP Server）对挂起的 HTTP 请求处理非常成熟，资源占用极低。当请求超时（比如 60秒）断开后，**服务器内存彻底释放**，没有任何残留状态。

**2. 优雅降级与负载保护 (Load Shedding)**
这是“可控”的关键所在。
*   **WebSocket:** 一旦连接建立，服务器很难“礼貌”地拒绝服务。如果服务器负载过高，断开连接会导致客户端立即重连，形成**惊群效应 (Thundering Herd)**，瞬间压垮服务器。
*   **Long Polling:**
    *   如果服务器负载高，它可以**拒绝新的轮询请求**，或者返回一个特定的 Header 告诉客户端：“我现在很忙，请 **5 分钟后** 再来轮询”（Backoff 策略）。
    *   服务器可以动态调整超时时间（比如从 60秒改为 30秒），灵活释放连接资源。这种**流量控制**在 WebSocket 中很难实现得这么平滑。

**3. 基础设施兼容性**
*   **WebSocket:** 需要负载均衡器（L7 Load Balancer）支持协议升级，且长时间保持连接不断开，容易被企业防火墙或运营商的中间设备切断。
*   **Long Polling:** 就是普通的 HTTP。**所有的** 代理、网关、防火墙、CDN 都完美支持。在复杂的全球网络环境下，长轮询的**穿透性**和**稳定性**更好。

#### 总结

*   **文件块**是为了解决**大文件存储、去重、断点续传**而设计的物理切片。
*   **长轮询**之所以在网盘场景下更优，是因为面对**海量低频连接**，它提供了更好的**容错性、流量控制能力**以及**基础设施兼容性**，避免了 WebSocket 维护长期空闲连接的昂贵开销。
