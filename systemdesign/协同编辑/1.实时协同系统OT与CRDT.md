# 1. 实时协同系统 OT 与 CRDT

实时协同系统的目标是让多个用户同时编辑同一份文档，并在网络延迟、乱序、离线重连的情况下最终看到一致结果。典型场景是在线文档、白板、协同表格和代码协作。

## 1. 基本架构

```text
Client
  -> WebSocket / QUIC 长连接
  -> Collaboration Gateway
  -> Document Session Service
  -> Operation Log / Snapshot Store
  -> Broadcast / Presence / Permission
```

关键状态：

1. 文档快照：当前稳定版本。
2. 操作日志：每个用户提交的编辑操作。
3. 版本号或向量时钟：用于判断操作基于哪个版本产生。
4. 在线会话：用户光标、选区、在线状态。

## 2. OT 方案

OT（Operational Transformation）把用户操作表示成 insert/delete/retain 等操作。当两个操作并发发生时，通过 transform 调整它们的位置，使不同客户端按不同顺序应用后仍能得到同一结果。

例子：

```text
初始: "abc"
用户 A 在位置 1 插入 X -> "aXbc"
用户 B 在位置 2 删除 b
```

服务端要根据操作的先后和版本，把 B 的删除位置转换到 A 插入后的坐标系，避免删错字符。

OT 优点是适合文本编辑，用户体验成熟；缺点是 transform 规则复杂，操作类型越多越难证明正确。

## 3. CRDT 方案

CRDT 通过给每个元素分配全局唯一、可排序的位置 ID，让并发插入和删除可以无冲突合并。每个副本本地操作后，即使消息乱序到达，只要最终收到所有操作，状态也能收敛。

常见做法：

1. 每个字符或块有唯一 ID，例如 `(site_id, counter)`。
2. 插入操作指定前后邻居或生成一个中间位置 ID。
3. 删除通常用 tombstone 或删除集合记录，避免并发消息把元素复活。
4. 合并规则满足交换律、结合律、幂等性。

CRDT 优点是离线友好、天然最终一致；缺点是元数据膨胀、位置 ID 管理和垃圾回收复杂。

## 4. 实时同步和冲突处理

1. 客户端本地先乐观应用操作，保证输入不卡顿。
2. 操作发送到服务端，服务端分配全局递增版本或确认序。
3. 服务端广播给同文档其他客户端。
4. 客户端收到远端操作后，根据 OT transform 或 CRDT merge 合并。
5. 断线重连时客户端带本地版本，服务端下发缺失操作或最新快照。
6. 周期性生成快照，避免从头回放全部操作日志。

## 5. 工程注意事项

1. 权限校验必须在服务端做，不能只相信客户端操作。
2. 操作要有幂等 ID，避免重传导致重复插入。
3. WebSocket 连接要有心跳、限流、背压和房间隔离。
4. 大文档要按块或段落分片，减少单次广播和 transform 范围。
5. 操作日志要能压缩、快照化和归档，否则长期文档成本很高。

## 6. 面试回答模板

实时协同系统我会用长连接维持文档会话，客户端本地乐观应用操作，服务端负责权限、排序、持久化和广播。冲突解决可以走 OT 或 CRDT：OT 通过 transform 把并发操作转换到同一坐标系，适合传统文本编辑但规则复杂；CRDT 给元素设计可合并的位置 ID，满足交换律和幂等性，离线友好但有元数据膨胀和垃圾回收问题。工程上还要有操作日志、快照、版本号、断线补偿、幂等、心跳、背压和权限控制。
