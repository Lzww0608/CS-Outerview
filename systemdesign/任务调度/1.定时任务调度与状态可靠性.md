# 1. 定时任务调度与状态可靠性

面试里问“定时任务 5 分钟轮询一次，如果任务执行超过 5 分钟，如何保证状态不丢失、不阻塞调度”，核心不是写一个 `cron`，而是把调度、执行、状态持久化和重试补偿拆开。

## 1. 问题本质

固定周期任务容易遇到这些问题：

1. 上一轮还没执行完，下一轮又被触发，导致重复处理。
2. 任务进程宕机，内存里的执行状态丢失。
3. 某个慢任务长期占用调度线程，后续任务无法触发。
4. 批处理执行到一半失败，不知道哪些数据已处理、哪些未处理。
5. 多实例部署时，多个实例同时扫到同一批任务。

所以设计目标通常是：

1. **调度不阻塞**：调度器只负责发现和投递任务，不直接执行耗时逻辑。
2. **状态不丢失**：任务状态、游标、重试次数和错误原因持久化。
3. **执行可恢复**：宕机后能从任务表、MQ 或 checkpoint 继续。
4. **重复可承受**：任务处理幂等，允许重试和重复投递。
5. **并发可控**：限制 worker 数、租约和每轮扫描数量。

## 2. 推荐架构

可以把定时任务拆成三层：

```text
Scheduler
  -> 扫描 due_time <= now 的任务
  -> 抢占任务租约或投递 MQ
Worker
  -> 执行业务逻辑
  -> 周期性刷新心跳/checkpoint
State Store
  -> 保存任务状态、租约、游标、重试和结果
```

调度器不要在同一个线程里执行任务。它每隔 5 分钟只做很轻的事情：扫描到期任务、把任务从 `PENDING` 改为 `RUNNING` 或投递到 MQ，然后立刻结束本轮调度。真正耗时的逻辑由 worker 线程池、独立进程或 MQ 消费者执行。

## 3. 任务状态机

任务表可以设计成状态机：

```text
PENDING -> RUNNING -> SUCCESS
                 -> FAILED -> RETRY_PENDING
                 -> TIMEOUT -> RETRY_PENDING
```

核心字段：

| 字段 | 作用 |
| --- | --- |
| `task_id` | 全局唯一任务 ID，用于幂等和追踪 |
| `biz_key` | 业务唯一键，例如订单号、分片编号、日期批次 |
| `status` | `PENDING/RUNNING/SUCCESS/FAILED` 等状态 |
| `next_run_at` | 下次可调度时间 |
| `lease_until` | 当前 worker 的租约过期时间 |
| `owner` | 当前执行实例 ID |
| `retry_count` | 已重试次数 |
| `checkpoint` | 批处理游标或已处理 offset |
| `last_error` | 最近失败原因 |
| `version` | 乐观锁版本，防止并发覆盖 |

抢占任务时使用条件更新：

```sql
UPDATE task
SET status = 'RUNNING',
    owner = :worker_id,
    lease_until = :now + INTERVAL '10 minutes',
    version = version + 1
WHERE task_id = :task_id
  AND status IN ('PENDING', 'RETRY_PENDING')
  AND next_run_at <= :now;
```

多实例同时扫描时，只有一个实例能更新成功。MySQL 可以用条件更新或 `SELECT ... FOR UPDATE SKIP LOCKED`；Redis 可以用 `SET lock_key value NX PX` 做短租约；Kubernetes 场景可以用 Lease/Leader Election。

## 4. 任务哈希、幂等和重新触发

长任务系统里，幂等的目标不是“不允许用户重复执行”，而是防止网络抖动、页面重复提交、服务重启和 MQ 重投导致重复副作用。

常见标识要分清：

| 标识 | 含义 | 是否唯一定位一次执行 |
| --- | --- | --- |
| `config_hash` | 规范化配置内容的哈希，表示同一份输入配置 | 不能单独唯一定位一次执行 |
| `biz_key` | 业务对象，例如项目、应用、环境、分支 | 不能单独唯一定位一次执行 |
| `run_id` | 用户发起的一次任务 | 可以定位一次任务 |
| `attempt_id` | 同一个 run 的第几次尝试 | 可以定位一次具体尝试 |
| `external_job_id` | Jenkins build number、queue id 或任务平台 job id | 定位外部执行 |

同一份配置算出的哈希是否固定，取决于是否先做规范化：

1. JSON 字段排序、去掉空白和无意义默认值。
2. 明确版本、环境、分支、镜像、参数和模板版本是否进入哈希。
3. 时间戳、随机数、用户备注这类非语义字段不要进入配置哈希。
4. 哈希算法和序列化规则要版本化，例如 `hash_algo=sha256, canonical_version=v1`。

哈希更适合表示“同一类输入”或“同一份配置”，不适合单独表示“同一次任务”。如果只拿 `config_hash` 查任务，可能查到历史成功任务、正在运行任务、失败重试任务和用户主动重新发起任务，存在歧义。

推荐唯一约束：

```text
task_run(run_id) unique
task_attempt(run_id, attempt_no) unique
dedup_key = workflow_id + env + branch + config_hash + trigger_mode
```

重试和重新发起要区分：

1. **重试 retry**：同一个 `run_id` 下新增 `attempt_id`，复用同一份配置和审批记录，通常用于网络抖动、Jenkins 临时失败、worker 宕机。
2. **重新发起 rerun**：创建新的 `run_id`，可以使用相同 `config_hash`，但代表用户明确要求再次执行，不能被旧幂等记录拦住。
3. **去重 dedup**：短时间内相同用户、相同配置、相同触发模式的重复点击可以合并到已有 `RUNNING` run，返回已有 `run_id`。
4. **强制重跑 force rerun**：用户确认后绕过 dedup，但仍要保留同一 `config_hash`，方便追踪“同配置多次执行”的结果差异。

面试里可以说：`config_hash` 用来判断配置是否相同，`run_id` 用来标识一次任务，`attempt_id` 用来标识一次尝试。幂等拦的是非预期重复，不拦用户明确的重新发起。

## 5. 执行超过 5 分钟怎么办

要先区分“调度周期”和“任务超时时间”。5 分钟一轮只是发现任务的频率，不代表单个任务必须 5 分钟内完成。

处理方式：

1. **不重入**：同一个 `biz_key` 在 `RUNNING` 且租约未过期时，下一轮调度不再启动新实例。
2. **租约续期**：worker 执行中周期性刷新 `lease_until`，表示任务仍存活。
3. **超时回收**：如果 `lease_until < now`，说明 worker 可能宕机，调度器把任务改回 `RETRY_PENDING`。
4. **checkpoint**：长任务每处理一批就保存游标，重试时从上次 checkpoint 继续。
5. **分片拆分**：如果单任务经常超过周期，把大任务拆成多个小分片，例如按用户 ID 范围、时间窗口或分页游标处理。
6. **队列隔离**：慢任务进入独立 worker pool，避免阻塞快任务。

## 6. Jenkins 任务如何断点续跑和接回

Jenkins 这类外部执行系统通常不能被 Agent 只当成同步函数调用。触发成功后，要把外部 ID 持久化，再通过轮询、回调或 webhook 接回状态。

推荐流程：

```text
创建 run
-> 规范化配置并计算 config_hash
-> 人工审批或策略校验
-> 触发 Jenkins，拿到 queue_id
-> 轮询 queue item，拿到 build_number/build_url
-> 持久化 external_job_id
-> 周期性同步 Jenkins 状态和日志摘要
-> SUCCESS/FAILED/ABORTED 后进入验证或重试分支
```

异常场景：

1. **网络抖动**：如果触发 Jenkins 请求超时，先用幂等 key 或 Jenkins 参数查询是否已经创建 queue/build；不能立刻再触发一遍。
2. **会话断开**：前端会话断了不影响任务，用户回来后用 `run_id` 查询任务状态，再根据 `build_url` 接上 Jenkins 进度。
3. **服务挂了**：worker 重启后扫描 `RUNNING` 且 `external_job_id` 不为空的任务，重新同步 Jenkins 状态。
4. **触发成功但状态未写入**：需要 outbox、事务日志或补偿查询，尽量避免“Jenkins 已跑但系统不知道”的悬挂任务。
5. **Jenkins 还在跑**：不要新建任务，恢复本地状态为 `RUNNING` 并继续观察原 build。
6. **Jenkins 已结束**：拉取 build result、artifact、日志摘要，补写本地终态并进入验证。

自动重启可以做，但边界要清楚：

1. 可自动重试：网络超时、Jenkins agent 临时离线、拉取日志失败、可重入的读操作。
2. 谨慎重试：构建失败、测试失败、配置校验失败，需要先判断是偶发环境问题还是配置本身错误。
3. 需要人工介入：重复失败达到上限、生产发布、回滚、数据修复、影响范围扩大、同一配置多次强制重跑。
4. 必须有上限：`max_attempts`、退避时间、总运行时间、同类错误指纹去重。

## 7. 如何保证状态不丢失

状态不丢失依赖持久化和幂等，而不是依赖内存变量。

关键措施：

1. **任务先落库再执行**：任务创建、状态流转和业务结果都要有持久化记录。
2. **业务处理幂等**：用唯一索引、幂等表、状态机条件更新或去重 key 保证重复执行不会产生重复副作用。
3. **先业务成功再提交状态**：外部副作用完成后再把任务置为 `SUCCESS`；如果状态提交失败，重试也应能幂等跳过。
4. **失败可追踪**：记录错误码、错误信息、重试次数和下一次重试时间。
5. **死信和人工介入**：超过最大重试次数进入 `DEAD` 或 `FAILED_FINAL`，告警并支持人工补偿。
6. **对账任务**：定期扫描业务表和任务表，发现状态不一致后补任务或修状态。

## 8. 不阻塞调度的实现要点

调度器本身要轻量：

1. 每轮只取有限数量任务，例如 `LIMIT 1000`。
2. 只做抢占、投递和状态修复，不做慢业务。
3. 使用线程池或 MQ 消费者执行任务，队列有容量上限。
4. worker 饱和时调度器减少投递或只更新 `next_run_at`，不要无限堆积。
5. 调度器有自己的超时和监控，避免数据库慢查询拖住整个调度循环。

如果使用 MQ，可以采用：

```text
任务表落库
-> Outbox 记录待投递事件
-> 投递 MQ
-> worker 消费并执行业务
-> 成功后更新任务状态和业务状态
```

这样即使投递 MQ 前进程宕机，Outbox 也能被后台任务重新投递。

## 9. 易错点

1. 只用分布式锁不记录任务状态，进程崩溃后不知道执行到哪里。
2. 锁 TTL 设得太短，任务未完成锁已过期，下一轮重复执行。
3. 锁 TTL 设得太长，worker 宕机后任务长时间无人接管。
4. 定时器线程直接执行业务，慢任务会阻塞下一轮调度。
5. 只靠“最多重试 3 次”，但业务操作没有幂等，重复执行会造成重复扣款、重复发券、重复通知。
6. 批任务没有 checkpoint，失败后只能从头扫，数据量大时容易形成重试风暴。
7. 只用 `config_hash` 查任务，没有 `run_id/attempt_id`，会把历史任务、当前任务和用户重新发起混在一起。
8. Jenkins 触发超时后直接再触发一次，可能造成同配置重复构建。

## 10. 面试回答模板

5 分钟轮询任务我会把调度和执行拆开。调度器每 5 分钟只扫描到期任务，通过数据库条件更新或分布式租约把任务从 `PENDING` 抢占为 `RUNNING`，然后投递给 worker 或 MQ，自己不执行耗时逻辑。任务状态、owner、lease、retry、checkpoint 都持久化；worker 执行中定期续租和保存 checkpoint。如果执行超过 5 分钟，下一轮看到租约未过期就不会重复启动；如果 worker 宕机导致租约过期，调度器把任务改成可重试并从 checkpoint 恢复。业务侧用唯一索引、幂等 key 或状态机条件更新保证重复执行也安全，超过重试上限进入死信并告警。
