# 3. 登录请求全链路

用户点击登录按钮到后端完成认证，不只是一次 HTTP 请求。面试里要把前端校验、网络链路、网关鉴权、业务校验、Redis/数据库访问、Token 签发和安全防护串起来。

## 1. 完整链路

典型账号密码或验证码登录链路：

```text
用户点击登录
-> 前端校验表单、收集设备信息和验证码票据
-> 浏览器发起 HTTPS 请求
-> DNS / TCP / TLS / HTTP 传输
-> CDN / WAF / 负载均衡 / API 网关
-> 网关做限流、黑名单、基础鉴权、trace id 注入
-> 登录服务校验参数、验证码或密码
-> 查询用户表、校验账号状态和风险状态
-> 生成 session 或 JWT
-> 写 Redis 会话、刷新登录时间、记录审计日志
-> 返回 Set-Cookie 或响应体 token
-> 前端保存登录态并跳转业务页面
```

如果是短信验证码登录，核心是 Redis 中的验证码校验和删除；如果是账号密码登录，核心是密码哈希校验、失败次数控制和风险拦截。

## 2. 前端和网络层

前端通常会做基础校验，但后端不能信任前端结果：

1. 手机号、邮箱、密码长度、验证码格式可以在前端提前拦截，减少无效请求。
2. 登录按钮要防重复点击，避免短时间重复提交。
3. 请求必须走 HTTPS，防止密码、验证码和 token 被明文窃听。
4. 浏览器请求会携带 Cookie、User-Agent、Referer、Origin 等信息，后端可用于安全校验和风控。

网络层要能说清楚：DNS 找到入口 IP，TCP 建连，HTTPS 做 TLS 握手，HTTP 请求进入负载均衡或网关，再路由到登录服务。

## 3. 网关层做什么

登录接口一般会在网关或接入层做第一层保护：

1. **限流**：按 IP、手机号、设备、账号、接口维度限制请求频率。
2. **WAF 和黑名单**：拦截恶意 IP、代理、异常 User-Agent、脚本攻击。
3. **CORS/CSRF**：浏览器场景要检查 Origin、SameSite、CSRF token。
4. **Trace**：生成或透传 trace id，便于定位登录失败和慢请求。
5. **路由和灰度**：把请求转发到对应版本的登录服务。

注意：登录接口本身是获取身份的入口，不能依赖“已登录鉴权”，但可以依赖验证码票据、设备指纹、签名参数和风控结果。

## 4. 登录服务核心逻辑

账号密码登录：

1. 根据账号查询用户基础信息，账号不存在时返回统一错误，避免枚举账号。
2. 使用 bcrypt、scrypt、Argon2 或 PBKDF2 校验密码哈希，不能明文存密码。
3. 校验账号状态，例如冻结、注销、未激活、风险命中。
4. 失败次数写 Redis，超过阈值要求验证码、临时锁定或二次认证。
5. 成功后清理失败计数，刷新最近登录时间和登录设备。

短信验证码登录：

1. 从 Redis 读取验证码 key，校验输入是否一致。
2. 校验通过后删除验证码，防止重复使用。
3. 手机号不存在时按业务规则创建用户或要求先注册。
4. 用户表手机号必须有唯一索引，防止并发注册重复账号。

## 5. Session 和 JWT 签发

登录成功后常见两种方案：

1. **Cookie + Redis Session**：服务端生成高随机 `session_id`，把 `session_id -> user_id/role/expire_at` 写 Redis，再通过 `Set-Cookie` 返回给浏览器。
2. **JWT**：服务端把 `sub、exp、iat、iss、aud、role、tenant_id` 等声明放入 payload，对 `header.payload` 签名，客户端后续通过 `Authorization: Bearer` 或 Cookie 携带。

浏览器 Web 场景更常用 `HttpOnly + Secure + SameSite` Cookie，降低 token 被 JavaScript 读取的风险；移动端和开放 API 常用 Bearer Token。JWT payload 不是密文，不能放密码、验证码、身份证号等敏感信息。

## 6. 易错点

1. 不能只做前端校验，所有参数、验证码、权限和账号状态都必须后端校验。
2. 密码不能用 MD5/SHA256 单次哈希保存，应使用带盐的慢哈希算法。
3. 登录失败提示不要区分“账号不存在”和“密码错误”，避免账号枚举。
4. 验证码校验成功后必须删除或标记已用，避免重放。
5. JWT 只验签不够，还要校验 `exp、nbf、iss、aud`，并设计撤销和密钥轮换。
6. 登录成功后应刷新 session_id，防止 session fixation。
7. 登录接口要有审计日志，但日志不能打印密码、验证码和完整 token。

## 7. 真实场景

真实系统里登录链路通常还会接入风控：

1. 新设备、新城市、代理 IP、短时间大量失败会触发图形验证码或 MFA。
2. 高风险账号登录成功后，也可能限制转账、改密、绑定设备等高危操作。
3. 登录成功事件会异步写 MQ，用于通知、设备管理、审计和风险建模。
4. Redis 故障时，验证码登录可以短暂 fail closed，账号密码登录可以保留数据库校验但提高风险挑战。

## 8. 面试回答模板

用户点击登录后，前端先做格式校验和防重复提交，然后通过 HTTPS 把账号密码或验证码发到后端入口。请求会经过 DNS、TCP/TLS、负载均衡和 API 网关，网关做限流、WAF、trace 和路由。登录服务拿到请求后校验参数、验证码或密码哈希，检查账号状态、失败次数和风控结果；成功后签发 Cookie Session 或 JWT，把 session 写入 Redis 或返回 token，同时记录审计日志和登录事件。安全上要注意 HTTPS、密码慢哈希、验证码一次性、失败限流、Cookie 安全属性、JWT 过期与撤销，以及不要在日志里泄露敏感信息。
