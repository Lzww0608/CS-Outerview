# 2. 用户注册、验证码与恶意注册防护

用户注册链路不是简单地“写一条用户记录”。面试里追问注册方式、验证码异常、Token 存储和恶意注册，本质是在考察登录态、安全风控、幂等和异常路径设计。

## 1. 常见注册方式

常见注册方式可以按身份凭证来源分类：

1. **账号密码注册**：用户提供手机号/邮箱/用户名和密码，服务端保存密码哈希。
2. **手机号验证码注册**：验证码验证通过后创建账号，适合移动端和低摩擦注册。
3. **邮箱验证码注册**：通过邮件验证用户对邮箱的控制权。
4. **第三方 OAuth/OIDC 登录注册**：如微信、QQ、企业 SSO，首次登录时绑定本平台用户。
5. **邀请注册**：通过邀请码、企业组织或活动资格控制注册入口。

真实系统通常会把“注册”和“登录”收敛成统一账号体系：如果手机号未注册，验证码通过后创建账号；如果已注册，验证码通过后直接登录。这样用户体验更顺，但后端必须做好幂等和并发控制。

## 2. 验证码异常怎么处理

验证码链路要覆盖发送、校验、过期、失败和重放。

常见状态：

1. **发送失败**：短信网关失败、限流、手机号非法、风险命中。不要创建验证码记录为成功状态，应返回可理解错误并记录失败原因。
2. **验证码过期**：验证码记录带 TTL，过期后直接失败，并提示重新获取。
3. **验证码错误**：同一手机号、IP、设备维度累计失败次数，超过阈值临时冻结。
4. **重复校验**：验证码校验成功后要标记已使用或删除，避免同一验证码重复注册。
5. **并发校验**：两个请求同时拿同一验证码注册时，要用原子校验或数据库唯一约束保证只创建一个账号。

Redis 中常见设计：

```text
code:register:phone:13800000000 -> 123456, TTL 5min
code:fail:phone:13800000000 -> 3, TTL 15min
code:send:phone:13800000000 -> 1, TTL 60s
```

校验通过后先删除验证码 key，再创建用户；用户表对手机号或邮箱建立唯一索引，防止并发重复注册。

## 3. Token 存在哪里

浏览器端常见有三种位置：

1. **Cookie**：浏览器自动携带，适合传统 Web 登录态。配合 `HttpOnly`、`Secure`、`SameSite` 降低 XSS/CSRF 风险。
2. **localStorage / sessionStorage**：前端手动读取后放到 `Authorization` 头，跨域 API 场景方便，但更容易被 XSS 读取。
3. **内存变量**：刷新页面丢失，安全性相对好，但用户体验和多标签页共享较差。

如果是同一个 Chrome 浏览器，登录后关闭标签页，短时间内再次访问是否需要密码，取决于登录凭证是否仍有效：

1. Cookie 或 localStorage 中 token 未过期：通常不需要重新输入密码或验证码。
2. sessionStorage 或内存 token：关闭标签页或浏览器后可能丢失，需要重新登录。
3. 服务端 session 已失效、token 被撤销、风险命中：即使本地还有凭证，也要重新认证。

同一台电脑跨浏览器通常需要重新登录，因为 Chrome、Edge、Firefox 的 Cookie 和 localStorage 不共享。除非接入操作系统级 SSO、企业统一身份或通过扫码/设备信任等方式重新授信。

## 4. Cookie 是怎么生成的

Cookie 不是浏览器凭空生成登录态，而是服务端通过响应头下发：

```http
Set-Cookie: sid=abc123; Max-Age=7200; HttpOnly; Secure; SameSite=Lax; Path=/
```

流程：

```text
登录成功
-> 服务端生成高随机 session_id 或签名 token
-> 服务端把 session_id 写入 Redis/DB，或直接签发 JWT
-> 响应 Set-Cookie
-> 浏览器保存 Cookie
-> 后续请求自动携带 Cookie
-> 服务端校验并恢复用户身份
```

注意事项：

1. session_id 必须高随机，不能由用户 ID、手机号直接拼接。
2. 登录成功后应刷新 session_id，防止 session fixation。
3. Cookie 中不要放密码、验证码、身份证号等敏感明文。
4. 跨站点登录要特别关注 `SameSite=None; Secure`、CSRF token 和 CORS 策略。

## 5. 恶意注册和刷验证码防护

恶意注册通常目标是消耗短信成本、批量养号、撞库、薅优惠券或污染平台数据。防护要多层叠加：

1. **入口限流**：按 IP、手机号、设备指纹、账号、接口和城市/运营商维度做滑动窗口限流。
2. **验证码挑战**：图形验证码、行为验证码、无感验证码，风险越高挑战越强。
3. **手机号风控**：识别虚拟号、接码平台、空号、异常号段和短时间大量注册号段。
4. **设备指纹**：结合浏览器指纹、App 设备 ID、模拟器特征、代理/VPN 特征。
5. **黑白名单和信誉分**：对历史可信设备降低摩擦，对异常来源提高验证强度。
6. **优惠券/活动隔离**：注册成功不等于立即可领取高价值权益，高价值动作二次风控。
7. **异步审核和封禁**：批量相似行为、异常 IP 段、异常设备簇可异步识别并处置。

高并发攻击下不要只依赖业务服务处理。网关、WAF、验证码服务、短信服务、Redis 限流和风控模型都应该参与，尽量在调用短信网关之前拦截。

## 6. 易错点

1. 验证码不能只按手机号限流，攻击者可以换手机号刷同一 IP 或同一设备。
2. 缓存验证码时不能明文长期保存，至少要短 TTL；高安全场景可存哈希。
3. Token 放在 localStorage 并不天然安全，XSS 后很容易被读取。
4. JWT 默认难主动撤销，需要短有效期、黑名单或 `token_version`。
5. 注册接口必须幂等，手机号/邮箱唯一索引是最后防线。

## 7. 面试回答模板

用户注册我会按账号密码、手机号验证码、邮箱验证码和第三方登录来设计。验证码注册要处理发送失败、过期、输错次数、重复校验和并发创建账号，Redis 保存短 TTL 验证码和失败计数，用户表用手机号唯一索引兜底。登录态可以用 Cookie + Session 或 JWT；同一浏览器短时间内是否免登录取决于 Cookie/token 是否还有效，跨浏览器通常不共享登录态。防恶意注册要在网关、验证码、限流、设备指纹、手机号风控、WAF 和活动权益发放上分层防护，核心是提高攻击成本，并在短信发送和优惠券发放前尽早拦截。
