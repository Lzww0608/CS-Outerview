# 1. Cookie、Session 与 JWT

## 1. 为什么需要登录态

HTTP 请求本身是无状态的。服务端收到一个请求时，不会天然知道它属于哪个用户。登录态的本质是：客户端在后续请求中携带一个可信凭证，服务端用这个凭证恢复用户身份和权限。

## 2. Cookie + Session

流程：

```text
用户提交账号密码
-> 服务端校验成功
-> 生成随机 session_id
-> 服务端保存 session_id -> 用户信息/权限/过期时间
-> 响应 Set-Cookie
-> 浏览器后续请求自动携带 Cookie
-> 服务端查 session 存储恢复登录态
```

服务端 session 存储：

1. **单机内存**：实现简单，但多实例不共享，重启丢失。
2. **Redis**：常见方案，支持 TTL、集中删除、踢下线。
3. **数据库**：持久但延迟高，一般不作为高频登录态校验主路径。

## 3. Cookie 关键属性

1. `HttpOnly`：禁止 JavaScript 读取，降低 XSS 窃取 Cookie 风险。
2. `Secure`：只在 HTTPS 下发送。
3. `SameSite`：限制跨站请求携带 Cookie，降低 CSRF 风险。
4. `Domain/Path`：控制 Cookie 生效范围。
5. `Max-Age/Expires`：控制过期时间。

## 4. JWT

JWT 通常由三部分组成：

```text
Header.Payload.Signature
```

服务端把用户身份、过期时间、权限等 claim 放到 payload 中，再用密钥签名。客户端携带 JWT，服务端验证签名和过期时间即可。

优点：

1. 服务端可以无状态校验，减少集中 session 存储压力。
2. 适合跨服务传递身份。
3. 和移动端、开放 API 集成方便。

缺点：

1. token 泄露后，在过期前可能一直有效。
2. 默认难以主动撤销，需要黑名单、版本号或短 token + refresh token。
3. payload 只是 Base64URL 编码，不是加密，不能放敏感明文。
4. token 太大会增加每次请求头开销。

## 5. Session 和 JWT 怎么选

1. 传统 Web、需要强撤销、踢下线：Cookie + Redis Session 更直接。
2. 多端 API、跨服务认证、无状态网关：JWT 更方便。
3. 高安全系统：短期 access token + refresh token + 服务端撤销表。
4. 浏览器场景：无论 session_id 还是 JWT，都要关注 XSS、CSRF 和 HTTPS。

## 6. 双 Token 校验机制

双 Token 通常指 `Access Token + Refresh Token`：

| Token | 有效期 | 使用位置 | 作用 |
| --- | --- | --- | --- |
| Access Token | 短，一般分钟级 | 每次业务请求 | 证明当前请求身份和权限 |
| Refresh Token | 长，一般天级或周级 | 续期接口 | 换取新的 access token |

典型流程：

```text
登录成功
-> 服务端签发 access_token 和 refresh_token
-> access_token 过期
-> 客户端携带 refresh_token 请求续期
-> 服务端校验 refresh_token、设备、版本号和风险状态
-> 签发新的 access_token，必要时轮换 refresh_token
```

Access Token 通常可以做成 JWT，便于网关无状态验签；Refresh Token 更建议服务端有状态保存或保存其哈希，便于撤销、踢下线和设备管理。

## 7. token version 怎么做

`token_version` 是让已签发 token 主动失效的常见机制。服务端在用户表、会话表或 Redis 中保存版本号：

```text
user_id -> token_version = 12
```

签发 token 时把版本写入 claim：

```json
{
  "sub": "10086",
  "token_version": 12,
  "exp": 1770000000
}
```

校验时不仅验签和过期时间，还要比较 token 内版本与服务端当前版本：

```text
token.version == current_user.token_version -> 通过
token.version < current_user.token_version  -> 拒绝，要求重新登录
```

触发版本递增的场景：

1. 用户修改密码。
2. 管理员封禁或强制下线。
3. 用户主动退出所有设备。
4. 权限、角色、租户归属发生高风险变化。
5. 检测到 token 泄露或异地异常登录。

如果需要“单设备踢下线”，只用用户级 `token_version` 不够，应使用 `device_id/session_id -> version/status`，避免一个设备退出影响全部设备。

## 8. 双 Token 易错点

1. Refresh Token 不能和 Access Token 一样只做长 JWT，否则泄露后很难撤销。
2. 续期接口要限流、防重放、校验设备指纹或 session 状态。
3. Refresh Token 轮换时要处理并发续期，可用版本号、单次使用标记或宽限窗口。
4. Access Token 短有效期不是越短越好，过短会导致频繁续期和网关压力。
5. token version 校验会引入一次 Redis/DB 查询，可以在网关做短 TTL 缓存，但要接受秒级撤销延迟。

## 9. 真实场景注意事项

1. 登录成功后刷新 session_id，防止 session fixation。
2. 退出登录时删除服务端 session 或加入 token 黑名单。
3. 改密码、改权限后要让旧凭证失效。
4. Redis session 要设置 TTL，并在活跃访问时按策略续期。
5. 多机房场景要考虑 session 复制、就近访问和一致性。
6. 网关层可以统一做认证，业务服务只接收可信用户上下文。

## 10. 面试回答模板

保持登录状态通常用 Cookie + Session 或 Token。Cookie + Session 是服务端生成随机 session_id，客户端 Cookie 保存 session_id，服务端在 Redis 中保存 session 对应的用户信息和过期时间；后续请求通过 Cookie 查 Redis 恢复身份。JWT 则把身份信息和过期时间放到 token 里并签名，服务端验证签名即可。Session 更容易主动失效和踢下线，JWT 更适合无状态和跨服务，但撤销更复杂。安全上要配合 HTTPS、HttpOnly、Secure、SameSite、CSRF 防护和合理过期时间。

如果问双 Token，我会说 access token 短有效期，用于业务请求；refresh token 长有效期，只用于续期，最好服务端有状态保存，支持撤销和设备管理。token version 用来主动失效旧 token，签发时把版本写进 token，校验时和服务端当前版本比较；改密码、踢下线、权限变化时递增版本。单设备控制还要引入 device/session 维度的版本或状态。
