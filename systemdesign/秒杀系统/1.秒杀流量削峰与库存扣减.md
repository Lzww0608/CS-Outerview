# 1. 秒杀流量削峰与库存扣减

秒杀场景的核心矛盾是：请求量远大于库存量，不能让所有请求都打到数据库。设计目标是尽早拦截无效流量，把同步链路做短，把数据库写入变成可控的小流量。

## 常见瓶颈

1. 瞬时请求打满网关、应用线程池和连接池。
2. 热点商品库存 key 被大量访问。
3. 数据库库存行成为写热点。
4. 下单、支付、库存、优惠券等链路过长，放大延迟。

## 削峰方案

1. **静态化和 CDN**：活动页、商品详情、规则说明尽量静态化，减少回源。
2. **网关限流**：按用户、IP、活动、商品维度限流，提前过滤异常流量。
3. **资格校验前置**：登录态、活动时间、用户资格、黑名单在网关或缓存层完成。
4. **库存预热到 Redis**：秒杀开始前把库存加载到 Redis，使用 Lua 脚本原子预扣减。
5. **异步下单**：预扣成功后写入 MQ，订单服务异步创建订单，前端轮询结果或通过消息通知结果。
6. **排队和令牌**：库存有限时只发放有限数量令牌，拿到令牌才允许进入下单链路。

## 库存扣减

Redis 预扣减可以用 Lua 保证检查和扣减原子性：

```lua
local stock = tonumber(redis.call('GET', KEYS[1]))
if stock == nil or stock <= 0 then
  return 0
end
redis.call('DECR', KEYS[1])
return 1
```

数据库最终扣减仍要带条件：

```sql
UPDATE sku_stock
SET stock = stock - 1
WHERE sku_id = ? AND stock > 0;
```

如果异步下单失败，需要发送补偿消息回补 Redis 库存，并记录失败原因。

## 热点优化

1. **库存分片**：把一个商品库存拆成多个 bucket，例如 `stock:sku:1:bucket:0..N`，分散单 key 压力。
2. **本地缓存**：活动配置、商品信息、售罄标记使用本地缓存，减少 Redis 访问。
3. **售罄标记**：库存扣完后设置 sold out 标记，后续请求直接失败。
4. **请求合并**：对相同商品的读请求做 singleflight，避免缓存击穿。
5. **降级保护**：Redis 或 MQ 异常时快速失败，避免请求继续压垮数据库。

## 单机 Redis 扛不住怎么办

如果秒杀量极大，单机 Redis 的瓶颈通常出现在单线程命令执行、网络带宽、热点 key、Lua 脚本耗时和主从复制延迟。扩展思路要分“横向分片”和“热点削峰”两类。

### 1. Redis Cluster 分片

把不同商品、不同活动或不同库存 bucket 分散到多个 Redis 主节点：

```text
stock:{sku100}:bucket:0 -> shard A
stock:{sku100}:bucket:1 -> shard B
stock:{sku100}:bucket:2 -> shard C
```

注意：Redis Cluster 只能分散不同 key 的压力。单个超热点 key 仍然只落在一个 slot 上，必须拆 key 或做本地缓存。

### 2. 库存分桶

把一个商品库存拆成多个桶，每个桶独立扣减：

```text
stock:sku100:bucket:0 = 100
stock:sku100:bucket:1 = 100
stock:sku100:bucket:2 = 100
```

请求按用户 ID、随机数或令牌路由到某个 bucket。某个 bucket 扣完后可以：

1. 尝试其他 bucket，提升库存利用率。
2. 直接失败，降低跨 bucket 重试成本。
3. 后台做 bucket 间库存再平衡。

库存分桶要避免总量不准。活动开始前分配总库存，数据库最终扣减仍要用条件更新和订单唯一约束兜底。

### 3. 令牌化削峰

库存只有 1 万件时，不需要让 1000 万请求都进入 Redis 扣库存。可以提前发放有限下单令牌：

```text
库存数 * 放大系数 -> token pool
抢到 token 的请求 -> 进入 Redis Lua 预扣
没 token 的请求 -> 直接失败或排队
```

令牌可以放在 Redis、网关内存、MQ 或专门的排队系统中。放大系数用于覆盖拿到令牌但不支付、风控拒绝、超时释放等情况。

### 4. 多级缓存和售罄广播

活动配置、商品详情、售罄标记不应每次都查 Redis：

```text
本地缓存 -> Redis -> DB
```

库存扣完后设置全局 sold out 标记，并通过 MQ、配置中心或 pub/sub 推送到应用本地，后续请求在应用层直接失败。售罄标记要允许短暂误判后补偿，例如异步订单失败释放库存时重新打开。

### 5. MQ 排队和异步落库

Redis 预扣成功只表示获得创建订单资格，不表示最终订单成功。订单创建、优惠券锁定、风控、支付单生成等动作应进入 MQ 异步处理：

```text
Redis Lua 预扣成功
-> 写 MQ / Redis Stream
-> 订单服务消费
-> MySQL 条件扣减 + 唯一订单
-> 失败补偿 Redis 库存
```

消费者要幂等，失败进入重试和死信队列，后台对账修复 Redis 和 DB 的差异。

### 6. 面试回答模板

单机 Redis 扛不住时，先不要让所有请求都进入扣库存链路。入口做限流、风控和令牌化削峰，活动配置和售罄标记放本地缓存。Redis 层用 Cluster 做横向分片，但单个热点 key 仍要拆成库存 bucket，按用户或随机路由分散到多个 key。预扣成功后写 MQ 异步下单，数据库用条件更新和唯一约束兜底，失败时补偿 Redis。核心原则是：读路径多级缓存，写路径分桶分片，订单异步化，最终一致靠幂等、补偿和对账。

## 抢票和秒杀的差异

12306 抢票可以看成更复杂的秒杀：库存不是单一商品数量，而是“车次、日期、区间、座席、席别”共同决定的可售资源。一个座位从北京到上海被购买后，中间区间的库存也会受影响，因此不能只用简单的 `stock--`。

设计时可以分层处理：

1. **查询链路缓存化**：车次、站点、余票展示读多写少，适合 CDN、本地缓存、Redis 和异步刷新，避免所有查询打数据库。
2. **购票资格前置**：登录态、实名信息、乘车人、限购规则、验证码或风控在进入扣库存前完成。
3. **令牌或排队削峰**：按车次、日期、席别发放有限下单令牌，拿到令牌才进入创建订单链路。
4. **库存预占**：缓存层可以做粗粒度预扣减，但最终要在数据库或强一致库存服务里锁定具体座位和区间。
5. **最终一致和补偿**：支付超时、出票失败、风控拒绝都要释放预占库存，并保证消息幂等。

核心一致性约束仍然要落到强校验上，例如唯一约束、条件更新、座位区间冲突检测、订单幂等号。缓存层负责挡流量和提升体验，不能作为唯一事实来源。

面试回答可以总结为：秒杀要把流量挡在前面，库存扣减放在缓存层原子预扣，订单创建异步化，数据库只处理已经通过资格和库存校验的小流量。

## 延迟队列和定时任务更新库存

库存更新里常见两类异步任务：

1. **延迟释放**：用户抢到资格或创建订单后未支付，到期要关闭订单并释放预占库存。
2. **定时校准**：缓存库存、数据库库存、订单状态可能短暂不一致，需要定时任务做对账和修复。

推荐组合是“延迟队列及时触发 + 定时扫描兜底”：

```text
创建待支付订单
-> 锁定库存或座位
-> 写 orders.expire_time
-> 发送 delay close_order(order_id)
-> 到期消费消息，条件更新订单 UNPAID -> CLOSED
-> 释放库存，记录库存流水
-> 定时任务扫描 expire_time <= now 的 UNPAID 订单兜底
```

库存释放必须绑定订单状态和库存流水，不能简单 `INCR stock`：

```sql
UPDATE orders
SET status = 'CLOSED'
WHERE order_id = ? AND status = 'UNPAID';

UPDATE stock_lock
SET status = 'RELEASED'
WHERE order_id = ? AND status = 'LOCKED';
```

只有订单状态更新成功，且库存锁定记录从 `LOCKED` 改成 `RELEASED` 成功，才真正回补库存。这样重复延迟消息、重复扫描或 worker 重启都不会重复释放。

易错点：

1. 延迟消息可能丢失、积压或重复，所以必须有定时扫描兜底和幂等状态机。
2. 定时任务不能全表扫，要按 `status + expire_time` 建索引，分批处理。
3. 支付成功和超时释放可能并发，必须用条件更新让二者只有一个成功。
4. Redis 库存回补要和数据库库存流水对账，避免 Redis 多加或少加。
5. 库存释放后如果有售罄标记、本地缓存或令牌池，也要同步刷新或允许短暂最终一致。

面试回答可以说：延迟队列负责订单到期后尽快释放库存，定时任务负责兜底补偿。核心不是定时器本身，而是订单状态机、库存锁定流水、幂等释放、支付并发竞争和对账校准。
