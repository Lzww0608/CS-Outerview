# 1. 秒杀流量削峰与库存扣减

秒杀场景的核心矛盾是：请求量远大于库存量，不能让所有请求都打到数据库。设计目标是尽早拦截无效流量，把同步链路做短，把数据库写入变成可控的小流量。

## 常见瓶颈

1. 瞬时请求打满网关、应用线程池和连接池。
2. 热点商品库存 key 被大量访问。
3. 数据库库存行成为写热点。
4. 下单、支付、库存、优惠券等链路过长，放大延迟。

## 削峰方案

1. **静态化和 CDN**：活动页、商品详情、规则说明尽量静态化，减少回源。
2. **网关限流**：按用户、IP、活动、商品维度限流，提前过滤异常流量。
3. **资格校验前置**：登录态、活动时间、用户资格、黑名单在网关或缓存层完成。
4. **库存预热到 Redis**：秒杀开始前把库存加载到 Redis，使用 Lua 脚本原子预扣减。
5. **异步下单**：预扣成功后写入 MQ，订单服务异步创建订单，前端轮询结果或通过消息通知结果。
6. **排队和令牌**：库存有限时只发放有限数量令牌，拿到令牌才允许进入下单链路。

## 库存扣减

Redis 预扣减可以用 Lua 保证检查和扣减原子性：

```lua
local stock = tonumber(redis.call('GET', KEYS[1]))
if stock == nil or stock <= 0 then
  return 0
end
redis.call('DECR', KEYS[1])
return 1
```

数据库最终扣减仍要带条件：

```sql
UPDATE sku_stock
SET stock = stock - 1
WHERE sku_id = ? AND stock > 0;
```

如果异步下单失败，需要发送补偿消息回补 Redis 库存，并记录失败原因。

## 热点优化

1. **库存分片**：把一个商品库存拆成多个 bucket，例如 `stock:sku:1:bucket:0..N`，分散单 key 压力。
2. **本地缓存**：活动配置、商品信息、售罄标记使用本地缓存，减少 Redis 访问。
3. **售罄标记**：库存扣完后设置 sold out 标记，后续请求直接失败。
4. **请求合并**：对相同商品的读请求做 singleflight，避免缓存击穿。
5. **降级保护**：Redis 或 MQ 异常时快速失败，避免请求继续压垮数据库。

## 抢票和秒杀的差异

12306 抢票可以看成更复杂的秒杀：库存不是单一商品数量，而是“车次、日期、区间、座席、席别”共同决定的可售资源。一个座位从北京到上海被购买后，中间区间的库存也会受影响，因此不能只用简单的 `stock--`。

设计时可以分层处理：

1. **查询链路缓存化**：车次、站点、余票展示读多写少，适合 CDN、本地缓存、Redis 和异步刷新，避免所有查询打数据库。
2. **购票资格前置**：登录态、实名信息、乘车人、限购规则、验证码或风控在进入扣库存前完成。
3. **令牌或排队削峰**：按车次、日期、席别发放有限下单令牌，拿到令牌才进入创建订单链路。
4. **库存预占**：缓存层可以做粗粒度预扣减，但最终要在数据库或强一致库存服务里锁定具体座位和区间。
5. **最终一致和补偿**：支付超时、出票失败、风控拒绝都要释放预占库存，并保证消息幂等。

核心一致性约束仍然要落到强校验上，例如唯一约束、条件更新、座位区间冲突检测、订单幂等号。缓存层负责挡流量和提升体验，不能作为唯一事实来源。

面试回答可以总结为：秒杀要把流量挡在前面，库存扣减放在缓存层原子预扣，订单创建异步化，数据库只处理已经通过资格和库存校验的小流量。
