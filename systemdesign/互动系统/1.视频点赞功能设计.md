# 1. 视频点赞功能设计

视频点赞是典型高并发互动功能。它看起来只是一个按钮，但要同时处理幂等、计数、热点、缓存一致性、反作弊和最终一致。

## 1. 核心需求

1. 用户对同一个视频只能点赞一次，也可以取消点赞。
2. 视频点赞数要能高并发读取。
3. 点赞状态要能快速判断，例如“当前用户是否点过赞”。
4. 点赞计数允许短暂延迟，但不能长期错误。
5. 热门视频可能出现热点 key 和数据库写热点。

## 2. 数据模型

权威表可以拆成两类：

```sql
-- 点赞明细表
CREATE TABLE video_like (
    video_id BIGINT NOT NULL,
    user_id BIGINT NOT NULL,
    status TINYINT NOT NULL, -- 1 liked, 0 canceled
    created_at DATETIME NOT NULL,
    updated_at DATETIME NOT NULL,
    PRIMARY KEY (video_id, user_id),
    KEY idx_user_time(user_id, updated_at)
);

-- 视频计数表
CREATE TABLE video_stat (
    video_id BIGINT PRIMARY KEY,
    like_count BIGINT NOT NULL,
    updated_at DATETIME NOT NULL
);
```

`(video_id, user_id)` 唯一键保证同一用户对同一视频只有一条状态记录。取消点赞可以软删除，即把 `status` 改成 0，便于审计和恢复。

## 3. 写路径

强一致简单版：

```text
用户点赞
  -> INSERT ... ON DUPLICATE KEY UPDATE status = 1
  -> 根据旧状态判断是否需要 like_count + 1
  -> 删除或更新缓存
```

高并发版：

```text
用户点赞
  -> Redis/Lua 做幂等状态判断和计数预更新
  -> 写 MQ
  -> 异步落 MySQL 明细表和计数表
  -> 定时对账修正
```

Redis 可以存：

1. `like:video:{video_id}:count`：点赞计数。
2. `like:user:{user_id}:videos`：用户点赞过的视频集合，或按业务规模拆分。
3. `like:video:{video_id}:users`：小规模视频可存 set，大规模不建议无限增长。

如果视频点赞量极大，不适合把所有用户集合都放 Redis，可以只缓存热点用户状态或用 Bloom/Bitmap/分片 set 辅助，权威状态仍在数据库。

## 4. 幂等和并发

点赞接口必须幂等：

1. 重复点赞不应让计数重复增加。
2. 取消未点赞的视频不应让计数变负。
3. 客户端重试、MQ 重试、服务超时都不能破坏状态。

数据库兜底方式：

```sql
INSERT INTO video_like(video_id, user_id, status, created_at, updated_at)
VALUES (?, ?, 1, NOW(), NOW())
ON DUPLICATE KEY UPDATE
    status = 1,
    updated_at = NOW();
```

但要知道旧状态才能准确增量更新计数。工程上常用：

1. 在事务里先查旧状态，再更新明细和计数。
2. 用 Redis Lua 原子判断状态并更新计数，异步落库。
3. MQ 消费端按事件 ID 或 `(video_id,user_id,version)` 去重。
4. 定时用明细表聚合校准计数表和缓存。

## 5. 读路径

视频详情页通常需要：

1. 视频点赞数。
2. 当前用户是否点赞。

读路径可以是：

```text
读点赞数: 本地短缓存 -> Redis count -> MySQL stat
读点赞状态: Redis user/video 状态 -> MySQL like 明细
```

热门视频点赞数可以短 TTL 本地缓存，降低 Redis 压力。用户态点赞状态更敏感，缓存 key 要包含用户和视频，不能跨用户共享。

## 6. 热点和削峰

1. 热门视频计数 key 分片：`like:count:{video_id}:{shard}`，读取时聚合。
2. 写入 MQ 削峰，消费者批量落库。
3. 对同一个视频的计数更新合并，减少数据库 update 频率。
4. 对异常用户/IP/设备限流，防止刷赞。
5. 对热点视频提前本地缓存计数，短 TTL 刷新。

## 7. 易错点

1. 只给点赞数 `+1` 不记录明细，无法处理重复点赞、取消点赞和审计。
2. 只依赖 Redis 可能在故障或过期后丢状态，权威数据要落库。
3. 计数和明细可能短暂不一致，要有对账和修正。
4. MQ 至少一次投递会重复消费，消费者必须幂等。
5. 热门视频单 key 计数会成为 Redis 或数据库热点。

## 8. 面试回答模板

我会把点赞拆成明细状态和聚合计数。明细表用 `(video_id,user_id)` 唯一键保证幂等，记录 liked/canceled；计数表或 Redis 计数用于高频读取。简单场景可以在数据库事务里更新明细和计数；高并发场景用 Redis Lua 原子判断旧状态并更新计数，再发 MQ 异步落库，消费端幂等处理，后台对账修正。读路径优先读 Redis 和本地短缓存，热点视频做计数分片和批量落库。要强调重复点赞不重复加、取消不减成负数、MQ 重试不产生脏计数。
