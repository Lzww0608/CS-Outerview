# 7. Agentic-RAG 与问题定位

Agentic-RAG 是把传统 RAG 的“固定检索再生成”扩展成可规划、可判断、可多步调用工具的问答系统。面试里问“判定节点怎么设置、数据怎么召回、为什么初始召回后还要其他逻辑、智能问答出问题怎么定位”，核心是在考 RAG 是否能工程化闭环。

## 1. 传统 RAG 和 Agentic-RAG 的区别

传统 RAG 常见链路：

```text
query -> retrieve -> rerank -> prompt -> answer
```

Agentic-RAG 会在链路中加入状态、判断和工具：

```text
query
-> 意图识别/路由
-> 查询改写
-> 多路召回
-> 证据判定
-> 必要时继续检索或调用工具
-> rerank
-> 生成答案
-> 引用校验/拒答
```

区别不在于“用了几个模型”，而在于系统是否能根据中间结果决定下一步。例如召回证据不足时继续改写查询，用户问题涉及实时订单时调用业务 API，涉及无权限文档时拒绝输出。

## 2. 主要逻辑

一个可落地的 Agentic-RAG 可以拆成这些节点：

1. **Query Understanding**：识别用户意图、语言、实体、时间范围、是否需要外部工具。
2. **Router**：判断查产品文档、FAQ、工单、代码库、数据库还是业务 API。
3. **Query Rewrite**：把省略、指代、多轮上下文改写成可检索查询。
4. **Retriever**：向量召回、BM25、规则召回、标题召回并行执行。
5. **Evidence Judge**：判断证据是否足够、是否冲突、是否有权限。
6. **Reranker**：对候选 chunk 做 Cross-Encoder 或规则重排。
7. **Generator**：基于证据回答，并输出引用。
8. **Verifier**：检查答案是否被证据支撑，必要时拒答或二次检索。

## 3. 判定节点用大模型还是函数

判定节点不应该一律交给大模型，也不应该全部写死规则。更稳的是分层：

| 判定类型 | 推荐方式 | 原因 |
| --- | --- | --- |
| 权限、租户、资源归属 | 函数/权限系统 | 必须确定、可审计，不能让模型决定 |
| 分数阈值、topK、超时、重试次数 | 函数/配置 | 可控、可压测、便于回滚 |
| query 类型、是否需要追问 | 小模型或 LLM 分类 | 自然语言表达复杂，规则覆盖困难 |
| 证据是否回答问题 | reranker/LLM judge + 规则兜底 | 需要语义判断，但要有阈值和引用检查 |
| 是否调用高风险工具 | 函数规则 + 人工审批 | 涉及副作用，模型只能提出建议 |

面试里可以说：权限、安全、状态流转用确定性函数；语义判断、意图识别、证据充分性可以用模型，但模型输出要结构化，并受阈值、白名单、最大步数和审计约束。

## 4. 为什么初始召回后还要其他逻辑

初始召回通常只解决“可能相关”，不保证“足以回答”。后续逻辑包括：

1. **权限过滤**：先保证不能把无权限 chunk 给模型。
2. **去重合并**：同一文档相邻 chunk 或重复来源要合并，避免浪费上下文。
3. **多路融合**：向量召回擅长语义，BM25 擅长关键词、编号、函数名。
4. **rerank**：把真正能回答问题的证据排到前面。
5. **上下文扩展**：命中小 chunk 后补前后段落、标题和父块。
6. **证据判定**：证据不足时追问、改写查询、二次检索或拒答。
7. **引用校验**：答案必须能对应到具体来源，降低幻觉。

## 5. 数据是怎么被召回的

召回一般是多路并行：

```text
用户问题
-> query rewrite
-> vector topK
-> BM25 topK
-> metadata filter
-> rule/title/entity recall
-> merge 去重
-> rerank
-> topN evidence
```

召回结果通常不是单纯文本，而是结构化对象：

```json
{
  "chunk_id": "c_001",
  "doc_id": "d_100",
  "score": 0.82,
  "source": "vector",
  "content": "......",
  "metadata": {
    "title": "Redis 持久化",
    "page": 3,
    "acl": "team-a",
    "version": 12
  }
}
```

保留 `source/score/metadata/version` 是为了排障、评测、引用和反馈学习。

## 6. 智能问答出问题怎么定位

不要直接说“模型答错了”，要按链路拆。

| 环节 | 常见问题 | 排查方法 |
| --- | --- | --- |
| 文档加载 | 原文解析乱码、表格丢失、权限缺失 | 查看原文、解析后文本、metadata、ACL |
| 文本切分 | chunk 太碎或太大，语义被切断 | 查看命中 chunk 的前后文和标题 |
| 向量化 | embedding 模型版本错、维度错、内容为空 | 检查向量维度、模型版本、入库日志 |
| 召回 | 正确证据没进 topK | 看 Recall@K、召回来源、query rewrite |
| rerank | 正确证据召回了但排后面 | 看 rerank 分数、候选列表、截断情况 |
| prompt | 证据放入顺序差、上下文超长被截断 | 打印最终 prompt 和 token 使用 |
| 生成 | 无证据编造、引用不对应 | 做引用校验、无答案拒答测试 |
| 工具调用 | 参数错、权限不足、超时 | 看工具输入输出、trace_id、错误码 |

线上应记录一次问答的 trace：

```text
request_id
query / rewritten_query
retrieval candidates
rerank scores
selected evidence
final prompt hash
answer
citations
latency / token / error_code
```

这样才能复现 badcase，而不是只拿用户看到的最终答案猜原因。

## 7. 真实场景降级

1. 向量库超时：退化到 BM25、热门 FAQ 或明确提示稍后重试。
2. reranker 超时：使用融合分数排序，缩小 topK。
3. 证据不足：追问用户或拒答，不要强行生成。
4. 权限系统异常：fail closed，不返回可能越权的内容。
5. 工具调用失败：返回可解释错误，保留 trace，必要时转人工。

## 8. 面试回答模板

Agentic-RAG 相比传统 RAG，多了意图识别、路由、查询改写、证据判定、工具调用和验证节点。我的做法是确定性规则和模型判断结合：权限、租户、阈值、重试和高风险动作由函数和配置控制；意图分类、证据是否足够、是否需要追问可以用模型或 reranker，但输出要结构化并有最大步数、阈值和审计。召回会走向量、BM25、规则和标题多路，合并去重后 rerank，再做上下文扩展和引用校验。用户反馈答错时，我会按加载、切分、向量化、召回、rerank、prompt、生成、工具调用逐层看 trace，先判断正确证据有没有入库、有没有召回、有没有排到前面，最后再定位是不是模型生成问题。
