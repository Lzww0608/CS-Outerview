# 3. 文档入库与文本存储

RAG 项目里“如何将文档传入数据库、如何检索相关文本片段、文本是否存全量”本质上是文档入库、索引和存储分层问题。

## 1. 文档入库流程

典型链路：

```text
上传文档
  -> 保存原始文件
  -> 解析文本和结构
  -> 清洗、去噪、权限标注
  -> chunk 切分
  -> embedding 向量化
  -> 写向量库
  -> 写元数据和全文存储
```

解析阶段要保留标题、页码、段落层级、表格、图片 OCR、URL、租户、权限和版本号。否则后面即使命中相关片段，也很难做引用溯源、权限过滤和增量更新。

## 2. 文本是否存全量

向量库不一定适合存全量原文。常见做法是分层存储：

| 数据 | 存储位置 | 作用 |
| --- | --- | --- |
| 原始文件 | 对象存储 / 文件系统 | 下载、重解析、审计 |
| 文档元数据 | MySQL / PostgreSQL | 文档状态、版本、权限、来源 |
| chunk 文本 | MySQL / Elasticsearch / 向量库 payload | 召回后拼 prompt、引用展示 |
| embedding | 向量数据库 | 语义检索 |
| 关键词索引 | Elasticsearch / OpenSearch | BM25、精确词、编号、错误码检索 |

中小规模项目可以把 chunk 文本直接放在向量库 payload 里，链路简单。大规模或权限复杂时，更推荐向量库只保存 `chunk_id/doc_id/metadata/embedding`，召回后再按 ID 去 MySQL、ES 或对象存储取文本。

## 3. 如何检索相关片段

在线查询通常不是单纯向量 topK：

```text
用户问题
  -> query rewrite
  -> 向量召回
  -> BM25/关键词召回
  -> 权限过滤
  -> merge 去重
  -> rerank
  -> 取 topN chunk 拼接 prompt
```

保留 `chunk_id` 很重要：

1. 用于去重，避免同一段文本重复进入上下文。
2. 用于权限校验，防止召回无权文档。
3. 用于引用溯源，展示文档标题、页码、URL。
4. 用于反馈闭环，记录用户点击或人工标注。

## 4. 数据很多怎么办

数据量变大后，重点不是“把数据库换大”，而是分层、分片和增量。

1. **分片分库**：按租户、业务线、知识库、时间或 doc_id 分片。
2. **冷热分层**：热点 chunk 放高性能向量索引，冷文档放低成本存储，需要时再召回或重建。
3. **增量索引**：文档更新只重建变更 chunk，并用版本号原子切换。
4. **混合召回**：向量召回负责语义相似，BM25 负责精确词、编号、代码符号。
5. **向量压缩**：用 IVF、PQ/SQ、HNSW 参数调优控制内存和召回率。
6. **异步管道**：上传和入库解耦，解析、embedding、索引写入通过 MQ 重试和限流。
7. **评测闭环**：用 Recall@K、NDCG、引用准确率、无答案拒答率监控质量。

## 5. 易错点

1. 整篇文档只做一个 embedding，召回粒度太粗。
2. 只存向量不存原文和元数据，召回后无法拼上下文和引用。
3. 不做权限过滤，RAG 很容易泄漏文档。
4. 文档更新不带版本号，可能同时召回新旧 chunk。
5. 数据量大时继续全量重建，会拖垮 embedding 服务和向量库。

## 6. 面试回答模板

文档入库我会先保存原始文件，再解析文本和结构，按段落或 token 切成 chunk，每个 chunk 生成 embedding。向量库保存 embedding、chunk_id、doc_id 和必要 metadata；chunk 文本可以中小规模直接放向量库 payload，大规模时放 MySQL/ES/对象存储，召回后按 ID 取回。在线检索会做向量召回和 BM25 混合召回，再做权限过滤、去重、rerank，最后取 topN 片段拼 prompt。数据很多时用分片、冷热分层、增量索引、向量压缩、异步入库和评测闭环来控制成本和质量。
