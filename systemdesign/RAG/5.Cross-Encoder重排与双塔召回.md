# 5. Cross-Encoder 重排与双塔召回

RAG 里常见链路是先用双塔模型或 BM25 做大范围召回，再用 Cross-Encoder 对少量候选精排。面试问 Cross-Encoder 和 Bi-Encoder 的区别，本质是在问召回和重排为什么要分阶段。

## 1. Bi-Encoder 是什么

Bi-Encoder 也叫双塔模型，它把 query 和 document 分别编码成向量：

```text
query -> encoder -> q_vec
doc   -> encoder -> d_vec
score = cosine(q_vec, d_vec) 或 dot(q_vec, d_vec)
```

优势：

1. 文档向量可以离线预计算并写入向量库。
2. 在线只需要计算 query 向量，再做 ANN 检索。
3. 延迟低、吞吐高，适合百万到亿级候选召回。

缺点：

1. query 和 doc 在编码阶段没有 token 级交互。
2. 对否定、条件、细粒度约束、表格行列关系的判断较弱。
3. 向量相似不等于证据能支撑答案，容易把语义相近但不能回答问题的片段召回到前面。

## 2. Cross-Encoder 是什么

Cross-Encoder 把 query 和 document 拼接后一起输入同一个模型：

```text
[CLS] query [SEP] document [SEP]
  -> Transformer
  -> relevance score
```

由于 query token 和 document token 可以在 self-attention 中直接交互，Cross-Encoder 能判断更细的匹配关系，例如：

1. 问题中的限定条件是否在文档中被满足。
2. 文档是否只是提到了关键词，还是确实给出了答案。
3. 数字、版本、错误码、函数名是否精确对应。
4. 否定句和条件句是否被正确理解。

代价是每个 query-document pair 都要跑一次模型，不能像双塔那样离线预计算文档向量，因此一般只用于 topK 候选重排。

## 3. Cross-Encoder 怎么计算相关性分数

以 BERT 类 reranker 为例，输入通常是：

```text
[CLS] query tokens [SEP] chunk tokens [SEP]
```

模型输出 hidden states 后，常见打分方式有两种：

1. **分类头**：取 `[CLS]` 向量接一个线性层，输出相关/不相关的 logits，再用 softmax 得到相关概率。
2. **回归头**：取 `[CLS]` 向量接线性层，直接输出一个实数 relevance score。

训练目标通常是：

1. **Pointwise**：单个 pair 标注相关或不相关，用交叉熵或 MSE。
2. **Pairwise**：给定正例和负例，要求正例分数高于负例，例如 margin ranking loss。
3. **Listwise**：对同一个 query 的候选列表整体排序，优化 NDCG 相关目标。

在线推理时，系统会对每个候选 chunk 计算分数：

```text
score_i = CrossEncoder(query, chunk_i)
```

然后按 `score_i` 降序取 topN 拼 prompt。这个分数通常不是概率的绝对真理，而是用于同一个 query 下候选之间比较。

## 4. 和双塔模型的对比

| 对比项 | Bi-Encoder | Cross-Encoder |
| --- | --- | --- |
| 输入方式 | query 和 doc 分开编码 | query 和 doc 拼接后共同编码 |
| token 交互 | 编码后只做向量相似度 | self-attention 中细粒度交互 |
| 文档预计算 | 支持 | 不支持 |
| 检索规模 | 适合大规模召回 | 适合小候选集重排 |
| 延迟成本 | 低 | 高 |
| 相关性判断 | 粗粒度语义相似 | 细粒度证据匹配 |
| 典型位置 | 第一阶段召回 | 第二阶段 rerank |

因此真实 RAG 通常不是二选一，而是组合使用：

```text
BM25 / Bi-Encoder / 规则召回
  -> merge 去重
  -> Cross-Encoder rerank
  -> prompt topN
```

## 5. 易错点

1. Cross-Encoder 准确率更高，但不能直接拿它扫全库，否则成本和延迟不可接受。
2. Bi-Encoder 召回的 Recall@K 决定候选池上限；如果正确证据没召回，reranker 再强也排不出来。
3. Cross-Encoder 的输入长度有限，chunk 太长会被截断，表格和代码块要特别注意切分。
4. rerank 分数只适合同一个 query 下排序，不一定能跨 query 直接比较。
5. 生产系统要给 reranker 设置超时和降级，失败时可以退回融合分数排序。

## 6. 真实场景

企业知识库问答可以这样设计：

1. 离线对 chunk 生成 embedding，写入向量库；同时建 BM25 倒排索引。
2. 在线 query 并行走向量召回 top50、BM25 top50 和标题召回 top20。
3. 使用 RRF 合并去重，取前 80 个候选。
4. 用 Cross-Encoder 对 80 个候选打分，取 top8 进入 prompt。
5. 记录召回来源、rerank 分数、最终引用和用户反馈，用于优化评测集。

如果延迟预算很紧，可以缩小 rerank 候选数、使用小型 reranker、批量推理、GPU 常驻服务或缓存热门 query 的重排结果。

## 7. 面试回答模板

Bi-Encoder 是双塔结构，query 和文档分别编码成向量，在线用向量相似度做 ANN 召回，优点是文档向量可预计算、速度快，适合大规模候选召回。Cross-Encoder 是把 query 和 chunk 拼接输入同一个 Transformer，让两边 token 在 attention 中直接交互，再通过 `[CLS]` 分类头或回归头输出相关性分数，判断更细但成本更高。真实 RAG 里我会先用 BM25 和 Bi-Encoder 保证 Recall@K，再用 Cross-Encoder 对几十个候选重排，最后取高分片段拼 prompt。
