# 1.RAG 架构与 Eino

RAG（Retrieval-Augmented Generation，检索增强生成）是一种把外部知识检索和大模型生成结合起来的架构。它先从知识库中召回和用户问题相关的文档片段，再把这些片段作为上下文交给大模型生成答案。

## 1. 为什么需要 RAG？

大模型本身有几个限制：

1. 训练数据有时间截止，无法知道最新业务知识。
2. 对企业内部文档、数据库、代码仓库没有天然访问能力。
3. 直接让模型回答容易产生幻觉。
4. 把所有文档都塞进 prompt 成本高，也受上下文长度限制。

RAG 的目标是让模型“带资料作答”，用检索结果约束回答范围，提升准确性、可追溯性和可更新性。

## 2. RAG 的整体架构

典型 RAG 系统分为两条链路：离线建库链路和在线问答链路。

### 2.1 离线建库链路

```text
文档采集
  -> 清洗解析
  -> 分块 chunking
  -> embedding 向量化
  -> 写入向量数据库
  -> 写入元数据和原文存储
```

关键点：

1. 文档解析要保留标题、层级、页码、URL、权限等元数据。
2. 分块不能太大，否则召回不精确；也不能太小，否则上下文丢失。
3. embedding 模型要和查询侧保持一致。
4. 向量库通常只保存向量、chunk id、元数据和必要文本；大原文可以放对象存储或数据库。

### 2.2 在线问答链路

```text
用户问题
  -> 查询改写 / 意图识别
  -> embedding 向量化
  -> 向量召回 / 关键词召回 / 混合召回
  -> rerank 重排
  -> prompt 拼接
  -> LLM 生成
  -> 引用来源 / SSE 流式返回
```

真实项目里，RAG 不只是“向量库 topK + LLM”。为了效果稳定，常见还会加入 query rewrite、多路召回、重排、权限过滤、上下文压缩、引用溯源和答案后校验。

## 3. 为什么使用 Eino？

Eino 是 CloudWeGo 下的 Go 语言 AI 应用开发框架，定位是用 Go 构建 LLM 应用。它提供组件抽象和编排能力，适合把 RAG 里的 Loader、Splitter、Indexer、Retriever、Embedding、ChatModel、Tool、PromptTemplate 等节点组合成稳定链路。

项目选择 Eino 可以从这些角度回答：

1. **Go 技术栈统一**：后端项目如果主要用 Go，使用 Eino 可以避免为了 RAG 单独引入 Python 服务。
2. **组件化**：RAG 的各个步骤可以抽象成组件，便于替换 embedding 模型、向量库、重排器和大模型。
3. **编排能力**：Eino 提供 Chain、Graph、Workflow 等编排方式，适合表达 RAG、Agent、多路召回这类有明确数据流的任务。
4. **流式处理**：大模型输出通常需要流式返回，Eino 对 stream 场景有框架层支持。
5. **可观测和扩展**：回调、日志、trace、评估等横切能力更容易统一接入。
6. **类型安全**：Go 的类型系统能减少复杂链路中输入输出结构不一致的问题。

## 4. Eino 适合放在哪一层？

Eino 更适合放在 AI 编排层，而不是替代业务系统所有逻辑。

```text
HTTP/Gin/Kratos 接入层
  -> 业务鉴权、配额、会话
  -> Eino RAG/Agent 编排层
      -> Retriever
      -> Reranker
      -> ChatModel
      -> Tool
  -> SSE/HTTP 返回
```

业务层仍然负责用户、权限、会话、审计、限流、计费等；Eino 负责 LLM 应用链路的组件组织和执行。

## 5. 面试回答模板

RAG 项目一般分为离线建库和在线问答两条链路。离线链路负责文档采集、清洗、切分、embedding 向量化和写入向量数据库；在线链路负责用户问题改写、向量召回、关键词召回、重排、拼接 prompt，然后调用大模型生成答案，最后通过 SSE 之类的方式流式返回。

使用 Eino 的原因是它更符合 Go 后端项目的技术栈，同时提供了 LLM 应用常见的组件抽象和编排能力。RAG 里的 Retriever、Indexer、ChatModel、PromptTemplate、Tool 都可以作为组件组织起来，通过 Chain、Graph 或 Workflow 表达复杂链路。这样比手写一堆串行调用更容易扩展、替换组件、做流式处理和接入日志追踪。
