# 1.RAG 架构与 Eino

RAG（Retrieval-Augmented Generation，检索增强生成）是一种把外部知识检索和大模型生成结合起来的架构。它先从知识库中召回和用户问题相关的文档片段，再把这些片段作为上下文交给大模型生成答案。

## 1. 为什么需要 RAG？

大模型本身有几个限制：

1. 训练数据有时间截止，无法知道最新业务知识。
2. 对企业内部文档、数据库、代码仓库没有天然访问能力。
3. 直接让模型回答容易产生幻觉。
4. 把所有文档都塞进 prompt 成本高，也受上下文长度限制。

RAG 的目标是让模型“带资料作答”，用检索结果约束回答范围，提升准确性、可追溯性和可更新性。

## 2. RAG 的整体架构

典型 RAG 系统分为两条链路：离线建库链路和在线问答链路。

### 2.1 离线建库链路

```text
文档采集
  -> 清洗解析
  -> 分块 chunking
  -> embedding 向量化
  -> 写入向量数据库
  -> 写入元数据和原文存储
```

关键点：

1. 文档解析要保留标题、层级、页码、URL、权限等元数据。
2. 分块不能太大，否则召回不精确；也不能太小，否则上下文丢失。
3. embedding 模型要和查询侧保持一致。
4. 向量库通常只保存向量、chunk id、元数据和必要文本；大原文可以放对象存储或数据库。

### 2.2 在线问答链路

```text
用户问题
  -> 查询改写 / 意图识别
  -> embedding 向量化
  -> 向量召回 / 关键词召回 / 混合召回
  -> rerank 重排
  -> prompt 拼接
  -> LLM 生成
  -> 引用来源 / SSE 流式返回
```

真实项目里，RAG 不只是“向量库 topK + LLM”。为了效果稳定，常见还会加入 query rewrite、多路召回、重排、权限过滤、上下文压缩、引用溯源和答案后校验。

### 2.2.1 RAG 和直接把文档丢给大模型的区别

直接把文档放进大模型上下文，本质是“长上下文阅读”；RAG 本质是“先检索再阅读”。两者不是互斥关系，很多系统会把 RAG 召回片段放进长上下文里让模型综合回答。

| 对比项 | 直接长上下文 | RAG |
| --- | --- | --- |
| 输入方式 | 把完整文档或大量文档直接拼进 prompt | 先检索 topK 片段，再拼进 prompt |
| 成本 | token 成本高，长文档每次都要重复输入 | 只输入相关片段，成本更可控 |
| 延迟 | 长输入会增加模型预填充延迟 | 增加检索和重排延迟，但减少模型输入 |
| 召回范围 | 受模型上下文窗口限制 | 知识库可远大于上下文窗口 |
| 更新方式 | 每次重新传文档 | 更新索引即可 |
| 权限控制 | 需要在拼 prompt 前过滤整批文档 | 检索阶段可按 ACL、租户、版本过滤 |
| 可追溯性 | 可引用上下文中的位置，但管理较粗 | chunk 天然带 doc_id、页码、URL、版本 |
| 适用场景 | 单份或少量文档精读、合同审阅、代码文件分析 | 企业知识库、海量文档问答、客服、运维知识检索 |

直接长上下文的优势是实现简单，模型能看到更完整的上下文，适合单份文档、多章节互相依赖的分析。缺点是成本高、窗口有限、无关内容会干扰注意力，且每次请求都要重新传大量文本。

RAG 的优势是可扩展、可更新、可控权限、可引用。缺点是系统复杂度更高，效果受解析、切分、embedding、召回、重排和 prompt 影响。如果检索召回错了，模型再强也可能答错。

真实项目里可以这样选：

1. 文档很少、一次性分析，优先长上下文。
2. 文档很多、知识频繁更新、需要权限和引用，优先 RAG。
3. 问题需要跨很多文档聚合，先 RAG 召回候选，再用长上下文综合。
4. 对实时业务数据，优先工具/API 查询，不要只依赖静态文档或模型记忆。

### 2.3 端到端 RAG 的关键细节

端到端 RAG 可以按“数据准备、索引构建、在线检索、生成校验、评测闭环”五段展开。

1. **数据准备**：文档采集后要解析正文、标题、表格、代码块、页码、URL、更新时间和权限字段。PDF、网页、Markdown、工单、代码仓库的清洗方式不同，不能只把纯文本拼成一段。
2. **切分和存储**：chunk 要兼顾语义完整和检索粒度。常见做法是按标题/段落切分，设置 overlap，并保留 `doc_id、chunk_id、section_path、version、acl` 等元数据。小块用于召回，父块或相邻块用于生成。
3. **多索引入库**：同一份 chunk 通常同时进入向量索引、BM25/关键词索引和原文存储。向量索引用于语义召回，BM25 用于错误码、函数名、专有名词，原文存储用于回填内容和引用。
4. **在线查询处理**：先做意图识别、权限上下文提取和 query rewrite，多轮对话要把“它怎么配置”补全成明确实体。检索时向量、BM25、标题召回可以并行执行，并分别设置超时预算。
5. **融合和重排**：多路召回结果要按 `doc_id/chunk_id` 去重，再用 RRF、加权分数或业务规则融合，最后用 cross-encoder reranker 把真正能支撑答案的片段排到前面。
6. **Prompt 构建**：只把 topN 高置信片段放入上下文，并带上来源、标题、时间和引用 ID。低分片段、重复片段和无权限片段不能进入 prompt。
7. **生成和后校验**：模型回答要受“只基于资料回答”的系统约束，输出后可以检查引用是否存在、答案是否越权、是否需要拒答或转人工。
8. **评测闭环**：用离线问题集评估 Recall@K、MRR/NDCG、答案正确率、引用准确率、无答案拒答率、P95/P99 延迟和 token 成本，再根据失败样本优化切分、改写、索引和重排。

### 2.4 RAG 和微调如何选择

RAG 和 Fine-tune 解决的问题不同。RAG 是“把外部知识拿进来”，微调是“改变模型的行为、风格或领域能力”。面试里不要把二者说成互斥关系，很多真实系统会组合使用。

优先选择 RAG 的场景：

1. **知识频繁变化**：商品、政策、文档、工单、代码仓库、数据库记录每天都变，重新训练成本高。
2. **需要引用来源**：客服、法务、运维、企业知识库问答需要给出文档片段、URL、页码或权限来源。
3. **私有知识量大**：知识本身不适合全部放进模型参数，也不希望把敏感数据用于训练。
4. **需要权限控制**：不同用户只能看到自己有权限的文档，检索阶段可以做 ACL 过滤。
5. **快速上线迭代**：改分块、索引、召回、重排和 prompt 通常比重新微调更快。

优先选择微调的场景：

1. **输出格式稳定**：模型需要长期按固定 JSON、SQL、DSL、标签体系或话术风格输出。
2. **任务技能稳定**：分类、抽取、改写、代码补全、特定领域推理模式相对固定。
3. **少量上下文难以教会**：靠 prompt 很难稳定遵守的风格、术语、步骤，可以用 SFT/LoRA 做行为对齐。
4. **追求低延迟低成本**：把常见能力内化到较小模型里，减少长 prompt 和多轮检索成本。

对比总结：

| 维度 | RAG | 微调 |
| --- | --- | --- |
| 主要目标 | 注入外部知识 | 改变模型行为和能力 |
| 知识更新 | 更新索引即可 | 通常要重新训练或增量训练 |
| 可追溯性 | 可以给引用 | 参数内知识难解释 |
| 权限控制 | 检索阶段可过滤 | 训练进参数后难按用户隔离 |
| 典型成本 | 向量库、重排、检索延迟 | 数据标注、训练、评测、部署 |

组合方案：

```text
RAG 提供最新、可引用、可控权限的知识
+ 微调让模型更会使用这些知识、遵守输出格式和业务话术
+ 评测集持续衡量召回、引用、答案正确率和格式稳定性
```

例如企业知识库问答通常先做 RAG；如果发现模型经常不按客服话术回答、JSON 格式不稳定或不会使用某类业务证据，再用高质量样本做轻量微调。反过来，不要用微调硬记每天变化的价格、库存、政策和用户数据，这类信息应该放在检索或工具调用里。

### 2.5 大模型认知和 RAG 检索冲突怎么办

大模型参数里的知识和 RAG 检索结果冲突时，不能让模型“凭感觉选一个”。工程上要先明确权威源和时效性：企业内部知识、实时业务数据、配置、价格、库存、权限、规章制度应以检索到的权威资料或工具查询结果为准；模型参数知识只能作为语言组织和通用推理能力。

常见冲突来源：

1. **知识时效不同**：模型训练时的知识过期，文档或数据库更新了。
2. **检索召回错误**：RAG 召回了相似但不相关的文档。
3. **文档版本冲突**：旧版本文档和新版本文档同时存在。
4. **权限或租户错配**：召回了用户无权访问或不属于当前租户的资料。
5. **用户问题歧义**：问题没有说明产品、版本、环境，导致模型和检索各自补全了不同上下文。

处理策略：

1. **Prompt 明确优先级**：系统指令中写明“回答必须基于检索资料；检索资料不足或冲突时说明冲突并拒绝编造”。
2. **资料带元数据**：每个 chunk 带 `source_id、version、updated_at、acl、product、env`，生成前先过滤过期和无权限内容。
3. **冲突检测**：对 topN 证据做版本、时间、来源可信度和实体一致性检查；必要时用规则或 NLI 模型判断相互矛盾。
4. **要求引用来源**：最终答案必须引用支撑结论的资料 ID，无法引用就降低置信度或拒答。
5. **澄清问题**：如果冲突来自版本、环境或业务对象不明确，先问用户补充，而不是强行回答。
6. **转工具查询**：对实时状态类问题，例如订单、库存、配置开关，优先调用业务 API，不用模型记忆和静态文档决策。
7. **转人工或升级**：高风险冲突，例如法务、财务、生产变更，输出冲突证据并交给人工确认。
8. **反馈闭环**：把冲突样本记录到评测集，修正文档版本、召回规则、重排模型或 Prompt。

示例回答策略：

```text
如果 RAG 检索结果和模型原有认知冲突，我会优先相信带权限、版本和时间戳的检索结果。
如果检索结果内部也冲突，就不直接给确定结论，而是展示冲突来源、说明需要确认的版本或环境，并请求用户补充或转人工。
```

易错点是把“检索到了内容”当成一定正确。RAG 只能降低幻觉，不自动保证事实正确；最终可靠性还要靠权威数据源、元数据过滤、重排、引用校验和人工兜底。

## 3. 为什么使用 Eino？

Eino 是 CloudWeGo 下的 Go 语言 AI 应用开发框架，定位是用 Go 构建 LLM 应用。它提供组件抽象和编排能力，适合把 RAG 里的 Loader、Splitter、Indexer、Retriever、Embedding、ChatModel、Tool、PromptTemplate 等节点组合成稳定链路。

项目选择 Eino 可以从这些角度回答：

1. **Go 技术栈统一**：后端项目如果主要用 Go，使用 Eino 可以避免为了 RAG 单独引入 Python 服务。
2. **组件化**：RAG 的各个步骤可以抽象成组件，便于替换 embedding 模型、向量库、重排器和大模型。
3. **编排能力**：Eino 提供 Chain、Graph、Workflow 等编排方式，适合表达 RAG、Agent、多路召回这类有明确数据流的任务。
4. **流式处理**：大模型输出通常需要流式返回，Eino 对 stream 场景有框架层支持。
5. **可观测和扩展**：回调、日志、trace、评估等横切能力更容易统一接入。
6. **类型安全**：Go 的类型系统能减少复杂链路中输入输出结构不一致的问题。

## 4. Eino 适合放在哪一层？

Eino 更适合放在 AI 编排层，而不是替代业务系统所有逻辑。

```text
HTTP/Gin/Kratos 接入层
  -> 业务鉴权、配额、会话
  -> Eino RAG/Agent 编排层
      -> Retriever
      -> Reranker
      -> ChatModel
      -> Tool
  -> SSE/HTTP 返回
```

业务层仍然负责用户、权限、会话、审计、限流、计费等；Eino 负责 LLM 应用链路的组件组织和执行。

## 5. 面试回答模板

RAG 项目一般分为离线建库和在线问答两条链路。离线链路负责文档采集、清洗、切分、embedding 向量化和写入向量数据库；在线链路负责用户问题改写、向量召回、关键词召回、重排、拼接 prompt，然后调用大模型生成答案，最后通过 SSE 之类的方式流式返回。

使用 Eino 的原因是它更符合 Go 后端项目的技术栈，同时提供了 LLM 应用常见的组件抽象和编排能力。RAG 里的 Retriever、Indexer、ChatModel、PromptTemplate、Tool 都可以作为组件组织起来，通过 Chain、Graph 或 Workflow 表达复杂链路。这样比手写一堆串行调用更容易扩展、替换组件、做流式处理和接入日志追踪。
