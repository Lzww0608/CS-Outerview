# 9. RAG 召回评测与优化闭环

RAG 召回优化不是“向量库 topK 调大”这么简单。真实链路通常会组合向量召回、BM25、规则召回、标题召回和 Rerank，并用离线评测集、线上 badcase 和可观测 trace 持续闭环。

## 1. 向量 + BM25 + Rerank 的来源

这个组合不是拍脑袋设计的，而是搜索和 RAG 系统里的常见多阶段检索架构：

```text
多路粗召回
  -> 候选合并去重
  -> 融合打分
  -> Cross-Encoder / LLM Rerank
  -> topN 证据进入 Prompt
```

可以参考的成熟原型或框架思路包括：

1. **搜索引擎架构**：先召回候选，再排序、重排、过滤和多样性控制。
2. **LlamaIndex / LangChain / Haystack**：都支持 retriever、reranker、query rewrite、metadata filter 等组件化链路。
3. **Elasticsearch / OpenSearch**：BM25、倒排、字段权重、过滤器和 hybrid search。
4. **向量数据库**：Milvus、Qdrant、Weaviate、pgvector 等提供 ANN 和 metadata filter。
5. **Eino / LangGraph 类编排框架**：用于把 Loader、Splitter、Retriever、Reranker、Generator 串成可观测链路。

面试里可以说：方案参考的是成熟搜索系统的“召回-粗排-精排”范式。向量负责语义相似，BM25 负责关键词、错误码、函数名、专有名词，Rerank 负责判断候选是否真正能回答问题。

## 2. 召回率怎么定义

RAG 里的召回率要先定义清楚。常见指标包括：

1. **Recall@K**：正确证据是否出现在前 K 个召回候选里。
2. **MRR**：第一个正确证据出现得越靠前越好。
3. **NDCG@K**：考虑多个证据的相关性等级和排序位置。
4. **Answer Support Rate**：进入 Prompt 的证据是否足以支撑最终答案。
5. **Citation Accuracy**：最终引用是否真的支持回答。

如果说“Rerank 后召回率 95%”，要说明是 Recall@K 提升，还是最终 topN 证据覆盖率提升。严格讲，Rerank 不能召回库里没进候选池的文档，它只能把已经召回的正确证据排到更靠前的位置。

## 3. 剩下 5% 没召回的原因

RAG badcase 要按链路拆，不要直接归因给模型。

| 环节 | 可能原因 | 例子 |
| --- | --- | --- |
| 数据采集 | 文档没入库、版本过旧、权限字段错误 | 新功能文档未同步 |
| 文档解析 | PDF 表格丢失、代码块被打乱、乱码 | 参数说明在表格里但解析后丢列 |
| Chunk 切分 | 语义被切断、chunk 太大被截断、标题丢失 | 问题在段落 A，答案在段落 B |
| Embedding | 领域词、缩写、错误码语义弱 | `E11000`、函数名、配置项不匹配 |
| BM25 | 同义改写覆盖不到、中文分词问题 | “登录态” vs “Session” |
| Query Rewrite | 多轮指代补全错、实体识别错 | “它怎么配置”没补成具体产品 |
| Metadata Filter | 租户、版本、环境过滤过严或过松 | 只查 prod，答案在 common 文档 |
| ANN 检索 | topK 太小、索引参数召回不足 | HNSW `efSearch` 太低 |
| Rerank | 正确证据被截断或排低 | 证据在 chunk 后半段，被模型截掉 |
| 评测标注 | 标准答案不完整或过期 | 评测集只标了旧文档 |

分析 5% 时可以把 badcase 分桶：

```text
未入库 / 解析失败 / 切分失败 / 查询改写失败 / 向量未召回 /
BM25 未召回 / rerank 排错 / 权限过滤错 / 评测标注错 / 用户问题本身无答案
```

每个桶对应不同优化动作。如果正确证据没进候选池，调 Rerank 没用；如果进了候选但排低，才应该优化 Rerank、融合分数或 chunk 表达。

## 4. 除了建库和分片还能怎么优化

### Query 侧

1. **Query Rewrite**：把多轮省略、指代、口语化表达改写成可检索查询。
2. **多查询扩展**：为同一问题生成同义词、英文缩写、错误码、产品名变体。
3. **意图路由**：区分 FAQ、代码、工单、配置、实时业务数据，走不同索引或工具。
4. **实体抽取**：抽取产品、版本、环境、地域、时间范围，用于 metadata filter。

### Index 侧

1. **父子 chunk**：小 chunk 负责精确召回，父块或相邻块负责补足上下文。
2. **标题路径增强**：把章节标题、文档名、产品线注入 chunk，提升短文本召回。
3. **多粒度索引**：段落、章节、整篇摘要分别建索引。
4. **字段化索引**：标题、正文、代码、表格、FAQ 问题分别设置权重。

### Ranking 侧

1. **RRF 融合**：把向量、BM25、标题召回的排名融合，避免分数尺度不一致。
2. **Cross-Encoder Rerank**：对 topK 候选做细粒度相关性判断。
3. **业务规则加权**：新版本、权威来源、同产品同环境文档加权。
4. **多样性控制**：避免 topN 全来自同一文档相邻 chunk。

### Generation 侧

1. **上下文压缩**：把重复、低分、过长证据裁剪成可用上下文。
2. **引用约束**：答案必须引用 chunk id、文档链接或页码。
3. **无答案拒答**：证据分数低或冲突时拒答或追问，不强行编造。
4. **答案后校验**：检查回答是否被证据支撑，是否越权或引用错位。

### 工程侧

1. **缓存**：缓存热门 query 的召回、rerank 或最终答案。
2. **并行和超时**：多路召回并行，分别设置 timeout 和降级。
3. **可观测 trace**：记录 query、rewrite、候选、分数、prompt hash、引用和反馈。
4. **A/B 与回放**：用线上 badcase 回放评估新分块、新模型、新权重。

## 5. 真实 badcase 处理流程

```text
用户反馈答案错
-> 取 request_id 查 trace
-> 看正确文档是否入库
-> 看 query rewrite 是否正确
-> 看 vector/BM25 各自 topK
-> 看 merge/rerank 后位置
-> 看进入 prompt 的证据
-> 看最终回答和引用是否被证据支撑
-> 给 badcase 打标签并回放验证修复
```

修复要能量化。例如：

```text
问题：错误码类问题向量召回失败
原因：embedding 对短错误码语义弱
方案：BM25 字段权重提升 + 错误码正则规则召回
验证：错误码测试集 Recall@20 从 82% 到 96%
```

## 6. 易错点

1. Rerank 不能拯救“根本没召回”的正确文档。
2. topK 调大能提升召回，但会增加 rerank 成本和噪声。
3. 只看最终答案正确率不够，要分别看召回、排序、引用和拒答。
4. 召回率 95% 要说明评测集构造、标注口径和 K 值。
5. 线上 badcase 不能直接进训练或记忆，要先脱敏、标注和复核。

## 7. 面试回答模板

向量 + BM25 + Rerank 参考的是成熟搜索系统的多阶段检索范式，不是纯自己拍脑袋。向量解决语义召回，BM25 解决关键词、错误码、函数名、专有名词，Rerank 用 Cross-Encoder 判断候选是否真正能回答问题。剩下没召回的 5% 我会按链路打标签：是否未入库、解析失败、切分不合理、query rewrite 错、向量没召回、BM25 没召回、metadata filter 错、rerank 排错或评测标注有问题。优化上除了建库和分片，还会做查询改写、多路召回、RRF 融合、父子 chunk、标题增强、上下文压缩、引用校验、无答案拒答、trace 观测和 badcase 回放闭环。
