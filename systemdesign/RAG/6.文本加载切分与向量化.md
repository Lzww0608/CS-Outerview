# 6. 文本加载、文本切分与向量化

RAG 的入库质量很大程度取决于文本加载、切分和向量化。面试里问“文本加载怎么设置、按 token 切分和语义感知切分有什么区别、为什么要向量化”，本质是在考你是否理解从原始文档到可检索 chunk 的工程链路。

## 1. 文本加载是什么

文本加载是把不同来源的原始内容转换成统一的文档对象。它不只是 `read file`，还要保留结构、元数据和权限。

常见输入：

1. PDF、Word、PPT、Excel、Markdown、HTML、纯文本。
2. 网页、知识库、工单、邮件、IM 记录。
3. 数据库记录、对象存储文件、代码仓库。
4. OCR 图片、扫描件、表格和日志。

统一后的文档对象通常包含：

| 字段 | 作用 |
| --- | --- |
| `doc_id` | 文档唯一标识 |
| `content` | 提取后的正文 |
| `metadata` | 标题、页码、章节、URL、来源、更新时间 |
| `acl` | 租户、用户、角色、可见范围 |
| `version` | 文档版本，用于增量更新和回滚 |

## 2. 常见开源加载器

工程上通常不会每种格式都手写解析器，可以基于现有生态组合：

1. **LangChain DocumentLoader**：生态丰富，适合快速接入 PDF、网页、Notion、GitHub、数据库等。
2. **LlamaIndex Reader**：更偏知识库入库，支持多种数据源和节点解析。
3. **Unstructured**：适合复杂 PDF、Office、HTML、表格和扫描件解析。
4. **Apache Tika**：老牌内容抽取工具，覆盖大量文件类型。
5. **PyMuPDF / pdfplumber**：适合需要精细处理 PDF 页码、坐标、表格的场景。
6. **自定义 Loader**：用于企业内部接口、权限系统、业务数据库和特殊日志格式。

选型时要看格式覆盖率、解析质量、表格能力、OCR 能力、速度、部署成本和许可证。

## 3. 加载阶段要做哪些处理

1. **格式解析**：抽取文本、标题、页码、表格、图片 OCR、代码块。
2. **清洗去噪**：删除页眉页脚、目录噪声、重复导航、广告和乱码。
3. **结构保留**：保留标题层级、段落、表格行列、代码函数边界。
4. **权限标注**：文档入库时写入租户、角色、部门和用户 ACL。
5. **版本管理**：同一文档更新时记录版本，避免新旧 chunk 混召回。
6. **失败隔离**：单个文档解析失败不能阻塞整批任务，要进入重试或死信队列。

## 4. 文本切分为什么重要

切分的目标是在“语义完整”和“检索精确”之间取平衡。

chunk 太大：

1. embedding 表达被稀释，相似度不够敏感。
2. prompt 成本高，容易塞入无关内容。
3. reranker 输入可能被截断。

chunk 太小：

1. 缺少上下文，单个片段无法回答问题。
2. 多个相关片段容易被分散，召回后需要额外合并。
3. 指代词、表格上下文、标题约束容易丢失。

## 5. 按 token 切分

按 token 切分是最常见的基线方案。它先用目标 embedding/LLM 对应的 tokenizer 估算 token 数，再按 `chunk_size` 和 `overlap` 切分。

典型配置：

```text
chunk_size: 300 ~ 1000 tokens
overlap: 50 ~ 150 tokens
```

流程：

```text
文本清洗
-> tokenizer 计数
-> 按 chunk_size 切分
-> 相邻 chunk 保留 overlap
-> 写入 chunk_id、doc_id、page、heading、offset
```

优点是实现简单、长度可控、适配模型上下文；缺点是可能切断段落、表格和代码块。

易错点：

1. 不要用字符数直接等同 token 数，中文、英文、代码、符号差异很大。
2. 切分要尽量在句号、段落、标题、代码块边界处断开。
3. overlap 不是越大越好，过大会带来重复召回和更高存储成本。
4. tokenizer 要和 embedding 模型或最终 LLM 尽量一致，否则长度估算会偏。

## 6. 语义感知切分

语义感知切分会优先尊重文档结构和语义边界，而不是机械按长度切。

常见策略：

1. **结构切分**：Markdown heading、HTML DOM、PDF 标题、代码函数、表格块。
2. **段落合并**：短段落按标题或主题合并，直到接近 token 上限。
3. **句向量断点**：对句子生成 embedding，检测相邻句子语义突变点。
4. **父子块策略**：小 chunk 用于召回，大 parent chunk 用于提供上下文。
5. **语义窗口**：召回命中后向前后扩展邻近 chunk，补齐上下文。

示例：

```text
## Redis 持久化
段落 A: RDB 原理
段落 B: AOF 原理
段落 C: 混合持久化
```

如果按固定 token 切，可能把 AOF 的解释切到两个 chunk 中；语义切分会按标题和段落组织，必要时把短段落合并成一个完整主题块。

## 7. 文本向量化

向量化是把 chunk 转成 embedding，使语义相近的 query 和 chunk 在向量空间中距离更近。

核心步骤：

```text
chunk text
-> embedding model
-> dense vector
-> 写入向量库，附带 chunk_id/doc_id/metadata/version
```

注意事项：

1. **模型版本固定**：embedding 模型变更后，新旧向量空间不可直接混用，通常要重建索引或按版本隔离。
2. **维度校验**：写向量库前校验维度、归一化方式和距离度量。
3. **批量推理**：入库时批量调用 embedding 服务，提高吞吐。
4. **幂等写入**：用 `doc_id + chunk_id + version` 防止重复消费产生重复 chunk。
5. **异常重试**：embedding 超时、限流、内容过长都要可重试或可跳过并记录。

## 8. 真实场景参数怎么调

调参不能只凭感觉，应使用评测集：

1. 准备真实用户问题和标准证据 chunk。
2. 对比不同 `chunk_size/overlap/切分策略/embedding 模型` 的 Recall@K。
3. 观察 rerank 后 NDCG、引用准确率和最终回答正确率。
4. 分析 badcase：是解析失败、切分断语义、向量召回弱、BM25 缺失，还是 rerank 排错。
5. 对不同文档类型分策略：FAQ、手册、代码、表格、日志不一定共用一套切分。

## 9. 面试回答模板

文本加载我会先把 PDF、Word、网页、数据库等来源统一成 Document，保留正文、标题、页码、来源、权限和版本号。加载器可以用 LangChain、LlamaIndex、Unstructured、Tika、PyMuPDF，也可以为内部系统写自定义 Loader。切分上先用 token-based splitter 做基线，控制 chunk size 和 overlap；更高质量的方案会按标题、段落、表格、代码函数做语义感知切分，必要时用父子块策略，小块召回、大块拼上下文。向量化时每个 chunk 生成 embedding，带 `chunk_id/doc_id/metadata/version` 写入向量库，并用模型版本、维度校验、幂等写入和评测集保证稳定性。
