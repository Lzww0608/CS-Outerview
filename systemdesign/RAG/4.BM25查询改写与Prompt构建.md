# 4. BM25、查询改写与 Prompt 构建

知识库问答里，召回质量通常比“换一个更大的模型”更先决定上限。面试问 BM25、查询改写和 Prompt 构建，本质是在问：如何把用户问题稳定地转成可检索、可约束、可生成的上下文。

## 1. BM25 是怎么检索的

BM25 是经典的关键词相关性排序算法，建立在倒排索引之上。文档入库时先分词，得到“词项 -> 文档列表”的倒排表；查询时也分词，找到包含这些词项的候选文档，再计算每个文档和查询的相关性分数。

常见 BM25 公式可以写成：

```text
score(D, Q) = sum IDF(q_i) * f(q_i, D) * (k1 + 1)
                         / (f(q_i, D) + k1 * (1 - b + b * |D| / avgdl))
```

其中：

1. `f(q_i, D)` 是词 `q_i` 在文档 `D` 中出现的次数。
2. `IDF(q_i)` 表示词的稀有程度，越少见越有区分度。
3. `|D| / avgdl` 是文档长度归一化，避免长文档因为词多而天然占优。
4. `k1` 控制词频饱和，词出现很多次后分数增长会变慢。
5. `b` 控制长度归一化强度，常见默认值接近 `0.75`。

BM25 的优势是对精确词、编号、错误码、函数名、人名、产品名非常敏感；缺点是不理解语义相似，比如“登录失败”和“无法进入账号”可能没有共同关键词。

## 2. RAG 中为什么要混合召回

向量召回擅长语义相似，BM25 擅长精确匹配。真实知识库问答通常使用混合召回：

```text
query
  -> 向量召回 topK
  -> BM25/关键词召回 topK
  -> 规则召回/标题召回
  -> merge 去重
  -> rerank
  -> topN 拼 Prompt
```

合并多路召回结果时常用：

1. **加权分数**：归一化后按 `alpha * vector_score + beta * bm25_score` 排序。
2. **RRF**：Reciprocal Rank Fusion，用名次融合而不是直接比分数，适合不同检索器分数不可比的情况。
3. **业务规则提升**：标题命中、同租户、同产品线、最近版本、人工置顶文档可以加权。
4. **reranker 重排**：用 cross-encoder 或轻量 LLM 判断 query 和 chunk 是否真正能支撑答案。

## 3. 查询改写怎么做

查询改写的目标不是让问题“更像人话”，而是让检索系统更容易召回正确证据。

常见做法：

1. **标准化**：统一大小写、全半角、繁简体、同义词、产品别名、错误码格式。
2. **意图识别**：区分问答、排障、配置查询、代码说明、闲聊、无答案请求，不同意图走不同知识源。
3. **多查询扩展**：把一个问题改写成多个检索 query，例如原问题、关键词版、同义词版、英文术语版。
4. **上下文补全**：多轮对话里把“它怎么配置”改写成“Redis Sentinel 怎么配置”。
5. **HyDE**：先让模型生成一个假想答案或摘要，再用这个文本做向量召回，适合语义问题，但要防止幻觉污染。
6. **结构化抽取**：抽出 `product`、`version`、`error_code`、`tenant_id`、`time_range` 等字段，用于过滤和路由。

改写必须可观测：要记录原始 query、改写后的 query、命中的文档、最终答案和用户反馈。否则召回效果变差时很难定位是改写、索引还是 rerank 的问题。

## 4. Prompt 怎么构建

最终给大模型的输入一般由五部分组成：

```text
系统约束：角色、安全边界、回答语言、禁止编造
任务说明：根据给定资料回答，资料不足时说明不知道
检索上下文：按相关性排序的 chunk，带 source_id、标题、时间、权限信息
用户问题：原始问题或经过澄清后的问题
输出格式：步骤、表格、引用、代码块、JSON schema 等
```

上下文片段建议结构化：

```text
[source: doc_12#chunk_3]
title: Redis 内存淘汰策略
content: ...

[source: doc_20#chunk_1]
title: Redis Cluster 槽迁移
content: ...
```

这样做有几个好处：

1. 模型可以引用来源，便于用户验证。
2. 系统可以检查答案是否使用了无权限或低相关片段。
3. 后续可以根据 source_id 统计哪些文档真正支撑答案。

## 5. Token 和安全控制

Prompt 不是把 topK 原样塞进去。真实系统要做预算和安全处理：

1. **按 token 预算裁剪**：保留问题、系统约束和高分片段，低分片段丢弃或压缩。
2. **去重和合并**：同一文档相邻 chunk 可以合并，重复片段只保留一份。
3. **父子块策略**：小块用于召回，大块用于生成，避免只给模型碎片化句子。
4. **Prompt Injection 防护**：检索文档只是资料，不允许覆盖系统指令；对“忽略上文”等内容做隔离提示。
5. **无证据拒答**：召回分数过低或 rerank 无命中时，应该拒答、提示补充信息或转人工，而不是让模型自由发挥。

## 6. 优化方向

RAG 下一步优化可以从四层回答：

1. **数据层**：优化文档清洗、分块、版本管理、权限字段、增量索引和过期文档清理。
2. **召回层**：引入 BM25 + 向量混合召回、查询路由、RRF、reranker、热门 query 缓存。
3. **生成层**：优化 Prompt 模板、引用格式、低置信度拒答、答案后校验和流式输出。
4. **评测层**：构造离线评测集，持续跟踪 Recall@K、NDCG、答案正确率、引用准确率、幻觉率、P99 和 token 成本。

## 7. 易错点

1. 只用向量召回，会漏掉错误码、编号、API 名称等精确匹配问题。
2. BM25 分数依赖分词器和字段设计，中文、代码、日志场景要定制 analyzer。
3. 查询改写不能只看生成效果，要看召回指标是否提升。
4. rerank 之后 Recall@K 可能不变，但正确证据排名提升，最终答案会明显更稳。
5. Prompt 中必须区分“系统指令”和“检索资料”，否则文档里的恶意指令可能影响模型行为。

## 8. 面试回答模板

知识库问答我会拆成离线建库和在线问答。离线侧做文档解析、清洗、分块、embedding、BM25 索引和元数据入库；在线侧先做意图识别和查询改写，再走向量召回、BM25 召回和规则召回，合并去重后用 reranker 重排，最后把高相关片段按 source_id 拼进 Prompt 交给大模型生成。

BM25 基于倒排索引，核心考虑词频、IDF 和文档长度归一化，适合精确词和编号类问题；向量召回适合语义相似，两者混合效果更稳。召回评估看 Recall@K、MRR/NDCG、引用准确率和无答案拒答率。Prompt 构建时要有系统约束、检索上下文、用户问题和输出格式，并控制 token、权限和 Prompt Injection 风险。
