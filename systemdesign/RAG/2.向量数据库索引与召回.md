# 2.向量数据库索引与召回

在 RAG 系统中，向量数据库负责存储文档片段的 embedding，并在查询时快速找到语义相近的片段。面试里常问两个问题：索引怎么设计，以及召回时召回的是文档 ID 还是文档内容。

## 1. 文档入库模型

不要直接把整篇文档作为一个向量写入向量库。更常见的做法是按 chunk 写入：

```text
document
  -> chunk_1
  -> chunk_2
  -> chunk_3
```

每条 chunk 记录通常包含：

| 字段 | 作用 |
| --- | --- |
| `chunk_id` | 片段唯一 ID |
| `doc_id` | 所属文档 ID |
| `embedding` | chunk 的向量 |
| `content` | chunk 文本，或文本存储位置 |
| `metadata` | 标题、页码、章节、URL、权限、时间、标签 |
| `version` | 文档版本，用于更新和删除 |

## 2. 分块策略

分块质量会直接影响召回质量。

常见策略：

1. **固定长度分块**：按 token 或字符数切分，实现简单。
2. **滑动窗口重叠**：相邻 chunk 保留一部分重叠，避免上下文被切断。
3. **按结构分块**：按标题、段落、Markdown heading、PDF 页、代码函数切分。
4. **父子块策略**：小块用于召回，大块或原段落用于拼接上下文。

典型参数：

```text
chunk_size: 300 ~ 1000 tokens
overlap: 50 ~ 150 tokens
topK: 5 ~ 20
```

具体取值要根据文档类型、embedding 模型、LLM 上下文长度和召回效果调参。

## 3. 向量索引怎么设计？

向量索引一般要在召回速度、召回率、内存占用之间取舍。

| 索引 | 特点 | 适用场景 |
| --- | --- | --- |
| Flat | 暴力精确搜索，召回率最高 | 数据量小、离线评估 |
| HNSW | 图索引，查询快，召回率高，占内存较多 | 在线 RAG 常用 |
| IVF | 先聚类再查部分簇，速度快 | 大规模向量检索 |
| PQ/SQ | 向量量化压缩，省内存但有精度损失 | 超大规模、成本敏感 |

业务上还需要设计标量索引或过滤字段：

1. `tenant_id`：多租户隔离。
2. `user_id` / `acl`：权限过滤。
3. `doc_type`：文档类型过滤。
4. `update_time`：按时间过滤或排序。
5. `source`：按知识来源过滤。

RAG 召回不能只看向量相似度，还要先保证权限和业务过滤正确。

### 3.1 自研向量检索引擎为什么需要 WAL / KV 内存索引 / HNSW / SIMD

如果面试里追问“为什么项目里要做 WAL、KV 内存索引、HNSW、SIMD”，可以按职责拆开回答，不要把它们说成同一类优化。

| 模块 | 解决的问题 | 关键点 |
| --- | --- | --- |
| WAL | 写入后崩溃可恢复 | 先追加日志，再修改内存索引或图索引；重启时重放完整日志记录 |
| KV 内存索引 | 精确定位对象 | 维护 `vector_id -> offset/version/deleted/metadata`，用于 upsert、delete、精确查找和恢复 |
| HNSW | 近似最近邻召回 | 用多层小世界图减少高维向量全量扫描成本，在召回率和延迟之间调参 |
| SIMD | 加速热点计算 | 批量计算 L2/IP/cosine 距离、归一化、CRC 校验等数据并行任务 |

它们分别覆盖可靠性、精确索引、语义召回和性能优化：

1. **WAL 是可靠性基础**：向量、metadata 和删除标记写入内存前，先写追加日志；进程崩溃后可以根据日志恢复到最后一条完整可校验记录。
2. **KV 内存索引补 HNSW 的短板**：HNSW 适合 topK 近似召回，不适合精确判断某个 ID 是否存在、当前版本是多少、是否被删除。
3. **HNSW 避免全量向量比较**：百万级向量如果每次都 Flat 扫描，延迟和 CPU 成本会很高；HNSW 通过图上贪心搜索把访问点数降下来。
4. **SIMD 优化计算密集路径**：距离计算本质是大量同构浮点运算，适合用 AVX/SSE/NEON 或编译器自动向量化提升吞吐。

真实项目里要强调取舍：自研引擎可以更贴合 Agent Memory、小规模本地部署或特殊数据格式，但不能轻易声称已经达到 FAISS/Milvus 的成熟度。可靠回答应该给出数据规模、召回率、P95/P99 延迟、索引构建时间、恢复测试和与基线的对比。

## 4. 召回的是文档 ID 还是内容？

工程上通常召回的是一组结构化结果，而不是单纯只有 ID 或只有内容。

```text
[
  {
    chunk_id,
    doc_id,
    score,
    content,
    metadata
  }
]
```

两种常见实现：

1. **向量库直接存 content**：召回时直接返回 chunk 文本和元数据，链路简单，适合中小规模 RAG。
2. **向量库只存 ID 和元数据**：召回时先拿到 chunk_id/doc_id，再去 MySQL、ES、对象存储取原文，适合大文档、权限复杂或多版本管理场景。

面试回答可以说：召回阶段至少要返回 `chunk_id/doc_id + score + metadata`。最终给 LLM 的是文本内容，但系统内部通常也保留 ID，便于去重、权限校验、引用溯源和点击反馈。

### 4.1 向量检索引擎和模型推理的边界

向量检索引擎在 RAG 中主要负责“找证据”，不等于大模型推理服务。

一条典型链路可以拆成：

```text
用户问题
  -> query embedding
  -> 向量检索 / BM25 / metadata filter
  -> rerank
  -> prompt 组装
  -> LLM 推理生成答案
```

其中向量库负责保存 embedding、metadata、索引和召回结果；embedding 模型负责把文本转成向量；reranker 可能是 Cross-Encoder 或小模型；vLLM/SGLang/TensorRT-LLM 这类框架负责 LLM 在线生成。自研向量检索引擎如果只做 ANN 召回和 KV 存储，就应该明确说“没有做大模型推理，只服务于 RAG 的检索阶段”。如果项目还接入了 embedding、rerank 或 generation，也要分别说明这些模型由哪个服务承载、延迟预算和 GPU/CPU 资源怎么隔离。

## 5. 混合召回和重排

只用向量召回容易漏掉关键词、编号、专有名词。真实场景常用混合召回：

```text
向量召回 topK1
关键词/BM25 召回 topK2
规则召回 topK3
    -> merge 去重
    -> rerank
    -> 取 topN 拼接 prompt
```

重排可以用 cross-encoder reranker、LLM rerank 或业务规则。重排的目标是把真正能回答问题的 chunk 排到前面，而不是只看 embedding 距离。

## 6. 不同体量知识库如何选型

RAG 方案不能只看“是否用了向量数据库”，更重要的是知识库规模、更新频率、权限复杂度和查询类型。

| 规模 | 常见方案 | 适用场景 |
| --- | --- | --- |
| 小型知识库 | 直接放入上下文、关键词搜索、Flat 向量检索 | 几十篇文档、FAQ、个人笔记、低并发 Demo |
| 中型知识库 | chunk + HNSW + metadata 过滤 + BM25 混合召回 | 团队文档、客服知识库、项目代码说明 |
| 大型知识库 | 分库分片、IVF/HNSW、混合召回、rerank、权限过滤、缓存 | 企业级文档库、多租户、多业务线 |
| 超大型知识库 | 查询路由、多阶段召回、向量量化、冷热分层、增量索引、离线评测闭环 | 海量文档、频繁更新、严格权限和成本约束 |

小型知识库不一定需要复杂架构。几十篇文档可以先用关键词搜索或 Flat 向量检索，甚至把精选内容直接放进 prompt。这样链路短、可解释性强，调试成本低。

中型知识库通常需要标准 RAG 链路：

```text
文档解析 -> chunk -> embedding -> 向量库
查询 -> query rewrite -> 向量召回 + BM25 -> merge -> rerank -> prompt
```

大型知识库要重点解决四类问题：

1. **召回效率**：使用 HNSW、IVF、PQ/SQ、分片或租户分区降低查询成本。
2. **权限正确性**：召回前或召回中必须做 ACL 过滤，不能把无权限片段交给 LLM。
3. **更新一致性**：文档更新后要有增量索引、版本号、删除标记和异步重建机制。
4. **结果质量**：只靠 topK 不稳定，需要 query rewrite、混合召回、重排和引用校验。

超大型或多业务知识库还会引入查询路由。先判断用户问题属于哪类知识源，再路由到产品文档、工单、代码库、数据字典或历史对话，避免在全库里盲目召回。

选型时可以按这个顺序回答：

1. 先看数据规模和更新频率。
2. 再看查询类型是语义问答、精确编号、代码符号还是多跳推理。
3. 再看权限和多租户是否复杂。
4. 最后根据延迟、成本和召回率选择索引、召回链路和缓存策略。

### 6.1 如何说明向量数据库规模和生产级程度

面试中被问到“向量数据库有多大”“是生产级还是单机原型”时，不要只回答“几十万条”或“很大”，更应该把规模拆成可验证的工程指标：

1. **数据规模**：原始文档数、切分后的 chunk 数、向量条数、向量维度、embedding 模型版本。
2. **内存规模**：向量本体约为 `向量条数 * 维度 * 每维字节数`，还要加上 HNSW 图边、IVF 聚类、PQ 码本、metadata 和倒排索引额外开销。
3. **查询规模**：平均 QPS、峰值 QPS、P95/P99 延迟、topK、召回率、rerank 是否同步执行。
4. **更新规模**：增量写入频率、删除和重建策略、索引版本切换方式、冷启动和回滚成本。
5. **可靠性**：是否有分片、副本、备份恢复、监控告警、租户隔离、权限过滤、灰度发布和压测结果。

单机原型通常只有本地索引、离线导入、少量数据、人工重建和有限监控；生产级系统需要支持稳定写入、在线查询、故障恢复、权限过滤、版本治理和效果评测。真实回答可以这样组织：“当前是单机原型，约 20 万个 chunk，768 维 float32 向量，向量本体约 600MB，HNSW 索引后约 1GB；主要验证召回效果和问答链路，还没有做多副本、自动扩缩容和线上 SLO，所以不能称为生产级。”

### 6.2 如何和 FAISS / Milvus 对比

被问“和 FAISS、Milvus 差距多少”时，最稳的回答是先说明是否做过同口径 benchmark。没有测过就不要给具体倍数，可以给出评估方法和工程差距。

对比时至少固定这些条件：

1. **数据集**：向量条数、维度、分布、是否归一化、是否包含删除和更新。
2. **距离函数**：L2、Inner Product、Cosine 不能混用口径。
3. **召回质量**：用 Flat 精确搜索作基线，计算 Recall@K、NDCG 或 MRR。
4. **性能指标**：QPS、P50/P95/P99、索引构建时间、内存占用、磁盘占用。
5. **更新能力**：在线插入、删除标记、批量重建、版本切换和回滚成本。
6. **可靠性和运维**：WAL 恢复、分片副本、监控告警、权限过滤、备份恢复。

一般来说：

1. **FAISS** 强在向量检索算法、SIMD/GPU 优化、IVF/PQ/HNSW 等索引实现和离线评测，是高性能向量算法库。
2. **Milvus** 强在服务化和分布式能力，包括 collection、segment、分片、副本、对象存储、查询节点、索引节点、监控和运维生态。
3. **自研单机引擎** 可以在本地 Agent Memory、轻量部署、特殊 WAL 格式、内存索引和业务 metadata 上更灵活，但通常在 GPU、分布式、索引生态、稳定性和运维工具上差距明显。

面试表达可以是：“我不会直接说比 FAISS/Milvus 快。我的项目主要验证本地 Agent Memory 场景下的持久化和召回链路，基线应该和 Flat、FAISS HNSW/IVF 以及 Milvus 单机部署在同一数据集上比 Recall@K、P99 和内存。如果没有完整测过，只能说当前是功能和工程验证，距离成熟生产级向量数据库还差分布式、副本、压测、监控和长期稳定性。”

## 7. RAG 召回质量如何评测

RAG 设计是否合理要用评测集验证。常见指标：

1. **Recall@K**：正确证据是否出现在前 K 个召回结果中。
2. **MRR / NDCG**：正确证据是否排在更靠前的位置。
3. **答案正确率**：最终回答是否解决用户问题。
4. **引用准确率**：答案引用的片段是否真实支撑结论。
5. **幻觉率**：没有证据时是否拒答或说明不确定。
6. **权限违规率**：是否召回或输出无权限内容。
7. **成本和延迟**：召回、重排、生成的平均耗时和 token 成本。

测试集要覆盖语义类问题、关键词/编号类问题、多文档综合问题、无答案问题、权限隔离问题和新旧版本冲突问题。只用人工挑选的简单 FAQ，很难暴露真实线上 RAG 的问题。

## 8. 向量数据库稳定性设计

面试里问“项目中的向量数据库如何保持稳定性”，不能只回答“加副本”。向量库稳定性要同时覆盖可用性、数据一致性、召回质量和成本延迟。

### 8.1 写入链路稳定性

文档入库通常是异步链路：

```text
文档变更 -> 消息队列 -> 解析/切块 -> embedding -> 写向量库 -> 写索引版本
```

关键设计：

1. **幂等写入**：用 `doc_id + chunk_id + version` 做唯一键，重复消费不会写出重复 chunk。
2. **版本化更新**：新版本写入完成后再把旧版本标记删除，避免查询读到半更新状态。
3. **失败重试和死信队列**：解析失败、embedding 超时、向量库写失败要可重试，超过次数进入死信队列人工处理。
4. **限流和背压**：大批量重建索引时限制并发，避免压垮 embedding 服务和向量库。
5. **数据校验**：检查向量维度、模型版本、metadata 字段和权限字段是否完整。

### 8.2 查询链路稳定性

在线查询要有超时、降级和兜底：

1. **超时控制**：向量召回、BM25、rerank 分别设置超时预算，避免单个组件拖垮整体响应。
2. **多副本查询**：核心索引按分片和副本部署，副本异常时路由到健康副本。
3. **降级策略**：向量库不可用时可以退化为关键词召回、缓存答案、热门 FAQ 或明确提示稍后重试。
4. **缓存**：对热门 query、标准问题、召回结果和 rerank 结果做短期缓存。
5. **熔断隔离**：单租户或单知识库异常流量不能拖垮全局向量服务。

### 8.3 索引构建和切换

大规模索引不建议边查边原地重建。更稳妥的做法是：

```text
旧索引在线服务
    -> 后台构建新索引
    -> 离线评测召回质量
    -> 小流量灰度
    -> 原子切换别名/版本
    -> 保留旧索引用于回滚
```

这样可以避免索引重建过程中查询结果抖动，也便于发现 embedding 模型升级、chunk 策略变化或量化参数变化带来的召回质量下降。

### 8.4 监控指标

稳定性监控至少包括：

1. **可用性**：查询成功率、错误率、超时率。
2. **性能**：P50/P95/P99 延迟、QPS、队列积压、CPU/内存/磁盘。
3. **数据质量**：入库成功率、失败文档数、向量维度异常、孤儿 chunk。
4. **召回质量**：Recall@K、NDCG、无结果率、rerank 后命中率。
5. **权限安全**：越权召回次数、无权限 chunk 过滤数。
6. **版本一致性**：查询命中的索引版本、文档版本冲突、删除延迟。

### 8.5 面试回答模板

向量数据库稳定性我会分写入、查询、索引和监控四层设计。写入链路用消息队列解耦，`doc_id + chunk_id + version` 保证幂等，失败进入重试和死信队列；文档更新用版本号和删除标记，避免半更新。查询链路要有分片副本、健康检查、超时、缓存、熔断和降级，向量库异常时可以退化到 BM25 或热门 FAQ。索引构建采用后台新建、离线评测、灰度和原子切换，保留旧索引回滚。监控上看成功率、P99、队列积压、入库失败、Recall@K、无结果率和权限违规率。

## 9. 易错点

1. **只存整篇文档向量**：召回粒度太粗，容易带入大量无关内容。
2. **chunk 太小**：语义不完整，召回后 LLM 缺上下文。
3. **chunk 太大**：相似度被稀释，prompt 成本高。
4. **不做权限过滤**：RAG 很容易泄漏用户无权查看的文档。
5. **只返回内容不返回 ID**：后续无法引用、去重、反馈学习和排查问题。
6. **只用向量召回**：对精确关键词、编号、错误码、函数名不稳定。
7. **小题大做**：小型知识库直接上复杂分布式向量库，开发和运维成本可能超过收益。
8. **忽略评测闭环**：没有 Recall@K、引用准确率和无答案测试集，调参很容易凭感觉。

## 10. 面试回答模板

文档入向量库时，我不会直接按整篇文档建一个向量，而是先清洗解析，再按段落或 token 数切成 chunk，每个 chunk 生成 embedding。向量库里保存 `chunk_id`、`doc_id`、embedding、必要文本和元数据，比如标题、页码、权限、来源、版本号。索引可以根据规模选择 HNSW、IVF、PQ 等，在线 RAG 常见是 HNSW，再配合租户、权限、文档类型等标量过滤。

不同体量的知识库选型不同。小型知识库可以先用关键词、Flat 向量检索甚至精选内容直接入上下文；中型知识库用 chunk、HNSW、metadata 过滤、BM25 混合召回和 rerank；大型知识库要考虑分片、多租户权限、增量索引、缓存、查询路由、量化压缩和冷热分层。选型时先看规模和更新频率，再看查询类型、权限复杂度、延迟和成本。

召回时系统内部通常召回的是结构化结果，包括 chunk ID、文档 ID、相似度分数、元数据和文本内容。最终喂给大模型的是内容，但保留 ID 很重要，因为要做去重、权限校验、引用溯源和问题排查。真实项目里还会做混合召回和 rerank，避免只靠向量相似度导致关键词类问题召回不准。RAG 质量要用 Recall@K、NDCG、答案正确率、引用准确率、幻觉率、权限违规率、成本和延迟来评测。
