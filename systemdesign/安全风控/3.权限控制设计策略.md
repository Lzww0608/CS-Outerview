# 3. 权限控制设计策略

权限控制讨论的是“某个主体能不能对某个资源执行某个动作”。面试里不要把它和登录态混在一起：

1. **认证 Authentication**：证明你是谁，例如账号密码、Session、JWT、OIDC、mTLS。
2. **授权 Authorization**：判断你能做什么，例如能否查看订单、审批退款、删除文件。
3. **审计 Audit**：记录谁在什么时候对什么资源做了什么，结果是什么。

一个完整权限判断可以抽象为：

```text
subject + action + resource + context -> allow / deny

subject: 用户、员工、服务账号、设备、第三方应用
action: read、write、delete、approve、export
resource: 订单、酒店、航班、文件、租户、接口、字段
context: 租户、部门、时间、IP、设备、风险等级、数据状态
```

## 1. 设计目标

权限系统通常要同时满足：

1. **最小权限原则**：默认不给权限，只授予完成工作所需的最小集合。
2. **默认拒绝**：没有明确允许就拒绝，异常、超时、策略缺失不能放行。
3. **职责分离**：申请、审批、执行、审计尽量分开，避免一个人闭环高危操作。
4. **可解释**：拒绝时能说明缺少哪个角色、策略或资源条件。
5. **可审计**：权限变更和敏感操作要留痕，支持追责和合规。
6. **可扩展**：从接口权限扩展到数据权限、字段权限、跨租户权限。
7. **低延迟**：权限校验在主链路上，不能每次都做复杂远程查询。

## 2. 常见权限模型对比

| 模型 | 核心思想 | 优点 | 缺点 | 真实使用场景 |
| --- | --- | --- | --- | --- |
| ACL | 资源上挂主体权限列表 | 直观，适合资源级共享 | 权限分散，批量管理困难 | 文件系统、对象存储、Kafka Topic ACL、早期协作系统 |
| RBAC | 用户属于角色，角色拥有权限 | 简单稳定，适合企业后台 | 难表达资源属性和复杂条件，角色膨胀 | OA、ERP、CRM、管理后台、Kubernetes RBAC |
| ABAC | 基于主体、资源、环境属性决策 | 表达能力强，适合动态条件 | 策略复杂，调试难，依赖属性治理 | 云 IAM、金融风控、数据权限、零信任 |
| ReBAC | 基于主体和资源之间的关系图 | 适合协作、组织、社交关系 | 图查询和一致性复杂 | Google Zanzibar、SpiceDB、OpenFGA、文档共享 |
| PBAC | 用策略语言统一描述允许/拒绝 | 策略集中、可审计、可测试 | 需要策略引擎和治理流程 | OPA/Rego、AWS Cedar、企业级 IAM |
| Capability | 持有能力令牌即可访问资源 | 分布式友好，校验快 | 泄露风险高，撤销复杂 | 预签名 URL、临时访问令牌、对象存储下载 |
| OAuth Scope | 第三方应用获得有限授权范围 | 适合开放平台和委托授权 | Scope 粗粒度，不能替代业务数据权限 | 微信/Google 登录、开放 API、第三方应用授权 |
| MAC/DAC | 系统级强制/自主访问控制 | 安全边界强，适合 OS/容器 | 对业务表达不友好 | SELinux、AppArmor、Linux 文件权限 |

实际系统很少只用一种模型。常见组合是：

```text
登录态认证
-> 网关做粗粒度接口权限
-> 服务内做 RBAC/ABAC/ReBAC
-> 数据库或查询层做行列级数据权限
-> 审计系统记录决策和操作
```

## 3. ACL：访问控制列表

ACL 把权限挂在资源上：

```text
file_123:
  user_a: read
  user_b: read, write
  group_admin: read, write, delete
```

适合场景：

1. 文件、文档、对象、Topic 这类资源本身就是共享单元。
2. 每个资源的授权对象不多。
3. 用户经常对单个资源做分享、取消分享。

优点：

1. 语义直观：看资源就能知道谁能访问。
2. 资源级权限表达自然。
3. 适合“把这个文件分享给某个人”的产品交互。

缺点：

1. 权限分散在资源上，批量授权和回收困难。
2. 用户离职或部门调整时，需要扫描大量资源 ACL。
3. 资源数量很大时，ACL 存储和查询成本高。

工程优化：

1. 支持用户 ACL、组 ACL、继承 ACL。
2. 对热点资源权限做本地缓存。
3. 权限变更通过版本号或消息失效缓存。
4. 高风险资源避免无限制公开分享。

## 4. RBAC：基于角色的访问控制

RBAC 是后台系统最常见的模型：

```text
用户 -> 角色 -> 权限
```

典型表结构：

```text
user(id, name, status)
role(id, name, tenant_id)
permission(id, code, action, resource_type)
user_role(user_id, role_id)
role_permission(role_id, permission_id)
```

权限码示例：

```text
order:read
order:refund
hotel:edit
report:export
admin:user:create
```

优点：

1. 简单清晰，管理后台容易实现。
2. 角色对应岗位，符合企业组织管理习惯。
3. 权限变更只需要改角色，不必逐个改用户。
4. 适合接口级、菜单级、按钮级权限。

缺点：

1. 对资源实例表达不足，例如“只能看自己部门的订单”。
2. 容易角色膨胀，例如“华东酒店运营主管临时导出角色”。
3. 角色命名和权限边界不清晰时，后期治理困难。
4. 不适合复杂条件，例如时间、地点、风险等级、数据状态。

真实使用：

1. 企业后台、OA、ERP、CRM 基本都会用 RBAC。
2. Kubernetes 使用 RBAC 管理用户、ServiceAccount 对 API Resource 的权限。
3. Spring Security、Shiro、Django Admin 这类框架常从 RBAC 起步。

RBAC 常见扩展：

1. **角色层级**：管理员继承普通成员权限。
2. **租户隔离**：角色必须带 `tenant_id`。
3. **数据范围**：角色不仅有动作权限，还绑定可访问组织范围。
4. **临时授权**：角色有有效期，到期自动回收。

## 5. ABAC：基于属性的访问控制

ABAC 根据属性做决策：

```text
subject.department == resource.department
and action == "read"
and context.risk_level < 3
and context.ip in company_network
```

可用属性：

1. 主体属性：用户 ID、部门、岗位、职级、租户、认证强度。
2. 资源属性：归属人、部门、数据等级、业务状态、所在区域。
3. 动作属性：读、写、审批、导出、删除、分享。
4. 环境属性：时间、IP、设备、地理位置、风险分、是否 VPN。

优点：

1. 表达能力强，可以覆盖复杂业务条件。
2. 减少角色膨胀。
3. 适合多租户、数据权限、零信任、风控联动。

缺点：

1. 策略难读、难测、难排查。
2. 属性来源复杂，必须保证属性准确、及时、可信。
3. 策略过多后可能冲突，需要明确优先级。
4. 每次决策可能依赖多个数据源，延迟和可用性要治理。

真实使用：

1. 云厂商 IAM 策略经常混合用户、资源、标签、请求上下文。
2. 数据平台常用 ABAC 做行级、列级、标签级权限。
3. 零信任系统会结合设备状态、地理位置、风险评分做动态授权。

## 6. ReBAC：基于关系的访问控制

ReBAC 把权限看成关系图查询：

```text
user:alice --member_of--> group:hotel_ops
group:hotel_ops --editor_of--> document:pricing_policy
document:pricing_policy --parent--> folder:hotel_docs
```

判断权限时查询：

```text
alice 是否通过某条关系路径拥有 document:pricing_policy 的 read/edit 权限？
```

适合场景：

1. 文档协作：文件、文件夹、团队、组织之间有继承关系。
2. 社交网络：好友、关注、群组、黑名单关系影响可见性。
3. 多层组织：集团、BU、部门、项目、成员关系复杂。
4. SaaS 多租户协作：用户、团队、项目、资源之间关系动态变化。

优点：

1. 很适合表达“用户和资源之间有什么关系”。
2. 支持权限继承，例如文件继承文件夹权限。
3. 比纯 RBAC 更适合协作产品。

缺点：

1. 图关系查询复杂，要控制递归深度和循环。
2. 关系变更后的缓存失效复杂。
3. 强一致权限判断和低延迟之间需要取舍。

真实使用：

1. Google Zanzibar 是业界 ReBAC 经典系统，支撑 Google 内部大量产品权限。
2. SpiceDB/Authzed、OpenFGA、Ory Keto 是 Zanzibar 思路的开源或商业实现。
3. 文档、网盘、知识库、项目协作工具常采用 ReBAC 或 ACL + ReBAC 混合模型。

## 7. PBAC 和策略引擎

PBAC 可以理解为“把授权逻辑写成策略，并由策略引擎统一决策”。

典型架构：

```text
PAP: Policy Administration Point，策略管理
PDP: Policy Decision Point，策略决策
PEP: Policy Enforcement Point，策略执行
PIP: Policy Information Point，属性查询
```

请求流程：

```text
业务服务 / 网关作为 PEP
-> 收集 subject/action/resource/context
-> 调用 PDP
-> PDP 读取策略和属性
-> 返回 allow/deny + reason
-> PEP 执行放行或拒绝
```

常见实现：

1. OPA/Rego：云原生、Kubernetes、微服务策略常用。
2. Cedar：AWS Verified Permissions 使用的策略语言。
3. Casbin：轻量级权限库，支持 RBAC、ABAC 等模型。
4. 自研规则引擎：很多公司会用配置化 DSL 表达权限策略。

优点：

1. 策略集中管理，便于审计和发布。
2. 授权逻辑从业务代码中抽离。
3. 支持策略测试、灰度、回滚。
4. 能统一网关、服务、数据层的授权风格。

缺点：

1. 引入外部决策链路，延迟和可用性要设计。
2. 策略语言有学习成本。
3. 过度抽象会让业务研发难以理解实际放行原因。

## 8. Capability Token 和预签名 URL

Capability 模型的核心是：持有某个能力令牌，就能执行对应操作。

例子：

```text
https://oss.example.com/file/a.jpg?expires=...&signature=...
```

服务端生成一个短期、带签名、带资源和动作约束的 URL，客户端拿到后可以直接下载或上传。

适合场景：

1. 对象存储临时上传、下载。
2. 第三方回调访问某个临时资源。
3. 一次性分享链接。
4. 短期服务间委托。

优点：

1. 校验快，资源服务不需要查复杂权限。
2. 适合跨系统临时授权。
3. 可以把权限限制在单个资源、单个动作、短时间内。

缺点：

1. URL 或 token 泄露后，在过期前可被滥用。
2. 主动撤销困难，除非引入黑名单或版本号。
3. 不能用于长期、复杂、可继承的权限管理。

工程注意：

1. 有效期要短。
2. 签名要覆盖资源、动作、过期时间、内容类型等关键字段。
3. 高风险操作不要只靠预签名 URL。
4. 日志中要避免泄露完整 URL。

## 9. OAuth2 Scope 和 OIDC

OAuth2 解决的是委托授权，OIDC 在 OAuth2 之上补充身份认证。

常见场景：

```text
用户授权第三方应用读取自己的订单
第三方应用拿到 access token
第三方应用调用开放 API
API 校验 token 和 scope
```

Scope 示例：

```text
profile:read
order:read
hotel:write
payment:refund
```

优点：

1. 适合开放平台和第三方应用授权。
2. 用户可以授予有限范围，而不是交出账号密码。
3. 支持授权码模式、客户端凭证模式、设备码等标准流程。

缺点：

1. Scope 通常较粗粒度，不能表达复杂数据权限。
2. Token 泄露、过期、撤销、刷新都要认真设计。
3. OAuth2 是授权框架，不等于完整业务权限系统。

真实使用：

1. 第三方登录：通常使用 OIDC 获取用户身份。
2. 开放 API：使用 OAuth2 access token + scope 控制接口范围。
3. 企业 SSO：OIDC/SAML 和公司身份源集成。

## 10. 数据权限、字段权限和多租户

很多系统不是“能不能访问接口”这么简单，而是：

```text
你能看哪些数据？
你能看哪些字段？
你能对哪些状态的数据执行动作？
```

### 数据范围

常见数据范围：

1. 仅本人。
2. 本部门。
3. 本部门及下级部门。
4. 指定项目、门店、酒店、供应商。
5. 全租户或全平台。

落地方式：

```text
接口权限：order:read
数据范围：department_id in user's authorized_departments
资源归属：order.tenant_id == user.tenant_id
```

### 字段权限

敏感字段例如手机号、身份证、成本价、供应商结算价，可能需要脱敏或完全隐藏：

```text
普通客服：138****1234
主管：13812341234
导出接口：需要额外 export_sensitive 权限
```

### 多租户隔离

多租户系统要把 `tenant_id` 作为权限控制的基础边界：

1. 所有核心表带 `tenant_id`。
2. 查询条件强制追加 `tenant_id`。
3. 缓存 key 带 `tenant_id`。
4. 消息、日志、对象存储路径也要带租户隔离信息。
5. 管理员跨租户操作必须有独立权限和审计。

## 11. 权限校验放在哪里

### 网关层

适合：

1. 登录态校验。
2. 粗粒度接口权限。
3. API Key、OAuth Scope、JWT 校验。
4. 限流、黑白名单、审计打点。

不适合：

1. 复杂资源归属判断。
2. 行级、字段级数据权限。
3. 强依赖业务状态的判断。

### 服务层

服务层是业务权限的核心位置：

1. 方法级权限：是否能调用这个业务能力。
2. 资源级权限：是否能操作这个订单、文件、项目。
3. 状态级权限：订单已完成是否还能退款。
4. 风险联动：高风险操作是否需要二次验证。

### 数据层

数据层可以做最后防线：

1. 查询条件自动拼接租户和数据范围。
2. 数据库 Row Level Security。
3. 字段脱敏视图。
4. 数据导出审批和水印。

注意：不要只依赖前端隐藏按钮。前端权限只能改善体验，不能作为安全边界。

## 12. 缓存和一致性

权限校验高频发生，通常需要缓存：

1. 用户角色和权限集合缓存。
2. 角色权限版本号。
3. 组织树和部门范围缓存。
4. 策略引擎本地 bundle。
5. ReBAC 关系图的局部缓存。

但权限缓存有风险：

1. 管理员回收权限后，旧缓存可能继续放行。
2. JWT 里放太多权限，权限变更后 token 仍然有效。
3. 多机房缓存失效有延迟。

常见解决：

1. 权限配置带版本号：`permission_version`。
2. 高风险接口实时查权限或查版本号。
3. 普通接口允许短 TTL 缓存，例如 30 秒到 5 分钟。
4. 权限变更发布消息，主动清理本地缓存。
5. Access Token 短有效期，Refresh Token 有状态可撤销。

## 13. 业界真正怎么用

真实系统通常是组合拳：

1. **企业后台**：RBAC 为主，补充部门/租户/数据范围，前端菜单和后端接口都校验。
2. **云厂商 IAM**：PBAC/ABAC 为主，策略里包含 action、resource、condition、principal。
3. **Kubernetes**：RBAC 控制主体对 API Resource 的操作，生产环境还配合 Admission Controller、OPA/Gatekeeper、NetworkPolicy。
4. **对象存储**：Bucket Policy/IAM Policy + ACL + 预签名 URL。
5. **文档协作**：ACL/ReBAC 为主，支持用户、组、链接分享、文件夹继承。
6. **开放平台**：OAuth2/OIDC + Scope + API Key 签名 + 限流审计。
7. **微服务内部调用**：mTLS/SPIFFE 证明服务身份，网关或 sidecar 传递用户上下文，服务内做业务授权。
8. **数据平台**：RBAC + ABAC + 行列级权限 + 标签脱敏 + 导出审批。
9. **金融/支付/后台高危操作**：权限 + 审批流 + MFA + 风险评分 + 全量审计。

## 14. 一个后端权限系统落地方案

可以按三层设计：

```text
身份层：用户、部门、租户、服务账号、登录态
授权层：角色、权限码、策略、关系、数据范围
执行层：网关、中间件、服务方法、查询构造器、审计
```

### 14.1 权限码设计

权限码要稳定、可读、可分层：

```text
order:read
order:create
order:refund
order:export
hotel:price:update
admin:user:disable
```

不要直接用菜单 ID 当权限码，因为菜单会变，权限语义应该更稳定。

### 14.2 校验流程

```text
请求进入
-> 网关验证登录态/JWT/API Key
-> 网关做粗粒度接口权限和限流
-> 后端服务读取用户上下文
-> 校验 action 权限码
-> 加载资源，校验 tenant_id、owner、department、status
-> 拼接数据范围和字段脱敏规则
-> 执行业务操作
-> 记录审计日志
```

### 14.3 审计日志

高风险操作要记录：

```text
operator_id
tenant_id
action
resource_type
resource_id
decision
reason
request_id
client_ip
device_id
before / after
timestamp
```

审计日志不能只记录成功操作，拒绝和失败也要记录，方便排查越权尝试。

## 15. 易错点

1. 只做前端按钮隐藏，不做后端校验。
2. 只在网关校验接口权限，不校验资源归属。
3. 把权限全集塞进 JWT，导致 token 过大且权限变更难生效。
4. 没有租户隔离条件，出现跨租户越权。
5. 管理员权限没有审批、MFA 和审计。
6. 权限缓存没有版本号，回收后仍可短时间访问高危资源。
7. 策略规则没有测试和灰度，上线后大面积误拒或误放。
8. 错误码暴露资源存在性，例如无权限资源直接返回详细信息。
9. 数据导出、批量查询、搜索接口遗漏字段级权限和数据范围。

## 16. 面试回答模板

可以这样回答：

> 权限控制要先区分认证、授权和审计。认证解决“你是谁”，授权解决“你能不能对某个资源做某个动作”。常见模型有 ACL、RBAC、ABAC、ReBAC、PBAC、Capability Token 和 OAuth Scope。企业后台最常用 RBAC，因为角色和岗位匹配，管理成本低；但它表达不了“只能看本部门订单”这类数据范围，所以通常会补充 ABAC 条件和租户字段。文档协作、网盘这类资源共享系统更适合 ACL/ReBAC，因为权限来自用户、组、文件夹、组织之间的关系。云厂商 IAM 和零信任系统常用 PBAC/ABAC，用策略语言表达 action、resource、condition。开放平台一般用 OAuth2/OIDC 和 scope，服务间调用再配合 mTLS。
>
> 真正落地时，我会分层做：网关负责登录态、JWT/API Key、粗粒度接口权限和限流；业务服务负责资源归属、数据状态、租户隔离和数据范围；查询层负责行级过滤和字段脱敏；高危操作加审批、MFA 和审计。权限缓存要有短 TTL、版本号和变更通知，权限回收后的高风险接口要实时校验。默认策略应该是 deny by default，不能只靠前端隐藏按钮，也不能把网关鉴权当成完整业务授权。
