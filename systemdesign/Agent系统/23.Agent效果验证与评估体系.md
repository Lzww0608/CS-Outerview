# 23. Agent 效果验证与评估体系

## 1. 问题背景

Agent 系统（无论是单 Agent 还是 Multi-Agent）在落地过程中面临一个核心难题：**如何客观、可量化地验证 Agent 最终产出的效果？**

与传统软件不同，Agent 的输出具有以下特点：

- **非确定性**：同一输入多次调用，输出可能不同（LLM 的随机性）；
- **多步骤链路**：从用户输入到最终产出经历规划、检索、工具调用、反思、生成等多个环节，任一环节出错都会影响最终效果；
- **主观性**：很多场景下"好"与"不好"没有标准答案（如内容生成、对话）；
- **长尾性**：常见场景表现良好，但用户真实诉求覆盖大量长尾 case；
- **评估成本高**：人工评测准、慢、贵；自动评测快、便宜但容易失真。

没有完善的效果验证体系，Agent 上线后会陷入"用户骂、团队改、改完不知是否变好"的困境。

**假设条件：**

- Agent 已具备基本可用形态，进入效果验证与持续优化阶段；
- 应用类型涵盖：问答 / 对话 / 工具调用 / 代码生成 / 工作流执行；
- 团队具备 LLM 调用能力，可用 GPT-4 / Claude 级别模型作为评测裁判；
- 已有线上日志采集和回流能力。

## 2. 问题现象

缺乏系统化效果验证时，常出现以下现象：

1. **凭感觉发布**：开发自测几个 case 通过就上线，线上效果断崖式下跌；
2. **改动无法回归**：修改 Prompt 或换模型后，不知是否影响历史正常 case；
3. **指标盲区**：只关注响应延迟和成功率，对答案质量无感知；
4. **A/B 难比较**：两个版本各有优劣，没有量化指标支撑决策；
5. **用户反馈滞后**：等到用户投诉激增才发现效果劣化；
6. **长尾失控**：常用 case 良好，但占 20% 的长尾 case 错误率高达 50%；
7. **幻觉难发现**：Agent 输出看似合理但事实错误（捏造 API、参数、数字）；
8. **多步链路失败定位难**：最终答案不对，但不知是规划、检索、工具调用哪一步出错。

## 3. 影响范围

| 影响维度 | 具体表现 |
|---------|---------|
| 用户体验 | 错误回答导致用户失去信任，使用频次下降 |
| 业务价值 | 工具调用错误造成误操作（如下单、转账、删数据） |
| 迭代效率 | 改动无量化指标，团队反复推翻、内耗严重 |
| 风险控制 | 幻觉、违规、安全问题难以提前发现 |
| 模型成本 | 无评测体系无法判断是否值得切换更便宜模型 |
| 团队信心 | 老板和业务方对 Agent 价值产生质疑 |

## 4. 原因分析

### 4.1 Agent 输出难评估的根因

1. **没有 ground truth**：开放式问题无标准答案，难以用精确匹配判断；
2. **多维度评估**：一个回答可能"事实正确但语气差"或"流畅但有幻觉"，单一指标难覆盖；
3. **链路黑盒**：LLM 内部决策不可见，只能从输入输出推断；
4. **样本分布漂移**：线上 query 分布持续变化，离线评测集逐渐失真；
5. **裁判模型偏好**：用 LLM 评估 LLM，存在自我偏好、长度偏好、格式偏好等系统性偏差。

### 4.2 评估的核心维度

一个完整的 Agent 效果应至少从以下维度评估：

| 维度 | 含义 | 评估手段 |
|------|------|---------|
| **正确性（Correctness）** | 答案事实是否准确，工具调用是否成功 | 标准答案比对 / 执行结果校验 |
| **相关性（Relevance）** | 是否真正回答了用户问题 | LLM 评判 / 用户标注 |
| **完整性（Completeness）** | 是否涵盖问题所有方面 | LLM 评判 / Rubric 评分 |
| **忠实性（Faithfulness）** | 是否基于检索/工具结果，无幻觉 | RAGAS / 引用比对 |
| **流畅性（Fluency）** | 表达是否通顺自然 | 困惑度 / LLM 评判 |
| **安全性（Safety）** | 是否违规、越权、有害 | 安全分类器 / 规则匹配 |
| **效率（Efficiency）** | 延迟、Token 消耗、工具调用次数 | 链路埋点 |
| **稳定性（Consistency）** | 同一问题多次回答的一致性 | 多次采样比对 |

### 4.3 评估的层次

```text
┌─────────────────────────────────────────┐
│  L4: 业务指标（任务完成率、用户留存）        │
├─────────────────────────────────────────┤
│  L3: 端到端效果（最终输出质量）              │
├─────────────────────────────────────────┤
│  L2: 子模块效果（检索召回率、工具成功率）     │
├─────────────────────────────────────────┤
│  L1: 基础指标（延迟、Token、错误率）         │
└─────────────────────────────────────────┘
```

从上往下越主观、越接近业务价值；从下往上越客观、越容易自动化。完整体系需要四层都覆盖。

## 5. 解决方案

### 5.1 离线评测：建立评测集与基线

#### 5.1.1 评测集构建

- **来源多样化**：
  - 真实线上日志采样（覆盖真实分布）；
  - 人工构造的边界 case（长尾、对抗、安全）；
  - 业务方提供的典型 case；
  - 模型自动扩写的同义 case（数据增强）。
- **分层标注**：
  - 黄金集（Golden Set）：100–500 条，人工精标，含标准答案与评分细则；
  - 回归集（Regression Set）：500–5000 条，覆盖常见场景，每次发版必跑；
  - 长尾集（Long-Tail Set）：1000+ 条，专攻易错场景。
- **持续更新**：
  - 每周从线上 bad case 中补充新样本；
  - 设计评测集老化机制，淘汰已不代表线上分布的样本。

#### 5.1.2 评估方法

**1. 规则评估（确定性任务）**

- 工具调用：参数完全匹配 / 执行结果匹配；
- 代码生成：单测通过率、编译通过率、Lint 通过率；
- 结构化输出：JSON Schema 校验、字段准确率；
- 数学/逻辑题：最终答案精确匹配。

**2. 模型评估（LLM-as-a-Judge）**

```python
def llm_judge(query, answer, reference=None):
    prompt = f"""你是严格的评委，按以下标准评分（1-5）：
    1) 正确性 2) 相关性 3) 完整性 4) 忠实性
    用户问题：{query}
    参考答案：{reference or "无"}
    模型回答：{answer}
    请输出 JSON：{{"correctness":x,"relevance":x,"completeness":x,"faithfulness":x,"reason":"..."}}
    """
    return parse_json(call_llm(prompt, model="gpt-4"))
```

**3. 检索/RAG 专项评估**

- 使用 RAGAS 框架计算：Faithfulness、Answer Relevance、Context Precision、Context Recall；
- 离线计算检索 Recall@K、MRR、NDCG。

**4. 人工评估（兜底）**

- 黄金集每月人工复核一次，保持标注质量；
- 关键发版前抽样 50–100 条人工复核；
- 建立标注规范（Rubric）和多人标注一致性检查（Kappa 系数）。

### 5.2 在线评测：灰度与 A/B

- **小流量灰度**：1% → 5% → 20% → 100%，每阶段观察关键指标 24h+；
- **A/B 实验**：
  - 用户维度分桶，对比两个版本的业务指标（完成率、点赞率、复用率）；
  - 关注用户行为代理指标（Proxy Metric）：
    - 是否复制答案、是否点赞/踩、是否追问、是否放弃会话、是否回到搜索引擎。
- **影子流量（Shadow Mode）**：
  - 新版本与老版本同时跑，不影响用户，仅做后台对比。

### 5.3 链路诊断：可观测性

- **全链路 Trace**：记录每次调用的 Plan、Tool Call、Retrieval、Reflection、Final Answer；
- **关键节点指标**：
  - 规划节点：是否选对工具、是否走对分支；
  - 检索节点：召回数、相关性分数、是否命中；
  - 工具调用：成功率、延迟、参数错误率；
  - 生成节点：Token 数、引用率、幻觉率。
- **错误归因**：自动将 bad case 归因到具体节点，便于针对性优化。

### 5.4 用户反馈闭环

- **显式反馈**：点赞/踩按钮、自由文本反馈、星级评分；
- **隐式反馈**：是否复制、是否追问、是否完成下游动作（如下单）；
- **反馈回流**：
  - 差评样本自动入 bad case 库；
  - 高频差评 query 进入优化优先级队列；
  - 用反馈数据微调奖励模型（RLHF / DPO）。

## 6. 可选方案对比

| 方案 | 优点 | 缺点 | 适用场景 |
|------|------|------|---------|
| 纯人工评测 | 准确、可解释 | 慢、贵、难规模化 | 黄金集、关键发版 |
| 规则评估 | 快、客观、低成本 | 仅适用确定性任务 | 工具调用、代码、JSON 输出 |
| LLM-as-a-Judge | 可扩展、覆盖主观维度 | 存在裁判偏差，成本不低 | 开放问答、内容生成 |
| RAGAS / DeepEval / TruLens 框架 | 开箱即用、维度全 | 需要适配业务场景 | RAG / Agent 通用评估 |
| 用户行为代理指标 | 真实业务价值 | 噪音大、归因复杂 | 线上 A/B、长期观察 |
| RLHF / DPO 偏好评估 | 与模型训练闭环 | 需大量标注、流程复杂 | 长期模型迭代 |
| 影子流量对比 | 不影响用户、对比客观 | 实施成本高 | 关键版本上线前 |

## 7. 推荐方案

建立 **四层评估体系 + 评测集 + 在线反馈** 的闭环：

### 7.1 评估体系（四层）

1. **L1 基础指标**（自动埋点）：延迟、Token、错误率、超时率；
2. **L2 子模块指标**（自动）：检索 Recall@K、工具成功率、规划准确率；
3. **L3 端到端效果**（半自动）：
   - 确定性任务：规则评估 100%；
   - 开放任务：LLM-as-a-Judge（覆盖正确性、相关性、忠实性、安全性）+ 人工抽检 5%；
4. **L4 业务指标**（线上）：任务完成率、用户满意度、复用率、追问率。

### 7.2 评测集

- 黄金集 200 条（人工精标，按月维护）；
- 回归集 2000 条（每次 PR 必跑）；
- 长尾集 1000 条（每月扩充）；
- 安全集 200 条（攻击/越权/有害测试）。

### 7.3 发布流程

```text
本地开发 → 单测/规则 → 回归集评测 → 黄金集评测 + 人工抽检
         → 影子流量对比 → 1% 灰度 + A/B → 5% → 20% → 全量
         → 持续监控 + 用户反馈 → bad case 回流
```

## 8. 实施步骤

### 阶段一：建立基础观测（第 1–2 周）

1. 全链路 Trace 接入（每个节点输入输出落库）；
2. 基础指标埋点（延迟、Token、错误率）；
3. 搭建简易评测脚本，能跑回归集并输出报告。

### 阶段二：构建评测集（第 3–4 周）

1. 从线上日志采样 500 条，人工标注形成黄金集；
2. 业务方与开发共建回归集（2000 条）；
3. 制定标注规范（Rubric）和评分细则。

### 阶段三：自动化评测（第 5–8 周）

1. 接入 RAGAS / DeepEval 框架，搭建自动评测流水线；
2. 实现 LLM-as-a-Judge 评测器（含偏差校准）；
3. CI 集成：每次 PR 自动跑回归集，给出评分对比；
4. 评测结果看板（Grafana / 自建）。

### 阶段四：在线反馈闭环（第 9–12 周）

1. 上线点赞/踩反馈按钮和行为埋点；
2. bad case 自动回流入评测集；
3. A/B 实验平台接入，支持版本对比；
4. 每周输出效果周报，持续驱动优化。

### 阶段五：长期迭代（持续）

1. 评测集老化更新机制；
2. 用反馈数据训练奖励模型 / 微调；
3. 评测框架版本化，与模型/Prompt 一起灰度。

## 9. 风险与注意事项

| 风险 | 影响 | 缓解措施 |
|------|------|---------|
| LLM 裁判存在自我偏好（偏向同模型输出） | 评分失真，错误决策 | 用多个不同模型交叉评判；定期与人工标注校准 |
| 评测集与线上分布漂移 | 离线指标好但线上效果差 | 每周从线上 bad case 补充样本，监控分布差异 |
| 评估成本失控（每条调用 LLM 裁判） | 评测费用高 | 分层评估：先规则筛，再 LLM 裁判，最后人工抽检 |
| 单一指标优化导致整体劣化 | 出现幸存者偏差 | 多指标加权评估，关注最差指标而非平均 |
| 用户反馈样本偏差（只有不满意的用户反馈） | 数据有偏 | 隐式反馈 + 主动抽样调研 |
| A/B 流量污染 | 实验结论不准 | 严格分桶、加锁定窗口、最小样本量计算 |
| 评测集泄露到训练集 | 评测失效 | 评测集严格隔离，定期更新避免过拟合 |
| 灰度阶段问题放大 | 部分用户体验恶化 | 设置自动回滚阈值（关键指标下跌 10% 自动回滚） |
| 安全/合规问题未在评测覆盖 | 上线后出事故 | 独立安全评测集，发版强制 100% 通过 |

## 10. 验证方式

1. **评测体系自身的验证**
   - LLM 裁判与人工标注的一致性（Kappa > 0.6 视为可用）；
   - 多次评测同一样本的稳定性（标准差 < 0.3）；
   - 评测结论与线上 A/B 结果一致性（相关系数 > 0.7）。
2. **发版前验证**
   - 回归集得分不低于上一版本基线；
   - 安全集 100% 通过；
   - 关键场景人工抽检通过率 > 95%。
3. **灰度验证**
   - 1% 灰度 24h：核心指标无显著下跌；
   - 5% 灰度 48h：用户反馈差评率 ≤ 基线；
   - 20% 灰度 7d：业务指标（完成率、复用率）持平或上升。
4. **长期监控**
   - 周报：bad case 数量、用户差评率、Token 成本、延迟分布；
   - 月报：评测集刷新、长尾问题分析、模型/Prompt 优化清单。
5. **故障演练**
   - 故意注入坏 case，验证监控告警是否触发；
   - 模拟模型降级（如切换到弱模型），验证自动回滚机制。

## 11. 总结

Agent 效果验证的核心是 **建立"指标-评测集-反馈"的闭环**，而非依赖某个单一指标或单次评测。关键原则：

1. **分层评估**：基础指标 → 子模块 → 端到端 → 业务指标，四层缺一不可；
2. **离线 + 在线结合**：离线评测保下限，在线 A/B 看真实价值；
3. **规则 + LLM + 人工三结合**：确定性用规则，开放性用 LLM 裁判，关键节点用人工；
4. **评测集动态维护**：从线上 bad case 持续回流，避免分布漂移；
5. **可观测性是前提**：没有全链路 Trace，所有评估都是黑盒猜测；
6. **关注最差而非平均**：长尾 case 决定用户口碑；
7. **评估与优化一体化**：评测结论必须能转化为可执行的优化动作。

一句话：**Agent 的效果验证不是发版前的一次性动作，而是贯穿设计-开发-上线-运营的持续工程**。没有评估体系的 Agent，就像没有仪表盘的飞机，迟早会失控。

- 反馈闭环测试：模拟用户差评，验证是否进入 bad case 库；
- 灰度回滚测试：模拟指标下跌，验证自动回滚生效。
