# 2. Agent 状态机、HIL 与 Jenkins 任务恢复

面试里问 Agent 优化项目的状态机、Human-in-the-loop、幂等哈希、Jenkins 断点续跑和上下文压缩，本质是在考：你有没有把 Agent 当成一个可靠后端系统，而不是一次模型调用。

## 1. 整体状态机

一个触发 Jenkins 的 Agent 任务可以设计成显式状态机：

```text
CREATED
-> CONFIG_NORMALIZED
-> HASHED
-> PLANNED
-> WAITING_HIL
-> APPROVED
-> JENKINS_QUEUED
-> JENKINS_RUNNING
-> RESULT_COLLECTING
-> VERIFYING
-> SUCCEEDED
```

失败和中断分支：

```text
FAILED_RETRYABLE -> RETRY_WAITING -> JENKINS_QUEUED
FAILED_FINAL
NEED_HUMAN
CANCELLED
TIMEOUT
```

关键节点职责：

1. **CONFIG_NORMALIZED**：把用户配置、默认值、环境、分支、模板版本整理成稳定结构。
2. **HASHED**：对规范化后的配置计算 `config_hash`，用于去重、追踪和对比。
3. **PLANNED**：Agent 生成执行计划、风险等级和验收条件。
4. **WAITING_HIL**：高风险或有副作用操作前等待人工确认。
5. **JENKINS_QUEUED/RUNNING**：记录 Jenkins `queue_id/build_number/build_url`，持续同步外部状态。
6. **RESULT_COLLECTING**：拉取日志摘要、artifact、测试报告和错误码。
7. **VERIFYING**：用业务规则、测试结果和指标判断任务是否真正成功。
8. **FAILED_RETRYABLE/NEED_HUMAN**：根据失败类型决定自动重试还是人工介入。

状态流转要通过条件更新完成，避免多个 worker 同时推进同一任务：

```sql
UPDATE agent_task
SET status = 'JENKINS_RUNNING',
    build_number = ?,
    version = version + 1
WHERE run_id = ?
  AND status = 'JENKINS_QUEUED'
  AND version = ?;
```

## 2. HIL 放在哪里

HIL 应该放在高风险副作用之前，而不是任务开始时统一问一次。

适合放 HIL 的位置：

1. **触发 Jenkins 前**：确认配置、环境、分支、影响范围和是否允许消耗 CI/CD 资源。
2. **生产写操作前**：发布、回滚、重启、配置变更、数据修复必须审批。
3. **重试上限前**：自动重试多次仍失败时，让人判断继续、停止还是改配置。
4. **重新发起前**：同一 `config_hash` 用户要求强制重跑时，确认不是误触发。
5. **低置信决策后**：模型判断和规则校验冲突，或者日志证据不足时。

HIL 后面的节点不能只写“继续执行”，至少要有：

1. **审批记录**：审批人、审批内容、风险、时间、审批结论、trace id。
2. **执行节点**：带 `run_id/attempt_id/config_hash` 调用 Jenkins。
3. **状态持久化节点**：写入 Jenkins queue/build 信息。
4. **观察节点**：同步 Jenkins 状态、日志和 artifact。
5. **验证节点**：根据验收条件判断是否成功。
6. **失败分流节点**：进入重试、人工介入或最终失败。

## 3. 幂等和哈希怎么设计

这里一定要做幂等，因为 Agent 任务通常跨前端、后端、Jenkins、数据库和消息队列。任一环节网络抖动或服务重启，都可能导致重复触发 Jenkins、重复写状态、重复发通知。

标识要分层：

| 标识 | 含义 | 用途 |
| --- | --- | --- |
| `config_hash` | 同一份规范化配置 | 判断配置是否变化、同配置追踪 |
| `run_id` | 用户发起的一次任务 | 唯一定位任务 |
| `attempt_id` | 同一任务的一次尝试 | 区分自动重试 |
| `jenkins_queue_id` | Jenkins 队列项 | 触发后未开始构建时接回 |
| `build_number/build_url` | Jenkins 构建实例 | 跟踪外部执行 |

同一份配置的哈希是否固定，取决于规范化规则是否稳定。需要把 JSON key 排序，去掉无语义空白和默认值，明确环境、分支、模板版本是否参与哈希。否则同一语义配置可能算出不同哈希。

`config_hash` 表示同一类输入或同一份配置，不应该单独表示同一个任务。拿哈希查任务可能有歧义：

1. 历史成功任务和当前运行任务配置相同。
2. 用户明确重新发起了一次同配置任务。
3. 同一配置在不同环境、分支或模板版本下执行。
4. 同一个 run 下有多次 retry attempt。

推荐唯一性：

```text
run_id 唯一定位一次任务
(run_id, attempt_no) 唯一定位一次尝试
(workflow_id, env, branch, config_hash, trigger_mode) 用于短时间去重
```

## 4. 重试和重新发起

幂等机制拦截的是非预期重复，不应该拦截用户明确要求的重新发起。

区别：

1. **retry**：同一个 `run_id` 下增加 `attempt_id`，通常复用配置和审批，用于 Jenkins 临时失败、网络抖动、worker 重启。
2. **rerun**：新建一个 `run_id`，可以使用同一个 `config_hash`，代表用户明确再跑一次。
3. **dedup**：短时间内重复点击或重复消息投递，返回已有 `RUNNING` 任务，不新建 Jenkins build。
4. **force rerun**：用户审批后创建新 run，即使已有相同 `config_hash` 的成功或运行任务。

示例：

```text
POST /agent-runs
  config_hash = H1
  trigger_mode = normal
  if exists RUNNING run with same dedup_key:
      return existing run_id
  else:
      create new run_id

POST /agent-runs/{run_id}/retry
  create new attempt under same run_id

POST /agent-runs/{run_id}/rerun
  create new run_id with same config_hash
```

## 5. 异常恢复和断点续跑

恢复能力依赖独立状态存储，而不是聊天 memory。

必须持久化：

1. `run_id、attempt_id、status、config_hash`。
2. Jenkins `queue_id、build_number、build_url`。
3. 当前状态机节点、retry_count、lease_until、owner。
4. checkpoint、last_error、artifact 引用、审批记录。
5. 压缩后的任务摘要和关键约束。

异常处理：

1. **触发 Jenkins 请求超时**：先查 dedup key、queue item 或 Jenkins 参数，不确认失败前不要再次触发。
2. **会话断开**：任务继续执行，用户回来后用 `run_id` 查状态和 build URL。
3. **服务挂了**：重启后扫描 `RUNNING` 且租约过期的任务，根据 Jenkins build 状态补写本地状态。
4. **Jenkins 还在跑**：本地恢复为 `JENKINS_RUNNING`，继续观察原 build。
5. **Jenkins 已完成**：拉取结果、日志摘要和 artifact，进入验证节点。
6. **本地成功写状态失败**：依靠 outbox、重试和对账任务补偿。

自动重启可以做，但要分级：

1. 网络抖动、日志拉取失败、Jenkins agent 临时离线可以自动重试。
2. 构建失败、测试失败要先分类，不能无脑重跑。
3. 影响生产、重复失败、需要改配置或扩大范围时进入 HIL。
4. 所有重试都有 `max_attempts`、退避、总超时和错误指纹去重。

## 6. 记忆和状态怎么分层

Agent 记忆分三层：

1. **短期上下文**：最近对话、当前计划、下一步动作、必要工具反馈，放进 prompt。
2. **长期记忆**：用户偏好、项目稳定事实、历史故障经验、常用 Jenkins job，放数据库或向量库。
3. **任务状态**：运行时正确性字段，放独立状态存储，不能只放 memory。

只进任务状态的信息：

1. 状态机节点、外部 job id、审批状态。
2. retry_count、lease_until、checkpoint。
3. 当前 attempt、错误码、artifact id。

只进短期上下文的信息：

1. 当前用户问题和刚发生的工具反馈。
2. 当前 step 的局部判断。
3. 下一步需要模型决策的少量证据。

可进入长期记忆的信息：

1. 稳定的项目结构和 Jenkins job 映射。
2. 用户明确偏好和团队规范。
3. 已验证的故障恢复经验。

## 7. 上下文压缩和 30 轮裁剪

30 轮裁剪不能按时间机械截断。长链路任务要保留“当前决策所需状态”，把其他内容外部化。

压缩结果建议包含：

1. 用户目标和硬性约束。
2. 当前状态机节点和下一步。
3. 已完成步骤、失败步骤、已排除方案。
4. Jenkins build URL、artifact ID、日志摘要。
5. 风险点、审批记录和人工结论。

续接流程：

```text
读取 run 状态
-> 读取最近对话窗口
-> 读取滚动摘要
-> 按状态机节点召回 Jenkins/artifact/日志
-> 重建 prompt
-> 从 checkpoint 继续
```

保证不丢关键任务信息：

1. 用结构化状态保存关键字段，而不是只靠自然语言摘要。
2. 摘要必须带外部证据引用，例如 build URL、文件路径、trace id。
3. 压缩后做规则校验，缺少目标、约束、状态、下一步或外部 ID 就拒绝覆盖旧摘要。
4. 用长任务回放集评测压缩前后是否还能正确续跑。

## 8. ReAct、Reflection 和死循环治理

ReAct 是“推理 + 行动 + 观察”的循环：

```text
Thought -> Action -> Observation -> Thought -> ...
```

Reflection 是在观察之后增加反思：判断上一步为什么失败、是否重复、是否需要换策略、是否应该停下来。

Reflection 的价值是减少盲目重试，但不能单独解决死循环。要靠工程约束：

1. 最大 step 数、最大工具调用数、最大运行时间和最大成本。
2. 同一工具、同一参数、同一错误指纹禁止重复调用。
3. 失败进入分类：参数错、权限错、环境错、业务错、外部服务错。
4. 指数退避和熔断，避免 Jenkins 或外部服务异常时被打爆。
5. 到达重试上限后进入 `NEED_HUMAN`，而不是继续反思。
6. 每个 step 有可验证验收条件，不能只靠模型自评。

## 9. 面试回答模板

我会把这个 Agent 设计成有状态工作流，而不是一次模型调用。用户配置先规范化并计算 `config_hash`，但 `config_hash` 只表示同一份配置，不能唯一表示一次任务；一次任务用 `run_id`，一次重试用 `attempt_id`。状态机从配置解析、计划、HIL 审批、Jenkins 排队、运行、结果收集、验证到成功或失败，每个节点都持久化。

HIL 放在高风险副作用前，比如触发 Jenkins、生产变更、强制重跑和重试上限前。触发 Jenkins 后要保存 `queue_id/build_number/build_url`，会话断开不影响任务；服务重启后通过状态表扫描 RUNNING 任务，再查询 Jenkins 接回原 build。重试和重新发起要区分：retry 是同一个 run 的新 attempt，rerun 是新的 run，可以复用同一个配置哈希。

上下文上，我会把短期 prompt、长期记忆和任务状态分开。任务状态必须在独立状态存储里，包含状态机节点、外部任务 ID、checkpoint、重试次数和审批记录；长期记忆只保存稳定事实和经验。超过上下文窗口时做滚动摘要和结构化状态，不按时间硬删。ReAct 负责边推理边调用工具，Reflection 负责失败后复盘和调整策略，但死循环要靠 max step、错误指纹去重、退避、熔断、验收条件和人工介入兜底。
