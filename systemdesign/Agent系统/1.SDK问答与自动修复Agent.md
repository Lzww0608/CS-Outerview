# 1. SDK 问答与自动修复 Agent

企业内部 Agent 设计要先区分两类能力：知识问答类 Agent 负责帮助研发查 SDK 用法、规范和历史问题；自动修复类 Agent 负责发现、定位、生成补丁和验证。前者偏 RAG，后者偏受控工作流，不能用同一套安全边界。

## 1. SDK 问答 Agent 怎么设计

目标是让研发用自然语言查询内部 SDK 的使用方法、示例、版本差异和常见错误。

整体链路：

```text
SDK 文档 / README / API 注释 / 示例代码 / issue / 工单
  -> 文档解析和代码切分
  -> embedding + BM25 索引
  -> 权限过滤
  -> query rewrite
  -> 混合召回 + rerank
  -> LLM 生成答案
  -> 引用来源和示例代码
```

核心设计：

1. **知识源**：官方文档、代码仓库、示例项目、CHANGELOG、FAQ、历史工单和错误码库。
2. **代码感知切分**：按包、类、函数、注释、示例块切 chunk，保留语言、版本、路径和符号名。
3. **混合检索**：BM25 处理函数名、错误码、类名；向量召回处理语义问题；reranker 提升证据排序。
4. **权限控制**：不同团队只能检索有权限的仓库、文档和内部接口。
5. **答案格式**：先给结论，再给最小示例代码、注意事项、版本要求和引用来源。
6. **反馈闭环**：用户点赞/纠错、无答案、低相关引用进入评测集，反向优化文档和检索。

## 2. 客户端提交代码让 Agent 修复问题

这个场景不能让 Agent 直接改线上代码。更安全的流程是让 Agent 在隔离环境中生成候选补丁，并通过测试和人工审批进入正常研发流程。

```text
问题描述 / 日志 / 用户环境 / 代码快照
  -> 复现和定位
  -> 生成最小补丁
  -> 本地测试 / 静态检查 / 安全扫描
  -> 生成 MR/PR
  -> 人工 Review
  -> 灰度发布
```

关键设计：

1. **隔离沙箱**：代码执行在容器或临时工作区，限制网络、文件系统和密钥访问。
2. **只改最小范围**：Agent 必须给出修改文件、原因、影响面和验证命令。
3. **测试优先**：先补失败用例或复现脚本，再改代码，避免只凭日志猜。
4. **权限分级**：Agent 可读代码和日志，生成补丁；合并、发布、回滚必须走人工或 CI/CD 审批。
5. **审计记录**：保存输入、工具调用、diff、测试结果和审批记录。

## 3. 告警触发后的自动恢复 Agent

自动恢复 Agent 的输入来自监控和告警，而不是用户对话：

```text
Prometheus / 日志平台 / Trace / 告警
  -> 事件归并和影响面判断
  -> 检索 runbook 和历史故障
  -> 诊断根因候选
  -> 低风险自动处置 / 高风险请求审批
  -> 验证恢复效果
  -> 生成复盘
```

可自动执行的低风险动作：

1. 重启单个无状态实例。
2. 摘除不健康实例。
3. 扩容 worker 或消费者。
4. 开启非核心功能降级。
5. 清理本地临时缓存或刷新配置。

需要人工审批的高风险动作：

1. 数据修复、删除、批量补偿。
2. 修改生产配置的大范围开关。
3. 回滚数据库结构或执行 DDL。
4. 支付、账号、权限相关写操作。
5. 大规模流量切换和跨地域容灾。

## 4. 如何避免修 A 引入 B/C/D

自动修复最怕“修一个问题引入更多问题”。要把 Agent 限制在可验证、可回滚的小步流程里。

1. **问题收敛**：先明确单一目标、影响范围和成功判据，不让 Agent 同时重构无关代码。
2. **最小 diff**：限制修改文件和行数，禁止顺手重构、格式化全仓库或改公共接口。
3. **测试护栏**：运行相关单测、回归测试、契约测试和静态检查；没有测试时先生成复现用例。
4. **依赖图分析**：改动公共函数、协议、数据库字段时，必须列出调用方和兼容影响。
5. **分阶段发布**：补丁先进入 PR，再灰度小流量，观察错误率和业务指标。
6. **自动回滚**：灰度指标恶化时自动回滚代码或关闭开关。
7. **人工审批点**：越权、删数据、改安全策略、改计费逻辑必须人工确认。
8. **故障样本回放**：用历史故障和线上脱敏样本回放，避免只修当前 case。

## 5. 系统组件

| 组件 | 作用 |
| --- | --- |
| Ingestion | 收集文档、代码、日志、告警、工单和 runbook |
| Retriever | RAG 检索相关知识、历史故障和代码片段 |
| Planner | 拆解诊断和修复步骤 |
| Tool Layer | 读日志、查指标、跑测试、创建 PR、操作发布平台 |
| Sandbox | 隔离执行命令和测试 |
| Policy Engine | 权限、风险等级、审批和可执行动作控制 |
| Evaluator | 判断测试、指标和恢复条件是否达标 |
| Audit | 保存轨迹、diff、审批和复盘 |

## 6. 易错点

1. SDK 问答 Agent 不能没有引用来源，否则用户无法信任答案。
2. 自动修复 Agent 不能直接拥有生产写权限。
3. 告警到处置之间要先做事件归并，否则告警风暴会让 Agent 重复执行动作。
4. 修复建议必须可验证，不能只输出“可能是缓存问题”。
5. 工具结果和日志要裁剪，避免把大量无关内容塞满上下文。
6. 自动恢复要有频率限制，不能在同一故障上无限重启或反复回滚。

## 7. 面试回答模板

如果做 SDK 问答 Agent，我会把 SDK 文档、代码注释、示例、FAQ、issue 和工单建成带权限的 RAG 知识库，使用 BM25 + 向量混合召回，再用 reranker 排序，答案必须带来源和最小可运行示例。自动修复 Agent 我会设计成受控工作流：告警触发后先聚合事件，检索日志、trace、runbook 和历史故障，生成诊断假设；低风险动作如重启、摘流、扩容、降级可以自动执行，高风险动作必须审批。代码修复只能在沙箱里生成最小补丁，跑测试和静态检查后创建 PR，经人工 Review 和灰度发布，避免修 A 引入 B/C/D。
