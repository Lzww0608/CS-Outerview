# 5. Agent Memory 设计

Agent 里的 Memory 不是简单的“把聊天记录存起来”，而是一个围绕**当前推理、任务状态、跨会话经验、用户偏好和外部知识**的上下文管理体系。

可以先用一句话概括：

```text
Agent Memory = 短期上下文 + 任务状态 + 长期记忆 + 检索机制 + 写入/遗忘策略 + 权限审计
```

面试里回答这个问题时，重点不是背某个框架的 API，而是说明：

1. 记忆有哪些类型。
2. 每类记忆存什么、存在哪里、什么时候读写。
3. 如何避免错误记忆、隐私泄露和上下文污染。
4. 工程上如何评估记忆是否真的有用。

## 1. Memory 和 Context 的区别

Context 是模型本次调用时实际看到的内容，Memory 是系统可以长期或短期保存、检索、压缩后再注入 Context 的信息。

```text
Memory Store
  -> retrieve / summarize / filter
  -> Context Builder
  -> Prompt / Tool Arguments
  -> LLM
```

也就是说，Memory 不一定都进入 Prompt。好的系统会根据当前任务只注入必要信息。

常见误区：

1. 把所有历史对话都塞进上下文。
2. 把所有向量检索结果都叫 Memory。
3. 把任务状态、用户偏好、知识库文档混在一个表里。
4. 让模型自己无约束写长期记忆。

## 1.1 Memory 和 RAG 的区别

面试里问“为什么这样做 memory，和 RAG 有什么区别”，核心是区分**用户/任务侧的持续状态**和**外部知识侧的检索增强**。

一句话：

```text
Memory 解决“这个用户、这个任务、这个项目之前发生过什么，以及哪些状态要延续”；
RAG 解决“当前问题需要哪些外部知识、文档和事实证据”。
```

| 维度 | Memory | RAG |
| --- | --- | --- |
| 主要对象 | 用户偏好、会话摘要、任务状态、项目事实、历史经验 | 文档、FAQ、代码、知识库、网页、工单 |
| 生命周期 | 可跨轮、跨会话，部分长期保存 | 随知识库更新，按查询临时召回 |
| 读写时机 | 会话中持续更新，任务结束后沉淀 | 文档入库时写，用户提问时检索 |
| 正确性要求 | 任务状态必须强一致，长期记忆要可纠错 | 召回结果要相关、权威、带来源 |
| 常用存储 | 关系库、Redis、事件日志、向量库、对象存储 | 向量库、全文索引、搜索引擎、文档库 |
| 最大风险 | 错误记忆长期污染、串用户、状态丢失 | 漏召回、误召回、权限泄露、引用错误 |

两者经常组合，但边界不同：

```text
用户问题
-> Memory：读取用户偏好、当前 topic、任务 run state、历史约束
-> RAG：检索产品文档、项目资料、外部知识和证据
-> ContextBuilder：权限过滤、去重、重排、压缩
-> LLM：基于当前任务状态和外部证据回答
```

为什么不能只用 RAG 做 Memory：

1. **RAG 召回不稳定**：同一条任务状态可能因为 query 改写或 embedding 漂移召回不到。
2. **状态需要事务语义**：`run_id、step_id、approval_status、external_job_id` 需要条件更新、幂等和审计。
3. **记忆有作用域**：用户偏好、项目事实、组织知识需要不同权限边界，不能只靠向量相似度。
4. **长期记忆要可编辑可删除**：用户纠错后要降低置信度、废弃或覆盖旧记忆。

为什么不能只用 Memory 替代 RAG：

1. Memory 通常保存摘要和偏好，不适合承载大量文档原文。
2. 外部知识会更新，RAG 可以按版本、时间、权限检索最新材料。
3. 回答事实性问题需要引用证据，Memory 更像上下文背景，不能替代来源。

真实场景可以这样设计：

1. 用户偏好、会话 topic、任务 checkpoint 放 Memory/State Store。
2. 产品文档、接口说明、代码库说明放 RAG。
3. ContextBuilder 先加载确定性状态，再召回知识证据。
4. 如果 Memory 和 RAG 冲突，按优先级处理：当前用户显式指令 > 权威业务 API/数据库 > 最新文档证据 > 历史记忆 > 模型常识。
5. 对会影响长期行为的 Memory 写入做候选区、置信度、TTL 和用户纠错，不让一次错误回答永久生效。

面试回答模板：

> 我不会把 memory 等同于 RAG。RAG 是知识检索链路，负责从文档、FAQ、代码库里召回当前问题需要的证据；Memory 是 Agent 的持续状态和经验体系，负责保存用户偏好、会话摘要、任务 checkpoint、项目事实和历史经验。任务状态这类正确性信息必须进结构化库或工作流引擎，不能只靠向量召回；长期记忆要有 scope、source、confidence、ttl 和删除纠错机制。实际系统里二者会组合：先读取 run state 和用户偏好，再用 RAG 检索外部证据，最后由 ContextBuilder 做权限过滤、重排和压缩。

## 2. 按生命周期分类

### 2.1 工作记忆 Working Memory

工作记忆是本轮推理要用的临时信息，通常直接放在上下文窗口里。

包括：

1. 当前用户问题。
2. 最近几轮消息。
3. 当前计划。
4. 本轮工具调用结果摘要。
5. 当前约束和风险提示。

特点：

1. 生命周期短，通常只在当前 `run_id` 内有效。
2. 延迟要求高。
3. 可以被压缩和裁剪。
4. 不适合作为恢复任务的唯一依据。

### 2.2 会话短期记忆 Short-term Memory

短期记忆通常是线程或会话级别的状态，作用是让同一会话可以多轮连续。

典型内容：

1. `conversation_id` 下的消息历史。
2. 当前任务目标和摘要。
3. 最近工具结果。
4. 用户在本会话内给出的临时偏好。

存储方式：

1. Redis：低延迟，适合短期缓存。
2. PostgreSQL/MySQL：适合持久化会话和回放。
3. LangGraph checkpointer：把 graph state 持久化，支持线程恢复。

注意：短期记忆不等于长期记忆。用户临时说“这次用英文回答”，不应该自动变成永久偏好。

### 2.3 任务状态 Task State

任务状态不是“记忆增强”，而是系统正确性的一部分。

例如：

```text
run_id
step_id
plan
current_node
tool_call_id
external_job_id
approval_status
retry_count
checkpoint
```

它必须结构化、可恢复、可审计，应该存到可靠数据库或工作流引擎里，而不是只放向量库。

适合存储：

1. MySQL/PostgreSQL。
2. Redis + 持久化队列。
3. Temporal、Cadence、Airflow、LangGraph checkpoint 等工作流/状态图系统。
4. 事件日志 Event Sourcing。

易错点：

1. 不能把 Jenkins build id、支付审批状态、库存扣减状态只写进自然语言摘要。
2. 模型召回失败不能导致任务丢状态。
3. 中断、重试、恢复都依赖任务状态，而不是模型记忆。

### 2.4 长期记忆 Long-term Memory

长期记忆跨会话存在，用来保存稳定事实、偏好、经验和外部产物索引。

包括：

1. 用户长期偏好：语言、格式、常用城市、常用技术栈。
2. 项目事实：仓库结构、测试命令、服务边界、部署流程。
3. 历史经验：某类错误的修复路径、某个工具的失败恢复方式。
4. 产物索引：报告 ID、文件路径、设计稿链接、工单 ID。

长期记忆必须有元数据：

```json
{
  "memory_id": "mem_123",
  "scope": "user|project|org|agent",
  "type": "semantic|episodic|procedural|profile",
  "content": "用户偏好回答使用中文，并给出修改文件摘要",
  "source": "conversation:conv_1:message_8",
  "confidence": 0.92,
  "created_at": "2026-05-04T10:00:00+08:00",
  "updated_at": "2026-05-04T10:00:00+08:00",
  "ttl": null,
  "permissions": {
    "owner_user_id": "u1",
    "tenant_id": "t1"
  }
}
```

### 2.5 用户级别隔离的长期记忆

如果面试追问“怎么实现用户级别隔离的长期记忆”，核心不是只给向量库加一个 `user_id` 字段，而是把**写入、检索、注入、删除和审计**都做成带权限边界的闭环。

推荐设计：

1. **命名空间隔离**：长期记忆的主键或索引命名空间至少包含 `tenant_id + user_id`，必要时再加 `project_id`、`agent_id`，避免个人记忆、项目记忆和组织记忆混用。
2. **结构化权限字段**：每条记忆都保存 `owner_user_id`、`tenant_id`、`scope`、`visibility`、`source`、`confidence`、`ttl`、`consent_status`，读写时由权限服务判断，而不是只依赖 Prompt 约束模型。
3. **检索强过滤**：向量检索、全文检索和 SQL 查询都必须带元数据过滤条件；如果向量库不支持强一致过滤，要在召回后再做二次 ACL 过滤，不能把越权结果交给模型自行忽略。
4. **写入审批与分级**：用户明确确认的偏好可以写长期 profile；从对话中自动抽取的事实要先进入候选记忆，经过置信度、敏感信息和冲突检查后再落库。
5. **上下文注入前复核**：Context Builder 在注入前再次检查当前 `request_user_id`、`tenant_id`、任务 scope 和记忆权限，防止缓存、摘要或跨会话恢复时串用户。
6. **删除与导出**：支持用户查看、编辑、删除、导出自己的长期记忆；软删除后检索层要立即不可见，后台再异步清理向量、摘要和对象存储。
7. **审计与评测**：记录谁在什么时候读写了哪类记忆，离线评测要包含“跨用户召回”“跨租户召回”“已删除记忆召回”等负样本。

一个简化表结构可以这样设计：

```sql
CREATE TABLE agent_memory (
    memory_id      BIGINT PRIMARY KEY,
    tenant_id      BIGINT NOT NULL,
    owner_user_id  BIGINT NOT NULL,
    project_id     BIGINT NULL,
    scope          VARCHAR(32) NOT NULL,
    memory_type    VARCHAR(32) NOT NULL,
    content        TEXT NOT NULL,
    embedding_id   VARCHAR(128),
    confidence     DOUBLE,
    ttl_at         TIMESTAMP NULL,
    deleted_at     TIMESTAMP NULL,
    source         VARCHAR(128),
    created_at     TIMESTAMP NOT NULL,
    updated_at     TIMESTAMP NOT NULL,
    INDEX idx_owner_scope (tenant_id, owner_user_id, scope, updated_at)
);
```

真实场景里还要注意：共享项目知识可以放在 `project` 或 `org` scope，但用户隐私和个人偏好默认只能本人可见；如果要做团队共享，必须有明确授权、脱敏和审计。最危险的错误是“召回时只按语义相似度查向量库”，这样即使应用层接口有鉴权，也可能在 Prompt 里泄露其他用户的记忆。

## 3. 按认知类型分类

Agent Memory 经常按 semantic、episodic、procedural 来分类。

| 类型 | 记什么 | 例子 | 存储方式 |
| --- | --- | --- | --- |
| Semantic Memory | 稳定事实和知识 | “项目用 pnpm 构建”“用户常驻杭州” | 结构化库、向量库、profile |
| Episodic Memory | 过去发生过的事件和案例 | “上次修 CI 是因为 Node 版本不一致” | 事件日志、摘要库、向量索引 |
| Procedural Memory | 怎么做某类任务 | “修 CI 的步骤”“PR review checklist” | Skill、规则文件、Runbook |
| Profile Memory | 用户或组织画像 | 偏好语言、常用城市、权限范围 | 用户画像表、KV、配置中心 |
| Archival Memory | 大量历史材料 | 旧对话、文档、工单、日志摘要 | 向量库、对象存储、搜索引擎 |
| Recall Memory | 可检索的旧消息 | 某次对话里用户提过的约束 | 消息库 + 全文/向量检索 |

### Semantic Memory

语义记忆回答“是什么”。

适合保存：

1. 用户明确确认的偏好。
2. 项目稳定配置。
3. 可复用业务事实。
4. 组织知识库摘要。

风险：

1. 事实过期。
2. 模型误抽取。
3. 不同作用域混用导致越权。

### Episodic Memory

情景记忆回答“过去发生过什么”。

适合保存：

1. 成功任务轨迹。
2. 失败案例和恢复路径。
3. 用户反馈。
4. 工具调用 trace 摘要。

用途：

1. 类似问题检索。
2. Few-shot 示例。
3. 失败复盘。
4. Agent 评测集构建。

### Procedural Memory

程序性记忆回答“怎么做”。

它可以是：

1. Skills。
2. Runbook。
3. 项目规则。
4. SOP。
5. Workflow 节点配置。

例如代码 Agent 的程序性记忆：

```text
修复 CI：
1. 先查看失败 job 和日志。
2. 复现失败命令。
3. 定位最近变更。
4. 最小范围修改。
5. 重新运行对应测试。
6. 输出失败原因和验证结果。
```

这类记忆不一定用向量库，很多时候以 Markdown、YAML、规则文件或 Skill 包形式存在。

## 4. 常见 Memory 实现方式

### 4.1 原始消息历史

保存完整对话消息：

```text
conversation_id -> messages[]
```

优点：

1. 实现简单。
2. 可回放、可审计。
3. 对短对话效果好。

缺点：

1. 上下文很快超长。
2. 历史噪声多。
3. 早期关键约束可能被截断。

适合：短对话、客服工单、审计回放。

### 4.2 滑动窗口

只保留最近 N 轮或最近 N tokens。

优点：

1. 简单、低成本。
2. 最近上下文相关性通常较高。
3. 延迟低。

缺点：

1. 容易丢早期硬性约束。
2. 不适合长任务。
3. 不能解决跨会话记忆。

工程上通常把滑动窗口和结构化状态、摘要结合使用。

### 4.3 滚动摘要

把旧消息压缩成摘要，新消息保留原文：

```text
summary_so_far + recent_messages -> next_context
```

摘要应包含：

1. 用户目标。
2. 硬性约束。
3. 已完成步骤。
4. 当前计划。
5. 关键资源 ID。
6. 已确认事实和已排除方案。

优点：

1. 降低 token。
2. 保留长任务连续性。
3. 适合多轮客服和研发 Agent。

缺点：

1. 摘要可能漏信息。
2. 摘要可能引入原文没有的错误事实。
3. 多次递归摘要会损失细节。

### 4.4 结构化状态

把目标、计划、变量和工具结果存成 JSON：

```json
{
  "goal": "修复 CI 中 test_user_login 失败",
  "constraints": ["不要修改数据库 schema"],
  "plan": [
    {"step": "读取 CI 日志", "status": "done"},
    {"step": "定位失败测试", "status": "doing"}
  ],
  "artifacts": [
    {"type": "ci_log", "url": "https://ci/job/123"}
  ]
}
```

优点：

1. 可恢复。
2. 可校验。
3. 对工具调用友好。
4. 不容易被自然语言摘要污染。

缺点：

1. 需要提前设计 schema。
2. 开放任务中的隐性信息不一定容易结构化。
3. schema 演进需要兼容。

### 4.5 向量记忆

把历史摘要、文档片段、经验记录 embedding 后存入向量库，按当前任务语义召回。

适合：

1. 历史经验检索。
2. 项目知识检索。
3. 用户偏好召回。
4. 长文档和工单查询。

注意点：

1. 必须带元数据过滤：`user_id、tenant_id、project_id、scope、ttl`。
2. 要做重排和去重，不要把相似但过期的记忆直接注入。
3. 要保留来源，便于用户纠错。
4. 不适合作为任务状态唯一存储。

### 4.6 关键词/全文检索记忆

有些记忆更适合全文检索，而不是向量检索：

1. 错误码。
2. 函数名。
3. 文件路径。
4. 工单 ID。
5. 精确配置项。

工程上常用混合检索：

```text
BM25 / keyword
+ vector search
+ metadata filter
+ rerank
```

### 4.7 Profile 记忆

Profile 是压缩后的用户画像或 Agent 画像。

例如：

```text
用户偏好：
- 默认中文回答。
- 代码任务希望先给修改摘要，再给验证命令。
- 常用技术栈：Java/Spring、Redis、MySQL。
```

优点：

1. 注入成本低。
2. 读取稳定。
3. 适合个性化。

缺点：

1. 容易固化错误偏好。
2. 需要用户可查看、可编辑、可删除。
3. 要区分长期偏好和本轮临时要求。

### 4.8 外部产物索引

大文件、大日志、报告、截图、设计稿不应该长期塞进上下文，而应该保存引用：

```text
artifact_id
type
path / url
summary
created_at
owner
permissions
```

需要时通过工具读取局部内容。

适合：

1. CI 日志。
2. PDF。
3. 代码 diff。
4. 图片和截图。
5. 生成报告。

### 4.9 Multi-Agent 共享记忆

多 Agent 系统常用共享黑板：

```text
Shared Memory / Blackboard
  - task brief
  - evidence
  - decisions
  - open questions
  - artifacts
```

注意点：

1. 追加写优先，避免互相覆盖。
2. 关键状态要有版本号或乐观锁。
3. 每个 Agent 只读取自己需要的上下文。
4. 高风险结论需要 Reviewer 或主控 Agent 验证。

## 5. Memory 写入策略

Memory 写入比读取更危险，因为错误记忆会长期污染后续任务。

推荐流程：

```text
对话/工具结果
-> 候选记忆抽取
-> 分类：偏好/事实/经验/状态/产物
-> 安全过滤：敏感信息、隐私、权限
-> 质量判断：重要性、稳定性、置信度
-> 去重合并
-> 设置 scope、ttl、source、confidence
-> 写入 memory store
-> 审计和可回滚
```

### 5.1 Hot Path 写入

Hot Path 指在用户请求链路里直接写记忆。

适合：

1. 用户明确说“记住我以后都用中文回答”。
2. 当前任务必须立刻持久化的结构化状态。
3. 工具执行产生必须记录的 checkpoint。

优点是即时生效，缺点是增加主链路延迟，并且容易把未经整理的信息写入长期记忆。

### 5.2 Background Consolidation

后台整理是更稳的做法：

```text
消息和工具 trace
-> 异步任务扫描
-> 提取候选记忆
-> 规则/模型打分
-> 人工或自动确认
-> 写长期记忆
```

优点：

1. 不阻塞主链路。
2. 可以做更复杂的去重、脱敏和质量判断。
3. 可以批量合并重复记忆。

缺点：

1. 生效有延迟。
2. 需要处理异步任务失败和重复执行。

### 5.3 用户显式确认

对隐私、偏好和长期影响大的记忆，最好让用户确认：

```text
“我可以记住你默认希望用中文回答吗？”
```

适合：

1. 个人偏好。
2. 常用地址、城市、身份信息。
3. 高敏业务规则。
4. 组织级知识更新。

## 6. Memory 检索和注入策略

读取 Memory 时不要“召回多少塞多少”，应该经过过滤和排序。

流程：

```text
当前任务
-> 解析意图、用户、租户、项目、资源范围
-> 读取 profile / task state
-> 检索 semantic / episodic / archival memory
-> 权限过滤
-> 相关性重排
-> 新鲜度和置信度过滤
-> 摘要压缩
-> 注入固定 prompt 段落
```

推荐注入格式：

```text
Relevant memory:
1. [user preference][source=mem_1][confidence=0.95]
   用户偏好中文回答。
2. [project fact][source=mem_8][updated=2026-05-01]
   该项目测试命令是 `pnpm test`。

Rules:
- 如果当前用户请求和记忆冲突，以当前用户请求为准。
- 不要把低置信记忆当作事实。
```

冲突处理：

1. 当前用户显式指令优先于历史偏好。
2. 高优先级系统规则优先于用户记忆。
3. 新版本项目事实优先于旧版本事实。
4. 低置信记忆只能作为提示，不能作为确定事实。

## 7. 遗忘、更新和纠错

Agent Memory 必须支持遗忘，否则错误和过期信息会长期污染系统。

常见机制：

1. **TTL**：临时偏好、定位、会话假设自动过期。
2. **版本号**：项目配置、角色权限、工具说明变更时更新版本。
3. **用户删除**：用户可以查看和删除个人记忆。
4. **纠错反馈**：用户说“这不对”时，降低置信度或标记废弃。
5. **周期性压缩**：多条重复记忆合并为 profile。
6. **访问衰减**：长期未使用的记忆降低召回优先级。

记忆记录建议增加：

```text
status: active | deprecated | deleted
valid_from / valid_to
last_used_at
usage_count
superseded_by
```

## 8. 安全和隐私

Memory 是 Agent 系统的高风险模块，因为它跨会话、跨时间保存信息。

必须注意：

1. **权限隔离**：个人、项目、租户、组织记忆不能串。
2. **敏感信息过滤**：密码、token、身份证、精确位置、密钥不应进入长期记忆。
3. **Prompt Injection**：外部文档里的“记住这条规则”不能直接写入长期记忆。
4. **数据最小化**：能保存城市就不要保存经纬度；能保存摘要就不要保存全文。
5. **审计**：谁写入、谁读取、谁删除记忆要可追踪。
6. **用户控制**：个人记忆要支持查看、修改、删除和关闭。
7. **合规**：涉及个人数据要考虑保留期限、删除权、跨境和授权范围。

写入长期记忆前的安全判断：

```text
这条信息是否由用户明确提供？
是否对未来任务稳定有用？
是否包含敏感信息？
是否有明确作用域？
是否需要用户确认？
是否可过期或撤销？
```

## 9. 真实框架里的做法

### 9.1 LangChain / LangGraph

LangChain 把短期记忆视为 thread-scoped state。LangGraph 通过 checkpointer 持久化状态，让同一个 thread 可以恢复。长期记忆则通过 store 按 namespace/key 保存 JSON 文档，可以跨 thread 召回。

这对应工程里的两层：

1. **Short-term memory**：当前会话状态和消息历史。
2. **Long-term memory**：跨会话的用户或应用级数据。

Deep Agents 还把长期记忆做成文件式 memory，Agent 可以读取和更新 memory files；Skills 也可以看作 procedural memory。

### 9.2 Letta / MemGPT

Letta/MemGPT 强调 memory hierarchy：

1. **Core memory / in-context memory**：始终在上下文中的 persona、用户信息、工作状态等 memory block。
2. **Recall memory**：被移出上下文的旧对话，可通过搜索工具找回。
3. **Archival memory**：长期语义存储，可通过 archival memory search 查询。

它的特点是让 Agent 通过工具主动编辑 memory，例如插入、替换、重写 memory block，或者把长期事实写入 archival memory。

工程上要注意：自编辑 memory 需要强约束和审计，否则模型可能把误解写成长期事实。

### 9.3 LlamaIndex

LlamaIndex 更偏数据和检索体系，常见做法是把历史对话、文档、知识片段放入 index，通过 retriever 召回，再由 Agent 或 query engine 使用。

适合：

1. 企业知识库。
2. 文档型长期记忆。
3. RAG Agent。
4. 多源数据索引。

### 9.4 自研企业 Agent

企业内部 Agent 常采用组合设计：

```text
Conversation DB: 原始消息、审计和回放
State Store: run/step/checkpoint
Profile Store: 用户偏好和组织画像
Vector DB: 历史摘要、经验、文档片段
Search Engine: 精确关键词、错误码、文件路径
Object Store: 大日志、报告、截图、文件
Policy Service: 权限过滤和脱敏
```

ContextBuilder 每次请求时把这些来源按优先级编排成 Prompt。

## 10. 一个落地架构

可以设计成这些模块：

| 模块 | 职责 |
| --- | --- |
| `ConversationStore` | 保存原始消息、角色、时间、trace |
| `RunStateStore` | 保存 run、step、plan、checkpoint |
| `MemoryExtractor` | 从对话和工具结果中抽取候选记忆 |
| `MemoryClassifier` | 分类为 semantic、episodic、procedural、profile |
| `MemoryPolicy` | 判断是否允许写入、作用域、TTL、是否需要确认 |
| `MemoryStore` | 保存结构化记忆和元数据 |
| `VectorIndex` | 对可语义检索的记忆建 embedding |
| `MemoryRetriever` | 按任务检索记忆，做权限过滤和重排 |
| `ContextBuilder` | 把记忆、任务状态、工具结果组装进上下文 |
| `MemoryAuditor` | 记录读写、删除、纠错和使用情况 |

一次请求流程：

```text
User Request
-> Auth / Tenant / Permission
-> Load RunState
-> Load Recent Messages
-> Retrieve Profile + Long-term Memory
-> Retrieve RAG / Artifacts if needed
-> Build Context
-> LLM / Agent Loop
-> Tool Calls
-> Update RunState
-> Async Memory Extraction
-> Audit
```

## 11. 如何评估 Memory 设计

不要只看“记住了多少”，要看记忆是否提升任务质量。

指标：

1. **Memory Precision**：召回的记忆有多少真正相关。
2. **Memory Recall**：需要历史信息时是否召回到关键记忆。
3. **Task Success Rate**：长任务成功率是否提高。
4. **Constraint Retention**：早期约束是否被保留。
5. **Personalization Gain**：用户偏好是否改善体验。
6. **Staleness Rate**：过期或错误记忆被使用的比例。
7. **Privacy Incident**：越权召回、敏感信息注入次数。
8. **Token Cost**：记忆注入带来的 token 成本。
9. **Latency**：检索、重排、摘要引入的延迟。
10. **Correction Effectiveness**：用户纠错后是否不再犯同样错误。

测试集要覆盖：

1. 多轮长对话。
2. 用户早期约束。
3. 偏好更新和冲突。
4. 过期记忆。
5. 跨租户隔离。
6. Prompt injection 诱导写记忆。
7. 工具失败和任务恢复。

## 12. 易错点

1. 把 Memory 等同于向量数据库。
2. 把完整聊天记录原样作为长期记忆。
3. 把任务状态和语义记忆混在一起。
4. 没有作用域，导致用户 A 的记忆被用户 B 召回。
5. 没有 TTL 和纠错机制，错误记忆长期污染。
6. 让模型无约束写入长期记忆。
7. 检索结果不做权限过滤。
8. 记忆与当前用户指令冲突时不做优先级处理。
9. 对外部不可信文档中的指令进行记忆写入。
10. 记忆注入过多，反而挤占当前任务上下文。

## 13. 面试回答模板

可以这样回答：

> Agent 里的 memory 不能只理解成聊天历史或向量库。我会分成几层：第一层是 working memory，也就是当前 prompt 里的最近消息、当前目标、计划和工具结果；第二层是 short-term memory，按 conversation/thread 保存消息和状态，用于多轮会话恢复；第三层是 task state，保存 run_id、step、checkpoint、外部任务 ID，这部分要进数据库或工作流系统，不能靠语义召回；第四层是 long-term memory，保存用户偏好、项目稳定事实、历史经验和产物索引；第五层是 procedural memory，比如 Skills、Runbook 和 SOP，告诉 Agent 某类任务该怎么做。
>
> 实现上，短期会话可以用 Redis 或数据库，任务状态用 MySQL/PostgreSQL/工作流引擎，长期语义记忆用结构化表加向量索引，精确内容用全文检索，大文件只保存对象存储引用。写入长期记忆要经过候选抽取、分类、脱敏、权限过滤、置信度和 TTL 设置，最好支持用户确认和删除。读取时要按用户、租户、项目做权限过滤，再按相关性、新鲜度、置信度重排，最后只把必要摘要注入上下文。业界里 LangGraph 用 checkpointer 管短期状态、store 管长期记忆；Letta/MemGPT 用 core memory、recall memory、archival memory 做层级记忆；企业自研一般会把 ConversationStore、RunStateStore、MemoryStore、VectorIndex、ContextBuilder 和审计系统组合起来。
