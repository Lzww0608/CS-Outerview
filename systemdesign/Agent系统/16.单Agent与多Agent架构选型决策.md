# 单 Agent 与多 Agent 架构选型决策指南

## 1. 问题背景

在设计 Agent 系统时，一个核心问题是：应该使用单 Agent 还是多 Agent？不同的选择会影响系统的复杂性、可维护性和能力边界。

```text
┌─────────────────────────────────────────────────────────────┐
│                                                             │
│  架构选择：                                                 │
│                                                             │
│  单 Agent：                                                │
│  一个强大模型处理所有任务                                  │
│                                                             │
│  多 Agent：                                                │
│  多个专业 Agent 协作分工                                   │
│                                                             │
│  问题：何时选择哪种架构？                               │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

---

## 2. 问题现象

| 现象 | 描述 |
|------|------|
| 能力边界模糊 | 不确定单个 Agent 能处理多复杂 |
| 上下文冲突 | 多任务在单一 Agent 中相互干扰 |
| 专业化需求 | 不同任务需要不同技能 |
| 扩展性困惑 | 未来需求变化如何应对 |

---

## 3. 影响范围

- Agent 系统架构设计
- 系统复杂度和成本
- 开发和维护难度

## 4. 原因分析

### 4.1 核心维度评估

```text
┌─────────────────────────────────────────────────────────────┐
│                                                             │
│  单 Agent vs 多 Agent 决策维度：                           │
│                                                             │
│  1. 任务复杂度                                           │
│     • 简单单一任务 → 单 Agent                           │
│     • 复杂多步骤 → 多 Agent (分工)                       │
│                                                             │
│  2. 技能差异性                                           │
│     • 相似技能 → 单 Agent + Prompt                 │
│     • 完全不同技能 → 多 Agent                       │
│                                                             │
│  3. 上下文独立性                                        │
│     • 任务间无依赖 → 单/多 Agent 均可               │
│     • 任务间强依赖 → 单 Agent 或紧耦合多 Agent      │
│                                                             │
│  4. 扩展性需求                                          │
│     • 固定任务 → 单 Agent                              │
│     • 持续扩展 → 多 Agent (模块化)                   │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

## 5. 解决方案

### 5.1 评估框架

```python
class AgentArchitectureEvaluator:
    """
    Agent 架构评估器
    """
    
    def __init__(self):
        self.criteria = {
            "task_complexity": {"weight": 0.25, "scorer": self.score_complexity},
            "skill_diversity": {"weight": 0.20, "scorer": self.score_skill},
            "independence": {"weight": 0.20, "scorer": self.score_independence},
            "scalability": {"weight": 0.15, "scorer": self.score_scalability},
            "latency_requirement": {"weight": 0.10, "scorer": self.score_latency},
            "cost": {"weight": 0.10, "scorer": self.score_cost}
        }
    
    def evaluate(self, requirements):
        """
        评估并给出建议
        
        Args:
            requirements: {
                "tasks": list,           # 任务列表
                "skills_needed": list,   # 需要的技能
                "task_dependencies": dict,# 任务依赖
                "latency_sla": float,     # 延迟要求（秒）
                "budget": str,           # 预算：高/中/低
                "expected_scale": str     # 扩展预期
            }
        """
        scores = {}
        
        for criterion, config in self.criteria.items():
            scores[criterion] = config["scorer"](requirements)
        
        weighted_score = sum(
            scores[k] * self.criteria[k]["weight"] 
            for k in scores
        )
        
        return self._make_decision(weighted_score, scores)
    
    def score_complexity(self, req):
        """评估任务复杂度"""
        tasks = req["tasks"]
        
        # 平均任务步骤数
        avg_steps = sum(len(t.get("steps", [])) for t in tasks) / len(tasks)
        
        # 判断
        if avg_steps > 10:
            return 0.9  # 高度复杂 → 多 Agent
        elif avg_steps > 5:
            return 0.5  # 中度复杂
        else:
            return 0.2  # 简单 → 单 Agent
    
    def score_skill(self, req):
        """评估技能多样性"""
        skills = req.get("skills_needed", [])
        
        # 不同技能的数量
        unique_skills = len(set(skills))
        
        if unique_skills >= 5:
            return 0.9  # 多样性高 → 多 Agent
        elif unique_skills >= 3:
            return 0.6
        else:
            return 0.2  # 技能相似 → 单 Agent
    
    def score_independence(self, req):
        """评估任务独立性"""
        deps = req.get("task_dependencies", {})
        
        # 依赖密度
        dep_count = sum(len(d) for d in deps.values())
        task_count = len(req.get("tasks", []))
        
        density = dep_count / max(task_count, 1)
        
        if density < 0.3:
            return 0.8  # 低依赖 → 多 Agent
        elif density < 0.6:
            return 0.5  # 中度依赖
        else:
            return 0.2  # 高依赖 → 单 Agent
    
    def score_scalability(self, req):
        """评估扩展性需求"""
        scale = req.get("expected_scale", "low")
        
        if scale == "high":
            return 0.8  # 高扩展需求 → 多 Agent
        elif scale == "medium":
            return 0.5
        else:
            return 0.2  # 低扩展需求 → 单 Agent
    
    def score_latency(self, req):
        """评估延迟要求"""
        sla = req.get("latency_sla", 10)
        
        if sla < 1:
            return 0.2  # 极低延迟 → 单 Agent
        elif sla < 5:
            return 0.5
        else:
            return 0.8  # 延迟要求不高 → 多 Agent
    
    def score_cost(self, req):
        """评估成本预算"""
        budget = req.get("budget", "medium")
        
        if budget == "low":
            return 0.2  # 低预算 → 单 Agent
        elif budget == "medium":
            return 0.5
        else:
            return 0.8  # 高预算 → 多 Agent
    
    def _make_decision(self, weighted_score, individual_scores):
        """基于得分做出决策"""
        if weighted_score >= 0.6:
            recommendation = "multi_agent"
            reason = "综合得分高，建议使用多 Agent 架构"
        elif weighted_score <= 0.3:
            recommendation = "single_agent"
            reason = "综合得分低，建议使用单 Agent 架构"
        else:
            recommendation = "hybrid"
            reason = "综合得分中等，建议使用混合架构"
        
        return {
            "recommendation": recommendation,
            "reason": reason,
            "weighted_score": round(weighted_score, 2),
            "individual_scores": {k: round(v, 2) for k, v in individual_scores.items()},
            "suggestions": self._get_suggestions(individual_scores)
        }
    
    def _get_suggestions(self, scores):
        """根据各项得分给出建议"""
        suggestions = []
        
        if scores["task_complexity"] > 0.7:
            suggestions.append("任务复杂，考虑使用多 Agent 分步骤处理")
        
        if scores["skill_diversity"] > 0.7:
            suggestions.append("技能多样，建议专业 Agent 分工")
        
        if scores["independence"] > 0.7:
            suggestions.append("任务独立，多 Agent 可并行处理")
        
        if scores["scalability"] > 0.7:
            suggestions.append("扩展性强，多 Agent 更易扩展")
        
        return suggestions
```

### 5.2 架构模式选择

```python
class ArchitecturePatternSelector:
    """
    架构模式选择器
    """
    
    PATTERNS = {
        "single_agent": {
            "description": "单 Agent 架构",
            "use_when": ["任务简单", "技能相似", "预算有限"],
            "example": "简单问答、单一技能任务"
        },
        "multi_agent_hierarchical": {
            "description": "层次化多 Agent",
            "use_when": ["有明确协调者", "任务分层"],
            "example": "主管 Agent + 专业 Agent"
        },
        "multi_agent_parallel": {
            "description": "并行多 Agent",
            "use_when": ["任务完全独立", "可并行处理"],
            "example": "并行搜索、并行分析"
        },
        "multi_agent_pipeline": {
            "description": "流水线多 Agent",
            "use_when": ["任务有依赖", "需顺序处理"],
            "example": "分析 → 推理 → 执行"
        },
        "multi_agent_debate": {
            "description": "辩论式多 Agent",
            "use_when": ["需要不同视角", "决策需要共识"],
            "example": "正方 Agent + 反方 Agent"
        }
    }
    
    def select_pattern(self, evaluation_result, requirements):
        """选择架构模式"""
        rec = evaluation_result["recommendation"]
        
        if rec == "single_agent":
            return self.PATTERNS["single_agent"]
        
        if rec == "multi_agent":
            # 进一步选择多 Agent 模式
            deps = requirements.get("task_dependencies", {})
            
            if self._is_pipeline(deps):
                return self.PATTERNS["multi_agent_pipeline"]
            elif self._is_parallel(requirements):
                return self.PATTERNS["multi_agent_parallel"]
            elif requirements.get("need_debate"):
                return self.PATTERNS["multi_agent_debate"]
            else:
                return self.PATTERNS["multi_agent_hierarchical"]
        
        # 混合模式
        return {
            "description": "混合架构",
            "use_when": ["单/多 Agent 混合使用"],
            "example": "核心单 Agent + 扩展专业 Agent"
        }
    
    def _is_pipeline(self, deps):
        """判断是否是流水线模式"""
        # 存在单向依赖链
        return len(deps) > 0
    
    def _is_parallel(self, req):
        """判断是否可以并行"""
        deps = req.get("task_dependencies", {})
        # 无依赖或依赖关系弱
        return len(deps) == 0 or sum(len(d) for d in deps.values()) < len(deps) * 0.3
```

def validate_architecture():

## 11. 总结

1. **核心评估维度**：任务复杂度、技能多样性、任务独立性、扩展性、延迟要求、成本
2. **决策原则**：简单任务 → 单 Agent；复杂多技能 → 多 Agent
3. **多 Agent 模式**：层次化（协调者）、并行（独立任务）、流水线（顺序依赖）、辩论（多视角）
4. **实施建议**：先单 Agent 验证，再根据需求演进到多 Agent
5. **关键考量**：避免过度设计，保持架构简洁，预留扩展空间

## 12. Shared State、Sharded State、Agent Team 和主子结构的区别

面试里如果追问“shared-state、sharded-state、agent team、主子结构和你的方案到底有什么区别”，核心是区分**状态组织方式**和**Agent 组织方式**。它们不是同一个维度。

| 模式 | 核心定义 | 优点 | 风险 | 适用场景 |
| --- | --- | --- | --- | --- |
| Shared State / Blackboard | 多个 Agent 读写同一个共享状态或黑板 | 信息集中，协作方便 | 并发覆盖、上下文污染、权限难控 | 多 Agent 共享证据、任务看板 |
| Sharded State | 按用户、任务、租户、领域或资源把状态分片 | 可扩展、隔离好、降低热点 | 跨分片查询和合并复杂 | 多用户、多租户、大规模任务 |
| Agent Team | 多个 Agent 平级或半平级协作，各有角色 | 并行和专业化强 | 沟通成本高、结果合并难 | 多方案评审、并行研究 |
| 主子结构 Supervisor-Worker | 主 Agent 拆任务，子 Agent 执行局部任务 | 主控清晰，便于收敛 | 子 Agent 幻觉或误汇报会污染主 Agent | 有明确分工的复杂任务 |
| 单主控状态机 + 工具/可选子任务 | 一个主 Agent 维护状态，子能力优先工具化 | 状态一致、可回放、成本低 | 主 Agent 上下文压力大 | 高耦合顺序任务、生产系统 |

更具体地说：

1. **Shared State** 是“大家看同一块白板”。它解决信息共享，但不天然解决谁能写、写冲突、版本回滚和错误事实污染。
2. **Sharded State** 是“状态怎么分区”。它关注扩展性和隔离，比如 `tenant_id/user_id/run_id` 分片，不代表一定是多 Agent。
3. **Agent Team** 是“组织结构”。它强调多个专家 Agent 分工协作，可能共享状态，也可能各自有独立上下文。
4. **主子结构** 是 Agent Team 的一种层级化形式。主 Agent 负责任务拆解和结果裁决，子 Agent 负责局部执行。
5. **单主控方案** 是尽量把可程序化能力变成工具，把不必要的子 Agent 去掉，只保留可验证、可限时、可并行的子任务。

如果要解释“我的设计和主子结构有什么区别”，可以这样说：

```text
我的方案不是让多个 Agent 平级讨论，也不是让子 Agent 拥有独立决策权。
主状态只在 SingleAgentRunner / Orchestrator 里维护，子能力优先做成工具或 workflow node。
如果确实需要子 Agent，它只是一个带输入 schema、输出 schema、deadline、budget 和只读权限的受控工具。
主 Agent 不直接相信子 Agent 的自然语言结论，而是根据证据、工具结果和验证器把结果写入 facts。
```

架构示意：

```text
User
 -> SingleAgentRunner
    -> RunState / Facts / Memory
    -> ToolRouter
       -> search_code()
       -> run_test()
       -> spawn_readonly_subagent(timeout, output_schema)
    -> StateReducer
    -> Verifier
```

这个设计和共享黑板的差异在于：共享状态不是任意 Agent 都能改，所有状态变更都经过 `StateReducer`；和 Agent Team 的差异在于：子 Agent 不是平级团队成员，而是主控可调用的受限执行单元；和 Sharded State 的差异在于：分片是存储和扩展策略，不是协作策略。

## 13. 主子模式下子 Agent 幻觉怎么办

主子模式最大的风险是：子 Agent 看起来完成了任务，但实际没有证据、误解了上下文、编造了工具结果，主 Agent 又把它的输出当事实继续推理。

原则是：**子 Agent 输出只能作为候选证据，不能直接进入最终事实表**。

可以从任务输入、执行权限、输出契约、主控校验四层控制。

### 13.1 限制子 Agent 的任务边界

子 Agent 的任务要小而具体：

```text
差：你帮我分析整个项目有没有问题。
好：只读以下 3 个文件，找出登录超时相关逻辑，输出函数名、行号、证据片段和不确定点。
```

输入中要明确：

1. 允许读取的资源范围。
2. 禁止执行的工具。
3. 期望输出 schema。
4. 成功标准和失败时如何返回。
5. deadline、最大工具调用次数和 token 预算。

### 13.2 子 Agent 输出必须结构化

不要让子 Agent 只返回一段自然语言总结。推荐输出：

```json
{
  "status": "completed",
  "claims": [
    {
      "claim": "登录超时由 token 过期时间解析错误导致",
      "evidence": [
        {"file": "src/auth/token.go", "line": 87, "quote": "parseExpiresAt(...)"}
      ],
      "confidence": 0.78
    }
  ],
  "unknowns": ["没有读取线上配置，无法确认生产 token_ttl"],
  "tools_used": ["read_file", "search_code"]
}
```

主 Agent 只接受带证据的 claim；没有证据的结论进入 `hypotheses`，不能进入 `facts`。

### 13.3 主控 Agent 做二次验证

主控校验可以包括：

1. **证据可读性验证**：文件、URL、日志行号是否存在。
2. **工具结果复核**：关键结论由主控重新读取原始工具结果。
3. **交叉验证**：高风险结论让另一个只读 reviewer 或规则检查器复核。
4. **约束检查**：子 Agent 是否越权访问、是否忽略用户限制。
5. **冲突检测**：多个子 Agent 结论不一致时，不合并成事实，转为待确认。
6. **低置信拒收**：置信度低、证据不足、无法复现的结论不进入主链路。

状态更新最好由确定性 reducer 控制：

```python
def reduce_subagent_result(state, result):
    for claim in result["claims"]:
        if not claim["evidence"]:
            state.hypotheses.append(claim)
            continue
        if not evidence_exists(claim["evidence"]):
            state.rejected_claims.append(claim)
            continue
        state.facts.append(claim)
    return state
```

### 13.4 高风险任务要加人工或规则门禁

以下场景不能只靠子 Agent：

1. 生产数据写入、删除、回滚。
2. 支付、订单、权限、安全策略变更。
3. 自动修改规则、skill、长期记忆。
4. 对外发送邮件、消息、合同或公告。
5. 无法通过工具验证的业务判断。

这些场景应要求主控 Agent 生成草稿、证据和风险说明，再由人工确认或规则系统审批。

面试回答模板：

```text
主子模式下我不会直接相信子 Agent 的自然语言结论。子 Agent 只是受控 worker，任务范围、工具权限、deadline、预算和输出 schema 都由主控给定。它必须返回结构化 claim、证据、置信度和 unknowns。主 Agent 收到后会做证据可读性验证、关键工具结果复核、冲突检测和约束检查，只有带证据且验证通过的 claim 才能进入 facts；没有证据的只能作为 hypothesis。高风险动作还要走人工审批或规则门禁。这样即使子 Agent 幻觉，也不会直接污染主状态或触发真实副作用。
```
