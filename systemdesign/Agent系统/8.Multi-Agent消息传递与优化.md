# Multi-Agent 消息传递机制与优化

## 1. 问题背景

Multi-Agent（多智能体）系统通过多个 Agent 协作完成复杂任务。Agent 之间需要高效、可靠地传递消息和协调工作。

```text
┌─────────────────────────────────────────────────────────────┐
│                                                             │
│  Multi-Agent 协作模式：                                     │
│                                                             │
│  Agent A ──消息──► Agent B                                 │
│      │                                                       │
│      └──► Agent C ──► Agent D                              │
│                                                             │
│  消息类型：指令、结果、状态、事件                          │
│  协调方式：点对点、发布订阅、共享黑板                      │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

---

## 2. 问题现象

| 现象 | 描述 |
|------|------|
| 消息丢失 | Agent 之间消息未送达 |
| 循环依赖 | Agent A 等待 B，B 等待 A |
| 消息风暴 | 大量 Agent 同时发送消息 |
| 顺序混乱 | 消息乱序到达 |
| 调试困难 | 消息链路不清晰 |

---

## 3. 影响范围

- 多 Agent 协作系统
- 分布式 AI 应用
- 复杂任务分解执行

## 4. 原因分析

### 4.1 消息传递模式

```text
┌─────────────────────────────────────────────────────────────┐
│                                                             │
│  消息传递模式对比：                                         │
│                                                             │
│  1. 点对点（P2P）                                         │
│     Agent A ──► Agent B                                     │
│     优点：直接、高效                                       │
│     缺点：N² 连接数，难扩展                                │
│                                                             │
│  2. 发布订阅（Pub/Sub）                                   │
│     Agent A ──► Topic ──► Agent B, C                      │
│     优点：解耦、易扩展                                     │
│     缺点：消息路由复杂                                     │
│                                                             │
│  3. 共享黑板（Blackboard）                                 │
│     ┌─────────────────────────────────┐                   │
│     │     共享状态空间                   │                   │
│     │  Agent A ←───────→ Agent B      │                   │
│     │         ↓                         │                   │
│     │     Agent C                       │                   │
│     └─────────────────────────────────┘                   │
│     优点：全局可见，便于协调                               │
│     缺点：竞争条件，性能瓶颈                               │
│                                                             │
│  4. 消息队列（Message Queue）                              │
│     Agent A ──► MQ ──► Agent B                             │
│     优点：异步、可靠                                       │
│     缺点：引入额外组件                                     │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 4.2 消息格式设计

class AgentMessage:
    """
    Agent 间消息格式
    """
    
    def __init__(self):

    def to_dict(self) -> dict:
        return {
            "sender": self.sender,
            "receiver": self.receiver,
            "type": self.msg_type,
            "content": self.content,
            "metadata": self.metadata,
            "timestamp": self.timestamp,
            "conversation_id": self.conversation_id,
            "reply_to": self.reply_to
        }

## 5. 解决方案

### 5.1 消息总线实现

```python
class MessageBus:
    """
    消息总线：Multi-Agent 通信中枢
    """
    
    def __init__(self):
        self.subscribers = {}     # topic -> [agent_ids]
        self.message_queue = Queue()
        self.routing_rules = {}
    
    def subscribe(self, agent_id: str, topic: str):
        """订阅主题"""
        if topic not in self.subscribers:
            self.subscribers[topic] = []
        self.subscribers[topic].append(agent_id)
    
    def publish(self, topic: str, message: AgentMessage):
        """发布消息"""
        for agent_id in self.subscribers.get(topic, []):
            self.deliver(agent_id, message)
    
    def send_direct(self, receiver: str, message: AgentMessage):
        """直接发送"""
        self.deliver(receiver, message)
```

### 5.2 Agent 通信协议

```python
class AgentProtocol:
    """
    Agent 通信协议
    """
    
    # 消息类型
    MSG_REQUEST = "request"
    MSG_RESPONSE = "response"
    MSG_NOTIFY = "notify"
    MSG_QUERY = "query"
    MSG_RESULT = "result"
    
    @staticmethod
    def create_request(sender, receiver, action, params):
        return AgentMessage(
            sender=sender,
            receiver=receiver,
            msg_type=AgentProtocol.MSG_REQUEST,
            content={"action": action, "params": params}
        )
    
    @staticmethod
    def create_response(sender, receiver, original_msg, result):
        return AgentMessage(
            sender=sender,
            receiver=receiver,
            msg_type=AgentProtocol.MSG_RESPONSE,
            content={"result": result},
            reply_to=original_msg.id
        )
```

### 5.3 消息优化策略

```python
class MessageOptimizer:
    """
    消息优化：减少通信开销
    """
    
    def __init__(self):
        self.compression = True
        self.batching = True
        self.caching = True
    
    def compress_message(self, message: AgentMessage) -> AgentMessage:
        """消息压缩"""
        if self.compression:
            message.content = compress_json(message.content)
            message.metadata["compressed"] = True
        return message
    
    def batch_messages(self, messages: list) -> list:
        """消息批量"""
        if self.batching and len(messages) > 1:
            return [self.create_batch_message(messages)]
        return messages
    
    def deduplicate(self, messages: list) -> list:
        """去重"""
        seen = set()
        unique = []
        for msg in messages:
            key = f"{msg.sender}:{msg.timestamp}"
            if key not in seen:
                seen.add(key)
                unique.append(msg)
        return unique
```

## 12. Google A2A 协议和自研消息设施怎么取舍

如果面试问“为什么不用 Google 的 A2A 协议，自己写一套设施”，不要直接说“自研更灵活”。更好的回答是先承认标准协议的价值，再说明项目约束。

A2A（Agent2Agent）的核心目标是让不同厂商、不同框架的 Agent 能互操作。公开规范里有几个重要抽象：

1. **Agent Card**：描述 Agent 身份、能力、技能、服务端点和认证要求。
2. **Task**：一次委派任务的核心单位，有 `submitted/working/completed/failed/canceled/input-required/auth-required` 等状态。
3. **Message**：Agent 间通信消息，用于发起任务、补充输入或传递状态。
4. **Artifact**：任务产物，例如文档、图片、结构化数据，和普通消息区分。
5. **Streaming / Push Notification**：长任务可以通过流式事件或 webhook 推送状态变化。
6. **Version / Auth**：协议版本、认证和授权要显式处理。

这些抽象对跨组织、跨平台协作很有价值。但在一个内部产品早期，直接全量采用标准协议也可能带来成本：

| 维度 | 直接用 A2A | 自研轻量设施 |
| --- | --- | --- |
| 互操作 | 跨框架、跨厂商更好 | 只服务内部系统 |
| 实现成本 | 要实现 Agent Card、Task、Artifact、版本、认证等完整语义 | 可以先覆盖当前链路 |
| 协议稳定性 | 跟随标准演进，兼容性要管理 | 内部字段可快速调整 |
| 业务状态 | 通用 Task 状态不一定覆盖内部审批、计费、风控、模型调度 | 可以贴合业务状态机 |
| 安全治理 | 标准提供基础模型，但仍需业务权限 | 可以直接接内部权限、审计、风控 |
| 生态收益 | 方便接第三方 Agent | 内部闭环收益更高 |

自研不是从零随便设计，应该吸收 A2A 的好抽象：

```text
AgentCard      -> 内部 Agent 能力注册表
Task           -> 内部 run/task 状态机
Message        -> 标准化请求和状态消息
Artifact       -> 结构化产物和对象存储引用
Streaming      -> SSE/WebSocket 进度事件
AuthRequired   -> 人工审批或 OAuth 授权状态
```

内部自研时至少要保留这些字段：

```json
{
  "message_id": "msg_123",
  "root_task_id": "root_1",
  "task_id": "task_2",
  "parent_task_id": "task_1",
  "context_id": "conv_1",
  "sender": "planner",
  "receiver": "search_agent",
  "type": "request",
  "parts": [{"type": "text", "text": "检索相关证据"}],
  "artifacts": [],
  "deadline_at": "2026-05-24T10:10:00+08:00",
  "budget": {"tool_calls": 10, "tokens": 30000},
  "metadata": {"trace_id": "trace_abc"}
}
```

可以这样解释取舍：

1. **早期内部闭环**：先自研轻量协议，把任务状态、权限、预算、trace 和内部工具调度跑通。
2. **保留标准映射**：字段设计尽量能映射到 A2A 的 Agent Card、Task、Message、Artifact，避免未来迁移困难。
3. **边界服务适配**：当需要和外部 Agent 互通时，在网关层做 A2A adapter，而不是把内部所有状态机强行改成 A2A。
4. **内部强约束优先**：计费、风控、审批、租户隔离、模型队列这些业务状态必须由内部系统控制。
5. **持续关注标准**：标准成熟、生态收益大于适配成本后，再逐步引入。

面试回答模板：

```text
我不会否定 Google A2A。A2A 的 Agent Card、Task、Message、Artifact、streaming 和 auth-required 这些抽象很适合跨厂商 Agent 互操作。但如果项目早期只在内部闭环运行，直接实现完整标准会引入版本、认证、产物模型和兼容成本，而且内部还有审批、计费、模型队列、租户隔离这些业务状态。

所以我会先自研一套轻量消息和任务设施，但字段设计参考 A2A：能力注册类似 Agent Card，run/task 状态机类似 Task，产物用 Artifact，进度用 SSE/WebSocket，授权用明确状态。等需要接第三方 Agent 时，在 gateway 做 A2A adapter。这样既能满足当前业务落地，又不会把未来互操作路径堵死。
```
