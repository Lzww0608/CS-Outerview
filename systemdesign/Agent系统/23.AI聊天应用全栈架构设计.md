# 23. AI 聊天应用全栈架构设计

面试里要求 50 分钟实现一个前后端全栈 AI 聊天应用，真正考察的不只是会不会调模型 API，而是能不能把前端交互、后端会话、模型调用、上下文管理、流式输出、存储、限流和可观测性串成一个可扩展系统。

## 1. 核心功能

最小可用版本：

1. 用户输入问题，前端显示用户消息和 AI 流式回答。
2. 后端保存会话、消息和一次生成 run 的状态。
3. 后端调用模型服务，支持 SSE 或 WebSocket 把 token 分片返回前端。
4. 支持停止生成、失败重试、历史会话查看。
5. 基础鉴权、限流、日志和错误处理。

生产版本还要补：

1. RAG 或工具调用。
2. 上下文压缩和历史摘要。
3. 敏感词、越权、Prompt Injection 防护。
4. 多模型路由、降级和成本统计。
5. Harness 评测和线上 badcase 回放。

## 2. 全栈链路

推荐链路：

```text
Frontend
  -> POST /chat/messages 创建用户消息和 run
  -> GET /chat/runs/{run_id}/events 订阅 SSE
API Service
  -> 鉴权、限流、参数校验
  -> Conversation Service 保存消息
  -> Context Builder 组装历史、摘要、RAG 证据
  -> Model Gateway 调用模型流式接口
  -> Stream Gateway 推送 token
  -> Message Store 落最终答案和用量
```

前端职责：

1. 输入框、消息列表、Markdown/代码块渲染。
2. SSE/WebSocket 流式接收和增量渲染。
3. `AbortController` 或关闭连接，实现停止生成。
4. 会话列表、重试、复制、重新生成。
5. 对 `run_id` 做隔离，旧 run 的迟到 token 不能写到新回答里。

后端职责：

1. 管理 `conversation_id/message_id/run_id`。
2. 组装上下文，控制 token 预算。
3. 封装模型 API，统一超时、重试、降级和用量统计。
4. 流式转发模型输出，处理前端断开和取消。
5. 持久化消息、运行状态、错误和 trace。

## 3. 数据模型

可以用关系型数据库保存会话元数据和消息，用对象存储保存大附件，用向量库保存知识库索引。

核心表：

```sql
CREATE TABLE conversations (
    id BIGINT PRIMARY KEY,
    user_id BIGINT NOT NULL,
    title VARCHAR(128),
    summary TEXT,
    created_at DATETIME NOT NULL,
    updated_at DATETIME NOT NULL
);

CREATE TABLE messages (
    id BIGINT PRIMARY KEY,
    conversation_id BIGINT NOT NULL,
    role VARCHAR(16) NOT NULL,
    content TEXT NOT NULL,
    run_id BIGINT,
    created_at DATETIME NOT NULL,
    INDEX idx_conv_time (conversation_id, created_at)
);

CREATE TABLE chat_runs (
    id BIGINT PRIMARY KEY,
    conversation_id BIGINT NOT NULL,
    user_message_id BIGINT NOT NULL,
    status VARCHAR(32) NOT NULL,
    model VARCHAR(64),
    prompt_tokens INT DEFAULT 0,
    completion_tokens INT DEFAULT 0,
    error_code VARCHAR(64),
    created_at DATETIME NOT NULL,
    updated_at DATETIME NOT NULL
);
```

状态流转：

```text
CREATED -> RUNNING -> SUCCEEDED
                  -> CANCELLING -> CANCELLED
                  -> FAILED
```

## 4. SSE 和 WebSocket 怎么选

AI 聊天的模型输出通常是服务端到客户端的单向 token 流，SSE 足够简单：

1. 浏览器原生支持 `EventSource`。
2. 复用 HTTP 鉴权、代理和网关能力。
3. 自动重连和事件 ID 比较方便。

如果需要客户端和服务端在同一连接上高频双向通信，例如多人协同、实时语音、工具执行过程交互，可以选 WebSocket。

生产上常见做法是：普通 AI 回答用 SSE，聊天输入仍走普通 HTTP POST；更复杂的实时协作再引入 WebSocket。

## 5. 大规模使用时后端怎么处理

大规模 AI 聊天的瓶颈通常在模型吞吐、上下文构建、长连接、数据库写入和成本。

处理思路：

1. **API 无状态化**：会话和 run 状态落 DB/Redis，API 实例可水平扩展。
2. **模型网关**：统一模型路由、限流、重试、降级、超时和成本统计。
3. **流式网关隔离**：SSE/WebSocket 连接占用时间长，和普通 API 分开部署。
4. **异步任务化**：长工具调用、RAG 入库、文件解析、总结任务进入队列。
5. **上下文压缩**：历史对话过长时滚动摘要，只保留最近消息和关键事实。
6. **缓存和复用**：Embedding、RAG 召回、系统 prompt、用户 profile 可以缓存。
7. **限流和配额**：按用户、租户、模型、IP、并发 run 数做限流。
8. **落库削峰**：token 不必每片都写库，内存聚合后按 run 终态或固定间隔批量落库。
9. **可观测性**：记录 trace_id、run_id、模型延迟、首 token 延迟、总 token、错误码和取消率。

## 6. 按分层架构水平扩展

可以按访问链路一层层讲：

1. **接入层**：DNS/CDN/L4/L7 负载均衡分发流量，静态资源走 CDN，网关做鉴权、限流、灰度。
2. **API 层**：服务无状态，按 QPS 水平扩容；连接池、线程池和下游超时要隔离。
3. **流式连接层**：SSE/WebSocket 网关单独扩容，维护连接和 `run_id -> connection` 映射。
4. **业务服务层**：Conversation、Billing、RAG、Tool、Moderation 拆成独立服务，按瓶颈扩容。
5. **模型网关层**：根据模型、租户和任务类型路由到不同供应商或自部署推理集群。
6. **异步任务层**：文件解析、向量化、总结、工具长任务进入 MQ，由 worker pool 消费。
7. **数据层**：MySQL 保存强一致元数据，Redis 保存短期状态和限流计数，向量库保存知识索引，对象存储保存附件。
8. **日志观测层**：日志、指标、Trace 独立管道采集，避免业务请求同步等待日志落盘。

## 7. 单服务器怎么提高性能

单机优化要先定位瓶颈，再分别处理 CPU、I/O、连接、内存和下游。

1. 使用异步 I/O 或事件驱动处理 SSE，避免一连接一线程。
2. 模型流式返回时边读边写，减少整段回答缓存。
3. 数据库和模型客户端使用连接池，设置超时和最大并发。
4. 请求队列、日志队列、输出缓冲区都要有上限和背压。
5. JSON 序列化、Markdown 处理、敏感词检测等 CPU 热点要避免重复执行。
6. 历史消息按窗口拉取，不要每次把整段会话全读入内存。
7. 日志异步批量写，避免每个 token 或每个 chunk 同步刷盘。
8. 对相同系统提示词、用户配置、RAG 召回结果做缓存。

## 8. 易错点

1. 前端停止展示不代表后端停止生成，必须有 `cancel(run_id)` 和后端 cancellation token。
2. 旧 run 的迟到 token 不能污染新 run，要用 `run_id/generation` 校验。
3. 不能把所有历史对话都塞进 prompt，长会话要摘要和裁剪。
4. 模型 API 超时和前端连接断开要分开处理。
5. 日志里不要记录完整用户隐私、密钥或未脱敏 prompt。
6. 流式接口不能套普通短请求超时，否则长回答会被误断开。
7. 只做 Demo 不做限流，容易被单用户并发请求打爆模型额度。

## 9. 面试回答模板

我会把 AI 聊天应用拆成前端、API、会话服务、上下文构建、模型网关、流式网关和存储几层。前端负责消息渲染、SSE/WebSocket 接收、停止生成和会话切换；后端用 `conversation_id/message_id/run_id` 管理状态，保存用户消息后构建上下文，通过模型网关调用流式接口，再把 token 推给前端并在结束时落库。大规模场景下 API 无状态化水平扩容，SSE 网关和普通 API 分开部署，模型网关做限流、降级和多模型路由，长任务进入 MQ，MySQL 保存元数据，Redis 做短期状态、限流和缓存，向量库做 RAG。单机优化重点是异步 I/O、有界队列、连接池、批量日志、上下文裁剪和背压。
