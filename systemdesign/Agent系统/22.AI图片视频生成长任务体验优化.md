# AI 图片视频生成长任务体验优化

图片、视频生成类 AI 产品的核心矛盾是：模型推理和后处理可能持续数秒到数分钟，但用户希望系统有即时反馈、可中断、可恢复、结果可追踪。面试里问“生成图片和视频需要长时间，怎么减少用户等待”，不要只回答“用异步”，要从链路、模型、调度、前端体验和状态可靠性一起说。

## 1. 问题本质

AI 图片/视频生成通常包含：

```text
用户输入 prompt
-> 安全审核和参数校验
-> 模型选择和资源排队
-> 文生图 / 图生图 / 文生视频推理
-> 后处理、超分、补帧、转码、水印
-> 对象存储和 CDN
-> 状态通知和结果展示
```

慢的原因主要有：

1. **GPU 推理耗时**：视频比图片更慢，时长、分辨率、帧率都会放大计算量。
2. **排队耗时**：高峰期 GPU worker 不够，任务在队列里等待。
3. **后处理耗时**：超分、去噪、补帧、转码、封面生成、内容安全复审都可能很慢。
4. **文件传输耗时**：图片/视频结果需要上传对象存储，再分发到 CDN。
5. **安全和权限链路**：敏感 prompt、版权素材、未成年人保护等需要审核。

所以优化目标不是让所有任务都同步变快，而是：

1. 用户尽快看到系统已接收任务。
2. 用户能看到真实进度或阶段状态。
3. 小任务尽量快路径返回，大任务可靠后台执行。
4. 任务可取消、可恢复、可通知。
5. 失败可解释，不让用户长时间空等。

## 2. 推荐架构

推荐把生成请求拆成同步控制面和异步执行面：

```text
Client
-> API Gateway / BFF
-> GenerateTaskService
   -> Prompt Moderation
   -> Task DB
   -> Queue / Scheduler
-> GPU Worker Pool
   -> Model Runtime
   -> Post Processor
   -> Object Storage / CDN
-> Progress Service
   -> SSE / WebSocket / Push / Polling
```

一次请求流程：

```text
POST /generations
-> 校验用户、额度、prompt、参数
-> 创建 task_id，状态 SUBMITTED
-> 投递 MQ / GPU 调度队列
-> 立即返回 task_id 和预计等待时间
-> 前端通过 SSE/WebSocket/轮询订阅进度
-> worker 执行并持续更新状态
-> 完成后返回 artifact URL、缩略图、种子和参数
```

任务状态机可以设计为：

```text
SUBMITTED -> QUEUED -> RUNNING -> POST_PROCESSING -> SUCCEEDED
                                 -> FAILED
                                 -> CANCELED
                                 -> EXPIRED
```

核心字段：

| 字段 | 作用 |
| --- | --- |
| `task_id` | 用户查询和幂等追踪 |
| `user_id` / `tenant_id` | 权限、计费、限流 |
| `idempotency_key` | 防止重复提交 |
| `status` | 当前任务状态 |
| `queue_position` | 排队位置或估算等待 |
| `progress_stage` | `审核中/排队中/生成中/后处理中/完成` |
| `model` / `quality` | 选择的模型和质量档位 |
| `seed` / `params_hash` | 复现和缓存 |
| `artifact_urls` | 结果图片、视频、封面、缩略图 |
| `error_code` / `error_message` | 失败解释和重试依据 |

## 3. 减少等待的工程手段

### 3.1 快速确认和异步任务

同步请求只做轻量校验和任务创建，不在 HTTP 请求里等待完整生成。这样前端能在几十到几百毫秒内拿到 `task_id`。

```json
{
  "task_id": "gen_123",
  "status": "QUEUED",
  "estimated_wait_seconds": 42,
  "events_url": "/generations/gen_123/events"
}
```

注意：异步不是“丢到后台就完了”。任务必须持久化、可查询、可取消、可重试，并且 worker 重启后能恢复或标记失败。

### 3.2 流式进度和阶段反馈

对用户感知最重要的是“系统在动”。可以通过 SSE 或 WebSocket 推送：

```text
event: status
data: {"status":"RUNNING","stage":"generating","progress":35}

event: preview
data: {"thumbnail_url":"https://cdn/preview_1.webp"}

event: done
data: {"image_url":"https://cdn/final.png"}
```

适用选择：

| 方式 | 适用场景 | 注意事项 |
| --- | --- | --- |
| 轮询 | 简单结果查询、低频任务 | 轮询间隔要退避，避免打爆服务 |
| SSE | 大模型 token、进度、日志、单向推送 | 代理要关闭缓冲，处理断线重连 |
| WebSocket | 双向交互、取消、多人协作看板 | 要维护连接路由、心跳和重连 |
| Push/站内信 | 用户离开页面后的完成通知 | 需要任务状态可持久查询 |

### 3.3 分阶段结果和渐进式预览

图片/视频生成可以先给低成本中间结果：

1. 图片先出低分辨率草图，再做高清重绘或超分。
2. 视频先出首帧、分镜图或低帧率预览，再生成完整视频。
3. 长视频按片段生成，先展示已完成片段。
4. 先返回封面和 ETA，最终结果完成后替换。

这不会减少真实总耗时，但会显著降低用户感知等待。

### 3.4 模型路由和质量档位

不要所有请求都走最慢模型。可以根据用户需求和额度路由：

| 档位 | 策略 | 场景 |
| --- | --- | --- |
| 快速草稿 | 小模型、低分辨率、少步数 | prompt 试错、预览 |
| 标准生成 | 默认模型和参数 | 普通用户请求 |
| 高清精修 | 大模型、超分、更多采样步 | 付费用户、最终产物 |
| 批量后台 | 低优先级队列 | 批量素材生成 |

用户体验上可以提供“先出草稿，满意后高清生成”的流程，减少用户对慢模型的无效等待。

### 3.5 缓存、复用和预热

可缓存的内容包括：

1. 相同 prompt、相同参数、相同模型版本的生成结果。
2. 常用风格、模板、LoRA、ControlNet 等模型组件的加载状态。
3. 热门 prompt 的示例结果。
4. 视频转码后的多清晰度切片和封面图。

缓存 key 要包含：

```text
model_version + prompt_hash + negative_prompt_hash + seed + size + steps + style + safety_version
```

易错点是缓存污染：模型版本、审核策略、用户权限或版权策略变化后，旧缓存不一定还能直接复用。

### 3.6 GPU 调度和队列优化

后端要把用户等待拆成 `queue_wait` 和 `run_time` 两类指标。

优化方向：

1. 按任务类型分队列：图片、短视频、长视频、高清后处理分开。
2. 按优先级调度：交互式任务优先于批量任务，付费任务可有更高权重。
3. 微批处理：相同模型和相近分辨率的请求合批，提高 GPU 利用率。
4. 模型常驻和预加载：减少冷启动和权重加载。
5. 自动扩缩容：队列长度、等待时间和 GPU 利用率触发扩容。
6. 限流和排队保护：避免无限接单导致 ETA 失真。

## 4. 取消、重试和失败处理

用户可能在生成中修改 prompt 或点击取消。取消要分层处理：

```text
Client cancel(task_id)
-> Task DB 标记 CANCELLING
-> Scheduler 不再调度未开始任务
-> Running worker 检查 cancellation token
-> 可中断则停止，不可中断则完成后丢弃结果或不计费
-> 状态改为 CANCELED
```

重试要区分：

1. **可自动重试**：GPU worker 临时失败、对象存储上传失败、转码服务超时。
2. **不应自动重试**：prompt 审核失败、用户额度不足、参数非法。
3. **用户可重试**：模型生成失败、结果不满意、网络中断。

失败后要返回可理解状态：

```json
{
  "status": "FAILED",
  "error_code": "MODEL_TIMEOUT",
  "retryable": true,
  "message": "生成服务超时，可以稍后重试或切换快速模式"
}
```

## 5. 真实场景应用

以通用 AI 助手类产品的图片/视频生成为例，可以这样回答：

1. 请求进来先做鉴权、额度、prompt 安全和参数校验。
2. 创建生成任务并立即返回 `task_id`，前端进入生成中页面。
3. 任务进入队列，由调度器选择图片或视频 GPU worker。
4. 前端通过 SSE 接收 `排队中/生成中/后处理中/完成` 状态。
5. 图片先出低清预览，视频先出封面或短片段预览。
6. 结果写对象存储，CDN 分发，任务表保存 artifact URL。
7. 用户离开页面后，完成结果通过站内信、Push 或历史记录展示。
8. 失败进入可重试或死信链路，后台记录 trace 和错误码。

## 6. 易错点

1. 不要在一个 HTTP 请求里同步等待长视频生成完成。
2. 不要只给“加载中”动画，要给阶段状态、预计等待或排队位置。
3. 不要让前端状态成为唯一状态源，任务状态必须以后端持久化为准。
4. 不要无限重试 GPU 任务，失败要分类、限次和进入死信。
5. 不要把用户取消只做成前端关闭页面，后端任务也要标记和清理。
6. 不要缓存未通过安全复审的结果。
7. 不要让低优先级批量任务挤占交互式生成队列。
8. 不要把进度百分比伪造成精确值，模型生成很多阶段只能给阶段性进度或 ETA 估算。

## 7. 评估指标

| 指标 | 含义 |
| --- | --- |
| `submit_latency_p95` | 提交请求到拿到 task_id 的延迟 |
| `queue_wait_p95` | 排队等待时间 |
| `generation_time_p95` | 模型真实生成耗时 |
| `first_preview_latency` | 首个预览出现时间 |
| `completion_rate` | 任务成功完成比例 |
| `cancel_rate` | 用户取消比例 |
| `retry_success_rate` | 重试后成功比例 |
| `gpu_utilization` | GPU 利用率 |
| `cost_per_artifact` | 单个结果成本 |
| `user_perceived_wait` | 用户感知等待时间，可由页面停留和反馈估算 |

## 8. 面试回答模板

图片和视频生成耗时长，我会把它设计成长任务系统，而不是同步接口。请求链路里只做鉴权、额度、prompt 审核和参数校验，然后创建 `task_id`、落库、投递队列并快速返回。后端用 GPU worker 异步生成，任务状态从 `SUBMITTED/QUEUED/RUNNING/POST_PROCESSING` 流转到 `SUCCEEDED/FAILED/CANCELED`，前端通过 SSE 或 WebSocket 获取阶段进度和预览结果。

降低等待感可以从几方面做：第一，快速返回任务 ID 和 ETA；第二，流式推送进度、首帧、缩略图或低清预览；第三，模型路由，草稿走快模型，高清精修走慢模型；第四，缓存相同参数结果、预热模型和常驻热门模型；第五，队列按任务类型和优先级隔离，交互式任务不要被批量任务挤占；第六，用户离开页面后通过历史记录或通知接回结果。工程上还要支持取消、幂等、重试、死信、对象存储、CDN、审核复审和完整 trace。
