# 4. Agent 会话全链路与天气 Agent

Agent 工程落地不能只说“调用大模型”。一次会话请求从用户发出到模型返回，通常会经过接入层、会话层、上下文层、模型编排层、工具层、流式返回和可观测闭环。

## 1. 一次会话请求的全链路

典型链路：

```text
Client
-> Gateway / BFF
-> Auth & RateLimit
-> ConversationService
-> ContextBuilder
-> AgentOrchestrator
-> LLM Planner / ReAct Loop
-> ToolRouter / Retriever / Business API
-> ResponseGenerator
-> SSE/WebSocket Stream
-> Trace / Metrics / Feedback
```

每层关注点不同：

1. **Client**：发送用户输入、会话 ID、设备信息、定位授权状态、端上上下文。
2. **Gateway/BFF**：鉴权、限流、灰度、trace id、请求规范化。
3. **ConversationService**：创建或读取 `conversation_id`、`message_id`、`run_id`，持久化用户消息。
4. **ContextBuilder**：读取用户画像、短期对话摘要、长期记忆、权限、端上传来的结构化上下文。
5. **AgentOrchestrator**：决定走普通聊天、RAG、ReAct、固定 Workflow 还是工具调用。
6. **LLM Planner**：生成下一步 action 或最终回答草稿。
7. **ToolRouter**：校验工具名、参数、权限、超时和风险等级，调用真实业务工具。
8. **ObservationProcessor**：把工具返回转成模型可用事实，裁剪敏感信息和冗余字段。
9. **ResponseGenerator**：基于证据生成最终回答，必要时带引用、时间戳、假设说明。
10. **StreamService**：通过 SSE 或 WebSocket 流式返回 token、工具状态和最终消息。
11. **TraceStore**：记录 prompt hash、工具调用、latency、token、错误码和引用，用于排障和评测。

## 2. 关键类和流转信息

可以用下面这些类解释工程实现：

```text
ChatRequest
  user_id
  conversation_id
  message
  client_context
  request_id

ConversationContext
  recent_messages
  user_profile
  location_context
  permissions
  memories

AgentRun
  run_id
  state
  step_count
  tool_calls
  trace_id

ToolCall
  tool_name
  arguments
  result
  error_code
  latency_ms

AgentResponse
  answer
  citations
  assumptions
  tool_trace_summary
```

一次请求里，`request_id/trace_id` 用于日志串联，`conversation_id` 用于多轮上下文，`run_id` 用于本次模型执行，`message_id` 用于消息幂等和回放，`tool_call_id` 用于追踪每次工具调用。

## 3. ReAct 和普通聊天的本质区别

普通大模型聊天通常是：

```text
user message + history -> LLM -> answer
```

ReAct 是：

```text
user goal
-> Reason: 判断缺什么信息
-> Act: 调用工具
-> Observe: 读取工具结果
-> Reason: 基于结果决定继续工具还是回答
-> Final Answer
```

本质区别：

1. **普通聊天依赖模型已有知识和上下文**，适合闲聊、总结、简单问答。
2. **ReAct 允许模型通过工具获取外部事实**，适合实时数据、业务系统、检索、排障。
3. **ReAct 是多步状态机**，需要最大步数、工具权限、参数校验、trace 和失败恢复。
4. **普通聊天的输出是答案**，ReAct 的中间产物还包括 action、observation 和状态更新。

生产环境里通常不会把完整 thought 暴露给用户，而是保存内部 trace，对用户展示工具状态和结论来源。

## 4. 天气问答 Agent 的模块设计

天气 Agent 不能让模型凭记忆编天气。它应该把天气查询做成受控工具调用。

核心模块：

| 模块/类 | 职责 |
| --- | --- |
| `WeatherAgentController` | 接收 HTTP/SSE 请求，创建 run |
| `ConversationService` | 管理对话消息和上下文摘要 |
| `IntentClassifier` | 判断是否为天气、穿衣、出行建议等意图 |
| `LocationResolver` | 从端参、用户资料、IP、历史偏好解析城市 |
| `WeatherTool` | 调用天气 API，返回结构化天气数据 |
| `ToolRouter` | 校验工具参数、权限、超时、重试 |
| `PromptBuilder` | 把天气数据、定位来源、时间戳注入模型上下文 |
| `ResponseGenerator` | 生成自然语言回答和建议 |
| `TraceLogger` | 记录定位来源、工具调用、耗时、错误 |

一个 ReAct 流程：

```text
用户：“天气怎么样”
-> IntentClassifier: weather_query
-> LocationResolver: city=杭州, source=client_gps, confidence=0.92
-> WeatherTool.get_current_weather(city=杭州)
-> Observation: 温度、天气、降雨概率、风力、更新时间
-> LLM: 生成回答，说明“按你当前定位杭州”
```

如果定位缺失或置信度低，可以选择：

1. 反问用户城市。
2. 用用户常驻城市或最近一次定位，并在回答里说明假设。
3. 用 IP 粗定位做低置信兜底。
4. 对隐私敏感场景直接要求用户授权定位。

## 5. 不靠大模型反问，如何拿地理位置

工程上拿地理位置不应该只依赖模型追问，常见来源包括：

1. **端上 GPS/系统定位**：App 经用户授权后上传经纬度或城市编码。
2. **用户资料**：注册城市、常驻城市、收货地址、门店城市。
3. **IP Geo**：根据 IP 粗定位到城市，适合兜底，精度有限。
4. **设备/请求上下文**：App locale、时区、运营区域、站点域名。
5. **历史会话偏好**：用户曾说“我在北京”，但要有 TTL 和置信度。
6. **业务场景上下文**：外卖、打车、同城业务已有当前位置或服务城市。
7. **前端页面参数**：城市选择器、URL query、cookie、local storage 同步到请求。

这些来源要做优先级和置信度：

```text
显式用户输入 > 端上 GPS > 当前业务城市 > 用户资料 > 最近历史定位 > IP 粗定位
```

隐私注意点：

1. 定位必须遵守用户授权和最小化原则。
2. Prompt 中尽量注入城市级信息，不注入精确经纬度，除非业务确实需要。
3. trace 和日志要脱敏，不记录不必要的精确位置。
4. 定位上下文要有来源、时间戳、置信度和过期策略。

## 6. 后端如何提取并无感注入定位

后端不要让模型从自然语言里猜所有参数，而是把结构化上下文在进入模型前补齐。

### 请求协议

端上可以随请求传：

```json
{
  "message": "天气怎么样",
  "client_context": {
    "location": {
      "lat": 30.2741,
      "lng": 120.1551,
      "city_code": "330100",
      "city_name": "杭州",
      "source": "gps",
      "accuracy_m": 80,
      "timestamp": "2026-05-04T10:00:00+08:00"
    },
    "timezone": "Asia/Shanghai",
    "locale": "zh-CN",
    "device": "ios"
  }
}
```

### 后端处理流程

```text
Controller 接收请求
-> AuthContext 解析 user_id、tenant、权限
-> ClientContextExtractor 解析 location/timezone/locale
-> LocationResolver 做优先级选择、TTL 校验、逆地理编码
-> 写入 ConversationContext.location_context
-> Tool 参数填充：WeatherTool(city_code)
-> Prompt 注入城市、来源、更新时间和置信度摘要
```

注入给模型的内容应该是摘要，而不是原始敏感字段：

```text
用户定位上下文：
- 当前城市：杭州
- 来源：端上 GPS 授权定位
- 定位时间：2026-05-04 10:00
- 置信度：高
回答天气问题时默认使用该城市；如果用户明确指定其他城市，以用户输入为准。
```

工具调用参数则使用结构化字段：

```json
{
  "tool_name": "get_weather",
  "arguments": {
    "city_code": "330100",
    "date": "today"
  }
}
```

## 7. 易错点

1. 不要把定位信息只拼在用户自然语言里，应该进入结构化上下文和工具参数。
2. 不要让模型决定是否有权限使用定位，权限由后端确定性逻辑判断。
3. IP 定位只能兜底，不能和 GPS 同等置信。
4. 用户显式说“查上海天气”时，显式输入优先于端上当前位置。
5. 天气工具返回要带更新时间和数据源，避免模型把旧数据说成实时。
6. 工具失败时要降级说明，不要编造天气。

## 8. 面试回答模板

一次 Agent 会话请求会先经过网关鉴权、限流和 trace，再进入会话服务保存消息、构建上下文，然后由 Agent 编排层决定走普通聊天、RAG 还是 ReAct。ReAct 和普通聊天的区别是它会在“推理 -> 工具调用 -> 观察结果”之间循环，工具结果会反过来影响下一步，不是只靠模型参数回答。天气 Agent 我会拆成意图识别、定位解析、天气工具、工具路由、Prompt 构建、回答生成和 trace 记录。用户只说“天气怎么样”时，后端可以从端上 GPS、用户资料、业务城市、历史偏好或 IP 粗定位拿城市；端上传来的定位参数由 `ClientContextExtractor` 解析，经 `LocationResolver` 校验 TTL、来源和置信度后写入结构化上下文，并作为 `WeatherTool` 的参数无感注入给模型。权限、脱敏和优先级由后端控制，模型只消费摘要和工具结果。
