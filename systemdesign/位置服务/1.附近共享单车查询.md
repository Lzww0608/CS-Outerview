# 附近共享单车查询

题目是：给定一个坐标，找出 1 公里内所有共享单车的位置。核心不是简单遍历全量单车，而是用空间索引把候选集合缩小，再做精确距离过滤。

## 1. 需求拆解

查询输入：

```text
lat, lng, radius = 1000m
```

输出通常包括：

1. 单车 id。
2. 经纬度。
3. 距离。
4. 可用状态、电量、车型等业务字段。

关键约束：

1. 单车位置高频更新。
2. 查询半径小，通常是 500m、1km、3km。
3. 用户只需要附近可用车辆，不需要全量精确排序。
4. 热点区域请求量高，要支持缓存和限流。

## 2. 空间索引方案

常见方案有三类：

| 方案 | 原理 | 适用场景 |
| --- | --- | --- |
| GeoHash | 把经纬度编码成字符串，前缀相同表示空间邻近 | 工程简单，适合 Redis GEO 或自建网格 |
| 网格索引 | 按固定经纬度/米级网格切分，坐标映射到 cell | 高可控、易分片，适合自研位置服务 |
| R-Tree | 用矩形边界组织空间对象 | 空间数据库、复杂多边形查询 |

共享单车这类点查询，最常用是 GeoHash/网格索引。

## 3. 查询流程

以网格或 GeoHash 为例：

```text
1. 把用户坐标映射到中心格子
2. 根据 1km 半径计算需要覆盖的周边格子
3. 从这些格子取出候选单车 id
4. 批量读取单车最新位置和状态
5. 用 Haversine 公式或近似平面距离做精确过滤
6. 按距离排序，返回前 N 辆
```

必须查周边格子，因为用户可能位于格子边缘，只查中心格会漏掉相邻格中很近的车辆。

## 4. 距离计算

精确计算可以用 Haversine：

```text
d = 2R * asin(sqrt(
    sin^2((lat2-lat1)/2) +
    cos(lat1)*cos(lat2)*sin^2((lng2-lng1)/2)
))
```

工程上可以先用矩形边界框做粗过滤，再对候选集算球面距离：

1. 纬度 1 度约 111km。
2. 经度 1 度约 `111km * cos(latitude)`。
3. 先筛 `[lat - deltaLat, lat + deltaLat]` 和 `[lng - deltaLng, lng + deltaLng]`。
4. 再计算真实距离，过滤超过 1km 的点。

## 5. 数据存储

一种可落地架构：

1. **Redis GEO / Redis ZSET**：存热点城市、热点区域的实时坐标索引。
2. **MySQL / HBase / Cassandra**：存单车元信息、状态、轨迹归档。
3. **位置更新流**：单车上报位置后写入 MQ，位置服务消费并更新空间索引。
4. **分片键**：按城市 + GeoHash 前缀或网格 id 分片，避免全国数据落到一个索引。

Redis GEO 底层使用 geohash 编码到有序集合，适合快速做 `GEOSEARCH`/`GEORADIUS` 类附近查询。规模更大时，可按城市和 geohash 前缀拆 key。

## 6. 一致性和异常

1. 单车位置不是强一致需求，秒级最终一致通常可以接受。
2. 查询结果要过滤不可用、维修、低电量、已被预约的车辆。
3. 位置上报延迟时，要根据 `last_update_time` 过滤过期位置。
4. 热点区域可以缓存查询结果几十秒，但要注意车辆状态变化。
5. 司机/运维后台和用户端查询可以使用不同精度和不同数据源。

## 7. 面试回答模板

我会用空间索引而不是全表扫描。把单车经纬度映射成 GeoHash 或网格 id，位置更新时维护“网格 -> 单车集合”的索引。用户查询 1 公里内车辆时，先计算中心格和周边格，取出候选单车，再批量查最新状态，用 Haversine 或近似距离做精确过滤，最后按距离排序返回。存储上热点实时位置可以放 Redis GEO/ZSET，权威状态和历史轨迹落 MySQL/HBase/Cassandra；分片按城市和 GeoHash 前缀做。要注意边界格不能漏查、过期位置要过滤、状态最终一致和热点区域限流缓存。
