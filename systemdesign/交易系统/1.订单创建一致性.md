# 1. 订单创建一致性

订单创建链路经常会协调库存、优惠券、风控、价格、支付等下游服务。它的难点不是单个 SQL 事务，而是本地订单数据、下游资源占用和异步消息之间的一致性。

## 核心原则

1. **本地事务只覆盖订单服务自己的数据**：订单主表、订单明细、操作流水、本地消息表在同一个事务中提交。
2. **跨服务使用最终一致**：下游动作通过冻结、确认、取消、补偿、重试来推进。
3. **订单状态机驱动流程**：例如 `INIT -> WAIT_PAY -> PAID -> FINISHED`，失败时进入 `CANCELLED` 或 `CLOSE_PENDING`。
4. **所有外部调用都要幂等**：库存扣减、优惠券锁定、支付单创建都要绑定 `order_id` 或业务流水号。

## 典型流程

1. 下单前执行参数、库存、价格、风控、优惠券等前置校验。
2. 订单服务开启本地事务，创建订单、订单明细、操作流水，并写入 outbox 事件。
3. 本地事务提交后，异步发送 `order_created` 消息。
4. 库存、优惠券等下游消费消息，执行冻结或确认动作。
5. 如果某一步失败，订单进入可补偿状态，由补偿任务重试或取消订单并释放资源。

## 创单失败或调用下游失败怎么处理

1. **创单前失败**：不生成有效订单，必要时记录失败流水，直接返回。
2. **订单 DB 事务失败**：订单和 outbox 消息一起回滚，下游不会收到成功事件。
3. **DB 成功但消息发送失败**：outbox 事件仍在库中，后台任务或 CDC 继续投递。
4. **下游消费失败**：MQ 重试，超过阈值进入死信队列；订单补偿任务根据状态重新推进。
5. **部分下游成功、部分失败**：使用 Saga 补偿。例如库存已冻结但优惠券锁定失败，则取消订单并释放库存。

## 易错点

1. 不要在一个数据库事务里等待多个远程 RPC 返回，事务时间过长会导致锁竞争和故障放大。
2. 不要假设 MQ 不会重复投递，下游必须幂等。
3. 不要只靠定时任务补偿，关键事件要有本地消息表或事务消息保证可追溯。
4. 订单状态更新要使用条件更新，避免支付成功后又被补偿任务关单。

一句话回答：订单创建的一致性一般通过“本地事务 + outbox/事务消息 + 状态机 + 幂等消费 + 补偿任务”保证，而不是通过跨服务大事务保证。
