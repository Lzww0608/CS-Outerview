# 4. 支付回调一致性与对账

支付链路里经常出现“第三方显示支付成功，但调用方显示失败”。这类问题不能只看一次同步接口返回，要从支付单状态机、回调、查询、幂等和对账一起分析。

## 1. 可能原因

常见原因：

1. **同步返回丢失**：调用第三方支付接口成功，但网络超时、连接断开或调用方解析失败，本地误判为失败。
2. **异步回调失败**：第三方已支付成功，但回调通知到调用方时被网关拦截、签名校验失败、接口超时、应用异常或消息丢失。
3. **本地事务失败**：调用方收到成功回调，但更新订单或支付单数据库失败，导致本地仍是未支付或失败。
4. **状态机写错**：本地把“支付处理中”直接标成失败，后续成功回调又因为状态不允许而被拒绝。
5. **幂等号不一致**：请求号、支付单号、订单号混用，第三方成功的是 A，本地查询或更新的是 B。
6. **签名和金额校验失败**：回调金额、币种、商户号、订单号不匹配，本地正确拒绝，但没有进入人工或自动对账流程。
7. **主从延迟或缓存未刷新**：支付单已更新成功，但查询接口读从库或缓存，短时间仍显示失败。
8. **补偿任务缺失**：既没有主动查单，也没有日终对账，导致临时异常长期停留。

## 2. 正确状态机

支付状态不应只有成功和失败。更稳妥的状态机：

```text
INIT
  -> PAYING
  -> SUCCESS
  -> FAILED
  -> CLOSED
```

对于同步调用超时或未知错误，不应直接标记失败，而应进入 `PAYING` 或 `UNKNOWN`，再通过查单确认最终状态。失败只能代表第三方明确返回失败，或超过业务有效期后主动关闭。

状态更新必须条件化：

```sql
UPDATE payment_order
SET status = 'SUCCESS',
    paid_at = NOW(),
    third_trade_no = ?
WHERE pay_order_id = ?
  AND status IN ('INIT', 'PAYING');
```

如果影响行数为 0，要查询当前状态并幂等返回，不能重复发货或重复推进订单。

## 3. 处理流程

推荐链路：

```text
创建支付单
  -> 本地落库 pay_order_id, amount, status=INIT
  -> 调第三方支付，传 out_trade_no/pay_order_id
  -> 同步返回只作为参考
  -> 成功回调验签、验金额、验商户号
  -> 条件更新支付单 SUCCESS
  -> 推进订单 PAID / 发消息
  -> 定时查单补偿 PAYING/UNKNOWN
  -> 日终账单对账修复差异
```

关键设计：

1. **幂等键**：用 `pay_order_id` 或 `out_trade_no` 做唯一约束。
2. **回调先验签**：签名、金额、币种、商户号、订单号都要校验。
3. **先落支付流水**：原始回调报文、第三方流水号、处理结果要保存，方便审计。
4. **本地事务 + 消息表**：支付单成功和发送订单已支付事件要在同一事务内记录 outbox。
5. **主动查单**：对超时、未知、回调失败的支付单按退避策略查询第三方。
6. **对账**：下载第三方账单，与本地支付流水按订单号、金额、状态核对。

## 4. 易错点

1. 同步接口返回失败不一定代表用户没付钱，超时和未知必须查单。
2. 回调可能重复、乱序、延迟到达，处理必须幂等。
3. 支付成功后不能被超时关单覆盖，订单和支付状态更新都要带条件。
4. 不能只更新订单不记录支付流水，否则对账时缺少证据。
5. 前端展示状态要读权威状态或处理缓存延迟，不能把短暂读旧当最终失败。

## 5. 面试回答模板

第三方成功但本地失败，可能是同步返回超时、异步回调失败、本地更新失败、状态机错误、幂等号不一致、主从延迟或缓存未刷新。支付系统要把同步返回、异步回调、主动查单和日终对账结合起来：本地先创建支付单，调用第三方后未知状态不能直接判失败；回调要验签、验金额并幂等更新支付单；更新成功后通过本地消息表推进订单；对长时间 PAYING 的单据主动查第三方，最终再用账单对账修复差异。
