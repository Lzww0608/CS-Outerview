# 2. 超时关单

超时关单是指订单创建后，如果在指定时间内没有支付，就自动关闭订单，并释放库存、优惠券、红包等锁定资源。

## 实现方式

1. **延迟队列**：创建订单后发送延迟消息，到期后消费消息并检查订单状态。
2. **时间轮**：适合大量短时间延迟任务，按时间槽批量触发。
3. **定时扫描**：按 `expire_time` 扫描过期未支付订单，作为延迟消息的兜底。
4. **任务表**：把关单任务落库，记录执行状态、重试次数和下次执行时间，适合强可观测的场景。

线上更稳妥的方案是“延迟消息 + 定时扫描兜底”。延迟消息负责及时触发，扫描任务负责修复漏消息、消费失败、服务宕机等异常。

## 并发正确性

支付回调和超时关单可能同时发生，所以不能先查状态再无条件更新，必须使用状态机条件更新。

```sql
UPDATE orders
SET status = 'CLOSED', close_reason = 'TIMEOUT'
WHERE order_id = ? AND status = 'UNPAID';
```

如果影响行数为 1，说明关单成功，然后发送释放库存、释放优惠券消息；如果影响行数为 0，说明订单已经支付或关闭，直接幂等返回。

支付回调同理：

```sql
UPDATE orders
SET status = 'PAID', paid_time = NOW()
WHERE order_id = ? AND status = 'UNPAID';
```

## 注意事项

1. 关单消息可能重复消费，释放资源也要用 `order_id` 做幂等。
2. 释放库存和优惠券建议异步化，但要有补偿任务扫描异常状态。
3. 扫描任务需要按分片、按批次、按索引推进，避免全表扫描。
4. 订单过期时间要落库，不要只依赖 MQ 延迟时间，否则消息丢失后难以恢复。

## 方案取舍

| 方案 | 优点 | 缺点 | 适用场景 |
| --- | --- | --- | --- |
| 延迟消息 | 到期触发及时，业务链路简单 | 依赖 MQ 延迟能力，消息丢失或积压要兜底 | 电商订单、支付单超时 |
| Redis ZSet | 实现简单，score 存过期时间，便于批量取到期任务 | 需要自己处理并发抢占、持久化和大 key | 中小规模延迟任务 |
| 时间轮 | 内存效率高，适合大量短延迟任务 | 进程重启恢复复杂，长延迟要多级时间轮 | 网关连接超时、短任务调度 |
| 定时扫描 | 强可恢复，所有状态都在数据库 | 延迟不够实时，扫描压力要控制 | 兜底补偿、低频关单 |
| 任务表 | 状态可观测，可重试可审计 | 需要任务调度和分片执行框架 | 金融、支付、强审计链路 |

生产中常用组合：

```text
创建订单
  -> orders.expire_time 落库
  -> 发送 delay close_order(order_id, expire_time)
  -> 到期消费后条件更新订单状态
  -> 释放库存/优惠券/红包
  -> 定时扫描 expire_time <= now and status = UNPAID 做兜底
```

定时扫描要有合适索引：

```sql
CREATE INDEX idx_status_expire_time ON orders(status, expire_time);
```

扫描时按批次推进：

```sql
SELECT order_id
FROM orders
WHERE status = 'UNPAID'
  AND expire_time <= NOW()
ORDER BY expire_time
LIMIT 500;
```

面试回答时要强调：关单不是简单定时器，核心是订单状态机、幂等释放资源、支付回调并发竞争、消息失败兜底和批量扫描压力控制。

## 12306 抢票后 20 分钟未支付关闭订单

抢票场景里的超时关单比普通电商更强调“座位/区间库存预占”。用户抢到票后，系统通常先生成待支付订单并锁定席位或区间库存，20 分钟内未支付则关闭订单并释放资源。

推荐链路：

```text
抢票成功
-> 创建订单 status = UNPAID, expire_time = now + 20min
-> 锁定座位或区间库存 lock_status = LOCKED
-> 发送 20 分钟延迟关单消息
-> 支付成功回调尝试 UNPAID -> PAID
-> 关单消息到期尝试 UNPAID -> CLOSED
-> 关单成功后释放座位/区间库存
-> 定时扫描 UNPAID and expire_time <= now 兜底
```

并发关键点：

1. 支付回调和关单任务都只能通过条件更新推进订单状态，谁先把 `UNPAID` 改走谁成功。
2. 支付成功后，关单消息即使到期也只能看到影响行数为 0，然后幂等返回。
3. 关单成功后释放库存也要有锁定流水，按 `order_id` 幂等释放，防止重复回补。
4. 如果支付渠道回调延迟，订单已关闭但渠道后续通知支付成功，要进入退款、人工或补偿流程，而不是重新改成已支付。
5. 余票查询缓存不能作为最终库存，最终出票要以库存服务或数据库强校验为准。

真实系统还要考虑分库分表和扫描压力。订单表应有 `(status, expire_time)` 索引，扫描任务按库表分片、按批次处理，并记录游标和失败重试。延迟消息保证大部分订单按时关闭，扫描任务负责处理消息丢失、服务宕机和消费失败。
