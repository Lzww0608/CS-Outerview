# 3. 优惠券数据模型与领取链路

优惠券系统常见追问是“添加优惠券经过哪些模块、涉及哪些表、店铺和优惠券是什么关系、秒杀抢券如何保证不乱”。回答时要把数据模型、创建链路、领取链路和并发控制分开。

## 1. 核心实体

常见表设计：

| 表 | 作用 | 关键字段 |
| --- | --- | --- |
| `shop` | 店铺主表 | `shop_id、name、status、owner_id` |
| `coupon_template` | 优惠券模板 | `template_id、shop_id、type、threshold、discount、valid_time、total_stock、status` |
| `coupon_stock` | 库存表 | `template_id、total_stock、available_stock、locked_stock` |
| `user_coupon` | 用户券实例 | `id、user_id、template_id、status、received_time、used_time、expire_time` |
| `coupon_receive_record` | 领取流水/幂等表 | `request_id、user_id、template_id、result、created_time` |
| `coupon_usage` | 核销记录 | `order_id、user_coupon_id、amount、status` |

店铺和优惠券通常是一对多关系：一个店铺可以创建多张优惠券模板，一张优惠券模板归属一个店铺。平台券则可以把 `shop_id` 设为空或归属平台主体，并通过适用范围表绑定类目、商品或店铺集合。

## 2. 添加优惠券流程

创建优惠券不是只插入一张表：

```text
商家/运营填写优惠券信息
-> API 参数校验和权限校验
-> 校验店铺状态、活动时间、预算和库存
-> 开启本地事务
-> 写 coupon_template
-> 写 coupon_stock
-> 写操作审计/发布事件
-> 提交事务
-> 异步刷新缓存、搜索索引和活动页
```

需要校验：

1. 优惠金额不能超过门槛或业务允许上限。
2. 生效时间早于过期时间。
3. 总库存非负，不能超过预算。
4. 店铺必须存在且处于可运营状态。
5. 权限上只有店主、运营或平台管理员能创建。

## 3. 领取优惠券流程

普通领取链路：

```text
用户请求领取
-> 登录态和风控校验
-> 查询模板状态和时间窗口
-> 判断一人限领次数
-> 扣减库存
-> 创建 user_coupon
-> 记录领取流水
-> 返回领取结果
```

数据库兜底写法：

```sql
UPDATE coupon_stock
SET available_stock = available_stock - 1
WHERE template_id = ? AND available_stock > 0;
```

如果影响行数为 1，再插入 `user_coupon`。同时给 `(user_id, template_id)` 或 `(user_id, template_id, receive_batch)` 建唯一约束，防止重复领取。

## 4. 秒杀抢券并发控制

高并发抢券不能让所有请求都打 MySQL。常见做法：

1. 活动开始前把库存、领取资格、限领规则预热到 Redis。
2. 请求先过网关限流和风控。
3. Redis Lua 原子判断库存、资格、是否已领取，并预扣库存。
4. 成功请求写入 MQ 或 Redis Stream。
5. 异步消费者写 MySQL，使用唯一键和条件更新保证幂等。
6. 消费失败时重试、死信、补偿库存和对账。

Lua 只能保证 Redis 内部多个命令的原子性，不等于订单或券实例已经最终创建成功。因此前端应展示“抢券成功，处理中”或轮询结果；MySQL 落库失败要有补偿。

## 5. 事务和锁

如果两个用户交易或领取同一资源，要区分本地事务和分布式一致性：

1. 同一数据库内的库存扣减、券实例创建、流水记录可以放在一个本地事务里。
2. 事务期间其他请求更新同一行会等待行锁，超时后可能失败。
3. 不要在数据库事务内等待短信、RPC、MQ ACK 等慢操作。
4. 跨服务动作使用状态机、幂等、MQ 和补偿保证最终一致。

## 6. 易错点

1. 只用 Redis 扣库存但不做 MySQL 唯一约束，重试或补偿时可能重复发券。
2. 一张券模板可能有总库存、每日库存、用户限领、店铺预算等多个约束，不能只看一个库存字段。
3. 秒杀抢券用分布式锁串行化所有请求性能很差，应优先用原子扣减、分片库存和异步落库。
4. 缓存里的模板状态要能从数据库重建，不能把 Redis 当唯一真实数据源。
5. 过期券、已使用券、退款退券都要进入状态机，不能只靠删除记录。

## 7. 面试回答模板

添加优惠券时，我会先做权限、店铺状态、时间、库存和预算校验，然后在一个本地事务里创建优惠券模板、库存记录和操作审计，再异步刷新缓存和活动页。店铺和优惠券模板通常是一对多关系，用户领取后会生成用户券实例和领取流水。高并发抢券时，库存和资格会预热到 Redis，通过 Lua 原子判断限领和预扣库存，成功后写 MQ 异步落库；MySQL 用唯一索引、条件更新和消费幂等兜底，失败时用补偿任务回补库存并对账。
