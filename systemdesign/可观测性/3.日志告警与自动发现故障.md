# 3. 日志告警与自动发现故障

线上功能不可用但用户没有主动反馈时，系统必须靠可观测性主动发现问题。可观测性不是只打日志，而是指标、日志、链路追踪、告警、探测和自动化处置的组合。

## 1. 怎么主动发现功能不可用

常见手段：

1. **服务端指标**：QPS、错误率、P95/P99、超时率、实例存活、线程池队列、连接池、CPU、内存、磁盘。
2. **业务指标**：登录成功率、支付成功率、下单量、内容发布成功率、AI 回答成功率、RAG 无答案率。
3. **客户端埋点**：页面白屏、接口失败、按钮点击后无响应、JS error、App crash。
4. **链路追踪**：跨网关、服务、数据库、缓存、外部依赖定位慢点和错误点。
5. **主动探测**：定时用合成请求模拟真实用户路径，例如登录、查询、提交、支付沙箱。
6. **日志异常检测**：按错误码、异常栈、关键字和日志模式突增触发告警。
7. **SLO/错误预算**：用可用性目标约束告警，例如 5 分钟错误率或延迟超过阈值。

只看机器 CPU 不够。很多功能不可用时机器资源正常，但业务成功率、依赖超时或客户端错误已经异常。

## 2. 日志怎么写

生产日志要结构化，便于检索、聚合和告警。

建议字段：

| 字段 | 作用 |
| --- | --- |
| `timestamp` | 事件发生时间 |
| `level` | INFO/WARN/ERROR |
| `service` | 服务名 |
| `env` | prod/staging/test |
| `trace_id` | 串联一次请求 |
| `span_id` | 链路追踪中的当前 span |
| `user_id` / `tenant_id` | 排查影响范围，必要时脱敏 |
| `api` / `method` | 接口或方法 |
| `error_code` | 稳定错误码 |
| `latency_ms` | 请求耗时 |
| `message` | 简短描述 |

示例：

```json
{
  "level": "ERROR",
  "service": "rag-api",
  "trace_id": "tr_123",
  "api": "/v1/chat",
  "error_code": "VECTOR_TIMEOUT",
  "latency_ms": 3200,
  "message": "vector search timeout",
  "tenant_id": "t_8"
}
```

日志注意事项：

1. 不把密码、token、密钥、身份证、手机号明文写入日志。
2. ERROR 日志要能定位原因，不要只写 `failed`。
3. 高频正常日志要采样，避免日志风暴。
4. 关键状态变更要记录操作人、对象、旧值摘要、新值摘要和 trace id。
5. 日志要和指标、trace 互相跳转，不能成为孤岛。

## 3. 告警怎么配置

告警要围绕用户影响和故障定位设计，而不是所有指标超阈值都通知人。

常见告警规则：

1. **错误率**：`5xx_rate > 1% for 5m`。
2. **延迟**：`P99 > 1s for 10m`。
3. **业务成功率**：登录成功率、支付成功率低于阈值。
4. **依赖异常**：MySQL 慢查询、Redis 超时、MQ 堆积、向量库超时。
5. **实例健康**：可用实例数低于副本期望，或者 readiness 失败。
6. **主动探测失败**：核心用户路径连续失败。
7. **日志异常突增**：某错误码或异常栈在短时间内明显增加。

告警链路：

```text
应用埋点 / 日志 / trace
  -> Prometheus / 日志平台 / Trace 系统
  -> 告警规则
  -> Alertmanager 分组、抑制、升级
  -> 飞书/钉钉/短信/PagerDuty
  -> 工单和复盘
```

## 4. 避免告警噪声

1. 按服务、等级、影响范围分组，避免同一故障发出几十条告警。
2. 对下游故障做告警抑制，上游错误率告警可以关联根因。
3. 设定持续时间，避免瞬时抖动。
4. 低优先级告警进日报或看板，高优先级才打断值班人。
5. 告警必须有 runbook：现象、排查入口、常见原因、止血手段。

## 5. 自动化处置

可以对低风险动作做自动化：

1. 重启异常实例。
2. 从负载均衡摘除不健康实例。
3. 触发扩容或扩消费者。
4. 开启降级开关或熔断慢依赖。
5. 回滚明显失败的灰度版本。

但自动化必须有边界：记录动作、限制频率、保留人工确认点。涉及数据修复、扣费、删除、生产配置大范围变更时不能直接自动执行。

## 6. 面试回答模板

用户不反馈时，我会靠监控和告警主动发现问题。服务端看 RED 指标，也就是 QPS、错误率、延迟；资源层看 CPU、内存、磁盘、连接池；业务层看登录成功率、支付成功率、核心链路转化；客户端看白屏、接口失败和 crash；再用主动探测模拟真实用户路径。日志要结构化，带 trace_id、service、api、error_code、latency 和用户/租户摘要，敏感字段脱敏。告警规则按用户影响设计，通过 Alertmanager 做分组、抑制和升级，并配 runbook。低风险问题可以自动摘流、扩容、重启或降级，高风险修复必须人工审批。
