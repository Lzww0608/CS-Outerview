# 2. MQ 与 MySQL 高 CPU 排查

线上排查高 CPU 要先确认“谁在消耗 CPU、消耗在用户态还是内核态、是计算热点还是等待放大”。MQ 和 MySQL 都是复杂系统，不能只看一个 `top` 就下结论。

## 1. 通用排查步骤

1. `top` / `htop` 看进程 CPU、load、上下文切换。
2. `top -H -p <pid>` 看进程内哪个线程消耗 CPU。
3. `pidstat -t -p <pid> 1` 看线程级 CPU 和上下文切换。
4. `perf top` / `perf record` / 火焰图看热点函数。
5. 看业务指标：QPS、P99、错误率、队列堆积、连接数、重试数。
6. 看最近变更：版本发布、配置变更、流量突增、DDL、索引变动。

用户态 CPU 高常见是计算、序列化、压缩、正则、JSON、SQL 执行计划差；内核态 CPU 高可能是网络包、磁盘 I/O、系统调用、锁竞争、上下文切换、软中断。

## 2. MQ 占用大量 CPU 怎么排查

以 Kafka/RabbitMQ/RocketMQ 这类 MQ 为例，先看是 broker 高 CPU 还是 consumer/producer 高 CPU。

### 2.1 Broker 侧

关注指标：

1. 入站/出站吞吐、消息大小、topic/queue 数量。
2. 消息堆积、消费者 lag、重试和死信数量。
3. 磁盘 I/O、page cache 命中、刷盘延迟。
4. 网络包量、连接数、TLS 加解密开销。
5. 压缩/解压算法，例如 gzip 比 lz4/snappy 更耗 CPU。
6. 分区/队列是否热点，是否有单分区打满。

排查动作：

1. 看 broker 线程热点，确认 CPU 花在网络、存储、复制、压缩还是协议解析。
2. 看是否有大量小消息，小消息会放大协议解析和系统调用成本。
3. 看是否开启高成本持久化、镜像队列、同步复制或事务消息。
4. 看消费者是否慢导致堆积，broker 需要维护更多待投递状态。
5. 看是否频繁创建连接，应该使用连接复用和 channel 复用。

### 2.2 Consumer/Producer 侧

常见原因：

1. 消费逻辑 CPU 重，例如 JSON 解析、正则、加解密、压缩。
2. 消费失败后快速重试，形成空转。
3. 批量太小，频繁 poll/ack/commit。
4. 日志过多，序列化和 I/O 放大。
5. 线程数过多，锁竞争和上下文切换变高。

优化思路：

1. 批量拉取、批量处理、批量 ack。
2. 降低重试频率，增加退避和死信队列。
3. 优化序列化格式和压缩算法。
4. 增加分区和消费者并行度，但避免超过有效分区数。
5. 对慢下游做隔离和限流，避免消费线程空转重试。

## 3. MySQL 占用大量 CPU 怎么排查

MySQL CPU 高通常来自 SQL 执行、锁竞争、连接风暴、排序临时表、JSON/函数计算或后台线程。

优先看：

1. `SHOW PROCESSLIST`：是否有大量同类 SQL、长事务、锁等待。
2. 慢 SQL 日志和 `performance_schema`：找高频高耗 SQL。
3. `EXPLAIN ANALYZE`：确认是否全表扫描、回表过多、filesort、temporary。
4. QPS/TPS、连接数、Threads_running、InnoDB row lock wait。
5. Buffer Pool 命中率、脏页比例、redo 刷盘压力。

常见根因：

1. 索引缺失或索引失效，导致全表扫描。
2. 返回行数太多，排序、分组和临时表消耗 CPU。
3. 大量短连接或连接池配置错误。
4. 热点行更新导致锁等待和重试。
5. 大事务、批量更新或 DDL 影响正常查询。
6. 业务循环调用数据库，导致 N+1 查询。

优化思路：

1. 给高频过滤、关联、排序字段建合适联合索引。
2. 改写 SQL，避免函数包索引列、隐式转换、大 offset。
3. 限制返回字段和行数，用覆盖索引减少回表。
4. 读多写少场景引入缓存、读写分离或预聚合。
5. 控制连接池大小和超时，避免连接风暴。
6. 热点写用分片计数、异步合并或业务维度拆分。

## 4. 易错点

1. CPU 高不一定是坏事，如果吞吐同步升高且延迟可控，可能只是资源被充分利用。
2. load 高不等于 CPU 高，I/O 等待和不可中断睡眠也会推高 load。
3. MQ 堆积可能是消费者慢，不一定是 broker 本身慢。
4. MySQL CPU 高不能只“加机器”，先看 SQL 和索引，否则扩容收益有限。
5. 排查要保留证据：时间点、指标截图、慢 SQL、火焰图、线程栈和变更记录。

## 5. 面试回答模板

如果 MQ 或 MySQL 占用大量 CPU，我会先用 `top/top -H/pidstat/perf` 确认热点进程和线程，再结合业务指标看是否伴随 QPS、延迟、队列堆积或错误率变化。MQ 侧重点看 broker 还是消费者，排查消息大小、批量、压缩、重试、堆积、分区热点和连接复用。MySQL 侧重点看 `SHOW PROCESSLIST`、慢 SQL、`EXPLAIN ANALYZE`、锁等待和连接数，常见原因是索引失效、全表扫描、排序临时表、大事务和连接风暴。优化必须用同一套指标验证，而不是凭感觉改配置。
