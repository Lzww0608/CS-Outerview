# 1. 对象存储核心设计与异常处理

对象存储以 `bucket + object key` 为主要访问模型，适合存储图片、视频、日志、备份包、模型文件等非结构化大对象。它和传统文件系统不同：对象通常没有真正的目录树，目录只是 key 前缀；对象写入后更强调整体读写、范围读、版本、权限和元数据管理。

## 1. 核心架构

常见对象存储会拆成三层：

1. **接入层**：鉴权、限流、协议解析、上传下载、Range 请求、分片上传。
2. **元数据层**：保存 bucket、object key、版本、大小、校验和、分片列表、权限、生命周期。
3. **数据层**：保存对象内容，可以是本地磁盘、分布式文件系统、Ceph、S3、OSS 或自研块存储。

```text
Client
  -> Gateway/API Server
  -> Metadata Service
  -> Data Node / Object Store
```

关键原则是元数据和数据分离。元数据小而热，需要低延迟和强一致；对象内容大而冷，可以走分片、副本、纠删码、冷热分层和 CDN。

## 2. 上传流程

大文件上传通常使用 multipart：

1. 客户端调用 `initMultipartUpload`，服务端返回 `uploadId`。
2. 客户端按固定大小切片，分片携带 `partNumber`、`offset`、`checksum` 上传。
3. 服务端写入临时对象或临时块，并记录分片状态。
4. 客户端调用 `completeMultipartUpload`。
5. 服务端校验分片完整性，生成最终对象元数据，提交版本并清理临时块。

幂等性设计：

1. 同一个 `uploadId + partNumber` 重试上传，内容相同可直接覆盖或返回成功。
2. `complete` 要防重复提交，可以用对象版本号或状态机控制。
3. 元数据提交和数据可见性要有顺序，避免对象元数据已可见但数据块缺失。

## 3. 下载流程

下载重点是范围读取和校验：

1. 根据 `bucket + key + version` 查元数据。
2. 校验权限和对象状态。
3. 普通下载按对象分片顺序读取；大对象支持 HTTP Range。
4. 返回 `ETag`、`Content-Length`、`Content-Range`、`Last-Modified` 等头。
5. 热对象可通过 CDN、边缘缓存或本地缓存池加速。

## 4. 缓存池怎么设计

缓存池可以缓存对象元数据、小对象内容、分片索引或热块。常见设计：

1. **缓存对象**：`key -> metadata/block`。
2. **淘汰策略**：LRU、LFU、TinyLFU、按大小成本淘汰。
3. **容量约束**：按条目数和字节数双限制，不能只按 key 数量。
4. **并发保护**：分段锁、读写锁或单线程事件循环，避免全局锁竞争。
5. **一致性**：写入或删除对象后失效缓存；版本化对象可用 `key+version` 降低一致性压力。

缓存池满时可以：

1. 淘汰冷数据，优先按成本和最近访问时间选择。
2. 对低优先级请求返回降级，例如绕过缓存直接读后端。
3. 对写入缓存失败做软失败，不能影响主链路对象写入成功。
4. 如果缓存承载的是上传临时分片，则必须返回明确错误并让客户端重试，不能静默丢弃。

## 5. 线程池和异步任务

对象存储项目里常见异步任务：

1. 分片校验、合并和压缩。
2. 后台清理过期 multipart。
3. 生成缩略图、转码、病毒扫描。
4. 冷热迁移、纠删码编码、跨机房复制。

线程池应轻量化：

1. I/O 线程只负责收发请求和状态机推进。
2. CPU 或阻塞任务投递到 worker pool。
3. 任务队列有上限，满了要限流或返回重试。
4. 每个任务带 traceId、对象 key、uploadId，方便排障。
5. 异步任务完成后通过 future、回调队列、eventfd 或消息队列通知状态机。

## 6. 数据可靠性

对象存储的数据可靠性来自多层机制：

1. **校验和**：分片和整体对象使用 CRC32C、MD5 或 SHA256 校验。
2. **多副本**：对象块写入多个节点和故障域。
3. **纠删码**：冷数据用 `k+m` 编码降低存储成本。
4. **后台巡检**：定期 scrub，发现坏块后从副本或纠删码恢复。
5. **WAL/状态机**：元数据修改先记录日志，崩溃后可恢复到明确状态。

## 7. 易错点

1. 把对象 key 当真实目录处理，会导致列表和重命名语义混乱。
2. 分片上传只记录 offset 不够，乱序和重试场景需要 partNumber、checksum 和状态。
3. 缓存命中不能绕过权限校验，尤其是多租户 bucket。
4. 元数据强一致和对象内容最终一致要讲清楚，不能笼统说“都强一致”。
5. 后台异步任务必须可重试、幂等、可观测，否则故障后容易留下临时垃圾。

## 8. 面试回答模板

对象存储我会按接入层、元数据层、数据层拆。接入层处理鉴权、限流、分片上传和 Range 下载；元数据层保存 bucket、key、版本、大小、checksum、分片列表和权限；数据层保存真实对象块，通过多副本、纠删码、校验和和后台巡检保证可靠性。大文件上传用 multipart，分片上传和 complete 都要幂等。缓存池可缓存热元数据和热块，满了按 LRU/LFU/TinyLFU 淘汰或绕过缓存，但上传临时状态不能静默丢。异步任务用线程池或 MQ 执行，必须有队列上限、超时、重试和监控。
