# 1. SDK 无感升级与配置推送

配置中心常见能力包括配置发布、版本管理、客户端订阅、灰度推送、回滚和审计。面试里问“SDK 暴露给开发者后，代码变动别人都要更新包，怎么无感升级”，本质是在考：**如何把变化从客户端 SDK 中移到服务端、配置、插件或本地 agent 中**。

## SDK 无感升级怎么做

如果 SDK 已经被很多业务方依赖，不能频繁要求所有人升级包，常见方案有：

1. **薄 SDK + 服务端控制面**：SDK 只保留稳定 API、协议编解码、容错和缓存，策略逻辑放到服务端配置或规则引擎。行为变化通过配置下发，不改 SDK 包。
2. **协议兼容和能力协商**：SDK 启动时上报版本、语言、能力位，服务端根据能力下发兼容格式，避免新字段让老客户端不可用。
3. **Sidecar / Agent 模式**：把复杂逻辑放到本机独立进程，业务进程只通过 Unix Domain Socket、HTTP localhost、gRPC 调用 agent。升级 agent 即可，不需要业务重新发版。
4. **插件化 / 动态加载**：SDK 支持从可信源下载插件或规则包，校验签名后热加载。适合规则频繁变化但安全要求可控的场景。
5. **服务端代理模式**：把原来 SDK 内部直连多个后端的逻辑收敛到统一网关，由网关做路由、鉴权、重试、灰度。
6. **强制兼容策略**：保留旧接口语义，新增能力走新字段或新 endpoint，避免破坏已有业务。

工程上最稳妥的是“薄 SDK + 配置/服务端控制 + 兼容协议”。Sidecar 和插件化能力更强，但引入运维、安全和资源隔离成本。

## Apollo 整体架构怎么讲

Apollo 这类配置中心通常不是单个“配置表”，而是一条从配置发布、变更通知到客户端本地快照的链路。面试里可以按角色说明：

1. **Portal**：给研发和运维使用的管理后台，负责配置编辑、发布、灰度、回滚和权限审计。
2. **Admin Service**：处理配置发布、版本管理、灰度规则和数据库写入。
3. **Config Service**：面向客户端 SDK 提供配置读取、长轮询通知和版本查询。
4. **Meta Service / 注册发现**：告诉客户端当前环境有哪些可用的 Config Service 实例。
5. **Client SDK**：启动时拉取配置，维护内存快照和本地缓存，并注册配置变更回调。
6. **数据库**：保存 app、cluster、namespace、release、灰度和审计信息，是配置权威源。

一个典型发布链路：

```text
开发者在 Portal 修改配置
-> Admin Service 写入新 Release 和审计记录
-> 通知 Config Service 有 namespace 发生变更
-> Config Service 唤醒相关长轮询请求，返回新 releaseKey
-> Client SDK 重新拉取配置
-> 原子替换内存快照，并触发业务监听器
```

这里的关键点是：服务端通常只把“有变化”通知给客户端，客户端再拉完整配置。这样可以避免长轮询响应携带大配置，也能让客户端自己做版本校验、本地缓存和失败回退。

## 客户端怎么感知配置变化

常见方式：

1. **定时拉取**：客户端周期性拉取配置版本。简单可靠，但实时性差，容易造成无效请求。
2. **长轮询**：客户端带当前版本请求服务端，服务端发现没有变化就挂起请求；有变化或超时再返回。Apollo、Nacos 等配置中心常用类似思路。
3. **服务端推送**：用 WebSocket、SSE、gRPC stream、HTTP/2 stream 或自定义 TCP 长连接推送变更事件。
4. **消息队列订阅**：客户端或本地 agent 订阅配置变更 topic，适合内部系统。
5. **本地文件 watch**：配置中心 agent 把配置落到本地文件，业务进程用 inotify/kqueue/watch service 感知文件变化。

典型客户端流程：

1. 启动时拉全量配置，落内存快照和本地磁盘缓存。
2. 建立长轮询或长连接，订阅 namespace/app/env。
3. 服务端返回新版本号后，客户端拉增量或全量配置。
4. 校验签名、版本号和格式。
5. 原子替换内存快照，并通知业务回调。
6. 失败时继续使用上一次可用配置。

## 配置修改后如何保证客户端及时拿到正确数据

配置中心通常追求的是“发布后秒级生效 + 客户端最终一致 + 失败时保留最后可用配置”，而不是每个业务请求都同步读配置中心。实现上要同时处理及时性和正确性：

1. **版本号或 releaseKey**：每次发布生成单调版本或不可变 releaseKey，客户端只接受更新版本，防止乱序通知把旧配置覆盖回去。
2. **长轮询通知**：客户端带当前版本请求 Config Service；没有变化时服务端挂起，有变化时立即返回，兼顾实时性和请求量。
3. **通知后再拉取**：长轮询只返回变更 namespace 和版本，客户端再拉配置内容，便于重试和校验。
4. **本地双缓存**：客户端同时维护内存快照和磁盘缓存；配置中心异常时继续使用最近一次成功配置，避免业务启动失败。
5. **原子替换配置快照**：先完整构建新配置对象，再一次性替换引用；业务线程读到的要么是旧完整配置，要么是新完整配置。
6. **变更回调隔离**：监听器异常不能影响 SDK 拉取线程；慢回调要异步执行并有超时或线程池隔离。
7. **灰度和回滚**：客户端拉取时带 app、cluster、ip、灰度标签等信息，服务端按规则返回对应 release；回滚本质上也是发布一个历史版本。
8. **观测和兜底**：监控客户端长轮询失败率、配置拉取延迟、版本分布和未更新实例，发现长时间未追上版本时告警。

易错点是把配置中心理解成“强一致数据库”。真实项目里，配置发布到所有客户端之间会有传播窗口；因此安全开关、支付比例、风控阈值这类高风险配置要支持灰度、小流量验证、快速回滚和服务端兜底校验。

## 自己实现配置推送

一个简单可靠的设计：

1. **服务端**：
   - 配置写入 DB，版本号单调递增。
   - 发布时写变更事件到内存队列、MQ 或事件总线。
   - 推送节点维护客户端订阅关系和长连接。
   - 收到配置变更后，只向订阅该配置的客户端推送版本号。
2. **客户端**：
   - 后台线程维护长轮询或长连接。
   - 收到变更通知后拉取配置内容。
   - 用 `atomic shared_ptr` 或读写锁切换配置快照。
   - 业务线程读配置时只读当前快照，不阻塞网络线程。

不要用线程死循环空转查询队列。更好的方式是：

1. 线程内用阻塞队列 `condition_variable` 等待通知。
2. 进程间用 `eventfd`、pipe、Unix Domain Socket 唤醒事件循环。
3. 服务端网络推送用 `epoll` 等事件驱动等待 socket 可读写。

## 用哪种进程间通信方式

如果 SDK 和业务在同一个进程内，优先用后台线程 + 内存快照：

```text
network thread -> parse new config -> build immutable snapshot -> atomic swap
business thread -> atomic load snapshot -> read config
```

线程能直接访问同一进程地址空间中的堆对象。为了并发安全，通常让配置对象不可变，用 `std::shared_ptr<const Config>` 原子替换，或者用读写锁保护。

如果使用独立 agent 进程，可以选：

1. **Unix Domain Socket**：推荐。支持双向通信、权限控制、传 fd，适合本机 RPC。
2. **命名管道 FIFO**：适合简单单向或半双工流式通知，语义比 socket 弱。
3. **共享内存 + eventfd/futex**：低延迟高吞吐，但协议、同步、崩溃恢复复杂。
4. **mmap 文件**：适合共享配置快照，配合版本号和通知机制使用。

配置中心 agent 常见做法是：agent 和服务端保持长连接，agent 把配置写本地缓存或共享内存，业务进程通过 Unix Domain Socket 查询或 watch 本地文件变更。

## 服务端主动推送怎么做

服务端不能为每个连接创建一个阻塞线程。更常见的是 Reactor 模型：

1. 所有客户端连接 fd 设置非阻塞。
2. 用 `epoll` 监听可读、可写、关闭事件。
3. 客户端建立连接后注册订阅关系：`config_key -> connection_set`。
4. 配置变更时，根据订阅表找到连接，把消息写入每个连接的发送缓冲区。
5. 给这些连接打开 `EPOLLOUT` 监听。
6. socket 可写时尽量写出，写完关闭 `EPOLLOUT`，避免一直触发可写事件。

这样线程数和连接数解耦，一个事件循环线程可以管理大量空闲长连接。

## 本地配置文件热更新模块怎么设计

如果题目要求“后端服务不重启，动态加载本地 JSON / YAML / INI 配置文件，并触发业务回调”，可以把它设计成一个本地配置中心 SDK，而不是简单地在循环里反复读文件。

### 核心模块

| 模块 | 职责 |
| --- | --- |
| `FileWatcher` | 监听配置文件或目录变更，支持 inotify/kqueue/WatchService/轮询兜底 |
| `Debouncer` | 合并连续写入事件，避免编辑器保存或原子替换触发多次 reload |
| `ParserRegistry` | 按扩展名选择 JSON/YAML/INI 解析器，统一转换成内部配置对象 |
| `Validator` | 校验必填项、类型、范围、枚举、依赖关系和业务约束 |
| `VersionedSnapshot` | 保存不可变配置快照、版本号、hash、加载时间和来源路径 |
| `CallbackDispatcher` | 异步触发业务回调，隔离慢回调和异常回调 |
| `AuditLogger` | 记录 reload 成功、失败原因、版本差异和回滚信息 |

典型流程：

```text
文件变化事件
-> debounce 等待写入稳定
-> 读取完整文件
-> 根据后缀选择 parser
-> 解析成统一 Config 对象
-> 校验 schema 和业务约束
-> 计算 hash，和当前版本相同则忽略
-> 原子替换内存快照
-> 异步触发业务回调
-> 记录版本、耗时、错误和 diff 摘要
```

### 快照和回调

读路径要尽量无锁或低锁。常见做法是构建不可变配置对象，然后用原子指针切换：

```cpp
struct AppConfig {
    int timeout_ms;
    std::string log_level;
    std::unordered_map<std::string, std::string> kv;
};

std::shared_ptr<const AppConfig> current;

std::shared_ptr<const AppConfig> getConfig() {
    return std::atomic_load(&current);
}

void publish(std::shared_ptr<const AppConfig> next) {
    auto old = std::atomic_exchange(&current, std::move(next));
    // callbacks run outside the publish path
}
```

业务线程读取到的要么是旧完整配置，要么是新完整配置，不能读到半解析状态。回调也不应该在文件监听线程里同步执行，否则某个业务回调很慢会阻塞后续 reload。更稳的方式是把回调投递到线程池，并给每个回调设置超时、异常捕获和指标。

回调接口可以这样设计：

```text
onConfigChanged(old_snapshot, new_snapshot, changed_keys)
```

业务方根据 `changed_keys` 决定是否重建连接池、刷新限流阈值、更新日志级别或重载规则。高风险配置，例如数据库地址、鉴权密钥、线程池大小，不一定允许自动热更新，可以标记为 `restart_required` 或需要人工确认。

### 文件写入和异常处理

本地文件热更新最容易出问题的是读到半写入文件。推荐发布方使用“临时文件 + fsync + rename”：

```text
write config.tmp
fsync(config.tmp)
rename config.tmp -> config.yaml
fsync(parent_dir)
```

加载方也要处理异常：

1. **解析失败**：保留旧快照，不触发回调，记录错误和文件版本。
2. **校验失败**：保留旧快照，明确是哪一个 key、类型或范围不合法。
3. **文件删除或为空**：根据业务选择保留旧配置、降级默认值或进入保护状态。
4. **连续变更**：用版本号或 hash 去重，避免重复回调。
5. **回调失败**：不能回滚全局快照，除非业务明确要求两阶段提交；至少要记录失败回调和影响模块。
6. **并发 reload**：同一时间只允许一个 reload pipeline 发布版本，避免新旧版本乱序覆盖。

### JSON / YAML / INI 的差异

三种格式可以统一成内部结构，但要注意语义差异：

1. JSON 类型严格，适合机器生成和 schema 校验。
2. YAML 表达能力强，但缩进、隐式类型和锚点容易引入歧义，生产解析要关闭不需要的复杂特性。
3. INI 简单，适合小配置，但嵌套和数组表达弱，通常映射成 `section.key -> value`。

工程上不要让业务代码直接依赖原始格式。更好的做法是解析成强类型配置对象，所有默认值、范围校验和兼容逻辑都集中在 SDK 里。

## 易错点

1. 推送消息最好只推版本号或变更摘要，客户端再拉取完整配置，避免大配置压垮推送链路。
2. 客户端必须有本地缓存和失败回退，否则配置中心故障会放大成业务故障。
3. 配置更新要有版本号和 CAS 语义，防止乱序推送导致旧配置覆盖新配置。
4. SDK 无感升级不能破坏 ABI/API；跨语言 SDK 还要考虑不同语言的依赖管理和运行时差异。
5. 插件化必须校验签名、来源和版本，避免供应链风险。
