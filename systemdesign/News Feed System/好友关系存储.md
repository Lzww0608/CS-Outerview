# 好友关系与关注关系存储设计

微博好友或关注关系本质是社交图谱问题。数据模型不是简单“用户表里放一个好友列表”，而是要支持关注、取关、双向好友、粉丝列表、共同关注、黑名单、分组、Feed 分发和权限判断。

## 1. 关系模型

微博更常见的是单向关注：

```text
user_a follows user_b
```

微信好友更接近双向关系：

```text
user_a friend user_b
user_b friend user_a
```

单向关注可以用边表表达：

```sql
CREATE TABLE user_follow (
    follower_id BIGINT NOT NULL,
    followee_id BIGINT NOT NULL,
    status TINYINT NOT NULL,
    created_at DATETIME NOT NULL,
    PRIMARY KEY (follower_id, followee_id),
    KEY idx_followee_follower (followee_id, follower_id)
);
```

核心索引：

1. `(follower_id, followee_id)`：查我关注了谁。
2. `(followee_id, follower_id)`：查谁关注了我。
3. `created_at` 或游标字段：支持分页。

### 1.1 Twitter follow 功能的基础 Schema

如果面试限定“设计 Twitter 的 follow 功能”，可以先给出一个可落地的关系表，再讨论规模化改造。

```sql
CREATE TABLE follow_edge (
    follower_id BIGINT NOT NULL,
    followee_id BIGINT NOT NULL,
    status TINYINT NOT NULL DEFAULT 1,
    created_at DATETIME NOT NULL,
    updated_at DATETIME NOT NULL,
    PRIMARY KEY (follower_id, followee_id),
    KEY idx_followee_created (followee_id, created_at, follower_id)
) ENGINE=InnoDB;

CREATE TABLE follow_count (
    user_id BIGINT PRIMARY KEY,
    following_count BIGINT NOT NULL DEFAULT 0,
    follower_count BIGINT NOT NULL DEFAULT 0,
    updated_at DATETIME NOT NULL
) ENGINE=InnoDB;
```

核心接口对应的查询：

```sql
-- 我是否关注了某人
SELECT 1
FROM follow_edge
WHERE follower_id = ?
  AND followee_id = ?
  AND status = 1;

-- 我的关注列表
SELECT followee_id, created_at
FROM follow_edge
WHERE follower_id = ?
  AND status = 1
ORDER BY created_at DESC
LIMIT ?;

-- 我的粉丝列表
SELECT follower_id, created_at
FROM follow_edge FORCE INDEX(idx_followee_created)
WHERE followee_id = ?
  AND status = 1
ORDER BY created_at DESC
LIMIT ?;
```

小到中等规模时 MySQL 更合适：有唯一约束、事务、二级索引和成熟运维，关注/取关可以做成幂等写。规模继续扩大后，可以按 `follower_id` 分片保存正向边，按 `followee_id` 分片保存反向边；如果粉丝列表和关系边达到极大规模，再考虑 HBase/Cassandra 这类宽列 NoSQL 承接海量边表。

## 2. 选 MySQL、NoSQL 还是图数据库

不同规模和查询需求选型不同。

| 方案 | 优点 | 缺点 | 适用场景 |
| --- | --- | --- | --- |
| MySQL 分库分表 | 事务成熟、唯一约束清晰、工程成本低 | 超大规模扩展和深度图查询困难 | 中小规模关系链、强一致关注取关 |
| Redis | 读写快，适合缓存集合、计数和热点关系 | 内存成本高，持久化和全量关系不适合作为唯一来源 | 关注列表缓存、粉丝数、共同关注近似计算 |
| HBase/Cassandra | 水平扩展强，适合海量宽表 | 二级索引和复杂查询弱 | 超大规模关注/粉丝列表、时间序列边 |
| 图数据库 | 多跳关系查询自然，例如共同好友、路径 | 高写入和超大规模在线业务成本高 | 推荐、风控、离线分析、关系探索 |
| ElasticSearch | 检索和过滤强 | 不适合事务权威源 | 搜索用户、关系筛选的辅助索引 |

面试里可以回答：关注/取关这种核心关系的权威源通常用 MySQL 分库分表或宽列 NoSQL；Redis 做缓存和计数；图数据库更适合多跳关系查询、推荐和离线分析，不一定作为在线主库。

## 3. 微博关注场景怎么落库

关系边通常按用户维度分片。

查询“我关注了谁”：

```text
shard = hash(follower_id)
row_key = follower_id
columns / rows = followee_id list
```

查询“谁关注了我”：

```text
shard = hash(followee_id)
row_key = followee_id
columns / rows = follower_id list
```

为了读写都高效，通常维护两份边：

1. **正向边**：`follower_id -> followee_id`，用于个人关注列表和发 Feed 时读取关注对象。
2. **反向边**：`followee_id -> follower_id`，用于粉丝列表和写扩散。

关注操作：

```text
写正向边
-> 写反向边
-> 更新计数
-> 删除或更新缓存
-> 发送关系变更事件
```

两份边很难用单机事务完全覆盖所有分片，所以真实系统常用最终一致：核心写成功后发事件补齐反向边、缓存和计数，并通过对账任务修复。

## 4. 大 V 和热点问题

微博类系统最大问题是热点用户。

大 V 的粉丝列表可能非常大，带来：

1. 粉丝列表存储过大。
2. 发帖写扩散成本极高。
3. 粉丝数计数更新热点。
4. 关系查询和共同关注计算变慢。

常见处理：

1. **推拉结合**：普通用户写扩散，大 V 发帖不推给所有粉丝，读 Feed 时再拉取大 V 内容。
2. **粉丝分桶**：按 `follower_id` hash 把同一个大 V 的粉丝拆到多个桶。
3. **计数异步化**：粉丝数用计数服务或缓存异步更新，允许短暂延迟。
4. **热点缓存**：大 V 基本资料、最新帖子、关注状态做多级缓存。
5. **离线图计算**：共同关注、推荐关系不在主链路实时全图计算。

## 5. 一致性和缓存

关注关系比点赞计数更敏感，但通常仍可以接受短暂最终一致。

要保证：

1. **关注/取关幂等**：重复请求不能产生重复边或负计数。
2. **唯一约束**：同一 `(follower_id, followee_id)` 只有一条有效关系。
3. **缓存失效顺序**：先写权威源，再删除或更新缓存。
4. **计数修正**：粉丝数、关注数可以异步维护，但要有定期对账。
5. **黑名单和隐私优先级**：读 Feed 和查关系时必须优先判断屏蔽、拉黑、可见性。
6. **事件补偿**：关系变更事件丢失时，通过扫描边表补偿缓存和反向索引。

## 6. 易错点

1. 把好友列表直接存在用户表一个字段里，会导致查询、分页、更新和索引都困难。
2. 只存正向边会让“谁关注了我”和 Feed 写扩散非常慢。
3. 图数据库适合图查询，但不一定适合作为海量在线关注关系的唯一主库。
4. 粉丝数不能完全依赖实时强事务更新，热点用户会造成严重写冲突。
5. 共同好友、推荐关系可以离线或近线计算，不要阻塞关注主链路。

## 7. 面试回答模板

微博关注关系可以抽象成有向图的边。在线主链路我会用 MySQL 分库分表或 HBase/Cassandra 这类宽列 NoSQL 存正向边和反向边：正向边支持“我关注了谁”，反向边支持“谁关注了我”和 Feed 分发；Redis 用来缓存关注列表、关注状态和计数；图数据库更适合共同关注、关系推荐、风控等多跳查询，不一定作为在线权威源。关注取关要保证幂等和唯一约束，缓存和计数可以最终一致，通过 MQ、binlog、补偿和对账修复。大 V 场景要用推拉结合、粉丝分桶、热点缓存和异步计数，避免一次发帖写爆所有粉丝时间线。
