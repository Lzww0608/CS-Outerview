# 1. API 网关鉴权与 JWT

API 网关位于客户端和后端服务之间，常承担统一入口、鉴权、限流、路由、协议转换、审计和观测等职责。鉴权放在网关层的价值是把通用安全逻辑前置，避免每个业务服务重复实现。

## 1. 网关鉴权流程

典型流程：

```text
客户端请求
-> 网关提取 Authorization/Cookie/API-Key
-> 校验 token 签名、过期时间、issuer、audience
-> 解析用户身份、租户、角色和权限
-> 做路由级权限校验、限流和审计
-> 向后端传递可信用户上下文
```

常见鉴权方式：

1. Cookie + Session：服务端保存会话，撤销方便，适合浏览器传统业务。
2. JWT：签名后的自包含声明，服务端可无状态校验，适合多服务共享身份。
3. API Key + 签名：开放平台常用，配合 timestamp/nonce 防重放。
4. OAuth2/OIDC：第三方授权和统一身份体系常用。
5. mTLS：服务到服务强身份认证。

## 2. JWT 是什么

JWT 由三段组成：

```text
base64url(header).base64url(payload).base64url(signature)
```

1. Header：算法和 token 类型，例如 `alg=RS256`。
2. Payload：声明，例如 `sub、exp、iat、iss、aud、role、tenant_id`。
3. Signature：对前两段做签名，防止篡改。

网关收到 JWT 后，不是“解密”，而是“验签”。payload 默认只是 Base64URL 编码，不应放密码、身份证号等敏感明文。

## 3. 网关如何安全传递身份

网关校验通过后，会把用户上下文传给后端。常见做法：

1. 内部 Header：如 `X-User-Id、X-Tenant-Id、X-Roles`。
2. 内部 JWT：网关重新签发短期内部 token。
3. RPC metadata：gRPC 内部调用通过 metadata 传递身份。

关键是防止客户端伪造内部 Header。入口网关应先清理所有外部传入的内部 Header，再由网关重新注入；后端只信任来自网关或 service mesh 的请求，必要时配合 mTLS。

## 4. JWT 的撤销和续期

JWT 的缺点是默认难以主动撤销。常见方案：

1. Access Token 短有效期，Refresh Token 长有效期。
2. 黑名单保存 `jti`，用于踢下线或风险 token 撤销。
3. 用户表保存 `token_version`，修改密码或踢下线时递增版本。
4. 高风险操作二次校验，如短信、MFA、重新登录。
5. 密钥轮换：Header 中带 `kid`，网关从 JWKS 或配置中心获取公钥集合。

## 5. 易错点

1. JWT payload 不是密文，不能放敏感信息。
2. 不要信任客户端传来的 `alg`，网关应固定允许算法，避免 alg=none 或算法混淆问题。
3. 只验签不够，还要验 `exp、iss、aud、nbf` 等声明。
4. 网关鉴权不能替代服务内部的细粒度授权，后端仍要校验资源归属。
5. WebSocket 握手鉴权通过后，也要处理连接续期、踢下线和权限变化。

## 6. 面试回答模板

API 网关鉴权一般先从请求里提取 Cookie、JWT 或 API Key，校验签名、过期时间、issuer、audience 和权限，再把可信的用户上下文传给后端。JWT 是 `header.payload.signature` 三段结构，payload 是声明不是密文，安全性来自签名校验。网关校验后可以注入内部 Header 或 RPC metadata，但必须清理外部伪造的内部 Header，后端也只信任来自网关的流量。JWT 默认难撤销，工程上用短 access token、refresh token、黑名单、token version 和密钥轮换解决。
