# 1. 柜机存取系统设计

智能快递柜系统要解决的是“格口这种有限物理资源”的在线分配、投递、取件和异常回收问题。它和普通订单系统不同，核心难点在于线上状态必须和线下柜门、格口占用、取件凭证、超时任务保持一致。

## 1. 核心需求

投递端能力：

1. 快递员登录后选择站点、快递公司、包裹尺寸和收件人信息。
2. 系统分配可用格口，生成投递记录和取件凭证。
3. 柜机开门，快递员放入包裹并关门确认。
4. 投递成功后通知用户，例如短信、App Push 或小程序消息。

用户取件端能力：

1. 用户通过取件码、扫码、手机号后四位加验证码等方式验证身份。
2. 验证通过后打开对应格口。
3. 关门检测成功后，投递记录进入已取件状态，格口释放。

管理和异常处理：

1. 柜机、格口、库存、故障状态可维护。
2. 占柜后长时间未投递要自动释放。
3. 包裹长时间未取要提醒、计费、转人工或退回。
4. 柜门异常、断网、重复开门、取件失败要有人工处理入口和操作日志。

## 2. 核心数据模型

常见表设计：

```sql
CREATE TABLE locker_site (
  id BIGINT PRIMARY KEY,
  name VARCHAR(64) NOT NULL,
  address VARCHAR(255) NOT NULL,
  status VARCHAR(32) NOT NULL,
  created_at DATETIME NOT NULL,
  updated_at DATETIME NOT NULL
);

CREATE TABLE locker_box (
  id BIGINT PRIMARY KEY,
  site_id BIGINT NOT NULL,
  box_no VARCHAR(32) NOT NULL,
  size VARCHAR(16) NOT NULL,
  status VARCHAR(32) NOT NULL,
  current_delivery_id BIGINT NULL,
  lock_until DATETIME NULL,
  version BIGINT NOT NULL,
  UNIQUE KEY uk_site_box (site_id, box_no),
  KEY idx_site_size_status (site_id, size, status)
);

CREATE TABLE delivery_record (
  id BIGINT PRIMARY KEY,
  package_no VARCHAR(64) NOT NULL,
  courier_id BIGINT NOT NULL,
  user_id BIGINT NULL,
  user_phone_hash VARCHAR(128) NOT NULL,
  site_id BIGINT NOT NULL,
  box_id BIGINT NOT NULL,
  status VARCHAR(32) NOT NULL,
  reserved_at DATETIME NOT NULL,
  delivered_at DATETIME NULL,
  picked_at DATETIME NULL,
  expire_at DATETIME NOT NULL,
  UNIQUE KEY uk_package_no (package_no),
  KEY idx_site_status_expire (site_id, status, expire_at),
  KEY idx_user_status (user_id, status)
);

CREATE TABLE pickup_credential (
  id BIGINT PRIMARY KEY,
  delivery_id BIGINT NOT NULL,
  credential_hash VARCHAR(128) NOT NULL,
  status VARCHAR(32) NOT NULL,
  expire_at DATETIME NOT NULL,
  failed_count INT NOT NULL,
  UNIQUE KEY uk_delivery (delivery_id),
  UNIQUE KEY uk_credential_hash (credential_hash)
);

CREATE TABLE locker_event (
  id BIGINT PRIMARY KEY,
  delivery_id BIGINT NULL,
  box_id BIGINT NOT NULL,
  event_type VARCHAR(32) NOT NULL,
  operator_id BIGINT NULL,
  request_id VARCHAR(64) NOT NULL,
  created_at DATETIME NOT NULL,
  UNIQUE KEY uk_request (request_id)
);
```

设计要点：

1. `locker_box` 表表达物理格口状态，`delivery_record` 表表达包裹业务状态，二者不要混成一张表。
2. 关键写操作记录 `locker_event`，用于审计、排查和幂等。
3. 手机号、取件码等敏感信息不要明文存储，至少做哈希、脱敏或加密。
4. `request_id` 用于防止柜机断网重试、前端重复点击导致重复投递或重复取件。

## 3. 状态机设计

格口状态可以简化为：

```text
EMPTY -> RESERVED -> OCCUPIED -> EMPTY
             |           |
             v           v
          EMPTY       FAULT
```

投递记录状态可以简化为：

```text
CREATED -> RESERVED -> DELIVERED -> PICKED_UP
              |             |
              v             v
          CANCELLED      EXPIRED -> RETURNING -> RETURNED
```

状态更新要使用条件更新，避免并发覆盖：

```sql
UPDATE delivery_record
SET status = 'PICKED_UP', picked_at = NOW()
WHERE id = ?
  AND status = 'DELIVERED';
```

如果影响行数为 0，说明状态已经被其他请求推进，当前请求要按幂等结果处理，而不是继续强行开门或释放格口。

## 4. 投递流程

典型投递流程：

1. 快递员提交 `package_no`、尺寸、收件人信息和幂等 `request_id`。
2. 服务端校验包裹是否已投递，校验快递员权限和站点状态。
3. 按站点和尺寸选择空格口，写入 `delivery_record`，把格口从 `EMPTY` 改成 `RESERVED`。
4. 调用柜机控制服务开门。
5. 柜机上报关门成功后，投递记录从 `RESERVED` 改成 `DELIVERED`，格口从 `RESERVED` 改成 `OCCUPIED`。
6. 生成取件通知，异步发送给用户。

并发分配格口时，不能先查出空格口再无条件更新。可以用行锁或条件更新：

```sql
SELECT id
FROM locker_box
WHERE site_id = ?
  AND size = ?
  AND status = 'EMPTY'
ORDER BY id
LIMIT 1
FOR UPDATE SKIP LOCKED;
```

拿到格口后在同一个事务内更新：

```sql
UPDATE locker_box
SET status = 'RESERVED',
    current_delivery_id = ?,
    lock_until = DATE_ADD(NOW(), INTERVAL 5 MINUTE),
    version = version + 1
WHERE id = ?
  AND status = 'EMPTY';
```

`SKIP LOCKED` 适合 MySQL 8 或 PostgreSQL。没有这个能力时，可以用乐观锁版本号、Redis 分布式锁或格口分配服务串行化热点站点，但最终仍要靠数据库条件更新兜底。

## 5. 长时间未投递怎么处理

“占柜后未投递”通常发生在格口已预占、柜门已打开，但快递员没有放入包裹或没有关门确认。

处理方式：

1. 预占时设置短 TTL，例如 3 到 5 分钟。
2. 后台任务扫描 `RESERVED AND lock_until < NOW()` 的格口和投递记录。
3. 如果柜门状态确认已关闭且无重量/红外占用，释放格口并取消投递记录。
4. 如果柜门未关闭或传感器异常，进入人工工单，避免误释放真实包裹。
5. 所有释放动作都要条件更新和记录事件，保证重复扫描不会产生副作用。

示例：

```sql
UPDATE locker_box
SET status = 'EMPTY',
    current_delivery_id = NULL,
    lock_until = NULL,
    version = version + 1
WHERE id = ?
  AND status = 'RESERVED'
  AND lock_until < NOW();
```

## 6. 包裹长时间未取怎么处理

包裹长时间未取不能只做一条定时删除记录。它涉及用户通知、计费、人工清柜和格口释放。

常见策略：

1. 投递成功后设置 `expire_at`，例如 24 小时或 48 小时。
2. 到期前发送提醒，到期后限制免费取件或产生滞留费。
3. 超过最大保管期进入 `EXPIRED` 或 `RETURNING`，通知快递员或运营人员清柜。
4. 人工清柜时扫码确认包裹，状态改为 `RETURNED`，格口释放。
5. 用户已经取件但状态未回传时，要通过柜机事件、门磁、重量传感器和人工复核修正。

真实系统里，超时任务要按站点分片扫描，并使用 `(status, expire_at, id)` 或 `(site_id, status, expire_at)` 索引，避免全表扫描。

## 7. 取件码设计

取件码不能“随便随机生成”，原因包括：

1. **唯一性**：同一有效期内不能两个包裹共用同一个取件码。
2. **安全性**：过短或递增的取件码容易被枚举撞库。
3. **有效期**：取件码要有 TTL，取件后立即失效。
4. **绑定关系**：取件码应绑定站点、包裹、用户或手机号校验，不能拿到码就能跨站取件。
5. **失败限制**：同一柜机、手机号、IP 或设备连续输错要限流或锁定。
6. **存储安全**：服务端保存哈希值，不保存明文取件码。

一种常见设计是“短随机码 + 站点维度唯一 + 有效期 + 失败次数限制”。例如 6 位数字码对用户友好，但熵不高，所以必须限制站点范围、有效期和尝试次数。更高安全场景可以使用二维码 token 或一次性签名链接。

注意：连续递增编号适合作为内部业务流水或柜机显示序号，不适合作为唯一取件密码。取件凭证如果可预测，会带来撞码风险。

## 8. 编号和并发唯一

如果业务要求生成不重复且连续递增的编号，要先确认“连续”的含义：

1. 如果只是趋势递增，Snowflake、号段模式、数据库自增都可以。
2. 如果要求严格连续且不能跳号，就必须接受集中式串行化和可用性下降。
3. 如果编号对用户可见，还要考虑是否会泄露业务量。

柜机系统可以把外部取件凭证和内部流水号分开：

1. `delivery_id` 用分布式 ID，保证全局唯一和趋势递增。
2. `display_no` 用站点内递增号，便于运营查询。
3. `pickup_code` 用安全随机码或 token，保证不可预测。

站点内连续编号可以用单行序列表：

```sql
UPDATE site_sequence
SET current_value = LAST_INSERT_ID(current_value + 1)
WHERE site_id = ? AND seq_name = 'delivery_display_no';

SELECT LAST_INSERT_ID();
```

MySQL 会对被更新的序列行加锁，并发请求串行通过该行，从而保证同一站点内唯一递增。高并发下可以按站点分散锁热点，或者使用号段模式提升吞吐，但号段模式在服务宕机时可能出现跳号。

## 9. 可用性和真实场景

柜机系统必须考虑弱网和硬件异常：

1. 柜机端要支持本地缓存必要配置和离线事件队列。
2. 服务端命令要有超时、重试和幂等 `request_id`。
3. 开门成功但服务端超时，要依赖柜机事件回传修正状态。
4. 柜门、锁控板、摄像头、重量传感器异常要进入故障状态，停止分配该格口。
5. 关键链路要有监控：可用格口数、投递成功率、取件失败率、开门耗时、超时占柜数、清柜任务积压。

扩展方向：

1. 使用 MQ 解耦通知、超时扫描、运营工单和数据分析。
2. 使用配置中心下发站点规则，例如保管时长、收费策略、节假日策略。
3. 使用风控模型识别撞码、频繁失败、异常开门和疑似盗取。
4. 使用数字孪生或设备管理平台统一管理柜机固件、在线状态和远程诊断。

## 10. 面试回答模板

我会把快递柜系统拆成柜机站点、格口、投递记录、取件凭证和事件日志几类核心模型。格口是有限物理资源，要用状态机管理 `EMPTY/RESERVED/OCCUPIED/FAULT`；投递记录用 `RESERVED/DELIVERED/PICKED_UP/EXPIRED` 推进。投递时先用行锁或条件更新分配空格口，再开门，关门确认后才算投递成功；长时间未投递通过短 TTL 释放预占格口，长时间未取通过提醒、过期、清柜和退回流程处理。取件码不能随便随机生成，要保证有效期内唯一、不可预测、绑定站点和包裹、失败限流，并且服务端只存哈希。连续递增编号适合内部流水，不适合做取件密码；并发下靠数据库序列表、行锁、唯一索引和幂等请求兜底。
