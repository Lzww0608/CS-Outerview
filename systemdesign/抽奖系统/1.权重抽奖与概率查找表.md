# 1. 权重抽奖与概率查找表

权重抽奖是指每个奖品有一个权重或概率，系统按权重随机选择奖品。它常出现在营销活动、积分抽奖、优惠券发放、AB 实验流量分配等场景。

## 1. 基础做法：前缀和

把每个奖品的概率转换成整数权重，然后构造前缀和数组。

```text
奖品 A 权重 10
奖品 B 权重 30
奖品 C 权重 60

前缀和：
A: 10
B: 40
C: 100
```

抽奖时生成 `[1, totalWeight]` 的随机数 `r`，找到第一个 `prefix[i] >= r` 的奖品。

```cpp
#include <algorithm>
#include <random>
#include <vector>

struct Prize {
    int id;
    int weight;
};

class WeightedLottery {
public:
    explicit WeightedLottery(const std::vector<Prize>& prizes) {
        int sum = 0;
        for (const Prize& prize : prizes) {
            if (prize.weight <= 0) {
                continue;
            }
            sum += prize.weight;
            ids_.push_back(prize.id);
            prefix_.push_back(sum);
        }
        total_ = sum;
    }

    int draw(std::mt19937& gen) const {
        std::uniform_int_distribution<int> dist(1, total_);
        int r = dist(gen);
        auto it = std::lower_bound(prefix_.begin(), prefix_.end(), r);
        return ids_[it - prefix_.begin()];
    }

private:
    std::vector<int> ids_;
    std::vector<int> prefix_;
    int total_ = 0;
};
```

复杂度：

```text
构建：O(n)
抽奖：O(log n)
空间：O(n)
```

## 2. 离散化查找表

如果总权重不大，可以把奖品按权重展开成数组：

```text
[A, A, ..., B, B, ..., C, C, ...]
```

随机生成数组下标即可得到奖品，抽奖是 `O(1)`。

优点：

1. 查询极快。
2. 实现简单。
3. 适合奖品种类少、权重总和小、概率精度有限的场景。

缺点：

1. 内存是 `O(totalWeight)`，总权重或精度放大后会很大。
2. 奖品种类多时构建成本和更新成本高。
3. 概率精度越高，数组越大。

例如概率精度要到百万分之一，离散表可能需要百万级槽位；活动多时本地内存和 Redis 内存都会被放大。

## 3. 奖品种类很多时怎么办

当奖品种类很多，或者概率精度很高时，不适合用完全展开的概率查找表。可选方案：

| 方案 | 查询复杂度 | 空间 | 适用场景 |
| --- | --- | --- | --- |
| 前缀和 + 二分 | `O(log n)` | `O(n)` | 权重静态，奖品较多 |
| Redis ZSet 区间 | `O(log n)` | `O(n)` | 需要集中存储和跨实例共享 |
| Alias Method | `O(1)` | `O(n)` | 权重静态，高频抽奖 |
| Fenwick Tree | `O(log n)` | `O(n)` | 权重动态变化 |
| Segment Tree | `O(log n)` | `O(n)` | 权重动态变化且需要区间统计 |
| 分层抽奖 | 取决于层数 | 可控 | 奖品按类目、等级、活动分组 |

### Alias Method

Alias Method 会把每个奖品拆成“主奖品 + 别名奖品 + 阈值”。构建成本 `O(n)`，抽奖时：

1. 随机选择一个桶。
2. 再生成一个小数。
3. 小数小于阈值返回主奖品，否则返回 alias 奖品。

它适合权重更新不频繁、抽奖 QPS 很高的场景。缺点是构建逻辑比前缀和复杂，权重变化后通常要重建。

### Redis ZSet 区间

可以把前缀和右边界作为 score，奖品 ID 作为 member：

```text
ZADD lottery:1001:prefix 10 A 40 B 100 C
```

抽奖时生成随机数 `r`，查询第一个 score 大于等于 `r` 的 member。Redis 版本和命令组合不同，实际实现可用 `ZRANGEBYSCORE key r +inf LIMIT 0 1`，或新版本按 score 范围查询。

这种方式适合多实例共享查找表，但每次抽奖都访问 Redis，QPS 很高时会增加网络开销。高频活动可以把 ZSet 或序列化表加载到本地内存。

## 4. 库存和概率的关系

概率命中奖品不等于一定发奖成功。真实抽奖还要考虑库存：

```text
概率命中奖品
-> Redis Lua 原子扣库存
-> 扣减成功，生成中奖记录
-> 扣减失败，走未中奖、兜底奖品或重新抽
```

常见策略：

1. **先抽奖后扣库存**：简单，但命中无库存奖品后要兜底。
2. **只把有库存奖品放入概率表**：命中更准，但库存变化后需要频繁更新表。
3. **奖池分层**：大奖单独控制，小奖或兜底奖走稳定概率。
4. **库存预扣 + 异步发奖**：高并发下减少数据库写压力。

不要只靠概率控制库存。概率只能控制期望发放量，不能保证不超发；不超发必须靠库存原子扣减或数据库条件更新。

## 5. 真实场景设计

一个活动抽奖链路可以设计为：

```text
活动发布
-> 预热奖品配置、库存、概率表到 Redis
-> 应用本地加载当前活动概率表
-> 用户请求进入后做资格校验和幂等校验
-> 本地概率表命中奖品
-> Redis Lua 扣库存和记录参与
-> 写中奖记录 / MQ 异步发奖
-> 返回结果
```

这样本地内存承担高频只读的概率计算，Redis 承担跨实例共享的库存、幂等和活动状态。

## 6. 易错点

1. 概率要用整数权重处理，避免浮点误差。
2. 总权重要校验，不能出现 0 或负数。
3. 离散表不能盲目提高精度，否则内存会线性膨胀。
4. 权重变化后要用版本号切换，避免请求同时读到新旧表。
5. 抽奖随机数要使用合适的伪随机生成器，不要用低质量随机导致分布偏斜。
6. 库存扣减必须是原子操作，不能只依赖本地概率结果。

## 7. 面试回答模板

权重抽奖可以先把概率离散成整数权重。奖品少、总权重小的时候，可以展开成概率查找表，随机下标 `O(1)` 命中奖品；但奖品种类多或精度高时，展开表会占用大量内存，构建和更新成本也高。更通用的方案是前缀和加二分，构建 `O(n)`、抽奖 `O(log n)`、空间 `O(n)`；高 QPS 且权重静态可以用 Alias Method 做到 `O(1)`；权重动态变化可以用树状数组或线段树。真实系统中概率表只决定命中结果，最终能否发奖还要通过 Redis Lua 或数据库条件更新做库存原子扣减。
