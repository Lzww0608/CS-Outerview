# 6.需求、接口与跨端协作

项目追问里经常会问“需求和实现怎么平衡”“先分析需求还是先定义接口”“和前端怎么沟通”“已有云厂商服务为什么还要做”。这些问题虽然偏项目经验，但回答要落到工程方法和技术取舍上。

## 1. 先分析需求还是先定义接口

通常先分析需求，再定义接口；但不是等所有需求完全确定后才写接口，而是先把核心场景、边界和验收标准弄清楚，再用接口草案反向验证需求是否完整。

合理顺序：

1. **业务目标**：这个功能服务谁，解决什么问题，成功指标是什么。
2. **核心流程**：主链路、异常链路、权限边界、幂等边界。
3. **数据模型**：核心实体、状态机、字段来源、生命周期。
4. **接口契约**：请求参数、响应结构、错误码、分页、排序、超时和幂等键。
5. **验收标准**：正常场景、边界场景、性能指标、降级策略。
6. **迭代切分**：先交付最小闭环，再补管理面、观测和优化。

接口设计不能只看字段够不够，还要看调用方能否稳定使用，后续能否兼容演进。

## 2. 接口设计检查清单

1. **语义清晰**：URL、方法名、字段名表达业务含义，不暴露内部实现细节。
2. **版本兼容**：新增字段默认兼容，删除/改语义要走版本迁移。
3. **错误码稳定**：区分参数错误、权限错误、资源不存在、冲突、限流、内部错误。
4. **幂等设计**：创建、支付、扣减、任务提交等接口需要幂等键或业务唯一键。
5. **分页与排序**：大列表不要一次全量返回，游标分页比深 offset 更稳定。
6. **超时与重试**：接口要定义超时语义，调用方只对幂等请求重试。
7. **可观测性**：请求 ID、用户 ID、资源 ID、耗时和错误码要能串起来。

接口文档可以使用 OpenAPI/Swagger、JSON Schema、Protobuf IDL 或 Markdown 表格。关键是前后端都以同一份契约为准，并配 mock 数据和联调用例。

## 3. 和前端沟通

跨端协作的问题通常不是“谁等谁”，而是契约不清、状态不清、异常不清。

有效做法：

1. 在开发前共同确认页面状态：加载中、空状态、无权限、部分失败、提交中、重复提交。
2. 接口返回结构保持稳定，业务字段缺失时明确是空数组、`null` 还是不返回。
3. 错误信息分层：机器读错误码给前端判断，人读提示文案可由前端按场景处理。
4. 提供 mock server 或静态样例，前后端并行开发。
5. 联调时优先跑主链路，再补边界；问题用请求 ID 和日志定位，不靠口头猜测。

## 4. 性能对比和压测

面试里问“有没有对比过性能”，可以从基线、指标和结论回答。

1. **基线**：旧实现、开源方案、云厂商方案或最简单实现。
2. **指标**：QPS、P50/P95/P99 延迟、错误率、CPU、内存、网络、冷启动时间、队列堆积。
3. **场景**：单用户、并发峰值、突发流量、长连接、慢下游、缓存失效。
4. **方法**：固定机器规格、固定数据集、预热后压测，多轮取稳定结果。
5. **结论**：说明瓶颈在哪里，优化后提升多少，还有哪些风险没有覆盖。

不要只说“性能更好”，要说在哪个指标、更适合哪个场景、用什么代价换来的。

## 5. Build or Buy 取舍

当 AWS、阿里云或开源项目已经有类似服务时，自己做的理由必须明确：

1. **私有化或合规**：数据不能出内网，或者需要部署在客户环境。
2. **定制需求**：云产品不支持特殊调度、协议、运行时、权限或计费模型。
3. **成本控制**：高频调用或大规模资源下，自建可能更便宜。
4. **系统集成**：需要和公司内部账号、网关、监控、发布系统深度打通。
5. **学习和验证**：原型阶段为理解问题和验证技术路线，后续再决定替换或融合。

如果只是重复已有能力，没有明确差异和收益，就应该优先复用成熟方案。

## 6. 短期学习语言并完成项目

短时间学习语言做项目，应围绕交付路径而不是从语法书第一页开始：

1. 先跑通官方 quick start 和项目骨架。
2. 学会包管理、测试、日志、配置、HTTP/RPC、数据库访问和调试工具。
3. 找一个成熟项目模仿目录结构、错误处理和工程规范。
4. 对核心语法、并发模型、内存模型和常见坑做专项补课。
5. 每天沉淀可复用脚手架、FAQ 和排错记录。

## 7. 面试回答模板

我会先分析需求，再定义接口，但接口草案会很早拿出来和前端、调用方对齐。需求阶段先明确业务目标、核心流程、状态机、异常链路和验收指标；接口阶段把参数、响应、错误码、幂等、分页、超时和版本兼容写清楚。联调时用 mock 和请求 ID 提高效率。

如果外部已有类似服务，我会先做 Build or Buy 分析：是否有私有化、成本、定制化、内部系统集成或性能目标上的差异。如果没有明确收益，就复用成熟方案；如果有，就把自研范围控制在真正有差异的部分，并通过压测和指标证明价值。
