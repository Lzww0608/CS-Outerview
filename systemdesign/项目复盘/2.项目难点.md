# 2.项目难点怎么讲

项目难点不要只说“技术栈不熟”或“开发周期紧”。面试官更关心的是：问题是否真实、你是否定位过根因、方案是否有取舍、结果是否可量化。

## 1. 回答结构

可以用下面的结构：

```text
背景 -> 问题 -> 根因 -> 方案 -> 取舍 -> 结果 -> 复盘
```

对应到面试回答：

1. **背景**：这个模块在系统里承担什么职责。
2. **问题**：遇到的具体故障、性能瓶颈或一致性问题是什么。
3. **根因**：通过日志、指标、压测、执行计划等方式定位到了什么。
4. **方案**：你做了哪些改动。
5. **取舍**：为什么没选其他方案。
6. **结果**：延迟、吞吐、错误率、资源占用有没有变化。
7. **复盘**：后续怎么避免同类问题。

## 2. 适合作为难点的方向

### 2.1 性能瓶颈

例子：

```text
接口 P99 延迟升高 -> 通过 trace 发现数据库查询慢 -> EXPLAIN 发现索引没命中
-> 调整联合索引和查询条件 -> 增加缓存 -> P99 从 800ms 降到 120ms
```

回答时要讲清楚：

1. 慢在哪里，是 CPU、I/O、锁竞争、网络还是外部依赖。
2. 怎么定位，不要只说“看日志”。
3. 优化后有没有副作用，例如缓存一致性、索引写入成本。

### 2.2 数据一致性

例子：

```text
数据库更新成功，但异步消息发送失败，导致下游状态不一致
```

可以讲：

1. 本地事务只保证数据库更新。
2. MQ 发送失败会让下游看不到事件。
3. 解决方案可以是本地消息表、事务消息、可靠重试、补偿任务。
4. 消费端需要幂等，避免重试导致重复写。

### 2.3 高并发和热点问题

例子：

```text
热点 key 被大量请求击中，Redis 或数据库压力异常
```

可以讲：

1. 热点 key 拆分或本地缓存。
2. 请求合并，避免缓存击穿时大量请求打到数据库。
3. 限流、降级、熔断保护核心链路。
4. 对特别高频的布尔判断，可以考虑 Bitmap 或 Bloom Filter。

### 2.4 异步任务可靠性

例子：

```text
任务执行失败后没有补偿，或者 worker 重启导致任务丢失
```

可以讲：

1. 任务状态机：待执行、执行中、成功、失败、重试中。
2. 重试次数和退避策略。
3. 幂等 key，避免重复执行造成副作用。
4. 超时扫描，把长时间执行中的任务重新投递。

### 2.5 可观测性不足

例子：

```text
线上偶发慢请求，单机日志很难串起完整链路
```

可以讲：

1. 引入 trace id，把入口、服务、DB、MQ、外部调用串起来。
2. 为核心路径加指标：QPS、错误率、P95/P99、队列堆积、缓存命中率。
3. 告警按影响面分级，避免只靠用户反馈发现问题。

## 3. 面试回答模板

我遇到的一个主要难点是核心链路在高峰期延迟不稳定。最开始只看到接口 P99 上升，后来通过 trace 拆分耗时，发现主要卡在数据库查询和缓存击穿后的并发回源。进一步用 `EXPLAIN` 看执行计划，发现部分查询没有命中合适的联合索引，同时热点数据过期后大量请求同时打到数据库。

我的处理方式是三步：第一，调整索引和查询条件，让主查询稳定命中索引；第二，对热点数据增加缓存预热和互斥回源，避免同一时刻大量请求穿透；第三，补充核心指标和慢查询日志，方便后续提前发现问题。这个方案的取舍是增加了一些缓存一致性维护成本，但换来了主链路延迟和数据库负载的稳定性。

## 4. 不推荐的回答

1. “难点是第一次用某个框架。”
2. “难点是需求经常变。”
3. “难点是代码很多。”
4. “难点是我花了很多时间调 bug。”

这些回答可以作为背景，但不能作为核心难点。真正的难点最好能落到并发、性能、一致性、稳定性、可观测性、工程取舍上。

## 5. 项目重构怎么讲

面试里问“项目难点，如何重构”，不要回答“把代码整理了一下”。重构要围绕可维护性、可测试性、性能或稳定性问题展开。

### 5.1 什么时候需要重构

常见触发点：

1. 一个类或函数承担太多职责，改一处影响多处。
2. 业务逻辑和 UI、网络、存储耦合，无法单测。
3. 重复代码多，同类 bug 反复出现。
4. 状态机散落在多个分支，边界情况不可控。
5. 性能瓶颈来自不合理的数据结构或同步方式。
6. 新需求总是要改旧流程，说明扩展点不清晰。

### 5.2 重构步骤

可靠顺序：

```text
补观测和测试 -> 梳理职责边界 -> 小步抽象 -> 灰度替换 -> 删除旧代码
```

具体做法：

1. 先补单测、接口测试、关键日志和指标，确保能判断行为是否变化。
2. 画出核心调用链和数据流，找出真正变化频繁的点。
3. 抽出稳定接口，把 UI、业务、存储、网络解耦。
4. 大函数拆成小函数，大类拆成领域对象、服务和适配器。
5. 用策略、工厂、责任链等模式处理明确变化点，但不为未知变化过度设计。
6. 保留旧逻辑开关或兼容层，分阶段替换。
7. 重构完成后删除废弃路径，补文档和回归用例。

### 5.3 重构风险

1. 没有测试就大改，容易引入回归。
2. 只追求“设计漂亮”，没有解决真实问题。
3. 抽象层过多，导致调用链更难理解。
4. 新旧逻辑长期并存，维护成本翻倍。
5. 忽略性能，对象拆分和虚调用可能影响热点路径。

### 5.4 面试回答模板

我会先说明为什么要重构：例如模块职责混在一起、状态机分散、重复代码导致 bug 多，或新需求扩展成本高。重构前先补测试和日志，确保有回归保护；然后梳理核心链路，把稳定接口和变化点分开，把 UI、业务、存储、网络拆成更清晰的边界。重构过程小步提交，每一步都能编译和回归，通过开关或兼容层逐步替换旧逻辑。重构后用指标说明收益，比如代码重复减少、核心函数复杂度下降、单测覆盖提升、缺陷率或开发周期下降。
