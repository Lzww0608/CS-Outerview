# 9.DAG 执行框架算子融合与调度

面试里问“DAG 执行框架”“算子融合”“调度优先级”，重点是看你是否理解一个复杂任务如何从静态依赖图变成可执行计划，以及如何在吞吐、延迟、资源隔离之间做取舍。

## 1. DAG 执行框架是什么

DAG 是有向无环图。一个业务请求可以拆成多个算子，每个算子是一个独立计算单元，边表示数据依赖或控制依赖。

```text
Query Parse
  -> Recall A
  -> Recall B
  -> Feature Join
  -> Rank
  -> Filter
  -> Response
```

DAG 执行框架的职责：

1. 根据配置或代码构建算子依赖图。
2. 校验图中是否有环、缺失输入、重复输出等问题。
3. 找出当前依赖已满足的 ready 节点。
4. 把 ready 节点投递到线程池、协程调度器或远程执行器。
5. 收集结果并触发后继节点。
6. 处理超时、失败、降级和取消。

## 2. 核心原理

常见实现会维护每个节点的入度计数：

```text
node.in_degree = 未完成前置依赖数量
前置节点完成 -> 后继节点 in_degree--
in_degree == 0 -> 节点进入 ready queue
```

执行时需要保存上下文：

1. 请求级上下文：trace id、用户 id、超时时间、取消标志。
2. 算子输入输出：每个节点读取哪些 key，写出哪些 key。
3. 资源标签：CPU 密集、I/O 密集、远程 RPC、可降级、强依赖。
4. 统计信息：排队耗时、执行耗时、失败原因、命中降级策略。

## 3. 算子融合是什么

算子融合是把多个相邻的小算子合并成一个执行单元，减少调度、内存读写和中间结果构造成本。

适合融合的场景：

1. 上下游是一对一关系，中间结果只被一个后继使用。
2. 算子很轻，单独调度成本接近或超过计算成本。
3. 数据局部性强，融合后可以少一次序列化、拷贝或哈希查找。
4. 错误处理和降级语义一致。

不适合融合的场景：

1. 下游被多个上游复用，融合会造成重复计算。
2. 算子耗时差异大，融合后慢节点拖住整条链路。
3. 中间结果需要被观测、缓存或调试。
4. 一个节点可降级，另一个节点不可降级，融合会模糊语义。

工程上常见做法是先做静态融合候选，再根据线上 profile 决定是否开启。不能只凭“节点多”就融合，真正依据应该是调度开销、数据拷贝开销、缓存命中率和 P99 延迟。

## 4. 调度优先级怎么设计

调度器不能只用 FIFO。常见优先级因素：

1. **关键路径长度**：处在最长依赖链上的节点优先执行，降低整体完成时间。
2. **截止时间**：请求剩余时间越短，越需要优先处理或提前降级。
3. **资源类型**：CPU 密集和 I/O 密集分池，避免互相挤占。
4. **业务等级**：核心请求、付费用户、召回主链路优先级更高。
5. **失败影响**：强依赖节点优先于可选补充节点。
6. **历史耗时**：长尾算子可以提前调度，避免最后拖住响应。

一个实用策略是“就绪队列 + 优先级队列 + 超时控制”：

```text
ready node
-> 根据 deadline / critical path / resource tag 计算 priority
-> 投递到对应执行队列
-> 节点完成后更新后继依赖
-> 请求超时则取消未开始节点，正在执行节点尽量快速返回
```

## 5. 易错点

1. DAG 必须无环，配置化 DAG 要在启动或发布前做拓扑校验。
2. 不能让节点隐式读写全局状态，否则依赖图看起来无环，实际数据依赖不可控。
3. 执行器要支持取消和超时，否则请求已经返回，后台任务还会继续消耗资源。
4. 算子融合提升性能的同时会降低可观测性，需要保留 trace 和 debug 开关。
5. 调度优先级不能导致低优先级节点长期饥饿，必要时要做 aging。

## 6. 真实场景应用

广告、推荐、搜索召回系统经常使用 DAG：

1. 多路召回可以并行执行。
2. 特征补全依赖召回结果。
3. 粗排、精排、过滤是串行链路。
4. 非核心召回源可以超时丢弃，核心召回源失败才影响整体响应。

在这类场景里，DAG 框架能把“业务拓扑”和“执行调度”分离。业务同学新增一路召回时只需要声明输入输出和依赖关系，框架负责并发、超时、降级、监控和结果汇总。

## 7. 面试回答模板

DAG 执行框架把请求拆成多个有依赖关系的算子，用拓扑排序或入度计数找出依赖已满足的节点并并发执行。调度时不能只按 FIFO，要考虑关键路径、deadline、资源类型、业务优先级和节点可降级性。算子融合是把轻量、上下游一对一、数据局部性强的算子合并，减少调度和中间结果开销；但融合会降低可观测性，也不适合多消费者、耗时差异大或错误语义不同的节点。真实系统还要配套超时、取消、trace、资源隔离和发布前 DAG 校验。
