# 3. 实习项目追问准备

## 1. 面试官问项目时在看什么

实习项目追问通常不是为了听你复述简历，而是判断：

1. 你是否真正参与了核心模块。
2. 你是否理解上下游链路，而不是只写局部代码。
3. 你是否能解释技术选型和取舍。
4. 你是否定位过真实问题，并能量化结果。
5. 你是否知道系统的边界、风险和后续优化方向。

## 2. 项目介绍顺序

可以按下面顺序准备 2 到 3 分钟版本：

```text
背景 -> 目标 -> 架构 -> 我的职责 -> 核心难点 -> 结果 -> 复盘
```

示例结构：

1. **背景**：这个项目服务什么业务，为什么要做。
2. **目标**：延迟、吞吐、稳定性、成本或体验上的目标。
3. **架构**：入口、业务服务、存储、缓存、消息、任务、监控。
4. **我的职责**：负责哪个模块、哪些接口、哪些表或哪些任务。
5. **核心难点**：性能、一致性、并发、可用性、兼容性、数据质量。
6. **结果**：上线范围、指标变化、问题修复、用户或业务收益。
7. **复盘**：如果重做，会怎么改。

## 3. 高频追问

### 3.1 你负责的模块在整体链路中的位置

要能画出一条请求链路：

```text
Client -> Gateway -> Service A -> Redis/MySQL/MQ -> Worker -> Downstream
```

并说清楚你的模块输入是什么、输出是什么、失败会影响谁。

### 3.2 为什么这样设计

不要只说“组里就是这么做的”。可以从这些角度回答：

1. 数据量和 QPS 是否需要缓存。
2. 是否需要异步解耦。
3. 是否需要事务一致性。
4. 是否允许最终一致。
5. 是否有历史系统兼容要求。

### 3.3 为什么 gRPC + Kafka 解耦，而不是纯 gRPC

如果项目里同时用了 gRPC 和 Kafka，可以按“同步请求”和“异步事件”的边界解释：

1. **gRPC 适合强交互同步调用**：例如查询用户状态、创建主订单、同步校验权限，调用方需要立即拿到结果。
2. **Kafka 适合异步解耦和削峰**：例如通知、审计、搜索索引更新、报表同步、下游慢任务，不应该阻塞主链路。
3. **纯 gRPC 的问题**：下游服务慢、抖动或不可用会把调用方线程池和连接池拖住，形成级联故障；高峰流量也会直接打到下游。
4. **Kafka 的代价**：链路变成最终一致，需要处理重复消费、消息延迟、乱序、死信和对账。
5. **回答重点**：不是“Kafka 比 gRPC 好”，而是同步强一致路径用 gRPC，异步最终一致路径用 Kafka。

一个回答模板：

```text
主链路需要立即返回、强依赖结果的地方我用 gRPC；耗时、可重试、可最终一致的副作用用 Kafka。
这样下游抖动不会直接拖垮入口服务，活动高峰也能通过队列削峰。
代价是系统要补幂等、重试、死信、补偿和监控，所以我会用业务唯一键、状态机条件更新和 lag 告警兜底。
```

面试追问“为什么不全部用 Kafka”时，要补充：用户同步等待的结果、权限校验、库存/余额这类需要明确成功失败的操作不能只靠异步消息；否则前端体验、错误处理和一致性边界都会变复杂。

### 3.4 双阶段流程为什么这样做

如果项目里有“双阶段流程”，回答时不要只说“先做 A，再做 B”，要解释拆分边界和收益。常见双阶段包括：

1. **同步校验 + 异步处理**：主链路只做参数、权限、幂等和必要落库，耗时计算、通知、发奖、同步下游放到异步 worker。
2. **召回 + 精排**：先用低成本方法召回候选集，再用更复杂模型或规则精排，兼顾性能和效果。
3. **预处理 + 提交**：先解析、校验、生成计划，用户确认或系统审批后再真正执行，适合高风险操作。
4. **写入 + 对账补偿**：在线写入保证主流程成功，后台对账发现不一致后重试、补偿或人工处理。

解释模板：

```text
第一阶段解决快速判断和主链路稳定性，第二阶段解决耗时、复杂或可最终一致的事情。
两个阶段之间用明确的状态机、任务表或消息队列衔接，并通过幂等 key、重试、死信、对账和监控保证可靠性。
```

需要讲清楚：

1. **为什么拆**：降低主链路延迟、隔离失败、削峰、支持人工审批或提升算法效果。
2. **阶段边界**：每个阶段输入输出是什么，哪些状态可以进入下一阶段。
3. **数据契约**：阶段间传递任务 ID、版本号、幂等 key、状态和错误原因，不只传自然语言描述。
4. **失败处理**：第一阶段失败直接返回；第二阶段失败要可重试、可补偿、可查。
5. **一致性取舍**：哪些结果必须强一致，哪些允许最终一致，用户侧如何展示中间状态。
6. **观测指标**：阶段成功率、队列堆积、重试次数、补偿数量、端到端耗时。

易错点是把双阶段讲成“为了代码清晰”。更好的回答是：它把用户同步等待的路径缩短，把高成本或高风险动作放到可重试、可监控、可回滚的后台链路里。

### 3.5 遇到过什么问题

优先准备真实问题：

1. 慢 SQL 或索引失效。
2. 缓存击穿、热点 key、大 key。
3. MQ 重复消费或消息堆积。
4. 接口超时和重试风暴。
5. 数据不一致和补偿。
6. 灰度发布或回滚。

回答时使用：

```text
现象 -> 定位 -> 根因 -> 方案 -> 结果
```

### 3.6 指标是多少

至少准备这些指标中的几个：

1. QPS / TPS。
2. P95 / P99 延迟。
3. 数据量、表大小、缓存 key 数量。
4. 错误率、超时率。
5. MQ 堆积量。
6. 资源消耗：CPU、内存、连接数。

没有精确线上数据时，可以说“我当时能看到的压测数据/测试环境指标是...”，不要编造不确定数字。

### 3.7 压测怎么做

压测问题不要只回答“写 Python 脚本”或“用 JMeter”。更完整的回答应包含目标、环境、流量模型、指标和复盘：

1. **确定目标**：是验证峰值 QPS、容量上限、P99 延迟、数据库瓶颈，还是验证扩容后的线性提升。
2. **准备环境**：尽量接近线上机器规格、数据量、索引、缓存预热、连接池和下游依赖；不能接近时要说明差异。
3. **设计流量模型**：读写比例、热点 key 分布、请求参数分布、并发用户数、突刺流量和持续压测时长。
4. **工具选择**：HTTP 接口可用 JMeter、wrk、ab、k6、Locust；gRPC 可用 ghz、fortio 或自写压测客户端；内部任务可以写脚本直接压消息或 RPC。
5. **分层压测**：先压空接口或 echo RPC 得到框架基线，再压业务逻辑，再打开真实下游，逐层定位瓶颈。
6. **观察指标**：QPS/TPS、P50/P95/P99、错误率、超时率、CPU、内存、GC、线程池队列、连接池、Redis 命中率、DB 慢 SQL、MQ lag。
7. **压测复盘**：记录瓶颈点、优化动作、优化前后对比、当前容量水位和告警阈值。

真实回答可以这样组织：

```text
我会先定目标，比如验证 2000 QPS 下 P99 是否小于 200ms。
压测前准备接近线上规模的数据并预热缓存，固定机器规格和版本。
然后用工具按真实读写比例打流量，逐步升压到目标值和极限值。
过程中同时看应用、Redis、MySQL、Kafka 和机器指标。
如果 P99 上升，我会用 trace、慢 SQL、线程池队列和火焰图定位瓶颈，优化后再回归压测。
```

易错点：只看平均延迟或单机 QPS 不够。后端服务更要关注 P95/P99、错误率、资源水位和下游指标，因为用户体感和线上事故通常出现在尾延迟、超时、队列堆积和依赖过载上。

## 4. 技术深挖准备清单

每个项目至少要准备下面几类问题：

1. **数据模型**：核心表结构、索引、唯一约束、状态机。
2. **一致性**：DB、缓存、MQ、下游之间如何保证一致或最终一致。
3. **幂等**：重复请求、重复消息、超时重试如何处理。
4. **并发**：锁、事务、CAS、唯一索引、Lua、分布式锁是否使用。
5. **性能**：慢查询、缓存、批量、异步、连接池。
6. **稳定性**：超时、重试、熔断、降级、限流、回滚。
7. **可观测性**：日志、指标、trace、告警。
8. **安全**：鉴权、权限、敏感字段脱敏、审计。

### 4.1 数据链路类项目追问

如果项目涉及日志、埋点、Kafka、ClickHouse、离线/实时分析，要额外准备：

1. **数据来源**：业务服务、客户端、Agent、数据库 binlog、第三方接口分别怎么接入。
2. **数据规模**：峰值 QPS、每日数据量、单条消息大小、topic 数、partition 数、表数据量。
3. **上下游**：上游是谁，下游是报表、告警、查询 API、离线任务还是推荐/风控系统。
4. **消息模型**：topic 为什么这样拆，partition key 怎么选，consumer group 怎么规划。
5. **落库模型**：最终落几张表，明细表、聚合表、异常表分别是什么引擎。
6. **存储模型**：分区键、排序键、分片键、副本数、TTL、冷热分层。
7. **数据质量**：脏数据、重复数据、延迟、丢失、乱序怎么处理。
8. **可观测性**：Kafka lag、ClickHouse 写入失败、物化视图异常、查询慢如何监控。

### 4.2 模型预测类项目的存储估算

如果项目涉及交易预测、广告预估、推荐打分或风控模型，面试官问“输入和输出需要存储，空间消耗有多大”时，重点不是背一个数字，而是说明估算方法和降本设计。

可以按下面公式估算：

```text
每日存储量 = 请求量 * 单条输入大小 + 预测结果量 * 单条输出大小 + 索引/副本/压缩开销
```

需要拆清楚：

1. **输入特征**：用户 ID、商品/交易 ID、上下文、数值特征、类别特征、特征版本。
2. **输出结果**：score、label、模型版本、阈值、召回原因、trace id、时间戳。
3. **是否存明细**：线上排查和训练回流可能需要明细；报表只需要聚合结果。
4. **保留周期**：热数据保留 7 到 30 天，冷数据进对象存储或离线数仓。
5. **压缩和编码**：文本 JSON 体积大，Protobuf/Parquet/ORC 加压缩通常更省。
6. **副本和索引**：MySQL/ClickHouse/ES/HDFS/S3 的副本、索引、分区元数据都会增加实际占用。

示例估算：

```text
峰值 2000 QPS，日均 5 千万次预测
每条输入特征压缩后 1KB
每条输出结果 200B
明细保留 14 天，副本系数 2

单日原始量约 5000万 * 1.2KB ≈ 60GB
14 天双副本约 60GB * 14 * 2 = 1.68TB
```

真实设计：

1. 在线库只保存最近明细和必要索引，避免高频查询扫冷数据。
2. 训练回流数据写 Kafka/HDFS/对象存储，使用 Parquet/ORC 分区压缩。
3. 对调试字段分级，默认只存特征 hash、模型版本和 score，异常样本再采样保存完整特征。
4. 通过 TTL、冷热分层、采样和字段裁剪控制成本。
5. 敏感特征要脱敏、加密或只存不可逆 hash，并记录数据访问审计。

## 5. 易错点

1. 不要把“我参与了”说成“我主导了”，面试官会继续追问细节。
2. 不要只讲技术名词，要讲它在项目链路里解决了什么问题。
3. 不要回避缺点，能说清楚边界和后续优化更可信。
4. 不要只准备成功经验，也要准备线上问题或测试中暴露的问题。
5. 不要脱离指标谈优化，优化前后最好有可比较的数据。

## 6. 面试回答模板

这个项目的背景是为了解决某条业务链路在高峰期的稳定性和处理效率问题。整体架构上，入口请求经过网关进入业务服务，服务会访问 Redis 做高频状态判断，核心数据落 MySQL，耗时或可异步的部分通过 MQ 交给 worker 处理。我主要负责其中的某个模块，包括接口实现、表结构/索引、缓存 key 设计和异常重试逻辑。

项目里比较有挑战的是某个核心接口在高峰期延迟不稳定。我通过 trace 和慢 SQL 定位到主要耗时在数据库查询和部分缓存击穿，后续调整了联合索引、补充缓存预热和互斥回源，并加了关键指标和告警。这个方案的取舍是增加了缓存一致性维护成本，但降低了主链路压力。复盘来看，如果继续优化，我会把补偿任务和对账指标做得更自动化。
