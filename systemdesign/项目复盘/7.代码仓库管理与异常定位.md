# 代码仓库管理与异常定位

面试里问“代码仓库怎么管理、用什么系统开发、异常怎么定位”，重点不是罗列工具名，而是说明工程协作、质量控制和线上问题闭环。

## 1. 代码仓库管理

常见仓库管理围绕 Git 展开：

1. **分支模型**：主干分支保持可发布，功能开发走 feature branch，紧急修复走 hotfix branch。
2. **提交粒度**：一个 commit 只做一类修改，提交信息说明背景、改动和影响。
3. **Code Review**：合入前检查正确性、边界条件、可维护性、性能和安全风险。
4. **CI 检查**：自动运行编译、单测、格式化、静态检查和必要的集成测试。
5. **版本标记**：发布时打 tag，记录版本号、配置、镜像 digest 和变更说明。
6. **回滚策略**：保留上一稳定版本，出现问题能快速回滚代码、配置或数据迁移。

如果项目较小，可以用 trunk-based development；如果发布节奏较慢，也可能用 Git Flow。选择不是固定答案，关键是保证主干稳定、变更可审计、发布可回滚。

### 1.1 GitHub 怎么用

GitHub 本质上是基于 Git 的远程托管和协作平台。面试里可以从日常流程回答：

```bash
git clone <repo>
git checkout -b feature/i2c-driver
git add .
git commit -m "driver: add i2c sensor init"
git push origin feature/i2c-driver
```

然后在 GitHub 上发 Pull Request，经过 Review、CI、讨论和修改后合入主干。

常见能力：

1. **Pull Request**：描述变更背景、测试结果和影响范围。
2. **Code Review**：通过 inline comment 讨论具体代码。
3. **Issues**：记录 bug、需求和任务状态。
4. **Actions/CI**：自动编译、测试、格式检查和静态扫描。
5. **Release/Tag**：发布版本和归档产物。
6. **Branch Protection**：要求 PR、Review、CI 通过后才能合并。

易错点：

1. 不要直接把所有修改推到主干，团队协作通常走分支和 PR。
2. commit message 不要只写 `fix`，要说明模块和原因。
3. 合并前要同步主干并解决冲突，避免把旧代码覆盖回来。
4. 密钥、token、私有配置不能提交到仓库，泄漏后要立即轮换。

## 2. 开发环境和工具

回答时可以按“系统 + 编译构建 + 调试 + 质量工具”组织：

1. **系统**：Linux 常用于服务端开发和部署；Windows 可用于客户端、Win32、Visual Studio 生态；macOS 常用于跨平台开发。
2. **构建**：CMake、Make、Ninja、Bazel 等管理编译参数、依赖和产物。
3. **调试**：GDB/LLDB、Visual Studio Debugger、core dump、日志、perf、strace、lsof。
4. **内存问题**：ASan、UBSan、TSan、Valgrind、heaptrack、gperftools。
5. **数据库工具**：MySQL、Redis、ClickHouse、MongoDB 等要结合具体项目说明使用场景。

不要只说“我用 VSCode”。更好的回答是：我在 Linux 下用 CMake 构建，GDB 和 core dump 定位崩溃，ASan/TSan 查内存和并发问题，CI 做编译和单测兜底。

## 3. 程序异常定位流程

定位异常可以按“复现 -> 观测 -> 缩小范围 -> 修复 -> 回归”回答：

1. **确认现象**：崩溃、超时、内存增长、CPU 飙高、数据错误还是连接失败。
2. **收集上下文**：版本、配置、输入、日志、错误码、机器负载、最近变更。
3. **复现问题**：本地复现、测试环境复现，或在线上用低风险方式采样。
4. **分析证据**：崩溃看 core dump 和调用栈；性能看火焰图、perf、慢 SQL；内存看 ASan/Valgrind/heap profile。
5. **定位根因**：结合代码路径、数据状态和时序判断，不只停留在表层报错。
6. **修复验证**：补单测或回归用例，验证原问题不再发生。
7. **复盘沉淀**：补监控、告警、日志字段、文档或防御性检查，避免同类问题重复出现。

## 4. core dump 定位

Linux C++ 程序崩溃时，典型定位流程：

```bash
ulimit -c unlimited
gdb ./server core
bt
frame 3
info locals
p variable
```

关键点：

1. 编译时保留调试符号，例如 `-g`。
2. 线上产物可以拆分 debug symbol，避免二进制过大。
3. 调用栈只能说明崩溃点，不一定就是根因；野指针和内存越界可能提前破坏状态。
4. 多线程程序要看所有线程调用栈，例如 GDB 中 `thread apply all bt`。

## 5. 常见异常和工具选择

| 问题 | 常见信号 | 工具 |
| --- | --- | --- |
| 空指针/越界 | SIGSEGV、core dump | GDB、ASan、UBSan |
| use-after-free | 随机崩溃、堆元数据损坏 | ASan、Valgrind |
| 内存泄漏 | RSS 持续增长 | ASan LeakSanitizer、heaptrack、memleak eBPF |
| 死锁 | 请求卡住、线程无进展 | GDB 线程栈、日志、锁顺序分析 |
| CPU 高 | load 高、延迟高 | perf、火焰图、top、pidstat |
| IO 慢 | 请求超时、队列堆积 | strace、iostat、慢日志 |

## 6. Win32 编程怎么回答

如果被问是否做过 Win32 编程，可以按真实经历回答。没有做过也可以说明理解边界：

1. Win32 是 Windows 原生 API，涉及窗口消息循环、句柄、线程、同步、文件、网络等。
2. GUI 程序核心是消息循环：`GetMessage -> TranslateMessage -> DispatchMessage`。
3. 资源通过 `HANDLE` 管理，通常要配合 RAII 封装，避免 `CloseHandle` 泄漏。
4. 如果岗位偏服务端，可以强调 Linux 网络和调试经验，同时说明能按 API 文档迁移学习。

## 7. 面试回答模板

代码仓库我会用 Git 管理，主干保持可发布，功能分支开发，合入前走 Code Review 和 CI，发布打 tag 并保留回滚路径。开发环境上，服务端通常在 Linux 下用 CMake/Make 构建，用 GDB、core dump、日志、ASan/TSan、perf 等工具定位问题。程序异常定位会先确认现象和版本，再收集日志、配置、输入和最近变更；崩溃看 core 调用栈，性能问题看火焰图和慢日志，内存问题用 ASan/Valgrind/heap profile，修复后补回归用例和监控。
