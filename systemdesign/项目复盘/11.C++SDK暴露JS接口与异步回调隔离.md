# 11.C++ SDK 暴露 JS 接口与异步回调隔离

面试里问“C++ SDK 怎么暴露给 JS”“异步回调怎么避免状态冲突”，重点是接口边界、对象生命周期、线程模型和回调隔离，而不是只说“用一个 binding 工具”。

## 1. 基本架构

常见形态是 C++ 核心能力封装成 SDK，再通过一层 binding 暴露给 JS：

```text
JavaScript API
  -> Binding 层(N-API / Node-API / V8 addon / WebAssembly glue)
  -> C++ SDK Facade
  -> 线程池 / I/O / native library
  -> callback / promise / event emitter
```

Binding 层负责类型转换、异常转换、生命周期管理和线程切换。C++ SDK 层负责真正的业务逻辑，尽量不直接依赖 JS runtime。

## 2. 同步接口和异步接口

同步接口适合轻量计算：

```js
const version = sdk.version()
```

异步接口适合 I/O、耗时计算、网络请求：

```js
const result = await sdk.query(request)
```

异步接口内部通常是：

1. JS 调用进入 binding。
2. binding 拷贝或引用必要参数，创建 request context。
3. C++ 把任务投递到 worker、协程或 I/O 线程。
4. 任务完成后把结果投递回 JS 主线程。
5. JS 侧 resolve promise 或触发 callback。

关键点是：大多数 JS runtime 要求 JS 对象只能在主线程或指定 isolate 所属线程访问，C++ worker 不能随意跨线程调用 JS 回调。

## 3. isolate、上下文和状态隔离

V8/Node 场景下，`isolate` 可以理解为一套独立的 JS 运行时状态。不同 isolate 的对象不能直接混用。

容易出错的点：

1. 在 C++ 后台线程里直接访问 JS object 或 function。
2. 保存裸的 JS 对象指针，回调时对象已经被 GC。
3. 多个请求共享一个全局 mutable state，异步回调乱序覆盖状态。
4. 一个用户的回调执行过慢，阻塞同一事件循环上的其他用户。

隔离方式：

1. 每个请求创建独立 context，保存 request id、取消标志、超时时间和必要参数副本。
2. 只在 JS 线程触发 JS 回调，后台线程通过 thread-safe function、event loop queue 或 `uv_async_t` 投递。
3. C++ 侧用 RAII 管理 native resource，JS wrapper 只持有安全句柄。
4. 对跨请求共享缓存加锁、分片锁、RCU 或只读快照，避免回调并发修改。
5. 回调结果携带 request id，JS 侧确认仍是当前请求后再更新状态。

## 4. 生命周期怎么管理

异步接口最容易出生命周期问题：

```text
JS 对象销毁
  -> C++ 任务还在跑
  -> worker 完成后回调旧对象
  -> use-after-free 或状态污染
```

常见做法：

1. JS wrapper 持有 `shared_ptr<NativeObject>`，异步任务持有 `weak_ptr`。
2. 回调前 `lock()`，失败说明对象已释放，直接丢弃结果。
3. NativeObject 内部有 `closed/cancelled` 标志，关闭后拒绝新任务。
4. 析构或 close 时取消未开始任务，正在执行任务只允许回调到安全的空操作。
5. 所有回调统一经过 dispatcher，集中处理异常、日志和状态检查。

示例：

```cpp
auto weak = native->weak_from_this();
pool.submit([weak, req] {
    Result r = doWork(req);
    postToJsThread([weak, r = std::move(r)] {
        auto self = weak.lock();
        if (!self || self->closed()) {
            return;
        }
        self->resolvePromise(r);
    });
});
```

## 5. 异常、取消和超时

接口设计要明确失败语义：

1. C++ 异常不能直接穿透到 JS runtime，要转换成 JS Error 或 reject promise。
2. 每个异步任务要有超时，避免 promise 永远 pending。
3. 用户取消时设置 cancellation token，任务在安全点检查并提前返回。
4. 资源错误、参数错误、业务失败要区分错误码，便于 JS 侧处理。
5. 回调必须只触发一次，避免 promise 被重复 resolve/reject。

## 6. 易错点

1. 暴露给 JS 的 C++ API 不要返回裸指针或内部引用。
2. 不要在 C++ worker 线程里直接调用 JS 回调。
3. 不要让多个 isolate 共享非线程安全的全局状态。
4. 绑定层要处理编码、Buffer 所有权和大对象拷贝成本。
5. 异步回调要考虑乱序返回，不能默认“后发的一定后到”。

## 7. 真实场景应用

客户端 SDK、游戏引擎脚本接口、Node 原生扩展、浏览器 WebAssembly 胶水层都会遇到这类问题。一个健壮设计通常会把 C++ 核心做成纯 native 模块，再用薄 binding 暴露 JS API，把线程切换、Promise、异常转换和生命周期放在统一适配层，避免业务逻辑散落在 V8 或 Node 细节里。

## 8. 面试回答模板

C++ SDK 暴露给 JS 一般分成 JS API、binding 层和 C++ 核心层。同步接口只做轻量操作，耗时任务走异步，后台线程完成后必须投递回 JS 所属线程再触发 callback 或 promise。状态隔离要围绕 request context、isolate、线程归属和对象生命周期设计：后台任务不直接访问 JS 对象，回调前检查 `weak_ptr`、取消标志和 request id。异常要转换成 JS Error，超时和取消要有明确语义，回调只能触发一次。
