# 9. 嵌入式驱动项目追问

面试里问“写过哪些驱动、怎么解决驱动问题”，不要只报设备名字。更好的回答是按硬件背景、内核接口、数据路径、调试方法和最终效果组织。

## 1. 驱动项目怎么介绍

可以用这个结构：

1. **设备和场景**：设备是什么，接在哪条总线上，给系统提供什么能力。
2. **硬件资源**：I2C/SPI/UART/USB/PCI、GPIO、IRQ、clock、reset、regulator、DMA。
3. **内核子系统**：字符设备、input、V4L2、ALSA、netdev、IIO、LED、PWM 等。
4. **用户态接口**：`/dev`、sysfs、ioctl、mmap、input event、socket。
5. **核心流程**：probe、上电、读 chip id、初始化寄存器、处理中断、数据上报、suspend/resume。
6. **问题和定位**：遇到的 bug、如何用日志/波形/寄存器 dump 定位。
7. **结果指标**：功能是否稳定、启动耗时、功耗、丢包/丢中断、异常恢复。

## 2. 示例回答：I2C 传感器驱动

```text
我做过一个 I2C 传感器驱动。设备通过 I2C 接 SoC，同时有 reset GPIO 和中断 GPIO。
设备树里配置 compatible、reg、interrupts、reset-gpios 和供电 regulator。
驱动 probe 中先打开 regulator，配置 pinctrl，释放 reset，等待芯片稳定后读 chip id。
之后用 regmap 写初始化寄存器，把中断注册成 threaded IRQ。
中断线程里读取状态寄存器和数据寄存器，再通过 input/IIO 子系统上报给用户态。
调试时遇到过无 ACK，最后用逻辑分析仪发现 reset 释放时序不满足 datasheet，
加上上电延时并修正 GPIO 极性后解决。
```

这个回答比“写过 I2C 驱动”更有信息量，因为它覆盖了硬件资源、Linux 子系统、协议细节和排查过程。

## 3. 常见追问

### probe 里做什么？

1. 获取设备树或 ACPI 资源。
2. 申请 GPIO、IRQ、clock、regulator、pinctrl。
3. 上电并释放 reset。
4. 读 chip id 或版本寄存器确认设备存在。
5. 初始化寄存器和软件状态。
6. 注册到对应子系统，例如 input、IIO、V4L2、字符设备。

### remove/suspend/resume 要注意什么？

1. 关闭中断并同步正在执行的中断线程。
2. 停止 workqueue/timer，避免资源释放后回调仍运行。
3. 保存或恢复关键寄存器。
4. 按硬件要求关闭 clock/regulator/reset。
5. 用户态还持有 fd 时，要处理引用计数和设备断开状态。

### 怎么证明问题是硬件还是软件？

1. 软件日志证明代码路径和配置是否正确。
2. 寄存器 dump 证明控制器和设备状态。
3. 示波器/逻辑分析仪证明线上是否真的有波形、ACK、中断边沿。
4. 换板、换线、降速、复位、单独裸机测试可以隔离硬件问题。
5. 如果波形正确但内核状态错，偏软件；如果软件发起了传输但线上无波形，查 pinctrl/clock/控制器；如果线上有地址无 ACK，查硬件电源、地址、reset 和焊接。

## 4. 易错点

1. 只讲应用层功能，不讲驱动接口和硬件资源。
2. 把设备树、pinctrl、clock、regulator 这些板级配置漏掉。
3. 只说“看日志”，没有说明如何用波形和寄存器交叉验证。
4. 不提 suspend/resume、remove、异常断开，显得只做了 demo。
5. 没有指标或结果，无法证明问题真正解决。

## 5. 面试回答模板

介绍驱动项目时，我会按设备、总线、硬件资源、内核子系统、用户态接口和调试过程来讲。比如 I2C 传感器驱动，设备树描述地址、中断、reset 和供电；probe 里上电、配置 pinctrl、释放 reset、读 chip id、初始化寄存器；中断用 threaded IRQ，下半部读取数据并通过 input/IIO 上报。遇到问题时先看 dmesg、返回值和设备树，再用寄存器 dump、示波器或逻辑分析仪确认波形，从软件配置和硬件电气两个方向收敛。
