# 1.项目系统架构与模块划分

面试里让你“讲讲项目架构”，重点不是把所有类和接口背一遍，而是说明这个系统解决什么问题、核心链路怎么走、模块为什么这样拆。

## 1. 回答顺序

可以按这个顺序讲：

1. **业务目标**：系统服务谁，解决什么问题。
2. **规模指标**：QPS、数据量、用户量、延迟要求、可用性要求。
3. **整体架构**：接入层、业务层、存储层、异步链路、观测治理。
4. **核心链路**：一条请求从入口到返回经过哪些模块。
5. **模块划分**：每个模块负责什么，模块之间如何交互。
6. **关键技术点**：缓存、消息队列、数据库、限流、降级、一致性、幂等。
7. **取舍**：为什么这样设计，有哪些替代方案，当前方案解决了什么问题。

## 2. 通用架构表达

可以把大多数后端项目抽象成下面几层：

```text
Client
  -> Gateway / API Server
      -> Auth / RateLimit / Router
      -> Business Service
          -> Cache
          -> Database
          -> MQ / Async Worker
          -> External Service
      -> Metrics / Log / Trace
```

面试时不要只说“用了 Redis、MySQL、MQ”，要把它们放到链路里：

1. Redis 是做热点缓存、分布式锁、限流还是 Bitmap 统计。
2. MQ 是削峰、异步解耦、延迟任务还是最终一致性。
3. MySQL 是核心事务数据、关系查询还是索引检索。
4. 定时任务或 worker 负责什么补偿逻辑。

## 3. 模块划分原则

模块划分可以从这些角度解释：

1. **按业务能力拆**：用户、订单、支付、内容、搜索、通知等。
2. **按读写链路拆**：写链路保证一致性，读链路关注低延迟和高吞吐。
3. **按同步/异步拆**：必须立即返回的走同步链路，可延迟处理的放到 MQ 或任务队列。
4. **按数据归属拆**：每个模块明确自己负责哪些表、缓存 key 和数据更新规则。
5. **按稳定性边界拆**：外部依赖、慢任务、非核心功能独立出来，便于降级和隔离。

## 4. 如何介绍自己参与的部分

面试官问“你参与了哪些地方，用到什么技术栈”，重点是把个人贡献讲清楚，而不是把整个团队架构背一遍。可以按“背景 -> 职责 -> 技术 -> 难点 -> 结果”组织。

1. **背景**：项目要解决什么业务问题，用户是谁，核心指标是什么。
2. **职责边界**：自己负责哪个模块、哪条链路、哪些接口或哪些数据表。
3. **技术栈**：语言、框架、数据库、缓存、消息队列、RPC、部署和观测工具分别用在什么位置。
4. **关键难点**：高并发、数据一致性、缓存穿透、慢查询、接口幂等、第三方依赖、灰度发布等。
5. **结果指标**：延迟、吞吐、错误率、资源消耗、开发效率或业务指标有什么变化。

回答时不要只说“用了 Redis、MySQL、Kafka”。更好的说法是：Redis 用于登录态和验证码 TTL，MySQL 存核心用户数据，Kafka 承接登录审计事件，Prometheus 监控登录成功率和 P99 延迟。技术栈要和业务链路绑定。

## 5. 技术栈介绍模板

可以这样拆：

| 层次 | 常见技术 | 说明重点 |
| --- | --- | --- |
| 接入层 | Nginx、API Gateway、Spring MVC、Gin | 鉴权、限流、路由、参数校验 |
| 业务层 | Java/Spring Boot、Go、C++、Python | 负责的核心服务和接口 |
| 存储层 | MySQL、PostgreSQL、Redis、ES | 哪些是权威数据，哪些是缓存或索引 |
| 异步层 | Kafka、RocketMQ、RabbitMQ、定时任务 | 削峰、解耦、补偿、审计 |
| 服务治理 | Nacos、ZooKeeper、Consul、gRPC、Dubbo | 注册发现、RPC、配置、负载均衡 |
| 可观测性 | 日志、Prometheus、Grafana、Trace | 如何定位错误、慢请求和容量问题 |

如果技术栈里有很多组件，要主动说明取舍：为什么这里用 Redis 而不是数据库，为什么同步 RPC 之外还要 MQ，为什么某个模块没有拆成微服务。

## 6. 面试回答模板

我的项目可以分成接入层、业务服务层、异步任务层、数据存储层和观测治理层。接入层负责鉴权、参数校验、路由和限流；业务层承载核心流程；数据层主要包括 MySQL 和 Redis，MySQL 保存核心状态，Redis 用于缓存和高频状态判断；异步层通过 MQ 或任务队列处理耗时操作、补偿任务和通知；观测层负责日志、指标和链路追踪。

核心请求进来后，先经过接入层做校验和限流，再进入业务服务。业务服务会先读缓存，缓存未命中再查数据库；涉及耗时或非强一致的操作会写入 MQ，由 worker 异步处理。模块划分上，我主要按业务能力和数据归属拆分，同时把高频读、慢任务和外部依赖隔离出来，避免一个模块的问题影响整条主链路。

## 7. 常见追问

### 为什么这样拆模块？

回答重点是边界清晰和故障隔离。每个模块负责稳定的数据和业务能力，模块之间通过接口、消息或明确的数据契约交互，减少互相直接访问内部状态。

### 请求量上来后哪里会成为瓶颈？

可以从接入层连接数、业务线程池、数据库慢查询、热点缓存 key、MQ 堆积、外部接口超时几个方向分析。

### 怎么保证可观测？

至少要有结构化日志、核心指标和链路追踪。日志用于定位具体请求，指标用于发现趋势和报警，trace 用于定位跨模块耗时。

## 8. 最突出的两个架构设计怎么讲

社招面试里问“你觉得项目里最突出的两个架构设计是什么，为什么”，不是让你罗列技术组件，而是看你能不能说明设计决策背后的业务约束、替代方案和收益指标。

可以按这个结构回答每个设计：

```text
问题背景
-> 约束和目标
-> 候选方案
-> 最终设计
-> 为什么这样选
-> 落地细节
-> 指标收益和风险
```

选择“突出设计”时，优先挑这些类型：

1. **解决核心瓶颈的设计**：例如同步链路改异步任务、热点缓存、分片、批处理。
2. **降低系统风险的设计**：例如幂等状态机、权限隔离、灰度回滚、人工审批。
3. **提升可扩展性的设计**：例如插件化工具、策略模式、模块化边界、任务调度。
4. **提高可观测性的设计**：例如 trace、事件日志、任务回放、失败样本闭环。
5. **产品体验导向的设计**：例如长任务进度反馈、断点续跑、结果可追踪。

一个 AI/Agent 项目可以这样挑两点：

### 8.1 设计一：单主控状态机 + 可选子任务

背景：如果直接做 Multi-Agent Team，Planner、Researcher、Executor、Reviewer 之间会频繁传自然语言摘要，容易丢上下文、成本高、失败难定位。

最终设计：

```text
User
-> SingleAgentRunner
   -> RunState / Facts / Memory
   -> ToolRouter
   -> Optional Readonly Subagent
   -> StateReducer
   -> Verifier
```

为什么这样选：

1. 高耦合顺序任务更需要统一状态，而不是多个 Agent 各自持有上下文。
2. 工具化能力比子 Agent 更稳定，输入输出有 schema。
3. 子 Agent 只在并行只读、可验证场景启动，降低幻觉污染主链路的风险。
4. 所有状态变更经过 reducer，方便回放和排障。

面试可以补充指标：平均模型调用次数下降、P95 延迟下降、trace 更短、失败归因更清楚、人工接管更容易。

### 8.2 设计二：Memory / State / RAG 分层上下文

背景：用户长期在一个 session 里提问，既有当前任务状态，又有历史偏好，还可能需要外部知识库。如果全部塞进 prompt，会导致上下文爆炸和信息污染。

最终设计：

```text
RunState：run_id、step、plan、checkpoint、审批状态
Short-term Memory：最近消息、当前 topic、会话摘要
Long-term Memory：用户偏好、项目事实、历史经验
RAG：产品文档、代码、FAQ、外部知识证据
ContextBuilder：权限过滤、重排、压缩和注入
```

为什么这样选：

1. 任务状态是正确性信息，必须结构化持久化，不能靠向量召回。
2. Memory 保存用户和项目的持续上下文，RAG 保存外部知识证据，二者边界清晰。
3. 同一 session 内通过 topic segmentation 处理话题切换，避免不同主题互相污染。
4. 长日志、图片、生成文件只保存 artifact 引用，不挤占上下文。
5. ContextBuilder 统一做权限和优先级，避免跨用户记忆或无权限文档泄露。

面试可以补充指标：长对话约束保持率、召回命中率、token 成本、任务恢复成功率、越权召回测试。

### 8.3 回答时的易错点

1. 不要只说“用了 Redis、Kafka、MySQL”，要说明它们解决的架构问题。
2. 不要只讲最终方案，要讲为什么没选替代方案。
3. 不要把所有设计都说成“高并发”，要结合项目真实约束。
4. 不要没有指标，至少给出延迟、成本、成功率、错误率、人工接管率等观察指标。
5. 不要把缺点藏起来，成熟回答要说明当前方案的边界和后续演进。

回答模板：

```text
我会挑两个最能体现架构取舍的点讲。第一个是单主控状态机，把原来可能拆成多个 Agent 的能力收敛到一个 run state 里，子能力优先工具化，必要时才启动只读可验证的子 Agent。这样降低了跨 Agent 通信成本和上下文丢失风险，trace 也更容易回放。第二个是 Memory/State/RAG 分层，把任务 checkpoint、会话记忆、长期偏好和外部知识分开存储和注入。这样能同时解决长 session 连贯性、任务恢复、知识检索和权限隔离问题。每个设计我都会说明当时的业务约束、替代方案、最终落地细节，以及上线后看的延迟、成本、成功率和错误率指标。
```
