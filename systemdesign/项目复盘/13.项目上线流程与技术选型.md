# 13. 项目上线流程与技术选型

面试里问“项目有没有上线，如果要上线需要哪些流程”“技术选型是你自己定的吗”，考察的是工程闭环：需求、设计、实现、测试、发布、观测、回滚和复盘。

## 1. 项目上线前要做什么

上线前至少要完成：

1. **需求和验收标准确认**：功能边界、异常场景、性能目标、兼容性和灰度范围。
2. **设计评审**：接口、数据模型、权限、幂等、缓存一致性、降级和回滚方案。
3. **代码 Review**：重点看边界条件、并发安全、资源释放、错误处理和安全风险。
4. **测试验证**：单元测试、接口测试、集成测试、回归测试、压测和安全测试。
5. **数据变更准备**：DDL、初始化数据、数据迁移、回滚脚本和备份。
6. **配置和密钥管理**：不同环境配置隔离，密钥不进代码仓库。
7. **观测埋点**：日志、指标、trace、业务成功率、告警规则和 dashboard。
8. **发布计划**：发布时间、负责人、灰度比例、验证点、回滚条件和通知渠道。

## 2. 上线流程

一个稳妥的流程：

```text
开发自测
  -> 测试环境验证
  -> 预发环境验证
  -> 小流量灰度
  -> 观察指标和日志
  -> 扩大灰度
  -> 全量发布
  -> 发布后复盘
```

灰度期间要观察：

1. 接口 QPS、错误率、P95/P99。
2. 业务成功率和核心转化。
3. MySQL 慢 SQL、Redis 命中率、MQ 堆积。
4. 实例 CPU、内存、GC、连接池和线程池。
5. 日志中新增错误码和异常栈。
6. 用户反馈和客服工单。

## 3. 回滚和止血

上线方案必须提前设计回滚：

1. **代码回滚**：镜像版本、二进制版本或发布平台一键回滚。
2. **配置回滚**：配置中心保留历史版本，支持快速恢复。
3. **流量回滚**：灰度流量切回旧版本，或从负载均衡摘除新实例。
4. **数据回滚**：DDL 和数据迁移最难回滚，要提前备份和设计兼容字段。
5. **降级开关**：非核心功能可以临时关闭，核心链路保留最小可用能力。

危险点是“代码能回滚，数据不能回滚”。涉及表结构、状态机、消息格式、缓存 key 的变更要做前后兼容，通常按“先兼容读写，再切流量，最后清理旧逻辑”的节奏。

## 4. 技术选型怎么回答

技术选型不应该只说“我喜欢这个框架”。可以按下面维度说明：

1. **业务目标**：系统要解决什么问题，核心指标是什么。
2. **团队技术栈**：团队熟悉 Go、Java、Python 还是 C++，已有基础设施是什么。
3. **数据规模**：QPS、数据量、增长速度、延迟和一致性要求。
4. **生态成熟度**：框架、文档、社区、运维工具、监控和问题排查是否成熟。
5. **成本和复杂度**：开发成本、运维成本、机器成本、学习成本。
6. **扩展和替换**：未来是否容易水平扩容、替换组件或兼容多语言。
7. **风险兜底**：故障降级、数据备份、回滚方案和迁移路径。

回答“是不是自己选的”可以说：核心选型通常会结合团队规范和导师/团队评审，不是一个人拍脑袋；自己负责调研候选方案、对比优缺点、做小规模验证，并在项目约束下落地。

## 5. 技术规划怎么讲

如果问项目未来规划，可以讲技术演进而不是职业规划：

1. **功能完善**：补齐权限、审计、配置、运营后台和用户反馈。
2. **稳定性提升**：增加限流、熔断、降级、重试、幂等和自动化告警。
3. **性能优化**：缓存热点、优化 SQL、异步化慢链路、批处理和压测。
4. **可观测性**：完善日志、指标、trace、dashboard 和告警 runbook。
5. **工程质量**：补单测、集成测试、契约测试、CI/CD 和灰度发布。
6. **架构演进**：从单体到模块化，再根据团队和流量决定是否拆微服务。

## 6. AI/Agent 项目部署和使用规模怎么讲

如果面试官问“项目有没有部署，多少人在用”，不要只回答“部署了”或“还没部署”。要说明部署形态、用户规模、流量指标、稳定性和反馈闭环。

可以按这些维度组织：

1. **部署环境**：本地 Demo、测试环境、预发环境、内网试点、生产灰度、全量生产。
2. **部署方式**：单服务、前后端分离、容器化、Kubernetes、Serverless、模型 API、私有化推理服务。
3. **用户规模**：注册用户、日活/周活、试点团队数、并发用户、请求量、核心功能使用次数。
4. **AI 指标**：RAG 无答案率、引用准确率、人工接管率、工具调用成功率、token 成本、P95/P99 延迟。
5. **稳定性指标**：错误率、超时率、队列积压、模型降级次数、外部工具失败率。
6. **安全和合规**：权限隔离、日志脱敏、Prompt Injection 样本、安全审批和审计。
7. **反馈闭环**：点赞点踩、人工纠错、失败样本回放、评测集更新、灰度版本对比。

AI/Agent 项目上线还要额外关注：

1. **模型降级**：强模型不可用或超预算时切小模型、模板回复或转人工。
2. **成本预算**：按用户、租户、接口设置 token 和工具调用配额。
3. **人工兜底**：低置信、高风险、证据冲突和用户投诉要能转人工。
4. **数据闭环**：线上失败样本进入 harness，不直接把用户隐私写进长期记忆。
5. **灰度开关**：按团队、租户、用户组开启新模型、新 prompt、新工具。

回答示例：

```text
这个项目目前部署在内网试点环境，主要给两个研发小组使用。
我会看日活、请求量、工具调用成功率、RAG 引用准确率、人工接管率、P95 延迟和 token 成本。
上线时先灰度给小范围用户，保留模型降级和人工兜底，失败样本会进入离线评测集回放。
```

如果项目还没上线，也可以诚实说明当前阶段：

```text
目前还在 Demo/测试环境，没有生产用户。
但我按上线标准补了鉴权、日志、限流、评测集、灰度和回滚设计；如果进入试点，会先用内部用户收集成功率、延迟、成本和人工反馈。
```

## 7. 易错点

1. 不要说“写完代码就上线”。上线是测试、发布、观测和回滚闭环。
2. 不要没有灰度和回滚方案就做全量发布。
3. 不要在业务高峰期做高风险 DDL 或大批量数据修复。
4. 不要只看功能正确，还要看性能、稳定性、安全和可观测性。
5. 不要把技术选型说成个人偏好，要结合业务、团队、生态和成本。
6. AI 项目不要只说“模型效果不错”，要有评测集、线上指标和人工反馈。
7. “多少人在用”不要只报数字，还要说明活跃度、使用场景和关键指标。

## 8. 面试回答模板

如果项目要上线，我会先确认验收标准和风险点，再做设计评审、代码 Review、单测、接口测试、集成测试和压测。上线前要准备配置、数据库变更、灰度方案、监控看板、告警规则和回滚预案。发布时先走测试和预发，再小流量灰度，观察错误率、P99、业务成功率、慢 SQL、Redis/MQ 指标和日志异常，稳定后逐步全量。技术选型上我会结合业务目标、团队栈、数据规模、生态成熟度、成本和回滚能力，不会只凭个人喜好。自己负责的部分会做方案对比和验证，再经过团队评审落地。
