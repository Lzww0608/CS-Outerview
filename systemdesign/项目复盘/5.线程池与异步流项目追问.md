# 5.线程池与异步流项目追问

面试里问“项目里的线程池怎么设计”“异步流是什么”，通常不是只想听代码实现，而是想确认你是否理解任务从提交、排队、执行、回调、失败处理到关闭的完整链路。

## 1. 线程池怎么讲

线程池的定义：预先创建一组 worker 线程，复用它们执行任务，避免每个任务都创建和销毁线程。

项目里介绍线程池可以按下面顺序：

1. **为什么需要线程池**：隔离耗时任务，避免事件循环或主线程被阻塞。
2. **线程数量**：CPU 密集型接近 CPU 核数，I/O 密集型可以适当更多，但要压测决定。
3. **任务队列**：有界队列更安全，可以防止突发流量打爆内存。
4. **同步机制**：互斥锁保护队列，条件变量唤醒 worker。
5. **返回结果**：可以用 `future/promise`、回调、事件投递或消息队列。
6. **关闭语义**：停止接收新任务，处理完存量任务，唤醒所有线程并 `join`。

## 2. 线程池关键取舍

| 问题 | 常见方案 | 取舍 |
| --- | --- | --- |
| 队列是否有界 | 固定容量任务队列 | 防止内存膨胀，但需要拒绝策略 |
| 队列满怎么办 | 拒绝、阻塞提交、调用方执行、丢弃低优先级任务 | 取决于业务是否允许降级 |
| 任务异常怎么办 | worker 捕获异常并记录日志 | 避免一个任务导致线程退出 |
| 任务是否有优先级 | 优先队列或多队列 | 提升关键任务响应，但可能饿死低优先级 |
| 如何监控 | 队列长度、活跃线程数、任务耗时、拒绝次数 | 便于发现堆积和容量不足 |

面试里要强调：任务执行不能持有队列锁，否则线程池会退化为串行执行。

## 2.1 线程池死锁和嵌套任务依赖

线程池死锁不是只有“两个线程互相拿锁”这一种形式。在线程池里更常见的是**任务依赖死锁**：父任务占着 worker 线程同步等待子任务完成，而子任务又被投递到同一个已经打满的线程池里，导致没有空闲 worker 能执行子任务。

典型场景：

```text
线程池大小 = 4
4 个父任务都在运行
每个父任务都 submit 一个子任务到同一个线程池
父任务同步 wait 子任务结果
子任务排在队列里，但没有 worker 可运行
```

这种问题线上表现通常是：CPU 不高、队列长度持续增长、活跃线程数打满、请求延迟飙升，但线程栈里大量 worker 停在 `future::get()`、条件变量、锁等待、RPC 等阻塞点。

排查思路：

1. **监控指标**：活跃线程数、队列长度、拒绝次数、任务等待时间、任务执行时间、超时数量。
2. **线程栈**：Java 看 `jstack`，C++ 看 core/gdb/pstack，确认 worker 是否都在同步等待。
3. **任务链路**：用 trace id 记录父任务、子任务、提交时间、开始执行时间和完成时间。
4. **锁与资源**：检查是否在持有锁时提交异步任务并等待结果，或者在回调里反向等待上游。

解决方式：

1. 不在 worker 内同步等待同一个线程池的子任务，改成回调、`then`、协程或异步状态机。
2. 父任务和子任务拆到不同线程池，至少保证子任务池有独立 worker。
3. 对同步等待设置超时和降级，避免无限占用 worker。
4. 对依赖关系建模为 DAG，由调度器在依赖满足后再提交可运行节点。
5. 业务允许时使用 work stealing 或“等待时帮忙执行队列任务”，但要控制重入和锁顺序。
6. 保留少量兜底线程或使用有界队列，防止所有 worker 被同类阻塞任务占满。

面试里可以直接说：线程池死锁的核心不是线程数量不够，而是“阻塞等待”和“被等待任务”共享同一组受限执行资源。设计时要避免池内同步等待池内任务。

## 2.2 流量激增打满线程池怎么办

突发流量超过线程池处理能力时，不能只靠继续加线程。线程过多会增加上下文切换、锁竞争和内存占用，甚至让系统更慢。

更稳妥的处理链路：

1. **入口限流**：令牌桶、漏桶、滑动窗口或网关限流，把不可承受的流量挡在系统边界。
2. **有界队列**：线程池任务队列必须有容量上限，队列满后快速失败、降级或返回重试建议。
3. **背压传播**：下游慢时让上游降速，而不是无限堆积请求。
4. **优先级隔离**：核心请求和非核心请求使用不同队列或线程池，低优先级任务可丢弃或延迟。
5. **熔断降级**：依赖服务超时或错误率过高时，返回缓存、默认值或降级结果。
6. **自动扩容**：容器化环境可以根据队列长度、CPU、延迟等指标扩容实例，但扩容不是毫秒级兜底。
7. **削峰填谷**：可异步化的任务进入 MQ，消费者按后端能力消费。

真实系统里要把这些策略和告警绑定：队列使用率、P99 延迟、拒绝率、超时率同时升高时，说明系统已经进入过载状态，应优先保护核心链路而不是追求“每个请求都排队等”。

## 3. 异步流是什么

项目里的“异步流”可以理解为一条由事件、队列、回调或协程串起来的异步处理流水线。它把请求拆成多个阶段，每个阶段完成后把结果投递给下一个阶段，而不是在一个线程里同步阻塞到底。

典型链路：

```text
请求进入
-> 参数校验
-> 投递到线程池或 MQ
-> worker 执行业务/IO
-> 结果回调到事件循环
-> 写响应或触发后续任务
```

异步流的核心价值：

1. **解耦**：上游不直接等待下游慢操作。
2. **削峰**：队列吸收短时间流量突刺。
3. **隔离**：慢任务不阻塞主线程或事件循环。
4. **可恢复**：持久化队列或任务状态机可以支持失败重试。
5. **可观测**：每个阶段都能记录耗时和失败原因。

## 3.1 异步有什么好处

异步的好处可以从性能和架构两个角度讲：

1. **降低同步等待时间**：主链路不必等待邮件、通知、日志、发奖、报表等慢任务完成。
2. **削峰填谷**：突发流量先进入队列，后端 worker 按可控速率消费。
3. **解耦上下游**：调用方只依赖消息或任务结果，不直接感知下游实现和临时故障。
4. **隔离故障**：下游慢或失败时，不直接拖死入口线程池。
5. **提升吞吐**：I/O 等待型任务可以让出线程或协程，系统同时处理更多请求。
6. **支持重试和补偿**：失败任务可以持久化后重试，避免用户请求一直阻塞。

但异步也有代价：

1. 用户不能立即拿到最终结果，需要轮询、回调、SSE 或状态查询。
2. 数据通常从强一致变成最终一致，需要幂等和补偿。
3. 队列堆积会造成延迟上升，必须有监控和背压。
4. 排查问题更依赖 trace id、任务状态和结构化日志。

所以面试里不能只说“异步提高性能”，还要说明异步把同步延迟变成了队列延迟和一致性问题，需要配套状态机、幂等、重试、死信和监控。

## 4. 背压和可靠性

异步不是无限排队。真正可用的异步流必须考虑背压：

1. 队列长度达到阈值时拒绝或降级。
2. 消费速度低于生产速度时扩容 worker 或限流入口。
3. 任务设置超时时间，避免一直占用资源。
4. 失败任务带重试次数和退避策略。
5. 写操作要有幂等 key，避免重试造成重复副作用。
6. 关键任务状态落库，worker 重启后能恢复。

## 5. 和事件循环的配合

在 WebServer 或 RPC 项目中，常见做法是：

1. Reactor 线程只做非阻塞 I/O、协议解析和事件分发。
2. CPU 计算、磁盘 I/O、数据库访问交给线程池。
3. worker 完成后不要直接跨线程操作连接 fd，而是把回调投递回连接所属的 EventLoop。
4. EventLoop 再把结果写入输出缓冲区，打开 `EPOLLOUT`。

这样可以避免多个线程同时读写同一个连接对象，也能保持连接生命周期清晰。

## 5.1 任务和 I/O 绑定怎么协调

高并发网络服务里，线程池和 I/O 线程的边界要非常清楚：

1. **EventLoop 拥有连接 fd**：读写事件、输出缓冲区和连接生命周期由所属 EventLoop 线程管理。
2. **worker 只做耗时业务**：CPU 计算、阻塞磁盘 I/O、数据库访问等放到 worker，避免卡住事件循环。
3. **结果投递回原 EventLoop**：worker 完成后不要直接跨线程写 fd，而是通过任务队列、`eventfd`、管道或 lock-free queue 唤醒连接所属 EventLoop。
4. **连接对象用弱引用或版本号保护**：worker 返回结果时，连接可能已经关闭，需要检查 `weak_ptr`、connection id 或 generation。
5. **I/O 密集和 CPU 密集分池**：磁盘、网络代理、压缩、加密等任务资源画像不同，混用一个线程池容易互相拖慢。
6. **保持亲和性**：同一连接或同一用户会话尽量固定在同一个 EventLoop，减少锁和缓存失效。

这也是 one loop per thread 模型常见的做法：每个 I/O 线程负责自己的 `epoll` 和连接集合，跨线程只通过明确的任务投递通信，不共享连接内部状态。

## 6. 易错点

1. 异步流不是“开个线程就完了”，要有队列、状态、错误处理和背压。
2. 线程池大小不是越大越好，线程过多会增加上下文切换和锁竞争。
3. 无界队列在压测中可能看起来吞吐高，但线上突刺会堆爆内存。
4. 回调跨线程执行时要明确对象生命周期，避免悬垂引用。
5. 异步任务失败后必须有重试、补偿或明确丢弃策略。

## 7. 面试回答模板

我的项目里线程池主要用来隔离耗时任务，避免事件循环线程被阻塞。线程池由固定 worker、有界任务队列、互斥锁、条件变量和停止标志组成；提交任务时入队并唤醒 worker，worker 取任务后释放锁再执行。队列满时根据业务做拒绝或降级，任务异常会捕获并记录，关闭时先停止接收新任务，再处理完存量任务并 join。

异步流可以理解为请求处理流水线：入口线程完成轻量校验后把任务投递到队列，worker 执行业务或 I/O，完成后把结果投递回事件循环写响应。它的价值是解耦、削峰和隔离慢操作，但必须配套背压、超时、重试、幂等和监控，否则只是把同步阻塞变成队列堆积。
