# 14. 项目设计模式与 DDD 落地

面试里问“项目中用过哪些设计模式、除了单例还用过什么、DDD 了解吗”，不要只背模式名。更好的回答是结合项目复杂度说明：为什么需要这个模式，它解决了哪个变化点，以及有没有带来过度设计。

## 1. 常见设计模式怎么落地

### 策略模式

策略模式把一组可替换算法封装成统一接口，调用方只依赖接口，不依赖具体实现。

适用场景：

1. 支付渠道：微信、支付宝、银行卡使用同一 `PaymentStrategy`。
2. 优惠计算：满减、折扣、会员价、运费券按规则选择。
3. 风控规则：不同业务线使用不同评分策略。

示例：

```java
interface DiscountStrategy {
    Money calculate(Order order);
}
```

真实项目里通常结合工厂或配置中心，根据业务类型、租户、活动 ID 选择策略，避免大量 `if-else` 堆在 service 中。

### 工厂模式

工厂模式把对象创建逻辑从业务流程中抽出来，适合创建过程复杂或实现类较多的场景。

常见用法：

1. 根据消息类型创建不同 handler。
2. 根据渠道创建不同 client。
3. 根据任务类型创建不同 executor。

注意：如果只是 `new` 一个简单对象，没有复杂创建逻辑，工厂会增加不必要层次。

### 模板方法

模板方法把固定流程放在父类或抽象层，把可变步骤留给子类实现。

例如订单履约流程：

```text
参数校验 -> 幂等校验 -> 执行业务 -> 记录流水 -> 发布事件
```

不同履约类型只重写“执行业务”部分。它适合流程稳定、步骤可扩展的场景，但继承层次过深会降低可读性，Java 项目中也常用组合和回调替代继承。

### 观察者 / 发布订阅

一个状态变化后，多个下游动作不应强耦合在主流程里时，可以用观察者或事件发布。

例如订单支付成功：

1. 更新订单状态。
2. 发布 `OrderPaidEvent`。
3. 积分、优惠券、通知、数据统计分别订阅处理。

真实系统通常不会只用内存观察者，而是用 MQ、事务消息、outbox 或领域事件保证可靠投递和可重试。

### 责任链

责任链适合一组处理器按顺序处理请求，例如网关过滤器、参数校验、风控规则、审批流。每个节点只关心自己的判断，链路可以配置化。

注意点：

1. 要有明确终止条件，避免链路过长难排查。
2. 每个 handler 要有可观测日志和耗时指标。
3. 高风险链路要定义失败策略，是中断、跳过还是降级。

## 2. 单例之外怎么回答

可以按项目模块举例：

1. **策略 + 工厂**：支付、优惠、规则计算这类多实现选择。
2. **模板方法**：导入、导出、审批、任务执行这类固定流程。
3. **观察者 / 领域事件**：主业务完成后通知多个下游。
4. **责任链**：网关过滤、权限校验、风控规则、参数校验。
5. **适配器**：对接第三方 SDK，把外部接口转换成内部统一接口。
6. **装饰器**：给 client 或 handler 增加超时、重试、日志、指标。

回答时要强调模式不是越多越好。简单 CRUD 不需要强行上模式，只有变化点明确、重复逻辑明显、扩展成本已经出现时才值得抽象。

## 3. DDD 的核心概念

DDD 不是目录规范，而是围绕业务领域建模的思想。

常见概念：

1. **领域 Domain**：业务问题空间，例如订单、库存、支付、履约。
2. **限界上下文 Bounded Context**：模型生效边界，同一个词在不同上下文里可以含义不同。
3. **实体 Entity**：有唯一标识和生命周期，例如订单。
4. **值对象 Value Object**：无身份、只关心值，例如金额、地址。
5. **聚合 Aggregate**：一组强一致对象的边界，聚合根负责维护不变量。
6. **领域服务 Domain Service**：不适合放在单个实体里的领域行为。
7. **仓储 Repository**：屏蔽持久化细节，提供聚合的读取和保存。
8. **领域事件 Domain Event**：领域内发生的重要事实，例如订单已支付。

## 4. DDD 和传统三层的区别

传统三层常按技术分为 Controller、Service、DAO，容易让业务规则散落在 service 脚本里。DDD 更强调业务模型和边界：

```text
接口层 -> 应用服务 -> 领域模型/领域服务 -> 仓储接口 -> 基础设施实现
```

应用服务负责编排事务、权限、调用外部系统；领域对象负责表达业务规则；基础设施负责数据库、MQ、RPC 等技术细节。

## 5. 真实场景下如何取舍

1. 业务简单、生命周期短的管理后台：保持清晰三层即可。
2. 规则复杂、状态机多、多人协作的核心业务：可以用 DDD 做边界和模型。
3. 先模块化单体，把包边界和依赖方向理清，再决定是否拆微服务。
4. 强一致的聚合内操作尽量放同一事务；跨聚合用领域事件、补偿和最终一致。
5. DDD 不能替代数据库约束、幂等、消息可靠性和监控。

## 6. 面试回答模板

项目里除了单例，我更常用策略、工厂、模板方法、观察者/发布订阅、责任链、适配器和装饰器。比如优惠计算用策略模式隔离不同规则，消息处理用工厂选择 handler，订单支付成功后用领域事件或 MQ 通知积分和通知模块。DDD 方面，我理解它的核心是按业务领域和限界上下文建模，让实体、值对象、聚合、领域服务、仓储和领域事件表达业务规则，而不是只按 Controller/Service/DAO 分层。真实项目要按复杂度取舍，简单 CRUD 不需要过度 DDD，复杂核心业务可以先在模块化单体内划清领域边界。
