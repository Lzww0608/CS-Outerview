# WebServer 项目追问

C++ WebServer 项目常被用来考察网络编程、I/O 多路复用、线程模型、HTTP 协议解析、资源管理和性能优化。介绍时不要只说“用了 epoll 和线程池”，要把请求从连接建立到响应返回的完整链路讲清楚。

## 介绍顺序

可以按下面结构讲 2 分钟版本：

```text
项目目标 -> 整体架构 -> 请求链路 -> 核心模块 -> 并发模型 -> 优化和难点
```

示例：

1. **项目目标**：实现一个 Linux 下的轻量级 HTTP WebServer，支持静态资源访问和简单动态请求。
2. **整体架构**：主线程负责监听连接和事件分发，工作线程处理请求解析和业务逻辑。
3. **请求链路**：`socket/bind/listen` 后加入 epoll，连接到来后 `accept`，读事件到来后读取到输入缓冲区，解析 HTTP 请求，生成响应，写回客户端。
4. **核心模块**：网络层、事件循环、HTTP 解析、线程池、定时器、日志、连接管理。
5. **并发模型**：非阻塞 I/O + epoll + Reactor + 线程池。
6. **优化点**：减少阻塞、控制连接超时、使用缓冲区处理半包、异步日志、合理设置 fd 上限和 socket 参数。

## 典型架构

```text
Client
  -> listen_fd
  -> epoll event loop
      -> accept new connection
      -> read into input buffer
      -> parse HTTP request
      -> dispatch to worker
      -> build response
      -> write output buffer
  -> close / keep-alive / timeout
```

关键点：

1. 监听 fd 和连接 fd 都设置为非阻塞。
2. epoll 只通知就绪，真正读写仍由应用调用 `recv/send`。
3. 每个连接维护输入缓冲区、输出缓冲区、状态机和超时时间。
4. HTTP keep-alive 下，一个 TCP 连接可能承载多个请求。
5. 写响应可能只写出一部分，需要记录写偏移并继续监听 `EPOLLOUT`。

## 核心模块怎么讲

### 1. 网络模块

1. `socket/bind/listen/accept4` 建立服务端。
2. `epoll_create1/epoll_ctl/epoll_wait` 做 I/O 多路复用。
3. `fcntl` 或 `accept4` 设置非阻塞。
4. 读写到 `EAGAIN`，避免 ET 模式漏事件。

### 2. HTTP 解析

HTTP/1.1 请求一般按：

```text
请求行 -> 请求头 -> 空行 -> 请求体
```

解析时常用状态机：

1. 解析请求行：方法、URL、版本。
2. 解析请求头：`Host`、`Connection`、`Content-Length`。
3. 根据 `Content-Length` 判断 body 是否读完整。
4. 生成响应状态行、响应头、空行和响应体。

### 3. 线程池

事件循环线程负责 I/O 就绪和连接状态，工作线程负责 CPU 或业务处理。注意：

1. 不要在事件循环线程里做阻塞磁盘 I/O、慢数据库查询或复杂业务。
2. 任务队列要有长度上限，避免请求堆积打爆内存。
3. 连接对象跨线程访问要明确所有权和同步方式。

### 4. 定时器

定时器用于关闭长时间不活跃连接。

常见实现：

1. 最小堆：取最近超时 `O(1)`，调整 `O(log n)`。
2. 红黑树：插入删除 `O(log n)`，取最小节点方便。
3. 时间轮：大量连接超时时效率高，但精度和跨度要权衡。

### 5. 日志

同步日志简单但可能阻塞请求线程；异步日志通常用队列 + 后台线程写盘。要关注：

1. 日志队列满了如何处理。
2. 是否需要落盘前刷新。
3. 崩溃时可能丢多少日志。
4. 日志格式是否包含 trace id、fd、状态码、耗时。

## 高频追问

### 为什么要用 I/O 多路复用

一连接一线程在大量长连接下会被线程栈、调度和上下文切换拖垮。I/O 多路复用让少量线程管理大量 fd，只在 fd 就绪时处理事件，适合高并发网络服务。

### Reactor 和线程池怎么配合

Reactor 负责监听事件和分发事件。常见做法是主 Reactor 接收连接，子 Reactor 或工作线程负责连接读写和业务处理。简单项目也可以单 Reactor + 线程池，但要避免多个线程同时操作同一个连接 fd。

### 怎么处理 TCP 粘包拆包

TCP 是字节流，没有消息边界。HTTP 通过请求行、头部空行、`Content-Length`、`Transfer-Encoding: chunked` 等应用层规则确定消息边界。服务端要维护输入缓冲区，数据不完整时继续等待下一次读事件。

### 怎么保证资源释放

1. fd 用 RAII 封装，析构时关闭。
2. 连接关闭时从 epoll 删除 fd，清理定时器和缓冲区。
3. 线程池退出时先停止接收新任务，再等待已有任务完成。
4. 智能指针要避免连接对象循环引用。

## 易错点

1. epoll 不是异步 I/O，它是就绪通知。
2. ET 模式必须非阻塞并读写到 `EAGAIN`。
3. `send` 成功返回不代表一次写完整个响应。
4. keep-alive 连接不能响应一次就直接关闭，除非协议或服务端策略要求关闭。
5. 线程池不是越大越好，过多线程会增加切换和锁竞争。
6. 压测指标不要只看 QPS，也要看 P99、错误率、CPU、内存、fd 数和连接超时。

## 面试回答模板

我的 WebServer 可以按连接生命周期介绍：启动时通过 `socket/bind/listen` 创建监听 fd，并把监听 fd 设置为非阻塞加入 epoll。新连接到来后用 `accept4` 得到连接 fd，也设置非阻塞并加入 epoll。读事件到来时循环 `recv` 到 `EAGAIN`，数据放入连接的输入缓冲区，通过 HTTP 状态机解析请求行、请求头和 body；请求完整后交给业务处理或线程池生成响应。写响应时维护输出缓冲区和写偏移，只在有待发送数据时关注 `EPOLLOUT`。连接长时间无活动由定时器关闭，日志用异步队列降低主链路阻塞。核心取舍是用 epoll/Reactor 管理大量连接，用线程池隔离耗时任务，同时通过缓冲区和状态机处理半包、粘包和部分写。
