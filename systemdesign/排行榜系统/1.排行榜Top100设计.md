# 排行榜 Top100 设计

排行榜系统的核心是按分数排序并高频读取 TopN。面试里问“排行榜排出前 100 怎么做”，要先确认规模、实时性和一致性要求：是单服活动榜、全服榜、好友榜，还是跨区跨服全球榜。

## 1. 单机或中小规模：Redis ZSet

如果数据量和 QPS 在单个 Redis 实例可承受范围内，最直接方案是 Redis ZSet：

```text
key: rank:activity:202508
member: user_id
score: score
```

常用命令：

```text
ZADD rank:activity:202508 10086 userA
ZINCRBY rank:activity:202508 10 userA
ZREVRANGE rank:activity:202508 0 99 WITHSCORES
ZREVRANK rank:activity:202508 userA
ZSCORE rank:activity:202508 userA
```

复杂度：

1. 更新分数：`O(log n)`。
2. 查询排名：`O(log n)`。
3. 查询 Top100：`O(log n + 100)`。

Redis ZSet 底层在大数据量时是 `dict + skiplist`：dict 负责按用户查分数，skiplist 负责按分数排序、范围查询和 rank。

## 2. 分数相同如何处理

排行榜要有稳定、可解释的排序规则。常见做法：

1. 主排序字段：分数 score，分数高在前。
2. 次排序字段：达成时间，先达到者靠前。
3. 再次排序字段：用户 id，保证全局确定性。

Redis ZSet 只有一个 double score，member 会作为同分时的字典序 tie-breaker。如果需要“分数相同按时间早晚”，可以把复合排序编码到 score 中，或者把 TopN 候选拉出后在应用层按 `(score, timestamp, user_id)` 排序。

复合 score 要谨慎：

```text
encoded_score = score * SCALE + time_weight
```

要避免 double 精度丢失，也要确保分数范围和时间权重不会互相覆盖。高精度和严格排序场景更适合在数据库或应用层维护复合排序键。

### 2.1 同分按时间先后排序怎么做

如果规则是“分数越高越靠前；分数相同，越早达到该分数越靠前”，Redis ZSet 有几种实现方式。

#### 方案一：复合 score

把业务分数和时间权重编码成一个数：

```text
encoded = score * SCALE + (SCALE - time_rank)
```

查询时用 `ZREVRANGE`。例如 `time_rank` 可以是当天第几毫秒，越早越小，`SCALE - time_rank` 越大，同分时越早越靠前。

注意：

1. Redis ZSet score 是 double，整数精确范围约到 `2^53`，复合编码不能超过精确范围。
2. `SCALE` 必须大于时间权重最大值，避免时间权重影响主分数排序。
3. 如果分数会非常大，或需要纳秒级时间，复合 score 容易精度不安全。

#### 方案二：member 中编码时间

利用 Redis 同分时按 member 字典序排序的特性，把 member 设计成可排序字符串：

```text
score = 业务分数
member = padded_time + ":" + user_id
```

如果使用 `ZREVRANGE` 查高分榜，同分时 member 字典序较大的排前；要让“时间早”排前，可以把时间取反后补齐：

```text
member = (MAX_TS - achieve_ts) + ":" + user_id
```

缺点是按 `user_id` 查排名或更新分数不方便，因为 member 不再只是用户 ID。通常还要额外维护：

```text
rank_member_map: user_id -> encoded_member
```

更新时先查旧 member，再 `ZREM` 旧 member，最后 `ZADD` 新 member。

#### 方案三：候选集应用层二次排序

如果只展示 Top100，可以从 Redis 多取一些候选，例如 Top1000，然后应用层按：

```text
(-score, achieve_time, user_id)
```

重新排序取前 100。这个方案简单、安全，适合 TopN 展示，但不适合精确查询任意用户的全局排名。

面试里可以这样回答：小规模或只查 TopN，我倾向于 Redis ZSet + 应用层二次排序；如果必须 Redis 内严格排序，可以做复合 score，但要强调 double 精度边界；如果要利用 member 字典序，需要额外维护 user_id 到 member 的映射。

## 3. 大规模排行榜：分片 + 聚合

如果全量用户太多，单个 ZSet 过大或更新热点太集中，可以按用户、区服或活动分片：

```text
rank:activity:202508:shard:0
rank:activity:202508:shard:1
...
rank:activity:202508:shard:K-1
```

全局 Top100 的查询流程：

1. 每个分片取本地 Top100。
2. 应用层或聚合服务用小根堆/多路归并合并候选。
3. 得到全局 Top100。
4. 把结果缓存到 `rank:activity:202508:global:top100`，设置短 TTL 或定时刷新。

这样每次全局榜不需要扫描全部用户，只处理 `K * 100` 个候选。对于游戏活动榜，可以接受秒级延迟时，常用定时任务每 1 到 5 秒聚合一次。

## 4. 写入链路和持久化

排行榜不能只依赖 Redis 内存态。常见链路：

```text
业务服务
  -> 校验本次得分是否合法
  -> Redis ZSet 实时更新
  -> MQ/日志流异步落库
  -> MySQL/ClickHouse/HBase 保存明细或最终分
  -> 定时校准 Redis 榜单
```

需要关注：

1. **幂等性**：同一场比赛或同一局游戏的分数上报不能重复计入。
2. **防作弊**：分数更新必须由服务端权威计算或校验。
3. **持久化**：Redis 故障后能从数据库或日志重建榜单。
4. **冷热分离**：近期活动榜放 Redis，历史榜单归档到数据库或对象存储。
5. **多级缓存**：Top100 是热点读，可以在应用本地缓存短时间结果。

## 5. 真实场景取舍

1. **实时活动榜**：Redis ZSet + 短 TTL 本地缓存，秒级刷新即可。
2. **好友榜**：先取好友列表，再批量查分数排序；好友数大时可预计算。
3. **全服榜**：按区服分片，分片 TopN 聚合。
4. **历史榜单**：落数据库或 OLAP，按日期/赛季查询。
5. **高并发写榜**：入口削峰、异步写日志、Redis pipeline、Lua 保证条件更新原子性。

## 6. 面试回答模板

中小规模排行榜我会直接用 Redis ZSet，member 是用户 id，score 是分数，`ZADD/ZINCRBY` 更新，`ZREVRANGE 0 99 WITHSCORES` 查 Top100，`ZREVRANK` 查个人排名。大规模时按区服、用户哈希或活动分片，每个分片维护本地榜，查询全局 Top100 时取各分片 Top100 后用堆做多路归并，并把全局榜缓存几秒。生产上还要考虑同分排序、幂等更新、防作弊、Redis 故障重建、持久化落库和热点榜单本地缓存。
