# 1. Kafka 到 ClickHouse 日志链路

## 1. 场景

日志分析平台常见链路是：业务服务、客户端或采集 Agent 产生日志，经 Kafka 做缓冲和解耦，最终进入 ClickHouse 做明细查询、聚合分析和报表。

面试里被追问“数据规模、怎么获取、下游是什么、几个 topic、几张表、表引擎、分片键、分区分片副本”，本质是在考察你是否理解完整数据链路，而不是只会说用了 Kafka 和 ClickHouse。

## 2. 数据链路

典型链路：

```text
App / Service / Agent
  -> Log Collector
  -> Kafka Topic
  -> ClickHouse Kafka Engine Table
  -> Materialized View
  -> ReplicatedMergeTree Local Table
  -> Distributed Table
  -> BI / API / 报警 / 离线任务
```

各层职责：

1. **Log Collector**：采集、清洗、补充环境字段、批量发送。
2. **Kafka**：削峰、缓冲、解耦上下游、支持多消费组订阅。
3. **Kafka Engine Table**：ClickHouse 消费 Kafka 的入口。
4. **Materialized View**：把 Kafka 中的数据解析并写入目标表。
5. **MergeTree 表**：存储明细日志或聚合结果。
6. **Distributed 表**：提供跨 shard 查询入口。

## 3. Topic 和 Partition 怎么设计

Topic 拆分可以按数据语义和消费链路划分，而不是按表随意拆：

1. `app_log`：应用日志。
2. `access_log`：网关或 Nginx 访问日志。
3. `metric_log`：指标类日志。
4. `trace_log`：链路追踪日志。
5. `audit_log`：审计日志。

Partition 数量主要由吞吐和消费并行度决定：

```text
partition 数 >= 最大消费并行度
```

还要考虑：

1. 单 partition 内消息有序，多 partition 只能保证分区内有序。
2. partition 过少会限制消费并行度。
3. partition 过多会增加 broker 文件句柄、leader 选举、元数据和 rebalance 成本。
4. 如果按 key 写入，例如 `trace_id` 或 `user_id`，同一个 key 会进入同一个 partition，方便局部有序。

面试回答可以给出量级而不是编造精确数：

```text
我们按日志类型拆了多个 topic，每个 topic 根据峰值写入量配置 partition。高吞吐的明细日志 topic partition 更多，低吞吐的审计 topic partition 更少，并保证 ClickHouse 消费端并行度不超过 partition 数。
```

## 4. ClickHouse 表结构设计

日志明细表常见字段：

```sql
CREATE TABLE log_detail_local
(
    event_time DateTime,
    dt Date,
    app_id UInt64,
    service LowCardinality(String),
    host String,
    level LowCardinality(String),
    trace_id String,
    user_id UInt64,
    topic LowCardinality(String),
    partition_id UInt16,
    offset UInt64,
    message String,
    extra String
)
ENGINE = ReplicatedMergeTree(
    '/clickhouse/tables/{shard}/log_detail_local',
    '{replica}'
)
PARTITION BY toYYYYMMDD(dt)
ORDER BY (app_id, service, event_time, trace_id)
TTL event_time + INTERVAL 30 DAY DELETE;
```

字段设计要考虑：

1. 高频过滤字段放进 `ORDER BY` 靠前位置。
2. 时间字段用于分区和 TTL。
3. `LowCardinality(String)` 适合低基数字符串，例如 `level`、`service`。
4. 保留 `topic/partition/offset` 方便排查消费重复和数据追溯。
5. 大 JSON 可以放 `String`，高频查询字段应提前抽取成独立列。

## 5. Log 最后落几张表

常见不是只落一张表，而是按查询和生命周期拆：

1. **Kafka 引擎表**：消费入口，不作为长期存储。
2. **明细本地表**：`ReplicatedMergeTree`，保存原始或清洗后的明细日志。
3. **分布式查询表**：`Distributed`，对外查询入口。
4. **聚合结果表**：`SummingMergeTree` 或 `AggregatingMergeTree`，保存分钟级、小时级统计。
5. **异常/错误日志表**：可选，便于报警和快速检索。

回答时要把每张表的角色和引擎说清楚。

## 6. 分片键选择

日志平台常见选择：

1. 按 `cityHash64(user_id)`：用户维度查询更局部。
2. 按 `cityHash64(trace_id)`：链路追踪查询更局部。
3. 按 `cityHash64(device_id)`：终端设备日志更均匀。
4. 按 `rand()` 或随机：写入均匀，但点查要广播，不适合高频定向查询。

不要只按时间分片，因为当前时间段写入会集中到一个 shard，形成热点。时间更适合作为分区键。

## 7. 副本数怎么回答

生产环境通常每个 shard 至少 2 副本：

1. 2 副本：常见成本和可用性平衡。
2. 3 副本：核心数据或高可用要求更高时使用。

多副本作用：

1. 节点故障时仍可查询。
2. 数据冗余，降低丢数据风险。
3. 查询读流量可以在副本间负载均衡。
4. 滚动升级和扩容时更平滑。

## 8. 下游是什么

ClickHouse 的下游通常包括：

1. BI 报表和可视化大盘。
2. 告警系统，例如错误率、P99、异常关键字。
3. 查询 API，给内部平台检索日志。
4. 离线任务或数据导出。
5. 数据质量和对账任务。

回答“下游是什么”时要说明数据被谁消费、消费频率、是否有延迟要求。

## 9. 易错点

1. `Kafka` 表引擎不是最终存储表，通常要配物化视图写入 MergeTree。
2. 分区不是分片，按天分区不能代替集群水平扩展。
3. 副本不是备份，副本用于高可用，误删数据可能同步到所有副本。
4. Kafka 到 ClickHouse 可能重复写入，要准备去重或幂等策略。
5. 不要只说“几个 topic”，要解释为什么这样拆 topic 和 partition。

## 10. 面试回答模板

我们的日志链路可以概括为采集端把业务日志批量写入 Kafka，Kafka 按日志类型拆 topic，并按峰值吞吐设置 partition。ClickHouse 侧用 Kafka 表引擎消费 topic，通过物化视图写入 `ReplicatedMergeTree` 明细表；对外查询走 `Distributed` 表，聚合报表会落到 `AggregatingMergeTree` 或 `SummingMergeTree`。表按天分区，便于时间范围裁剪和 TTL 清理；分片键不选时间，而是按 `user_id`、`device_id` 或 `trace_id` hash，保证数据均匀并贴合查询。生产一般每个 shard 2 副本，核心场景可 3 副本，用于高可用和读扩展。
