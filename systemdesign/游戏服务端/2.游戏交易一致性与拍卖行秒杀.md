# 游戏交易一致性与拍卖行秒杀

游戏中的交易、拍卖、邮件附件和玩家背包都属于资产系统。资产系统的核心要求是：不能凭空增发，不能重复扣减，不能一方付出后另一方没收到，也不能因为重试或并发导致重复成交。

## 1. 玩家交易怎么保证一致性

以 A 向 B 买道具为例，不能直接让 A 先扣钱、B 再给道具，因为中间任一步失败都会造成不一致。常见设计是**服务端权威 + 托管状态机**：

```text
INIT
-> LOCK_ASSET：冻结 A 的货币和 B 的道具
-> CONFIRM：双方确认交易内容
-> COMMIT：同一事务内扣 A 冻结货币、转移道具、给 B 货币
-> DONE
```

如果任一步失败，走取消流程：

```text
CANCEL -> 解冻 A 的货币和 B 的道具 -> END
```

关键点：

1. **冻结而不是立即转移**：确认前资产不可再被其他交易使用。
2. **状态机驱动**：每个交易单有唯一 `trade_id` 和明确状态。
3. **幂等操作**：重复提交同一 `trade_id` 不应重复扣款或重复发货。
4. **事务边界**：同一数据库内优先用本地事务；跨服务时用 TCC、Saga 或消息最终一致。
5. **超时回滚**：长时间未确认的交易自动取消并解冻资产。

## 2. 协程在交易流程中的作用

协程可以把异步 DB、Redis、RPC 调用写成同步风格，减少回调嵌套：

```text
co_await freezeMoney(A)
co_await freezeItem(B)
co_await waitConfirm(A, B)
co_await commitTrade(trade_id)
```

但协程只改善控制流，不自动保证事务一致性。真正保证一致性的是状态机、幂等、锁、事务和补偿逻辑。

易错点：

1. 协程挂起期间交易对象可能被取消，恢复后要重新检查状态。
2. 超时、取消、异常都要释放冻结资产。
3. 不要在协程中持有普通互斥锁跨 `co_await`，否则容易死锁或长时间阻塞。

## 3. 拍卖行秒杀会出现什么问题

拍卖行秒杀本质是热点库存竞争，常见问题：

1. **超卖**：多个请求同时认为商品还在，重复成交。
2. **重复扣款**：客户端超时重试或网关重试导致多次扣货币。
3. **重复发货**：成交消息被重复消费。
4. **热点行锁**：同一商品被大量请求更新，数据库锁等待升高。
5. **恶意抢购**：脚本刷请求，压垮拍卖服务。
6. **缓存不一致**：Redis 显示有库存，数据库已成交。

## 4. 拍卖行秒杀方案

典型链路：

```text
请求鉴权和限流
-> 幂等 key 校验
-> Redis/Lua 原子抢占库存或订单资格
-> 写成交订单/扣款/发货
-> MQ 异步通知和补偿
```

方案要点：

1. **单商品原子抢占**：Redis Lua、数据库乐观锁 `where stock > 0` 或唯一索引保证只能成交一次。
2. **幂等 key**：按 `user_id + auction_id` 或客户端请求号防止重复扣款。
3. **资产冻结**：抢购前冻结货币，成交后转移，失败后解冻。
4. **唯一成交记录**：`auction_id` 建唯一索引，数据库兜底防重复。
5. **队列削峰**：请求先进入队列，按商品分片串行处理，降低热点锁竞争。
6. **补偿任务**：扫描冻结超时、支付成功未发货、发货失败等中间态。

## 5. 面试回答模板

游戏交易不能只靠“先扣钱再给道具”。我会把交易设计成服务端权威的状态机，先冻结双方资产，双方确认后在同一事务或同一状态机步骤里提交；失败或超时则解冻。每个交易有唯一 `trade_id`，扣款、发货、确认都要幂等。协程可以让冻结、确认、提交这些异步步骤写起来像同步代码，但一致性仍然靠状态机、事务、幂等和补偿。拍卖行秒杀要重点防超卖、重复扣款和重复发货，可以用 Redis Lua 或数据库唯一约束做原子抢占，用 MQ 削峰，用补偿任务处理异常中间态。
