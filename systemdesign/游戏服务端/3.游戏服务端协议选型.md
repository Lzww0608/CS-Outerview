# 游戏服务端协议选型

游戏服务端选择 TCP 还是 UDP，不能简单说“游戏都用 UDP”或“TCP 一定可靠所以最好”。要看游戏类型、同步模型、延迟要求、丢包容忍度和开发成本。

## 1. TCP 适合什么游戏场景

TCP 面向连接、可靠、有序，适合：

1. 回合制、卡牌、棋牌、经营类游戏。
2. 登录、充值、背包、任务、聊天、邮件、拍卖行等强一致业务。
3. MMO 中大部分可靠状态同步，例如进入地图、属性变化、道具变更。
4. 开发团队希望降低协议复杂度，优先保证正确性。

缺点是 TCP 有队头阻塞。某个包丢失时，后续已到达的数据也要等重传包补齐后才能交付给应用。

## 2. UDP 适合什么游戏场景

UDP 无连接、保留消息边界、延迟低，适合：

1. FPS、MOBA、竞速、动作游戏中的位置、朝向、输入帧同步。
2. 可丢弃的高频状态，例如玩家移动、子弹轨迹、临时特效。
3. 需要应用层自定义可靠性和重传策略的场景。

UDP 的问题是应用要自己处理丢包、乱序、重复、拥塞控制、NAT 和安全防护。真实项目常使用 KCP、ENet、RakNet、QUIC 或自研可靠 UDP。

## 3. 常见混合方案

很多游戏会混用：

1. **TCP 负责可靠资产链路**：登录、支付、背包、交易、聊天。
2. **UDP/KCP 负责实时战斗**：移动、输入、帧同步、状态广播。
3. **可靠 UDP 分通道**：关键消息可靠有序，位置消息只保留最新值，避免过期包阻塞。
4. **服务端权威**：客户端上传输入或操作意图，服务端校验并广播结果。

## 4. 选型注意事项

1. 实时状态不一定要可靠重传，过期位置包重传可能比丢弃更差。
2. 资产变化必须可靠且幂等，不能因为 UDP 丢包导致扣款或发货不确定。
3. UDP 大包会有 IP 分片风险，公网常控制在 MTU 以下。
4. TCP 长连接要处理心跳、超时、粘包拆包和慢连接。
5. UDP 也要有拥塞控制和限速，否则可能造成网络拥塞或被运营商设备丢弃。

## 5. 面试回答模板

游戏服务端协议要按业务分。交易、背包、登录、聊天这些强一致链路更适合 TCP，因为可靠有序、实现成本低；实时战斗、位置同步、动作输入更适合 UDP 或 KCP，因为更关注低延迟，过期状态可以丢弃。大型游戏常用混合方案：TCP 处理资产和管理类请求，UDP/KCP 处理高频实时同步，并在应用层按消息类型实现可靠、半可靠或只保留最新状态。无论协议怎么选，关键逻辑都应该服务端权威处理。
