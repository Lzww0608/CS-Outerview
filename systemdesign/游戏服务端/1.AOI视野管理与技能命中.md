# AOI视野管理与技能命中

AOI（Area of Interest）用于解决游戏服务端“谁需要看到谁”的问题。玩家、怪物、掉落物和技能效果都在地图上不断移动，如果每次状态变化都广播给全服，网络和 CPU 会被浪费。AOI 的目标是只把对象变化同步给附近或相关的玩家。

## 1. 常见 AOI 方案

### 1.1 九宫格/网格划分

把地图按固定大小切成格子，每个对象根据坐标落到某个格子。查询附近对象时，只查自身格子和周围若干格子。

适用场景：

1. MMO、房间制地图、2D/2.5D 场景。
2. 地图比较规则，视野半径相对固定。
3. 对实现简单、性能稳定要求高。

核心点：

1. 格子大小通常接近视野半径或技能最大作用距离。
2. 玩家移动跨格时，要计算进入视野和离开视野的对象集合。
3. 对象很多时，格子内仍可能需要二次距离过滤。

### 1.2 四叉树/八叉树

按空间密度动态划分区域，二维场景用四叉树，三维场景用八叉树。适合对象分布不均、地图较大且局部热点明显的场景。

缺点是对象频繁移动时树结构更新成本更高，实现复杂度也高于网格。

### 1.3 十字链表/灯塔模型

十字链表把对象按 x、y 坐标分别维护有序链表，移动时更新链表位置，查询时按坐标范围找候选对象。灯塔模型则把地图划成区域或兴趣点，用订阅关系维护可见对象。

这些方案适合特定类型游戏，但工程上最常见的仍是网格和分层网格。

## 2. 技能命中怎么计算

技能命中不要直接“遍历全地图对象”。推荐流程：

```text
收到施法请求
-> 校验玩家状态、技能 CD、资源、位置和朝向
-> 根据 AOI 或空间索引拿候选目标
-> 按技能形状做几何过滤
-> 做阵营、无敌、障碍、距离、时间戳校验
-> 计算伤害和效果
-> 广播结果给相关 AOI 玩家
```

常见技能形状：

1. **圆形范围**：判断目标点到圆心距离是否小于半径。
2. **扇形范围**：同时判断距离和方向夹角。
3. **矩形/胶囊体**：适合冲锋、直线弹道、激光类技能。
4. **投射物**：按时间推进位置，检测路径上的碰撞体。

示例：扇形技能判定可以先用 AOI 找候选，再做距离平方和点积判断：

```cpp
bool inSector(Vec2 caster, Vec2 forward, Vec2 target,
              float radius, float cosHalfAngle) {
    Vec2 d = target - caster;
    float len2 = dot(d, d);
    if (len2 > radius * radius) {
        return false;
    }
    Vec2 dir = normalize(d);
    return dot(forward, dir) >= cosHalfAngle;
}
```

## 3. 逻辑要不要发给服务端处理

核心逻辑必须由服务端权威处理。客户端可以做预测、表现和输入采集，但不能让客户端决定最终结果。

服务端应该负责：

1. 位置合法性、移动速度和穿墙校验。
2. 技能 CD、资源消耗、技能范围和目标状态校验。
3. 掉落、交易、拍卖、货币、经验等资产变化。
4. 战斗结算和随机数结果。

客户端可以负责：

1. 预播放技能动画和移动预测。
2. 本地插值、平滑、镜头和特效。
3. 收到服务端结果后做校正和回滚。

## 4. 同步范围管理和数据压缩

游戏服务端同步的关键不是“所有状态都广播”，而是维护每个玩家的可见集合。玩家移动、对象创建或销毁时，服务端需要计算新旧 AOI 集合差异：

```text
old_visible = 上一帧可见对象集合
new_visible = 当前帧可见对象集合
enter = new_visible - old_visible
leave = old_visible - new_visible
stay  = new_visible & old_visible
```

常见同步策略：

1. `enter` 发送完整快照，让客户端创建实体。
2. `leave` 发送离开视野或销毁消息，让客户端移除实体。
3. `stay` 只发送位置、朝向、血量等变化字段，尽量做增量同步。
4. 远处或低优先级对象降低同步频率，近处战斗对象提高频率。
5. 不在视野内的玩家不进行同步，既节省带宽，也避免泄露隐藏信息。

数据压缩可以分层做：

1. **字段级压缩**：坐标量化为整数，朝向用较少 bit 表示，布尔状态用 bitset 打包。
2. **增量压缩**：只发送和上一次快照不同的字段，位置发送 delta 而不是全量坐标。
3. **编码压缩**：实体 ID、物品数量等使用 varint；协议层可选 Protobuf、FlatBuffers、自定义二进制协议。
4. **批量压缩**：多个小包合并后再用 LZ4/Zstd 等压缩；非常小的包直接压缩可能得不偿失。
5. **语义压缩**：只同步客户端渲染需要的信息，例如远处单位不发精确动作细节。

实际工程中要平衡 CPU 和带宽：对高频小包优先做字段级和增量压缩，对低频大包才考虑通用压缩算法。压缩前还要先做兴趣过滤，否则把无关对象压缩得再小也会浪费带宽。

## 5. 易错点

1. AOI 粗筛后仍要做精确距离和业务条件过滤。
2. 格子过大会导致候选对象过多，格子过小会导致跨格维护成本变高。
3. 技能判定不能只相信客户端传来的命中列表，否则容易被外挂利用。
4. 服务器要处理延迟和乱序，关键请求应带序号、时间戳或帧号。
5. 广播时只发给相关玩家，避免把隐藏对象或远处状态泄露给客户端。

## 6. 面试回答模板

AOI 是兴趣区域管理，核心是减少广播范围。常见做法是把地图切成网格，玩家移动时维护对象所在格子，查询视野时只看当前格和周围格，再按真实距离过滤。同步时维护每个玩家的可见集合，进入视野发完整快照，离开视野发移除消息，停留在视野内只发增量状态；不在视野内的玩家不进行同步。技能命中也不遍历全地图，而是先用 AOI 找候选目标，再按圆形、扇形、矩形或弹道做几何判定，并校验 CD、资源、阵营、无敌和障碍。最终战斗和资产逻辑必须由服务端权威处理，客户端只做预测和表现，避免外挂直接伪造命中结果。
