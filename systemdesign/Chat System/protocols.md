### 1. Polling (短轮询 / 传统轮询)

这是最古老、最简单的实现方式。

*   **比喻：**
    你每隔10分钟就去快递点问老板：“我的快递到了吗？”
    老板立刻回答：“没到。”
    你回家，过10分钟再去问：“到了吗？”
    老板：“没到。”
    ...
    直到某一次，老板说：“到了，给你。”

*   **技术原理：**
    客户端使用 `setInterval` 或类似机制，**定期**（例如每秒）向服务器发送 HTTP 请求。服务器收到请求后，立刻查询有没有新数据，无论有没有，都立刻返回响应。

*   **优点：**
    *   **实现简单：** 前后端都无需特殊配置，标准的 AJAX 请求。
    *   **兼容性好：** 支持所有浏览器。

*   **缺点：**
    *   **延迟高：** 消息到达的延迟取决于轮询的间隔（间隔设为5秒，消息可能晚5秒才看到）。
    *   **资源浪费严重：** 90% 的请求可能都是空的（无效请求），但依然消耗带宽、流量和服务器的 CPU，且每次都要重新建立 TCP 连接和发送 HTTP 头。

---

### 2. Long Polling (长轮询)

这是对短轮询的一种改进，也称为 "Comet" 技术。

*   **比喻：**
    你去快递点问老板：“我的快递到了吗？”
    **老板不立刻回答你，而是让你站在柜台前等着。**
    老板一直盯着仓库，直到：
    1.  快递到了 -> 老板给你快递，你拿回家，然后立刻跑回来再次排队等着。
    2.  或者等太久了（比如30秒），老板说“还是没到，你先歇会儿再来” -> 你出去转一圈立刻回来接着排队。

*   **技术原理：**
    客户端发起 HTTP 请求，服务器**不立刻返回**，而是将连接**挂起 (Hold)**。
    一旦服务器有新数据产生，或者连接超时（通常是30-60秒），服务器才返回响应。客户端收到响应后，**立刻**再次发起新的请求。

*   **优点：**
    *   **实时性较好：** 数据一旦产生，服务器几乎可以立刻推送给客户端。
    *   **减少无效请求：** 相比短轮询，大大减少了请求次数。

*   **缺点：**
    *   **服务器压力大：** 服务器需要为每个用户保持一个挂起的连接，这会消耗大量内存和线程资源（虽然现代 Node.js 等异步架构缓解了这个问题）。
    *   **仍然是 HTTP：** 每次数据传输完毕后连接会断开，再次发起请求时仍然需要重新发送 HTTP 头部，对于频繁的小数据通信（如打字中的状态），开销依然不小。

---

### 3. WebSocket

这是现代实时通信的标准解决方案，也是 Chat System 的首选。

*   **比喻：**
    你和快递点老板**拉了一条专用的电话线**。
    电话接通后就不挂断。
    你有事可以直接说话，老板有快递到了也可以直接告诉你。
    双方可以**同时**说话。

*   **技术原理：**
    WebSocket 是一种在单个 TCP 连接上进行**全双工 (Full-duplex)** 通信的协议。
    它始于一个 HTTP 请求（握手），一旦握手成功，连接就从 HTTP 协议“升级”为 WebSocket 协议。此后，连接保持打开，双方可以随时互发数据，不需要发送 HTTP 头。

*   **优点：**
    *   **真正的实时：** 延迟极低。
    *   **双向通信：** 服务器可以主动推，客户端也可以主动发。
    *   **开销极低：** 建立连接后，数据包头部非常小（只有几个字节），不像 HTTP 每次都要带几百字节的 Header。

*   **缺点：**
    *   **实现复杂：** 需要专门的服务器支持，且是有状态的（Stateful），在分布式系统中需要考虑会话保持或 Redis 广播。
    *   **网络限制：** 极少数严格的企业防火墙可能会屏蔽非 HTTP 流量。

---

### 总结对比表

| 特性                | Polling (短轮询)                      | Long Polling (长轮询)         | WebSocket                                |
| :------------------ | :------------------------------------ | :---------------------------- | :--------------------------------------- |
| **通信方式**        | 单向 (客户端请求)                     | 单向 (客户端请求，服务端挂起) | **双向 (全双工)**                        |
| **连接性质**        | 短连接 (请求-响应-断开)               | 长连接 (请求-等待-响应-断开)  | **持久连接 (握手后一直连通)**            |
| **实时性**          | 低 (受间隔限制)                       | 中/高                         | **极高**                                 |
| **开销 (Overhead)** | **极高** (频繁建立连接+HTTP头)        | 中 (重复建立连接+HTTP头)      | **极低** (轻量级帧头)                    |
| **服务器负载**      | 高 (处理大量无效请求)                 | 高 (Hold住大量连接占用资源)   | 低/中 (主要消耗内存维持连接)             |
| **适用场景**        | 这里的业务数据变化不频繁 (如新闻列表) | 简单的通知系统，旧系统改造    | **聊天室、即时通讯、即时游戏、股票行情** |

### 应该怎么选？

*   如果是做**聊天系统 (Chat System)**：**必须选 WebSocket**。它是为了这个场景而生的。
*   如果只是做一个简单的“是否有新通知”的小红点功能，且不想引入复杂的 WebSocket 架构：**Long Polling** 是可以接受的。
*   **Polling** 在现代高并发实时系统中通常**不推荐使用**，除非数据更新频率极低（例如每10分钟更新一次的天气）。



**WebSocket 是一个独立的协议，它不属于 HTTP，但在建立连接的“第一步”必须借助于 HTTP。**

你可以把它们的关系理解为：**HTTP 是 WebSocket 的“引路人”或“垫脚石”。**

以下是详细的层级和关系解析：

### 1. 它们的关系：握手 (Handshake)

WebSocket 协议的设计非常巧妙，为了兼容现有的互联网设施（防火墙、代理服务器等），它并没有另起炉灶开一个新的端口，而是**伪装**成一个 HTTP 请求来发起连接。

这个过程叫做 **协议升级 (Protocol Upgrade)**。

#### 过程演示：
1.  **第一阶段（HTTP）：**
    客户端（浏览器）先发一个标准的 HTTP GET 请求给服务器。但是，这个请求的 Header 里带了几个特殊的暗号：
    ```http
    GET /chat HTTP/1.1
    Host: server.example.com
    Upgrade: websocket        <-- 关键点：我想升级协议
    Connection: Upgrade       <-- 关键点：请保持连接
    Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==
    ```

2.  **第二阶段（服务器确认）：**
    如果服务器支持 WebSocket，它会返回一个特殊的 HTTP 响应码 **101 Switching Protocols**：
    ```http
    HTTP/1.1 101 Switching Protocols
    Upgrade: websocket
    Connection: Upgrade
    Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo=
    ```

3.  **第三阶段（WebSocket）：**
    **关键时刻来了！** 一旦客户端收到这个 101 响应，**HTTP 协议的任务就结束了**。
    原本的 HTTP 连接（TCP连接）**不会断开**，而是瞬间“变身”为 WebSocket 协议通道。
    此后，双方传输的数据不再遵守 HTTP 的规则（Header+Body），而是遵守 WebSocket 的二进制帧（Frame）规则。

### 2. 形象的比喻：英语与法语

想象一下 HTTP 是**英语**，WebSocket 是**法语**。

*   **场景：** 两个法国特工在英国（互联网环境）接头。
*   **握手（HTTP）：**
    特工A（客户端）走过来，先用**英语**（HTTP）大声说：“你好，我想和你用**法语**（WebSocket）交流，可以吗？”
    特工B（服务器）用**英语**（HTTP）回答：“好的，没问题，切换语言！”
*   **通信（WebSocket）：**
    从这一秒开始，两人立刻改用**法语**（WebSocket）进行极速交流。旁边的英国人（不支持 WS 的老旧设备）只听懂了开头的英语，后面的就听不懂了。

### 3. 为什么说它们是“不同”的协议？

虽然借用了 HTTP 握手，但它们在本质上区别巨大：

| 特征         | HTTP                                                         | WebSocket                                                    |
| :----------- | :----------------------------------------------------------- | :----------------------------------------------------------- |
| **层级**     | 应用层 (Layer 7)                                             | 应用层 (Layer 7)                                             |
| **底层传输** | TCP                                                          | TCP                                                          |
| **通信模式** | **请求-响应 (Request-Response)**<br>必须客户端先开口，服务器才能回话。 | **全双工 (Full-Duplex)**<br>双方地位平等，服务器可以随时主动发消息。 |
| **状态**     | **无状态 (Stateless)**<br>每个请求都是独立的，服务器不记得上个请求是谁发的。 | **有状态 (Stateful)**<br>连接一旦建立就一直保持，服务器知道“这条线”对面是谁。 |
| **数据格式** | 文本为主，头部 (Header) 很大，冗余多。                       | 二进制帧，头部极小 (2-14字节)，非常轻量。                    |

### 4. 为什么 WebSocket 要设计成这样？

既然 WebSocket 这么强，为什么不直接建立 TCP 连接，非要披着 HTTP 的外衣？

**为了生存（兼容性）。**

互联网的世界里充满了防火墙、负载均衡器和代理服务器。
*   这些设备通常只允许 **80端口 (HTTP)** 和 **443端口 (HTTPS)** 的流量通过。
*   如果 WebSocket 发明一个新的协议，运行在 8888 端口，大概率会被公司的防火墙直接拦截。
*   通过伪装成 HTTP 发起握手，WebSocket 可以顺利骗过防火墙，“混”进内网，然后再升级协议。

### 总结

*   **WebSocket 不是基于 HTTP 的**（它不是 HTTP 的一部分，也不是 HTTP 的补丁）。
*   **WebSocket 依赖 HTTP 进行握手**（借道）。
*   一旦握手成功，HTTP 协议就被“踢开”了，剩下的就是纯粹的 WebSocket 协议在 TCP 上裸奔。

### 5. WebSocket 能做负载均衡吗？

WebSocket 可以做负载均衡，但它和普通 HTTP 短请求不同：连接建立后会长期保持，连接状态、订阅关系和在线用户映射通常落在某一台网关实例上，所以负载均衡要同时处理“新连接怎么分配”和“连接状态怎么共享”。

常见方案：

1. **四层负载均衡**：按 TCP 连接转发，性能高，适合只需要把连接分散到多个 WebSocket 网关的场景。
2. **七层负载均衡**：先处理 HTTP Upgrade 握手，可以按路径、Header、Cookie 或用户维度路由。
3. **会话保持**：如果网关保存用户连接状态，可以使用 Cookie、IP Hash 或一致性哈希，让同一用户尽量落到同一实例。
4. **无状态网关 + 共享状态**：连接在网关本地，用户在线状态、房间订阅、消息路由写入 Redis、etcd 或专用 Presence 服务。
5. **消息广播层**：跨网关投递消息时，通过 Redis Pub/Sub、Kafka、Pulsar、NATS 或内部 RPC 把消息送到持有连接的网关。

真实系统里更推荐把 WebSocket 网关做成“连接层有状态、业务层无状态”。网关只维护连接、心跳、限流和用户到连接的映射，业务消息通过后端服务或消息队列路由。这样扩容时只需要增加网关实例，新连接由负载均衡分配；老连接等自然断开或主动 drain。

易错点：

1. WebSocket 连接建立后不会像 HTTP 请求一样每次重新负载均衡，长连接会一直占住后端实例。
2. 单纯加负载均衡不能解决跨节点发消息问题，必须知道目标用户连接在哪个网关。
3. 发布新版本或缩容时要做连接排水：停止接新连接，保留一段时间处理旧连接，再主动关闭。
4. 心跳和空闲超时要和负载均衡器配置一致，否则中间设备可能提前断开连接。
5. 如果使用粘性会话，要考虑实例故障后用户重连和订阅恢复。
