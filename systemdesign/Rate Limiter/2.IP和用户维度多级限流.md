# 2. IP 和用户维度多级限流

IP 和用户维度的多级限流，是指同一个请求进入系统时，不只按一个 key 做限流，而是同时经过多层、多个维度的流量保护，例如全局限流、接口限流、IP 限流、用户限流、设备限流、租户限流和下游资源限流。

面试里可以先说结论：**IP 维度适合拦截未登录流量、爬虫、撞库和同源异常流量；用户维度适合控制登录用户的资源使用、付费配额和业务公平性。真实系统通常采用网关粗限流 + 应用精细限流 + Redis/本地混合计数 + 风控动态规则的多级方案，而不是只用一个 Redis key。**

## 1. 为什么要同时做 IP 和用户限流

只做 IP 限流的问题：

1. 大量真实用户可能共用一个出口 IP，例如公司 NAT、校园网、运营商 NAT，容易误伤。
2. 攻击者可以使用代理池、云主机、移动网络切换 IP 绕过。
3. 登录后只按 IP 限流，无法控制单个用户的高成本行为。

只做用户限流的问题：

1. 未登录接口没有 userId，只能依赖 IP、设备指纹、session、手机号等维度。
2. 攻击者可以批量注册账号，绕过单用户阈值。
3. 单个 IP 下大量账号并发请求时，仍可能打爆系统。

所以多级限流的目标是：

1. 对未登录流量，用 IP、设备、接口维度先挡住异常流量。
2. 对登录流量，用用户、租户、接口、资源维度限制公平使用。
3. 对核心资源，用全局和下游限流保护数据库、Redis、MQ、第三方接口。
4. 对风险接口，用更严格的滑动窗口、验证码、风控和黑名单策略。

## 2. 多级限流放在哪些层

典型链路：

```text
客户端
-> CDN / WAF
-> Nginx / API Gateway
-> BFF / 应用服务
-> Redis 限流状态
-> DB / MQ / 第三方服务
```

可以分层做：

| 层级 | 主要维度 | 作用 |
| --- | --- | --- |
| CDN/WAF | IP、国家、ASN、UA、路径 | 拦截明显攻击、爬虫、异常地区流量 |
| Nginx/API Gateway | IP、接口、租户、AppKey | 入口粗限流，保护后端整体容量 |
| 应用服务 | userId、deviceId、业务资源、接口 | 业务精细限流，结合权限和套餐 |
| Redis/集中限流服务 | 多实例共享计数 | 保证分布式场景下限流状态一致 |
| 本地限流器 | 实例级别、下游调用 | Redis 故障兜底、削峰和降低 Redis 压力 |

原则：

1. 越靠前，规则越粗，成本越低。
2. 越靠后，规则越精细，能拿到更多业务身份。
3. 高成本接口要在更前面就做限流，避免请求进入业务深处后才被拒绝。

## 3. 常见限流维度

### 3.1 IP 维度

适用：

1. 未登录接口。
2. 登录、注册、验证码、找回密码。
3. 爬虫、扫描、撞库防护。
4. 同一来源流量异常增长。

key 示例：

```text
rl:ip:{api}:{ip}
rl:ip:login:1.2.3.4
rl:ip:sms:1.2.3.4
```

注意真实 IP 获取：

1. 网关后面不能直接用 TCP remote address，因为它可能是上一层代理 IP。
2. 要从可信代理写入的 `X-Forwarded-For`、`X-Real-IP` 或内部 header 中取真实 IP。
3. 不能直接信任客户端传入的 `X-Forwarded-For`，否则攻击者可以伪造 IP 绕过限流。
4. IPv6 要做规范化，必要时按前缀聚合，例如 `/64`。

### 3.2 用户维度

适用：

1. 登录后接口。
2. AI 调用、导出、搜索、下单、发帖等高成本行为。
3. 付费套餐配额。
4. 防止单用户占用过多资源。

key 示例：

```text
rl:user:{api}:{userId}
rl:user:search:10086
rl:user:export:10086
```

用户维度更精准，但要注意：

1. 登录态必须可信，不能用客户端传入 userId。
2. 多端登录要共享同一用户限额。
3. 管理员、普通用户、付费用户、企业用户阈值可能不同。
4. 单用户下面还可以细分资源维度，例如 `userId + skuId`、`userId + modelId`。

### 3.3 其他维度

真实系统还会组合：

```text
rl:device:{api}:{deviceId}
rl:tenant:{api}:{tenantId}
rl:appkey:{api}:{appKey}
rl:phone:{scene}:{phone}
rl:resource:{resourceId}
rl:global:{api}
```

例如短信验证码接口通常同时看：

1. 同一手机号 1 分钟 1 次。
2. 同一手机号 1 天 10 次。
3. 同一 IP 1 分钟 30 次。
4. 同一设备 1 小时 20 次。
5. 全局短信供应商 QPS 不超过阈值。

## 4. 规则模型怎么设计

限流规则可以抽象为：

```json
{
  "name": "login_ip_1m",
  "scope": "IP",
  "api": "/api/login",
  "algorithm": "SLIDING_WINDOW",
  "windowMs": 60000,
  "limit": 30,
  "action": "REJECT",
  "priority": 10
}
```

常见字段：

| 字段 | 含义 |
| --- | --- |
| `scope` | 限流维度，例如 IP、USER、DEVICE、TENANT、GLOBAL |
| `api` | 接口、方法或业务动作 |
| `windowMs` | 时间窗口 |
| `limit` | 窗口内最大请求数 |
| `algorithm` | 固定窗口、滑动窗口、令牌桶、漏桶 |
| `action` | 拒绝、验证码、排队、降级、只读 |
| `priority` | 多条规则命中时的优先级 |
| `burst` | 短时突发容量 |
| `ttlMs` | 计数 key 保留时间 |

规则来源可以是：

1. 配置中心。
2. 数据库规则表。
3. 网关动态配置。
4. 风控系统实时下发。

规则要支持灰度和回滚，避免阈值配错导致大面积误伤。

## 5. 多级限流的执行顺序

推荐顺序：

```text
1. 全局限流：保护整个系统容量
2. 接口限流：保护某个高成本接口
3. IP 限流：拦截未登录或同源异常流量
4. 设备限流：拦截多账号同设备
5. 用户限流：控制登录用户公平使用
6. 租户/套餐限流：控制企业或付费等级配额
7. 下游资源限流：保护 DB、Redis、第三方服务
```

一个请求只要命中任意强拒绝规则，就可以直接拒绝。

但并不是所有规则都必须强拒绝：

1. IP 轻度超限：返回验证码。
2. 用户轻度超限：排队或降级。
3. 高风险接口超限：直接拒绝。
4. 内部系统超限：返回明确错误码并告警。

## 6. 算法如何选择

| 算法 | 特点 | 适用 |
| --- | --- | --- |
| 固定窗口 | 简单，边界有突刺 | 粗粒度统计、低风险接口 |
| 滑动窗口日志 | 精确，内存随请求数增长 | 登录、短信、风控接口 |
| 滑动窗口计数 | 近似，内存稳定 | 高 QPS API |
| 令牌桶 | 允许突发，限制平均速率 | 网关、用户配额、下载上传 |
| 漏桶 | 平滑输出 | 保护下游、异步消费 |

常见组合：

1. 网关入口：令牌桶，允许合理突发。
2. 登录/验证码：滑动窗口日志，精确判断短时间爆破。
3. 普通 API：滑动窗口计数，降低存储开销。
4. 下游调用：漏桶或并发隔离，平滑访问数据库和第三方。

## 7. Redis + Lua 多维度原子判断

多级限流如果拆成多次 Redis 调用，可能出现部分维度已计数、部分维度失败的问题。工程上可以用 Lua 把“检查多个 key + 通过后全部计数”放到一次脚本里。

### 7.1 固定窗口简化版

固定窗口适合讲清楚多维度原子检查：

```lua
-- KEYS: rate limit keys
-- ARGV[1] = limit count for key1
-- ARGV[2] = ttl ms for key1
-- ARGV[3] = limit count for key2
-- ARGV[4] = ttl ms for key2
-- ...

local n = #KEYS

-- first pass: check all dimensions
for i = 1, n do
    local limit = tonumber(ARGV[(i - 1) * 2 + 1])
    local current = tonumber(redis.call('GET', KEYS[i]) or '0')
    if current >= limit then
        return {0, KEYS[i], current, limit}
    end
end

-- second pass: all allowed, then increment all dimensions
for i = 1, n do
    local ttl = tonumber(ARGV[(i - 1) * 2 + 2])
    local current = redis.call('INCR', KEYS[i])
    if current == 1 then
        redis.call('PEXPIRE', KEYS[i], ttl)
    end
end

return {1, '', 0, 0}
```

调用时可以传入多个维度：

```text
KEYS[1] = rl:global:/api/search
KEYS[2] = rl:ip:/api/search:1.2.3.4
KEYS[3] = rl:user:/api/search:10086
```

返回结果：

```text
{1, "", 0, 0}                         -> 放行
{0, "rl:user:/api/search:10086", 100, 100} -> 用户维度超限
```

### 7.2 滑动窗口日志版

严格风控接口可以用 ZSet：

```lua
-- KEYS: rate limit keys
-- ARGV[1] = now ms
-- ARGV[2] = window ms for key1
-- ARGV[3] = limit for key1
-- ARGV[4] = member suffix
-- ARGV[5] = window ms for key2
-- ARGV[6] = limit for key2
-- ARGV[7] = member suffix
-- ...

local now = tonumber(ARGV[1])
local n = #KEYS

for i = 1, n do
    local base = 2 + (i - 1) * 3
    local window = tonumber(ARGV[base])
    local limit = tonumber(ARGV[base + 1])

    redis.call('ZREMRANGEBYSCORE', KEYS[i], 0, now - window)
    local count = redis.call('ZCARD', KEYS[i])
    if count >= limit then
        return {0, KEYS[i], count, limit}
    end
end

for i = 1, n do
    local base = 2 + (i - 1) * 3
    local window = tonumber(ARGV[base])
    local member = tostring(now) .. ':' .. ARGV[base + 2] .. ':' .. tostring(i)
    redis.call('ZADD', KEYS[i], now, member)
    redis.call('PEXPIRE', KEYS[i], window)
end

return {1, '', 0, 0}
```

注意：

1. `member` 不能只用时间戳，否则同毫秒多请求会覆盖。
2. 滑动日志精确但内存更高，高 QPS 场景要谨慎。
3. Redis Cluster 下，多 key Lua 要求所有 key 在同一个 slot。

## 8. Redis Cluster 下怎么设计 key

如果一个 Lua 脚本要同时检查多个 key，它们必须在同一个 hash slot。

可以使用 hash tag：

```text
rl:{login}:global
rl:{login}:ip:1.2.3.4
rl:{login}:user:10086
```

但这样同一个接口的所有限流 key 都可能落到一个 slot，热点接口会压到单个 Redis 分片。

取舍方案：

1. **强原子多维度检查**：同一接口使用 hash tag，同 slot 执行 Lua。
2. **高吞吐优先**：不同维度拆开执行，接受极小窗口内的非严格原子，配合补偿和拒绝优先策略。
3. **集中限流服务**：由限流服务在内存中聚合规则，再批量同步状态或按一致性哈希分片。
4. **网关本地预限流 + Redis 精确限流**：先用本地令牌桶削峰，再访问 Redis，降低 Redis 热点。

面试里要说明：跨 slot 无法靠一个 Redis Lua 做分布式事务，不能把 Redis Cluster 的多分片误认为天然支持全局原子限流。

## 9. 本地限流和分布式限流怎么配合

纯 Redis 限流的问题：

1. 每个请求都访问 Redis，增加延迟。
2. Redis 成为热点瓶颈。
3. Redis 故障时限流链路失效。

可以加本地限流：

```text
请求
-> 本地快速令牌桶，挡掉明显超额流量
-> Redis 分布式限流，保证多实例共享额度
-> 业务逻辑
```

本地限流适合：

1. 实例保护。
2. Redis 故障兜底。
3. 粗粒度削峰。
4. 高频接口降低 Redis 调用量。

但本地限流不能单独保证全局额度。例如 10 个实例，每个实例本地允许 100 QPS，总量可能达到 1000 QPS。因此全局精确限额仍要用 Redis、网关集中状态或专门限流服务。

## 10. 如何处理真实 IP

真实 IP 获取是 IP 限流最容易出错的地方。

反向代理链路可能是：

```text
Client
-> CDN
-> WAF
-> Nginx
-> API Gateway
-> App
```

处理原则：

1. 只信任内部代理写入的 header。
2. 在边界网关清洗用户传入的 `X-Forwarded-For`。
3. 从可信代理链中取第一个真实客户端 IP。
4. 对 IPv6 做规范化和前缀聚合。
5. 对内网 IP、保留地址、空 IP 做异常处理。

错误做法：

```text
直接使用客户端传入的 X-Forwarded-For
```

攻击者可以构造：

```text
X-Forwarded-For: 8.8.8.8
```

从而绕过基于 IP 的限流。

## 11. NAT、代理池和误伤问题

IP 限流天然有误伤和绕过风险。

### 11.1 NAT 误伤

同一个公司、学校、运营商出口 IP 后面可能有大量正常用户。

优化：

1. IP 限流不要过低。
2. 登录后以 userId 为主，IP 为辅助。
3. 对可信企业客户、内网出口做白名单或更高阈值。
4. 超限后优先验证码、排队，而不是直接封禁。

### 11.2 代理池绕过

攻击者可以用大量 IP 分散请求。

优化：

1. 组合用户、设备、手机号、UA、行为特征。
2. 对异常 IP 段、ASN、机房 IP 做风险加权。
3. 短时间大量新账号、新设备、新 IP 关联时触发风控。
4. 高风险行为要求验证码、二次验证或人工审核。

## 12. 返回什么错误和如何降级

HTTP 层通常返回：

```text
429 Too Many Requests
Retry-After: 10
```

响应体可以包含：

```json
{
  "code": "RATE_LIMITED",
  "message": "请求过于频繁，请稍后再试",
  "retryAfterSeconds": 10
}
```

不同场景的动作：

| 场景 | 处理 |
| --- | --- |
| 普通接口轻度超限 | 返回 429，提示稍后再试 |
| 登录/验证码异常 | 触发验证码、短信二次校验 |
| 高成本导出 | 进入排队任务 |
| AI/搜索接口 | 降级模型、减少结果数、返回配额不足 |
| 支付/下单 | 通常 fail closed，避免风险扩大 |
| Redis 限流服务故障 | 普通读接口可本地限流后 fail open，风险接口 fail closed |

## 13. 监控指标

多级限流必须可观测，否则阈值很难调。

建议监控：

1. 每条规则命中次数。
2. 按 IP、用户、接口、租户统计的拒绝率。
3. 429 数量和占比。
4. Redis 限流脚本耗时和错误率。
5. 本地限流和 Redis 限流命中比例。
6. 被限流后的业务成功率和投诉量。
7. 下游 DB、Redis、MQ、第三方接口负载是否下降。
8. Top IP、Top user、Top device、Top appKey。

告警不要只看限流命中高。限流命中高可能是策略生效，也可能是误伤。要结合错误率、业务转化率、下游负载和风险事件一起判断。

## 14. 易错点

1. 只按 IP 限流会误伤 NAT 后面的正常用户。
2. 只按用户限流挡不住未登录和批量账号攻击。
3. 直接信任 `X-Forwarded-For` 会被伪造。
4. 多维度 Redis 计数如果不是原子操作，可能出现部分计数成功或并发放大。
5. Redis Cluster 下多 key Lua 需要同 slot。
6. 阈值不能拍脑袋，要结合压测、业务峰值和下游容量。
7. 限流失败策略要区分场景，不能所有接口都 fail open 或 fail closed。
8. 只有限流没有监控，线上无法判断是攻击、误伤还是阈值过低。
9. 限流不能替代鉴权、风控、验证码和黑名单。
10. 高 QPS 场景使用滑动日志要注意 Redis 内存和 ZSet 清理开销。

## 15. 面试回答模板

IP 和用户维度的多级限流，我会分层设计。最前面在 CDN/WAF 或 API Gateway 做粗粒度 IP、路径、AppKey 限流，先挡爬虫、扫描和明显异常流量；进入应用后，根据登录态拿到 userId，再做用户维度、设备维度、租户维度和接口维度的精细限流；最后还要有全局限流和下游资源限流，保护数据库、Redis、MQ 和第三方服务。

算法上，网关入口可以用令牌桶，允许一定突发但限制平均速率；登录、短信验证码这类风险接口用滑动窗口日志，更精确地判断短时间爆破；普通高 QPS API 可以用滑动窗口计数或固定窗口加随机分桶。分布式场景下限流状态可以放 Redis，用 Lua 一次性检查多个 key，例如 `global + ip + user`，只有所有维度都没超限才统一计数并放行，避免并发下多条命令不原子。

实现时要特别注意真实 IP 获取，只信任网关清洗后的 `X-Forwarded-For` 或内部 header，不能直接信任客户端传入值。IP 维度容易误伤 NAT 后面的正常用户，所以登录后应以 userId 为主、IP 为辅助；攻击者使用代理池时，还要结合设备指纹、账号、手机号、UA、行为特征和风控。超限后普通接口返回 429 和 `Retry-After`，风险接口可以触发验证码或 fail closed。最后必须接入监控，看每条规则命中率、Top IP/用户、Redis 脚本耗时、429 占比和下游负载变化，避免阈值配置造成大面积误伤。
