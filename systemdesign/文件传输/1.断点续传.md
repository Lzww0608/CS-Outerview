# 断点续传

断点续传是指文件传输中断后，不从头重新传，而是从已经成功传输的位置继续。它既可以用于下载，也可以用于上传；核心是“可定位的字节范围、可校验的文件状态、可恢复的会话元数据”。

## 1. 下载断点续传

HTTP 下载常用 Range 请求：

```http
GET /video.mp4 HTTP/1.1
Range: bytes=1048576-
```

服务端如果支持范围下载，会返回：

```http
HTTP/1.1 206 Partial Content
Content-Range: bytes 1048576-2097151/8388608
Accept-Ranges: bytes
```

客户端需要保存：

1. 已下载文件大小或分片完成情况。
2. 文件唯一标识，例如 URL、文件 ID、ETag、Last-Modified、版本号。
3. 临时文件路径和校验信息。

恢复时先确认文件没有变化。如果 ETag 或版本变了，旧的本地部分可能失效，应重新下载。

## 2. 上传断点续传

上传通常采用分片上传：

1. 客户端计算文件 ID，例如 `hash(file)` 或服务端生成 uploadId。
2. 文件切成固定大小 chunk，例如 4MB、8MB。
3. 客户端上传 chunk，携带 `uploadId`、`chunkIndex`、`offset`、`checksum`。
4. 服务端记录每个 chunk 的完成状态。
5. 中断后客户端查询已上传分片，只补传缺失分片。
6. 所有分片完成后，服务端合并文件并做整体校验。

示例接口：

```text
POST /uploads/init        -> uploadId
PUT  /uploads/{id}/parts/{index}
GET  /uploads/{id}/parts  -> uploaded parts
POST /uploads/{id}/merge
```

## 3. 文件大小、分片和请求头

获取文件大小要区分客户端、协议和服务端三个位置：

1. **客户端本地文件**：浏览器可用 `File.size`，移动端或桌面端可用文件 API 获取长度。
2. **HTTP 请求体大小**：普通上传依赖 `Content-Length`，分块传输可能是 `Transfer-Encoding: chunked`，不能只靠一次请求头判断完整文件大小。
3. **服务端本地文件**：落盘后用 `stat/fstat` 获取逻辑大小；排查磁盘占用时再看 `du`。
4. **分片数量**：`totalChunks = ceil(fileSize / chunkSize)`，最后一个分片大小可能小于 `chunkSize`。

上传分片常见请求头或字段：

```http
PUT /uploads/u123/parts/7 HTTP/1.1
Content-Length: 4194304
Content-Range: bytes 25165824-29360127/104857600
Content-Type: application/octet-stream
X-Upload-Id: u123
X-Part-Number: 7
X-Checksum-SHA256: ...
```

如果使用表单上传，常见格式是：

```http
Content-Type: multipart/form-data; boundary=----WebKitFormBoundary...
```

下载续传常用：

```http
Range: bytes=1048576-
If-Range: "etag-or-last-modified"
```

服务端返回：

```http
206 Partial Content
Accept-Ranges: bytes
Content-Range: bytes 1048576-2097151/8388608
ETag: "file-version"
```

## 4. 服务端落盘涉及的系统调用

服务端上传链路通常是“从 socket 读数据，再写入临时文件或对象存储”：

1. `accept/epoll_wait/recv/read`：接收客户端连接和请求体。
2. `open/openat`：创建临时分片文件。
3. `write/pwrite`：把当前 chunk 写到指定文件或指定 offset。乱序分片更适合 `pwrite`。
4. `fsync/fdatasync`：对强可靠场景，把分片或元数据刷盘；普通场景可批量或异步刷盘。
5. `rename`：分片合并或最终文件提交时，用原子 rename 从临时路径切到正式路径。
6. `close/unlink`：关闭文件和清理失败、过期的临时文件。

注意：`sendfile` 更常用于**下载**静态文件，上传方向一般还是从 socket 读到用户态或由网关/对象存储协议直接接管。`mmap` 适合随机访问或多进程共享，不适合盲目用来承接所有大文件上传。

## 5. 一致性和校验

断点续传不能只相信 offset，必须校验数据：

1. **分片校验**：每个 chunk 上传后校验 MD5/SHA256/CRC32C。
2. **整体校验**：合并后计算完整文件 hash。
3. **幂等上传**：同一个 `uploadId + chunkIndex` 重复上传时，要么覆盖同内容，要么校验冲突并拒绝。
4. **并发控制**：同一文件多个客户端或多线程上传时，要避免重复 merge 和状态覆盖。
5. **过期清理**：长期未完成的 uploadId 和临时分片需要定期清理。

## 6. 存储设计

元数据表可以包含：

| 字段 | 含义 |
| --- | --- |
| upload_id | 上传会话 ID |
| file_id | 文件业务 ID 或内容 hash |
| file_size | 文件总大小 |
| chunk_size | 分片大小 |
| total_chunks | 分片数量 |
| uploaded_chunks | 已完成分片 bitmap 或单独分片表 |
| status | uploading/merged/failed/expired |
| checksum | 整体校验值 |

小规模可以用数据库记录分片状态；大规模对象存储可以直接使用 S3 Multipart Upload、MinIO multipart、云厂商分片上传能力。

## 7. 易错点

1. 只按文件名判断是否同一个文件不可靠，文件可能被替换。
2. 只记录 offset 不适合乱序并发分片上传，更推荐记录 chunk bitmap。
3. 合并文件要幂等，避免重复合并生成脏数据。
4. 分片大小不是越小越好，太小会放大元数据和请求开销。
5. 上传成功不等于文件可用，必须等 merge 和整体校验完成。

## 8. 面试回答模板

断点续传的核心是把文件拆成可定位、可校验的字节范围。下载侧用 HTTP Range 和 `206 Partial Content`，客户端保存已下载长度、ETag 和临时文件；恢复时先确认文件版本没变。上传侧用分片上传，服务端为文件创建 uploadId，客户端按文件大小计算 chunk 数，上传时携带 `Content-Length`、`Content-Range`、partNumber 和 checksum。服务端通过 `recv/read` 接收请求体，通过 `open/write/pwrite/rename` 写临时分片和提交最终文件，记录每个 chunk 的完成状态和校验值。中断后客户端查询已上传分片并补传缺失部分，全部完成后服务端合并并做整体 hash 校验。工程上要保证 chunk 上传和 merge 幂等，处理过期清理、并发上传和校验冲突。
