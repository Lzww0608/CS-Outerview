# 3. 熔断降级与超时重试

熔断机制用于防止下游持续失败时把调用方也拖垮。它的思想类似电路保险丝：当失败率或超时率超过阈值时，调用方暂时停止访问下游，快速失败或走降级逻辑，等待一段时间后再小流量探测恢复。

## 1. 熔断状态机

常见三态：

1. **Closed**：正常调用，持续统计错误率、超时率和慢调用比例。
2. **Open**：熔断打开，直接拒绝或返回降级结果，不再打到下游。
3. **Half-Open**：等待窗口结束后放少量探测请求，如果成功率达标则关闭熔断，否则重新打开。

```text
Closed --失败率超阈值--> Open --等待窗口--> Half-Open
Half-Open --探测成功--> Closed
Half-Open --探测失败--> Open
```

## 2. 熔断和超时、重试的关系

熔断不能单独使用，通常和这些机制配套：

1. **超时**：每个 RPC/HTTP 调用必须有 deadline，否则线程池和连接池会被慢请求占满。
2. **重试**：只对幂等请求做有限重试，配合指数退避和 jitter。
3. **限流**：限制入口流量，避免过载请求继续堆积。
4. **隔离**：不同下游使用不同线程池、连接池或 bulkhead，避免互相拖垮。
5. **降级**：返回缓存、默认值、空结果、排队受理或“稍后再试”。

错误顺序通常是：先设置合理超时，再决定是否重试；连续失败超过阈值时熔断；熔断期间走降级或快速失败。

## 3. 指标和阈值怎么设计

熔断判断不能只看单次失败，要有滑动窗口：

1. 请求量达到最小阈值后才判断，避免低流量下偶发失败触发熔断。
2. 统计失败率、超时率、慢调用比例、连续失败次数。
3. 区分业务错误和系统错误，例如参数错误不应计入下游故障。
4. Half-Open 探测请求数量要有限，避免刚恢复就被流量打垮。

真实系统里可以按服务、接口、实例、调用方维度做熔断。实例级熔断用于摘除坏节点，接口级熔断用于保护慢接口，服务级熔断用于下游整体不可用。

## 4. 易错点

1. 无超时的重试会放大故障。
2. 非幂等写请求不能随意重试，要有幂等键或业务去重。
3. 熔断不是限流，熔断针对下游失败，限流针对入口过载。
4. 降级结果要符合业务语义，不能把错误数据当成功写入。
5. 熔断状态和阈值要有监控，否则线上只看到“请求突然失败”，不知道是保护机制生效。

## 5. 面试回答模板

熔断是服务治理里的保护机制。调用下游时先设置超时和有限重试，并在滑动窗口里统计错误率、超时率和慢调用比例；如果超过阈值，就从 Closed 进入 Open，后续请求快速失败或走缓存、默认值等降级逻辑。等待一段时间后进入 Half-Open，只放少量探测请求，如果成功率恢复就关闭熔断，否则继续打开。它要和限流、隔离、退避重试、幂等和监控配套，否则可能把故障放大。
