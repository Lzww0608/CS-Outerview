# 2. 压测与业务监控系统设计

压测的目的不是跑出一个好看的 QPS，而是在可控环境中找出系统瓶颈、容量边界和退化方式。业务监控系统的目的也不是只画大盘，而是能快速发现异常、定位影响范围、辅助止损和复盘。

## 1. 压测的目的

常见目的：

1. **容量评估**：当前架构能承受多少 QPS/TPS、并发连接和数据量。
2. **瓶颈定位**：瓶颈在 CPU、I/O、锁、数据库、缓存、网络还是下游。
3. **稳定性验证**：长时间运行是否有内存泄漏、连接泄漏、队列堆积。
4. **扩容依据**：估算单机容量和水平扩容比例。
5. **保护策略验证**：限流、熔断、降级、超时、重试、背压是否生效。
6. **发布风险评估**：新版本和旧版本在同等流量下的性能差异。

## 2. 压测主要关注哪些指标

入口指标：

1. QPS/TPS。
2. 并发连接数。
3. P50/P95/P99/P999 延迟。
4. 错误率、超时率、重试率。
5. 请求和响应大小。

系统指标：

1. CPU 使用率、load average、运行队列。
2. 内存、RSS、page fault、OOM。
3. 上下文切换、锁等待、线程池队列长度。
4. fd 数、端口耗尽、accept 队列、SYN backlog。
5. 磁盘 IOPS、吞吐、fsync 延迟。
6. 网络带宽、丢包、重传、连接建立耗时。

依赖指标：

1. 数据库慢 SQL、扫描行数、锁等待、连接池等待。
2. Redis 命中率、热点 key、大 key、命令延迟。
3. MQ 堆积、消费延迟、重试和死信。
4. 下游 RPC 延迟、错误率、熔断状态。

业务指标：

1. 下单成功率、支付成功率、登录成功率。
2. 库存扣减成功率和超卖/少卖。
3. 消息送达率。
4. 关键链路漏斗转化率。

## 3. 压测怎么设计

压测要尽量接近真实流量，而不是只压一个接口。

设计要点：

1. **流量模型**：按真实业务比例组合读、写、登录、查询、支付等接口。
2. **数据模型**：准备足够大的用户、订单、商品、关系链数据，避免全是缓存命中。
3. **阶段推进**：阶梯升压、峰值压测、长稳压测、突刺压测、恢复压测。
4. **隔离环境**：压测环境和线上隔离；线上全链路压测要有影子库、影子表和压测标识。
5. **可回滚**：压测流量必须能快速停止，写入数据能识别和清理。
6. **监控同步**：压测开始前确认指标、日志、trace、告警都可用。
7. **瓶颈复验**：优化后用同样流量模型复测，不能只看局部指标。

### 单机 QPS 1w+ 是怎么统计或得到的

面试里说“单机 QPS 1w+”要能解释数据来源，否则很容易被追问穿。

常见统计方式：

1. **压测工具侧**：wrk、JMeter、Locust、ghz、ab 等工具统计成功响应数除以压测时间。
2. **服务指标侧**：应用暴露 Prometheus Counter，例如 `http_requests_total`，用 `rate(http_requests_total[1m])` 计算每秒请求数。
3. **网关侧**：Nginx/Envoy/API Gateway 按 upstream、接口和状态码统计 RPS。
4. **日志侧**：访问日志按秒聚合，但日志异步和采样可能带来误差。

更严谨的表达：

```text
单机 8C16G，Release 构建，压测机和服务机同机房
压测 10 分钟，前 1 分钟预热，统计后 9 分钟
真实接口读写比例 8:2，数据量 100 万，缓存命中率约 85%
P99 < 80ms，错误率 < 0.1%，CPU 约 70%，无明显 GC/队列堆积
服务侧 Prometheus 和压测工具统计都在 1w QPS 左右
```

注意事项：

1. 只报 QPS 不够，要同时报机器规格、接口类型、数据量、命中率、延迟分位数和错误率。
2. 裸 echo 接口、全缓存命中、关闭日志、Debug/Release 构建不同，结果没有可比性。
3. 压测机也可能成为瓶颈，要观察压测机 CPU、网络和连接数。
4. 单机峰值 QPS 不等于线上可用容量，线上要留冗余并考虑发布、故障摘流和流量突刺。
5. 如果是估算值，要明确是压测、监控统计还是按 CPU/耗时推算，不能把估算说成线上实测。

## 4. 业务检测系统怎么设计

如果要检测大型业务系统，可以从四层设计：指标、日志、链路追踪、主动探测。

```text
业务埋点 / 系统指标 / 日志 / Trace / 主动探测
  -> 采集 Agent / SDK
  -> MQ 或流处理
  -> 时序库 + 日志库 + Trace 存储
  -> 规则告警 + 异常检测
  -> 看板 + 事件中心 + 自动化处置
```

核心模块：

1. **指标采集**：QPS、延迟、错误率、资源、队列、依赖状态。
2. **业务埋点**：订单、支付、登录、发货等关键事件。
3. **日志采集**：结构化日志带 `trace_id`、`user_id`、`biz_id`、错误码。
4. **链路追踪**：跨服务记录调用拓扑、耗时和错误点。
5. **主动探测**：模拟用户定时访问核心路径，发现真实用户前的问题。
6. **告警规则**：静态阈值、同比环比、错误预算、突增突降。
7. **异常检测**：基于基线、季节性和分位数识别异常。
8. **自动化处置**：限流、摘流、回滚、扩容、降级开关。

## 5. 告警怎么避免噪声

告警系统最怕误报太多。

优化策略：

1. 按业务影响分级：P0/P1/P2/P3。
2. 使用多条件组合，例如错误率升高且 QPS 足够大才告警。
3. 使用 P95/P99 和错误预算，不只看平均值。
4. 增加静默、抑制和聚合，避免同一故障刷屏。
5. 告警必须带上下文：影响接口、地域、版本、trace 示例、最近变更。
6. 告警后要能闭环：确认、处理、恢复、复盘。

## 6. 真实场景例子

检测下单业务可以设计这些指标：

1. `order_create_qps`
2. `order_create_success_rate`
3. `order_create_p99_latency`
4. `db_lock_wait_ms`
5. `inventory_deduct_fail_rate`
6. `payment_rpc_timeout_rate`
7. `mq_order_event_lag`
8. `duplicate_order_count`

如果下单成功率下降，同时支付 RPC 超时率上升、trace 显示耗时集中在支付服务，就可以快速定位不是入口服务 CPU 问题，而是支付依赖异常。

## 7. 易错点

1. 只看平均延迟，忽略 P99 和长尾。
2. 压测数据太少，导致全量命中缓存，结果虚高。
3. 只压单接口，不压真实业务链路。
4. 压测不验证限流、熔断和降级，线上过载时不可控。
5. 监控只采系统指标，没有业务成功率和错误码。
6. 告警没有归因上下文，值班人员只能人工翻日志。

## 8. 面试回答模板

我做压测的目的主要是评估容量、定位瓶颈、验证稳定性和保护策略。指标上会看 QPS、并发连接、P95/P99 延迟、错误率、CPU、内存、上下文切换、fd、网络丢包、数据库慢 SQL、Redis 命中率、MQ 堆积和下游 RPC 延迟。压测要模拟真实流量比例和真实数据量，做阶梯升压、峰值、长稳和突刺，并确保监控、日志、trace 同步可用。

如果设计业务检测系统，我会采集系统指标、业务埋点、结构化日志、链路追踪和主动探测，进入时序库、日志库和 trace 系统后做规则告警、异常检测和看板展示。告警要按业务影响分级，结合错误率、流量、P99、同比环比和最近变更，输出影响范围和 trace 示例，必要时联动限流、摘流、回滚、扩容或降级。
