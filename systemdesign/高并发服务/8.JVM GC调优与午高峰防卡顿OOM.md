# 8. JVM GC 调优与午高峰防卡顿 OOM

## 1. 问题背景

外卖平台在午高峰（约 11:00–13:00）流量急剧攀升。订单创建、商家接单、骑手调度、支付回调等核心链路并发量可达日常的 5–10 倍。服务端主要采用 Java 技术栈，JVM 的垃圾回收（GC）行为直接影响响应延迟和稳定性。午高峰大流量下，GC 停顿（卡顿）和 OOM（Out Of Memory）是最常见的两类 JVM 稳定性问题。

**假设条件：**

- 服务端为 Java 8+ 应用，单实例堆内存 4–16 GB；
- 当前使用默认或仅做了基础 GC 配置；
- 午高峰 QPS 为日常 5–10 倍，GC 压力同比例上升；
- 无极端外部依赖阻塞（如数据库慢查询已单独治理）。

## 2. 问题现象

1. **GC 卡顿（STW 停顿过长）**
   - 接口 P99 延迟从日常 50ms 飙升至 500ms 甚至数秒；
   - 监控显示 Young GC 耗时从 20–50ms 增长到 200ms+，偶发 Full GC 停顿数秒；
   - 用户侧表现为页面加载卡顿、下单超时、骑手定位更新延迟。
2. **OOM**
   - 日志出现 `java.lang.OutOfMemoryError: Java heap space` 或 `GC overhead limit exceeded`；
   - 服务实例被 OOM Killer 终止或触发熔断降级；
   - 部分节点掉线后流量雪崩到其他节点，引发级联故障。

## 3. 影响范围

| 影响维度 | 具体表现 |
|---------|---------|
| 用户体验 | 下单失败、页面白屏、骑手接单延迟 |
| 业务指标 | 午高峰转化率下降 5–15%，客诉量激增 |
| 系统稳定性 | 单节点 OOM → 集群雪崩 → 全链路不可用 |
| 运维成本 | 频繁扩容、紧急重启、值班压力 |

## 4. 原因分析

### 4.1 GC 卡顿原因

1. **堆内存分配不合理**：年轻代过小导致对象过早晋升老年代，老年代快速填满触发 Full GC。
2. **大流量下对象分配速率飙升**：午高峰请求量暴增，Young GC 频率大幅上升，单次 GC 耗时因存活对象多而增加。
3. **内存碎片**：长期运行后老年代碎片化，Full GC 后仍无法满足大对象分配，触发连续 Full GC。
4. **Humongous 分配（G1）**：大对象（> Region Size 的 50%）直接在老年代分配，触发并发标记甚至 Full GC。

### 4.2 OOM 原因

1. **内存泄漏**：未关闭的资源、静态集合持续增长、ThreadLocal 未清理等，导致老年代持续增长。
2. **瞬态对象过多**：午高峰大量请求同时涌入，线程池满载，每个线程持有请求上下文对象，堆内存瞬时打满。
3. **堆外内存溢出**：Direct Buffer、Metaspace、JNI 分配等未纳入堆内监控，难以提前预警。
4. **GC 效率低下**：GC 回收速度跟不上分配速度，堆占用持续上升直到 OOM。

### 4.3 流量特征分析

```text
日常:  QPS ~2000,  对象分配速率 ~500MB/s, Young GC 间隔 ~2s
午高峰: QPS ~15000, 对象分配速率 ~3.5GB/s, Young GC 间隔 ~300ms
→ GC 频率提升 6–7 倍，单次 GC 耗时因存活对象增加而上升
→ 累积 STW 时间大幅增加，用户感知卡顿
```

## 5. 解决方案

### 5.1 JVM 层面：GC 选型与调优

#### 5.1.1 G1 GC 调优（适用 JDK 8–17，堆 4–16GB）

```bash
-XX:+UseG1GC
-XX:MaxGCPauseMillis=100              # 目标停顿 100ms
-XX:G1HeapRegionSize=8m               # Region 大小，减少 Humongous 对象
-XX:InitiatingHeapOccupancyPercent=45 # 更早启动并发标记
-XX:G1ReservePercent=15
-XX:ParallelGCThreads=8
-XX:ConcGCThreads=4
-Xms8g -Xmx8g                         # 固定堆大小避免动态扩缩
```

**要点：**

- 设置合理的 `MaxGCPauseMillis`（建议 50–100ms），G1 据此调整每次回收的 Region 数量；
- 增大 `G1HeapRegionSize` 避免大对象直接进入 Humongous 区域；
- 降低 `IHOP` 让并发标记更早启动，避免老年代占用过高时来不及回收；
- 固定 `Xms=Xmx` 避免堆动态扩缩带来的额外停顿。

#### 5.1.2 ZGC 调优（JDK 15+ 生产可用，JDK 21+ 分代 ZGC 推荐，堆 8GB–TB 级）

```bash
-XX:+UseZGC
-XX:+ZGenerational                    # JDK 21+ 启用分代 ZGC
-Xms8g -Xmx8g
-XX:ZAllocationSpikeTolerance=2       # 预留分配缓冲
-XX:ParallelGCThreads=8
-XX:ConcGCThreads=4
```

**要点：**

- ZGC 的 STW 停顿与堆大小无关，通常 < 1ms（JDK 21）；
- 不需要手动设置暂停目标，ZGC 自适应；
- 适合对延迟极度敏感的场景；
- JDK 15+ 开始生产可用，JDK 21 分代 ZGC 吞吐量大幅提升。

### 5.2 应用层面：减少 GC 压力

1. **减少对象分配**
   - 使用对象池复用高频对象（如 Protobuf 编解码对象）；
   - 避免在热路径上创建大数组或大字符串，改用流式处理；
   - 使用基本类型集合（如 `IntArrayList` 替代 `ArrayList<Integer>`）。
2. **控制内存水位**
   - 对缓存设置 TTL 和最大容量（如 Caffeine 的 `maximumSize`）；
   - 请求上下文使用完后及时释放，避免线程池中线程复用导致上下文堆积；
   - 限制线程池队列长度，拒绝排队过多请求。
3. **堆外内存治理**
   - 监控 Direct Buffer 使用量（`BufferPoolMXBean`）；
   - 及时释放 Netty ByteBuf、NIO ByteBuffer；
   - 设置 `-XX:MaxDirectMemorySize` 限制堆外内存上限。

### 5.3 架构层面：流量治理

1. **限流降级**：午高峰 QPS 超阈值后快速失败，避免线程积压；
2. **异步化**：非核心逻辑（通知、日志）异步化，减少同步处理占用的内存和线程；
3. **多级缓存**：减少重复计算和数据库查询，降低对象分配速率；
4. **弹性扩容**：基于 CPU/内存/GC 指标自动扩容，提前 30 分钟预热。

## 6. 可选方案对比

| 维度 | G1 GC | ZGC | CMS（已废弃） | Parallel GC |
|------|-------|-----|---------------|-------------|
| 适用 JDK | JDK 8+ | JDK 15+ 生产，JDK 21+ 推荐 | JDK 8（已移除） | JDK 8+ |
| 适用堆大小 | 4–32 GB | 8 GB–TB 级 | 4–8 GB | 任意 |
| STW 停顿 | 50–200ms | < 1ms（JDK 21） | 10–100ms | 数百ms–秒级 |
| 吞吐量 | 高（~90%） | 中高（~85–90%，分代 ZGC 更高） | 中 | 最高（~95%） |
| 调优复杂度 | 中等 | 低 | 高 | 低 |
| 内存开销 | Region 元数据 | 着色指针 + 转发表 | 较低 | 较低 |
| 大堆表现 | 良好，Full GC 仍需 STW | 优秀，停顿与堆大小无关 | 差，CMS 失败退回 Serial | 差，Full GC 停顿随堆增大 |
| 分代支持 | 是（原生分代） | JDK 21+ 分代 ZGC | 是 | 是 |
| 生产成熟度 | 非常成熟 | 成熟（JDK 21+） | 已废弃 | 成熟 |

### G1 与 ZGC 适用场景总结

**G1 适用场景：**

- 堆内存在 4–32 GB 范围；
- JDK 版本为 8–17，暂无法升级；
- 对延迟有一定要求（P99 < 200ms），但可容忍偶尔较长停顿；
- 团队对 G1 调优有经验；
- 需要稳定的分代回收模型。

**ZGC 适用场景：**

- 堆内存 > 8 GB，尤其是 32 GB–TB 级超大堆；
- JDK 21+ 可用（推荐使用分代 ZGC）；
- 对延迟极度敏感（P99 < 10ms），要求亚毫秒级 STW；
- 午高峰流量波动大，需要 GC 停顿不随堆大小和流量波动；
- 希望减少 GC 调优工作量（ZGC 几乎无需调优）。

## 7. 推荐方案

### 短期（1–2 周，低风险）

1. 升级到 G1 GC 并调优参数（适用于当前 JDK 8+ 环境）；
2. 排查并修复内存泄漏（堆 Dump + MAT 分析）；
3. 调整容器内存和堆大小至合理值（建议为容器内存预留 25% 给堆外和系统）；
4. 增加基于 GC 指标的告警（Full GC 次数、老年代占用率 > 80%）。

### 中期（1–2 月，中等投入）

1. 升级 JDK 至 21+，启用分代 ZGC；
2. 重构热点路径，减少对象分配（对象池、流式处理、基本类型集合）；
3. 实现基于内存水位的自适应限流；
4. 建立午高峰前的自动扩容策略。

### 长期（3–6 月，架构演进）

1. 服务拆分：将内存密集型模块（如推荐、搜索）独立部署，避免相互影响；
2. 引入堆外缓存（如 Netty pooled buffer、off-heap cache）；
3. 建设 GC 全链路可观测：GC 日志 → Prometheus → Grafana 大盘 → 告警。

## 8. 实施步骤

### 阶段一：诊断与基线（第 1–3 天）

1. 开启 GC 日志：`-Xlog:gc*:file=gc.log:time,uptime,level,tags`（JDK 9+）或 `-XX:+PrintGCDetails -XX:+PrintGCDateStamps -Xloggc:gc.log`（JDK 8）；
2. 收集午高峰 GC 日志，用 GCEasy / GCViewer 分析；
3. 抓取午高峰堆 Dump（`jmap -dump:format=b,file=heap.hprof <pid>`），用 MAT 分析内存占用 TOP 对象；
4. 记录当前 P50/P99 延迟、Young GC / Full GC 频率和耗时作为基线。

### 阶段二：G1 调优（第 4–7 天）

1. 在预发环境应用 G1 调优参数；
2. 使用 JMeter / wrk 模拟午高峰流量压测；
3. 对比调优前后 GC 指标和接口延迟；
4. 灰度发布到 10% → 50% → 100% 节点。

### 阶段三：内存治理（第 2–4 周）

1. 修复 MAT 分析发现的内存泄漏点；
2. 重构热点路径减少对象分配；
3. 添加缓存淘汰策略和大小限制；
4. 每轮修改后压测验证。

### 阶段四：ZGC 升级（第 5–8 周）

1. 升级 JDK 至 21+；
2. 在预发环境启用分代 ZGC 并压测；
3. 对比 ZGC 与 G1 的延迟和吞吐指标；
4. 灰度发布，逐步替换 G1 节点。

## 9. 风险与注意事项

| 风险 | 影响 | 缓解措施 |
|------|------|---------|
| G1 参数不当导致 Full GC 更频繁 | 服务卡顿加剧 | 预发压测验证，灰度发布，保留回滚方案 |
| JDK 升级兼容性问题 | 应用启动失败或运行时异常 | 提前在预发环境全量回归测试 |
| ZGC 内存开销比 G1 高 5–10% | 同等堆下可用内存减少 | 适当增加堆大小或优化对象分配 |
| 堆 Dump 导致 STW 停顿 | 生成 Dump 期间服务暂停 | 使用 `-XX:+HeapDumpOnOutOfMemoryError` 自动触发，或低峰期手动 Dump |
| 自动扩容延迟 | 流量突增时扩容来不及 | 提前 30 分钟定时预热扩容 |
| 限流误杀正常请求 | 业务损失 | 限流阈值基于压测数据设置，留有安全余量 |

## 10. 验证方式

1. **GC 日志验证**
   - Young GC 平均耗时 < 50ms，Full GC 频率 < 1 次/小时；
   - ZGC 环境下 STW 停顿 < 1ms。
2. **延迟指标验证**
   - 接口 P99 延迟午高峰 < 200ms（G1）/ < 50ms（ZGC）；
   - 无因 GC 导致的超时熔断。
3. **内存指标验证**
   - 老年代占用率午高峰 < 70%；
   - 无 OOM 事件发生；
   - 堆外内存使用量稳定在合理范围。
4. **压力测试验证**
   - 模拟 2 倍午高峰 QPS，持续 30 分钟，无 OOM 且 P99 延迟达标；
   - 模拟单节点 OOM，验证流量自动转移和自动恢复。
5. **线上观测**
   - 连续 5 个工作日午高峰 GC 和内存指标正常；
   - 对比调优前后同时间段 GC 指标改善 > 50%。

## 11. 总结

外卖午高峰大流量下的 GC 卡顿和 OOM 本质是 **对象分配速率飙升与 GC 回收速率不匹配** 导致的。解决方案需要从三个层面协同发力：

1. **JVM 层**：选择合适的 GC 算法（G1 适合 4–32GB 堆，ZGC 适合 8GB–TB 级堆且延迟要求极高），配合针对性调优参数；
2. **应用层**：减少对象分配、控制缓存水位、及时释放资源，从根本上降低 GC 压力；
3. **架构层**：限流降级、异步化、弹性扩容，从流量侧削峰填谷，避免内存瞬时打满。

G1 和 ZGC 的核心选择依据：**如果堆 < 32GB 且可容忍 50–200ms 停顿，G1 足够成熟稳定；如果堆 > 32GB 或要求亚毫秒级停顿，ZGC 是更优选择**。JDK 21+ 分代 ZGC 的推出让 ZGC 在吞吐量上大幅补齐短板，是未来 Java 高并发服务 GC 的推荐方向。

### 附：可能涉及的代码修改

**可能需要修改的模块：**

- JVM 启动参数配置模块（部署脚本 / Dockerfile / K8s Deployment）
- 缓存模块（Caffeine / Guava Cache / Redis 客户端配置）
- 线程池配置模块
- 序列化 / 反序列化模块

**可能涉及的文件：**

- `Dockerfile` 或 `deployment.yaml`：JVM 启动参数
- `application.yml` / `application.properties`：线程池、缓存大小配置
- 缓存工具类：`CacheManager.java`、`LocalCacheConfig.java`
- 线程池配置类：`ThreadPoolConfig.java`
- 热点业务 Service 类：订单创建、查询等

**核心修改逻辑：**

- JVM 参数从默认 / Parallel GC 切换到 G1 或 ZGC，设置合理堆大小和 GC 参数；
- 缓存增加 `maximumSize` 和 `expireAfterWrite`，防止无界增长；
- 线程池队列改为有界队列，拒绝策略使用 `CallerRunsPolicy` 或自定义降级策略；
- 热点路径使用对象池或基本类型集合减少 GC 压力。

**测试重点：**

- 模拟午高峰 QPS 压测，关注 GC 停顿和内存水位；
- 长时间稳定性测试（72h+），关注内存泄漏；
- 限流降级测试，验证超阈值请求的快速失败；
- OOM 恢复测试，验证 HeapDump 自动生成和节点自动恢复。
