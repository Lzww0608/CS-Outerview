# 5. Web 中间层内存与拷贝优化

Web 服务的中间层通常负责接入、协议解析、鉴权、路由、聚合、转发和响应生成。高并发下，读写消耗的内存资源不仅来自业务对象，还来自 socket 缓冲区、应用缓冲区、序列化对象、日志、压缩临时区和请求排队。

## 1. 核心目标

减少中间层内存资源，核心是减少**全量缓存、重复拷贝、无界排队和慢连接堆积**。

典型数据路径：

```text
网卡 -> 内核 socket 接收缓冲区 -> 应用输入缓冲区 -> 协议解析/业务处理
业务响应 -> 应用输出缓冲区 -> 内核 socket 发送缓冲区 -> 网卡
```

如果每一层都复制一份完整请求或响应，大文件上传、下载、代理转发和慢客户端场景会很快把内存打满。

## 2. 常见优化手段

1. **流式处理**：请求体或文件不要一次性读入内存，按 chunk 解析、校验、转发或落盘。
2. **零拷贝**：静态文件下载优先考虑 `sendfile`；Linux 管道转发可考虑 `splice`；分散聚集 I/O 可用 `readv/writev`。
3. **应用缓冲区复用**：使用 buffer pool、对象池或 arena，减少频繁分配释放带来的内存碎片和 CPU 开销。
4. **有界队列**：请求队列、线程池队列、日志队列和输出缓冲区都要设置上限，超过上限时快速失败或降级。
5. **反压机制**：当下游慢、客户端不读或输出缓冲区超过高水位线时，暂停读取、限速或关闭连接。
6. **增量序列化/反序列化**：避免把 JSON/Protobuf 全量转成多个中间对象；能透传时尽量透传。
7. **压缩策略控制**：压缩可以省网络，但会增加 CPU 和临时内存；小响应、已压缩内容或高 CPU 压力下不应盲目压缩。

## 3. 典型场景

### 3.1 静态文件下载

使用 `read + write` 会把数据从磁盘页缓存拷贝到用户态，再从用户态拷贝到内核 socket 缓冲区。`sendfile` 可以让数据在内核态从页缓存直接发送到 socket，减少用户态拷贝和上下文切换。

```cpp
off_t offset = 0;
while (offset < fileSize) {
    ssize_t n = ::sendfile(connFd, fileFd, &offset, fileSize - offset);
    if (n > 0) {
        continue;
    }
    if (errno == EAGAIN || errno == EWOULDBLOCK) {
        // 保存 offset，等待 EPOLLOUT 后继续
        break;
    }
    // 错误处理
    break;
}
```

注意：传统 TLS 会让数据必须进入加密层，普通 `sendfile` 不能直接完成端到端加密发送；可以考虑 kTLS、反向代理缓存、分块发送或 CDN。

### 3.2 网关代理转发

中间层如果只是把上游请求转发到下游，尽量不要构造完整业务对象。可以保留原始 body 流，边读边转发；只对必须修改的 Header 或字段做解析。

对于慢下游，要设置超时和最大缓冲区。否则上游读得快、下游写得慢时，中间层会不断积累待转发数据。

### 3.3 大请求上传

上传服务应采用分片上传、临时文件或对象存储直传，避免 Web 进程缓存完整文件。常见设计是服务端签发上传凭证，客户端直接上传对象存储，中间层只保存元数据和回调结果。

## 4. 易错点

1. 零拷贝不是完全没有拷贝，而是减少用户态和内核态之间的无谓拷贝。
2. `mmap` 不一定比 `read` 更省内存，大量随机映射可能带来缺页、TLB 和地址空间压力。
3. 只优化一次拷贝意义有限，真正的大头常常是无界输出缓冲区、请求排队和慢连接。
4. 对象池不是越多越好，池化对象生命周期复杂，可能导致脏数据复用和峰值内存常驻。
5. 压缩、加密、日志格式化也会制造临时内存，压测时要观察 RSS、PSS、GC/allocator 指标和队列长度。

## 5. 面试回答模板

写 Web 服务时，我会从数据路径减少中间层内存：请求和响应尽量流式处理，不把大 body 全量读入内存；静态文件用 `sendfile`，代理转发用分块读写和 `writev`，减少用户态拷贝；应用层维护有界输入/输出缓冲区，慢连接触发高水位反压；线程池、日志队列和请求队列都设置容量上限；上传类场景尽量让客户端直传对象存储。这样既减少内存占用，也避免高并发下排队把内存打满。
