# 7. 服务器选型与容量规划

服务器选型不是先看“买几核几 G”，而是先看业务负载画像、峰值流量、延迟目标、可用性目标和成本约束。面试里问“怎么选择服务器”，重点是说明你会用数据估算，而不是凭经验拍机器规格。

## 1. 先判断业务负载类型

不同后端服务瓶颈不同：

| 负载类型 | 主要瓶颈 | 选型关注点 | 典型场景 |
| --- | --- | --- | --- |
| CPU 密集 | CPU、上下文切换、锁竞争 | 核数、主频、NUMA、线程模型 | 战斗结算、压缩、加密、图片处理 |
| I/O 密集 | 网络、磁盘、下游延迟 | 网卡带宽、连接数、异步 I/O、连接池 | 网关、文件上传下载、RPC 聚合 |
| 内存密集 | 内存容量、GC、缓存命中率 | 内存大小、对象生命周期、堆外内存 | 缓存、排行榜、在线状态 |
| 磁盘密集 | IOPS、吞吐、fsync 延迟 | SSD/NVMe、RAID、云盘类型 | 日志、数据库、对象块存储 |
| 长连接 | fd、内存、心跳和网络包量 | 单连接内存、epoll、内核参数 | 游戏网关、IM、WebSocket |

游戏后端通常还要拆模块看：接入网关更关注长连接和网络包处理；房间/战斗服更关注 CPU 和低延迟；数据服务更关注 MySQL、Redis、磁盘和缓存命中率；文件服务更关注带宽、对象存储和 CDN。

## 2. 容量估算方法

常见估算公式：

```text
实例数 = 峰值 QPS * 单请求资源消耗 / 单实例可承载资源
```

更具体一点：

1. **CPU**：`所需核数 ≈ 峰值 QPS * 单请求 CPU 时间 / 目标 CPU 利用率`。
2. **内存**：`连接数 * 单连接内存 + 缓存 + 业务对象 + 运行时开销 + 安全余量`。
3. **带宽**：`QPS * 平均响应字节数 * 8`，再加上峰值系数和上下行差异。
4. **磁盘**：`每日新增数据 * 保留天数 * 副本系数 / 压缩率`。
5. **连接数**：要同时看应用 fd、`ulimit -n`、连接池、NAT 端口、负载均衡连接保持策略。

线上机器不要压到极限。常见目标是 CPU 长期低于 60% 到 70%，内存和磁盘留出 20% 到 30% 余量，并能承受一台机器下线后的流量转移。

## 3. 选型步骤

1. 明确 SLI/SLO：例如 P99 延迟、错误率、可用性、最大并发连接数。
2. 用历史流量或预估流量计算峰值，考虑活动、开服、版本更新等突发。
3. 压测单实例能力，记录 CPU、RSS、GC、网络、磁盘、线程池队列和下游耗时。
4. 按瓶颈选择规格：CPU 不够加核，内存不足加内存，I/O 不够换 SSD/NVMe 或独立数据面。
5. 做故障域规划：多实例、多可用区、负载均衡、健康检查和自动摘除。
6. 灰度上线后用真实指标校准容量模型，避免只相信压测数据。

## 4. 易错点

1. 只看平均 QPS，不看峰值、P99 和突发流量。
2. 只扩应用实例，不看 MySQL、Redis、MQ、对象存储这些下游容量。
3. 队列和线程池无上限，低峰没问题，高峰时内存被排队任务打爆。
4. 云服务器只看 vCPU 数，不看共享型/独享型、突发积分、云盘 IOPS 和网络上限。
5. 单可用区部署，机器没问题但机房故障时整体不可用。
6. 选型后不压测、不监控，导致真实瓶颈和估算模型偏差很大。

## 5. 面试回答模板

我会先按业务负载选服务器，而不是直接报规格。比如游戏网关主要看长连接数、单连接内存、网络包量和 fd；战斗服看 CPU、低延迟和锁竞争；文件上传下载看带宽、磁盘和对象存储。容量上用峰值 QPS、单请求 CPU 时间、平均响应大小、并发连接数估算 CPU、内存和带宽，再通过压测校准单实例上限。生产上机器不能跑满，要保留故障转移余量，并结合负载均衡、健康检查、多可用区和监控告警保证扩容后是真的可用。
