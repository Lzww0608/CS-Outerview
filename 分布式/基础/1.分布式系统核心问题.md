# 分布式系统核心问题

分布式系统是由多台机器通过网络协作完成同一个业务目标的系统。它的核心难点不是“多部署几台机器”，而是网络不可靠、节点会故障、时钟不一致、状态复制存在延迟，以及跨节点操作很难像单机事务一样简单。

## 1. 为什么需要分布式

常见动机：

1. **容量扩展**：单机 CPU、内存、磁盘或连接数不够，需要水平扩展。
2. **高可用**：单机故障不能导致整体不可用，需要副本和故障转移。
3. **地理就近**：多地域部署降低访问延迟。
4. **团队协作**：复杂业务按边界拆分成服务，独立开发和发布。
5. **资源隔离**：把高风险、慢任务、热点模块隔离，避免拖垮核心链路。

## 2. 分布式系统的基本问题

### 2.1 网络不可靠

网络调用可能成功、失败、超时、重复、乱序。调用方看到超时时，无法确定服务端到底有没有执行成功。

工程措施：

1. 超时控制，不能无限等待。
2. 重试要有退避和最大次数。
3. 写操作要有幂等 key，避免重试造成重复扣款、重复下单。
4. 对外部依赖要做熔断、限流和降级。

### 2.2 数据一致性

多副本和多服务会带来一致性问题。常见一致性模型：

1. **强一致性/线性一致性**：写成功后，后续读一定看到最新值。
2. **顺序一致性**：所有节点看到的操作顺序一致，但不一定符合真实时间。
3. **最终一致性**：短时间允许不一致，最终通过同步、重试、补偿收敛。

金融扣款、库存扣减通常更偏强一致；点赞数、阅读数、Feed 计数可以接受最终一致。

### 2.3 共识和选主

当多个节点维护同一份关键状态时，需要通过共识协议决定谁是 leader、哪些日志已经提交。典型协议包括 Paxos、Raft、ZAB。

核心思想：

1. 通过多数派避免两个分区各自提交冲突写入。
2. leader 统一写入顺序，降低复制复杂度。
3. 少数派在网络分区时不可写，牺牲局部可用性换一致性。

### 2.4 分片和负载均衡

数据量或请求量太大时，需要分片。常见分片方式：

1. 按范围分片：便于范围查询，但可能热点集中。
2. 按哈希分片：分布均匀，但范围查询困难。
3. 一致性哈希：节点变化时减少迁移量。
4. 虚拟节点：缓解节点数量少导致的数据倾斜。

负载均衡常见策略包括轮询、随机、最少连接、一致性哈希、权重和本地优先。

### 2.5 分布式事务

跨服务、跨库事务不能直接依赖单机 ACID。常见方案：

1. **2PC/TCC**：一致性强，但实现复杂、阻塞风险高。
2. **本地消息表**：本地事务写业务数据和消息表，再异步投递 MQ。
3. **事务消息**：由 MQ 提供半消息和回查机制。
4. **Saga**：把长事务拆成多个本地事务，每步有补偿操作。
5. **最终一致性 + 幂等消费 + 补偿任务**：互联网业务最常见。

## 3. 常见组件

| 组件 | 作用 |
| --- | --- |
| 注册中心 | 服务注册、发现和健康检查 |
| 配置中心 | 动态配置、灰度、回滚 |
| MQ | 异步解耦、削峰、最终一致 |
| 缓存 | 降低数据库压力、加速热点读 |
| 分布式锁 | 控制跨节点互斥，但要谨慎使用 |
| 链路追踪 | 定位跨服务调用耗时和错误 |
| 限流熔断 | 防止故障扩散 |

## 4. 易错点

1. 分布式系统里“超时”不等于“失败”，可能服务端已经执行成功。
2. 重试必须配合幂等，否则会放大副作用。
3. 分布式锁不能替代事务，锁超时、主从切换、时钟漂移都可能出问题。
4. 多副本读写要明确一致性级别，不能只说“主从同步”。
5. CAP 不是平时随便“三选二”，真正权衡发生在网络分区时。
6. 拆成微服务会引入网络调用和数据一致性成本，不是越拆越好。

## 5. 真实场景

以订单创建为例：

1. 用户请求进入网关，先做鉴权、限流和参数校验。
2. 订单服务本地事务写订单表。
3. 库存扣减可以用本地事务、TCC 或库存预扣模型。
4. 支付、通知、积分等非核心链路通过 MQ 异步触发。
5. 消费端按订单号做幂等，失败后重试，超过次数进入死信或补偿任务。
6. 全链路用 trace id 串联日志、指标和调用耗时。

## 6. 面试回答模板

我理解分布式系统的核心是多节点协作带来的不确定性：网络会超时和重复，节点会故障，副本同步有延迟，跨节点事务也不再像单机一样简单。因此要围绕高可用、扩展性和一致性做取舍。常见问题包括服务发现、负载均衡、分片、多副本一致性、选主、分布式事务、幂等重试、限流熔断和可观测性。实际设计时会先明确业务能接受强一致还是最终一致，再选择 Raft/数据库事务、MQ 最终一致、缓存、分片和补偿机制等方案。
