在 Chord 算法中，当节点加入或离开（无论是主动退出还是故障宕机）时，**Finger Table（手指表）的更新并不是瞬间在全网完成的**。

为了保证大规模网络的扩展性，Chord 采用的是**“惰性更新”（Lazy Update）**和**“周期性探测”**机制。这意味着网络会容忍短时间内的路由表不准确，通过后台进程逐步收敛到正确状态。

核心原则是：**“Finger Table 的不准确只会影响查找速度（从 $O(\log N)$ 变慢），但只要后继关系（Successor）正确，查找结果就是准确的。”**

------



### 1. 节点加入 (Node Join)

假设一个新节点 **$N$** 加入网络。

#### A. 新节点 $N$ 初始化自己的表

1. $N$ 通过已知的引导节点，查找自己的后继节点（Successor）。
2. $N$ 初始化自己的 Finger Table。它需要向网络发起查询，计算出自己每一项 finger 应该指向谁。
   - 例如：$N$ 询问网络 "谁是 $N+1$ 的后继？"、"谁是 $N+2$ 的后继？" 等等。



#### B. 其他节点的表如何指向 $N$？

这部分最关键。旧节点怎么知道 $N$ 来了？有两种策略：

- **理想化策略（主动通知）：** $N$ 算出有哪些节点的 Finger Table 应该指向它，然后逐个通知这些节点更新。但这在大规模网络中开销太大（$O(\log^2 N)$），实际上很少完全依赖此方法。
- **实际策略（周期性修正）：** 依靠后台的 **fix_fingers()** 协议。
  - 网络中的每个现有节点都会周期性地随机选择自己 Finger Table 中的某一项，重新发起查找。
  - 比如节点 $A$ 原本的 finger 指向节点 $S$。现在 $N$ 插在了 $A$ 和 $S$ 之间。
  - 当 $A$ 下一次运行 `fix_fingers` 时，它会发现：“咦，这个 ID 现在的后继变成了 $N$”，于是更新表项指向 $N$。

------



### 2. 节点离开/故障 (Node Leave/Failure)

当节点离开时，Finger Table 中指向它的条目会变成“死链接”。Chord 处理主动离开和故障的机制类似，重点在于**容错**。

#### A. 核心防线：Successor List（后继列表）

Finger Table 只是为了快，Successor List 才是为了活。

每个节点不仅维护一个 successor，而是维护一个 Successor List（通常包含大小为 $r$ 的节点，例如最近的 3-4 个后继）。

- 如果节点发现它的直接 successor 宕机了（Ping 不通）：
  1. 它会查阅 Successor List，尝试联系第二个节点。
  2. 一旦联系上，就将它设为新的直接 successor，并从该节点拉取新的列表来修补自己的列表。
- **这保证了环的连通性不会断裂。**



#### B. Finger Table 的修复

Finger Table 的修复完全依赖于周期性的探测：

1. **发现失效：** 当节点试图利用 Finger Table 路由查找时，如果指向的节点无响应（超时），该节点会将这个 Finger 条目标记为失效。
2. **降级处理：** 本次查找会退化，尝试使用前一个有效的 Finger，或者直接转发给 Successor。
3. **后台修复：** 节点的 **fix_fingers()** 进程在后台运行。当轮到检测这个失效的条目时，节点会重新发起查询：“谁是 $n + 2^{i-1}$ 的后继？”
4. **更新：** 网络会返回那个已离开节点的下一个存活节点，Finger Table 随之更新。

------



### 3. 关键的后台维护进程

为了实现上述功能，每个 Chord 节点在后台周而复始地运行以下三个轻量级协议：

| **协议名称**            | **作用**                                   | **频率** | **目的**                                                     |
| ----------------------- | ------------------------------------------ | -------- | ------------------------------------------------------------ |
| **Stabilize()**         | 询问 Successor：“你的前驱是谁？”           | 很高     | **最重要**。确保环没有断，确保新加入的节点能被立即识别进环中。 |
| **Fix_Fingers()**       | 随机选取一个 Finger 表项，重新计算并更新。 | 较低     | 修复 Finger Table，让路由保持 $O(\log N)$ 的速度。           |
| **Check_Predecessor()** | Ping 自己的前驱节点。                      | 中等     | 如果前驱死了，将其置空，准备接受新的前驱。                   |

------



### 4. 更新过程中的状态（举例说明）

假设节点 $N_{add}$ 加入到了 $N_{old}$ 和 $N_{next}$ 之间。

1. **加入瞬间 (T0)：**
   - 环的连通性由 `Stabilize` 快速修复：$N_{old} \to N_{add} \to N_{next}$。
   - 此时，如果远处的节点 $X$ 想要查找属于 $N_{add}$ 的数据，$X$ 的 Finger Table 可能还指向 $N_{next}$。
2. **路由过程 (T1)：**
   - $X$ 发消息给 $N_{next}$。
   - $N_{next}$ 检查发现：“这个 Key 不归我管了，它归我的前驱 $N_{add}$ 管。”（或者在查询路径的最后一步，请求会正确落在 $N_{add}$ 上）。
   - **结论：** 查找依然成功，只是可能多跳了一步。
3. **收敛完成 (T2)：**
   - $X$ 运行了 `fix_fingers()`，发现 $N_{add}$ 存在，更新 Finger Table。下次就直接跳到 $N_{add}$ 了。



### 总结

Finger Table 的更新机制是**“最终一致性” (Eventual Consistency)** 的：

1. **不是立即更新：** 节点增删后，全网的 Finger Table 会在一段时间内不准确。
2. **依靠周期性进程：** 通过 `fix_fingers()` 慢慢修正。
3. **正确性优于速度：** 只要 `Successor` 指针是对的（由 `Stabilize` 保证），查询一定能找到结果，Finger Table 仅仅是为了让查找变快。
