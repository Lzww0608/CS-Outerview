# 3. Service Mesh 与 Serverless 取舍

## 1. Service Mesh 是什么

Service Mesh 是把服务治理能力从业务进程中下沉到基础设施的一种架构。典型形态是每个服务实例旁边部署一个 sidecar proxy，例如 Envoy，业务流量先经过 sidecar，再转发到目标服务。

常见能力：

1. 服务发现和负载均衡。
2. 超时、重试、熔断、限流。
3. mTLS、认证、授权。
4. 灰度发布、流量镜像、金丝雀。
5. 指标、日志、链路追踪。

优点是治理能力统一、跨语言一致、业务代码更轻；缺点是引入 sidecar 资源开销、网络跳数、控制面复杂度和排障难度。

## 2. Serverless 是什么

Serverless 强调开发者只关心函数或服务逻辑，实例创建、扩缩容、资源分配由平台负责。FaaS 是 Serverless 的常见形式。

适合场景：

1. 流量波峰波谷明显。
2. 事件驱动任务，例如图片处理、Webhook、定时任务。
3. 运维人手少，希望平台托管扩缩容。

典型问题：

1. 冷启动导致 P99 延迟抖动。
2. 运行时间、连接复用、本地状态受限制。
3. 观测、调试和依赖管理更依赖平台。
4. 不适合所有低延迟、高状态、长连接业务。

## 3. 如何避免微服务过度拆分

过度拆分会把简单问题变成分布式问题：调用链变长、接口版本膨胀、数据一致性变难、测试环境复杂、排障成本增加。

判断是否拆分可以看：

1. 是否有稳定业务边界，而不是按技术层随意拆。
2. 是否需要独立扩容、独立发布、独立故障隔离。
3. 是否有清晰的数据归属和一致性方案。
4. 团队是否有服务治理、监控、CI/CD、压测和回滚能力。
5. 拆分收益是否大于网络调用和协作成本。

常见做法是先模块化单体，边界稳定后再拆服务；对热点模块、独立团队负责模块、资源需求特殊模块优先拆；对强一致、高内聚、小团队维护的模块保持合并。

## 4. 面试回答模板

Service Mesh 是把流量治理能力下沉到 sidecar 和控制面，统一做发现、负载均衡、熔断限流、mTLS、灰度和观测，适合多语言和治理能力复杂的微服务体系，但会增加资源开销和排障复杂度。Serverless 是把实例生命周期和扩缩容交给平台，适合事件驱动和弹性波动大的任务，但要处理冷启动、状态受限和可观测性问题。架构演进时不能为了技术潮流拆服务，要先看业务边界、独立扩容发布需求、数据归属和团队治理能力。
