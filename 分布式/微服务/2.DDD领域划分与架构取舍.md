# 2. DDD领域划分与架构取舍

领域划分是把复杂业务系统按业务能力拆成边界清晰的领域或限界上下文。它常和 DDD、微服务、模块化单体一起出现，核心目标是让模型、代码、数据和团队边界尽量一致。

## 1. 什么是领域划分

领域划分不是按技术层拆 Controller、Service、DAO，而是按业务能力拆。例如一个营销抽奖系统可以拆成：

1. **活动域**：活动生命周期、时间窗口、规则配置。
2. **奖品域**：奖品配置、库存、发放状态。
3. **资格域**：用户资格、黑白名单、参与次数。
4. **抽奖域**：概率模型、随机命中、奖池策略。
5. **履约域**：优惠券发放、实物发货、积分到账。
6. **风控域**：异常用户、刷奖识别、限流。

每个领域要有自己的核心概念、状态变化和业务规则，而不是只为了拆目录。

## 2. 限界上下文

限界上下文是一个模型生效的边界。同一个词在不同上下文里含义可能不同：

```text
奖品域：奖品 = 可配置的发放资源
履约域：奖品 = 待履约的权益或物流任务
财务域：奖品 = 有成本和预算占用的资产
```

划清上下文后，不同领域之间通过 API、领域事件或防腐层交互，避免一个领域直接操作另一个领域的内部表和对象。

## 3. 粒度过粗怎么办

粒度过粗的表现：

1. 一个服务或模块承担太多业务能力。
2. 需求变更经常影响大面积代码。
3. 数据表被多个流程共同修改，状态机混乱。
4. 团队并行开发容易互相阻塞。
5. 核心概念越来越多，单个模型难以解释。

处理方法：

1. 按业务流程拆出独立能力，例如把“抽奖命中”和“奖品履约”拆开。
2. 按数据归属拆边界，明确哪一个领域拥有哪张表和状态。
3. 按变化频率拆，高频变化规则独立成规则域或策略域。
4. 先在模块化单体内拆清包边界，再决定是否演进成微服务。
5. 对外提供稳定接口，内部模型逐步重构，避免一次性大迁移。

## 4. 粒度过细怎么办

粒度过细的表现：

1. 一次请求跨很多服务，链路长、延迟高。
2. 服务之间大量同步调用，失败面扩大。
3. 每个小服务都要独立部署、监控、告警，运维成本高。
4. 数据一致性被过早分布式化。
5. 简单需求需要改多个服务。

处理方法：

1. 合并生命周期一致、变化原因一致的模块。
2. 对强一致、强耦合的能力保持同一服务或同一数据库事务。
3. 把共享能力沉淀成库或平台服务，不要把每个小函数都拆成远程服务。
4. 用异步事件降低同步调用数量。
5. 以团队规模和发布频率为依据，不为“微服务”而拆服务。

## 5. 两个领域重合怎么办

领域重合通常说明边界语言不清，或者存在共享概念。处理时不要简单复制代码，也不要让两个领域共同写一张表。

常见做法：

1. **明确主数据归属**：一个实体只能有一个领域拥有写权限，其他领域通过接口查询或订阅事件。
2. **拆共享内核**：非常稳定且多个领域都需要的概念，可以抽成共享内核，但要严格控制范围。
3. **防腐层**：当外部领域模型不适合直接进入本领域时，用转换层隔离。
4. **领域事件**：一个领域状态变化后发布事件，其他领域维护自己的读模型。
5. **重新命名概念**：如果两个领域里的“订单”“奖品”“用户”含义不同，就用更准确的术语区分。

例如抽奖系统中，“奖品库存”归奖品域或库存域管理；抽奖域只调用扣减接口或消费库存快照，不直接改库存表。履约域只关心中奖记录和发放状态，不应该反向修改抽奖概率。

## 6. 架构优势和不足

按领域划分的优势：

1. 业务边界清晰，代码更容易维护。
2. 团队可以按领域并行开发和独立发布。
3. 热点领域可以独立扩容。
4. 故障影响面更容易隔离。
5. 模型贴近业务语言，和产品、运营沟通更顺畅。

不足：

1. 前期建模成本高，需要持续和业务对齐。
2. 边界划错后，跨领域调用和数据同步会变复杂。
3. 微服务化会引入网络延迟、超时、重试和分布式一致性问题。
4. 需要配套服务治理、监控、链路追踪、配置和发布能力。
5. 过度拆分会让简单系统复杂化。

## 7. 易错点

1. 不要把领域划分等同于数据库表划分。
2. 不要让多个领域共享写同一份核心数据。
3. 不要一开始就把所有领域拆成独立微服务，可以先模块化。
4. 领域边界不是一次设计永远不变，业务变化后要持续调整。
5. 共享内核要小而稳定，否则会变成新的大泥球。

## 8. 面试回答模板

我做领域划分时会先按业务能力和核心状态来拆，而不是按技术层拆。比如抽奖系统可以拆成活动、奖品、资格、抽奖、履约和风控几个领域，每个领域明确自己拥有的数据和规则。粒度过粗时，通常表现为一个模块承担太多变化原因，我会按数据归属、流程阶段和变化频率继续拆；粒度过细时，会带来链路过长、部署和一致性成本上升，我会把强一致、强耦合、生命周期一致的能力合并。两个领域重合时，先确定主数据归属，再通过接口、领域事件或防腐层交互，避免多个领域共同写一张表。
