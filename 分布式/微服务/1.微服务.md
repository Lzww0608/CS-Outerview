# 1.微服务

微服务是一种系统架构风格：把一个复杂系统拆成一组围绕业务能力组织的小服务，每个服务可以独立开发、独立部署、独立扩缩容，并通过明确的接口进行通信。

## 1. 核心特征

微服务不是“把代码拆成很多仓库”这么简单，关键在于服务边界和独立演进能力。

1. **按业务能力拆分**：例如用户、订单、支付、库存、搜索、通知等。
2. **独立部署**：一个服务发布不应该要求整套系统一起发布。
3. **独立数据归属**：一个服务应尽量拥有自己的数据模型，其他服务通过接口或事件访问。
4. **轻量通信**：常见方式包括 HTTP、gRPC、消息队列。
5. **去中心化治理**：每个服务可以独立选择合适的技术方案，但要遵守统一的协议、监控、日志、配置规范。

## 2. 和单体架构的区别

| 对比项 | 单体架构 | 微服务架构 |
| --- | --- | --- |
| 部署单元 | 整个应用一起部署 | 每个服务可独立部署 |
| 代码边界 | 模块边界主要靠代码规范 | 服务边界由接口和数据归属约束 |
| 扩容方式 | 整体扩容 | 热点服务单独扩容 |
| 调用成本 | 进程内调用，成本低 | 网络调用，存在延迟和失败 |
| 复杂度 | 开发初期简单 | 运维、治理和一致性复杂 |

## 3. 微服务带来的问题

微服务提升了系统演进能力，但也引入了分布式系统复杂度：

1. **服务发现**：调用方如何找到目标服务实例。
2. **负载均衡**：多个实例之间如何分摊请求。
3. **配置管理**：配置如何动态下发和回滚。
4. **链路追踪**：一次请求跨多个服务时如何定位耗时和错误。
5. **服务容错**：超时、重试、熔断、限流、降级如何设计。
6. **数据一致性**：跨服务事务通常不能简单依赖本地数据库事务。
7. **接口兼容性**：服务独立发布后，接口版本必须保持兼容演进。

## 4. 常见基础组件

| 组件 | 作用 |
| --- | --- |
| API Gateway | 统一入口、鉴权、路由、限流、协议转换 |
| Registry | 服务注册与发现，如 Consul、Etcd、Nacos |
| Config Center | 配置中心，支持动态配置 |
| MQ | 异步解耦、削峰、事件驱动 |
| Observability | 日志、指标、链路追踪 |
| Service Mesh | 把流量治理能力下沉到 Sidecar 或基础设施 |

### 4.1 最基础配套组件怎么回答

面试问“微服务最基础配套组件有哪些”，不要只列注册中心。一个能上线的微服务体系至少要覆盖入口、服务间调用、配置、稳定性、数据和观测。

1. **API 网关**：统一入口，做鉴权、路由、限流、灰度、协议转换和审计。
2. **注册中心和服务发现**：服务实例动态上下线，调用方通过服务名找到可用实例，常见 Consul、Nacos、Etcd、ZooKeeper、Kubernetes Service。
3. **负载均衡**：客户端负载均衡、网关负载均衡或服务端负载均衡，策略包括轮询、权重、最少连接、本地优先和一致性哈希。
4. **配置中心**：动态配置、灰度发布、回滚和配置审计，避免配置写死在镜像或代码里。
5. **RPC/IDL 和契约管理**：HTTP/gRPC/Thrift、Protobuf/OpenAPI，解决跨服务接口定义、版本兼容和代码生成。
6. **消息队列**：异步解耦、削峰填谷、事件驱动和最终一致性，常见 Kafka、RabbitMQ、RocketMQ。
7. **限流、熔断、降级、超时和重试**：防止慢下游或故障实例拖垮调用方；重试必须配合幂等。
8. **可观测性**：结构化日志、指标、链路追踪、告警和 dashboard，用 trace id 串起跨服务调用。
9. **数据治理**：每个服务明确数据归属，跨服务一致性用本地消息表、事务消息、Saga、TCC 或补偿任务处理。
10. **发布和运维体系**：CI/CD、容器镜像、健康检查、滚动发布、蓝绿/金丝雀、回滚和容量管理。

如果团队刚从单体演进，第一阶段通常先补 API 网关、注册发现、配置中心、日志指标和超时重试；等服务数量和团队规模上来，再引入链路追踪、服务网格、自动化治理和更复杂的发布策略。

## 5. 真实场景

适合微服务的场景：

1. 业务复杂，多个团队并行开发。
2. 不同模块流量差异大，需要独立扩容。
3. 某些模块有独立的技术栈或资源需求。
4. 发布频率高，需要降低单次发布影响面。

不适合过早微服务化的场景：

1. 业务边界还不稳定。
2. 团队规模小，服务治理能力不足。
3. 系统主要瓶颈不是组织协作或独立扩容。

## 6. 面试回答模板

微服务是把一个系统按业务能力拆成多个可独立部署、独立扩缩容的小服务。每个服务负责清晰的业务边界和数据归属，服务之间通过 HTTP、gRPC 或 MQ 通信。它的好处是降低单个模块变更对整体系统的影响，支持团队并行开发和热点服务独立扩容。

但微服务不是只有好处，它会把进程内调用变成网络调用，引入服务发现、负载均衡、超时重试、链路追踪、分布式一致性和接口兼容性问题。所以我理解微服务的关键不是“拆得越多越好”，而是围绕稳定业务边界拆分，并配套治理能力。
