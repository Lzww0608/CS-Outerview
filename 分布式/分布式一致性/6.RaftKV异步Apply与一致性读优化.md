# 6. Raft KV 异步 Apply 与一致性读优化

## 1. 问题背景

基于 Raft 的分布式 KV，一般采用 **复制日志 + 状态机** 模型。客户端写请求先交给 leader，leader 把写操作编码成 Raft log，复制到多数派并提交；随后各节点把已提交日志 apply 到本地 KV 状态机，例如 RocksDB、LevelDB、B+Tree 或内存 map。

典型链路：

```text
Client Put(k, v)
-> Leader Propose log entry
-> AppendEntries replicate to followers
-> Majority ack
-> Leader advances commit_index
-> Apply committed log to KV state machine
-> Respond to client
```

在真实系统中，Raft KV 不只要保证一致性，还要处理吞吐、延迟和可用性。因此会引入几个工程优化：

1. **异步 Apply**：Raft 模块提交日志后，由 apply worker 异步写入状态机，避免 Raft 主循环被慢状态机阻塞。
2. **ReadIndex**：线性一致读不写日志，通过 leader 确认自己仍在多数派并获得当前 commit index，再等本地 apply 到该 index 后读取。
3. **Follower Read**：让 follower 承担读流量，但要通过 ReadIndex、lease 或 safe timestamp 保证读一致性。
4. **PreVote**：正式选举前先预投票，避免少数派节点无效自增 term 打断健康 leader。

**假设条件**：

1. 本文讨论的是非拜占庭故障模型下的 Raft KV，节点可能宕机、重启、网络分区、消息延迟或乱序。
2. KV 状态机是确定性的，同一条日志在所有节点 apply 后得到相同结果。
3. 写请求需要线性一致；读请求默认讨论线性一致读，同时也说明 follower stale read 的边界。
4. Raft log、term、vote、snapshot、hard state 等持久化细节遵循标准 Raft 工程实现。
5. 具体代码以常见 `raftstore`、`raft_node`、`apply_worker`、`read_index_queue` 这类模块命名举例，不限定某个开源项目。

## 2. 问题现象

如果这些机制设计不当，分布式 KV 会出现以下现象：

1. **写入延迟高**：所有已提交日志同步 apply 到状态机后才继续处理 Raft 消息，慢磁盘或大事务会阻塞心跳和复制。
2. **读到旧数据**：leader 已经提交到 `commit_index=100`，但本地状态机只 apply 到 `applied_index=95`，直接读状态机会漏掉 96~100 的写入。
3. **线性一致读退化成写日志读**：每次读都走一条 no-op log，正确但开销高。
4. **Follower Read 读旧值**：follower 落后 leader，直接从 follower 状态机读会返回过期数据。
5. **Leader 被无效选举打断**：少数派 follower 网络隔离后超时，不断自增 term，网络恢复时迫使健康 leader 下台。
6. **ReadIndex 卡住**：leader 能提交写日志，但 apply worker 落后，读请求等待 `applied_index >= read_index` 超时。
7. **Apply 队列堆积**：状态机写入慢、snapshot 生成慢或大批量日志导致 apply backlog 增长。
8. **读写乱序响应**：写请求已经告诉客户端成功，但同一客户端紧接着读却读不到刚写入的数据。

一个典型错误流程：

```text
1. Leader commit_index 推进到 200
2. Apply worker 只 apply 到 180
3. Leader 收到线性一致读请求
4. 直接读取本地 KV
5. 返回的是 index=180 的状态，漏掉 181~200 的已提交写入
```

正确做法是：读请求必须拿到一个安全的 read index，并等待本地状态机至少 apply 到该 index。

## 3. 影响范围

这些机制会影响 Raft KV 的核心模块：

1. **Raft Core**：term、vote、log replication、commit index、ReadIndex、PreVote。
2. **Raft Ready/Advance 循环**：把 committed entries、messages、snapshot、hard state 从 Raft Core 交给外部系统处理。
3. **Apply Worker**：异步消费 committed entries，写入 KV 状态机，推进 applied index。
4. **KV State Machine**：执行 Put/Delete/Txn 等命令，维护状态机数据和 apply checkpoint。
5. **Read Index Queue**：管理等待 read index 和等待 apply 的读请求。
6. **Lease / Clock 模块**：如果使用 lease read，需要处理时钟单调性、漂移和心跳确认。
7. **Follower Read Router**：决定读请求是走 leader、local follower，还是转发。
8. **Snapshot 模块**：apply 落后太多时可能需要安装 snapshot，读请求需要感知 snapshot 状态。
9. **监控告警**：需要暴露 apply lag、read index latency、follower lag、election/prevote 指标。

如果涉及代码实现，可能需要修改的模块包括：

1. `raft/node.go` 或 `raft_core.cc`：实现 PreVote、ReadIndex、heartbeat ack 和 commit 推进。
2. `raftstore/peer.rs` 或 `raft_node.cc`：处理 Ready、持久化日志、发送消息、派发 apply task。
3. `apply_worker.rs` / `apply_executor.go`：异步 apply committed entries，更新 applied index。
4. `read_index_queue.go`：缓存等待 ReadIndex 的请求，并在 apply 到位后唤醒。
5. `kv_engine.cc`：执行状态机命令，支持按 apply index 读取。
6. `follower_read.go`：处理 follower 的 lease/readindex/safe-ts 判断。
7. `metrics.rs`：记录 apply lag、read wait、read index round trip、prevote reject 等指标。
8. `raft_kv_test.go`：补充分区、重启、慢 apply、follower read 和 stale read 测试。

## 4. 原因分析

### 4.1 Raft 提交和状态机可见不是一回事

Raft 的 `commit_index` 表示日志已经被多数派确认，可以安全提交。但状态机真正能读到该写入，还要等日志被 apply：

```text
commit_index >= applied_index
```

如果系统异步 apply，就一定会出现短暂的：

```text
commit_index = 100
applied_index = 95
```

这不是错误，而是异步 apply 的自然结果。问题在于：读请求不能只看 commit index，也不能直接读未追到 read index 的状态机。

### 4.2 为什么需要异步 Apply

Raft 核心循环要处理心跳、AppendEntries、投票、日志持久化和消息发送。如果把状态机 apply 放在 Raft 主循环里，慢状态机会拖慢 Raft 协议本身：

```text
慢 RocksDB 写入
-> Apply 阻塞
-> Raft tick/heartbeat 延迟
-> follower 误判 leader 超时
-> 选举抖动
```

异步 apply 把复制协议和状态机执行解耦：

```text
Raft Core: 快速推进 commit、收发消息
Apply Worker: 顺序执行 committed entries
```

代价是读路径必须处理 commit 与 applied 之间的滞后。

### 4.3 为什么需要 ReadIndex

线性一致读要求读操作必须看到读开始前已经完成的所有写入。如果 leader 直接读本地状态机，有两个风险：

1. 当前节点可能已经不是 leader，只是自己还不知道。
2. 当前节点 commit 了日志，但状态机尚未 apply 到最新安全点。

最保守做法是把读也写成一条 Raft log，例如 no-op read entry。这样一定线性一致，但每次读都要复制日志到多数派，开销太高。

ReadIndex 的目标是：**不写日志，也能确认 leader 仍然有效，并确定一个安全读取的 commit index**。

### 4.4 为什么 Follower Read 难

Follower 可能落后 leader：

```text
leader commit_index = 100
follower applied_index = 80
```

如果 follower 直接读本地 KV，就可能返回旧数据。要让 follower 提供线性一致读，必须满足两个条件：

1. follower 知道一个线性一致的 read index。
2. follower 本地已经 apply 到该 read index。

否则 follower read 只能是 stale read 或 bounded stale read。

### 4.5 为什么 PreVote 能减少抖动

没有 PreVote 时，少数派 follower 收不到心跳后会自增 term 并发起选举。它拿不到多数派，无法成为 leader，但 term 已经变大。网络恢复后，健康 leader 看到更高 term 会退位，造成不必要的 leader 切换。

PreVote 把流程改成：

```text
先不增加 term
-> 问多数派：如果我以 term+1 参选，你们会投我吗
-> 拿到多数派预投票后，才正式增加 term 并 RequestVote
```

少数派拿不到多数派 PreVote，因此不会把 term 推高。

## 5. 解决方案

### 5.1 异步 Apply

异步 Apply 的基本结构：

```text
Raft ready loop:
  persist hard state / log entries
  send messages
  push committed entries to apply queue
  advance raft

Apply worker:
  pop committed entries
  apply to state machine in log order
  update applied_index
  notify waiters
```

伪代码：

```go
func raftReadyLoop() {
    for {
        rd := node.Ready()
        wal.Save(rd.HardState, rd.Entries)
        transport.Send(rd.Messages)

        if len(rd.CommittedEntries) > 0 {
            applyCh <- ApplyTask{entries: rd.CommittedEntries}
        }

        node.Advance()
    }
}

func applyWorker() {
    for task := range applyCh {
        for _, ent := range task.entries {
            cmd := Decode(ent.Data)
            kv.Apply(cmd)
            appliedIndex.Store(ent.Index)
        }
        readIndexQueue.NotifyApplied(appliedIndex.Load())
    }
}
```

关键约束：

1. Apply 必须按 log index 顺序执行。
2. `applied_index` 必须在状态机写入成功后再推进。
3. 写请求如果要求“写成功后可读”，通常要等对应 index apply 完成再响应客户端。
4. 读请求要等待 `applied_index >= read_index`。
5. Snapshot apply 和普通 log apply 不能乱序。

### 5.2 ReadIndex

ReadIndex 的典型流程：

```text
1. Leader 收到线性一致读请求
2. Leader 记录当前 commit_index 作为 read_index 候选
3. Leader 向多数派发送 heartbeat/readindex context
4. 多数派确认该 leader 仍在当前 term
5. Leader 返回 read_index = 当前 commit_index
6. 等本地 applied_index >= read_index
7. 读取本地状态机并返回
```

为什么要多数派确认？

因为 leader 必须确认自己仍然是当前 term 的合法 leader。网络分区中旧 leader 可能还以为自己是 leader，但拿不到多数派确认，就不能服务线性一致读。

伪代码：

```go
func LinearizableRead(req ReadRequest) {
    ctx := newReadContext(req)
    raft.ReadIndex(ctx.id)
    pendingReads[ctx.id] = req
}

func onReadIndexResp(ctxID string, index uint64) {
    if appliedIndex.Load() >= index {
        serveRead(ctxID)
        return
    }
    readIndexQueue.Wait(index, ctxID)
}

func onApplied(index uint64) {
    readIndexQueue.FireReady(index, func(ctxID string) {
        serveRead(ctxID)
    })
}
```

优化点：

1. 合并同一时间窗口内的多个读请求，共享一次 ReadIndex。
2. 对同一个 region/shard 批量唤醒等待读。
3. 如果 `applied_index` 已经足够新，读请求无需额外等待 apply。
4. 对只读高峰做 read index pipeline。

### 5.3 Lease Read

Lease Read 是 ReadIndex 的进一步优化。leader 如果能基于心跳确认自己在一段时间内仍持有多数派 lease，就可以在 lease 有效期内直接本地读：

```text
leader heartbeat 得到多数派 ack
-> 建立 leader lease 到 now + lease_timeout
-> lease 内直接读本地状态机
-> 仍需确保 applied_index 足够新
```

优势：

1. 不需要每次读都向多数派确认。
2. 读延迟低，适合读多写少。

风险：

1. 依赖时钟单调性和漂移上界。
2. GC pause、系统时钟跳变、虚拟化环境可能破坏 lease 假设。
3. lease 读仍然要等待本地 apply 到安全 index。

工程上通常：

1. lease timeout 小于 election timeout。
2. 使用 monotonic clock，不使用 wall clock。
3. GC pause 后主动失效 lease。
4. 不确定时回退到 ReadIndex。

### 5.4 Follower Read

Follower Read 有多种语义：

1. **Stale Read**：直接读 follower 本地状态，可能旧，但延迟低。
2. **Bounded Stale Read**：要求 follower 落后不超过某个时间或 index。
3. **Linearizable Follower Read**：follower 先从 leader 获取 read index 或 safe timestamp，再等本地 apply 到位后读取。

线性一致 follower read 流程：

```text
1. Client 向 follower 发起读
2. Follower 向 leader 请求 ReadIndex
3. Leader 通过多数派确认后返回 read_index
4. Follower 等待自身 applied_index >= read_index
5. Follower 从本地状态机读取并返回
```

伪代码：

```go
func FollowerRead(req ReadRequest) {
    if req.allowStale {
        serveLocalRead(req)
        return
    }

    leader.SendReadIndex(req.ctx)
    waitReadIndex(req.ctx, func(index uint64) {
        waitApplied(index, func() {
            serveLocalRead(req)
        })
    })
}
```

优化点：

1. follower 缓存最近一次安全 read index，短时间内复用。
2. leader 主动广播 read state 或 safe timestamp。
3. follower apply 追不上时，把读转发给 leader。
4. 对热点 follower 读做 local read queue 和批量 ReadIndex。

### 5.5 PreVote

PreVote 实现流程：

```text
Follower election timeout
-> 如果开启 PreVote，进入 PreCandidate
-> 发送 PreVote(term = currentTerm + 1, lastLogIndex, lastLogTerm)
-> 收到多数派 PreVoteGranted
-> 才自增 currentTerm，转 Candidate
-> 发送正式 RequestVote
```

PreVote 请求必须检查：

1. candidate 的日志是否至少和自己一样新。
2. 本节点是否刚收到合法 leader 心跳。
3. candidate 预期 term 是否合理。
4. 当前配置中 candidate 是否有资格参选。

PreVote 不应该：

1. 修改本地 `currentTerm`。
2. 写入 `votedFor`。
3. 让健康 leader 因为预投票消息下台。

### 5.6 写请求响应时机

Raft KV 写请求有两个常见响应时机：

1. **Committed 后响应**：日志已提交，但状态机可能尚未 apply。
2. **Applied 后响应**：日志已提交且状态机已执行。

如果 KV 对外承诺“写成功后立即可读”，推荐 applied 后响应：

```text
Propose -> Commit -> Apply -> Respond
```

否则可能出现：

```text
Put 返回成功
Get 立刻走本地状态机
因为 apply 落后，Get 读不到刚写入
```

有些系统为了降低写延迟会 committed 后响应，但必须保证后续读路径通过 ReadIndex 等机制等待 apply，或者在客户端层面处理 read-your-write。

## 6. 可选方案对比

| 方案 | 核心原理 | 优点 | 缺点 | 适用场景 |
| --- | --- | --- | --- | --- |
| 同步 Apply | commit 后立即在 Raft 主循环 apply | 实现简单，读路径直观 | 慢状态机会阻塞 Raft 心跳和复制 | 教学、小型系统 |
| 异步 Apply | apply worker 独立消费 committed entries | 吞吐高，Raft 主循环更轻 | 读路径要等待 applied index | 生产级 Raft KV |
| Log Read | 每次读写一条 no-op log | 线性一致容易证明 | 读延迟高，吞吐低 | 简单强一致系统 |
| ReadIndex | 多数派确认 leader 后本地读 | 不写日志，线性一致 | 需要等待 applied index | 常规强一致读 |
| Lease Read | lease 内本地读 | 延迟最低 | 依赖时钟和 pause 假设 | 低延迟读、多数派稳定 |
| Follower Stale Read | follower 直接本地读 | 延迟低，扩展读吞吐 | 非线性一致 | 可接受旧读 |
| Follower ReadIndex | follower 获取 leader read index 后读 | 线性一致，可分担读流量 | 多一次 leader 交互，落后时等待 | 读多、follower 资源充足 |
| 无 PreVote | 超时直接 RequestVote | 实现简单 | 少数派推高 term，leader 抖动 | 简化实现 |
| PreVote | 正式选举前预投票 | 降低无效选举 | 多一轮消息和状态 | 生产集群 |

## 7. 推荐方案

推荐生产级 Raft KV 采用：

1. **异步 Apply**：Raft Core 不直接执行慢状态机。
2. **写请求 Applied 后响应**：减少 read-your-write 问题。
3. **默认 ReadIndex 线性一致读**：不写 no-op log，平衡正确性和性能。
4. **Lease Read 作为可选快路径**：只有在时钟和 pause 控制可靠时开启。
5. **Follower Read 分层提供**：默认线性一致 follower read 走 leader ReadIndex；业务明确接受旧读时才允许 stale read。
6. **开启 PreVote**：减少少数派分区和网络抖动导致的无效选举。
7. **读请求等待 applied index**：所有线性一致读都必须满足 `applied_index >= read_index`。
8. **监控 apply lag 和 read wait**：否则很难定位“Raft 已提交但读还慢”的问题。

面试回答模板：

```text
基于 Raft 的 KV 通常把日志提交和状态机执行解耦，Raft 负责复制并推进 commit_index，apply worker 异步把 committed entries 顺序应用到 KV 状态机，并推进 applied_index。
异步 Apply 提高吞吐，但读必须等待状态机 apply 到安全 index。
ReadIndex 是线性一致读优化，leader 通过多数派心跳确认自己仍是合法 leader，拿当前 commit_index 作为 read_index，然后等本地 applied_index >= read_index 再读状态机。
Follower Read 如果要线性一致，follower 也要从 leader 获取 read_index，并等自己 apply 到该 index；否则只是旧读。
PreVote 是正式自增 term 前的预投票，少数派节点拿不到多数派预投票就不会推高 term，从而减少健康 leader 被打断。
```

## 8. 实施步骤

### 8.1 拆分 Raft Core 和 Apply Worker

建立两个队列：

```text
raft_ready_queue
apply_queue
```

Ready loop 负责：

1. 持久化 hard state 和 entries。
2. 发送 Raft 消息。
3. 把 committed entries 放入 apply queue。
4. 调用 Advance。

Apply worker 负责：

1. 顺序 decode committed entries。
2. 写入 KV 状态机。
3. 持久化 apply checkpoint。
4. 推进 applied index。
5. 唤醒等待该 index 的读写请求。

### 8.2 实现 Apply Index 等待器

需要一个等待结构：

```go
type ApplyWaiter struct {
    mu      sync.Mutex
    waiters map[uint64][]chan struct{}
}

func (w *ApplyWaiter) Wait(index uint64) <-chan struct{} {
    ch := make(chan struct{})
    w.mu.Lock()
    w.waiters[index] = append(w.waiters[index], ch)
    w.mu.Unlock()
    return ch
}

func (w *ApplyWaiter) Notify(applied uint64) {
    w.mu.Lock()
    for index, list := range w.waiters {
        if index <= applied {
            for _, ch := range list {
                close(ch)
            }
            delete(w.waiters, index)
        }
    }
    w.mu.Unlock()
}
```

真实实现要用 heap 或有序 map，避免每次 `Notify` 扫全表。

### 8.3 实现 ReadIndex 队列

读请求进入：

```text
read_ctx -> pending_read_map
raft.ReadIndex(read_ctx)
```

收到 ReadIndex 回调：

```text
read_index = resp.index
if applied_index >= read_index:
    serve read
else:
    wait apply
```

核心修改逻辑：

1. ReadIndex 请求要有唯一 context。
2. 多个请求可以 batch 到同一个 ReadIndex。
3. 超时后要返回 retryable error 或重试。
4. leader 变更时要清理旧 pending read。

### 8.4 实现 Follower Read

Follower 收到读请求：

```text
if stale read:
    local read
else:
    request read_index from leader
    wait own applied_index >= read_index
    local read
```

需要处理：

1. follower 不知道 leader 时，返回重定向或重试。
2. follower apply lag 过大时，转发 leader。
3. follower 正在 apply snapshot 时，拒绝或等待。
4. leader 变更时，丢弃旧 read index。

### 8.5 实现 PreVote

状态机增加 `PreCandidate`：

```text
Follower
-> election timeout
-> PreCandidate
-> PreVote majority
-> Candidate
-> RequestVote majority
-> Leader
```

PreVote RPC：

```go
type PreVoteRequest struct {
    Term         uint64 // currentTerm + 1
    CandidateID uint64
    LastLogIndex uint64
    LastLogTerm  uint64
}
```

收到 PreVote：

```go
func onPreVote(req PreVoteRequest) PreVoteResponse {
    if recentlyHeardFromLeader() {
        return reject()
    }
    if !isLogUpToDate(req.LastLogIndex, req.LastLogTerm) {
        return reject()
    }
    return grant()
}
```

### 8.7 测试重点

如果涉及代码实现，测试重点包括：

1. **异步 Apply 顺序测试**：committed entries 必须按 index 顺序 apply。
2. **读等待 Apply 测试**：ReadIndex 返回 100，applied 只有 90 时，读请求必须等待。
3. **写后读测试**：Put 成功后立即 Get，必须读到新值。
4. **Leader 旧读测试**：旧 leader 分区后拿不到多数派 ReadIndex，不能返回线性一致读。
5. **Follower Read 测试**：follower 落后时不能直接返回线性一致读。
6. **Lease Read 测试**：lease 过期、GC pause、时钟异常后必须回退 ReadIndex。
7. **PreVote 少数派测试**：少数派节点超时不能推高多数派 leader 的 term。
8. **Snapshot Apply 测试**：安装 snapshot 时读请求不能读到半状态。
9. **重启恢复测试**：applied checkpoint 和状态机数据一致。
10. **压力测试**：写入、ReadIndex、Follower Read、snapshot、compaction 并发执行。

## 9. 风险与注意事项

1. **异步 Apply 不能乱序**  
   Raft 日志顺序就是状态机执行顺序，apply 并发化时只能跨 shard/region 并发，单 Raft group 内必须有序。

2. **ReadIndex 后必须等 applied index**  
   只拿到 read index 不够，状态机没 apply 到该 index 时直接读仍然会旧读。

3. **Follower Read 默认不等于强一致读**  
   只有通过 ReadIndex/lease/safe timestamp 并等待本地 apply 到位，才能称为线性一致 follower read。

4. **Lease Read 依赖工程假设**  
   时钟漂移、长时间 stop-the-world、线程调度冻结都会影响 lease 安全，保守系统应优先 ReadIndex。

5. **写请求响应时机要明确**  
   committed 后响应延迟低，但可能影响写后读；applied 后响应语义更直接但延迟更高。

6. **PreVote 不能跳过日志新旧检查**  
   日志落后的节点不应该通过 PreVote，否则会增加无效选举概率。

7. **Leader 变更要清理 pending read**  
   旧 leader 上未完成的 ReadIndex 请求不能在新 term 下继续使用。

8. **Apply backlog 是可用性风险**  
   Raft 还能提交不代表用户能读到新值，apply lag 过大会让读请求大量等待。

9. **Snapshot 和 Apply 互斥边界要清楚**  
   安装 snapshot 期间不能和普通 log apply 交错破坏状态机。

10. **多 Raft Group 要分别维护 index**  
   每个 shard/region 的 commit/applied/read index 独立，不能用全局一个 index 混用。

## 10. 验证方式

### 10.1 异步 Apply 验证

构造日志：

```text
index 10: Put(a, 1)
index 11: Put(a, 2)
index 12: Delete(a)
```

验证：

1. apply 顺序必须是 10、11、12。
2. `applied_index` 只能在状态机执行成功后推进。
3. 重启后状态机和 applied checkpoint 一致。

### 10.2 ReadIndex 验证

测试流程：

```text
leader commit_index = 100
leader applied_index = 90
readindex returns 100
```

预期：

1. 读请求不能立即读状态机。
2. apply 到 100 后才能返回。
3. 返回值必须包含 100 之前所有已提交写入。

### 10.3 旧 Leader 验证

网络分区：

```text
旧 leader A 被隔离到少数派
B/C/D 形成多数派并选出新 leader B
A 仍以为自己是 leader
```

验证：

1. A 无法获得多数派 ReadIndex ack。
2. A 不能返回线性一致读。
3. A 收到更高 term 后退回 follower。

### 10.4 Follower Read 验证

构造：

```text
leader commit_index = 200
follower applied_index = 150
follower 收到线性一致读
```

预期：

1. follower 必须向 leader 获取 read index。
2. 如果 read index 为 200，follower 要等 apply 到 200。
3. 如果等待超时，可以转发 leader 或返回重试。

### 10.5 PreVote 验证

场景：

```text
A/B/C 是多数派，leader A 正常
D/E 在少数派分区中超时
```

验证：

1. D/E 只能发 PreVote，不能自增 term 成功打断 A。
2. 网络恢复后，A 不应因为 D/E 的预投票消息退位。
3. 如果 leader 真的失效，多数派节点仍能通过 PreVote 后正式选举。

### 10.6 性能验证

指标对比：

1. 同步 Apply vs 异步 Apply 的写吞吐。
2. Log Read vs ReadIndex 的读延迟。
3. ReadIndex vs Lease Read 的 P99。
4. Leader Read vs Follower Read 的读扩展能力。
5. 开启 PreVote 前后的 leader 切换次数。
6. Apply lag 对读延迟的影响。

压测组合：

```text
高写入 + 慢 apply
高读 + ReadIndex
Follower Read + follower 落后
网络分区 + PreVote
Snapshot apply + 读写并发
```

## 11. 总结

基于 Raft 的分布式 KV，核心不是“日志复制成功就万事大吉”，而是要把复制、apply 和读可见性边界讲清楚。

1. **异步 Apply**：Raft 提交日志后，把状态机执行交给 apply worker。这样能避免慢状态机阻塞 Raft 主循环，但读请求必须等待 `applied_index >= read_index`。
2. **ReadIndex**：leader 不写读日志，而是通过多数派 heartbeat 确认自己仍是合法 leader，拿当前 commit index 作为 read index，再等本地 apply 到位后读取状态机。
3. **Follower Read**：如果要线性一致，follower 必须从 leader 获取 read index，并等待自己 apply 到该 index；直接读 follower 只能算 stale read。
4. **PreVote**：正式选举前先预投票，不自增 term，只有确认可能获得多数派后才发起 RequestVote，减少少数派节点打断健康 leader。
5. **优化方向**：ReadIndex 批量化、lease read 快路径、follower read 转发/等待策略、apply worker 批量写、按 Raft group 并行 apply、监控 apply lag 和 read wait。

面试时可以用一句话收束：

```text
Raft KV 的强一致读写要同时满足日志提交和状态机可见。异步 Apply 提升吞吐，但引入 commit_index 与 applied_index 的差距；ReadIndex 和 Follower Read 都必须拿到安全 read index 并等待 apply 到位；PreVote 则是选举稳定性优化，防止少数派无效自增 term 造成 leader 抖动。
```
