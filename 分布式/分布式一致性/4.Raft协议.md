# Raft 协议

Raft 是一种强一致复制协议，目标是在一组可能宕机、重启、网络延迟或网络分区的节点之间，维护一份一致的复制日志。它和 Paxos 一样属于崩溃容错协议，不处理节点恶意作恶这类拜占庭错误。

## 1. 角色和任期

Raft 节点有三种角色：

1. **Leader**：处理客户端写请求，复制日志给 follower。
2. **Follower**：被动接收 leader 心跳和日志复制请求。
3. **Candidate**：选举超时后发起投票，尝试成为 leader。

Raft 用 `term` 表示任期。任期单调递增，类似逻辑时钟：

1. 发现更大 term 的消息，节点必须更新本地 term 并退回 follower。
2. 每个 term 最多只有一个合法 leader。
3. 请求和响应都携带 term，用来识别过期 leader 或过期 candidate。

## 2. Leader 选举

流程：

1. follower 在 election timeout 内没有收到 leader 心跳，会转为 candidate。
2. candidate 增加 term，给自己投票，并向其他节点发送 `RequestVote`。
3. 获得多数派投票后成为 leader。
4. 如果收到合法 leader 的 `AppendEntries`，candidate 会退回 follower。

为了减少多个节点同时发起选举导致票数分裂，Raft 使用随机 election timeout。

投票时不仅看 term，还要看日志新旧。投票节点只会投给“日志至少和自己一样新”的 candidate，避免选出缺失已提交日志的 leader。

## 3. 日志复制和提交

客户端写请求只由 leader 处理：

```text
client -> leader append log
leader -> followers AppendEntries
majority replicated
leader commit
leader apply to state machine
leader response to client
```

关键点：

1. 日志条目包含 `index`、`term` 和 command。
2. `AppendEntries` 会带上前一个日志的 `prevLogIndex` 和 `prevLogTerm`。
3. follower 如果发现前置日志不匹配，会拒绝复制。
4. leader 回退 `nextIndex`，直到找到共同前缀，再覆盖 follower 冲突日志。
5. 一条日志被当前 leader 复制到多数派后，才可以提交。

Raft 保证：已提交日志不会被后续 leader 覆盖。

## 3.1 多数派提交与可用性追问

Raft 要求一条日志复制到多数派后才能提交，核心原因是**任意两个多数派一定有交集**。只要已提交日志存在于某个多数派，后续能当选 leader 的 candidate 也必须获得另一个多数派的投票，这两个多数派的交集节点会把“日志新旧”约束传递给选举过程，阻止缺失已提交日志的节点当选。

如果只要求小于等于 `N/2` 的节点确认，会出现两个互不相交的分区都认为自己提交成功，网络恢复后无法同时保留两份冲突日志。如果 leader 不等 follower 确认就提交，本质上退化成单副本写入；leader 崩溃后这条日志可能没有任何其他节点保存，无法保证写成功后的持久性和一致性。

日志提交期间通常不会让整个集群不可用：健康 leader 可以持续接收写请求、复制日志并在多数派确认后返回。但 Raft 不是“永远无不可用时间”：

1. leader 故障或网络分区后，集群需要等待 election timeout 并选出新 leader，这段时间写请求不可用。
2. 少数派分区不可提交写入，只能牺牲可用性保证一致性。
3. 线性一致读不能随便读 follower 的旧日志；通常要通过 leader ReadIndex、lease read 或把读请求转发给 leader。
4. 如果业务接受旧读，可以读 follower，但要明确这不是线性一致读。

## 3.2 如何保证 leader 日志最新

Raft 通过投票规则保证新 leader 不会缺失已提交日志。`RequestVote` 会携带 candidate 的 `lastLogTerm` 和 `lastLogIndex`，投票节点只会投给“日志至少和自己一样新”的 candidate。

日志新旧比较规则：

1. 先比较最后一条日志的 `term`，`term` 更大说明日志更新。
2. 如果 `term` 相同，再比较 `index`，`index` 更大说明日志更长。

这个规则和多数派提交结合起来保证安全性：已提交日志已经复制到多数派；新 leader 必须拿到多数派投票；两个多数派有交集；交集节点如果拥有更新的已提交日志，就不会把票投给缺失该日志的 candidate。因此，能当选的 leader 至少包含所有已提交日志。

## 4. 网络故障时 Raft 如何工作

Raft 依赖多数派机制处理网络故障。

### 4.1 少数派分区

如果集群被分成多数派和少数派：

1. 多数派分区可以选出或保留 leader，继续处理写请求。
2. 少数派分区无法获得多数票，不能选出有效 leader。
3. 少数派节点可能不断自增 term 并发起选举，但无法提交日志。
4. 这牺牲了少数派可用性，换取一致性。

### 4.2 旧 leader 被隔离

旧 leader 如果落入少数派：

1. 它可能暂时以为自己仍是 leader。
2. 但它无法把新日志复制到多数派，因此不能提交新写入。
3. 多数派会选出新 leader 继续服务。
4. 网络恢复后，旧 leader 收到更大 term 的请求或响应，会退回 follower。

### 4.3 网络恢复

网络恢复后：

1. term 较小的节点看到更大 term，会更新 term 并转为 follower。
2. 日志落后的节点会被新 leader 通过 `AppendEntries` 修复。
3. 未提交日志可能被覆盖，客户端需要基于超时和幂等机制重试。
4. 已提交日志依靠多数派和日志新旧投票规则保持安全。

## 5. PreVote

PreVote 是 Raft 工程实现中常见的选举优化，Raft 原论文扩展版和 etcd/raft 等实现都讨论过类似机制。它的目的不是改变 Raft 安全性，而是减少无效选举对健康 leader 的干扰。

没有 PreVote 时，少数派分区里的 follower 收不到 leader 心跳，会不断增加 `currentTerm` 并发起 RequestVote。网络恢复后，这个更大的 term 会让原 leader 退位，即使原 leader 一直在多数派中正常工作，也会造成一次不必要的 leader 切换。

PreVote 的做法是：

1. 节点超时后先不自增 term。
2. 先发送 PreVote 请求，询问其他节点：“如果我以 `term+1` 发起选举，你会不会投票给我？”
3. 只有拿到多数派 PreVote 响应后，才真正增加 term 并发起正式 RequestVote。
4. 如果节点处在少数派，它拿不到多数派 PreVote，也就不会把 term 推高。

PreVote 仍然要检查 candidate 日志是否足够新，否则可能让日志落后的节点获得预投票。PreVote 降低的是可用性抖动，不是多数派、日志新旧和提交规则这些安全性基础。

## 6. Raft 需要持久化的信息

Raft 论文中的持久化状态包括：

1. `currentTerm`：当前任期。
2. `votedFor`：当前任期投给了谁。
3. `log[]`：日志条目，每条包含 command 和 term。

这些状态必须在响应 RPC 前持久化，否则重启后可能违反安全性。

工程实现通常还会持久化：

1. snapshot 数据和 snapshot 的 `lastIncludedIndex/lastIncludedTerm`。
2. 当前集群配置或 joint consensus 配置。
3. 已应用状态机自身的数据。

`commitIndex` 和 `lastApplied` 在论文里属于 volatile state。节点重启后可以通过 leader 的 commit 信息、日志和状态机恢复推进。但很多工程实现会把 applied index 或状态机 checkpoint 落盘，用于加速恢复。

如果 `votedFor` 丢失，节点重启后可能在同一个 term 给多个 candidate 投票。这样会破坏“一个 term 最多一个 leader”的基础假设，在特定网络时序下可能导致两个 candidate 都认为自己获得多数派，影响选举安全。因此 `currentTerm` 和 `votedFor` 要作为同一个稳定状态谨慎刷盘。

## 7. Joint Consensus

Joint Consensus 用于 Raft 集群成员变更，例如从 `{A,B,C}` 扩容到 `{A,B,C,D,E}`。直接切换配置有风险：旧配置和新配置可能形成两个不同多数派，导致两个 leader 或冲突提交。

Raft 的做法是两阶段：

1. **联合配置阶段 `C_old,new`**：日志提交必须同时获得旧配置多数派和新配置多数派。
2. **新配置阶段 `C_new`**：联合配置日志提交并生效后，再提交只包含新配置的日志，之后按新配置多数派运行。

这样保证任意一次提交所依赖的多数派集合仍然有交集，不会在成员变更过程中破坏已提交日志安全性。

工程注意点：

1. 成员变更本身也是日志条目，必须经过 Raft 日志复制提交。
2. 一次最好只做少量节点变更，降低恢复和排障复杂度。
3. 新节点加入前通常先追日志或装快照，否则会拖慢提交。
4. 老节点移除后要处理它仍以旧配置发起请求的情况。

## 8. 工程注意事项

1. 客户端请求要带唯一请求 ID，避免 leader 切换后重试导致重复执行。
2. 读请求如果要线性一致，leader 也要确认自己仍在多数派中，例如 ReadIndex 或 lease read。
3. election timeout 要明显大于心跳间隔，否则容易频繁选举。
4. 持久化 `currentTerm`、`votedFor` 和日志后才能响应成功，避免崩溃恢复破坏安全性。
5. Raft 只能容忍少于半数节点故障，`2n + 1` 个节点最多容忍 `n` 个故障。

## 9. 面试回答模板

Raft 用 leader 统一处理写入，并把日志复制到多数派后提交。节点角色有 leader、follower、candidate，任期 term 用来识别新旧领导者。网络分区时，只有多数派分区能选出 leader 并提交日志，少数派即使自增 term 也不能提交写入；旧 leader 被隔离后无法拿到多数派确认，网络恢复时会根据更大的 term 退回 follower，并由新 leader 修复落后日志。PreVote 会在正式自增 term 前先询问是否可能获得多数票，减少少数派节点无效选举导致的 leader 抖动。Raft 必须持久化 `currentTerm`、`votedFor` 和日志，`votedFor` 丢失可能导致同一 term 重复投票。成员变更用 Joint Consensus，联合配置阶段要求旧多数派和新多数派同时确认，保证配置切换时多数派仍有交集。

## 10. Raft 和 Paxos 的对比

Raft 和 Paxos 都是多数派共识协议，都能在非拜占庭故障下保证已达成的决定不会被推翻。区别主要在工程表达方式：

| 对比项 | Paxos / Multi-Paxos | Raft |
| --- | --- | --- |
| 核心抽象 | 提案号、Prepare/Accept、Acceptor | 任期、Leader、日志复制 |
| 易理解性 | 理论强，但 Basic Paxos 到工程实现跨度大 | 角色和流程拆分清晰，更适合教学和落地 |
| 连续日志 | Multi-Paxos 通过稳定 Leader 优化 | 天然围绕复制日志设计 |
| 选主 | Paxos 本身不强制具体选主形式 | 内置 Leader Election |
| 日志安全 | 依靠提案编号和多数派交集 | 依靠日志新旧投票和 AppendEntries 一致性检查 |

工程上 Raft 更流行的原因是：它把 leader 选举、日志复制、安全性约束、成员变更拆成了更明确的模块，状态机和 RPC 含义更直观，写代码、排查问题和做可视化都更容易。Paxos 理论更基础，很多系统实际使用的是 Multi-Paxos 或 Paxos 变体。

## 11. Go 简化实现：日志复制核心

下面代码只保留日志复制的核心逻辑，用于面试说明 `prevLogIndex/prevLogTerm` 如何保证日志前缀一致，以及 follower 如何删除冲突日志。

```go
package raft

type LogEntry struct {
    Term    int
    Command []byte
}

type AppendEntriesArgs struct {
    Term         int
    LeaderID     int
    PrevLogIndex int
    PrevLogTerm  int
    Entries      []LogEntry
    LeaderCommit int
}

type AppendEntriesReply struct {
    Term    int
    Success bool
}

type Node struct {
    currentTerm int
    log         []LogEntry // log[0] 可以放哨兵，真实日志从 1 开始更方便
    commitIndex int
}

func (n *Node) AppendEntries(args AppendEntriesArgs) AppendEntriesReply {
    if args.Term < n.currentTerm {
        return AppendEntriesReply{Term: n.currentTerm, Success: false}
    }
    if args.Term > n.currentTerm {
        n.currentTerm = args.Term
        // 真实实现里还要转 follower、清 votedFor、重置选举计时器
    }

    if args.PrevLogIndex >= len(n.log) {
        return AppendEntriesReply{Term: n.currentTerm, Success: false}
    }
    if args.PrevLogIndex >= 0 && n.log[args.PrevLogIndex].Term != args.PrevLogTerm {
        return AppendEntriesReply{Term: n.currentTerm, Success: false}
    }

    // 找到共同前缀后，删除 follower 上与 leader 冲突的后缀。
    insert := args.PrevLogIndex + 1
    i := 0
    for ; i < len(args.Entries); i++ {
        pos := insert + i
        if pos >= len(n.log) {
            break
        }
        if n.log[pos].Term != args.Entries[i].Term {
            n.log = n.log[:pos]
            break
        }
    }
    n.log = append(n.log, args.Entries[i:]...)

    if args.LeaderCommit > n.commitIndex {
        lastNewIndex := len(n.log) - 1
        if args.LeaderCommit < lastNewIndex {
            n.commitIndex = args.LeaderCommit
        } else {
            n.commitIndex = lastNewIndex
        }
    }
    return AppendEntriesReply{Term: n.currentTerm, Success: true}
}
```

真实实现还必须补充持久化、锁、快照、快速回退 `nextIndex`、幂等请求、apply 协程、心跳、选举计时器和成员变更。面试中用这段代码说明核心机制即可：follower 只有在前一条日志的 index 和 term 都匹配时才接受新日志，否则拒绝；leader 根据拒绝结果回退 `nextIndex`，直到找到共同前缀。
