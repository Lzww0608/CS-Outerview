# 5. Raft PreVote、持久化状态与 Joint Consensus

## 1. 问题背景

Raft 是一种面向复制状态机的崩溃容错共识协议，核心目标是在节点宕机、重启、网络分区、消息延迟和重复的情况下，让多个副本对同一组日志达成一致。面试里问 “Raft 大论文中的 PreVote 是什么？Raft 需要持久化哪些信息？`voteFor/votedFor` 丢失会怎么样？Joint Consensus 是什么？” 通常不是只考概念，而是在考你是否理解 Raft 的三个关键工程边界：

1. **选举稳定性**：如何避免少数派节点无效自增 term，导致健康 leader 被打断。
2. **崩溃恢复安全性**：哪些状态必须落盘，为什么投票记录不能丢。
3. **成员变更安全性**：集群扩缩容时，如何保证新旧配置不会各自形成独立多数派。

**假设条件**：

1. 这里讨论的是标准 Raft 及工程实现中的常见扩展，故障模型是崩溃故障，不讨论拜占庭作恶。
2. `voteFor` 和 Raft 论文中的 `votedFor` 表示同一含义：当前任期本节点已经投票给哪个 candidate。
3. “Raft 大论文”按 Ongaro 的扩展论文/博士论文语境理解，重点讨论工程化增强，例如 PreVote 和成员变更。
4. 本文以工程实现为目标，会同时说明论文状态和实际系统常见持久化项。

一句话回答：

```text
PreVote 是正式自增 term 前的预投票，目的是减少无效选举打断健康 leader；
Raft 必须持久化 currentTerm、votedFor 和 log，votedFor 丢失可能导致同一 term 重复投票，破坏 Election Safety；
Joint Consensus 是成员变更的两阶段方案，联合配置阶段要求旧多数派和新多数派同时确认，保证配置切换时多数派仍然相交。
```

## 2. 问题现象

没有正确处理这三个点时，Raft 集群会出现一些典型问题。

### 2.1 没有 PreVote 的现象

一个节点处于少数派网络分区，长时间收不到 leader 心跳。它会反复 election timeout，然后：

```text
follower -> candidate
currentTerm++
发送 RequestVote
拿不到多数票
再次超时
currentTerm 再次增加
```

网络恢复后，这个少数派节点可能带着更大的 term 回来。健康 leader 收到更大 term 的请求或响应后，按照 Raft 规则必须退回 follower。结果是：

1. 原 leader 本来在多数派中正常服务，却被无效 term 打断。
2. 集群发生一次不必要的 leader 切换。
3. 写请求短暂不可用。
4. 客户端看到延迟尖刺或重试。

### 2.2 `votedFor` 丢失的现象

节点在 term `T` 已经投票给 candidate A，如果它崩溃重启后丢失了 `votedFor`，就可能在同一个 term `T` 再投票给 candidate B。

这会破坏 Raft 的核心约束：

```text
一个节点在一个 term 内最多投一票。
```

如果多数派交集中的那个节点重复投票，就可能让两个 candidate 都认为自己获得多数票，出现同 term 双 leader 风险。

### 2.3 没有 Joint Consensus 的现象

假设集群从旧配置 `{A,B,C}` 直接切到新配置 `{C,D,E}`。旧配置多数派可能是 `{A,B}`，新配置多数派可能是 `{D,E}`，它们没有交集。

这会导致：

1. 旧配置选出一个 leader。
2. 新配置也选出另一个 leader。
3. 两个 leader 都认为自己有多数派。
4. 两边可能提交不同日志。
5. 状态机安全性被破坏。

## 3. 影响范围

这三个问题分别影响 Raft 的不同模块。

1. **PreVote** 影响 leader election、term 推进、网络分区恢复和可用性。
2. **持久化状态** 影响 crash recovery、投票安全、日志安全和快照恢复。
3. **Joint Consensus** 影响 membership change、扩容缩容、节点替换和配置日志提交。

如果涉及代码实现，可能需要修改的模块包括：

1. `Election`：增加 PreCandidate 状态或 PreVote 流程。
2. `RequestVote` RPC：区分 PreVote 和正式 RequestVote。
3. `HardState` / `StableStore`：持久化 `currentTerm`、`votedFor`、日志和快照元数据。
4. `LogStore`：保证日志 append/fsync 后才能向 leader 返回成功。
5. `ConfigManager`：处理旧配置、新配置、联合配置和配置日志条目。
6. `CommitCalculator`：联合配置期间同时检查 old majority 和 new majority。
7. `SnapshotManager`：快照中保存配置状态和 `lastIncludedIndex/lastIncludedTerm`。
8. `Recovery`：重启后恢复 term、vote、log、snapshot 和 membership config。
9. `TestHarness`：构造网络分区、崩溃恢复、重复投票和成员变更测试。

可能涉及的文件包括：

1. `raft_node.go`、`raft_state.go`、`raft_election.go`。
2. `raft_rpc.proto`、`request_vote.go`、`append_entries.go`。
3. `storage.go`、`wal.go`、`snapshot.go`。
4. `membership.go`、`config_change.go`。
5. `commit_index.go`、`progress_tracker.go`。
6. `raft_recovery_test.go`、`raft_prevote_test.go`、`raft_joint_consensus_test.go`。

## 4. 原因分析

### 4.1 PreVote 解决的根因

Raft 的基本选举规则是：节点 election timeout 后自增 term，转为 candidate，发起 `RequestVote`。这保证了节点最终可以选出 leader，但也带来一个副作用：**不具备当选条件的节点也会推动 term 增长**。

网络分区中的少数派节点没有多数派，不可能当选 leader，但它仍会不断自增 term。term 是 Raft 中判断请求新旧的逻辑时钟，任何节点看到更大的 term 都必须更新 term 并退回 follower。因此少数派节点恢复通信后，会让健康 leader 下台。

PreVote 的根因分析是：

```text
问题不是少数派节点发起选举，而是它在确认自己有机会赢之前就自增了 term。
```

PreVote 把流程改成：

```text
先不增加 term
先问其他节点：如果我以 term+1 参选，你会支持我吗？
拿到多数派预投票后，才真正增加 term 并发起 RequestVote。
```

这样少数派节点拿不到多数派 PreVote，就不会把 term 推高。

### 4.2 `votedFor` 必须持久化的根因

Raft 的 Election Safety 依赖两个条件：

1. 一个节点在一个 term 内最多投一票。
2. 一个合法 leader 必须获得多数派投票。

任意两个多数派一定有交集。如果每个节点每个 term 最多投一票，那么同一个 term 内不可能有两个不同 candidate 都获得多数派，因为两个多数派的交集节点不可能同时投给两个 candidate。

如果 `votedFor` 丢失，交集节点可能重复投票，多数派交集约束就失效了。

示例，5 节点集群 `{A,B,C,D,E}`：

```text
term = 8

A 获得 A、B、C 投票，认为自己当选。
C 崩溃重启，丢失 votedFor。
C 又投给 D。
D 获得 C、D、E 投票，也认为自己当选。
```

两个多数派 `{A,B,C}` 和 `{C,D,E}` 的交集是 `C`。如果 `C` 在同一个 term 投了两票，就可能产生两个 leader。

所以 `currentTerm` 和 `votedFor` 必须在响应 `RequestVote` 前持久化。

### 4.3 Joint Consensus 解决的根因

成员变更不是简单改一个节点列表。Raft 的安全性依赖多数派交集：

```text
任意两个提交多数派必须有交集。
```

如果直接从旧配置切换到新配置，旧多数派和新多数派可能不相交。Joint Consensus 的核心思想是引入过渡配置 `C_old,new`，在过渡阶段提交日志必须同时满足：

```text
旧配置多数派同意
并且
新配置多数派同意
```

这样可以保证：

1. 旧配置的提交和联合配置的提交有交集。
2. 联合配置的提交和新配置的提交有交集。
3. 任意阶段都不会出现两个互不相交的多数派各自提交日志。

## 5. 解决方案

### 5.1 PreVote 实现方案

增加一个预投票阶段：

```text
Follower election timeout
-> PreCandidate
-> 发送 PreVote(term = currentTerm + 1)
-> 获得多数派 PreVote
-> currentTerm++
-> Candidate
-> 发送 RequestVote
-> 获得多数派正式投票
-> Leader
```

PreVote 请求通常携带：

1. `candidateId`。
2. `nextTerm = currentTerm + 1`。
3. `lastLogIndex`。
4. `lastLogTerm`。

节点收到 PreVote 时，判断：

1. candidate 的日志是否至少和自己一样新。
2. 自己是否认为当前 leader 仍有效。
3. 如果 candidate 真以该 term 参选，自己是否愿意投票。

PreVote 不应该立即修改本地 `currentTerm`，否则就失去了避免无效 term 增长的意义。

伪代码：

```go
func (n *Node) onElectionTimeout() {
    if n.preVoteEnabled {
        n.role = PreCandidate
        n.startPreVote(n.currentTerm + 1)
        return
    }
    n.startElection()
}

func (n *Node) startPreVote(nextTerm uint64) {
    req := PreVoteRequest{
        Term:         nextTerm,
        CandidateID:  n.id,
        LastLogIndex: n.log.lastIndex(),
        LastLogTerm:  n.log.lastTerm(),
    }
    n.broadcastPreVote(req)
}

func (n *Node) onPreVoteGrantedMajority() {
    n.startElection()
}

func (n *Node) startElection() {
    n.currentTerm++
    n.votedFor = n.id
    n.persistHardState()
    n.role = Candidate
    n.broadcastRequestVote()
}
```

### 5.2 持久化状态实现方案

Raft 论文中的持久化状态：

| 状态 | 含义 | 为什么必须持久化 |
| --- | --- | --- |
| `currentTerm` | 当前任期 | 防止重启后 term 回退，接受旧 leader 或旧 vote |
| `votedFor` | 当前 term 投给谁 | 防止同一 term 重复投票 |
| `log[]` | 复制日志 | 保证已确认复制的日志不会因重启丢失 |

工程实现还常持久化：

| 状态 | 含义 |
| --- | --- |
| snapshot | 状态机快照 |
| `lastIncludedIndex` | 快照包含的最后日志 index |
| `lastIncludedTerm` | 快照包含的最后日志 term |
| membership config | 当前配置或联合配置 |
| applied index | 状态机已应用到哪里，用于快速恢复 |
| client dedup table | 客户端请求去重信息，防止重放 |

持久化顺序原则：

1. 更新 `currentTerm/votedFor` 后，必须落盘再回复 vote granted。
2. follower append 日志后，必须日志落盘再向 leader 返回 append success。
3. leader 返回客户端写成功前，必须确保日志已提交并应用到状态机。
4. snapshot 写入要原子替换，不能留下半快照。
5. 配置变更日志和普通日志一样复制和提交。

伪代码：

```go
func (n *Node) grantVote(req RequestVoteRequest) RequestVoteReply {
    if req.Term > n.currentTerm {
        n.currentTerm = req.Term
        n.votedFor = None
    }

    if n.canVoteFor(req.CandidateID) && n.isLogUpToDate(req) {
        n.votedFor = req.CandidateID
        n.persistHardState() // 必须先落盘
        return RequestVoteReply{Term: n.currentTerm, VoteGranted: true}
    }

    n.persistHardStateIfTermChanged()
    return RequestVoteReply{Term: n.currentTerm, VoteGranted: false}
}
```

### 5.3 `votedFor` 丢失后的防护

根本解决方式是保证 `votedFor` 不丢：

1. `currentTerm` 和 `votedFor` 放在同一份 HardState。
2. 使用 WAL 或稳定 KV 存储。
3. 更新后 `fsync` 或按实现要求持久化。
4. 持久化成功后才能回复 `VoteGranted=true`。
5. 崩溃恢复时先加载 HardState，再处理任何 RPC。

如果检测到持久化损坏：

1. 不能简单把 `votedFor` 当作空值继续参与投票。
2. 保守做法是节点进入不可服务或 learner/recovering 状态。
3. 从多数派 leader 重新同步日志和元数据。
4. 需要人工修复或数据目录重建。

### 5.4 Joint Consensus 实现方案

成员变更分两阶段：

```text
C_old
-> append config entry C_old,new
-> C_old,new committed
-> append config entry C_new
-> C_new committed
```

联合配置阶段提交规则：

```text
committed(index) =
  replicated_on_majority(C_old, index)
  &&
  replicated_on_majority(C_new, index)
```

示例：

```text
旧配置 C_old = {A, B, C}
新配置 C_new = {A, B, C, D, E}

联合配置 C_old,new 提交要求：
1. {A,B,C} 中至少 2 个节点复制到该日志
2. {A,B,C,D,E} 中至少 3 个节点复制到该日志
```

只有联合配置日志提交后，集群才进入联合配置语义。之后再提交 `C_new` 配置日志，提交规则切换到新配置多数派。

伪代码：

```go
func (c Config) isCommitted(matchIndex map[NodeID]uint64, index uint64) bool {
    if c.IsJoint() {
        return majority(c.Old, matchIndex, index) &&
               majority(c.New, matchIndex, index)
    }
    return majority(c.Voters, matchIndex, index)
}
```

## 6. 可选方案对比

### 6.1 选举优化方案

| 方案 | 原理 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 无 PreVote | 超时后直接自增 term 并 RequestVote | 实现简单 | 少数派会推高 term，打断健康 leader |
| PreVote | 自增 term 前先确认能否获得多数派 | 降低无效选举和 leader 抖动 | 多一轮消息，代码更复杂 |
| CheckQuorum | leader 定期确认仍能联系多数派 | 避免孤立 leader 长期服务 | 需要和 lease/read 语义配合 |
| Leader Lease | leader 在租约内处理读 | 读延迟低 | 对时钟和网络假设更敏感 |

### 6.2 成员变更方案

| 方案 | 原理 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 直接切换配置 | 旧配置直接变新配置 | 实现简单 | 可能出现不相交多数派 |
| Joint Consensus | 先联合配置，再新配置 | 安全性清晰，论文方案 | 实现复杂，两阶段 |
| Single-server change | 一次只增删一个 voting 节点 | 实现更简单，常见于工程实现 | 多节点变更要分多次 |
| Learner 预热后提升 | 新节点先追日志，不投票 | 降低新节点拖慢提交 | 仍要安全切换 voter |

### 6.3 持久化策略对比

| 策略 | 优点 | 风险 |
| --- | --- | --- |
| 每次 vote/log 都 fsync | 安全边界清晰 | 性能较低 |
| WAL 批量刷盘 | 吞吐更高 | 必须确保回复前语义正确 |
| 内存 vote 不落盘 | 快 | 破坏 Election Safety |
| 日志 append 后不落盘就 ack | 快 | follower 崩溃后丢失已确认复制 |

## 7. 推荐方案

推荐工程实现采用：

1. **开启 PreVote**：减少少数派节点无效 term 增长造成的 leader 抖动。
2. **严格持久化 HardState**：`currentTerm` 和 `votedFor` 一起落盘，日志成功落盘后再 ack。
3. **配置变更使用安全协议**：支持 Joint Consensus，或至少使用一次只变更一个 voter 的安全成员变更。
4. **新节点先作为 learner 追日志**：追到足够新后再加入 voting config。
5. **所有配置变更都走日志复制**：成员变更不能绕过 Raft 日志直接改本地配置。
6. **用故障注入测试验证安全性**：重点测崩溃、重启、分区、迟到消息和配置切换。

推荐回答逻辑：

```text
PreVote 解决选举可用性抖动；
HardState 持久化解决崩溃恢复后的安全性；
Joint Consensus 解决成员变更时多数派交集问题。
```

## 8. 实施步骤

### 8.1 增加 PreVote

1. 增加 `PreCandidate` 状态。
2. 增加 `PreVoteRequest/PreVoteResponse` RPC。
3. election timeout 后先进入 PreVote。
4. PreVote 不修改 `currentTerm`，不写 `votedFor`。
5. PreVote 通过多数派后再正式自增 term。
6. PreVote 和 RequestVote 都必须检查日志新旧。
7. 收到合法 leader 心跳时退出 PreVote。

### 8.2 完善持久化

1. 定义 `HardState{currentTerm, votedFor, commit}`，其中 `commit` 是否持久化取决于实现。
2. 定义 `LogStore`，日志条目 append 后必须可恢复。
3. 定义 `SnapshotMeta{lastIncludedIndex,lastIncludedTerm,confState}`。
4. `RequestVote` 投票前更新 HardState 并持久化。
5. `AppendEntries` 成功前持久化日志。
6. 重启时先恢复 snapshot，再恢复 log，再恢复 HardState。
7. 对 WAL 做 checksum，发现损坏进入恢复流程。

### 8.3 实现 Joint Consensus

1. 配置状态支持 `SimpleConfig` 和 `JointConfig`。
2. 成员变更请求先生成 `C_old,new` 日志条目。
3. `C_old,new` 提交后进入联合配置语义。
4. 联合配置阶段提交日志需要 old majority 和 new majority。
5. 再生成 `C_new` 日志条目。
6. `C_new` 提交后退出联合配置。
7. 被移除节点看到自己不在新配置后停止参与 voting。

### 8.4 核心修改逻辑

核心逻辑可以拆成三段：

```text
Election:
  timeout -> PreVote -> RequestVote -> Leader

Persistence:
  update term/vote/log -> persist -> reply success

Membership:
  C_old -> C_old,new -> C_new
  commit rule changes with config state
```

### 8.5 测试重点

如果涉及代码实现，测试重点包括：

1. **少数派 PreVote 测试**：少数派节点超时不能推高多数派 leader 的 term。
2. **网络恢复测试**：分区恢复后健康 leader 不应因无效 term 立刻下台。
3. **日志新旧测试**：日志落后的节点即使 PreVote 也不能获得通过。
4. **`votedFor` 崩溃测试**：投票后立刻崩溃，重启后不能在同 term 投第二票。
5. **日志持久化测试**：AppendEntries ack 后崩溃重启，日志不能丢。
6. **快照恢复测试**：snapshot 后的配置和 last included term/index 正确恢复。
7. **Joint Consensus 提交测试**：联合配置必须满足 old majority 和 new majority。
8. **配置切换测试**：`C_new` 提交前后 commit 规则正确切换。
9. **移除 leader 测试**：leader 被新配置移除后能正确下台。
10. **故障注入测试**：在任意持久化点、配置提交点、RPC 返回点崩溃重启。

## 9. 风险与注意事项

1. **PreVote 不改变 Raft 安全性基础**  
   它主要提升可用性和稳定性，不能替代多数派投票、日志新旧检查和持久化。

2. **PreVote 不能无条件投票**  
   仍要检查 candidate 日志是否足够新，否则会帮助落后节点发起正式选举。

3. **`votedFor` 必须在回复前持久化**  
   先回复再落盘，一旦崩溃就可能同 term 重复投票。

4. **`currentTerm` 不能回退**  
   term 回退会让节点接受旧 leader 或旧请求。

5. **日志 ack 前必须持久化**  
   follower 如果未落盘就返回成功，崩溃后 leader 可能误以为该日志已复制。

6. **commitIndex 论文中是 volatile，不代表工程中不能持久化**  
   工程实现可以持久化 applied index 或 commit index 加速恢复，但安全性不能依赖错误的持久化语义。

7. **Joint Consensus 阶段不要绕过日志复制**  
   配置变更必须作为日志条目提交，否则不同节点可能看到不同配置。

8. **新节点不能一加入就投票拖慢集群**  
   通常先作为 learner 追日志，追到接近 leader 后再变成 voter。

9. **一次变更多个节点风险更高**  
   Joint Consensus 可以支持复杂变更，但排障更难。工程上常倾向逐个 voter 变更。

10. **被移除节点可能仍按旧配置发请求**  
    其他节点必须根据当前配置和 term 处理，不能让旧节点重新影响多数派。

## 10. 验证方式

### 10.1 PreVote 验证

构造 5 节点集群 `{A,B,C,D,E}`：

1. A 是 leader。
2. 隔离 E，让 E 收不到心跳。
3. E 多次 election timeout。
4. 验证 E 只发送 PreVote，不增加持久化 term。
5. 恢复网络。
6. 验证 A 不会因为 E 的无效 term 下台。

### 10.2 `votedFor` 持久化验证

测试流程：

```text
节点 C 在 term=10 投票给 A
在回复 VoteGranted 后立刻崩溃
重启 C
B 在 term=10 请求投票
验证 C 拒绝 B
```

如果 C 投给 B，说明 `votedFor` 没有正确持久化。

### 10.3 日志持久化验证

测试流程：

```text
leader append entry X 到 follower C
C 返回 AppendEntries success
C 立刻崩溃重启
验证 C 仍然有 entry X
```

如果 X 丢失，说明 follower 在日志未持久化前错误 ack。

### 10.4 Joint Consensus 验证

从 `{A,B,C}` 扩容到 `{A,B,C,D,E}`：

1. 提交 `C_old,new`。
2. 隔离旧多数派或新多数派的一部分节点。
3. 验证只有同时满足旧多数派和新多数派时才能提交。
4. 提交 `C_new`。
5. 验证后续日志按新配置多数派提交。
6. 验证旧配置中被移除节点不能单独影响选举。

### 10.5 指标和工具

建议监控：

| 指标 | 含义 |
| --- | --- |
| `leader_changes_total` | leader 切换次数 |
| `prevote_rejected_total` | PreVote 被拒绝次数 |
| `term_increase_total` | term 增长次数 |
| `election_timeout_total` | 选举超时次数 |
| `wal_fsync_latency` | WAL 刷盘延迟 |
| `vote_persist_fail_total` | vote 持久化失败次数 |
| `config_change_duration` | 成员变更耗时 |
| `joint_config_commit_latency` | 联合配置提交延迟 |

故障注入工具应覆盖：

1. RPC 丢包、乱序、重复。
2. 节点崩溃重启。
3. WAL 部分写入。
4. 快照安装中断。
5. 网络分区和恢复。
6. 配置变更过程中 leader 崩溃。

## 11. 总结

PreVote、持久化状态和 Joint Consensus 分别对应 Raft 工程实现中的三个关键问题。

1. **PreVote**：正式选举前先预投票，不自增 term，只有确认可能获得多数派后才发起正式选举。它主要减少少数派分区节点无效自增 term 对健康 leader 的干扰。
2. **持久化状态**：Raft 必须持久化 `currentTerm`、`votedFor` 和 `log[]`。工程实现还会持久化 snapshot、配置和状态机 checkpoint。`votedFor` 丢失会导致同一 term 重复投票，破坏同 term 单 leader 的安全基础。
3. **Joint Consensus**：成员变更不能直接切换配置，而要先进入联合配置 `C_old,new`，提交要求同时满足旧多数派和新多数派，再切到 `C_new`，保证多数派交集不断裂。

面试回答可以这样说：

```text
PreVote 是 Raft 的选举优化。普通 Raft 中 follower 超时会直接自增 term 并发起 RequestVote，少数派分区节点会不断推高 term，网络恢复后可能迫使健康 leader 下台。PreVote 会先不增加 term，询问多数派“如果我以 term+1 参选你会不会投我”，只有拿到多数派预投票后才真正自增 term 发起正式选举，所以它减少的是无效选举和 leader 抖动。

Raft 必须持久化 currentTerm、votedFor 和 log。currentTerm 防止 term 回退，votedFor 防止同一 term 重复投票，log 保证已确认复制的日志崩溃后不丢。votedFor 如果丢失，节点重启后可能在同一个 term 投给另一个 candidate。多数派交集节点如果重复投票，就可能让两个 candidate 都获得多数派，破坏 Election Safety。因此 vote 必须先落盘再回复 VoteGranted。

Joint Consensus 是 Raft 的成员变更方案。直接从旧配置切到新配置可能导致旧多数派和新多数派不相交，出现两个 leader。Joint Consensus 先提交联合配置 C_old,new，在这个阶段日志提交必须同时获得旧配置多数派和新配置多数派；联合配置提交后再提交 C_new。这样配置切换期间多数派始终有交集，不会破坏已提交日志安全性。
```
