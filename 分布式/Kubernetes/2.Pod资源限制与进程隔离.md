# 2. Pod 资源限制与进程隔离

Kubernetes 里的 Pod 本质上是一组共享网络命名空间和存储卷的容器集合。资源限制解决的是“一个节点上多个 Pod 如何共享 CPU、内存、磁盘、设备等资源”的问题；进程隔离解决的是“容器内进程为什么看起来像运行在独立系统里”的问题。

## 1. 只有 1 份资源却有 2 个 Pod 怎么办

如果节点上的某类资源只够 1 个 Pod 使用，不能只依赖业务自觉，应该在调度层和运行时层同时限制。

常见做法：

1. **设置 requests/limits**：`requests` 用于调度阶段预留资源，`limits` 用于运行时约束资源上限。
2. **Guaranteed QoS**：关键 Pod 可以设置 `requests == limits`，让调度和驱逐优先级更可控。
3. **独占节点或资源池**：用 `nodeSelector`、node affinity、taints/tolerations 把 Pod 调度到专用节点。
4. **设备类资源**：GPU、专用网卡等用 Device Plugin 暴露为扩展资源，K8s 会按整数个资源调度，天然避免两个 Pod 同时占用同一设备。
5. **共享外部资源**：数据库迁移、定时任务、单实例消费者这类逻辑独占要用 Lease、分布式锁、Leader Election 或队列分片，不能只靠 Pod 数量。
6. **存储独占**：块存储或单写卷可以用 PVC 的访问模式，如 `ReadWriteOnce`，由存储层限制同一时间写入者。

示例：

```yaml
resources:
  requests:
    cpu: "1"
    memory: "1Gi"
  limits:
    cpu: "1"
    memory: "1Gi"
```

如果一个节点只有 1 核 CPU 可分配，两个都 `requests.cpu=1` 的 Pod 不会同时被调度到这个节点；如果已经运行的 Pod 超过 memory limit，容器会被 cgroup 限制并可能触发 OOM kill。

## 2. requests 与 limits 的区别

1. **requests**：告诉调度器“至少需要多少资源”，调度器用它判断节点能否放下 Pod。
2. **limits**：告诉运行时“最多能用多少资源”，由 cgroup 在节点上强制执行。
3. CPU limit 通常通过 CFS quota 限制 CPU 时间片，超过后会被 throttle。
4. memory limit 是硬上限，超过后可能被 OOM kill。
5. 只设置 limit 不设置 request 时，默认 request 可能等于 limit，也可能由 LimitRange 决定，生产环境要显式配置。

## 3. Docker/容器如何实现进程隔离

容器不是轻量虚拟机，它共享宿主机内核。隔离主要由 Linux 内核能力实现：

| 机制 | 作用 |
| --- | --- |
| PID namespace | 容器内只能看到自己的进程树 |
| Network namespace | 独立网卡、路由表、端口和 iptables 视图 |
| Mount namespace | 独立文件系统挂载视图，配合 overlayfs |
| UTS namespace | 独立 hostname/domainname |
| IPC namespace | 隔离 System V IPC、POSIX 消息队列等 |
| User namespace | 容器内 root 可映射为宿主机普通用户 |
| cgroup | 限制和统计 CPU、内存、IO、pids 等资源 |
| capabilities/seccomp/AppArmor/SELinux | 收缩系统调用和内核权限 |

Docker 创建容器时，会为容器进程设置 namespace 和 cgroup，再通过 overlayfs 组合镜像层和可写层。Kubernetes 通过容器运行时，如 containerd、CRI-O，间接完成这些设置。

## 4. 易错点

1. namespace 负责“看不见”，cgroup 负责“用不超”，两者解决的问题不同。
2. Pod 内多个容器共享同一个 Pod 网络命名空间，所以它们可以通过 `localhost` 互相访问。
3. CPU limit 不是独占 CPU，只是限制可使用的 CPU 时间；要减少抖动可以用绑核、独占节点或 CPU Manager static policy。
4. 内存超过 limit 可能直接 OOM kill，应用要设置合理堆大小和缓存上限。
5. 分布式锁适合逻辑互斥，不适合替代资源调度；资源不足应优先用 requests/limits 和调度约束表达。

## 5. 面试回答模板

如果只有 1 份资源却有 2 个 Pod，我会先区分物理资源和逻辑资源。CPU、内存这类物理资源用 requests 做调度预留，用 limits 通过 cgroup 做运行时限制，必要时用亲和性、污点容忍或独占节点保证只调度一个 Pod；GPU 这类设备用 Device Plugin 暴露为整数资源。数据库任务、定时任务这类逻辑独占则用 Lease、Leader Election 或分布式锁。容器隔离底层靠 namespace 隔离视图，靠 cgroup 限制资源，再配合 capabilities、seccomp 和 LSM 降低权限。
