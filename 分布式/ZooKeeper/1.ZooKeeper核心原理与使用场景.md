# ZooKeeper 核心原理与使用场景

ZooKeeper 是分布式协调服务，提供一致的层次化命名空间、节点监听、临时节点和顺序节点。它常用于服务发现、配置管理、分布式锁、选主和集群元数据管理。

## 1. 数据模型

ZooKeeper 的数据组织类似文件系统：

```text
/services/order/instance-000000001
/services/order/instance-000000002
/config/payment/rate-limit
```

每个节点叫 znode，常见类型：

| znode 类型 | 含义 | 典型用途 |
| --- | --- | --- |
| 持久节点 | 客户端断开后仍存在 | 配置、元数据目录 |
| 临时节点 | 会话断开后自动删除 | 服务实例注册、锁持有者 |
| 顺序节点 | 名字自动追加递增序号 | 分布式锁排队、选主 |
| 临时顺序节点 | 临时 + 顺序 | 公平锁、leader election |

## 2. 一致性和会话

ZooKeeper 集群通过多数派协议保证元数据一致性。写请求需要经过 leader 协调并得到 quorum 确认；读请求可以由 follower 提供，但强一致读场景要注意同步语义。

会话是 ZooKeeper 很重要的抽象：

1. 客户端和集群保持 session。
2. 临时节点绑定 session，而不是绑定某条 TCP 连接。
3. 如果短暂断线后在 session timeout 内重连，临时节点仍保留。
4. 如果 session 过期，临时节点会被删除，其他客户端收到 watch 通知。

## 3. 服务发现

服务提供方启动后在服务目录下创建临时节点：

```text
/services/order/instance-000000001 = 10.0.0.8:8080
```

调用方读取 `/services/order` 子节点列表并设置 watch。实例宕机或网络隔离导致 session 过期后，临时节点被删除，调用方收到通知后刷新本地实例缓存。

工程注意：

1. 客户端不要每次调用都查 ZooKeeper，应本地缓存实例列表。
2. watch 通知是一次性的，收到后要重新注册。
3. 实例摘除存在 session timeout 延迟，调用方仍要有超时、重试和熔断。
4. 服务下线最好先主动注销或置为不可接流量，再做连接 drain。

## 4. 分布式锁和选主

分布式锁常用临时顺序节点实现：

1. 所有客户端在 `/locks/job` 下创建临时顺序节点。
2. 序号最小的客户端获得锁。
3. 其他客户端只 watch 自己前一个节点。
4. 持锁客户端释放锁或 session 过期后，后继节点收到通知竞争锁。

这样比所有等待者 watch 同一个节点更好，可以避免锁释放时大量客户端同时被唤醒。

选主也类似，序号最小或特定临时节点创建成功者成为 leader；leader session 失效后，其他候选者重新选举。

## 5. 易错点

1. ZooKeeper 适合协调元数据，不适合存放大对象或高频业务数据。
2. watch 不是消息队列，不能承诺每次业务事件都像 MQ 一样持久投递。
3. 临时节点跟 session 生命周期绑定，不是跟进程 PID 直接绑定。
4. session timeout 太短容易误判，太长会延迟故障摘除。
5. ZooKeeper 可用于一致性协调，但不能替代数据库事务或业务幂等。

## 6. 面试回答模板

ZooKeeper 是分布式协调服务，提供 znode、watch、临时节点、顺序节点和多数派一致性。服务发现里，服务实例创建临时节点，调用方 watch 服务目录并维护本地缓存；实例宕机后 session 过期，临时节点删除，调用方刷新列表。分布式锁通常用临时顺序节点，序号最小者持锁，其他客户端 watch 前驱节点，避免惊群。它适合做元数据协调、选主、锁和配置，不适合放大数据量、高吞吐业务数据。
