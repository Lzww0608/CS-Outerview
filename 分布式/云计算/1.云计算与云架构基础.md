# 1. 云计算与云架构基础

云计算是把计算、存储、网络、安全和平台能力以服务化方式提供出来，让业务可以按需申请、弹性扩缩容、按量计费，并通过自动化运维降低交付成本。面试里问“对云计算和云架构了解多少”，重点不是背厂商产品名，而是讲清资源模型、架构组件和高可用设计。

## 1. 云计算服务模型

常见服务模型：

| 模型 | 提供什么 | 使用者关注什么 | 例子 |
| --- | --- | --- | --- |
| IaaS | 虚拟机、磁盘、VPC、负载均衡 | 操作系统、运行时、中间件 | ECS/EC2、云硬盘、VPC |
| PaaS | 托管运行平台和中间件 | 应用代码、配置、容量 | RDS、Redis、Kubernetes、消息队列 |
| SaaS | 完整软件服务 | 账号、权限、业务配置 | 企业邮箱、CRM、在线协作 |
| FaaS/Serverless | 函数运行环境和事件触发 | 函数逻辑、触发器、冷启动 | 云函数、OpenFaaS |

真实项目通常混合使用：核心服务跑在 Kubernetes 或虚拟机上，数据库用托管 RDS，静态资源放对象存储和 CDN，异步任务用 MQ，边缘流量走负载均衡和 API 网关。

## 2. 云架构的基础组件

一个典型云上后端架构可以拆成：

```text
DNS / CDN / WAF
  -> L4/L7 Load Balancer
  -> API Gateway / Ingress
  -> Service / Pod / VM
  -> Cache / MQ / Database / Object Storage
  -> Logging / Metrics / Trace / Alert
```

核心组件：

1. **计算**：虚拟机、容器、Kubernetes、Serverless，负责承载业务进程。
2. **网络**：VPC、子网、路由表、安全组、NAT 网关、负载均衡，负责隔离和流量调度。
3. **存储**：云盘、对象存储、文件存储，分别适合块设备、海量对象和共享文件。
4. **数据库和中间件**：RDS、Redis、Kafka、ElasticSearch 等托管服务降低自运维成本。
5. **安全**：IAM、KMS、证书、WAF、安全组、密钥管理和审计。
6. **可观测性**：日志、指标、链路追踪、告警和审计，用来定位故障和容量瓶颈。
7. **自动化交付**：镜像仓库、CI/CD、IaC、灰度发布和回滚。

## 3. 高可用和弹性设计

云架构的核心能力是把故障域拆开，并让系统能自动扩缩。

常见设计：

1. **多可用区部署**：业务实例、负载均衡、数据库副本跨 AZ，避免单机房故障。
2. **无状态服务水平扩展**：会话放 Redis/JWT/数据库，实例可以随时扩缩容和替换。
3. **健康检查和自动摘流**：实例异常时从负载均衡或服务发现中摘除。
4. **自动扩缩容**：按 CPU、内存、QPS、队列积压、P95 延迟或自定义指标扩容。
5. **数据备份和容灾**：数据库备份、binlog/PITR、跨地域灾备、定期恢复演练。
6. **限流降级**：流量超过容量时优先保护核心链路，非核心功能返回降级结果。
7. **灰度和回滚**：发布时小流量验证，发现错误快速回滚镜像、配置或流量权重。

高可用不是只“多部署几台机器”。如果所有实例依赖同一个单点数据库、同一个配置中心或同一个 NAT 网关，仍然可能被单点拖垮。

## 4. 云原生和传统部署的区别

云原生强调容器化、动态调度、声明式配置、弹性伸缩和可观测性。

| 对比项 | 传统部署 | 云原生部署 |
| --- | --- | --- |
| 交付单位 | 机器或进程包 | 容器镜像 |
| 扩容方式 | 手工加机器、改配置 | HPA/弹性伸缩 |
| 服务发现 | 静态配置或注册中心 | Kubernetes Service、DNS、注册中心 |
| 配置管理 | 本地文件、人工修改 | ConfigMap、Secret、配置中心 |
| 故障恢复 | 人工重启或脚本 | 控制器自动拉起、健康检查 |
| 发布 | 全量发布 | 滚动、蓝绿、金丝雀 |

云原生不是必须上 Kubernetes。业务规模小、团队运维能力有限时，托管 PaaS 或简单虚拟机也可能更合适。架构选型要看规模、稳定性要求、团队能力和成本。

## 5. 易错点

1. 云计算不等于“服务器在别人机房”，它还包括弹性、自动化、托管服务、计费和安全边界。
2. 多副本不等于高可用，副本要跨故障域，并且流量、数据和配置都要能切换。
3. 使用托管数据库不代表不用做备份、慢 SQL、容量、连接数和权限治理。
4. Serverless 适合事件驱动和弹性波动任务，但要注意冷启动、状态外置、执行时长和可观测性。
5. 上云后网络边界更复杂，安全组、IAM、密钥、公网暴露和审计都要纳入设计。

## 6. 真实场景

一个中小型 AI 应用可以这样上云：

1. 前端静态资源放对象存储和 CDN。
2. API 服务容器化部署在 Kubernetes，入口用 Ingress/API Gateway。
3. RAG 检索服务和模型调用服务拆分，分别设置超时、限流和熔断。
4. 文档原文放对象存储，元数据放 RDS，向量索引用托管向量库或自建 Milvus。
5. 异步入库链路使用 MQ，解析、embedding、索引写入由 worker 消费。
6. 监控 QPS、P99、错误率、模型 token 成本、向量库 Recall@K 和队列积压。
7. 核心服务跨可用区部署，数据库开启备份和只读副本，发布使用灰度流量。

## 7. 面试回答模板

云计算可以理解为把计算、存储、网络、安全和中间件服务化，业务按需申请、弹性扩缩容、按量计费。IaaS 提供虚拟机、云盘、VPC，PaaS 提供托管数据库、Kubernetes、MQ，SaaS 是完整软件服务，Serverless 则把实例管理进一步交给平台。云架构里我会关注入口层的 DNS/CDN/WAF/LB，计算层的 VM/容器/K8s，数据层的 RDS/Redis/MQ/对象存储，以及 IAM、安全组、日志、指标、trace 和 CI/CD。高可用要跨可用区、多副本、健康检查、自动扩缩容、备份恢复、限流降级和灰度回滚一起设计，而不是简单把服务多起几个实例。
