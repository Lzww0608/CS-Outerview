# 2. 四层与七层负载均衡

负载均衡的目标是把请求分发到多个后端实例，提升吞吐、可用性和扩展能力。面试里常问四层和七层的区别，本质是转发决策发生在不同协议层。

## 1. 四层负载均衡

四层负载均衡工作在传输层，主要依据源/目的 IP、端口、协议和连接状态转发 TCP/UDP 流量。它通常不理解 HTTP 路径、Header、Cookie 等应用层语义。

核心特点：

1. 性能高，转发路径短，适合作为入口接入层或大流量 TCP/UDP 服务。
2. 对应用协议侵入小，适合 MySQL、Redis、游戏长连接、RPC 长连接等场景。
3. 只能按连接或五元组调度，很难直接做 URL 路由、灰度 Header 路由和应用层鉴权。
4. 后端健康检查通常是端口级或简单协议级检查，无法完整判断业务是否可用。

常见实现包括 LVS、云厂商 NLB、F5 四层模式、iptables/ipvs、Envoy/HAProxy 的 TCP proxy 模式。

## 2. 七层负载均衡

七层负载均衡工作在应用层，会解析 HTTP、HTTPS、gRPC 等协议，再根据域名、路径、Header、Cookie、方法、用户标签或流量比例选择后端。

核心特点：

1. 能做精细路由，例如 `/api/order` 到订单服务，`/api/user` 到用户服务。
2. 能做灰度发布、A/B 实验、鉴权、限流、WAF、压缩、缓存、TLS 终止和观测埋点。
3. 需要解析协议，性能和延迟开销高于纯四层转发。
4. HTTPS 场景如果要基于路径或 Header 路由，通常需要在七层终止 TLS；如果只做 SNI 路由，也可以不解密业务内容。

常见实现包括 Nginx、HAProxy、Envoy、Traefik、API Gateway、Kubernetes Ingress Gateway。

## 3. 使用场景对比

| 维度 | 四层负载均衡 | 七层负载均衡 |
| --- | --- | --- |
| 转发依据 | IP、端口、协议、连接 | Host、Path、Header、Cookie、Body 元信息 |
| 性能 | 更高 | 略低但功能更强 |
| 协议感知 | 不理解应用协议 | 理解 HTTP/gRPC 等协议 |
| 典型场景 | TCP 长连接、数据库代理、游戏网关、入口大流量 | Web 网关、微服务路由、灰度、鉴权、WAF |
| 健康检查 | 端口或简单协议 | 可做业务探针 |

## 4. 为什么七层更常见

互联网 Web 和微服务系统流量大多是 HTTP/HTTPS/gRPC。七层负载均衡可以把路由、鉴权、限流、观测和灰度统一沉淀到网关层，业务服务只关注核心逻辑，因此工程收益很高。

但七层不是四层的替代品。真实架构常常是：

```text
DNS/GSLB -> 四层 LB -> 七层网关/Ingress -> 业务服务
```

四层负责高性能接入和故障域切换，七层负责应用语义治理。长连接、非 HTTP 协议或极致性能场景仍然会优先考虑四层。

## 5. 易错点

1. 四层不等于“不维护状态”。TCP 四层转发仍要处理连接跟踪、会话保持或 NAT 映射。
2. 七层终止 TLS 后，网关要保护证书和私钥，并处理后端链路是否再次加密。
3. 长连接场景不能只按请求数均衡，连接建立后的流量可能严重不均。
4. 负载均衡不能替代限流和熔断，后端整体过载时还需要拒绝、排队、降级或削峰。
5. 健康检查只检查端口可能误判，业务依赖数据库、缓存、线程池时应提供 readiness 探针。

## 6. 面试回答模板

四层负载均衡按 IP、端口和连接转发，性能高、协议无关，适合 TCP 长连接、数据库代理和大流量入口；七层负载均衡会解析 HTTP/gRPC 等应用协议，可以按域名、路径、Header、Cookie 做路由，也能承载鉴权、限流、灰度、WAF 和观测。Web 和微服务里七层更流行，是因为应用治理能力强；但生产架构常常四层和七层组合使用，四层做高性能接入，七层做业务语义路由。
