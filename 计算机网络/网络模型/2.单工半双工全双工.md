# 2. 单工、半双工与全双工

单工、半双工和全双工描述的是通信双方在同一条通信链路上的发送和接收能力，关注点是方向和是否能同时传输。

## 1. 三种模式

| 模式 | 定义 | 例子 |
| --- | --- | --- |
| 单工 | 数据只能单向传输 | 广播电视、传感器单向上报 |
| 半双工 | 双方都能发送和接收，但同一时刻只能一个方向传输 | 对讲机、早期共享介质网络 |
| 全双工 | 双方可以同时发送和接收 | 电话、现代交换式以太网、TCP 连接 |

单工强调“只有一个方向”，半双工强调“能双向但不能同时”，全双工强调“能双向且能同时”。

## 2. 和 TCP/UDP 的关系

TCP 连接是全双工字节流。连接建立后，两端都可以同时发送数据，也都可以分别关闭自己的发送方向，所以 TCP 断开连接需要四次挥手：一端发送 FIN 只表示“我不再发送”，并不表示对端也不能继续发送。

UDP 本身是无连接报文协议，不维护全双工连接状态，但在应用层上两个端点可以互相发送 UDP 报文。它更像“每个报文独立发送”，是否双向取决于应用协议如何设计。

## 3. 为什么面试会问 ACK

TCP 报文头里的 ACK 标志位表示确认号字段有效。连接建立后的绝大多数 TCP 报文都会带 ACK，因为 TCP 是可靠传输协议，需要通过确认号告诉对方“我已经收到了哪些字节，下一个期望收到哪个字节”。

三次握手中：

1. 第一次 SYN：客户端还没有收到服务器数据，所以通常只有 SYN。
2. 第二次 SYN + ACK：服务器确认客户端 SYN，同时发送自己的 SYN。
3. 第三次 ACK：客户端确认服务器 SYN，连接进入 ESTABLISHED。

这也是全双工连接建立的体现：双方都要证明自己的发送和接收能力正常。

## 4. 易错点

1. 全双工不是“不会阻塞”，它只表示方向上可以同时收发。
2. TCP 是全双工，但应用协议可以设计成请求-响应式，看起来像一问一答。
3. 半双工需要冲突检测或介质访问控制，否则双方同时发送会互相干扰。
4. UDP 没有连接状态，不能说“UDP 连接是全双工”，只能说应用双方可以互发报文。

## 5. 真实场景

1. WebSocket 基于 TCP，可以在一个连接上全双工传输消息，适合在线协作、游戏同步、实时推送。
2. HTTP/1.1 常见使用方式是请求-响应，但底层 TCP 仍然是全双工。
3. 游戏语音、视频会议需要双向实时传输，应用层会关注全双工能力、延迟和丢包恢复。
