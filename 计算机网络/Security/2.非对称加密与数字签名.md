# 2. 非对称加密与数字签名

非对称密码使用一对密钥：公钥可以公开，私钥必须保密。它既可以用于加密/解密，也可以用于数字签名/验签，但这两类用途的方向和目标不同。

## 1. 非对称加密流程

加密解决的是“只有目标接收方能看懂”：

```text
发送方使用接收方公钥加密明文
-> 网络传输密文
-> 接收方使用自己的私钥解密
```

特点：

1. 公钥可以公开分发，私钥不能泄露。
2. 非对称加密计算成本高，不适合直接加密大量数据。
3. 工程上通常用它做密钥交换或加密一个小的会话密钥，再用对称加密传输正文。

现代 TLS 1.3 中，应用数据主要用 AES-GCM 或 ChaCha20-Poly1305 这类对称加密；服务端证书私钥主要用于签名证明身份，密钥交换则使用临时 ECDHE/DHE。

## 2. 数字签名流程

签名解决的是“证明消息来自私钥持有者，并且没有被篡改”：

```text
发送方对消息计算摘要 hash
-> 使用私钥对摘要或签名输入进行签名
-> 接收方用发送方公钥验证签名
-> 验证通过说明消息和身份可信
```

签名通常不直接对整段大消息做私钥运算，而是对消息摘要或协议规定的 transcript 做签名。原因是摘要长度固定、效率更高，也能把完整上下文绑定进签名。

## 3. RSA、DSA、ECDSA

| 算法 | 数学基础 | 常见用途 | 注意事项 |
| --- | --- | --- | --- |
| RSA | 大整数因子分解困难 | 加密、签名、证书体系 | 密钥更长，签名/验签成本和填充模式要关注 |
| DSA | 有限域离散对数困难 | 数字签名 | 只用于签名，随机数质量非常关键 |
| ECDSA | 椭圆曲线离散对数困难 | 数字签名、证书 | 同等安全强度下密钥更短，随机数泄露会暴露私钥 |

ECDSA/DSA 都依赖每次签名的随机数 `k`。如果 `k` 重复、可预测或泄露，攻击者可能反推出私钥。工程上常用确定性 ECDSA（如 RFC 6979 思路）或高质量 CSPRNG 降低风险。

## 4. 易错点

1. “私钥加密、公钥解密”不是现代签名的严谨表述。更准确说法是：私钥生成签名，公钥验证签名。
2. 加密保证机密性，签名保证身份认证、完整性和不可否认性，目标不同。
3. HTTPS 不是用 RSA 加密全部 HTTP 数据，正文主要是对称加密。
4. 证书绑定的是域名、主体和公钥，证书链可信不代表业务逻辑一定安全。
5. 旧算法或弱参数会降低安全性，例如 SHA1、过短 RSA 密钥、不安全随机数。

## 5. 真实场景

1. **HTTPS 证书**：CA 对服务器证书签名，客户端用 CA 公钥验证证书链；服务器用证书私钥签名握手上下文证明自己持有私钥。
2. **软件包发布**：发布方对安装包或摘要签名，用户或包管理器验签，防止镜像源篡改。
3. **接口鉴权**：客户端用私钥对请求时间戳、路径、body hash 签名，服务端用公钥验证，防止伪造和篡改。
4. **区块链交易**：账户私钥对交易签名，网络节点用公钥或地址恢复/验证交易发起者。

## 6. 网络传输安全怎么设计

如果面试问“网络编程中如何保证数据传输安全”，可以按目标拆开：

1. **机密性**：防止中间人看到明文，通常用 TLS，业务数据走 AES-GCM、ChaCha20-Poly1305 等对称加密。
2. **完整性**：防止数据被篡改，TLS 记录层使用 AEAD；自定义协议至少要有 HMAC 或签名。
3. **身份认证**：服务端证书证明域名和公钥绑定；高安全场景可以做双向 TLS。
4. **防重放**：请求带时间戳、nonce、序列号或一次性 token，服务端校验窗口和去重。
5. **密钥更新**：会话密钥要定期协商或轮换，避免长期使用同一密钥。
6. **降级防护**：禁止弱协议、弱加密套件和明文回退。

自研“加密协议”风险很高。真实项目里优先使用 TLS/QUIC、成熟密码库和标准算法；如果必须在应用层签名，要把 method、path、query、body hash、timestamp、nonce 都纳入签名输入，避免只签部分字段导致绕过。

## 7. 面试回答模板

非对称密码有公钥和私钥。加密场景下，发送方用接收方公钥加密，接收方用私钥解密，目标是机密性；数字签名场景下，发送方用私钥对消息摘要或协议上下文签名，接收方用公钥验签，目标是身份认证和完整性。RSA 基于大数分解，DSA 基于离散对数，ECDSA 基于椭圆曲线离散对数；同等安全强度下 ECDSA 密钥更短，但对随机数质量非常敏感。真实系统里通常用非对称算法做认证和密钥协商，用对称算法加密大量数据。
