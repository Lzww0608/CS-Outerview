# 3. 端到端密钥协商方案

端到端密钥方案的目标是：通信两端协商出只有彼此知道的会话密钥，中间信令服务器、转发节点或网络设备只能转发密文，不能解密业务内容。可以借鉴 TLS 1.3 的思路：临时密钥交换、身份认证、握手 transcript、HKDF 派生和 AEAD 加密。

## 1. 设计目标

1. **机密性**：中间节点看不到明文。
2. **完整性**：消息被篡改时能被发现。
3. **身份认证**：确认对端确实是目标用户、设备或服务。
4. **前向保密**：长期身份私钥泄露后，历史会话仍尽量安全。
5. **防重放**：旧握手包或旧业务包不能被重复利用。
6. **密钥轮换**：长连接要定期更新密钥，降低单个密钥暴露影响。

## 2. 核心材料

每个端持有两类密钥：

1. **长期身份密钥**：例如设备证书、用户身份公私钥、服务端证书，用于签名和身份绑定。
2. **临时 ECDHE 密钥**：每次会话临时生成，用于协商共享秘密，完成后销毁私钥。

服务器可以作为信令服务，负责转发双方公钥、证书和握手消息，但不应该拿到 ECDHE 私钥或派生后的业务会话密钥。

## 3. 握手流程

简化流程：

```text
A -> Server -> B: A_id, A_eph_pub, nonce_a, supported_algorithms
B -> Server -> A: B_id, B_eph_pub, nonce_b, selected_algorithm, B_signature
A -> Server -> B: A_signature, finished_a
B -> Server -> A: finished_b
```

关键点：

1. A 和 B 分别生成临时 ECDHE 密钥对。
2. 双方交换临时公钥、随机数、协议版本和算法列表。
3. 双方用自己的临时私钥和对端临时公钥计算共享秘密。
4. 使用 HKDF 从共享秘密和握手 transcript 派生会话密钥。
5. 双方用长期身份私钥签名握手 transcript，证明身份并防止中间人替换公钥。
6. `finished` 消息用握手密钥计算 MAC，确认双方看到的握手内容一致。

签名内容必须覆盖双方身份、临时公钥、随机数、算法选择和会话上下文：

```text
signature_input = hash(
  protocol_version ||
  A_id || B_id ||
  A_eph_pub || B_eph_pub ||
  nonce_a || nonce_b ||
  selected_algorithm ||
  session_id
)
```

如果只签名自己的公钥，而不签名完整上下文，中间人可能通过替换身份、降级算法或复用旧消息绕过校验。

## 4. 密钥派生

不要直接把 ECDHE 输出当业务密钥。应使用 HKDF 派生不同用途的密钥：

```text
shared_secret = ECDHE(self_eph_priv, peer_eph_pub)
handshake_secret = HKDF-Extract(salt, shared_secret)

client_write_key = HKDF-Expand(handshake_secret, "client app key" || transcript)
server_write_key = HKDF-Expand(handshake_secret, "server app key" || transcript)
client_nonce_key = HKDF-Expand(handshake_secret, "client nonce" || transcript)
server_nonce_key = HKDF-Expand(handshake_secret, "server nonce" || transcript)
```

不同方向使用不同 key，可以降低 nonce 复用和密钥混用风险。业务数据建议使用 AEAD，例如 AES-GCM 或 ChaCha20-Poly1305，同时把协议头、序号、消息类型作为 AAD 参与认证。

## 5. 业务消息格式

一个简化消息头：

```text
version | session_id | direction | seq | msg_type | ciphertext | tag
```

设计要点：

1. `seq` 单调递增，用于构造 nonce 和防重放。
2. 接收方维护已接收窗口，拒绝重复序号和过旧序号。
3. `msg_type`、`session_id`、`seq` 放入 AEAD 的 AAD，防止头部被篡改。
4. 长连接达到一定包数或时间后重新 ECDHE 或派生新 key。
5. 握手失败、验签失败、MAC 校验失败都要关闭会话并记录安全日志。

## 6. 和 TLS 的关系

真实工程优先直接使用 TLS 1.3、QUIC 或 WebRTC DataChannel，而不是自研密码协议。只有在业务确实需要“服务器只能转发，不能解密”的端到端加密时，才在应用层再做 E2E 密钥协商。

可借鉴 TLS 的部分：

1. 临时 ECDHE 提供前向保密。
2. transcript hash 防止握手消息被篡改。
3. HKDF 分层派生不同用途的密钥。
4. AEAD 同时保证机密性和完整性。
5. Finished 消息确认双方握手视图一致。

不能照搬或忽略的部分：

1. 身份体系要和业务账号、设备、公钥注册、证书吊销结合。
2. P2P 场景还要处理 NAT 穿透、信令服务器可信边界和设备换端。
3. 多设备登录要有设备级身份密钥，而不是只用账号密码。
4. 群聊或多端同步需要群组密钥管理、成员变更和历史消息访问策略。

## 7. 易错点

1. 只用公钥加密一个随机数不等于完整安全握手，缺少身份认证会被中间人攻击。
2. 长期私钥直接参与会话密钥生成会削弱前向保密。
3. nonce 不能在同一个 AEAD key 下重复。
4. 0-RTT 或会话恢复要特别处理重放，非幂等业务不要允许早期数据。
5. 自研协议必须做版本号、算法协商和降级防护。
6. 密钥、明文和崩溃 dump 要避免落日志或长期留在内存。

## 8. 面试回答模板

我会借鉴 TLS 1.3 设计端到端密钥方案。双方先各自生成临时 ECDHE 密钥并通过信令服务器交换临时公钥、随机数和算法列表；然后用 ECDHE 得到共享秘密，用 HKDF 结合握手 transcript 派生不同方向的加密密钥和 nonce key；再用双方长期身份私钥对完整握手上下文签名，防止中间人替换公钥或降级算法。业务消息用 AES-GCM 或 ChaCha20-Poly1305 这类 AEAD，加上 session id、方向、序号和消息类型做 AAD，接收方用序号窗口防重放。真实项目优先用 TLS/QUIC/WebRTC，只有服务器不能解密业务内容时才在应用层额外做 E2E。
