# TIME_WAIT 与 CLOSE_WAIT

`TIME_WAIT` 和 `CLOSE_WAIT` 都是 TCP 关闭阶段常见状态，但含义完全不同。`TIME_WAIT` 通常说明本端主动关闭连接并等待 2MSL；`CLOSE_WAIT` 通常说明对端已经发来 `FIN`，本端应用还没有关闭 socket。

## 1. TIME_WAIT

主动关闭方发送最后一个 `ACK` 后会进入 `TIME_WAIT`，等待 2MSL 后才真正释放连接。

作用：

1. **保证最后一个 ACK 可重传**：如果对端没有收到最后 ACK，会重发 `FIN`，本端仍能再次回复 ACK。
2. **让旧连接报文自然消失**：避免相同四元组的新连接收到旧连接中滞留的报文段。

大量 `TIME_WAIT` 的常见原因：

1. 服务端主动关闭短连接，例如 HTTP 短连接或服务端超时踢连接。
2. 没有使用连接池、长连接或 keep-alive，连接创建和销毁过于频繁。
3. 反向代理、网关、RPC 客户端作为主动关闭方，短时间打出大量连接。
4. 下游处理慢或超时策略过短，导致上游频繁主动断开。

影响：

1. 占用一定内核连接状态和内存。
2. 对客户端或代理来说，可能消耗本地临时端口，导致无法继续建立到同一目标的连接。
3. 一般不会长期占用应用层 fd，因为 socket 已经关闭，主要是内核协议栈状态。

优化方式：

1. 优先使用连接池、HTTP keep-alive、RPC 长连接。
2. 让真正发起短连接的一侧承担主动关闭，避免核心服务端堆积大量 `TIME_WAIT`。
3. 调大临时端口范围，例如 `net.ipv4.ip_local_port_range`。
4. 客户端场景可谨慎评估 `tcp_tw_reuse`，不要把它当成服务端通用解法。
5. 不建议使用已经废弃且有 NAT 风险的 `tcp_tw_recycle`。

## 2. CLOSE_WAIT

被动关闭方收到对端 `FIN` 后，内核回复 ACK，并把连接交给应用处理。此时连接进入 `CLOSE_WAIT`，等待应用调用 `close()`。

大量 `CLOSE_WAIT` 的常见原因：

1. 应用读到 EOF 后没有关闭 socket。
2. 连接对象引用泄漏，生命周期没有释放。
3. 线程池阻塞、业务卡住，导致关闭逻辑没有执行。
4. 异常分支漏掉 `close()`，例如解析失败、鉴权失败、超时返回。
5. 代码只关闭输入流或包装对象，没有真正关闭底层 fd。

影响：

1. 占用应用 fd，可能触发 `too many open files`。
2. 占用连接对象、缓冲区和业务上下文内存。
3. 长期堆积通常说明应用层有 bug，而不是内核参数问题。

解决方式：

1. 确认所有异常路径都释放连接，C++ 中优先使用 RAII 管理 fd。
2. 读到 `read == 0` 后及时关闭 socket。
3. 给连接设置读写超时、空闲超时和最大生命周期。
4. 监控 `CLOSE_WAIT` 数量、fd 数量、线程池队列和业务耗时。
5. 抓包和日志结合，定位对端关闭后本端哪段业务没有释放资源。

## 3. 面试回答模板

`TIME_WAIT` 是主动关闭方等待 2MSL 的状态，主要是为了重传最后 ACK 和避免旧报文污染新连接。大量 `TIME_WAIT` 常见于短连接和主动关闭过多，优先用连接池、长连接、keep-alive 和端口范围调优解决。`CLOSE_WAIT` 是被动关闭方收到 FIN 后等待应用 close 的状态，大量出现通常是应用没有正确关闭 socket，应该从资源生命周期、异常分支、超时和 RAII 入手排查。
