# 11.TCP 保活、应用心跳与 Nagle 算法

## 1. TCP Keepalive 是什么

TCP Keepalive 是内核提供的连接探测机制。连接长时间空闲后，内核发送探测包，判断对端是否仍然可达。如果多次探测失败，连接会被内核判定异常。

特点：

1. 工作在 TCP 层，由内核管理。
2. 默认探测时间通常很长，Linux 默认常见是小时级，不适合业务秒级故障检测。
3. 只能判断 TCP 连接是否大致可达，不能判断对端应用是否健康。
4. 可以通过 `SO_KEEPALIVE` 和 `TCP_KEEPIDLE/TCP_KEEPINTVL/TCP_KEEPCNT` 调整。

## 2. 为什么有 TCP 保活还要应用心跳

应用心跳是业务协议自己定义的 ping/pong、heartbeat 或空消息。它解决的问题比 TCP Keepalive 更贴近业务。

需要应用心跳的原因：

1. **检测更快**：业务可以按 5s、10s、30s 等粒度检测，而不是等内核默认小时级探测。
2. **检测应用存活**：TCP 通不代表对端业务线程、事件循环或依赖服务正常。
3. **穿透中间设备超时**：NAT、负载均衡、防火墙会清理空闲连接，心跳可以刷新连接活跃时间。
4. **携带业务状态**：心跳可以带版本、负载、订阅状态、客户端时间等信息。
5. **统一跨协议行为**：WebSocket、RPC、IM、游戏长连接通常都需要业务层断线重连和会话恢复。

常见设计：

```text
client -> ping(seq, timestamp)
server -> pong(seq, timestamp)
```

如果连续 N 次未收到 pong，就认为连接不可用，关闭并重连。心跳间隔要小于中间设备空闲超时，也不能过小，否则会造成无意义流量和唤醒。

## 3. Nagle 算法是什么

Nagle 算法用于减少小包数量。它的核心思想是：当连接上还有未确认的小数据包时，后续小数据先攒起来，等收到 ACK 或攒到足够大再发送。

优点：

1. 减少小包数量，降低网络和协议栈开销。
2. 对 telnet 这类小字节交互和低带宽网络有历史意义。

问题：

1. 对低延迟小消息场景，Nagle 可能引入等待 ACK 的延迟。
2. 和延迟确认 Delayed ACK 叠加时，可能出现明显的几十毫秒级延迟。
3. RPC、游戏、IM、实时控制这类小包低延迟业务通常不希望攒包。

关闭方式：

```cpp
int on = 1;
setsockopt(fd, IPPROTO_TCP, TCP_NODELAY, &on, sizeof(on));
```

## 4. TCP_NODELAY 和 TCP_CORK

1. `TCP_NODELAY`：关闭 Nagle，尽快发送小包，适合低延迟交互。
2. `TCP_CORK`：尽量攒包，适合先写 header 再写 body，希望组合成更完整报文的场景。
3. 两者目标相反，不能只背“优化性能”，要看业务是追求低延迟还是高吞吐。

## 5. 易错点

1. TCP Keepalive 不等于应用心跳，前者是连接探测，后者是业务健康和会话保活。
2. 心跳不是越频繁越好，移动端和大规模长连接会被心跳流量、耗电和唤醒影响。
3. 开启 `TCP_NODELAY` 可能增加小包数量，不一定提高整体吞吐。
4. 如果应用自己做批量和缓冲，是否关闭 Nagle 要结合实际抓包和延迟指标判断。

## 6. 面试回答模板

TCP Keepalive 是内核层的空闲连接探测，默认时间通常很长，只能说明连接在 TCP 层大致可达。应用心跳是业务协议的一部分，可以更快发现断线、检测应用层是否健康、刷新 NAT/负载均衡空闲超时，并携带业务状态。Nagle 算法用于合并小包，减少网络开销，但会增加小消息延迟；低延迟 RPC、游戏、IM 常通过 `TCP_NODELAY` 关闭它，而文件传输或批量发送更关注吞吐和包聚合。
