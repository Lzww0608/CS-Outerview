# 11.TCP 保活、应用心跳与 Nagle 算法

## 1. TCP Keepalive 是什么

TCP Keepalive 是内核提供的连接探测机制。连接长时间空闲后，内核发送探测包，判断对端是否仍然可达。如果多次探测失败，连接会被内核判定异常。

特点：

1. 工作在 TCP 层，由内核管理。
2. 默认探测时间通常很长，Linux 默认常见是小时级，不适合业务秒级故障检测。
3. 只能判断 TCP 连接是否大致可达，不能判断对端应用是否健康。
4. 可以通过 `SO_KEEPALIVE` 和 `TCP_KEEPIDLE/TCP_KEEPINTVL/TCP_KEEPCNT` 调整。

## 1.1 HTTP Keep-Alive 和 TCP Keepalive 的区别

这两个名字很像，但解决的问题不在同一层。

| 对比项 | HTTP Keep-Alive | TCP Keepalive |
| --- | --- | --- |
| 所在层次 | 应用层 HTTP 连接复用策略 | 传输层 TCP 空闲探测机制 |
| 核心目的 | 复用同一条 TCP/TLS 连接发送多个请求，减少重复握手 | 探测长时间空闲的 TCP 连接是否还可达 |
| 是否携带业务语义 | 有 HTTP 请求响应语义和连接池策略 | 没有业务语义，只是内核探测 |
| 触发方式 | 客户端、服务端、代理根据 HTTP 版本、`Connection`、idle timeout 决定 | socket 开启 `SO_KEEPALIVE` 后由内核定时发送探测包 |
| 常见时间尺度 | 秒级到分钟级，和连接池、网关超时相关 | 默认常是小时级，需要显式调短才适合服务端探活 |
| 能否判断应用健康 | 不能保证，但每次复用时会发真实请求 | 不能，只能判断 TCP 层大致可达 |

HTTP/1.1 默认长连接，常见客户端会维护连接池；服务端或代理可以在空闲超时、最大请求数、过载保护时关闭连接。TCP Keepalive 则是在连接没有应用层数据时由内核发探测包，适合作为半开连接清理的兜底。

真实场景中，HTTP/RPC 服务通常用 HTTP Keep-Alive 或连接池降低握手成本，同时配置应用层心跳、读写超时和 TCP Keepalive。不要把 TCP Keepalive 当成业务心跳，也不要认为 HTTP Keep-Alive 能保证连接永远可用；复用连接时必须处理对端已关闭、RST、写失败和重连。

## 2. 为什么有 TCP 保活还要应用心跳

应用心跳是业务协议自己定义的 ping/pong、heartbeat 或空消息。它解决的问题比 TCP Keepalive 更贴近业务。

需要应用心跳的原因：

1. **检测更快**：业务可以按 5s、10s、30s 等粒度检测，而不是等内核默认小时级探测。
2. **检测应用存活**：TCP 通不代表对端业务线程、事件循环或依赖服务正常。
3. **穿透中间设备超时**：NAT、负载均衡、防火墙会清理空闲连接，心跳可以刷新连接活跃时间。
4. **携带业务状态**：心跳可以带版本、负载、订阅状态、客户端时间等信息。
5. **统一跨协议行为**：WebSocket、RPC、IM、游戏长连接通常都需要业务层断线重连和会话恢复。

常见设计：

```text
client -> ping(seq, timestamp)
server -> pong(seq, timestamp)
```

如果连续 N 次未收到 pong，就认为连接不可用，关闭并重连。心跳间隔要小于中间设备空闲超时，也不能过小，否则会造成无意义流量和唤醒。

## 3. 客户端突然断电服务端如何快速知道

客户端突然断电、拔网线或进程被强杀时，服务端通常不会立刻收到 FIN。TCP 连接在内核里可能仍处于 ESTABLISHED，服务端只有在后续探测或读写失败时才知道连接不可用。

常见发现方式：

1. **正常关闭**：客户端主动 `close`，服务端 `read` 返回 0，表示收到 FIN。
2. **异常复位**：客户端内核还在并发送 RST，服务端读写会得到 `ECONNRESET` 等错误。
3. **断电或网络黑洞**：没有 FIN/RST，服务端写数据后经过多次重传仍失败，最终由 TCP 超时判定错误。
4. **TCP Keepalive**：开启并调短 keepalive 参数后，内核可在空闲连接上做探测。
5. **应用心跳**：业务层 ping/pong 连续超时后主动关闭连接，是长连接系统里最常用的快速发现方式。

真实业务一般组合使用：

```text
应用心跳 10s 一次，连续 3 次失败关闭连接
TCP keepalive 作为兜底，防止业务层长时间无读写
负载均衡/NAT 空闲超时前发送心跳，避免中间设备清理连接
```

易错点是把“TCP 是可靠的”和“能立刻感知对端断电”混为一谈。TCP 只能保证已建立连接上的字节流可靠传输，不能保证对端物理掉线会马上通知应用；检测速度取决于心跳、keepalive、读写超时和中间网络状态。

## 4. Nagle 算法是什么

Nagle 算法用于减少小包数量。它的核心思想是：当连接上还有未确认的小数据包时，后续小数据先攒起来，等收到 ACK 或攒到足够大再发送。

优点：

1. 减少小包数量，降低网络和协议栈开销。
2. 对 telnet 这类小字节交互和低带宽网络有历史意义。

问题：

1. 对低延迟小消息场景，Nagle 可能引入等待 ACK 的延迟。
2. 和延迟确认 Delayed ACK 叠加时，可能出现明显的几十毫秒级延迟。
3. RPC、游戏、IM、实时控制这类小包低延迟业务通常不希望攒包。

关闭方式：

```cpp
int on = 1;
setsockopt(fd, IPPROTO_TCP, TCP_NODELAY, &on, sizeof(on));
```

## 5. TCP_NODELAY 和 TCP_CORK

1. `TCP_NODELAY`：关闭 Nagle，尽快发送小包，适合低延迟交互。
2. `TCP_CORK`：尽量攒包，适合先写 header 再写 body，希望组合成更完整报文的场景。
3. 两者目标相反，不能只背“优化性能”，要看业务是追求低延迟还是高吞吐。

## 6. 易错点

1. TCP Keepalive 不等于应用心跳，前者是连接探测，后者是业务健康和会话保活。
2. 心跳不是越频繁越好，移动端和大规模长连接会被心跳流量、耗电和唤醒影响。
3. 开启 `TCP_NODELAY` 可能增加小包数量，不一定提高整体吞吐。
4. 如果应用自己做批量和缓冲，是否关闭 Nagle 要结合实际抓包和延迟指标判断。

## 7. 面试回答模板

TCP Keepalive 是内核层的空闲连接探测，默认时间通常很长，只能说明连接在 TCP 层大致可达。应用心跳是业务协议的一部分，可以更快发现断线、检测应用层是否健康、刷新 NAT/负载均衡空闲超时，并携带业务状态。Nagle 算法用于合并小包，减少网络开销，但会增加小消息延迟；低延迟 RPC、游戏、IM 常通过 `TCP_NODELAY` 关闭它，而文件传输或批量发送更关注吞吐和包聚合。
