# 8. TCP 可靠传输机制

TCP 是面向连接的可靠字节流协议。可靠不是指网络不丢包，而是 TCP 在不可靠的 IP 之上，通过序号、确认、重传、校验、流量控制和拥塞控制，尽量让应用看到有序、无重复、无丢失的字节流。

## TCP 如何保证可靠

1. **三次握手**：确认双方收发能力，交换初始序列号 ISN。
2. **序号 Sequence Number**：TCP 按字节编号，接收方可以识别乱序、重复和缺失数据。
3. **确认 ACK**：接收方用确认号告诉发送方“下一个期望收到的字节序号”。
4. **超时重传 RTO**：发送后迟迟没收到 ACK，会根据 RTT/RTO 估计触发重传。
5. **快速重传**：收到多个重复 ACK 时，推测中间段丢失，提前重传。
6. **滑动窗口**：发送方可以在未收到全部 ACK 前连续发送多个段，提高吞吐。
7. **流量控制**：接收窗口 `rwnd` 告诉发送方接收缓冲区剩余空间，避免压垮接收方。
8. **拥塞控制**：拥塞窗口 `cwnd` 根据网络状态调节发送速率，避免压垮网络。
9. **校验和**：检测 TCP 首部和数据在传输中是否损坏。
10. **有序交付**：乱序数据可以先缓存，最终按序交付给应用层。

实际可发送窗口通常是：

```text
send_window = min(rwnd, cwnd)
```

## 拥塞控制算法

TCP 拥塞控制关注网络路径是否过载，核心是调节 `cwnd`。

| 算法 | 核心思想 | 特点 |
| --- | --- | --- |
| Reno | 慢启动、拥塞避免、快速重传、快速恢复 | 经典丢包驱动算法，丢包后降窗明显 |
| CUBIC | 用三次函数控制窗口增长 | Linux 常见默认算法，适合高带宽长 RTT 网络 |
| BBR | 基于带宽和 RTT 估计瓶颈带宽和最小 RTT | 不单纯以丢包为拥塞信号，追求高吞吐和低队列 |
| DCTCP | 利用 ECN 标记估计拥塞程度 | 数据中心网络常用，要求交换机支持 ECN |
| Vegas | 根据 RTT 增长推测排队拥塞 | 提前降速，但和丢包型算法共存时可能吃亏 |

## 流量控制和拥塞控制区别

1. 流量控制保护接收方，核心窗口是 `rwnd`。
2. 拥塞控制保护网络路径，核心窗口是 `cwnd`。
3. 接收方缓冲区满会导致零窗口；网络拥塞会导致丢包、RTT 升高、ECN 标记等。

## 易错点

1. TCP 可靠传输不保证业务处理成功，应用仍需要业务 ACK、幂等和重试。
2. ACK 确认的是字节序号，不是“第几个包”。
3. UDP 不可靠不代表应用不能可靠，QUIC 就是在 UDP 上实现了可靠传输。
4. `cwnd` 不在 TCP 首部里，它是发送端本地拥塞控制状态。
5. 延迟、丢包和吞吐问题不一定是应用 bug，可能来自拥塞控制、窗口大小、Nagle、Delayed ACK、队头阻塞等。

## 面试回答模板

TCP 通过三次握手建立连接并交换初始序列号；传输时用序号和 ACK 判断数据是否到达、是否乱序或重复；丢包时通过超时重传和快速重传恢复；用校验和发现损坏；用滑动窗口提高吞吐；用接收窗口做流量控制，用拥塞窗口做拥塞控制。拥塞控制算法包括 Reno、CUBIC、BBR、Vegas、DCTCP 等，真实系统中 Linux 常见默认是 CUBIC，也可以根据场景启用 BBR 或数据中心里的 DCTCP。
