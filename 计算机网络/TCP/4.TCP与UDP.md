# 4. TCP与UDP

## 1. 定义

TCP 和 UDP 都是传输层协议，负责端到端进程通信。它们都使用端口号区分同一主机上的不同进程，但提供的语义不同。

1. **TCP**：面向连接、可靠、字节流协议。
2. **UDP**：无连接、不保证可靠、数据报协议。

## 2. 核心区别

| 对比项 | TCP | UDP |
| --- | --- | --- |
| 连接 | 需要三次握手建立连接 | 无连接，直接发送 |
| 可靠性 | 确认、重传、序号、校验、流量控制 | 只提供校验和，不保证送达 |
| 数据边界 | 字节流，没有消息边界 | 数据报，有消息边界 |
| 顺序 | 保证按序交付 | 不保证顺序 |
| 拥塞控制 | 有拥塞控制 | 协议本身没有 |
| 首部开销 | 至少 20 字节 | 8 字节 |
| 典型场景 | HTTP/1.1、HTTP/2、MySQL、SSH | DNS、QUIC/HTTP/3、实时音视频、游戏 |

## 3. TCP 核心机制

1. **三次握手**：协商初始序列号，确认双方收发能力。
2. **序号和确认号**：让接收方知道数据顺序，发送方知道哪些数据已送达。
3. **超时重传和快速重传**：丢包后重新发送。
4. **滑动窗口**：实现流量控制，避免发送方压垮接收方。
5. **拥塞控制**：通过慢启动、拥塞避免、快速恢复等机制保护网络。
6. **四次挥手**：双向关闭连接。

## 4. UDP 核心机制

UDP 只提供很薄的一层封装：

```text
源端口 + 目的端口 + 长度 + 校验和 + 数据
```

它不负责连接管理、重传、排序、拥塞控制。应用如果需要可靠性，要自己实现，或者使用基于 UDP 的上层协议，例如 QUIC。

## 4.1 UDP 报文最大长度

UDP 头部中的 Length 字段是 16 位，表示 UDP 首部加数据的总长度，因此理论最大 UDP 报文长度是：

```text
2^16 - 1 = 65535 字节
```

扣掉 8 字节 UDP 首部后，UDP payload 理论最大是 `65527` 字节。

但在 IPv4 下，IP 数据报总长度也受 16 位 Total Length 限制，且还要扣掉 IP 首部。无 IP 选项时：

```text
最大 UDP payload = 65535 - 20 - 8 = 65507 字节
```

IPv6 的普通 Payload Length 字段也是 16 位，常规情况下 UDP 数据也受 MTU 和分片机制约束；Jumbo Payload 是特殊扩展，不是普通面试默认答案。

真实工程不建议发送接近 64KB 的 UDP 包，因为超过路径 MTU 会发生 IP 分片，任意一个分片丢失都会导致整个 UDP 数据报不可用。公网常按路径 MTU 控制在约 1200 字节以内，例如 QUIC 常以 1200 字节作为初始数据报大小。

## 4.2 UDP 适用场景

UDP 适合“低延迟、可容忍少量丢包、应用能自己处理可靠性或不需要可靠性”的场景：

1. **DNS**：请求响应小，优先低延迟；大响应或区域传送可切到 TCP。
2. **实时音视频**：过期帧重传价值低，宁可丢帧也不要延迟累积。
3. **在线游戏**：位置同步、状态广播更关注实时性。
4. **QUIC/HTTP/3**：在 UDP 之上由用户态实现可靠传输、拥塞控制和 TLS。
5. **日志、指标、心跳**：部分监控数据允许丢失，低开销更重要。
6. **广播/组播**：局域网发现、组播分发等 TCP 不适合的通信方式。

选择 UDP 不等于不考虑拥塞控制。公网大流量 UDP 如果没有限速和拥塞控制，可能造成网络拥塞，也容易被中间设备限流。

## 4.3 TCP 和 UDP 能否绑定同一个端口

可以。TCP 端口空间和 UDP 端口空间相互独立，内核用协议号区分：

```text
(protocol, local_ip, local_port)
```

例如 DNS 同时使用 UDP/53 和 TCP/53。实现上需要分别创建两个 socket：

```cpp
int tcp_fd = socket(AF_INET, SOCK_STREAM, 0);
bind(tcp_fd, ... port 53 ...);
listen(tcp_fd, SOMAXCONN);

int udp_fd = socket(AF_INET, SOCK_DGRAM, 0);
bind(udp_fd, ... port 53 ...);
```

TCP socket 要 `listen/accept`，每个连接会产生新的连接 fd；UDP socket 不需要 `listen/accept`，直接用 `recvfrom/sendto` 收发数据报。

## 5. 为什么 QUIC 选择 UDP

QUIC 基于 UDP 不是因为 UDP 更可靠，而是因为 UDP 足够简单，容易在用户态实现新的传输协议能力：

1. 避开内核 TCP 协议栈升级慢的问题。
2. 合并 TLS 1.3 握手和传输层握手，降低建连时延。
3. 支持 stream 级别多路复用，缓解 TCP 队头阻塞。
4. 支持连接迁移，例如移动网络切 Wi-Fi 后保持连接。

## 6. 易错点

1. TCP 是字节流，不保留业务消息边界，粘包/拆包要应用层处理。
2. UDP 有消息边界，但消息可能丢失、乱序、重复。
3. TCP 可靠不代表应用一定成功，只代表数据尽力可靠送到对端协议栈；应用处理失败仍要业务确认。
4. UDP 并不等于不能可靠，可靠性可以在应用层实现。
5. 实时音视频常用 UDP，是因为宁可丢少量帧，也不希望重传导致延迟累积。
6. TCP 和 UDP 可以使用同一个端口号，因为协议号不同；但需要分别创建 TCP socket 和 UDP socket。

## 7. 面试回答模板

TCP 是面向连接的可靠字节流协议，通过三次握手、序号确认、重传、滑动窗口和拥塞控制保证可靠有序传输，适合 Web、数据库、SSH 等对可靠性要求高的场景。UDP 是无连接的数据报协议，保留消息边界，但不保证可靠、有序和不重复，首部开销小、延迟低，适合 DNS、实时音视频、游戏、心跳监控，以及 QUIC 这类在用户态重新实现可靠传输的协议。TCP 和 UDP 可以绑定同一个端口，因为端口空间按协议分开，服务端要分别创建 `SOCK_STREAM` 和 `SOCK_DGRAM` 两个 socket。
