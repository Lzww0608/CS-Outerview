# 14. 长连接安全与多连接管理

长连接是指客户端和服务端建立连接后，在较长时间内复用这条连接传输多次消息，而不是每次请求都重新建连。面试里问“TCP/IP 如何保证长连接安全”和“一个服务端与一个客户端有多个长连接怎么处理”，要把 TCP 能提供的能力和应用层必须补充的能力区分清楚。

## 1. TCP 本身能保证什么

TCP 提供的是传输层可靠字节流：

1. 通过三次握手建立连接。
2. 通过序号、ACK、重传保证尽力可靠交付。
3. 通过校验和发现部分传输错误。
4. 通过滑动窗口做流量控制。
5. 通过拥塞控制避免发送端压垮网络。

但 TCP 本身不解决这些安全问题：

1. 不加密，明文可能被窃听。
2. 不认证应用身份，无法确认对端业务身份。
3. 不防重放和业务越权。
4. 不判断对端应用是否健康。
5. 不限制恶意连接长期占用资源。

所以“长连接安全”不能只靠 TCP，要在 TLS、认证、会话、心跳、限流和协议设计上共同保证。

## 2. 长连接安全设计

### 2.1 加密和身份认证

常见方案：

1. **TLS**：保护传输机密性和完整性，防止中间人窃听和篡改。
2. **证书校验**：客户端校验服务端证书链、域名和有效期。
3. **双向 TLS mTLS**：服务端也校验客户端证书，适合内部服务、设备接入和高安全场景。
4. **应用层 token**：连接建立后在登录帧或认证帧里携带 token、签名或临时票据。

如果是公网长连接，通常至少使用 TLS；如果是设备、无人机、工业控制等场景，还要关注设备证书、密钥轮换和吊销。

### 2.2 会话和权限

长连接建立成功不代表所有消息都可信。服务端通常会维护连接上下文：

```text
fd / connection_id
  -> user_id / device_id
  -> auth_state
  -> subscriptions
  -> last_active_time
  -> rate_limit_state
```

每条业务消息都要校验：

1. 当前连接是否已认证。
2. 用户或设备是否有权限执行该操作。
3. 消息序号、时间戳或 nonce 是否正常。
4. 是否超过连接、用户、设备维度的速率限制。

### 2.3 心跳和超时

长连接必须主动处理半开连接、NAT 超时和客户端异常退出。

常见做法：

1. 应用层 ping/pong。
2. 记录 `last_read_time` 和 `last_write_time`。
3. 连续 N 次心跳无响应则关闭连接。
4. 空闲超过阈值的连接主动断开。
5. 断线后客户端指数退避重连，避免服务恢复时被重连风暴打垮。

TCP Keepalive 可以作为兜底，但默认间隔通常太长，不适合作为业务级故障检测。

### 2.4 抗滥用和资源保护

长连接会长期占用 fd、内存、定时器、订阅关系和发送缓冲区。服务端要限制：

1. 单 IP 最大连接数。
2. 单账号或单设备最大连接数。
3. 单连接最大未发送缓冲区。
4. 单连接消息速率和字节速率。
5. 认证超时时间，未认证连接不能长期挂着。
6. 异常协议帧、畸形包、慢读慢写连接要尽快清理。

高并发长连接服务通常还会按连接数、活跃度、用户或房间做分片，避免单进程维护过大的状态。

## 3. 一个客户端和服务端有多个长连接

TCP 连接由四元组标识：

```text
(src_ip, src_port, dst_ip, dst_port)
```

同一个客户端进程可以用不同本地端口和同一个服务端端口建立多条 TCP 连接。服务端每次 `accept` 都会得到一个新的连接 fd。

服务端要做的是为每条连接建立独立上下文：

```cpp
struct Connection {
    int fd;
    std::string conn_id;
    std::string user_id;
    Buffer input;
    Buffer output;
    TimePoint last_active;
    AuthState auth_state;
};

std::unordered_map<int, Connection> fd_to_conn;
std::unordered_map<std::string, std::unordered_set<int>> user_to_fds;
```

处理流程：

1. `accept` 返回新 fd，分配 `Connection` 对象。
2. fd 加入 epoll，监听读写事件。
3. 收到认证消息后绑定 `user_id/device_id`。
4. 同一用户多连接时按业务决定是否允许共存。
5. 发送消息时可以发给某个连接，也可以按 `user_id -> fds` 广播到该用户所有在线端。
6. 连接关闭时从所有索引中删除，释放缓冲区和订阅关系。

## 4. 多连接共存的业务策略

同一客户端或同一账号多连接，不一定都是错误，要看业务语义：

| 策略 | 含义 | 场景 |
| --- | --- | --- |
| 允许多连接 | 每个连接独立存在 | 多标签页、多个设备、控制面和数据面分离 |
| 踢掉旧连接 | 新连接成功后关闭旧连接 | 单设备登录、强一致控制通道 |
| 主备连接 | 主连接传业务，备用连接故障切换 | 高可用控制链路 |
| 多路复用 | 一条连接内承载多个 stream/channel | HTTP/2、QUIC、自定义 RPC |

如果多个长连接都能修改同一资源，还要做请求幂等、版本号、锁或状态机校验，避免并发命令互相覆盖。

## 5. 应用层协议要解决的问题

TCP 是字节流，多连接管理还需要应用协议配合：

1. **消息边界**：使用长度前缀、分隔符或固定头部解决粘包拆包。
2. **请求响应匹配**：使用 `request_id` 匹配响应。
3. **连接身份**：认证帧绑定用户、设备或客户端实例。
4. **消息顺序**：需要有序时使用序号；跨连接不天然保序。
5. **重放保护**：时间戳、nonce、递增序号或签名。
6. **断线恢复**：客户端带上上次 ack 的消息位点，服务端补发或重新同步状态。

## 6. 易错点

1. TCP 可靠不等于业务安全，认证、授权、加密、限流都要应用层设计。
2. TCP Keepalive 不等于业务心跳，不能判断对端业务逻辑是否还健康。
3. 同一客户端多连接在内核层是不同四元组，服务端要用 fd 或连接 ID 区分。
4. 多条连接之间没有全局顺序，跨连接消息顺序要由业务协议定义。
5. 连接关闭时要清理所有索引和订阅关系，否则会出现内存泄漏、误推送和幽灵在线。

## 7. 面试回答模板

TCP 能保证长连接的可靠字节流传输，但不保证业务安全。长连接安全通常要用 TLS 加密和证书校验，连接建立后再做 token 或设备身份认证，后续每条消息做权限、序号、限流和重放校验。同时要有应用心跳、空闲超时、最大连接数、发送缓冲区上限和断线重连策略。一个客户端和服务端可以建立多条 TCP 长连接，因为四元组里的源端口不同；服务端每次 `accept` 得到一个新的 fd，为每个 fd 建独立连接上下文，并维护 `fd -> Connection`、`user -> fds` 这类索引。多连接是否允许共存取决于业务，可以允许多端在线，也可以新连接踢旧连接，或者改用一条连接里的多路复用。
