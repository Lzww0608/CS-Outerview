# 16.TCP字节流与粘包

TCP 是面向连接、可靠、有序的字节流协议。它只保证字节按顺序可靠到达，不保留应用层“消息边界”。因此发送端一次 `send` 和接收端一次 `recv` 不存在一一对应关系，这就是网络编程里常说的粘包和拆包问题。

## 1. 什么是粘包和拆包

粘包和拆包不是 TCP 出错，而是应用层协议没有正确处理消息边界。

1. **粘包**：发送端连续发送两条业务消息，接收端一次 `recv` 读到了两条甚至多条消息的数据。
2. **拆包**：发送端发送一条业务消息，接收端多次 `recv` 才读完整。
3. **粘拆同时出现**：一次读取可能包含上一条消息的尾部、当前消息的全部和下一条消息的头部。

例如客户端连续发送：

```text
hello
world
```

服务端可能读到：

```text
helloworld
```

也可能先读到：

```text
hel
```

再读到：

```text
loworld
```

所以服务端不能把一次 `recv` 当作一条完整业务消息。

## 2. 为什么 TCP 会这样

根本原因是 TCP 的抽象是字节流，而不是消息队列。

常见影响因素：

1. 发送缓冲区和接收缓冲区会合并或拆分应用写入的数据。
2. MSS、拥塞窗口、接收窗口会影响 TCP 段切分。
3. Nagle 算法可能把多个小包合并发送。
4. 延迟 ACK、操作系统调度、应用读取速度都会影响接收端看到的数据批次。
5. 非阻塞 I/O 下，应用每次读取到多少字节还取决于当前内核缓冲区已有多少数据。

面试里可以强调：TCP 层没有“包”的业务语义，所谓粘包是应用层协议设计和解析的问题。

## 3. 如何解决

应用层协议必须自己定义消息边界，常见方案如下：

| 方案 | 原理 | 适用场景 | 注意事项 |
| --- | --- | --- | --- |
| 固定长度 | 每条消息固定 N 字节 | 简单二进制协议、定长记录 | 浪费空间，扩展性差 |
| 分隔符 | 用 `\n`、`\r\n`、特殊字符结束消息 | 文本协议、日志协议 | 内容中出现分隔符要转义 |
| 长度前缀 | 消息头里写 body 长度 | RPC、IM、私有 TCP 协议 | 要处理半包和非法长度 |
| TLV | Type-Length-Value | 可扩展二进制协议 | 编码复杂度更高 |
| 成熟协议 | HTTP、WebSocket、gRPC 等 | 业务系统 | 直接复用标准解析器 |

长度前缀协议的接收端通常维护一个输入缓冲区：

```text
read socket bytes -> append buffer
while buffer contains full header:
    parse length
    if buffer contains full body:
        cut one message and handle
    else:
        wait more bytes
```

易错点是只在发送端 `sleep` 或关闭 Nagle。这样不能从根本上解决问题，因为 TCP 仍然是字节流，网络和接收端读取批次依然不可控。

## 4. HTTP 是否有粘包问题

HTTP 基于 TCP 时，底层仍然是字节流，所以 TCP 层仍然可能粘包或拆包。但 HTTP 协议定义了清晰的报文边界，正确的 HTTP 解析器不会把它暴露成业务层“粘包问题”。

HTTP/1.1 常见边界：

1. 请求行或状态行 + header，以空行 `\r\n\r\n` 标识头部结束。
2. 有固定 body 时，用 `Content-Length` 表示 body 字节数。
3. body 长度未知时，用 `Transfer-Encoding: chunked`，每个 chunk 自带长度，最后以 0 长度 chunk 结束。
4. 长连接上可以连续发送多个请求或响应，解析器按上述规则逐个切分。

HTTP/2 不再使用文本报文，而是二进制分帧。每个 frame 有长度和 stream id，接收端按 frame length 解析，再按 stream id 组装不同请求响应。

因此回答“HTTP 是否存在粘包”可以说：底层 TCP 仍然没有消息边界，但 HTTP 自身已经定义了应用层边界。只要 HTTP parser 实现正确，业务代码通常不需要关心 TCP 粘包；如果自己写 HTTP 解析器，就必须处理半包、连续报文和非法长度。

## 5. 真实场景

1. **自定义 RPC 协议**：常用 4 字节长度 + 序列化 body，服务端循环从缓冲区拆完整包。
2. **IM 长连接**：消息头包含版本、命令、序列号、body 长度，方便心跳、重连和 ACK。
3. **网关代理**：必须正确处理半包和 backpressure，不能假设一次读写完成完整请求。
4. **HTTP 服务**：一般依赖 Netty、Nginx、Tomcat、Go net/http 等成熟解析器，避免手写报文边界。

## 6. 面试回答模板

TCP 是可靠有序的字节流协议，不保留应用层消息边界，所以一次 send 不一定对应一次 recv。粘包是多条业务消息被一次读到，拆包是一条业务消息被多次读到，本质是应用层协议需要自己定界。解决方式有定长、分隔符、长度前缀、TLV 或直接使用 HTTP/WebSocket/gRPC 等成熟协议。

HTTP 基于 TCP 时底层仍可能发生粘包和拆包，但 HTTP/1.1 通过 `Content-Length`、`chunked` 和 `\r\n\r\n`，HTTP/2 通过二进制 frame length 定义了消息边界，所以正确的 HTTP 解析器能处理这个问题，业务层一般不感知。
