# 6. 流量控制与零窗口

## 1. TCP 流量控制是什么

TCP 流量控制是接收方保护自己的一种机制。接收方通过 TCP 首部里的接收窗口 `rwnd` 告诉发送方自己还能接收多少数据，发送方不能无限制发送。

发送方实际可发送窗口通常是：

```text
send_window = min(rwnd, cwnd)
```

其中：

1. `rwnd` 是接收窗口，用于流量控制，保护接收方。
2. `cwnd` 是拥塞窗口，用于拥塞控制，保护网络。

## 2. 滑动窗口为 0 怎么办

当接收方应用层处理太慢，接收缓冲区被占满时，接收方会通告：

```text
rwnd = 0
```

这表示发送方暂时不能再发送普通数据，否则会压垮接收方。

问题在于：如果接收方后续窗口恢复的 ACK 丢了，发送方会一直以为窗口是 0，双方可能僵住。

TCP 用 **零窗口探测** 解决这个问题：

1. 发送方收到零窗口通告后，停止发送普通数据。
2. 启动 persist timer。
3. 定时发送很小的窗口探测报文。
4. 接收方回复当前窗口大小。
5. 如果窗口仍为 0，继续退避等待；如果窗口恢复，发送方继续发送数据。

## 3. 零窗口和糊涂窗口综合征

零窗口恢复后，如果接收方每次只释放很小空间，比如 1 字节，发送方也立刻发送 1 字节，会造成大量小包，吞吐很差。这类问题叫糊涂窗口综合征。

常见优化：

1. **接收方 Clark 策略**：窗口太小时先不通告，等缓冲区释放到足够大再通告。
2. **发送方 Nagle 算法**：小数据先合并，等待 ACK 或积累到 MSS 再发送。
3. **应用层批处理**：消费者及时读取 socket，避免长时间占满接收缓冲区。

## 4. 和拥塞控制的区别

1. 流量控制看的是接收方缓冲区是否够用。
2. 拥塞控制看的是网络路径是否过载。
3. 零窗口是接收方明确告诉发送方“我收不下了”。
4. 丢包、RTT 上升、ECN 标记通常是拥塞控制关心的信号。

## 5. 接收缓冲区里放的是什么

TCP 接收缓冲区是内核为每个连接维护的 socket buffer。它存放的是已经到达本机、通过校验、属于该连接的 TCP 字节流数据，以及必要的协议元信息。

可以这样理解：

```text
网卡收包
  -> IP/TCP 协议栈校验和重组
  -> 根据四元组找到 socket
  -> 按序数据进入接收缓冲区
  -> 应用调用 recv/read 拷贝到用户态 buffer
```

接收缓冲区相关细节：

1. TCP 是字节流协议，缓冲区里不是“一个个完整业务包”，而是一段连续或等待重排的字节流。
2. 乱序到达的数据可能先暂存在内核队列中，等缺口补齐后再按序交付给应用。
3. 应用 `recv` 读走数据后，接收缓冲区释放空间，接收窗口 `rwnd` 才可能变大。
4. 如果应用层长期不读，接收缓冲区会被占满，接收方通告零窗口，发送方停止发送普通数据。
5. socket 接收缓冲区大小受 `SO_RCVBUF` 和系统参数影响，但调大缓冲区只能缓解突发，不能替代应用消费能力。

易错点：

1. `recv` 一次返回多少字节由缓冲区已有数据、用户 buffer 大小和协议状态共同决定，不等于对端一次 `send` 的大小。
2. 接收窗口是接收方缓冲区剩余能力的通告，不是发送方真正能无限发送的许可；发送方还受拥塞窗口限制。
3. 内核接收缓冲区满时，问题常在应用处理慢、事件循环被阻塞或业务线程池积压，不一定是网络带宽不足。

## 6. 面试回答模板

滑动窗口为 0 表示接收方缓冲区满了，发送方要暂停发送普通数据。为了避免窗口恢复通知丢失导致双方一直等待，TCP 会启动零窗口探测，也就是 persist timer 周期性发送小探测包，让接收方返回最新窗口。如果窗口恢复就继续发送，否则继续等待。这个问题属于流量控制，保护的是接收方；拥塞控制保护的是网络，核心窗口是 `cwnd`。
