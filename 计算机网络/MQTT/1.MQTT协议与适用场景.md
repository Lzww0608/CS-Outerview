# 1. MQTT 协议与适用场景

MQTT（Message Queuing Telemetry Transport）是一种轻量级发布订阅协议，常用于物联网、弱网络设备、移动端长连接和低带宽消息传输。它运行在 TCP 之上，通过 Broker 做消息转发。

## 1. 核心模型

MQTT 有三个核心概念：

1. **Client**：发布或订阅消息的客户端。
2. **Broker**：消息代理，负责连接管理、主题路由、权限和消息分发。
3. **Topic**：主题名，订阅者按主题接收消息，例如 `device/123/status`。

通信方式是发布订阅：

```text
Publisher -> Broker -> Subscriber
```

发布者和订阅者不需要直接知道对方地址，这让设备数量多、上下线频繁的场景更容易扩展。

## 2. QoS 级别

MQTT 定义了三种服务质量：

| QoS | 语义 | 代价 | 场景 |
| --- | --- | --- | --- |
| 0 | 至多一次，可能丢 | 最低 | 高频状态上报、可丢指标 |
| 1 | 至少一次，可能重复 | 中等 | 重要但可幂等处理的消息 |
| 2 | 恰好一次 | 最高 | 少量关键控制消息 |

工程上常用 QoS 1，再通过业务幂等去处理重复消息。QoS 2 流程复杂、延迟更高，不适合所有链路默认使用。

## 3. 为什么选择 MQTT

适合选择 MQTT 的原因：

1. **弱网络友好**：协议头小，适合低带宽、高延迟和移动网络。
2. **长连接轻量**：心跳、会话保持和重连机制简单。
3. **发布订阅解耦**：设备或客户端不需要知道服务端具体实例。
4. **离线消息**：Broker 可以在持久会话下保存部分离线消息。
5. **主题路由**：按 topic 做设备、用户、业务事件的分层管理。

不适合的场景：

1. 大文件上传下载，应该使用 HTTP Range、分片上传或对象存储协议。
2. 强事务请求响应，RPC/HTTP 更直观。
3. 超大规模复杂流处理，Kafka、Pulsar 这类日志型 MQ 更合适。

## 4. 和 HTTP/RPC/MQ 的区别

| 方案 | 特点 | 更适合 |
| --- | --- | --- |
| HTTP | 请求响应，生态成熟，易调试 | Web API、文件上传下载 |
| RPC/gRPC | 强接口契约、低延迟服务调用 | 服务间同步调用 |
| MQTT | 轻量发布订阅、弱网络长连接 | 设备消息、状态上报、控制指令 |
| Kafka/RocketMQ | 高吞吐、可回放、持久日志 | 后端事件流、削峰、异步解耦 |

如果项目中同时有文件传输和设备状态通知，可以用 HTTP/对象存储处理文件数据，用 MQTT 传状态、进度、控制命令和异步通知。

## 5. 易错点

1. MQTT 基于 TCP，不等于天然实时可靠；网络断开、Broker 故障、客户端重连都要处理。
2. QoS 1 会重复投递，消费者必须幂等。
3. Topic 设计不能太随意，通配符订阅过宽可能造成流量放大。
4. Retain 消息和离线消息要控制大小和过期时间，避免 Broker 内存膨胀。
5. 安全上要启用 TLS、用户名密码或证书，并做 topic 级 ACL。

## 6. 面试回答模板

MQTT 是基于 TCP 的轻量级发布订阅协议，核心是客户端连接 Broker，通过 topic 发布和订阅消息。它适合设备状态上报、移动端长连接、弱网络控制消息和异步通知，因为协议头小、长连接轻量、发布订阅解耦，并且支持 QoS 和持久会话。如果是大文件传输我不会用 MQTT 承载文件本体，而是用 HTTP 分片上传或对象存储；MQTT 更适合传上传进度、任务完成、设备心跳和控制指令。工程上要注意 QoS 1 重复投递、topic 权限、离线消息膨胀和 TLS 安全。
