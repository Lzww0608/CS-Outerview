# 负载均衡：一层、二层、四层、七层详解

## 一、OSI 七层模型回顾

### 1.1 七层划分

```text
┌─────────────────────────────────────────────────────────────┐
│  7. 应用层 (Application)    - HTTP, FTP, SMTP, DNS        │
├─────────────────────────────────────────────────────────────┤
│  6. 表示层 (Presentation)   - TLS, SSL, JPEG, ASCII        │
├─────────────────────────────────────────────────────────────┤
│  5. 会话层 (Session)        - NetBIOS, RPC                  │
├─────────────────────────────────────────────────────────────┤
│  4. 传输层 (Transport)      - TCP, UDP, SCTP              │
├─────────────────────────────────────────────────────────────┤
│  3. 网络层 (Network)        - IP, ICMP, Router            │
├─────────────────────────────────────────────────────────────┤
│  2. 数据链路层 (Data Link)  - Ethernet, Switch, MAC       │
├─────────────────────────────────────────────────────────────┤
│  1. 物理层 (Physical)       - Cable, Hub, Signal          │
└─────────────────────────────────────────────────────────────┘
```

### 1.2 负载均衡的分层

```text
负载均衡层次：
┌─────────────────────────────────────────────────────────────┐
│  L1 (一层) - 物理层负载均衡                                │
│     基于物理端口、线缆的负载分发                            │
├─────────────────────────────────────────────────────────────┤
│  L2 (二层) - 数据链路层负载均衡                            │
│     基于 MAC 地址的负载分发                                 │
├─────────────────────────────────────────────────────────────┤
│  L3 (三层) - 网络层负载均衡                                │
│     基于 IP 地址的负载分发（通常划入四层）                  │
├─────────────────────────────────────────────────────────────┤
│  L4 (四层) - 传输层负载均衡                                │
│     基于 TCP/UDP 端口和连接的负载分发                       │
├─────────────────────────────────────────────────────────────┤
│  L7 (七层) - 应用层负载均衡                                │
│     基于应用层协议（HTTP、HTTPS、DNS）的负载分发            │
└─────────────────────────────────────────────────────────────┘
```

## 二、一层负载均衡（物理层）

### 2.1 定义

一层负载均衡基于物理层面的负载分发，最常见的是**线路聚合**（Link Aggregation）。

### 2.2 实现方式

**LACP（Link Aggregation Control Protocol）**：

```text
┌─────────────────────────────────────────────────────────────┐
│                    LACP 链路聚合                             │
│                                                             │
│  服务器 ──┬── 物理线缆 1 ──┬──► 交换机 Port 1              │
│           │                │                               │
│           ├── 物理线缆 2 ──┼──► 交换机 Port 2              │
│           │                │                               │
│           └── 物理线缆 3 ──┴──► 交换机 Port 3              │
│                                                             │
│  逻辑上看起来是一个 Port（PortChannel/Trunk）               │
└─────────────────────────────────────────────────────────────┘
```

### 2.3 配置示例

```bash
# Linux 链路聚合
# 创建 bond0 设备
ip link add bond0 type bond mode 802.3ad

# 添加物理网卡到 bond
ip link set eth0 master bond0
ip link set eth1 master bond0
ip link set eth2 master bond0

# 配置负载均衡模式（LACP）
ip link set bond0 type bond mode 802.3ad
```

## 三、二层负载均衡（数据链路层）

### 3.1 定义

二层负载均衡基于 **MAC 地址**进行负载分发，通常通过 **VLAN** 或 **MACVLN** 实现。

### 3.2 实现方式

**MAC 地址哈希负载均衡**：

```c
// 二层负载均衡算法
int select_backend_by_mac(uint8_t src_mac[6], uint8_t dst_mac[6], 
                          Backend** backends, int count) {
    // 计算 MAC 地址哈希
    uint64_t mac_value = 0;
    for (int i = 0; i < 6; i++) {
        mac_value = mac_value * 256 + src_mac[i];
        mac_value = mac_value * 256 + dst_mac[i];
    }
    
    // 选择后端
    int index = mac_value % count;
    return index;
}
```

### 3.3 二层负载均衡器架构

```text
┌─────────────────────────────────────────────────────────────┐
│                   二层负载均衡架构                           │
│                                                             │
│  客户端 ──► MAC 地址 ──► 二层交换机 ──► 服务器 A (MAC_A)   │
│                               │                              │
│                               └──► 服务器 B (MAC_B)          │
│                               │                              │
│                               └──► 服务器 C (MAC_C)          │
│                                                             │
│  分发依据：源/目标 MAC 地址                                  │
└─────────────────────────────────────────────────────────────┘
```

### 3.4 特点

| 优点 | 缺点 |
|------|------|
| 速度快（仅看 MAC 头） | 无法感知上层协议 |
| 几乎无延迟 | 负载分发不均匀 |
| 适合内网 | 无会话保持 |

## 四、四层负载均衡（传输层）

### 4.1 定义

四层负载均衡基于 **TCP/UDP** 端口和连接进行负载分发，是最常见的负载均衡类型。

### 4.2 实现方式

**NAT 模式**：

```text
┌─────────────────────────────────────────────────────────────┐
│                    NAT 模式四层负载均衡                        │
│                                                             │
│  客户端 ──► VIP:80 ──► L4 LB ──► Real Server 1:8080       │
│                                │                              │
│                                └──► Real Server 2:8080       │
│                                │                              │
│                                └──► Real Server 3:8080       │
│                                                             │
│  L4 LB 修改：                                              │
│  - 源 IP → L4 LB IP                                        │
│  - 目标 IP → Real Server IP                                │
│  - 源端口 → L4 LB 分配端口                                 │
│  - 目标端口 → Real Server 端口                             │
└─────────────────────────────────────────────────────────────┘
```

**DR 模式（Direct Routing）**：

```text
┌─────────────────────────────────────────────────────────────┐
│                  DR 模式四层负载均衡                          │
│                                                             │
│  客户端 ──► VIP:80 ──► L4 LB ──► Real Server 1:80 (Lo:VIP) │
│                                │                              │
│                                └──► Real Server 2:80         │
│                                                             │
│  L4 LB 只修改 MAC 地址，源 IP 保持不变                       │
│  Real Server 必须配置 lo:VIP 才能响应                       │
└─────────────────────────────────────────────────────────────┘
```

### 4.3 四层负载均衡算法

```c
// 轮询 (Round Robin)
Backend* select_round_robin(int* current_index, Backend** backends, int count) {
    *current_index = (*current_index + 1) % count;
    return backends[*current_index];
}

// 加权轮询 (Weighted Round Robin)
Backend* select_weighted_round_robin(Backend** backends, int count) {
    for (int i = 0; i < count; i++) {
        if (backends[i]->weight > 0) {
            backends[i]->weight--;
            return backends[i];
        }
    }
    // 重置权重
    for (int i = 0; i < count; i++) backends[i]->weight = backends[i]->base_weight;
    return select_weighted_round_robin(backends, count);
}

// 最少连接 (Least Connection)
Backend* select_least_connection(Backend** backends, int count) {
    Backend* best = NULL;
    int min_conn = INT_MAX;
    
    for (int i = 0; i < count; i++) {
        if (backends[i]->active_connections < min_conn) {
            min_conn = backends[i]->active_connections;
            best = backends[i];
        }
    }
    return best;
}

// 源 IP 哈希 (Source IP Hash)
Backend* select_source_ip_hash(uint32_t client_ip, Backend** backends, int count) {
    int index = client_ip % count;
    return backends[index];
}
```

### 4.4 特点

| 优点 | 缺点 |
|------|------|
| 性能高（仅解析到传输层） | 无法感知应用层内容 |
| 支持 TCP/UDP | 无法做 URL 级别分发 |
| 支持会话保持（连接级） | 无法修改请求内容 |
| 支持端口映射 | - |

## 五、七层负载均衡（应用层）

### 5.1 定义

七层负载均衡基于 **应用层协议**（HTTP、HTTPS、DNS、SMTP）进行负载分发，可以理解请求内容。

### 5.2 实现方式

**HTTP 反向代理**：

```text
┌─────────────────────────────────────────────────────────────┐
│                  七层负载均衡架构                             │
│                                                             │
│  客户端 ──► GET /api/users ──► L7 LB                      │
│                    │                                          │
│                    ├──► /api/* ──► API Server Pool          │
│                    │    │                                    │
│                    │    ├──► Server 1                       │
│                    │    ├──► Server 2                       │
│                    │    └──► Server 3                       │
│                    │                                          │
│                    └──► /static/* ──► CDN/Static Pool      │
│                         │                                    │
│                         ├──► Static Server 1                 │
│                         └──► Static Server 2                 │
│                                                             │
│  L7 LB 解析：HTTP Header → URL → Cookie → 进行路由           │
└─────────────────────────────────────────────────────────────┘
```

### 5.3 七层负载均衡能力

```c
// URL 路径路由
struct RouteRule {
    const char* path_prefix;      // /api/
    const char* backend_pool;    // api_pool
    int rewrite_enabled;          // 是否重写路径
    const char* new_path;        // 替换后的路径
};

// Header 修改
struct HeaderRule {
    const char* header_name;     // X-Forwarded-For
    const char* header_value;    // $client_ip
    int action;                  // ADD/SET/REMOVE
};

// 会话保持（Cookie）
struct SessionRule {
    const char* cookie_name;     // JSESSIONID
    int sticky_session;          // 是否启用粘性会话
    const char* hash_key;       // 基于 Cookie 值的哈希
};
```

### 5.4 七层负载均衡功能

```text
┌─────────────────────────────────────────────────────────────┐
│                    七层负载均衡功能                            │
│                                                             │
│  1. URL 路由：基于路径前缀、扩展名、正则匹配                  │
│  2. Header 操作：添加、删除、修改请求/响应头                  │
│  3. Cookie 处理：会话保持、Cookie 注入                        │
│  4. 内容转换：压缩、缓存、重定向                              │
│  5. SSL 终止：HTTPS 卸载、加解密                             │
│  6. 安全防护：WAF、DDoS 防护                                 │
│  7. 灰度发布：基于 Header、Cookie 的流量切分                │
└─────────────────────────────────────────────────────────────┘
```

### 5.5 特点

| 优点 | 缺点 |
|------|------|
| 感知应用层内容 | 延迟更高（需解析内容） |
| 智能路由 | 资源消耗更大 |
| 支持内容修改 | 配置更复杂 |
| 安全防护 | - |

## 六、四层 vs 七层对比

### 6.1 核心区别

| 维度 | 四层负载均衡 | 七层负载均衡 |
|------|-------------|-------------|
| 工作层次 | 传输层 | 应用层 |
| 转发依据 | IP + 端口 | URL + Header + Cookie |
| 协议支持 | TCP/UDP | HTTP/HTTPS/SMTP/DNS |
| 性能 | 高（~100万 CPS） | 中（~10万 CPS） |
| 延迟 | 低 | 中 |
| 智能路由 | 否 | 是 |
| 内容修改 | 否 | 是 |
| SSL 终止 | 否 | 是 |
| 典型产品 | LVS, IPVS, F5 | Nginx, HAProxy, Envoy |

### 6.2 选型决策树

```text
需要智能路由吗？
    │
    ├── 否 → 只需要 TCP/UDP 分发
    │         │
    │         ├── 高性能要求 → 四层（LVS/F5）
    │         │
    │         └── 一般要求 → 四层（Nginx Stream）
    │
    └── 是 → 需要 HTTP/HTTPS 分发
              │
              ├── 需要 WAF/安全防护 → 七层（WAF Gateway）
              │
              ├── 需要灰度/AB测试 → 七层（Envoy/Istio）
              │
              └── 简单 HTTP 代理 → 七层（Nginx）
```

## 七、组合使用：四层 + 七层架构

### 7.1 典型架构

```text
┌─────────────────────────────────────────────────────────────┐
│                    四层 + 七层组合架构                        │
│                                                             │
│                      ┌─────────────────┐                    │
│  客户端 ───────────►│    四层负载均衡    │                │
│                      │    (LVS/F5)     │                │
│                      └────────┬────────┘                    │
│                               │                              │
│                      ┌────────┴────────┐                    │
│                      │                   │                    │
│                      ▼                   ▼                    │
│              ┌───────────────┐ ┌───────────────┐          │
│              │  七层负载均衡  │ │  七层负载均衡  │          │
│              │   (Nginx)    │ │  (Envoy)     │          │
│              └───────┬───────┘ └───────┬───────┘          │
│                      │                   │                    │
│                      ▼                   ▼                    │
│              ┌───────────────┐ ┌───────────────┐          │
│              │   API Pool    │ │  Static Pool  │          │
│              └───────────────┘ └───────────────┘          │
│                                                             │
│  四层：处理海量连接，快速分发                                  │
│  七层：智能路由，内容处理                                     │
└─────────────────────────────────────────────────────────────┘
```

### 7.2 配置示例

```nginx
# Nginx 七层配置
upstream backend_api {
    server 10.0.1.1:8080 weight=5;
    server 10.0.1.2:8080 weight=3;
    server 10.0.1.3:8080 weight=2;
}

server {
    listen 80;
    
    location /api/ {
        proxy_pass http://backend_api;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header Host $http_host;
    }
    
    location /static/ {
        proxy_pass http://backend_static;
    }
}
```

## 九、面试常见问题

### Q1: 四层负载均衡和七层负载均衡的区别？

四层基于 IP + 端口分发，转发效率高但不能理解请求内容；七层基于 HTTP URL/Header 分发，可以做智能路由和内容修改，但性能稍低。

### Q2: L4+L7 组合架构的好处？

四层处理海量连接，七层做精细化路由。四层快速分发避免七层成为瓶颈，七层提供智能路由和安全防护。

### Q3: 会话保持怎么实现？

四层：基于源 IP 哈希或连接绑定表；七层：基于 Cookie（如 JSESSIONID）或 Header（如 X-Forwarded-For）。

### Q4: 为什么七层负载均衡延迟更高？

需要完整解析 HTTP 请求头、URL、Body，内容越多解析越慢；四层只解析到传输层头部，延迟更低。

## 十、总结

1. **一层**：物理层线路聚合（LACP）
2. **二层**：MAC 地址级分发，速度最快但能力有限
3. **四层**：IP + 端口级分发，最常用的负载均衡
4. **七层**：应用层协议级分发，智能但性能稍低
5. **组合使用**：四层做入口分流，七层做精细路由
