# 14. 浏览器和服务器消息传递

浏览器和服务器之间传递消息，本质上是在应用层选择合适的通信方式。最常见的是 HTTP 请求响应模型；如果需要服务端主动通知、实时双向通信或流式输出，则可以使用轮询、长轮询、SSE、WebSocket 等方案。

## 1. 普通 HTTP 请求响应

普通 Web 页面、表单提交、`fetch/ajax` 都属于 HTTP 请求响应模型：

```text
Browser -> HTTP Request
Server  -> HTTP Response
```

特点：

1. 浏览器主动发起请求，服务端被动响应。
2. 每个请求都要携带足够的上下文，例如 Cookie、Authorization、请求体和查询参数。
3. HTTP 本身是无状态的，服务端不会天然知道请求属于哪个用户。
4. HTTP/1.1 可以通过长连接复用 TCP 连接，但不改变“一次请求对应一次响应”的语义。

适用场景：

1. 页面加载。
2. REST API。
3. 表单提交。
4. 普通查询和写入请求。

## 2. 轮询、长轮询、SSE 和 WebSocket

| 方式 | 核心机制 | 优点 | 缺点 | 适用场景 |
| --- | --- | --- | --- | --- |
| 短轮询 | 客户端定时请求服务端 | 实现简单，兼容性好 | 空请求多，实时性受间隔影响 | 简单状态刷新 |
| 长轮询 | 请求到达后服务端挂起，有消息再返回 | 比短轮询省请求，兼容 HTTP | 连接管理复杂，请求仍会反复建立 | 低频实时通知 |
| SSE | 服务端保持 HTTP 响应流，持续推送文本事件 | 浏览器原生重连，适合单向推送 | 只能服务端到客户端，主要传文本 | 日志、进度、LLM 流式输出 |
| WebSocket | HTTP Upgrade 后切换为全双工连接 | 双向实时，消息开销小 | 需要心跳、重连、连接状态管理 | IM、协同编辑、游戏、实时看板 |

如果面试问“浏览器和服务器如何传递消息”，不要只回答 HTTP。更完整的回答应先说普通请求响应，再根据实时性和方向性扩展到 SSE 和 WebSocket。

## 3. HTTP 安全性与加密

HTTP 明文传输，不提供机密性、完整性和身份认证，存在三类典型风险：

1. 中间人可以读取请求和响应内容。
2. 中间人可以篡改报文。
3. 客户端无法确认服务端是否真的是目标站点。

HTTPS = HTTP + TLS，主要解决：

1. **机密性**：用对称加密保护应用数据。
2. **完整性**：用 AEAD 或 MAC 机制发现篡改。
3. **身份认证**：通过证书链、域名、有效期和签名验证服务端身份。

但 HTTPS 不是万能的：

1. HTTPS 保护传输链路，不负责业务鉴权。
2. HTTPS 不能防止服务端代码漏洞、SQL 注入、XSS、CSRF。
3. HTTPS 不能让 JWT payload 自动变成密文，JWT 的 payload 只是 Base64URL 编码。
4. HTTPS 可以缓解 DNS 被劫持后的伪站攻击，因为攻击者通常没有目标域名的合法证书；但它不能阻止 DNS 解析结果本身被污染。

## 4. 服务器如何找到对应用户

HTTP 无状态，所以“服务器找到用户”的关键是客户端后续请求携带身份凭证，服务端再根据凭证恢复用户上下文。

常见方案：

| 方案 | 请求携带什么 | 服务端如何恢复用户 | 特点 |
| --- | --- | --- | --- |
| Cookie + Session | 浏览器自动携带 `session_id` Cookie | 查 Redis/内存/数据库中的 session | 易撤销，适合传统 Web |
| JWT | `Authorization: Bearer <token>` 或 Cookie | 验证签名、过期时间和 claim | 服务端可无状态校验，撤销更复杂 |
| API Key | Header 或查询参数中的 key | 查 key 对应的账号和权限 | 常用于开放平台和服务调用 |
| WebSocket 登录态 | 握手时携带 Cookie/Token | 网关把连接 ID 绑定到用户 ID | 适合长连接推送 |

服务端通常会维护几类映射：

```text
session_id -> user_id / roles / expire_time
user_id    -> online_connection_ids
connection_id -> user_id / device_id / gateway_node
```

在多实例或多机房系统中，这些映射通常放在 Redis、分布式缓存或连接网关的路由表里。服务端给某个用户推送消息时，先找到用户所在连接，再由对应网关写回客户端。

## 5. JWT 鉴权流程

JWT 的核心是“签名后的声明”：

```text
Header.Payload.Signature
```

典型流程：

1. 用户登录成功。
2. 服务端生成包含 `user_id`、权限、过期时间等 claim 的 JWT。
3. 服务端用密钥或私钥对 `Header.Payload` 签名。
4. 客户端后续请求携带 JWT。
5. 服务端验证签名、过期时间、签发方、受众和权限。
6. 校验通过后把用户身份注入请求上下文。

易错点：

1. JWT payload 不是加密，不能放密码、身份证号等敏感明文。
2. JWT 一旦签发，在过期前默认难以主动撤销，需要黑名单、token version、短 access token + refresh token 等机制。
3. 浏览器里保存 JWT 要考虑 XSS 和 CSRF。放 `localStorage` 容易被 XSS 读取；放 Cookie 要配合 `HttpOnly`、`Secure`、`SameSite` 和 CSRF 防护。
4. 网关校验 JWT 后，向后端服务传递用户上下文时要防止客户端伪造内部 Header。

## 6. 真实场景选型

1. 普通业务接口：HTTP/HTTPS + Cookie Session 或 JWT。
2. 后台任务进度、日志流、模型流式回答：SSE。
3. 聊天、协同编辑、直播间互动：WebSocket。
4. 服务端广播通知：WebSocket 网关 + Redis Pub/Sub、Kafka 或 MQ。
5. 开放 API：HTTPS + API Key/OAuth2/JWT，配合限流和签名防重放。

## 7. 面试回答模板

浏览器和服务器最基础的通信方式是 HTTP 请求响应，浏览器通过表单、页面加载或 `fetch/ajax` 发请求，服务端返回响应。HTTP 本身是无状态且明文的，所以生产环境要用 HTTPS，通过 TLS 保证机密性、完整性和服务端身份认证。

如果要做服务端主动通知，可以用短轮询、长轮询或 SSE；如果要做双向实时通信，就用 WebSocket。至于服务端如何找到对应用户，本质是后续请求或连接握手里携带 Cookie、Session ID、JWT 或 API Key，服务端验证后恢复 `user_id` 和权限。长连接场景还会维护 `user_id -> connection_id -> gateway_node` 的映射，用于定向推送。
