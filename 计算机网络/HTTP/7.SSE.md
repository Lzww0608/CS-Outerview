# 7.SSE

SSE（Server-Sent Events）是一种基于 HTTP 的服务器向客户端推送消息的机制。客户端通过普通 HTTP 请求建立连接，服务端保持这个响应不关闭，并持续以 `text/event-stream` 格式向客户端发送事件。

## 1. SSE 和 HTTP 是什么关系？

SSE 不是 HTTP 的替代品，而是运行在 HTTP 之上的一种流式响应方式。

普通 HTTP 请求通常是：

```text
client -> request
server -> response
连接结束或复用
```

SSE 是：

```text
client -> GET /events
server -> HTTP 200 Content-Type: text/event-stream
server -> event chunk
server -> event chunk
server -> event chunk
连接长期保持
```

也就是说，SSE 仍然使用 HTTP 请求头、响应头、状态码、代理、Cookie、鉴权等机制，只是响应体变成了持续输出的事件流。

## 2. SSE 是单向的吗？

SSE 是 **服务端到客户端的单向推送**。

客户端可以通过普通 HTTP 请求向服务端发送数据，但这不是同一条 SSE 连接里的双向通信。如果需要同一连接上的全双工通信，通常选择 WebSocket。

## 3. 数据格式

SSE 响应头通常是：

```http
Content-Type: text/event-stream
Cache-Control: no-cache
Connection: keep-alive
```

事件格式：

```text
id: 1001
event: message
data: hello

```

空行表示一个事件结束。常见字段：

| 字段 | 作用 |
| --- | --- |
| `data` | 事件数据，可出现多行 |
| `event` | 事件类型 |
| `id` | 事件 ID，断线重连时可通过 `Last-Event-ID` 续传 |
| `retry` | 建议客户端重连间隔，单位毫秒 |

## 4. 客户端示例

浏览器可以直接使用 `EventSource`：

```js
const source = new EventSource("/events");

source.onmessage = (event) => {
  console.log(event.data);
};

source.addEventListener("done", (event) => {
  console.log("done", event.data);
});

source.onerror = () => {
  console.log("connection error, browser will retry");
};
```

## 5. 和 WebSocket 的区别

| 对比项 | SSE | WebSocket |
| --- | --- | --- |
| 通信方向 | 服务端到客户端单向推送 | 全双工 |
| 协议基础 | HTTP 长响应 | HTTP Upgrade 后切换协议 |
| 浏览器 API | `EventSource` | `WebSocket` |
| 数据格式 | 文本事件流，UTF-8 | 文本或二进制 |
| 重连 | 浏览器原生支持自动重连 | 需要业务自己实现 |
| 适用场景 | 通知、进度、日志、LLM 流式输出 | IM、协同编辑、游戏、双向实时交互 |

## 6. 真实场景

SSE 适合服务端持续输出、客户端主要接收的场景：

1. 大模型流式回答。
2. 任务进度推送。
3. 日志实时查看。
4. 告警和通知。
5. 后台管理页面的状态刷新。

在 RAG 或 AI 应用里，SSE 很常见：用户提交问题后，后端调用模型生成答案，并把 token 或片段通过 SSE 持续返回给前端，用户可以边生成边看到结果。

## 6.1 SSE 和 HTTP 各版本

SSE 只规定了应用层事件格式，不强绑定某个 HTTP 版本。不同版本的承载方式和限制不同：

| HTTP 版本 | SSE 承载方式 | 注意事项 |
| --- | --- | --- |
| HTTP/1.1 | 长响应，常配合 `Transfer-Encoding: chunked` 分块发送 | 浏览器对同域名连接数有限，多个 SSE 连接可能挤占普通请求连接 |
| HTTP/2 | 多路复用下的一个 stream，事件数据放在 DATA frame 中 | 连接数压力更小，但仍受 TCP 丢包造成的连接级队头阻塞影响 |
| HTTP/3 | QUIC stream 上传输 HTTP 语义 | 弱网和移动场景更友好，但服务端、代理和网关支持度要验证 |

LLM 流式输出里常见链路是：

```text
POST /chat 创建任务
-> 后端开始调用模型或 agent
-> GET /chat/{taskId}/events 建立 SSE
-> 服务端持续写 data/event/id
-> done 事件结束
```

响应头通常需要：

```http
Content-Type: text/event-stream
Cache-Control: no-cache
Connection: keep-alive
X-Accel-Buffering: no
```

`X-Accel-Buffering: no` 常用于提示 Nginx 不要缓冲响应。不同代理还可能需要关闭 gzip、调大 idle timeout、配置 flush 策略，否则服务端已经写出 token，浏览器却迟迟看不到。

## 6.2 stdio 流和 SSE 的区别

面试里同时问 stdio 和 SSE，通常想区分“进程内字节流”和“网络事件流”。

1. **stdio**：标准输入、标准输出、标准错误，面向本机进程或父子进程管道，典型场景是 CLI 工具、子进程输出、MCP stdio transport。
2. **SSE**：基于 HTTP 响应的浏览器友好事件流，典型场景是 Web 页面接收服务端进度、日志和大模型 token。
3. **桥接方式**：后端可以读取子进程 stdout 或模型 SDK 的流式回调，再转换成 `data: ...\n\n` 写到 SSE 响应。
4. **边界处理**：stdio 是原始字节流，需要自己按行、长度或协议解析；SSE 有 event/data/id/retry 和空行结束事件的格式。

所以 stdio 更像本地传输通道，SSE 更像面向浏览器的 HTTP 流式协议封装。两者都可能是流，但可靠性、鉴权、代理、重连和可观测性完全不同。

## 7. 易错点

1. SSE 本质是 HTTP，不是独立传输层协议。
2. SSE 默认是单向推送，不适合强双向交互。
3. `EventSource` 默认使用 GET，请求体不适合放复杂参数，复杂输入通常先 POST 创建任务，再 SSE 订阅任务输出。
4. 经过 Nginx 等代理时，要注意关闭响应缓冲，否则服务端写出的事件可能被代理攒住。
5. 长连接要处理心跳和超时，常用注释行 `: ping\n\n` 保活。
6. HTTP/2 可以降低多连接压力，但不能消除 TCP 层丢包导致的队头阻塞；HTTP/3 才把可靠性拆到 QUIC stream 层。

## 8. 面试回答模板

SSE 是基于 HTTP 的服务端推送技术。客户端发起一个普通 HTTP GET 请求，服务端返回 `text/event-stream`，并保持连接不断开，后续持续向响应体写入事件。它和 HTTP 的关系是：SSE 复用了 HTTP 的连接、头部、状态码、Cookie 和代理能力，只是响应变成了流式事件。

SSE 是单向的，方向是服务端到客户端。客户端要发送数据仍然要走普通 HTTP 请求。如果需要同一条连接双向通信，应该用 WebSocket。SSE 更适合通知、任务进度、日志推送和大模型流式输出。
