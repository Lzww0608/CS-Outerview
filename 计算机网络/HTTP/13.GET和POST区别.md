# GET 和 POST 的区别

GET 和 POST 都是 HTTP 请求方法。面试里不要只回答“GET 参数在 URL，POST 参数在 body”，更重要的是语义、安全性、幂等性、缓存和工程约束。

## 1. 语义区别

1. **GET**：获取资源，不应该修改服务端资源。
2. **POST**：提交数据给服务端处理，常用于创建资源、提交表单、触发非幂等动作。

HTTP 方法语义是约定，不是技术强制。服务端完全可以把 GET 写成修改数据，但这违反规范，也会导致缓存、预取、爬虫和重试带来风险。

## 2. 安全性和幂等性

| 方法 | 安全 | 幂等 | 说明 |
| --- | --- | --- | --- |
| GET | 是 | 是 | 多次获取同一资源，不应改变服务端状态 |
| POST | 否 | 通常否 | 多次提交可能创建多条记录或重复扣款 |

安全不是“加密安全”，而是“不修改资源”。幂等是“执行一次和执行多次对资源状态影响相同”。

## 3. 参数位置和长度

GET 常把参数放在 URL query 中：

```http
GET /search?q=cpp&page=1 HTTP/1.1
```

POST 常把参数放在请求体中：

```http
POST /orders HTTP/1.1
Content-Type: application/json

{"sku":"A100","count":1}
```

HTTP 协议本身没有规定 URL 的统一最大长度，但浏览器、代理、网关和服务端都有各自限制。POST body 也不是无限大，通常受网关、框架和业务配置限制。

## 4. 缓存和重试

GET 更容易被浏览器、代理、CDN 缓存，也可能被浏览器预取、爬虫访问或自动重试。POST 默认不适合缓存，重试也要非常谨慎。

真实工程里：

1. 查询、分页、筛选适合 GET。
2. 登录、下单、支付、提交表单适合 POST。
3. POST 如果需要防重复，要配合幂等号、唯一请求号或业务去重表。
4. GET URL 会进入浏览器历史、日志、Referer，不适合放密码、token 等敏感信息。

## 5. GET 能不能带 body

协议层并没有绝对禁止 GET body，但语义不清晰，很多代理、网关、框架不会处理或会丢弃 GET body。工程上应避免依赖 GET body，复杂查询可以：

1. 保持 GET，把查询条件编码到 query 中。
2. 使用 POST 创建查询任务或提交复杂查询条件。
3. 用服务端保存查询条件，GET 只携带查询 ID。

## 6. 面试回答模板

GET 的语义是获取资源，安全且幂等，参数通常放在 URL query 中，适合查询并天然更容易被缓存；POST 的语义是提交数据处理，通常不安全也不幂等，参数常放在 body 中，适合创建资源、提交表单、下单支付等会改变状态的操作。两者不是安全性的区别，HTTPS 下 GET 和 POST 都会被加密；但 GET URL 可能出现在历史、日志和 Referer 中，所以敏感信息不要放 URL。复杂查询不要依赖 GET body，工程兼容性不好。
