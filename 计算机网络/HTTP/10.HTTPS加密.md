# 10. HTTPS 加密

## 1. HTTPS 加密解决什么问题

HTTPS = HTTP + TLS。它主要解决三类问题：

1. **机密性**：传输内容被加密，中间人无法直接读取 HTTP 内容。
2. **完整性**：报文被篡改会被发现。
3. **身份认证**：客户端通过证书链验证服务端是否真的是目标域名。

HTTPS 不是单纯“用公钥加密全部数据”。真实流程是：非对称密码用于身份认证和密钥协商，对称密码用于加密大量应用数据。

## 2. TLS 加密的基本流程

以 TLS 1.3 为例：

1. 客户端发送 `ClientHello`，带支持的 TLS 版本、加密套件、随机数、key share、SNI 等。
2. 服务端返回 `ServerHello`，选择算法并返回自己的 key share。
3. 双方用 ECDHE 等密钥交换算法计算共享密钥。
4. 服务端发送证书和签名，客户端验证证书链、域名、有效期、吊销状态等。
5. 双方通过 HKDF 派生握手密钥和应用数据密钥。
6. 后续 HTTP 请求响应使用对称加密算法传输，例如 AES-GCM 或 ChaCha20-Poly1305。

## 3. 为什么不用 RSA 直接加密所有数据

1. 非对称加密性能远低于对称加密。
2. 大数据加密不适合直接用 RSA。
3. TLS 1.3 已移除静态 RSA 密钥交换，强制使用具备前向安全性的临时密钥交换。
4. ECDHE 可以保证即使服务器私钥将来泄露，历史会话数据也难以被解密。

## 4. 证书验证做了什么

客户端验证服务端证书时，通常关注：

1. 证书链是否能追溯到受信任 CA。
2. 证书域名是否匹配访问域名。
3. 证书是否过期。
4. 证书用途是否符合服务端认证。
5. 证书是否被吊销，工程上可能通过 OCSP、CRL 或 OCSP Stapling。

如果 DNS 被污染到错误 IP，但攻击者没有目标域名的合法证书，TLS 证书校验会失败。这也是 HTTPS 能缓解 DNS 劫持后伪站攻击的原因。

## 5. 对称加密、非对称加密、摘要和签名

HTTPS 里几类密码学工具分工不同：

1. **对称加密**：AES-GCM、ChaCha20-Poly1305，加密应用数据，性能高。
2. **非对称密钥交换**：ECDHE，用于协商共享密钥。
3. **数字签名**：服务端用证书私钥签名握手上下文，客户端用证书公钥验证身份。
4. **摘要/HKDF**：用于完整性校验、密钥派生和握手 transcript 绑定。

### 公钥、私钥和数字证书

公钥和私钥是一对非对称密钥。私钥由持有者保密，公钥可以公开。用法要区分两个方向：

1. **加密场景**：别人用你的公钥加密，只有你的私钥能解密。
2. **签名场景**：你用私钥签名，别人用你的公钥验证签名确实来自你。

HTTPS 里的证书不是简单的一段公钥，而是 CA 对“域名、主体信息、公钥、有效期、用途”等信息做签名后的文件。客户端信任操作系统或浏览器内置的根 CA，再沿证书链验证中间 CA 和站点证书，最终确认“这个公钥确实属于正在访问的域名”。

因此，证书解决的是公钥归属问题。如果没有证书，攻击者可以在中间人攻击中替换成自己的公钥；客户端虽然也能建立加密连接，但实际是在和攻击者加密通信。

### HTTPS 如何防范中间人攻击

中间人攻击的关键是攻击者试图截获连接并伪装成服务端。HTTPS 的防护来自证书校验和握手绑定：

1. 服务端返回包含公钥的证书链。
2. 客户端验证证书链是否由受信任 CA 签发。
3. 客户端验证证书域名、有效期、用途和吊销状态。
4. 服务端用证书私钥对握手上下文签名，证明自己持有该证书对应私钥。
5. 握手 transcript 会参与密钥派生，攻击者篡改握手参数会导致校验失败。

如果攻击者没有目标域名的合法证书和对应私钥，就无法通过客户端验证。真实风险通常来自用户忽略证书错误、设备被安装恶意根证书、CA 误签、私钥泄漏或应用关闭证书校验。

## 6. 易错点

1. HTTPS 不是只用非对称加密；应用数据主要用对称加密。
2. 证书用于身份认证，不是用来加密所有 HTTP 内容。
3. TLS 1.3 不再使用静态 RSA 密钥交换。
4. HTTPS 不能阻止 DNS 解析被篡改，但能阻止没有合法证书的伪站完成 TLS 验证。
5. 0-RTT 有重放风险，只适合幂等请求。

## 7. HTTPS 是否一定安全

HTTPS 提供的是传输层安全，不代表业务系统绝对安全。常见风险包括：

1. 客户端忽略证书错误，或被安装恶意根证书后遭遇中间人代理。
2. CA 误签、证书私钥泄露、证书过期或吊销检查失效。
3. 服务器端被入侵，TLS 只能保护链路，不能保护已经落到服务端的明文。
4. 页面混合加载 HTTP 资源，脚本或图片可能被篡改。
5. 使用过旧 TLS 版本、弱加密套件或错误配置。
6. TLS 1.3 0-RTT 存在重放风险，只应承载幂等请求。
7. 应用层仍可能有 XSS、CSRF、SQL 注入、越权等漏洞。

所以回答“HTTPS 安全吗”时应强调：它能解决传输过程中的窃听、篡改和服务器身份认证问题，但不能替代证书管理、服务端安全、浏览器安全策略和应用层安全设计。

## 8. HTTPS 太慢如何优化

HTTPS 的额外开销主要来自握手往返、证书验证和加解密。常见优化手段：

1. 使用 TLS 1.3，减少握手 RTT，并使用更现代的加密套件。
2. 开启会话复用，如 session ticket、PSK，减少重复握手成本。
3. 谨慎使用 0-RTT，只承载幂等请求，避免重放风险。
4. 使用 HTTP/2 或 HTTP/3 复用连接，减少频繁建连。
5. 保持长连接和连接池，避免每个请求都重新握手。
6. 使用 ECDSA 证书、AES-NI 或 ChaCha20-Poly1305 等更适合硬件/移动端的算法组合。
7. 开启 OCSP Stapling，减少客户端额外查询证书吊销状态的延迟。
8. 通过 CDN 或边缘节点做 TLS 终止，降低用户到入口的 RTT。
9. 减少跨域资源域名数量，配合 HSTS、preconnect 等浏览器优化。

实际场景中，现代 TLS 的对称加解密开销通常不是主要瓶颈，更多瓶颈来自建连 RTT、证书链验证、后端处理和网络质量。

## 9. 面试回答模板

HTTPS 本质是 HTTP over TLS。握手阶段，客户端和服务端通过 ECDHE 协商共享密钥，并通过服务端证书完成身份认证；双方再用 HKDF 派生出会话密钥。真正传输 HTTP 数据时使用 AES-GCM 或 ChaCha20-Poly1305 这类对称加密，性能更好。证书链、域名、有效期和签名验证保证客户端连到的是目标服务端；同时 TLS 还能保证报文完整性，防止中间人篡改。
