# 8. HTTP 连接建立过程

严格来说，HTTP 本身是应用层请求/响应协议，没有像 TCP 那样的“握手”。面试里问“HTTP 握手过程”，通常是在问一次 HTTP/HTTPS 请求从建连到发请求的完整链路。

## HTTP 请求过程

以 HTTP/1.1 over TCP 为例：

1. **DNS 解析**：把域名解析成 IP 地址。
2. **TCP 三次握手**：客户端和服务端建立可靠连接。
3. **发送 HTTP 请求**：客户端发送请求行、请求头、请求体。
4. **服务端处理并响应**：服务端返回状态行、响应头、响应体。
5. **连接复用或关闭**：HTTP/1.1 默认 keep-alive，可以复用 TCP 连接；关闭时走 TCP 四次挥手。

```text
DNS -> TCP SYN/SYN+ACK/ACK -> HTTP Request -> HTTP Response -> keep-alive/close
```

## HTTPS 请求过程

HTTPS = HTTP + TLS。相比 HTTP，多了 TLS 握手：

1. DNS 解析域名。
2. TCP 三次握手。
3. TLS 握手：协商协议版本、加密套件、密钥材料，验证服务端证书。
4. 用协商出的会话密钥加密传输 HTTP 请求和响应。

TLS 1.2 完整握手通常需要 2-RTT，TLS 1.3 完整握手通常是 1-RTT，并支持有重放风险的 0-RTT。

## HTTP/2 和 HTTP/3 的区别

1. **HTTP/2**：通常仍然跑在 TCP + TLS 上，TLS 完成后会发送连接前言和 SETTINGS 帧，然后通过 stream 多路复用请求。
2. **HTTP/3**：跑在 QUIC 上，QUIC 基于 UDP，并把传输层建连和 TLS 1.3 握手合并，减少握手时延，也避免 TCP 层队头阻塞。

## 易错点

1. HTTP 不是传输层协议，真正负责连接建立的是 TCP 或 QUIC。
2. HTTPS 不只是“加密 HTTP 内容”，还包括证书校验和密钥协商。
3. Keep-Alive 复用的是已有连接，后续请求不需要重复 TCP/TLS 握手。
4. 如果是短连接，每个请求都要重复建连，延迟和系统开销都会显著增加。
