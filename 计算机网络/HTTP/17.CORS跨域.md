# 17. CORS 跨域

跨域问题是浏览器的同源策略导致的。它不是后端接口“不能被访问”，而是浏览器为了安全限制前端 JavaScript 读取不同源的响应。

## 1. 什么是同源

同源要求三者都相同：

1. 协议相同，例如 `https`。
2. 域名相同，例如 `api.example.com`。
3. 端口相同，例如 `443`。

下面这些都算跨域：

```text
https://www.example.com -> https://api.example.com
http://example.com      -> https://example.com
https://example.com     -> https://example.com:8443
```

同源策略主要限制浏览器脚本读取跨源响应，目的是防止恶意网站利用用户登录态读取其他站点的敏感数据。

## 2. CORS 是什么

CORS（Cross-Origin Resource Sharing）是浏览器和服务器约定的一套跨域访问机制。服务器通过响应头告诉浏览器：哪些来源、方法、请求头可以访问当前资源。

核心响应头：

| 响应头 | 作用 |
| --- | --- |
| `Access-Control-Allow-Origin` | 允许哪些 Origin |
| `Access-Control-Allow-Methods` | 允许哪些 HTTP 方法 |
| `Access-Control-Allow-Headers` | 允许哪些自定义请求头 |
| `Access-Control-Allow-Credentials` | 是否允许携带 Cookie/认证信息 |
| `Access-Control-Max-Age` | 预检结果缓存时间 |

## 3. 简单请求和预检请求

满足特定条件的请求是简单请求，例如 `GET/POST/HEAD`，且请求头和 `Content-Type` 受限。简单请求会直接发送，浏览器收到响应后检查 CORS 头，决定是否把响应暴露给 JS。

复杂请求会先发预检请求：

```http
OPTIONS /api/orders HTTP/1.1
Origin: https://www.example.com
Access-Control-Request-Method: POST
Access-Control-Request-Headers: authorization, content-type
```

服务器允许后返回：

```http
Access-Control-Allow-Origin: https://www.example.com
Access-Control-Allow-Methods: POST
Access-Control-Allow-Headers: authorization, content-type
Access-Control-Max-Age: 600
```

浏览器再发送真正的业务请求。

## 4. 为什么用户访问会有跨域问题

常见原因：

1. 前端页面部署在 `www.example.com`，API 部署在 `api.example.com`。
2. 本地开发时前端是 `localhost:3000`，后端是 `localhost:8080`。
3. 前端带了 `Authorization`、自定义 header 或 JSON `Content-Type`，触发预检。
4. 请求携带 Cookie，但后端没设置 `Access-Control-Allow-Credentials: true`。
5. 后端允许了 `Origin`，但网关、Nginx 或错误响应没有带 CORS 头。
6. 预检 `OPTIONS` 被鉴权中间件、网关或防火墙拦截。

## 5. 怎么解决

后端或网关统一处理 CORS：

1. 白名单匹配允许的 `Origin`，不要对生产接口无脑 `*`。
2. 正确响应 `OPTIONS` 预检请求。
3. 明确允许的方法和请求头。
4. 如果需要 Cookie，设置 `Access-Control-Allow-Credentials: true`，同时 `Allow-Origin` 不能是 `*`。
5. 确保错误响应也带 CORS 头，否则前端只看到跨域失败，看不到真实错误。
6. 本地开发可以用 dev server proxy，把跨域问题变成同源代理。

Nginx 示例：

```nginx
add_header Access-Control-Allow-Origin "https://www.example.com" always;
add_header Access-Control-Allow-Methods "GET,POST,PUT,DELETE,OPTIONS" always;
add_header Access-Control-Allow-Headers "Authorization,Content-Type" always;

if ($request_method = OPTIONS) {
    return 204;
}
```

生产中更推荐在网关或服务端中间件统一配置，并按环境区分白名单。

## 6. 易错点

1. CORS 是浏览器限制，不是 curl 或服务端之间调用的限制。
2. `Access-Control-Allow-Origin: *` 不能和凭证请求一起使用。
3. 预检失败时真正的业务请求不会发出。
4. 跨域失败不等于后端没响应，可能是浏览器拒绝把响应交给 JS。
5. 只给成功响应加 CORS 头不够，401/403/500 也要加，否则前端排查困难。
6. WebSocket 不走标准 CORS 流程，但也要校验 `Origin` 防止跨站滥用。

## 7. 面试回答模板

跨域来自浏览器同源策略，同源要求协议、域名和端口都一致。前端 JS 访问不同源 API 时，浏览器会要求服务端通过 CORS 头声明允许访问。简单请求直接发，复杂请求会先发 `OPTIONS` 预检，服务端要返回允许的 Origin、Method、Headers。解决时通常在网关或后端中间件配置 Origin 白名单、处理预检、允许必要 Header；如果携带 Cookie，还要设置 `Access-Control-Allow-Credentials: true`，并且 `Allow-Origin` 不能是 `*`。注意 CORS 是浏览器安全策略，服务端调用服务端不受它限制。
