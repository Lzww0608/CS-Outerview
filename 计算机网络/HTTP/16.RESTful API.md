# 16. RESTful API

RESTful API 是一种面向资源的接口设计风格。它不是某个具体协议，而是基于 HTTP 方法、URI、状态码和表示层来组织服务端资源访问。

## RESTful 的核心思想

REST 关注资源，而不是把接口设计成一批动作函数。

```text
GET    /users/1001        查询用户
POST   /users             创建用户
PUT    /users/1001        整体替换用户
PATCH  /users/1001        局部修改用户
DELETE /users/1001        删除用户
```

资源用名词表达，动作交给 HTTP 方法表达。响应通常使用 JSON，也可以使用 XML、Protobuf 或其他表示格式。

## HTTP 方法语义

| 方法 | 语义 | 是否安全 | 是否幂等 |
| --- | --- | --- |
| GET | 查询资源 | 是 | 是 |
| POST | 创建资源或提交动作 | 否 | 通常否 |
| PUT | 整体替换资源 | 否 | 是 |
| PATCH | 局部更新资源 | 否 | 通常需要额外设计 |
| DELETE | 删除资源 | 否 | 是 |

安全表示请求不应修改服务端状态；幂等表示同一个请求执行一次和执行多次的最终效果一致。幂等不代表响应完全相同，例如重复 `DELETE` 第一次返回 `204`，第二次可能返回 `404`。

## 状态码设计

常见状态码：

1. `200 OK`：请求成功并返回内容。
2. `201 Created`：资源创建成功，常配合 `Location` 响应头。
3. `204 No Content`：请求成功但无响应体，删除成功常用。
4. `400 Bad Request`：参数格式或业务校验失败。
5. `401 Unauthorized`：未认证。
6. `403 Forbidden`：已认证但无权限。
7. `404 Not Found`：资源不存在。
8. `409 Conflict`：资源版本冲突、重复提交、状态不允许迁移。
9. `429 Too Many Requests`：触发限流。
10. `500/502/503`：服务端或下游异常。

## 设计注意事项

1. **URI 使用名词**：优先 `/orders/{id}`，少用 `/getOrder`。
2. **版本管理**：可以用 `/v1/orders`，也可以通过 Header 管理版本。
3. **分页排序过滤**：用 query 参数表达，例如 `/orders?status=paid&page=1&page_size=20`。
4. **错误响应统一**：包含错误码、错误消息、请求 ID 和可定位字段。
5. **幂等设计**：支付、下单、重试接口要使用幂等 key 或唯一约束。
6. **认证授权**：常用 Cookie Session、JWT、OAuth2、API Key 等。
7. **并发更新**：可用版本号、`ETag`、`If-Match` 或数据库条件更新避免覆盖。

## RESTful 和 RPC 的区别

RESTful 偏资源建模，适合开放 API、CRUD、跨团队接口和浏览器生态；RPC 偏动作调用，适合内部服务间强类型、高性能、复杂命令式接口，例如 gRPC、Thrift、Dubbo。

实际工程不必教条。比如“订单支付”既可以设计成：

```text
POST /orders/{id}/payment
```

也可以作为 RPC 方法：

```text
PayOrder(order_id, idempotency_key)
```

关键是语义清晰、幂等可控、错误码稳定、监控和文档完整。

## 面试回答模板

RESTful API 是基于 HTTP 的资源导向接口风格，用 URI 表示资源，用 GET、POST、PUT、PATCH、DELETE 表示操作，用状态码表达结果。设计时要关注方法的安全性和幂等性、统一错误响应、分页过滤、版本管理、认证授权和并发更新。REST 更适合开放资源接口，内部高性能调用可以选择 gRPC 等 RPC 框架。
