# 18. 建立连接常用超时时间

面试里问“建立连接时常用的超时时间有哪些，分别起什么作用”，不要只回答 `connect timeout`。真实后端一次 HTTP/RPC 调用可能经历 DNS、连接池、TCP 三次握手、TLS 握手、代理隧道、写请求、等待响应、读取响应、连接复用和空闲回收。不同阶段要用不同 timeout 控制，否则排查时会把“连不上”“连上但握手慢”“服务端处理慢”“响应读不完”混在一起。

## 1. 一次请求的超时链路

以 HTTPS 请求为例：

```text
获取连接
  -> 连接池等待
  -> DNS 解析
  -> TCP connect（三次握手）
  -> TLS handshake
  -> 写请求头/请求体
  -> 等待响应首字节或响应头
  -> 读取响应体
  -> keep-alive 复用或空闲回收
```

对应 timeout：

| 超时 | 控制阶段 | 主要作用 |
| --- | --- | --- |
| 总超时 / deadline | 整个调用 | 防止一次请求无限占用线程、连接和业务资源 |
| 连接池等待超时 | 从连接池拿连接 | 防止连接池耗尽时请求一直排队 |
| DNS 解析超时 | 域名解析 | 防止 DNS 服务慢或不可达拖住建连 |
| TCP connect timeout | TCP 三次握手 | 防止目标不可达、丢包、黑洞网络导致一直等待 |
| TLS handshake timeout | TLS 握手 | 防止证书、加密协商、服务端负载导致握手卡住 |
| 代理 CONNECT 超时 | HTTP 代理或隧道 | 防止代理建立隧道慢或失败 |
| 写超时 | 发送请求 | 防止对端读得慢、本机发送缓冲区堵住 |
| 响应头超时 / TTFB 超时 | 请求发出后等首包 | 防止服务端处理慢或上游挂起 |
| 读超时 / idle read timeout | 读取响应体 | 防止响应体传输中途卡住 |
| keep-alive idle timeout | 空闲连接 | 回收长时间不用的连接，避免 fd 和中间设备状态浪费 |
| 最大连接生命周期 | 连接整体寿命 | 避免长期连接遇到负载均衡、DNS 变更、服务滚动发布后不刷新 |

## 2. DNS 解析超时

DNS timeout 控制“域名解析成 IP”的时间。很多人把连接慢都归因于 TCP，但请求卡在建连前也可能是 DNS 慢、DNS 包丢失、递归解析异常或本地 DNS 缓存失效。

作用：

1. 防止 DNS 服务器不可达时业务线程长时间阻塞。
2. 让客户端可以切换备用 DNS、使用缓存或快速失败。
3. 便于区分“域名解析失败”和“目标 IP 连不上”。

注意点：

1. `getaddrinfo()` 在很多环境里是阻塞调用，线程池里大量 DNS 阻塞会拖垮请求处理。
2. DNS 可能返回多个 A/AAAA 记录，客户端要考虑 IPv6/IPv4 选择、Happy Eyeballs 和失败切换。
3. DNS 缓存 TTL 不能无限长，否则服务扩缩容或故障切换后仍访问旧 IP。

真实场景：

```text
域名解析 200ms
TCP connect 20ms
TLS handshake 40ms
服务处理 30ms
```

如果只看总耗时 290ms，可能误以为服务端慢；拆出 DNS timeout 和耗时后，才能定位到解析链路。

## 3. 连接池等待超时

连接池等待超时也叫 connection request timeout、pool acquire timeout。它控制“从连接池拿到一条可用连接”的等待时间。

作用：

1. 防止连接池满时请求无限排队。
2. 保护调用方线程和内存队列。
3. 暴露下游慢、连接泄漏、连接池太小、并发过高等问题。

例子：

```text
最大连接数 100
当前 100 条连接都在等待慢下游响应
第 101 个请求如果没有连接池等待超时，就会一直排队
```

处理方式：

1. 给连接池设置最大连接数和等待超时。
2. 对不同下游设置独立连接池，避免慢下游拖垮所有依赖。
3. 监控连接池活跃连接数、空闲连接数、等待队列长度和 acquire timeout 次数。
4. 连接用完必须归还，响应体未关闭会导致连接泄漏。

## 4. TCP connect timeout

TCP connect timeout 控制 TCP 三次握手阶段。客户端发出 SYN 后，如果目标不可达、路径丢包、防火墙静默丢弃、对端 SYN backlog 满或网络黑洞，就可能一直等内核重传。

作用：

1. 限制三次握手最长等待时间。
2. 快速识别目标端口不可达、链路异常或防火墙丢包。
3. 为多 IP、主备机房、服务发现重试留出时间。

它和内核的 SYN 重传不同：

1. 内核有自己的 SYN 重传和最终失败策略。
2. 应用设置的 connect timeout 通常比内核默认更短。
3. 非阻塞 connect 常见做法是 `connect()` 返回 `EINPROGRESS` 后，用 `poll/epoll/select` 等待可写，再用 `getsockopt(SO_ERROR)` 判断结果。

伪代码：

```cpp
int ret = connect(fd, addr, len);
if (ret < 0 && errno == EINPROGRESS) {
    // epoll/poll 等待 fd 可写，最多等待 connect_timeout
    // 可写后用 SO_ERROR 判断是否连接成功
}
```

常见错误：

1. 把 `ECONNREFUSED` 当成 timeout。`ECONNREFUSED` 通常是对端主动 RST，失败很快。
2. 防火墙静默丢包会表现为 connect timeout，而不是连接拒绝。
3. connect timeout 设得太短会误杀跨地域或弱网请求；太长会拖垮线程和连接池。

## 5. TLS handshake timeout

HTTPS 在 TCP 连接建立后，还要进行 TLS 握手。TLS handshake timeout 控制证书校验、密钥协商、ALPN、SNI 等握手阶段。

作用：

1. 防止 TCP 已连上但 TLS 握手卡住。
2. 区分网络层连通和安全层失败。
3. 避免服务端 TLS 计算、证书链、OCSP、客户端证书校验过慢拖住连接。

常见原因：

1. 服务端证书链配置错误。
2. SNI 不匹配，服务端返回错误证书。
3. 客户端和服务端 TLS 版本或加密套件不兼容。
4. 服务端 CPU 高，握手处理慢。
5. mTLS 双向认证中客户端证书验证慢或失败。

HTTP/2、HTTP/3 还会在握手中涉及 ALPN 协商。TLS 握手成功不代表 HTTP 请求成功，只说明安全通道建好了。

## 6. 写超时

写超时控制发送请求头或请求体的时间。对小请求来说写超时很少触发；对大文件上传、慢网络、对端不读数据、发送缓冲区满的场景很重要。

作用：

1. 防止请求体发送阶段无限阻塞。
2. 保护上传、流式写入、代理转发等大请求链路。
3. 避免下游读慢导致上游连接和内存一直被占用。

注意点：

1. TCP `send()` 成功只代表数据进入本机内核发送缓冲区，不代表对端应用已收到。
2. 非阻塞 I/O 下写超时通常是“多久没有写入进展”。
3. 写请求体前如果服务端已经返回错误，客户端还要能中断上传。

## 7. 响应头超时和首包超时

响应头超时也叫 response header timeout，TTFB timeout（time to first byte）更关注请求发出后等到第一个响应字节的时间。

作用：

1. 限制服务端处理请求的最长等待时间。
2. 防止上游应用线程卡死、DB 慢查询、锁等待、队列积压导致客户端无限等待。
3. 和 read timeout 区分：前者是等待响应开始，后者是响应开始后的读取过程。

例子：

```text
connect 20ms
TLS 40ms
write request 5ms
response header wait 2s
read body 10ms
```

这里慢的是服务端处理或上游依赖，不是建连。

工程上一般会给不同接口不同响应头超时：

1. 缓存查询、配置查询：几十到几百毫秒。
2. 普通内部 RPC：几百毫秒到几秒。
3. 报表、导出、AI 推理：需要单独长超时或异步任务化。

## 8. 读超时和空闲读超时

读超时控制读取响应体阶段。它有两种常见语义：

1. **整体读超时**：响应体必须在指定时间内读完。
2. **空闲读超时**：两次成功读取之间不能超过指定时间。

作用：

1. 防止响应体传输中途卡住。
2. 防止慢下游或慢客户端占住连接。
3. 保护流式接口和大响应下载。

注意点：

1. 对 SSE、WebSocket、长轮询、下载等长连接/流式接口，不能简单套普通短请求 read timeout。
2. 空闲读超时通常比整体读超时更适合流式传输：只要持续有数据就不超时。
3. 响应体不读完或不关闭，HTTP 连接池可能无法复用该连接。

## 9. 总超时和分阶段超时

总超时控制一次业务调用的最大生命周期。分阶段超时控制某个阶段不能卡住。

推荐做法：

```text
total deadline = 800ms
  DNS <= 50ms
  pool acquire <= 20ms
  TCP connect <= 100ms
  TLS handshake <= 150ms
  write <= 50ms
  response header <= 500ms
  read body <= 剩余预算
```

原则：

1. 总超时必须覆盖所有阶段，避免重试把总耗时无限放大。
2. 分阶段超时不能简单相加超过业务 SLA 太多。
3. 重试要受总 deadline 约束，不能每次重试都重新拿完整超时。
4. 超时后结果通常是“未知”，不一定代表请求没有到达服务端。

支付、下单、写数据库这类非幂等操作尤其要注意：客户端超时后服务端可能已经执行成功，不能简单重试导致重复扣款或重复创建。

## 10. Keep-Alive 空闲超时和连接生命周期

连接建立成功后，长连接会进入连接池。此时还需要：

1. **idle timeout**：空闲多久未使用就关闭。
2. **keep-alive timeout**：HTTP/网关允许连接空闲复用的时间。
3. **max connection lifetime**：连接最长存活时间。
4. **TCP keepalive**：内核层探测长期空闲连接是否仍可达。

作用：

1. 回收长期不用的 fd、内存和连接状态。
2. 避免 NAT、负载均衡、防火墙提前清理空闲连接后，客户端复用到“半死连接”。
3. 让客户端定期刷新 DNS、服务发现和负载均衡结果。
4. 避免服务滚动发布后老连接长期粘在旧实例上。

配置建议：

1. 客户端连接池 idle timeout 要略小于服务端或负载均衡 idle timeout。
2. 长连接业务用应用心跳刷新中间设备状态。
3. TCP keepalive 默认时间通常很长，只能做兜底，不适合作为业务秒级超时。

## 11. 服务端也有哪些连接超时

服务端接收连接时也需要一组 timeout：

| 超时 | 作用 |
| --- | --- |
| accept 队列等待 | 防止 accept 不及时导致连接堆积，通常通过 backlog 和监控体现 |
| TLS handshake timeout | 防止客户端连上后不完成 TLS 握手 |
| read header timeout | 防 Slowloris，防止客户端慢慢发请求头占连接 |
| read body timeout | 防止大请求体慢上传拖住连接 |
| write timeout | 防止慢客户端读响应太慢 |
| idle timeout | 回收 keep-alive 空闲连接 |
| request timeout | 限制单个请求在服务端处理总耗时 |

其中 `read header timeout` 很重要。攻击者可以建立大量连接，每条连接慢慢发送 HTTP 头，如果没有请求头超时和头部大小限制，服务端 fd 和内存会被耗尽。

## 12. Java/Go/网关里的常见名字

不同框架名字不同，但含义大体一致。

| 语义 | 常见名字 |
| --- | --- |
| 总超时 | `timeout`、`deadline`、`context deadline`、`call timeout` |
| 连接池等待 | `connectionRequestTimeout`、`poolAcquireTimeout` |
| TCP 建连 | `connectTimeout`、`dial timeout` |
| TLS 握手 | `TLSHandshakeTimeout`、`ssl handshake timeout` |
| 写请求 | `writeTimeout` |
| 等响应头 | `ResponseHeaderTimeout`、`readHeaderTimeout`、`TTFB timeout` |
| 读响应 | `readTimeout`、`socketTimeout`、`idle timeout` |
| 空闲连接 | `idleConnTimeout`、`keepAliveTimeout` |
| 连接寿命 | `maxConnectionAge`、`maxConnectionLifetime` |

Go 示例：

```go
client := &http.Client{
    Timeout: 800 * time.Millisecond, // 总超时
    Transport: &http.Transport{
        DialContext: (&net.Dialer{
            Timeout:   100 * time.Millisecond, // TCP connect
            KeepAlive: 30 * time.Second,
        }).DialContext,
        TLSHandshakeTimeout:   150 * time.Millisecond,
        ResponseHeaderTimeout: 500 * time.Millisecond,
        IdleConnTimeout:       60 * time.Second,
        MaxIdleConnsPerHost:   100,
    },
}
```

Java/Apache HttpClient 常见：

```text
connectionRequestTimeout：从连接池拿连接的等待时间
connectTimeout：TCP 建连时间
socketTimeout / responseTimeout：读响应数据的等待时间
```

## 13. 超时设置的工程原则

1. **按阶段拆指标**：DNS、connect、TLS、TTFB、read、pool acquire 分开打点。
2. **总 deadline 兜底**：任何分阶段超时都不能突破业务总预算。
3. **按下游分级**：核心链路、慢任务、外部三方接口不要共用一套超时。
4. **重试要有限制**：只对幂等、可重入、明确可重试错误重试；使用指数退避和抖动。
5. **超时不等于失败语义明确**：写请求后超时通常是未知状态，要查单、幂等或补偿。
6. **连接池要有限流**：最大连接数、等待队列、空闲回收和连接寿命都要设置。
7. **客户端超时小于上游网关超时**：调用方应先超时并释放资源，避免网关先断导致错误语义混乱。
8. **监控超时原因**：不要只统计一个 `timeout`，要区分 DNS timeout、connect timeout、read timeout、pool timeout。

## 14. 易错点

1. connect timeout 只覆盖 TCP 建连，不覆盖 DNS、TLS 和服务端处理。
2. read timeout 不等于总超时，很多库的 read timeout 是两次读之间的 idle timeout。
3. TCP keepalive 不是 HTTP Keep-Alive，也不是业务心跳。
4. 客户端超时后，服务端可能已经处理成功，写操作必须有幂等设计。
5. 连接池耗尽时看到的可能是 pool acquire timeout，不是下游 connect timeout。
6. 复用长连接时没有新建 TCP/TLS，所以不会触发 connect timeout 和 TLS handshake timeout。
7. 超时设得过长会造成线程、fd、连接池和队列被慢请求占满；设得过短会误杀正常请求。

## 15. 面试回答模板

建立连接相关的超时要分阶段说。一次 HTTPS/RPC 调用通常先从连接池拿连接，然后 DNS 解析、TCP connect、TLS 握手、写请求、等响应头、读响应体，最后连接可能进入 keep-alive 池。因此常见超时包括：连接池等待超时，防止连接池耗尽后无限排队；DNS 超时，防止解析卡住；connect timeout，控制 TCP 三次握手；TLS handshake timeout，控制证书和密钥协商；write timeout，控制请求发送；response header 或 TTFB timeout，控制服务端多久开始响应；read timeout，控制响应体读取；total timeout 或 deadline，控制整个调用生命周期；idle timeout 和 max connection lifetime，用来回收和刷新长连接。

工程上我会设置总 deadline，再按阶段设置子超时，并且把每个阶段耗时都打点。重试必须受总 deadline 限制，只对幂等请求重试。还要注意超时不一定代表服务端没执行，尤其是请求已经写出去之后超时，状态通常是未知的，需要幂等号、查单或补偿。服务端侧也要有 TLS 握手超时、请求头超时、请求体超时、写超时和空闲连接超时，防止慢连接和半开连接耗尽资源。
