# 12. 长连接与短连接

长连接和短连接描述的是连接复用策略。短连接通常是一次请求响应后关闭连接；长连接会在一次建连后复用同一条连接发送多个请求。

## 短连接

短连接流程：

```text
TCP 握手 -> 请求 -> 响应 -> TCP 挥手
```

优点：

1. 实现简单，连接生命周期清晰。
2. 服务端长期维护的连接少。
3. 对低频、简单请求足够。

缺点：

1. 每个请求都要重复 TCP 握手，HTTPS 还要重复 TLS 握手或恢复。
2. 高并发下容易产生大量 `TIME_WAIT`、端口和 fd 压力。
3. 延迟高，吞吐差。

## 长连接

长连接流程：

```text
TCP/TLS 握手 -> 请求1/响应1 -> 请求2/响应2 -> ... -> 空闲超时或主动关闭
```

优点：

1. 复用 TCP/TLS 连接，减少握手 RTT 和 CPU 成本。
2. 降低端口、连接建立和关闭开销。
3. 适合 HTTP Keep-Alive、HTTP/2、多次 RPC、数据库连接池、WebSocket 等。

缺点：

1. 服务端需要维护更多 fd、内存、连接状态和心跳。
2. 空闲连接要有超时回收策略。
3. 大量长连接需要 epoll/kqueue/io_uring 等事件驱动模型，而不是一连接一线程。

## HTTP 中的长连接

1. HTTP/1.0 默认短连接，可通过 `Connection: keep-alive` 使用长连接。
2. HTTP/1.1 默认长连接，除非 `Connection: close`。
3. HTTP/2 在一个连接上支持多个 stream 多路复用。
4. HTTP/3 基于 QUIC，在 UDP 上实现连接、加密和 stream。

## 什么时候用长连接，什么时候用短连接

选型看的是交互频率、建连成本、服务端状态成本和基础设施兼容性。

适合长连接的场景：

1. 高频交互或低延迟请求，例如 RPC、数据库连接池、IM、游戏、WebSocket 推送。
2. HTTPS 请求密集，复用连接可以减少 TCP/TLS 握手成本。
3. 服务端能用 epoll/kqueue/io_uring 管理大量 fd，并有心跳、限流和超时回收。

适合短连接的场景：

1. 低频、无状态、非交互式请求，例如偶发配置拉取、简单上报。
2. 连接间隔很长，长期保活反而浪费 fd、内存、心跳流量和电量，例如部分 IoT 设备。
3. 单次查询非常短，协议本身也偏无连接，例如传统 DNS 常用 UDP 请求响应。
4. 通过代理、网关或移动网络时，如果中间设备容易回收空闲连接，短连接或长轮询可能更稳定。

真实系统通常会混用：对内部高频调用使用连接池和长连接，对低频外部调用或一次性任务使用短连接；移动端和 IoT 还要把心跳频率、耗电和 NAT 超时一起纳入设计。

## Connection 选项的作用

`Connection` 是逐跳首部（hop-by-hop header），只对当前这一段连接有效，不会端到端透传到最终服务。它常见作用有两个：

1. 控制连接是否复用：`Connection: keep-alive` 或 `Connection: close`。
2. 声明哪些逐跳首部只对当前连接有效，代理转发时应移除这些首部。

示例：

```http
Connection: keep-alive
```

表示希望当前 TCP 连接在本次响应后继续复用。

```http
Connection: close
```

表示本次响应后关闭连接。HTTP/1.1 默认长连接，因此服务端想关闭时通常会显式返回 `Connection: close`。

逐跳首部示例：

```http
Connection: Upgrade
Upgrade: websocket
```

表示当前 HTTP 连接要升级为 WebSocket。代理如果不参与升级，不能盲目把逐跳语义当成端到端语义转发。

## 连接为什么会断开，谁来实现

连接断开不是只由某一层决定，而是应用层策略、传输层状态和中间网络设备共同作用的结果。

常见断开原因：

1. **应用层主动关闭**：HTTP 返回 `Connection: close`、服务端达到最大请求数、业务完成后主动关闭 socket。
2. **空闲超时**：服务端、客户端、反向代理、负载均衡器或防火墙发现连接长时间没有数据，主动回收连接。
3. **异常退出**：进程崩溃、容器重启、机器宕机，可能表现为 FIN、RST 或对端长时间无响应。
4. **网络异常**：链路中断、NAT 表项过期、移动网络切换、路由变化，连接两端可能只能通过读写失败或心跳超时发现。
5. **协议错误或资源保护**：请求格式错误、TLS 错误、连接数过高、后端过载时，服务端可能直接关闭或发送 RST。

谁来实现也要分层回答：

1. **应用程序**决定是否复用连接、何时调用 `close()`、是否发心跳、idle timeout 多久。
2. **内核 TCP 协议栈**负责 FIN/RST、重传、保活探测、连接状态机和 fd 可读/可写事件。
3. **代理和负载均衡器**可能有自己的连接池和超时策略，它们可以关闭客户端侧连接或后端侧连接。
4. **客户端库**负责连接复用、失败重试、连接池淘汰和错误上报。

真实场景中，长连接服务通常同时配置应用层心跳、读写超时、TCP keepalive 和连接池健康检查。HTTP Keep-Alive 只表示“可以复用连接”，不保证连接永久可用；每次复用前都要能处理对端已关闭、半开连接或写入失败。

## 易错点

1. 长连接不等于连接永远不关，要设置 idle timeout、keepalive、最大请求数等。
2. TCP Keepalive 是内核探活机制，HTTP Keep-Alive 是应用层连接复用策略，两者不是一回事。
3. 长连接减少建连成本，但会增加服务端连接状态维护成本。
4. 短连接高并发时，主动关闭方可能出现大量 `TIME_WAIT`。
5. `Connection` 是逐跳首部，经过代理时要按规范处理，不能当成端到端业务首部。

## 面试回答模板

短连接是每次请求都新建连接，请求响应后关闭，简单但握手和关闭开销大；长连接是一次建连后复用连接，能减少 TCP/TLS 握手和端口消耗，适合多次请求、RPC、数据库连接池和 WebSocket。HTTP 里的 `Connection` 用来表达当前这一跳连接的控制语义，例如 `keep-alive`、`close`、`Upgrade`，它是逐跳首部，不是端到端首部。长连接要关注 fd、内存、心跳、空闲超时和事件驱动模型，短连接要关注 `TIME_WAIT` 和端口耗尽。
