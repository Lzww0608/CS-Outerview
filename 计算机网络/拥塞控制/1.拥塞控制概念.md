# 1. 拥塞控制概念

拥塞控制是传输层根据网络承载能力动态调整发送速率的机制。它解决的问题不是单条连接两端的接收能力，而是网络中路由器、链路、队列等共享资源是否已经过载。

## 和流量控制的区别

1. **流量控制**：保护接收方，避免发送方发得太快导致接收缓冲区被打爆，典型机制是 TCP 接收窗口 `rwnd`。
2. **拥塞控制**：保护网络，避免过多连接同时发送导致链路拥塞、队列堆积和丢包，典型机制是拥塞窗口 `cwnd`。

TCP 实际发送窗口通常取：

```text
send_window = min(rwnd, cwnd)
```

## 拥塞窗口的单位是什么

`cwnd` 的本质是发送方允许自己在网络中“在途”的数据量。概念上它表示字节数，因为 TCP 是字节流协议；工程实现和教材讲解中也经常用 MSS 或报文段数量来描述窗口增长，例如“每收到一个 ACK 增加 1 MSS”。

面试里可以这样区分：

1. **协议语义**：TCP 序号、ACK、接收窗口通告都以字节为单位。
2. **算法表达**：慢启动、拥塞避免常用 MSS 作为增长粒度，便于描述每个 RTT 内窗口如何变化。
3. **内核实现**：不同字段可能用字节、packet/segment 或定点比例表示，但最终都会换算成可发送的字节数。
4. **真实发送量**：发送方不能只看 `cwnd`，还要受接收窗口 `rwnd`、发送缓冲区、MSS、TSO/GSO、pacing 和未确认在途数据影响。

常见易错点是把 `cwnd` 当成“能同时发多少个包”的固定包数。更准确的说法是：`cwnd` 控制的是在途数据上限，经典算法为了便于讨论常按 MSS 粒度调整；如果 MSS 变小，同样的字节窗口对应的报文段数量会变多。

## TCP 经典拥塞控制阶段

1. **慢启动**：连接开始时 `cwnd` 较小，每收到 ACK 就增大窗口，近似指数增长，快速探测可用带宽。
2. **拥塞避免**：当 `cwnd` 达到 `ssthresh` 后，转为线性增长，避免过快打满网络。
3. **快速重传**：收到多个重复 ACK 时，推断某个包丢失，不等 RTO 超时就重传。
4. **快速恢复**：丢包后降低窗口，但不一定回到最小窗口，尽量保持链路利用率。

## 丢包时为什么阈值会减半

经典 Reno 把丢包视为网络拥塞信号。`ssthresh` 是慢启动阈值，用来决定窗口增长方式：低于它时慢启动指数增长，高于它时拥塞避免线性增长。

发生丢包后把 `ssthresh` 设为当前拥塞窗口的一半，背后是 AIMD（Additive Increase, Multiplicative Decrease）思想：

1. **加性增大**：没看到拥塞时，每 RTT 让窗口线性增加，谨慎探测更多带宽。
2. **乘性减小**：看到拥塞时，快速把发送速率降下来，给网络队列释放空间。
3. **公平性**：多个 TCP 流都采用 AIMD 时，长期会趋向比较公平地分享瓶颈链路。
4. **避免震荡过大**：直接降到 1 会过于保守；只减一点又可能继续拥塞，减半是经典折中。

不同丢包信号处理不同：

1. **超时 RTO**：说明网络反馈严重不足，Reno 通常把 `ssthresh = cwnd / 2`，再把 `cwnd` 降到 1 MSS，重新慢启动。
2. **三个重复 ACK**：说明仍有后续包到达，网络没有完全断，触发快速重传/快速恢复，窗口通常减半而不是回到 1。

现代算法不一定都“丢包就减半”。CUBIC 使用三次函数控制窗口，BBR 更关注瓶颈带宽和 RTT，DCTCP 借助 ECN 标记按拥塞程度调整窗口。但面试回答 Reno 的减半逻辑时，要抓住“丢包作为拥塞信号 + AIMD 的乘性减小 + 公平性和队列释放”。

## 常见算法

1. **Reno**：基于丢包判断拥塞，慢启动、拥塞避免、快速重传、快速恢复是经典面试模型。
2. **CUBIC**：Linux 长期默认算法之一，窗口增长使用三次函数，更适合高带宽长 RTT 网络。
3. **BBR**：基于带宽和 RTT 估计瓶颈带宽与最小 RTT，不单纯把丢包当作拥塞信号。
4. **Vegas**：基于 RTT 增长推测队列堆积，试图在丢包前降低速率。
5. **DCTCP**：数据中心网络常见，结合 ECN 标记感知交换机队列拥塞。

## 真实场景如何选取

1. 公网 Linux 服务一般使用系统默认的 CUBIC，兼容性好。
2. 跨地域、高带宽、高 RTT 链路可以评估 BBR，提高吞吐并降低排队延迟。
3. 数据中心内部如果交换机支持 ECN，可以使用 DCTCP 一类算法降低尾延迟。
4. 实际生产要结合丢包率、RTT、队列延迟、公平性和业务延迟目标压测，不是只看单连接吞吐。

## 易错点

1. 拥塞控制不是防止接收方处理不过来，那是流量控制。
2. 丢包不一定全是拥塞，也可能是无线链路误码、链路抖动或设备策略丢包。
3. 更激进的拥塞控制可能提高单连接吞吐，但会影响公平性和其他连接体验。
