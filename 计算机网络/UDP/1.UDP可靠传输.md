# 1. UDP可靠传输

UDP 本身只提供无连接的数据报传输，不保证可靠、有序、不重复，也没有拥塞控制。所谓 UDP 可靠传输，是在应用层或用户态协议层自己补上 TCP 的一部分能力，同时保留 UDP 的低开销、消息边界和灵活性。

典型例子包括 QUIC、KCP、实时游戏私有协议、音视频中的关键帧确认和部分可靠传输。

## 1. 为什么不用 TCP

可靠 UDP 不是为了“重新造 TCP”，而是为了在特定场景下定制可靠性。

常见原因：

1. **延迟敏感**：实时游戏、音视频不希望 TCP 队头阻塞导致旧数据拖住新数据。
2. **部分可靠**：位置同步、语音帧过期后重传意义不大，但登录、结算、关键帧必须可靠。
3. **用户态演进**：拥塞控制、加密、连接迁移可以在用户态快速迭代，例如 QUIC。
4. **保留消息边界**：UDP 数据报天然是一条一条的消息，应用层协议更容易表达包级语义。

如果只是普通文件传输、数据库连接、HTTP/1.1 或 HTTP/2，一般直接用 TCP 更合适。

## 2. 可靠传输要补哪些能力

可靠 UDP 至少要考虑：

1. **序号**：每个数据包带 `seq`，用于去重、排序和确认。
2. **确认 ACK**：接收方返回已收到的序号或区间。
3. **重传**：发送方根据超时、NACK 或选择性确认判断丢包并重发。
4. **滑动窗口**：限制未确认数据量，避免发送方无限制堆积。
5. **乱序缓存**：接收方缓存乱序包，按业务决定是否必须有序交付。
6. **流量控制**：接收方告知可接收窗口，避免缓冲区被打爆。
7. **拥塞控制**：根据 RTT、丢包、ECN 或带宽估计控制发送速率，避免压垮网络。
8. **连接状态**：握手、心跳、超时关闭、连接迁移和会话恢复。
9. **MTU 控制**：避免 IP 分片，公网通常把单个 UDP payload 控制在约 1200 字节附近。

## 2.1 P2P 可靠传输 SDK 怎么设计

如果场景是 P2P SDK，底层用 UDP，偶尔丢包，但业务希望 SDK 提供可靠传输，可以按“连接管理、包格式、发送窗口、接收重排、重传、拥塞控制、安全和可观测性”设计。

包头可以包含：

```text
connection_id | channel_id | flags | seq | ack | ack_bitmap | send_ts | payload_len
```

核心模块：

1. **会话层**：维护 `connection_id`、对端地址、NAT 变化、心跳、超时关闭和重连。
2. **发送缓冲**：已发送但未确认的包放入 resend queue，按 `seq` 索引。
3. **ACK/SACK**：`ack` 表示最大连续确认序号，`ack_bitmap` 表示最近若干包的选择性确认，减少无效重传。
4. **接收重排**：接收方按 `seq` 去重和缓存乱序包，可靠有序 channel 等缺口补齐后再交付。
5. **重传策略**：根据 RTT/RTO、NACK 或 ACK 缺口做快速重传，超过次数或 TTL 后失败。
6. **多 channel**：可靠有序、可靠无序、不可靠、部分可靠分开，避免位置同步这类过期数据拖住关键控制消息。
7. **拥塞控制**：用发送窗口、令牌桶或 BBR/CUBIC/KCP 类算法控制发送速率，丢包和 RTT 上升时降速。
8. **MTU 探测和分片**：应用层分片要有 fragment id、offset、count 和超时清理，优先控制单包小于路径 MTU。
9. **线程模型**：一个 I/O 线程负责收发和定时器，业务线程通过无锁队列或加锁队列投递消息，回调时避免长时间占用 I/O 线程。
10. **安全层**：结合握手密钥，用 AEAD 加密 payload 和认证包头关键字段，防止篡改、重放和伪造 ACK。

发送流程：

```text
业务 send
-> 按 channel 编号和优先级入队
-> 受发送窗口和拥塞控制限制发包
-> 记录 seq、发送时间、重传次数
-> 收到 ACK 后从发送缓冲删除
-> 超时或 NACK 后重传
```

接收流程：

```text
收到 UDP 包
-> 校验 connection_id、版本、AEAD tag
-> 去重并更新 ACK 状态
-> 可靠有序 channel 进入重排队列
-> 能连续交付时回调业务
-> 定时 piggyback ACK 或立即回 ACK
```

真实 SDK 要暴露清晰语义：哪些消息可靠、是否有序、超时后如何通知业务、最大缓存多少、网络恢复后是否继续重传。不要把所有 UDP 包都做成 TCP 式可靠有序，否则会重新引入队头阻塞。

## 3. ACK、NACK 和 SACK

三种确认方式：

| 方式 | 含义 | 适用场景 |
| --- | --- | --- |
| ACK | 告诉发送方某个包或某个连续区间已经收到 | 简单可靠传输 |
| NACK | 告诉发送方缺了哪些包 | 丢包率较低、接收方能发现空洞 |
| SACK | 选择性确认多个已收到区间 | 乱序明显、希望减少无效重传 |

例如接收方收到 `1,2,4,5`，缺少 `3`，可以返回：

```text
ack = 2
sack = [4, 5]
```

发送方只重传 `3`，而不是从 `3` 之后全部重传。

## 4. 重传和超时

重传不能只写一个固定超时时间。网络 RTT 会波动，固定超时太短会误判丢包，太长会恢复慢。

常见策略：

1. **RTO 估计**：根据平滑 RTT 和 RTT 方差估算重传超时。
2. **快速重传**：连续收到缺口后的 ACK/NACK 时，不等超时就重传。
3. **重传次数上限**：超过上限认为连接不可用，释放资源。
4. **退避**：多次失败后增大重传间隔，避免网络拥塞时持续加压。
5. **按消息级别重传**：关键消息可靠重传，过期消息直接丢弃。

## 5. 有序、无序和部分可靠

可靠 UDP 不一定要求所有数据严格有序。

常见设计：

1. **可靠有序**：类似 TCP，适合 RPC、登录、结算、状态变更。
2. **可靠无序**：每条消息必须到，但可以乱序交付，适合独立事件。
3. **不可靠无序**：允许丢失，适合位置同步、实时音视频普通帧。
4. **部分可靠**：消息带 TTL 或优先级，过期后不再重传。

真实项目常把不同业务放到不同 channel：

```text
channel 0: 可靠有序，登录和结算
channel 1: 可靠无序，道具事件
channel 2: 不可靠无序，位置同步
channel 3: 部分可靠，关键帧或状态快照
```

## 6. 拥塞控制不能省

只做 ACK 和重传还不够。公网环境下如果没有拥塞控制，丢包时继续高速重传，会进一步放大拥塞。

常见拥塞控制思路：

1. **基于丢包**：丢包认为网络拥塞，降低发送窗口，例如 Reno/CUBIC 思路。
2. **基于延迟**：RTT 或排队延迟升高时提前降速，例如 Vegas/COPA 思路。
3. **基于带宽估计**：估算瓶颈带宽和最小 RTT，例如 BBR 思路。
4. **基于 ECN**：网络设备显式标记拥塞，发送方提前降速，例如数据中心 DCTCP。

面试里可以说：可靠 UDP 不是“UDP + 重传”这么简单，真正上线要有拥塞控制、限速、重传上限和监控，否则比 TCP 更容易伤害网络。

## 7. 常见开源可靠 UDP 实现

面试被追问“可靠 UDP 有哪些开源实现”时，不要只说“自己加 ACK 和重传”，可以按场景回答：

| 实现 | 定位 | 典型场景 | 注意事项 |
| --- | --- | --- | --- |
| QUIC | 标准化的 UDP 传输协议，内置 TLS 1.3、多路复用、拥塞控制和连接迁移 | HTTP/3、移动网络、弱网长连接 | 工程复杂度高，优先使用成熟库，如 MsQuic、quiche、ngtcp2、quic-go |
| KCP | 轻量级可靠 ARQ 协议，强调低延迟 | 游戏、实时交互、弱网加速 | 本身不是完整安全传输栈，通常还要补加密、鉴权、拥塞/限速和监控 |
| ENet | 面向游戏的可靠 UDP 网络库，支持通道和可靠/不可靠消息 | 多人游戏、实时状态同步 | 协议生态偏游戏，跨公网大规模服务仍需结合业务治理 |
| RakNet / SLikeNet | 游戏网络库，提供可靠消息、排序、连接管理等能力 | 游戏、仿真、实时应用 | 需要关注维护状态、许可证和跨平台适配 |
| UDT | 面向高速数据传输的可靠 UDP 协议 | 高带宽长距离传输、科研数据传输 | 现在通用互联网业务更多会选 QUIC 或直接 TCP |
| WebRTC DataChannel | SCTP over DTLS over UDP，提供可靠/不可靠、顺序/乱序组合 | 浏览器 P2P、音视频旁路数据通道 | NAT 穿透、拥塞控制和安全链路通常交给 WebRTC 栈处理 |

选型思路：

1. Web、移动端、跨语言服务优先考虑 QUIC，因为它有标准、TLS、安全和拥塞控制生态。
2. 游戏或强实时状态同步可以考虑 KCP、ENet 这类轻量协议，但要明确哪些消息可靠、哪些消息过期丢弃。
3. 浏览器或音视频场景优先考虑 WebRTC DataChannel，不要重复造 NAT 穿透和安全链路。
4. 自研可靠 UDP 之前要确认是否真的需要绕开 TCP/QUIC，否则很容易遗漏拥塞控制、MTU、NAT、重放攻击和可观测性。

## 8. 易错点

1. UDP 包超过路径 MTU 会触发 IP 分片，任一分片丢失整个数据报都失败。
2. 重传旧包可能增加延迟，实时业务要区分关键数据和过期数据。
3. 只做可靠性不做拥塞控制，会在弱网下雪崩。
4. ACK 本身也可能丢失，所以协议要能处理重复包和重复 ACK。
5. 可靠 UDP 需要处理 NAT、端口变化、心跳保活和连接迁移。
6. 能用 TCP 或 QUIC 时，不要轻易自研完整传输协议。

## 9. 面试回答模板

UDP 本身不可靠，可靠 UDP 是在应用层加序号、ACK/SACK、重传、滑动窗口、乱序缓存、流量控制、拥塞控制和连接状态管理。它适合实时游戏、音视频、QUIC 这类需要低延迟、部分可靠或用户态快速演进的场景。如果设计 P2P SDK，我会定义带 `connection_id/channel/seq/ack/ack_bitmap` 的包头，发送侧维护 resend queue，接收侧做去重和重排，不同 channel 区分可靠有序、可靠无序、不可靠和部分可靠；重传结合 RTT 估计、快速重传、退避和次数上限；同时必须控制 MTU 并加入拥塞控制和安全认证，否则丢包时盲目重传会把网络打得更差。
