# 游戏网络：改进型UDP协议详解

## 一、为什么游戏不用标准UDP

### 1.1 UDP的问题

UDP是无连接的，丢包、乱序、重复都无法处理：

```text
标准UDP的问题：

┌─────────────────────────────────────────────────────────────┐
│                      UDP 特性                                │
│                                                             │
│  丢包: 包可能在网络中丢失，发送方不知道                      │
│  乱序: 包可能不按发送顺序到达                               │
│  重复: 包可能被复制，到达多次                                │
│  错误: UDP校验和很弱，无法可靠检测错误                       │
│                                                             │
│  结论: 标准UDP不适合需要可靠传输的游戏                       │
└─────────────────────────────────────────────────────────────┘
```

### 1.2 TCP为什么也不适合

TCP虽然可靠，但有些特性对游戏不友好：

```text
TCP的问题：

┌─────────────────────────────────────────────────────────────┐
│                      TCP 特性                                │
│                                                             │
│  拥塞控制: 丢包就减速，高延迟下性能差                       │
│  队头阻塞: 一个包丢了，后面的都要等                          │
│  传输速率: 不保证及时性，只保证顺序                          │
│                                                             │
│  结论: TCP适合文件传输，但不适合实时游戏                     │
└─────────────────────────────────────────────────────────────┘
```

### 2.2 可靠传输机制

核心是实现类似TCP的确认应答（ACK）机制：

```c
// 可靠传输的核心数据结构
struct PacketHeader {
    uint32_t sequence;      // 序列号，唯一标识每个包
    uint32_t timestamp;     // 时间戳，用于RTT计算
    uint16_t length;        // 负载长度
    uint8_t  flags;         // 标志位：ACK/NAK/数据
    uint8_t  checksum;      // 校验和
};

// 发送方维护
struct SenderState {
    std::map<uint32_t, Packet*> sent_packets;    // 已发送待确认的包
    uint32_t next_sequence;                       // 下一个序列号
    uint32_t oldest_unacked;                      // 最老的未确认序列号
};

// 接收方维护
struct ReceiverState {
    std::map<uint32_t, Packet*> received_packets; // 已接收的包
    uint32_t last_acked;                           // 最后确认的序列号
    uint32_t expected_sequence;                     // 期望的下一个序列号
};
```

### 2.3 ACK确认机制

```c
// 收到数据包后，发送ACK
void on_receive_packet(Packet* pkt) {
    // 生成ACK包
    AckPacket ack;
    ack.ack_number = pkt->sequence;
    ack.ack_bits = generate_ack_bits();  // 位图，表示连续收到的包
    
    sendto(ack);
    
    // 放入接收缓冲区
    if (pkt->sequence == expected_sequence) {
        // 顺序到达，直接交付给应用层
        deliver_to_game(pkt);
        expected_sequence++;
        
        // 检查后续连续包
        while (received_packets.count(expected_sequence)) {
            deliver_to_game(received_packets[expected_sequence]);
            expected_sequence++;
        }
    } else {
        // 乱序，先缓存
        received_packets[pkt->sequence] = pkt;
    }
}

// 发送方收到ACK
void on_receive_ack(AckPacket* ack) {
    uint32_t acked_seq = ack->ack_number;
    
    // 标记包已确认
    if (sent_packets.count(acked_seq)) {
        sent_packets[acked_seq]->acked = true;
        
        // 更新RTT
        RTT = current_time - sent_packets[acked_seq]->send_time;
        
        // 释放内存
        delete sent_packets[acked_seq];
        sent_packets.erase(acked_seq);
    }
    
    // 处理位图中的确认
    for (int i = 0; i < 32; i++) {
        if (ack->ack_bits & (1 << i)) {
            uint32_t seq = acked_seq + i + 1;
            if (sent_packets.count(seq)) {
                sent_packets[seq]->acked = true;
                delete sent_packets[seq];
                sent_packets.erase(seq);
            }
        }
    }
}
```

## 三、拥塞控制

### 3.1 为什么不直接用TCP的拥塞控制

```text
TCP拥塞控制的问题：

┌─────────────────────────────────────────────────────────────┐
│  1. 慢启动: 从很小窗口开始，增长慢                          │
│  2. 拥塞避免: 线性增长，遇到丢包就减半                       │
│  3. 快速恢复: 丢包后进入恢复阶段                             │
│                                                             │
│  问题: 在高延迟、高丢包网络下，TCP几乎无法正常工作           │
└─────────────────────────────────────────────────────────────┘
```

### 3.2 游戏常用的拥塞控制算法

#### 3.2.1 固定窗口 + 丢包降窗

```c
struct CongestionControl {
    uint32_t window_size;      // 拥塞窗口大小
    uint32_t max_window;       // 最大窗口
    float    increase_rate;    // 增窗速率
    
    // 收到ACK时增窗
    void on_ack() {
        if (window_size < max_window) {
            window_size += increase_rate;
        }
    }
    
    // 丢包时降窗
    void on_loss() {
        window_size = window_size * 0.5;  // 减半
        if (window_size < MIN_WINDOW) {
            window_size = MIN_WINDOW;
        }
    }
};
```

#### 3.2.2 CODEC（专为游戏设计）

有些游戏使用类似QUIC的COEC（Constrained Elastic Congestion Control）：

```c
// 基于延迟的拥塞控制
void on_ack(AckPacket* ack) {
    // 计算延迟
    int64_t rtt = current_time - ack->send_time;
    
    // 延迟变化检测
    if (rtt > base_rtt * 1.5) {
        // 延迟上升，可能是拥塞信号
        window_size *= 0.8;
    } else {
        // 正常，增窗
        window_size += increase_rate;
    }
    
    base_rtt = min(base_rtt, rtt);
}
```

## 四、序列号与顺序控制

### 4.1 序列号设计

```c
// 序列号使用32位无符号整数，循环使用
// 设计要点：

// 1. 序列号比较要考虑回绕
bool sequence_less(uint32_t a, uint32_t b) {
    // 序列号回绕到0时，差值会很大，需要特殊处理
    if (a > b && a - b < 0x80000000) return true;
    if (b > a && b - a > 0x80000000) return true;
    return false;
}

// 2. 判断是否在窗口内
bool in_window(uint32_t seq, uint32_t start, uint32_t end) {
    return sequence_less(start, seq) && sequence_less(seq, end);
}
```

### 4.2 乱序处理

```c
class PacketBuffer {
    std::map<uint32_t, Packet*> buffer;  // 乱序包缓存
    uint32_t next_expected;                // 期望的下一个序列号
    
public:
    void add_packet(Packet* pkt) {
        if (pkt->sequence == next_expected) {
            // 顺序到达
            deliver(pkt);
            next_expected++;
            
            // 检查后续连续包
            while (buffer.count(next_expected)) {
                deliver(buffer[next_expected]);
                next_expected++;
            }
        } else {
            // 乱序，先缓存
            buffer[pkt->sequence] = pkt;
        }
    }
};
```

## 六、防作弊与安全

### 6.1 基本安全措施

```c
// 1. 包加密（防止明文被抓包分析）
struct EncryptedPacket {
    uint32_t session_id;      // 会话ID
    uint32_t sequence;        // 序列号（防重放）
    uint8_t  iv[8];           // 初始向量
    uint8_t  encrypted[0];    // 加密数据
    uint32_t checksum;        // 校验和
};

// 2. 序列号校验（防重放攻击）
struct AntiReplay {
    std::set<uint32_t> received_sequences;  // 已收到的序列号
    uint32_t window_size = 128;               // 窗口大小
    
    bool check_sequence(uint32_t seq) {
        if (received_sequences.count(seq)) {
            return false;  // 重放！
        }
        
        // 清理太老的序列号
        for (auto it = received_sequences.begin(); 
             it != received_sequences.end();) {
            if (sequence_less(*it, seq - window_size)) {
                it = received_sequences.erase(it);
            } else {
                ++it;
            }
        }
        
        received_sequences.insert(seq);
        return true;
    }
};

// 3. 服务器校验（防客户端作弊）
bool validate_input(PlayerInput* input) {
    // 检查输入合法性
    if (input->velocity > MAX_VELOCITY) return false;
    if (input->distance > MAX_DISTANCE) return false;
    if (out_of_map(input->position)) return false;
    
    // 检查与服务器预测的一致性
    ServerState predicted = predict(input);
    if (abs(predicted.position - input->position) > TOLERANCE) {
        return false;  // 作弊！
    }
    
    return true;
}
```

## 八、面试常见问题

### Q1: 为什么游戏不用TCP？

1. **延迟问题**：TCP的拥塞控制和重传在高延迟网络下表现很差
2. **队头阻塞**：一个包丢了，后面的都要等
3. **流量控制**：TCP适合大块数据传输，不适合高频小包

### Q2: 改进型UDP的核心是什么？

1. **可靠传输**：ACK确认、重传机制
2. **顺序控制**：序列号、乱序处理
3. **拥塞控制**：适应网络状况
4. **安全机制**：加密、防作弊

### Q3: 可靠UDP vs TCP的主要区别？

| 特性 | 可靠UDP | TCP |
|------|---------|-----|
| 拥塞控制 | 可定制，轻量 | 固定、较重 |
| 重传策略 | 可选择重传哪些 | 全量重传 |
| 队头阻塞 | 无（多流） | 有 |
| 连接建立 | 可选 | 必须 |
| 头部大小 | 可优化 | 固定20字节+ |

### Q4: 如何选择可靠程度？

```c
// 根据数据类型选择传输方式
switch (data_type) {
    case PLAYER_INPUT:      // 每帧输入，必须可靠
        send_reliable(data);
        break;
        
    case POSITION_UPDATE:  // 位置更新，允许一定丢失
        send_unreliable(data);
        break;
        
    case GAME_STATE:        // 游戏状态，关键但可延迟
        send_reliable(data);
        break;
        
    case CHAT_MESSAGE:     // 聊天消息，必须可靠
        send_reliable(data);
        break;
        
    case PARTICLE_EFFECT:   // 粒子效果，允许丢失
        send_unreliable(data);
        break;
}
```

## 九、总结

1. **为什么改进UDP**：标准UDP丢包乱序，TCP延迟太高
2. **核心机制**：可靠传输、顺序控制、拥塞控制
3. **拥塞控制**：游戏常用轻量算法，丢包降窗、延迟检测
4. **安全考虑**：加密、防重放、服务器校验
5. **实践选择**：ENet、RakNet、QUIC等成熟方案
