# 6. KCP 协议详解

KCP 是一个基于 ARQ（Automatic Repeat reQuest，自动重传请求）的快速可靠传输协议，常被放在 UDP 之上使用。它的定位不是“替代 TCP 的完整协议栈”，而是一个可嵌入业务协议栈的可靠传输算法模块：底层怎么收发包、怎么建连、怎么鉴权、怎么加密、怎么做 NAT 保活，都由使用方自己实现，KCP 只负责把不可靠的数据报变成更低延迟的可靠、有序交付。

官方实现主要由 `ikcp.h` 和 `ikcp.c` 两个文件组成，接口很小，适合嵌入游戏、隧道、实时交互和弱网加速类系统中。

## 1. KCP 解决什么问题

UDP 本身只提供数据报传输，不保证可靠、有序和不重复。TCP 虽然可靠，但它是一条严格有序的字节流，并且拥塞控制、RTO 退避、ACK 策略都在内核协议栈里，应用很难按业务定制。

KCP 主要解决的是“弱网下可靠消息的延迟抖动”问题：

1. 业务希望消息可靠到达，但不希望 TCP 丢一个包就让后续数据长期阻塞。
2. 业务更关心单个包到达耗时，而不是极限吞吐。
3. 应用希望在用户态控制重传、ACK、窗口、RTO、快速模式和流控策略。
4. 协议栈需要可拆分，可以在 KCP 下层组合 UDP、动态路由、NAT 穿透，也可以在上层组合加密、握手、FEC、应用层流控。

可以把 KCP 理解为：

```text
业务消息
  -> 会话层：连接管理、鉴权、加密、心跳、断线重连
  -> KCP：序号、ACK、UNA、窗口、重传、RTO、乱序重排
  -> UDP：端口复用和数据报收发
  -> IP
```

KCP 不直接面对 socket，因此它既能跑在 UDP 上，也能跑在其他数据报通道上。只要底层能把 KCP 生成的字节发出去，并把收到的字节喂给 KCP，它就能工作。

## 2. 基本使用方式

KCP 的最小接入流程如下：

```c
// 1. 创建 KCP 控制块，conv 是会话编号，两端必须一致。
ikcpcb *kcp = ikcp_create(conv, user);

// 2. 设置下层输出回调。KCP 需要发包时会调用 output。
int udp_output(const char *buf, int len, ikcpcb *kcp, void *user) {
    // 使用方在这里调用 sendto/sendmsg 或自己的网络库发送 UDP 包。
    return 0;
}
ikcp_setoutput(kcp, udp_output);

// 3. 业务发送数据。
ikcp_send(kcp, data, len);

// 4. 收到底层 UDP 包后输入给 KCP。
ikcp_input(kcp, udp_payload, udp_payload_len);

// 5. 周期性驱动 KCP 定时器。
ikcp_update(kcp, now_ms);

// 6. 从 KCP 接收已按序恢复的数据。
int n = ikcp_recv(kcp, buffer, buffer_size);
```

这个设计有两个关键点：

1. **KCP 是纯算法实现**：内部不主动调用系统时间、socket、线程、锁、内存池之外的外部网络能力。
2. **必须由外部驱动 `update`**：如果没有周期性调用 `ikcp_update`，ACK、重传、窗口探测都不会被及时触发。

工程里通常不会给每条 KCP 连接开一个线程，而是用事件循环或时间轮统一调度：

```text
UDP recv loop
  -> 根据 conv / endpoint 找到 KCP 会话
  -> ikcp_input
  -> 尝试 ikcp_recv 并投递业务

timer loop
  -> 遍历活跃 KCP 会话
  -> 到期则 ikcp_update
  -> 或使用 ikcp_check 计算下次最早更新时间
```

## 3. 包格式和核心字段

KCP 把业务数据拆成 segment，每个 segment 都带有控制信息。典型头部语义如下：

```text
conv | cmd | frg | wnd | ts | sn | una | len | data
```

字段含义：

| 字段 | 作用 |
| --- | --- |
| `conv` | 会话编号，用于区分不同 KCP 连接。 |
| `cmd` | 命令类型，常见有数据、ACK、窗口探测、窗口回应。 |
| `frg` | 分片编号，用于把大消息拆成多个 segment 后重组。 |
| `wnd` | 接收窗口，告诉对端自己还能接收多少 segment。 |
| `ts` | 发送时间戳，用于 RTT/RTO 计算。 |
| `sn` | 当前 segment 的序号。 |
| `una` | 表示小于该序号的包都已被接收，类似累计确认。 |
| `len` | payload 长度。 |

常见命令：

1. `PUSH`：携带业务数据。
2. `ACK`：确认某个 `sn` 已收到。
3. `WASK`：窗口探测，请求对端汇报接收窗口。
4. `WINS`：窗口回应，告诉对端当前接收窗口。

`ACK + UNA` 是 KCP 很重要的设计。单独 ACK 可以精确确认某个包，UNA 可以批量表达“这个序号之前都收到了”。两者结合后，发送端既能清理连续确认的数据，也能做选择性重传，减少“从丢包点之后全部重传”的浪费。

## 4. 内部队列模型

KCP 的核心状态可以抽象为四个队列加一个 ACK 列表：

```text
发送侧：
snd_queue  -> 业务刚写入、还没真正进入发送窗口的数据
snd_buf    -> 已经分配 sn、已经发送或等待重传的数据

接收侧：
rcv_buf    -> 已收到但还不能连续交付的乱序数据
rcv_queue  -> 可以交付给业务的连续数据

acklist    -> 等待发送给对端的 ACK
```

发送流程：

```text
ikcp_send
  -> 按 mss 拆分业务消息
  -> 生成 segment 放入 snd_queue
  -> ikcp_flush 时检查 snd_wnd、rmt_wnd、cwnd
  -> 从 snd_queue 移入 snd_buf，分配 sn 并发送
  -> 收到 ACK/UNA 后从 snd_buf 删除
```

接收流程：

```text
ikcp_input
  -> 解码 segment
  -> 校验 conv、cmd、长度和窗口范围
  -> PUSH 数据进入 rcv_buf，并记录 ACK
  -> 按 sn 排序和去重
  -> rcv_nxt 连续的数据移动到 rcv_queue
  -> ikcp_recv 从 rcv_queue 取完整消息
```

这个模型和 TCP 类似，也使用滑动窗口和重传缓存；不同点在于 KCP 更强调消息分片、选择性确认、快速重传和用户态参数控制。

## 5. 重传和 RTO 原理

KCP 的可靠性来自三类机制：

1. **超时重传**：每个已发送 segment 记录发送时间和重传时间，当前时间超过 `resendts` 后重发。
2. **快速重传**：如果某个包被后续 ACK 多次跨过，说明后面的包已经到了，而它大概率丢了，可以不用等 RTO 到期就重传。
3. **选择性重传**：只重传真正丢失或超时的 segment，而不是从丢失位置之后全部重传。

RTT/RTO 的基本思想是：

```text
收到 ACK
  -> 用当前时间 - segment.ts 得到一次 RTT 样本
  -> 更新平滑 RTT 和 RTT 抖动
  -> 计算新的 RTO
  -> RTO 不能低于最小值，也不能超过最大值
```

KCP 普通模式更接近保守 ARQ；快速模式下会降低内部调度间隔、启用快速重传、降低最小 RTO，并且超时退避不再像 TCP 那样激进。这样做能缩短丢包发现和恢复时间，但代价是更多重传、更高带宽占用和更强的网络侵略性。

## 6. KCP 做了哪些改进

KCP 的改进不是把 UDP 改成 TCP，而是围绕“低延迟恢复”重新取舍。

### 6.1 RTO 退避更激进

TCP 为了全网公平和稳定，连续超时时会指数退避，RTO 可能迅速变大。KCP 快速模式下的退避更温和，丢包后恢复更快。

收益：弱网短时抖动时，业务更快恢复。

代价：网络真的拥塞时，过快重传会增加带宽消耗。

### 6.2 选择性重传

KCP 根据 ACK 精确判断哪些 segment 已经收到，重传时只补丢失的包。

收益：避免“一个包丢了，后面一串都重发”。

代价：需要维护更多发送缓存和 ACK 状态。

### 6.3 快速重传

如果发送了 `1, 2, 3, 4, 5`，接收方确认了 `1, 3, 4, 5`，发送端可以推断 `2` 很可能丢了。KCP 可以通过 `resend` 参数控制被 ACK 跨过几次后触发快速重传。

收益：不必等待超时，降低丢包恢复延迟。

代价：乱序严重时可能误判，导致多余重传。

### 6.4 ACK 可调

TCP 常通过延迟 ACK 提高吞吐和减少 ACK 包数量。KCP 更关注延迟，ACK 策略可以通过快速模式和 flush 频率调节。

收益：RTT 样本更及时，丢包判断更快。

代价：ACK 包比例可能上升。

### 6.5 ACK + UNA

KCP 同时使用单包 ACK 和累计确认 UNA：

```text
ACK(sn=10)   -> 10 号包已收到
UNA=15       -> 15 之前的包都已收到
```

收益：既保留选择性确认能力，又能快速清理发送缓存。

代价：协议头部和实现复杂度高于只做累计确认。

### 6.6 可关闭拥塞退让

`ikcp_nodelay(kcp, nodelay, interval, resend, nc)` 中的 `nc` 可以关闭拥塞控制相关退让，仅按发送窗口和对端接收窗口控制发送。

收益：对强实时小流量业务，延迟更低。

代价：公平性更差，在拥塞网络中可能恶化链路质量。公网服务不能无脑开启，需要配合限速、队列长度、丢包率和 RTT 监控。

## 7. 参数怎么理解

常用配置：

```c
// 普通模式：更保守
ikcp_nodelay(kcp, 0, 40, 0, 0);

// 快速模式：更低延迟，更多带宽开销
ikcp_nodelay(kcp, 1, 10, 2, 1);

// 设置发送窗口和接收窗口，单位是 segment，不是字节
ikcp_wndsize(kcp, 128, 128);

// 设置 MTU，KCP 会据此计算 mss 并做消息分片
ikcp_setmtu(kcp, 1200);
```

参数含义：

| 参数 | 含义 | 调优方向 |
| --- | --- | --- |
| `nodelay` | 是否启用快速模式 | 延迟敏感业务可开启。 |
| `interval` | 内部 flush 间隔，单位毫秒 | 越小响应越快，CPU 和包量越高。 |
| `resend` | 快速重传阈值 | 常见设置为 2，过小容易误重传。 |
| `nc` | 是否关闭拥塞控制 | 只建议小流量、强实时、受控网络谨慎使用。 |
| `sndwnd/rcvwnd` | 发送/接收窗口 | 带宽时延积越大，窗口通常要越大。 |
| `mtu` | 单个底层包大小上限 | 公网要避免 IP 分片，常从 1200 左右保守起步。 |

调参时不要只看平均延迟，还要看：

1. P95/P99 延迟。
2. 丢包率和重传率。
3. ACK 包比例。
4. 发送队列和接收队列长度。
5. UDP 被限速或阻断后的 fallback 比例。
6. 单连接和全局出口带宽。

## 8. 效果如何

KCP 官方 README 给出的定位是：用额外带宽换延迟，典型说法是以约 10%-20% 的带宽浪费换取平均延迟降低约 30%-40%，最大延迟明显降低。

这类效果成立的前提是：

1. 网络存在丢包、抖动、无线链路切换或跨地域传输。
2. 业务消息较小，且交互延迟比吞吐更重要。
3. 发送端有合理限速，不把链路打爆。
4. 参数根据网络情况调优，而不是所有场景都使用极速模式。

如果网络几乎不丢包，或者业务是大文件吞吐型传输，KCP 不一定比 TCP 更好。TCP 的内核实现、拥塞控制、零拷贝、网卡卸载和中间设备兼容性非常成熟，在吞吐、公平性和运维可见性上仍然有优势。

因此可以这样评价：

| 维度 | KCP | TCP |
| --- | --- | --- |
| 可靠性 | 应用层 ARQ 实现可靠有序交付 | 内核原生可靠字节流 |
| 延迟恢复 | 更积极，快速模式下恢复快 | 更保守，拥塞时退避明显 |
| 吞吐 | 不一定占优，包头和重传开销更高 | 长连接大吞吐更成熟 |
| 公平性 | 取决于参数和外层限速 | 拥塞控制成熟 |
| 工程完整性 | 只是一块协议组件 | 操作系统完整支持 |
| 适用场景 | 游戏、隧道、实时交互、弱网加速 | Web、数据库、RPC、文件传输、SSH |

## 9. 真实使用场景

KCP 适合“需要可靠，但更怕延迟抖动”的场景。

### 9.1 实时游戏

游戏里有些消息必须可靠，例如登录、匹配、结算、道具变化；有些消息更关注实时，例如位置、朝向、技能预表现。KCP 常用于可靠消息通道，或者配合应用层多 channel，把关键消息和可丢弃状态同步拆开。

注意：KCP 本身提供可靠有序交付，如果把所有状态同步都塞进同一个 KCP 流，仍然可能形成应用层队头阻塞。游戏协议通常还需要区分可靠通道、不可靠通道和部分可靠通道。

### 9.2 弱网加速和隧道

kcptun、部分代理和内网穿透工具会用 KCP 在 UDP 上做可靠传输，目标是在跨运营商、跨地域、无线网络或高丢包环境下降低交互卡顿。

这类场景一般还会补：

1. 会话握手和认证。
2. 加密和防重放。
3. FEC，减少小比例丢包下的重传等待。
4. 限速和拥塞控制，避免对公网不友好。
5. TCP fallback，避免 UDP 被企业网络或运营商策略阻断。

### 9.3 音视频推流和实时互动

音视频更常见的是 RTP/RTCP、SRT、WebRTC 等协议栈，但 KCP 也可以用于某些推流加速、控制信令或弱网传输优化。它的优势是实现简单、可嵌入、调参直接；不足是缺少完整媒体传输生态，需要业务自己补拥塞估计、码率自适应、FEC、NACK 和抖动缓冲策略。

### 9.4 移动端长连接

移动网络下 NAT 超时、IP 切换、抖动和丢包都比较常见。KCP 可以作为长连接传输组件，但连接迁移、断线重连、心跳保活和多端状态恢复都不是 KCP 自带能力，需要在会话层实现。

## 10. 工程落地注意事项

### 10.1 不要把 KCP 当完整协议栈

KCP 不负责这些事情：

1. UDP socket 创建和收发。
2. 握手、登录态和连接生命周期。
3. 加密、认证、防重放。
4. NAT 穿透和保活。
5. 多路复用和多 channel 语义。
6. 服务端会话路由和负载均衡。
7. 全局限速和跨连接公平性。

如果面试里说“我用 KCP 替代 TCP”，要补一句：KCP 只是可靠传输组件，工程上还要加会话层、安全层、拥塞/限速、监控和 fallback。

### 10.2 避免 IP 分片

KCP 有 MTU 和 MSS 概念，但它不负责路径 MTU 探测。公网 UDP 如果触发 IP 分片，任意一个分片丢失都会导致整个 UDP 包丢失，反而放大丢包损失。

常见做法：

1. 单包 payload 从 1200 字节左右保守起步。
2. 应用层大消息切片，不依赖 IP 分片。
3. 监控大包丢失率和重传率。
4. 对移动网络和隧道网络单独压测。

### 10.3 服务端大规模调度

大量 KCP 会话不能简单每连接一个定时器线程。更好的方式是：

1. 用单线程或多 reactor 处理 UDP 收发。
2. 用小根堆、时间轮或 `ikcp_check` 找出最早需要 update 的连接。
3. 活跃连接才调度，空闲连接降低 update 频率。
4. 控制每轮 flush 的最大包量，避免瞬时突刺。
5. 按用户、房间、连接、出口 IP 做限速和熔断。

### 10.4 可观测性

KCP 问题经常不是“代码错了”，而是网络状态、参数和限速策略不匹配。建议至少打点：

1. RTT、RTO、RTT 抖动。
2. 发送窗口、接收窗口、拥塞窗口。
3. 发送队列和接收队列长度。
4. 重传次数、快速重传次数、超时重传次数。
5. ACK 数量、ACK 延迟。
6. UDP 丢包率、乱序率、重复包率。
7. 会话超时、重连、fallback 次数。

## 11. 和 QUIC、TCP、ENet 怎么选

| 方案 | 更适合 | 不适合 |
| --- | --- | --- |
| TCP | 通用可靠字节流、数据库、RPC、Web、文件传输 | 强实时弱网交互，不能接受队头阻塞的场景 |
| KCP | 游戏、隧道、弱网加速、可控协议栈里的低延迟可靠消息 | 需要标准化、浏览器生态、完整安全握手的通用 Web 场景 |
| QUIC | HTTP/3、现代 Web、连接迁移、多 stream、安全传输 | 只想嵌入一个很小的 ARQ 组件，或者已有私有 UDP 协议栈 |
| ENet/RakNet | 游戏完整网络库、连接管理和通道语义 | 只想要一个可拆分的可靠传输算法模块 |

选型建议：

1. Web 和浏览器生态优先 QUIC/HTTP/3。
2. 业务私有协议、实时游戏、隧道加速可以考虑 KCP。
3. 数据库、内部管理连接、文件传输默认 TCP。
4. 如果需要不可靠、可靠无序、可靠有序、部分可靠多通道，KCP 之外还要设计 channel 层。
5. 如果团队没有 UDP 运维经验，不要直接上生产替换 TCP，先灰度和 fallback。

## 12. 未来发展方向

KCP 的未来更像“可组合传输组件”，而不是成为统一标准协议。

可能方向：

1. **和 FEC 组合**：小比例丢包时用 Reed-Solomon、XOR 或 Raptor 类 FEC 提前恢复，减少等待重传。
2. **更现代的拥塞控制**：结合 BBR、Copa、LEDBAT 或业务自定义限速，改善公网公平性和吞吐稳定性。
3. **多路径传输**：同时探测 Wi-Fi、蜂窝、不同中转节点或多条 UDP 路径，选择 RTT/丢包更好的路径。
4. **安全层标准化**：默认集成 AEAD 加密、密钥协商、防重放、连接 token，减少业务重复造安全层。
5. **多 channel 语义**：在 KCP 上层形成可靠有序、可靠无序、不可靠、部分可靠的统一接口。
6. **云边协同加速**：结合边缘节点、中转路由和动态选路，用 KCP 负责单段链路内的低延迟可靠恢复。
7. **更好的观测和自适应调参**：根据 RTT、丢包、队列长度自动调整窗口、RTO、FEC 比例和发送速率。

同时要看到 QUIC 的影响：如果业务是通用应用层协议，QUIC 由于已经包含 TLS、多 stream、连接迁移、拥塞控制和标准化生态，长期会覆盖很多“可靠 UDP”的需求。KCP 更适合仍然需要私有协议、轻量嵌入、深度调参和强实时取舍的场景。

## 13. 面试回答模板

KCP 是一个基于 UDP 的快速可靠 ARQ 协议，但它不是完整网络协议栈。它不负责 socket、握手、加密和连接管理，只提供可靠传输算法：业务调用 `ikcp_send` 写入数据，收到 UDP 包后调用 `ikcp_input`，定时调用 `ikcp_update` 驱动 ACK、窗口和重传，最后通过 `ikcp_recv` 获取按序恢复的数据。

它的核心是 segment 序号、ACK、UNA、发送/接收窗口、发送缓存、接收重排和 RTO 计算。相比 TCP，KCP 更强调低延迟恢复，做了更积极的 RTO 策略、选择性重传、快速重传、ACK 可调和 ACK+UNA 组合确认；快速模式下还可以关闭部分拥塞退让，用更多带宽和更差公平性换更低延迟。

真实工程里，KCP 适合游戏、隧道、弱网加速、实时交互这类“可靠但怕延迟”的场景。落地时不能只接一个 KCP 库，还要补会话层、鉴权加密、NAT 保活、MTU 控制、限速、监控、fallback 和多 channel 语义。对于普通 Web、数据库、文件传输和强标准化场景，TCP 或 QUIC 往往更合适。
