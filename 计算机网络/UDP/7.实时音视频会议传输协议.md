# 7. 实时音视频会议传输协议

面试里问“会议的传输协议是什么”，不能只回答“UDP”。更准确的回答是：实时音视频媒体流通常基于 UDP 承载，在应用层使用 RTP/RTCP/SRTP 或 WebRTC 协议栈；信令、登录、会控等控制面通常走 HTTPS、WebSocket 或 RPC。

## 1. 会议系统的两类链路

| 链路 | 作用 | 常见协议 |
| --- | --- | --- |
| 信令链路 | 加入房间、交换 SDP、协商媒体参数、静音、举手、成员状态 | HTTPS、WebSocket、gRPC |
| 媒体链路 | 传输音频、视频、屏幕共享、弱网反馈 | RTP/RTCP/SRTP over UDP、WebRTC、QUIC/WebTransport |

信令链路强调可靠和业务状态一致，媒体链路强调低延迟和抗抖动。二者不能混为一谈。

## 2. 为什么媒体流常用 UDP

实时音视频的核心目标是低延迟。过期的视频帧、音频包即使重传成功，也可能已经错过播放时间。

UDP 的优势：

1. **无连接、首部小**：协议开销低，适合高频小包。
2. **保留报文边界**：一个 UDP datagram 对应一个应用层包，便于媒体包处理。
3. **避免 TCP 队头阻塞**：TCP 丢一个包会阻塞后续字节交付，视频会议更希望新帧继续播放。
4. **应用层可自定义可靠性**：关键帧、控制包、普通音频包可以采用不同重传策略。
5. **便于弱网优化**：可结合 FEC、NACK、Jitter Buffer、码率自适应和拥塞控制。

选择 UDP 不代表不可靠，而是把“哪些包要可靠、哪些包可以丢、等待多久还值得重传”交给媒体协议和业务策略决定。

## 3. RTP、RTCP、SRTP

| 协议 | 作用 |
| --- | --- |
| RTP | Real-time Transport Protocol，承载音视频媒体包，包含序号、时间戳、payload type 等字段 |
| RTCP | RTP Control Protocol，传输接收质量、丢包率、抖动、RTT 等反馈 |
| SRTP | Secure RTP，对 RTP/RTCP 做加密、认证和防重放 |

RTP 解决媒体包排序、时间戳和播放同步；RTCP 提供网络质量反馈；SRTP 提供安全性。工程上常与 DTLS、ICE、STUN、TURN 一起组成 WebRTC 媒体传输链路。

## 4. WebRTC 协议栈

浏览器和很多实时会议 SDK 会使用 WebRTC。典型栈如下：

```text
信令: HTTPS / WebSocket
协商: SDP
打洞: ICE + STUN
中继: TURN
安全: DTLS-SRTP
媒体: RTP / RTCP / SRTP over UDP
数据: SCTP over DTLS over UDP (DataChannel)
```

关键点：

1. **ICE** 负责收集候选地址并选择可用路径。
2. **STUN** 用于探测 NAT 后的公网映射地址。
3. **TURN** 在 P2P 打洞失败时中继流量。
4. **DTLS-SRTP** 为媒体流协商密钥并加密传输。
5. **RTCP** 上报丢包、抖动、RTT，供码率控制和重传策略使用。

## 5. 会议架构中的传输形态

| 架构 | 说明 | 适用场景 |
| --- | --- | --- |
| P2P | 参会端之间直接传媒体流 | 1v1、小规模、网络可直连 |
| SFU | 服务端选择性转发媒体流，不解码混流 | 多人会议主流方案，延迟低，端侧压力较高 |
| MCU | 服务端解码、混流、重新编码后下发 | 大会、弱端设备、需要统一画面 |

SFU 场景下，每个客户端通常上行一路或多路媒体流，SFU 根据订阅、带宽和布局选择转发哪些流。为了适配不同网络，常使用 simulcast、SVC、动态码率和关键帧请求。

## 6. 什么时候会用 TCP

1. **信令和会控**：加入会议、权限、成员列表、聊天文本通常走 HTTPS/WebSocket/TCP。
2. **防火墙或 NAT 限制 UDP**：WebRTC 可退化到 TURN over TCP/TLS，但延迟和成本通常更高。
3. **录制和上传**：会议录制文件、日志、回放上传更适合可靠传输。
4. **非实时数据**：会议信息查询、历史消息、文档同步可用 HTTP/RPC。

媒体流如果被迫走 TCP，要注意队头阻塞和重传导致的延迟抖动。很多系统宁愿降低码率、丢弃过期帧，也不希望播放端持续等待旧包。

## 7. 易错点

1. “会议用 UDP”太粗，完整回答要区分信令和媒体。
2. RTP 不负责加密，安全媒体通常使用 SRTP。
3. RTCP 不传主要媒体内容，它负责质量反馈和控制信息。
4. UDP 上也必须做拥塞控制，否则公网大流量媒体会伤害网络。
5. TURN 中继不是免费的，带宽成本高，通常作为打洞失败兜底。
6. TCP 可靠不等于适合实时媒体，可靠重传可能让延迟持续累积。

## 8. 真实场景

一个多人会议的简化链路：

```text
客户端 A -> HTTPS 登录并拿 token
客户端 A -> WebSocket 加入房间并交换 SDP
客户端 A -> ICE/STUN/TURN 找到媒体路径
客户端 A -> SRTP/UDP 上行音视频到 SFU
SFU -> 根据订阅和带宽把其他人的流转发给客户端 A
客户端 A -> RTCP 反馈丢包、抖动、RTT
SFU/发送端 -> 降码率、请求关键帧、调整转发层
```

弱网优化常见手段包括：音频优先、视频降分辨率、动态帧率、FEC、NACK、关键帧请求、Jitter Buffer、拥塞控制和上行限速。

## 9. 面试回答模板

视频会议不是单一协议。信令和会控一般走 HTTPS 或 WebSocket，保证可靠和状态一致；真正的音视频媒体流通常走 UDP，上层使用 RTP/RTCP/SRTP 或 WebRTC。UDP 更适合实时媒体，因为它避免 TCP 队头阻塞，允许业务按包类型决定是否重传。WebRTC 还会用 ICE、STUN、TURN 做 NAT 穿透，用 DTLS-SRTP 做加密。多人会议常见架构是 SFU，服务端选择性转发媒体流，并根据 RTCP 反馈做码率和弱网调节。
