# 5. UDP 会取代 TCP 吗

结论先说：**UDP 不会简单取代 TCP，但会成为越来越多新传输协议的承载底座**。更准确的说法不是“UDP 变得可靠后取代 TCP”，而是“QUIC、实时音视频、游戏同步等协议在 UDP 之上重新实现了自己需要的可靠性、拥塞控制、加密、连接迁移和多路复用能力”。

## 1. 为什么会出现基于 UDP 的改进协议

TCP 的可靠、有序、拥塞控制都在内核协议栈里实现，稳定成熟，但升级慢。一旦应用想改变传输层行为，例如减少队头阻塞、做连接迁移、把握手和加密合并、按业务选择可靠性，就很难修改全球操作系统和中间设备里的 TCP 实现。

UDP 的优势是足够薄：

```text
UDP = 源端口 + 目的端口 + 长度 + 校验和 + 数据
```

它只提供端口复用和数据报边界，不提供连接、重传、排序、拥塞控制。也正因为它简单，应用可以在用户态实现新的传输协议。

典型例子：

1. **QUIC / HTTP/3**：基于 UDP，实现 TLS 1.3、可靠传输、拥塞控制、多路复用、连接迁移。
2. **实时音视频 RTP/RTCP**：更关注低延迟，允许丢弃过期帧，配合 FEC、NACK、Jitter Buffer。
3. **在线游戏协议**：位置、状态同步更关注实时性，可靠消息和不可靠消息按业务拆开。
4. **VPN/隧道协议**：例如 WireGuard 使用 UDP，方便穿透 NAT，协议逻辑在用户态或内核模块中控制。
5. **DNS**：小请求响应优先 UDP，必要时再切 TCP。

## 2. HTTP/3 为什么选择 QUIC/UDP

HTTP/1.1 和 HTTP/2 常跑在 TCP/TLS 上。HTTP/2 虽然在应用层支持多路复用，但底层 TCP 仍是一条有序字节流：只要某个 TCP 段丢失，后续已到达的数据也不能越过缺口交给应用，这会造成 TCP 层队头阻塞。

QUIC 把传输能力搬到 UDP 之上，主要收益是：

1. **减少队头阻塞**：QUIC 在连接内有多个 stream，一个 stream 丢包不会阻塞其他 stream 的应用层交付。
2. **握手更快**：QUIC 集成 TLS 1.3，建连和加密握手合并，支持 0-RTT，但 0-RTT 有重放风险。
3. **连接迁移**：连接不再强绑定四元组，移动网络切 Wi-Fi 后可以通过 Connection ID 继续连接。
4. **用户态快速迭代**：拥塞控制、丢包恢复、版本协商可以随应用和库升级，不完全依赖内核。
5. **默认加密**：QUIC 大量传输元数据被加密，中间设备更难错误干预协议细节。

所以 HTTP/3 的选择不是“UDP 比 TCP 更可靠”，而是“QUIC 在 UDP 上实现了更适合现代 Web 的传输语义”。

## 3. UDP 为什么不能直接取代 TCP

UDP 本身没有可靠性和拥塞控制。如果大量应用直接用裸 UDP 发送数据，不做限速、重传、乱序处理和拥塞控制，会造成网络拥塞，也会让应用面对大量复杂边界。

TCP 仍然有很强的现实优势：

1. **生态成熟**：操作系统、负载均衡、防火墙、代理、监控、抓包、内核参数都围绕 TCP 积累多年。
2. **默认可靠**：应用直接拿到可靠有序字节流，不需要自己实现重传、排序和拥塞控制。
3. **中间设备友好**：企业网络、运营商网络、防火墙、代理对 TCP 支持最稳定；UDP 可能被限速、阻断或 NAT 超时。
4. **内核优化丰富**：TCP 有成熟的拥塞控制、零拷贝、TSO/GSO/GRO、拥塞窗口调优和硬件卸载能力。
5. **简单业务成本低**：数据库连接、内部 RPC、SSH、传统 HTTP 服务使用 TCP 足够稳定，没必要额外引入 QUIC 复杂度。
6. **可靠顺序语义有价值**：很多业务就是需要严格有序字节流，例如文件传输、数据库协议、远程登录。

因此未来不是“UDP 替代 TCP”，而是“TCP 继续承担大量稳定可靠连接，UDP 承载需要自定义传输行为的新协议”。

## 4. 改进版 UDP 的本质

面试里要避免说“UDP 变可靠了”。UDP 协议本身没有变，可靠性来自上层协议。

可以这样分层：

```text
HTTP/3
  -> QUIC：连接、stream、多路复用、TLS、重传、拥塞控制、连接迁移
  -> UDP：端口和数据报
  -> IP
```

或者游戏协议：

```text
Game Transport
  -> unreliable channel：位置、朝向、瞬时状态，丢了就丢
  -> reliable channel：登录、购买、匹配结果，必须 ACK/重传/去重
  -> UDP
```

“改进版 UDP”通常是指应用层或传输层库在 UDP 上实现：

1. 包序号和 ACK。
2. 超时重传和快速重传。
3. 拥塞控制和限速。
4. 乱序缓存和去重。
5. FEC 前向纠错。
6. 多路 stream。
7. 加密和身份认证。
8. NAT keepalive 和连接迁移。

## 5. 哪些场景适合 UDP/QUIC

| 场景 | 更适合原因 |
| --- | --- |
| HTTP/3、移动端 Web | 连接迁移、减少队头阻塞、握手更快 |
| 实时音视频 | 低延迟优先，过期帧重传价值低 |
| 在线游戏 | 状态同步频繁，可靠性要按消息类型区分 |
| 弱网移动端 | 网络切换频繁，QUIC Connection ID 更友好 |
| 自定义传输协议 | 想在用户态快速迭代拥塞控制和恢复策略 |
| VPN/隧道 | NAT 穿透和用户态部署更方便 |

但不适合无脑使用：

1. 企业内网或老旧网络大量阻断 UDP。
2. 需要通过传统 HTTP 代理、WAF、七层网关。
3. 团队没有能力实现和运维拥塞控制、丢包恢复、观测体系。
4. 延迟收益不明显，但复杂度、成本和排障难度明显增加。

## 6. 工程选型和落地方案

如果要在系统里引入 QUIC/UDP，不应该直接把所有 TCP 链路替换掉。建议按灰度和回退设计：

1. **协议协商**：客户端优先尝试 HTTP/3，失败后回退 HTTP/2 或 HTTP/1.1。
2. **Alt-Svc / 版本协商**：服务端通过 Alt-Svc 告诉客户端支持 HTTP/3，客户端缓存能力探测结果。
3. **双栈部署**：入口同时支持 TCP/TLS 和 QUIC/UDP，避免 UDP 被阻断时不可用。
4. **拥塞控制**：使用成熟 QUIC 库，不要裸 UDP 自己乱发；至少要有 BBR/CUBIC/NewReno 等拥塞控制策略。
5. **MTU 控制**：控制 UDP payload，避免 IP 分片；公网常以 1200 字节作为保守起点。
6. **NAT keepalive**：移动网络和 NAT 设备会清理 UDP 映射，需要心跳和连接迁移策略。
7. **安全和反滥用**：UDP 容易被用于反射放大攻击，服务端要做地址验证、限流和放大因子控制。
8. **可观测性**：记录 RTT、丢包率、重传率、拥塞窗口、0-RTT 使用率、连接迁移次数和 fallback 比例。
9. **A/B 验证**：用 P50/P95/P99 延迟、首包时间、成功率、流量成本和错误率验证收益。

真实回答可以说：对移动端、跨地域和弱网用户，我会优先尝试 HTTP/3/QUIC；对内网 RPC、数据库、运维 SSH 和企业代理环境，TCP 仍然是默认选择。

## 7. 易错点

1. HTTP/3 基于 QUIC，QUIC 基于 UDP，但 QUIC 不是裸 UDP。
2. UDP 不提供可靠性，可靠性、顺序和拥塞控制要由上层实现。
3. QUIC 减少的是 TCP 层队头阻塞，不是完全没有丢包等待。
4. 0-RTT 可以降低延迟，但有重放风险，只适合幂等请求。
5. UDP 可能被防火墙、企业代理、运营商策略影响，必须有 TCP 回退。
6. 自研可靠 UDP 协议很容易低估拥塞控制、NAT、MTU、重传和安全成本。

## 8. 面试回答模板

我不认为 UDP 会直接取代 TCP。更准确地说，未来会有更多新协议选择 UDP 作为承载层，例如 QUIC/HTTP/3、实时音视频、游戏和 VPN。原因是 UDP 足够简单，应用可以在用户态实现连接迁移、多路复用、拥塞控制、FEC、加密和按业务定制的可靠性；HTTP/3 基于 QUIC，就是为了解决 TCP 升级慢、移动网络切换和 TCP 层队头阻塞等问题。

但 TCP 仍然会长期存在。它生态成熟，默认提供可靠有序字节流，中间设备和内核优化支持最好，很多数据库、RPC、SSH、传统 HTTP 和企业网络场景没有必要承担 QUIC/UDP 的复杂度。工程上我会做双栈和回退：支持 HTTP/3/QUIC 的客户端优先走 UDP，失败或网络不支持时回退 HTTP/2/TCP；同时监控 RTT、丢包、重传、连接迁移、fallback 比例和 P95 延迟。最终不是 UDP 取代 TCP，而是 TCP、QUIC 和业务自定义 UDP 协议按场景共存。
