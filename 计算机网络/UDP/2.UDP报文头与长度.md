# 2. UDP 报文头与长度

UDP 是无连接的数据报协议。它只在 IP 之上增加端口、长度和校验能力，不负责连接管理、重传、排序、流量控制和拥塞控制。

## 1. UDP 报文头

UDP 头部固定 8 字节：

| 字段 | 长度 | 作用 |
| --- | --- | --- |
| Source Port | 16 bit | 源端口，可为 0 |
| Destination Port | 16 bit | 目的端口 |
| Length | 16 bit | UDP 头部加数据的总长度 |
| Checksum | 16 bit | 校验 UDP 伪首部、头部和数据 |

`Length` 的最小值是 8，表示只有 UDP 头，没有 payload。

UDP 校验和计算时会加入 IP 伪首部，伪首部包含源 IP、目的 IP、协议号和 UDP 长度。这样可以发现“送错主机或协议”的一类错误。

## 2. UDP 最大长度

UDP `Length` 字段是 16 bit，理论上 UDP 报文最大长度为：

```text
2^16 - 1 = 65535 字节
```

扣除 8 字节 UDP 头：

```text
UDP payload 理论上限 = 65535 - 8 = 65527 字节
```

但在 IPv4 下，IP 数据报总长度字段也是 16 bit，并且还要扣除 IP 头。无 IP option 时：

```text
最大 UDP payload = 65535 - 20 - 8 = 65507 字节
```

这个值是理论上限，不是工程推荐值。

## 3. 为什么不建议发接近 64KB 的 UDP 包

大 UDP datagram 超过路径 MTU 时会触发 IP 分片。任意一个分片丢失，整个 UDP datagram 都无法重组成功。

公网或复杂内网中还会遇到：

1. NAT 或防火墙丢弃分片包。
2. ICMP 被拦截导致路径 MTU 发现失效。
3. 接收端重组缓存压力增大。
4. 分片攻击或异常分片触发安全设备拦截。

因此实时音视频、游戏、QUIC 等 UDP 应用通常会主动控制单包大小，常见策略是保持在 1200 字节左右或不超过路径 MTU。

## 4. UDP 和 TCP 头部对比

| 对比项 | UDP | TCP |
| --- | --- | --- |
| 头部长度 | 固定 8 字节 | 最小 20 字节，最大 60 字节 |
| 数据边界 | 保留 datagram 边界 | 字节流，无消息边界 |
| 可靠性 | 不保证送达、顺序、不重复 | 确认、重传、排序 |
| 流量控制 | 无 | 接收窗口 |
| 拥塞控制 | 无，需要应用层考虑 | 内置拥塞控制 |
| 典型场景 | DNS、QUIC、音视频、游戏、心跳 | HTTP/1.1、HTTP/2、MySQL、SSH |

## 5. 真实场景

1. **DNS**：常规查询优先走 UDP，响应过大或区域传送时可切到 TCP。
2. **QUIC/HTTP/3**：在 UDP 之上重新实现可靠传输、拥塞控制、TLS 和多路复用。
3. **实时音视频**：过期帧重传价值低，低延迟优先于完全可靠。
4. **游戏状态同步**：位置、朝向等状态可用新包覆盖旧包，允许少量丢包。
5. **监控心跳**：部分指标或心跳允许偶发丢失，换取低开销。

## 6. 易错点

1. UDP 有校验和，但校验和不等于可靠传输。
2. UDP 有消息边界，但消息可能丢失、乱序、重复。
3. UDP 理论最大 payload 和工程推荐单包大小不是一回事。
4. UDP 没有拥塞控制，不代表应用可以无限速发送。
5. 基于 UDP 可以实现可靠协议，QUIC 就是在用户态实现的一套可靠传输协议。

## 7. 面试回答模板

UDP 头部固定 8 字节，包括源端口、目的端口、长度和校验和。Length 是 16 bit，理论上 UDP 报文最长 65535 字节，扣掉 UDP 头 payload 是 65527 字节；但 IPv4 还要扣 IP 头，所以无 option 时最大 payload 是 65507 字节。工程上不建议发这么大，因为超过路径 MTU 会 IP 分片，任意分片丢失都会导致整个 UDP 报文失败。UDP 适合低延迟、可容忍丢包或在应用层自定义可靠性的场景，例如 DNS、QUIC、实时音视频、游戏和心跳监控。
