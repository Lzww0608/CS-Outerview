# 6. FastAPI 与 Async IO

FastAPI 基于 ASGI 生态，天然支持 `async def` 路由和异步中间件。面试问“FastAPI 有用到 Async IO 吗”，可以回答：FastAPI 本身支持异步编程模型，运行时通常由 Uvicorn/Hypercorn 提供事件循环和 ASGI Server，但是否真的异步高效，取决于你的依赖调用是不是也使用异步非阻塞库。

## 1. Async IO 是什么

Async IO 是一种单线程或少量线程内处理大量 I/O 等待任务的并发模型。核心不是让 CPU 同时执行多段 Python 代码，而是在等待网络、数据库、文件或外部 API 时把控制权让回事件循环，去处理其他请求。

基本概念：

1. **协程**：`async def` 定义的可暂停函数。
2. **await**：等待一个可等待对象完成，同时把执行权交还给事件循环。
3. **事件循环**：负责调度协程、监听 I/O 就绪、恢复任务执行。
4. **Task**：被事件循环管理的协程执行单元。

示例：

```python
import asyncio
import httpx


async def fetch(url: str) -> str:
    async with httpx.AsyncClient() as client:
        resp = await client.get(url, timeout=3)
        return resp.text


async def main():
    results = await asyncio.gather(
        fetch("https://example.com/a"),
        fetch("https://example.com/b"),
    )
    print(len(results))
```

两个请求的等待时间可以重叠，所以 I/O 密集场景吞吐更高。

## 2. FastAPI 中怎么使用

FastAPI 路由可以写成同步函数，也可以写成异步函数：

```python
from fastapi import FastAPI
import httpx

app = FastAPI()


@app.get("/async-search")
async def async_search(q: str):
    async with httpx.AsyncClient() as client:
        resp = await client.get("https://api.example.com/search", params={"q": q})
    return {"status": resp.status_code}
```

如果路由内部要访问数据库、Redis、外部 HTTP 服务，最好使用异步客户端，例如：

1. HTTP：`httpx.AsyncClient`、`aiohttp`。
2. PostgreSQL：`asyncpg`、SQLAlchemy async engine。
3. Redis：`redis.asyncio`。
4. MQ：支持 asyncio 的客户端或后台 worker。

## 3. 易错点

1. **async 函数里调用阻塞库**：例如在 `async def` 中直接用 `requests.get()`、同步 ORM、同步 Redis 客户端，会阻塞事件循环，让其他请求也卡住。
2. **CPU 密集任务不适合 Async IO**：大模型本地推理、图像处理、压缩、加密、复杂计算会占用 CPU，应该放线程池、进程池、任务队列或专门推理服务。
3. **await 不是开新线程**：`await` 是协作式让出执行权，不等于并行执行 CPU 代码。
4. **忘记超时和取消**：异步外部调用也要设置 timeout，否则大量挂起协程会耗尽连接池和内存。
5. **连接池要复用**：高并发下不要每次请求都无限创建客户端连接，生产中要管理生命周期和连接池大小。

## 4. 和多线程的区别

| 对比项 | Async IO | 多线程 |
| --- | --- | --- |
| 适用场景 | 大量网络 I/O 等待 | 阻塞库、少量并发、部分 CPU 任务 |
| 调度方式 | 事件循环协作式调度 | 操作系统抢占式调度 |
| 切换成本 | 低 | 相对高 |
| Python GIL 影响 | CPU 代码仍受 GIL 影响 | CPU 密集也受 GIL 影响 |
| 编程要求 | 依赖链都要 async 友好 | 同步代码改造成本低 |

FastAPI 对同步路由通常会放到线程池里执行，避免直接阻塞事件循环；但线程池不是无限的，阻塞调用太多仍然会排队。

## 5. 真实场景

适合 FastAPI Async IO 的场景：

1. API 聚合服务：一个请求并发访问多个下游 HTTP/RPC 服务。
2. RAG 服务：并行做 query rewrite、向量召回、BM25 召回、rerank 和模型流式返回。
3. WebSocket/SSE：大量长连接等待事件或流式 token。
4. 轻量模型网关：主要转发请求到外部模型服务，而不是本地重计算。

不适合只靠 Async IO 的场景：

1. 本地 CPU/GPU 推理耗时很长。
2. 大文件压缩、图像处理、PDF OCR。
3. 同步数据库驱动无法替换，且调用延迟很高。

这些任务可以改成后台任务队列，例如 Celery/RQ/Arq，或拆成独立 worker 服务。

## 6. 面试回答模板

FastAPI 支持 Async IO，因为它运行在 ASGI 生态上，路由可以写成 `async def`，底层由 Uvicorn/Hypercorn 的事件循环调度协程。Async IO 的核心是 I/O 等待时通过 `await` 让出执行权，让同一个线程处理其他请求，适合网络调用、数据库查询、Redis、SSE/WebSocket 这类 I/O 密集场景。但它不是自动变快，如果在 `async def` 里调用 `requests` 或同步 ORM，仍然会阻塞事件循环。CPU 密集任务要放进线程池、进程池、任务队列或单独服务。生产中还要注意超时、连接池、取消、限流和阻塞依赖排查。
