# 1. Elasticsearch 核心原理与使用场景

Elasticsearch 是基于 Lucene 的分布式搜索和分析引擎，适合做全文检索、日志检索、指标分析和近实时查询。它不是传统关系型数据库，核心优势是倒排索引和分布式查询。

## 1. 核心概念

1. **Document**：一条 JSON 文档，是 ES 的基本存储单位。
2. **Index**：一类文档的逻辑集合，类似一张表，但不是关系表。
3. **Mapping**：字段类型和分词规则定义，决定字段如何索引和查询。
4. **Shard**：索引被切分成多个主分片，分布在不同节点上。
5. **Replica**：分片副本，用于高可用和提升读吞吐。
6. **倒排索引**：从词项映射到文档集合，适合全文检索。

## 2. 倒排索引为什么适合搜索

普通数据库 B+ 树更擅长按字段值做精确匹配和范围查询；全文搜索要回答“哪些文档包含某个词，相关度如何”，更适合倒排索引。

简化流程：

```text
文档: "go grpc service discovery"
分词: go, grpc, service, discovery
倒排: grpc -> [doc1, doc5, doc9]
```

查询时，ES 根据关键词找到候选文档，再结合 BM25、字段权重、过滤条件和排序规则返回结果。

## 3. 我会怎么使用 ES

常见使用方式：

1. **日志检索**：应用日志写入 Kafka，再通过 Logstash/Filebeat/Vector 写入 ES，按 traceId、服务名、错误码检索。
2. **业务搜索**：商品、用户、文章、工单等内容建立搜索索引，支持关键词、过滤、排序和高亮。
3. **辅助索引**：MySQL 作为权威存储，ES 作为查询侧索引，通过 binlog/Canal/MQ 同步变更。
4. **聚合分析**：按时间、字段、标签做统计聚合，适合运营看板和故障排查。

设计时要关注：

1. mapping 提前设计，避免动态 mapping 把字段识别错。
2. text 用于分词检索，keyword 用于精确匹配、聚合和排序。
3. 分片数量不要盲目过大，分片太多会增加集群管理和查询开销。
4. 写入链路要做幂等，文档 ID 通常用业务主键或 `业务主键 + version`。
5. ES 不是事务权威源，重要业务状态仍应落在 MySQL、PostgreSQL 等主存储中。

## 4. 和数据库的关系

ES 常作为查询侧系统，而不是主交易库：

```text
MySQL/binlog -> Canal/MQ -> Indexer -> Elasticsearch
                              |
                              -> 失败重试/死信/补偿任务
```

这样做的原因是 MySQL 保证事务和一致性，ES 提供复杂检索能力。缺点是存在同步延迟和双写一致性问题，因此要用版本号、重试、补偿扫描和监控来兜底。

## 5. 易错点

1. ES 默认是近实时搜索，写入后通常要等 refresh 才能被搜索到。
2. 分词字段不能直接用于精确聚合，通常要配套 keyword 子字段。
3. 深分页代价高，应该用 `search_after` 或 scroll/PIT。
4. ES 不适合高频单文档事务更新，频繁 update 本质上会产生新段和旧版本回收压力。
5. 查询过宽、聚合基数过高、分片过多都会造成堆内存和查询延迟问题。

## 6. 面试回答模板

Elasticsearch 是基于 Lucene 的分布式搜索引擎，核心是倒排索引。文档写入后会按 mapping 做分词和字段索引，查询时通过词项快速找到候选文档，再按相关度、过滤和排序返回结果。我通常把 ES 用在日志检索、全文搜索、辅助索引和聚合分析里，MySQL 仍作为权威数据源，ES 作为查询侧。工程上要重点关注 mapping、分片副本、refresh 延迟、同步一致性、深分页和高基数聚合。
