# 1. Nginx架构与事件模型

Nginx 是高性能 Web 服务器、反向代理和负载均衡器。面试里问“讲下 Nginx”，通常不是让背配置指令，而是考察它为什么能支撑高并发连接、master/worker 模型怎么工作、事件驱动和 epoll 如何结合。

## 1. Nginx 的核心能力

常见用途：

1. 静态资源服务。
2. HTTP 反向代理。
3. 七层负载均衡。
4. TLS 终止。
5. 限流、访问控制、灰度路由。
6. WebSocket、长连接代理。
7. 日志和可观测入口。

它的核心优势是用少量 worker 进程通过事件驱动处理大量连接，而不是一连接一线程。

## 2. Master/Worker 模型

Nginx 通常由一个 master 进程和多个 worker 进程组成。

Master 负责：

1. 读取和校验配置。
2. 创建监听 socket。
3. fork worker。
4. 处理信号，例如 reload、quit、stop、reopen log。
5. 平滑重载配置和平滑升级。
6. 监控 worker，异常退出后重新拉起。

Worker 负责：

1. 接收新连接。
2. 运行事件循环。
3. 处理 HTTP 状态机。
4. 读写 socket。
5. 访问 upstream。
6. 写访问日志和错误日志。

Worker 之间通常互不共享请求状态，这让 Nginx 的并发模型更简单，也减少锁竞争。

## 3. 事件驱动模型

在 Linux 下，Nginx 主要使用 `epoll` 处理连接事件。

简化流程：

```text
worker 启动
-> 把 listen fd 加入 epoll
-> epoll_wait 等待事件
-> accept 新连接
-> 连接 fd 加入 epoll
-> 可读时解析请求
-> 需要代理时连接 upstream
-> 可写时发送响应
-> keep-alive 或关闭连接
```

Nginx 的事件模型有几个关键点：

1. **非阻塞 I/O**：socket 读写不能阻塞 worker。
2. **状态机**：HTTP 解析、upstream 请求、响应发送都拆成多个事件阶段。
3. **定时器**：连接空闲、upstream 超时、keep-alive 都由定时器管理。
4. **缓冲区**：读写过程中维护输入输出缓冲，处理半包、部分写和慢客户端。
5. **sendfile/零拷贝**：静态文件发送可以减少用户态和内核态拷贝。

## 4. 为什么 Nginx 高并发

主要原因：

1. **事件驱动**：一个 worker 可以管理大量空闲连接。
2. **非阻塞 I/O**：慢连接不会长期占住线程。
3. **多进程隔离**：worker 崩溃影响范围小，进程间锁竞争少。
4. **高效内存管理**：请求级内存池减少频繁 malloc/free。
5. **零拷贝和缓存**：静态资源可用 `sendfile`、open file cache 等优化。
6. **成熟超时控制**：连接、读、写、upstream 都有超时和限速配置。
7. **热重载**：配置变更时不中断已有连接。

## 5. 负载均衡策略

Nginx upstream 常见策略：

1. **轮询**：默认策略，简单均衡。
2. **加权轮询**：按机器配置或容量设置权重。
3. **ip_hash**：同一客户端尽量落到同一后端，适合简单会话保持。
4. **least_conn**：优先发给连接数少的后端。
5. **hash key consistent**：按 key 做一致性哈希，适合缓存命中或分片路由。

生产中还要配合健康检查、超时、重试、熔断和摘除故障节点。

## 6. 和业务服务器的边界

Nginx 适合做接入层和代理层，不适合把复杂业务逻辑都塞进去。

常见边界：

1. TLS、限流、静态文件、压缩、反向代理放在 Nginx。
2. 复杂业务规则、事务、权限模型放在后端服务。
3. OpenResty/Lua 可以做轻量鉴权、灰度、路由和边缘聚合，但要控制阻塞调用。
4. 需要强业务状态时，交给应用服务和数据库。

## 7. 易错点

1. Nginx 高并发不是因为线程特别多，而是事件驱动和非阻塞 I/O。
2. worker 数不是越多越好，通常接近 CPU 核数，并结合压测调整。
3. 反向代理要设置合理超时，否则慢 upstream 会拖住连接资源。
4. 重试要谨慎，非幂等请求重试可能造成重复写。
5. 长连接和 WebSocket 会占用连接资源，要配置连接数和空闲超时。
6. 日志同步写盘可能影响性能，高流量场景要关注日志缓冲和采样。

## 8. Nginx 和 Apache 的实现差异

Apache HTTP Server 更早，模块生态强，历史上常见模型是阻塞 I/O 加进程/线程池；Nginx 从设计上更偏事件驱动和反向代理。

Apache 常见 MPM：

1. **prefork**：多个进程，每个进程一次处理一个连接。兼容性好，隔离强，但内存占用高。
2. **worker**：多进程 + 多线程，一个线程处理一个连接，资源利用率更好。
3. **event**：在 worker 基础上把 keep-alive 空闲连接交给事件机制，减少工作线程被空闲连接占住。

对比：

| 对比项 | Nginx | Apache |
| --- | --- | --- |
| 典型模型 | master/worker + 非阻塞事件驱动 | prefork/worker/event MPM |
| 高并发长连接 | 更擅长，少量 worker 管理大量连接 | prefork/worker 下容易被连接数占满，event MPM 改进 |
| 模块生态 | 反向代理、接入层能力强 | 历史模块生态丰富，动态内容集成多 |
| 内存模型 | worker 进程较少，请求状态机推进 | 进程/线程数量可能随并发上升 |
| 适用边界 | 反向代理、静态资源、负载均衡、TLS | 传统 Web 服务、复杂模块生态、兼容性场景 |

简单回答：Nginx 的核心优势是非阻塞事件驱动，适合大量连接和代理场景；早期 Apache prefork 是一连接一进程，隔离强但资源重，后续 worker/event MPM 才逐步降低线程和 keep-alive 连接成本。

## 9. 面试回答模板

Nginx 是典型 master/worker 多进程事件驱动服务器。Master 负责配置、信号、fork worker、平滑重载和监控；worker 负责处理连接和请求。Linux 下 worker 用 epoll 等待监听 socket 和连接 socket 的就绪事件，所有 fd 都是非阻塞的，HTTP 解析、upstream 代理和响应发送通过状态机推进。它高并发的核心不是一连接一线程，而是少量 worker 通过 epoll 管理大量连接，再配合内存池、sendfile、定时器、缓冲区和成熟的超时控制。作为接入层，Nginx 适合做静态资源、反向代理、TLS 终止、负载均衡、限流和灰度，复杂业务逻辑仍应放在后端服务。
