# Q49.实现高可用

Redis为了实现高可用，主要可以通过主从复制（Replication）、哨兵（Sentinel）、以及集群（Cluster）等机制来实现：

1. **主从复制（Replication）**: 通过主从复制可以实现Redis的数据备份，也是实现高可用、故障恢复、负载均衡的基础。复制的核心思想就是，设置一个主节点（Master），将数据写入主节点，然后由一个或多个从节点（Slave）复制主节点的数据。如果主节点服务中断，可以立即将备用的从节点数据提升为主节点，继续提供服务。
2. **哨兵（Sentinel）**: 哨兵模式是在主从复制基础上实现自动故障转移。哨兵通过监控主节点和从节点的运行情况，如果主节点发生故障，哨兵可以自动将从节点晋升为主节点，实现服务的无缝转移。
3. **集群（Cluster）**: Redis Cluster通过分片技术将数据分布在多个Redis实例中，实现了数据的横向扩展以及高可用。如果某个Redis实例发生故障，可以依靠Redis Cluster的故障转移机制，将故障实例上的数据管理权迁移到其他正常的Redis实例上，继续提供服务。

使用这些机制时，需要根据具体的使用场景和需求进行选择，以上三种方式也可以结合使用，以达到最好的高可用效果。比如一般生产环境下，会使用主从复制和哨兵两者结合的方式进行部署，以实现高可用。

## 主从、哨兵、Cluster 的区别

| 架构 | 解决的问题 | 是否分片 | 故障转移 | 典型场景 |
| --- | --- | --- | --- | --- |
| 主从复制 | 数据副本、读扩展、备份基础 | 不分片 | 需要人工或外部组件切主 | 数据量可放单机，主要想读扩展 |
| Sentinel | 主从架构的自动故障转移 | 不分片 | 哨兵选主、通知客户端 | 数据量可放单机，但要求自动高可用 |
| Cluster | 分片扩容 + 高可用 | 按 16384 槽分片 | 分片内从节点提升为主 | 数据量或 QPS 超过单机，需要水平扩展 |

主从复制本身不等于完整高可用。主节点挂掉后，如果没有哨兵、运维平台或客户端切换逻辑，业务仍然不知道该写哪个节点。

哨兵解决的是“谁是新主”的问题，但所有数据仍然在一个主从复制组中，写入能力和总容量仍受单主限制。

Cluster 解决的是水平扩展。它把 key 映射到固定的 `16384` 个 hash slot，每个主节点负责一部分槽，每个主节点再配从节点。客户端根据槽路由请求，遇到 `MOVED` 或 `ASK` 重定向时更新本地槽表。

## 数据分片原理

Redis Cluster 的 key 路由大致是：

```text
slot = CRC16(key) % 16384
slot -> master node
```

如果 key 中带 hash tag，只有 `{}` 内的内容参与槽计算：

```text
user:{1001}:profile
user:{1001}:order
```

这两个 key 会落到同一个 slot，适合需要同槽多 key 操作的场景。但不要滥用 hash tag，否则会把大量 key 强行打到同一个槽，造成热点。

分片的价值：

1. **扩展容量**：单机内存放不下时，把数据拆到多个主节点。
2. **扩展吞吐**：不同 key 的请求分散到不同节点。
3. **缩小故障域**：某个分片异常时，只影响部分槽。

分片带来的代价：

1. 跨槽多 key 命令受限，例如跨 slot 的 `MGET/MSET`、Lua 脚本、事务都要谨慎。
2. 扩缩容需要迁移 slot，迁移期间客户端要处理 `ASK` 重定向。
3. 热点 key 或 hash tag 设计不当仍会造成单分片过载。
4. Redis Cluster 采用异步复制，不能承诺强一致，主节点故障时可能丢失尚未同步到从节点的写入。

## 如何选择

1. **纯缓存、数据量小、希望自动切主**：主从 + Sentinel 通常足够。
2. **缓存数据量大或单机 QPS 不够**：选择 Redis Cluster。
3. **老系统迁移且客户端不支持 Cluster**：可以考虑代理层方案，但要评估代理高可用和延迟。
4. **强一致核心数据**：不要只依赖 Redis 高可用。Redis 可以做缓存、限流、会话、排行榜，余额、库存最终扣减等仍应以数据库事务或强一致服务兜底。

## 面试回答模板

Redis 高可用可以分三层回答：主从复制提供副本和读扩展，哨兵在主从基础上做监控、选主和自动故障转移，Redis Cluster 则进一步用 16384 个 hash slot 做数据分片，同时每个分片内部通过主从实现高可用。主从和哨兵不解决单机容量和写入瓶颈；Cluster 能水平扩展，但会引入跨槽命令限制、槽迁移、热点分片和异步复制丢数据风险。选型时先看数据量和 QPS 是否超过单机，再看客户端支持、运维复杂度和业务一致性要求。
