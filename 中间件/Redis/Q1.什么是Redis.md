# Q1.什么是Redis

Redis 是一个基于内存的高性能 Key-Value 数据库，也常被用作缓存、分布式锁、计数器、排行榜、延迟队列和轻量消息通道。它不是只支持简单字符串，而是提供了 String、Hash、List、Set、ZSet、Bitmap、HyperLogLog、Stream 等数据结构。

## 1. Redis 的核心特点

1. **内存读写**：主要数据结构常驻内存，读写路径短，延迟通常在微秒到毫秒级。
2. **数据结构丰富**：不同业务可以选择不同结构，避免所有需求都落到关系表或 JSON 大字段。
3. **单线程命令执行模型**：核心命令在主线程串行执行，避免复杂锁竞争；网络 I/O 和后台任务在新版本中可以部分多线程化。
4. **I/O 多路复用**：通过 Reactor 模型管理大量连接，Linux 下常用 epoll。
5. **持久化能力**：支持 RDB 快照和 AOF 日志，也可以两者结合。
6. **高可用和扩展**：支持主从复制、哨兵、Cluster 分片。

## 2. 常见数据结构和场景

| 类型 | 底层思路 | 典型场景 |
| --- | --- | --- |
| String | SDS，支持整数编码、embstr/raw | 缓存值、计数器、分布式锁 value |
| Hash | listpack/hashtable | 对象字段缓存、用户信息 |
| List | quicklist | 简单队列、最新消息列表 |
| Set | intset/hashtable | 去重、共同关注、标签集合 |
| ZSet | listpack/skiplist + dict | 排行榜、延迟队列、按分数范围查询 |
| Bitmap | String 上的位操作 | 签到、在线状态、布尔特征集合 |
| HyperLogLog | 概率统计 | UV 去重计数 |
| Stream | radix tree + 消费组 | 消息流、轻量 MQ |

面试回答时不要只说“Redis 很快”，最好能把数据结构和业务场景对应起来。例如排行榜优先考虑 ZSet，签到可以用 Bitmap，热点对象缓存可以用 String 或 Hash。

## 3. 为什么 Redis 快

1. 数据主要在内存中，避免磁盘随机 I/O。
2. 核心命令串行执行，不需要在每个数据结构上做细粒度锁。
3. 使用 epoll/kqueue 等 I/O 多路复用模型，少量线程管理大量连接。
4. 数据结构实现针对场景优化，例如小 Hash 用紧凑编码，大对象再转为哈希表。
5. 后台线程处理 AOF fsync、lazy free、关闭文件等慢操作，减少主线程阻塞。

需要补充的是：单线程不代表所有操作都快。大 key 删除、全量扫描、复杂 Lua、大范围 ZSet 查询都可能阻塞主线程。

## 4. 持久化和高可用

Redis 常见持久化方式：

1. **RDB**：周期性生成快照，恢复快，占用文件小，但两次快照之间的数据可能丢失。
2. **AOF**：记录写命令，丢数据窗口取决于 fsync 策略，文件可能更大，需要 rewrite 压缩。
3. **混合持久化**：AOF 文件前半部分是 RDB，后半部分是增量命令，兼顾恢复速度和数据完整性。

高可用常见方案：

1. 主从复制用于读扩展和故障恢复。
2. 哨兵负责主节点故障检测、选主和通知客户端。
3. Cluster 用哈希槽做分片，支持数据横向扩展。

## 5. 易错点

1. Redis 适合做缓存和高频状态，不适合替代关系数据库保存复杂事务关系。
2. `KEYS *`、大范围 `HGETALL`、大 key 删除都可能阻塞线上实例，应使用 `SCAN`、分批处理或 lazy free。
3. 分布式锁必须设置过期时间和唯一 value，释放时要校验 value，避免误删别人的锁。
4. 缓存要考虑穿透、击穿、雪崩和一致性，不是“加一层 Redis”就一定安全。
5. Redis 的引用场景要关注内存上限、淘汰策略、热 key、大 key、持久化和主从延迟。

## 6. 面试回答模板

Redis 是一个内存型 Key-Value 数据库，核心优势是低延迟、数据结构丰富和生态成熟。它通过内存读写、单线程命令执行、I/O 多路复用和紧凑数据结构实现高性能，常用于缓存、排行榜、计数器、分布式锁、限流和轻量消息流。生产上还要关注 RDB/AOF 持久化、主从复制、哨兵或 Cluster 高可用，以及缓存穿透、热点 key、大 key、慢命令和内存淘汰策略。
