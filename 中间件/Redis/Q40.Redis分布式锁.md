# Q40.Redis分布式锁

分布式锁的三个核心要素

**1、加锁**

推荐使用 Redis 2.6.12 之后的 `SET key value NX EX seconds` 一条命令完成加锁和设置过期时间。key 是锁的唯一标识，按业务来决定命名；value 不要写固定字符串，应该写随机 token，例如 UUID，用于后续安全解锁。

```redis
SET lock:order:1001 8f3b1c6a-4a55-4d78-9e2b-1f8b2fd7f9f0 NX EX 30
```

返回 `OK` 表示 key 原本不存在，当前客户端成功获得锁；返回 `nil` 表示 key 已存在，抢锁失败。

`SET NX EX` 能实现锁的效果，是因为 Redis 单条命令在服务端执行是原子的：

1. `NX` 保证只有 key 不存在时才能写入，多个客户端并发竞争时只有一个会成功。
2. `EX` 给锁设置过期时间，避免持锁客户端宕机后锁永远不释放。
3. value 使用随机 token，保证解锁时只能释放自己加的锁。

不要再用 `SETNX` 后接 `EXPIRE` 的两条命令实现锁，因为两条命令之间客户端可能宕机，留下无过期时间的死锁 key。

**2、解锁**

有加锁就得有解锁。当得到的锁的线程执行完任务，需要释放锁，以便其他线程可以进入。释放锁的最简单方式就是执行del指令。

```redis
DEL lock:order:1001
```

但直接 `DEL` 有误删风险：如果业务执行超过 30 秒，锁自动过期后被客户端 B 获取，客户端 A 再执行 `DEL` 会删掉 B 的锁。

安全解锁要用 Lua 保证“校验 token + 删除”原子完成：

```lua
if redis.call("GET", KEYS[1]) == ARGV[1] then
    return redis.call("DEL", KEYS[1])
else
    return 0
end
```

调用时：

```redis
EVAL <script> 1 lock:order:1001 8f3b1c6a-4a55-4d78-9e2b-1f8b2fd7f9f0
```

**3、锁超时**

锁超时指的是：如果一个得到锁的线程在执行任务的过程中挂掉，来不及显式地释放锁，这块资源将会永远被锁住，别的线程无法进来。

所以，setnx的key必须设置一个超时时间，以保证即使没有被显式释放，这把锁也要在一段时间后自动释放。setnx不支持超时参数，所以需要额外指令，

```java
expire key 30
```

**上述分布式锁存在的问题**：

通过上述setnx 、del和expire实现的分布式锁还是存在着一些问题。

**1、SETNX 和 EXPIRE 非原子性**

假设一个场景中，某一个线程刚执行setnx，成功得到了锁。此时setnx刚执行成功，还未来得及执行expire命令，节点就挂掉了。此时这把锁就没有设置过期时间，别的线程就再也无法获得该锁。

**解决措施:**

由于setnx指令本身是不支持传入超时时间的，而在Redis2.6.12版本上为set指令增加了可选参数, 用法如下：

```java
SET key value [EX seconds][PX milliseconds] [NX|XX]
```

- EX second: 设置键的过期时间为second秒；
- PX millisecond：设置键的过期时间为millisecond毫秒；
- NX：只在键不存在时，才对键进行设置操作；
- XX：只在键已经存在时，才对键进行设置操作；
- SET操作完成时，返回OK，否则返回nil。

所以更推荐的加锁命令是：

```redis
SET lock_key unique_token NX PX 30000
```

其中 `PX 30000` 表示 30 秒过期，粒度比 `EX` 更细。

**2、锁误解除**

如果线程 A 成功获取到了锁，并且设置了过期时间 30 秒，但线程 A 执行时间超过了 30 秒，锁过期自动释放，此时线程 B 获取到了锁；随后 A 执行完成，线程 A 使用 DEL 命令来释放锁，但此时线程 B 加的锁还没有执行完成，线程 A 实际释放的线程 B 加的锁。

**解决办法：**

在del释放锁之前加一个判断，验证当前的锁是不是自己加的锁。

具体在加锁的时候把当前线程的id当做value，可生成一个 UUID 标识当前线程，在删除之前验证key对应的value是不是自己线程的id。

还可以使用 lua 脚本做验证标识和解锁操作。

**3、超时解锁导致并发**

如果线程 A 成功获取锁并设置过期时间 30 秒，但线程 A 执行时间超过了 30 秒，锁过期自动释放，此时线程 B 获取到了锁，线程 A 和线程 B 并发执行。

A、B 两个线程发生并发显然是不被允许的，一般有两种方式解决该问题：

- 将过期时间设置足够长，确保代码逻辑在锁释放之前能够执行完成。
- 为获取锁的线程增加守护线程，为将要过期但未释放的锁增加有效时间。

**4、不可重入**

当线程在持有锁的情况下再次请求加锁，如果一个锁支持一个线程多次加锁，那么这个锁就是可重入的。如果一个不可重入锁被再次加锁，由于该锁已经被持有，再次加锁会失败。Redis 可通过对锁进行重入计数，加锁时加 1，解锁时减 1，当计数归 0 时释放锁。

**5、无法等待锁释放**

上述命令执行都是立即返回的，如果客户端可以等待锁释放就无法使用。

## Redisson 分布式锁和性能评估

Redisson 在 Redis 分布式锁上封装了可重入、阻塞等待、自动续期和发布订阅通知等能力。常见实现思路是：

1. 锁 key 使用 Hash 结构，field 保存客户端线程标识，value 保存重入次数。
2. 加锁成功后，如果没有显式 lease time，启动 watchdog 定期续期，避免业务未执行完锁过期。
3. 解锁时减少重入计数，计数为 0 才删除锁 key。
4. 等锁线程不只靠忙等，通常结合 Pub/Sub 等待释放通知，再重试获取。

性能测试不能只测“单次加锁耗时”，要看业务场景：

1. **低竞争**：主要成本是 Redis 往返延迟和 Lua 执行，通常比较稳定。
2. **高竞争**：大量客户端争同一把锁会导致等待、重试、通知风暴，吞吐接近串行。
3. **锁粒度过大**：即使 Redis 很快，业务也会被锁串行化。
4. **长事务/长任务**：watchdog 续期会增加 Redis 写流量，服务暂停或 STW 可能导致续期失败。
5. **Redis 故障切换**：主从异步复制下，极端情况下可能出现锁状态丢失或短暂双持有，需要业务幂等兜底。

秒杀、抢券这类高并发扣库存场景，一般不推荐用一把分布式锁串行化所有请求。更常见的做法是 Redis Lua 原子扣减、库存分片、令牌桶、MQ 异步落库和数据库条件更新兜底。分布式锁更适合低频排他任务，例如定时任务防重复执行、缓存重建互斥、资源迁移互斥。

## 面试回答模板

Redis 分布式锁最基础的实现是 `SET lock_key unique_token NX EX 30`。`NX` 保证只有 key 不存在时才能写入，所以并发竞争下只有一个客户端成功；`EX` 设置过期时间，防止客户端宕机后死锁；`unique_token` 用来标识锁的持有者。释放锁不能直接 `DEL`，要用 Lua 脚本先判断 value 是否等于自己的 token，再删除，避免误删别人的锁。长任务还要考虑锁续期、业务幂等和超时导致的并发执行；如果对一致性要求很高，可以考虑 ZooKeeper、etcd 或数据库唯一约束等方案。
