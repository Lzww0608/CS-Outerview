# Q29.引入多线程

虽然Redis的主要操作仍然是单线程执行的，但是在Redis 6.0版本中，它引入了多线程来处理某些特定的任务，特别是网络I/O的处理。这是因为随着硬件和网络技术的发展，多核处理器和高速网络已经变得普遍，对于CPU密集型的服务来说，单线程可能无法充分利用这些资源。

具体来说，在Redis 6.0中，主线程负责执行命令，而额外的IO线程则用来处理客户端和服务器之间的数据交换，包括接收请求和发送响应。这样做的好处是可以充分利用多核处理器，同时还能减少因网络I/O阻塞导致的处理速度下降。

需要注意的是，这些I/O线程并不会直接处理Redis命令，执行命令仍然是单线程的。只是在读取客户端请求和发送响应的时候使用了多线程处理。这样在提升吞吐量的同时，避免了多线程编程中数据一致性和同步问题的复杂性。

此外，Redis 6.0版中的多线程默认是关闭的，需要在Redis的配置文件中手动开启。使用”io-threads”选项可以指定线程数，使用”io-threads-do-reads”选项可以启动多线程。

## 为什么不是多线程执行命令

Redis 引入多线程主要是为了缓解网络 I/O 和协议读写的瓶颈，而不是把核心命令执行改成多线程。

一次请求大致分成几段：

```text
读取 socket -> 解析 RESP -> 执行命令 -> 生成响应 -> 写回 socket
```

Redis 6 的 I/O 多线程主要分担读写 socket、协议解析/响应写回相关工作；真正修改 Redis 内部数据结构的命令执行仍由主线程串行完成。

这样设计的原因：

1. **保持命令原子性**：单条命令不需要额外加锁就能保证执行期间不被其他命令打断。
2. **避免复杂锁粒度**：Redis 内部有 string、list、hash、set、zset、stream、过期字典、复制状态等结构，多线程执行命令会带来大量锁和一致性问题。
3. **减少上下文切换和锁竞争**：热点 key 场景下，多线程命令执行未必更快，反而可能被锁竞争拖慢。
4. **兼容 Lua 和事务语义**：Lua 脚本、MULTI/EXEC、过期删除、AOF/复制都依赖较清晰的串行执行模型。

## 什么时候收益明显

I/O 多线程更适合以下场景：

1. 大 value 读写较多，网络收发和协议编解码成本高。
2. 单实例 QPS 很高，CPU 主要消耗在读写 socket，而不是命令逻辑。
3. 机器有多核可用，且 Redis 主线程已经接近瓶颈。

收益不明显的场景：

1. 主要瓶颈在慢命令，例如大 key、复杂 Lua、`KEYS`、大范围 `ZRANGE`。
2. 主要瓶颈在磁盘 AOF fsync、复制网络、下游业务。
3. value 很小、命令很简单且单线程已经足够。

## 面试回答模板

Redis 早期坚持单线程执行命令，是为了让内部数据结构天然串行化，避免加锁和上下文切换。Redis 6 引入多线程主要处理网络 I/O：读取请求、解析协议、写回响应可以交给 I/O 线程，但命令执行仍在主线程完成。因此它提升的是高吞吐场景下的网络读写能力，不改变 Redis 命令原子性模型。是否开启要看瓶颈，如果是大 key、慢命令或磁盘 fsync，I/O 多线程解决不了核心问题。
