# Q58.Redis Lua解决超卖和一人一单

Redis + Lua 解决超卖和一人一单，本质是把“查库存、判断用户是否已下单、扣减库存、记录用户已下单、投递下单消息”这几个步骤放到 Redis 服务端一次性原子执行，避免并发请求在多条命令之间穿插执行。

面试里可以先说结论：**Redis Lua 能解决的是 Redis 层的并发原子性问题，可以快速拦截超卖和重复下单；但它不能单独保证整个交易链路最终正确，最终还要靠数据库唯一约束、库存条件更新、消息幂等、失败补偿和定时对账兜底。**

## 1. 超卖和一人一单分别是什么

### 1.1 超卖

超卖是指实际成功订单数量超过可售库存。例如库存只有 100 件，但并发请求下最终生成了 101 个有效订单。

常见原因：

1. 先查库存再扣库存不是原子操作。
2. 多个应用实例同时读到库存大于 0。
3. 数据库更新没有条件约束，例如没有 `stock > 0`。
4. 缓存扣减成功但数据库落库失败后补偿不正确。
5. MQ 重复消费导致重复扣减或重复创建订单。

### 1.2 一人一单

一人一单是指同一个用户在同一个活动或商品维度只能成功购买一次。

常见风险：

1. 用户重复点击。
2. 客户端或网关重试。
3. 多个设备同时下单。
4. MQ 重复消费。
5. 应用服务多实例并发处理同一用户请求。

如果只在应用内存加锁，只能限制单个 JVM 或单个进程，不能解决多实例并发。

## 2. 为什么普通 Redis 命令不够

错误写法通常是：

```text
GET stock
SISMEMBER bought userId
DECR stock
SADD bought userId
```

这些命令单条都是原子的，但组合起来不是原子的。两个请求可能同时执行到 `GET stock > 0` 和 `SISMEMBER = false`，然后都扣减成功，导致超卖或重复下单。

Lua 的价值在于把多步操作合并成一个不可插入的执行单元：

```text
请求 A 执行 Lua
  查库存
  查已购集合
  扣库存
  记录已购
  写消息
请求 B 只能等 A 完整执行完之后再执行
```

Redis 单线程执行脚本期间，其他客户端命令不能插入同一个 Redis 实例的执行流，因此可以保证这段逻辑在 Redis 节点内原子。

## 3. Key 设计

假设活动 ID 是 `act100`，商品 ID 是 `sku200`，可以设计：

```text
stock:{act100}:sku200      -> String，库存数量
bought:{act100}:sku200     -> Set，已成功预扣的 userId
order_stream:{act100}      -> Stream，成功预扣后的下单消息
```

如果使用 Redis Cluster，多 key Lua 脚本要求所有 key 在同一个 hash slot。可以用 hash tag：

```text
stock:{act100}:sku200
bought:{act100}:sku200
order_stream:{act100}
```

这些 key 的 hash tag 都是 `{act100}`，会落到同一个 slot，脚本才能在 Cluster 下执行。

注意取舍：

1. 同一个活动的所有热点 key 放到一个 slot，原子性强，但可能形成单 slot 热点。
2. 如果活动流量极高，可能需要库存分桶，但分桶后每次 Lua 只能操作一个桶，不能跨 slot 做全局原子扣减。
3. 一人一单维度要明确：是同一活动一单、同一商品一单，还是同一用户全场一单。

## 4. Lua 脚本实现

### 4.1 基础版本

```lua
-- KEYS[1] = stock key
-- KEYS[2] = bought users set key
-- KEYS[3] = order stream key
-- ARGV[1] = userId
-- ARGV[2] = orderId
-- ARGV[3] = skuId
-- ARGV[4] = nowMillis

local stock = tonumber(redis.call('GET', KEYS[1]) or '0')
if stock <= 0 then
    return 1 -- sold out
end

if redis.call('SISMEMBER', KEYS[2], ARGV[1]) == 1 then
    return 2 -- duplicate order
end

redis.call('DECR', KEYS[1])
redis.call('SADD', KEYS[2], ARGV[1])
redis.call(
    'XADD',
    KEYS[3],
    '*',
    'orderId', ARGV[2],
    'userId', ARGV[1],
    'skuId', ARGV[3],
    'time', ARGV[4]
)

return 0 -- success
```

返回码可以约定为：

```text
0: 成功，进入异步下单链路
1: 库存不足
2: 重复下单
```

执行方式：

```text
EVALSHA sha1 3 stock:{act100}:sku200 bought:{act100}:sku200 order_stream:{act100} user123 order789 sku200 1714800000000
```

线上一般使用 `SCRIPT LOAD` 预加载脚本，再用 `EVALSHA` 调用。遇到 `NOSCRIPT` 时，客户端回退到 `EVAL` 或重新加载脚本。

### 4.2 为什么先校验再写入

Lua 不提供数据库事务那样的自动回滚。脚本执行中如果前面已经写入，后面因为运行时错误失败，Redis 不会自动撤销已经执行的写操作。

所以脚本要遵守：

1. 先做所有必要校验。
2. 再做状态修改。
3. 写入逻辑尽量短小、确定、无复杂循环。
4. 避免在写入之后执行可能报错的复杂逻辑。

上面的脚本中，先判断库存和重复下单，再执行 `DECR`、`SADD`、`XADD`。

## 5. 整体链路设计

一个更完整的秒杀链路是：

```text
活动预热
  -> MySQL 活动和库存加载到 Redis
  -> 网关限流、风控、验证码或排队
  -> 应用调用 Redis Lua
  -> Lua 原子校验、预扣库存、记录已购、写 Stream/MQ
  -> 应用立即返回“排队中/下单成功受理”
  -> 消费者异步创建订单并落 MySQL
  -> 失败重试、死信、补偿、对账
```

Redis 负责挡住高并发峰值，MySQL 不直接承受全部秒杀流量。

但 Redis 预扣成功不等于订单最终成功。真正的订单状态要以 MySQL 落库结果为准。

## 6. 数据库如何兜底

即使用了 Redis Lua，数据库仍然必须有最终约束。

### 6.1 一人一单唯一约束

订单表加唯一索引：

```sql
CREATE UNIQUE INDEX uk_user_activity_sku
ON seckill_order(user_id, activity_id, sku_id);
```

消费者落库时，如果重复消费或重复消息到达，唯一索引会阻止重复订单。

### 6.2 库存条件更新

如果最终库存仍在 MySQL 里维护，扣减时要带条件：

```sql
UPDATE seckill_stock
SET stock = stock - 1
WHERE activity_id = ?
  AND sku_id = ?
  AND stock > 0;
```

只有影响行数为 1 才表示扣减成功。影响行数为 0 说明数据库侧库存不足或状态不满足。

### 6.3 幂等消费

消费者处理 Redis Stream 或 MQ 消息时要幂等：

```sql
CREATE UNIQUE INDEX uk_order_id
ON seckill_order(order_id);
```

处理流程：

```text
读取消息
-> 开启本地事务
-> 插入订单，依赖 order_id 或 user_id + activity_id 唯一约束
-> 条件扣减 DB 库存或写库存流水
-> 提交事务
-> ACK 消息
```

如果 ACK 失败导致消息再次投递，唯一约束和业务状态判断要保证重复处理结果等价于处理一次。

## 7. Redis 预扣和 MySQL 落库不一致怎么办

典型不一致：

1. Redis 预扣成功，消息投递失败。
2. Redis 预扣成功，消息投递成功，但消费者落库失败。
3. 消费者落库成功，但 ACK 失败，消息重复消费。
4. Redis 主从切换导致最近预扣状态丢失。
5. 活动结束后 Redis 和 DB 库存不一致。

处理方式：

1. **Lua 内写 Stream**：把扣库存、记录已购、写消息放在同一个 Lua 脚本里，减少“预扣成功但消息没写”的窗口。
2. **消费者重试**：落库失败不要直接丢消息，使用 pending list、重试队列或死信队列。
3. **数据库唯一约束**：兜住重复消费和重复下单。
4. **库存补偿**：确认订单最终失败时，回补 Redis 库存并移除已购记录，或记录补偿流水由后台统一处理。
5. **定时对账**：活动结束后比对 Redis 预扣数、订单成功数、库存流水和 MySQL 库存。
6. **状态机**：订单使用 `INIT/SUCCESS/FAIL/CANCEL` 等状态，避免简单地把 Redis 成功当作最终成功。

补偿要非常谨慎。如果用户已经被记录为已购，但订单落库失败，需要决定是释放资格允许重试，还是让用户查询到失败后重新下单。不同业务策略不同，但必须可追踪、可重放。

## 8. 高并发下的性能优化

### 8.1 减少 Redis 热点

单个活动库存 key 是典型热点 key。可选方案：

1. 网关限流，减少无效流量进入 Redis。
2. 本地缓存活动状态、活动是否开始、是否结束。
3. 对明显无资格用户提前拦截。
4. 库存分桶，例如 `stock:{act100}:sku200:bucket01`。
5. 热点活动单独 Redis 实例或独立 Cluster。

库存分桶示例：

```text
stock:{act100}:sku200:0
stock:{act100}:sku200:1
stock:{act100}:sku200:2
```

请求按用户 ID hash 到某个 bucket，只扣该 bucket。这样能分散热点，但会带来库存碎片问题：有的 bucket 卖完，有的 bucket 还有库存。需要配合桶间重平衡、兜底重试或活动预估分配。

### 8.2 控制 Lua 脚本耗时

Lua 执行期间阻塞 Redis 主线程，所以脚本要短：

1. 不遍历大 Set。
2. 不在脚本里做复杂排序和分页。
3. 不做不可控循环。
4. 不把大对象写入 Stream。
5. 返回码简单，复杂逻辑交给业务服务。

### 8.3 限流和削峰

秒杀不能只靠 Redis 硬扛，前面要有多层削峰：

1. CDN 或网关限流。
2. 用户维度限流。
3. 活动维度令牌桶。
4. 风控识别脚本请求。
5. 排队页或异步受理。
6. MQ/Stream 消费端限速落库。

## 9. Redis Cluster 下的注意事项

Redis Cluster 中，Lua 多 key 原子性有明确边界：

1. 多个 key 必须在同一个 slot。
2. 使用 hash tag 可以强制同 slot。
3. 同 slot 会牺牲一部分分片扩展性。
4. 跨 slot 不要试图用一个 Lua 脚本实现分布式事务。

如果需要跨活动、跨商品、跨仓库扣减库存，应优先考虑：

1. 拆成多个独立原子操作。
2. 使用业务状态机、Saga 和补偿。
3. 对强一致库存使用数据库条件更新或专门库存服务。
4. 活动维度尽量避免一次请求同时扣多个 Redis 分片资源。

## 10. Redis 故障时怎么办

如果 Redis 承担库存和幂等主状态，故障时通常应当 fail closed：

```text
Redis 正常 -> 走 Lua 预扣
Redis 超时/不可用 -> 返回稍后再试、排队或活动繁忙
```

不要在 Redis 故障时直接绕过 Redis 打 MySQL，否则秒杀流量会把数据库打垮，也可能绕开一人一单和预扣逻辑。

可以做的兜底：

1. Redis 主从、哨兵或 Cluster 高可用。
2. 客户端短超时、熔断和限流。
3. 活动状态本地缓存，用于快速拒绝已结束活动。
4. 对关键活动设置独立 Redis 资源池。
5. 活动结束后基于 DB 和消息日志对账修复。

## 11. 易错点

1. Redis 单条命令原子，不代表多条命令组合原子。
2. Lua 原子性只在单个 Redis 节点内成立，不是分布式事务。
3. Lua 不会自动回滚，脚本要先校验后写入。
4. Redis 预扣成功不等于订单最终成功，MySQL 必须有唯一约束和条件更新。
5. 一人一单不能只靠前端禁用按钮，也不能只靠本地锁。
6. `DECR` 后库存可能变负，必须先判断 `stock > 0`，再扣减。
7. 只用 Redis Set 记录已购，Redis 数据丢失或主从切换时可能失效，最终要有 DB 约束兜底。
8. 库存补偿不能随意 `INCR`，要绑定订单状态和补偿流水，避免重复补偿。
9. Redis Cluster 下多 key 脚本要设计 hash tag，否则会遇到跨 slot 问题。
10. 脚本过长会阻塞 Redis 主线程，秒杀链路里 Lua 只做必要判断和状态变更。

## 12. 面试回答模板

Redis + Lua 解决超卖和一人一单的核心是把“判断库存、判断用户是否已经下单、扣减库存、记录已购、写入下单消息”放到一个 Lua 脚本里执行。Redis 执行 Lua 脚本时，在单个 Redis 节点内不会被其他命令插入，所以可以保证这几步在 Redis 层原子完成。库存可以用 String 保存，已购用户用 Set 保存，成功后写入 Redis Stream 或 MQ，让消费者异步创建订单。

脚本逻辑一般是：先 `GET stock`，如果库存小于等于 0 返回库存不足；再 `SISMEMBER bought userId` 判断是否重复下单；校验通过后 `DECR stock`、`SADD bought userId`，最后 `XADD` 下单消息。这样高并发请求进来时，只有先执行成功的请求会扣到库存，后续请求会看到库存减少或用户已购，从而避免 Redis 层超卖和一人一单失效。

但我不会只依赖 Redis。Redis Lua 只能保证单节点原子性，不能替代数据库事务，也不能解决主从切换丢数据、消息重复消费、消费者落库失败等问题。所以 MySQL 订单表要加 `user_id + activity_id + sku_id` 唯一索引，库存扣减要带 `stock > 0` 条件，消费者要用 `order_id` 做幂等，失败要重试、死信、补偿和对账。Redis 故障时关键链路通常 fail closed，返回活动繁忙或稍后再试，而不是绕过 Redis 直接打数据库。
