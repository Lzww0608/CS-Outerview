# Q32.Redis事务

Redis事务是一种将多个命令请求打包，一次性、按顺序地执行所有命令的机制，主要包括以下几个命令：

1. `MULTI`：标记一个事务块的开始。
2. `EXEC`：执行所有事务块内的命令。
3. `DISCARD`：取消事务，放弃执行事务块内的所有命令。
4. `WATCH`：监视键，如果键的值在事务执行之前发生改变，事务队列中的命令就不会执行。

值得注意的是，Redis的事务与传统意义上的数据库事务略有不同。在传统数据库中，事务有所谓的ACID属性——原子性、一致性、隔离性、持久性。但在Redis中，只支持命令执行阶段的连续性，即事务队列中的命令会连续、不中断地执行，执行过程中不会被其他命令插入。但是，如果事务队列中的某个命令执行失败，Redis并不会回滚其他已经执行的命令。

## Redis 事务的执行语义

Redis 事务更准确地说是“命令排队 + 顺序执行 + 乐观锁”，不是传统关系型数据库里的完整事务。

执行流程：

```text
WATCH key1 key2
MULTI
命令入队
命令入队
EXEC
```

关键语义：

1. `MULTI` 之后的命令先进入队列，不立即执行。
2. `EXEC` 时 Redis 会按顺序执行队列中的命令，执行期间不会穿插其他客户端命令。
3. 如果被 `WATCH` 的 key 在 `EXEC` 前被其他客户端修改，`EXEC` 返回空结果，事务不执行。
4. 入队阶段出现语法错误，`EXEC` 会拒绝执行整个事务。
5. 执行阶段某条命令运行时错误，例如对字符串执行 `LPUSH`，其他命令不会回滚。

所以 Redis 事务适合保证一小段 Redis 命令的连续执行和基于 `WATCH` 的乐观并发控制，不适合承担跨系统强一致事务。

## MySQL 事务和 Redis 事务的区别

| 对比项 | MySQL 事务 | Redis 事务 |
| --- | --- | --- |
| 核心目标 | 保证数据库读写满足 ACID | 批量命令按顺序连续执行 |
| 原子性 | 支持提交和回滚 | 执行阶段命令失败不回滚已执行命令 |
| 隔离性 | 通过锁和 MVCC 支持多种隔离级别 | `EXEC` 执行期间不插入其他命令，但没有 MVCC 隔离级别 |
| 持久性 | 依赖 redo log、binlog、刷盘策略 | 依赖 RDB/AOF 配置，不等同于事务日志 |
| 并发控制 | 行锁、间隙锁、MVCC、死锁检测 | `WATCH` 乐观锁，key 被改则事务放弃 |
| 适用场景 | 订单、库存、账务等核心一致性 | 缓存状态更新、计数、轻量 CAS |

例如“扣库存 + 创建订单 + 扣余额”这类核心链路，最终一致性落点应在 MySQL 或专门的交易系统里。Redis 可以用于资格预校验、限流、库存预扣和幂等标记，但要配合数据库唯一约束、消息队列、补偿任务和对账。

## 易错点

1. Redis 事务不是“要么全部成功，要么全部不执行”。只有入队阶段错误会让整个事务不执行，执行阶段错误不会自动回滚。
2. `WATCH` 只能监视 key 是否被修改，不能像 MySQL 一样提供复杂谓词锁或 MVCC 快照。
3. Redis 单线程执行命令不等于业务事务安全，脚本或事务里仍要避免慢命令和大 key。
4. Cluster 下多 key 事务仍受 slot 限制，跨 slot 强一致不能靠 Redis 事务解决。
5. 如果需要多步读-改-写原子逻辑，Lua 脚本通常比 `MULTI/EXEC` 更直接，但 Lua 也没有自动回滚。

## 面试回答模板

Redis 事务通过 `MULTI/EXEC/DISCARD/WATCH` 实现。`MULTI` 后命令入队，`EXEC` 时按顺序连续执行，中间不会插入其他客户端命令；`WATCH` 提供乐观锁，如果 key 在执行前被改，事务放弃。但 Redis 事务不提供 MySQL 那样的完整 ACID，执行阶段某条命令失败不会回滚已经执行的命令，也没有 MVCC 和多隔离级别。核心订单、库存、账务一致性应交给数据库或交易系统，Redis 更适合缓存状态、限流、资格校验和轻量 CAS。
