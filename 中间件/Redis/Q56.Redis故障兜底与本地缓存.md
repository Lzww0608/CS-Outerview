# Q56. Redis故障兜底与本地缓存

当系统十分依赖 Redis 时，要先区分 Redis 在系统中的角色：如果只是缓存，故障时可以降级或回源；如果 Redis 承担库存扣减、幂等校验、分布式锁、限流等关键状态，故障处理必须更保守，不能简单绕过。

## 1. Redis 挂了会发生什么

常见表现：

1. 请求 Redis 超时，应用线程池和连接池被拖住。
2. 缓存命中率下降，大量请求回源数据库，引发雪崩。
3. 库存、计数、资格校验等依赖 Redis 的逻辑无法判断。
4. 分布式锁失效，可能出现重复处理或并发冲突。
5. 如果客户端没有超时和熔断，故障会从 Redis 扩散到应用和数据库。

## 2. 基础高可用方案

Redis 自身高可用一般靠：

1. **主从复制**：从节点复制主节点数据，主故障后可以提升从节点。
2. **哨兵**：监控主从，自动选主并通知客户端。
3. **Cluster**：哈希槽分片，每个分片有主从，支持自动故障转移和横向扩展。
4. **多机房方案**：核心读缓存可以按机房就近部署，跨机房不强依赖同步。

但要注意：Redis 复制通常是异步的，故障切换可能丢少量最近写入的数据。对于库存扣减这类强约束，要有数据库最终校验或补偿机制。

## 3. 应用侧兜底

应用侧不能把所有希望寄托在 Redis 自动恢复上，还要做保护：

1. **超时**：Redis 调用必须有短超时，不能一直阻塞业务线程。
2. **熔断**：连续失败时快速失败或走降级逻辑，避免压垮线程池。
3. **限流**：Redis 异常时限制入口流量，保护数据库。
4. **降级**：非核心功能返回默认值、旧值、空结果或稍后重试。
5. **本地缓存**：对热点配置和只读查找表保留本地副本，Redis 短暂异常时读本地。
6. **异步补偿**：写失败或状态不确定时进入补偿任务，不在请求链路里无限重试。

抽奖系统里，如果 Redis 负责库存扣减，Redis 挂了通常应当 fail closed：暂停抽奖或返回稍后再试，而不是直接走数据库扣减，避免数据库被突发流量打垮和奖品超发。

## 4. 本地内存适合存什么

本地内存适合存读多写少、体积可控、短时间不一致可接受的数据：

1. 活动配置、奖品展示信息、规则开关。
2. 概率查找表、前缀和数组、alias table。
3. 热点商品信息、售罄标记、降级文案。
4. 黑白名单快照、布隆过滤器、路由表。
5. 短 TTL 的接口结果缓存。

不适合只放本地内存的数据：

1. 奖品库存的唯一真实扣减状态。
2. 用户参与次数、幂等记录这类需要跨实例共享的数据。
3. 分布式锁和全局限流计数。
4. 强一致账户余额、订单状态。

概率查找表通常可以放本地内存，因为它是只读或低频更新的数据。做法是 Redis 或数据库保存权重配置和版本号，应用启动或版本变化时构造本地前缀和/alias table。抽奖请求只在本地做概率命中，再通过 Redis/DB 做库存扣减和幂等校验。

## 5. 本地内存放不下怎么办

如果本地缓存或概率表太大，系统可能出现：

1. 内存占用过高，触发 GC 压力或 OOM。
2. 缓存频繁淘汰，命中率下降，请求回 Redis 或数据库。
3. 构造和更新缓存耗时增加，活动切换变慢。
4. 多实例重复保存同一份大表，整体资源浪费。
5. 延迟抖动，P99 上升。

解决方式：

1. **换结构**：离散展开表改成前缀和、ZSet、alias table，避免按权重展开。
2. **压缩存储**：用整数 ID、数组、二进制序列化，减少对象开销。
3. **按活动分片加载**：只加载当前活跃活动和热点活动。
4. **LRU/LFU/TTL 淘汰**：冷活动从本地移除，需要时从 Redis 加载。
5. **二级缓存**：本地缓存放热点，Redis 放全量。
6. **服务拆分或分片**：按活动 ID 路由到不同实例，降低每台机器持有的数据量。

## 6. 易错点

1. 本地缓存提高性能，但会带来多实例一致性问题。
2. 本地缓存更新要有版本号、TTL、MQ 通知或配置中心推送，不能长期不刷新。
3. Redis 故障时不要让所有请求直接打数据库，否则缓存故障会变成数据库故障。
4. 对关键写路径，降级要偏保守，宁可暂时拒绝也不能制造超发或重复处理。
5. 缓存对象数量多时，语言对象头、指针和 map 结构本身也会占大量内存，不只看业务字段大小。

## 7. 面试回答模板

如果系统强依赖 Redis，我会分两层处理。Redis 层用主从、哨兵或 Cluster 做高可用；应用层给所有 Redis 调用加超时、熔断、限流和降级，避免 Redis 故障扩散到应用线程池和数据库。对于活动配置、奖品信息、概率查找表这类读多写少的数据，可以放本地缓存，并用版本号、TTL 或 MQ 推送更新；但库存扣减、用户参与次数、幂等记录这类全局状态不能只放本地。Redis 故障时，非核心读可以返回本地旧值，关键写链路通常 fail closed，返回稍后再试，避免超发和数据不一致。
