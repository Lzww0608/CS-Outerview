# Q59.缓存逻辑过期与物理过期

缓存物理过期和逻辑过期都是控制缓存时效性的方式，但它们解决的问题不同。

面试里可以先说结论：**物理过期依赖 Redis TTL，到期后 key 会被 Redis 删除或在访问时判定不存在；逻辑过期是 key 物理上不删除，而是在 value 里保存业务过期时间，读请求发现逻辑过期后仍可先返回旧值，并触发后台异步刷新。物理过期更适合普通缓存和临时状态，逻辑过期更适合热点 key，主要解决缓存击穿、热点 key 集中过期和用户请求阻塞回源问题。**

## 1. 什么是物理过期

物理过期是指给 Redis key 设置真实 TTL，例如：

```bash
SET product:1001 "{...}" EX 300
```

到期后，Redis 会通过惰性删除和定期删除清理 key：

1. 惰性删除：访问 key 时发现已经过期，先删除再返回不存在。
2. 定期删除：Redis 后台周期性抽样检查带 TTL 的 key，删除已经过期的部分 key。

物理过期后，业务读缓存会得到 miss：

```text
读缓存
-> key 不存在
-> 查数据库
-> 重建缓存并设置 TTL
-> 返回新值
```

## 2. 什么是逻辑过期

逻辑过期是业务自己在缓存 value 中保存过期时间，而 Redis key 本身通常不设置 TTL，或者设置一个很长的兜底 TTL。

示例 value：

```json
{
  "data": {
    "id": 1001,
    "name": "phone",
    "price": 3999
  },
  "expireTime": 1714800000000
}
```

读取流程：

```text
读缓存
-> key 存在
-> 解析 value.expireTime
-> 未逻辑过期：直接返回 data
-> 已逻辑过期：尝试抢刷新锁
   -> 抢到锁：后台异步查数据库并重建缓存
   -> 没抢到锁：直接返回旧 data
```

逻辑过期的核心不是“让数据永不过期”，而是把“缓存失效导致所有请求回源”的模式，改成“请求先读旧值，后台单线程刷新”的模式。

## 3. 二者核心区别

| 对比项 | 物理过期 | 逻辑过期 |
| --- | --- | --- |
| 过期位置 | Redis 过期字典维护 TTL | 业务 value 里保存过期时间 |
| 到期后 key 是否存在 | 可能被删除，访问时视为不存在 | key 通常仍存在 |
| 读到过期数据时 | 缓存 miss，回源数据库 | 可先返回旧值，异步刷新 |
| 数据新鲜度 | 更容易读到新数据 | 可能短时间读到旧数据 |
| 可用性 | 热点 key 过期时可能击穿 | 热点 key 可持续命中 |
| 内存释放 | Redis 可自动释放 | 需要兜底 TTL 或清理机制 |
| 适用场景 | 普通缓存、会话、验证码、幂等 key | 热点商品、首页配置、活动详情、榜单快照 |

## 4. 物理过期解决什么问题

物理过期主要解决缓存生命周期和内存释放问题：

1. **自动淘汰过期数据**：过期后 Redis 可以删除 key，释放内存。
2. **降低脏数据长期存在风险**：即使缓存更新失败，TTL 到期后也能重新回源。
3. **适合短期状态**：验证码、登录 token、幂等 key、分布式锁都需要自然失效。
4. **实现简单**：业务代码只需要处理 cache miss 后重建缓存。

典型流程：

```java
String value = redis.get(key);
if (value != null) {
    return deserialize(value);
}

Object data = db.query(id);
redis.setex(key, 300, serialize(data));
return data;
```

物理过期的问题是：热点 key 到期瞬间，如果有大量并发请求同时 miss，就会一起打数据库，形成缓存击穿。

## 5. 逻辑过期解决什么问题

逻辑过期主要解决热点缓存的可用性和回源削峰问题：

1. **解决缓存击穿**：热点 key 不会物理消失，请求仍能命中旧值。
2. **减少用户请求阻塞**：刷新缓存由后台线程做，前台请求不等数据库。
3. **避免热点 key 集中过期**：即使逻辑过期，也不会让所有请求同时 miss。
4. **提高高并发读稳定性**：用短暂旧数据换取低延迟和系统稳定。

典型伪代码：

```java
CacheEntry entry = redis.get(key);
if (entry == null) {
    return null; // 热点 key 通常提前预热，正常不走这里
}

if (entry.getExpireTime() > System.currentTimeMillis()) {
    return entry.getData();
}

boolean locked = redis.set(lockKey, requestId, "NX", "PX", 30000);
if (locked) {
    executor.submit(() -> {
        try {
            Object fresh = db.query(id);
            CacheEntry newEntry = new CacheEntry(fresh, now() + logicalTtl);
            redis.set(key, serialize(newEntry));
        } finally {
            unlock(lockKey, requestId);
        }
    });
}

return entry.getData(); // 返回旧值
```

这里的锁通常是缓存重建锁，不是业务强一致锁。即使锁失败，也只是说明其他线程正在刷新，当前请求可以直接返回旧值。

## 6. 为什么逻辑过期适合热点 key

热点 key 的特点是：

1. QPS 高。
2. 数据读多写少。
3. 用户可以接受短时间旧值。
4. 一旦 miss，数据库压力会瞬间暴涨。

例如商品详情页、活动配置、首页推荐模块、排行榜快照等，短时间读到旧值通常比请求大量超时更可接受。

逻辑过期把热点 key 的回源从同步路径挪到异步路径：

```text
物理过期：
热点 key 到期 -> 所有请求 miss -> 抢锁或等待 -> 用户请求阻塞

逻辑过期：
热点 key 到期 -> 所有请求仍命中旧值 -> 只有一个后台任务刷新 -> 用户请求不阻塞
```

## 7. 逻辑过期的代价

逻辑过期不是万能方案，主要代价是读旧数据和内存管理。

### 7.1 可能读到旧值

逻辑过期后，在后台刷新完成之前，用户会继续读到旧值。

因此不适合：

1. 库存精确扣减。
2. 余额、支付状态。
3. 权限撤销后必须立即生效的接口。
4. 强一致订单状态。

适合：

1. 商品详情展示。
2. 活动页面配置。
3. 首页模块。
4. 热点文章、评论数近似展示。
5. 排行榜快照。

### 7.2 内存不会自然释放

如果 key 不设置物理 TTL，逻辑过期数据会长期占 Redis 内存。

常见处理：

1. 给逻辑过期 key 设置较长的物理兜底 TTL。
2. 活动结束后主动删除相关 key。
3. 后台定时扫描业务索引清理冷 key。
4. 配合 `maxmemory-policy` 进行缓存淘汰，但关键数据不要依赖随机淘汰。

示例：

```text
逻辑 TTL: 5 分钟
物理兜底 TTL: 1 天
```

这样正常读路径按 5 分钟刷新，异常情况下 1 天后 Redis 仍能释放内存。

### 7.3 后台刷新可能失败

如果数据库查询失败、线程池满、锁没有释放，缓存会长期停留在旧值。

需要：

1. 刷新失败记录日志和指标。
2. 刷新锁设置过期时间。
3. 后台线程池隔离，避免被业务线程池拖垮。
4. 连续刷新失败时降级或缩短返回旧值窗口。
5. 对核心热点 key 做定时预刷新。

## 8. 和互斥锁重建的区别

互斥锁重建通常用于物理过期后的 cache miss：

```text
key 不存在
-> 抢锁
   -> 抢到锁：查 DB 重建缓存
   -> 没抢到锁：等待、重试、返回空或降级
```

逻辑过期用于 key 仍存在但已经过业务有效期：

```text
key 存在但逻辑过期
-> 抢锁异步刷新
-> 无论是否抢到锁，都可以先返回旧值
```

核心差异：

1. 互斥锁重建强调“只有一个请求回源”。
2. 逻辑过期强调“请求不阻塞，并且热点 key 不消失”。
3. 两者可以组合使用：逻辑过期发现过期后，用互斥锁控制只有一个线程刷新。

## 9. 和缓存雪崩、击穿、穿透的关系

逻辑过期主要解决击穿和热点雪崩，不解决穿透。

| 问题 | 含义 | 逻辑过期是否适合 |
| --- | --- | --- |
| 缓存击穿 | 单个热点 key 过期，大量请求回源 | 适合 |
| 缓存雪崩 | 大量 key 同时过期或 Redis 故障 | 可缓解热点批量过期，但不能解决 Redis 故障 |
| 缓存穿透 | 请求不存在的数据，缓存和 DB 都没有 | 不适合，应用空值缓存、布隆过滤器、参数校验 |

如果是 Redis 整体故障，逻辑过期也读不到旧值，所以还需要本地缓存、限流、熔断和降级。

## 10. 如何选择

### 10.1 适合物理过期

1. 数据不是超热点。
2. 能接受 cache miss 后同步回源。
3. 数据要求相对新鲜。
4. key 数量大，需要 Redis 自动释放内存。
5. 短期状态必须自然失效，例如验证码、token、锁、幂等 key。

### 10.2 适合逻辑过期

1. 热点 key QPS 很高。
2. 数据读多写少。
3. 可以接受短时间旧值。
4. 回源成本高，不能让用户请求直接打 DB。
5. 需要高可用优先，而不是强实时优先。

### 10.3 常见组合

真实系统通常组合使用：

```text
普通 key:
  物理 TTL + 随机抖动 + cache miss 互斥回源

热点 key:
  逻辑过期 + 后台刷新 + 长物理兜底 TTL + 预热

不存在 key:
  空值缓存短 TTL + 布隆过滤器 + 参数校验

强一致 key:
  不只靠缓存，读主库或使用数据库事务/唯一约束/条件更新
```

## 11. 工程注意事项

1. 逻辑过期 value 要包含数据版本、逻辑过期时间和必要的元信息。
2. 后台刷新要有独立线程池，避免和主业务线程互相拖垮。
3. 刷新锁要设置 TTL，释放锁要校验 value，避免误删别人的锁。
4. 返回旧值要有最大容忍窗口，不能无限返回旧数据。
5. 数据变更时可以主动删除缓存或发布消息刷新热点 key。
6. 热点 key 要提前预热，逻辑过期不适合冷 key 首次加载。
7. 监控刷新失败次数、旧值返回比例、缓存命中率、DB 回源 QPS。
8. 大 value 逻辑过期会长期占内存，要控制对象大小和兜底 TTL。

## 12. 面试回答模板

缓存物理过期是 Redis key 设置 TTL，例如 `SET key value EX 300`，到期后 Redis 通过惰性删除和定期删除让 key 不存在。它的优点是简单、能自动释放内存、能作为缓存一致性的兜底；缺点是热点 key 到期瞬间会出现大量 cache miss，如果没有互斥回源，就可能造成缓存击穿。

缓存逻辑过期是 key 物理上不立刻删除，而是在 value 里保存一个业务过期时间。读请求发现没有逻辑过期就直接返回；发现逻辑过期后，尝试抢锁让一个后台线程刷新缓存，当前请求仍然可以先返回旧值。它主要解决热点 key 过期导致的击穿、集中回源和用户请求阻塞问题，适合商品详情、活动配置、首页模块、排行榜快照这类读多写少且能容忍短时间旧值的场景。

两者不是互斥的。普通缓存我会用物理 TTL 加随机抖动，miss 时用 singleflight 或互斥锁控制回源；超热点缓存我会用逻辑过期加后台刷新，同时设置一个较长的物理兜底 TTL 防止内存长期不释放。逻辑过期不能用于余额、库存精确扣减、权限撤销这类强一致场景，这些场景最终要靠数据库事务、唯一约束、条件更新或消息补偿保证正确性。
