# Q55.Lua脚本与资格校验

## 1. 为什么用 Lua 做资格校验

秒杀、抽奖、优惠券领取这类资格校验通常要同时判断：

1. 用户是否有资格。
2. 用户是否已经领取或下单。
3. 库存是否充足。
4. 校验成功后扣减库存并记录占用。
5. 必要时写入 Stream/List，交给异步消费者落库。

如果这些动作拆成多条 Redis 命令，客户端在命令之间可能被其他请求插入，出现超卖、重复领取或资格绕过。Lua 脚本可以把多步命令放到 Redis 服务端一次执行。Redis 执行脚本期间不会穿插执行其他命令，因此可以保证这段逻辑的原子性。

## 2. 典型数据结构

可以按业务规模选择不同结构：

1. **资格集合**：`SADD qual:{activityId} userId`，适合资格名单不太大、需要直接判断成员关系的场景。
2. **资格 Bitmap**：`SETBIT qual:{activityId} offset 1`，适合用户 ID 可映射为连续 offset、名单很大的场景。
3. **已购集合**：`SADD bought:{activityId} userId`，用于一人一单或防重复领取。
4. **库存 key**：`GET stock:{activityId}` / `DECR stock:{activityId}`。
5. **订单消息**：`XADD order_stream:{activityId}`，异步消费者从 Redis Stream 读取并写 MySQL。

Redis Cluster 下脚本访问的多个 key 必须落在同一个 hash slot。常见做法是使用 hash tag：

```text
stock:{act100}
qual:{act100}
bought:{act100}
order_stream:{act100}
```

## 2.1 Cluster 模式下一致性边界

Redis Lua 脚本的原子性只在**单个 Redis 节点**内成立。Cluster 模式下，key 被分散到 16384 个 slot，不同 slot 可能落在不同主节点。一个 Lua 脚本如果访问多个 key，Redis Cluster 要求这些 key 必须在同一个 slot，否则会报错或无法执行跨节点原子操作。

这会带来几个边界：

1. **同 slot 多 key**：脚本在一个节点内执行，具备单节点原子性。
2. **跨 slot 多 key**：不能用一个 Lua 脚本原子完成，不能假装是分布式事务。
3. **主从复制**：脚本执行结果复制到从节点通常仍是异步的，主节点故障时可能存在最近写入丢失窗口。
4. **槽迁移**：迁移期间客户端可能遇到 `MOVED/ASK`，需要使用支持 Cluster 的客户端并正确重试。

常见解决方式：

1. **hash tag 强制同槽**：把同一活动、同一订单或同一库存操作涉及的 key 设计成 `{actId}`，例如 `stock:{act100}`、`bought:{act100}`。
2. **拆小原子边界**：把跨活动、跨商品的操作拆成多个独立脚本，业务层用 Saga、补偿和对账处理最终一致。
3. **单库存服务**：对强一致库存使用独立库存服务或数据库条件更新，不把跨 slot 原子性寄托给 Redis。
4. **预分桶同槽或有意分散**：如果多个 bucket 要在一个脚本里聚合扣减，需要同槽；如果目标是分散热点，则每次只操作一个 bucket，避免跨 slot 脚本。
5. **幂等和补偿**：脚本成功但 MQ/DB 失败时，用订单号、用户活动唯一键和补偿任务修复。

hash tag 也不能滥用。如果所有热点 key 都使用同一个 `{act100}`，它们会被强行放到同一个 slot，可能把 Cluster 的分片能力抵消掉。设计时要在“同槽原子性”和“分片扩展性”之间取舍。

## 3. Lua 脚本流程

下面以集合存资格、集合防重复、Stream 投递订单为例：

```lua
-- KEYS[1] = stock key
-- KEYS[2] = qualified users set
-- KEYS[3] = bought users set
-- KEYS[4] = order stream
-- ARGV[1] = userId
-- ARGV[2] = orderId

if redis.call('SISMEMBER', KEYS[2], ARGV[1]) == 0 then
    return 1 -- no qualification
end

if redis.call('SISMEMBER', KEYS[3], ARGV[1]) == 1 then
    return 2 -- duplicated request
end

local stock = tonumber(redis.call('GET', KEYS[1]) or '0')
if stock <= 0 then
    return 3 -- sold out
end

redis.call('DECR', KEYS[1])
redis.call('SADD', KEYS[3], ARGV[1])
redis.call(
    'XADD',
    KEYS[4],
    '*',
    'userId',
    ARGV[1],
    'orderId',
    ARGV[2]
)

return 0 -- success
```

返回码由业务服务翻译成具体错误：

```text
0: 成功
1: 无资格
2: 重复请求
3: 库存不足
```

## 4. 核心原理

Redis Lua 的关键点：

1. 脚本在 Redis 主线程中执行，执行期间不会被其他客户端命令打断。
2. 客户端可以先 `SCRIPT LOAD`，后续用 `EVALSHA` 调用，减少脚本传输成本。
3. 脚本里的多条 Redis 命令共享同一段执行上下文，适合做读、判断、写的原子组合。
4. 脚本返回结果后，业务服务再决定是否继续异步落库、返回下单成功或失败。

## 4.1 Lua 脚本实现原理

Redis 内部嵌入了 Lua 解释器。客户端通过 `EVAL` 发送脚本文本，或者先 `SCRIPT LOAD` 把脚本加载进 Redis，拿到 SHA1 后再用 `EVALSHA` 执行。

调用形式：

```text
EVAL script numkeys key [key ...] arg [arg ...]
EVALSHA sha1 numkeys key [key ...] arg [arg ...]
```

脚本内部通过 `KEYS` 和 `ARGV` 取参数：

1. `KEYS` 放脚本访问的 Redis key，Cluster 会根据它检查 slot。
2. `ARGV` 放普通参数，例如用户 ID、订单 ID、时间戳。
3. `redis.call()` 执行 Redis 命令，命令错误会让脚本报错。
4. `redis.pcall()` 执行 Redis 命令，错误会以 Lua 值返回，脚本可以自己处理。

执行模型：

```text
客户端发送 EVAL/EVALSHA
-> Redis 解析参数
-> Lua 解释器在 Redis 主线程中执行脚本
-> 脚本通过 redis.call 访问 Redis 数据结构
-> 执行完成后一次性返回结果
-> Redis 继续处理后续客户端命令
```

Lua 原子性的来源不是日志回滚，而是 Redis 主事件循环串行执行。脚本运行期间，其他客户端命令不能插入同一个 Redis 实例的执行流。因此脚本适合短小的读改写逻辑，但长脚本会阻塞整个实例。

脚本缓存和容错：

1. `SCRIPT LOAD` 后 Redis 用脚本文本计算 SHA1，后续 `EVALSHA` 只传 SHA1，减少网络传输。
2. Redis 重启、主从切换或 `SCRIPT FLUSH` 后，客户端可能收到 `NOSCRIPT`，需要回退到 `EVAL` 或重新 `SCRIPT LOAD`。
3. 不要在脚本里依赖随机、时间、外部状态等不可控行为；需要时间时优先由业务传入或使用 Redis 命令并理解复制语义。
4. 脚本执行太久时会影响所有请求。没有写操作的长脚本可以尝试 `SCRIPT KILL`，已经执行写操作的脚本通常不能安全杀掉。

复制和持久化层面，Redis 会把脚本或脚本产生的写命令同步给 AOF 和副本。面试里不需要展开版本细节，但要说明：Lua 保证的是单主节点执行原子性，不保证跨主节点事务，也不能替代数据库事务和对账。

## 5. 易错点

1. **Lua 原子不等于事务回滚**：脚本执行中如果前面已经写入，后面因为运行时错误失败，Redis 不会自动回滚已经执行的写操作。因此脚本要尽量先完成校验，再执行写入，并避免运行时错误。
2. **脚本不能太慢**：Lua 执行期间会阻塞 Redis 主线程。不要在脚本里遍历大 key、做复杂计算或执行不可控循环。
3. **不要只依赖 Redis 成功就认为订单最终成功**：Redis 扣减库存和写入 Stream 后，MySQL 落库仍可能失败。真实系统要有消费者重试、幂等订单号、失败补偿或定时对账。
4. **重复请求要幂等**：`orderId` 可以由业务服务提前生成，落库时使用唯一索引保证同一用户同一活动只有一单。
5. **资格数据要可重建**：资格名单、库存、已购集合最好能从 DB 或日志重放恢复，避免 Redis 故障后状态不可恢复。
6. **Cluster 跨 slot 不具备脚本原子性**：多 key 脚本要么用 hash tag 放到同一 slot，要么拆分业务原子边界。

## 6. 真实场景应用

秒杀系统中常见链路是：

1. 活动开始前预热资格名单和库存到 Redis。
2. 请求进入后先做网关限流和风控。
3. 业务服务调用 Lua 脚本做资格校验、幂等判断和预扣库存。
4. 成功请求写入 Redis Stream 或 MQ。
5. 异步消费者创建订单并写 MySQL。
6. 如果消费者落库失败，通过重试、死信队列、库存补偿和对账任务修复。

这样可以把高并发读写挡在 Redis 层，把 MySQL 从峰值流量中解耦出来，同时用 Lua 保证 Redis 内部状态不会被并发请求打穿。

## 7. 面试回答模板

Redis Lua 能保证脚本在单个 Redis 节点内原子执行，适合秒杀资格校验、库存预扣、幂等记录和写 Stream 这些多步操作。但在 Redis Cluster 下，多 key 脚本要求所有 key 落在同一个 hash slot，否则不能跨节点原子执行。解决方式是对同一活动使用 hash tag，例如 `stock:{act100}`、`bought:{act100}`；如果为了分散热点把库存拆到不同 slot，就不能一个脚本跨 bucket 聚合扣减，而要把每次扣减限制在单 bucket，再由业务层做补偿和对账。还要注意 Lua 不回滚、不能执行太久、主从复制仍可能有故障丢失窗口，最终正确性要靠数据库唯一约束、幂等和补偿兜底。
