# Q11.缓存穿透

缓存穿透是指在使用缓存系统时，恶意请求或者不存在的数据频繁地被发送到缓存中，导致缓存无法命中，最终请求会直接落到后端数据库，造成数据库压力过大。

缓存穿透可能出现的原因包括：

1. 恶意攻击：攻击者有意发送不存在的数据请求，试图使缓存失效，以达到影响系统性能或者触发系统错误的目的。
2. 随机查询：大量并发的随机查询请求，其中大部分请求的数据都不存在于缓存中。
3. 存在但很少访问的数据：一些数据很少被访问，经常被请求但却不存在于缓存中，导致缓存穿透。

为了解决缓存穿透问题，可以采取以下措施：

1. 布隆过滤器（Bloom Filter）：布隆过滤器是一种高效的数据结构，用于判断某个元素是否存在于集合中。在请求到来时，先使用布隆过滤器进行判断，如果被拦截则不再继续访问缓存和数据库，减轻了数据库的压力。
2. 缓存空对象（Cache Null Object）：当某个请求查询的数据不存在时，将空对象或者null放入缓存，以防止相同的请求频繁查询数据库。在一定时间内，如果有相同的请求再次到来，则直接从缓存中获取到空对象，避免了对数据库的重复查询。
3. 数据预热（Cache Pre-warming）：在系统启动时，将一些常用或重要的数据预先加载到缓存中，提前热身缓存，避免了对这部分数据的缓存穿透问题。
4. 异步加载（Asynchronous Loading）：对于即将过期的缓存数据，可以在后台异步地进行数据加载和缓存的更新，避免了数据过期期间的缓存穿透。
5. 限流和防护机制：通过对请求进行限流、IP白名单校验和请求验证等手段，防止恶意攻击和异常流量对缓存系统造成压力。

## 缓存空值应该缓存空对象还是 null

工程上更推荐缓存一个**可序列化的空对象 / 哨兵值**，而不是直接缓存语言层面的 `null`。

原因：

1. 很多缓存客户端把 `null` 当成“没有命中”，无法区分“查过数据库但确实不存在”和“缓存里没有这个 key”。
2. `null` 在不同序列化框架里的表现不一致，容易和反序列化失败、字段缺失混在一起。
3. 空对象可以携带语义，例如 `{"exists":false}`、`"__NULL__"`、空列表 `[]` 或业务状态码，调用方可以稳定判断。

常见写法：

```text
GET product:detail:10086
  miss -> query MySQL
  not found -> SET product:detail:10086 "__NULL__" EX 60
  found -> SET product:detail:10086 "{...}" EX 3600
```

注意事项：

1. 空值 TTL 要短，一般几十秒到几分钟，避免数据后来创建后长时间读到空。
2. 空值缓存要和布隆过滤器、参数校验配合，不能让恶意随机 key 填满 Redis。
3. 空对象要和正常对象有明确区分，避免业务把空对象当真实数据展示。
4. 数据写入成功后，要删除对应空值 key，否则会出现“数据库有值但缓存仍为空”的不一致。

## Redis Cluster 下缓存穿透还存在吗

存在。Redis Cluster 解决的是容量、分片和高可用问题，不会改变“请求的 key 在缓存和数据库中都不存在”这个事实。

集群化之后可能出现新的问题：

1. **穿透流量被分散到多个 Redis 节点**，但最终仍会落到数据库，数据库压力没有本质消失。
2. **随机 key 会污染多个分片**，如果缓存大量空对象，内存压力会扩散到整个集群。
3. **布隆过滤器要考虑部署位置**：可以本地缓存一份，也可以按业务分片放 Redis；更新时要处理版本和误判率。
4. **热点不存在 key 仍会击穿数据库**：同一个不存在 key 被大量请求时，要用短 TTL 空对象、singleflight 或互斥加载。
5. **跨 slot 操作受限**：如果穿透防护依赖多个 key，例如统计、黑名单和空值 key，Redis Cluster 下要设计好 hash tag 或拆分逻辑。

所以，Redis 集群只能提高缓存层承载能力，不能替代参数校验、布隆过滤器、空值缓存、限流和风控。

面试回答模板：缓存空值的本质是把“数据库不存在”这个结果也缓存起来，避免同一个不存在 key 反复打数据库。我会缓存短 TTL 的空对象或哨兵值，而不是直接缓存语言 null；同时配合布隆过滤器和参数校验，防止大量随机空 key 把缓存打满。
