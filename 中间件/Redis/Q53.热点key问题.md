# Q53. 热点 key 问题

热点 key 是指某个 Redis key 在短时间内被大量访问，导致单个 Redis 分片、单个 CPU 核或网络连接成为瓶颈。它和大 key 不一样：大 key 是 value 太大，热点 key 是访问频率太高。

## 常见场景

1. 秒杀商品库存、售罄标记。
2. 热门微博、热榜、明星资料页。
3. 首页配置、活动配置、全站开关。
4. 某个缓存 key 过期后大量请求同时回源。

## 解决思路

1. **本地缓存**：热点配置、热门商品信息可以放到应用本地缓存，降低 Redis QPS。
2. **多副本读**：同一个热点 key 复制成多个副本 key，读请求随机访问不同副本，例如 `hot:sku:1:0..N`。
3. **拆 key**：库存、计数器等可拆成多个 bucket，写入时分散到不同 key，读取时聚合。
4. **互斥重建**：热点 key 过期时只允许一个线程回源，其他线程等待或读旧值。
5. **逻辑过期**：value 中存过期时间，物理 key 不立刻删除；过期后异步刷新，避免瞬时击穿。
6. **限流和熔断**：对热点访问做用户/IP/接口限流，Redis 异常时快速失败或返回降级数据。
7. **提前预热**：活动开始前预加载热点数据，并设置随机过期时间，避免同一时刻集中过期。

## 注意事项

1. 多副本 key 会带来一致性问题，适合读多写少或能容忍短暂不一致的场景。
2. 库存类热点 key 拆分后要处理总库存准确性，通常需要预分配 bucket 库存，并在 DB 层做最终校验。
3. 本地缓存要有失效机制，可以通过 MQ、配置中心、版本号或短 TTL 刷新。
4. 不要把所有热点都交给 Redis Cluster 自动分片，因为单个 key 仍然只能落到一个 slot。
