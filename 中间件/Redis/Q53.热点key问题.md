# Q53. 热点 key 问题

热点 key 是指某个 Redis key 在短时间内被大量访问，导致单个 Redis 分片、单个 CPU 核或网络连接成为瓶颈。它和大 key 不一样：大 key 是 value 太大，热点 key 是访问频率太高。

## 常见场景

1. 秒杀商品库存、售罄标记。
2. 热门微博、热榜、明星资料页。
3. 首页配置、活动配置、全站开关。
4. 某个缓存 key 过期后大量请求同时回源。

## 解决思路

1. **本地缓存**：热点配置、热门商品信息可以放到应用本地缓存，降低 Redis QPS。
2. **多副本读**：同一个热点 key 复制成多个副本 key，读请求随机访问不同副本，例如 `hot:sku:1:0..N`。
3. **拆 key**：库存、计数器等可拆成多个 bucket，写入时分散到不同 key，读取时聚合。
4. **互斥重建**：热点 key 过期时只允许一个线程回源，其他线程等待或读旧值。
5. **逻辑过期**：value 中存过期时间，物理 key 不立刻删除；过期后异步刷新，避免瞬时击穿。
6. **限流和熔断**：对热点访问做用户/IP/接口限流，Redis 异常时快速失败或返回降级数据。
7. **提前预热**：活动开始前预加载热点数据，并设置随机过期时间，避免同一时刻集中过期。

## 高并发下如何避免请求全部打到 Redis

如果 Redis 已经是高频链路，不应让所有请求无脑透传到 Redis。常见分层保护：

```text
浏览器/客户端缓存
-> CDN/网关短缓存
-> 应用本地缓存 Caffeine/Guava/进程内 LRU
-> Redis Cluster
-> DB / 后端服务
```

具体手段：

1. **本地短缓存**：热点只读数据、配置、售罄标记可以在应用内缓存几十毫秒到几秒，直接削掉大量重复读。
2. **请求合并**：同一个 key 同一时刻只有一个请求访问 Redis 或回源，其他请求等待结果，类似 singleflight。
3. **逻辑过期**：物理 key 不删除，过期后由后台线程刷新；前台请求先返回旧值，避免大量请求同时打 Redis。
4. **热点 key 副本**：读多写少 key 拆成多个副本，随机读，更新时异步刷新全部副本。
5. **分片计数**：计数器、库存预扣这类热点写按 bucket 分散，最终聚合或由 DB 兜底。
6. **入口限流**：在网关、应用和 Redis 调用前分别限流，Redis 超时后快速失败，保护线程池。
7. **预热与随机 TTL**：活动开始前加载热点数据，TTL 加抖动，避免集中失效。

要注意，本地缓存和副本 key 会牺牲强一致性，只适合读多写少或能短暂接受旧值的场景。库存、余额、资格校验这类关键状态不能只靠本地缓存绕过 Redis，必须有数据库约束、幂等和对账兜底。

## 注意事项

1. 多副本 key 会带来一致性问题，适合读多写少或能容忍短暂不一致的场景。
2. 库存类热点 key 拆分后要处理总库存准确性，通常需要预分配 bucket 库存，并在 DB 层做最终校验。
3. 本地缓存要有失效机制，可以通过 MQ、配置中心、版本号或短 TTL 刷新。
4. 不要把所有热点都交给 Redis Cluster 自动分片，因为单个 key 仍然只能落到一个 slot。

## 面试回答模板

高并发下不能让所有请求都直接打 Redis。我会先做多级缓存：客户端/CDN/网关短缓存、应用本地缓存、Redis、数据库；对热点 key 用本地短 TTL、请求合并、逻辑过期和后台刷新削峰。读多写少热点可以做副本 key 随机读，计数或库存热点可以拆 bucket 分散写。Redis 异常时要有限流、熔断和降级，避免 Redis 故障扩散到应用线程池和数据库。关键状态不能只用本地缓存绕过 Redis，最终还要靠 DB 条件更新、幂等和对账保证正确性。
