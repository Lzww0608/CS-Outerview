# Q24.持久化策略

Redis 持久化主要解决“进程退出或机器故障后，内存数据如何恢复”的问题，常见方式是 RDB、AOF 和混合持久化。

## 1. RDB、AOF 和混合持久化

| 方式 | 核心机制 | 优点 | 缺点 |
| --- | --- | --- | --- |
| RDB | 定期生成内存快照 | 文件紧凑、恢复快、适合备份和灾备 | 两次快照之间的数据可能丢失，fork 和写时复制会带来开销 |
| AOF | 追加记录写命令 | 数据丢失窗口更小，可读性强 | 文件更大，恢复通常比 RDB 慢，需要 AOF rewrite |
| 混合持久化 | AOF 文件前半段是 RDB 快照，后半段是增量命令 | 兼顾恢复速度和数据完整性 | 文件格式更复杂，仍需要关注 rewrite 开销 |

AOF 并不天然等于强一致。`appendfsync always` 每次写都刷盘，持久性最强但性能最低；`appendfsync everysec` 是常见折中，通常最多丢失约 1 秒数据；`appendfsync no` 依赖操作系统刷盘，性能高但风险更大。

## 2. RDB 适合什么场景

1. 数据主要作为缓存，允许丢失一小段时间的数据。
2. 需要定期做全量备份、跨机房迁移或离线分析。
3. 希望故障后快速加载数据。
4. 写入压力较大，不希望每条写命令都追加日志。

注意 RDB 生成快照时通常需要 `fork` 子进程，写多时会产生明显的写时复制内存开销。

## 3. AOF 适合什么场景

1. 数据价值较高，希望尽量缩小故障丢失窗口。
2. 需要通过命令日志做更细粒度恢复。
3. 能接受 AOF 文件增长和 rewrite 带来的额外成本。

生产中常见配置是 `appendfsync everysec`，在持久性和吞吐之间折中。如果业务要求极高持久性，还需要结合主从复制、磁盘可靠性、`WAIT`、备份和业务侧补偿，而不是只依赖 AOF。

## 4. 生产取舍

1. 缓存型 Redis：可以只开 RDB，甚至不开持久化，依赖上游数据库重建。
2. 会话、计数、队列类数据：更倾向开启 AOF 或混合持久化。
3. 备份场景：常在从节点生成 RDB，减少主节点 fork 和 I/O 压力。
4. 高写入场景：要关注 AOF rewrite、磁盘带宽、`no-appendfsync-on-rewrite` 和延迟尖刺。

## 5. 面试回答模板

Redis 持久化主要有 RDB 和 AOF。RDB 是周期性快照，文件小、恢复快，适合备份，但可能丢失最近一次快照后的数据。AOF 是追加写命令，数据丢失窗口更小，但文件更大、恢复更慢，需要重写。Redis 4.0 后支持混合持久化，用 RDB 做基底，再追加 AOF 增量，兼顾恢复速度和数据完整性。生产中要根据数据价值、写入压力、恢复速度和可接受丢失窗口来选择。
