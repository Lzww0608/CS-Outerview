# Q54. Redis 多机房多主同步

Redis 官方 Cluster 更偏向单地域集群内分片和高可用，并不天然提供强一致的跨机房多主复制。多机房多主 Redis 设计的核心难点是：**网络延迟高、链路可能分区、多个机房同时写同一份数据会产生冲突**。

## 常见架构

1. **单写多读**：只允许一个主机房写，其他机房只读或作为灾备。实现简单，一致性最好，但异地写延迟高。
2. **就近写 + 异步复制**：每个机房都能写本地 Redis，再异步同步到其他机房。延迟低，但冲突处理复杂。
3. **按 key/业务分片归属机房**：某个 key 只允许归属机房写，其他机房路由过去写，本地可读副本。
4. **多活代理层**：客户端写入本地代理，代理根据路由、冲突策略、复制日志决定写本地还是转发。
5. **CRDT Redis**：使用支持 CRDT 的产品或模块，让部分数据类型天然可合并，例如计数器、集合。

## 同步规则怎么定

跨机房多主必须明确冲突规则：

1. **Last Write Wins (LWW)**：用时间戳或逻辑时钟，保留“最后一次写”。简单但可能丢更新，且依赖时钟。
2. **版本向量 / Lamport clock**：记录因果关系，能识别并发冲突，但元数据更重。
3. **业务幂等流水**：写入携带 `request_id`、`version`、`op_id`，重复同步不重复执行。
4. **按数据类型合并**：
   - 计数器可用增量日志累加。
   - set 可做并集合并。
   - string 覆盖写最容易冲突。
5. **业务侧仲裁**：余额、库存、优惠券这类强一致数据不建议多主并发写 Redis，应回源到单写 DB 或强一致服务。

## 写最近机房还是所有机房都能写

答案取决于一致性要求：

1. **强一致核心数据**：通常不做 Redis 多机房多主写。请求路由到主写机房，其他机房读本地副本或回源主机房。
2. **读多写少配置/缓存**：可以主机房写，异步分发到其他机房。
3. **用户维度数据**：可以按用户归属机房写，用户请求尽量路由到归属机房。
4. **可合并数据**：例如计数、点赞集合，可以允许就近写，再用 CRDT 或操作日志合并。

如果所有机房都能写同一个 key，就必须接受最终一致，并明确冲突解决和回滚补偿。

## 真实场景建议

1. **缓存场景**：优先把 Redis 当缓存，跨机房不追求强同步；每个机房本地缓存，失效时回源。
2. **会话场景**：尽量做用户路由粘性；跨机房切换时允许短暂重新登录或从中心存储恢复。
3. **排行榜/计数**：可用本地累计 + 异步汇总，允许秒级延迟。
4. **库存/余额**：不要依赖 Redis 多主解决一致性，使用数据库事务、库存中心或强一致 KV。

## 易错点

1. “多主”不等于“强一致”。跨机房网络分区时，CAP 下必须在可用性和一致性之间取舍。
2. Redis 主从复制是异步的，跨机房复制延迟更明显，故障切换可能丢最近写入。
3. LWW 依赖时钟同步，时钟回拨或不同机房时钟漂移会导致旧值覆盖新值。
4. 缓存数据可以最终一致，资金、库存、订单状态不能简单用最终一致覆盖写。
