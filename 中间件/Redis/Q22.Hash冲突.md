# Q22.Hash冲突

Redis 通过**链式哈希**解决冲突：**也就是同一个 桶里面的元素使用链表保存**。但是当链表过长就会导致查找性能变差可能，所以 Redis 为了追求快，使用了两个全局哈希表。用于 rehash 操作，增加现有的哈希桶数量，减少哈希冲突。

开始默认使用 「hash 表 1 」保存键值对数据，「hash 表 2」 此刻没有分配空间。当数据越来越多触发 rehash 操作，则执行以下操作：

1. 给 「hash 表 2 」分配更大的空间；
2. 将 「hash 表 1 」的数据重新映射拷贝到 「hash 表 2」 中；
3. 释放 「hash 表 1」 的空间。

**值得注意的是，将 hash 表 1 的数据重新映射到 hash 表 2 的过程中并不是一次性的，这样会造成 Redis 阻塞，无法提供服务。**

而是采用了**渐进式 rehash**，每次处理客户端请求的时候，先从「 hash 表 1」 中第一个索引开始，将这个位置的 所有数据拷贝到 「hash 表 2」 中，就这样将 rehash 分散到多次请求过程中，避免耗时阻塞。

## Redis 字典的结构

Redis 的全局 key 空间、Hash 对象底层 hashtable、过期字典等都会用到字典结构。可以抽象为：

```text
dict
  -> ht[0]
      -> table[bucket]
          -> dictEntry -> dictEntry -> ...
  -> ht[1]  // rehash 时使用
  -> rehashidx
```

每个 `dictEntry` 保存 key、value 和 `next` 指针。多个 key 哈希到同一个 bucket 时，通过 `next` 串成链表，这就是链地址法。

## 渐进式 rehash 的触发和过程

Redis 会根据负载因子决定是否扩容或收缩。rehash 时不会一次性搬完整张表，而是：

1. 为 `ht[1]` 分配新表。
2. 设置 `rehashidx`，表示正在迁移。
3. 每次执行增删改查时，顺便迁移一部分 bucket。
4. 后台定时任务空闲时也会帮忙迁移。
5. `ht[0]` 迁移完后释放旧表，把 `ht[1]` 变成新的 `ht[0]`。

rehash 过程中查找、删除、更新可能需要同时看两张表；新增元素通常直接写到 `ht[1]`，避免继续扩大旧表。

## 还有哪些哈希冲突解决方式

除了 Redis 使用的链地址法，常见方式还有：

| 方式 | 原理 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 链地址法 | 每个桶挂链表或其他结构 | 删除简单，装载因子可较高 | 指针跳转多，极端冲突会退化 |
| 开放寻址 | 冲突后在数组中继续探测空位 | 内存连续，缓存友好 | 删除复杂，需要 tombstone，装载因子不能太高 |
| 线性探测 | 依次探测下一个位置 | 实现简单，局部性好 | 容易主聚集 |
| 二次探测 | 按平方步长探测 | 缓解主聚集 | 仍可能探测失败，需要容量设计 |
| 双重哈希 | 第二个 hash 决定探测步长 | 分布更均匀 | 计算成本和实现复杂度更高 |
| 再哈希扩容 | 增加桶数量重新分布 | 降低平均冲突 | 扩容有搬迁成本 |

Redis 选择链地址法，是因为删除和渐进式 rehash 更直接，也方便在不长时间阻塞主线程的情况下逐步搬迁。

## 易错点

1. 哈希冲突不能完全避免，只能通过好哈希函数、扩容和控制负载因子降低概率。
2. Redis 的渐进式 rehash 是为了减少阻塞，不是为了让 rehash 完全没有成本。
3. rehash 期间内存会短暂上升，因为新旧两张表同时存在。
4. Redis Hash 类型的小对象可能使用 listpack 等紧凑编码，不一定一开始就是 hashtable。
5. 链地址法平均 `O(1)`，但极端碰撞仍可能退化，因此外部输入 key 还要考虑碰撞攻击风险。

## 面试回答模板

Redis 字典用链地址法解决哈希冲突，同一个 bucket 下的多个 entry 通过 next 指针串成链表。为了降低冲突，Redis 会在负载因子较高时扩容，但 rehash 不是一次性完成，而是用 `ht[0]` 和 `ht[1]` 两张表做渐进式迁移，每次命令执行顺便搬一部分 bucket，避免主线程长时间阻塞。其他冲突解决方式还有开放寻址、线性探测、二次探测、双重哈希和扩容 rehash。
