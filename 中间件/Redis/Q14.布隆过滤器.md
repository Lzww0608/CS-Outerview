# Q14.布隆过滤器

布隆过滤器（Bloom Filter）是一种数据结构，用于快速判断一个元素是否属于一个集合，它的原理、优点和缺陷如下：

**原理**：

1. 哈希函数：布隆过滤器使用多个哈希函数（通常是非加密哈希函数），将输入元素映射成多个不同的位数组索引。
2. 位数组：布隆过滤器内部维护一个位数组，所有位的初始值都为0。
3. 添加元素：当要将一个元素添加到布隆过滤器中时，对该元素应用多个哈希函数，然后将相应位数组索引位置的位设置为1。
4. 查询元素：当要查询一个元素是否存在于布隆过滤器中时，同样对该元素应用多个哈希函数，检查相应位数组索引位置的位是否都为1。如果所有位都为1，则可能存在；如果有任何一位为0，则一定不存在。

**优点**：

1. 节省内存：相比于使用散列表或集合等数据结构，布隆过滤器占用的内存较少，因为它只需要维护位数组。
2. 快速查询：布隆过滤器的查询操作非常快速，通常只需要几个哈希函数的计算和位的检查。
3. 可用于大规模数据：适用于处理大规模数据集，尤其是在内存有限的情况下，可以快速过滤掉大部分不可能存在的元素，减轻后续查询的压力。

**缺陷**：

1. 误判率：布隆过滤器可能会产生误判，即判断一个元素存在时，实际上它可能不存在。这是因为多个元素可能映射到相同的位数组索引，导致冲突。
2. 不支持删除：由于布隆过滤器的位数组只能设置为1，不能删除元素。如果需要删除元素，需要重新构建布隆过滤器。
3. 容量不可扩展：一旦位数组的大小确定，就不能动态扩展，因此需要在设计时估计好位数组的大小以应对数据规模的增长。

总之，布隆过滤器是一种高效的数据结构，适用于需要快速过滤数据的场景，但要注意其误判率和不支持删除的特点。在实际应用中，通常需要根据具体需求权衡其优点和缺陷。

## 面试追问：它到底是什么样的数据结构？

布隆过滤器的核心结构可以概括为：

```text
一个长度为 m 的 bit array + k 个哈希函数
```

它里面存储的不是原始元素，也不是元素的哈希值列表，而是一组被置为 `1` 的 bit 位。也就是说，布隆过滤器只能回答“这个元素可能存在 / 一定不存在”，不能从过滤器里反查出有哪些元素。

插入元素时，用 k 个哈希函数把元素映射到 k 个下标，并把这些下标对应的 bit 置为 1。查询元素时，再计算同样的 k 个下标：

- 只要有任意一个 bit 是 0，说明元素一定不存在。
- 如果所有 bit 都是 1，说明元素可能存在。

它会误判，是因为不同元素可能把同一批 bit 置为 1，导致一个从未插入过的元素查询时也命中所有 bit。但它不会漏判已经插入的元素，前提是底层 bit array 没有被错误清理或重建。

## 误判怎么处理

普通布隆过滤器的误判是结构性特征，不能对某一次误判做“删除修正”。工程上通常把它当成第一层过滤器，而不是最终判定来源。

常见处理方式：

1. **二次校验真实数据源**：布隆过滤器返回“可能存在”后，再查 Redis、MySQL、对象存储或业务索引；只有真实数据源命中才返回存在。
2. **短 TTL 空值缓存**：误判导致查库为空时，可以缓存 `__NULL__` 这类哨兵值，避免同一个误判 key 反复打到数据库。
3. **控制误判率**：根据预计元素量和可接受误判率设计 `m`、`k`，并监控实际插入量；超过容量后要扩容或重建。
4. **分层过滤**：先用参数校验和 key 空间白名单拦截明显非法请求，再用布隆过滤器过滤业务 ID，最后才访问缓存和数据库。
5. **选择可扩展实现**：RedisBloom 这类实现可以支持自动扩容；需要删除时考虑 Counting Bloom Filter 或 Cuckoo Filter。

易错点是把布隆过滤器当成强一致索引。它适合防缓存穿透、黑名单预判、爬虫 URL 去重这类“宁可少量误判，也不能漏判已加入元素”的场景；如果业务要求精确存在性判断，最终仍要查权威数据源。

## 误判率和参数选择

布隆过滤器需要提前估算元素数量 `n` 和可接受误判率 `p`，然后选择 bit array 长度 `m` 和哈希函数个数 `k`。

常用近似公式：

```text
m = -n * ln(p) / (ln2)^2
k = (m / n) * ln2
p ≈ (1 - e^(-kn/m))^k
```

面试里可以按下面步骤快速估算：

1. 先问清预计元素数量 `n` 和可接受误判率 `p`。
2. 用 `m/n ≈ -ln(p)/(ln2)^2` 估算每个元素需要多少 bit。
3. 用 `k ≈ (m/n) * 0.693` 估算哈希函数个数。
4. 如果已经给了内存，就先算 `m/n`，再用 `p ≈ 0.6185^(m/n)` 反推误判率。

常见量级：

| 目标误判率 | 约每元素 bit 数 | 最优哈希函数个数 |
| --- | --- | --- |
| 1% | 9.6 bit | 7 |
| 0.1% | 14.4 bit | 10 |
| 0.01% | 19.2 bit | 13 |

直观理解：

1. `m` 越大，bit 越稀疏，误判率越低，但越耗内存。
2. `k` 太少，bit 利用不充分；`k` 太多，会让 bit 很快被置 1，反而增加误判率。
3. 插入元素超过设计容量后，误判率会明显上升。

### 1 亿数据占用 170MB 怎么算

如果面试官追问“1 亿参数占用 170MB 是怎么算的”，可以反推它大约对应千分之一量级的误判率。

假设：

```text
n = 100,000,000
memory = 170 MiB = 170 * 1024 * 1024 bytes
m = memory * 8 = 1,426,063,360 bits
```

那么每个元素平均占用 bit 数是：

```text
m / n ≈ 14.26 bits / element
```

最优哈希函数个数：

```text
k = (m / n) * ln2 ≈ 14.26 * 0.693 ≈ 9.88
```

工程上取 `k = 10` 个哈希函数。对应误判率可以用近似公式估算：

```text
p ≈ (0.6185)^(m/n)
  ≈ (0.6185)^14.26
  ≈ 0.001
```

也就是说，1 亿元素、170MiB 左右内存、10 个哈希函数，大致可以做到 `0.1%` 误判率。如果用十进制 MB 计算，170MB 是 `1.36e9` bit，约 `13.6 bits/element`，误判率会略高一些，但仍在千分之一量级。

回答时要说明单位：数据库、缓存和操作系统里经常混用 MB 与 MiB，精确计算时最好明确 `1MiB = 1024 * 1024 bytes`。

## 删除问题

普通布隆过滤器不能直接删除元素，因为一个 bit 可能由多个元素共同置为 1。如果删除某个元素时把对应 bit 清 0，可能会破坏其他元素的判断结果。

如果业务需要删除，可以考虑：

1. **Counting Bloom Filter**：把 bit 替换成计数器，插入时加一，删除时减一，代价是内存变大。
2. **定期重建**：从真实数据源重新构建布隆过滤器。
3. **Cuckoo Filter**：换成支持删除的近似集合结构。

## 和 Redis 的关系

Redis 原生 Bitmap 可以作为布隆过滤器的 bit array；工程中也可以使用 RedisBloom 模块，它封装了布隆过滤器的创建、插入、查询、扩容等逻辑。
