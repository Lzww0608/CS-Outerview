# Q57.Redis 读写风险与一致性边界

Redis 读写是否有风险，要先区分 Redis 在系统中的角色。Redis 可以做缓存、计数器、限流器、分布式锁、排行榜、会话和轻量消息流；不同角色的风险完全不同。

## 1. Redis 做缓存时的读写风险

缓存场景的权威数据通常在 MySQL 或其他数据库中，Redis 只是加速读路径。主要风险是缓存和数据库短时间不一致。

常见风险：

1. **脏缓存**：数据库已更新，但 Redis 仍保存旧值。
2. **旧值回填**：写请求删除缓存后，读请求从从库读到旧值并写回缓存。
3. **缓存击穿**：热点 key 过期，大量请求同时回源数据库。
4. **缓存雪崩**：大量 key 同时过期或 Redis 故障，流量直接打到数据库。
5. **缓存穿透**：恶意或不存在的 key 绕过缓存，持续访问数据库。

常见处理：

1. 写路径优先“更新数据库后删除缓存”，删除失败用 MQ 或 binlog 订阅补偿。
2. 写后读主库，或等待复制位点，避免从库延迟导致旧值回填。
3. 热点 key 用互斥回源、singleflight、逻辑过期和后台刷新。
4. TTL 加随机抖动，避免同一时间大量过期。
5. 不存在的数据用布隆过滤器、空值缓存和入口限流防穿透。

## 2. Redis 做主状态时的写入风险

如果 Redis 承担库存、余额、参与次数、分布式锁、全局限流这类关键状态，风险更高，因为 Redis 变成了业务正确性链路的一部分。

需要关注：

1. **持久化丢数据窗口**：RDB 可能丢最近快照后的数据，AOF `everysec` 可能丢最近 1 秒左右数据。
2. **主从复制延迟**：主库写成功但还没复制，从库或新主可能没有这次写。
3. **故障切换脑裂**：旧主和新主同时接收写入会产生冲突。
4. **非原子多步操作**：先 `GET` 再 `SET` 在并发下会丢更新。
5. **跨 key 一致性**：多个 key 同时更新时，如果没有 Lua、事务或状态机，很容易出现部分成功。

处理思路：

1. 单 key 原子修改优先用 `INCR`、`HINCRBY`、`SET NX PX` 等原子命令。
2. 多步校验和修改用 Lua 脚本合并成一个原子操作。
3. 关键写入可以结合 AOF、主从、`WAIT`、幂等表和数据库最终落库。
4. Redis 故障时关键链路通常 fail closed，返回稍后再试，而不是绕过 Redis 继续超发。
5. 最终正确性要有数据库唯一约束、条件更新、流水表或对账补偿兜底。

## 3. 读风险和一致性模型

Redis 单实例命令执行是串行的，但这不等于整个系统强一致。

1. 读主库通常能读到该实例已执行的最新写。
2. 读从库可能读到旧数据，因为复制是异步或半同步链路。
3. Cluster 下不同 key 分布在不同主节点，跨 key 操作没有天然全局事务。
4. 客户端重试可能导致重复写，必须设计幂等键。
5. Pipeline 只减少网络往返，不保证一组命令作为事务原子执行。

## 4. 真实场景

秒杀库存可以先用 Redis Lua 做资格校验和预扣，拦截大部分流量，再用 MQ 异步落库。但数据库仍要使用条件更新和订单唯一约束兜底，防止 Redis 故障、重复消费或补偿异常导致超卖。

排行榜用 Redis ZSet 很合适，因为它本身就是高频读写的派生视图。即使 Redis 短暂故障，也可以从行为日志或数据库重建。它的风险更多是延迟和可用性，而不是核心资产一致性。

验证码、限流、登录失败次数这类短 TTL 状态可以接受一定丢失，但要评估安全边界。Redis 故障时，登录、支付、优惠券这类风险接口通常应收紧策略；普通内容读接口可以降级或短暂放行。

## 5. 面试回答模板

Redis 读写当然有风险，关键看它是缓存还是主状态。做缓存时主要风险是数据库和缓存不一致、旧值回填、击穿、雪崩和穿透，通常用更新数据库后删缓存、binlog/MQ 补偿、写后读主库、互斥回源和 TTL 抖动处理。做关键状态时，还要考虑持久化丢数据、主从切换、复制延迟、非原子多步操作和跨 key 一致性，必须用原子命令或 Lua，并让数据库约束、幂等和对账作为最终兜底。Redis 很快，但不能把“单线程命令原子”误认为“分布式业务强一致”。
