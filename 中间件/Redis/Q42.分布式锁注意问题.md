# Q42.分布式锁注意问题

Redis实现分布式锁时需要注意以下几个关键的问题：

1. **原子性**: 在设置锁时，我们需要确保一旦一个请求获取了锁，其他的请求要么处于等待状态要么就去做其他的事情。Redis提供的命令

   ```
   SET key value NX PX milliseconds
   ```

   可以保证这个过程的原子性，代表只有当key不存在时，我们才设置value. PX参数指这把锁会在指定的时间后(毫秒)自动删除。

2. **锁超时**: 很重要的一点是，我们需要防止一个客户端在获取一个锁后因为某些原因(比如程序崩溃)导致无法释放这把锁。为了防止其他的客户端永远等待下去，我们需要为这把锁设一个超时时间。

3. **锁续期**: 对于一些预计会长时间持有锁的操作，我们可能需要实现一个自动续期的机制，防止在任务执行过程中锁过期被其他客户端获取。

4. **谨慎处理解锁过程**: 解锁的时候也需要注意，确保只有获取到锁的客户端才能解锁，不能由别的客户端解锁。可以存储一个随机的value，每个客户端解锁比对value是否为自己，相同才执行解锁。

5. **加锁失败的处理**: 在锁已经被其他客户端持有的情况下，加锁请求会失败，此时需要实现重试机制或者直接失败。

举个简单的例子，比如在秒杀系统中，为了保证商品的一致性，我们需要在用户下单的时候对商品库存进行加锁，防止多个请求同时修改库存导致超卖现象. 在这种场景下，我们就需要通过Redis来实现分布式锁，而且需要处理以上所述的各种情况。

## SET NX 实现分布式锁的风险

`SET key value NX PX ttl` 只能解决“加锁命令本身原子”和“客户端崩溃后锁能过期”两个问题，不代表这把锁在所有分布式场景下都绝对可靠。

常见风险：

1. **锁过期但业务未完成**：客户端 A 执行业务太慢，锁过期后客户端 B 获得锁，A 后续继续写共享资源，形成并发写。
2. **误删别人的锁**：A 的锁过期后 B 加锁成功，如果 A 直接 `DEL key`，会删掉 B 的锁。
3. **Redis 主从切换丢锁**：主节点加锁成功但还没复制到从节点，主节点宕机，从节点升主后锁丢失，其他客户端可再次加锁。
4. **网络分区和 GC 停顿**：客户端以为自己仍持锁，但实际上锁已过期或集群视图变化。
5. **锁粒度过大**：所有库存或订单共用一把锁，会把系统串行化，性能很差。

正确释放锁要用 value 校验加 Lua 保证原子性：

```lua
if redis.call("GET", KEYS[1]) == ARGV[1] then
    return redis.call("DEL", KEYS[1])
else
    return 0
end
```

长任务可以做续期，但续期也要满足“仍然是自己的锁”这个条件。常见做法是 watchdog 周期性检查 value 并延长 TTL；如果续期失败，业务应尽快停止或进入补偿路径。

## 分布式锁不能替代最终一致性兜底

Redis 锁适合保护短临界区，例如防止缓存击穿时多个请求同时回源、避免同一用户重复提交、控制某个低频任务只被一个实例执行。

强一致场景不能只靠 Redis 锁：

1. 库存扣减最终要用数据库条件更新、唯一约束、幂等表或订单状态机兜底。
2. 对外部系统写入要有业务幂等键，锁失败或锁过期都不能导致重复扣款、重复发货。
3. 如果锁保护的是数据库资源，数据库层仍要有事务和约束。
4. 如果必须防止旧持锁者继续写，可以引入 fencing token：每次加锁返回递增版本，下游只接受更大的 token。

面试回答可以总结：Redis 分布式锁的标准写法是 `SET key randomValue NX PX ttl` 加 Lua 校验删除；风险在于锁过期、误删、主从切换、网络分区和长任务续期。真实业务里分布式锁只是降低并发冲突，最终正确性仍要靠数据库约束、幂等和补偿兜底。
