# Q38.缓存预热

缓存预热是指系统上线后，提前将相关的缓存数据加载到缓存系统。避免在用户请求的时候，先查询数据库，然后再将数据缓存的问题，用户直接查询事先被预热的缓存数据。

如果不进行预热，那么Redis初始状态数据为空，系统上线初期，对于高并发的流量，都会访问到数据库中， 对数据库造成流量的压力。

缓存预热解决方案：

- 数据量不大的时候，工程启动的时候进行加载缓存动作；
- 数据量大的时候，设置一个定时任务脚本，进行缓存的刷新；
- 数据量太大的时候，优先保证热点数据进行提前加载到缓存。

## 抽奖系统里的预热

抽奖、秒杀、优惠券这类活动系统里，预热通常不只是把一条缓存写进 Redis，而是把活动执行所需的读路径数据提前构造成高效结构。

常见预热内容：

1. **活动配置**：活动时间、参与条件、每日次数、风控开关，适合用 `String` 或 `Hash`。
2. **奖品配置**：奖品 ID、库存、概率、展示信息，适合用 `Hash` 保存字段，或用 `String` 保存压缩后的 JSON/Protobuf。
3. **库存计数**：奖品库存适合用 `String` 数字，扣减时用 Lua 保证判断和扣减原子性。
4. **概率查找结构**：可以预先构造前缀和表、ZSet 分数区间、离散化数组或 alias table。
5. **黑白名单/资格集合**：适合用 `Set`、`Bitmap` 或 Bloom Filter。

预热链路一般是：

```text
后台配置活动
-> 审核发布
-> 生成活动版本号
-> 预热任务读取 DB
-> 构造 Redis key 和本地缓存快照
-> 校验数量、概率总和、库存
-> 活动开始时切换到新版本
```

## 离散化是什么

离散化是把小数概率或权重转换成整数区间，方便用随机整数做查找。

例如三个奖品概率为：

```text
A: 0.1
B: 0.3
C: 0.6
```

可以乘以 10000 转成整数权重：

```text
A: [1, 1000]
B: [1001, 4000]
C: [4001, 10000]
```

抽奖时生成 `1..10000` 的随机数，再查它落在哪个区间。

Redis 中常见存储方式：

1. **ZSet 前缀和**：score 存区间右端点，member 存奖品 ID；随机数 `r` 后查询第一个 `score >= r` 的奖品。
2. **String 序列化数组**：把前缀和数组或 alias table 序列化存入 Redis，应用启动后加载到本地内存。
3. **List 离散表**：按权重展开成数组，随机下标直接 `LINDEX`，实现简单但内存可能很大。
4. **Hash 配置 + 本地构造**：Redis 只存奖品权重配置，应用本地构造前缀和或 alias table。

## 易错点

1. 预热要带版本号，避免活动配置更新时读到新旧混合数据。
2. 预热后要校验概率总和、库存非负、奖品状态和 key TTL。
3. 大规模活动不要在请求路径临时构造概率表，否则首批请求会被构造成本拖慢。
4. 离散化要统一精度，避免浮点误差导致概率总和不是预期值。
5. 预热失败时要阻止活动切流，不能让请求落到半成品缓存。

## 面试回答模板

缓存预热就是在流量到来前，把热点数据提前加载到 Redis 或应用本地缓存，避免活动刚开始时大量请求同时回源数据库。抽奖系统里我会预热活动配置、奖品配置、库存计数、资格集合和概率查找结构。概率通常会离散化，把小数概率乘以固定倍率转成整数区间，再用前缀和、ZSet 或 alias table 查找。工程上会用版本号隔离新旧配置，预热完成后校验概率、库存和 key，再切换线上活动版本。
