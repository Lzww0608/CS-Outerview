# Q60.缓存穿透中缓存空值的问题与优化

缓存空值是解决缓存穿透的常见方案：当数据库确认某个对象不存在时，不是什么都不缓存，而是把“不存在”这个结果也写入 Redis，后续相同请求直接命中空对象，避免反复打数据库。

面试里可以先说结论：**缓存空值能解决同一个不存在 key 反复查库的问题，但它会带来内存污染、短时间数据不一致、恶意随机 key 打满 Redis、空值语义混淆、过期风暴等问题。优化方式是短 TTL、随机抖动、参数校验、布隆过滤器、空值 key 数量限制、写入后删除空值、回源合并和监控治理。**

## 1. 缓存空值解决什么问题

缓存穿透的典型链路是：

```text
请求 product:detail:999999
-> Redis miss
-> MySQL 查询不存在
-> 返回空
-> 下次相同请求又 Redis miss
-> 再次查 MySQL
```

如果某个不存在的 key 被高频访问，数据库会持续承压。缓存空值后变成：

```text
请求 product:detail:999999
-> Redis miss
-> MySQL 查询不存在
-> SET product:detail:999999 "__NULL__" EX 60
-> 下次相同请求命中 "__NULL__"
-> 直接返回不存在
```

它的核心收益是：**把“数据库不存在”也变成可缓存结果，拦截重复无效查询。**

## 2. 为什么不能直接缓存语言 null

工程里通常不要直接缓存语言层面的 `null`，更推荐缓存可序列化的空对象或哨兵值。

常见写法：

```text
"__NULL__"
{"exists":false}
[]
{"code":"NOT_FOUND"}
```

原因：

1. 很多缓存客户端把 `null` 当成 cache miss，无法区分“缓存里没有 key”和“查过 DB 确认不存在”。
2. 不同序列化框架对 `null` 的处理不同，容易出现反序列化歧义。
3. 空对象可以携带语义，例如不存在、无权限、已删除、未发布。
4. 显式哨兵值便于监控空值命中率和排查问题。

## 3. 缓存空值有什么问题

### 3.1 内存污染

如果攻击者构造大量随机不存在 ID：

```text
product:detail:random_1
product:detail:random_2
product:detail:random_3
...
```

系统每次都把空值写入 Redis，会导致大量无业务价值的 key 占用内存。

风险：

1. Redis 内存被空值 key 挤占。
2. 正常热点缓存被淘汰。
3. Redis Cluster 下空值污染扩散到多个分片。
4. 大量 key 过期时带来删除开销和 CPU 抖动。

### 3.2 短时间数据不一致

空值缓存期间，如果数据库后来创建了这条数据：

```text
T1: 查询商品 10086，不存在，缓存 "__NULL__" 60 秒
T2: 后台创建商品 10086
T3: 用户查询商品 10086，命中 "__NULL__"，仍然返回不存在
```

这就是“数据库已有数据，但缓存仍为空”的不一致。

空值 TTL 越长，这个不一致窗口越大。

### 3.3 业务语义混淆

“空”不一定只有一种含义：

1. 数据确实不存在。
2. 数据存在但无权限。
3. 数据已删除。
4. 数据未发布。
5. 数据源异常导致查询失败。

如果全部缓存成 `"__NULL__"`，调用方可能无法区分业务语义，甚至把临时异常当作永久不存在缓存起来。

尤其要注意：**数据库查询异常、超时、下游失败时，不应该缓存空值。** 否则会把故障结果固化到缓存里。

### 3.4 热点空值也会击穿

如果某个不存在 key 是热点，例如被爬虫或脚本持续访问：

```text
product:detail:not_exist_hot
```

空值 TTL 到期瞬间，大量请求仍可能同时回源数据库。缓存空值只能减少重复查询，不能自动解决热点空值过期时的并发重建。

### 3.5 删除和更新容易漏

当真实数据被创建或恢复时，需要删除对应空值 key。否则会持续返回空。

常见漏删场景：

1. 商品从异步审核流程创建，创建服务没有删除空值缓存。
2. 用户注册成功，但用户资料查询空值缓存没有删除。
3. 文档从草稿发布，发布事件没有通知缓存层。
4. 多租户或多语言 key 维度不一致，删除了一个 key，另一个空值 key 还在。

### 3.6 空值缓存可能被当成攻击放大器

缓存空值的初衷是保护数据库，但如果没有限制，它会让攻击者用随机 key 把 Redis 打满。

所以缓存空值不是防穿透的第一道防线。第一道防线应该是：

1. 参数格式校验。
2. key 空间白名单。
3. 业务 ID 范围校验。
4. 网关限流和风控。
5. 布隆过滤器或本地只读集合预判。

## 4. 如何优化缓存空值

### 4.1 空值 TTL 要短

空值 TTL 通常短于正常缓存。

示例：

```text
正常商品详情 TTL: 30 分钟
空值缓存 TTL: 30 秒 ~ 5 分钟
```

原因：

1. 降低数据创建后仍返回空的时间。
2. 降低 Redis 被空值 key 长期污染的风险。
3. 让空值只挡住短时间重复请求，而不是长期占用缓存。

不要为了省一次 DB 查询，把空值 TTL 设置成几小时甚至一天。

### 4.2 TTL 加随机抖动

如果大量空值 key 同一时间写入，并设置相同 TTL，可能同一时间过期，形成回源峰值。

可以加抖动：

```text
empty_ttl = 60 + random(0, 30)
```

或者按业务风险区分：

```text
正常用户误查: 60s
高风险来源: 10s
热点不存在 key: 120s + jitter
```

### 4.3 写入真实数据后删除空值 key

只要某个对象从不存在变为存在，就要主动删除对应缓存 key。

示例：

```text
create product 10086
-> commit MySQL
-> DEL product:detail:10086
-> 后续读请求回源真实数据并重建缓存
```

如果使用 binlog 或 MQ 做缓存一致性，也要覆盖空值 key：

```text
MySQL insert/update
-> Canal/binlog/MQ
-> 删除 product:detail:{id}
```

注意 key 设计必须统一。不要真实值用 `product:detail:10086`，空值用 `product:null:10086`，否则删除和查询路径容易不一致。

### 4.4 参数校验前置

不要把任何用户输入都直接拼成 Redis key。

先校验：

1. ID 是否是数字或合法 UUID。
2. ID 长度是否合理。
3. ID 是否在业务号段范围内。
4. 租户、用户、资源类型是否匹配。
5. 接口是否允许查询该类资源。

示例：

```java
if (!isValidProductId(productId)) {
    return NotFound;
}

String key = "product:detail:" + productId;
```

非法参数直接拒绝或返回空，不进入 Redis 和数据库，更不写空值缓存。

### 4.5 配合布隆过滤器

布隆过滤器适合放在 Redis 和数据库之前，用于判断 ID 是否可能存在。

流程：

```text
参数校验
-> 布隆过滤器判断一定不存在
   -> 直接返回空，不查 Redis，不查 DB
-> 布隆过滤器判断可能存在
   -> 查 Redis
   -> miss 后查 DB
   -> DB 不存在时写短 TTL 空值
```

布隆过滤器有误判：判断“可能存在”但 DB 实际不存在。这时空值缓存可以兜住误判后的重复查询。

所以两者关系是：

1. 布隆过滤器拦截大部分随机不存在 key。
2. 空值缓存处理布隆误判、热点不存在 key 和真实业务误查。
3. 参数校验和限流防止攻击者制造无限 key 空间。

### 4.6 限制空值 key 数量

可以按来源限制空值写入：

1. 单 IP 每分钟最多制造 N 个空值 key。
2. 单账号每分钟最多制造 N 个空值 key。
3. 单设备、租户、接口维度统计空值率。
4. 空值率过高时只返回空，不再写 Redis。
5. 高风险来源触发验证码、限流或封禁。

伪代码：

```text
if emptyKeyCreateRate(source) > threshold:
    return NotFoundWithoutCaching
else:
    SET key "__NULL__" EX short_ttl
```

这样可以避免 Redis 被随机空值 key 填满。

### 4.7 对热点空值做回源合并

同一个不存在 key 过期后，如果并发很高，仍然要控制回源。

可以使用：

1. 进程内 `singleflight`。
2. Redis 分布式锁。
3. 短时间本地缓存空值。
4. 逻辑过期式空值刷新。

流程：

```text
空值 key 过期
-> 多个请求 miss
-> 只有一个请求查 DB
-> 其他请求等待、快速返回空或读本地短缓存
```

### 4.8 区分“不存在”和“查询失败”

只在权威数据源明确返回“不存在”时缓存空值。

不要缓存：

1. 数据库超时。
2. 数据库连接失败。
3. 下游 RPC 失败。
4. 权限服务异常。
5. SQL 执行报错。

正确处理：

```text
DB 返回 not found -> 写空值缓存
DB 超时/异常 -> 不写空值，返回错误或降级
```

否则一次短暂故障可能导致用户在 TTL 内持续看到错误空结果。

## 5. 空值缓存的推荐流程

```text
请求进入
-> 参数校验和权限预判
-> 风控/限流
-> 布隆过滤器或本地合法 ID 集合
-> 查 Redis
   -> 命中真实值：返回数据
   -> 命中空值：返回不存在
   -> miss：singleflight/互斥回源
-> 查数据库
   -> 存在：写真实缓存，返回数据
   -> 不存在：写短 TTL 空值，返回不存在
   -> 异常：不写空值，返回错误或降级
```

## 6. Key 和 value 设计

推荐同一个业务对象使用同一个 key：

```text
product:detail:{productId}
user:profile:{tenantId}:{userId}
article:public:{articleId}
```

不要设计成：

```text
product:detail:{productId}
product:null:{productId}
```

因为读路径和删除路径容易遗漏。

value 可以设计为：

```json
{
  "exists": false,
  "reason": "NOT_FOUND",
  "cachedAt": 1714800000000
}
```

如果追求简单，也可以是：

```text
__NULL__
```

但必须保证调用方能明确区分空值和真实对象。

## 7. 监控指标

空值缓存必须监控，否则很难发现攻击和内存污染。

建议关注：

1. 空值缓存写入 QPS。
2. 空值缓存命中率。
3. 空值 key 数量和内存占比。
4. 按 IP、账号、设备、租户统计的空值制造数量。
5. Redis keyspace 增长速度。
6. 数据库 not found 查询 QPS。
7. 布隆过滤器拦截率和误判后的空值写入量。
8. 数据创建后仍命中空值的次数。

异常现象：

1. 空值写入 QPS 突然升高：可能是攻击或上游参数错误。
2. 空值 key 数量持续增长：TTL 过长或 key 空间未限制。
3. 某个来源空值率异常高：需要风控、限流或封禁。
4. 数据创建后仍返回空：缓存删除链路有问题。

## 8. 适用边界

适合缓存空值：

1. 查询对象确实可能不存在。
2. 同一个不存在 key 会被重复查询。
3. 短时间返回空可以接受。
4. 数据创建不是强实时可见。
5. 已经有参数校验和限流。

不适合只靠缓存空值：

1. 用户输入 key 空间无限且没有校验。
2. 数据创建后必须立即可见。
3. 不存在结果涉及复杂权限语义。
4. Redis 内存资源紧张。
5. 攻击流量远大于正常流量。

## 9. 易错点

1. 空值缓存不是万能防穿透，随机 key 攻击会把 Redis 打满。
2. 空值 TTL 不能太长，否则新数据创建后仍返回空。
3. 不能把 DB 异常、超时当成不存在写入空值缓存。
4. 空值 key 和真实 key 要统一，否则数据创建后容易删漏。
5. 空值 value 要可识别，不要和正常空数组、空字符串混淆。
6. 布隆过滤器有误判，仍需要 DB 二次确认和空值缓存兜底。
7. 热点空值过期时也可能击穿，需要 singleflight 或互斥回源。
8. 要监控空值比例，否则可能直到 Redis 内存异常才发现问题。

## 10. 面试回答模板

缓存空值的作用是把“数据库确认不存在”这个结果也缓存起来，比如查询商品不存在后写入 `product:detail:10086 = "__NULL__"`，设置一个短 TTL。这样同一个不存在 key 再次请求时可以直接命中空值，避免反复查数据库，适合解决缓存穿透里的重复无效查询。

它的问题主要有几个：第一，攻击者可以构造大量随机不存在 key，导致 Redis 里堆积大量空值，形成内存污染；第二，空值 TTL 内如果数据库创建了真实数据，读请求仍会命中空值，出现短时间不一致；第三，不能区分“不存在、无权限、下游异常”等语义时容易误缓存；第四，热点空值过期时仍可能发生并发回源。

优化上我会把空值 TTL 设置得比正常值短，并加随机抖动；数据创建或更新成功后主动删除同一个缓存 key；只在数据库明确返回不存在时缓存空值，DB 超时或异常不缓存；在入口做参数校验、key 空间白名单、限流和风控；用布隆过滤器拦截大部分随机不存在 ID；限制单 IP、账号、设备能制造的空值 key 数量；对热点空值用 singleflight 或互斥锁合并回源。也就是说，空值缓存只是一层兜底，不能替代参数校验、布隆过滤器、限流和监控。
