# Q18.内存淘汰策略

Redis提供了一些策略，以便在届满最大内存限制时进行内存淘汰：

1. **noeviction**：当内存不足以容纳更多数据时，新的写入操作会报错。这是默认策略。
2. **allkeys-lru**：在内存不足时让位于新值内容的，是最近最少使用的键（LRU：Least Recently Used）。
3. **volatile-lru**：在设置了过期时间的键中，淘汰最近最少使用的键，新的写入操作会报错。
4. **allkeys-random**：在内存不足时随机删除某个键的值，为新值让出空间。
5. **volatile-random**：在设置了过期时间的键中，随机淘汰一些键。
6. **volatile-ttl**：在设置了过期时间的键中，有更早过期时间的键优先被淘汰。
7. **allkeys-lfu**：从所有键中淘汰访问频率最低的键。
8. **volatile-lfu**：从设置了过期时间的键中淘汰访问频率最低的键。

选择哪种策略取决于你的特定应用。如果你的程序可以接受偶发的性能下降，allkeys-lru可能是一个好选择。如果你知道一些键是可以安全删除的，你可以为它们设置过期时间，然后使用volatile-lru。如果数据的重要性不等，你可以为重要的数据设置过期时间，然后使用volatile-ttl策略。

## allkeys 和 volatile 的区别

1. `allkeys-*`：从所有 key 中选择淘汰对象，适合 Redis 纯缓存场景。
2. `volatile-*`：只从设置了过期时间的 key 中选择淘汰对象，适合 Redis 同时保存缓存和不可淘汰数据的场景。
3. 如果使用 `volatile-*`，但没有足够多设置 TTL 的 key，Redis 可能无法淘汰出空间，写入仍会失败。

## LRU 和 LFU 的实现注意

Redis 的 LRU 和 LFU 都不是严格全局最优算法，而是采样近似：

1. LRU 根据对象的最近访问时间近似淘汰最久未访问的 key。
2. LFU 根据访问频率计数近似淘汰低频 key，并带有时间衰减，避免历史热点永久占用内存。
3. 采样数量越大，淘汰结果越接近真实 LRU/LFU，但 CPU 成本越高。

### Redis 的近似 LRU 怎么实现

严格 LRU 通常要维护“哈希表 + 双向链表”，每次访问都把节点移动到链表头。Redis 没有这样做，原因是 Redis key 数量可能非常大，如果每次访问都改全局链表，会带来额外内存、指针操作和锁/一致性成本。

Redis 的 LRU 是近似实现：

1. 每个 Redis 对象头里有一个 `lru` 字段，记录最近访问时间的逻辑时钟。
2. 命中或访问 key 时，更新对象的 `lru` 字段。
3. 达到 `maxmemory` 后，根据 `maxmemory-policy` 判断从所有 key 还是带 TTL 的 key 中淘汰。
4. Redis 随机采样若干个候选 key，默认采样数量由 `maxmemory-samples` 控制。
5. 在样本中选择 `lru` 最老的 key 淘汰，必要时维护一个小的 eviction pool，让选择结果更接近全局最老。

这种方式不是绝对精确，但复杂度和内存开销更可控。`maxmemory-samples` 越大，越接近真实 LRU，CPU 成本也越高。

和手撕 LRU 的区别：

1. 手撕 LRU 为了做到精确 `O(1)`，用哈希表定位节点，用双向链表维护全局访问顺序。
2. Redis 为了适配海量 key 和高吞吐，不维护全局链表，而是用对象时间戳 + 随机采样做近似淘汰。
3. 面试中如果问算法实现，回答哈希表 + 双向链表；如果问 Redis 实现，要强调近似 LRU。

## 选择建议

1. 纯缓存、希望保留最近访问数据：`allkeys-lru`。
2. 纯缓存、希望保留长期热点数据：`allkeys-lfu`。
3. 只允许淘汰带 TTL 的缓存数据：`volatile-lru` 或 `volatile-lfu`。
4. 希望快过期的 key 先被淘汰：`volatile-ttl`。
5. 不允许 Redis 自动淘汰核心数据：`noeviction`，由业务处理写入失败。

面试回答时可以补一句：Redis 内存淘汰由 `maxmemory` 和 `maxmemory-policy` 控制，过期删除策略和内存淘汰策略不是一回事；前者处理 TTL 到期，后者处理内存达到上限。
