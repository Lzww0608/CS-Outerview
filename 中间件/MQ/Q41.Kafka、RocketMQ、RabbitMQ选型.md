# Q41.Kafka、RocketMQ、RabbitMQ选型

选择消息队列时，不能只说“Kafka 吞吐高”。要结合业务目标：吞吐、延迟、顺序、事务消息、延迟消息、消费模型、运维成本和生态。

## 1. 三者定位

| MQ | 核心定位 | 更适合的场景 |
| --- | --- | --- |
| Kafka | 分布式日志和流处理平台 | 日志采集、埋点、实时数仓、事件流、高吞吐削峰 |
| RocketMQ | 面向业务消息的分布式 MQ | 订单、交易、事务消息、延迟消息、顺序消息 |
| RabbitMQ | AMQP 消息代理 | 任务分发、低延迟异步、复杂路由、传统企业集成 |

## 2. Kafka 的优势和不足

优势：

1. **吞吐高**：顺序追加日志、批量发送、零拷贝、Page Cache 利用好。
2. **可扩展**：Topic 分区天然支持横向扩展和消费者组并行消费。
3. **可回放**：消息按 offset 保留，消费者可以重置 offset 重放历史数据。
4. **生态强**：Kafka Streams、Connect、Flink/Spark 集成成熟。

不足：

1. 单条消息低延迟和复杂路由不如 RabbitMQ 灵活。
2. 分区内有序，跨分区不保证全局有序。
3. 延迟消息、事务消息等业务特性需要额外设计或能力有限。
4. 运维要关注分区数、副本、磁盘、ISR、rebalance 和积压。

## 3. RocketMQ 的优势和不足

优势：

1. 支持事务消息，适合本地事务和消息发送最终一致。
2. 延迟消息、顺序消息、死信队列等业务功能较完整。
3. 消费模型贴近业务系统，常用于订单、支付、履约链路。

不足：

1. 大规模流式数据生态通常不如 Kafka 丰富。
2. 跨语言和周边生态要看具体团队技术栈。
3. 事务消息也不是分布式事务万能解，需要业务幂等和补偿。

## 4. RabbitMQ 的优势和不足

优势：

1. 路由模型丰富，exchange 支持 direct、fanout、topic、headers。
2. 单条消息延迟低，确认机制和死信队列成熟。
3. 管理 UI 和 AMQP 生态友好，适合任务队列和复杂路由。

不足：

1. 高吞吐和海量积压通常不如 Kafka。
2. 消息大量堆积会显著影响 broker 压力。
3. 流式回放和大数据生态不是强项。

## 5. 选型思路

1. **埋点、日志、行为流、实时计算**：优先 Kafka。
2. **订单、库存、支付、事务消息、延迟消息**：优先 RocketMQ。
3. **任务分发、复杂路由、小规模异步解耦**：RabbitMQ 更直接。
4. **只需要简单异步削峰**：团队已有哪个稳定组件就优先用哪个，避免为了“更强”引入更高运维成本。

如果场景是缓存删除、数据变更事件或搜索索引同步，选择 Kafka 的常见理由是：

1. **事件量大且可批量处理**：商品、库存、价格、用户画像这类变更可能高频发生，Kafka 的批量发送、顺序追加和消费者组扩展更适合高吞吐。
2. **需要回放能力**：缓存删除失败、索引构建异常或下游逻辑 bug 修复后，可以按 offset 重放一段时间的事件。
3. **按业务 key 保序**：同一个商品或用户的变更可以按 key 进入同一分区，降低乱序带来的旧事件覆盖问题。
4. **消费者多样**：同一份变更事件可以同时给缓存失效、搜索索引、实时数仓、监控告警等多个消费者使用。
5. **保留时间可控**：Kafka 保留消息一段时间，适合做事件审计和失败补偿；RabbitMQ 更偏任务队列，通常不以长期保留和回放为核心。

但如果业务强依赖延迟消息、事务消息和复杂业务消息语义，RocketMQ 会更直接；如果只是少量后台任务分发和复杂路由，RabbitMQ 的模型更轻。

## 6. 面试回答模板

我选择 Kafka 通常是因为它更像分布式日志系统，分区顺序追加、批量发送、Page Cache 和零拷贝带来高吞吐，消费者可以按 offset 回放，适合日志、埋点、事件流和削峰。但 Kafka 的不足是复杂路由、延迟消息和业务事务能力不如专门的业务 MQ，顺序也只能保证分区内顺序。如果业务更关注订单事务消息、延迟消息和顺序消费，我会考虑 RocketMQ；如果是任务分发、复杂路由和低延迟异步，RabbitMQ 更合适。选型最终要看吞吐、延迟、可靠性、顺序性、运维成本和团队已有经验。
