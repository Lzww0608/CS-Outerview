# Q31.架构和设计方案

在我过去的一个项目中，我们使用了Kafka消息队列来构建一个实时数据处理平台，旨在捕捉和分析来自网站和移动应用的用户行为数据。以下是我们的架构和设计方案的概述：

1. **数据生产者**：网站和应用的后端服务作为生产者，它们负责发布用户的点击流、页面浏览、交互等事件到Kafka的不同主题（topics）中。
2. **Kafka集群**：我们部署了一个多节点的Kafka集群来确保高可用性和数据冗余。每个主题都有多个分区（partitions），以及对应的副本（replicas），确保在节点失效时仍能处理消息。
3. **消费者群组**：我们有多个消费者群组（consumer groups），每个群组负责读取特定主题的消息并进行处理。这些消费者群组可以是实时数据处理服务，如流处理引擎，它们可以对数据进行过滤、聚合或其他转换操作。
4. **数据处理和存储**：处理后的数据被发送到下游系统，如Hadoop集群进行批处理，或者Elasticsearch进行实时搜索和分析。
5. **容错和监控**：我们使用了Kafka的内置容错机制，并且部署了监控工具（如Prometheus和Grafana）来实时监控Kafka的性能和健康状态。

这个架构允许我们实时处理大量数据流，同时提供了扩展性和可靠性。比如，在大型促销活动期间，我们能够快速扩展消费者群组来处理增加的消息流量，而不会影响系统的整体性能。

## 如果自己实现一个消息队列，要考虑什么

消息队列的核心不是“把消息放进一个 List”，而是解决生产、存储、投递、确认、重试、扩展和可观测性的一整套问题。

### 1. 基础模型

1. **Topic / Queue**：消息按主题或队列隔离。
2. **Partition / Shard**：单队列拆成多个分区，提升吞吐并控制顺序边界。
3. **Producer**：负责发送、批量、压缩、重试和幂等。
4. **Broker**：负责接入、持久化、索引、复制和投递。
5. **Consumer Group**：同一组内分摊分区，不同组各自消费一份逻辑消息。
6. **Offset / Ack**：记录消费进度，支持失败重试和恢复。

### 2. 存储设计

高吞吐 MQ 通常使用顺序追加日志：

```text
topic-partition-0/
  00000000000000000000.log
  00000000000001000000.log
  index
```

设计点：

1. 顺序写磁盘，减少随机 I/O。
2. 按 segment 滚动文件，便于删除过期数据。
3. 建 offset 到物理位置的稀疏索引，支持快速定位。
4. 利用 Page Cache，避免大量消息进入 JVM 堆。
5. 支持保留策略，例如按时间、大小、压缩或归档。

### 3. 可靠性语义

消息语义通常分三类：

1. **At most once**：最多一次，可能丢消息，延迟低。
2. **At least once**：至少一次，可能重复，工程最常见，消费者要幂等。
3. **Exactly once**：精确一次，通常依赖幂等生产、事务、去重表或流处理框架语义，成本最高。

Broker 侧要考虑：

1. producer ack 何时返回，是写入 leader 内存、落盘，还是复制到多数副本。
2. 消费 offset 何时提交，是处理前提交还是处理后提交。
3. 重试和死信队列如何设计，避免毒丸消息阻塞整个分区。
4. 消息重复投递时，下游如何用业务 key 幂等。

### 4. 高可用和扩展

1. **多副本复制**：leader 写入，follower 复制，故障时选主。
2. **分区再均衡**：broker 或 consumer 增减时迁移分区，但要避免频繁 rebalance。
3. **限流和背压**：消费者慢时不能无限推送，Broker 要限制内存、连接和堆积。
4. **顺序性边界**：通常只保证单分区内有序，跨分区全局有序代价很高。
5. **延迟消息**：可用时间轮、延迟队列、分层时间桶或 Redis ZSet 实现。
6. **安全**：鉴权、ACL、TLS、租户隔离和消息加密。

### 5. 拉模式还是推模式

| 模式 | 优点 | 缺点 | 代表 |
| --- | --- | --- | --- |
| Pull 拉模式 | 消费者自己控制速率，容易批量拉取和背压，堆积时 Broker 压力更可控 | 实时性取决于轮询和长轮询参数，消费者逻辑稍复杂 | Kafka |
| Push 推模式 | 实时性好，Broker 能主动投递，客户端使用简单 | 消费者慢时容易被打爆，需要复杂流控、ack 和重投 | RabbitMQ 部分模式、很多通知系统 |

高吞吐日志和流处理更适合拉模式，因为消费者可以按能力拉取、批量处理、控制 offset，并且天然支持堆积削峰。低延迟通知、任务派发、小规模在线消费者可以用推模式，但必须有 prefetch、ack、重试和限流。

面试回答可以说：如果是 Kafka 这类高吞吐日志队列，我会优先选 pull；如果是实时通知或任务分发，push 的体验更好。真正的关键不是绝对谁更好，而是背压、批量、失败重试和消费进度怎么设计。
