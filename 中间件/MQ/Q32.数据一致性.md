# Q32.数据一致性

在处理消息队列中的数据一致性问题时，尤其是在分布式事务的场景下，我们通常采用以下策略：

1. **事务消息**: 某些消息队列技术如Apache Kafka支持事务消息。这允许生产者在一个事务中发送一系列消息，这些消息要么全部提交，要么全部不提交，从而保证了原子性。
2. **双阶段提交**: 双阶段提交（2PC）是分布式事务中常用的一个协议，它包括准备阶段和提交/回滚阶段。但是，它可能会导致性能问题和更复杂的系统设计。
3. **最终一致性**: 在某些场景下，我们可以采用最终一致性模型，确保在一定时间内系统状态会变得一致。例如，使用补偿事务或者利用幂等性来确保重试操作不会影响系统状态。
4. **本地事务与消息表**: 结合本地数据库事务和消息队列，将消息存储在数据库的同一个事务中，然后由独立的进程或服务读取并发送到消息队列，从而保证本地事务和消息发送的一致性。
5. **幂等性**: 确保消息处理是幂等的，即重复处理相同的消息不会对系统状态产生影响。这通常需要业务逻辑来实现，例如通过检查数据库中的记录是否存在来避免重复处理。

应用场景举例：在电子商务系统中，用户下单操作涉及到库存服务和订单服务的数据更新。可以使用本地事务与消息表的方式来处理。用户下单时，订单服务在本地数据库中创建订单，并将消息写入本地的消息表，然后提交事务。独立服务读取消息表中的消息，并发布到消息队列中去更新库存服务，这样就保证了订单创建和库存更新的一致性。

## 事务性消息和非事务性消息的区别

**非事务性消息**只保证一次普通发送流程：生产者把消息发给 Broker，Broker 返回 ACK，之后由消费者消费。它能配合持久化、ACK、重试提高可靠性，但无法天然保证“本地 DB 事务成功”和“消息一定发出”这两个动作的原子性。

**事务性消息**会把消息发送拆成两个阶段。以 RocketMQ 这类支持半消息的 MQ 为例：

1. 生产者先发送半消息或 prepare 消息，此时消费者不可见。
2. 生产者执行本地事务，例如创建订单。
3. 本地事务成功则提交消息，失败则回滚消息。
4. 如果生产者宕机，Broker 会回查本地事务状态，再决定提交还是回滚消息。

因此事务性消息解决的是“本地事务和消息投递之间的一致性”。它不是让所有下游消费都变成强一致，下游仍然需要重试、幂等和补偿。

## 只有普通消息时如何做出类似事务消息的保证

如果 MQ 不支持事务消息，可以用本地消息表或 outbox 模拟“本地事务 + 消息发送”的一致性：

1. 在同一个 DB 事务中写业务数据和消息表，消息状态为 `NEW`。
2. DB 事务提交后，由后台发送器扫描 `NEW/FAILED` 消息并发送普通 MQ。
3. MQ 返回发送成功后，把消息状态更新为 `SENT`，记录发送时间和重试次数。
4. 如果发送失败或服务宕机，消息仍在表中，下一轮继续重试。
5. 消费端使用 `message_id` 或业务键做幂等，保证重复投递不会重复执行业务结果。

这个方案牺牲了一些实时性，但把“可能丢消息”的窗口变成了“可扫描、可重试、可人工修复”的状态。

## 保存订单和发送订单创建成功消息放在事务内还是事务外

不建议在 DB 事务中直接调用 MQ 发送并等待结果。原因是 MQ 是数据库以外的资源，数据库回滚无法撤销已经投递出去的消息，同时外部 IO 会拉长数据库事务时间，增加锁持有时间和死锁风险。

常见方案有两种：

1. **本地消息表 / Outbox**：订单和消息事件在同一个 DB 事务内落库，事务提交后由后台任务或 CDC 发送 MQ，发送成功后标记消息状态。
2. **MQ 事务消息**：先发半消息，再执行订单 DB 事务，最后提交或回滚 MQ 消息。

如果只是“DB 提交后再发普通消息”，会有 DB 成功但服务宕机导致消息没发出的窗口；如果“先发消息再提交 DB”，会有消费者看到消息但订单不存在的窗口。所以核心不是把发送放在事务里或事务外，而是引入能恢复的中间状态。
