# Q13. 消息的幂等性

在计算机科学中，幂等性 (Idempotence) 描述了一个操作无论执行多少次，结果都是相同的特性。在消息队列的上下文中，幂等性通常涉及到消息的处理。如果一个操作是幂等的，那么无论你处理一次消息还是多次消息，结果都是相同的。

这主要是因为在分布式系统中，网络问题、服务的暂时不可用或者其他故障可能会导致消息被处理多次。如果操作不是幂等的，那么重复处理消息可能会导致不一致的状态。

例如，假设你正在使用一个消息队列来处理银行转账。一个消息代表了从账户 A 向账户 B 转账 100 美元的操作。如果这个操作是幂等的，那么无论消息被处理一次还是多次，账户 A 和账户 B 的余额都会保持一致。如果操作不是幂等的，那么重复处理消息可能会导致账户 B 的余额增加超过 100 美元。

因此，幂等性在消息队列中是非常重要的，它能够帮助我们避免在面临网络问题或者服务暂时不可用的情况下，确保系统状态的一致性。

## 常见实现方式

1. **唯一业务键**：使用 `order_id`、`payment_id`、`request_id` 等天然唯一字段，数据库加唯一索引。重复消息再次插入时直接失败或转为查询已有结果。
2. **消费去重表**：消费者处理前先写入 `message_id` 到去重表，成功写入才执行业务逻辑；如果唯一键冲突，说明已经处理过。
3. **状态机条件更新**：用状态流转约束幂等，例如订单只能从 `UNPAID` 更新为 `PAID`，重复支付回调执行 `UPDATE ... WHERE status='UNPAID'` 时影响行数为 0，就直接返回成功。
4. **乐观锁版本号**：更新时带上 `version` 或业务流水号，防止并发重复扣减、重复累加。
5. **Redis 短期幂等键**：对高频请求可以使用 `SET key value NX EX ttl` 做入口去重，但关键结果仍建议落 DB，避免 Redis 丢失后无法追溯。

## 易错点

1. 幂等不是“不重复消费”，而是“重复消费不会产生重复结果”。MQ 的重试、ACK 丢失、消费者重启都可能导致重复投递。
2. 不能只依赖分布式锁。锁只解决某个时间窗口内的并发，不能解决消息延迟重放、服务重启后的重复执行。
3. 金额、库存、积分这类累加/扣减操作不能简单重放，必须绑定业务流水。例如扣库存要记录 `order_id + sku_id` 是否已扣减。
4. 消费者最好先完成本地事务，再 ACK 消息；如果先 ACK 后处理，处理失败会直接丢消息。
