# Q9.消息堆积现象

在消息队列中，消息堆积是指消息在队列中积累得比消费得快，导致队列中消息数量持续增加。

原因：

+ **消费者处理速度太慢**：如果消费者的处理速度与生产者相差太多，消息就会在队列中积累。
+ **生产者产生消息的速度太快**：如果生产者生产速度远高于消费速度，也会如此。
+ **消费者出现故障**：如果消费者出现故障，暂时无法处理消息，同样会导致消息在队列中积累。



解决方法：

+ **增加消费者**
+ **优化消息处理速度**：如并行处理消息，优化处理算法。
+ **控制生产者的速度**
+ **消息的合并**
+ **设置消息的过期时间**

## 如何定位消息堆积

消息堆积的本质是生产速度长期大于消费速度，或者消费链路某个环节阻塞。排查时不要只看队列长度，还要看增长速度和消费延迟。

常看指标：

1. **生产速率和消费速率**：判断是突发流量还是消费者整体能力不足。
2. **消费 lag**：Kafka 看 consumer group lag，RocketMQ/RabbitMQ 看待消费消息数和最老消息时间。
3. **消费者错误率**：反序列化失败、业务异常、下游超时会导致反复重试。
4. **单条消息耗时**：业务处理慢、批量提交小、同步 RPC 太多都会拖慢消费。
5. **分区或队列倾斜**：某些 partition lag 很高，可能是 key 分布不均或单分区顺序消费卡住。
6. **死信和重试队列**：重试风暴会占满消费能力。

## 处理思路

短期止血：

1. 临时扩容消费者实例，但要确认分区数或队列数足够，否则扩了也消费不到更多分区。
2. 关闭或降级非核心生产者，入口限流，避免堆积继续扩大。
3. 对可丢弃的低价值消息设置过期或转储，保护核心消息。
4. 下游异常时先熔断或切到降级路径，避免消费者线程都卡在超时重试上。

长期优化：

1. 增加 topic 分区或队列数量，提升并行消费上限。
2. 消费端批量拉取、批量写库、批量确认，减少网络和持久化开销。
3. 慢业务异步化，把下载、转码、推送等耗时步骤拆到后续队列。
4. 对同一 key 必须顺序的场景，只保证 key 内顺序，不要把所有消息放到单队列串行。
5. 给消费者加幂等，允许失败后安全重试。
6. 对重试设置最大次数、退避和死信队列，避免毒丸消息反复阻塞主队列。

## 易错点

1. 只增加消费者不一定有效，Kafka 单个 partition 同一消费组内同一时刻只能被一个消费者消费。
2. 堆积期间盲目加大批量可能降低提交频率，失败重放成本变高。
3. 顺序消息遇到一条毒丸消息可能阻塞后续同 key 或同队列消息。
4. 消费者处理成功后再 ACK；如果先 ACK 再处理，消费者宕机会丢消息。
5. 积压清理要区分业务价值，订单、支付类消息不能简单丢弃。

## 面试回答模板

消息堆积说明生产速度超过消费速度，或消费者被慢业务、下游故障、重试和分区倾斜卡住。我会先看生产/消费速率、lag、最老消息时间、消费者错误率和下游延迟。止血上可以扩容消费者、限流生产者、降级慢下游、把毒丸消息转死信；长期要增加分区、批量消费、优化业务耗时、拆分慢任务、保证幂等和重试退避。扩消费者前要确认分区数足够，否则并行度上不去。
