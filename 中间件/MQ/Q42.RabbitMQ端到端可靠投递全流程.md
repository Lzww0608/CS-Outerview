# Q42. RabbitMQ 端到端可靠投递全流程

面试题：整条链路怎么确保消息完整落地、百分百入库，梳理生产到消费全流程。这道题考察的是消息可靠性的完整链路认知，不是某一个点的配置。

## 1. 端到端链路梳理

```text
业务方法
  -> 本地事务写 DB
  -> 发送消息到 Broker
  -> Broker 持久化 + 镜像/Quorum 复制
  -> Broker 投递到 Consumer
  -> Consumer 处理业务
  -> Consumer ACK
```

每一段都可能丢消息，必须分段防护：

| 链路段 | 可能丢失原因 | 兜底机制 |
| --- | --- | --- |
| 业务到生产者 | 进程崩溃，消息没发出 | 本地消息表 / Outbox |
| 生产者到 Broker | 网络抖动，Broker 未收到 | Publisher Confirm + 重试 |
| Broker 到磁盘 | Broker 宕机，内存消息丢失 | 队列/消息持久化 |
| Broker 单点故障 | 节点宕机 | 镜像队列 / Quorum Queue |
| Broker 到 Consumer | 消费者拉到但宕机 | 手动 ACK |
| Consumer 处理失败 | 业务异常或超时 | 死信队列 + 重试 + 幂等 |

## 2. 生产端可靠性

### 2.1 Publisher Confirm 机制

RabbitMQ 提供 publisher confirm 让生产者确认 Broker 已收到消息：

1. Channel 开启 confirm 模式：`channel.confirmSelect()`。
2. 每条消息发送后，Broker 异步返回 ack 或 nack。
3. 生产者维护未确认消息表，nack 或超时重试。

伪代码：

```java
channel.confirmSelect();
channel.addConfirmListener(
    (deliveryTag, multiple) -> ackHandler(deliveryTag, multiple),
    (deliveryTag, multiple) -> nackHandler(deliveryTag, multiple)
);
channel.basicPublish(exchange, routingKey,
    MessageProperties.PERSISTENT_TEXT_PLAIN, body);
```

### 2.2 Mandatory + Return Listener

如果消息路由不到任何队列（exchange 绑定缺失），默认 Broker 会丢弃。设置 `mandatory=true` 后 Broker 会通过 basic.return 把无法路由的消息退回生产者，生产者捕获后做兜底处理或告警。

### 2.3 本地消息表 / Outbox

光靠 confirm 不够。如果业务 DB 事务提交成功但消息没发出（进程崩溃在两步之间），消息就丢了。

工程标准做法是 Outbox：

```text
业务事务:
    INSERT 业务表
    INSERT outbox(消息体, status='PENDING')
COMMIT

异步发送任务:
    SELECT * FROM outbox WHERE status='PENDING'
    发送到 Broker
    confirm 成功 -> UPDATE status='SENT'
    confirm 失败 -> 保持 PENDING 等待重试
```

这样消息持久化在 DB，发送和业务事务原子，进程崩溃后定时任务能重发未确认消息。

### 2.4 消息唯一 ID

每条消息生成全局唯一 ID（业务 ID + 类型 + UUID），写在 message properties 的 messageId 字段。消费端拿这个 ID 做幂等去重。

## 3. Broker 端可靠性

### 3.1 队列和消息持久化

队列声明：

```java
channel.queueDeclare(queueName, true /*durable*/, false, false, null);
```

消息发送：

```java
channel.basicPublish(exchange, routingKey,
    MessageProperties.PERSISTENT_TEXT_PLAIN /*deliveryMode=2*/, body);
```

队列 durable + 消息 persistent，Broker 重启后队列和未消费消息都还在。

注意：persistent 不等于发送完就刷盘。RabbitMQ 默认是批量异步刷盘，仍可能有秒级窗口丢失。强一致场景需要配合 publisher confirm 等待 Broker 真正刷盘后 ack。

### 3.2 镜像队列与 Quorum Queue

单节点持久化解决不了节点宕机。RabbitMQ 提供：

1. **镜像队列**（旧版本）：主队列在一个节点，镜像同步到其他节点。主节点宕机后镜像晋升为主。但同步是异步的，可能丢消息。
2. **Quorum Queue**（推荐）：基于 Raft 协议，写入要多数节点确认才回 ack，强一致。RabbitMQ 3.8+ 默认推荐。

代价：写入延迟更高、内存占用更大、不支持优先级队列等部分特性。

### 3.3 集群与高可用

生产环境至少 3 节点集群：

1. 节点间复制元数据。
2. 配合 HAProxy / Keepalived 做负载均衡和故障切换。
3. 客户端配置多个连接地址，自动重连。

## 4. 消费端可靠性

### 4.1 手动 ACK

```java
channel.basicConsume(queue, false /*autoAck*/, deliverCallback, cancelCallback);
// 业务处理成功后
channel.basicAck(deliveryTag, false);
// 业务失败
channel.basicNack(deliveryTag, false, true /*requeue*/);
```

关闭 autoAck 后，Broker 投递消息到 Consumer 前先标记为 unacked。Consumer 业务处理成功才 ack，Broker 才真正删除消息。

如果 Consumer 宕机或断开连接，Broker 会把未 ack 的消息重新投递给其他 Consumer。

### 4.2 prefetch 控制

```java
channel.basicQos(10);
```

限制每个 Consumer 同时持有 10 条未 ack 消息，避免某个慢消费者堆积大量未 ack 影响整体。

### 4.3 业务幂等

消息重投不可避免，消费端必须幂等。常见手段：

1. **唯一索引去重**：业务唯一键作为 DB 唯一索引，重复消息插入失败。
2. **状态机校验**：订单从 CREATED 到 PAID，重复 PAID 直接忽略。
3. **去重表**：单独维护 message_id 去重表，处理前先检查。
4. **Redis SETNX**：临时存 message_id，设置 TTL 防止 Redis 满。
5. **乐观锁**：`UPDATE ... WHERE version=?`，重复消息更新失败不影响最终结果。

### 4.4 死信队列兜底

消息处理失败多次后不能无限重试，需要进入死信队列：

```text
业务队列:
    x-dead-letter-exchange: dlx.exchange
    x-message-ttl: 5min（可选）
```

进入死信的条件：

1. basicNack/Reject 且 requeue=false
2. 消息 TTL 到期
3. 队列达到 max-length 上限

死信队列由专门任务处理，可以告警、人工处理或延迟重投。

## 5. 完整链路兜底设计

把上述机制串起来，端到端可靠投递的标准模板：

```text
1. 业务 DB 事务 + Outbox 表（原子）
2. 异步任务读 Outbox，发送到 Broker（开启 confirm，mandatory=true）
3. confirm 成功更新 Outbox status='SENT'，失败保留 PENDING 重试
4. Broker 端开启 Quorum Queue + 消息持久化
5. Consumer 关闭 autoAck，开启 prefetch
6. 业务处理前查去重表/Redis SETNX 判幂等
7. 业务事务成功后 channel.basicAck
8. 失败多次进死信队列，人工或定时任务处理
9. 全链路埋点 trace_id，便于排查丢失或重复
```

## 6. 性能与可靠性取舍

完全的强可靠会牺牲吞吐：

| 配置 | 吞吐 | 可靠性 |
| --- | --- | --- |
| autoAck + 非持久化 | 高 | 极低 |
| 手动 ACK + 持久化 | 中 | 高 |
| Quorum Queue + Confirm + Outbox | 低 | 极高 |

实际系统按业务等级分队列：

1. 交易类（订单、支付）：全部开启，宁可慢不能丢。
2. 通知类（短信、推送）：手动 ACK + 重试即可，丢一两条可接受。
3. 日志类：autoAck 即可，关心吞吐。

## 7. 易错点

1. 只开了 durable 没开 persistent：队列存了但消息内存里，Broker 重启丢消息。
2. autoAck=true：消息一投递就标记删除，Consumer 处理失败也无法重投。
3. confirm 只看 publish 没等回调：confirm 是异步的，必须 listener 处理。
4. 没有 Outbox：业务事务和发送消息不原子，进程崩溃丢消息。
5. 消费端不幂等：重投导致重复扣款、重复发券。
6. 死信队列只建不监控：消息积压在 DLQ 没人处理。
7. nack 时 requeue=true 死循环：毒丸消息反复消费失败又入队，把队列堵死。
8. prefetch 不设置：单个 Consumer 拉走全部消息，其他 Consumer 闲置。

## 8. 总结

RabbitMQ 端到端可靠投递不是单一配置能搞定，而是一整套链路防护：生产端用 Outbox + Publisher Confirm + mandatory 保证业务与消息原子；Broker 端用 Quorum Queue + 持久化 + 集群高可用；消费端用手动 ACK + prefetch + 业务幂等 + 死信队列兜底。每个环节都可能丢消息，必须分段防护。强可靠会牺牲吞吐，要按业务等级分级配置。面试回答从链路图开始，逐段说防护机制，再讲取舍和监控，比堆配置更能体现工程思维。
