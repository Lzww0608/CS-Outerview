# Q12.重复消费问题

消息队列中的消息重复消费问题指的是同一条消息被消费者处理多次的情况。这在分布式系统中是一个常见问题，可能由于网络问题、消息队列的重试机制或者消费者的故障等原因引起。处理消息重复消费的策略包括：



+ **幂等性设计**：确保消息处理逻辑具有幂等性，即多次执行相同操作的结果与执行一次的结果是相同的。这样，即使消费被重复消费，也不会对系统状态产生重大影响。
+ **消息去重**：在消息中包含一个唯一的标识符（如UUID（Universally Unique Identifier，通用唯一识别码）或者消息ID），消费者在处理消息之前先查看标记是否已经被处理过，可以通过维护已处理消息的标识符的数据库或者缓存来实现。
+ **使用事务**：如果消息消费和业务逻辑可以在一个数据库事务中完成，那么即使消息被重复消费，数据库的事务控制也能保证业务逻辑不会被重复执行。
+ **消息确认机制**：合理使用消息队列提供的确认机制，确保消息只有被处理之后才确认，这样可以避免先确认后处理失败导致消息丢失。
+ **限制重试次数**：对于可能因为暂时性问题而失败的消息处理，可以设定重试次数和重试间隔，避免无限制的重试导致消息的重复消费。
+ **顺序消费**：在需要保证消息顺序的场景下，通过单一消费者顺序处理消息或者使用消息队列提供的顺序消费特性来防止消息重复。

例如，在一个电子商务系统中，如果顾客的订单创建操作产生了一个消息，该消息包含了一个订单ID，那么即使这个消息被重复消费，系统也会识别出这个订单ID已经被处理过，从而避免创建重复的订单。

## 重复消费为什么会发生

重复消费通常不是 MQ “出错”，而是可靠消息语义下的正常结果。只要系统追求至少一次投递，就必须接受消息可能重复。

常见原因：

1. **消费者处理成功但 ACK 失败**：Broker 没收到确认，会重新投递。
2. **消费者处理超时**：处理时间超过可见性超时或会话超时，消息被认为未完成。
3. **消费者重启或 Rebalance**：offset 还没提交，分区被分配给其他消费者后从旧 offset 继续消费。
4. **生产者重试**：生产者没有收到 Broker ACK，重试发送同一业务消息。
5. **死信重放或人工补偿**：历史消息重新投递，如果没有幂等设计就会重复执行。

## 消费端处理顺序

推荐的顺序是：

```text
读取消息
    -> 校验 message_id / 业务唯一键
    -> 在本地事务中执行业务处理和幂等记录
    -> 事务提交成功
    -> ACK 或提交 offset
```

如果先 ACK 再处理，业务处理失败会造成消息丢失；如果处理成功后 ACK 失败，可能重复消费，所以必须依赖幂等。

## 幂等落地方案

1. **唯一索引**：订单、支付、发货等场景使用业务唯一键，重复插入直接失败或返回已有结果。
2. **消费记录表**：以 `message_id` 为主键，业务处理和插入消费记录放在同一个数据库事务中。
3. **状态机条件更新**：例如订单只能从 `CREATED` 变为 `PAID`，重复支付消息更新影响行数为 0 时直接返回成功。
4. **流水表**：金额、库存、积分类操作用业务流水号去重，不能只做简单加减。
5. **Redis 去重**：高频短期去重可用 `SET key value NX EX ttl`，但关键业务仍要落数据库。

## 面试回答模板

重复消费通常来自 ACK 丢失、消费者重启、Rebalance、处理超时、生产者重试或死信重放。可靠消息一般追求至少一次投递，所以重复是必须设计处理的。消费者应该先完成业务事务和幂等记录，再 ACK 或提交 offset。幂等可以用业务唯一键、消费记录表、状态机条件更新、流水表或 Redis 短期去重实现。重点是保证同一条业务消息处理多次，最终业务状态仍然等价于处理一次。
