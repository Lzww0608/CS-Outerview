# Q5.持久化与非持久化

+ **持久化**：当一个消息被发送到消息队列，它将被存储到在磁盘或其他持久化的存储设备，直到它被消费或者到期。即使在消息队列重启或者系统崩溃之后，消息也不会丢失。
+ **非持久化**：消息只存在内存中，一旦消息队列重启或者系统崩溃，消息将会丢失。



持久化的主要目的是提高系统的可靠性。通过持久化，即使在系统故障时，消息也不会丢失，可以在系统恢复后继续被处理。这对于那些不能丢失任何消息的应用场景（如金融交易、订单处理等）是非常重要的。然而，持久化也会带来一些性能开销，因为写入磁盘或其他持久化设备通常比写入内存要慢。因此，是否需要持久化取决于你的具体需求和场景。

## MQ 持久化通常怎么实现

不同 MQ 实现不同，但核心思路都是把消息先写入可恢复的日志或文件，再通过刷盘策略和副本机制控制丢失窗口。

常见机制：

1. **顺序追加日志**：Kafka、RocketMQ 这类系统把消息追加到 commit log 或 segment 文件，顺序写磁盘吞吐高。
2. **页缓存加异步刷盘**：写入先进入 OS Page Cache，再由后台刷盘，性能好但机器断电可能丢最近数据。
3. **同步刷盘**：生产请求等待 `fsync` 或等价持久化动作完成后返回，可靠性更高但延迟更大。
4. **副本复制**：leader 写入后复制到 follower，多副本确认后再认为消息成功，可以抵御单机故障。
5. **消费位点持久化**：不仅消息要持久化，消费者 offset/ack 状态也要持久化，否则恢复后会重复消费或跳过消息。

## 可靠性不只靠持久化

一条消息“不丢”通常要同时保证生产、Broker、消费三段：

1. **生产端**：发送失败要重试；Kafka 常配置 `acks=all`，并开启幂等生产者避免重试重复写。
2. **Broker 端**：消息落盘或复制到足够副本后再 ACK；监控 ISR、副本落后和磁盘错误。
3. **消费端**：业务处理成功后再提交 offset 或 ACK；失败时重试，超过次数进入死信队列。
4. **业务端**：消费者必须幂等，因为至少一次投递下重复消费是常态。

如果只开启消息持久化，但生产者发送后不确认、消费者先 ACK 后处理、或者没有副本，仍然可能丢消息。

## 性能取舍

持久化会增加延迟，但可以通过工程手段降低成本：

1. 批量发送和批量刷盘，减少 `fsync` 次数。
2. 顺序写文件，避免小随机写。
3. 压缩消息，降低网络和磁盘带宽，但会增加 CPU。
4. 根据业务等级区分队列：核心交易消息高可靠，日志埋点消息可以更偏吞吐。
5. 使用多分区并行写入，提升吞吐。

## 易错点

1. 持久化不等于强一致，异步刷盘和异步复制都有丢数据窗口。
2. 副本数多不代表一定可靠，还要看生产确认策略是否等待副本确认。
3. 消息持久化不能解决重复消费，重复消费要靠业务幂等。
4. 死信队列不是垃圾桶，必须有告警、排查和重放策略。
5. 过期消息如果还没消费就被清理，本质上也是业务可见的消息丢弃，要提前确认业务能接受。

## 面试回答模板

MQ 持久化是把消息写入磁盘日志或持久化存储，Broker 重启后可以恢复。常见实现是顺序追加 commit log、利用 Page Cache、按策略同步或异步刷盘，并通过多副本复制提高可用性。但可靠消息不只靠持久化，还要生产端确认和重试、Broker 端落盘或副本确认、消费端处理成功后再 ACK，以及业务幂等。同步刷盘可靠但延迟高，异步刷盘吞吐好但有丢失窗口，真实系统要按交易消息、通知消息、日志消息的价值选择不同可靠性等级。
