# 1.Canal 原理与配置

Canal 是阿里开源的基于 MySQL binlog 的增量数据订阅与同步组件。它把自己伪装成 MySQL 从库，向 MySQL 主库发起 binlog dump 请求，解析 binlog 中的数据变更事件，再把这些变更投递给客户端或消息队列。

## 1. 为什么使用 Canal？

项目里使用 Canal，通常是为了做 **数据库变更捕获（CDC, Change Data Capture）**。

常见场景：

1. **缓存同步**：MySQL 变更后，异步更新或删除 Redis 缓存。
2. **搜索索引同步**：MySQL 变更后，同步到 Elasticsearch。
3. **数据异构**：把业务库数据同步到数仓、报表库、风控系统。
4. **事件驱动**：把数据库变更转换成业务事件，投递给下游系统。
5. **低侵入改造**：不改业务代码，通过监听 binlog 获取增量变更。

相比在业务代码里手动发消息，Canal 的优势是对业务代码侵入小，能捕获所有数据库变更；缺点是需要处理 binlog 配置、位点管理、表结构变更、幂等消费和延迟监控。

## 2. 工作原理

Canal 的核心链路：

```text
MySQL binlog
    -> Canal Server 模拟 MySQL Slave 拉取 binlog
    -> 解析 binlog event
    -> Canal Client / Kafka / RocketMQ 消费
    -> 更新缓存、索引、下游库
```

MySQL 主从复制大致也是这个思路：

1. MySQL master 把数据变更写入 binlog。
2. slave 的 I/O 线程拉取 binlog。
3. slave 的 SQL 线程重放变更。

Canal 借用了这套机制，但它不真正重放 SQL，而是解析成结构化变更事件，交给业务消费。

## 3. MySQL 侧配置

MySQL 需要开启 binlog，并建议使用 ROW 格式：

```ini
[mysqld]
log-bin=mysql-bin
binlog-format=ROW
server-id=1
```

Canal 需要一个具备复制权限的账号：

```sql
CREATE USER 'canal'@'%' IDENTIFIED BY 'canal_password';
GRANT SELECT, REPLICATION SLAVE, REPLICATION CLIENT ON *.* TO 'canal'@'%';
FLUSH PRIVILEGES;
```

为什么推荐 `ROW`？

1. `STATEMENT` 记录 SQL，遇到非确定函数或复杂 SQL 时不容易准确还原每一行变化。
2. `ROW` 记录行级变更，能拿到变更前后的列值，适合缓存删除、索引同步和数据异构。
3. Canal 对 DML 的结构化解析通常依赖行变更事件。

## 4. Canal instance 常见配置

典型配置项：

```properties
canal.instance.master.address=127.0.0.1:3306
canal.instance.dbUsername=canal
canal.instance.dbPassword=canal_password
canal.instance.connectionCharset=UTF-8
canal.instance.filter.regex=.*\\..*
canal.instance.gtidon=false
```

如果只订阅部分库表，可以配置过滤规则：

```properties
canal.instance.filter.regex=mydb\\.user,mydb\\.order_.*
```

如果投递到 MQ，还需要配置 destination、topic、分区路由等参数。实际项目里要保证同一主键的数据尽量路由到同一分区，方便保持局部顺序。

## 5. 消费端怎么处理？

消费 Canal 事件时，重点不是“拿到消息”本身，而是要保证可恢复和幂等。

1. **幂等消费**：同一个 binlog 事件可能因为重试被消费多次，下游更新要能重复执行。
2. **位点管理**：消费成功后再 ack，避免位点前移但业务处理失败。
3. **顺序性**：同一行数据的多次变更最好按 binlog 顺序处理。
4. **表结构变更**：DDL 可能导致列数量、列名、类型变化，消费端要兼容。
5. **延迟监控**：监控 Canal 与 MySQL 当前 binlog 位点差距，避免同步滞后。

## 6. 常见难点

### 6.1 DDL 兼容

业务表加字段、删字段、改类型后，消费端如果写死列下标或字段列表，很容易解析失败。更稳妥的做法是基于列名处理，并对未知字段保持兼容。

### 6.2 消息重复

Canal 或 MQ 重启后，可能从上一个位点重新投递一批消息。下游更新缓存、索引或异构库时，要用主键、版本号、binlog 位点、更新时间等信息做幂等。

### 6.3 全量和增量衔接

如果先做历史全量导入，再接 Canal 增量，需要记录全量开始和结束时的 binlog 位点，避免漏数据或重复覆盖。

### 6.4 数据一致性

Canal 链路是异步链路，不能保证下游和 MySQL 强一致。适合最终一致场景。如果读请求对一致性要求很高，需要结合缓存双删、版本号校验、回源兜底等方案。

## 7. 面试回答模板

项目里用 Canal 主要是为了监听 MySQL binlog 做增量同步，比如同步缓存、搜索索引或异构数据。Canal 的原理是模拟 MySQL 从库，向主库拉取 binlog，然后解析成结构化事件给客户端或 MQ 消费。

配置上，MySQL 要开启 binlog，并且通常配置成 ROW 模式；Canal 侧需要配置 MySQL 地址、复制账号、订阅的库表正则、位点或 GTID，以及下游投递方式。实际难点主要在 DDL 兼容、重复消费幂等、全量增量衔接、同步延迟监控和下游最终一致性处理。
