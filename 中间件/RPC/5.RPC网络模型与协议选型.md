# RPC 网络模型与协议选型

面试里问“除了 JSON-RPC 还了解什么 RPC”“设计一个 RPC 网络通信服务会用什么网络框架模型”，重点是把协议、序列化、连接模型、线程模型和治理能力说完整。

## 1. 常见 RPC 方案

1. **JSON-RPC**：基于 JSON 表达方法名、参数、id 和结果。优点是简单、可读、调试方便；缺点是类型约束弱、包体大、性能一般。
2. **gRPC**：基于 HTTP/2 和 Protobuf，支持 IDL、代码生成、多路复用、流式调用、deadline 和拦截器，适合跨语言微服务。
3. **Thrift**：同时提供 IDL、序列化协议和服务框架，支持多语言、多协议、多传输层。
4. **Dubbo**：偏 Java 生态，强调服务治理、注册发现、负载均衡、路由、容错和泛化调用。
5. **REST/OpenAPI**：严格来说不是 RPC，但常用于服务间 HTTP API，生态成熟、可观测和网关支持好。
6. **自定义二进制 RPC**：可以为低延迟、高吞吐场景定制协议，但要自己处理兼容性、治理和工具链。

## 2. 网络模型

高并发 RPC 服务通常采用 Reactor 模型：

```text
acceptor
  -> event loop group
      -> connection
      -> codec / framing
      -> request dispatch
          -> worker pool
          -> business handler
```

核心设计：

1. **非阻塞 I/O**：Linux 下常用 `epoll`，一个 event loop 管理大量连接。
2. **连接抽象**：每个连接维护输入缓冲区、输出缓冲区、协议状态、最后活跃时间和未完成请求表。
3. **协议编解码**：先解决粘包拆包，再做序列化反序列化。
4. **请求分发**：I/O 线程只做网络和轻量编解码，耗时业务交给 worker pool。
5. **回写结果**：业务线程不要直接阻塞写 socket，而是把响应放入连接输出队列，由 event loop 统一发送。

## 3. 协议帧设计

自定义 RPC 至少需要定义帧边界：

```text
magic | version | flags | request_id | codec | body_length | body
```

字段含义：

1. `magic`：快速识别非法协议。
2. `version`：支持协议演进。
3. `flags`：标记请求/响应、压缩、心跳、单向调用等。
4. `request_id`：支持连接复用和异步响应匹配。
5. `codec`：标识 JSON、Protobuf、MsgPack 等序列化方式。
6. `body_length`：解决 TCP 粘包拆包。

## 4. 线程模型怎么选

常见选择：

1. **单 Reactor 单线程**：实现简单，适合连接少、业务轻的场景。
2. **单 Reactor 多线程**：一个 I/O 线程接入连接，业务丢到 worker pool，适合中等规模服务。
3. **主从 Reactor**：主 Reactor 只 accept，从 Reactor 负责连接读写，适合高连接数和多核机器。
4. **one loop per thread**：每个 I/O 线程有独立 epoll、连接集合和任务队列，减少锁竞争，是常见网络库模型。

选择时要避免两类问题：业务处理阻塞 I/O 线程；多个线程同时操作同一连接导致响应乱序或缓冲区竞争。

### 4.1 小请求、轻业务下的瓶颈

如果请求很小、业务逻辑很轻，瓶颈往往不在 worker 业务线程，而在 I/O 事件循环和协议处理：

1. **系统调用和事件分发**：大量小包会放大 `epoll_wait/read/write`、唤醒和回调调度成本。
2. **拆包和解码**：Length-Prefix、Protobuf/JSON 解码、校验和对象构造会占用 I/O 线程 CPU。
3. **内存分配和拷贝**：每个请求都新建 buffer、string、request 对象，会让 allocator 和 cache miss 成为热点。
4. **跨线程投递**：I/O -> worker -> I/O 的队列入队、锁、eventfd 唤醒和上下文切换成本可能超过业务逻辑本身。
5. **日志和监控**：每请求同步打日志、上报指标或生成 trace，也会拖慢轻量接口。

优化时要先用 echo RPC 和空 handler 测基线，再逐层打开编解码、日志、业务和下游。常见优化包括批量读写、复用 buffer/request 对象、减少小对象分配、I/O 线程做足够轻量的 framing、批量投递任务、按连接亲和到固定 EventLoop、只在输出队列从空变非空时唤醒。

### 4.2 I/O 线程只读不解析时 Length-Prefix 怎么办

如果 I/O 线程完全不解析协议，只把字节流随便丢给 worker，Length-Prefix 半包会失去连接级状态，worker 也很难知道一条完整请求什么时候到齐。更稳的边界是：

```text
I/O 线程:
  read 到 connection input buffer
  只做 framing 状态机
  凑齐完整 frame 后投递 frame buffer / slice

decode 线程:
  反序列化 body
  构造 request 对象
  按方法或路由分发到 worker
```

也就是说，I/O 线程至少要维护每个连接的输入缓冲区和帧边界状态。Length-Prefix 的处理流程通常是：先等 header 字节够，解析 body_length；如果 body 还没收全，继续留在连接 buffer；只有完整 frame 到齐后，才能投递给解码线程或业务线程。

新增解码线程组后，也不一定要直接在解码线程里完成轻量业务。解码线程适合做 CPU 密集但无业务阻塞的反序列化、校验和对象构造；worker 负责业务隔离、限流、优先级、超时、访问下游和错误处理。若轻量业务确实没有阻塞和共享状态，也可以合并 decode + handle，但要避免解码线程被慢业务拖住，导致所有连接的请求都无法解码。

跨线程投递常用 MPSC 队列、无锁环形队列、mutex + condition_variable、eventfd/pipe 唤醒 EventLoop。网络库里更常见的是每个 EventLoop 自带任务队列，其他线程 `queueInLoop` 后写 `eventfd` 唤醒目标 loop。

## 5. RPC 治理能力

生产 RPC 不只是网络收发，还要有：

1. **超时和取消**：每次调用必须有 deadline，超时后释放未完成请求。
2. **重试和幂等**：只对幂等请求做有限重试，避免把故障放大。
3. **限流和熔断**：保护下游服务和自身线程池。
4. **负载均衡**：随机、轮询、一致性哈希、最小连接、P2C 等。
5. **服务发现**：通过 Nacos、Consul、Zookeeper、etcd 或 Kubernetes Service 获取实例。
6. **可观测性**：日志、指标、trace、错误码、请求大小和慢调用统计。
7. **背压**：输出队列过长、worker 队列堆积或下游超时时要拒绝或降级。

## 6. 为什么分布式 RPC 常用自定义协议而不是直接 HTTP

这里的“自定义协议”通常不是重新发明 TCP，而是在 TCP 或 QUIC 之上定义自己的消息帧、元信息和序列化格式。是否不用 HTTP，要看调用场景。

使用自定义二进制协议的原因：

1. **帧格式更紧凑**：固定 header + Protobuf body 可以减少 HTTP 文本头、通用解析和字符串字段开销。
2. **请求匹配更直接**：头部带 `request_id`，一条连接上可以做异步并发调用和乱序响应。
3. **治理元信息可控**：deadline、trace id、路由 key、压缩标记、幂等 key、鉴权信息可以固定编码，避免每次解析大量 header。
4. **连接和背压语义更贴业务**：可以按连接维护 pending 表、输出队列、流控窗口、心跳和熔断状态。
5. **兼容内部高性能场景**：内网服务间调用通常不需要浏览器、中间代理和缓存语义，二进制协议更容易做低延迟优化。

但不能把 HTTP 一概否定：

1. gRPC 本身就基于 HTTP/2，保留了 HTTP/2 多路复用、流控、TLS、代理和生态能力。
2. 面向开放平台、浏览器、第三方集成时，HTTP/REST/OpenAPI 的可调试性和兼容性更重要。
3. 自定义协议要自己补抓包工具、协议文档、版本兼容、网关转发、鉴权、TLS、限流和可观测性。

真实工程常见折中是“内部自定义固定 header + Protobuf body”，或者直接使用 gRPC/Thrift/Dubbo 这类成熟框架。回答时要说清楚：选择自定义协议是为了内部高频调用的性能和控制力，不是因为 HTTP 不能做 RPC。

## 7. RPC 项目瓶颈怎么定位

如果面试官问“RPC 项目目前瓶颈在哪”，不要只说“网络 I/O”。RPC 链路瓶颈可能出现在多个位置：

1. **连接层**：连接数、fd 上限、accept 队列、TLS 握手、连接复用不足。
2. **I/O 线程**：event loop 被阻塞、单线程 CPU 打满、跨线程唤醒过多。
3. **编解码**：Protobuf/JSON 序列化、压缩、拷贝、大包拆包消耗 CPU。
4. **业务线程池**：worker 队列堆积、慢请求占满线程、线程数过多导致上下文切换。
5. **下游依赖**：数据库、Redis、其他 RPC 超时导致调用链拖长。
6. **锁和共享状态**：pending map、连接输出队列、全局路由表、日志锁竞争。
7. **网络路径**：丢包、重传、P99 RTT、带宽或 PPS 瓶颈。

定位方法：

1. 指标先分层：入站 QPS、P50/P99、错误率、超时率、连接数、pending 数、队列长度。
2. 单独压测 echo/空 handler，剥离业务耗时，得到网络框架上限。
3. 压测编解码和业务 handler，分别看 CPU 火焰图、内存分配和锁竞争。
4. 对慢请求打 trace，区分排队时间、编解码时间、业务执行时间和下游等待时间。
5. 优化只改一个变量，再用同样流量模型复测。

面试里可以这样说：我会先用 echo RPC 测网络框架基线，再逐层加 Protobuf、业务逻辑和真实下游，观察 QPS、P99、CPU、队列和 pending 数。如果 echo 很高但真实接口低，瓶颈多半在业务或下游；如果 echo 自身就低，再看 event loop、编解码、锁和网络参数。

## 8. 面试回答模板

如果让我设计 RPC 网络通信服务，我会采用多 Reactor 模型：主线程负责 accept，多个 I/O 线程各自维护 epoll 和连接状态，业务逻辑丢给 worker pool，响应再投递回对应 I/O 线程发送。协议上先定义 length-based frame 解决粘包拆包，头部带 version、request_id、codec 和 body_length，body 可以选 Protobuf 或 JSON。JSON-RPC 适合调试和低复杂度内部工具，gRPC/Thrift 更适合跨语言、强类型和生产治理场景。生产环境还必须补超时、重试、服务发现、负载均衡、限流熔断、trace 和背压。
