# Thrift 框架

Thrift 是 Apache 开源的跨语言 RPC 框架，最早来自 Facebook。它通过 IDL 定义服务接口和数据结构，再生成多种语言的客户端、服务端代码，让不同语言的服务可以用统一协议通信。

## 1. 核心组成

Thrift 一次调用可以拆成四层：

| 层次 | 作用 | 常见实现 |
| --- | --- | --- |
| IDL | 定义 struct、service、exception、enum | `.thrift` 文件 |
| Protocol | 序列化格式 | Binary、Compact、JSON |
| Transport | 字节传输抽象 | Socket、Framed、HTTP |
| Server | 服务端并发模型 | Simple、ThreadPool、Nonblocking、THsHa |

示例 IDL：

```thrift
namespace cpp user

struct User {
  1: i64 id
  2: string name
}

service UserService {
  User getUser(1: i64 id)
}
```

生成代码后，客户端像调用本地方法一样调用 `getUser`，Thrift 负责参数编码、网络传输、服务端分发和结果解码。

## 2. Protocol 和 Transport

Protocol 决定“数据怎么编码”：

1. **TBinaryProtocol**：二进制编码，通用、性能较好。
2. **TCompactProtocol**：更紧凑，适合带宽敏感场景，但编解码略复杂。
3. **TJSONProtocol**：可读性好，常用于调试，不适合高性能主链路。

Transport 决定“字节怎么传”：

1. **TSocket**：基于 TCP socket。
2. **TFramedTransport**：每个消息前带长度，常用于非阻塞服务端，能解决消息边界。
3. **TBufferedTransport**：缓冲读写，减少系统调用。
4. **THttpTransport**：走 HTTP 传输，便于穿过部分网关。

## 3. 服务端模型

常见服务端：

1. **TSimpleServer**：单线程串行处理，适合调试。
2. **TThreadPoolServer**：线程池处理请求，适合阻塞业务逻辑。
3. **TNonblockingServer**：非阻塞 I/O，适合高并发连接。
4. **THsHaServer**：Half-Sync/Half-Async，I/O 线程接收请求，worker 线程处理业务。

工程选型时要结合业务：如果业务处理会访问数据库、Redis、下游 RPC，线程池模型更直接；如果连接数很多且单次处理很轻，可以考虑非阻塞模型。

## 4. Thrift 和 gRPC 对比

| 对比项 | Thrift | gRPC |
| --- | --- | --- |
| IDL | Thrift IDL | Protobuf |
| 传输 | TCP、HTTP 等多种组合 | 主要基于 HTTP/2 |
| 序列化 | Binary、Compact、JSON 等 | Protobuf 为主 |
| 流式能力 | 原生较弱，依赖实现 | 原生支持 unary/server/client/bidi streaming |
| 生态 | 老牌、多语言、轻量灵活 | 云原生生态更强，和 HTTP/2、LB、观测集成好 |

Thrift 的优势是跨语言、协议/传输可组合、性能较好；不足是生态治理、流式能力、服务治理能力通常不如现代 gRPC 体系完整。

## 5. 易错点

1. IDL 字段编号是协议兼容的关键，不能随意复用或修改语义。
2. 新增字段要保持可选或提供默认值，避免老客户端解析失败。
3. 非阻塞服务端通常需要 framed transport，否则不知道一条完整消息边界。
4. RPC 超时、重试、幂等、熔断、限流不是 Thrift 自动全部解决的，需要业务框架或治理层补齐。
5. 二进制协议可读性差，排查问题时要配合日志、trace id 和抓包解码工具。

## 6. 面试回答模板

Thrift 是一个跨语言 RPC 框架，用 `.thrift` IDL 定义结构体和服务，再生成各语言的客户端和服务端 stub。它的核心分层是 IDL、Protocol、Transport 和 Server：Protocol 负责序列化，比如 Binary、Compact；Transport 负责传输，比如 Socket、Framed；Server 决定并发模型，比如线程池或非阻塞。相比 gRPC，Thrift 更灵活、老系统使用多，但 gRPC 基于 HTTP/2 和 Protobuf，流式和云原生生态更完整。
