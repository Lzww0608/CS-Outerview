# gRPC 原理

gRPC 是一个基于 HTTP/2 和 Protocol Buffers 的高性能 RPC 框架。它让调用方通过本地生成的 Stub 调用远端服务，底层负责序列化、连接管理、流式传输、超时、状态码和负载均衡等细节。

## 核心组成

1. **IDL / Protobuf**：用 `.proto` 文件定义服务、方法、请求和响应类型，再通过 `protoc` 生成多语言代码。
2. **Stub**：客户端 Stub 把本地方法调用转换成 RPC 请求；服务端 Stub 把网络请求分发到业务实现。
3. **HTTP/2**：提供长连接、多路复用、Header Compression、Stream、流控等能力。
4. **Channel**：客户端到服务端的一组连接抽象，负责连接复用、状态管理、负载均衡和 name resolver。
5. **Interceptor**：拦截请求和响应，可用于鉴权、日志、链路追踪、重试、限流等横切逻辑。

## 一次调用流程

1. 客户端调用生成的 Stub 方法。
2. Stub 把请求对象按 Protobuf 编码成二进制消息。
3. gRPC 把方法名、metadata、deadline 等信息封装成 HTTP/2 headers，把请求体放入 DATA frame。
4. HTTP/2 在同一 TCP/TLS 连接上为每个 RPC 创建独立 stream，可以并发传输多个 RPC。
5. 服务端收到 headers 和 DATA frame 后，根据 `:path` 中的服务名和方法名找到 handler。
6. 服务端反序列化请求，执行业务逻辑，返回 Protobuf 响应和 gRPC status。
7. 客户端收到响应后反序列化为本地对象，Stub 把结果返回给调用方。

## 四种调用模式

| 模式 | 含义 | 场景 |
| --- | --- | --- |
| Unary RPC | 一个请求对应一个响应 | 普通查询、创建订单、配置读取 |
| Server Streaming | 一个请求对应服务端多个响应 | 日志订阅、配置推送、模型流式输出 |
| Client Streaming | 客户端多个请求对应一个响应 | 批量上传、分片统计 |
| Bidirectional Streaming | 双方都可以持续发送消息 | 实时协作、语音视频控制通道、长连接网关 |

示例：

```protobuf
syntax = "proto3";

service UserService {
  rpc GetUser(GetUserRequest) returns (GetUserResponse);
  rpc WatchUser(GetUserRequest) returns (stream GetUserResponse);
}

message GetUserRequest {
  int64 id = 1;
}

message GetUserResponse {
  int64 id = 1;
  string name = 2;
}
```

## 为什么 gRPC 性能较好

1. Protobuf 是二进制编码，字段使用编号而不是重复字段名，体积小、解析快。
2. HTTP/2 多路复用减少连接数量，避免 HTTP/1.1 队头阻塞在应用层连接池里放大。
3. 长连接复用降低频繁建连和 TLS 握手成本。
4. Header 压缩减少 metadata 重复传输。
5. 支持流式 RPC，适合大结果集、推送和边生产边消费的场景。

## 易错点

1. gRPC 不是“不走 HTTP”，主流实现通常跑在 HTTP/2 之上。
2. HTTP/2 多路复用解决的是一个 TCP 连接上多个 stream 的并发传输，但 TCP 层丢包仍可能造成传输层队头阻塞。
3. Protobuf 字段编号不能随意修改或复用，否则会破坏兼容性。
4. gRPC 的 deadline 要主动设置，否则下游慢调用可能拖垮线程池或连接池。
5. RPC 成功到达服务端不代表业务一定幂等，重试必须结合请求 ID、幂等键或业务去重。
6. 浏览器原生 gRPC 支持受限，面向浏览器通常使用 gRPC-Web、REST 或网关转码。

## 真实场景

1. 微服务内部调用常用 gRPC 表达强类型服务契约，配合服务发现和客户端负载均衡。
2. 配置中心可以用 server streaming 或双向流把配置变更推送给客户端。
3. 大文件、日志、模型推理输出适合使用 streaming，减少一次性大包和等待时间。
4. 统一网关可以把外部 HTTP/JSON 转为内部 gRPC，兼顾外部易用性和内部强类型高性能。

## 面试回答模板

gRPC 是基于 HTTP/2 和 Protobuf 的 RPC 框架。开发者先用 `.proto` 定义服务契约，再生成客户端和服务端 Stub。调用时客户端 Stub 序列化请求，通过 HTTP/2 stream 发送 metadata 和 DATA frame；服务端按服务名、方法名分发到业务 handler，执行后把 Protobuf 响应和 gRPC status 返回。它的优势是强类型、跨语言、二进制编码、高效连接复用和流式调用；工程上要注意 deadline、重试幂等、字段兼容、服务发现、负载均衡和链路追踪。
