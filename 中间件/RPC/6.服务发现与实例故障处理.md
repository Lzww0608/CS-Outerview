# 6. 服务发现与实例故障处理

服务发现解决的是“调用方如何找到可用服务实例”的问题。微服务实例会动态扩缩容、重启、迁移 IP，如果调用方把地址写死，系统很快会变得不可维护。

## 1. 基本实现思路

常见角色：

1. **服务提供方**：启动后把 `service_name、ip、port、metadata、weight` 注册到注册中心。
2. **注册中心**：保存服务实例列表，并通过租约、心跳或健康检查判断实例是否可用。
3. **调用方**：根据服务名获取实例列表，在本地缓存，然后通过负载均衡选择一个实例发起 RPC。

典型流程：

```text
provider 启动 -> 注册实例 -> 周期性续约/心跳
consumer 启动 -> 订阅服务 -> 本地缓存实例列表
consumer 调用 -> 本地负载均衡 -> RPC 请求
provider 下线 -> 注销或租约过期 -> 注册中心通知 consumer 更新缓存
```

调用方通常不会每次请求都先查注册中心，否则注册中心会成为高频链路瓶颈。更常见做法是启动或缓存失效时拉取一次，然后通过 watch、长轮询或推送机制增量更新本地实例列表。

## 2. 实例突然 crash 会发生什么

如果被调服务突然崩溃，注册中心不一定能立即知道。它通常要等心跳超时、健康检查失败或 TCP 连接断开后才摘除实例。

已经拿到旧 IP 的客户端可能遇到：

1. **连接失败**：新建连接时收到 `ECONNREFUSED`、超时或路由不可达。
2. **已有连接断开**：读写返回错误，例如连接 reset。
3. **请求超时**：实例进程卡死、网络黑洞或负载过高时，调用方只能等 deadline 超时。
4. **少量失败窗口**：注册中心摘除实例和客户端缓存刷新之间存在传播延迟。

调用方应做：

1. 为每次 RPC 设置超时/deadline，避免无限等待。
2. 只对幂等请求做有限次数重试，配合退避和抖动。
3. 连续失败时临时熔断该实例，把它从本地可选列表里摘除一段时间。
4. 上报错误率、超时率和实例维度指标，辅助注册中心或治理层判断。

## 3. 被调服务如何降低影响

服务端无法完全避免 crash，但可以减少“已经不可用还继续接流量”的窗口：

1. **优雅下线**：先向注册中心注销或把 readiness 置为 false，再等待连接 drain，最后退出进程。
2. **健康检查分层**：liveness 判断进程是否该重启，readiness 判断是否可接新流量。
3. **心跳租约**：注册信息带 TTL，续约失败会被自动删除。
4. **连接保活和最大连接年龄**：避免客户端长期持有失效连接。
5. **过载保护**：队列满、线程池满或下游异常时快速失败，而不是拖到全局超时。
6. **灰度和滚动发布**：批量下线前先摘流量，避免所有客户端同时打到坏实例。

## 4. 常见注册中心和模式

| 模式 | 说明 | 代表组件 |
| --- | --- | --- |
| 客户端发现 | 客户端直接订阅实例列表并负载均衡 | etcd、Consul、Nacos、Zookeeper |
| 服务端发现 | 客户端请求负载均衡器，由 LB 选择实例 | Nginx、Envoy、Kubernetes Service |
| DNS 发现 | 服务名解析为多个地址 | CoreDNS、K8s DNS |
| Service Mesh | Sidecar 负责发现、负载均衡和治理 | Istio、Linkerd、Envoy |

客户端发现灵活，但 SDK 要实现缓存、订阅、负载均衡和故障摘除。服务端发现对业务更透明，但 LB 层要高可用，且长连接场景要考虑连接重建和负载再均衡。

### Consul 服务发现原理

Consul 可以同时提供服务注册发现、健康检查、KV 配置和多数据中心能力。典型部署里，每台机器运行一个 Consul Agent，服务把自身实例注册到本机 Agent；Agent 负责执行 TCP、HTTP、脚本或 TTL 健康检查，并把结果同步给 Consul Server 集群。Server 节点之间通过 Raft 保证元数据一致性，节点成员状态通常通过 gossip 协议传播。

调用方获取实例常见有两种方式：

1. **HTTP API / blocking query**：客户端传入上次的 index，Consul 在实例列表变化前阻塞返回，适合 SDK 增量更新本地缓存。
2. **DNS 查询**：通过服务名解析得到健康实例地址，接入简单，但负载均衡、权重、元数据过滤能力弱一些。

真实场景中，Consul 不应该在每次 RPC 前被同步查询；正确做法是客户端维护本地缓存，收到变更后更新实例列表。否则注册中心会变成高频链路瓶颈，也会把注册中心抖动放大成业务故障。

### NodeBalance 与客户端负载均衡

NodeBalance 可以理解为“拿到一组服务节点后，在本地选择一个节点”的策略层。常见策略包括随机、轮询、加权轮询、最少连接、P2C（Power of Two Choices）、一致性哈希和按地域/标签优先。

选择策略要结合场景：

1. **无状态 RPC**：随机、轮询或 P2C 足够简单，P2C 在节点负载不均时通常比纯随机更稳。
2. **有会话或缓存亲和**：用一致性哈希或按用户 ID 分片，减少缓存抖动。
3. **节点能力不同**：用权重表达机器规格、机房距离或灰度比例。
4. **故障处理**：本地要过滤不健康节点，对连续失败节点做短暂摘除，避免每次都打到坏节点。

易错点：负载均衡不是“平均分配请求数”这么简单。长连接、慢请求、节点异构、机房延迟和重试都会让请求数平均但负载不平均，因此生产系统通常还要结合连接数、延迟、错误率和熔断状态做动态选择。

### 注册中心不可用时如何使用本地缓存

注册中心不可用时，调用方不能因为无法刷新实例列表就立刻让业务全部失败。合理做法是把本地缓存当成短时间降级数据源，但要控制陈旧数据风险。

基本策略：

1. **保留最后一次成功快照**：客户端订阅服务时把实例列表、版本号、更新时间、metadata 和权重保存在内存中，必要时也可以落本地文件用于进程重启后的冷启动兜底。
2. **区分软 TTL 和硬 TTL**：软 TTL 过期后优先尝试刷新，刷新失败仍可短时间使用旧快照；硬 TTL 过期后说明数据太旧，强一致业务应 fail closed，普通读业务可降级返回。
3. **本地健康状态覆盖注册中心状态**：即使缓存里有某个实例，如果本地连续连接失败、超时或熔断，也要临时摘除，过一段时间半开探测。
4. **按业务约束过滤实例**：选择前先过滤 region、az、版本、灰度标签、协议版本、租户隔离等 metadata，不能为了可用性把流量打到不兼容实例。
5. **负载均衡要避开坏节点**：在剩余健康实例里用 P2C、加权随机、轮询或一致性哈希选择；长连接场景要考虑连接池里旧连接是否还指向已摘除实例。
6. **重试要有边界**：只对幂等请求做有限重试，并避免同一请求重试到同一个坏实例；非幂等写请求要依赖请求 ID、幂等表或业务状态机。

一个常见选择流程：

```text
读取本地实例快照
  -> 过滤硬 TTL 过期、标签不匹配、被本地熔断的实例
  -> 优先同机房/同可用区
  -> 按权重或 P2C 选择实例
  -> 调用失败时记录实例维度错误
  -> 达到阈值后本地摘除并半开探测
```

“正确性”主要来自三个约束：第一，不能把请求发给协议、版本、租户或灰度规则不匹配的实例；第二，不能对非幂等请求无脑重试；第三，不能无限期使用陈旧缓存。注册中心恢复后，客户端应通过 watch、长轮询或全量拉取刷新快照，并用版本号避免旧通知覆盖新数据。

## 5. 易错点

1. 服务发现不是每次调用都请求注册中心，调用方通常维护本地缓存。
2. 注册中心摘除实例不是瞬时的，客户端必须能承受短暂失败。
3. 重试不能无脑做，非幂等写请求重试可能造成重复扣款、重复下单。
4. 健康检查只检查端口不够，还要检查事件循环、线程池、依赖和业务探针。
5. 连接池里的旧连接也要治理，否则实例已摘除但旧连接仍可能被使用。
6. 注册中心不可用时可以短时间使用本地缓存，但不能忽略 TTL、metadata 兼容性、本地熔断和幂等边界。

## 6. 面试回答模板

服务发现一般是服务启动时向注册中心注册实例，调用方按服务名订阅实例列表并缓存在本地，请求时从本地列表做负载均衡，不会每次都先查注册中心。实例 crash 后，注册中心通常要等心跳或健康检查超时才摘除，所以已经拿到 IP 的客户端会出现连接失败、读写错误或请求超时。调用方要设置 deadline、有限重试、熔断和本地摘除；服务端要做优雅下线、readiness、心跳租约和连接 drain。注册中心不可用时，客户端可以短时间使用最后一次成功的本地快照，但要有 TTL、metadata 过滤、本地健康剔除、半开探测和幂等重试边界，不能无限期相信陈旧实例列表。这个失败窗口不能完全消除，只能通过健康检查、治理策略和观测指标把影响控制住。
