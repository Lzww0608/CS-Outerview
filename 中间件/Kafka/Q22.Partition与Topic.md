# Q22.Partition与Topic

Partition和Topic是Kafka中的两个核心概念，它们之间存在一定的关系。

首先，Topic是消息的逻辑分类，可以认为它是一个带类别的消息队列。在Kafka中，每一条消息都必须被写入到一个Topic中。Topic是消息的逻辑单位，可以用来区分不同的业务逻辑或者消息类型。

其次，Partition是Topic的物理单元，它是消息在磁盘上的物理存储单元。每个Partition对应一个文件夹，该文件夹下存储这个Partition的所有消息和索引文件。每个Partition中有多个大小相等的segment数据文件，每个segment的大小是相同的，但每个消息的大小可能不同，因此segment数据文件中消息的数量可能不相等。

在Kafka中，每个Topic都可以设置多个Partition，每个Partition都是一个有序的、不可变的消息序列。Partition上的每条消息都会被分配一个唯一的序列号，该序列号被称为位移（offset）。该位移是从0开始顺序递增的整数，位移信息可以定位到Partition下的一条消息。Kafka中的一条消息其实就是一个<topic,partition,offset>三元组(tuple)，通过该元组可以在kafka集群中找到唯一对应的那条消息。

因此，Partition和Topic之间存在一定的关系。Topic是消息的逻辑分类，而Partition是Topic的物理存储单元，用于存储消息在磁盘上的物理位置和索引信息。在Kafka中，每个Topic都可以包含多个Partition，每个Partition都是一个有序的消息序列。

## 项目里 Topic 和 Partition 怎么设计

面试追问“你们有几个 topic、几个 partition”时，不要只报数字，要说明拆分依据。

Topic 通常按业务语义、数据格式和消费链路拆分：

1. 不同日志类型可以拆不同 topic，例如 `access_log`、`app_log`、`trace_log`、`audit_log`。
2. 数据格式、保留时间、权限等级差异很大时，适合拆 topic。
3. 如果多个下游都要消费同一类数据，不需要为每个下游单独建 topic，可以用不同 consumer group。
4. 如果只是字段稍有不同，但生命周期、吞吐和下游相同，可以统一 topic，避免 topic 过多增加运维成本。

Partition 数量通常由吞吐、并行度和顺序性决定：

1. 分区数至少要支撑目标消费并行度，同一个 consumer group 内，一个 partition 同时只会分配给一个消费者实例。
2. 单 partition 内有序；如果要求某个 key 内有序，应按这个 key 分区，例如 `user_id`、`order_id`、`trace_id`。
3. 分区数过少会限制吞吐，过多会增加 broker 文件句柄、元数据、leader 选举和 rebalance 成本。
4. 分区数后续可以增加，但增加后 key 到 partition 的映射可能变化，顺序性和数据分布要重新评估。

日志项目里可以这样回答：

```text
我们按日志语义拆 topic，高吞吐明细日志 topic 配更多 partition，低吞吐审计或配置类 topic 配更少 partition。partition 数量主要按峰值写入量和下游 ClickHouse/流处理消费并行度估算，同时保证同一个 trace_id 或 user_id 的数据尽量进入同一分区，方便局部有序和问题追踪。
```
