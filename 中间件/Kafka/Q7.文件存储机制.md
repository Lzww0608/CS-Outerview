# Q7.文件存储机制

Kafka的文件存储机制是基于日志的，它将所有的消息都保存在一个或多个主题（topic）的日志文件中。每个主题都由一个或多个分区（partition）组成，每个分区都是一个有序的、不可修改的消息日志。消息按照它们的写入顺序追加到分区中，并分配一个唯一的偏移量（offset）来标识它们在分区中的位置。

Kafka使用了两个文件来存储消息：**消息文件**和**索引文件**。索引文件以`.index`后缀结尾，存储当前数据文件的索引；数据文件以`.log`后缀结尾，存储当前索引文件消息的偏移量和物理位置信息。这种分离的存储方式使得Kafka可以高效地执行消息的写入和读取操作。

Kafka的文件存储机制还包括了消息的压缩和清理策略。它支持Gzip、Snappy和LZ4三种压缩算法，可以将消息在写入到日志文件中之前进行压缩，从而减少磁盘空间的占用。同时，Kafka也支持基于时间或日志大小的消息清理策略，可以根据设定的阈值自动删除过期或过大的消息，以释放存储空间。

此外，Kafka的文件存储机制还支持多副本机制，通过副本机制可以实现高可用性和数据冗余。每个分区都可以配置多个副本（replica），副本分布在不同的Broker上，可以提高数据的可靠性和可用性。当某个Broker宕机时，其他Broker上的副本可以自动接管它的工作，保证数据不会丢失。

Kafka的文件存储机制还支持批量写入和读取，可以将多个消息一次性写入日志文件中，或一次性读取多个消息，从而提高数据的处理效率。

## 持久化、删除与消费进度

Kafka 更像一个分布式提交日志，而不是“消费一条就删除一条”的传统队列。消息写入分区后会追加到日志段文件中，消费者按 offset 拉取；消费是否完成不会立即影响消息文件是否删除。

### 1. 如何持久化

Kafka 的持久化路径可以概括为：

1. Producer 把消息发送到 Topic 的某个 Partition。
2. Broker Leader 将消息追加写入该 Partition 的日志文件，写入通常先进入操作系统 Page Cache。
3. Partition 日志按 segment 切分，每个 segment 配套 `.log`、`.index`、`.timeindex` 等文件。
4. 副本机制把 Leader 的数据同步到 Follower，`acks=all` 和 `min.insync.replicas` 可以提高写入可靠性。
5. 操作系统和 Kafka 刷盘策略共同决定数据何时真正落盘。

顺序追加、Page Cache、批量写入和零拷贝是 Kafka 高吞吐的重要原因。

### 2. 消费后会不会删除消息

Kafka 默认不会因为某个消费者已经消费就立即删除消息。消息删除主要由保留策略控制：

1. `log.retention.ms/hours`：按时间保留。
2. `log.retention.bytes`：按分区日志大小保留。
3. `log.segment.bytes`：控制日志段滚动，只有关闭的旧 segment 才方便整体清理。
4. compact 类型 Topic 可以按 key 做日志压缩，保留每个 key 的较新版本。

这样设计的好处是同一份日志可以被多个 Consumer Group 独立消费，也可以重置 offset 回放历史数据。

### 3. 如何维护消费进度

Kafka 用 offset 表示消费者在某个 Partition 上的消费位置。每个 Consumer Group 对每个 Partition 维护自己的已提交 offset，通常保存在内部 Topic `__consumer_offsets` 中。

常见提交方式：

1. **自动提交**：客户端周期性提交 offset，简单但可能出现“业务没处理完 offset 已提交”的丢消息风险。
2. **手动同步提交**：业务处理成功后提交，语义清晰，但提交路径会影响吞吐。
3. **手动异步提交**：吞吐更高，但要处理提交失败和乱序回调。
4. **事务消费处理**：在需要端到端一致性时，结合幂等生产者、事务和业务幂等设计。

实践中通常遵循：

```text
拉取消息 -> 处理业务成功 -> 提交 offset
```

如果先提交 offset 再处理业务，消费者宕机后这条消息可能不会重放；如果处理成功但提交失败，消息可能重复消费。因此消费者侧必须设计幂等。

## 面试回答模板

Kafka 会把消息追加写入 Partition 的日志文件，并通过 segment、索引文件、Page Cache、批量顺序写和副本同步实现高吞吐持久化。消息被消费后不会立刻删除，而是按保留时间、保留大小或日志压缩策略清理。消费进度由 Consumer Group 维护 offset，通常提交到 `__consumer_offsets`；为了避免丢消息，应在业务处理成功后再提交 offset，同时用幂等机制处理重复消费。
