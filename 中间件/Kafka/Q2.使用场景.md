# Q2.使用场景

1. **实时数据流处理**：Kafka 适用于处理大规模的实时数据流，例如用户行为数据、传感器数据等。我可以使用 Kafka 的流处理 API 来构建实时数据管道和流应用，实现数据的实时分析和处理。
2. **异步通信**：Kafka 可以作为异步通信工具，用于解耦和削峰填谷。我可以将一些不那么紧急的请求或者非实时的请求发送到 Kafka，然后由 Kafka 异步地处理这些请求，这样可以避免对系统造成过大的压力。
3. **消息队列**：Kafka 可以作为消息队列使用，用于在分布式系统中实现进程间或跨系统通信。我可以将消息发送到 Kafka，然后由其他系统从 Kafka 中消费这些消息，实现不同系统之间的数据共享和交互。
4. **日志收集**：Kafka 适用于日志收集，例如系统日志、用户行为日志等。我可以将日志数据发送到 Kafka，然后由 Kafka 存储和转发这些日志数据，以便于集中管理和分析。
5. **事件驱动型微服务**：Kafka 可以作为事件驱动型微服务之间的通信桥梁。我可以将事件数据发送到 Kafka，然后由其他微服务从 Kafka 中消费这些事件数据，实现微服务之间的解耦和通信。

## 项目里怎么回答 Kafka 使用场景

项目面试里不要只说“用 Kafka 做异步”，最好说明它在链路中的位置、消息内容、消费方、可靠性要求和失败处理。

常见回答方式：

1. **异步解耦**：主接口只完成核心事务，例如订单创建、库存扣减、状态落库；非核心的通知、积分、埋点、风控后处理通过 Kafka 事件异步消费。
2. **削峰填谷**：活动高峰时先把事件写入 Kafka，由消费者按处理能力慢慢消费，避免下游数据库、搜索、报表系统被瞬时流量打垮。
3. **数据同步**：业务库变更后，通过 Kafka 投递给 ES、ClickHouse、数仓或缓存失效服务，形成最终一致的数据管道。
4. **日志和行为流**：用户点击、曝光、支付状态、物流轨迹等事件进入 Kafka，供实时计算、离线分析、监控告警和推荐模型使用。
5. **跨服务事件通知**：一个服务只发布事实事件，例如 `OrderPaid`、`PackageShipped`，订阅方按自己的业务处理，减少服务之间的同步 RPC 依赖。

示例：

```text
订单服务提交 MySQL 事务
-> 写 outbox/order_event
-> 投递 Kafka topic: order_event
-> 消费者组 A：更新搜索索引
-> 消费者组 B：发送通知
-> 消费者组 C：写入数仓
```

要强调边界：Kafka 适合高吞吐事件流和异步最终一致，不适合要求同步强一致返回结果的核心交易判断。余额扣减、库存条件更新、订单状态机这类最终正确性仍要落在数据库事务、唯一约束、幂等和对账上。
