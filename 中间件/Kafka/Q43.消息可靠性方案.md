# Q43.消息可靠性方案

Kafka 的可靠性要分三段看：生产者是否成功写入 Broker，Broker 是否可靠保存并复制，消费者是否在业务处理成功后再提交 offset。只说“Kafka 有副本”不够，因为消息可能丢在发送前、Broker 故障时，也可能丢在消费端提前提交 offset 后。

## 1. 生产者侧

生产者侧目标是确认消息真的被 Broker 接收，并避免重试导致乱序或重复扩大。

1. **acks 配置**：
   - `acks=0`：不等待 Broker 确认，吞吐高但可能丢。
   - `acks=1`：leader 写入成功就返回，leader 宕机且 follower 未同步时可能丢。
   - `acks=all/-1`：leader 等 ISR 中副本确认后返回，可靠性最高。
2. **重试和回调**：发送失败要通过 callback 感知，结合 `retries`、`delivery.timeout.ms` 做有界重试。
3. **幂等生产者**：开启 `enable.idempotence=true`，通过 producer id 和 sequence number 避免重试写入同一分区时产生重复消息。
4. **顺序风险控制**：如果强依赖单分区顺序，要关注 `max.in.flight.requests.per.connection`，旧版本或未开启幂等时过大可能导致重试乱序。
5. **本地事务边界**：如果消息由数据库变更触发，建议用 outbox 或事务消息方案，避免“数据库提交成功但消息没发出”。

## 2. Broker 侧

Broker 侧目标是消息写入后即使单个 broker 故障也能恢复。

1. **日志持久化**：Kafka 以 partition log 追加写磁盘，利用 Page Cache 和顺序写提高吞吐。
2. **副本机制**：每个 partition 有 leader 和 follower，读写通常走 leader，follower 从 leader 拉取复制。
3. **ISR 机制**：ISR 表示和 leader 保持同步的副本集合，`acks=all` 依赖 ISR 确认。
4. **最小同步副本数**：`min.insync.replicas` 要和 `acks=all` 配合。例如副本因子为 3 时常设为 2，避免只剩 leader 时仍返回写成功。
5. **禁止不干净选举**：`unclean.leader.election.enable=false` 可以降低已确认消息丢失风险，代价是可用性可能下降。

## 3. 消费者侧

消费者侧目标是业务处理成功后再推进消费进度。

1. **手动提交 offset**：关闭自动提交，业务处理成功后再 `commitSync` 或 `commitAsync`。
2. **先处理后提交**：如果先提交 offset 再处理业务，消费者宕机会导致这条消息逻辑丢失。
3. **幂等消费**：Kafka 常见语义是至少一次，重复消费要靠业务幂等兜底，例如唯一索引、去重表、状态机条件更新。
4. **失败重试和死信**：毒丸消息不能无限阻塞同一分区，可以设置重试次数、延迟重试 topic 和 DLQ。
5. **消费位点监控**：监控 consumer lag、提交失败、rebalance 次数和处理耗时，避免堆积后恢复困难。

## 4. 易错点

1. `acks=all` 不等于绝对不丢，还要配合足够副本、`min.insync.replicas` 和 ISR 健康。
2. Kafka 可靠性通常换吞吐和延迟，强一致链路不能无脑把所有配置拉满。
3. 手动提交 offset 只能避免“处理前提交”，不能避免业务自身失败或重复执行。
4. 幂等生产者解决的是单生产者单分区重试重复，不等于全链路 exactly once。
5. Kafka 事务可以把“消费一批消息 + 生产结果消息 + 提交 offset”做成原子，但不能自动把外部 MySQL 事务也纳入同一个事务。

## 5. 面试回答模板

Kafka 可靠性我会分生产者、Broker、消费者三段回答。生产者侧用 `acks=all`、有界重试、发送回调和幂等生产者，必要时用 outbox 保证数据库变更和消息发送不丢。Broker 侧依靠 partition log 持久化、副本、ISR、`min.insync.replicas` 和禁止不干净选举降低 leader 故障丢数据风险。消费者侧关闭自动提交，业务处理成功后再提交 offset，并用唯一键、幂等表或状态机条件更新应对重复消费。最后还要有重试、死信、lag 监控和对账，因为 Kafka 更常提供至少一次语义，全链路正确性仍要业务兜底。
