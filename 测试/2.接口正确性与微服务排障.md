# 接口正确性与微服务排障

面试里问“微服务中用户调用接口错误怎么排查”和“怎么确保自己写的接口正确”，本质是在考察工程闭环：需求理解、接口契约、测试、灰度、可观测性和故障定位。

## 1. 拿到需求怎么完成

一个需求从理解到上线，建议按以下步骤推进：

1. **明确业务目标**：确认要解决什么问题、影响哪些用户、成功标准是什么。
2. **拆分边界**：确认涉及哪些服务、接口、表、缓存、消息和外部依赖。
3. **定义接口契约**：请求参数、响应结构、错误码、幂等语义、超时、权限和兼容策略。
4. **设计数据与状态机**：明确状态流转、并发冲突、回滚补偿和异常分支。
5. **先写测试用例**：覆盖正常、异常、边界、权限、幂等、并发和依赖失败。
6. **实现与自测**：本地单测、接口测试、联调、压测或回归。
7. **灰度上线**：小流量验证指标，异常可回滚。
8. **沉淀文档和监控**：记录接口契约、变更点、告警和排障手册。

开发完成后更应该看重的是：业务目标是否达成、线上风险是否可控、代码是否可维护、接口是否兼容、问题是否可观测，而不是只看“功能能跑通”。

## 2. 如何确保接口正确

接口正确性可以从多个层次保证：

### 2.1 契约正确

1. 请求字段必填、类型、范围、默认值明确。
2. 响应字段、错误码、HTTP/gRPC 状态码稳定。
3. 接口版本兼容，新增字段不破坏老客户端。
4. 幂等 key、请求唯一号或业务单号明确。
5. 权限和数据归属校验写进契约，而不是只依赖前端。

### 2.2 单元测试

单元测试关注局部逻辑，应该尽量不依赖真实数据库、Redis 和远程服务。

适合单测的内容：

1. 参数校验函数。
2. 状态机流转。
3. 权限判断。
4. 金额、库存、冷却时间等核心计算。
5. 错误码映射和边界条件。

示例：

```go
func TestValidateCreateOrder(t *testing.T) {
    cases := []struct {
        name string
        req  CreateOrderReq
        want error
    }{
        {"empty user", CreateOrderReq{UserID: 0, SkuID: 1}, ErrInvalidUser},
        {"empty sku", CreateOrderReq{UserID: 1, SkuID: 0}, ErrInvalidSku},
        {"ok", CreateOrderReq{UserID: 1, SkuID: 2}, nil},
    }

    for _, tc := range cases {
        t.Run(tc.name, func(t *testing.T) {
            got := ValidateCreateOrder(tc.req)
            if !errors.Is(got, tc.want) {
                t.Fatalf("got %v, want %v", got, tc.want)
            }
        })
    }
}
```

### 2.3 集成测试和接口测试

1. 使用测试数据库、测试 Redis 或容器环境验证真实依赖。
2. 覆盖接口主流程、异常流程和权限流程。
3. 校验数据库状态、缓存状态、消息投递和下游调用。
4. 对关键接口做回归用例，接入 CI。
5. 对外部服务使用 mock、fake server 或契约测试，避免联调时才发现协议不一致。

### 2.4 并发和异常验证

1. 重复提交：同一个请求重放是否幂等。
2. 并发写入：库存、余额、道具、订单状态是否出现超卖或状态倒退。
3. 超时和重试：调用方超时后服务端是否可能已经成功。
4. 下游失败：是否有补偿、重试、死信和人工处理入口。
5. 灰度回滚：新老版本是否能同时处理同一类请求。

## 3. 用户调用接口错误怎么排查

排查要先按层缩小范围，不要一上来改代码。

### 3.1 确认现象

1. 错误是 4xx、5xx、超时、连接失败，还是业务错误码。
2. 是否所有用户都失败，还是某个用户、地区、版本、灰度流量失败。
3. 是否刚发布、配置变更、依赖变更或流量突增。
4. 获取请求时间、用户 ID、接口名、参数摘要、trace id/request id。

### 3.2 按链路定位

```text
客户端
  -> DNS / LB / 网关
  -> 鉴权 / 限流 / 路由
  -> 业务服务
  -> DB / Redis / MQ / 下游 RPC
```

每一层看不同证据：

1. **网关层**：状态码、限流命中、鉴权失败、路由是否到正确服务。
2. **服务层**：结构化日志、错误堆栈、业务错误码、线程池/协程池/队列堆积。
3. **链路追踪**：哪个 span 耗时高，哪个下游返回错误。
4. **指标**：QPS、错误率、P95/P99、CPU、内存、连接池、DB 慢查询、Redis 命中率。
5. **依赖层**：数据库锁等待、慢 SQL、缓存不可用、MQ 积压、RPC 超时。
6. **网络层**：必要时用 `curl`、`dig`、`ss`、`tcpdump` 验证连通性、握手和重传。

### 3.3 常见根因

1. 参数不兼容：客户端传了老字段或新字段，服务端解析失败。
2. 权限问题：token 过期、用户无权限、租户隔离错误。
3. 灰度问题：部分实例配置、代码版本或路由规则不一致。
4. 数据问题：脏数据、缺数据、缓存与数据库不一致。
5. 依赖问题：DB 慢查询、Redis 超时、下游 RPC 错误。
6. 并发问题：重复请求、锁等待、状态机并发更新。
7. 容量问题：线程池打满、连接池耗尽、限流阈值过低。

## 4. 易错点

1. 只看应用日志，不看网关、trace、指标和依赖状态。
2. 只复现正常参数，不复现用户真实请求。
3. 看到超时就认为服务端没执行，实际可能已经执行成功。
4. 错误码没有分层，导致客户端、网关、业务、下游错误混在一起。
5. 单元测试只测 happy path，没有覆盖异常、边界、幂等和并发。
6. 接口变更没有契约测试，导致老客户端或下游服务被破坏。

## 5. 真实场景

例如用户反馈“创建订单失败”：

1. 先通过 request id 找到网关日志，确认状态码和目标服务实例。
2. 查 trace，发现订单服务调用库存服务超时。
3. 看库存服务指标，发现 P99 升高、DB 慢查询增多。
4. 查慢 SQL，发现新版本少了索引或查询条件不走索引。
5. 临时回滚或降级，再补索引、补压测和回归用例。
6. 最后补告警：库存服务 P99、慢 SQL 数量、超时率和订单失败率联动报警。

## 6. 面试回答模板

微服务接口报错我会先拿到用户、时间、接口、参数摘要和 trace id，确认是 4xx、5xx、超时还是业务错误码。然后按客户端、网关、业务服务、DB/Redis/MQ/RPC 依赖逐层查日志、指标和链路追踪，结合最近发布和配置变更定位影响范围。确保接口正确则要从契约、单元测试、接口测试、集成测试、并发幂等测试、灰度和监控告警几个层次做闭环。开发完成后我更看重业务目标达成、兼容性、可维护性、可观测性和线上风险可控。
