# 24. Harness Engineering 理解

Harness Engineering 可以理解为：给 LLM 应用、Agent、Skill、Prompt 搭建一个**可重复运行、可观测、可评测、可回放的实验和回归环境**。

它解决的问题不是“怎么让模型回答一次看起来更好”，而是：

```text
我如何证明这个 Agent/Prompt/Skill 版本真的比上一个版本更好？
它修复了哪些失败样本？
有没有破坏旧能力？
成本、延迟、安全风险有没有上升？
```

一句话：

```text
Harness = 测试集 + 工具环境 + Runner + Judge + Trace + Report + 回归闭环
```

## 1. 为什么需要 Harness

传统软件可以用单元测试、集成测试、CI 来验证。但 Agent 系统多了几个不稳定因素：

1. 模型输出非确定。
2. 工具调用路径多。
3. 上下文长度和内容会影响结果。
4. 外部工具可能超时、返回空结果或权限不足。
5. 只看最终答案不够，工具选择和中间状态也可能错。
6. Prompt、Skill、模型版本、工具描述一改，行为可能整体变化。

没有 Harness 时，优化经常变成：

```text
改一下 prompt
-> 手动试几个例子
-> 感觉变好了
-> 上线
-> 线上又坏别的 case
```

有 Harness 时，流程变成：

```text
收集样本
-> 固化输入、工具、环境和判定标准
-> 批量运行多个版本
-> 采集最终答案和执行轨迹
-> 自动/人工判分
-> 输出差异报告
-> 决定是否发布
```

## 2. Harness 和普通 Eval 的区别

普通 Eval 往往只评测“输入问题 -> 输出答案”。Harness 更像一个运行时测试平台。

| 对比项 | 普通 Eval | Harness Engineering |
| --- | --- | --- |
| 评测对象 | 最终文本 | 文本、工具调用、状态、成本、安全 |
| 输入 | 问题和标准答案 | 用户请求、上下文、工具环境、权限、历史状态 |
| 环境 | 静态 | 可 mock、可沙箱、可回放 |
| 判定 | 答案对不对 | 是否选对工具、参数、步骤、验证和输出 |
| 产物 | 分数 | trace、diff、badcase、成本报告、回归结果 |
| 目标 | 衡量模型效果 | 支撑工程迭代和上线门禁 |

对 Agent 来说，只看最终回答很危险。比如一个 Agent 最后回答“已完成”，但中间其实：

1. 调用了错误工具。
2. 读了无权限文件。
3. 重试了 20 次。
4. 没有真正跑测试。
5. 修改了不该改的文件。

Harness 要把这些过程都纳入评测。

## 3. Harness 的核心组成

### 3.1 Test Case Store

测试集不是简单问题列表，而是结构化样本。

一个样本可以包含：

```json
{
  "case_id": "ci_fix_001",
  "category": "coding_agent",
  "user_input": "修复登录接口单测失败",
  "initial_context": {
    "repo_snapshot": "git_sha_abc",
    "conversation_summary": "用户要求不要改数据库 schema",
    "permissions": ["read_repo", "edit_src", "run_test"]
  },
  "expected": {
    "must_run_tools": ["read_file", "run_test"],
    "forbidden_tools": ["git_push"],
    "changed_files_allowlist": ["src/**", "tests/**"],
    "tests_should_pass": ["test_login"]
  },
  "judge": {
    "type": "rule+test",
    "success_condition": "test_login exit_code == 0 and no schema file changed"
  }
}
```

样本来源：

1. 人工设计的典型任务。
2. 线上失败样本。
3. 用户投诉和人工接管案例。
4. 红队攻击样本。
5. 长上下文和权限边界样本。
6. 每次事故复盘产生的回归样本。

### 3.2 Environment Builder

Harness 必须能恢复评测环境。

对于代码 Agent：

1. checkout 指定 Git commit。
2. 安装依赖或使用缓存镜像。
3. 准备测试数据。
4. 注入环境变量，但不能注入真实密钥。
5. 配置工具权限。

对于 RAG Agent：

1. 准备固定文档集。
2. 构建指定版本索引。
3. 固定 embedding 模型和 reranker 版本。
4. 设置权限 metadata。

对于业务 Agent：

1. 使用 mock API。
2. 使用沙箱数据库。
3. 使用假账号、假订单、假支付回调。
4. 避免真实发券、退款、发短信。

### 3.3 Tool Mock / Sandbox

Agent 会调用工具，Harness 要控制工具行为。

常见方式：

1. **Mock**：固定返回值，适合确定性评测。
2. **Replay**：回放线上工具返回，适合复现线上问题。
3. **Sandbox**：在隔离环境执行真实命令，适合代码任务。
4. **Fault Injection**：注入超时、空结果、权限不足、500 错误。
5. **Golden API**：对部分工具用真实只读接口，但限制范围和速率。

工具评测不只看有没有调用，还要看：

1. 工具是否选对。
2. 参数是否正确。
3. 是否最小权限。
4. 是否处理错误。
5. 是否重复无意义调用。
6. 是否越权或触发副作用。

### 3.4 Runner

Runner 负责批量运行样本，并固定变量。

需要记录：

1. 模型版本。
2. Prompt 版本。
3. Skill 版本。
4. Tool schema 版本。
5. 代码版本。
6. 随机种子或 temperature。
7. token 上限、工具上限、超时时间。
8. sandbox 镜像版本。

Runner 还要支持：

1. 并发运行。
2. 失败重试。
3. 成本预算。
4. 中断和恢复。
5. 多版本 A/B 对比。
6. 输出统一 trace。

### 3.5 Judge

Judge 负责判定样本是否通过。

常见 Judge：

1. **规则 Judge**：JSON schema、正则、字段值、状态码。
2. **程序 Judge**：跑测试、编译、lint、SQL 校验。
3. **引用 Judge**：答案必须引用正确文档。
4. **工具轨迹 Judge**：必须调用某工具，不能调用某工具。
5. **人工 Judge**：复杂开放问题人工标注。
6. **LLM-as-Judge**：判断语义正确性，但要控制偏差。

Judge 最好分层：

```text
Hard Check: 安全、权限、格式、测试是否通过
Soft Check: 答案质量、表达、完整性
Cost Check: token、工具次数、延迟是否超预算
```

不要让 LLM-as-Judge 判断所有东西。安全和权限必须用确定性规则。

### 3.6 Trace Collector

Harness 要保存完整执行轨迹：

```text
case_id
run_id
model_version
prompt_version
input_context_hash
tool_calls[]
tool_args
tool_results_summary
exit_code
changed_files
final_answer
token_usage
latency
judge_result
failure_reason
```

Trace 的价值：

1. 解释为什么失败。
2. 对比两个版本的路径差异。
3. 发现工具误用和重复调用。
4. 生成新的 badcase。
5. 支持回放和审计。

### 3.7 Report / Dashboard

最终输出不只是总分，而是可行动报告：

1. 总通过率。
2. 分类型通过率。
3. 新修复样本。
4. 新失败样本。
5. 成本和延迟变化。
6. 工具调用分布。
7. 安全违规次数。
8. 失败原因聚类。
9. 和基线版本对比。

示例：

```text
v12 -> v13
任务成功率: 82% -> 87%
工具参数错误率: 9% -> 5%
平均 token: +12%
P95 latency: +18%
安全拒绝: 0 -> 0
回归失败: 3 cases
结论: 不能直接全量发布，需要修复 3 个回归样本或灰度。
```

## 4. Harness 如何用于 Prompt / Skill / Agent 迭代

### Prompt 迭代

对比：

```text
prompt_v1 vs prompt_v2
```

关注：

1. 答案正确率。
2. 格式遵守率。
3. 拒答准确率。
4. 幻觉率。
5. token 成本。

### Skill 迭代

Skill 的评测不只看最终答案，还看触发和流程。

指标：

1. 触发准确率：该触发时是否触发。
2. 误触发率：不该触发时是否误触发。
3. 步骤遵守率：是否按 Skill 流程做。
4. 工具调用质量。
5. 失败恢复能力。
6. 是否降低 token 或反而增加上下文噪声。

### Agent 迭代

Agent Harness 要评测完整链路：

1. 计划是否合理。
2. 工具是否选对。
3. 参数是否正确。
4. 状态是否正确更新。
5. 失败是否能恢复。
6. 高风险操作是否审批。
7. 最终结果是否可验证。

## 5. 常见测试集设计

### 5.1 功能成功集

覆盖正常任务：

1. 简单问答。
2. 单步工具调用。
3. 多步任务。
4. 代码修改和测试。
5. RAG 查询和引用。

### 5.2 失败恢复集

覆盖工具和环境异常：

1. 工具超时。
2. 空结果。
3. 500 错误。
4. 权限不足。
5. 测试失败。
6. 依赖缺失。

### 5.3 安全权限集

覆盖不可放行场景：

1. 读取 `.env`。
2. 生产写操作。
3. 越权文档召回。
4. Prompt injection。
5. 高风险命令。
6. 用户请求泄露系统提示词。

### 5.4 长上下文集

覆盖：

1. 早期硬性约束。
2. 多轮修改。
3. 旧决策和新需求冲突。
4. 摘要压缩后继续任务。
5. 历史工具结果召回。

### 5.5 回归集

每个线上问题都应该变成回归样本：

```text
线上失败
-> 脱敏
-> 固化输入和环境
-> 标注期望行为
-> 加入 harness
-> 后续版本必须通过
```

## 6. 如何判断 Harness 做得好

好的 Harness 应该满足：

1. **可复现**：同一版本、同一环境能重复运行。
2. **可定位**：失败能看到工具、上下文、参数、输出。
3. **可比较**：不同模型、Prompt、Skill 版本能横向对比。
4. **可扩展**：新业务场景能加入测试样本和工具 mock。
5. **可治理**：安全、权限、成本、延迟有硬门禁。
6. **可闭环**：线上 badcase 能进入回归集。

不好的 Harness：

1. 只有几个 demo 问题。
2. 只看最终文本，不看工具轨迹。
3. 依赖真实生产环境，无法重复。
4. 没有版本记录，无法解释为什么变好或变差。
5. LLM-as-Judge 没有校准，评分不稳定。
6. 没有安全和权限样本。

## 7. 一个落地架构

可以设计成：

```text
CaseStore
  -> EnvironmentBuilder
  -> ToolMock/Sandbox
  -> Runner
  -> TraceCollector
  -> Judge
  -> Report
  -> Badcase Miner
  -> Regression Set
```

模块职责：

| 模块 | 职责 |
| --- | --- |
| `CaseStore` | 保存测试样本、标签、期望行为和元数据 |
| `EnvironmentBuilder` | 准备 repo、数据、索引、mock 服务 |
| `ToolMock` | 固定工具返回、注入异常、限制副作用 |
| `Runner` | 批量运行不同版本 Agent |
| `TraceCollector` | 采集输入、上下文、工具轨迹、输出、成本 |
| `Judge` | 自动或人工判分 |
| `ReportService` | 生成对比报告和趋势图 |
| `BadcaseMiner` | 从线上日志和人工反馈抽取失败样本 |
| `Gatekeeper` | 根据阈值决定是否允许发布 |

上线门禁示例：

```text
任务成功率不能下降超过 1%
安全违规必须为 0
权限越权必须为 0
平均成本不能上升超过 20%
关键回归集必须 100% 通过
```

## 8. Harness Engineering 和传统测试的关系

它不是替代传统测试，而是补齐 LLM/Agent 特有的不确定性。

| 传统测试 | Harness 中的对应 |
| --- | --- |
| 单元测试 | 单步工具/函数调用测试 |
| 集成测试 | 多工具、多节点 Agent 任务 |
| E2E 测试 | 完整用户任务回放 |
| Mock 服务 | Tool Mock / Sandbox |
| CI 报告 | Harness Report |
| 回归测试 | Badcase Replay |
| 覆盖率 | 场景覆盖、工具覆盖、失败类型覆盖 |

对于代码 Agent，最终还要回到传统测试：

```text
Agent 生成修改
-> Harness 检查工具轨迹
-> 编译 / 单测 / lint / 安全扫描
-> Judge 汇总结果
```

## 9. 易错点

1. 把 Harness 当成几个 prompt demo。
2. 只评测最终答案，不评测工具和状态。
3. 没有固定模型、prompt、工具 schema 版本。
4. 评测时调用真实生产写接口。
5. 安全和权限用 LLM-as-Judge 判断，而不是硬规则。
6. 没有 badcase 回放，新版本反复犯旧错。
7. 样本只覆盖成功路径，不覆盖失败、空结果、权限不足和恶意输入。
8. 不记录 token、延迟和工具调用次数，导致效果提升但成本失控。
9. 没有人工复核复杂开放样本，自动 Judge 误判。

## 10. 面试回答模板

可以这样回答：

> Harness Engineering 是给 Agent、Prompt、Skill 搭一个可重复运行的评测和回归环境。它不只是写几条测试问题，而是把测试样本、上下文、工具 mock、沙箱环境、Runner、Judge、Trace 和报告都工程化。这样每次改 Prompt、模型、工具描述或 Skill 时，都能批量回放历史样本，比较任务成功率、工具选择、参数正确率、恢复率、安全违规、token 成本和延迟。
>
> 我理解它的核心价值是把 AI 系统从“主观感觉变好了”变成“有证据证明变好了”。比如一个代码 Agent，Harness 会 checkout 固定仓库版本，注入固定失败测试，限制工具权限，运行 Agent，记录它读了哪些文件、改了哪些文件、跑了哪些命令，最后用单测、lint、文件 allowlist 和安全规则做 Judge。线上失败样本脱敏后进入回归集，新版本必须回放通过，才能上线或灰度。它和传统测试类似，但更强调工具轨迹、上下文、模型版本、外部环境和安全边界。
