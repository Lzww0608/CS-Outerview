# 大语言模型项目选型

面试里问“项目中用过哪些大语言模型”，重点不是只报模型名，而是说明为什么选它、怎么接入、怎么评估，以及业务上如何兜底。

## 1. 常见模型类型

按部署和来源可以分为：

1. **闭源 API 模型**：例如 GPT、Claude、Gemini 等，优点是效果强、接入快，缺点是成本、数据合规和可控性要评估。
2. **开源/开放权重模型**：例如 Llama、Qwen、GLM、DeepSeek、Mistral 等，优点是可私有化部署、可微调，缺点是需要推理资源和工程维护。
3. **垂直领域模型**：面向代码、法律、医疗、金融、客服等场景进一步训练或对齐。
4. **Embedding 模型**：用于语义检索、RAG、聚类、去重、推荐召回。
5. **Reranker 模型**：对召回结果二次排序，提升 RAG 答案相关性。

## 2. 项目选型维度

| 维度 | 关注点 |
| --- | --- |
| 效果 | 指令遵循、推理、代码、中文、领域知识 |
| 延迟 | 首 token 延迟、总生成时间、并发吞吐 |
| 成本 | API 单价、GPU 成本、缓存命中率 |
| 上下文长度 | 是否能容纳文档、历史对话和工具结果 |
| 部署方式 | 公有云 API、私有化、混合部署 |
| 安全合规 | 数据是否能出域、日志脱敏、权限控制 |
| 工程生态 | SDK、函数调用、结构化输出、观测工具 |

真实项目一般不会只用一个模型：

1. 简单分类、改写、摘要可以用小模型。
2. 复杂推理、代码生成、规划可以用强模型。
3. 长文档问答通常组合 embedding、向量数据库、reranker 和生成模型。
4. 高 QPS 场景会加 prompt cache、结果缓存、批处理和降级模型。

## 3. RAG 场景怎么回答

如果项目是知识库问答，可以这样组织：

```text
文档切分 -> embedding -> 向量库召回 -> reranker -> prompt 拼接 -> LLM 生成 -> 引用/校验
```

关键点：

1. 文档切分要控制 chunk 大小和 overlap，避免语义被切断。
2. embedding 模型决定召回质量，reranker 决定最终上下文排序。
3. prompt 中要约束“只基于检索内容回答”，降低幻觉。
4. 生成结果要带引用来源，便于用户核查。
5. 对敏感问题、低置信度问题要拒答、转人工或返回检索结果。

## 4. 易错点

1. 不要只说“用了某某大模型”，要说明业务任务和评价指标。
2. 大模型不是数据库，不能直接依赖其记忆回答企业内部知识。
3. RAG 不是把所有文档塞进 prompt，召回、排序、上下文压缩都很关键。
4. 私有化部署不等于安全完成，还要做权限、审计、脱敏和数据隔离。
5. 评估不能只靠主观感觉，要有离线题集、人工标注、线上反馈和成本延迟指标。

## 5. 面试回答模板

项目里大语言模型我会按任务选型：通用问答和复杂推理用能力更强的模型，简单分类摘要用小模型控制成本；内部知识问答走 RAG，用 embedding 召回文档、reranker 排序，再把高相关片段交给生成模型。选型时主要看效果、延迟、成本、上下文长度、私有化和合规要求。上线后会用离线评测集、人工抽检、线上反馈、token 成本和延迟监控评估，并通过缓存、降级模型、敏感词和低置信度拒答做兜底。
