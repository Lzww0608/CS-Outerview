# 30. 用户中断正在执行的对话并开启新对话

## 1. 问题背景

Agent 或大模型对话系统不再只是“一问一答”。一次用户请求可能触发长时间运行的任务：

1. 流式调用大模型生成答案。
2. 执行多轮 ReAct：模型思考、调用工具、观察结果、继续执行。
3. 查询 RAG、数据库、日志平台、CI 系统或外部 API。
4. 启动浏览器自动化、代码修改、测试执行、Jenkins 构建等后台任务。
5. 在多轮对话中维护 `conversation_id`、`run_id`、`message_id`、`tool_call_id` 和上下文状态。

用户在任务执行过程中可能点击“停止生成”、发送新的问题、切换会话，或者明确要求“别继续了，重新开始”。这时系统必须能中断当前对话的执行流，并安全地开启新对话或新一轮执行。

**假设条件**：

1. 这里讨论的是 LLM/Agent 系统里的“用户中断”，不是操作系统层面的硬件中断。
2. “正在执行的对话”可能包含 LLM 流式请求、工具调用、后台任务、消息持久化和上下文构建。
3. “开启新对话”有两种含义：一种是在同一个 `conversation_id` 下取消旧 `run_id` 并创建新 `run_id`；另一种是创建全新的 `conversation_id`，完全隔离上下文。
4. 如果旧任务已经执行了有副作用的写操作，系统不一定能物理回滚，只能通过幂等、补偿、状态检查和迟到结果丢弃来保证不污染新对话。

一句话回答：

```text
用户中断的核心是：前端发 cancel，后端把旧 run 标记为 cancelling/cancelled，通过 cancellation token 尽力取消 LLM 和工具调用；不可取消的任务返回后必须检查 run 状态并丢弃迟到结果；新请求创建新的 run_id 或 conversation_id，使用独立上下文继续。
```

## 2. 问题现象

如果没有设计好中断机制，常见现象包括：

1. **前端停止了，后端还在跑**：用户看不到流式输出，但模型请求、工具调用或后台任务仍在消耗资源。
2. **旧结果污染新对话**：用户开启新问题后，旧 run 的工具结果迟到写入当前上下文。
3. **消息顺序错乱**：旧回答晚于新回答返回，前端展示顺序混乱。
4. **资源泄漏**：浏览器会话、临时文件、锁、线程、数据库连接、流式连接没有释放。
5. **重复写入或半执行状态**：旧任务取消前已经调用业务写接口，取消后没有补偿或状态标记。
6. **上下文混用**：新对话复用了旧 run 的计划、工具结果或压缩摘要。
7. **无法恢复和审计**：中断时没有保存 checkpoint、cancel reason、operator 和清理结果。
8. **用户体验不一致**：用户点击停止后系统仍继续输出，或者新问题被排队等待旧任务结束。

典型错误链路：

```text
用户发起请求 A
-> 后端创建 run_A
-> run_A 调用 LLM 和日志查询工具
-> 用户点击停止，并马上发送请求 B
-> 前端关闭 run_A 的流式展示
-> 后端 run_A 的日志查询仍在执行
-> run_B 创建并开始回答
-> run_A 工具结果迟到，写入 conversation summary
-> run_B 后续上下文被旧日志污染
```

正确做法应该是：

```text
用户点击停止
-> cancel(run_A)
-> run_A 状态变为 cancelling/cancelled
-> 可取消调用收到 cancel signal
-> 不可取消调用返回后检查 run_A 已取消，结果作废
-> 请求 B 创建 run_B 或 conversation_B
-> run_B 只读取自己的上下文和被允许继承的摘要
```

## 3. 影响范围

用户中断涉及完整链路，不是只改前端按钮。

1. **前端交互层**：停止按钮、新消息发送、流式连接关闭、会话切换、取消反馈。
2. **API 层**：`POST /runs/{run_id}/cancel`、`POST /conversations`、`POST /messages` 等接口。
3. **会话服务**：管理 `conversation_id`、`message_id`、`run_id` 的关系。
4. **Agent Runner**：执行模型调用、工具调用、状态机推进和中断检查。
5. **任务调度器**：取消排队任务、停止后续 step、通知 worker。
6. **模型调用层**：取消 HTTP/SSE/WebSocket 请求或停止读取流。
7. **工具执行层**：给 HTTP、DB、Shell、浏览器、CI、MCP 工具传递取消信号。
8. **状态存储层**：持久化 run 状态、cancel reason、checkpoint 和清理结果。
9. **结果写入层**：迟到结果写入前必须检查 run 状态和 generation 版本。
10. **可观测性**：记录取消耗时、取消成功率、迟到结果数量、资源清理结果。

如果涉及代码实现，可能需要修改的模块包括：

1. `ConversationController` / `ChatController`：增加停止、开启新对话、新消息中断旧 run 的接口逻辑。
2. `RunService`：维护 run 状态机，支持 `RUNNING -> CANCELLING -> CANCELLED`。
3. `AgentRunner`：在每个 step 前后检查 cancellation token 和 run 状态。
4. `LLMClient`：支持 abort streaming、HTTP cancel、timeout 和连接关闭。
5. `ToolRouter`：向工具传递 cancel context，并规范不可取消工具的迟到结果处理。
6. `TaskQueue` / `Worker`：取消排队任务，运行中任务进入协作式取消。
7. `ContextBuilder`：新 run 不读取已取消 run 的临时上下文。
8. `TraceStore`：记录 cancel event、cancel reason、cleanup result。
9. `MessageStore`：避免旧 run 继续写 assistant message 或 summary。

可能涉及的文件包括：

1. `chat_controller.py`、`conversation_controller.go`、`ChatController.java`。
2. `agent_runner.py`、`agent_executor.go`。
3. `run_service.py`、`run_state_machine.go`。
4. `llm_client.py`、`streaming_client.ts`。
5. `tool_router.py`、`mcp_client.py`。
6. `worker.py`、`task_queue.go`。
7. `context_builder.py`、`memory_manager.py`。
8. `db/migrations/create_agent_runs.sql`。
9. `tests/agent/test_cancel_run.py`、`tests/e2e/test_interrupt_conversation.ts`。

## 4. 原因分析

用户中断难做，是因为 Agent 执行不是一个单点函数调用，而是跨前端、后端、模型服务、工具服务和外部系统的分布式流程。

### 4.1 前端停止不等于后端取消

很多系统只在前端停止渲染：

```text
Abort SSE reader / close WebSocket / stop rendering tokens
```

这只能让用户看不到继续输出，不代表：

1. 后端模型请求已取消。
2. 工具调用已取消。
3. Worker 已停止。
4. 临时资源已释放。
5. 旧结果不会写入数据库。

因此必须有后端 run 状态和取消协议。

### 4.2 不是所有任务都能强制取消

不同任务的取消能力不同：

| 任务类型 | 是否容易取消 | 说明 |
| --- | --- | --- |
| LLM HTTP 请求 | 中等 | 可关闭连接，但服务端可能已完成计算 |
| SSE 流式输出 | 较容易 | 停止读取和关闭连接 |
| 普通 HTTP 工具 | 中等 | 需要工具端支持 timeout/cancel |
| 数据库查询 | 取决于驱动 | 有些支持 query cancel，有些只能等超时 |
| Shell 命令 | 中等 | 可发送 SIGTERM/SIGKILL，但要清理子进程 |
| 浏览器自动化 | 中等 | 可关闭 page/context，但要释放浏览器资源 |
| Jenkins/CI 构建 | 中等 | 需要调用外部取消 API |
| 业务写接口 | 难 | 已执行副作用不能简单撤销，只能补偿 |

所以中断要分成两层：

1. **尽力物理取消**：能取消的请求、进程、任务尽快停止。
2. **逻辑取消兜底**：即使物理取消失败，旧结果也不能污染新 run。

### 4.3 迟到结果是最大风险

取消不是瞬间完成的。旧任务可能在取消后仍返回结果：

```text
T1：run_A 调用工具
T2：用户 cancel run_A
T3：run_B 开始
T4：run_A 工具返回
T5：如果不检查状态，run_A 结果写入上下文，污染 run_B
```

因此所有写入点都要检查：

1. `run_id` 是否仍是当前 active run。
2. run 状态是否仍允许写入。
3. `generation` 或 `epoch` 是否匹配。
4. message 是否属于当前 conversation。
5. 工具结果是否已过期。

### 4.4 conversation_id 和 run_id 要分清

常见标识：

| 标识 | 含义 |
| --- | --- |
| `conversation_id` | 一条多轮会话线程 |
| `message_id` | 用户或助手的一条消息 |
| `run_id` | 针对某条用户消息启动的一次模型/Agent 执行 |
| `step_id` | run 内的一步模型调用或工具调用 |
| `tool_call_id` | 一次具体工具调用 |
| `trace_id` | 观测链路 ID |

用户“开启新对话”时：

1. 如果是同一聊天线程里打断旧回答并问新问题，可以保留 `conversation_id`，但必须新建 `run_id`。
2. 如果用户点击“新建会话”，应创建新的 `conversation_id`，上下文和记忆范围都要隔离。

## 5. 解决方案

推荐把中断设计成 **状态机 + cancellation token + 迟到结果防护 + 新旧上下文隔离**。

### 5.1 Run 状态机

一次执行 run 可以定义为：

```text
PENDING
-> RUNNING
-> CANCELLING
-> CANCELLED
-> COMPLETED
-> FAILED
```

状态含义：

| 状态 | 含义 |
| --- | --- |
| `PENDING` | 已创建，还未开始执行 |
| `RUNNING` | 正在模型调用、工具调用或状态机推进 |
| `CANCELLING` | 收到取消请求，正在通知执行层和清理资源 |
| `CANCELLED` | 已取消，后续结果不能写入主上下文 |
| `COMPLETED` | 正常完成 |
| `FAILED` | 执行失败 |

状态转移要持久化，不能只放内存。

```sql
CREATE TABLE agent_runs (
  run_id VARCHAR(64) PRIMARY KEY,
  conversation_id VARCHAR(64) NOT NULL,
  user_message_id VARCHAR(64) NOT NULL,
  status VARCHAR(32) NOT NULL,
  generation BIGINT NOT NULL,
  cancel_reason VARCHAR(255),
  active BOOLEAN NOT NULL DEFAULT TRUE,
  created_at TIMESTAMP NOT NULL,
  updated_at TIMESTAMP NOT NULL,
  cancelled_at TIMESTAMP NULL
);
```

### 5.2 Cancel API

接口示例：

```http
POST /api/agent-runs/{run_id}/cancel
Content-Type: application/json

{
  "reason": "user_interrupt",
  "mode": "start_new_run"
}
```

返回：

```json
{
  "run_id": "run_A",
  "status": "CANCELLING",
  "new_run_allowed": true
}
```

`mode` 可以是：

| mode | 含义 |
| --- | --- |
| `stop_only` | 只停止当前 run，不创建新请求 |
| `start_new_run` | 同一 conversation 下创建新 run |
| `start_new_conversation` | 创建全新 conversation |

### 5.3 前端中断逻辑

前端需要同时做两件事：

1. 停止当前流式展示。
2. 通知后端取消当前 `run_id`。

伪代码：

```ts
async function stopCurrentRun() {
  if (!currentRunId) return;

  abortController?.abort(); // 停止本地读取 SSE/Fetch 流

  await fetch(`/api/agent-runs/${currentRunId}/cancel`, {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ reason: "user_interrupt", mode: "stop_only" })
  });

  markRunStopped(currentRunId);
}
```

如果用户发送新消息：

```ts
async function sendNewMessage(text: string) {
  if (currentRunId && isRunning(currentRunId)) {
    await cancelRun(currentRunId, "start_new_run");
  }

  const res = await createMessage({
    conversation_id: currentConversationId,
    text,
    interrupt_previous: true
  });

  subscribeStream(res.run_id);
}
```

### 5.4 后端取消逻辑

后端收到取消请求时：

1. 用 CAS 或事务把 run 从 `RUNNING` 改成 `CANCELLING`。
2. 触发内存中的 cancellation token。
3. 通知队列或 worker 停止后续 step。
4. 尝试取消模型请求、HTTP 请求、Shell 进程、浏览器任务。
5. 清理临时资源。
6. 把状态改成 `CANCELLED`。
7. 记录 cancel trace。

伪代码：

```python
def cancel_run(run_id: str, reason: str):
    run = run_store.get(run_id)
    if run.status in ["COMPLETED", "FAILED", "CANCELLED"]:
        return run

    updated = run_store.compare_and_set_status(
        run_id,
        from_status=["PENDING", "RUNNING"],
        to_status="CANCELLING",
        cancel_reason=reason,
    )

    if not updated:
        return run_store.get(run_id)

    cancellation_registry.cancel(run_id)
    task_queue.cancel_pending(run_id)
    tool_runtime.cancel(run_id)
    cleanup_manager.cleanup(run_id)

    run_store.mark_cancelled(run_id)
    trace_store.append(run_id, event="cancelled", reason=reason)
    return run_store.get(run_id)
```

### 5.5 Agent Runner 检查取消

Agent Runner 必须在安全点检查取消：

1. 开始执行前。
2. 每次 LLM 调用前后。
3. 每次工具调用前后。
4. 每轮状态更新前。
5. 写入消息、摘要、memory 前。

伪代码：

```python
def run_agent(run_id):
    ctx = cancellation_registry.get_context(run_id)

    while True:
        assert_not_cancelled(run_id, ctx)

        decision = llm_client.call(build_context(run_id), cancel_token=ctx.token)
        assert_not_cancelled(run_id, ctx)

        action = parse_action(decision)
        result = tool_router.execute(action, cancel_token=ctx.token)
        assert_not_cancelled(run_id, ctx)

        if run_store.is_writable(run_id):
            state_store.apply_step(run_id, action, result)
        else:
            trace_store.append(run_id, event="late_result_discarded")
            return
```

### 5.6 迟到结果防护

所有异步回调和工具结果写入前都要检查：

```python
def on_tool_result(run_id, tool_call_id, result):
    run = run_store.get(run_id)

    if run.status in ["CANCELLING", "CANCELLED"]:
        trace_store.append(
            run_id,
            event="discard_tool_result",
            tool_call_id=tool_call_id,
            reason="run_cancelled",
        )
        return

    if not run.active:
        return

    tool_result_store.save(run_id, tool_call_id, result)
```

如果同一 conversation 只允许一个 active run，可以维护 generation：

```text
conversation.active_generation = 12
run_A.generation = 11
run_B.generation = 12

run_A 迟到结果返回时发现 generation 不匹配，直接丢弃。
```

### 5.7 开启新对话

开启新对话有两种方式。

#### 方式一：同一 conversation 下开启新 run

适合用户只是打断旧回答，继续在同一主题里问新问题。

```text
conversation_id = conv_1
run_A cancelled
run_B running
```

处理原则：

1. 新 run 可以读取旧 conversation 的稳定历史。
2. 不能读取旧 run 的临时工具结果。
3. 已取消 run 的未完成计划不能进入新上下文。
4. 如果需要继承旧信息，只继承已完成消息和已验证摘要。

#### 方式二：创建新 conversation

适合用户点击“新建对话”，希望完全重新开始。

```text
conv_1 / run_A cancelled
conv_2 / run_B running
```

处理原则：

1. 新 `conversation_id` 只继承用户长期偏好，不继承旧对话临时上下文。
2. 上下文缓存、summary、tool results 按 conversation 隔离。
3. 前端路由和消息列表切换到新 conversation。
4. 旧 conversation 的后台结果即使返回，也只能写回旧 conversation 的 trace，不能影响新 conversation。

### 5.8 有副作用工具的处理

中断最难的是写操作，例如发邮件、退款、下单、改配置、删文件、执行发布。

设计原则：

1. **写操作前确认**：高风险动作必须 Human-in-the-loop。
2. **幂等 key**：每次写操作带 `run_id/tool_call_id/idempotency_key`。
3. **两阶段输出**：先生成草稿或计划，用户确认后再执行。
4. **补偿动作**：已执行的业务写操作要有取消、回滚或修正路径。
5. **状态标记**：取消后不能假装未发生，必须记录已执行到哪一步。

示例：

```text
发送邮件：
1. Agent 生成邮件草稿。
2. 用户确认发送。
3. send_email 带 idempotency_key。
4. 如果用户在发送后取消，只能标记 run cancelled_after_side_effect。
5. 不能声称邮件未发送。
```

## 6. 可选方案对比

| 方案 | 原理 | 优点 | 缺点 | 适用场景 |
| --- | --- | --- | --- | --- |
| 仅前端停止 | 关闭 SSE/停止渲染 | 实现简单 | 后端仍跑，旧结果污染 | 只适合 Demo |
| 后端状态取消 | run 标记 cancelled | 能阻止迟到写入 | 资源可能仍消耗 | 所有生产系统底线 |
| cancellation token | 逐层传递取消信号 | 能尽快停止可取消任务 | 需要工具链支持 | LLM、HTTP、DB、Shell |
| 队列取消 | 取消 pending job | 减少无效任务 | running job 不一定能停 | 异步任务系统 |
| generation 隔离 | 新 run 增加版本号 | 防止迟到结果污染 | 需要全链路校验 | 同一会话多 run |
| 新 conversation 隔离 | 新建 conversation_id | 上下文最干净 | 不能继承当前主题 | 用户明确新建对话 |
| Saga/补偿 | 写操作后用补偿修正 | 处理副作用 | 复杂，可能补偿失败 | 业务写操作 |

结论：

```text
生产系统至少要有：后端状态取消 + cancellation token + 迟到结果防护。
如果支持新对话，还要有 conversation/run 隔离。
如果涉及写操作，还要有幂等和补偿。
```

## 7. 推荐方案

推荐方案是 **前端 Abort + 后端 Run 状态机 + cancellation token + generation 隔离 + 迟到结果丢弃 + 新 conversation/run 隔离**。

架构示意：

```text
Frontend
  |-- AbortController 停止本地流
  |-- POST /runs/{run_id}/cancel
  |-- POST /messages 创建新 run
  |
Backend API
  |-- RunService 标记 CANCELLING/CANCELLED
  |-- CancellationRegistry 触发 cancel token
  |-- ConversationService 创建新 run/conversation
  |
AgentRunner
  |-- 每个 step 检查 cancel
  |-- LLMClient 传递 cancel token
  |-- ToolRouter 传递 cancel token
  |
ResultWriter
  |-- 检查 run status/generation
  |-- 丢弃迟到结果
  |
TraceStore
  |-- 记录 cancel、cleanup、late result
```

关键原则：

1. **用户体验上立即停止**：前端先停止流式展示。
2. **系统语义上真正取消**：后端 run 状态必须进入取消流程。
3. **执行层尽力取消**：能取消的请求、进程、工具尽快停止。
4. **结果层强一致防污染**：旧结果写入前必须检查状态和 generation。
5. **新旧上下文隔离**：新 run 或新 conversation 不读取旧 run 的临时状态。
6. **副作用可审计**：已执行写操作必须有记录、幂等和补偿。

## 8. 实施步骤

### 8.1 建立 ID 模型

先明确几个 ID：

```text
conversation_id：一条会话线程
message_id：一条用户或助手消息
run_id：一次 Agent 执行
step_id：run 内一步执行
tool_call_id：一次工具调用
generation：同一 conversation 下 active run 版本
trace_id：可观测链路 ID
```

不要只用 `conversation_id` 表示当前任务，否则中断、重试、新消息都会混在一起。

### 8.2 建立 Run 状态表

建议字段：

```sql
CREATE TABLE agent_runs (
  run_id VARCHAR(64) PRIMARY KEY,
  conversation_id VARCHAR(64) NOT NULL,
  user_message_id VARCHAR(64) NOT NULL,
  status VARCHAR(32) NOT NULL,
  generation BIGINT NOT NULL,
  cancel_reason VARCHAR(255),
  side_effect_status VARCHAR(32),
  active BOOLEAN NOT NULL,
  created_at TIMESTAMP NOT NULL,
  updated_at TIMESTAMP NOT NULL,
  cancelled_at TIMESTAMP NULL
);
```

`side_effect_status` 可以是：

```text
NONE
PENDING_CONFIRMATION
EXECUTED
COMPENSATED
COMPENSATION_FAILED
```

### 8.3 实现 Cancel API

核心修改逻辑：

1. 根据 `run_id` 查询 run。
2. 如果 run 已完成，返回当前状态。
3. 如果 run 运行中，用 CAS 改成 `CANCELLING`。
4. 触发 cancellation token。
5. 取消 pending job。
6. 清理资源。
7. 标记 `CANCELLED`。
8. 写 trace。

### 8.4 改造模型调用层

LLMClient 要支持：

1. HTTP timeout。
2. 请求 abort。
3. SSE 流关闭。
4. 用户取消时停止 token 回调。
5. 回调前检查 run 状态。

如果底层模型服务不支持取消，也要在本服务侧停止读取响应，并把迟到结果丢弃。

### 8.5 改造工具调用层

每个工具执行接口建议带 `RunContext`：

```python
class RunContext:
    def __init__(self, run_id, trace_id, cancel_token, deadline):
        self.run_id = run_id
        self.trace_id = trace_id
        self.cancel_token = cancel_token
        self.deadline = deadline
```

工具执行：

```python
def execute_tool(tool, args, ctx: RunContext):
    if ctx.cancel_token.cancelled:
        raise CancelledError()

    result = tool.call(args, timeout=ctx.deadline, cancel_token=ctx.cancel_token)

    if ctx.cancel_token.cancelled:
        raise CancelledError()

    return result
```

### 8.6 新消息自动中断旧 run

同一 conversation 下，如果用户发新消息，可以有两种策略：

1. 自动取消当前 active run，再创建新 run。
2. 询问用户是否停止当前任务。

常见产品会采用自动取消：

```python
def create_user_message(conversation_id, text):
    active_run = run_store.get_active_run(conversation_id)
    if active_run:
        cancel_run(active_run.run_id, reason="new_user_message")

    message_id = message_store.create_user_message(conversation_id, text)
    run_id = run_store.create_run(conversation_id, message_id)
    return run_id
```

### 8.7 新 conversation 隔离

创建新 conversation 时：

1. 生成新的 `conversation_id`。
2. 不继承旧 conversation 的 `summary/run_state/tool_results`。
3. 可选择继承用户长期偏好，例如语言偏好。
4. 前端切换到新会话流。
5. 旧 run 迟到结果只能写旧 run trace，不写新 conversation。

### 8.8 清理资源

中断后需要清理：

1. SSE/WebSocket 连接。
2. HTTP 请求。
3. 临时文件和临时工作区。
4. 浏览器 page/context。
5. Shell 子进程。
6. 数据库游标和连接。
7. 分布式锁。
8. 未开始的队列任务。

### 8.9 测试重点

如果涉及代码实现，测试重点包括：

1. **前端取消测试**：点击停止后流式输出立即停止。
2. **后端状态测试**：run 从 `RUNNING` 正确进入 `CANCELLED`。
3. **模型取消测试**：LLM 流式请求能停止读取和停止回调。
4. **工具取消测试**：HTTP、Shell、浏览器、队列任务能收到 cancel。
5. **迟到结果测试**：旧 run 返回结果不能写入新 run。
6. **新 run 隔离测试**：新消息创建新的 `run_id`，不复用旧临时状态。
7. **新 conversation 隔离测试**：新会话不读取旧会话上下文。
8. **副作用测试**：已执行写操作有幂等记录和补偿状态。
9. **并发测试**：用户连续点击停止、连续发送消息，不产生多个 active run。
10. **恢复测试**：worker 重启后能根据 run 状态继续取消或丢弃旧结果。

## 9. 风险与注意事项

1. **只取消前端是不够的**  
   前端停止展示只是用户体验，后端必须有 run 状态取消。

2. **取消不是回滚**  
   如果写操作已经执行，取消不能让副作用自动消失，需要补偿或人工处理。

3. **迟到结果必须丢弃**  
   所有异步写入都要检查 run status 和 generation。

4. **新旧上下文要隔离**  
   新 run 不能读取旧 run 的临时计划、未验证工具结果和未完成摘要。

5. **不可取消任务要有超时**  
   工具不支持 cancel 时，必须设置 deadline，避免后台任务长期占资源。

6. **状态机要幂等**  
   用户可能重复点击停止，Cancel API 要支持重复调用。

7. **资源清理要可观测**  
   清理失败不能静默，要记录 trace 和告警。

8. **高风险工具要两阶段执行**  
   先生成草稿或计划，确认后再执行，避免用户取消时已经产生不可逆副作用。

9. **长期记忆写入要谨慎**  
   被取消 run 的临时结论不能直接写入长期 memory。

10. **多端同步要一致**  
    用户在 Web 停止，移动端也应该看到 run 已取消。

## 10. 验证方式

### 10.1 功能验证

1. 用户点击停止，前端立即停止 token 展示。
2. 后端 run 状态进入 `CANCELLING/CANCELLED`。
3. 新消息创建新的 `run_id`。
4. 新对话创建新的 `conversation_id`。
5. 已取消 run 不再写 assistant message。
6. 已取消 run 不再更新 conversation summary。

### 10.2 迟到结果验证

构造测试：

```text
run_A 调用一个延迟 5 秒返回的工具
1 秒后 cancel run_A
立即创建 run_B
5 秒后 run_A 工具返回
验证：
1. run_A 工具结果被标记 discarded
2. run_B 上下文不包含 run_A 工具结果
3. conversation summary 不包含 run_A 迟到结论
```

### 10.3 副作用验证

对写工具做测试：

1. 写操作未执行前取消，状态为 `CANCELLED`。
2. 写操作执行中取消，状态为 `CANCELLING`，等待工具返回。
3. 写操作已执行后取消，状态记录 `cancelled_after_side_effect`。
4. 重复取消不会重复补偿。
5. 幂等 key 能防止重复写。

### 10.4 并发验证

验证场景：

1. 用户连续点击停止 10 次。
2. 用户连续发送 3 条新消息。
3. Web 端停止，移动端继续发消息。
4. Worker 在取消过程中重启。
5. 队列任务在取消后才被 worker 拉取。

预期：

1. 同一 conversation 只有一个 active run。
2. 旧 run 全部进入终态。
3. 新 run 不被旧结果污染。
4. trace 能解释每个 run 的状态变化。

### 10.5 指标验证

建议监控：

| 指标 | 含义 |
| --- | --- |
| `cancel_request_count` | 用户取消次数 |
| `cancel_success_rate` | 取消成功率 |
| `cancel_latency_p95` | 从点击停止到 run cancelled 的 P95 |
| `late_result_discard_count` | 迟到结果丢弃次数 |
| `active_run_conflict_count` | 同一 conversation 多 active run 冲突 |
| `resource_cleanup_fail_count` | 资源清理失败次数 |
| `side_effect_after_cancel_count` | 取消后仍产生副作用次数 |
| `new_run_after_cancel_success_rate` | 取消后新 run 正常启动比例 |

## 11. 总结

实现用户中断正在执行的对话，不能只做前端“停止显示”。完整方案要把一次 Agent 执行抽象为可持久化的 `run_id`，并围绕它设计状态机、取消信号、资源清理和迟到结果防护。

核心要点：

1. 前端用 `AbortController` 或关闭 SSE/WebSocket 让用户立即停止看到输出。
2. 后端提供 Cancel API，把旧 `run_id` 标记为 `CANCELLING/CANCELLED`。
3. Agent Runner、LLMClient、ToolRouter、Worker 都要传递 cancellation token。
4. 工具和模型请求能取消就取消，不能取消也要通过 run 状态丢弃迟到结果。
5. 新消息要创建新的 `run_id`，新对话要创建新的 `conversation_id`。
6. 新旧上下文、summary、tool result、memory 写入必须隔离。
7. 对有副作用的写操作，要用幂等、审批、补偿和审计兜底。

面试回答可以这样说：

```text
我会把一次 Agent 执行抽象成 run。用户点击停止或发送新消息时，前端先 abort 当前流式请求，同时调用后端 cancel(run_id)。后端用状态机把 run 从 RUNNING 改成 CANCELLING/CANCELLED，并触发 cancellation token，通知 LLM 请求、工具调用、worker 和队列停止。对于不能强制取消的工具，返回时必须检查 run 状态或 generation，如果旧 run 已取消，就把结果标记为 discarded，不能写入新对话上下文。

开启新对话时，如果只是同一聊天里打断旧回答，就复用 conversation_id 但创建新的 run_id；如果用户点击新建会话，就创建新的 conversation_id，隔离 summary、tool result 和 run state。高风险写操作不能指望取消自动回滚，要通过幂等 key、两阶段确认、补偿和审计处理。验证时重点测前端停止、后端状态、迟到结果、新旧上下文隔离、资源清理和并发重复取消。
```
