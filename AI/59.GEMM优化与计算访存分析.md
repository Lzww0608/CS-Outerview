# 59. GEMM优化与计算访存分析

## 1. 问题背景

GEMM（General Matrix Multiply，通用矩阵乘法）是深度学习中最核心的计算原语，几乎所有的线性层、卷积、Attention 计算最终都归约到 GEMM。在大模型推理中，GEMM 的性能直接决定吞吐和延迟。面试常考 GEMM 的优化层次、计算量与访存量的估计方法、cuBLAS 的使用，以及如何判断一个算子是计算密集型还是访存密集型。

**假设条件**：本文档基于 CUDA 12.x + cuBLAS + CUTLASS 生态，假设使用 NVIDIA A100/H100 GPU，矩阵维度为 LLM 推理典型规模。

## 2. 问题现象

1. **Naive GEMM 性能极低**：三重循环实现仅利用 GPU 不到 1% 算力
2. **不清楚 GEMM 的计算量怎么算**：无法估算推理延迟
3. **cuBLAS 接口复杂**：行优先/列优先、转置参数容易搞混
4. **无法判断优化方向**：不知道瓶颈在计算还是访存

## 3. 影响范围

| 影响维度 | 程度 | 说明 |
| --- | --- | --- |
| 推理吞吐 | 高 | GEMM 占推理 80%+ 计算量 |
| 延迟 | 高 | GEMM 延迟直接决定首 Token 延迟 |
| 显存 | 中 | 中间矩阵占显存 |
| 功耗 | 中 | GEMM 是 GPU 功耗主要来源 |

## 4. 原因分析

### 4.1 GEMM 计算量与访存量估计

对于矩阵乘法 C = A × B，其中 A 为 M×K，B 为 K×N，C 为 M×N：

```
计算量（FLOPs）：
  每个输出元素需要 K 次乘法 + K-1 次加法 ≈ 2K FLOPs
  总 FLOPs = 2 × M × K × N

访存量（Bytes）：
  读 A: M × K × sizeof(dtype)
  读 B: K × N × sizeof(dtype)
  写 C: M × N × sizeof(dtype)
  总访存 ≈ (M×K + K×N + M×N) × sizeof(dtype)

算术强度（Arithmetic Intensity）：
  AI = FLOPs / Bytes = 2MKN / ((MK + KN + MN) × sizeof(dtype))
  
  当 M=N=K 时：
  AI ≈ 2K / (3 × sizeof(dtype))
  FP16: AI ≈ 2K/6 ≈ K/3
```

**计算密集 vs 访存密集的判断**：
- GPU 的计算带宽比例（Ops:Byte）约为 200:1（A100: 312 TFLOPS / 2 TB/s）
- 若 AI > 200（A100），则为计算密集型，优化方向是提高算力利用率
- 若 AI < 200，则为访存密集型，优化方向是减少访存量

```
LLM 推理场景分析：
  Prefill 阶段（大 batch、长序列）：M 和 N 大 → AI 高 → 计算密集
  Decode 阶段（batch=1、seq=1）：M=1, N=vocab_size → AI 低 → 访存密集
```

### 4.2 GEMM 优化层次

```
┌─────────────────────────────────────────────────────┐
│              GEMM 优化层次（从低到高）               │
├─────────────────────────────────────────────────────┤
│ Level 0: Naive（三重循环）                          │
│   → 每个线程计算一个输出元素                        │
│   → 性能 < 1% 峰值                                  │
│                                                     │
│ Level 1: Shared Memory Tiling                       │
│   → 将大矩阵分块，块内数据加载到 Shared Memory      │
│   → 减少 HBM 访问次数                               │
│   → 性能 ~30-50% 峰值                               │
│                                                     │
│ Level 2: Register Tiling + Warp 级优化              │
│   → 每个线程计算多个输出（如 4×4 小块）             │
│   → 利用寄存器减少 Shared Memory 访问               │
│   → 性能 ~60-80% 峰值                               │
│                                                     │
│ Level 3: Tensor Core (WMMA/MMA)                     │
│   → 利用 Tensor Core 硬件加速矩阵乘                │
│   → FP16: 16×16×16 或 8×32×16 fragment              │
│   → 性能 ~80-95% 峰值                               │
│                                                     │
│ Level 4: CUTLASS/cuBLAS                             │
│   → 工业级实现，包含所有优化                        │
│   → 性能 ~90-98% 峰值                               │
└─────────────────────────────────────────────────────┘
```

### 4.3 Shared Memory Tiling 原理

```
将大矩阵 C(M,N) = A(M,K) × B(K,N) 分块计算：
  - 将 A 按 M 方向分成 BM 大小的块
  - 将 B 按 N 方向分成 BN 大小的块
  - 沿 K 方向迭代，每次取 BK 大小的块
  - 每个块从 HBM 加载到 Shared Memory，多个线程复用

关键优化点：
  1. 数据复用：A 的一行块被 BN 个线程复用，B 的一列块被 BM 个线程复用
  2. Coalesced Access：连续线程读连续地址，合并内存访问
  3. Bank Conflict 避免：Shared Memory padding 避免银行冲突
  4. Double Buffering：计算当前块时预取下一块到另一块 Shared Memory
```

### 4.4 cuBLAS 接口使用

```c
// cuBLAS GEMM 接口
cublasStatus_t cublasGemmEx(
    cublasHandle_t handle,
    cublasOperation_t transa,    // CUBLAS_OP_N 或 CUBLAS_OP_T
    cublasOperation_t transb,
    int m, int n, int k,         // 维度
    const void *alpha,           // 标量
    const void *A, int lda,      // A 矩阵 + leading dimension
    const void *B, int ldb,
    const void *beta,
    void *C, int ldc,
    cudaDataType_t Atype,        // 数据类型
    cudaDataType_t Btype,
    cudaDataType_t Ctype,
    cublasComputeType_t computeType,  // 计算精度
    cublasGemmAlgo_t algo        // 算法选择
);
```

```python
# PyTorch 中使用 cuBLAS（间接调用）
import torch

# 等价于 cuBLAS GEMM
C = torch.matmul(A, B)  # 自动调用 cuBLAS
C = A @ B               # Python 语法糖

# 显式使用 cuBLAS
# PyTorch 内部会自动选择 cuBLAS/cuBLASLt
```

**cuBLAS 使用注意事项**：
- cuBLAS 默认列优先（Column-Major），PyTorch 使用行优先（Row-Major）
- 行优先矩阵 A(M,K) 传给 cuBLAS 时，需要转置参数设置为 `CUBLAS_OP_T`，或理解为 A^T
- Leading dimension：行优先中 lda = K（A 的列数），列优先中 lda = M（A 的行数）
- `cublasGemmEx` 支持混合精度计算，可指定输入/输出/计算的不同精度

### 4.5 Attention 计算的 FLOPs 估计

```
标准 Attention: O = softmax(QK^T / sqrt(d)) × V

设 seq_len = S, hidden_dim = D, num_heads = H, head_dim = d = D/H

计算量分解：
  1. QK^T:  [B, H, S, d] × [B, H, d, S] → [B, H, S, S]
     FLOPs = 2 × B × H × S × S × d = 2 × B × S × S × D
  
  2. softmax: [B, H, S, S]
     FLOPs ≈ 3 × B × H × S × S (exp + sum + div)
  
  3. AV: [B, H, S, S] × [B, H, S, d] → [B, H, S, d]
     FLOPs = 2 × B × H × S × S × d = 2 × B × S × S × D
  
  Total ≈ 4 × B × S × S × D (忽略 softmax)

对比 FFN:
  FFN: up_proj + gate_proj + down_proj
  FLOPs ≈ 2 × B × S × D × 4D × 2/3 (SwiGLU) ≈ 16/3 × B × S × D²

当 S < D 时 (常见): FFN 计算量 > Attention 计算量
当 S > D 时 (长序列): Attention 计算量占主导（O(S²) 增长）
```

## 5. 解决方案

| 优化方案 | 提升幅度 | 实现难度 | 适用场景 |
| --- | --- | --- | --- |
| Naive → Shared Memory Tiling | 30-50x | 中 | 所有 GEMM |
| Shared Memory → Register Tiling | 2-3x | 高 | 大矩阵 |
| Register → Tensor Core | 2-8x | 高 | FP16/BF16/INT8 |
| cuBLAS 直接调用 | 直接最优 | 低 | 生产环境 |
| CUTLASS 模板 | 接近最优 | 中 | 自定义融合 |

## 7. 推荐方案

- **生产环境**：直接使用 cuBLAS / cuBLASLt，性能最优
- **需要融合**：使用 CUTLASS Epilogue Fusion 或 Triton
- **学习/面试**：掌握 Shared Memory Tiling 和 Tensor Core 原理即可

## 8. 实施步骤

1. 理解 GEMM 的计算量和访存量公式
2. 实现 Naive GEMM 和 Shared Memory 版本
3. 使用 `ncu` 分析 kernel 的 roofline 位置
4. 对比 cuBLAS 性能，理解差距来源
5. 尝试 Tensor Core 版本（WMMA API）

## 9. 风险与注意事项

- **cuBLAS 行列优先混淆**是最常见的 bug 来源，务必确认内存布局
- **Tensor Core 对矩阵维度有对齐要求**：M/N 通常需要是 8 或 16 的倍数
- **FP16 精度问题**：大数吃小数，可能需要 FP32 累加
- **Decode 阶段 GEMM 是访存密集型**：优化方向是减少权重读取，而非提高算力利用

## 10. 验证方式

1. 正确性：对比 cuBLAS 结果，`torch.allclose(rtol=1e-2, atol=1e-2)`
2. 性能：`ncu --set full` 查看 SM 利用率、HBM 带宽利用率
3. Roofline：确认 kernel 在 roofline 图上的位置，是否逼近理论峰值

## 11. 总结

GEMM 是大模型推理的核心计算原语。面试常考计算量估计（`2MKN`）、算术强度判断（计算密集 vs 访存密集）、优化层次（Naive → Tiling → Register → Tensor Core）、cuBLAS 接口使用注意事项（行列优先、leading dimension）。推理场景中，prefill 阶段 GEMM 是计算密集型，decode 阶段是访存密集型，优化方向完全不同。
