# 1. Agent、Tools、Skills 与 MCP

面试里问 “skills 有没有用过”“agent 里的 tool 和 skills 是什么”“skills 和 rules 有什么区别”，通常不是在考某个具体产品按钮，而是在考你是否理解 AI Agent 工程化：模型如何调用外部能力、如何复用上下文、如何把复杂任务沉淀成可执行流程。

不同平台对 Skills、Rules、Tools、MCP 的命名会有差异，回答时可以先说明：下面按通用 LLM 应用和 AI 编码工具里的工程概念来讲。

## 1. Agent 是什么

Agent 可以理解为带有目标、上下文、工具调用和多步规划能力的 LLM 应用。

普通 Chatbot 通常是：

```text
用户问题 -> 模型回答
```

Agent 更像是：

```text
用户目标
  -> 任务拆解
  -> 选择工具 / 检索资料 / 修改文件 / 执行命令
  -> 观察结果
  -> 继续决策
  -> 输出最终结果
```

核心能力：

1. **规划**：把复杂目标拆成多个步骤。
2. **工具调用**：访问文件、数据库、搜索、浏览器、代码执行环境、业务 API。
3. **记忆和上下文管理**：保留任务相关信息，丢弃无关噪声。
4. **反思和校验**：根据工具返回结果修正下一步动作。
5. **权限控制**：对高风险操作做确认、审计和沙箱隔离。

## 2. Tool 是什么

Tool 是模型可以调用的外部函数或能力，通常有明确的输入输出 schema。

例子：

1. `read_file(path)`：读取文件。
2. `search_code(query)`：在代码仓库中检索。
3. `run_tests(command)`：执行测试命令。
4. `query_db(sql)`：查询数据库。
5. `create_ticket(title, body)`：创建工单。

Tool 的价值是让模型不只靠参数记忆回答，而是能访问真实环境和实时状态。

设计 Tool 时要注意：

1. 输入输出要结构化，减少模型猜参数。
2. 工具粒度不能太粗，否则不可控；也不能太碎，否则编排成本高。
3. 高风险工具要有权限边界，例如删除文件、发生产消息、执行线上 SQL。
4. 工具返回内容要精简，避免把大量无关日志塞进上下文。

## 3. Skills 是什么

Skills 可以理解为可复用的任务能力包，通常包含：

1. 何时使用这个 skill。
2. 任务执行步骤。
3. 领域知识和注意事项。
4. 可复用脚本、模板、示例。
5. 推荐调用哪些工具以及调用顺序。

Tool 更像“函数”，Skill 更像“方法论 + 资料包 + 工作流”。

例如一个 “修复 CI” skill 可能包含：

```text
触发条件：用户要求修复失败的 CI
步骤：
1. 查看失败 job
2. 拉取日志
3. 定位失败测试
4. 最小化复现
5. 修改代码
6. 重新运行对应测试
7. 总结原因和修复
```

它不一定直接执行动作，而是指导 Agent 使用合适的工具完成任务。

## 4. Skills 和 Rules 的区别

| 对比项 | Rules | Skills |
| --- | --- | --- |
| 作用 | 约束模型行为 | 指导模型完成某类任务 |
| 生效范围 | 通常全局或项目级长期生效 | 按任务触发，按需加载 |
| 内容形态 | 禁止/必须/风格/边界 | 步骤、领域知识、脚本、模板 |
| 例子 | 不要提交密钥；代码必须跑测试；回答用中文 | 如何修 CI；如何写 PRD；如何做 RAG 评估 |
| 目标 | 降低风险，统一规范 | 提高某类任务完成质量和效率 |

二者的联系：

1. Rules 是底线约束，Skills 是执行策略。
2. Skills 不能违反 Rules。
3. 好的 Skills 会内置对 Rules 的遵守方式，例如涉及生产操作时先请求确认。

面试回答可以说：Rules 更像系统的“交通规则”，Skills 更像“专项作业手册”。

## 5. Skills 会不会降低 token

不一定。更准确的说法是：Skills 可以降低无效 token 和重复沟通，但不是天然减少总 token。

可能降低 token 的原因：

1. **按需加载**：不把所有项目知识都塞进系统提示词，只在任务匹配时加载对应 skill。
2. **流程固定**：减少模型反复试错和来回询问。
3. **复用模板**：减少临场生成长提示和长格式说明。
4. **工具结果筛选**：skill 可以要求只读取必要文件或摘要长日志。

可能增加 token 的原因：

1. skill 写得太长，每次触发都会带入大量无关内容。
2. 触发条件过宽，导致简单任务也加载复杂流程。
3. skill 内部包含过多示例，模型上下文被示例占满。

所以工程上要做：

1. skill 粒度清晰，一个 skill 只解决一类任务。
2. 触发条件具体，避免误触发。
3. 大资料放到引用文件或脚本里，按需读取。
4. skill 内容以步骤和约束为主，不堆百科。

## 5.1 Skill 动态加载怎么做

Skill 动态加载的目标是：让 Agent 在需要时才加载对应能力包，而不是把所有技能说明、模板和示例都塞进系统提示词。它解决的是上下文窗口、触发准确率和能力扩展问题。

一个常见架构：

```text
用户请求
-> 意图识别和任务分类
-> 检索 Skill 元数据
-> 选择候选 Skill
-> 读取 Skill 主文件
-> 按需读取引用资料、脚本或模板
-> 执行任务并记录轨迹
```

Skill 元数据通常包括：

1. `name`：稳定名称。
2. `description`：能力边界和典型触发语义。
3. `triggers`：关键词、任务类型、文件类型、工具需求等触发条件。
4. `permissions`：是否需要读文件、写文件、联网、调用生产系统。
5. `version`：用于灰度、回滚和评测对比。
6. `entrypoint`：主说明文件、脚本入口或模板路径。

核心设计点：

1. **先加载元数据，后加载正文**：元数据短小，适合常驻；正文和资料按需读取。
2. **触发要可解释**：记录为什么选中某个 skill，便于排查误触发。
3. **支持多 skill 编排**：例如“修 CI 并发 PR”可能同时需要 GitHub、调试和发布类 skill。
4. **冲突处理**：多个 skill 规则冲突时，系统规则优先，其次是更具体的 skill。
5. **缓存和版本**：热门 skill 可以缓存，但要按版本失效，避免旧流程长期生效。
6. **权限隔离**：加载 skill 不代表自动获得危险工具权限，写操作、生产操作仍要审批。
7. **评测闭环**：记录触发准确率、任务成功率、token 成本和工具误用率。

易错点：

1. 只靠关键词触发容易误加载，应该结合任务类型、上下文和文件类型。
2. skill 正文过长会抵消动态加载收益，应把大资料拆成引用文件。
3. skill 之间没有优先级会导致指令冲突。
4. 动态加载不能绕过全局安全规则，尤其是文件删除、生产写入和隐私数据访问。

真实项目里，Skill 动态加载常和上下文压缩一起使用：当前任务只保留已选 skill 的关键步骤、用户硬性约束、计划状态和工具结果摘要；完整资料通过路径或资源 ID 外部引用，需要时再读取。

## 6. MCP 是什么

MCP 可以理解为一种把外部工具、资源和数据源标准化暴露给模型的协议层。它解决的问题是：不同工具都要接入 Agent，如果每个工具都单独适配，成本高且权限难管。

MCP 类似一个工具网关：

```text
Agent
  -> MCP Client
  -> MCP Server
      -> GitHub / 数据库 / 文件系统 / 内部服务 / 搜索系统
```

它的价值：

1. 用统一方式描述工具能力和输入输出。
2. 让 Agent 能发现可用工具和资源。
3. 把权限、审计、连接配置收敛在服务端。
4. 方便企业把内部系统安全地接给 AI 应用。

### MCP 的使用场景

MCP 适合把“模型需要访问但不能直接裸连”的外部能力封装起来，尤其适合企业内部系统。

典型场景：

1. **知识库和文档系统**：把 Confluence、语雀、飞书文档、内部 Wiki 暴露成只读 resource，配合权限过滤和引用来源。
2. **代码研发**：接 Git 仓库、CI、测试平台、代码搜索和 issue 系统，让研发 Agent 可以查代码、跑测试、创建 PR。
3. **运维排障**：接日志、指标、trace、发布平台和告警系统，低风险查询只读开放，高风险处置走审批。
4. **客服和运营**：接订单、工单、CRM、商品、优惠券系统，查询类工具只读，退款、补偿、发券需要幂等和审批。
5. **数据分析**：接数仓、BI、指标平台，但要限制 SQL 模板、扫描量、脱敏字段和查询超时。
6. **个人或团队工具链**：把日历、邮件、任务系统、设计稿、云盘等能力统一接入 Agent。

不适合 MCP 直接承载的场景：

1. 高频低延迟主链路调用，MCP 的模型编排和权限开销可能太大。
2. 没有权限边界的万能 SQL、万能 shell、万能生产操作工具。
3. 需要强事务一致性的核心交易链路，MCP 只能做受控入口，不能替代业务事务。
4. 大批量数据搬运，应该用离线任务、数据同步或专门管道，不应把大量数据塞回模型上下文。

## 6.1 MCP 工具如何描述和定义

一个 MCP 工具至少要让模型知道三件事：这个工具能做什么、需要什么参数、返回什么结果。工程上通常会包含：

1. **name**：稳定、短小、语义明确，例如 `search_orders`、`create_ticket`。
2. **description**：说明使用场景、边界和注意事项，帮助模型判断何时调用。
3. **inputSchema**：用 JSON Schema 描述参数类型、必填字段、枚举、范围和默认值。
4. **output**：返回文本、结构化 JSON、资源 URI 或二进制内容的引用。
5. **权限和副作用说明**：是否只读，是否会写库、发消息、扣费或触发生产动作。

示例：

```json
{
  "name": "search_orders",
  "description": "按用户 ID 和时间范围查询订单摘要。只读工具，不返回敏感支付信息。",
  "inputSchema": {
    "type": "object",
    "properties": {
      "user_id": {
        "type": "string",
        "description": "业务系统中的用户 ID"
      },
      "start_time": {
        "type": "string",
        "description": "查询开始时间，ISO-8601 格式"
      },
      "end_time": {
        "type": "string",
        "description": "查询结束时间，ISO-8601 格式"
      },
      "limit": {
        "type": "integer",
        "minimum": 1,
        "maximum": 50,
        "default": 10
      }
    },
    "required": ["user_id", "start_time", "end_time"]
  }
}
```

工具描述要避免两个问题：

1. **过于宽泛**：例如 `execute_sql(sql)`，模型可能执行高风险 SQL，权限也难控制。
2. **过于含糊**：只写“查询订单”但不说明参数、返回范围、是否含隐私字段，模型容易误用。

更好的设计是把高风险能力拆成受限工具，例如 `query_order_summary` 只查摘要，`refund_order` 必须要求人工确认和幂等 key。

## 6.2 自己实现 MCP 工具的流程

可以按这个流程回答：

1. **确定工具边界**：只做单一能力，明确只读还是写操作。
2. **定义 schema**：参数类型、必填字段、范围、枚举和描述写清楚。
3. **实现 handler**：校验参数，调用内部服务或数据库，处理超时和错误。
4. **返回精简结果**：只返回模型决策需要的信息，不把大日志、大表全塞回上下文。
5. **权限控制**：按用户、租户、环境做鉴权，生产写操作要审计和确认。
6. **可观测性**：记录 tool name、调用耗时、错误码、trace id，不记录敏感明文。
7. **测试和回放**：准备典型输入、非法输入、空结果、超时和权限不足等用例。

真实企业里，MCP 工具最好是业务 API 的安全适配层，而不是让模型直接连生产数据库。这样可以复用已有权限、限流、审计和幂等机制。

## 6.3 复杂场景下 MCP 协议怎么设计

复杂场景下 MCP 不能只理解成“把函数暴露给模型”，它更像 Agent 和企业系统之间的协议边界。设计时要同时考虑能力发现、权限控制、长任务、错误语义和可观测性。

核心设计点：

1. **能力分层**：把 `tools`、`resources`、`prompts` 分清楚。Tool 用于执行动作，Resource 用于读取上下文或数据，Prompt 用于提供可复用模板。
2. **Schema 稳定性**：工具名、参数名和返回结构要版本化，避免模型或客户端升级后调用旧协议失败。
3. **权限和租户隔离**：每次调用都要带上用户、租户、环境和授权上下文，服务端不能只相信模型传入的参数。
4. **副作用声明**：只读、写操作、发消息、扣费、删除资源等能力要显式标注风险级别，高风险动作要求人工确认。
5. **长任务机制**：耗时任务不要阻塞一次调用，可以返回 `job_id`，再通过查询、订阅或回调获取进度和结果。
6. **取消和恢复**：长任务要支持 cancel、resume、checkpoint，避免用户中断后任务继续写入错误上下文。
7. **幂等和事务边界**：写操作使用 idempotency key；跨系统写入用 Saga 或补偿动作，不要假设所有工具都能本地事务回滚。
8. **错误模型**：区分参数错误、鉴权失败、业务失败、空结果、超时、限流和系统异常，让 Agent 能做不同恢复策略。
9. **分页和输出上限**：列表类接口必须支持分页、排序和字段裁剪，防止一次返回大量数据污染上下文。
10. **审计和追踪**：记录 trace id、tool name、调用人、参数摘要、耗时、错误码和审批记录，敏感字段只保存脱敏摘要。

一个更稳的返回结构可以设计成：

```json
{
  "ok": false,
  "error_code": "PERMISSION_DENIED",
  "message": "当前用户无权查看该订单",
  "retryable": false,
  "trace_id": "tr_123",
  "data": null
}
```

这样 Agent 可以根据 `retryable` 判断是否重试，根据 `error_code` 判断是补参数、换工具、请求授权还是停止任务。

## 6.4 Skill 和 Harness 的自我迭代本质

Skill 的自我迭代不是让模型“凭感觉变聪明”，而是把任务失败样本沉淀成可复现、可回放、可评测的改进循环。Harness 可以理解为运行和评测 Agent/Skill 的外层环境，负责准备输入、注入工具、采集轨迹、判断结果和回放回归集。

典型闭环：

```text
线上任务失败或人工反馈
-> 保存输入、上下文、工具调用轨迹和最终输出
-> 标注失败原因
-> 修改 skill 步骤、工具描述、约束或示例
-> 在 harness 中回放旧样本和新样本
-> 指标提升且无明显回归后发布
```

本质上它执行的是评测驱动优化：

1. **把隐性经验显性化**：把“这类任务应该先查日志再改代码”写进 skill。
2. **把偶发失败样本数据化**：保留最小复现输入和判定标准。
3. **把主观好坏指标化**：用成功率、工具误用率、token 成本、人工介入率衡量。
4. **把改动回归化**：新 skill 不能只修一个样本，还要避免破坏已有任务。

### Harness Engineering 怎么设计

Harness engineering 可以理解为给 Agent/Skill/Prompt 搭一个可重复运行的实验和回归环境。它不只是“写几条测试问题”，而是把输入、工具、环境、判定标准和轨迹采集都工程化。

核心组件：

1. **Case Store**：保存任务输入、用户约束、初始文件、知识库版本、期望结果和风险标签。
2. **Tool Mock / Sandbox**：对外部工具提供模拟返回或隔离执行环境，避免评测时真的发消息、扣费、改生产数据。
3. **Runner**：批量运行 Agent，控制模型版本、prompt 版本、skill 版本、随机种子、超时和成本上限。
4. **Judge**：用规则、单元测试、schema 校验、人工标注或 LLM-as-judge 判断结果。
5. **Trace Collector**：记录工具调用、参数、错误码、token、耗时、最终答案和中间状态。
6. **Regression Dashboard**：比较新旧版本在成功率、成本、延迟、安全违规、工具误用上的变化。

典型评测集：

1. 正常成功样本：验证常见任务是否能稳定完成。
2. 失败恢复样本：工具超时、权限不足、空结果、网络抖动。
3. 安全样本：提示词攻击、越权请求、敏感信息、危险工具。
4. 长上下文样本：早期约束、历史决策、长日志和多轮修正。
5. 回归样本：线上失败案例和人工纠错案例。

面试里可以说：Harness 的价值是让 Agent 自我纠正有证据。没有 harness，所谓“进化”只是改 prompt 后主观感觉变好；有 harness，才能证明新版本修复了哪些失败样本，是否破坏了旧任务，成本和风险有没有上升。

### Hermes 类 Agent 如何自我纠正和进化

如果面试里提到 Hermes Agent 这类“持续自我纠正”的系统，可以抽象成一个闭环：

```text
执行任务
-> 采集轨迹和结果
-> 判定成功/失败
-> 归因失败原因
-> 生成修正建议
-> 更新 prompt/skill/tool 描述/检索策略
-> harness 回放验证
-> 灰度发布
```

自我纠正发生在单次任务内：

1. 工具失败后根据错误码分类，而不是盲目重试。
2. 结果不满足验证条件时回到计划节点，修改策略。
3. 发现上下文不足时补充检索或请求用户澄清。
4. 多次失败后进入人工介入，而不是无限循环。

自我进化发生在任务之后：

1. 把失败样本沉淀进回归集。
2. 把稳定修复流程写进 skill 或 workflow。
3. 调整工具 schema 和错误语义，让模型更容易正确调用。
4. 优化 RAG 的查询改写、召回、重排和 Prompt。
5. 用 A/B、灰度和回放数据验证新策略确实提升。

易错点是让 Agent 自动改自己的生产规则并立即上线。自我进化必须经过版本管理、评测回放、人工审核和灰度；否则一个错误经验会被固化，放大到更多任务里。

## 6.5 Skill 如何评测好坏

评测 Skill 时不能只看单次回答是否顺眼，要比较“加载 skill”和“不加载 skill”在同一批任务上的差异。

常见指标：

1. **触发准确率**：该用时是否加载，不该用时是否误加载。
2. **任务成功率**：最终产物是否满足用户目标和硬性约束。
3. **工具调用质量**：工具是否选对、参数是否正确、是否避免危险工具。
4. **恢复能力**：工具失败、空结果、权限不足时是否能解释并选择合理下一步。
5. **上下文成本**：skill 引入后 token、时延和工具调用次数是否可接受。
6. **安全合规**：是否遵守权限、隐私、审批和沙箱要求。
7. **回归风险**：历史成功样本是否仍然成功。

真实项目里可以建立三类测试集：

1. **正例集**：必须触发该 skill 的典型任务。
2. **负例集**：相似但不该触发的任务，用于测误触发。
3. **压力集**：长上下文、工具失败、歧义输入、权限不足、多步骤恢复等复杂样本。

## 6.6 MCP 工具是不是越多越好

MCP 工具不是越多越好。工具越多，Agent 的能力边界更广，但选择成本、权限风险、上下文噪声和评测难度都会上升。

工具过多的风险：

1. **工具选择混乱**：多个工具描述相似，模型可能选错能力或重复调用。
2. **上下文成本变高**：工具 schema 和描述会占用上下文，降低任务相关信息比例。
3. **权限面扩大**：接入更多工具意味着更多潜在越权、误操作和审计压力。
4. **错误恢复复杂**：不同工具错误码和重试语义不统一，Agent 更难做稳定恢复。
5. **维护成本上升**：工具版本、字段兼容、废弃策略、测试样本都要维护。

更好的做法是按任务域暴露最小必要工具集：

1. 只读工具优先，写工具拆小并加审批。
2. 工具命名和描述要互斥清晰，避免多个工具都像“查询用户信息”。
3. 对高频复合能力可以封装成业务工具，而不是让 Agent 连续调用多个底层工具拼结果。
4. 根据用户、团队、租户、场景动态加载工具，而不是一次把全公司工具都暴露给模型。
5. 定期根据调用日志下线低价值、误用率高或风险过大的工具。

## 6.7 多团队多业务域 MCP 工具架构

多个外部团队接入 MCP 工具时，建议按业务域拆分 MCP Server，再用统一网关对外提供发现、鉴权、审计和路由。

```text
Agent / Client
  -> MCP Gateway
      -> Account MCP Server
      -> Payment MCP Server
      -> Content MCP Server
      -> Ops MCP Server
```

核心设计：

1. **业务域隔离**：账号、支付、内容、运维等能力分不同 server 或 namespace，避免一个工具集膨胀成全能服务。
2. **统一网关**：负责认证、租户识别、团队授权、限流、审计、工具目录和版本路由。
3. **按需工具清单**：A 团队只看到账号类工具，B 团队只看到支付类工具；工具发现结果由团队权限、场景和环境动态生成。
4. **权限分层**：只读、低风险写、高风险写分级；支付、退款、删除、生产变更必须有审批、幂等 key 和回滚策略。
5. **契约版本化**：工具名、参数、返回结构和错误码要版本化，旧客户端有迁移窗口。
6. **统一错误模型**：所有域返回 `ok/error_code/retryable/trace_id/data`，便于 Agent 做恢复。
7. **可观测和审计**：记录调用方、团队、工具、参数摘要、结果、耗时、审批和 trace id，敏感字段脱敏。
8. **独立发布**：各业务域 MCP Server 独立迭代，网关只维护目录、策略和路由，不把所有业务逻辑塞进一个进程。

真实企业里，MCP Server 应该是内部业务 API 的安全适配层。它不应绕过原有权限系统直接连库，也不应把生产写操作包装成无审批的“万能工具”。

## 6.8 多智能体如何协作

Multi-Agent 不是简单把多个大模型实例放在一起聊天，而是把一个复杂目标拆给多个有角色、工具和权限边界的 Agent，并通过协议协调它们的输入、输出和交接。

常见协作模式：

1. **Supervisor / Worker**：一个主控 Agent 负责拆任务、分配子任务、检查结果；多个 Worker Agent 各自处理检索、代码、测试、写作、数据分析等子任务。
2. **Pipeline**：上游 Agent 的输出成为下游 Agent 的输入，例如 Planner 产出计划，Executor 执行，Reviewer 审查，Reporter 总结。
3. **Critic / Reflexion**：一个 Agent 生成方案，另一个 Agent 从事实、风险、测试和约束角度批判，再由原 Agent 修改。
4. **Debate**：多个 Agent 针对同一问题提出不同假设，裁判 Agent 根据证据选择或融合结果。
5. **Blackboard / Shared Memory**：所有 Agent 读写同一个任务状态、证据库或中间产物，通过共享状态而不是长对话传递上下文。

协作协议要明确：

1. **任务契约**：每个 Agent 的目标、输入、输出格式、完成标准和失败语义。
2. **上下文裁剪**：只把该 Agent 需要的资料发给它，避免所有 Agent 都看到完整上下文导致成本和干扰上升。
3. **工具隔离**：检索 Agent 可以读知识库，执行 Agent 可以调用业务 API，高风险写操作只给少数 Agent 并加审批。
4. **状态同步**：共享任务状态要有版本、锁或追加日志，避免多个 Agent 覆盖彼此结论。
5. **终止条件**：限制最大轮次、最大工具调用次数和预算，防止循环委派。
6. **结果校验**：主控或 Reviewer 要检查引用、代码 diff、测试结果和业务约束，而不是直接相信子 Agent 输出。

真实场景里，多智能体适合长链路研发、复杂数据分析、客服工单分流、投研报告和运维排障。易错点是过度拆分：如果子任务高度耦合、共享状态频繁变化，多 Agent 的通信成本可能超过收益。

## 6.9 Agent 系统核心模块

设计一个 Agent 系统，可以按“接入层、规划层、执行层、记忆层、安全层、观测评测层”展开。

```text
用户请求
-> 会话/权限/配额
-> Planner 拆解任务
-> Memory/RAG 检索上下文
-> Tool Router 选择工具
-> Executor 执行和观察结果
-> Critic/Evaluator 校验
-> 最终回答或人工确认
```

核心模块：

1. **接入层**：处理用户身份、租户、会话、限流、配额、审计和多轮上下文。
2. **Planner**：把目标拆成步骤，决定是否需要检索、调用工具、委派子 Agent 或请求用户确认。
3. **Memory / Context**：管理短期会话、长期偏好、任务状态、外部知识检索结果和上下文压缩。
4. **Tool / MCP 层**：把文件、数据库、搜索、工单、业务 API 等能力封装成结构化工具，并处理权限、超时、重试和错误码。
5. **Executor Runtime**：执行计划、记录观察结果、处理工具失败、恢复任务和控制最大轮次。
6. **Guardrails**：做输入输出安全、敏感信息脱敏、越权检测、危险操作确认、幂等和回滚。
7. **Observability**：记录 prompt 版本、工具调用轨迹、trace id、耗时、token、错误和人工反馈。
8. **Evaluation**：用离线数据集和线上回放评估成功率、引用准确率、工具误用率、成本和安全违规率。
9. **Human-in-the-loop**：高风险写操作、低置信答案、权限不足和合规场景交给人工审批或接管。

面试里可以强调：Agent 的难点不只是“会调用模型”，而是如何把不稳定的模型输出收敛在可控的工程边界里。工具 schema、权限、可观测性、评测和人工确认，通常比 prompt 本身更决定系统能否上线。

## 7. 真实场景怎么用

### 代码研发 Agent

1. Rules：不能泄漏密钥；不能直接改生产配置；提交前要跑测试。
2. Tools：读写文件、代码搜索、运行测试、查看 Git diff、查询 CI。
3. Skills：修复 CI、做代码审查、迁移接口、补单元测试、写发布说明。
4. MCP：接 GitHub、Jira、知识库、CI 系统和内部代码搜索。

### 客服或运营 Agent

1. Rules：不能承诺退款；不能输出用户隐私。
2. Tools：查询订单、创建工单、发送模板消息。
3. Skills：退款咨询处理、投诉分级、物流异常排查。
4. MCP：接订单系统、工单系统、CRM 和知识库。

### RAG 问答 Agent

1. Rules：没有证据不回答；必须给引用来源。
2. Tools：向量检索、关键词检索、重排、权限过滤。
3. Skills：法律条款问答、故障手册检索、代码仓库问答。
4. MCP：接文档库、向量库、权限系统和审计系统。

## 8. 易错点

1. 不要把 Skill 说成简单 prompt。Skill 更像可复用工作流，可能包含脚本、模板和工具调用规范。
2. Tool 不等于 Skill。Tool 是外部能力接口，Skill 是指导 Agent 如何完成任务。
3. Rules 不等于 Skill。Rules 解决边界和规范，Skills 解决专项任务执行。
4. Skills 不是越多越好。过多、过宽、过长的 Skills 会增加匹配成本和上下文噪声。
5. Agent 不是完全自动化越权执行。真实企业场景必须有权限、审计、回滚和人工确认。

## 9. 面试回答模板

我理解的 Skills 是 AI Agent 的可复用能力包，它不是单个工具函数，也不是简单 prompt，而是把某类任务的触发条件、步骤、领域知识、模板和工具使用方式沉淀下来。Tool 更像函数，比如读文件、查数据库、跑测试；Skill 更像作业手册，比如如何修 CI、如何做代码审查；Rules 则是全局约束，比如不能泄漏密钥、生产操作要确认。

Skills 的好处是把经验流程标准化，减少模型每次从零规划，也能按需加载，降低无效上下文。但它不一定天然省 token，如果 skill 写得太长或触发过宽，反而会增加上下文成本。工程上要控制粒度、触发条件和权限边界。企业里通常会结合 MCP，把 GitHub、数据库、知识库、工单系统等工具标准化接入 Agent，再用 Rules 管风险，用 Skills 提升专项任务质量。

复杂 MCP 设计要把工具、资源和提示模板分层，明确 schema、版本、权限、副作用、长任务、取消恢复、幂等、错误码、分页和审计。Skill 和 harness 的自我迭代，本质是把失败样本、工具轨迹和人工反馈变成可回放的评测集，再修改 skill、工具描述或流程，并用回归集验证是否真的提升。评测 Skill 时要看触发准确率、任务成功率、工具调用质量、失败恢复能力、token 成本、安全合规和回归风险。
