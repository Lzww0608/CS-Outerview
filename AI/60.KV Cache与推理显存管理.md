# 60. KV Cache与推理显存管理

## 1. 问题背景

在大模型自回归推理中，每生成一个新 token 都需要对之前所有 token 做 Attention 计算。如果不缓存历史 token 的 Key/Value 状态，每步都要重新计算全部历史，计算量随序列长度线性增长。KV Cache 通过缓存历史 KV 状态避免重复计算，是 LLM 推理的核心优化技术。面试常考 KV Cache 的索引机制、显存管理策略、prefill/decode 阶段的差异，以及为什么相同 prompt 不会索引到同一 KV Cache。

**假设条件**：本文档基于 Transformer Decoder 架构的 LLM 推理场景，假设使用 vLLM/SGLang 等推理框架，GPU 为 A100/H100。

## 2. 问题现象

1. **显存占用随序列长度线性增长**：KV Cache 成为长序列推理的显存瓶颈
2. **相同 prompt 不共享 KV Cache**：用户疑惑为什么相同输入不命中缓存
3. **prefill 和 decode 性能差异大**：prefill 计算密集，decode 访存密集
4. **推理输出不确定**：相同 prompt 多次调用结果不同

## 3. 影响范围

| 影响维度 | 程度 | 说明 |
| --- | --- | --- |
| 推理吞吐 | 高 | KV Cache 显存直接决定最大并发数 |
| 首 Token 延迟 | 高 | prefill 阶段计算量与序列长度成正比 |
| 生成延迟 | 中 | decode 阶段每步只生成一个 token |
| 显存占用 | 高 | KV Cache 占推理总显存 50%+ |

## 4. 原因分析

### 4.1 KV Cache 原理

```
自回归推理过程：
  Step 1: 输入 [t1]        → 生成 t2，缓存 K1, V1
  Step 2: 输入 [t1,t2]     → 生成 t3，缓存 K1,V1, K2,V2
  Step 3: 输入 [t1,t2,t3]  → 生成 t4，缓存 K1~V3
  ...

无 KV Cache：每步重新计算所有历史 token 的 K/V → O(T²) 计算
有 KV Cache：只计算最新 token 的 K/V，历史从缓存读取 → O(T) 计算

KV Cache 大小估算（单层）：
  KV_Cache = 2 × batch_size × seq_len × num_heads × head_dim × sizeof(dtype)
  
  示例（Llama-2-70B, FP16）：
    num_kv_heads = 64, head_dim = 128
    单层 KV Cache / token = 2 × 64 × 128 × 2B = 32KB
    80 层 × 32KB = 2.56MB / token
    4096 token 序列 = ~10GB
```

### 4.2 相同 Prompt 为什么不会索引到同一 KV Cache

```
┌──────────────────────────────────────────────────────────┐
│        相同 Prompt 不共享 KV Cache 的原因                 │
├──────────────────────────────────────────────────────────┤
│ 1. 请求隔离性：不同请求的 KV Cache 物理上独立            │
│    → 安全隔离，防止一个请求读到另一个请求的缓存          │
│    → 请求结束后 KV Cache 立即释放                        │
│                                                          │
│ 2. Prefix Cache（可选优化）：                             │
│    → 只有完全相同的前缀部分可以复用 KV Cache             │
│    → 需要精确匹配，模糊/语义相似不能命中                 │
│    → vLLM 的 automatic prefix caching 支持此功能         │
│                                                          │
│ 3. 即使 prefix 相同，后续生成也不同：                    │
│    → 解码策略（top-k/top-p/temperature）引入随机性       │
│    → prefill 阶段的浮点计算本身也有微小差异              │
│    → 不同 batch size 下数值结果可能不同                   │
└──────────────────────────────────────────────────────────┘
```

### 4.3 大模型输出不确定性的来源

```
┌──────────────────────────────────────────────────────────┐
│           输出不确定性的三个来源                           │
├──────────────────────────────────────────────────────────┤
│ 1. 解码策略（最主要）                                    │
│    → temperature > 0 时 softmax 后概率分布非 one-hot     │
│    → top-k/top-p 截断后仍有多个候选 token               │
│    → 采样时的随机数种子不同                               │
│                                                          │
│ 2. Prefill 阶段的浮点非结合性                            │
│    → 并行计算 Attention 时，浮点加法不满足结合律         │
│    → 不同 batch size / CUDA stream 导致归约顺序不同      │
│    → 累积误差可能导致 softmax 后概率分布微小差异          │
│    → 这种差异在 greedy decoding (temperature=0) 时       │
│      也能导致不同 run 选择不同 token                     │
│                                                          │
│ 3. 硬件层面的不确定性                                    │
│    → GPU 并行计算的执行顺序不完全确定                    │
│    → FP16/BF16 的舍入误差随执行路径变化                  │
│    → Tensor Core 的矩阵乘结果与 CUDA Core 略有差异      │
└──────────────────────────────────────────────────────────┘
```

### 4.4 Prefill 与 Decode 阶段对比

```
┌──────────────────────────────────────────────────────┐
│           Prefill vs Decode 对比                     │
├────────────────┬─────────────┬───────────────────────┤
│ 维度           │ Prefill     │ Decode                │
├────────────────┼─────────────┼───────────────────────┤
│ 输入           │ 完整 prompt │ 单个新 token          │
│ 计算模式       │ 并行       │ 串行（逐步生成）      │
│ GEMM 形状      │ 大 M, 大 N │ M=1, N=vocab_size     │
│ 计算密集度     │ 计算密集   │ 访存密集              │
│ 瓶颈           │ 算力       │ 显存带宽              │
│ KV Cache       │ 写入       │ 读取 + 追加写入       │
│ 延迟特征       │ 首Token延迟│ 每 token 延迟         │
│ 优化方向       │ 并行计算   │ 减少权重读取、 batching│
│ Attention 复杂度│ O(S²)     │ O(S)（S 为已生成长度）│
└────────────────┴─────────────┴───────────────────────┘
```

### 4.5 显存管理策略

```
┌──────────────────────────────────────────────────────────┐
│              KV Cache 显存管理策略                        │
├──────────────────────────────────────────────────────────┤
│ 1. 静态预分配（vLLM 早期版本）                           │
│    → 为每个请求预分配最大长度的连续显存                   │
│    → 简单但浪费显存，碎片严重                            │
│                                                          │
│ 2. PagedAttention（vLLM 核心创新）                       │
│    → 类似 OS 的虚拟内存分页机制                          │
│    → KV Cache 按固定大小 block 分配（如 16 tokens/block）│
│    → Block Table 记录逻辑 block → 物理 block 映射       │
│    → 消除显存碎片，提高并发数 2~4x                      │
│                                                          │
│ 3. Continuous Batching                                   │
│    → 请求完成时立即释放 KV Cache，新请求立即可用         │
│    → 配合 PagedAttention 实现动态内存管理                │
│                                                          │
│ 4. Prefix Caching                                       │
│    → 相同前缀的请求共享 KV Cache block                   │
│    → 适用于 system prompt 相同的场景                     │
└──────────────────────────────────────────────────────────┘
```

## 5. 解决方案

| 方案 | 显存利用率 | 实现复杂度 | 吞吐提升 | 适用场景 |
| --- | --- | --- | --- | --- |
| 静态预分配 | 低（~30%） | 低 | 基线 | 简单场景 |
| PagedAttention | 高（~90%） | 高 | 2~4x | 通用推理服务 |
| Prefix Caching | 更高 | 中 | 额外 1.5~2x | System Prompt 场景 |
| KV Cache 量化 | 高 | 中 | 额外 1.2~1.5x | 极致压缩 |

## 6. 可选方案对比

| 维度 | PagedAttention | Prefix Cache | KV Cache 量化 |
| --- | --- | --- | --- |
| 显存节省 | 2~3x | 1.5~2x | 2~4x |
| 精度影响 | 无 | 无 | 微小 |
| 实现难度 | 高 | 中 | 中 |
| 兼容性 | vLLM/SGLang | vLLM | vLLM/SGLang |

## 7. 推荐方案

生产环境使用 **PagedAttention + Continuous Batching + Prefix Caching** 组合方案，vLLM 和 SGLang 均已原生支持。对精度不敏感的场景可额外开启 KV Cache 量化（FP8/INT8）。

## 8. 实施步骤

1. 评估当前推理服务的显存利用率和 KV Cache 占比
2. 部署 vLLM/SGLang 开启 PagedAttention
3. 开启 Continuous Batching 和 Prefix Caching
4. 监控 KV Cache 命中率、显存利用率、首 Token 延迟
5. 按需开启 KV Cache 量化

## 9. 风险与注意事项

- **KV Cache 量化可能影响长序列精度**：INT8 量化在超长上下文中误差累积
- **Prefix Cache 需要精确匹配**：一个 token 的差异就不能复用缓存
- **prefill 阶段的浮点非结合性**：不同框架/硬件的 prefill 结果可能有微小差异
- **temperature=0 不等于确定性输出**：prefill 的并行浮点计算仍可能引入差异

## 10. 验证方式

1. 显存利用率：`nvidia-smi` 监控 KV Cache 占用比例
2. 吞吐提升：对比开启/关闭 PagedAttention 的 QPS
3. 精度验证：对比 KV Cache 量化前后的输出质量（BLEU/ROUGE）
4. 不确定性验证：相同 prompt 多次调用，统计输出差异

## 11. 总结

KV Cache 是 LLM 推理的核心优化，避免重复计算历史 token 的 K/V 状态。面试常考：相同 prompt 不共享 KV Cache（请求隔离 + 浮点非结合性）、prefill/decode 的计算特征差异（计算密集 vs 访存密集）、输出不确定性的三个来源（解码策略、prefill 浮点误差、硬件不确定性）、显存管理策略（PagedAttention 分页管理 + Continuous Batching 动态调度）。理解 prefill 也有不确定性是面试加分点。
