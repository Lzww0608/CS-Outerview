# 64. RAG 知识库搭建全流程

面试题：RAG 知识库搭建全流程。考察对 RAG 工程化的理解，不止是"检索 + 生成"两句话，而是文档处理、切片策略、Embedding、向量库、检索、重排和 Prompt 拼接的完整链路。

## 1. RAG 完整执行流程

```text
用户查询
    |
    v
[查询改写] <- 可选：拆子问题、补充上下文、纠正错词
    |
    v
[多路召回] <- 向量检索 + 关键词检索 (BM25 / 全文索引)
    |
    v
[合并 / 去重]
    |
    v
[Rerank] <- 精排序，保留 Top-K
    |
    v
[上下文压缩] <- 去冗余、抽关键句、拼接 Prompt
    |
    v
[LLM 生成] <- 参考召回片段 + 指令
    |
    v
[引用校验] <- 检查生成内容是否在召回片段中
```

## 2. 知识库搭建全流程

### 2.1 资料收集与清洗

原始文档来源：PDF、Word、Markdown、HTML、数据库导出、API 接口。

清洗步骤：

1. 格式统一：转纯文本或 Markdown。
2. 去噪：去除页眉页脚、导航栏、广告、水印、注释标记。
3. 去重：相同内容不同版本保留最新，段落级别用 SimHash 或 MinHash 去重。
4. 敏感信息过滤：脱敏手机号、身份证、密钥。
5. 语言识别：混入非目标语言文档需要识别和过滤。

### 2.2 文档切分（Chunking）

切片策略决定了召回粒度。

| 策略 | 说明 | 适合场景 |
| --- | --- | --- |
| 固定长度切片 | 按 token 数切（如 512 tokens），overlap 10-20% | 通用问答、代码库 |
| 语义切片 | 按段落、标题、自然段落边界切 | 长文文档、书籍 |
| 递归字符切片 | LangChain 式：按 \n\n -> \n -> 句号递减优先级 | 多数场景的默认选择 |
| 父子切片 | 小 chunk 检索，大 chunk（父段落）给 LLM | 上下文需要完整段落时 |
| 结构化切片 | 按 Markdown heading 或 JSON 字段切 | 文档站点、API 文档 |

关键参数：

- **chunk_size**：512-1024 tokens。太小缺少上下文，太大增加噪声和 token 成本。
- **overlap**：chunk 间重叠 10-20%，防止切在关键句中间。
- **max_chunks_to_retrieve**：控制在 3-5 个 chunks 以内，避免上下文超长。
- **embedding_batch_size**：大批量文档 embedding 时的分批大小，防止 OOM。

### 2.3 Embedding 模型选型

Embedding 模型决定召回质量上限。选型要点：

1. **维度**：768D-1536D，维度高精度高但存储和检索成本也高。
2. **语言适配**：中文场景优先支持中文的模型。
3. **最大序列长度**：常见 512-8192 tokens，要和 chunk_size 匹配。
4. **对比**：text-embedding-3-small（1536D，通用）、bge-m3（支持多语言和多粒度）、m3e（中文友好）。

### 2.4 向量数据库选型

| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| FAISS（内存索引） | 速度快，支持多种索引类型 | 无持久化，无分布式，只适合离线场景 |
| Milvus | 分布式，支持标量过滤，生产级 | 运维复杂，资源消耗大 |
| Qdrant | Rust 实现，性能好，REST API | 集群部署需商业版 |
| Chroma | 轻量，快速启动，开发者友好 | 不适合大规模生产 |
| PostgreSQL + pgvector | 复用已有 PG 生态，支持 SQL | 大数据量查询效率不如专用向量库 |
| Elasticsearch 8.x | 原生向量支持，全文+混合检索 | 资源占用较高 |

选型依据：

- 几十万向量以内：pgvector 或 Chroma。
- 百万到千万：Milvus、Qdrant 或 ES 8.x。
- 十亿级以上：需要分布式 + 分片 + GPU 加速。

### 2.5 索引构建

```text
文档 -> 切片 -> 每条 chunk embedding -> 写入向量库
同时提取每条 chunk 的 metadata（标题、段落号、来源、时间）
```
metadata 用于权限过滤和引用展示，也是混合检索的关键。

建立索引时设置合适的 index 类型：

- **IVF_FLAT**：速度快，精度可接受，适合百万级。
- **HNSW**：图索引，检索精度高，适合千万级以下。
- **IVF_PQ**：量化压缩，适合大容量但精度有损失。

### 2.6 混合检索

纯向量检索在精确匹配（ID、地址、代码变量）场景可能不佳。

混合检索 = 向量检索 + 关键词检索（BM25/TF-IDF/全文索引）。

```text
Query
  -> 向量检索（语义匹配，Top-K1）
  -> 关键词检索（精确匹配，Top-K2）
  -> 合并去重
  -> Rerank 排序
```

BM25 在新版 Elasticsearch 中内置支持，向量库如 Milvus 也提供混合搜索接口。

### 2.7 Rerank（重排）

向量检索返回 Top-K（如 50 条），但 LLM 上下文窗口有限。Rerank 模型把 Top 50 精排成 Top 3-5。

Rerank 和 embedding 的区别：

| 维度 | Embedding | Reranker |
| --- | --- | --- |
| 输入 | 单条文本 | query + 候选文档对 |
| 输出 | 向量 | 相关性分数 |
| 计算量 | 可预先计算 | 每条查询实时计算 |
| 精度 | 中等 | 较高 |

推荐 reranker：bge-reranker-v2-m3、Cohere Rerank。注意 reranker 的计算成本高于 embedding，只在最终 Top-K 上做。

### 2.8 Prompt 拼接与生成

召回片段拼到系统提示词中：

```text
系统指令: 根据以下参考内容回答问题。如果参考内容不足以作答，请说明不知道。
参考内容：
[chunk_1]
[chunk_2]
[chunk_3]
---
用户问题：xxx
```

设计要点：

1. **引用来源**：每段 chunk 前标记来源（文档名、段落号），LLM 生成时引用。
2. **相关度标记**：低相关 chunk 前加 `[低相关]` 前缀，让 LLM 谨慎使用。
3. **长度控制**：控制召回总 token 数，留空间给指令和回复。
4. **指令清晰**：给出回答格式、引用风格、拒答条件。

### 2.9 引用校验

生成答案后，逐一检查 LLM 声称的引用是否在召回片段中可验证。如果 LLM 引用了不存在的内容，应删除该引用或拒答。这是防止 RAG 幻觉的最后关卡。

## 3. 知识库更新策略

| 策略 | 操作 | 场景 |
| --- | --- | --- |
| 全量重建 | 重新处理全部文档 | 初始建库、大规模内容更新 |
| 增量更新 | 新增文档直接 embedding 插入 | 日常文档新增 |
| 定时刷新 | 定期重新 embedding 旧文档 | 原 embedding 模型升级 |
| 实时更新 | 文档变更时立即更新 | 动态数据、实时知识库 |

增量更新涉及索引的增量构建。FAISS 不支持高效增量，IVF 类索引需要定期重建。Milvus 和 Qdrant 原生支持增量写入。

## 4. 评估指标

| 维度 | 指标 | 说明 |
| --- | --- | --- |
| 召回质量 | Recall@K、MRR、MAP | K 个召回中涵盖正确答案的比例 |
| 检索精度 | Precision@K | 前 K 个结果中相关的比例 |
| 排序质量 | NDCG | 考虑顺序的排序质量 |
| 端到端 | Answer Accuracy、Citation Hit Rate | 最终 LLM 答案正确率 |
| 延迟 | P50/P99 检索延迟 | 影响用户体验 |
| 覆盖率 | 文档级命中率 | 知识库内容是否被充分覆盖 |

## 5. 常见问题

1. **切片边界切断了关键信息**：增加 overlap 或改用语义切片。
2. **召回不相关**：优化 embedding 模型、加 Rerank、调整 chunk_size。
3. **知识库内容过时**：建更新 pipeline，设置文档过期时间。
4. **权限交叉**：metadata 带权限标签，检索时过滤。
5. **多轮对话丢失上下文**：每轮将历史问题和答案做查询改写，把原始问题转成独立 query 后再检索。
6. **长文档丢失细节**：用小 chunk 检索 + 父 chunk 生成策略。

## 6. 总结

RAG 知识库搭建流程就是：文档清洗 -> 切片 -> Embedding -> 建索引 -> 查询改写 -> 混合检索 -> Rerank -> 上下文压缩 -> Prompt 拼接 -> LLM 生成 -> 引用校验。质量瓶颈主要在切片策略和 Embedding 模型的选择，Rerank 能显著提升最终精度。线上了要持续监控检索召回率和答案正确率，按反馈调整切片参数、Rerank 阈值和 Prompt 模板。
