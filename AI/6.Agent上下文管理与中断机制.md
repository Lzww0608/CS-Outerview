# 6. Agent上下文管理与中断机制

Agent 项目里，“如何保持上下文”“多次 loop 怎么办”“超过上下文窗口怎么办”“如何中断正在执行的对话”都是核心工程问题。它们本质上是在有限上下文、外部工具调用和用户实时控制之间做状态管理。

## 1. Agent 的上下文包含什么

上下文不只是聊天记录，一般包括：

1. 系统指令和安全规则。
2. 用户当前目标和显式约束。
3. 历史对话摘要。
4. 当前任务计划和执行状态。
5. 工具调用参数和工具返回结果。
6. 外部检索到的文档片段。
7. 用户偏好、项目配置、权限信息。

工程上要区分短期上下文和长期记忆。短期上下文放在 prompt 中参与当前推理；长期记忆放在数据库、向量库、对象存储或业务系统里，按需召回。

## 2. 多次 loop 如何保持状态

Agent 常见执行模式是 ReAct 或 Plan-Execute：

```text
观察用户目标
-> 制定计划
-> 选择工具
-> 执行工具
-> 观察结果
-> 更新状态
-> 继续下一轮
```

每一轮 loop 都要保存结构化状态，而不是只依赖自然语言聊天历史。

建议保存：

1. `conversation_id`：对话 ID。
2. `run_id`：本次执行 ID。
3. `step_id`：当前执行步骤。
4. `plan`：任务计划和完成状态。
5. `tool_calls`：工具调用记录和结果摘要。
6. `artifacts`：生成的文件、图片、设计、查询结果等外部产物引用。
7. `checkpoint`：可恢复的中间状态。

这样 worker 重启、用户刷新页面或模型需要继续执行时，可以从 checkpoint 恢复。

## 3. 超过上下文窗口怎么办

上下文窗口有限，不能把所有历史、日志和工具结果一直塞进 prompt。常见策略：

1. **滑动窗口**：保留最近几轮对话，丢弃较早细节。
2. **摘要压缩**：把旧对话压缩成任务摘要、决策记录和未完成事项。
3. **结构化状态**：把计划、变量、约束保存成 JSON，而不是长篇自然语言。
4. **向量检索**：历史记录、文档、代码按需召回，不全量注入。
5. **工具结果裁剪**：大日志只保留错误片段、统计摘要和引用位置。
6. **分层记忆**：长期偏好、项目知识、当前任务状态分别存储和召回。
7. **引用外部产物**：大文件不进上下文，只保留路径、ID、摘要和检索入口。

压缩时要保留：

1. 用户目标和硬性约束。
2. 已经做出的关键决策。
3. 当前计划和未完成步骤。
4. 外部资源 ID、文件路径、版本号。
5. 错误原因和已经排除的方案。

不要保留：

1. 大段重复日志。
2. 已经过期的中间推理。
3. 与当前目标无关的寒暄。
4. 可通过工具重新查询的大量原文。

## 4. 如何降低 token

降低 token 的核心不是简单截断，而是让模型只看到当前决策必需的信息。

常见做法：

1. **状态结构化**：把计划、约束、决策、错误原因保存成 JSON 或表格，减少长篇自然语言复述。
2. **结果摘要化**：工具返回大日志时只保留错误栈、失败用例、关键统计和定位链接。
3. **按需检索**：历史对话、知识库、代码文件只在相关时召回，避免全量塞入 prompt。
4. **去重和归并**：重复约束、重复报错、重复搜索结果只保留一次，并标明出现次数。
5. **外部引用**：大文件、大 diff、大网页用路径、URL、chunk id 和摘要引用，必要时再读取。
6. **输出预算**：对模型输出设置格式和长度边界，避免每轮都生成冗长解释。
7. **缓存稳定前缀**：系统提示词、工具说明、项目规则等稳定内容可以利用 prompt cache 或服务端缓存。

易错点是只按时间丢弃旧上下文。旧消息里可能包含用户硬性约束，例如“不要改数据库结构”“必须兼容 Windows”，这类约束即使很早出现也要进入结构化状态。

## 4.1 上下文压缩的工程落地

上下文压缩不是简单让模型“总结一下历史记录”，而是把长对话和工具轨迹压成下一步决策真正需要的状态。

推荐把压缩结果分层：

1. **任务摘要**：用户目标、硬性约束、验收标准。
2. **计划状态**：已完成步骤、当前步骤、阻塞点和下一步。
3. **事实表**：已经确认的环境信息、文件路径、接口名、错误原因。
4. **决策记录**：为什么选择某个方案，哪些方案已经排除。
5. **外部引用**：大文件、长日志、网页、工具结果只保留路径、ID、行号或摘要。

压缩策略：

1. 对聊天消息按轮次做滑动窗口，保留最近交互。
2. 对工具结果按类型裁剪，日志保留错误片段，代码搜索保留文件和行号，长文档保留章节摘要。
3. 对用户约束做去重归并，并标记优先级。
4. 对中间推理不长期保存，只保留对外可验证的结论和证据。
5. 每次压缩后可以用规则校验，例如是否仍包含用户目标、未完成任务、关键文件路径和风险提示。

评估压缩质量时，可以用同一批长任务对比压缩前后：

1. 是否丢失早期硬性约束。
2. 是否还能正确选择下一步工具。
3. 是否保留足够证据支持最终回答。
4. token 成本和延迟是否下降。
5. 压缩摘要是否引入了原文没有的错误事实。

## 5. 短期记忆如何转化为长期记忆

短期记忆是当前 run 中的临时上下文，长期记忆是跨会话可复用的事实、偏好、经验或产物索引。二者不能简单等同，长期记忆必须经过筛选和整理。

推荐流程：

```text
对话和工具轨迹
-> 抽取候选记忆
-> 重要性和安全性过滤
-> 摘要与结构化
-> 存入数据库 / 向量库 / 知识库
-> 后续按需召回
-> 根据反馈更新或过期
```

可以沉淀为长期记忆的内容：

1. 用户明确偏好，例如常用语言、代码风格、输出格式。
2. 项目稳定事实，例如仓库结构、构建命令、测试入口。
3. 任务决策记录，例如为什么选择某个架构方案。
4. 可复用失败经验，例如某类工具报错的恢复步骤。
5. 外部产物索引，例如文件路径、设计 ID、知识库文档 ID。

不应该长期保存：

1. 临时中间推理和已失效假设。
2. 未经用户授权的隐私信息。
3. 密钥、token、密码、身份证等敏感明文。
4. 只对本轮任务有用的日志全文。

工程上要给长期记忆加 `source`、`created_at`、`updated_at`、`confidence`、`scope`、`ttl` 和权限字段。召回时先做权限过滤，再根据任务相关性注入上下文。

## 6. 上下文设计如何评测

上下文管理质量要通过任务集评测，而不是只看 prompt 是否整洁。

常见指标：

1. **任务成功率**：长对话后是否仍能完成用户目标。
2. **约束保持率**：早期硬性约束是否在后续步骤中仍被遵守。
3. **召回命中率**：需要历史信息时，是否能召回正确记忆或文档。
4. **上下文利用率**：注入的内容是否真的被答案或工具调用使用。
5. **token 成本**：平均输入 token、输出 token 和压缩后节省比例。
6. **恢复能力**：worker 重启、用户刷新、工具失败后能否从 checkpoint 继续。
7. **延迟和稳定性**：摘要、检索、重排和缓存是否引入不可接受的时延。

测试集最好覆盖短任务、长任务、多轮纠错、用户中断、上下文超过窗口、历史约束召回、错误工具结果污染等场景。只有在这些场景下表现稳定，才能说明上下文设计可靠。

## 7. 如何实现用户中断

用户中断正在执行的对话，可以借鉴操作系统中断思想：当前执行流收到中断信号后，保存必要状态，停止或挂起旧任务，把控制权交还给新的用户请求。

工程实现可以分为四层：

1. **前端层**：用户点击停止或发送新消息，前端带上当前 `run_id` 发起 cancel。
2. **调度层**：把该 `run_id` 标记为 `cancelling/cancelled`，后续 step 不再调度。
3. **执行层**：通过 cancellation token、context cancel、AbortController 等机制通知模型请求、工具调用和 worker。
4. **结果层**：旧 run 返回的迟到结果要检查 run 状态，如果已取消就丢弃，不能写回新对话。

流程：

```text
用户点击中断
-> cancel(run_id)
-> 设置取消标志
-> 取消可取消的 LLM/HTTP/工具调用
-> 不可取消任务继续后台完成但结果作废
-> 保存中断摘要和资源清理状态
-> 新消息创建新的 run_id
```

## 8. 和操作系统中断的类比

| 操作系统中断 | Agent 中断 |
| --- | --- |
| 中断请求 IRQ | 用户点击停止或发送新消息 |
| 保存现场 | 保存 conversation/run/step/checkpoint |
| 中断服务例程 | cancel handler，清理资源和更新状态 |
| 恢复或调度新任务 | 开启新 run，继续或重建上下文 |
| 屏蔽和优先级 | 高风险工具不可强杀时标记结果作废 |

这个类比能帮助回答“如何开启新对话”：新对话最好有新的 `conversation_id`；如果是在同一对话中打断旧回答，则至少要有新的 `run_id`，避免旧工具结果污染新一轮状态。

## 9. 易错点

1. 只在前端停止显示不等于后端任务已取消。
2. 工具调用可能不可强制取消，必须用 run 状态检查丢弃迟到结果。
3. 中断后要释放资源，例如临时文件、锁、浏览器会话、数据库连接。
4. 新旧对话要隔离 `conversation_id`、`run_id` 和上下文缓存。
5. 压缩上下文不能丢用户硬性约束，否则后续回答会偏离目标。
6. 取消写操作要考虑幂等和补偿，不能在半执行状态留下脏数据。
7. 长期记忆不能无条件写入，必须考虑权限、隐私、有效期和错误记忆污染。

## 10. 面试回答模板

我会把 Agent 的上下文分成短期 prompt 上下文和长期外部状态。短期保留最近消息、当前目标、计划和必要工具结果；长期把稳定偏好、项目事实、历史摘要、工具结果和产物 ID 存到数据库或向量库。超过上下文窗口时，不是简单截断，而是做滑动窗口、摘要压缩、结构化状态、按需检索、工具结果裁剪和外部产物引用，重点保留用户硬性约束、关键决策、当前计划、资源 ID 和已排除的错误方案。

短期记忆转长期记忆时要先抽取候选事实，再做重要性、安全性、权限和有效期过滤，不能把临时推理、敏感信息和错误假设长期保存。上下文设计可以用任务成功率、约束保持率、召回命中率、上下文利用率、token 成本、恢复能力和延迟来评测。

用户中断可以类比操作系统中断。前端发送 cancel 当前 `run_id`，调度器设置取消状态，执行层通过 cancellation token 取消 LLM 请求和可取消工具；不可取消的任务即使后来返回，也要检查 run 状态并丢弃结果，不能污染新对话。然后新请求创建新的 `run_id` 或新的 `conversation_id`，从保留的用户目标和摘要重新开始。
