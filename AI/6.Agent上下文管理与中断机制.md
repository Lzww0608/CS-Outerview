# 6. Agent上下文管理与中断机制

Agent 项目里，“如何保持上下文”“多次 loop 怎么办”“超过上下文窗口怎么办”“如何中断正在执行的对话”都是核心工程问题。它们本质上是在有限上下文、外部工具调用和用户实时控制之间做状态管理。

## 1. Agent 的上下文包含什么

上下文不只是聊天记录，一般包括：

1. 系统指令和安全规则。
2. 用户当前目标和显式约束。
3. 历史对话摘要。
4. 当前任务计划和执行状态。
5. 工具调用参数和工具返回结果。
6. 外部检索到的文档片段。
7. 用户偏好、项目配置、权限信息。

工程上要区分短期上下文和长期记忆。短期上下文放在 prompt 中参与当前推理；长期记忆放在数据库、向量库、对象存储或业务系统里，按需召回。

## 1.1 单 Session 下如何保证主题连贯

很多 AI 产品的用户会习惯一直在同一个 session 里聊天，因此不能简单假设“同一 session = 同一任务”。比如用户先问“原神圣遗物怎么配”，下一句问“崩铁这个角色呢”，这不是突然从游戏跳到经济，而是从一个游戏子领域切到另一个相关游戏子领域。系统要做的是维护**会话连续性**，同时识别**话题边界和指代关系**。

可以把同一 session 的上下文拆成三层：

| 层级 | 内容 | 作用 |
| --- | --- | --- |
| 全局会话上下文 | 用户画像、语言偏好、当前产品入口、历史摘要 | 保持整体交互风格和跨轮偏好 |
| 当前话题上下文 | 最近实体、领域、意图、约束、未完成问题 | 支撑连续追问和省略指代 |
| 话题片段 Topic Segment | 某一段连续讨论的实体集合和结论 | 切换话题后仍可按需召回 |

处理流程可以是：

```text
新消息
-> 意图和实体识别
-> 和最近 Topic Segment 计算相关性
-> 判断是延续、弱切换、强切换还是新任务
-> 选择要注入的最近消息、话题摘要、长期记忆和外部知识
-> 如果实体或约束不明确，再追问用户
```

判断是否延续当前话题时，可以综合：

1. **实体连续性**：原神、崩铁、角色、装备、抽卡都属于游戏域，但实体不同。
2. **意图连续性**：都在问角色培养、配队、攻略，通常可以继承“回答风格”和用户偏好。
3. **代词和省略**：用户说“这个角色”“那套方案”时，要回看最近实体；如果最近有多个候选，要追问。
4. **时间间隔和交互动作**：短时间连续问更可能延续，长时间后回来要降低历史权重。
5. **显式切换信号**：用户说“换个问题”“不聊游戏了”“再问个经济问题”，应开启新话题片段。

工程上可以维护一个结构化的 `conversation_state`：

```json
{
  "conversation_id": "c1",
  "active_topic_id": "topic_game_002",
  "topics": [
    {
      "topic_id": "topic_game_001",
      "domain": "game",
      "entities": ["原神", "胡桃", "圣遗物"],
      "summary": "用户在问原神角色培养和圣遗物搭配",
      "last_active_at": "2026-05-24T10:00:00+08:00"
    },
    {
      "topic_id": "topic_game_002",
      "domain": "game",
      "entities": ["崩铁", "黄泉", "遗器"],
      "summary": "用户切到崩铁角色养成，但仍是游戏攻略意图",
      "last_active_at": "2026-05-24T10:03:00+08:00"
    }
  ]
}
```

易错点：

1. 不要把整个 session 的所有历史都塞进 prompt，否则成本高且容易互相干扰。
2. 不要只按时间裁剪，早期的硬性偏好可能仍然重要。
3. 不要把弱相关话题完全割裂，例如原神和崩铁在用户偏好、术语、回答格式上可能可复用。
4. 不要把跨话题记忆写成长期事实，用户这次问游戏攻略不代表长期偏好就是游戏。
5. 不要在实体歧义时强行继承上下文，应通过追问或候选确认降低误答。

面试回答可以说：同一个 session 里我会做 topic segmentation，而不是简单保留全部历史。每条新消息先识别意图、实体和领域，再和当前话题摘要计算相关性，决定是延续、弱切换还是新任务。上下文构建时只注入当前话题必要的最近消息、结构化状态和相关历史摘要；对跨话题但同领域的内容，只复用回答偏好和少量背景，不把具体实体混进来。这样既能保证“原神 -> 崩铁”这种相关切换的连贯性，也能避免经济、代码、游戏等不同话题互相污染。

## 1.2 任务状态、短期上下文和长期记忆怎么分层

Agent 长任务里，“任务状态”和“记忆”不能混在一起。任务状态是运行时正确性的一部分，必须可恢复、可审计；记忆是帮助模型推理的辅助信息，可以按需召回。

分层方式：

| 层级 | 存什么 | 存哪里 | 作用 |
| --- | --- | --- | --- |
| 短期上下文 | 最近对话、当前目标、当前 step、必要工具结果 | Prompt / 上下文窗口 | 支撑当前一轮推理 |
| 任务状态 | `run_id`、`step_id`、状态机节点、外部任务 ID、审批状态、checkpoint、retry_count | MySQL/PostgreSQL/Redis durable store/工作流引擎 | 宕机恢复、断点续跑、审计 |
| 长期记忆 | 稳定偏好、项目事实、历史经验、产物索引 | 数据库/向量库/知识库 | 跨会话复用 |
| 外部产物 | 日志、报告、Jenkins build URL、文件、截图 | 对象存储/制品库/CI 系统 | 通过 ID 引用，不全文塞入上下文 |

为什么任务状态不要只放 memory：

1. memory 可能被压缩、淘汰或召回失败，不能承担正确性。
2. worker 重启、会话断开、模型上下文丢失时，任务状态必须仍能恢复。
3. 任务状态需要支持条件更新、乐观锁、租约、超时和审计，这些是数据库或工作流引擎的职责。
4. 长期记忆可能被错误事实污染，而任务状态必须以结构化、可验证字段为准。

例如 Jenkins Agent 至少要持久化 `run_id、config_hash、jenkins_queue_id、build_number、status、checkpoint、retry_count、last_error`。对话上下文里只保留这些字段的摘要和下一步动作，不把完整日志长期塞进 prompt。

## 2. 多次 loop 如何保持状态

Agent 常见执行模式是 ReAct 或 Plan-Execute：

```text
观察用户目标
-> 制定计划
-> 选择工具
-> 执行工具
-> 观察结果
-> 更新状态
-> 继续下一轮
```

每一轮 loop 都要保存结构化状态，而不是只依赖自然语言聊天历史。

建议保存：

1. `conversation_id`：对话 ID。
2. `run_id`：本次执行 ID。
3. `step_id`：当前执行步骤。
4. `plan`：任务计划和完成状态。
5. `tool_calls`：工具调用记录和结果摘要。
6. `artifacts`：生成的文件、图片、设计、查询结果等外部产物引用。
7. `checkpoint`：可恢复的中间状态。

这样 worker 重启、用户刷新页面或模型需要继续执行时，可以从 checkpoint 恢复。

## 3. 超过上下文窗口怎么办

上下文窗口有限，不能把所有历史、日志和工具结果一直塞进 prompt。常见策略：

1. **滑动窗口**：保留最近几轮对话，丢弃较早细节。
2. **摘要压缩**：把旧对话压缩成任务摘要、决策记录和未完成事项。
3. **结构化状态**：把计划、变量、约束保存成 JSON，而不是长篇自然语言。
4. **向量检索**：历史记录、文档、代码按需召回，不全量注入。
5. **工具结果裁剪**：大日志只保留错误片段、统计摘要和引用位置。
6. **分层记忆**：长期偏好、项目知识、当前任务状态分别存储和召回。
7. **引用外部产物**：大文件不进上下文，只保留路径、ID、摘要和检索入口。

压缩时要保留：

1. 用户目标和硬性约束。
2. 已经做出的关键决策。
3. 当前计划和未完成步骤。
4. 外部资源 ID、文件路径、版本号。
5. 错误原因和已经排除的方案。

不要保留：

1. 大段重复日志。
2. 已经过期的中间推理。
3. 与当前目标无关的寒暄。
4. 可通过工具重新查询的大量原文。

### 3.1 滑动窗口和其他上下文存储方法

大模型的“滑动窗口”通常指在上下文窗口有限时，只保留最近一段消息或最近若干 token，把更早的内容淘汰或压缩。它实现简单，适合闲聊、短任务和最近上下文最重要的场景；缺点是容易丢掉早期硬性约束、重要决策和外部资源 ID。

除了滑动窗口，常见上下文存储方式还有：

| 方法 | 原理 | 适用场景 | 风险 |
| --- | --- | --- | --- |
| 滑动窗口 | 保留最近 N 轮或 N tokens | 短对话、最近信息更重要 | 早期约束丢失 |
| 滚动摘要 | 旧消息压缩成摘要，新消息保留原文 | 长对话、客服、Agent 长任务 | 摘要可能漏事实或引入错误 |
| 结构化状态 | 把目标、计划、变量、约束保存成 JSON | 工具调用、工作流、任务续跑 | 设计不好会漏掉非结构化细节 |
| 向量记忆 | 历史消息或文档 embedding 后按需召回 | 历史知识、项目记忆、RAG | 召回不稳定，需要权限过滤 |
| 外部产物引用 | 大文件、日志、报告只保存 ID/路径/摘要 | 代码、CI 日志、PDF、图片 | 需要工具可重新读取 |
| 层级记忆 | 短期上下文、任务状态、长期记忆分层 | Agent 系统、企业助手 | 权限和过期策略复杂 |
| Prompt cache | 稳定前缀由服务端缓存 | 固定系统提示词、工具说明 | 只省成本/延迟，不解决遗忘 |

面试里可以强调：滑动窗口是最低成本方案，但不能承担任务正确性。长任务必须把“不可丢失的信息”结构化持久化，例如用户目标、约束、当前计划、外部任务 ID、审批状态和资源路径；大段历史和工具结果则摘要化或外部化。

### 3.2 GPT 上下文长度怎么回答

“GPT 支持多长上下文”不能给一个永久固定数字，因为不同模型、不同 API、不同版本的上下文窗口不同。回答时要说“看具体模型”。截至 2026-05-04，OpenAI 官方 Models 页面显示：`gpt-5.5` 和 `gpt-5.4` 的 Context window 为 1M，`gpt-5.4-mini` 为 400K；`gpt-4.1` 页面显示 1,047,576 context window；旧 `gpt-5` 页面显示 400,000 context window。具体项目中应以官方 Models 页面和当前账号可用模型为准：https://developers.openai.com/api/docs/models

面试时更稳的回答是：

1. 不同 GPT 模型上下文不同，旧模型可能是 8K/32K/128K，新模型可以到数十万甚至百万 token。
2. 上下文窗口不是“可无限有效利用”的保证，越长越要关注注意力稀释、位置偏置、成本和延迟。
3. 超长文档处理通常不会简单全塞进去，而是结合 RAG、摘要、分块、层级索引、Map-Reduce、递归压缩和工具查询。
4. 如果必须处理几十万 token，要把任务拆成“定位相关内容 -> 局部精读 -> 全局综合”，并做引用和校验。

### 3.3 几万到几十万数据如何处理

面对几万甚至几十万 token 的输入，常见处理方式不是单一“扩大窗口”，而是组合策略：

1. **分块检索**：把文档切成 chunk 建索引，先召回相关片段，再交给模型。
2. **层级摘要**：先对章节、文件、日志段分别摘要，再对摘要做二级综合。
3. **Map-Reduce**：每个分片独立抽取答案候选，最后归并、去重、冲突检测。
4. **Refine**：模型按顺序读取片段，逐步更新答案草稿，适合长报告总结。
5. **窗口化扫描**：用重叠窗口滑过长文本，抽取实体、错误、事件，再汇总。
6. **结构化解析**：表格、日志、JSON、代码先用解析器或 SQL/脚本处理，模型只看统计和异常片段。
7. **外部工具查询**：数据库、搜索引擎、代码索引、日志平台负责定位，模型负责解释和生成。

真实工程中要同时评估准确率、引用准确率、漏召回率、token 成本、P95 延迟和隐私权限。长上下文是能力上限，不是架构替代品。

## 4. 如何降低 token

降低 token 的核心不是简单截断，而是让模型只看到当前决策必需的信息。

常见做法：

1. **状态结构化**：把计划、约束、决策、错误原因保存成 JSON 或表格，减少长篇自然语言复述。
2. **结果摘要化**：工具返回大日志时只保留错误栈、失败用例、关键统计和定位链接。
3. **按需检索**：历史对话、知识库、代码文件只在相关时召回，避免全量塞入 prompt。
4. **去重和归并**：重复约束、重复报错、重复搜索结果只保留一次，并标明出现次数。
5. **外部引用**：大文件、大 diff、大网页用路径、URL、chunk id 和摘要引用，必要时再读取。
6. **输出预算**：对模型输出设置格式和长度边界，避免每轮都生成冗长解释。
7. **缓存稳定前缀**：系统提示词、工具说明、项目规则等稳定内容可以利用 prompt cache 或服务端缓存。

易错点是只按时间丢弃旧上下文。旧消息里可能包含用户硬性约束，例如“不要改数据库结构”“必须兼容 Windows”，这类约束即使很早出现也要进入结构化状态。

## 4.1 上下文压缩的工程落地

上下文压缩不是简单让模型“总结一下历史记录”，而是把长对话和工具轨迹压成下一步决策真正需要的状态。

推荐把压缩结果分层：

1. **任务摘要**：用户目标、硬性约束、验收标准。
2. **计划状态**：已完成步骤、当前步骤、阻塞点和下一步。
3. **事实表**：已经确认的环境信息、文件路径、接口名、错误原因。
4. **决策记录**：为什么选择某个方案，哪些方案已经排除。
5. **外部引用**：大文件、长日志、网页、工具结果只保留路径、ID、行号或摘要。

压缩策略：

1. 对聊天消息按轮次做滑动窗口，保留最近交互。
2. 对工具结果按类型裁剪，日志保留错误片段，代码搜索保留文件和行号，长文档保留章节摘要。
3. 对用户约束做去重归并，并标记优先级。
4. 对中间推理不长期保存，只保留对外可验证的结论和证据。
5. 每次压缩后可以用规则校验，例如是否仍包含用户目标、未完成任务、关键文件路径和风险提示。

评估压缩质量时，可以用同一批长任务对比压缩前后：

1. 是否丢失早期硬性约束。
2. 是否还能正确选择下一步工具。
3. 是否保留足够证据支持最终回答。
4. token 成本和延迟是否下降。
5. 压缩摘要是否引入了原文没有的错误事实。

## 4.2 30 轮裁剪和长链路续接

“30 轮裁剪”不能理解成固定保留最后 30 轮、前面全部丢弃。更稳的做法是把上下文分成可丢弃历史和不可丢失状态。

可以这样裁剪：

1. **最近窗口**：保留最近若干轮用户输入、模型决策和关键工具反馈。
2. **结构化状态常驻**：用户目标、硬性约束、当前计划、未完成步骤、风险边界、外部任务 ID 始终保留。
3. **历史摘要滚动更新**：超过窗口的对话压缩成阶段摘要、决策记录和失败排除列表。
4. **工具结果外部化**：长日志、Jenkins 控制台输出、测试报告只保留 URL、build number、错误片段和摘要。
5. **按需召回**：需要早期细节时，用 `conversation_id/run_id/artifact_id` 到外部存储重新取。

复杂任务超过 30 轮时，续接流程可以是：

```text
读取 run 状态
-> 读取最近窗口
-> 读取滚动摘要
-> 按当前 step 召回相关 artifact 和历史决策
-> 重新构造 prompt
-> 从 checkpoint 继续执行
```

保证压缩不丢关键任务信息，可以做三类校验：

1. **字段校验**：摘要必须包含目标、约束、当前状态、下一步、外部任务 ID、风险和阻塞点。
2. **证据校验**：关键结论要带来源，例如日志 URL、文件路径、行号、Jenkins build URL。
3. **回放校验**：用压缩后的上下文让 Agent 继续执行固定长任务，观察是否还能正确选择工具和遵守早期约束。

易错点是把“旧上下文”全部压成自然语言摘要。面试里可以强调：摘要只是给模型读的，真正的任务状态要结构化持久化，外部产物要可重新读取，这样压缩丢失的信息才有机会被恢复。

## 5. 短期记忆如何转化为长期记忆

短期记忆是当前 run 中的临时上下文，长期记忆是跨会话可复用的事实、偏好、经验或产物索引。二者不能简单等同，长期记忆必须经过筛选和整理。

推荐流程：

```text
对话和工具轨迹
-> 抽取候选记忆
-> 重要性和安全性过滤
-> 摘要与结构化
-> 存入数据库 / 向量库 / 知识库
-> 后续按需召回
-> 根据反馈更新或过期
```

可以沉淀为长期记忆的内容：

1. 用户明确偏好，例如常用语言、代码风格、输出格式。
2. 项目稳定事实，例如仓库结构、构建命令、测试入口。
3. 任务决策记录，例如为什么选择某个架构方案。
4. 可复用失败经验，例如某类工具报错的恢复步骤。
5. 外部产物索引，例如文件路径、设计 ID、知识库文档 ID。

不应该长期保存：

1. 临时中间推理和已失效假设。
2. 未经用户授权的隐私信息。
3. 密钥、token、密码、身份证等敏感明文。
4. 只对本轮任务有用的日志全文。

工程上要给长期记忆加 `source`、`created_at`、`updated_at`、`confidence`、`scope`、`ttl` 和权限字段。召回时先做权限过滤，再根据任务相关性注入上下文。

## 5.1 记忆持久化怎么实现

记忆持久化不是把完整聊天记录原样塞进数据库，而是把可复用的信息抽取成有边界、有来源、可过期、可删除的结构化资产。

常见存储分层：

| 存储 | 适合内容 | 说明 |
| --- | --- | --- |
| Redis | 当前会话、短期缓存、运行中 run 状态 | 延迟低，但不能单独承担长期事实来源 |
| MySQL/PostgreSQL | 用户偏好、项目配置、任务 checkpoint、审计记录 | 结构化强，适合事务和权限过滤 |
| 向量数据库 | 历史摘要、文档片段、经验记录 | 适合语义召回，但要配合元数据过滤和重排 |
| 对象存储 | 大日志、截图、报告、生成文件 | 上下文里只保留 ID、路径和摘要 |
| 事件日志 | 工具调用、审批、状态流转 | 便于回放、排错和评测 |

写入流程：

```text
对话/工具结果
-> 抽取候选记忆
-> 分类为事实、偏好、任务状态、经验或产物索引
-> 权限和敏感信息过滤
-> 去重、合并、版本化和设置 ttl
-> 写入结构化库 / 向量库 / 对象存储
-> 记录 source、confidence、scope 和审计日志
```

读取流程：

```text
当前任务目标
-> 根据 user_id/project_id/conversation_id 过滤权限范围
-> 召回结构化偏好和任务状态
-> 向量检索相关历史摘要和知识片段
-> 重排、去重、压缩
-> 注入 prompt 的固定位置
```

一个记忆记录可以设计成：

```json
{
  "memory_id": "mem_123",
  "user_id": "u1",
  "scope": "project",
  "type": "preference",
  "content": "用户希望回答默认使用中文，并给出修改文件摘要",
  "source": "conversation:2026-05-02:run_8",
  "confidence": 0.92,
  "created_at": "2026-05-02T10:00:00+08:00",
  "ttl": null
}
```

易错点：

1. **任务状态不等于长期记忆**：库存扣减、审批状态、外部 job id 这类正确性状态要进事务库或工作流引擎，不能只靠语义记忆召回。
2. **记忆要有权限边界**：个人偏好、项目事实、组织知识不能混用，否则会出现越权泄漏。
3. **记忆要能删除和过期**：错误事实、临时路线、过期配置不能永久影响后续回答。
4. **召回要可解释**：关键记忆最好带来源，方便用户纠错和系统审计。
5. **不要保存敏感明文**：token、密码、身份证、隐私聊天内容要过滤或脱敏。

## 6. 上下文设计如何评测

上下文管理质量要通过任务集评测，而不是只看 prompt 是否整洁。

常见指标：

1. **任务成功率**：长对话后是否仍能完成用户目标。
2. **约束保持率**：早期硬性约束是否在后续步骤中仍被遵守。
3. **召回命中率**：需要历史信息时，是否能召回正确记忆或文档。
4. **上下文利用率**：注入的内容是否真的被答案或工具调用使用。
5. **token 成本**：平均输入 token、输出 token 和压缩后节省比例。
6. **恢复能力**：worker 重启、用户刷新、工具失败后能否从 checkpoint 继续。
7. **延迟和稳定性**：摘要、检索、重排和缓存是否引入不可接受的时延。

测试集最好覆盖短任务、长任务、多轮纠错、用户中断、上下文超过窗口、历史约束召回、错误工具结果污染等场景。只有在这些场景下表现稳定，才能说明上下文设计可靠。

## 7. 如何实现用户中断

用户中断正在执行的对话，可以借鉴操作系统中断思想：当前执行流收到中断信号后，保存必要状态，停止或挂起旧任务，把控制权交还给新的用户请求。

工程实现可以分为四层：

1. **前端层**：用户点击停止或发送新消息，前端带上当前 `run_id` 发起 cancel。
2. **调度层**：把该 `run_id` 标记为 `cancelling/cancelled`，后续 step 不再调度。
3. **执行层**：通过 cancellation token、context cancel、AbortController 等机制通知模型请求、工具调用和 worker。
4. **结果层**：旧 run 返回的迟到结果要检查 run 状态，如果已取消就丢弃，不能写回新对话。

流程：

```text
用户点击中断
-> cancel(run_id)
-> 设置取消标志
-> 取消可取消的 LLM/HTTP/工具调用
-> 不可取消任务继续后台完成但结果作废
-> 保存中断摘要和资源清理状态
-> 新消息创建新的 run_id
```

## 8. 和操作系统中断的类比

| 操作系统中断 | Agent 中断 |
| --- | --- |
| 中断请求 IRQ | 用户点击停止或发送新消息 |
| 保存现场 | 保存 conversation/run/step/checkpoint |
| 中断服务例程 | cancel handler，清理资源和更新状态 |
| 恢复或调度新任务 | 开启新 run，继续或重建上下文 |
| 屏蔽和优先级 | 高风险工具不可强杀时标记结果作废 |

这个类比能帮助回答“如何开启新对话”：新对话最好有新的 `conversation_id`；如果是在同一对话中打断旧回答，则至少要有新的 `run_id`，避免旧工具结果污染新一轮状态。

## 9. 易错点

1. 只在前端停止显示不等于后端任务已取消。
2. 工具调用可能不可强制取消，必须用 run 状态检查丢弃迟到结果。
3. 中断后要释放资源，例如临时文件、锁、浏览器会话、数据库连接。
4. 新旧对话要隔离 `conversation_id`、`run_id` 和上下文缓存。
5. 压缩上下文不能丢用户硬性约束，否则后续回答会偏离目标。
6. 取消写操作要考虑幂等和补偿，不能在半执行状态留下脏数据。
7. 长期记忆不能无条件写入，必须考虑权限、隐私、有效期和错误记忆污染。

## 10. 面试回答模板

我会把 Agent 的上下文分成短期 prompt 上下文和长期外部状态。短期保留最近消息、当前目标、计划和必要工具结果；长期把稳定偏好、项目事实、历史摘要、工具结果和产物 ID 存到数据库或向量库。超过上下文窗口时，不是简单截断，而是做滑动窗口、摘要压缩、结构化状态、按需检索、工具结果裁剪和外部产物引用，重点保留用户硬性约束、关键决策、当前计划、资源 ID 和已排除的错误方案。

短期记忆转长期记忆时要先抽取候选事实，再做重要性、安全性、权限和有效期过滤，不能把临时推理、敏感信息和错误假设长期保存。上下文设计可以用任务成功率、约束保持率、召回命中率、上下文利用率、token 成本、恢复能力和延迟来评测。

用户中断可以类比操作系统中断。前端发送 cancel 当前 `run_id`，调度器设置取消状态，执行层通过 cancellation token 取消 LLM 请求和可取消工具；不可取消的任务即使后来返回，也要检查 run 状态并丢弃结果，不能污染新对话。然后新请求创建新的 `run_id` 或新的 `conversation_id`，从保留的用户目标和摘要重新开始。
