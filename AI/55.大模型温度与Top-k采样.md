# 大模型温度与 Top-k 采样参数分析

## 1. 问题背景

在大模型文本生成过程中，模型每一步都会输出一个词表大小的 logits 向量。系统需要把 logits 转换成概率分布，并从候选 token 中选择下一个 token。温度（temperature）和 Top-k 是最常见的采样控制参数，直接影响回答的稳定性、多样性、创造性和幻觉风险。

面试中问“大模型的温度是什么，top-k 是什么”，通常不是考 API 参数记忆，而是考察对自回归生成流程、softmax 概率分布、采样策略和工程调参取舍的理解。

### 假设条件

1. 这里讨论的是 LLM 推理阶段的文本生成参数。
2. “温度”指 logits softmax 前的缩放参数，不是知识蒸馏中的 distillation temperature，也不是硬件温度。
3. “Top-k”指 token 采样候选集截断，不是 MoE 中选择 top-k expert 的路由策略。
4. 默认生成流程为自回归生成：每次根据当前上下文预测下一个 token，直到达到停止条件。

## 2. 问题现象

当 temperature 和 Top-k 配置不合适时，常见现象如下：

| 现象 | 可能原因 | 表现 |
| --- | --- | --- |
| 输出过于固定 | temperature 太低，或关闭采样 | 同一问题几乎总是同一答案 |
| 输出发散 | temperature 太高 | 回答跳跃、事实错误增多 |
| 创造性不足 | Top-k 太小 | 候选 token 被过度限制 |
| 无关内容增多 | Top-k 太大且 temperature 较高 | 低概率 token 被采样到 |
| JSON 或代码不稳定 | 随机采样过强 | 格式漂移、字段遗漏 |

例如同一个 prompt，如果使用 `temperature=0` 或 greedy decoding，模型会始终选择概率最高的 token；如果使用 `temperature=1.2` 且 `top_k=100`，候选范围更大，输出更有变化，但不稳定性也更高。

## 3. 影响范围

1. **对话问答**：影响回答是否自然、多样、稳定。
2. **代码生成**：影响代码风格一致性、正确性和可复现性。
3. **结构化抽取**：影响 JSON、表格、枚举值等格式稳定性。
4. **创意写作**：影响文案、故事、标题生成的发散程度。
5. **离线评测**：影响 benchmark 结果是否可重复。
6. **RLHF / GRPO rollout**：影响采样探索度和 reward 信号质量。

## 4. 原因分析

### 4.1 生成过程

大模型生成下一个 token 的核心流程可以简化为：

```text
上下文 tokens
  -> Transformer 前向计算
  -> 输出 logits
  -> temperature 缩放
  -> softmax 转概率
  -> Top-k / Top-p 等候选过滤
  -> 按概率采样或选择最大概率 token
  -> 拼接 token，继续下一轮
```

### 4.2 Temperature 的含义

Temperature 用来控制概率分布的尖锐或平滑程度。典型公式是：

```text
prob_i = softmax(logit_i / T)
```

其中 `T` 是 temperature：

| Temperature | 概率分布变化 | 生成效果 |
| --- | --- | --- |
| `T = 0` | 通常退化为 greedy 选择 | 最确定，几乎无随机性 |
| `0 < T < 1` | 分布更尖锐 | 更稳定、更保守 |
| `T = 1` | 保持原始分布 | 标准采样 |
| `T > 1` | 分布更平滑 | 更多样、更发散 |

直观理解：temperature 越低，模型越偏向选择最高概率 token；temperature 越高，原本概率较低的 token 也更容易被选中。

### 4.3 Top-k 的含义

Top-k 采样会先保留概率最高的 k 个 token，把其他 token 的概率置为 0，再在这 k 个 token 内重新归一化并采样。

```text
原始候选：A 0.40, B 0.25, C 0.15, D 0.10, E 0.05, F 0.05
Top-k=3： 保留 A/B/C，丢弃 D/E/F
重新归一化后：A 0.50, B 0.31, C 0.19
```

Top-k 的核心作用是限制候选空间，避免模型采样到长尾低质量 token。

### 4.4 Temperature 与 Top-k 的关系

Temperature 调整的是概率分布形状，Top-k 调整的是候选集合大小。两者通常一起使用：

1. 先用 temperature 缩放 logits。
2. 再做 Top-k 过滤。
3. 最后在候选集合内采样。

低 temperature + 小 Top-k 会更稳定；高 temperature + 大 Top-k 会更开放，但更容易产生无关或错误输出。

## 5. 解决方案

### 5.1 面试回答模板

可以这样回答：

> Temperature 是控制大模型生成随机性的参数，本质是在 softmax 前对 logits 做缩放。temperature 越低，概率分布越尖锐，模型越倾向选择最高概率 token，输出更稳定；temperature 越高，概率分布越平滑，低概率 token 被选中的机会增加，输出更多样但也更容易发散。
>
> Top-k 是一种采样截断策略。模型每一步会给词表中所有 token 一个概率，Top-k 只保留概率最高的 k 个 token，再在这 k 个候选中重新归一化并采样。k 越小输出越保守，k 越大候选越丰富，但噪声和幻觉风险也更高。

### 5.2 工程配置建议

| 场景 | 推荐参数倾向 | 原因 |
| --- | --- | --- |
| 代码生成、SQL 生成 | `temperature=0~0.3`, `top_k=1~20` | 追求确定性和正确性 |
| JSON 抽取、分类 | `temperature=0`, 可关闭采样 | 追求格式稳定 |
| 普通问答 | `temperature=0.3~0.7`, `top_k=20~50` | 平衡稳定性和自然度 |
| 创意写作 | `temperature=0.7~1.2`, `top_k=50~100` | 提高多样性 |
| RL rollout 探索 | 适当提高 temperature | 增加候选响应差异 |

### 5.3 代码实现说明

如果在项目或服务中落地采样参数控制，可能需要关注以下内容：

- **可能需要修改的模块**：模型推理服务、LLM Client 封装层、Prompt 调用配置、评测脚本。
- **可能涉及的文件**：请求参数结构体、模型调用配置文件、生成接口适配器、单元测试或回归测试用例。
- **核心修改逻辑**：在调用模型时显式传入 `temperature`、`top_k` 等生成参数，并按业务场景设置默认值和参数边界。
- **测试重点**：输出格式稳定性、同 prompt 多次调用的一致性、创造性任务的多样性、非法参数边界处理。

简化伪代码如下：

```python
def sample_next_token(logits, temperature=1.0, top_k=50):
    if temperature <= 0:
        return argmax(logits)

    scaled_logits = logits / temperature
    probs = softmax(scaled_logits)

    if top_k is not None:
        probs = keep_only_top_k(probs, k=top_k)
        probs = normalize(probs)

    return random_sample(probs)
```

## 6. 可选方案对比

| 方案 | 原理 | 优点 | 缺点 | 适用场景 |
| --- | --- | --- | --- | --- |
| Greedy decoding | 每步选择最大概率 token | 稳定、可复现 | 容易死板，可能陷入局部最优 | 分类、抽取、代码生成 |
| Temperature sampling | 调整概率分布平滑度 | 参数直观，易调节 | 过高会发散 | 问答、创意生成 |
| Top-k sampling | 只在前 k 个 token 内采样 | 过滤长尾噪声 | k 固定，不能适配分布形状 | 通用文本生成 |
| Top-p sampling | 保留累积概率达到 p 的候选 | 候选数可动态变化 | 参数理解稍复杂 | 开放式问答、创意写作 |
| Beam search | 保留多条高分路径 | 适合短文本和翻译 | 多样性差，成本高 | 翻译、摘要 |

## 7. 推荐方案

推荐把 temperature 和 Top-k 作为业务场景级配置，而不是全局固定参数。

1. 对确定性任务，优先使用 `temperature=0` 或很低的 temperature，并限制 Top-k。
2. 对开放式问答，使用中等 temperature，并配合 Top-k 或 Top-p 控制候选范围。
3. 对创意任务，适当提高 temperature 和候选范围，但要增加安全过滤、事实校验或人工审核。
4. 对线上服务，记录每次调用的采样参数，方便复现问题和做 A/B 实验。

面试回答中建议突出一句话：temperature 控制概率分布的平滑程度，Top-k 控制候选 token 的数量；前者调“随机性强弱”，后者调“候选范围大小”。

## 8. 实施步骤

1. 明确业务目标：稳定性优先、创造性优先，还是探索优先。
2. 选择基础参数：从 `temperature=0.3~0.7`、`top_k=20~50` 开始。
3. 建立评测集：覆盖正常输入、边界输入、格式约束输入和长上下文输入。
4. 多次重复调用：同一 prompt 调用多轮，统计输出一致性和错误率。
5. 调整参数：
   - 输出太死板：提高 temperature 或 Top-k。
   - 输出太发散：降低 temperature 或 Top-k。
   - 格式不稳定：降低 temperature，必要时关闭采样。
6. 上线灰度：按场景或用户流量逐步放开。
7. 记录参数：日志中保留 model、temperature、top_k、top_p、seed、prompt version。

## 9. 风险与注意事项

1. **temperature 不是越高越智能**：它只增加采样随机性，不提升模型能力。
2. **Top-k 不是越大越好**：候选过大会引入长尾噪声。
3. **`temperature=0` 不一定绝对可复现**：并行计算、量化、服务端实现和随机种子也可能影响结果。
4. **不同模型参数含义不完全一致**：不同厂商可能对 `temperature=0`、`top_k=-1`、`top_k=0` 有不同约定。
5. **不要混淆 Top-k 和 Top-p**：Top-k 固定候选数量，Top-p 固定累计概率阈值。
6. **结构化输出要保守**：JSON、SQL、代码等任务不适合高随机性配置。

## 10. 验证方式

1. **一致性验证**：同一 prompt 连续调用 10~100 次，统计输出是否一致。
2. **格式验证**：对 JSON、SQL、代码输出做解析或编译检查。
3. **质量评估**：人工或自动打分，比较事实正确率、相关性和完整性。
4. **多样性评估**：统计不同回答数量、distinct n-gram、语义相似度。
5. **线上指标**：观察用户重试率、投诉率、人工接管率和安全拦截率。
6. **参数回放**：根据日志中的 prompt、model、temperature、top_k 和 seed 尝试复现问题。

## 11. 总结

Temperature 和 Top-k 都是大模型生成阶段的采样参数，但控制维度不同。Temperature 通过缩放 logits 改变概率分布形状，决定模型输出更保守还是更发散；Top-k 通过截断候选 token 集合，决定模型能从多大的候选范围内采样。

面试中可以用“temperature 控制随机性，Top-k 控制候选范围”快速概括，再补充 softmax 缩放、候选截断、场景化调参和风险边界。工程实践中，应根据任务类型配置参数：结构化和高正确性任务使用低 temperature、小候选范围；开放式和创意任务可以适当提高随机性，但要配合评测、日志和安全兜底。
