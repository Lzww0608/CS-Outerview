# 25. OpenClaw、Claude Code、Hermes 对比

如果面试问“OpenClaw、Claude Code、Hermes 各自有什么特点”，不要只回答“它们都是 Agent 工具”。更好的回答是：三者解决的是 Agent 工程里的不同层次问题。

```text
OpenClaw：偏个人/团队的通用执行型 Agent Runtime，重点是多渠道接入、工具编排、技能扩展和本地优先。
Claude Code：偏软件工程场景的代码 Agent，重点是仓库理解、文件修改、命令执行、权限、Hooks、MCP 和验证闭环。
Hermes：偏自我学习型 Agent Shell，重点是长期记忆、经验沉淀、技能自动生成/改进和可迁移的执行轨迹。
```

一句话总结：

```text
OpenClaw 更像“能在你的数字环境里长期运行的操作型助手”；
Claude Code 更像“受控地进入代码仓库工作的工程 Agent”；
Hermes 更像“把记忆、技能和执行经验持续沉淀下来的自进化 Agent”。
```

## 1. 总体定位对比

| 维度 | OpenClaw | Claude Code | Hermes |
| --- | --- | --- | --- |
| 核心定位 | 自托管、常驻、多渠道的个人 AI 助手 | 代码仓库内的 agentic coding tool | 自改进、自沉淀的长期 Agent Shell |
| 主要入口 | WhatsApp、Telegram、Slack、Discord、CLI、Gateway | Terminal、IDE、桌面、Web、CI、Slack 等 | CLI/TUI、Telegram、Discord、Slack、WhatsApp、Gateway |
| 主要任务 | 邮件、日程、消息、浏览器、脚本、文件、自动化流程 | 写代码、修 bug、跑测试、做 code review、发 PR | 长期任务、技能沉淀、跨会话记忆、任务轨迹生成 |
| 核心资产 | Gateway、channels、tools、skills、sessions、sandbox | 仓库上下文、`CLAUDE.md`、settings、hooks、MCP、subagents | memory、skills、trajectory、toolsets、terminal backends、subagents |
| 能力边界 | 更通用，更接近“个人 OS/数字员工” | 更垂直，更贴近软件工程闭环 | 更强调学习闭环和经验复用 |
| 最大风险 | 权限过大、第三方 skill 安全、远程入口暴露 | 错改代码、误执行命令、上下文污染、权限配置不当 | 错误经验被固化、自动生成技能不可靠、长期记忆污染 |
| 最适合场景 | 多应用自动化、个人助理、消息驱动工作流 | 研发、测试、CI、代码审查、仓库维护 | 需要长期积累经验的个人/团队 Agent、MLOps、训练轨迹生成 |

## 2. OpenClaw：通用执行型 Agent Runtime

OpenClaw 的特点不是“模型更强”，而是把 Agent 放进一个长期运行的执行环境里。它通常包含：

1. **Gateway 控制面**：统一管理会话、渠道、工具和事件。
2. **多消息渠道入口**：用户可以通过 WhatsApp、Telegram、Slack、Discord、iMessage、WeChat 等渠道触发任务。
3. **本地优先和自托管**：运行在自己的设备、VPS 或内部机器上，数据和上下文更容易由用户自己控制。
4. **工具和 Skills 扩展**：通过浏览器、文件、命令行、定时任务、第三方服务 API 等完成真实操作。
5. **常驻运行能力**：可以做 cron、提醒、后台任务、长期跟踪和主动通知。
6. **多 Agent / 多 Session 隔离**：可以把不同渠道、不同账号或不同任务路由到隔离的 agent session。

OpenClaw 的关键价值是：**把 Agent 从一次性聊天变成一个接入真实软件环境的常驻执行层**。

例如：

```text
用户在 Telegram 里说：“帮我整理今天会议，发一封总结邮件给团队。”

OpenClaw 可以：
1. 从消息渠道收到请求；
2. 读取日历、邮件、会议记录或本地文档；
3. 调用模型生成总结；
4. 通过邮件工具发送；
5. 把执行结果回传到 Telegram；
6. 将用户偏好、联系人或固定格式沉淀到记忆/技能里。
```

### 2.1 OpenClaw 的优点

1. **入口自然**：用户不需要打开 IDE 或专门的 AI 页面，可以从日常通信工具里直接发起任务。
2. **覆盖面广**：文件、浏览器、日历、邮件、Webhook、脚本、定时任务都可以纳入执行链路。
3. **适合长期自动化**：它不是只解决一次问答，而是适合持续运行的个人/团队工作流。
4. **开放可扩展**：skills 机制让用户能把常用流程封装成可复用能力。
5. **本地部署有优势**：隐私、内网系统、个人文件和设备能力更容易接入。

### 2.2 OpenClaw 的问题

1. **权限半径很大**：如果 Agent 同时能读文件、发邮件、跑命令、操作浏览器，任何错误判断都可能变成真实副作用。
2. **第三方 Skill 风险高**：skill 本质上是可执行能力和提示词规则的组合，必须当作不可信代码审查。
3. **消息入口容易被注入**：群聊、外部 DM、邮件、网页内容都可能携带 prompt injection。
4. **调试难度高**：多渠道、多工具、多会话导致链路很长，必须有 trace、日志、回放和权限审计。
5. **业务一致性弱**：如果没有事务、幂等和补偿设计，Agent 做真实操作时容易出现半成功状态。

### 2.3 OpenClaw 的工程落地建议

1. 默认把外部消息视为不可信输入。
2. 对高风险工具做 allowlist，例如发邮件、转账、删除文件、执行 shell、访问密钥。
3. 第三方 skill 安装前做源码审查、依赖扫描和沙箱运行。
4. 每个 action 保存 trace：输入、模型决策、工具参数、工具返回、最终输出。
5. 对真实世界操作加确认机制，例如“草稿生成”和“用户确认发送”分离。
6. 对多 Agent/多用户做隔离，不要让个人助手和公司助手共享同一套高权限上下文。

## 3. Claude Code：工程闭环最强的 Coding Agent

Claude Code 的核心不是“会补全代码”，而是一个运行在真实工程环境里的受控 Agent。它可以读取代码库、编辑文件、运行命令，并和开发工具集成。

它最值得学习的设计包括：

1. **仓库上下文优先**：围绕当前项目、文件、测试、Git diff 和命令输出工作。
2. **`CLAUDE.md` 分层记忆**：把项目规则、构建命令、架构约束、代码风格沉淀成可 review 的 Markdown。
3. **权限系统**：读文件、改文件、执行 shell、访问网络等操作可以配置 allow/ask/deny。
4. **Hooks**：在工具调用前后、用户提交 prompt 时、任务结束时触发确定性脚本。
5. **MCP 扩展**：通过 MCP 接入 Jira、Slack、Google Drive、数据库、内部服务等外部工具。
6. **Subagents**：把复杂任务拆给具备独立上下文和工具权限的子 Agent。
7. **验证闭环**：不只生成代码，还能运行测试、分析失败、继续修复。

### 3.1 Claude Code 的优点

1. **软件工程适配度高**：它天然理解“读代码 -> 改代码 -> 跑测试 -> 看 diff -> 解释变更”这条链路。
2. **权限边界清楚**：高风险操作可以通过 settings、sandbox、hooks 和人工确认控制。
3. **可维护性强**：项目规则以 `CLAUDE.md`、skills、settings 等形式沉淀，团队可以版本化和 review。
4. **可接入企业流程**：CI、PR、代码审查、issue triage、release note 等都能进入自动化流程。
5. **Unix 风格组合性强**：可以 pipe 日志、git diff、测试输出，让 Agent 成为开发流水线的一环。

### 3.2 Claude Code 的问题

1. **领域比较垂直**：它的强项是代码仓库和研发流程，不是全场景个人助手。
2. **上下文依赖项目质量**：如果项目结构混乱、测试缺失、构建脚本不可用，Agent 的验证能力会下降。
3. **仍然需要人审查**：Agent 能跑测试不代表业务正确，复杂重构、权限逻辑、数据迁移仍需要人工把关。
4. **规则会老化**：`CLAUDE.md` 和 hooks 如果不维护，会把旧架构、旧命令、旧约束持续注入给模型。

### 3.3 Claude Code 的工程启发

1. Agent 不应该直接拥有无限权限，工具权限要显式配置。
2. 长期规则最好用人能读、人能改、人能 review 的文本表达。
3. 模型输出不可靠，测试、lint、typecheck、diff、hook 才是工程确定性边界。
4. Coding Agent 的价值不只是“写代码快”，而是把需求、实现、验证、提交、审查串成闭环。

## 4. Hermes：自我学习和经验沉淀型 Agent

Hermes 更值得关注的是它的 **learning loop**。它不是只把工具接进来，而是希望 Agent 在运行过程中持续形成可复用经验：

1. **跨会话记忆**：保存用户偏好、项目背景、环境信息和历史任务结论。
2. **技能自动生成**：当 Agent 解决一个复杂问题后，把步骤、依赖、注意事项沉淀成 skill。
3. **技能自改进**：下次执行相似任务时，如果发现旧 skill 有问题，可以根据新 trace 迭代它。
4. **历史会话检索**：通过全文检索、摘要或向量检索找回过去的任务过程。
5. **用户模型**：随着交互变多，形成对用户偏好、工作方式和约束的理解。
6. **轨迹生成**：记录工具调用、思考步骤、环境状态和结果，可用于评测、训练或 fine-tuning。

它的核心思想可以抽象成：

```text
任务执行 -> 保存 trace -> 识别可复用经验 -> 写入 memory/skill
-> 后续任务检索经验 -> 复用或修正 skill -> 继续沉淀
```

### 4.1 Hermes 的优点

1. **越用越贴合环境**：不是每次都从零开始，而是把用户项目、工具链和习惯持续积累。
2. **适合复杂重复任务**：例如研究报告、数据处理、MLOps、定时巡检、代码维护流程。
3. **可沉淀组织知识**：如果技能经过 review，可以变成团队共享的操作手册。
4. **对 Agent 评测友好**：完整 trajectory 能帮助分析失败原因，而不是只看最终回答。
5. **模型无关性更强**：通过 provider 抽象切换不同模型，把能力沉淀在 runtime 和 skills 层。

### 4.2 Hermes 的问题

1. **错误记忆会放大错误**：如果一次错误经验被写入 skill，后续任务会系统性复用错误。
2. **自动改 skill 有安全风险**：skill 既是知识也是执行策略，自动修改必须有 review 和回滚。
3. **评判标准很难设计**：什么时候该沉淀？什么时候该更新？什么时候该丢弃？需要 Harness 支撑。
4. **长期记忆会污染上下文**：过期偏好、旧项目路径、旧 API、错误结论都可能影响新任务。
5. **工程复杂度高**：需要 memory store、skill store、trace store、judge、版本管理、权限和审计。

### 4.3 Hermes 的工程落地建议

1. 自动生成的 skill 默认进入草稿区，不直接上线。
2. 每条长期记忆都要有来源、时间、适用范围和过期策略。
3. skill 更新必须保留版本，支持 diff、review、rollback。
4. 将 trace 分层保存：用户输入、工具调用、环境状态、失败原因、最终结果。
5. 用 Harness 做回归：新 skill 不能只修一个 badcase，还要验证不会破坏旧任务。
6. 对安全相关经验做人工审批，例如密钥、权限、支付、生产环境操作。

## 5. 三者不是互斥关系

三者可以看成 Agent 工程的三层：

```text
OpenClaw：运行入口和操作平台
Claude Code：软件工程垂直能力
Hermes：长期学习和经验沉淀机制
```

真实系统里可以组合使用：

```text
用户从 Telegram 发起：“线上登录接口 500，帮我排查。”

OpenClaw：
1. 接收 Telegram 消息；
2. 做身份校验和权限判断；
3. 将任务路由到工程 Agent。

Claude Code：
1. 进入代码仓库；
2. 读取日志、issue、最近 diff；
3. 修改代码或配置；
4. 跑测试、生成 PR。

Hermes：
1. 记录这次排查 trace；
2. 抽取“登录接口 500 排查流程”；
3. 生成或更新 skill；
4. 下次遇到相似问题时直接加载该经验。
```

这种组合的重点不是“让 Agent 无限自治”，而是给每一层明确边界：

1. OpenClaw 管入口、身份、渠道、路由和通用工具。
2. Claude Code 管代码仓库内的工程执行和验证。
3. Hermes 管经验沉淀、技能演化和长期记忆。
4. Harness 管评测、回放、审计和上线门禁。

## 6. 为什么它们的设计选择不同

### 6.1 OpenClaw 为什么强调渠道和工具

个人助手的核心不是写出一段漂亮回答，而是连接用户真实生活和工作环境。用户的任务入口往往来自聊天工具、邮件、日历和通知，所以 OpenClaw 要先解决：

1. 怎么接收自然渠道里的请求；
2. 怎么找到对应的工具；
3. 怎么持续运行；
4. 怎么把结果送回用户；
5. 怎么隔离不同身份、渠道和会话。

因此它更像一个“Agent 操作系统”。

### 6.2 Claude Code 为什么强调权限和验证

软件工程的失败成本很具体：代码错了、测试挂了、数据迁移错了、生产配置被改了、密钥泄漏了。因此 Claude Code 必须强调：

1. 文件读写权限；
2. shell 命令权限；
3. hooks 约束；
4. 测试和 lint；
5. diff 审查；
6. Git/PR 工作流。

因此它更像一个“受控工程执行器”。

### 6.3 Hermes 为什么强调学习闭环

长期 Agent 最大的问题是每次都重新摸索。Hermes 的设计目标是把一次任务的经验变成以后可复用的能力，所以它强调：

1. memory；
2. skill；
3. trajectory；
4. history search；
5. user model；
6. self-improvement。

因此它更像一个“经验累积系统”。

## 7. 真实选型建议

| 场景 | 更适合的选择 | 原因 |
| --- | --- | --- |
| 主要做代码开发、修 bug、跑测试、PR | Claude Code | 工程闭环完整，权限、hooks、测试链路成熟 |
| 想在 Telegram/Slack/WhatsApp 里驱动多个工具做自动化 | OpenClaw | 多渠道、Gateway、长期运行和工具编排更合适 |
| 想让 Agent 长期学习自己的项目和流程 | Hermes | memory、skill 自演化和 trace 沉淀更突出 |
| 企业内部要接生产系统 | Claude Code + 自研权限层/Harness | 需要强审计、强权限和可验证执行 |
| 个人效率自动化 | OpenClaw 或 Hermes | 取决于更看重渠道生态还是自学习能力 |
| 研究 Agent 训练数据和轨迹 | Hermes | trajectory、batch runner、训练数据生成更贴近研究需求 |

## 8. 易错点

1. **不要把“接了很多工具”误认为 Agent 强**  
   工具越多，权限和攻击面越大。真正关键的是工具选择、参数校验、权限控制、失败补偿和 trace。

2. **不要把“有记忆”误认为会学习**  
   记忆只是存储。学习还需要筛选、抽象、验证、版本管理和回归测试。

3. **不要让 Agent 自己无审查地更新自己的规则**  
   自动修改 skill、prompt、memory 很有价值，但必须能 diff、review、rollback。

4. **不要用通用 Agent 替代业务系统事务**  
   发邮件、改代码、调用支付、操作数据库，都要有幂等、补偿、审批和审计。

5. **不要忽略外部输入注入**  
   邮件、网页、聊天消息、issue、日志都可能包含恶意指令。Agent 不能把外部内容当成系统指令。

## 9. 面试回答模板

可以这样回答：

```text
我会从定位上区分三者。

OpenClaw 更像通用执行型 Agent Runtime，特点是自托管、多渠道接入、Gateway、工具和 Skills 编排，适合个人助理、多应用自动化和长期后台任务。它的挑战是权限半径大、第三方 skill 安全和多渠道 prompt injection，所以落地时要做身份校验、工具白名单、sandbox、trace 和人工确认。

Claude Code 更像面向软件工程的 Coding Agent。它的亮点是能读代码库、改文件、运行命令、接入 MCP，并通过 CLAUDE.md、settings、hooks、subagents、测试和 diff 审查形成工程闭环。它适合修 bug、写测试、PR、CI 和代码审查，但仍然需要权限控制和人工 review。

Hermes 更像自我学习型 Agent Shell，重点是跨会话记忆、技能自动沉淀、历史轨迹检索和 self-improvement。它适合长期重复任务、个人/团队工作流沉淀和 Agent 训练数据生成。风险是错误经验会被固化，所以要用 Harness 做评测、版本管理、回归和人工审批。

所以三者不是简单替代关系。OpenClaw 解决入口和操作平台，Claude Code 解决代码工程执行，Hermes 解决经验沉淀和持续学习。真正的企业落地会把它们的设计思想组合起来，再加上权限、审计、沙箱和评测闭环。
```
