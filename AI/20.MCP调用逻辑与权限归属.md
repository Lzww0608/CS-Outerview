# MCP 调用逻辑与权限归属

## MCP 是什么

MCP（Model Context Protocol）可以理解为让大模型或 Agent 以标准方式访问外部工具、资源和数据源的协议层。它把文件系统、数据库、搜索、工单、Git、日历、内部业务 API 等能力封装成结构化工具，让模型通过 MCP Client 调用 MCP Server，而不是为每个工具单独写一套接入逻辑。

它主要解决四类问题：

1. **能力标准化**：工具有清晰的名称、参数 schema、返回值和错误语义。
2. **上下文接入**：模型可以按需读取外部事实，而不是只依赖训练记忆或长 prompt。
3. **权限边界**：工具调用可以统一做鉴权、审批、审计、限流和租户隔离。
4. **生态复用**：同一个 MCP Server 可以被不同 Agent、IDE、客服机器人或内部平台复用。

MCP 不等于让模型直接操作生产系统。真实企业里，它更像安全适配层：只暴露必要工具，服务端重新校验权限，高风险写操作需要确认或审批，所有调用要可观测和可追溯。

## 问题背景

在 MCP（Model Context Protocol）架构中，一个核心问题是：**谁有权力决定调用哪个 MCP 工具？** 这个权力归属于模型（Agent）、用户、还是系统？这不仅是技术问题，更涉及安全、责任边界和用户体验。

## 一、三种调用主导模式

### 1.1 模型主导（Model-Driven）

模型根据对话上下文和工具描述，自主决定调用哪些工具。

```text
用户: 帮我查一下订单12345的状态
  -> 模型分析意图
  -> 模型决定调用 search_order(order_id="12345")
  -> 返回结果给模型
  -> 模型生成回答
```

**特点**：
- 模型拥有完整的工具调用决策权
- 适合开放性任务，用户不需要知道背后用了什么工具
- 对模型能力要求高，需要准确的工具选择能力

**优势**：
- 用户体验流畅，减少交互摩擦
- 可以处理复杂的多工具编排场景
- 适合自动化程度高的任务

**风险**：
- 模型可能选错工具或参数错误
- 模型可能调用危险工具（删除、支付等）
- 权限边界模糊，责任归属不清

### 1.2 用户主导（User-Driven）

每个工具调用都需要用户明确授权，模型只推荐但不直接执行。

```text
用户: 帮我查一下订单12345的状态
  -> 模型推荐调用 search_order(order_id="12345")
  -> 询问用户是否执行
  -> 用户确认
  -> 实际执行工具
  -> 返回结果给模型
  -> 模型生成回答
```

**特点**：
- 用户对每个操作有最终决策权
- 适合高风险操作或敏感环境
- 交互成本高，需要多次确认

**优势**：
- 安全边界清晰，用户完全掌控
- 便于审计和责任追溯
- 适合金融、医疗、法律等合规要求高的场景

**风险**：
- 交互繁琐，用户体验差
- 不适合高频自动化任务
- 用户可能不理解工具调用的实际影响

### 1.3 混合模式（Hybrid）

根据工具的风险等级和用户授权范围，动态选择模型主导或用户主导。

```text
工具分类:
- 低风险（只读查询）: 模型直接调用
- 中风险（写入操作）: 需要二次确认
- 高风险（删除、支付）: 必须用户明确授权
```

**特点**：
- 平衡安全性和用户体验
- 可配置的权限层级
- 企业级安全标准

**优势**：
- 灵活性高，可按场景配置
- 安全和效率兼顾
- 便于企业合规管理

**风险**：
- 配置复杂，需要仔细设计权限模型
- 用户可能不理解不同风险等级的区别

## 二、权限归属模型

### 2.1 权限控制的位置

MCP 权限控制可以在三个层面实现：

#### 服务端控制（Server-Side）

```text
Agent/模型
  -> MCP Client
  -> MCP Server（权限控制在这里）
      -> 校验用户身份
      -> 校验工具权限
      -> 校验参数范围
      -> 执行工具
```

服务端控制的优势：
- 所有权限逻辑集中管理，难以绕过
- 便于统一审计和日志记录
- 不依赖客户端的信任假设

#### 客户端控制（Client-Side）

```text
用户/Agent请求
  -> MCP Client（权限控制在这里）
      -> 检查用户权限
      -> 过滤可用工具
      -> 发送请求到 Server
```

客户端控制的优势：
- 减少无效请求，降低服务端压力
- 可以做本地缓存和优化
- 便于快速迭代权限规则

#### 双层控制（Dual-Layer）

```text
用户请求
  -> Client: 检查用户Token、过滤可用工具
  -> Server: 再次校验租户权限、参数范围、业务规则
```

双层控制的优势：
- 安全冗余，一层被攻破还有另一层保护
- 便于分离关注点：客户端管接入，服务器管业务

### 2.2 权限模型类型

#### 基于角色的访问控制（RBAC）

```json
{
  "roles": {
    "developer": {
      "tools": ["read_file", "search_code", "run_tests"],
      "writable": true,
      "dangerous_tools": []
    },
    "senior_developer": {
      "tools": ["read_file", "write_file", "search_code", "run_tests", "deploy"],
      "writable": true,
      "dangerous_tools": ["deploy"]
    },
    "admin": {
      "tools": ["*"],
      "writable": true,
      "dangerous_tools": ["*"]
    }
  }
}
```

#### 基于属性的访问控制（ABAC）

```json
{
  "policies": [
    {
      "effect": "allow",
      "actions": ["search_order", "query_user"],
      "conditions": {
        "environment": ["production", "staging"],
        "user_department": "customer_service",
        "time_range": ["09:00", "18:00"]
      }
    }
  ]
}
```

#### 基于标签的访问控制（Label-Based）

```json
{
  "tool_labels": {
    "search_order": ["read_only", "customer_data", "pii_safe"],
    "refund_order": ["write", "financial", "requires_approval"],
    "delete_data": ["dangerous", "irreversible", "requires_approval", "admin_only"]
  },
  "user_clearance": "customer_service",
  "approved_labels": ["read_only", "customer_data", "pii_safe"]
}
```

## 三、实际架构设计

### 3.1 典型 MCP 权限架构

```text
用户请求
  |
  v
+-------------------+
|   MCP Gateway     |
|   - 认证鉴权      |
|   - 工具路由      |
|   - 限流审计      |
+-------------------+
  |
  v
+-------------------+
|  Tool Permission  |
|     Service       |
|  - RBAC/ABAC      |
|  - 工具过滤       |
|  - 参数校验       |
+-------------------+
  |
  v
+-------------------+
|   MCP Servers     |
|   - Account       |
|   - Payment       |
|   - Order         |
|   - Content       |
+-------------------+
```

### 3.2 权限流转示例

#### 场景：客服 Agent 查询订单

```text
1. 用户发起请求: "帮我查一下用户 1001 的最近订单"

2. Client 权限检查:
   - 用户角色: customer_service
   - 可用工具列表: [search_order, query_user, create_ticket]
   - 权限通过

3. MCP Gateway 鉴权:
   - 验证用户 Token
   - 识别租户 ID
   - 记录审计日志

4. Tool Permission Service 决策:
   - search_order 属于 read_only 工具
   - 当前环境: production
   - 用户有 read_only 权限
   - 决策: 允许调用

5. MCP Server 执行:
   - search_order(order_id=*, user_id=1001, limit=10)
   - 返回订单摘要（脱敏处理）

6. 返回结果给用户:
   - "用户 1001 最近有 3 笔订单..."
```

#### 场景：高风险操作

```text
1. 用户发起请求: "帮我退款订单 12345"

2. Client 发现:
   - refund_order 属于 dangerous_tools
   - 需要用户确认

3. 提示用户确认:
   - "即将执行退款操作，是否继续？"
   - 用户点击确认

4. 权限检查升级:
   - 检查用户是否有 financial 权限
   - 检查操作是否在工作时间内
   - 记录完整审计日志

5. 执行并返回:
   - 退款成功
   - 记录: 操作人、时间、订单号、金额
```

## 四、谁来主导的工具选择策略

### 4.1 决策矩阵

| 维度 | 模型主导 | 用户主导 | 混合模式 |
|------|----------|----------|----------|
| **安全性** | 中 | 高 | 高 |
| **用户体验** | 高 | 低 | 中 |
| **自动化程度** | 高 | 低 | 中 |
| **适用场景** | 内部工具、低风险操作 | 高风险操作、外部用户 | 企业级应用 |
| **实现复杂度** | 低 | 中 | 高 |
| **合规能力** | 中 | 高 | 高 |

### 4.2 工具风险分级

```python
class ToolRiskLevel(Enum):
    # 只读查询，无副作用
    LOW = 1        # 模型直接调用
    
    # 有轻微副作用，但可恢复
    MEDIUM = 2     # 用户确认后调用
    
    # 有明显副作用，需要审批
    HIGH = 3       # 必须用户授权 + 审批流程
    
    # 高风险，不可逆操作
    CRITICAL = 4   # 多人审批 + 完整审计
```

### 4.3 智能决策引擎

```python
def should_auto_execute(tool: Tool, user: User, context: Context) -> Decision:
    # 1. 检查工具风险等级
    risk = tool.risk_level
    
    if risk == ToolRiskLevel.LOW:
        # 低风险：模型直接执行
        return Decision.AUTO_EXECUTE
    
    if risk == ToolRiskLevel.MEDIUM:
        # 中风险：检查用户授权范围
        if user.has_approved(tool):
            return Decision.AUTO_EXECUTE
        return Decision.REQUIRE_CONFIRM
    
    if risk == ToolRiskLevel.HIGH:
        # 高风险：必须确认
        return Decision.REQUIRE_CONFIRM
    
    if risk == ToolRiskLevel.CRITICAL:
        # 极高风险：需要审批
        return Decision.REQUIRE_APPROVAL

def auto_execute_contexts() -> List[str]:
    """模型主导的典型场景"""
    return [
        "内部开发工具",
        "知识库查询",
        "数据分析",
        "代码搜索",
        "只读监控"
    ]

def user_dominant_contexts() -> List[str]:
    """用户主导的典型场景"""
    return [
        "财务操作",
        "用户数据修改",
        "删除操作",
        "生产环境变更",
        "外部系统交互"
    ]
```

## 五、常见问题与最佳实践

### 5.1 常见问题

#### Q: 模型选错工具怎么办？

建立工具调用评估和反馈机制：

```python
# 1. 工具调用后评估
result = execute_tool(tool, params)
evaluation = evaluate_tool_call(tool, params, result)

# 2. 如果选错，记录错误样本
if evaluation.wrong_tool:
    log_error_sample(
        task=current_task,
        suggested_tool=tool,
        actual_needed_tool=evaluation.correct_tool,
        reason=evaluation.reason
    )

# 3. 定期优化工具描述
# 4. 用错误样本微调模型
```

#### Q: 如何防止权限绕过？

多层防护：

1. **客户端过滤不可靠**：恶意客户端可能绕过客户端过滤
2. **服务端必须重新校验**：每次请求都要在服务端验证权限
3. **最小权限原则**：不给模型超出需要的权限
4. **操作审计**：记录所有操作，支持事后审计

#### Q: 用户误确认怎么办？

增强确认信息的可理解性：

```python
# 不好的确认框
"是否执行 refund_order?"

# 好的确认框
"""
即将执行退款操作：
- 订单号: 12345
- 退款金额: ¥299.00
- 退款方式: 原路退回
- 影响: 此操作不可逆

请输入"确认退款"以继续
"""
```

### 5.2 最佳实践

1. **分层授权**：低风险自动执行，高风险人工确认
2. **上下文感知**：根据用户角色、环境、数据敏感度动态调整权限
3. **渐进式授权**：新用户先受限，随着信任度提升逐步开放权限
4. **可解释性**：让用户和模型都清楚为什么某个工具可用或不可用
5. **完整审计**：记录所有操作，包括被拒绝的尝试
6. **快速撤销**：能够立即撤销某个用户或工具的所有权限

## 六、面试常见问题

### Q1: MCP 工具调用的权限归属问题怎么理解？

权限归属涉及三个层面的责任：

1. **模型层**：模型负责理解用户意图并选择合适的工具，但不能突破预设权限边界
2. **服务端层**：服务端是权限控制的最终防线，必须校验所有请求，不能信任客户端
3. **用户层**：用户拥有最终决策权，尤其是高风险操作必须用户明确授权

关键是：模型可以"推荐"工具，但"执行"权限必须由权限系统控制。

### Q2: 如何平衡安全性和用户体验？

核心思路是**风险分级**：

- 低风险操作（只读查询）→ 模型直接执行，用户无感知
- 中风险操作（写入）→ 用户确认后执行，有明确的确认界面
- 高风险操作（删除、支付）→ 必须用户授权，可能需要额外审批

这样可以让大多数普通操作保持流畅，同时确保高风险操作有足够的保护。

### Q3: 模型会绕过权限控制吗？

设计上要假设模型是不可信的：

1. 客户端的权限检查只是优化，不能作为安全边界
2. 服务端必须重新校验每个请求的权限
3. 敏感操作要有额外的确认和审计机制
4. 模型只能看到它有权限访问的工具列表

### Q4: 多租户环境下权限如何设计？

```text
Tenant A (租户A)
  -> User A1 (角色: developer)
  -> User A2 (角色: admin)
  
Tenant B (租户B)
  -> User B1 (角色: developer)
  -> User B2 (角色: admin)

权限模型:
- 租户隔离: A用户不能访问B的数据
- 角色权限: developer只能访问自己的数据
- 数据权限: 用户只能访问与自己相关的资源
```

## 七、总结

MCP 调用逻辑的权限归属不是简单的"谁说了算"，而是一个涉及安全、体验、合规的复杂系统设计问题：

1. **模型主导**适合低风险、高频的内部操作，追求效率和自动化
2. **用户主导**适合高风险、低频的敏感操作，追求安全和合规
3. **混合模式**通过风险分级，平衡安全性和用户体验
4. **服务端控制**是权限的最终防线，不能信任客户端
5. **完整审计**是责任追溯的基础，也是合规的必要条件

核心设计原则：**模型可以决策，但不能突破边界；用户拥有最终权力，但不是每个操作都需要用户决策。**
