# 29. 上下文压缩原理与工程实践

## 1. 问题背景

大模型和 Agent 系统里的“上下文”指模型本次调用时实际能看到的输入内容，包括系统指令、用户问题、历史对话、任务状态、工具结果、检索文档、代码片段、权限信息和长期记忆等。

上下文窗口是有限的，即使模型支持很长上下文，也会受到成本、延迟、注意力稀释、位置偏置和安全风险影响。因此工程上不能把所有历史、日志、文档和工具结果都塞进 prompt，而要做上下文压缩。

**假设条件**：

1. 用户问题里的“s上下文压缩”理解为“上下文压缩”，主要讨论 LLM/Agent/RAG 场景。
2. 这里的上下文压缩不是 gzip、zstd 这类字节级压缩，而是面向模型输入的语义压缩、结构化压缩和检索式压缩。
3. 目标是在 token 预算有限时，尽量保留对当前任务有用的信息，丢弃、外部化或摘要化低价值信息。
4. 如果是模型底层 KV Cache 压缩、注意力稀疏化、量化压缩，那属于推理系统优化，和本文的“Prompt/Agent 上下文压缩”相关但不是同一层。

一句话回答：

```text
上下文压缩的本质，是在有限 token 预算下，把原始历史信息转换成更短、更结构化、更可检索、更贴近当前任务的上下文，同时尽量保留目标、约束、事实、证据和下一步状态。
```

它解决的问题不是“让模型记住所有东西”，而是：

```text
哪些信息必须保留？
哪些信息可以摘要？
哪些信息可以丢弃？
哪些信息应该放到外部存储，等需要时再取？
压缩后如何验证没有丢掉关键事实？
```

## 2. 问题现象

需要上下文压缩的系统通常会出现以下现象：

1. **超过上下文窗口**：长对话、长文档、长日志、多轮工具调用后，prompt 无法继续拼接。
2. **token 成本过高**：每轮请求重复携带大量历史内容，成本随对话长度线性甚至超线性增长。
3. **响应延迟上升**：输入 token 越长，prefill 时间越长，首 token 延迟和总延迟都会上升。
4. **模型注意力被稀释**：无关历史太多，模型抓不住当前问题和关键约束。
5. **早期约束丢失**：简单滑动窗口只保留最近消息，导致“不要改 schema”“必须中文回答”等早期要求被忘记。
6. **工具结果污染上下文**：日志、SQL 结果、搜索片段、网页内容过长，夹杂大量噪声和 prompt injection。
7. **摘要引入错误**：滚动摘要如果不校验，可能把未验证猜测写成事实。
8. **长任务无法恢复**：Agent 执行到一半重启或中断后，缺少结构化状态和压缩摘要，无法继续。

典型例子：

```text
用户让 Agent 修 CI：
1. 第 1 轮说“不能修改数据库 schema”；
2. 第 5 轮 Agent 读取大量测试日志；
3. 第 12 轮 Agent 修改代码并运行测试；
4. 第 20 轮上下文超长，系统只保留最近 8 轮；
5. 早期“不能修改 schema”的约束被裁掉；
6. Agent 为了修测试修改了 schema，违反用户约束。
```

这说明上下文压缩不能只按时间裁剪，还要保留不可丢失的信息。

## 3. 影响范围

上下文压缩会影响 LLM 应用的多个模块：

1. **ContextBuilder**：决定每次模型调用要放哪些内容。
2. **ConversationStore**：保存原始消息、摘要、压缩版本和外部产物引用。
3. **MemoryManager**：管理短期记忆、长期记忆、任务状态和用户偏好。
4. **ToolResultProcessor**：裁剪、摘要、脱敏和结构化工具返回结果。
5. **RAG Pipeline**：对召回文档做去重、rerank、片段压缩和引用保留。
6. **Agent Runner**：在多步执行中维护目标、计划、事实、错误和下一步状态。
7. **Permission/Safety 模块**：压缩前后都要保留安全规则和权限边界。
8. **Eval Harness**：评估压缩后任务是否还能正确完成。
9. **Observability**：记录压缩率、丢弃内容、摘要版本、引用 ID 和失败原因。

如果涉及代码实现，可能需要修改的模块包括：

1. `ContextBuilder`：增加 token 预算分配、压缩策略选择和最终 prompt 组装。
2. `Summarizer` / `Compressor`：实现滚动摘要、结构化摘要、证据压缩。
3. `MemoryManager`：区分短期上下文、任务状态、长期记忆和外部产物。
4. `ToolResultProcessor`：对日志、搜索结果、SQL 返回、网页内容做裁剪和脱敏。
5. `RetrievalPipeline`：增加上下文压缩器，例如 rerank 后再抽取关键句。
6. `TraceStore`：保存原始内容引用、压缩内容、压缩模型版本和校验结果。
7. `EvalHarness`：增加长上下文、早期约束、摘要失真、工具日志压缩相关测试集。

可能涉及的文件包括：

1. `context_builder.py`、`context_builder.go`、`ContextBuilder.java`。
2. `memory_manager.py`、`conversation_service.go`。
3. `summarizer.py`、`compressor.py`、`tool_result_processor.py`。
4. `rag_pipeline.py`、`retriever.py`、`reranker.py`。
5. `agent_runner.py`、`agent_state_machine.go`。
6. `eval_cases/context_compression/*.jsonl`。
7. `config/context_budget.yaml`、`config/compression_policy.yaml`。

## 4. 原因分析

上下文压缩的根本原因是：**模型上下文窗口、推理成本和注意力质量都是有限资源**。

### 4.1 Token 预算有限

一次模型调用的输入通常包括：

```text
系统指令 + 安全规则 + 工具说明 + 用户问题 + 历史对话
+ 当前任务状态 + 工具结果 + RAG 片段 + 输出预留 token
```

这些内容共享同一个上下文窗口。如果输入占满窗口，模型没有足够空间生成答案；如果工具说明、历史对话和文档片段过长，当前问题就会被稀释。

因此工程上要做 token 预算：

| 内容 | 优先级 | 处理方式 |
| --- | --- | --- |
| 系统安全规则 | 最高 | 不压缩、不丢弃 |
| 用户当前问题 | 最高 | 原文保留 |
| 用户硬性约束 | 最高 | 结构化保留 |
| 当前任务状态 | 高 | 结构化保留 |
| 已验证事实 | 高 | 摘要 + 引用 |
| 最近对话 | 中 | 保留最近窗口 |
| 历史对话 | 中 | 滚动摘要或检索 |
| 工具长结果 | 中 | 裁剪、摘要、外部引用 |
| RAG 片段 | 中 | rerank、去重、关键句抽取 |
| 闲聊和重复内容 | 低 | 丢弃 |

### 4.2 长上下文不等于有效上下文

即使模型支持几十万甚至百万 token，也不代表全部输入都能被稳定利用。长上下文会带来：

1. **成本上升**：输入 token 越多，费用越高。
2. **延迟上升**：prefill 阶段更慢。
3. **注意力稀释**：无关内容太多会降低关键信息被使用的概率。
4. **位置偏置**：模型更容易关注开头和结尾，中间内容可能被忽略。
5. **安全风险**：更多外部内容意味着更多 prompt injection 和敏感信息暴露。

所以长上下文是能力上限，不是上下文工程的替代品。

### 4.3 压缩本质是信息选择

上下文压缩不是单纯把文本变短，而是在做信息选择：

```text
原始上下文 C
当前任务目标 G
token 预算 B

选择一个压缩后的上下文 C'
使得 len(C') <= B
并且 C' 对完成 G 的信息损失最小
```

这个过程必然有取舍。最重要的是区分：

1. **不可丢失信息**：目标、硬约束、权限、外部 ID、当前状态、已验证事实。
2. **可摘要信息**：历史对话、工具返回、文档片段、决策过程。
3. **可外部化信息**：完整日志、文件内容、搜索结果、长报告。
4. **可丢弃信息**：寒暄、重复内容、无关细节、过期中间推理。

### 4.4 压缩和记忆不是一回事

Memory 是信息存储体系，Compression 是把信息变成适合本轮模型使用的过程。

```text
Memory：存在哪里、存多久、谁能访问、怎么召回。
Compression：召回或历史内容太长时，怎么裁剪、摘要、结构化和引用。
Context：最终真正放进模型输入的内容。
```

一个稳定系统通常是：

```text
原始消息/工具结果 -> 外部持久化
关键字段 -> 结构化状态
历史内容 -> 摘要或索引
当前请求 -> 按 token 预算组装进 Context
```

## 5. 解决方案

上下文压缩通常不是单一算法，而是一组组合策略。

### 5.1 滑动窗口

滑动窗口保留最近 N 轮消息或最近 N 个 token，丢弃更早内容。

优点：

1. 实现简单。
2. 延迟低。
3. 适合最近上下文最重要的闲聊或短任务。

缺点：

1. 容易丢早期硬约束。
2. 不知道哪些历史内容重要。
3. 不适合长任务、代码修复、审批流程。

改进方式：

```text
最近消息原文保留
+ 早期硬约束结构化保留
+ 旧历史滚动摘要
+ 外部资源 ID 保留
```

### 5.2 滚动摘要

滚动摘要把较早历史压缩成一段摘要，新消息继续原文保留。

```text
旧摘要 + 新增对话/工具结果 -> 新摘要
```

摘要应该包含：

1. 用户目标。
2. 硬性约束。
3. 已完成步骤。
4. 当前计划。
5. 已验证事实。
6. 未解决问题。
7. 外部资源 ID。
8. 风险和审批状态。

摘要不应该包含：

1. 未验证猜测。
2. 与任务无关的闲聊。
3. 大段日志原文。
4. 过期计划。

摘要模板示例：

```text
任务目标：
- 修复 LoginServiceTest 失败。

硬性约束：
- 不允许修改数据库 schema。
- 只做最小范围修改。

已验证事实：
- 失败用例：LoginServiceTest.testExpiredToken。
- 失败日志位置：artifact://ci/123/report.txt。

当前计划：
- 读取 LoginService token 校验逻辑。
- 修改过期 token 判断。
- 运行 LoginServiceTest。

未完成事项：
- 尚未运行全量回归。
```

### 5.3 结构化状态压缩

结构化状态把自然语言历史转换成 JSON、表格或字段。

适合 Agent 长任务：

```json
{
  "goal": "修复登录接口单测失败",
  "constraints": ["不能修改数据库 schema", "只做最小修改"],
  "phase": "DEBUGGING",
  "current_plan": ["定位失败用例", "阅读相关代码", "修改实现", "运行测试"],
  "verified_facts": [
    {
      "fact": "失败用例是 LoginServiceTest.testExpiredToken",
      "source": "artifact://ci/123/report.txt"
    }
  ],
  "artifacts": {
    "ci_report": "artifact://ci/123/report.txt"
  },
  "risks": ["尚未运行全量回归"]
}
```

它的优势是：

1. 不容易被自然语言摘要污染。
2. 便于恢复、审计和版本管理。
3. 便于规则校验，例如必须包含 `goal/constraints/phase`。

### 5.4 工具结果压缩

工具结果往往是上下文膨胀的主要来源，例如日志、SQL 查询结果、搜索结果、网页正文、测试报告。

处理方式：

1. **日志压缩**：只保留错误栈、错误码、异常时间、关键上下文和日志文件引用。
2. **SQL 结果压缩**：只保留 schema、行数、统计摘要、异常样本，不把全表塞进 prompt。
3. **搜索结果压缩**：去重、rerank、只保留标题、摘要、命中原因和 URL。
4. **代码结果压缩**：保留函数签名、关键片段、调用链、文件路径和行号。
5. **测试报告压缩**：保留失败用例、错误类型、堆栈顶层、失败断言和报告路径。

示例：

```text
原始日志 50,000 行
-> 提取 ERROR/WARN 附近窗口
-> 聚合同类错误
-> 保留 top stack trace
-> 附带 artifact_id
-> 压缩成 500 tokens
```

### 5.5 RAG 上下文压缩

RAG 场景下，压缩通常发生在召回之后、拼 prompt 之前：

```text
Query -> 多路召回 -> 去重 -> rerank -> 上下文压缩 -> Prompt
```

常见做法：

1. **TopK 控制**：只取高分片段。
2. **MMR 去冗余**：减少相似 chunk 重复。
3. **关键句抽取**：从长 chunk 中抽取能回答问题的句子。
4. **父子 chunk**：召回小 chunk，展示父段落摘要或必要上下文。
5. **Query-aware compression**：根据当前问题压缩文档，而不是通用摘要。
6. **引用保留**：压缩后保留 `doc_id/chunk_id/page/line`，便于校验。

RAG 压缩的关键是忠实度。压缩器不能编造原文没有的结论。

### 5.6 层级摘要

面对超长文档、长代码库、长会议记录，可以使用层级摘要：

```text
段落摘要 -> 章节摘要 -> 文档摘要 -> 项目摘要
```

优点：

1. 适合几十万 token 的资料。
2. 可以逐层控制粒度。
3. 支持从全局摘要回到局部证据。

缺点：

1. 多轮摘要会累积误差。
2. 需要保留原文引用。
3. 需要评测摘要是否漏掉关键点。

### 5.7 外部产物引用

很多内容不应该进入 prompt，而应该进入外部存储：

| 内容 | 处理方式 |
| --- | --- |
| 完整日志 | 对象存储 + 错误摘要 + artifact_id |
| 大文件 | 文件路径 + 文件索引 + 局部读取工具 |
| 数据库查询结果 | 统计摘要 + sample rows + query_id |
| 网页正文 | 清洗摘要 + URL + 检索入口 |
| 图片/截图 | OCR 摘要 + image_id |
| 长代码 | 文件路径 + 函数摘要 + 按需读取 |

模型看到的是：

```text
测试报告摘要：LoginServiceTest.testExpiredToken 失败。
完整报告：artifact://ci/123/report.txt，可通过 read_artifact 工具读取。
```

这样既压缩了上下文，也保留了可追溯性。

### 5.8 压缩后校验

上下文压缩最容易出问题的是漏掉关键约束或引入错误事实。因此需要校验：

1. 压缩后必须包含用户目标。
2. 压缩后必须包含硬性约束。
3. 压缩后必须包含当前状态和下一步。
4. 压缩后的事实必须带来源。
5. 未验证猜测不能写入 `verified_facts`。
6. 压缩前后关键字段数量要一致。
7. 缺少关键字段时拒绝覆盖旧摘要。

## 6. 可选方案对比

| 方案 | 原理 | 优点 | 缺点 | 适用场景 |
| --- | --- | --- | --- | --- |
| 滑动窗口 | 保留最近 N 轮 | 简单、低延迟 | 丢早期约束 | 短对话、闲聊 |
| 滚动摘要 | 旧历史摘要化 | 成本低，适合长对话 | 摘要可能失真 | 客服、会议、多轮问答 |
| 结构化状态 | 把目标/计划/事实存字段 | 稳定、可恢复、可校验 | 需要设计 schema | Agent 长任务、工具调用 |
| RAG 压缩 | 召回后抽取关键片段 | 保留相关证据 | 依赖召回和 rerank | 知识库问答、文档问答 |
| 层级摘要 | 分块逐层摘要 | 适合超长材料 | 多层误差累积 | 长报告、代码库、会议记录 |
| 外部引用 | 大内容只存 ID/路径 | 省 token，可追溯 | 需要工具再读取 | 日志、文件、测试报告 |
| 规则裁剪 | 按字段、行数、错误码裁剪 | 可控、确定性强 | 不理解语义 | 日志、表格、结构化数据 |
| 模型压缩 | 让 LLM 按任务摘要 | 语义能力强 | 成本高，可能幻觉 | 非结构化长文本 |
| Embedding 检索 | 历史内容向量化后按需召回 | 不必全量注入 | 召回不稳定 | 长期记忆、历史案例 |

容易混淆的概念：

| 概念 | 是否属于本文上下文压缩 | 说明 |
| --- | --- | --- |
| Prompt Cache | 不完全是 | 主要降低重复前缀成本和延迟，不减少模型看到的语义内容 |
| KV Cache 压缩 | 不是同一层 | 属于推理系统优化，压缩注意力缓存 |
| 文件 gzip 压缩 | 不是 | 压缩字节大小，模型仍无法直接理解压缩后的二进制 |
| 向量量化压缩 | 不是同一层 | 压缩 embedding 存储，不等于压缩 prompt |
| 摘要 | 是 | 最常见的语义压缩方法 |
| 结构化状态 | 是 | Agent 工程里最可靠的压缩方式之一 |

## 7. 推荐方案

推荐使用 **分层上下文压缩方案**：

```text
系统规则：不压缩，强制保留
当前用户问题：原文保留
硬性约束：结构化保留
任务状态：JSON 保留
最近对话：滑动窗口保留
旧对话：滚动摘要
工具结果：规则裁剪 + 摘要 + 外部引用
RAG 文档：rerank + 去重 + query-aware compression
长期记忆：按需检索 + 权限过滤
```

核心原则：

1. **先分类，再压缩**：不同上下文类型不能用同一种压缩方式。
2. **硬约束不摘要化丢弃**：目标、权限、安全规则、审批状态必须结构化保留。
3. **事实必须带来源**：摘要里的关键事实要能回到原文、日志、文件或工具结果。
4. **大内容外部化**：完整日志、文件、报告不要塞 prompt，只保留引用和摘要。
5. **压缩结果可评测**：必须用长任务回放验证压缩后是否还能正确执行。

推荐架构：

```text
ConversationStore / ToolResultStore / MemoryStore
    |
    v
ContextCompressor
    |-- MessageWindowCompressor
    |-- RollingSummarizer
    |-- StructuredStateExtractor
    |-- ToolResultCompressor
    |-- RAGContextCompressor
    |
    v
ContextBudgetAllocator
    |
    v
ContextBuilder
    |
    v
LLM / Agent
```

## 8. 实施步骤

### 8.1 定义上下文类型

先把上下文来源分类：

1. `system_policy`：系统规则、安全规则、输出格式。
2. `user_current_input`：当前用户问题。
3. `hard_constraints`：用户硬性约束、权限、审批状态。
4. `recent_messages`：最近对话。
5. `conversation_summary`：历史摘要。
6. `run_state`：任务状态、计划、阶段、checkpoint。
7. `tool_results`：工具调用结果。
8. `retrieved_chunks`：RAG 召回片段。
9. `long_term_memory`：用户偏好、项目知识、历史经验。
10. `artifacts`：外部文件、日志、报告、图片引用。

### 8.2 设计 token 预算

示例预算：

```yaml
context_budget:
  total_input_tokens: 24000
  reserve_output_tokens: 4000
  system_policy: 2000
  current_user_input: 1000
  hard_constraints: 1000
  run_state: 2500
  recent_messages: 4000
  conversation_summary: 2500
  tool_results: 5000
  retrieved_chunks: 5000
  long_term_memory: 1000
```

预算不是固定死的，可以根据任务类型动态调整。例如 RAG 问答给 `retrieved_chunks` 更多预算，代码修复给 `tool_results` 和 `run_state` 更多预算。

### 8.3 实现压缩器

核心接口可以设计为：

```python
class ContextItem:
    def __init__(self, type, content, priority, source_id=None, metadata=None):
        self.type = type
        self.content = content
        self.priority = priority
        self.source_id = source_id
        self.metadata = metadata or {}

class CompressionResult:
    def __init__(self, content, tokens, sources, warnings=None):
        self.content = content
        self.tokens = tokens
        self.sources = sources
        self.warnings = warnings or []

class ContextCompressor:
    def compress(self, items: list[ContextItem], budget: int) -> CompressionResult:
        raise NotImplementedError
```

不同类型使用不同压缩器：

```text
recent_messages -> sliding window
old_messages -> rolling summary
tool_results -> rule-based extraction + summary
retrieved_chunks -> rerank + extractive compression
run_state -> structured JSON
```

### 8.4 实现压缩主流程

伪代码：

```python
def build_context(request, run_id, max_input_tokens):
    budget = allocate_budget(request.task_type, max_input_tokens)

    policy = load_system_policy()
    current_input = request.user_input
    run_state = load_run_state(run_id)
    recent_messages = load_recent_messages(request.conversation_id)
    old_summary = load_or_create_summary(request.conversation_id)
    tool_results = load_recent_tool_results(run_id)
    retrieved = retrieve_related_chunks(request)
    memory = retrieve_memory(request.user_id, request.project_id, request.user_input)

    parts = []
    parts.append(no_compress(policy, budget.system_policy))
    parts.append(no_compress(current_input, budget.current_user_input))
    parts.append(structured_state(run_state, budget.run_state))
    parts.append(sliding_window(recent_messages, budget.recent_messages))
    parts.append(rolling_summary(old_summary, budget.conversation_summary))
    parts.append(compress_tool_results(tool_results, budget.tool_results))
    parts.append(compress_rag_chunks(retrieved, budget.retrieved_chunks))
    parts.append(compress_memory(memory, budget.long_term_memory))

    context = assemble(parts)
    validate_context(context)
    return context
```

### 8.5 压缩后校验

校验规则示例：

```python
def validate_context(context):
    assert context.has("current_user_input")
    assert context.has("hard_constraints")
    assert context.has("run_state")
    assert context.token_count <= context.max_tokens

    for fact in context.verified_facts:
        assert fact.source_id is not None

    for constraint in context.hard_constraints:
        assert constraint in context.rendered_prompt
```

### 8.6 持久化压缩结果

每次压缩建议保存：

1. `compression_id`。
2. `conversation_id` / `run_id`。
3. 原始内容引用。
4. 压缩后内容。
5. 压缩策略和版本。
6. 使用的模型版本。
7. token 压缩率。
8. 校验结果。
9. 生成时间。

不要只保存最终 prompt，否则很难复盘压缩是否导致错误。

### 8.7 测试重点

如果涉及代码实现，测试重点包括：

1. **预算测试**：最终 prompt 是否小于 token 限制。
2. **硬约束保留测试**：早期用户约束是否仍在压缩上下文中。
3. **事实忠实测试**：摘要是否引入原文没有的事实。
4. **来源引用测试**：关键事实是否带 `source_id`。
5. **长任务续跑测试**：压缩后 Agent 是否能从正确状态继续。
6. **工具日志压缩测试**：错误码、栈顶、失败用例是否保留。
7. **RAG 引用测试**：压缩后答案是否仍能引用正确文档。
8. **安全测试**：外部网页或文档中的 prompt injection 是否被隔离或降权。
9. **回归测试**：压缩策略升级后是否破坏旧成功 case。

## 9. 风险与注意事项

1. **摘要可能丢事实**  
   解决方式是保留结构化硬约束、外部引用和压缩前后对比校验。

2. **摘要可能编造事实**  
   摘要中的关键事实必须带来源。没有来源的内容只能放入“待验证假设”，不能放入“已验证事实”。

3. **递归摘要会累积误差**  
   多次滚动摘要后应定期从原始消息重新生成基线摘要，或保留分层摘要树。

4. **滑动窗口会遗忘早期约束**  
   早期硬约束必须提取到结构化状态，而不是依赖最近消息。

5. **RAG 压缩可能破坏证据链**  
   抽取关键句后必须保留文档 ID、chunk ID、页码或行号。

6. **压缩器本身也可能被注入**  
   外部文档里可能写“忽略之前规则”。压缩器要把外部内容当作数据，不当作指令。

7. **过度压缩会降低效果**  
   压缩率不是越高越好。应以任务成功率、引用准确率和约束保留率为准。

8. **只做语义摘要不够**  
   Agent 长任务必须有结构化状态，否则摘要一旦错，任务会跑偏。

9. **敏感信息不能因为摘要而泄漏**  
   压缩前要做权限过滤和脱敏，摘要中也不能保留密钥、身份证、手机号等敏感原文。

10. **Prompt Cache 不能替代压缩**  
    Prompt Cache 只是缓存稳定前缀以降低成本和延迟，不解决无关上下文干扰模型的问题。

## 10. 验证方式

### 10.1 离线评测

构造长上下文评测集：

1. 早期约束在第 1 轮，关键操作在第 20 轮。
2. 长日志中只有少数错误行关键。
3. 文档中多个相似片段，只有一个能回答问题。
4. 历史对话中有过期计划和新计划冲突。
5. 外部文档包含 prompt injection。

验证指标：

| 指标 | 含义 |
| --- | --- |
| `compression_ratio` | 压缩后 token / 原始 token |
| `constraint_recall` | 硬约束保留率 |
| `fact_faithfulness` | 摘要事实忠实度 |
| `source_coverage` | 关键事实来源覆盖率 |
| `task_success_rate` | 压缩后任务成功率 |
| `answer_quality` | 答案质量或人工评分 |
| `citation_accuracy` | 引用是否指向正确来源 |
| `latency_p95` | P95 延迟 |
| `cost_per_run` | 单任务成本 |

### 10.2 A/B 对比

对比不同策略：

```text
A：不压缩，直接截断
B：滑动窗口
C：滚动摘要
D：结构化状态 + 滚动摘要
E：结构化状态 + RAG 压缩 + 外部引用
```

重点看：

1. 任务成功率是否提升。
2. 硬约束是否被保留。
3. token 和延迟是否下降。
4. 摘要是否有幻觉。
5. 长任务能否正确恢复。

### 10.3 回放验证

Agent 场景必须做回放：

```text
原始长对话 -> 执行到第 N 步 -> 触发压缩
-> 用压缩上下文继续执行 -> 判断最终结果是否一致
```

如果压缩后 Agent 不能继续执行正确下一步，说明压缩策略没有保留必要状态。

### 10.4 人工抽检

人工抽检重点：

1. 摘要是否忠实。
2. 是否漏掉用户硬性约束。
3. 是否把模型猜测写成事实。
4. 是否保留证据引用。
5. 是否泄漏敏感信息。

## 11. 总结

上下文压缩的原理，是在有限上下文窗口和成本约束下，对历史信息做 **选择、摘要、结构化、检索和外部化**，让模型看到“完成当前任务最需要的信息”，而不是看到“所有信息”。

核心方法包括：

1. 滑动窗口保留最近上下文。
2. 滚动摘要压缩旧历史。
3. 结构化状态保存目标、约束、计划、事实和外部 ID。
4. 工具结果只保留关键错误、统计、样本和引用。
5. RAG 召回后做去重、rerank 和 query-aware compression。
6. 大文件、日志、报告外部化，只把摘要和引用放进 prompt。
7. 用 Harness 验证压缩后是否仍能正确完成任务。

面试回答可以这样说：

```text
上下文压缩不是简单截断，也不是把所有历史总结成一句话。它的本质是在 token 预算有限的情况下，对上下文做信息选择：系统规则、当前问题、硬约束和任务状态必须保留；旧对话可以滚动摘要；工具长结果要裁剪成关键错误和引用；RAG 文档要召回、rerank、去重后再抽取相关片段；完整日志和文件应该放外部存储，通过 artifact_id 按需读取。

工程上我会把上下文分成系统规则、当前输入、结构化任务状态、最近消息、历史摘要、工具结果、RAG 片段和长期记忆，再按 token 预算组装。压缩后要校验目标、约束、当前状态、关键事实和来源是否还在，不能让摘要引入幻觉。最后用长任务回放集评测压缩前后任务成功率、约束保留率、引用准确率、token 成本和延迟。
```
