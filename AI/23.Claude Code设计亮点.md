# 23. Claude Code 设计亮点

如果面试问“Claude Code 里印象最深刻的设计是什么”，不要只回答“它能写代码”。更好的回答是：Claude Code 把大模型从聊天框变成了一个**运行在真实工程环境里的受控 Agent Runtime**。

它的核心不是某个单点功能，而是一组组合设计：

```text
代码仓库上下文
+ 终端工具执行
+ 文件读写编辑
+ 分层记忆
+ 权限和沙箱
+ Hooks
+ MCP 工具扩展
+ Subagents
+ 可恢复的任务流程
```

我最值得展开讲的是：**它没有把 Agent 做成一个“全能自动驾驶黑盒”，而是把能力、上下文、权限和执行过程都拆成可配置、可审计、可接管的工程边界。**

## 1. 从聊天助手到终端内 Agent

Claude Code 的定位是 agentic coding tool。它可以读代码库、编辑文件、运行命令，并接入开发工具。这个设计和普通 IDE 补全最大的区别是：

1. 普通补全主要在当前文件或当前光标附近工作。
2. Claude Code 面向任务，可以跨文件理解、修改、运行命令和验证。
3. 它运行在终端、IDE、桌面和 Web 等多种入口，但核心能力围绕真实项目环境。

这类设计的关键价值：

1. **靠近工程现场**：直接在仓库、Shell、Git、测试命令里工作。
2. **可执行闭环**：不是只生成答案，而是能读文件、改文件、跑测试、根据错误继续修。
3. **用户保持控制**：高风险操作通过权限、确认、Hook、设置文件控制。

面试里可以说：它更像“带工具权限和状态管理的开发代理”，不是单纯代码生成模型。

## 2. 分层记忆：CLAUDE.md

Claude Code 的 Memory 设计很工程化。它用不同位置的 `CLAUDE.md` 表达不同作用域的长期上下文：

| 记忆类型 | 位置 | 作用 |
| --- | --- | --- |
| Enterprise policy | 系统级路径，例如 `/etc/claude-code/CLAUDE.md` | 组织级安全、合规、编码标准 |
| Project memory | `./CLAUDE.md` 或 `./.claude/CLAUDE.md` | 团队共享的项目架构、命令、约定 |
| User memory | `~/.claude/CLAUDE.md` | 个人偏好和常用流程 |
| Local project memory | 本地项目偏好 | 个人项目内偏好，适合不提交的信息 |

这个设计亮点在于：

1. **把隐性上下文显式化**：构建命令、测试命令、代码规范不用每次重新告诉模型。
2. **有层级和优先级**：企业策略、项目规则、个人偏好分开，避免混在一个超长 prompt 里。
3. **可版本化**：项目级 `CLAUDE.md` 可以进入 Git，团队共享同一套 Agent 规则。
4. **可维护**：用户可以用 `/memory` 或 `#` 快速追加记忆。

这和 Agent Memory 里的长期记忆、项目记忆、程序性记忆是一致的。它没有把所有记忆都做成神秘向量库，而是优先使用人能读、人能改、能 review 的 Markdown。

易错点：

1. `CLAUDE.md` 不适合存密钥、token、生产密码。
2. 记忆要定期清理，否则旧命令和旧架构会污染后续任务。
3. 企业策略应高于个人偏好，不能让个人设置覆盖安全底线。

## 3. 权限系统：默认不盲目执行

Claude Code 的工具权限设计是我认为最重要的安全边界之一。它把工具分成不同风险等级，例如：

1. `Read`、`Grep`、`Glob` 这类读操作通常风险较低。
2. `Edit`、`Write` 会修改文件，需要权限控制。
3. `Bash` 可以执行任意命令，风险最高。
4. `WebFetch`、`WebSearch` 涉及外部网络和数据流动，也需要控制。

权限可以在 `settings.json` 里配置：

```json
{
  "permissions": {
    "allow": ["Bash(git diff:*)"],
    "ask": ["Bash(git push:*)"],
    "deny": [
      "Read(./.env)",
      "Read(./secrets/**)",
      "Bash(curl:*)"
    ]
  }
}
```

这个设计的价值：

1. **最小权限**：不是所有工具都默认开放。
2. **敏感文件不可见**：用 `deny` 规则避免模型读取 `.env`、密钥目录。
3. **高风险操作确认**：例如 `git push`、删除文件、网络请求。
4. **企业可管控**：企业级 managed policy 优先级最高，个人无法覆盖。

它体现了一个重要原则：**Agent 的安全不能只靠 prompt，要靠工具权限、文件边界和执行策略。**

## 4. 沙箱设计：把执行风险收敛到环境边界

Claude Code 支持 Bash sandboxing，Docker 也提供 Claude Code sandbox 运行方式。沙箱的意义不是让模型“更聪明”，而是把命令执行风险隔离在可控范围内。

典型控制点：

1. 文件系统访问范围。
2. 网络访问范围。
3. 是否允许本地端口绑定。
4. 哪些命令必须在沙箱外执行。
5. 是否自动允许已沙箱化的 Bash 命令。

工程启发：

1. AI 编程工具必须假设模型会犯错。
2. 错误命令不应该直接影响真实主机、真实凭证或生产环境。
3. 对高风险命令，沙箱和用户确认要同时存在。

面试时可以说：沙箱是把 Agent 从“危险的本机自动化脚本”变成“受控执行器”的关键。

## 5. Hooks：把不可控模型输出接入确定性工程规则

Hooks 是 Claude Code 很有工程味的设计。它允许在工具执行前后、用户提交 prompt 时、通知事件时运行自定义命令。

典型事件：

1. `PreToolUse`：工具执行前触发。
2. `PostToolUse`：工具执行成功后触发。
3. `UserPromptSubmit`：用户输入提交后触发。
4. `Notification`：需要用户许可或等待输入时触发。

示例用途：

1. 修改 Python 文件后自动跑 formatter。
2. 写文件前检查是否在受保护目录。
3. 执行 Bash 前拦截危险命令。
4. 用户 prompt 提交前注入项目上下文或做敏感信息检查。
5. 工具执行后记录审计日志。

`PreToolUse` Hook 还可以返回 `allow`、`deny`、`ask` 这类决策，直接影响工具是否执行。

这个设计很关键，因为它把 LLM 的不确定输出接到了确定性规则系统里：

```text
模型提出动作
-> Hook 检查
-> allow / deny / ask
-> 执行工具
-> Post Hook 校验和记录
```

真实企业落地时，Hooks 可以做：

1. 密钥扫描。
2. 代码格式化。
3. 禁止改生产配置。
4. 自动跑单测。
5. 安全审计。
6. 成本和工具调用统计。

## 6. MCP：工具生态的标准化扩展

Claude Code 可以通过 Model Context Protocol 接外部工具、数据库和 API。MCP 的价值是解决 `N 个 Agent * M 个工具` 的重复集成问题。

MCP 把外部能力分成：

1. **Tools**：可执行动作，例如查 Jira、建 PR、查数据库。
2. **Resources**：可读取数据，例如文档、文件、记录。
3. **Prompts**：可复用提示模板。

Claude Code 接入 MCP 后，可以让编码任务跨越代码仓库边界：

```text
Jira issue
-> GitHub repo
-> Sentry / 监控
-> Postgres / 业务数据
-> Slack / Figma / Gmail
-> 代码修改和 PR
```

这个设计最值得借鉴的是“工具标准化 + 权限声明”。MCP 工具需要表达是否只读、是否有破坏性等 hint，帮助模型和用户理解风险。

易错点：

1. MCP 不是安全本身，只是标准化协议。
2. 每个 MCP server 仍要做鉴权、租户隔离、审计和参数校验。
3. 不要给 Agent 接太多工具，工具越多，选择成本和误用风险越高。
4. 数据库类 MCP 必须限制只读、扫描量和敏感字段。

## 7. Subagents：上下文隔离和工具隔离

Claude Code 的 Subagents 设计也很值得讲。每个 subagent 可以有：

1. 独立的系统提示。
2. 独立的上下文窗口。
3. 指定工具权限。
4. 特定任务描述。
5. 可复用的 Markdown 配置。

适合场景：

1. Code reviewer：只读代码、跑检查，不直接改文件。
2. Test fixer：允许读日志、运行测试、改测试相关文件。
3. Security auditor：只读和 grep，关注密钥、注入、越权。
4. Docs writer：只改文档目录。

这个设计解决两个问题：

1. **上下文污染**：主 Agent 不需要背所有审查规则、测试规则、文档规则。
2. **权限隔离**：不同角色的 Agent 拿不同工具，避免一个 Agent 全权访问。

它本质上是把复杂任务拆成多个受限角色：

```text
Main Agent: 规划和整合
Reviewer Subagent: 检查风险
Test Subagent: 跑测试和定位失败
Docs Subagent: 更新文档
```

面试里要补一句：Subagent 不是越多越好。任务边界清楚、可并行、输出可校验时才适合拆；如果多个 agent 同时改同一批文件，反而会增加冲突。

## 8. 配置层级：个人、项目、企业分治

Claude Code 的 settings 也有层级：

```text
Enterprise managed policy
> Command line arguments
> Local project settings
> Shared project settings
> User settings
```

这个设计很适合企业落地：

1. 企业可以强制禁用危险模式。
2. 项目可以共享工具权限、Hooks、环境变量。
3. 个人可以保留自己的偏好。
4. 本地实验配置不需要提交到仓库。

它背后的思想是：Agent 工具不是个人玩具，而是团队工程基础设施。团队需要可复制的规则和可治理的权限。

## 9. 我认为最值得借鉴的设计

如果只能选一个，我会选：

```text
权限化工具调用 + Hooks + 分层记忆
```

原因是这三者把 Agent 能力从“会生成文本”推进到“能在真实工程里做事”：

1. **分层记忆**让 Agent 理解项目和团队约定。
2. **权限化工具调用**让 Agent 可以执行真实动作但不越界。
3. **Hooks**让企业把确定性规则插入模型动作前后。

这套设计形成了一个闭环：

```text
CLAUDE.md 提供长期上下文
-> 模型规划下一步
-> 工具权限判断风险
-> Hook 做确定性拦截/补充/审计
-> 工具执行
-> 结果回到上下文
-> 继续迭代或交给用户确认
```

这比单纯“让模型更强”更重要，因为真实工程中的核心问题往往是：

1. 它有没有读到正确上下文。
2. 它有没有权限做这件事。
3. 它做完后有没有验证。
4. 出错后能不能追踪和回滚。

## 10. 对自研 Agent 的启发

如果自己设计一个代码 Agent，可以借鉴：

1. **上下文显式化**：用项目规则文件记录构建命令、目录边界、编码规范。
2. **工具分级**：读、写、执行、网络、生产操作分不同权限。
3. **默认保守**：高风险操作 ask，敏感文件 deny。
4. **Hook 机制**：在写文件、跑命令、提交 PR 前后插入企业规则。
5. **MCP 化工具**：把 Git、CI、Jira、监控、数据库统一成结构化工具。
6. **Subagent 角色化**：Reviewer、Tester、Security、Docs 分开上下文和权限。
7. **审计和回放**：保存工具调用、参数、结果摘要、拒绝原因和用户确认。
8. **沙箱执行**：不可信代码和命令在容器或受限环境执行。

## 11. 易错点

1. 不要把 Claude Code 理解成“代码补全工具”，它更接近 Agent Runtime。
2. 不要把 MCP 当成安全边界，MCP server 自身仍要鉴权和审计。
3. 不要把 `CLAUDE.md` 写成超长杂货铺，记忆越多不一定越好。
4. 不要让模型自由执行 Bash，高风险命令必须权限控制。
5. 不要只靠 prompt 禁止危险行为，必须用 deny、sandbox、hook、审批。
6. 不要滥用 Subagents，拆分要有清晰输入输出和工具边界。
7. 不要把敏感文件交给 Agent 读取后再要求“不要泄露”，应直接在权限层不可见。

## 12. 面试回答模板

可以这样回答：

> 我对 Claude Code 印象最深的是它把 AI 编程工具做成了一个受控 Agent Runtime，而不是普通聊天框。它可以读代码、改文件、跑命令、接 MCP 工具，但这些能力被分层记忆、权限、沙箱、Hooks 和 Subagents 管起来。比如 `CLAUDE.md` 把企业、项目、个人规则显式化，让模型每次进仓库都能知道构建命令和代码约定；`settings.json` 里可以 allow/ask/deny 工具，敏感文件可以直接对模型不可见；Hooks 可以在工具执行前后插入确定性规则，比如阻止改生产配置、自动跑 formatter 或记录审计；MCP 则把 Jira、GitHub、数据库、监控这类外部系统标准化接入；Subagents 用独立上下文和工具权限做专业分工。
>
> 这个设计最值得借鉴的地方是它没有把 Agent 做成全能黑盒，而是把上下文、权限、工具和审计拆成清晰边界。真实工程里，模型强不强只是一部分，更关键的是它有没有正确上下文、有没有被限制在最小权限内、执行前后有没有确定性校验、失败后能不能追踪和恢复。所以如果我设计类似系统，会优先做项目规则文件、工具权限分级、Hook 拦截、MCP 工具标准化、Subagent 角色隔离和沙箱执行。
