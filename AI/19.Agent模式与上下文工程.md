# 19. Agent 模式与上下文工程

面试里问 Agent 发展、ReAct、subagent、上下文工程、Skill/MCP/Rule 和“Skill 能不能百分百触发”，重点不是评价概念热不热，而是说明 Agent 能做什么、不能做什么，以及如何把不稳定的大模型收敛到可控工程系统里。

## 1. Agent 当前能做什么

Agent 可以理解为“模型 + 上下文 + 工具 + 状态机 + 评测”的组合。它当前更适合增强知识工作和工程流程，而不是完全替代人。

适合场景：

1. **信息检索和总结**：跨文档、代码库、工单、日志检索并给出带引用的总结。
2. **研发辅助**：代码解释、单测补充、CI 排障、迁移样板、Review 辅助。
3. **客服和运营**：标准问答、工单分流、查订单、生成处理建议。
4. **数据分析**：生成 SQL、解释指标、制作报表草稿，但需要权限和扫描量限制。
5. **运维排障**：聚合告警、日志、trace 和 runbook，给出处置建议或执行低风险动作。

不适合完全放权的场景：

1. 强事务核心链路，例如支付、库存、账务最终决策。
2. 高风险生产写操作，例如删库、回滚、退款、封禁。
3. 缺少验证标准的开放任务，例如“把系统优化好”。
4. 需要长期责任归属和复杂组织协调的决策。

面试里可以概括：Agent 会替代一部分重复的信息收集、样板生成、初步排障和流程执行，但很难替代对业务目标、风险收益、最终责任负责的人。真实落地的关键是工具权限、状态管理、评测和人工确认。

## 2. Agent 常见模式

| 模式 | 核心流程 | 适用场景 | 风险 |
| --- | --- | --- | --- |
| 单轮问答 | query -> answer | 简单知识问答 | 容易幻觉，缺少工具验证 |
| RAG | retrieve -> generate | 企业知识库、文档问答 | 召回质量决定上限 |
| ReAct | Reason -> Act -> Observe 循环 | 排障、检索、开放式工具使用 | 容易循环、误用工具 |
| Plan-and-Execute | 先计划，再逐步执行 | 多步骤研发、数据分析 | 计划可能过期，需要动态修正 |
| Workflow/Graph | 固定节点和条件边 | 客服、审批、代码修复、RAG 链路 | 灵活性弱，流程设计成本高 |
| Multi-Agent | Supervisor/Worker 等协作 | 长链路复杂任务、并行分析 | 通信成本高，状态容易混乱 |

## 3. ReAct 模式

ReAct 是 Reasoning + Acting。它让模型在推理和工具调用之间循环：

```text
Thought: 需要确认测试失败原因
Action: read_ci_log(job_id)
Observation: test_xxx timeout
Thought: 需要查看 timeout 相关代码
Action: search_code("test_xxx")
...
```

价值：

1. 不只生成答案，而是能根据工具观察修正下一步。
2. 适合信息不足、需要逐步探索的问题。
3. 工具结果可以降低纯模型猜测。

工程约束：

1. 设置 `max_steps/max_tool_calls/max_runtime`。
2. 同一工具、同一参数、同一错误码不要重复调用。
3. 高风险 Action 前要求审批。
4. 每一步要记录 trace，便于复盘和评测。
5. 最终结果要经过外部验证，而不是模型自称完成。

## 3.1 ReAct 架构怎么实现

ReAct 可以用现成框架搭，也可以自己实现。面试里不要只说“用 LangChain”，更重要的是说清楚它本质上是一个受约束的状态机。

核心组件：

1. **LLM/Planner 节点**：根据用户问题、当前状态和工具结果决定下一步。
2. **Tool Router**：把模型输出的结构化 action 路由到真实工具，例如地图、搜索、数据库、代码检索。
3. **Observation Parser**：把工具返回压缩成模型可读的事实，过滤异常、空结果和低置信内容。
4. **Memory/Context Manager**：注入用户偏好、历史任务摘要、权限、可用工具和当前计划。
5. **Guardrail**：限制最大步数、最大耗时、工具白名单、危险动作审批和参数 schema。
6. **Trace Store**：记录每一步 thought/action/observation/final answer，便于调试、评测和回放。

实现方式：

1. **框架方式**：LangGraph、LangChain Agents、Semantic Kernel、Eino 等框架适合快速搭建 tool calling、状态图和 trace。
2. **自研方式**：用数据库保存 `run_id/step_id/state/tool_calls`，用代码循环执行“模型决策 -> 工具调用 -> 状态更新”，适合对权限、审计、恢复要求更强的生产系统。
3. **混合方式**：外层用自研工作流控制强约束节点，内部某些节点用 ReAct 做开放检索或排障。

一个简化状态机：

```text
receive_user_query
-> build_context
-> llm_decide_action
-> validate_action_schema
-> call_tool
-> summarize_observation
-> update_state
-> should_continue ? llm_decide_action : final_answer
```

真实工程里通常不让模型自由输出任意字符串，而是要求输出结构化 action：

```json
{
  "thought_summary": "需要先确认目的高铁站，再查询路线和实时拥堵",
  "action": "query_route",
  "arguments": {
    "from": "深圳南山区",
    "to": "深圳北站",
    "mode": "transit"
  }
}
```

如果问题是“深圳南山区到高铁站的路线和人流量情况”，ReAct 流程可以是：

1. 识别“高铁站”有歧义，候选包括深圳北站、福田站、深圳坪山站等；如果业务允许，可以先默认最常用的深圳北站，同时在答案里说明假设。
2. 调用地理编码工具，把“深圳南山区”和“深圳北站”转换成坐标或站点 ID。
3. 调用路线规划工具，查询地铁、驾车、打车等方案，拿到耗时、换乘、费用和拥堵等级。
4. 调用实时人流或热力工具，查询出发地、换乘站、目的站的人流拥挤度。
5. 对工具结果做一致性检查，例如时间戳是否新、路线是否跨城市、是否缺少实时数据。
6. 生成答案时带上查询时间、默认目的站、推荐路线、拥堵风险和备选方案。
7. 把用户偏好写入记忆，例如“用户常从南山区出发，默认高铁站是深圳北站”，但要避免把一次性临时路线长期保存。

易错点：

1. ReAct 的 “Thought” 不一定要暴露给用户，生产系统通常只保存内部 trace，对用户展示摘要和证据。
2. 不要让模型自己编造实时路线和人流量，必须接地图、交通、热力或业务数据工具。
3. 不要把框架当成架构。框架只能简化调用，真正的可靠性来自状态机、权限、重试、审计和评测。
4. 对实时工具结果要带时间戳和数据来源，否则答案很快过期。

## 4. 什么时候用 subagent

Subagent 适合“可并行、边界清楚、输出可校验”的子任务，不适合把主线阻塞问题随手丢出去。

适合使用：

1. **并行检索**：一个 agent 查代码调用链，另一个查文档或历史 issue。
2. **角色分工**：Planner 产出计划，Worker 执行，Reviewer 检查风险。
3. **独立模块修改**：多个模块写集不重叠，例如前端表单和后端接口文档。
4. **验证 sidecar**：主 agent 实现时，子 agent 并行跑测试、查兼容风险。
5. **长文档处理**：不同 agent 分别总结不同资料，再由主 agent 汇总。

不适合使用：

1. 子任务高度耦合，需要频繁共享最新状态。
2. 写同一批文件，容易互相覆盖。
3. 子任务输出没有明确验收标准。
4. 只是为了“看起来更智能”而拆分，通信成本超过收益。

使用 subagent 时要定义任务契约：

```text
目标: 查清 Redis Lua 在 Cluster 下的限制
输入: 指定文档和问题
输出: 结论、引用、风险点
禁止: 修改文件
验收: 能回答是否支持跨 slot 原子操作
```

## 5. 约束 AI 的手段

约束 AI 不能只靠 prompt。真实项目通常多层防护：

1. **System/Developer Rules**：全局安全和风格约束，例如不能泄漏密钥、生产操作要审批。
2. **项目规则文件**：仓库内约定编码风格、测试命令、目录边界、提交规范。
3. **工具权限**：只给必要工具，高风险工具默认不可用或需要审批。
4. **结构化输出**：用 JSON Schema、函数参数、枚举值限制模型输出形态。
5. **状态机/Workflow**：高风险流程固定节点和条件边，不让模型自由跳转。
6. **检索增强**：让模型先读真实代码、文档、规则，再行动。
7. **验证门禁**：编译、测试、lint、静态扫描、权限检查、引用校验。
8. **沙箱隔离**：文件、网络、凭证、进程和资源隔离。
9. **人工审批**：删除、退款、发券、生产变更、批量消息等动作前确认。
10. **观测和回放**：记录 prompt、工具调用、trace、输出和人工反馈，形成回归集。

让 AI 遵守复杂项目规则的关键是把规则转成可执行边界：目录权限、工具白名单、schema、测试命令、CI gate 和 review checklist，而不是只写一段“请遵守规范”。

## 6. 上下文工程是什么

上下文工程是围绕“模型当前能看到什么、以什么结构看到、什么时候更新、如何验证”的工程体系。它比提示词工程更宽，包含输入组织、检索、记忆、工具结果裁剪和状态管理。

核心对象：

1. **Rules**：长期约束，告诉模型不能做什么、必须做什么。
2. **Skills**：按任务触发的流程包，告诉模型如何做某类任务。
3. **MCP/Tools**：连接外部真实系统，让模型能查事实、执行动作。
4. **Memory**：长期偏好、项目事实、历史经验。
5. **RAG Context**：按需检索的文档、代码、日志、工单。
6. **Task State**：当前目标、计划、已完成步骤、外部 job id、失败原因。
7. **Artifacts**：文件、报告、截图、测试结果，用引用传递而不是全文塞入。

好的上下文工程会控制三件事：

1. **相关性**：只放当前任务需要的信息。
2. **优先级**：系统规则 > 项目规则 > skill > 用户偏好 > 检索资料。
3. **可验证**：每个关键结论最好能追溯到文件、工具结果或测试。

## 7. Skill 能保证百分之百触发吗

不能。Skill 触发通常依赖意图识别、关键词、上下文分类、文件类型、工具需求和模型判断，不可能在开放自然语言输入下保证 100% 正确。

可能不触发的原因：

1. 用户表达太隐晦，没有命中触发语义。
2. skill 描述过窄或过宽，分类器选择失败。
3. 当前上下文太长，关键信号被压缩或截断。
4. 多个 skill 相似，路由选择了另一个。
5. 工具或权限不可用，系统没有加载对应 skill。

提升触发准确率的方法：

1. **清晰 description**：写明适用场景和不适用场景。
2. **正负例评测**：准备必须触发和不该触发的样本。
3. **元数据检索**：常驻短 metadata，正文按需加载。
4. **显式用户触发**：允许用户说“使用某某 skill”。
5. **路由日志**：记录候选 skill、得分和选择原因。
6. **回归集优化**：把漏触发和误触发案例加入评测。

面试回答要强调：Skill 不是强安全边界，也不是强制执行引擎。它更像“可复用作业手册”。真正的强约束要靠 Rules、权限、工具白名单、状态机、schema 和验证门禁。

## 8. 面试回答模板

Agent 现在更适合做知识工作和工程流程增强，比如检索总结、代码辅助、测试生成、客服分流和运维排障。它能替代一部分重复的信息收集和低风险流程执行，但不能替代核心业务责任和高风险决策。Agent 常见模式有 RAG、ReAct、Plan-and-Execute、Workflow/Graph 和 Multi-Agent。ReAct 是推理、行动、观察的循环，适合开放式排障，但必须加最大步数、工具权限和验证。

Subagent 适合边界清晰、可并行、输出可校验的任务，比如并行检索、独立模块实现、Reviewer 检查；如果任务高度耦合或写同一批文件，拆 subagent 反而增加通信和冲突成本。约束 AI 要多层做：Rules 定底线，Skills 给流程，MCP/Tools 接真实系统，Workflow 限制高风险路径，schema 约束输出，测试和审计做验证。上下文工程就是管理模型看到什么、何时看到、如何按优先级组织，并用检索、记忆、状态和工具结果保持任务连续。Skill 不能保证百分百触发，只能通过清晰描述、显式触发、正负例评测和路由日志提高准确率；强约束不能依赖 skill，要靠权限和系统边界。
