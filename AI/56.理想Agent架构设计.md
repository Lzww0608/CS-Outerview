# 56. 理想 Agent 架构设计

面试里被问到 "讲一下你理想中的 Agent 架构是怎么设计的"，本质上是考察对 Agent 系统的工程理解，而不是堆砌概念。理想的 Agent 架构不是单一 LLM + Tool 循环，而是一个可控、可观测、可演进的多层系统，能在 ReAct、Plan-Execute、Multi-Agent、Workflow 之间灵活切换，并把幻觉、死循环、上下文污染、权限失控等风险收敛到工程可控范围。

## 1. 问题背景

近年来 Agent 从最初的 ReAct 循环，发展到 Plan-Execute、LangGraph、Multi-Agent、Claude Code、Hermes、OpenCode 等多种形态。但生产环境中暴露的问题也越来越集中：

1. 上下文越来越长，成本和延迟同步上升，关键信息被淹没。
2. 工具调用失控，权限边界模糊，高危操作缺审计。
3. 多 Agent 协作通信成本高，状态难统一。
4. Agent 行为难评测，回归质量靠人工抽检。
5. 模型升级、Prompt 升级会引发系统性回退，缺少 A/B 与回滚机制。

理想的 Agent 架构需要在 "灵活" 和 "可控" 之间取得平衡：既要允许模型探索，也要让工程团队可以观察、约束、复现、回放、评测每一步。

### 假设条件

1. 讨论对象为通用企业级 Agent 系统，目标场景包含研发辅助、运维排障、客服、数据分析等。
2. 底层 LLM 通过 API 或自部署推理服务提供，支持 function calling/tool use。
3. 已具备基础设施：消息队列、对象存储、可观测性 (trace/metric/log)、权限中心、向量库。
4. 不限定具体框架，可在 LangGraph、Eino、Semantic Kernel、自研之间选型。
5. "理想" 指可演进的目标架构，不要求一次落地，强调分层、解耦、可替换。

## 2. 问题现象

当 Agent 架构设计不合理时，常见现象：

| 现象 | 触发原因 | 表现 |
| --- | --- | --- |
| 上下文爆炸 | 未做压缩与裁剪 | Token 成本高、延迟大、关键信息丢失 |
| 工具滥用 | 缺少路由与权限 | 同一工具反复调用，高危操作直接执行 |
| 死循环 | 缺少 Guardrail | max_steps 未设、相同动作反复执行 |
| 多 Agent 混乱 | 缺少 Supervisor | 子 Agent 互相覆盖结果，状态不一致 |
| 不可复现 | Trace 缺失 | 同一问题结果差异大，无法回放 |
| 升级回退 | 缺少评测 | Prompt/模型更新后线上质量下降 |
| 越权 | 权限粒度粗 | Agent 用管理员 token 执行普通查询 |

## 3. 影响范围

| 维度 | 程度 | 说明 |
| --- | --- | --- |
| 用户体验 | 高 | 响应慢、答非所问、任务失败 |
| 系统成本 | 高 | Token、推理算力、外部 API 成本飙升 |
| 安全合规 | 高 | 数据外泄、越权操作、审计缺失 |
| 工程效率 | 中 | 调试困难、迭代慢、回归无保障 |
| 业务可信度 | 高 | 关键决策幻觉、错误执行难追责 |

## 4. 原因分析

理想 Agent 架构难以一次成型，根因可归纳为四类：

1. **职责未分层**：Planner、Executor、Memory、Tool 揉在一起，难以独立演进与替换。
2. **缺乏中间表示**：模型直接输出自然语言驱动工具，无结构化 action schema，难审计、难重放。
3. **观测与评测缺失**：没有 trace store 与离线评测集，质量靠人工感觉。
4. **权限与安全后置**：把权限当作业务层逻辑，没有在 Tool 调用层统一拦截，导致越权与高危操作难收敛。

## 5. 解决方案

理想 Agent 架构按 "六层 + 三横切" 设计：

### 5.1 六层主链路

```
+--------------------------------------------------------------+
| L6  Application / Channel  (Web, IDE 插件, IM, CLI, API)      |
+--------------------------------------------------------------+
| L5  Agent Orchestrator     (Workflow Graph + Mode Router)     |
+--------------------------------------------------------------+
| L4  Planner / Reasoner     (单 Agent ReAct, Plan-Execute,     |
|                              Multi-Agent Supervisor)          |
+--------------------------------------------------------------+
| L3  Tool & Skill Layer     (Tool Router, Skill, MCP, Sandbox) |
+--------------------------------------------------------------+
| L2  Memory & Context Engine(Working/Short/Long Memory, RAG,   |
|                              上下文压缩与裁剪)                  |
+--------------------------------------------------------------+
| L1  Model Gateway          (多模型路由, 限流, 重试, 缓存)        |
+--------------------------------------------------------------+
```

三横切：可观测性 (Trace/Metric/Log)、安全与权限 (AuthZ/Policy/Audit)、评测与发布 (Eval/AB/Rollback)。

### 5.2 各层职责

1. **L1 Model Gateway**：统一封装多家模型 (Claude、GPT、DeepSeek、Qwen、自研)，做路由、限流、降级、prompt 缓存、KV cache 复用、按任务分层选择模型 (小模型做路由、大模型做规划)。
2. **L2 Memory & Context Engine**：维护 Working Memory (本轮 scratchpad)、Short Memory (近 N 轮对话)、Long Memory (向量库 + 结构化 profile)，统一做上下文压缩、摘要、裁剪与 Token 预算控制。
3. **L3 Tool & Skill Layer**：所有外部能力以 Tool/Skill/MCP 形式注册，统一 schema、权限标签、超时、重试、沙箱执行；高危 Tool 走审批通道。
4. **L4 Planner / Reasoner**：根据任务复杂度路由到不同模式：简单问答走 RAG，单步任务走 ReAct，多步任务走 Plan-Execute，复杂协作走 Multi-Agent Supervisor/Worker。
5. **L5 Agent Orchestrator**：用 Workflow Graph (类 LangGraph) 描述节点和条件边，把模型 + 工具 + 人工审批 + 重试 + 回滚组合成可视化、可回放的有向图。
6. **L6 Application / Channel**：屏蔽渠道差异，做会话管理、流式输出、用户中断、多模态输入输出适配。

### 5.3 关键机制

1. **结构化 Action Schema**：模型输出统一为 JSON `{tool, args, reason, confidence}`，由 Tool Router 校验后再执行，禁止直接执行自然语言指令。
2. **上下文工程**：每轮请求前做预算分配 (System / Skill / Memory / RAG / History / Scratchpad)，超额自动摘要或裁剪，关键事实做 pin。
3. **Guardrail**：max_steps、max_tool_calls、max_runtime、相同 (tool, args, error) 不重复、危险动作审批、PII 与敏感词过滤。
4. **Trace Store**：每个 run 记录 `run_id/step_id/thought/action/observation/tokens/cost`，可回放、可 diff、可作为评测样本。
5. **评测闭环**：离线评测集 + 在线 A/B + 线上抽检 + 自动回归，Prompt 与模型变更必须先过评测门禁。

## 6. 可选方案对比

| 方案 | 优点 | 缺点 | 适用场景 |
| --- | --- | --- | --- |
| 单 Agent ReAct | 实现简单, 灵活 | 容易死循环, 长链路状态丢失 | 信息检索, 简单工具调用 |
| Plan-Execute | 链路清晰, 易复盘 | 计划过期需重规划, 首 Token 慢 | 多步研发、数据分析 |
| Multi-Agent (Supervisor/Worker) | 可并行, 角色清晰 | 通信成本高, 状态易冲突 | 大型分析、多领域协作 |
| Workflow/Graph (LangGraph) | 可视化, 可控, 可回放 | 灵活性弱, 设计成本高 | 客服、审批、代码修复 |
| Single-Agent + 子任务隔离 (Claude Code 风格) | 上下文干净, 行为收敛 | 子任务结果合并需设计 | 编程 Agent、运维 Agent |
| Hermes/OpenCode 风格 (任务图 + 工具沙箱) | 强可观测, 强安全 | 平台投入大 | 企业级生产 Agent 平台 |

## 7. 推荐方案

推荐 **以 Workflow Graph 为骨架, 内嵌单 Agent ReAct, 在必要节点引入 Multi-Agent 协作** 的混合架构：

1. 默认模式：Workflow Graph 描述主流程，模型只在节点内决策，状态由 Graph 管理，可回放。
2. 节点内部：简单节点用单步模型调用，复杂节点用 ReAct 子循环，子循环受 Guardrail 约束。
3. 复杂任务：在 "调研 / 评估 / 多方案对比" 等并行场景引入 Supervisor + Worker，结果由 Supervisor 汇总。
4. 全局横切：Model Gateway 统一接入、Trace Store 全量记录、Policy 引擎统一鉴权、Eval 平台守门。

理由：

1. 工程可控性最高，状态、Trace、回放、审批天然成立。
2. 灵活性足够，节点内仍可用 ReAct 探索。
3. 模型可替换，Tool 可热插拔，符合 "可演进" 目标。

## 8. 实施步骤

### Phase 1：最小可用骨架 (2-3 周)

1. 搭建 Model Gateway：封装 1-2 个模型，实现路由与重试。
2. 实现 ReAct 循环：Thought -> Action -> Observation，加 max_steps 与 Trace 记录。
3. 注册 3-5 个核心 Tool (搜索、代码查询、SQL 执行)，统一 schema。
4. 实现 Working Memory：本轮 scratchpad 管理。

### Phase 2：Workflow Graph 与 Guardrail (2-4 周)

1. 引入 Workflow Graph (LangGraph 或自研)，描述主流程节点和条件边。
2. 实现 Guardrail：max_tool_calls、重复动作检测、高危 Tool 审批。
3. 实现 Short Memory：近 N 轮对话摘要。
4. 建立基础 Eval 集：50-100 条典型 case，自动评分。

### Phase 3：多模式与 Multi-Agent (3-4 周)

1. 实现 Plan-Execute 模式：复杂任务先规划再执行，支持重规划。
2. 实现 Multi-Agent Supervisor/Worker：并行调研、多方案对比。
3. Tool 沙箱：高危 Tool 在容器中执行，结果审核后放行。

### Phase 4：安全与评测闭环 (2-3 周)

1. Policy 引擎：按 Tool/用户/场景 粒度鉴权，审计日志全量记录。
2. Long Memory：向量库 + 用户 Profile 持久化。
3. 评测平台：离线评测门禁 + 在线 A/B + 自动回归。
4. Prompt 版本管理与灰度发布。

### 代码实现指引

可能需要修改的模块：

1. `agent/core/orchestrator.py`：主编排逻辑，Workflow Graph 定义与执行。
2. `agent/core/planner.py`：Plan-Execute 与 ReAct 模式切换。
3. `agent/memory/context_engine.py`：上下文压缩、摘要、Token 预算。
4. `agent/tools/router.py`：Tool 路由、权限校验、沙箱调度。
5. `agent/gateway/model_gateway.py`：模型路由、限流、缓存。
6. `agent/observability/trace_store.py`：Trace 全量记录与回放。
7. `agent/guardrail/policy_engine.py`：权限策略与审计。
8. `agent/eval/eval_runner.py`：评测集执行与门禁。

可能涉及的文件：

1. `agent/config/workflow_graphs/`：Workflow YAML/JSON 定义文件。
2. `agent/tools/definitions/`：Tool schema 注册文件。
3. `agent/config/policies.yaml`：权限策略配置。
4. `agent/eval/cases/`：评测用例 JSON 文件。

核心修改逻辑：

1. Orchestrator 增加 mode 路由：根据任务标签或 Planner 输出选择 ReAct / Plan-Execute / Multi-Agent。
2. Context Engine 增加 Token 预算分配：请求前按 System/Skill/Memory/History 分配，超额触发摘要。
3. Tool Router 增加权限拦截：所有 Tool 调用前走 Policy Engine 校验，高危 Tool 强制审批。
4. Trace Store 改为结构化持久化：每步记录 thought/action/observation/tokens/cost，支持 run 回放与 diff。

测试重点：

1. ReAct 死循环防护：构造会循环的场景，验证 max_steps 和重复动作检测。
2. Tool 权限拦截：构造越权调用，验证 Policy Engine 拦截。
3. 上下文裁剪：构造超长历史，验证 Token 预算控制与关键信息保留。
4. Multi-Agent 状态一致性：构造子 Agent 并发写同一资源，验证 Supervisor 仲裁。
5. 评测门禁：构造质量回退的 Prompt 变更，验证门禁拦截。
6. Trace 回放：构造已知 run，验证回放结果一致。

## 9. 风险与注意事项

| 风险 | 等级 | 缓解措施 |
| --- | --- | --- |
| 模型输出格式不稳定 | 高 | 强 schema 校验 + fallback 规则解析 |
| 上下文压缩丢失关键信息 | 高 | 关键事实 pin + 压缩后人工抽检 |
| Multi-Agent 状态冲突 | 中 | Supervisor 仲裁 + 乐观锁 |
| Tool 超时或异常 | 中 | 统一超时、重试、降级策略 |
| 评测集维护成本 | 中 | 自动挖掘线上 case + 人工审核 |
| 架构过度设计 | 中 | 按阶段落地，Phase 1 只做骨架 |
| 权限策略膨胀 | 低 | 策略分层 (全局/角色/场景)，定期审计 |

## 10. 验证方式

1. **功能验证**：50 条典型任务通过率 > 90%，含信息检索、多步推理、工具调用、Multi-Agent 协作。
2. **安全验证**：构造 20 条越权/注入/敏感词 case，拦截率 100%。
3. **稳定性验证**：100 次相同输入，输出一致性 > 85% (temperature=0)。
4. **成本验证**：平均 Token 消耗相比纯 ReAct 降低 > 30% (上下文压缩 + Token 预算)。
5. **回放验证**：随机抽取 10 个历史 run，回放结果与原始记录一致。
6. **评测门禁验证**：提交质量回退的 Prompt，门禁拦截率 100%。

## 11. 总结

理想的 Agent 架构不是"最强的模型 + 最多的工具"，而是一个 **六层 + 三横切** 的工程系统：

1. **六层**：Model Gateway -> Memory & Context Engine -> Tool & Skill Layer -> Planner / Reasoner -> Agent Orchestrator -> Application / Channel，每层可独立替换和演进。
2. **三横切**：可观测性 (Trace Store)、安全与权限 (Policy Engine)、评测与发布 (Eval Platform)，贯穿所有层。
3. **核心原则**：结构化 Action、上下文工程、Guardrail、Trace 全量、评测闭环。
4. **落地策略**：先骨架后细节，Phase 1 ReAct 可用，Phase 2 Graph 可控，Phase 3 Multi-Agent 可扩展，Phase 4 安全与评测闭环。

面试回答一句话总结：**理想 Agent 架构 = 分层解耦 + 结构化 Action + 上下文工程 + Guardrail + Trace + 评测闭环**，核心是把 LLM 的不确定性收敛到工程可控范围内。
