# 18. AI 辅助开发收益风险与工程落地

面试里问“项目中有没有用 AI 进行开发，怎么用，依赖 AI 有什么好处和坏处”，重点不是说“会用大模型”，而是说明你能把 AI 当成工程辅助工具，并且知道验证、边界和风险控制。

## 1. AI 可以怎么辅助开发

常见用法：

1. **需求澄清和方案拆解**：把模糊需求拆成模块、接口、状态流和边界条件。
2. **代码生成和样板代码**：生成 DTO、API handler、测试桩、SQL、脚本和配置模板。
3. **代码解释和迁移**：理解陌生代码、跨语言改写、升级 SDK 或框架版本。
4. **测试用例补充**：覆盖空输入、边界值、异常路径、并发和回归用例。
5. **日志和报错分析**：根据堆栈、trace、慢 SQL、CI 日志定位可能原因。
6. **文档生成**：生成接口文档、README、变更说明和排障手册。
7. **Code Review 辅助**：检查空指针、并发安全、资源释放、SQL 注入、日志泄漏等风险。

适合交给 AI 的是“有上下文、有验证标准、可回滚”的任务；不适合让 AI 独立决定生产高风险操作。

## 2. 好处

1. **降低启动成本**：面对新框架、新语言、新代码库时，能更快理解结构和常见写法。
2. **提升重复劳动效率**：样板代码、测试数据、文档和脚本生成更快。
3. **扩大检查视角**：AI 可以提醒遗漏的边界条件、异常路径和可观测性。
4. **辅助学习迁移**：从 Java 转 Go、从同步代码转异步代码时，可以快速对比概念。
5. **加快排障初筛**：对日志、错误码和堆栈做初步归类，减少人工翻大量文本的时间。

## 3. 风险

1. **幻觉和过时信息**：AI 可能编造 API、参数、配置或框架行为。
2. **上下文不完整**：不知道项目里的隐含约束、历史兼容、线上数据和安全边界。
3. **代码看似正确但不可维护**：生成代码可能风格不一致、抽象过度或缺少测试。
4. **安全和隐私风险**：不能把密钥、用户隐私、生产数据、未公开代码随意发给外部模型。
5. **依赖导致能力退化**：如果只复制结果，不理解原理，面试和线上排障都会暴露问题。
6. **生产副作用不可控**：让 AI 直接执行删除、发消息、扣费、改配置等操作风险很高。

## 3.1 Claude Code 产生幻觉的原因和解决方法

Claude Code、Cursor、Copilot 这类 AI 编程工具的幻觉，本质上来自“语言模型按概率生成答案”与“工程事实必须可验证”之间的差异。常见原因：

1. **上下文缺失**：模型没有读到真实文件、接口定义、构建脚本或业务约束，只能根据相似经验补全。
2. **检索不充分**：只看了局部代码，没找到调用方、测试、配置和历史兼容逻辑。
3. **知识过期**：框架 API、依赖版本、编译选项和运行环境已经变化。
4. **工具反馈被误读**：命令失败、测试没跑全、日志截断时，模型仍然可能继续给出确定结论。
5. **目标不够具体**：用户只说“优化一下”“修一下”，模型会自行假设验收标准。
6. **长上下文干扰**：早期约束被压缩或遗忘，不相关文件和历史对话污染当前判断。

治理方式：

1. **先读事实再生成**：要求工具先查真实代码、README、测试和依赖版本，再提出修改。
2. **小步改动**：一次只改一个清晰问题，避免让模型生成大段难以审查的核心逻辑。
3. **外部验证**：用编译、单测、集成测试、lint、类型检查、静态分析和运行日志验证，而不是相信模型口头解释。
4. **约束输出格式**：让模型列出修改文件、依据、风险、验证命令和未验证项。
5. **保留人工 Review**：尤其是并发、内存管理、权限、安全、账务、数据迁移等高风险代码。
6. **用最小权限运行**：默认只读；写文件、删文件、联网、生产操作需要审批和审计。
7. **沉淀失败样本**：把 AI 误判案例加入 checklist、测试或 skill，避免下次重复。

真实开发里可以把 AI 输出分成三类处理：

| 输出类型 | 处理方式 |
| --- | --- |
| 解释已有代码 | 对照真实文件和调用链确认 |
| 生成样板代码 | 人工审查后跑格式化、编译和单测 |
| 修改核心逻辑 | 要求最小 diff、补回归测试、做代码 Review |

面试回答可以强调：AI 幻觉不可完全消除，只能通过“上下文检索 + 工具验证 + 权限控制 + 人工审查”把风险降到工程可接受范围。

## 3.2 Spec 怎么写

让 AI 写代码前，Spec 不是一句“实现某功能”，而是把任务边界、验收标准和禁止事项写清楚。一个可执行的 Spec 至少包含：

1. **目标和背景**：要解决什么问题，影响哪些用户、接口、任务或数据。
2. **输入输出**：接口参数、返回结构、错误码、状态流转和数据格式。
3. **范围和非目标**：本次允许改哪些模块，不改哪些历史逻辑，哪些优化暂不做。
4. **约束条件**：性能、并发、幂等、兼容性、安全、权限、日志、配置和超时要求。
5. **边界场景**：空值、重复请求、异常下游、超时重试、老版本客户端、脏数据和并发冲突。
6. **验收标准**：哪些测试必须通过，哪些指标不能恶化，哪些行为要和旧版本一致。
7. **验证命令**：明确需要跑的单测、集成测试、lint、构建、压测或回归脚本。
8. **回滚方案**：是否有开关、灰度策略、数据兼容和失败后的恢复步骤。

示例：

```text
任务：给订单查询接口增加按订单状态过滤。

范围：
- 只修改 order-service 的查询条件构造、接口文档和相关测试。
- 不改变响应字段，不修改订单状态枚举含义。

约束：
- 老客户端不传 status 时行为保持不变。
- status 非法返回 ErrInvalidStatus。
- 查询必须继续走 idx_user_status_time 索引。

验收：
- 新增单测覆盖空 status、合法 status、非法 status。
- 跑 go test ./internal/order/...
- 用 EXPLAIN 确认核心 SQL 使用预期索引。
```

Spec 写得越像工程验收单，AI 越不容易自行脑补；后续人工 Review 也能对照 Spec 判断“是否做多了、做偏了、漏验证了”。

## 3.3 AI 写好的东西怎么验证

AI 生成代码后要按风险分层验证，不能只看它解释得是否合理。

验证顺序：

1. **读 diff**：确认改动范围是否符合 Spec，是否有顺手重构、格式化大面积文件或引入无关依赖。
2. **编译和静态检查**：先跑构建、类型检查、lint、格式化检查，排除低级错误。
3. **单元测试**：覆盖核心函数、边界条件、错误码、权限判断和状态机。
4. **集成测试**：涉及 DB、Redis、MQ、RPC、文件系统时，用测试环境或容器验证真实依赖行为。
5. **回归测试**：对旧行为做 golden case 或快照对比，确保兼容性没有被破坏。
6. **安全检查**：关注 SQL 注入、越权访问、敏感日志、密钥泄漏、路径遍历和不安全反序列化。
7. **并发和幂等验证**：对库存、订单、余额、任务状态这类逻辑，用并发用例和重复请求验证。
8. **灰度和监控**：上线后看错误率、P95/P99、慢 SQL、资源占用和业务成功率，异常能快速回滚。

对于高风险改动，可以增加“双跑对比”：旧逻辑和新逻辑同时计算，只让旧逻辑生效，把新旧结果写日志或指标做差异分析。等差异收敛后再切流量。这样 AI 只参与生成候选实现，最终正确性由测试、观测和灰度闭环保证。

## 4. 工程落地原则

1. **AI 生成，人工负责**：提交前必须自己理解代码和取舍。
2. **小步使用**：让 AI 处理明确、边界小的任务，不一次生成大段核心逻辑。
3. **用工具验证**：编译、单测、集成测试、lint、性能测试和灰度结果比模型解释更可信。
4. **最小权限**：AI 工具默认只读；写文件、改配置、生产操作需要审批和审计。
5. **上下文脱敏**：日志、数据库样本、密钥、用户信息要脱敏或只给结构。
6. **保留轨迹**：记录 AI 生成内容、人工修改点、测试结果和上线验证，便于追责和复盘。

## 5. 真实场景

一个后端项目中可以这样用 AI：

```text
需求文档
  -> AI 帮助拆接口和测试点
  -> 人工确认数据模型和一致性要求
  -> AI 生成部分样板代码和单测
  -> 本地测试 / Review / 压测
  -> 灰度上线
  -> AI 辅助分析日志和告警
```

如果是 RAG 或 Agent 项目，还可以用 AI 生成离线评测问题、归类失败样本、总结用户反馈，但评测指标和判定标准要由工程系统固化。

## 5.1 开发阶段怎么用 AI

不同阶段使用 AI 的重点不一样：

1. **需求阶段**：更适合让 AI 帮助拆用户故事、接口清单、异常路径、验收标准和测试点，但最终业务边界要由产品、研发和测试确认。
2. **设计阶段**：可以让 AI 对比方案、列风险、补充一致性、幂等、权限、监控和扩展性问题，但不能直接替代架构评审。
3. **开发阶段**：适合生成样板代码、DTO、单测、脚本、SQL、迁移模板和局部函数；核心状态机、权限、账务、并发控制要人工主导。
4. **测试阶段**：适合补边界用例、构造异常数据、分析失败日志、生成回归 checklist。
5. **上线和排障阶段**：适合快速归纳日志、告警和变更记录，辅助定位方向，但线上操作需要最小权限和人工确认。

面试里可以说：需求和测试阶段 AI 的性价比很高，因为它擅长枚举遗漏；开发阶段要把任务拆小并用编译、单测和 Review 兜底。

## 5.2 AI 始终达不到要求怎么办

如果一个模块让 AI 反复生成仍达不到要求，不应该无限改提示词。可以按下面顺序处理：

1. **确认输入是否充分**：补充真实接口、数据结构、调用链、约束、失败样例和验收标准。
2. **缩小任务边界**：把“写完整模块”拆成“生成接口定义”“补一个函数”“写测试用例”等可验证小任务。
3. **提供反例和测试**：让 AI 根据失败用例修正，而不是只说“再好一点”。
4. **切换角色**：让 AI 从生成者变成 reviewer、解释器或测试生成器。
5. **人工接管核心逻辑**：当问题涉及复杂业务规则、并发一致性、安全权限、线上数据迁移或模型连续两三轮都不满足测试时，应该自己写核心代码。
6. **沉淀约束**：把这次失败的规则写进文档、模板、测试或 skill，降低下次重复失败概率。

判断标准：

| 情况 | 更适合继续调提示词 | 更适合自己写 |
| --- | --- | --- |
| 上下文不够、需求可补充 | 是 | 否 |
| 样板代码、测试、文档 | 是 | 否 |
| 核心交易、权限、安全、并发 | 否 | 是 |
| 生成结果能被单测快速验证 | 是 | 视复杂度 |
| 多轮仍编译不过或误解业务 | 否 | 是 |

好的回答不是“AI 不行就不用”，而是把 AI 放到合适位置：让它加速检索、枚举和样板生成，核心判断、最终代码和质量责任仍由工程师承担。

## 6. 面试回答模板

我在项目里会把 AI 当成辅助研发工具，而不是替代工程判断。它适合做需求拆解、样板代码、测试用例、日志分析、文档和代码解释，能降低重复劳动和学习新技术栈的成本。但我不会直接信任生成结果，因为它可能幻觉、忽略项目约束或带来安全风险。我的做法是把任务拆小，给 AI 明确上下文和验收标准，生成后自己 review，并用编译、测试、lint、压测和灰度验证。涉及密钥、用户数据和生产写操作时要脱敏、最小权限和人工审批。
