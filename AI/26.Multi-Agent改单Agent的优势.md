# 26. Multi-Agent 改单 Agent 之后有什么优势

## 1. 问题背景

在 Agent 系统早期设计里，很多团队会倾向于 Multi-Agent 架构：Planner 负责任务拆解，Researcher 负责检索，Coder 负责写代码，Reviewer 负责检查，Executor 负责执行工具。这个设计直观上符合人类团队分工，也便于给不同 Agent 配置不同 prompt、工具和上下文。

但真实工程落地后，Multi-Agent 往往会暴露出额外复杂度：

1. Agent 之间需要频繁通信和转交上下文。
2. 每个 Agent 都有自己的 prompt、memory、toolset 和状态。
3. 子 Agent 输出不稳定，上游 Agent 还要做校验和合并。
4. 问题定位困难，不清楚错误来自任务拆解、工具调用、上下文传递还是结果合并。
5. Token、延迟、并发资源和评测成本显著上升。

因此很多场景会从 Multi-Agent 改成单 Agent，或者改成“单主控 Agent + 工具/工作流/可选子任务”的混合架构。

**假设条件**：

1. 这里讨论的“Multi-Agent”是指多个 LLM Agent 之间通过消息协作，而不是普通服务模块拆分。
2. “单 Agent”不是一个大 prompt 包打天下，而是一个主 Agent 统一维护状态，并通过工具、函数、工作流节点、规则和记忆完成任务。
3. 任务以工程开发、RAG 问答、客服处理、数据分析、运维排障这类可工具化任务为主。
4. 如果任务天然可以强并行、互不依赖、需要不同权限域，Multi-Agent 仍然可能更合适。

核心结论可以先给出来：

```text
Multi-Agent 改单 Agent 的收益，不是“Agent 数量少了”这么简单，
而是把跨 Agent 的自然语言通信，改成一个主状态机内的结构化状态、工具调用和验证闭环。
```

换句话说，真正要减少的是：

1. 多个 Agent 之间的自然语言交接。
2. 多份上下文和记忆的分裂。
3. 多套 prompt 和权限策略的维护成本。
4. 多个 LLM 节点带来的非确定性。
5. 多个中间结果合并时的责任不清。

单 Agent 更适合做成：

```text
单主控 Agent
+ 显式任务状态
+ 工具 schema
+ 权限控制
+ Harness 评测
+ 可选的只读/并行子任务
```

## 2. 问题现象

Multi-Agent 改单 Agent 通常是因为出现了以下现象：

1. **延迟过高**：一次用户请求需要多个 Agent 轮流思考、沟通和确认，响应时间不可控。
2. **成本过高**：每个 Agent 都要重复携带系统提示词、任务背景、工具说明和中间结果。
3. **结果不一致**：Planner 的目标、Worker 的理解、Reviewer 的标准不一致，最后输出互相打架。
4. **上下文丢失**：任务经过多次转交后，用户真实意图、约束条件或关键事实被遗漏。
5. **调试困难**：失败时 trace 很长，难以判断是哪个 Agent 的决策导致问题。
6. **权限难管**：不同 Agent 工具权限不同，配置复杂，容易出现越权或漏权。
7. **评测困难**：每个 Agent 的中间输出都可能变化，回归测试不稳定。
8. **并发冲突**：多个 Agent 同时修改同一份状态、文件、数据库记录或计划，容易产生覆盖和竞态。

一个典型例子：

```text
用户：帮我修复登录接口的单测失败。

Multi-Agent 链路：
Planner 拆任务 -> Researcher 查日志 -> Coder 修改代码 -> Reviewer 审查 -> Executor 跑测试

问题：
1. Researcher 摘要遗漏了真正失败原因；
2. Coder 基于错误摘要修改了无关文件；
3. Reviewer 只检查代码风格，没有重新跑失败用例；
4. Executor 跑了全量测试超时；
5. 用户看到的是“任务失败”，但排查 trace 很长。
```

如果改成单 Agent：

```text
一个主 Agent 直接维护同一份任务状态：
读日志 -> 查代码 -> 修改 -> 跑目标测试 -> 根据失败继续修 -> 输出 diff 和验证结果
```

链路更短，状态更集中，责任边界更清楚。

从线上指标上，通常会看到：

1. **P95/P99 延迟下降**：少了多轮 Agent 互相调用和总结。
2. **平均 token 成本下降**：系统 prompt、工具说明、任务背景不需要在多个 Agent 中重复携带。
3. **失败可复现性提升**：同一个 `run_id` 下只有一个状态机，回放更简单。
4. **工具误用减少**：所有工具选择集中经过同一套 router、schema 和权限策略。
5. **用户打断更容易处理**：只有一个主任务状态，不需要协调多个子 Agent 的中止。
6. **人工接管更清楚**：人只需要看主状态、当前计划、最近工具结果和风险，不需要读完整 Agent 群聊记录。

一个经验判断是：如果多个 Agent 之间 80% 的消息都在重复解释上下文、同步进度、请求确认或合并摘要，而不是产生新的独立成果，就说明这个 Multi-Agent 设计很可能应该收敛成单 Agent。

## 3. 影响范围

Multi-Agent 改单 Agent 会影响以下模块：

1. **Agent Orchestrator**：从多 Agent 调度器变成单 Agent 状态机或单 Agent Runner。
2. **Prompt 模板**：多个角色 prompt 合并为一个主 prompt，角色分工改成内部策略或工具说明。
3. **Tool Router**：由“不同 Agent 持有不同工具”改成“单 Agent 通过权限策略选择工具”。
4. **Memory 管理**：由多份记忆合并为统一任务记忆、用户记忆和项目记忆。
5. **Trace 与日志**：由多 Agent 会话 trace 合并为单 run 下的 step trace。
6. **权限系统**：由多角色权限矩阵简化为单 Agent 的工具 allowlist、denylist、审批策略。
7. **评测系统**：从多 Agent 中间过程评测，转为对单 Agent 的任务成功率、工具选择、成本、延迟和安全行为评测。
8. **产品体验**：用户看到的中间状态更少，系统解释要从“多个角色讨论”变成“任务步骤进展”。

如果涉及代码实现，可能需要修改的模块包括：

1. `AgentRunner` / `AgentExecutor`：统一任务循环。
2. `Planner`：从外部 Planner Agent 改为主 Agent 内部计划或确定性 planning 函数。
3. `ToolRouter`：集中处理工具选择、参数校验和权限。
4. `MemoryManager`：统一管理上下文压缩、历史摘要和长期记忆。
5. `TraceStore`：统一记录 `run_id -> step_id -> action/observation`。
6. `PermissionManager`：集中处理工具权限、危险操作确认和审计。
7. `EvalHarness`：更新评测指标和回归用例。

可能涉及的文件或配置类型包括：

1. Agent 编排入口：`agent_runner.py`、`agent_executor.go`、`AgentOrchestrator.java`。
2. 多 Agent 配置：`agents.yaml`、`roles/*.md`、`planner_prompt.md`、`reviewer_prompt.md`。
3. 工具注册：`tools/registry.*`、`mcp_servers.json`、`tool_schema.json`。
4. 状态存储：`agent_runs`、`agent_steps`、`agent_artifacts`、`agent_checkpoints` 表。
5. 评测集：`eval_cases/*.jsonl`、`harness_config.yaml`。
6. 权限配置：`permissions.yaml`、`tool_policy.json`、`approval_rules.yaml`。

核心修改逻辑是：

```text
原来：User -> Supervisor -> Planner/Researcher/Coder/Reviewer/Executor -> Supervisor -> Final
改成：User -> SingleAgentRunner -> ToolRouter/WorkflowNode -> Verify -> Final
```

也就是把“多个会说话的 Agent”改成“一个会调度工具和状态机的 Agent”。

## 4. 原因分析

Multi-Agent 的核心问题不是“Agent 多”，而是 **LLM Agent 之间的通信不是稳定接口**。

传统软件模块之间通过类型、schema、RPC 协议和测试约束交互；而多个 LLM Agent 之间通常通过自然语言摘要交互。自然语言摘要会带来几个问题：

1. **信息压缩有损**：子 Agent 汇报时会丢失细节。
2. **语义不稳定**：同一个中间结果，不同 Agent 可能理解不同。
3. **责任链变长**：每多一个 Agent，就多一次决策和错误传播。
4. **验证不充分**：上游 Agent 很难完全验证下游 Agent 的中间推理。
5. **状态一致性差**：每个 Agent 看到的上下文不完全一样。

从系统角度看，Multi-Agent 会引入类似分布式系统的问题：

| 分布式系统问题 | Multi-Agent 中的对应表现 |
| --- | --- |
| 网络通信成本 | Agent 之间传递摘要和消息消耗 token 与延迟 |
| 状态一致性 | 不同 Agent 持有不同上下文和记忆 |
| 并发冲突 | 多个 Agent 同时修改计划、文件或工具状态 |
| 故障定位 | 无法快速定位失败来自哪个节点 |
| 协议演化 | 一个 Agent 输出格式变化会影响另一个 Agent |
| 权限隔离 | 每个 Agent 的工具权限都要配置和审计 |

因此，当任务本身不是强并行、强角色隔离、强专业分工时，单 Agent 往往更工程化。

### 4.1 Multi-Agent 的隐藏复杂度

Multi-Agent 看起来像组织分工，实际上更接近一个小型分布式系统。它至少多出四类复杂度。

第一类是 **通信协议复杂度**。如果子 Agent 输出自然语言，主控 Agent 需要理解和再解释；如果子 Agent 输出 JSON，又要处理 schema 演进、字段缺失、兼容性和异常。

第二类是 **状态同步复杂度**。Planner 认为任务已经进入执行阶段，Executor 可能发现前提不成立，Reviewer 又可能基于旧 diff 做审查。多个 Agent 如果没有共享黑板、版本号和锁，就很容易出现状态错位。

第三类是 **权限复杂度**。Researcher 可以读日志，Coder 可以改文件，Executor 可以跑 shell，Reviewer 可以读 diff。每个角色都要配置工具权限、参数限制和审计规则，任何一个角色权限过大都会扩大风险。

第四类是 **评测复杂度**。Multi-Agent 的结果受多个 prompt、多个模型调用、多个中间总结影响。一次失败可能是 Planner 拆错、Worker 执行错、Reviewer 漏查、Supervisor 合并错，也可能只是中间摘要把事实写偏了。

### 4.2 为什么不能简单把所有角色 prompt 拼在一起

改单 Agent 不等于把 Planner、Researcher、Coder、Reviewer 的 prompt 全部拼接成一个超长 system prompt。这样通常会带来新的问题：

1. 角色指令冲突，例如“大胆探索”和“只做最小修改”同时出现。
2. 上下文太长，真正关键的硬约束被稀释。
3. 角色边界从架构层消失后，模型可能在错误阶段做错误动作。
4. prompt 维护困难，任何一个角色规则修改都会影响全局行为。

更好的做法是把角色能力拆成三类：

| 原角色能力 | 改造方式 |
| --- | --- |
| 稳定、可程序化的能力 | 改成工具、函数或 workflow node |
| 需要 LLM 判断但不需要独立上下文的能力 | 放进主 Agent 的阶段性 checklist |
| 需要隔离、并行或独立评审的能力 | 保留为可选 Subagent |

### 4.3 判断是否应该改单 Agent 的标准

可以用以下问题判断：

1. 子 Agent 之间是否频繁共享同一份上下文？
2. 子 Agent 输出是否经常需要主控重新解释？
3. 任务是否主要是顺序执行而不是并行执行？
4. 子 Agent 是否只是包装了一个工具调用？
5. 多 Agent 是否显著增加 token 和延迟？
6. 失败时是否难以定位具体责任节点？
7. 是否缺少强理由让不同 Agent 拥有不同权限域？

如果以上多数答案是“是”，改单 Agent 大概率更合适。

## 5. 解决方案

推荐的改造方向不是把所有能力塞进一个超长 prompt，而是把 Multi-Agent 的角色分工改造成单 Agent 内部的结构化执行能力。

### 5.1 单 Agent + 工具模块

将原本的子 Agent 改成确定性工具或函数：

```text
Researcher Agent -> search_docs/search_code/search_logs 工具
Coder Agent      -> edit_file/apply_patch 工具
Reviewer Agent   -> run_lint/run_tests/static_check 工具
Executor Agent   -> shell/sql/http 工具
```

好处：

1. 工具输入输出有 schema。
2. 工具结果更容易测试。
3. 权限可以按工具控制。
4. 不需要额外 LLM 轮次。

### 5.2 单 Agent + 显式状态机

将任务拆成固定阶段：

```text
INIT -> UNDERSTAND -> PLAN -> ACT -> VERIFY -> SUMMARIZE -> DONE
```

每个阶段由同一个 Agent 执行，但状态由系统维护：

```json
{
  "run_id": "run_001",
  "phase": "VERIFY",
  "goal": "修复登录接口单测失败",
  "plan": ["读取失败日志", "定位代码", "修改实现", "运行目标测试"],
  "facts": ["失败用例是 LoginServiceTest.testExpiredToken"],
  "changed_files": ["src/login/service.java"],
  "verification": {
    "target_test": "passed",
    "lint": "not_run"
  }
}
```

这样既保留了任务结构，又避免多 Agent 状态分裂。

### 5.3 单 Agent + 内部角色模式

可以保留“角色思维”，但不要真的创建多个 Agent。比如在同一个 Agent 内部要求：

```text
先作为 Planner 给出计划；
再作为 Executor 执行一步；
最后作为 Reviewer 根据测试和 diff 做检查。
```

这本质上是 prompt 内部的工作模式切换，不需要跨 Agent 通信。

### 5.4 单 Agent + Harness 评测

改单 Agent 后要重新建立评测指标：

1. 任务成功率。
2. 平均工具调用次数。
3. 平均 token 成本。
4. 平均端到端延迟。
5. 高风险工具调用次数。
6. 回归用例通过率。
7. 用户中断/人工接管次数。
8. 错误修改率或误操作率。

如果没有 Harness，只凭肉眼感觉“单 Agent 更简单”，很容易忽略质量下降。

### 5.5 保留可选 Subagent

单 Agent 不等于永远不用子 Agent。更稳妥的方式是：

1. 默认单 Agent。
2. 只有当任务满足明确条件时才临时启动子 Agent。
3. 子 Agent 只做只读、可并行、可校验的任务。
4. 子 Agent 输出必须结构化，并由主 Agent 验证。

适合启动子 Agent 的条件：

1. 需要并行阅读大量互不相关的文件。
2. 需要多个独立方案对比。
3. 需要 reviewer 做只读检查。
4. 需要隔离不同权限域。

### 5.6 主控 Agent 执行循环

单 Agent 的核心可以写成一个可恢复的循环：

```python
def run_agent(user_request, run_id):
    state = load_or_create_state(run_id, user_request)

    while not state.done:
        context = build_context(
            goal=state.goal,
            constraints=state.constraints,
            facts=state.facts,
            plan=state.plan,
            recent_steps=state.recent_steps,
            tool_schemas=get_allowed_tool_schemas(state),
        )

        decision = llm_decide(context)
        action = parse_and_validate(decision)

        if action.requires_approval:
            state = wait_human_approval(state, action)
            continue

        result = execute_tool(action)
        state = reduce_state(state, action, result)
        save_step_trace(run_id, action, result, state)

        if should_verify(state):
            verify_result = run_verification(state)
            state = reduce_state(state, "verify", verify_result)

        if should_stop(state):
            state.done = True

    return build_final_answer(state)
```

这个循环里，LLM 只负责决策和解释；状态、权限、工具执行、验证和持久化都由工程系统控制。

### 5.7 工具契约设计

把子 Agent 改成工具后，工具返回必须结构化。不要只返回一段自然语言。

```json
{
  "ok": false,
  "tool": "run_test",
  "error_code": "TEST_FAILED",
  "retryable": false,
  "summary": "LoginServiceTest.testExpiredToken failed",
  "evidence": {
    "file": "build/reports/tests/LoginServiceTest.txt",
    "line": 128,
    "trace_id": "trace_abc"
  },
  "suggested_next_actions": [
    "read_file(src/login/LoginService.java)",
    "search_code(validateExpiredToken)"
  ]
}
```

这样主 Agent 可以基于 `ok/error_code/retryable/evidence` 做下一步，而不是猜测工具到底发生了什么。

### 5.8 上下文组织方式

单 Agent 上下文要分层，不要把所有历史都塞进 prompt：

| 上下文类型 | 内容 | 存储位置 | 注入策略 |
| --- | --- | --- | --- |
| 当前目标 | 用户请求、成功标准、硬约束 | Run State | 每次注入 |
| 当前计划 | 步骤、阶段、下一步动作 | Run State | 每次注入摘要 |
| 已验证事实 | 日志结论、测试结果、文件位置 | Fact Store | 每次注入 |
| 原始工具结果 | 完整日志、搜索结果、命令输出 | Artifact Store | 按需引用 |
| 长期记忆 | 项目规则、用户偏好、历史经验 | Memory Store | 检索后注入 |
| 安全策略 | 工具权限、审批规则、敏感资源 | Policy Store | 系统侧强制 |

关键原则是：**主 Agent 看到的是决策所需的事实摘要，完整证据放在外部 artifact 中按需读取**。

## 6. 可选方案对比

| 方案 | 优点 | 缺点 | 适用场景 |
| --- | --- | --- | --- |
| 全量 Multi-Agent | 并行能力强，角色分工清晰，适合复杂任务 | 成本高、延迟高、状态混乱、调试困难 | 大规模研究、复杂方案评审、强并行分析 |
| 单 Agent | 链路短、成本低、状态一致、易调试 | 专业分工弱，长任务容易上下文膨胀 | 代码修复、客服处理、RAG、常规工具任务 |
| 单 Agent + 工具模块 | 稳定、便宜、易测、权限清晰 | 工具建设成本较高 | 生产级 Agent 系统 |
| 单 Agent + 工作流 | 确定性强，可控性高 | 灵活性下降，流程设计成本高 | 审批、客服、CI 修复、固定业务流程 |
| 单 Agent + 可选 Subagent | 默认简单，必要时并行 | 仍需处理子任务协议和结果校验 | 复杂但可拆分的研发/分析任务 |
| Supervisor + 多 Worker | 权限和角色隔离好 | 编排复杂，Supervisor 容易成为瓶颈 | 多团队协作、不同工具域隔离 |

还可以从决策维度做判断：

| 判断维度 | 倾向单 Agent | 倾向 Multi-Agent |
| --- | --- | --- |
| 任务依赖关系 | 强顺序、强共享状态 | 多个子任务基本独立 |
| 上下文范围 | 大量共享同一上下文 | 每个角色只需局部上下文 |
| 权限模型 | 同一权限域内操作 | 不同权限域必须隔离 |
| 延迟要求 | 强实时、用户等待 | 可异步、可批处理 |
| 成本要求 | 成本敏感 | 成本不是主要瓶颈 |
| 结果校验 | 可以用测试/规则验证 | 需要多专家独立判断 |
| 调试要求 | 要求强可复现 | 可以接受较长 trace |
| 业务风险 | 高风险，需要集中管控 | 低风险探索或离线研究 |

## 7. 推荐方案

推荐采用 **单 Agent 主控 + 工具模块 + 显式状态机 + 可选 Subagent**。

核心原则：

1. 默认所有任务由一个主 Agent 维护目标、计划、事实、工具结果和最终输出。
2. 子能力优先做成工具、函数、workflow node，而不是独立 LLM Agent。
3. 只有明确能并行、只读、可校验、低耦合的任务才启动临时子 Agent。
4. 所有工具调用必须有 schema、权限控制、trace 和错误处理。
5. 用 Harness 比较改造前后的质量、成本、延迟和安全性。

这个方案的优势是：保留单 Agent 的简单性，又不完全放弃 Multi-Agent 的并行能力。

推荐架构可以表示为：

```text
User Request
    |
    v
Single Agent Runner
    |
    +-- Context Builder
    |      +-- Run State
    |      +-- Facts
    |      +-- Memory
    |      +-- Tool Schemas
    |
    +-- LLM Decision
    |
    +-- Policy / Permission Check
    |
    +-- Tool Router
    |      +-- Search Tool
    |      +-- Code Tool
    |      +-- Test Tool
    |      +-- Business API
    |
    +-- State Reducer
    |
    +-- Verification / Harness
    |
    v
Final Answer + Trace + Artifacts
```

如果要保留 Subagent，建议只作为 `ToolRouter` 下的一类特殊工具：

```text
spawn_readonly_subagent(task, input, output_schema, timeout, allowed_tools)
```

也就是说，Subagent 不是平级决策者，而是主 Agent 可调用、可限时、可验证的异步工具。

### 7.1 什么时候不建议改单 Agent

以下场景仍然可以保留 Multi-Agent：

1. **强并行研究**：例如同时分析 50 篇论文、多个竞品、多个代码模块。
2. **多专家独立评审**：例如安全审计、架构评审、法律合规，需要独立观点避免单点偏差。
3. **权限强隔离**：例如一个 Agent 只能读日志，另一个 Agent 才能申请生产变更。
4. **长周期后台任务**：多个子任务可以独立运行数小时，最终由主控汇总。
5. **探索型方案生成**：需要多个不同假设、不同策略互相辩论。
6. **组织边界明显**：不同团队维护不同工具、数据域和审批流程。

所以面试里不能绝对说 Multi-Agent 不好。更准确的说法是：**高耦合任务改单 Agent，低耦合并行任务保留 Multi-Agent**。

## 8. 实施步骤

### 8.1 盘点现有 Multi-Agent 链路

先列出每个 Agent 的职责：

```text
Planner：拆任务
Researcher：检索文档/代码/日志
Coder：修改文件
Reviewer：审查结果
Executor：运行命令
```

然后判断每个职责是否真的需要 LLM：

1. 如果只是查文档，改成检索工具。
2. 如果只是跑命令，改成执行工具。
3. 如果只是检查格式，改成 lint/test。
4. 如果需要复杂判断，再保留在主 Agent prompt 中。

### 8.2 设计单 Agent 状态模型

建议状态字段包括：

1. `goal`：用户目标。
2. `constraints`：限制条件，例如不能改 schema、不能访问生产库。
3. `plan`：当前计划。
4. `facts`：已经验证过的事实。
5. `tool_results`：关键工具返回。
6. `changed_files`：修改范围。
7. `risks`：当前风险。
8. `verification`：验证结果。
9. `next_action`：下一步动作。

### 8.3 合并 Prompt

把多个角色 prompt 合并成主 Agent 的执行规范：

```text
你是一个单主控 Agent。
你需要先明确目标和约束，再选择工具执行。
不要把未验证的观察当作事实。
修改文件后必须运行最小相关测试。
高风险操作必须请求用户确认。
最终输出必须包含变更、验证和风险。
```

不要把所有历史角色 prompt 直接拼接，否则会变成长而冲突的系统提示。

### 8.4 重构工具权限

将权限从“按 Agent”改为“按工具 + 参数 + 场景”：

```text
read_file：默认允许
edit_file：仅允许 workspace 内
run_test：允许
shell：危险命令需要确认
database_write：默认禁止
external_api_write：需要审批
```

### 8.5 建立 Trace

每一步记录：

1. 当前状态。
2. Agent 决策。
3. 工具名称。
4. 工具参数。
5. 工具返回。
6. 错误信息。
7. 状态变更。

这样改造后才能比较单 Agent 是否真的更稳定。

### 8.6 回归评测

准备一组改造前后都能跑的 case：

1. 简单问答。
2. 多轮 RAG。
3. 代码修复。
4. 工具失败重试。
5. 权限拒绝。
6. prompt injection。
7. 长上下文任务。
8. 用户中途变更需求。

比较指标：

1. 成功率是否下降。
2. 平均延迟是否下降。
3. 平均 token 是否下降。
4. 工具调用是否减少。
5. 安全违规是否减少。
6. 失败 case 是否更容易定位。

### 8.7 灰度迁移计划

建议按以下顺序迁移：

1. **只读任务先迁移**：例如 RAG 问答、日志总结、代码解释。
2. **低风险写任务再迁移**：例如生成草稿、创建 PR、生成测试。
3. **高风险任务最后迁移**：例如生产变更、数据写入、自动恢复。
4. **保留回退开关**：同一个 case 可以切回原 Multi-Agent 链路。
5. **双跑对比**：一段时间内 Multi-Agent 和单 Agent 同时离线执行，只把一个结果给用户。
6. **按指标放量**：成功率、P95 延迟、成本、安全违规都达标后再扩大流量。

### 8.8 迁移清单

| 检查项 | 说明 |
| --- | --- |
| 角色清单 | 列出所有旧 Agent 的职责、工具和 prompt |
| 工具替换 | 判断哪些 Agent 可以替换为工具或 workflow node |
| 状态字段 | 定义单 Agent 需要持久化的 run state |
| 权限策略 | 从角色权限改成工具权限和参数权限 |
| Trace 格式 | 统一记录 step、action、observation、artifact |
| 验证规则 | 定义每类任务的成功标准和最小测试 |
| 回退策略 | 支持按用户、任务类型或流量比例回退 |
| 灰度指标 | 成本、延迟、成功率、接管率、安全违规 |

### 8.9 Prompt 改造示例

旧 Multi-Agent prompt 可能是：

```text
Planner：你负责拆解任务，不执行工具。
Researcher：你负责检索资料，不修改文件。
Coder：你负责修改代码。
Reviewer：你负责检查 Coder 的输出。
```

单 Agent 可以改成：

```text
你是单主控 Agent。你必须维护统一任务状态。

执行规则：
1. 先明确目标、硬约束和成功标准。
2. 每次只能选择一个下一步 action。
3. 工具结果必须先转化为“已验证事实”再用于后续推理。
4. 修改前说明修改范围，修改后运行最小相关验证。
5. 如果需要扩大范围、执行高风险工具或访问敏感资源，必须请求确认。
6. 最终输出包含：问题原因、修改内容、验证结果、剩余风险。
```

注意：prompt 只定义行为准则，真正的权限和验证必须由代码强制执行。

### 8.10 代码实现重点

核心修改逻辑可以拆成四步：

1. 删除或下线 `Supervisor -> Worker Agent` 的消息编排。
2. 新增 `SingleAgentRunner`，负责加载状态、构建上下文、调用模型和推进状态。
3. 把旧 Worker 能力改造成工具，例如 `search_code`、`run_test`、`create_patch`、`review_diff`。
4. 更新评测脚本，让同一批 case 可以分别跑旧链路和新链路。

伪代码结构：

```text
AgentRunService
  - create_run()
  - resume_run()
  - cancel_run()

SingleAgentRunner
  - build_context()
  - decide_next_action()
  - execute_action()
  - reduce_state()
  - verify()

ToolRouter
  - validate_schema()
  - check_permission()
  - execute_tool()
  - normalize_result()

TraceStore
  - append_step()
  - save_artifact()
  - replay_run()
```

## 9. 风险与注意事项

1. **单 Agent 可能上下文过载**  
   原来分散在多个 Agent 的上下文现在集中到一个 Agent，需要上下文压缩、事实表和短期记忆管理。

2. **专业能力可能下降**  
   原来的 Coder、Reviewer、Researcher 如果 prompt 设计得很好，合并后可能丢失专业约束。可以用内部模式和 checklist 保留。

3. **权限集中风险增加**  
   单 Agent 持有更多工具，必须通过工具级权限、参数校验和人工确认控制风险。

4. **不要为了简单牺牲验证**  
   Reviewer Agent 被移除后，必须用测试、lint、static check、rule judge 或人工 review 补上验证能力。

5. **不要完全否定 Multi-Agent**  
   当任务天然独立、需要并行或权限隔离时，Multi-Agent 仍然有价值。

6. **迁移要灰度**  
   不要一次性替换所有链路。应先选择高频、低风险、耦合度高的任务试点。

7. **单 Agent 的失败可能更集中**  
   Multi-Agent 至少有角色间互相检查的可能；改单 Agent 后，要用外部验证、规则检查和人工审批补上制衡。

8. **工具过多会让单 Agent 决策变差**  
   如果一次性暴露几十个工具，模型可能选错。应该按任务阶段动态注入工具。

9. **状态 Reducer 要确定性**  
   工具结果如何写入 facts、plan、verification，最好由代码 reducer 控制，不要完全让模型自由改状态。

10. **长期记忆不要随便合并**  
    多 Agent 的记忆合并到单 Agent 时，要清理过期规则、错误经验和角色私有假设。

11. **可观测性不能降级**  
    少了 Agent 间消息，不代表 trace 可以减少。每个工具调用、状态变更和审批都要保留。

12. **回退机制必须存在**  
    如果单 Agent 在某类复杂任务上成功率下降，要能按任务类型回退到 Multi-Agent 或人工流程。

## 10. 验证方式

验证单 Agent 改造是否有效，不能只看主观体验，要看数据。

### 10.1 离线验证

1. 用相同测试集分别跑 Multi-Agent 和单 Agent。
2. 对比成功率、成本、延迟、工具调用次数。
3. 对失败 case 做分类：理解错误、工具错误、权限错误、验证缺失、上下文丢失。
4. 检查单 Agent 是否更容易复现和定位问题。

### 10.2 在线验证

1. 小流量灰度。
2. 对比用户满意度、人工接管率、任务完成率。
3. 监控高风险工具调用次数。
4. 监控任务超时率和重试率。
5. 记录用户中断和撤销操作。

### 10.3 测试重点

如果涉及代码实现，测试重点包括：

1. **状态迁移测试**：不同阶段是否能正确流转。
2. **工具权限测试**：危险工具是否被拦截。
3. **上下文压缩测试**：长任务是否丢失关键约束。
4. **失败恢复测试**：工具超时、空结果、异常返回时是否能继续。
5. **回归测试**：改造后是否破坏原有成功 case。
6. **安全测试**：外部文档或消息中的 prompt injection 是否会影响系统指令。
7. **并发测试**：多个用户或多个任务同时执行时状态是否隔离。

### 10.4 指标设计

建议至少采集这些指标：

| 指标 | 含义 | 预期变化 |
| --- | --- | --- |
| `task_success_rate` | 任务最终成功率 | 不能低于旧链路 |
| `avg_model_calls` | 平均模型调用次数 | 明显下降 |
| `avg_tool_calls` | 平均工具调用次数 | 不应异常上升 |
| `avg_tokens_per_run` | 单任务 token 消耗 | 下降 |
| `p95_latency` | 端到端 P95 延迟 | 下降 |
| `human_takeover_rate` | 人工接管率 | 不应上升 |
| `unsafe_action_blocked` | 被拦截的危险动作 | 可观测、可审计 |
| `rollback_rate` | 用户撤销或系统回退比例 | 不应上升 |
| `replay_success_rate` | trace 回放成功率 | 上升 |
| `state_conflict_count` | 状态冲突次数 | 下降 |

### 10.5 A/B 对比样例

可以设计一批固定 case：

```json
{
  "case_id": "fix_login_test_001",
  "input": "修复登录接口单测失败，不要修改数据库 schema",
  "expected": {
    "must_not_change": ["db/schema.sql"],
    "must_run": ["LoginServiceTest"],
    "must_report": ["root_cause", "changed_files", "verification"]
  },
  "judge": {
    "tests_pass": true,
    "schema_unchanged": true,
    "no_forbidden_tool": true
  }
}
```

对旧 Multi-Agent 和新单 Agent 分别记录：

1. 是否成功。
2. 是否遵守约束。
3. 是否运行必要测试。
4. 是否修改无关文件。
5. token、延迟、工具调用次数。
6. 失败时能否通过 trace 定位原因。

### 10.6 验收标准

可以设定上线门槛：

1. 成功率不低于旧链路，或在高频任务上提升。
2. P95 延迟至少下降 20%。
3. token 成本至少下降 20%。
4. 高风险工具调用全部经过权限校验。
5. 禁止修改的文件或资源没有越权写入。
6. 所有失败 case 都能通过 trace 定位到具体 step。
7. 用户可中断、可取消、可回退。

## 11. 总结

Multi-Agent 改单 Agent 的最大优势是 **把一个分布式、难调试、状态分裂的 Agent 系统，收敛成一个状态集中、链路更短、成本更低、权限更清楚的执行系统**。

主要收益包括：

1. 降低 token 成本和端到端延迟。
2. 减少 Agent 间通信和上下文丢失。
3. 提高状态一致性和可解释性。
4. 简化权限、日志、trace 和评测。
5. 降低并发冲突和结果合并复杂度。
6. 更容易做灰度、回归和故障定位。

可以把收益拆成四个层面：

| 层面 | Multi-Agent 常见问题 | 单 Agent 改造收益 |
| --- | --- | --- |
| 架构 | 多角色编排复杂 | 单主控状态机更清晰 |
| 成本 | 多轮模型调用和重复上下文 | token 与延迟下降 |
| 可靠性 | 中间摘要失真、状态分裂 | 统一事实表和状态 reducer |
| 安全 | 多角色权限矩阵复杂 | 工具级权限集中治理 |
| 评测 | 失败归因困难 | run/step/artifact 更易回放 |

但单 Agent 不是银弹。它适合高耦合、顺序执行、需要统一上下文的任务；对于强并行、强专业分工、强权限隔离的任务，仍然可以保留临时子 Agent 或 Multi-Agent。工程上更推荐的答案是：

```text
默认单 Agent 主控；
子能力优先工具化；
流程用状态机约束；
必要时才启动可校验的临时子 Agent；
最终用 Harness 数据证明改造收益。
```

面试里可以这样回答：

```text
Multi-Agent 改单 Agent 的优势主要是工程复杂度下降。多 Agent 最大的问题是跨 Agent 通信不是稳定接口，子 Agent 经常通过自然语言摘要传递状态，容易丢事实、解释不一致、难以回放，成本和延迟也高。改单 Agent 后，目标、计划、事实、工具结果和权限都集中在一个 run state 里，链路更短，token 更少，trace 更容易看，失败也更容易定位。

但我不会把它理解成一个大 prompt 解决一切。更合理的做法是单 Agent 主控，子能力工具化，流程用状态机约束，工具有 schema 和权限，修改后必须验证。对于只读并行检索、多方案评审、权限强隔离这类场景，可以保留临时 subagent，但它应该像受控工具一样被主 Agent 调用，而不是和主 Agent 平级决策。

所以结论是：高耦合、顺序型、需要统一上下文的任务适合改单 Agent；低耦合、强并行、强隔离的任务仍然适合 Multi-Agent。是否改造最终要用 Harness 对比成功率、延迟、token、工具误用率和安全违规率。
```
