# 52. 弹性伸缩分布式训练调度系统设计

## 1. 问题背景

在大规模模型训练中，资源需求随训练阶段动态变化：初期需要大量资源进行快速探索，中期需要稳定资源进行长时训练，后期可能需要灵活调整资源进行调优和评估。传统的静态资源分配方式无法适应这种动态需求，导致资源浪费或训练效率低下。

**假设条件**：本文档基于 Kubernetes + PyTorch 生态的弹性训练场景，假设使用多租户 GPU 集群（100~1000 张 GPU），训练框架支持 Elastic Training（PyTorch Elastic）、FSDP 或 DeepSpeed，调度器使用 Volcano 或 YarnFair，训练任务需要支持从 8 卡动态扩展到 64 卡甚至更多。

## 2. 问题现象

1. **资源静态分配导致浪费**：训练初期和后期资源需求低，但预留的资源无法释放。
2. **资源争抢影响训练**：多任务共享集群时，资源争抢导致训练不稳定。
3. **故障恢复时间长**：节点故障时需要手动重新调度，训练中断时间长。
4. **扩缩容速度慢**：新增节点需要手动配置网络、挂载存储，耗时长。
5. **状态同步困难**：动态变更参与训练的 GPU 数量时，模型状态同步复杂。

## 3. 影响范围

| 影响维度 | 程度 | 说明 |
| --- | --- | --- |
| 资源利用率 | 高 | 弹性伸缩可提高 30~50% 资源利用率 |
| 训练效率 | 高 | 动态资源分配减少等待时间 |
| 容错能力 | 高 | 自动故障恢复减少中断时间 |
| 运维成本 | 中 | 自动化调度减少人工干预 |
| 训练稳定性 | 中 | 动态变更可能引入扰动 |

## 4. 原因分析

### 4.1 静态资源分配的局限性

```python
# 传统静态分配方式

    "name": "llama-training",
    "replicas": 8,        # 固定 8 个 Pod

# 1. 训练全程使用 64 GPU，无法根据阶段调整
# 2. 即使只使用 20 GPU，也要占用 64 GPU 的资源
# 3. 节点故障时，需要人工重新调度
```

### 4.2 弹性伸缩的核心挑战

```text
弹性伸缩的技术挑战：

1. 状态一致性
   - 增加节点：需要将新节点加入通信组，同步模型状态
   - 减少节点：需要将状态迁移到剩余节点，重新分区

2. 通信组重建
   - FSDP/ZeRO 依赖分布式通信组
   - 动态变更需要重建 NCCL 通信组，开销大

3. 训练连续性
   - 扩缩容不能中断训练流程
   - 需要支持从中断点恢复

4. 资源协调
   - 调度器需要感知训练任务优先级
   - 抢占式调度需要保存被抢占任务的状态
```

### 4.3 调度器与训练框架的协同

```python
# 调度器与训练框架的协同问题
def traditional_flow():
    """
    传统流程：调度器与训练框架割裂
    """
    # 1. 调度器分配资源
    allocated_gpus = scheduler.request(64)
    
    # 2. 训练框架初始化
    dist.init_process_group(allocated_gpus)
    
    # 3. 训练中发生节点故障
    if node_failure:
        # 手动请求重新调度
        new_gpus = scheduler.request(64)  # 可能等待很久
        dist.destroy_process_group()
        dist.init_process_group(new_gpus)
        load_checkpoint()  # 从上次保存点恢复
    
    # 问题：步骤 3 的中断时间可能很长

def elastic_flow():
    """
    弹性流程：调度器与训练框架协同
    """
    # 1. 训练框架注册到调度器
    elastic_agent = ElasticAgent()
    elastic_agent.register()
    
    # 2. 调度器动态调整
    scheduler.set_membership_callback(elastic_agent.update_membership)
    
    # 3. 节点故障时，调度器自动触发 membership 更新
    # 训练框架自动处理 membership 变化，无需手动介入
```

import torchelastic.agent.server as elg

def elastic_training_entrypoint():
    """
    PyTorch Elastic 训练入口
    """
    run(
        entrypoint=train_step,
        backend="nccl",
        rendezvous=rdzv.etcd(
            endpoint="http://etcd:2379",

            max_nodes=64,

def train_step(args):
    """训练函数（每个 worker 执行）"""
    import torch.distributed as dist
    
    # Elastic 会自动处理 worker 数量变化
    local_batch_size = args.batch_size // args.world_size
    
    model = build_model()
    optimizer = torch.optim.AdamW(model.parameters())
    
    # 训练循环
    for epoch in range(100):

            # 反向传播

            optimizer.step()

### 5.3 动态资源分配策略

```python
# resource_allocator.py
class ElasticResourceAllocator:
    """
    弹性资源分配器
    
    策略：
    1. 基于训练阶段的资源调整
    2. 基于资源利用率的自动扩缩容
    3. 基于优先级的资源抢占
    """
    
    def __init__(self, scheduler_client):
        self.scheduler = scheduler_client
        self.current_gpus = 0
        self.target_gpus = 0
        self.stage_thresholds = {
            "warmup": {"min": 64, "max": 128},
            "steady": {"min": 64, "max": 64},
            "finetune": {"min": 8, "max": 16},
        }
    
    def adjust_for_stage(self, training_stage):
        """根据训练阶段调整资源"""
        threshold = self.stage_thresholds[training_stage]
        
        if self.current_gpus < threshold["min"]:
            self._scale_up(threshold["min"] - self.current_gpus)
        elif self.current_gpus > threshold["max"]:
            self._scale_down(self.current_gpus - threshold["max"])
    
    def adjust_for_utilization(self, gpu_util_avg, memory_util_avg):
        """基于利用率调整"""
        if gpu_util_avg > 0.9:
            # GPU 利用率高，尝试扩容
            self._scale_up(self.current_gpus // 4)
        elif gpu_util_avg < 0.5 and memory_util_avg < 0.6:
            # 利用率低，尝试缩容
            self._scale_down(self.current_gpus // 4)
    
    def _scale_up(self, delta):
        """扩容"""
        new_gpus = self.scheduler.request(self.current_gpus + delta)
        if new_gpus > self.current_gpus:
            self._notify_training_framework(new_gpus - self.current_gpus)
            self.current_gpus = new_gpus
    
    def _scale_down(self, delta):
        """缩容"""
        # 先保存 checkpoint，确保状态安全
        save_checkpoint()
        self.scheduler.release(delta)
        self.current_gpus -= delta
```

### 5.4 状态迁移与同步

```python
# state_migration.py
class ElasticStateManager:
    """
    弹性伸缩状态管理器
    """
    
    def __init__(self, model, optimizer, checkpoint_dir):
        self.model = model
        self.optimizer = optimizer
        self.ckpt_dir = checkpoint_dir
        self.current_rank = 0
        self.world_size = 1
    
    def handle_membership_change(self, new_world_size, new_rank_assignment):
        """
        处理 membership 变化
        
        Args:
            new_world_size: 新的 GPU 总数
            new_rank_assignment: {old_rank: new_rank} 映射
        """
        if new_world_size == self.world_size:
            return
        
        print(f"Membership changed: {self.world_size} -> {new_world_size}")
        
        # Step 1: 保存当前状态
        self._save_local_state()
        
        # Step 2: 等待所有 worker 完成保存
        dist.barrier()
        
        # Step 3: 重新分区模型（如果需要）
        if new_world_size > self.world_size:
            # 扩容：从更少的 GPU 重新分区到更多 GPU
            self._redistribute_for_expansion(new_rank_assignment)
        else:
            # 缩容：将状态迁移到剩余 GPU
            self._redistribute_for_contraction(new_rank_assignment)
        
        # Step 4: 重新初始化通信组
        self._reinitialize_comm_group(new_world_size)
        
        # Step 5: 恢复训练
        self._restore_state()
        
        self.world_size = new_world_size
    
    def _redistribute_for_expansion(self, rank_map):
        """扩容时重新分区"""
        # ZeRO/FSDP 状态需要重新分片
        # 加载完整模型到当前 GPU
        self.model = self._load_full_model()
        
        # 重新初始化优化器状态
        self.optimizer = self._create_optimizer(self.model.parameters())
    
    def _redistribute_for_contraction(self, rank_map):
        """缩容时迁移状态"""
        # 将被移除 GPU 的状态迁移到保留 GPU
        for old_rank, new_rank in rank_map.items():
            if new_rank == -1:  # 被移除的 rank
                state = self._collect_state_from_rank(old_rank)
                self._migrate_state_to_remaining(state, old_rank)
```

### 步骤 3：实现自动扩缩容控制器

```python
# autoscaler.py
import asyncio

class TrainingAutoscaler:
    def __init__(self, job_client, prometheus_url):
        self.job_client = job_client
        self.prometheus = prometheus_url
        self.scale_factor = 0.25  # 每次调整 25%
    
    async def monitor_and_scale(self):
        while True:
            # 获取当前指标
            metrics = await self._fetch_metrics()
            
            # 计算目标副本数
            target_replicas = self._compute_target_replicas(metrics)
            
            # 触发扩缩容
            await self._apply_scaling(target_replicas)
            
            await asyncio.sleep(60)  # 每分钟检查一次
    
    async def _fetch_metrics(self):
        """从 Prometheus 获取指标"""
        query = """
            avg(gpu_utilization{service="training"}) as $avg_gpu,
            avg(memory_utilization{service="training"}) as $avg_mem
        """
        return await self.prometheus.query(query)
    
    def _compute_target_replicas(self, metrics):
        """根据指标计算目标副本数"""
        current = self.job_client.get_replicas()
        avg_gpu = metrics["avg_gpu"]
        avg_mem = metrics["avg_mem"]
        
        if avg_gpu > 0.85:
            return min(int(current * (1 + self.scale_factor)), 64)
        elif avg_gpu < 0.5 and avg_mem < 0.6:
            return max(int(current * (1 - self.scale_factor)), 8)
        
        return current
```

## 9. 风险与注意事项

| 风险 | 缓解措施 |
| --- | --- |
| 扩容时状态不一致 | 使用分布式 barrier 同步，或先 checkpoint 再扩容 |
| 缩容时丢失计算进度 | 增量 checkpoint，保存优化器状态 |
| 频繁扩缩容震荡 | 设置冷却时间，Hysteresis 阈值 |
| 资源抢占导致训练失败 | 设置优先级，预留资源池 |
| 多租户资源争抢 | 资源配额，公平调度 |

## 11. 总结

弹性伸缩训练调度系统通过 PyTorch Elastic 和 Volcano 调度器的协同，实现资源动态调整和故障自动恢复，提高集群资源利用率和训练稳定性。

**核心要点**：
- PyTorch Elastic 处理训练框架级别的 membership 变化
- Volcano 负责 Kubernetes 资源调度和 Pod 管理
- 自动扩缩容根据资源利用率和训练阶段动态调整
- 状态迁移确保扩缩容后训练连续性
- 定期 checkpoint 和故障检测保证容错能力
