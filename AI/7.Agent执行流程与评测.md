# 7. Agent执行流程与评测

面试里问“Agent 执行一个进程有哪几种方式”“执行 step 后问题没解决怎么办”“执行 step 又产生新问题怎么办”“Agent 如何自我判断问题”“Agent 需要哪些测试集和指标”，核心考察的是 Agent 运行时设计，而不是单纯会不会调大模型。

## 1. Agent 执行一个进程有哪几种方式

这里的“进程”可以按广义理解：Agent 为完成任务启动的一次外部执行，包括系统命令、工具调用、浏览器自动化、后台任务或远程工作流。

常见方式：

1. **本地子进程**：通过 `subprocess`、`execve`、Shell、Node `child_process` 等方式执行命令，适合编译、测试、脚本和本地工具。
2. **沙箱或容器**：在 Docker、Firecracker、Kubernetes Job、受限工作区里执行，适合不可信代码、用户脚本和高风险操作。
3. **远程执行**：通过 SSH、CI Runner、Kubernetes、任务调度平台执行，适合需要特定环境或资源的任务。
4. **MCP/Tool Server**：Agent 不直接启动进程，而是调用工具服务，由服务端封装鉴权、执行、审计和结果裁剪。
5. **异步队列任务**：把长任务投递到 MQ、任务表或工作流引擎，返回 `job_id` 后轮询、订阅或回调。
6. **浏览器或 GUI 自动化**：启动或连接浏览器进程，通过快照、点击、输入、截图完成网页任务。
7. **内嵌工作流运行时**：把多个步骤编排成一个确定性工作流，由运行时负责状态、审批、恢复和输出约束。

选择时要看三件事：

1. 是否有副作用和安全风险。
2. 是否需要长时间运行、取消和恢复。
3. 结果是否需要结构化返回给模型继续推理。

## 2. 工具反馈信息代表什么

Agent 调用工具后，不能只看自然语言结果，而要解析结构化反馈。

常见反馈字段：

| 字段 | 含义 | Agent 应该怎么用 |
| --- | --- | --- |
| `exit_code` | 命令退出码，0 通常表示成功 | 非 0 时进入错误分析或重试 |
| `stdout` | 标准输出 | 提取成功结果、统计信息或结构化 JSON |
| `stderr` | 标准错误 | 提取错误类型、堆栈、失败用例 |
| `error_code` | 工具定义的业务错误码 | 区分参数错误、权限不足、超时、限流 |
| `trace_id` | 服务端追踪 ID | 用于日志排查和问题复现 |
| `artifacts` | 生成的文件、报告、截图、链接 | 后续引用，不必全文塞入上下文 |
| `retryable` | 是否可重试 | 决定重试、换工具还是停止 |
| `requires_approval` | 是否需要人工确认 | 暂停执行，等待用户审批 |

例如运行测试时：

```json
{
  "exit_code": 1,
  "stderr": "test_login_timeout failed: expected 200, got 504",
  "artifacts": ["reports/unit.xml"],
  "retryable": false
}
```

这说明任务不是“没有回答好”，而是测试真实失败。Agent 应该定位 `test_login_timeout` 相关代码和报告，而不是盲目重跑。

## 3. Agent 如何自我判断出现问题

Agent 的自我判断本质是把“预期状态”和“观测结果”做对比。

常见判断依据：

1. **退出码异常**：命令非 0、工具返回 `ok=false`。
2. **断言失败**：测试、lint、schema 校验、业务规则校验失败。
3. **结果缺失**：期望生成文件、记录或链接，但 artifacts 为空。
4. **状态不一致**：计划标记已完成，但验证命令仍失败。
5. **置信度不足**：模型输出没有引用证据，或证据不能支撑结论。
6. **工具误用**：参数缺失、权限不足、调用了错误环境。
7. **外部约束冲突**：用户要求、系统规则和工具能力互相矛盾。

更稳的做法是每个 step 都定义验证条件：

```text
step: 修复登录超时测试
action: 修改超时处理逻辑
verification: 运行 test_login_timeout 且 exit_code = 0
```

没有验证条件的 step 容易变成“模型觉得做完了”，真实工程里风险很高。

## 4. 执行 step 后问题没有解决怎么办

执行失败后不要立即扩大修改范围，应该先分类。

处理流程：

```text
观察反馈
-> 判断失败类型
-> 检查是否可重试
-> 补充上下文或换工具
-> 执行最小修复
-> 重新验证
-> 达到重试上限后停止并说明阻塞点
```

常见策略：

1. **参数错误**：修正参数、补齐必填字段、缩小查询范围。
2. **环境错误**：检查依赖、路径、权限、网络、配置。
3. **偶发错误**：有限次数重试，并使用指数退避。
4. **真实业务失败**：阅读日志、定位根因、修改实现或数据。
5. **权限不足**：请求授权或切换到只读、低风险方案。
6. **工具能力不足**：换工具、拆分任务或请求用户提供信息。
7. **无法确定**：停止自动执行，输出已验证事实和下一步建议。

要避免无限循环。工程上可以设置 `max_attempts`、`max_tool_calls`、`max_runtime` 和“同类错误不重复重试”的规则。

## 5. step 产生了新的问题怎么办

复杂任务中，一个 step 可能发现新的子问题。例如修复一个测试时发现配置缺失，或者检索知识库时发现权限模型不完整。

处理时要把新问题纳入任务图，而不是打乱主线：

1. **判断关系**：新问题是阻塞当前目标、独立副作用，还是可延后的优化。
2. **记录依赖**：如果它阻塞主任务，就插入到当前 step 前；如果不阻塞，就放入待办。
3. **隔离副作用**：新问题涉及写操作、删除、发消息时必须重新确认风险。
4. **更新计划**：让用户和系统状态都能看到新增 step 的原因。
5. **重新验证**：解决新问题后回到原目标，验证原问题是否真正消失。

可以用任务图表达：

```text
A: 修复登录测试
  depends_on B: 修复测试环境配置
B 完成后再回到 A 的验证
C: 顺手发现的日志格式优化 -> 非阻塞，进入 backlog
```

## 6. LangGraph 图结构工作流和自主 Agent 的区别

LangGraph 可以理解为把 LLM 应用组织成“有状态图”的框架。图里每个节点是一段可执行逻辑，例如调用模型、检索、工具执行、人工审批、结果校验；边表示节点之间的流转关系，条件边根据状态决定下一步。

一个简化结构：

```text
State
  -> plan node
  -> retrieve node
  -> tool node
  -> verify node
  -> conditional edge: done / retry / ask_user
```

它和“完全让 Agent 自主决定下一步”最大的区别在控制权：

1. **图工作流**：开发者预先定义可走的节点、边、循环和终止条件，模型只在节点内部做判断或生成。优点是可控、可观测、容易加审批和恢复。
2. **自主 Agent**：模型每一步根据目标、历史和工具列表自由决定下一个 action。优点是灵活，适合开放问题；缺点是更容易跑偏、重复调用工具或绕过业务约束。

LangGraph 的价值在于把 Agent 从“自由循环”收敛成可管理状态机：

1. **状态显式**：把用户问题、检索结果、工具输出、错误次数、审批状态放进 state。
2. **分支可控**：通过 conditional edge 处理成功、失败、重试、人工介入。
3. **循环有上限**：例如最多检索 3 次、工具失败 2 次后停止。
4. **可恢复**：配合 checkpointer 可以从某个状态继续执行，适合长任务。
5. **可观测**：每个节点的输入输出可以记录，便于评测和排障。

真实项目里可以这样取舍：

1. RAG 问答、审批流、客服工单、代码修复这类有明确步骤的任务，更适合图结构工作流。
2. 探索性研究、信息收集、开放式排障可以保留更多自主 Agent 空间。
3. 高风险工具调用要放在固定节点和审批边里，不建议完全交给模型自由决定。

面试回答可以说：LangGraph 不是让 Agent 失去智能，而是把可预期的流程固化，把不确定性限制在节点内部。这样既能利用 LLM 做理解和决策，又能让工程系统拥有状态、重试、审批、恢复和评测能力。

## 7. Agent 状态机和 HIL 怎么设计

Agent 状态机的目标是把模型的不确定推理收敛到可审计、可恢复、可暂停的工程流程里。一个长任务 Agent 可以设计成：

```text
CREATED
-> PLANNING
-> TOOL_SELECTING
-> WAITING_HUMAN_APPROVAL
-> EXECUTING
-> OBSERVING
-> VERIFYING
-> REFLECTING / RETRY_WAITING
-> SUCCEEDED / FAILED / CANCELLED / NEED_HUMAN
```

关键节点：

1. **PLANNING**：拆分目标，生成步骤、风险等级和验收条件。
2. **TOOL_SELECTING**：选择 Jenkins、数据库、配置中心、代码仓库等工具，并生成结构化参数。
3. **WAITING_HUMAN_APPROVAL**：高风险动作、低置信动作、生产写操作、重复触发任务前暂停，让人确认。
4. **EXECUTING**：调用工具或投递异步任务，记录 `run_id/job_id/build_id`。
5. **OBSERVING**：拉取工具反馈、日志、产物和状态码。
6. **VERIFYING**：用测试、指标、schema、业务规则判断是否达成目标。
7. **REFLECTING / RETRY_WAITING**：失败后分类原因，决定重试、换工具、补上下文、请求人工介入或停止。

HIL 通常不放在所有节点之前，而是放在**高风险副作用发生前**和**低置信自动决策之后**：

1. 触发 Jenkins 构建、生产配置变更、重启服务、回滚发布之前。
2. 模型推理结果和规则校验冲突时。
3. 同一任务达到重试上限、出现非幂等风险或影响范围扩大时。
4. 需要用户选择策略时，例如“重试同一次 run”还是“重新发起一条新 run”。

HIL 后面的节点一般包括：

1. **审批记录节点**：保存审批人、审批时间、审批内容、风险说明和幂等 key。
2. **执行节点**：真正调用 Jenkins/API/脚本，必须带上 `run_id`、`attempt_id` 和幂等参数。
3. **状态同步节点**：把外部任务 ID、队列 ID、build number、checkpoint 写入状态存储。
4. **观察验证节点**：轮询或订阅外部任务结果，并用验收条件判断是否完成。
5. **失败分流节点**：可重试进入退避重试，不可重试进入人工介入或最终失败。

易错点是把 HIL 当成“问一句用户要不要继续”。真正的 HIL 是状态机节点，必须有输入输出、超时策略、审批记录、恢复能力和后续分支。

## 8. ReAct 和 Reflection

ReAct 是 Reasoning + Acting。它让模型在“思考下一步”和“调用工具观察结果”之间循环：

```text
Thought -> Action -> Observation -> Thought -> Action -> ...
```

它的价值是让 Agent 不只生成答案，还能根据工具结果修正下一步。ReAct 里可以介入人，常见介入点是：

1. **Action 前**：高风险工具调用前审批。
2. **Observation 后**：工具返回异常、权限不足、结果歧义时让人补充信息。
3. **Plan 变更时**：Agent 准备扩大修改范围或改变目标时确认。
4. **Loop 上限前**：多次失败后让人判断继续、降级还是停止。

Reflection 是在 ReAct 基础上增加“反思和自我评估”步骤。它会检查上一轮计划、工具选择、输出和验证结果，提炼失败原因，再修改后续策略。

Reflection 的核心价值：

1. 把失败从“盲目重试”变成“分类后重试”。
2. 记录已尝试方案和排除原因，减少重复犯错。
3. 生成更好的下一步计划，例如换工具、补上下文、缩小范围或请求审批。
4. 把失败样本沉淀到评测集、规则或长期记忆中。

但 Reflection 不能真正保证解决死循环。模型可能反思出相同结论，也可能在错误假设上越走越远。工程上必须叠加硬性终止机制：

1. `max_steps`、`max_tool_calls`、`max_runtime`、`max_cost`。
2. 同一工具、同一参数、同一错误码不重复调用。
3. 失败原因指纹去重，例如 `error_type + tool + target`。
4. 退避重试和熔断，避免外部服务故障时形成重试风暴。
5. 状态机环路计数，超过阈值进入 `NEED_HUMAN`。
6. 验收条件必须外部可验证，不能只靠模型说“已解决”。

## 9. OpenClaw 和 Lobster 类系统的理解

OpenClaw 这类系统可以理解为把模型、工具、浏览器、技能、插件、任务调度和本地运行环境组合成一个 Agent Runtime。它强调 Agent 不只是聊天，而是能在受控环境中读取信息、操作浏览器、调用工具、执行工作流并保留状态。

Lobster 类工作流层的价值是把多次工具调用压成可审计、可恢复、带审批点的确定性流程。它适合邮件处理、批量数据清洗、发布流程、运维排障这类“步骤固定但需要模型做部分判断”的任务。

如果用这类思路设计自己的项目，可以考虑增加：

1. **隔离浏览器或沙箱**：避免 Agent 直接污染用户真实会话和本机环境。
2. **工具权限分级**：只读工具默认开放，写操作和高风险工具需要审批。
3. **任务图和 checkpoint**：支持失败恢复、中断恢复和长任务续跑。
4. **工作流 DSL 或模板**：把稳定流程固化，减少模型每次重新编排。
5. **轨迹记录和回放**：保存工具调用、输入输出摘要、审批和最终产物，用于评测。
6. **成本与安全上限**：限制运行时间、输出大小、工具调用次数和网络访问范围。

是否有必要取决于项目目标。如果只是简单问答或单次 RAG，完整 Agent Runtime 成本偏高；如果任务需要跨工具、多步骤、长时间执行、可恢复和可审计，就有引入价值。

## 10. Agent 评测需要哪些测试集

Agent 评测要覆盖“会不会答”和“会不会做”两个层面。

常见测试集：

1. **单步工具集**：给定明确目标，评测是否选择正确工具和参数。
2. **多步任务集**：需要计划、执行、观察、修正多个 step。
3. **失败恢复集**：工具超时、权限不足、空结果、测试失败、环境缺失。
4. **长上下文集**：早期约束、历史决策、旧工具结果需要在后续正确使用。
5. **安全权限集**：高风险操作、敏感信息、越权访问、审批流程。
6. **中断恢复集**：用户取消、切换目标、worker 重启、迟到结果。
7. **回归集**：线上失败样本和历史关键任务，防止新策略破坏旧能力。
8. **对抗集**：提示注入、恶意网页、工具返回污染、假引用。

## 11. Agent 评测指标

常见指标：

1. **任务成功率**：最终是否达成用户目标。
2. **step 成功率**：每个子步骤是否正确完成。
3. **工具选择准确率**：是否调用了正确工具，是否避免无关工具。
4. **参数正确率**：工具参数是否完整、合法、最小权限。
5. **恢复率**：失败后能否自我诊断并完成修复。
6. **幻觉率**：是否在缺少证据时编造结论或结果。
7. **安全违规率**：是否越权、泄漏隐私或跳过审批。
8. **人工介入率**：需要用户补充或接管的比例。
9. **成本指标**：token、工具调用次数、运行时间、外部 API 成本。
10. **可审计性**：是否保留足够 trace、日志和产物引用。

真实评测最好同时记录最终答案和执行轨迹。只看最终文本，无法发现工具误用、重复重试、绕过权限和上下文污染等问题。

## 12. 易错点

1. 把 Agent 评测等同于大模型问答评测，忽略工具调用和状态恢复。
2. step 没有验证条件，只靠模型口头声明“已完成”。
3. 工具错误不分类，所有失败都重试，容易无限循环。
4. 长任务没有 checkpoint，用户中断或 worker 重启后无法恢复。
5. 高风险工具缺少审批和幂等，失败后难以回滚。
6. 只评测成功样本，不评测空结果、权限不足、恶意输入和长上下文。

## 13. 面试回答模板

我会把 Agent 执行看成一个可观测的状态机，而不是简单的模型连续输出。执行方式可以是本地子进程、容器沙箱、远程 runner、MCP 工具、异步队列、浏览器自动化或工作流运行时。每个 step 都要有输入、动作、工具反馈、预期结果和验证条件。

如果 step 没解决问题，先根据退出码、错误码、stderr、trace、artifacts 判断是参数、环境、权限、业务逻辑还是偶发错误，再决定重试、换工具、补上下文、修改实现或停止升级。若 step 产生新问题，就把它放进任务图，判断是否阻塞主线，更新依赖和 checkpoint。评测时不仅看最终答案，还要看工具选择、参数正确率、恢复率、权限违规率、token 成本、长上下文保持和中断恢复能力。
