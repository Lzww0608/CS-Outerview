# 线程池实现

线程池用于复用一组工作线程处理任务，避免每个任务都创建和销毁线程。面试手写时，核心是任务队列、互斥锁、条件变量、停止标志和优雅退出。

## 1. 设计要点

1. 主线程调用 `submit` 把任务放入队列。
2. worker 线程阻塞等待条件变量。
3. 队列非空时取出任务执行。
4. 析构时设置停止标志，唤醒所有 worker。
5. worker 在“停止且队列为空”时退出。
6. 不能在持锁状态下执行任务，否则会阻塞其他提交和取任务操作。

## 2. C++ 实现

```cpp
#include <condition_variable>
#include <functional>
#include <future>
#include <memory>
#include <mutex>
#include <queue>
#include <stdexcept>
#include <thread>
#include <type_traits>
#include <utility>
#include <vector>

class ThreadPool {
public:
    explicit ThreadPool(size_t threadCount) {
        if (threadCount == 0) {
            throw std::invalid_argument("threadCount must be positive");
        }

        workers_.reserve(threadCount);
        for (size_t i = 0; i < threadCount; ++i) {
            workers_.emplace_back([this] { workerLoop(); });
        }
    }

    ThreadPool(const ThreadPool&) = delete;
    ThreadPool& operator=(const ThreadPool&) = delete;

    ~ThreadPool() {
        {
            std::lock_guard<std::mutex> lock(mutex_);
            stopping_ = true;
        }
        cv_.notify_all();

        for (auto& worker : workers_) {
            if (worker.joinable()) {
                worker.join();
            }
        }
    }

    template <class F, class... Args>
    auto submit(F&& f, Args&&... args)
        -> std::future<std::invoke_result_t<F, Args...>> {
        using R = std::invoke_result_t<F, Args...>;

        auto task = std::make_shared<std::packaged_task<R()>>(
            std::bind(std::forward<F>(f), std::forward<Args>(args)...)
        );
        std::future<R> result = task->get_future();

        {
            std::lock_guard<std::mutex> lock(mutex_);
            if (stopping_) {
                throw std::runtime_error("submit on stopped ThreadPool");
            }
            tasks_.emplace([task] { (*task)(); });
        }
        cv_.notify_one();
        return result;
    }

private:
    void workerLoop() {
        while (true) {
            std::function<void()> task;
            {
                std::unique_lock<std::mutex> lock(mutex_);
                cv_.wait(lock, [this] {
                    return stopping_ || !tasks_.empty();
                });

                if (stopping_ && tasks_.empty()) {
                    return;
                }

                task = std::move(tasks_.front());
                tasks_.pop();
            }

            task();
        }
    }

    std::vector<std::thread> workers_;
    std::queue<std::function<void()>> tasks_;
    std::mutex mutex_;
    std::condition_variable cv_;
    bool stopping_ = false;
};
```

## 3. 易错点

1. `wait` 必须带谓词，防止虚假唤醒和先通知后等待。
2. 任务执行前要释放队列锁，否则线程池会退化成串行。
3. 析构时要先设置停止标志，再 `notify_all`，最后 `join`。
4. 停止时可以选择“清空队列立即退出”或“执行完已有任务再退出”，要和面试官确认语义。
5. 生产级线程池还要考虑队列容量、拒绝策略、任务优先级、异常隔离、监控指标和线程命名。

## 4. 线程池状态和任务流转

面试里问“线程池状态和核心线程执行完任务后的状态转换”，可以参考 Java `ThreadPoolExecutor` 的状态模型，也可以映射到 C++ 自己实现的线程池。

常见状态：

| 状态 | 含义 |
| --- | --- |
| RUNNING | 接收新任务，也处理队列任务 |
| SHUTDOWN | 不再接收新任务，但继续处理队列中已有任务 |
| STOP | 不接收新任务，也不继续处理队列任务，并尝试中断正在执行的任务 |
| TIDYING | 工作线程数为 0，即将执行终止清理 |
| TERMINATED | 线程池完全终止 |

一个任务的典型流转：

```text
submit
  -> 如果核心线程未满，创建或唤醒核心线程执行
  -> 否则进入任务队列
  -> 如果队列满且线程数未到最大值，创建非核心线程
  -> 如果仍无法接收，执行拒绝策略
```

核心线程执行完一个任务后不会立刻销毁，而是继续从队列取任务；如果队列为空，就阻塞在条件变量或阻塞队列上等待新任务。允许核心线程超时回收时，核心线程也可能在空闲超过 keepAliveTime 后退出。

## 5. 线程池工作流程

可以按生产者消费者模型理解：

1. 提交方是生产者，把任务放入阻塞队列。
2. worker 是消费者，循环取任务并执行。
3. 队列为空时 worker 阻塞等待，避免空转浪费 CPU。
4. 新任务入队后 `notify_one` 唤醒一个 worker。
5. 关闭线程池时设置停止状态并 `notify_all`，让所有 worker 检查退出条件。

需要注意先通知后等待的问题：条件变量的通知本身不保存状态，真正保存状态的是任务队列和停止标志。所以 worker 必须使用带谓词的 `wait`：

```cpp
cv.wait(lock, [this] {
    return stopping_ || !tasks_.empty();
});
```

这样即使提交线程先 `notify_one`，worker 后进入 `wait`，也会因为队列非空而直接继续执行，不会永久睡眠。

## 6. 线程池线程数如何选择

线程数不是越多越好，核心是让 CPU、I/O 和下游资源都处在可控利用率内。

1. **CPU 密集型任务**：线程数通常取 `CPU 核数` 或 `CPU 核数 + 1`。线程过多会增加上下文切换、缓存失效和调度开销，反而降低吞吐。
2. **I/O 密集型任务**：线程会大量等待磁盘、网络、数据库或 RPC，线程数可以大于 CPU 核数。常见估算是 `线程数 = CPU 核数 * (1 + 等待时间 / 计算时间)`。
3. **混合型任务**：把 CPU 计算、阻塞 I/O、定时任务拆到不同线程池，避免慢 I/O 把 CPU 任务饿死。
4. **依赖下游的任务**：线程数还要受数据库连接池、RPC 并发限制、队列长度和限流策略约束，不能只按本机 CPU 算。

示例：8 核机器上纯计算任务可以从 8 个 worker 起步；如果任务 80% 时间在等待远端接口、20% 时间在本机计算，粗略估算是 `8 * (1 + 0.8 / 0.2) = 40`。真实上线还要通过压测观察 QPS、P95/P99 延迟、CPU 使用率、run queue、上下文切换次数和队列堆积，再决定是否扩容或改成异步 I/O。

易错点：

1. 线程池过大可能把 CPU 打满，也可能把数据库、Redis 或下游 RPC 打挂。
2. 队列无界会把压力藏起来，延迟升高后才暴露，生产环境更推荐有界队列和拒绝策略。
3. I/O 密集不代表无限加线程。如果系统主要在等网络，事件驱动、协程或异步 I/O 往往比堆线程更稳。
4. 多个业务共用一个线程池时，慢任务可能阻塞快任务，核心链路应该隔离线程池。

## 7. 生产级扩展

1. **有界队列**：避免无限积压导致内存打满。
2. **拒绝策略**：丢弃、阻塞、调用者执行、返回错误或降级。
3. **动态扩缩容**：按队列长度、延迟和 CPU 使用率调整线程数。
4. **任务超时和取消**：避免慢任务长期占用线程。
5. **异常隔离**：任务抛异常不能导致 worker 线程退出后无人补充。
6. **监控指标**：线程数、活跃数、队列长度、任务耗时、拒绝数。

## 8. 面试回答模板

线程池由固定数量 worker、任务队列、互斥锁、条件变量和停止标志组成。提交任务时加锁入队并 `notify_one`；worker 用 `condition_variable` 等待队列非空，取出任务后释放锁再执行；析构时设置停止标志并唤醒所有线程，等队列处理完后退出并 `join`。关键点是 wait 带谓词、任务执行不持锁、关闭语义明确。
