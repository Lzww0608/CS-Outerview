# 162. 模型并行调度器

## 1. 问题背景

题目要求手写一个简单的模型并行调度器。模型并行常见于大模型训练或推理场景：单张 GPU 放不下完整模型，或者单卡计算时间过长，需要把模型拆到多张设备上执行。

这里将问题抽象为面试中可手写的版本：给定一组按顺序执行的模型层和一组设备，调度器需要把连续的层分配到不同设备上，并生成 micro-batch 的流水线执行计划。这个问题本质上结合了：

1. **分段划分**：把模型层切成多个 stage。
2. **资源约束**：每个 stage 的显存不能超过设备容量。
3. **负载均衡**：尽量让每个 stage 的计算时间接近，减少流水线空泡。
4. **执行调度**：保证同一个 micro-batch 按 stage 顺序执行，同时不同 micro-batch 可以流水线并行。

### 假设条件

由于题目信息没有给出完整输入输出格式，本文基于项目中的手撕代码类文档风格做如下假设：

1. 模型由 `N` 个顺序层组成，每层有计算耗时 `cost` 和显存占用 `memory`。
2. 有 `K` 张设备，每张设备有显存上限 `memoryLimit`，简单版本默认设备算力一致。
3. 每个 stage 只能包含连续的层，不做非连续切分。
4. 默认实现 pipeline parallel，不实现复杂的 tensor parallel、ZeRO/FSDP 状态切分。
5. 调度目标是最小化所有 stage 中最大的计算耗时，即降低流水线瓶颈。
6. 如果某个层或某个分段无法满足显存约束，则返回调度失败。

## 2. 问题现象

如果没有调度器，模型并行实现中容易出现以下问题：

| 现象 | 说明 |
| --- | --- |
| 单卡显存不足 | 完整模型或某些连续层无法放入一张 GPU |
| stage 负载不均 | 某张卡计算时间明显更长，其他卡等待 |
| pipeline bubble 较大 | micro-batch 进入和退出流水线时设备空闲 |
| 执行顺序混乱 | micro-batch 必须先过前一 stage，不能越级执行 |
| 缺少失败判定 | 显存约束无法满足时仍然生成错误计划 |

## 3. 影响范围

该类调度器会影响大模型训练和推理链路中的资源利用率：

1. **训练吞吐**：stage 不均衡会导致整体吞吐由最慢 stage 决定。
2. **推理延迟**：分段不合理会放大跨设备通信和排队等待。
3. **显存稳定性**：错误放置可能直接导致 OOM。
4. **工程复杂度**：调度器输出会影响执行引擎、通信模块和测试用例设计。
5. **可扩展性**：后续扩展到 tensor parallel、异构设备、动态 batch 时，需要基于当前抽象继续演进。

## 4. 原因分析

模型并行调度难点主要来自两个矛盾：

1. **显存约束和负载均衡的矛盾**：为了负载均衡，希望每个 stage 的计算量接近；但某些层显存大，可能限制可行分段。
2. **局部最优和全局最优的矛盾**：贪心地把层平均分给设备，不一定能得到最小瓶颈耗时。

例如有 6 层，计算耗时如下：

```text
layer:  0  1  2  3  4  5
cost:   3  2  8  2  3  2
```

如果有 3 张设备，平均按层数切分为 `[0,1] [2,3] [4,5]`，stage cost 是 `5, 10, 5`，瓶颈为 10。更好的切分可能是 `[0,1,2] [3,4] [5]`，但如果第一段显存超限又不可行。

所以调度器需要同时考虑：

1. 分段必须连续。
2. 每段显存不能超过对应设备上限。
3. 目标函数是最小化最大 stage cost。
4. 分段结果还要能转换成合法的流水线时间表。

## 5. 解决方案

### 5.1 核心思路

使用动态规划完成模型层到设备 stage 的划分：

```text
dp[i][k] 表示前 i 层切成 k 个 stage 后，最大 stage cost 的最小值
```

转移时枚举最后一个 stage 的起点 `j`：

```text
dp[i][k] = min(
    max(dp[j][k - 1], cost(j, i - 1))
)
```

其中 `[j, i - 1]` 是最后一个 stage 的层范围，必须满足显存约束。

得到 stage 划分后，再生成 pipeline forward 调度表。对于第 `m` 个 micro-batch 和第 `s` 个 stage：

```text
start[m][s] = max(finish[m][s - 1], finish[m - 1][s])
finish[m][s] = start[m][s] + stageCost[s]
```

含义是：

1. 同一个 micro-batch 必须等前一个 stage 完成。
2. 同一个 stage 必须等上一个 micro-batch 使用完该设备。

### 5.2 C++ 手写实现

```cpp
#include <algorithm>
#include <climits>
#include <iostream>
#include <stdexcept>
#include <string>
#include <vector>

using namespace std;

struct Layer {
    string name;
    int cost;
    int memory;
};

struct Device {
    string name;
    int memoryLimit;
};

struct Stage {
    int device;
    int left;
    int right;
    int cost;
    int memory;
};

struct Step {
    int microBatch;
    int stage;
    int start;
    int finish;
};

class ModelParallelScheduler {
public:
    vector<Stage> partition(const vector<Layer>& layers, const vector<Device>& devices) {
        int n = static_cast<int>(layers.size());
        int k = static_cast<int>(devices.size());
        if (n == 0 || k == 0) {
            throw invalid_argument("layers and devices must not be empty");
        }
        if (k > n) {
            k = n;
        }

        vector<int> prefixCost(n + 1, 0);
        vector<int> prefixMemory(n + 1, 0);
        for (int i = 0; i < n; ++i) {
            prefixCost[i + 1] = prefixCost[i] + layers[i].cost;
            prefixMemory[i + 1] = prefixMemory[i] + layers[i].memory;
        }

        const int INF = INT_MAX / 4;
        vector<vector<int>> dp(n + 1, vector<int>(k + 1, INF));
        vector<vector<int>> pre(n + 1, vector<int>(k + 1, -1));
        dp[0][0] = 0;

        for (int parts = 1; parts <= k; ++parts) {
            for (int i = 1; i <= n; ++i) {
                for (int j = parts - 1; j < i; ++j) {
                    if (dp[j][parts - 1] == INF) {
                        continue;
                    }

                    int memory = prefixMemory[i] - prefixMemory[j];
                    if (memory > devices[parts - 1].memoryLimit) {
                        continue;
                    }

                    int cost = prefixCost[i] - prefixCost[j];
                    int bottleneck = max(dp[j][parts - 1], cost);
                    if (bottleneck < dp[i][parts]) {
                        dp[i][parts] = bottleneck;
                        pre[i][parts] = j;
                    }
                }
            }
        }

        if (dp[n][k] == INF) {
            throw runtime_error("cannot partition model under memory limits");
        }

        vector<Stage> stages;
        int i = n;
        for (int parts = k; parts >= 1; --parts) {
            int j = pre[i][parts];
            stages.push_back({
                parts - 1,
                j,
                i - 1,
                prefixCost[i] - prefixCost[j],
                prefixMemory[i] - prefixMemory[j]
            });
            i = j;
        }
        reverse(stages.begin(), stages.end());
        return stages;
    }

    vector<Step> buildForwardSchedule(const vector<Stage>& stages, int microBatches) {
        int m = microBatches;
        int s = static_cast<int>(stages.size());
        vector<vector<int>> finish(m, vector<int>(s, 0));
        vector<Step> plan;

        for (int mb = 0; mb < m; ++mb) {
            for (int stage = 0; stage < s; ++stage) {
                int depFinish = stage > 0 ? finish[mb][stage - 1] : 0;
                int deviceFree = mb > 0 ? finish[mb - 1][stage] : 0;
                int start = max(depFinish, deviceFree);
                finish[mb][stage] = start + stages[stage].cost;
                plan.push_back({mb, stage, start, finish[mb][stage]});
            }
        }

        return plan;
    }
};

int main() {
    vector<Layer> layers = {
        {"emb", 3, 4},
        {"block1", 4, 5},
        {"block2", 8, 6},
        {"block3", 3, 4},
        {"block4", 4, 5},
        {"head", 2, 2}
    };

    vector<Device> devices = {
        {"gpu0", 12},
        {"gpu1", 12},
        {"gpu2", 12}
    };

    ModelParallelScheduler scheduler;
    auto stages = scheduler.partition(layers, devices);
    auto plan = scheduler.buildForwardSchedule(stages, 4);

    for (const auto& st : stages) {
        cout << "device " << st.device
             << " layers [" << st.left << "," << st.right << "]"
             << " cost=" << st.cost
             << " memory=" << st.memory << endl;
    }

    for (const auto& step : plan) {
        cout << "mb=" << step.microBatch
             << " stage=" << step.stage
             << " start=" << step.start
             << " finish=" << step.finish << endl;
    }
}
```

### 5.3 复杂度分析

设模型层数为 `N`，设备数为 `K`：

1. 分段动态规划时间复杂度：`O(K * N^2)`。
2. 前缀和查询每段 cost 和 memory：`O(1)`。
3. 空间复杂度：`O(K * N)`。
4. 生成调度表复杂度：`O(M * K)`，其中 `M` 是 micro-batch 数量。

### 5.4 如果涉及代码实现

可能需要修改的模块：

1. **模型描述模块**：维护 layer 的计算耗时、显存估算、层序关系。
2. **设备资源模块**：维护 GPU 显存、算力、通信拓扑。
3. **调度模块**：实现分段算法、失败检测和执行计划生成。
4. **执行引擎模块**：根据调度计划提交 forward/backward 任务。
5. **监控模块**：采集实际耗时，用于后续重新调度。

可能涉及的文件：

1. `model/layer_desc.*`：层信息描述。
2. `runtime/device_manager.*`：设备资源管理。
3. `scheduler/model_parallel_scheduler.*`：模型并行分段和计划生成。
4. `executor/pipeline_executor.*`：按计划执行 micro-batch。
5. `tests/model_parallel_scheduler_test.*`：调度器单元测试。

核心修改逻辑：

1. 根据模型层构建前缀 cost 和 memory。
2. 使用动态规划寻找满足显存约束的最优连续切分。
3. 保存回溯数组，恢复每个设备负责的层范围。
4. 基于 stage cost 生成 micro-batch pipeline 时间表。
5. 对不可行输入抛出明确错误，例如单层超过显存、设备数为 0、无法分段。

测试重点：

1. 正常分段是否满足层顺序和显存约束。
2. stage 最大 cost 是否为最优或符合预期。
3. 单层显存超过所有设备时是否报错。
4. 设备数大于层数时是否能降级处理。
5. pipeline 计划是否满足依赖顺序和设备互斥。
6. 空输入、单层、单设备等边界用例。

## 6. 可选方案对比

| 方案 | 核心思想 | 优点 | 缺点 | 适用场景 |
| --- | --- | --- | --- | --- |
| 平均按层切分 | 每张卡分配近似相同层数 | 实现最简单 | 忽略层耗时和显存差异 | 面试快速口述、层很均匀 |
| 贪心切分 | 当前 stage 接近目标 cost 就切到下一张卡 | 代码短，速度快 | 可能不是全局最优 | 在线粗略调度 |
| 二分答案 + 贪心校验 | 二分最大 stage cost，检查能否切出不超过 K 段 | 时间复杂度较低 | 不方便适配异构设备 | 同构设备、目标只看瓶颈 |
| 动态规划切分 | 枚举最后一段起点，最小化最大 stage cost | 结果稳定，可回溯最优切分 | `O(K * N^2)`，层很多时较慢 | 面试手写、离线计划生成 |
| 图调度/DAG 调度 | 把算子作为 DAG 节点做资源调度 | 表达能力最强 | 实现复杂 | 真实训练框架或编译器 |

## 7. 推荐方案

推荐使用 **动态规划分段 + pipeline 时间表生成**。

原因：

1. 题目要求是“简单模型并行调度器”，不需要实现完整深度学习框架。
2. 动态规划能清晰表达最优化目标，面试中可解释性强。
3. 连续层切分符合 pipeline parallel 的常见工程约束。
4. 可以自然加入显存限制，避免生成不可执行计划。
5. 输出 stage 划分后，再生成 micro-batch 时间表，职责边界清楚。

如果面试官要求进一步优化，可以补充：

1. 同构设备下用二分答案降低复杂度。
2. 异构设备下将 `cost` 除以设备算力，加入通信 cost。
3. 训练场景中扩展 backward schedule，例如 GPipe 或 1F1B。
4. 单层过大时引入 tensor parallel，把矩阵乘按 head 或 hidden dimension 切分。

## 8. 实施步骤

1. **定义输入结构**：模型层包含 `name/cost/memory`，设备包含 `name/memoryLimit`。
2. **做参数校验**：检查层数、设备数、显存限制是否有效。
3. **构建前缀数组**：用 `prefixCost` 和 `prefixMemory` 支持区间查询。
4. **执行 DP 分段**：计算 `dp[i][k]`，并记录回溯点。
5. **恢复 stage 结果**：得到每张设备负责的连续层范围。
6. **生成 pipeline 计划**：对每个 micro-batch 和 stage 计算开始/结束时间。
7. **输出可执行计划**：包括设备编号、层范围、stage cost、stage memory、每步时间。
8. **补充异常路径**：无法满足显存约束时返回明确错误。
9. **接入执行引擎**：实际工程中由执行器按计划触发跨设备传输和算子执行。

## 9. 风险与注意事项

1. **显存估算偏差**：真实显存还包括激活、通信 buffer、临时 workspace，不能只看参数。
2. **通信成本被低估**：stage 之间需要传输激活，跨机通信可能成为瓶颈。
3. **异构设备问题**：不同 GPU 算力和显存不同，简单 cost 不能直接比较。
4. **单层过大问题**：如果单层超过单设备显存，pipeline 切层无法解决，需要 tensor parallel。
5. **训练调度更复杂**：训练还要处理 backward、梯度同步、权重更新和激活释放。
6. **pipeline bubble**：micro-batch 数量太少时流水线利用率低。
7. **动态输入长度**：LLM 推理中序列长度变化会导致 cost 和 memory 变化。
8. **计划与实际偏离**：静态估算得到的最优切分，运行时可能不是最优，需要监控反馈。

## 10. 验证方式

可以从单元测试、性质测试和端到端模拟三个层次验证。

### 10.1 单元测试

1. `N=1, K=1`：单层单设备能正常调度。
2. `K>N`：设备数大于层数时能降级为最多 `N` 个 stage。
3. 单层显存超限：必须抛出错误。
4. 多层显存刚好等于上限：应该允许分段。
5. 典型输入下 stage 范围连续且不重叠。

### 10.2 最优性验证

对小规模 `N`，可以暴力枚举所有连续切分，对比 DP 输出的最大 stage cost 是否等于暴力最优值。

```text
layers cost = [3, 4, 8, 3, 4, 2]
K = 3
期望：DP 输出的 max(stageCost) 等于所有合法切分中的最小值
```

### 10.3 调度合法性验证

对生成的 pipeline plan 检查：

1. 同一个 micro-batch 的 stage 顺序递增。
2. 同一个 stage 上不同 micro-batch 的时间不重叠。
3. 每个 micro-batch 都经过所有 stage。
4. 总 step 数等于 `microBatches * stageCount`。

## 11. 总结

简单模型并行调度器可以拆成两个核心问题：先做模型层到设备的连续分段，再生成 micro-batch 流水线执行计划。分段阶段推荐使用动态规划，在显存约束下最小化最大 stage cost；执行阶段用依赖时间和设备空闲时间共同决定每一步的开始时间。

这个方案足够适合手写算法题：输入输出清晰、复杂度可分析、能处理不可行情况，也能自然扩展到异构设备、通信成本、1F1B 训练调度和 tensor parallel。
