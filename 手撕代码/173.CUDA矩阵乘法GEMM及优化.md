# CUDA 矩阵乘法 GEMM 及优化版本

GEMM (General Matrix Multiply) 是深度学习中最核心的计算原语，面试常要求手写 CUDA 实现，包括 naive 版本和 shared memory 优化版本。题目要求实现 `C = A @ B`，其中 A 为 M×K，B 为 K×N，C 为 M×N。

## Naive 版本

每个 thread 负责计算 C 中的一个元素。

```cuda
#include <cuda_runtime.h>

// Naive GEMM: 每个 thread 计算一个 C[i][j]
__global__ void gemm_naive(
    const float* A, const float* B, float* C,
    int M, int N, int K
) {
    int row = blockIdx.y * blockDim.y + threadIdx.y;
    int col = blockIdx.x * blockDim.x + threadIdx.x;

    if (row < M && col < N) {
        float sum = 0.0f;
        for (int k = 0; k < K; k++) {
            sum += A[row * K + k] * B[k * N + col];
        }
        C[row * N + col] = sum;
    }
}

// Host 端调用
void launch_gemm_naive(
    const float* d_A, const float* d_B, float* d_C,
    int M, int N, int K
) {
    dim3 block(16, 16);  // 256 threads/block
    dim3 grid((N + 15) / 16, (M + 15) / 16);
    gemm_naive<<<grid, block>>>(d_A, d_B, d_C, M, N, K);
}
```

复杂度与性能分析：

```text
计算量: 2 × M × N × K FLOPs
访存量: 每个 thread 读 K 次 A + K 次 B + 写 1 次 C
       总访存: (M×N) × (2K + 1) × 4 bytes
算术强度: AI = 2MNK / (MN × 2K × 4) = 1/4 → 极低，严重访存密集
性能: < 5% GPU 峰值算力
```

Naive 版本的问题：每个 thread 独立从 HBM 读取 A 和 B 的元素，没有数据复用，全局内存访问次数极多。

## Shared Memory 版本

利用 Shared Memory 缓存 A 和 B 的分块，让一个 block 内的 thread 共享数据。

```cuda
#define TILE_SIZE 16

// Shared Memory Tiling 优化版
__global__ void gemm_shared(
    const float* A, const float* B, float* C,
    int M, int N, int K
) {
    // Shared Memory 缓存 A 和 B 的 tile
    __shared__ float As[TILE_SIZE][TILE_SIZE];
    __shared__ float Bs[TILE_SIZE][TILE_SIZE];

    int tx = threadIdx.x;
    int ty = threadIdx.y;
    int row = blockIdx.y * TILE_SIZE + ty;
    int col = blockIdx.x * TILE_SIZE + tx;

    float sum = 0.0f;

    // 沿 K 维度分块迭代
    for (int t = 0; t < (K + TILE_SIZE - 1) / TILE_SIZE; t++) {
        // 协作加载 A 的 tile 到 Shared Memory
        int a_col = t * TILE_SIZE + tx;
        if (row < M && a_col < K) {
            As[ty][tx] = A[row * K + a_col];
        } else {
            As[ty][tx] = 0.0f;
        }

        // 协作加载 B 的 tile 到 Shared Memory
        int b_row = t * TILE_SIZE + ty;
        if (b_row < K && col < N) {
            Bs[ty][tx] = B[b_row * N + col];
        } else {
            Bs[ty][tx] = 0.0f;
        }

        __syncthreads();  // 等待所有 thread 加载完成

        // 计算当前 tile 的部分和
        #pragma unroll
        for (int k = 0; k < TILE_SIZE; k++) {
            sum += As[ty][k] * Bs[k][tx];
        }

        __syncthreads();  // 等待计算完成再加载下一 tile
    }

    if (row < M && col < N) {
        C[row * N + col] = sum;
    }
}
```

优化点：

```text
1. 数据复用: A 的 tile 被 TILE_SIZE 个 thread 共享 → HBM 访问减少 TILE_SIZE 倍
2. Coalesced Access: 连续 thread 读连续地址，合并内存访问
3. 计算访存比提升: AI 从 1/4 提升到 ~4 (TILE_SIZE=16)
4. 性能: ~30-50% GPU 峰值算力
```

## 更进一步的优化

实际工业实现还会做：

1. Register Tiling：每个 thread 计算 4×4 或 8×8 的输出，减少 Shared Memory 访问
2. Double Buffering：当前 tile 计算时预取下一 tile，隐藏内存延迟
3. Vectorized Load：用 `float4` 一次加载 4 个 float
4. Tensor Core：FP16 矩阵乘使用 WMMA API，性能可达 90%+ 峰值
5. CUTLASS：模板化 GEMM 实现，工业级性能

## 复杂度对比

```text
版本              | HBM 访问量              | 算术强度 | 峰值性能
Naive             | O(MNK)                  | 1/4      | <5%
Shared Memory     | O(MNK / TILE_SIZE)      | ~4       | 30-50%
Register Tiling   | O(MNK / TILE_SIZE / RT) | ~16      | 60-80%
Tensor Core       | 同上 + FP16             | ~32      | 80-95%
cuBLAS            | 工业级优化              | 接近最优 | 90-98%
```

## 易错点

```text
1. __syncthreads() 必须放在所有 thread 都执行的路径上
2. 边界处理: M/N/K 不是 TILE_SIZE 倍数时要补零
3. Shared Memory bank conflict: 用 padding (TILE_SIZE+1) 避免
4. 行优先 vs 列优先要明确，索引计算容易错
5. block size 选择: 16x16 = 256 threads/block 是常见配置
```

面试时如果时间有限，先写 naive 版本说明正确性，再写 shared memory 版本说明优化思路，并能口述 register tiling 和 tensor core 的进一步优化方向即可。完整实现 register tiling 通常需要 100+ 行代码，面试不要求写完。
