# Q56. channel 底层 hchan

Go 的 channel 底层核心结构通常称为 `hchan`。它既要保存缓冲区，也要维护等待发送和等待接收的 goroutine 队列，并用锁保护内部状态。

可以简化理解为：

```text
hchan {
    qcount   当前缓冲区元素数量
    dataqsiz 环形缓冲区容量
    buf      环形缓冲区地址
    elemsize 元素大小
    sendx    下一个写入位置
    recvx    下一个读取位置
    recvq    等待接收的 goroutine 队列
    sendq    等待发送的 goroutine 队列
    closed   是否已关闭
    lock     互斥锁
}
```

## 1. 无缓冲 channel 如何同步

无缓冲 channel 的 `dataqsiz = 0`，没有存放数据的队列。发送和接收必须直接配对：

1. 发送方到来时，如果已有接收方在 `recvq` 等待，就直接把数据拷贝给接收方，并唤醒它。
2. 如果没有接收方，发送方会封装成 `sudog` 挂到 `sendq`，当前 goroutine 阻塞。
3. 接收方到来时也类似，如果 `sendq` 有等待发送者，就直接取走数据并唤醒发送方；否则进入 `recvq` 阻塞。

所以无缓冲 channel 既传数据，也提供同步语义。

## 2. 有缓冲 channel 如何通信

有缓冲 channel 内部有一个环形数组：

1. 发送时，如果缓冲区未满，把元素拷贝到 `buf[sendx]`，移动 `sendx`。
2. 接收时，如果缓冲区非空，从 `buf[recvx]` 拷贝元素，移动 `recvx`。
3. 缓冲区满时发送方阻塞到 `sendq`。
4. 缓冲区空时接收方阻塞到 `recvq`。
5. 如果等待队列里有对端 goroutine，发送/接收会优先唤醒对端，保持队列推进。

## 3. close channel 的语义

`close(ch)` 会把 `closed` 标记置位，并唤醒等待队列：

1. 等待接收的 goroutine 会被唤醒，读到缓冲区剩余数据；缓冲区读空后继续读会得到零值和 `ok=false`。
2. 等待发送的 goroutine 会被唤醒并 panic，因为关闭后不允许再发送。
3. 对已经关闭的 channel 再次 close 会 panic。
4. 对 nil channel close 会 panic；对 nil channel 发送或接收会永久阻塞。

从设计上避免重复 close 的方式：

1. 明确唯一关闭者，通常由生产者或协调者关闭，消费者不关闭。
2. 多生产者时用 `sync.WaitGroup` 等待所有 producer 退出，再由单独 goroutine close。
3. 用 `context.Context` 表达取消，不要把 close 数据 channel 当作通用取消信号。
4. 如果确实需要多方触发关闭，用 `sync.Once` 包装 close。

```go
var once sync.Once
closeSafe := func() {
    once.Do(func() { close(ch) })
}
```

## 4. 易错点

1. channel 内部有锁，不等于任何使用 channel 的程序都不会死锁。
2. 有缓冲 channel 只能缓冲固定数量元素，不是无限队列。
3. `len(ch)` 只能表示瞬时长度，不能作为并发正确性的判断依据。
4. `close` 是广播“不会再发送”，不是清空缓冲区。
5. 不要用 recover 掩盖重复 close，应该从所有权上设计清楚。

## 5. 面试回答模板

channel 底层可以理解为 `hchan`：包含环形缓冲区、发送和接收下标、等待发送队列、等待接收队列、关闭标志和一把锁。无缓冲 channel 没有队列容量，发送和接收必须直接配对；有缓冲 channel 先写入或读取环形缓冲区，满了发送阻塞，空了接收阻塞。关闭 channel 会唤醒等待接收者，缓冲读完后返回零值和 `ok=false`；等待发送者会 panic。工程上要明确唯一关闭者，多生产者用 WaitGroup 或 `sync.Once` 避免重复关闭。
