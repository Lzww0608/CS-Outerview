# Go 实现 ORM 框架

ORM（Object Relational Mapping）把结构体对象和关系型数据库表映射起来，让业务代码用对象和方法表达增删改查，而不是到处拼 SQL。

## 1. ORM 带来的好处

1. **减少重复 SQL**：通用 CRUD、分页、条件构造、事务封装可以沉淀在框架里。
2. **类型友好**：结构体字段和表字段有明确映射，减少手写列名错误。
3. **统一工程规范**：连接池、超时、日志、慢查询、事务和错误处理可以统一收口。
4. **跨数据库适配**：通过 Dialect 抽象 MySQL、PostgreSQL、SQLite 的占位符、分页语法和返回值差异。
5. **扩展能力**：可以支持 hook、软删除、自动时间戳、迁移、读写分离等能力。

代价也要说明：复杂查询可能不如手写 SQL 清晰，反射有运行时开销，隐藏 SQL 后也更容易写出 N+1 查询或低效关联。

## 2. 核心模块设计

一个最小可用 ORM 可以拆成这些模块：

1. **Model 解析**：通过反射读取结构体字段、tag、主键、表名。
2. **Dialect**：封装不同数据库的占位符、字段转义、自增主键、分页语法。
3. **Session/DB**：持有 `database/sql` 的连接池、上下文、日志和事务状态。
4. **Query Builder**：构造 `SELECT/INSERT/UPDATE/DELETE`，参数使用占位符绑定。
5. **Scanner**：把 `rows.Scan` 的结果写回结构体字段。
6. **Hook/Callback**：在创建、更新、删除前后执行业务扩展。

结构体 tag 示例：

```go
type User struct {
	ID        int64  `db:"id,primary,auto"`
	Name      string `db:"name"`
	Email     string `db:"email"`
	CreatedAt int64  `db:"created_at"`
}
```

## 3. Model 解析示例

Go ORM 通常依赖反射解析结构体：

```go
type Field struct {
	Name   string
	Column string
	Index  int
}

func ParseModel(model any) ([]Field, error) {
	t := reflect.TypeOf(model)
	if t.Kind() == reflect.Pointer {
		t = t.Elem()
	}
	if t.Kind() != reflect.Struct {
		return nil, fmt.Errorf("model must be struct")
	}

	fields := make([]Field, 0, t.NumField())
	for i := 0; i < t.NumField(); i++ {
		sf := t.Field(i)
		if sf.PkgPath != "" {
			continue
		}
		tag := sf.Tag.Get("db")
		if tag == "-" {
			continue
		}
		column := strings.Split(tag, ",")[0]
		if column == "" {
			column = snakeCase(sf.Name)
		}
		fields = append(fields, Field{Name: sf.Name, Column: column, Index: i})
	}
	return fields, nil
}
```

## 4. 查询与扫描

查询构造要坚持参数绑定，不能把用户输入直接拼进 SQL：

```go
func (s *Session) First(ctx context.Context, dest any, where string, args ...any) error {
	table := tableName(dest)
	query := "SELECT * FROM " + table + " WHERE " + where + " LIMIT 1"

	row := s.db.QueryRowContext(ctx, query, args...)
	return scanStruct(row, dest)
}
```

真实框架里不会直接暴露裸 `where` 字符串，而是提供更安全的表达式构造：

```go
db.Model(&User{}).
    Where(Eq("email", email)).
    OrderBy("id DESC").
    Limit(1).
    Find(ctx, &user)
```

## 5. 事务和上下文

ORM 必须把 `context.Context` 和事务作为一等能力：

1. 每个 SQL 调用都应使用 `QueryContext/ExecContext`，支持超时和取消。
2. 事务内的所有操作绑定同一个 `*sql.Tx`，不能混用连接池上的 `*sql.DB`。
3. 事务函数要处理 panic、错误回滚和提交失败。

```go
func (db *DB) Transaction(ctx context.Context, fn func(tx *Session) error) error {
	tx, err := db.sql.BeginTx(ctx, nil)
	if err != nil {
		return err
	}
	s := &Session{tx: tx}
	if err := fn(s); err != nil {
		_ = tx.Rollback()
		return err
	}
	return tx.Commit()
}
```

## 6. 易错点

1. 反射设置字段时必须传指针，并且字段必须可导出，否则会 panic。
2. ORM 不能为了“通用”牺牲 SQL 可控性，复杂报表和强优化查询应允许手写 SQL。
3. 自动迁移要谨慎，生产环境 DDL 可能锁表或触发长时间复制延迟。
4. 连接池参数、慢查询日志、SQL trace 和错误码转换比 CRUD 封装更接近生产可用性。
5. 批量插入、预加载关联、分页和软删除都要关注生成 SQL 是否符合预期。

## 7. 面试回答模板

如果在 Go 里实现 ORM，我会先基于 `database/sql` 做一个轻量 Session 层，统一连接池、上下文、事务、日志和错误处理。模型层通过反射读取结构体 tag，生成表名、字段、主键等元数据；SQL 层用 Query Builder 生成参数化 SQL，并通过 Dialect 适配不同数据库差异；查询结果通过反射扫描回结构体。生产可用还要补上事务函数、慢查询日志、hook、批量写入、软删除和手写 SQL 逃生口，避免 ORM 把复杂查询变成黑盒。
