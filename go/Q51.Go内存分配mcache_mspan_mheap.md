# Q51.Go 内存分配：mcache、mspan、mheap

Go 运行时的内存分配器借鉴了 TCMalloc 思路，把堆内存按层级管理，核心目标是减少全局锁竞争、提高小对象分配速度，并让 GC 能高效扫描堆对象。

## 1. 三层结构

| 结构 | 粒度 | 作用 |
| --- | --- | --- |
| `mcache` | 每个 P 本地 | 无锁或少锁地给当前 P 上运行的 goroutine 分配小对象 |
| `mspan` | 一组连续页 | 管理同一 size class 的对象槽位 |
| `mheap` | 全局堆 | 负责向操作系统申请大块内存，并把 span 分配给各个 mcache |

可以按这个路径理解一次小对象分配：

```text
goroutine -> 当前 P 的 mcache -> 对应 size class 的 mspan -> 空闲对象槽
```

如果 `mcache` 中对应 `mspan` 没有空闲对象，就向 `mcentral` 申请；`mcentral` 不够再向全局 `mheap` 申请；`mheap` 不够再向操作系统申请内存。

## 2. 为什么要分层

如果所有 goroutine 都直接向一个全局堆加锁申请内存，高并发下锁竞争会非常严重。分层设计带来的好处是：

1. **本地缓存减少锁竞争**：多数小对象分配直接从当前 P 的 `mcache` 完成。
2. **按大小分类降低碎片**：小对象按 size class 放入不同 span，避免每次都切割任意大小内存。
3. **批量向上申请**：本地缓存耗尽时按 span 批量补充，减少频繁全局操作。
4. **配合 GC 元数据**：span 能记录对象大小、位图、是否含指针等信息，便于扫描和回收。

## 3. 小对象、大对象和逃逸

Go 编译器先通过逃逸分析判断对象能否放在栈上。不能放在栈上的对象才进入堆分配。

堆分配大致分为：

1. 小对象：按 size class 从 `mcache` 的 `mspan` 分配。
2. 大对象：超过特定阈值时直接从 `mheap` 分配独立 span。
3. 无指针对象：运行时可以减少 GC 扫描成本。

这也是为什么减少逃逸、复用 buffer、避免频繁分配临时对象能改善 Go 服务性能。

## 4. 和 GC 的关系

Go 的 GC 负责回收不可达的堆对象，但分配器负责把可用内存组织成可快速分配的结构。GC 标记清扫后，span 中死亡对象会重新变成可分配槽位；完全空闲或利用率低的 span 可能被归还给上层结构，最终在合适时机归还给操作系统。

面试里可以这样关联：

1. 分配越频繁，GC 触发越频繁。
2. 逃逸到堆上的对象会增加 GC 扫描和回收压力。
3. 大对象可能直接走全局路径，分配和回收成本更高。
4. `pprof` 的 heap profile 本质上来自运行时分配采样。

## 5. 易错点

1. `mcache` 不是 CPU cache，而是 Go 运行时的 per-P 分配缓存。
2. goroutine 不直接持有 `mcache`，当前运行它的 P 才持有。
3. 栈上分配不需要 GC 回收，函数返回即可释放；堆上对象由 GC 管理。
4. `new`、`make` 不一定都分配到堆上，是否逃逸由编译器分析决定。
5. Go 的内存分配优化不能替代对象生命周期设计，长期引用仍会导致内存无法回收。

## 6. 面试回答模板

Go 的堆分配器是分层的：每个 P 有本地 `mcache`，里面按 size class 缓存 `mspan`；`mspan` 管理一组连续页里的对象槽；全局 `mheap` 负责向操作系统申请和管理大块内存。小对象优先从当前 P 的 `mcache` 分配，减少全局锁竞争；本地不够再逐级向上申请。对象是否进入堆先由逃逸分析决定，堆上对象再由 GC 标记清扫，所以减少逃逸和临时分配能降低 GC 压力。
