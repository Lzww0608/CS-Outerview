# Q12.对关闭的channel进行读写

在`Go`语言中对已经关闭的`channel`进行读写，结果会有所不同。

## 读操作

我们可以安全地从一个已经关闭的 `channel` 中读取数据。如果是有缓冲 channel，并且缓冲区里还有未读取的数据，读操作会先返回这些数据，`ok` 为 `true`；当缓冲区被读空后，再读会立即返回该元素类型的零值，`ok` 为 `false`。这种特性可以使得我们通过 `range` 语句读取 channel 中的所有数据，直到 channel 被关闭并且缓冲区被读空。



```go
package main

import (
    "fmt"
    "time"
)

func main() {
    // 创建一个整型channel
    ch := make(chan int)

    // 启动一个goroutine向channel中发送数据
    go func() {
        for i := 0; i < 5; i++ {
            ch <- i
            time.Sleep(time.Millisecond * 200) // 模拟一些工作
        }
        close(ch) // 发送完数据后关闭channel
    }()

    // 从已经关闭的channel中读取数据
    for {
        if value, ok := <-ch; ok {
            // ok 为 true 表示这次读到了有效数据；即使 channel 已关闭，只要缓冲区还有数据也可能为 true
            fmt.Println("Received:", value)
        } else {
            // ok 为 false 表示 channel 已关闭且没有更多数据
            fmt.Println("Channel closed!")
            break
        }
    }
}
```



## 写操作

如果我们试图向一个已经关闭的 `channel` 写入数据，运行时会触发 `panic`。这是因为一旦 `channel` 被关闭，就不能再向其中添加新的数据，这会导致严重的并发错误。

```go
ch := make(chan int)
close(ch)
ch <- 1 // panic
```

关闭已经关闭的 channel 也会 panic；关闭 nil channel 同样会 panic。nil channel 的发送和接收才会永久阻塞。因此工程上通常遵循“由发送方关闭 channel”的原则，接收方不要随意关闭。

## 有缓冲 channel 正在写入时被 close 会怎样

如果一个 goroutine 正在向 channel 发送，而另一个 goroutine 同时 close 这个 channel，存在竞态：

1. 如果发送先完成，数据进入缓冲区或被接收者拿走，随后 close 成功。
2. 如果 close 先发生，发送方会 panic。
3. 如果多个发送方同时存在，必须由额外同步机制保证所有发送结束后再 close。

常见写法是用 `sync.WaitGroup` 等待所有 producer 退出，再由唯一的协调者关闭 channel：

```go
var wg sync.WaitGroup
ch := make(chan int, 16)

for i := 0; i < 3; i++ {
    wg.Add(1)
    go func(id int) {
        defer wg.Done()
        ch <- id
    }(i)
}

go func() {
    wg.Wait()
    close(ch)
}()
```

## 面试回答模板

关闭 channel 表示发送方不再发送数据。读已关闭的 channel 是安全的：有缓冲数据时先读出数据且 `ok=true`，缓冲读空后返回零值且 `ok=false`，这也是判断 channel 是否已经关闭的标准方式；对已关闭 channel 写入、重复关闭、关闭 nil channel 都会 panic。多个发送者场景下不能让任意发送者随便 close，通常要用 WaitGroup 或单独的 owner 确认所有发送完成后再关闭。
