# Q52. Slice 长度、容量与扩容

Go 的 `slice` 不是数组本身，而是一个描述连续数组片段的头部结构。可以把它理解为：

```text
slice = {
    ptr: 指向底层数组的起始位置
    len: 当前可访问的元素个数
    cap: 从 ptr 开始到底层数组末尾还能容纳的元素个数
}
```

## 1. len 和 cap 的区别

1. `len(s)` 表示当前 slice 中能通过下标访问的元素数量。
2. `cap(s)` 表示从 slice 起点开始到底层数组末尾的容量。
3. `append` 时如果 `len < cap`，通常会复用原底层数组。
4. `append` 时如果容量不够，运行时会申请新的底层数组，把旧元素拷贝过去，再追加新元素。

示例：

```go
package main

import "fmt"

func main() {
    a := []int{1, 2, 3, 4}
    b := a[:2]

    fmt.Println(len(b), cap(b)) // 2 4

    b = append(b, 99)
    fmt.Println(a) // [1 2 99 4]
    fmt.Println(b) // [1 2 99]
}
```

这里 `b` 的容量足够，`append` 复用了 `a` 的底层数组，所以修改了 `a[2]`。

## 2. Slice 扩容后还会共享底层数组吗

不一定。核心判断是有没有触发扩容。

```go
a := []int{1, 2}
b := append(a, 3) // 可能触发新数组，取决于 a 的 cap
```

如果 `append` 没有超过容量，`a` 和 `b` 共享同一个底层数组；此后通过任意一个 slice 修改共享范围内的元素，另一个 slice 也能看到变化。

如果 `append` 超过容量，`b` 指向新的底层数组；此后修改 `a` 的旧数组不会影响 `b`，修改 `b` 也不会影响 `a`。

工程中如果不希望子切片后续 `append` 污染原数组，可以使用完整切片表达式限制容量：

```go
a := []int{1, 2, 3, 4}
b := a[:2:2] // len=2, cap=2
b = append(b, 99)

fmt.Println(a) // [1 2 3 4]
fmt.Println(b) // [1 2 99]
```

## 3. 扩容策略和易错点

Go 标准不保证具体扩容倍率，不同版本会有细节变化。面试里不要背死“永远 2 倍”。更稳妥的回答是：小容量时通常增长较快，大容量后增长会放缓，运行时会结合元素大小、内存对齐和分配规格选择新容量。

常见易错点：

1. `slice` 作为参数传递时，slice header 是值拷贝，但底层数组共享。
2. 函数内修改 `s[i]` 会影响调用方可见的底层数组。
3. 函数内 `append` 后如果触发扩容，新 slice header 只在函数内部变化，调用方原 slice 不会自动指向新数组，除非返回新 slice。
4. 子切片可能持有大数组引用，导致大数组无法被 GC 回收。需要释放时可以 `copy` 到新切片。

## 4. 和 C++ vector 扩容对比

Go slice 和 C++ `std::vector` 都有“连续内存 + 扩容搬迁”的特征，但暴露的语义不同。

1. Go slice 扩容后返回一个新的 slice header，因此必须接住 `append` 的返回值：`s = append(s, x)`。
2. C++ `vector` 扩容后容器对象本身仍然是同一个对象，但旧元素地址会变化。
3. C++ 中如果在 `vector` 上取了引用、指针或迭代器，随后 `push_back/emplace_back` 触发扩容，这些引用、指针、迭代器全部失效。
4. 如果提前 `reserve` 了足够容量，`push_back` 不触发扩容时，已有元素引用通常仍有效，但 `end()` 迭代器会变化。

## 5. 面试回答模板

Slice 底层是一个 header，包含指针、长度和容量。`len` 是当前可访问元素数，`cap` 是从起点到底层数组末尾的容量。`append` 容量够时复用底层数组，因此多个 slice 可能互相影响；容量不够时会分配新数组并拷贝元素，之后新旧 slice 不再共享。工程上要注意子切片持有大数组、函数内 append 后要返回新 slice，以及可以用 `s[:len:len]` 限制容量避免误共享。
