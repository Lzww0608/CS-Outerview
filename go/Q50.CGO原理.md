# Q50. CGO 原理

CGO 是 Go 调用 C 代码、C 库以及让 C 调用 Go 导出函数的桥接机制。它允许 Go 项目复用已有 C/C++ 生态，例如系统库、数据库客户端、图像处理库和硬件 SDK，但代价是构建、运行时调度和内存管理都会更复杂。

## 1. CGO 怎么工作

Go 文件中通过特殊注释和 `import "C"` 引入 C 代码：

```go
/*
#include <stdlib.h>
int add(int a, int b) { return a + b; }
*/
import "C"

func Add(a, b int) int {
    return int(C.add(C.int(a), C.int(b)))
}
```

构建时，`go tool cgo` 会生成一组中间文件：

1. Go 侧包装代码：把 Go 调用转换成运行时可识别的 cgo 调用。
2. C 侧胶水代码：负责调用真正的 C 函数。
3. 类型转换声明：把 `C.int`、`C.char*` 等映射成 Go 可用类型。
4. 链接参数：调用系统 C 编译器和链接器，把 C 对象文件和 Go 对象文件链接到一起。

## 2. 运行时调用过程

Go 调用 C 函数时，会从 Go runtime 的调度模型切到外部 C 调用：

1. 当前 goroutine 进入 cgo call，runtime 认为它可能阻塞。
2. runtime 会确保还有其他 M/P 能继续运行 Go goroutine，避免整个程序被一个 C 调用卡住。
3. C 函数在系统线程上执行，不能被 Go runtime 抢占和扫描内部栈帧。
4. C 调用返回后，结果再转换回 Go 类型。

因此，CGO 调用比普通 Go 函数调用重得多。频繁小粒度调用会有明显开销，应该批量调用或把热路径留在 Go 内部。

## 3. 内存与指针规则

CGO 最大的坑是 Go GC 和 C 指针生命周期不同：

1. Go 指针不能随意长期交给 C 保存，因为 Go 对象可能被 GC 移动或回收，且 GC 需要知道指针关系。
2. C 分配的内存不受 Go GC 管理，需要手动 `C.free`。
3. C 字符串和 Go 字符串需要拷贝转换，例如 `C.CString` 和 `C.GoString`。
4. 跨边界传递 buffer 时，要明确谁分配、谁释放、生命周期到什么时候。

示例：

```go
cs := C.CString("hello")
defer C.free(unsafe.Pointer(cs))
C.puts(cs)
```

如果 C 需要长期持有数据，通常让 C 自己分配内存，Go 只传内容；或者使用句柄表，让 C 保存整数 handle，真正的 Go 对象仍由 Go 侧管理。

## 4. 易错点

1. 开启 CGO 后交叉编译更麻烦，需要目标平台 C 编译器和依赖库。
2. CGO 会降低构建可移植性，静态链接、musl/glibc、容器镜像都要额外处理。
3. C 代码崩溃会直接带崩整个 Go 进程，Go 的 `recover` 捕获不了 C 的段错误。
4. C 回调 Go 时要遵守导出规则，不能随便传 Go 闭包给 C 长期保存。
5. 高频 CGO 调用会破坏 Go 的轻量调度优势，适合粗粒度、批处理、复用成熟 C 库。

## 5. 面试回答模板

CGO 是 Go 和 C ABI 的桥接机制。编译时 `go tool cgo` 会生成 Go 包装代码和 C 胶水代码，再调用 C 编译器参与链接；运行时 Go 调 C 会进入 cgo call，runtime 会把它当作可能阻塞的外部调用处理。它的价值是复用 C/C++ 库，但代价是调用开销、交叉编译复杂、GC 指针规则严格和崩溃隔离弱。工程中要减少高频小调用，明确内存所有权，C 分配的内存必须由 C 释放，跨边界接口最好保持简单稳定。
